# 设计 Pastebin：先让两条核心路径成立

Pastebin 的核心功能只有两条：提交一段文本，得到一个可分享的地址；访问这个地址，读取原来的文本。

系统设计的复杂度应该从这两条路径和实际约束中长出来。先画缓存、消息队列、对象存储和多区域部署，再回头寻找它们要解决的问题，通常只能得到一张组件很多的架构图。组件数量不是容量规划。

## 先固定这次设计的范围

为了让方案可以继续推导，先采用五个假设：

- 文本创建后不可修改。
- 文本可以设置过期时间，也可以长期保留。
- 读取次数明显多于创建次数。
- 链接默认不容易被枚举，但不把“难猜”当成访问控制。
- 内容按纯文本返回，或者在展示前完成安全转义，不执行用户提交的 HTML。

搜索、公开内容流、协同编辑和富文本渲染暂不纳入核心范围。它们都可以做，但会分别引入索引、排序、并发编辑和内容安全问题。如果需求里没有搜索，就不需要先把 Elasticsearch 请进会议室。

## 规模先用变量表达

没有实际业务数据时，直接假设一个很大的 QPS，只会让后面的组件显得合理。更稳妥的方式是先保留决定架构的变量：

| 变量 | 含义 | 主要影响 |
| --- | --- | --- |
| `W` | 每秒创建数量 | ID 生成、写入吞吐、分片需求 |
| `R` | 每秒读取数量 | 缓存、带宽、热点处理 |
| `S` | 平均文本大小 | 存储选择、网络成本 |
| `T` | 平均保留时间 | 总存储量、清理策略 |

忽略副本和元数据时，长期存储量可以近似写成：

```text
storage ≈ W × S × T
```

如果 `R / W` 很高，优化重点在读取路径。如果 `S` 很大，正文与元数据分离的收益会上升。如果大部分内容很快过期，清理策略和缓存有效期会比永久归档更重要。

架构选择需要这些关系，不需要一组看起来精确、实际没有来源的数字。

## 最小数据模型先放在一个存储里

最小版本可以使用一张表：

```text
paste_id
content
created_at
expires_at
owner_id
status
```

`paste_id` 是对外地址的一部分，必须唯一。`expires_at` 为空表示没有主动设置过期时间。`status` 用于表示正常、已删除或被封禁，避免把所有状态都编码成“查不到”。

当文本较小、规模有限时，把元数据和正文放在同一个关系数据库里最简单。它提供唯一约束、事务和成熟的运维工具。只有当 `S`、总存储量或成本成为明确瓶颈时，再把正文迁移到对象存储，数据库只保留元数据和对象键。

对象存储不是免费复杂度。正文与元数据分离后，创建流程需要处理部分成功，删除也要协调两处状态。

## ID 选择取决于链接语义

常见方案有三种：

1. 自增 ID 再做 Base62 编码：没有随机碰撞，生成简单，但相邻地址容易被枚举。
2. 内容哈希：相同内容可以复用地址，但会暴露内容相同这一事实，也需要处理哈希碰撞和隐私语义。
3. 随机 Base62 字符串：地址不连续，适合默认不可枚举的分享场景，但必须检测碰撞。

在当前假设下，可以选择随机 Base62 ID。数据库对 `paste_id` 建立唯一约束；发生碰撞时重新生成并重试。字符串长度由预计创建总量和可接受碰撞概率决定，不在缺少规模数据时拍一个永远正确的数字。

随机地址只能降低被顺序扫描的概率。真正的私密内容仍然需要身份认证、授权或独立访问令牌。

## 创建路径先保证“返回的地址真的可读”

创建流程可以保持同步：

```text
Client → API → Validate → Generate ID → Store → Return URL
```

服务依次完成：

1. 校验内容大小、类型和过期时间。
2. 执行身份、频率和内容安全检查。
3. 生成 `paste_id`。
4. 持久化内容与元数据。
5. 存储成功后返回分享地址。

服务不能在持久化完成前返回 URL。否则客户端会得到一个格式正确、暂时或永久读不到的地址。异步写入可以降低表面延迟，却把最重要的成功语义改掉了。

读取响应需要使用明确的纯文本类型或安全的输出编码。内容存储成功，不代表浏览器可以不经处理地执行它。

如果正文后来迁移到对象存储，可以先写正文，再提交包含对象键的元数据。对象写入成功但元数据提交失败时，需要由后台任务清理孤立对象。这里引入异步任务，是因为已经出现了可观察的部分失败，并且清理不需要阻塞主请求。

## 读取路径按命中顺序缩短

最小读取路径是：

```text
Client → API → Database → Response
```

当读取压力成为主要成本时，再在数据库前增加缓存：

```text
Client → Edge / Load Balancer → API → Cache → Database
```

正文迁移到对象存储后，缓存未命中时先从元数据库读取状态、过期时间和对象键，再访问对象存储。

内容创建后不可修改，使缓存策略相对简单。缓存值需要包含正文、状态和过期时间，缓存 TTL 不能超过内容剩余有效期。删除或封禁内容时，需要主动失效缓存，否则数据库已经拒绝访问，旧内容仍可能从缓存返回。

对不存在的 ID 可以使用较短的负缓存，减少随机扫描对存储层的压力。负缓存时间不能太长，避免与刚创建的内容产生不必要的不一致。

热门内容会形成单 Key 热点。应用缓存仍然承压时，可以继续使用边缘缓存或 CDN，让响应更接近读者。这个组件由热点和跨地域延迟引入，不需要在第一天就存在。需要身份认证的私密内容不能直接复用公开缓存策略。

## 过期需要同时定义读取和清理

过期首先是一条读取语义：当前时间超过 `expires_at` 后，服务必须停止返回内容。

物理删除可以稍后发生。读取时检查过期状态保证语义正确，后台任务再批量清理数据库记录、对象和缓存。这样不会要求清理任务精确地在某一秒完成，也不会因为任务短暂延迟继续暴露过期内容。

删除、封禁和过期都需要沿着相同的数据路径传播。状态只在数据库里改变，却没有处理缓存和对象存储，系统会同时拥有几个互相矛盾的真相。

## 规模增长后再拆组件

组件出现的顺序由瓶颈决定：

- `R` 增长：先增加缓存和只读副本，再根据热点与地域增加边缘缓存。读副本会引入复制延迟，因此需要定义创建后的读一致性，例如短时间读取主库或等待副本确认。
- `W` 或数据总量增长：按 `paste_id` 哈希分片，使写入和读取可以定位到同一分片。
- `S` 或存储成本增长：正文进入对象存储，数据库保留元数据。
- 可用性要求增长：部署到多个故障域，增加副本、故障转移和恢复验证。
- 跨区域需求增长：明确数据主写区域、一致性目标和故障切换语义，再决定复制方式。

每增加一个组件，都要能回答它消除了哪个瓶颈，并说明新的失败方式。缓存带来失效问题，对象存储带来跨存储一致性，分片带来迁移与热点，多区域带来复制延迟和冲突。架构扩展不是免费升级，只是把旧问题换成更值得处理的新问题。

## 最后验证完整路径

方案完成后，至少检查这些结果：

- 创建成功率，以及成功返回后立即读取的成功率。
- 读取延迟、缓存命中率和热点 Key 分布。
- ID 碰撞与重试次数。
- 存储失败、孤立对象和后台清理积压。
- 过期、删除或封禁后，缓存是否仍然返回正文。
- 随机扫描、超大内容和高频创建是否受到限制。

一个可用的 Pastebin 设计，不是把常见组件全部摆上去。它先保证创建与读取两条路径的语义成立，再根据 `W`、`R`、`S`、`T` 和可用性目标逐步增加复杂度。

当每个组件都有清楚来路时，架构图才是在解释系统，而不是罗列技术选项。
