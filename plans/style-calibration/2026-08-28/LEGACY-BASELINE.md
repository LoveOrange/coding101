# Coding101 旧文文风基线 v0.1

这份基线回答一个问题：新样稿在变得更准确、更紧凑之后，有没有顺手把原来属于 Linsama 的东西也删掉？

结论先说。现有文章的辨识度主要不来自某个固定句式，而来自四种习惯：用具体问题带出概念、用同一个例子持续推导、直接和读者说话、在有亲历证据时让作者本人出现。首轮新样稿保留了前两项，明显收紧了后两项。这个变化是否成立，需要明天确认。

## 这份基线怎样得出

本次对 `docs/` 下 72 个 Markdown/MDX 文件做了粗略表达标记扫描，并精读四篇代表性旧文：

| 旧文 | 作为基线的原因 |
| --- | --- |
| [研发类面试流程](../../../docs/interview/interview-process.mdx) | 作者经历、面试官视角、直接建议最集中 |
| [TCP 三次握手与四次挥手](../../../docs/basic-knowledge/network/tcp_handshake.mdx) | 生活类比、问题驱动和重复确认很典型 |
| [事务](../../../docs/basic-knowledge/database/transaction/index.mdx) | 从业务例子进入定义，并用提示框反复收束 |
| [41. 缺失的第一个正整数](../../../docs/leetcode/re-leetcode/arrays/leetcode-41.mdx) | 从限制推到解法，结尾加入个人面试经历 |

扫描结果只能说明哪些表达在当前仓库中常见，不能证明全部由同一时期、同一种写作意图产生。这里把它当线索，不把数字当文风判决书。

## 值得保留的旧文特征

### 1. 复杂概念先找到一个人能理解的问题

[《事务》](../../../docs/basic-knowledge/database/transaction/index.mdx)先用转账解释为什么一组操作必须共同成功或失败，再引入事务与 ACID。[《TCP 三次握手与四次挥手》](../../../docs/basic-knowledge/network/tcp_handshake.mdx)先用双方通话建立确认关系，再映射到 `SYN` 和 `ACK`。

这种写法的价值不是“通俗”，而是给后面的术语提供来路。新样稿应该继续保留问题或场景，只需要控制类比的长度和技术边界。

### 2. 同一个例子会被持续使用，而不是解释一次就丢掉

事务文章从转账进入原子性，又用事务 A、事务 B 解释并发可见性。TCP 文章从建立通话继续推到结束通话。读者不用反复加载新场景，注意力可以留给机制本身。

首轮技术样稿延续了这一点：事务 A 统计订单，事务 B 修改或新增订单。这个特征可以直接进入全局文风，只需要确认例子的篇幅上限。

### 3. 个人经历会在它真正能增加信息时出现

[《研发类面试流程》](../../../docs/interview/interview-process.mdx)使用面试官经历解释项目介绍、算法环节和候选人判断。[旧版 LeetCode 41](../../../docs/leetcode/re-leetcode/arrays/leetcode-41.mdx)在结尾说明这道题曾经真实出现在个人面试中。

这些内容让文章不只是资料整理，也让建议有清楚来源。新样稿目前更客观、更克制，但可能因此少了一层“为什么由 Linsama 来讲”的理由。个人经历不需要每篇都有；一旦出现，就应该承担证据、背景或判断依据，而不是只负责增加亲切感。

### 4. 讲完原理后，会主动把内容接回面试和实践

旧文不会把知识点停在定义。事务文章补充默认隔离级别，算法文章解释复杂度并连接个人面试，面试流程文章反复说明面试官实际观察什么。

Coding101 的定位不是百科全书。读者最后需要知道这段知识怎样用于回答、实现、排障或选择。新样稿里的“工程选择”“验证方法”和“限制怎样推出数据结构”延续了这个方向。

## 明天需要重新决定的地方

### 1. 与读者的距离是否收得太远

旧文大量使用“我们”“你”“大家”，有陪着读者走一遍的感觉。新样稿更多采用客观叙述，逻辑更紧，但可能显得少了一点人。

需要决定的不是这些词能不能用，而是它们分别在什么场景出现：共同推导可以用“我们”，教程动作是否直接用“你”，面试建议是否继续称呼“大家”。

### 2. 重复确认是帮助理解，还是拖慢文章

旧事务文章经常先用 `:::tip` 给结论，正文随后再完整解释一次。TCP 文章也会用类比、步骤和提示框多次表达同一个判断。

这种重复对第一次学习的人友好，但会降低阅读速度。新样稿把它压缩为“先给最小结论，再逐步增加机制”。明天需要判断压缩后的版本是否太快，以及提示框应当负责导航、总结还是面试速记。

### 3. 强语气应该保留多少

旧文常见“显然”“一定”“最简单”“彻底理解”等表达。它们让文章有推动力，也容易把特定条件下的判断写成普遍结论。

新样稿更多使用“通常”“可能”“取决于实现”。技术边界更稳，声音也更冷静。要确认的是：观点文是否可以更强，技术说明是否继续保持限定，教程里的动作句是否直接省略缓冲。

### 4. 结尾应该鼓励读者，还是完成判断

旧文经常以鼓励、期待或个人感受收尾。新样稿改为落在判断、验证标准或可迁移的方法上。

两者不必二选一。个人文章可以保留情绪，技术文章通常更适合在结论完成时停下。明天需要为不同文体分别确定，而不是设置一个全站统一结尾。

### 5. 个人经历放在主线里，还是放在旁注里

旧版 LeetCode 41 的面试经历很有辨识度，但它出现在算法已经结束之后，与解法主线分开。面试流程文章则把个人经历直接作为论据。

可以形成一条文体规则：经历决定结论时放入正文；只是提供背景或趣味时，放在开头短注、文末旁注或作者备注。最终形式需要结合明天的实际阅读感受决定。

## 文风继承不等于内容继承

旧文提供的是声音证据，不是事实豁免。

部分旧技术说明为了降低理解成本，使用了比较绝对的简化。例如把串行化直接描述成所有事务实际串行执行。新样稿改成“执行结果等价于某种串行顺序，并可能通过等待或重试实现”。这是准确性修正，不应被当作文风背离。

旧文里的经验性建议也需要单独判断其事实依据、适用边界和价值取向。即使某段很有个人辨识度，也不会自动成为以后继续生成的规则。本轮只观察表达方式，不替旧内容做正确性背书，也暂不修改旧文。

## 初步判断

首轮新样稿没有偏离 Coding101 的问题驱动和推导习惯，但整体比旧文更短、更客观、更少直接称呼读者。最需要明天确认的不是“像不像技术文章”，而是这种收紧有没有收过头。

理想结果不是回到旧文的所有习惯，也不是把旧文统一洗成新模板。更合理的方向，是保留旧文的场景感、共同推导和真实经验，同时减少重复、过度承诺和没有边界的结论。
