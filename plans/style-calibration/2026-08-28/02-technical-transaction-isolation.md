# 事务隔离级别与数据可见性

事务 A 正在统计某个用户的订单。事务 B 在同一时间修改了一笔订单，又插入了一笔新订单。A 连续执行两次查询时，结果是否相同，取决于数据库为这次事务提供的数据视图。

隔离级别规定事务能够读取哪些数据版本，以及并发冲突发生后由谁等待或重试。规则越严格，查询结果越稳定，协调事务的成本也会增加。

## 并发读取中的三种异常

继续使用事务 A 和事务 B：

- **脏读（Dirty Read）**：A 读到 B 尚未提交的修改。B 随后回滚，这份数据也随之失效。
- **不可重复读（Non-repeatable Read）**：A 两次读取同一行。两次读取之间，B 修改并提交了该行，因此 A 得到两个结果。
- **幻读（Phantom Read）**：A 两次执行相同的范围查询。两次查询之间，B 插入并提交了符合条件的新行，结果集因此发生变化。

这三种异常都可以放回事务的执行顺序中理解。先标出每次读取发生的时间，再检查当时有哪些修改已经提交，现象就会清楚很多。

## 四种隔离级别的读取行为

| 隔离级别 | 常见读取行为 | 需要考虑的问题 |
| --- | --- | --- |
| 读未提交 | 允许读取其他事务尚未提交的修改 | 可能出现脏读、不可重复读和幻读 |
| 读已提交 | 每次普通读取使用当时已经提交的数据 | 同一事务中的多次读取可能使用不同快照 |
| 可重复读 | 同一事务中的普通读取通常使用稳定快照 | 锁定读取、并发写入和范围查询由具体数据库决定 |
| 串行化 | 已提交事务的整体效果对应某个串行执行顺序 | 冲突可能导致等待、事务终止或重试 |

SQL 标准规定的是各级别必须提供的最低保证。数据库可以提供更强的行为。PostgreSQL 会把读未提交按读已提交处理，它的可重复读也不会出现幻读。MySQL InnoDB 的可重复读会让同一事务中的一致性读取共享快照；范围更新和锁定读取还会涉及间隙锁或 Next-Key Lock。

因此，隔离级别的名称还不足以确定运行结果。数据库产品、SQL 类型和索引访问路径都会影响锁与快照的行为。

## 读已提交与可重复读的差异

在读已提交级别下，每条语句通常会建立新的已提交快照。事务 A 完成第一次查询后，如果事务 B 提交了修改，A 的第二次查询可以看到这些变化。PostgreSQL 和 MySQL InnoDB 都采用这种常见行为。

可重复读会保留更稳定的读取视图。MySQL InnoDB 的普通一致性读取使用第一次读取时建立的快照；PostgreSQL 则使用事务中第一条非事务控制语句开始时的快照。后续普通查询沿用该视图，因此更适合需要多次计算同一批数据的事务。

稳定快照处理的是读取视图。事务更新当前数据、锁定范围或与其他写事务冲突时，仍然可能等待或失败。应用需要能够识别这类错误，并在安全的前提下重试整个事务。

## MVCC 如何提供读取视图

多版本并发控制（Multi-Version Concurrency Control，MVCC）会保留一行数据的多个版本。查询根据自己的快照选择可见版本，读取事务因此可以避开一部分写锁等待。

旧版本需要存储和清理，写事务之间也仍会争用同一份当前数据。涉及余额、库存、名额等业务约束时，稳定快照只解决了观察问题。约束本身还需要原子条件更新、唯一约束、检查约束、显式锁或串行化隔离来保护。

以扣减库存为例，`UPDATE inventory SET stock = stock - 1 WHERE id = ? AND stock > 0` 把“库存必须大于零”放进同一条原子更新中。应用再检查受影响行数，即可判断扣减是否成功。只在应用代码里先查库存、再执行扣减，会在两个操作之间留下并发窗口。

## 选择隔离级别时需要确认的条件

短事务和普通查询可以先沿用数据库默认级别。MySQL InnoDB 默认使用可重复读，PostgreSQL 默认使用读已提交。调整级别之前，应当先写出事务中的 SQL 顺序，并确认每次读取是否要求使用同一快照。

并发事务可能修改同一行时，需要确认锁等待和死锁的处理方式。业务规则跨越多行或多张表时，还要判断约束能否下沉到数据库；无法直接表达的约束可能需要显式锁或串行化，并配套完整事务重试。

分析具体问题时，可以画出事务 A 和事务 B 的执行时间线，标记每次读取建立快照的时点、当时已经提交的写入，以及发生冲突后的处理结果。根据这三项信息，再选择隔离级别、锁和重试策略。
