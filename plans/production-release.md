# 正式发布流程

Coding 101 的正式域名是 `coding101.linsama.com`，发布目标是现有 Cloudflare Worker `coding101`。所有任务使用同一个入口；GitHub Pages 工作流只负责镜像。

## 1. 使用方法

先同步远端 `main`，阅读本文件及当前 `AGENTS.md`，完成并提交改动。正式发布前将提交合并、推送到 `main`，然后在干净 checkout 中运行：

```bash
npm ci
npm run release:production
```

只有检查全部通过才会上线。根目录的 `npm run deploy` 和 `worker/` 的 `npm run deploy` 都调用同一脚本，不再分别调用 Docusaurus 和 Wrangler。不要在命令后追加 `--keep-vars`、路径、环境或跳过检查参数；发布入口固定处理这些选项。

开发分支可先运行只检查命令：

```bash
npm run release:check
```

它要求包含最新远端 `main` 和线上源码，但允许尚未推送的候选提交。它执行相同的构建、测试、公司元信息预检、远端状态读取和 Wrangler dry run，不获取远端锁、不创建 Cloudflare 版本、不切换流量、不写生产数据库。它的结果不表示已经发布，正式发布仍重新检查。

工作区有其他任务的未提交修改时，不替其他任务提交、暂存或丢弃。使用已提交候选版本的干净 checkout；临时目录也必须具有完整 Git 历史并满足入口检查。脚本会从候选提交重新克隆到自己的隔离目录，工作区现有 `build/`、依赖、环境文件均不会被上传。

需要 Node.js 20 或更高版本、Git、npm、已启动的 Docker，以及站点 GitHub 仓库写权限、私有 `linsama-account` 仓库读取权限和现有 Cloudflare Wrangler 登录。数据库测试只使用脚本创建的 `postgres:17-alpine` 容器及随机本机端口，不读取生产数据库配置。公司元信息的生产预检和同步是单独步骤，使用下文的受限连接文件。

### 公司元信息准备

有来源的卡片先在私有仓库 `linsama-account/content/coding101/companies.json` 中登记，并合并、推送到该仓库的 `main`。正式发布每次直接获取私有远端 `main` 的已提交快照，不使用本机私有工作区的未提交文件；文章构建和元信息快照必须对应。公司未披露时保留 `companies: []` 和原始来源；本站自测题不登记公司元信息。

生产写入连接默认保存在 `~/.config/coding101-content-import/.env`，目录权限 `700`、文件权限 `600`：

```dotenv
DIRECT_DATABASE_URL=<Neon coding101 数据库的现有写入连接>
```

其他机器可以通过 `CODING101_CONTENT_ENV_FILE` 指定受限文件的位置。不要把连接串放进命令参数、Git、发布日志或聊天，也不要使用运营只读角色。入口只从这个文件读取生产连接，不继承通用 `DATABASE_URL`；数据库主机与库名须匹配 `release/production.json` 中的固定目标。

`worker/scripts/import-companies.mjs` 是正式入口的内部步骤，不再支持手工传入公司 JSON 直接替换全表。缺少连接、权限不足、漏登记来源、自测归属冲突或元信息源在检查期间更新，都会阻止发布通过；没有跳过同步的参数。

## 2. 源码和并发保护

发布按以下顺序执行：

1. 拒绝有未提交或未跟踪文件的 checkout，并固定候选提交号。
2. 从 GitHub 读取真实 `main`，不依赖缓存的 `origin/main`。正式发布要求候选提交与远端 `main` 完全一致。
3. 原子创建远端分支 `release-lock/coding101` 作为发布锁。多个 checkout、机器共用这把锁；锁已存在时停止，不抢占。
4. 固定私有元信息仓库远端 `main` 的提交与内容哈希，保存在公开 checkout 外的受限目录。在独立目录安装站点和 Worker 依赖，读取当前 Cloudflare 部署及源码标记。候选提交必须包含线上提交；未知源码版本、灰度分流、缺少 Git 对象均停止。
5. 运行第 3 节的全部检查，重新构建并生成 `release.json`。用本次构建产生的真实卡片索引校验元信息覆盖，并以只读事务检查生产库、记录数据摘要及新增／更新数量。
6. 上传前再次检查原工作区与提交、两个远端 `main`、锁的所有者及线上部署。任一变化都停止，禁止把旧检查结果用于新版本。
7. 使用 `wrangler deploy --keep-vars --strict --message …` 发布。版本消息记录完整源码提交与唯一发布批次。
8. 确认 Cloudflare 已切换到本次版本后，再次核对锁和私有源码，事务内锁定公司表并核对预检摘要，先保存旧数据备份，再新增或更新元信息；事务内及提交后逐条回读，最后通过带本次发布查询参数的线上公司数量接口核对结果。
9. 核对线上 `release.json`、主包和运行时包的 SHA-256，以及首页、主题页、账户页引用的资源。最后再次读取线上版本，确认验收期间没有被覆盖。站点和元信息验收全部通过才记录发布成功。
10. 清理本次测试容器，只释放自己持有的锁，保存结果与日志。

锁通过 Git 的 expected-value lease 创建和删除。正常失败或中断会执行清理；进程被强制终止、机器断网时可能留下锁。脚本不会按时间自动删锁，因为旧任务可能仍在运行。

这套保护约束统一入口。直接持有 Cloudflare 发布凭据的外部工具仍可以绕过它；仓库规则禁止这样操作，但 Git 锁不是 Cloudflare 权限隔离。此类发布会让下次入口发现无源码标记或线上版本变化并停止。要从权限层彻底禁止绕过，需要另行收敛发布凭据到唯一受控执行环境。

## 3. 必须通过的检查

- 发布保护回归：旧快照、分叉提交、脏工作区、未知线上版本、线上变化、两个 checkout 竞争锁、错误所有者删锁。
- 公司元信息回归：漏登记、重复或未知卡片、自测归属冲突、私有源变化、错误数据库或凭据权限、只读预检、事务回滚、并发变化、重复同步及丢失提交回执。数据库回归使用独立测试库，验证学习记录保持不变。
- 现有内容格式和学习内容解析测试。
- 运营测试与 UTM 参数过滤、异步路由回归；PostgreSQL 聚合测试在本次容器中执行。
- Worker 服务测试，使用本次独立 PostgreSQL 容器。
- 站点与 Worker 类型检查。
- 完整生产构建：文档链接、复习资源、文章格式、内容状态检查。
- 公开内容发现检查及 Worker 打包 dry run。

仅通过祖先关系检查不能证明功能没有被主动删掉，因此 UTM 回归测试也是发布必经步骤。GA4 网络接收验收仍单独记录：当前用户已暂停 Google 网络排查，本流程不把本地回归测试当作 GA4 接收成功。

## 4. 生产配置与版本记录

`release/production.json` 记录目标、生产功能开关和首次采用统一流程前的已核验版本。当前账号与购买入口开启、广告关闭，`PUBLIC_I18N` 为 `false`，多语言暂不公开。启停功能时修改此文件、提交并按流程发布；临时 shell 变量不会改变正式构建开关。

`npm run build:production` 从该文件读取开关，并关闭本地预览、模拟账户和样式预览。广告审核与隐私设置的要求仍按 README 执行，不能仅因修改开关就宣称审核或隐私验收通过。

新发布在 `https://coding101.linsama.com/release.json` 提供源码提交号、发布批次、构建时间、功能开关与两个入口包的 SHA-256，不含密钥。Cloudflare 版本消息使用 `coding101-release:<源码提交>:<发布批次>`，作为下一次发布的在线源码基线。

当前尚未带版本消息的已核验基线为 `8b1c9622-e36e-4973-9e0e-9a434a472c9b`，对应源码 `781271d18cff81c5f230e853077d612318b4357c`。该版本来自本次任务保留的生产构建，线上主包和运行时包已逐字节核对，SHA-256 分别为 `0922d93bbba6edec48fea643336c17ef15d2256f929cecc810af2786f18597a9` 和 `268381dac1a87e1b0e5521b2a681ac208a75f3410b77c4e65ff2eb91d524f0ff`。候选源码必须同时包含最新远端 `main`，保留 UTM、内容使用说明和产品更新。此映射只识别这个已核验版本，不是遇到未知版本时可随意改写的后备值；后续带源码标记的版本优先。

每次执行会输出临时日志目录和 `result.json`，包含源码、前后线上版本、各步骤退出码及失败原因。未确认上传结果时不得直接重试；先读取实际线上版本。日志中的部署步骤成功但验收失败，表示可能已经上线，不能写成“没有部署”。

`result.json` 还记录私有元信息提交、哈希、预检差异、数据库提交状态和线上数量核对结果。私有快照、`company-metadata/before.json` 原数据备份与步骤结果保存在本次受限日志目录，均不进入公开构建、`release.json` 或 Git；备份包含公司和原始来源，不能公开分享。清理发布产物时保留这些恢复记录。

同步只新增、更新有来源的卡片，内容未变的记录不会刷新时间，也不访问学习记录表。生产库里已退役的额外记录保留；若需要撤销归属或清理退役记录，先核对来源和 ID 迁移，另做有备份的数据变更，不通过发布自动删除。线上数量接口有一小时缓存，验收使用独立查询参数直接核对新数据，其他已缓存的数量会在到期后刷新；付费公司名称接口不使用这层数量缓存。

## 5. 失败、锁恢复与回滚

源码落后或分叉时，先同步并合并当前 `main`，保留已经上线的修复，重新检查。测试失败时修复原因，不加 `--skip` 或改用裸 Wrangler。线上版本没有标记时，先核对该次发布的源码与资源，不猜测提交号。

公司元信息校验失败发生在上传前，不会写生产库。同步发生在站点切换之后，因此同步失败可能意味着站点已上线、元信息未完成，发布结果仍为失败；不要把两个系统的操作视为同一个原子事务，也不要自动回滚整个站点。先读取步骤结果与实际数据库：`not-committed` 表示尚未发送提交，`committed` 表示已收到提交回执，`unknown` 或缺少结果表示必须人工核对。提交结果未知时保留本任务的锁，确认原进程已结束、实际数据及线上版本后再恢复。重新运行入口会重新检查，已同步的相同数据不会重复更新。

锁未释放时先确认原任务及其子进程已停止，检查 Cloudflare 当前版本和原日志。读取 `release-lock/coding101` 的当前提交并核对锁记录；只有确认它是已结束任务的遗留锁，才用匹配该完整 SHA 的 `--force-with-lease` 删除该引用。不要无条件 `git push --delete` 或删除其他任务仍持有的锁。

默认通过 `git revert` 产生新的修复提交，合并到最新 `main` 后使用统一入口发布。这样可撤销本次故障而保留其他已经上线的更新。需要整版本紧急回滚时，必须先明确将被撤回的改动、处理正在运行的发布并记录实际版本；不要在正常任务中自动回滚整个站点。回滚后同步修正源码，再恢复常规发布。

Wrangler 命令依据：[Cloudflare Workers CLI](https://developers.cloudflare.com/workers/wrangler/commands/workers/)。
