# Agentic Development 复习知识点与建设顺序

Agentic Development 在本路线中指使用能读取工程、调用工具、修改代码并利用执行反馈推进任务的 Agent 开展软件开发。复习目标是能完成和验证一个有约束的开发任务，并解释需求、代码、测试和工具结果之间的关系。

这是待建设知识点的内容草稿。面试依据来自 [219 份材料的研究](../audits/agentic-development/frequency/README.md)，频率主统计为 167 篇公开复盘。使用 Agent 开发软件与实现 Agent 系统分别组织：前者沿本文复习，后者进入 [AI 应用与 Agent 复习知识树与文档目录](./agent.md)。共享概念只建设一份正文。

## 1. 复习范围

第一轮要求能独立阅读和调试一门语言的程序，使用 Git，运行项目现有测试。Agent 能提供候选代码和方案，开发者仍需判断它是否符合需求、是否破坏现有行为，以及哪些动作需要进一步授权。

一次开发任务至少需要四类信息：目标与验收条件、相关工程上下文、可执行动作及权限、用于判断结果的证据。一次模型回答可能提出下一步行动；实际读取、修改和运行由外部工具执行，工具结果再参与后续判断。模型声称完成与程序通过验收是两件需要分别检查的事。

本文的“必会”构成 AI 辅助开发第一轮最小集合；“常考”用于第二轮补充；“按岗选学”由 JD、项目和面试形式决定。回答深度单独标注，不代表职级。

## 2. 第一轮知识点

| 标准主题 | 优先级／回答深度 | 需要掌握的结论与停止条件 | 证据或建设理由 |
| --- | --- | --- | --- |
| 需求分析 | 必会／场景分析 | 把目标拆成输入、输出、约束和验收用例；不明确且会改变实现的问题先澄清。能解释什么结果算完成 | C01：11/70；复用通用需求分析，增加 AI 开发练习 |
| 代码库理解 | 必会／原理解释 | 先定位入口、调用链、数据结构及现有测试，再选择修改点。能用文件与调用关系证明理解，避免把整个仓库无差别塞入上下文 | C02：8/70；实作子样本 6/24 |
| 开发任务分解 | 必会／基础回答 | 按依赖和可验证产物拆分，先完成最小可运行部分；计划随实际结果调整。能列出本次修改的下一步和验证方式即可 | C03：5/70；作为实践前置，不要求复杂规划算法 |
| 提示与反馈迭代 | 必会／原理解释 | 提供目标、约束、相关代码和实际反馈；报错、失败输入和差异比反复要求“再检查”更有用。能基于一次运行反馈缩小问题范围 | C04：9/70 |
| AI 代码调试 | 必会／场景分析 | 先复现，区分环境、需求理解、实现和测试问题，再验证假设。不能只让模型连续重写。能解释一个修复为何消除了根因 | C05：13/70；实作 10/24 |
| 测试与结果验证 | 必会／场景分析 | 区分编译通过、单测通过、集成可用和需求满足；测试依据来自行为契约。能覆盖正常、边界和失败路径，并说明未验证部分 | C06：17/70；引用通用测试正文 |
| 代码评审 | 必会／场景分析 | 沿需求、正确性、复杂度、兼容性与副作用审查差异；对生成代码同样要求能解释。能指出一个具体缺陷、影响与复现方式 | C07：14/70；引用通用评审正文 |
| 算法与数据结构 | 必会／原理解释 | AI 辅助实现仍需要判断复杂度、不变量和边界。能独立解释代码并修改错误实现 | C08：11/70；沿现有算法主题复习，不新增单题题解系列 |
| Git 工作区 | 必会／基础回答 | 检查已有修改、限定改动范围、阅读 diff，并保留可恢复状态。能在不覆盖他人改动的情况下交付本次修改 | 通用工程前置；本轮没有单独统计为 AI 高频题 |
| 工具授权 | 必会／基础回答 | 读取、写文件、运行进程、联网和发布的影响不同；权限由执行环境检查。能说明任务需要哪些权限及授权范围 | 复用 Agent 安全正文；不能从低披露率推断可省略 |

“必会”不要求每次任务都写长计划、创建新测试框架或用多个 Agent。简单任务可以短流程完成，但修改范围、结果判断和现有工程约束仍要明确。

## 3. 第二轮与岗位扩展

| 标准主题 | 优先级／回答深度 | 核心范围与停止条件 | 正文归属 |
| --- | --- | --- | --- |
| 上下文管理 | 常考／原理解释 | 区分稳定规则、当前需求、代码证据、工具结果与待验证判断；按当前步骤选择材料，识别陈旧或冲突信息 | 共享 `llm/context-management.mdx` |
| 上下文压缩 | 长任务常考／场景分析 | 压缩可能丢失约束和失败线索；保留任务目标、已验证状态、产物位置及未解决问题。恢复时重新核对实际文件和测试 | 拆为 `llm/context-compaction.mdx`，避免打断上下文基础主线 |
| 仓库指令 | 常考／基础回答 | 保存稳定的构建、验证和代码规范；避免混入每次任务的临时状态。具体文件名、层级与作用域按所用工具核验 | 新增 `development/repository-instructions.mdx`；本样本仅 2/70，优先级来自重复使用价值 |
| 编码 Agent 评测 | 常考／场景分析 | 用代表任务、相同环境及明确验收比较方案，同时记录成功率、耗时、成本和人工返工；不能只用代码量或 Token 量证明提效 | 新增 `evaluation/coding-agent-evaluation.mdx`；复用 Agent 评估方法 |
| Agent Skills | Agent 应用岗位常考，普通开发按岗／原理解释 | 知识、流程和资源如何组织、发现并按需加载；能与普通提示词、工具接口区分，并解释为何技能说明不能授予权限 | 共享 `agents/skills.mdx`；应用样本 31/142，全为中文 |
| MCP | Agent 应用岗位常考，普通开发按岗／原理解释 | 解释 Host、Client、Server 及工具接入职责；知道接入协议与授权、工具执行分别解决什么问题 | 共享 `agents/mcp.mdx`；应用样本 26/142 |
| 多 Agent 协作 | Agent 应用岗位常考，普通开发按岗／场景分析 | 按任务依赖、上下文隔离和验证方式决定是否拆分；能处理结果冲突、重复劳动、文件竞争与局部失败 | 共享 `agents/multi-agent.mdx`；应用样本 39/142；复杂通信协议选学 |
| Agent Harness | 编码 Agent 研发岗位常考／原理解释 | 解释模型之外的工具执行、上下文、状态、权限、预算与验证如何配合；能画出一次读取、修改、测试及恢复的链路 | 新增共享 `agents/harness.mdx`；架构宽口径 43/142，不能当作术语本身的频率 |
| Agent 状态 | 长任务或平台岗位按需必会／场景分析 | 保存哪些已执行动作及结果，重启后怎样查证；区分恢复、重试与重新发起。可能有副作用的动作不能盲目重放 | 共享 `agents/state.mdx`、`agents/durable-execution.mdx` |
| 执行沙箱 | 编码 Agent 研发岗位必会基础，实现按岗／场景分析 | 说明文件、网络、进程与资源边界；能验证越界操作确实被拒绝，而非仅靠提示词限制 | 共享 `security/sandboxing.mdx` |

RAG、向量数据库和微调不列为普通 AI 辅助开发的默认前置。需要实现代码索引、知识库问答或 Agent 产品时，再从 [AI 应用与 Agent 复习知识树与文档目录](./agent.md)选择相应节点。

## 4. 内容建设与练习顺序

| 顺序 | 核心阅读与练习 | 本轮停止条件 | 深入阅读 |
| --- | --- | --- | --- |
| 1 | 需求分析、代码库理解、提示与反馈迭代；在已有项目中补一个小功能 | 能指出修改位置，列出验收条件，解释输入给 Agent 的材料 | 仓库指令、上下文管理 |
| 2 | AI 代码调试、测试与结果验证、代码评审；修复一个带失败测试的问题 | 能复现、提出假设、完成修复并说明测试未覆盖的风险 | 集成测试、性能分析 |
| 3 | 算法与数据结构、需求变更；限时完成允许使用 AI 的实现任务 | 能解释不变量、复杂度和边界，需求改变后仍能修改实现 | 目标岗位的算法主题 |
| 4 | 上下文管理、上下文压缩、Git 工作区；中断后恢复一个开发任务 | 能从实际仓库恢复进度，不把摘要中的“完成”当成验收结果 | 编码 Agent 评测 |
| 5 | 按岗选择工具、执行循环、状态、Harness、Skills、MCP 和多 Agent | 能解释选型和失败处理；只有可测的收益才增加结构 | Agent 应用分支的实现与系统设计 |

面向 AI Coding 面试，先完成前三步。面向 Agent 开发岗位，在第一步后即可并行复习应用分支的工具调用、执行循环和评估。框架实践选择一套实现，不把多个框架的 API 都作为第一轮背诵内容。

拟新增正文只覆盖 AI 开发特有的问题：`development/codebase-context.mdx`（代码库上下文）、`development/feedback-iteration.mdx`（开发反馈迭代）、`development/ai-code-debugging.mdx`（AI 代码调试）、`development/repository-instructions.mdx`（仓库指令）。通用需求、测试、评审、Git、算法继续引用共享内容；具体综合任务另写教程。

## 5. 面试自测

以下题目根据公开任务或问法整理，参考回答为本项目的原理推导。公司信息仅说明候选人曾公开复盘相关考察。

<a id="practice-5-1"></a>

### 5.1 配置文件热更新任务中，如何发现并修正 AI 生成实现的问题？
<!-- 出现公司：阿里云。公开任务及评审过程来源：https://www.nowcoder.com/discuss/872120976190816256 。本题为任务改述，不是逐字引文。 -->

**出现公司**：阿里云。

**考察重点**：需求边界、代码评审、基于反馈的修改，以及验证是否真正满足任务。

**相关内容**：[第一轮知识点](#2-第一轮知识点)中的需求分析、提示与反馈迭代、测试与结果验证。

<details>
<summary>参考回答</summary>

先确定热更新的外部行为：支持哪些格式、修改后何时生效、解析失败时保留旧配置还是报错，以及读取方能否看到不完整状态。再沿文件变化、解析、校验和发布新配置的链路评审实现。

例如发现代码在配置解析失败前就覆盖共享状态，应构造损坏配置的输入，观察旧配置是否仍可用，再要求修改发布时机。反馈应包含具体代码、复现步骤、实际结果和期望结果。修复后除正常更新外，还要验证失败配置和重复变化；是否需要并发用例由任务要求决定。

</details>

<a id="practice-5-2"></a>

### 5.2 面对陌生代码库和失败测试，如何借助 AI 定位并修复问题？
<!-- 出现公司：Meta。公开 AI 辅助编程任务来源：https://www.reddit.com/r/leetcode/comments/1p35b98/meta_e4_software_product_interview_experience/ 。本题概括其多文件项目修复任务，不是逐字引文。 -->

**出现公司**：Meta。

**考察重点**：代码库理解、失败定位、可检验的假设和修复范围。

**相关内容**：[第一轮知识点](#2-第一轮知识点)中的代码库理解、AI 代码调试、代码评审。

<details>
<summary>参考回答</summary>

先运行能复现问题的测试，确认环境和失败位置；沿测试输入、调用链与关键状态查找相关实现。把必要代码、错误输出和行为约束交给 Agent，要求提出可以验证的解释，并逐个排查。

修复应针对导致失败的机制。修改后运行相关用例，再根据影响范围做回归，并检查 diff 是否引入无关改动。若模型建议改测试，需要先判断测试是否违背需求；不能仅因为测试妨碍通过就删除断言。最后能解释修复前后的行为差异及尚未验证的部分。

</details>

<a id="practice-5-3"></a>

### 5.3 AI 一次生成大量代码时，代码评审应怎样分配给 AI 与人工？
<!-- 出现公司：汇川技术。公开问法来源：https://www.nowcoder.com/feed/main/detail/28032c48a90c4f69827704deb3fae34c 。公司归属为候选人自述。 -->

**出现公司**：汇川技术。

**考察重点**：审查依据、自动检查边界、业务正确性和交付责任。

**相关内容**：[第一轮知识点](#2-第一轮知识点)中的代码评审、测试与结果验证，以及[第二轮与岗位扩展](#3-第二轮与岗位扩展)中的编码 Agent 评测。

<details>
<summary>参考回答</summary>

先按功能和依赖拆分差异，识别权限、数据修改、接口兼容等关键位置。格式、类型、静态规则与已有行为可交给自动检查，AI 可以辅助梳理调用链和寻找疑点，但它给出的结论仍需代码与运行证据支持。

人工重点核对需求、架构约束和高影响行为，并判断证据是否充分。如果变更大到无法解释，应缩小变更或分批验证。多个模型都表示认可不能替代测试，也不能证明它们没有遗漏同一问题。验收者需要明确已验证的范围及剩余风险。

</details>
