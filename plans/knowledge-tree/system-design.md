# 系统设计复习知识树与文档目录

系统设计分支训练把需求转换成可解释、可验证的系统方案。内容分为设计方法、通用原理与模式、完整设计题，数据库和中间件实现引用共享基础。

> 本文是[总纲](../interview-roadmap-outline-proposal.md)的分纲。默认优先级面向需要参加系统设计面试的候选人；普通 Java 后端路线只取基础接口、数据、一致性与可靠性核心。完整设计练习可超过 5—10 分钟，原理文章保持短篇复习范围。

## 1. 知识树与停止条件

| 分组 | 核心节点 | 深入或按岗节点 | 默认优先级／深度 | 前置与停止条件 |
| --- | --- | --- | --- | --- |
| S01 设计方法 | 系统设计面试、需求分析、容量规划、接口设计、数据建模、系统架构 | 负载测试、约束变化下的重新设计 | 必会／场景分析 | 前置：HTTP、SQL、基础存储。能限定需求，定义关键实体与接口，画出可完成业务的最小读写链路 |
| S02 分布式故障 | 部分失败、超时、重试、幂等键 | 时钟、租约、故障检测 | 必会／原理解释 | 前置：网络与并发。能解释超时后结果未知、重复请求与节点恢复的影响 |
| S03 复制与一致性 | 主备复制、一致性模型、CAP 理论、分布式一致性 | Raft、Quorum、跨地域复制 | 常考／原理解释；具体业务需要场景分析 | 前置：事务与 S02。能根据读写路径说明承诺、失效窗口和副本延迟，不靠 CAP 标签决定所有方案 |
| S04 分区与扩展 | 数据拆分、负载均衡、一致性哈希、分布式 ID | 在线扩容、热点分区、跨分片查询 | 必会／场景分析 | 前置：索引、访问模式、S03。能选分片键、识别热点，并说明扩容时如何定位和迁移数据 |
| S05 分布式业务流程 | Saga、Transactional Outbox、CDC、分布式流程恢复 | 两阶段提交、TCC、对账 | 常考／场景分析 | 前置：本地事务、消息语义、幂等。能画出每一步提交、失败和补偿，说明哪些业务状态允许暂时不一致 |
| S06 扩展模式 | 缓存引用、异步处理、读写分离、扇出、长任务 | CQRS、事件溯源、实时推送、大对象传输 | 常考／场景分析 | 前置：缓存、消息、S03/S04。能从具体瓶颈引入机制，说明额外存储、延迟和一致性成本 |
| S07 服务可靠性 | 超时、重试、幂等键、限流、服务容错 | 熔断、降级、隔离、背压 | 必会／场景分析 | 前置：S02、容量与任务执行。能从依赖故障推导重试预算、排队、拒绝与降级结果 |
| S08 可用性与容量 | 服务等级目标（SLO）、灾难恢复、故障转移 | 多租户、成本归因、多地域方案 | 常考／场景分析 | 前置：复制与 S07。能指定可观测目标和可恢复结果，解释 RTO/RPO、备份与冗余的区别 |
| S09 架构与服务治理 | 模块化单体、微服务架构、API 网关、服务发现 | 限界上下文、聚合、配置中心、灰度发布、控制平面与数据平面 | 基础架构常考，其余按岗／场景分析 | 前置：服务边界、事务与 S07。能解释边界为何这样划分，以及调用、数据和运维成本 |
| S10 架构决策与演进 | 架构决策记录（ADR）、架构迁移、绞杀者模式 | 设计评审、事故复盘、技术债 | 按岗选学／场景分析 | 前置：真实项目或明确题设。能用约束、备选方案和结果说明决策；不把这些主题扩展为管理课程 |
| S11 面向对象设计 | SOLID 面向对象设计原则、对象职责、状态机 | 策略模式、工厂方法模式、装饰器模式、观察者模式、适配器模式、单例模式、代理模式、责任链模式 | 按面试类型选择／场景分析 | 前置：语言对象模型。能从用例设计对象协作和扩展点，说明模式解决的问题与间接层成本 |
| S12 综合设计题 | 内容读写、交易流程、知识库问答、客服 Agent | 消息、社交、搜索、任务平台、存储与多租户 | 核心案例必练／场景分析 | 前置：案例关联的核心节点。能交付完整方案，再用瓶颈和失败场景检查；无需先读完全部分支 |

S02 与 S07 共享超时、重试和幂等文章：S02 建立故障模型，S07 组合容量保护方案。S03 与 S05 同样引用唯一的一致性文章，分别应用于存储复制和业务流程。

## 2. 第一轮复习集合

1. 读设计方法，明确需求、实体、接口和主链路；容量计算只针对会改变架构的量。
2. 复习 SQL、索引、事务、缓存、消息、HTTP 与鉴权；已经掌握的节点直接跳过。
3. 掌握复制与一致性的基础，解释超时、重试、幂等、限流和故障恢复。
4. 完成一个内容读写案例和一个多步骤业务案例，再根据目标岗位选 AI、消息或平台案例。

**停止条件**：给出完整的读写路径、主要数据模型和一个合理扩展方案，并能讨论重复请求、部分成功、依赖不可用与恢复。对于每个新增组件，都能说明引入原因、保存的状态和失败行为。

## 5. 案例文风与验证

先描述本题必须实现的能力与约束，再引出数据、组件与故障处理。规模由明确题设或标注的假设给出；计算结论必须改变存储、分片、缓存或交付策略。

图至少标出关键数据流和保存的状态。深入讨论按“触发条件—备选方案—选择理由—新成本—失败行为”推进，不罗列所有中间件名称。结尾用具体输入和故障检查方案，不重复开头。

首篇继续评审现有 Pastebin 样稿，第二篇用订单支付验证业务一致性的写法，第三、四篇用 AI 案例验证模型不确定性与传统工程故障能否讲清楚。四篇都通过后，再扩充同类案例。
