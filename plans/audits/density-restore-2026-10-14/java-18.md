### 改动较大的段落

原文：

> 覆盖率衡量执行范围。行覆盖率达到 100%，仍会漏掉分支与输入组合。即使分支全覆盖，错误结果也能通过薄弱断言。

改写：

> 覆盖率用来回答测试执行到了哪里。JaCoCo 把至少一条指令执行过的行标为已覆盖。分支计数覆盖 if 和 switch 的分支。异常处理不计入它的分支覆盖率。
>
> 行覆盖率达到 100%，仍会留下**五类盲区**：
>
> - 代码执行了，但断言没有检查关键结果。
> - 某行中的分支尚未走全，或分支全覆盖后仍遗漏输入组合。
> - 测试复制了实现中的错误算法，算出的期望值也错了。
> - 并发时序和外部协议边界尚未验证。
> - 异常被捕获后，测试没有检查数据或对象是否处于正确状态。
>
> 所以，覆盖率适合寻找未执行区域，质量判断还要结合这些盲区。边界用例和真实集成检查行为，变异测试进一步检查断言能否发现代码错误。具体要覆盖什么，仍由业务风险决定。

### 改动较大的段落

原文：

> 缓存 key 应包含区分业务结果的参数，如租户和资源 ID。`condition` 控制是否应用缓存，`unless` 可在执行后否决缓存写入。

改写：

> 缓存增强需要先确定缓存项的身份，再确定结果何时可见。缓存 key 是定位缓存项的键，应包含租户和资源 ID 等影响业务结果的参数。设计 key 时，重点避免以下**三类错误**：
>
> - 用可变参数作为键，写入后参数变化，使键与原结果失去对应关系。
> - 自定义键使用不稳定的 `toString()`，导致同一业务对象在不同调用中得到不同键。
> - 遗漏租户字段，让不同租户命中同一缓存项。
>
> `condition` 控制是否应用缓存，`unless` 则可在方法执行后否决缓存写入。数据库提交前就写缓存，后续回滚会让缓存留下尚未生效的数据。可以在提交后失效或更新缓存，也可使用支持事务同步的缓存管理器延后变更。
>
> 数据库与远程缓存仍需分别处理失败，并明确缓存更新失败后的重试方式。最终时机要通过实际拦截链验证，因为切面顺序会改变执行位置。

> 判断异常能否统一处理，要先看它从哪里抛出。`ControllerAdvice` 参与 `DispatcherServlet` 的异常解析链。链中的 `HandlerExceptionResolver` 负责寻找合适的方式，把异常转换成响应。
>
> 需要区分以下**三种异常路径**：
>
> - Filter 在进入 MVC 前抛出的异常，由过滤链或 Servlet 容器处理。安全过滤链可使用自己的错误处理器，容器也可发起 error dispatch，即错误派发。
> - MVC 的 `Callable` 抛错后，会触发异步派发，重新进入 MVC 处理流程。`DeferredResult.setErrorResult(exception)` 也会把异常交给 MVC resolver。
> - 独立后台任务没有对应的 MVC 请求派发，其失败由任务结果或任务异常处理器承接。
>
> 响应提交后，状态和已写出的正文已经交给客户端，错误处理器无法重新设置完整响应。这时应记录序列化或写出失败，再按连接状态结束处理。客户端断开造成的 I/O 错误应单独统计，避免全部计为应用 500。
