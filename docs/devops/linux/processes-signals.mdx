# 进程管理与信号

Linux 用进程运行程序，用信号通知进程处理退出、暂停等事件。启动一个程序、请求它退出、回收它留下的退出信息，是三个不同的步骤。理解这些步骤由谁完成，才能解释僵尸进程为什么不能再被杀死、`kill` 成功为什么不代表进程已经退出，以及长期服务为什么需要托管。

## 1. 面试核心 {#core}

- 系统调用、中断和异常都可以进入内核执行路径，但**进入内核不等于切换线程**。[卡](#user-kernel-mode)
- 僵尸进程**已经退出，只是退出信息尚未回收**，需要父进程通过 `wait` 系列接口完成回收。[卡](#zombie-orphan)
- 孤儿进程失去了原父进程，由**最近的子进程收养者（subreaper）或所在 PID 命名空间的 init 接管**。[卡](#zombie-orphan)
- `SIGTERM` 可以捕获并处理，**`SIGKILL` 和 `SIGSTOP` 无法捕获、屏蔽或忽略**。发送成功后，仍要确认进程最终状态。[卡](#signal-delivery)
- systemd 的 **`After` 控制顺序，`Wants` 声明弱依赖**。只配置顺序，不会自动启动另一个服务。[卡](#systemd-ordering)

## 2. 用户态与内核态 {#用户态与内核态}

**用户态**是应用程序运行时受到权限限制的执行状态，**内核态**则允许内核执行受特权保护的操作。CPU 的特权级限制可执行的指令和可访问的地址，内核结合页表与权限检查维护进程之间的隔离。

用户程序通过自己的虚拟地址空间访问数据；需要共享内存时，可以把共享区域显式映射进来。应用要使用文件、设备等系统资源，则通过系统调用请求内核服务。进入内核执行路径的入口包括：

| 入口 | 触发条件 |
| --- | --- |
| 系统调用 | 应用请求 read、write、open 等内核服务 |
| 中断 | 时钟、网卡等设备触发 |
| 异常 | 缺页、非法指令等执行事件 |

进入内核时，要保存恢复执行所需的上下文。但这不意味着一定要换一个线程运行：系统调用完成后，原线程可以直接回到用户态继续执行。特权级切换和线程调度是两件事。

频繁的小块 I/O 会增加调用与复制开销，批量 I/O 可以通过减少调用次数降低其中一部分开销。`strace -c -p <pid>` 可用于统计系统调用。协程之间的切换可以由用户态运行时完成，但协程内执行阻塞系统调用时，仍然会进入内核。

## 3. 进程状态与父子关系 {#进程状态与父子关系}

进程列表里能看到一个 PID，不代表它还在执行代码。先看状态，才能区分它是在运行、等待、暂停，还是已经退出：

| 状态 | 含义 |
| --- | --- |
| R | 正在运行或等待 CPU |
| S | 可中断睡眠 |
| D | 不可中断睡眠 |
| T | 停止 |
| t | 被调试器跟踪而停止 |
| Z | 已退出，等待回收 |

`fork` 创建子进程后，父子进程各有自己的虚拟地址空间。私有可写页采用**写时复制**：开始时共享物理页，发生写入时再分离副本。显式共享的映射则仍可让修改对双方可见。

父子进程继承的文件描述符还可能指向同一份内核打开文件记录，因此共享文件偏移。这个关系与地址空间是否独立是两回事，详见[文件描述符](../../basic-knowledge/operating-system/file-descriptors.mdx)。

**僵尸进程**是已经退出、但退出信息尚未被回收的进程。子进程结束后，内核保留 PID、退出状态等信息，让父进程可以通过 `wait` 或 `waitpid` 取得结果并完成回收。大量僵尸会继续占用 PID 等内核资源，但它们已经没有正在执行的代码。

**孤儿进程**是原父进程先退出、需要被其他进程接管的进程。**subreaper** 是被设置为收养后代孤儿进程的进程，系统会选择祖先进程中最近的 subreaper 接管；没有这样的收养者时，则由所在 PID 命名空间的 init 接管。接管以后能否及时回收退出的子进程，仍取决于收养者有没有正确调用回收接口。

容器中的 PID 1 也要处理信号，并回收它收养的子进程。如果应用没有实现这些职责，可以通过 `docker run --init` 补充轻量 init。

## 4. 信号 {#信号}

**信号**是通知进程发生了某个事件的机制。每种信号都有默认动作，应用也可以为允许处理的信号注册处理逻辑。`SIGKILL` 和 `SIGSTOP` 是例外，不能被捕获、屏蔽或忽略。

| 信号 | 默认动作 | 典型用途 |
| --- | --- | --- |
| SIGHUP | 终止 | 终端挂断；部分服务约定为重载 |
| SIGINT | 终止 | 终端前台任务中断 |
| SIGTERM | 终止 | 请求正常退出 |
| SIGKILL | 终止 | 强制终止 |
| SIGSTOP | 停止 | 暂停执行 |
| SIGCONT | 继续 | 恢复停止任务 |
| SIGCHLD | 默认忽略 | 通知子进程状态变化 |

信号编号存在架构差异，脚本应优先使用名称。`kill -TERM <pid>` 向进程发出退出请求；要实现优雅退出，应用需要处理 `SIGTERM`，先停止接收新任务，再收尾正在执行的工作并清理资源。

`kill` 成功只表示发送请求被接受，不保证目标已经退出。任务处于 D 状态、等待内核操作完成时，终止可能被延迟；`SIGKILL` 无法让它跳过这段尚未结束的内核等待。因此，发信号后还要检查进程状态。

普通信号在阻塞期间多次产生，只保留一个尚待处理的实例；实时信号则可以排队。`SIGCHLD` 属于普通信号，所以多个子进程先后退出，父进程可能只收到一次待处理通知。处理时应循环调用 `waitpid`，回收所有已经退出的子进程，不能把一次通知当成只有一个子进程退出。

`SIGCHLD` 的默认动作虽然写作「忽略」，却不等于应用显式设置 `SIG_IGN`。默认行为仍可留下等待回收的僵尸；显式设置 `SIG_IGN` 或使用 `SA_NOCLDWAIT`，才可以让退出的子进程自动回收。

## 5. 服务托管与后台运行 {#服务的托管与后台运行}

让命令离开前台，只解决终端能否继续使用的问题。长期服务还需要失败重启、日志和资源管理，因此要按任务用途选择运行方式：

| 方式 | 行为 |
| --- | --- |
| `cmd &` | 交给 Shell 后台执行 |
| `nohup cmd >out.log 2>&1 &` | 忽略 SIGHUP，并重定向输出 |
| tmux、screen | 保留可重连的终端会话 |
| systemd | 管理启动、依赖、失败重启和资源 |

`nohup` 可以避免挂断信号按默认动作结束任务，但不会监督进程，也不会在它失败后自动重启。systemd 则通过单元文件管理服务的运行。版本环境也要区分：CentOS 7 使用 systemd，CentOS 6 使用 Upstart，并兼容 SysV 服务脚本。

下面是一个服务单元示例：

```ini
[Unit]
Description=Demo app
Wants=network-online.target
After=network-online.target

[Service]
Type=exec
User=app
ExecStart=/opt/app/bin/app --config /etc/app.yaml
Restart=on-failure
RestartSec=3s
TimeoutStopSec=30s
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

示例要求 systemd 240 及以上版本，`app` 用户、程序和配置文件需要事先存在。服务默认把输出交给 journal 日志系统。`Type=exec` 在程序成功执行后确认启动步骤完成，但此时业务未必已经能接收请求；业务就绪仍需额外机制确认。

写好单元文件后，用 `systemctl daemon-reload` 让 systemd 重读定义，再用 `systemctl enable --now app` 设置开机启动并立即启动。排查实际配置时，`systemctl cat app` 会显示单元定义及覆盖配置；查看运行日志则用 `journalctl -u app -f`。

## 6. systemd 依赖与重启策略 {#systemd-依赖与重启策略}

systemd 把「是否需要启动另一个单元」和「谁先启动」分开配置。`After` 只规定两个单元之间的顺序，不会主动启动另一个单元。`Wants` 把另一个单元加入本次启动操作，但对方启动失败不会因此阻止本单元启动，这称为弱依赖。`Requires` 声明更强的依赖；配合 `After` 时，如果所依赖的单元启动失败，本单元也不会启动。

前面的示例同时配置 `Wants=network-online.target` 和 `After=network-online.target`，就是既要求启动该目标，又要求本服务排在它后面。但 `network-online.target` 只描述启动阶段的网络条件，具体效果取决于等待网络的实现，不能保证远端数据库可用。

`Restart=on-failure` 在异常退出等失败后重启服务，`RestartSec` 控制重试间隔。启动频率还受到 `StartLimitIntervalSec` 和 `StartLimitBurst` 的限制，所以配置了自动重启，也不意味着服务会无限、立即地重试。

`daemon-reload` 与 `reload` 操作的对象不同：前者让 systemd 重读单元文件，后者请求服务重新加载自己的配置。修改单元文件后，先执行 `daemon-reload`，再按需重启服务；服务是否支持 `reload`，则取决于应用及单元定义。

## 7. 面试题 {#面试题}

### 7.1 用户态和内核态有什么区别？什么情况下会切换到内核态？ {#user-kernel-mode}

**考察重点**

- 特权级与内存访问范围的区别。
- 系统调用、中断、异常三种进入方式；切换的开销与优化方向。

**相关内容**：[用户态与内核态](#用户态与内核态)。

<details>
<summary>参考回答</summary>

**用户态与内核态拥有不同的执行和访问权限。**

用户程序通过自己的虚拟地址空间访问数据，需要系统服务时发起系统调用，由内核执行受特权保护的操作。中断和异常也可以使 CPU 进入内核执行路径。

进入内核需要保存执行上下文，但未必发生线程切换，原线程完成系统调用后可以直接继续运行。协程切换可以由用户态运行时完成，协程发起系统调用时仍然需要进入内核。频繁的小块 I/O 可以考虑批量处理，以减少调用开销。

</details>

### 7.2 僵尸进程和孤儿进程有什么区别？僵尸进程怎样处理？ {#zombie-orphan}

**考察重点**

- 两种进程产生的条件和谁负责回收。
- 僵尸进程不能被 kill，要处理父进程；容器中的 PID 1 问题。

**相关内容**：[进程状态与父子关系](#进程状态与父子关系)。

<details>
<summary>参考回答</summary>

**僵尸已退出但尚未回收，孤儿的父进程先退出。**

父进程通过 `wait` 系列接口读取子进程的退出信息并完成回收。孤儿则由最近的 subreaper 或所在 PID 命名空间的 init 接管，之后由收养者负责回收。

僵尸已经结束执行，发送 `SIGKILL` 无法再次终止它。应定位父进程并修复回收逻辑；即使结束父进程，仍需要收养者正确执行回收。容器 PID 1 缺少这项能力时，可以使用轻量 init。

</details>

### 7.3 怎样让程序在后台长期运行？systemd 是什么，怎样知道一个服务运行的是哪个程序？ {#systemd-background}

**考察重点**

- `nohup`、`tmux` 与 `systemd` 的适用场景。
- 单元文件的关键配置；SysV init 与 systemd 的差异；优雅停止。

**相关内容**：[服务托管与后台运行](#服务的托管与后台运行)、[信号](#信号)。

<details>
<summary>参考回答</summary>

**长期服务适合由 systemd 监督运行。**

临时后台任务可以用 `nohup`，需要重新连接终端的交互任务可以用 `tmux`；长期服务则需要 systemd 管理失败重启和资源。

`systemctl status app` 查看服务与主进程。`systemctl cat app` 查看 ExecStart 及覆盖配置。需要确认实际程序时，可进一步核对主进程信息。

单元文件定义运行用户、启动命令和重启策略。`After` 控制顺序，`Wants` 或 `Requires` 定义依赖。停止行为受 `KillSignal` 和 `TimeoutStopSec` 等配置影响，默认先发 `SIGTERM`，超时后可发送 `SIGKILL`，因此应用也要配合处理退出信号。

</details>

### 7.4 kill -9 后进程为什么还在？一次 SIGCHLD 能对应多个退出吗？ {#signal-delivery}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：信号发送、内核等待与普通信号合并。

**相关内容**：[信号](#信号)。

<details>
<summary>参考回答</summary>

**进程可处于尚未结束的内核等待，或已经变成僵尸。**

先用 `ps` 确认状态。D 状态可能还在等待内核操作完成，要检查等待点；Z 状态说明已经退出，应检查父进程为什么没有回收。

一次 `SIGCHLD` 可以对应多个子进程退出，因为普通信号的多个待决通知会合并。处理时应循环调用 `waitpid`，直到没有已经退出、等待回收的子进程。

</details>

### 7.5 After 能保证依赖服务被启动吗？daemon-reload 与 reload 有何区别？ {#systemd-ordering}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：依赖事务、启动顺序与配置重载。

**相关内容**：[systemd 依赖与重启策略](#systemd-依赖与重启策略)。

<details>
<summary>参考回答</summary>

**`After` 不能保证依赖被启动，它只规定顺序；`daemon-reload` 重读单元文件，`reload` 则让服务重读自己的配置。**

需要另一个服务先启动时，应组合 `Wants` 或 `Requires` 与 `After`。修改单元定义后执行 `daemon-reload`，再按需重启；应用配置能否通过 `reload` 生效，要看应用是否支持以及单元如何定义。

</details>
