# Linux 性能排查

Linux 性能排查要回答的是：请求变慢时，时间花在计算上，还是花在等待上。CPU、内存和 I/O 指标提供不同的线索，但任何一个数值都不能单独解释故障。面试中需要讲清楚指标的含义，再把机器、进程、线程和请求的证据联系起来。

## 1. 面试核心 {#core}

- Linux 的 load average 统计 **R 与 D 状态任务的平均数量，不是 CPU 使用率**；其中既有运行或等待 CPU 的任务，也有不可中断睡眠的任务。[卡](#load-average)
- CPU 高时要先区分**用户态、内核态和软中断时间**，在 `top` 中分别对应 `us`、`sy` 和 `si`，再找进程、线程和热点代码。[卡](#high-cpu)
- 排查 I/O 时，**`iostat` 看设备，`pidstat -d` 看任务**，需要把设备延迟与具体请求的等待联系起来。[卡](#slow-but-idle)
- PSI 量化的是**任务因 CPU、内存和 I/O 资源受阻的时间**，可以补充利用率无法说明的等待情况。[卡](#psi-throttling)
- 容器用完 CPU 配额后，即使**宿主还有空闲 CPU，也可能继续等待**，因此要同时检查容器及其父组的限制。[卡](#psi-throttling)

## 2. load average 指标 {#load-average-指标}

**平均负载**（load average）是 Linux 对 R 与 D 状态任务数量计算出的平均值，任务包含线程。`uptime` 和 `top` 显示的三个值对应 1、5、15 分钟时间尺度，采用指数衰减计算，越近的状态影响越大。

R 包括正在运行和等待 CPU 的任务；D 表示不可中断睡眠，例如等待某些存储操作或内核资源。D 状态的任务此刻没有使用 CPU，却也计入负载，所以负载很高时，CPU 仍然可能空闲。

| 现象 | 后续判断 |
| --- | --- |
| 负载高、CPU 忙、r 队列长 | 检查计算和 CPU 竞争 |
| 负载高、CPU 空闲、D 多 | 检查不可中断等待 |
| 1 分钟值高于 15 分钟值 | 近期负载高于较长时间尺度 |
| 负载低、单核持续忙 | 检查单线程瓶颈 |

把负载与 CPU 核数比较，只能作为初步线索。比如负载等于核数，如果其中包含 D 状态任务，就不能据此说 CPU 刚好用满。还要同时查看任务状态、每核使用率和进程实际能用的 CPU 配额。

## 3. 常用工具与关键字段 {#常用工具与关键字段}

先用总体指标确定方向，再选择能定位到设备或任务的工具。比如设备延迟上升后，要继续查哪些进程在发起 I/O，不能停在「磁盘忙」这个结论上。

| 工具 | 关键证据 |
| --- | --- |
| `top`、`mpstat -P ALL 1` | 总体与每核 CPU；us、sy、si、wa、st |
| `vmstat 1` | r 可运行任务、b 阻塞任务、si/so 交换、cs 切换 |
| `free -h` | available 与 swap 用量 |
| `iostat -x 1` | await、aqu-sz、吞吐与 util |
| `pidstat -u -d -w 1` | 任务的 CPU、I/O 和切换 |
| `iotop` | 任务 I/O 活动 |
| `perf top -p <pid>` | 热点函数采样 |
| `dmesg` | OOM、设备错误等内核记录 |

`vmstat` 和 `iostat` 的首次报告包含启动以来的统计。排查刚发生的故障时，应重点观察后续按间隔输出的数据，避免把长期平均值当成故障时刻的状态。

`iostat` 的 `await` 是 I/O 请求的平均等待时间，包含排队和设备处理时间；`util` 表示统计周期内设备处理 I/O 的时间占比。SSD 和 RAID 可以并行处理多个请求，所以 `util` 接近 100% 只说明设备持续有工作，是否已经成为瓶颈，还要结合延迟和吞吐判断。

`wa` 统计 CPU 空闲且有待完成 I/O 的时间，不能单独指出哪个设备或进程有问题。`st` 表示虚拟 CPU 等待宿主调度的时间。它与容器 CPU 配额限流不是同一个指标，两类资源约束要分别检查。

## 4. 三类场景的排查路径 {#三类场景的排查路径}

### 4.1 CPU 热点 {#cpu-热点}

CPU 热点要沿着「机器—进程—线程—代码」逐步缩小范围，同时确认高占用与故障发生在同一时段：

1. 对比故障时间、流量和发布记录。
2. 用 `top` 找高占用进程，再用每核统计检查分布。
3. 用 `top -Hp <pid>` 或 `pidstat` 找线程。
4. 用户态热点用 `perf` 或语言工具定位。
5. 内核态热点结合调用、中断与上下文切换分析。

`sy` 高时，可用 `strace -c -p <pid>` 统计系统调用，检查是否有大量调用造成开销；`si` 高时，则要核对网络包量和软中断分布。采样和跟踪本身也会消耗资源，应控制采集范围，避免让已经繁忙的机器承受更多压力。

### 4.2 内存压力 {#内存压力}

内存排查要区分已经占用了多少，以及当前是否因回收或交换而等待。可以按下面的顺序收集证据：

1. 查看 `available`，并观察 `vmstat 1` 的 `si/so`。
2. 按进程核对驻留内存（RSS）、缓存和工作集的变化，工作集指程序当前运行需要使用的内存。
3. 查看 OOM 日志与 cgroup 内存事件。
4. 结合 GC、回收和 I/O 指标确认因果关系。

swap 已用量表示有页面驻留在交换空间，并不说明当前还在频繁交换；持续换入换出才是当前交换活动的证据。没有启用 swap，也可能发生内存压力。怀疑泄漏时，还要证明对象或内存持续保留，不能把内存占用高直接等同于泄漏。

### 4.3 低 CPU 与高延迟 {#低-cpu-与高延迟}

机器平均 CPU 低，不能排除 CPU 瓶颈。一个线程占满一核时，在多核机器上的平均使用率仍可能很低；容器用完配额时，也可能在宿主空闲的情况下等待。因此，先检查每核使用率和容器限流，再继续查其他等待。

接下来按请求的执行过程分解耗时。设备 `await` 上升时，关联进程 I/O 和资源受阻时间，后者可以用下一节的 PSI 查看。怀疑线程池、连接池或锁等待时，检查队列和线程栈；怀疑下游变慢时，用追踪记录和下游指标核对。

线程处于等待状态本身不代表故障。只有把堆栈与慢请求、队列增长联系起来，才能判断它是否挡住了请求。日志、指标和追踪的关联方法见[可观测性](../../system-design/production/logs-metrics-traces-correlation.mdx)。

## 5. PSI 与容器限流 {#psi-与容器限流}

**PSI**（Pressure Stall Information）记录任务因资源不足而受阻的时间。启用 PSI 的内核通过 `/proc/pressure/` 下的 `cpu`、`memory`、`io` 文件提供三类压力信息。`avg10`、`avg60`、`avg300` 分别表示 10、60、300 秒时间尺度上的受阻时间比例，`total` 是累计受阻时间，单位为微秒。

`some` 表示至少一个任务因该资源受阻的时间比例，`full` 表示所有非空闲任务同时受阻的时间比例。`full` 是 `some` 中更严重的部分：这段时间内，所有非空闲任务都在等待。系统级 CPU `full` 未定义，输出保持为零，所以 CPU 排查应重点结合 `some`、运行队列和配额。

**cgroup** 是内核对一组进程实施资源管理的机制，cgroup v2 还提供组级 `pressure` 文件。容器延迟升高时，除了看宿主指标，还要检查容器所在组及父组的资源限制。`cpu.stat` 中的限流计数持续增加，说明任务正在受 CPU 配额限制。具体机制见[容器原理](../containers/container-principles.mdx#cgroups)。

利用率说明资源有多忙，PSI 说明任务为资源等了多久。把两者与同一时段的请求延迟对照，才能判断资源压力是否影响了业务。

## 6. 面试题 {#面试题}

### 6.1 top 显示的 load average 三个数字是什么含义？怎样判断 CPU 处于高负载？负载高可能有哪些原因？ {#load-average}

**考察重点**

- 负载统计的是 R 和 D 状态的任务数，包含线程，不是 CPU 使用率。
- 与核数比较的判断方法；区分 CPU 忙和 I/O 等待。

**相关内容**：[load average 指标](#load-average-指标)、[常用工具与关键字段](#常用工具与关键字段)。

<details>
<summary>参考回答</summary>

**三个数对应 1、5、15 分钟时间尺度上的平均负载，统计 R 和 D 状态的任务数量，不是 CPU 使用率。**

R 包括正在运行和等待 CPU 的任务，D 是不可中断睡眠，统计中也包含线程。因为 D 不一定在消耗 CPU，所以高负载不能直接解释为 CPU 用满。

CPU 忙且 `r` 队列长时，检查计算与调度竞争；CPU 空闲但 D 状态任务多时，检查 I/O 和内核等待。与核数比较之外，还要核对单核热点、任务能在哪些 CPU 上运行，以及容器配额。

</details>

### 6.2 发现某台机器 CPU 使用率很高、系统很卡，你怎样排查？ {#high-cpu}

**考察重点**

- 从机器到进程、线程、代码的定位链路。
- 区分用户态与内核态；内存不足引起的交换与 OOM。

**相关内容**：[三类场景的排查路径](#三类场景的排查路径)、[CPU 使用率](../../basic-knowledge/java/jvm/cpu-high-diagnosis.mdx)。

<details>
<summary>参考回答</summary>

**先确认时间和范围，再定位进程、线程与热点。**

先对照流量和发布记录，用 `top` 找高占用进程，用 `mpstat` 看每核分布。再通过 `top -Hp <pid>` 或 `pidstat` 找到线程，最后用 `perf` 或语言工具定位代码。

`us` 高时重点查计算、序列化和 GC；`sy` 高时结合系统调用、上下文切换和中断分析。如果同时有内存压力，还要检查 `available`、换页速率及 OOM 记录。采集现场时控制工具开销，再根据业务影响选择恢复措施。

</details>

### 6.3 一台 Linux 服务器 CPU 占用不高，但接口访问很慢，你会怎样排查？ {#slow-but-idle}

**考察重点**

- 识别单核热点、配额与各种等待。
- `iostat` 与 `iotop` 的分工；按层次排除。

**相关内容**：[三类场景的排查路径](#三类场景的排查路径)、[常用工具与关键字段](#常用工具与关键字段)。

<details>
<summary>参考回答</summary>

**先排除平均值掩盖的单核热点和容器限流。**

确认没有这两类问题后，再按请求耗时检查 I/O、锁、线程池或连接池队列，以及下游调用。

用 `iostat` 看设备延迟和队列，用 `pidstat` 或 `iotop` 关联具体任务；内存方面，用 `vmstat` 的 `si/so` 判断当前交换活动，不能只凭 `free` 的容量数据下结论。线程栈要与慢请求和队列变化对应，追踪记录则用于定位慢依赖。

处理后，观察请求延迟是否恢复、队列是否回落，验证找到的等待是否确实影响了业务。

</details>

### 6.4 宿主 CPU 很空闲，容器为什么仍会慢？PSI 能补充什么证据？ {#psi-throttling}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：配额、局部热点与受阻时间。

**相关内容**：[PSI 与容器限流](#psi-与容器限流)。

<details>
<summary>参考回答</summary>

**容器仍会受到自身和父级 CPU 配额约束。**

配额用尽后，即使宿主还有空闲 CPU，任务也要等待后续周期。可以用 `cpu.stat` 检查限流计数，并核对是否存在单核热点。

PSI 补充的是任务因资源受阻的时间。把组级 PSI、限流计数和请求延迟放在同一时间范围内比较，有助于判断资源约束与业务变慢是否相关。

</details>
