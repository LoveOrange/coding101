# Linux 网络排查

网络问题的排查从“通不通”到“快不快”分层进行：域名能否解析、IP 能否到达、端口能否建立连接、应用是否正常响应。本文讲每一层用什么工具确认，连接状态怎样统计和解读，TIME_WAIT 和 CLOSE_WAIT 过多的原因，tcpdump 的常用写法，以及 iptables 的表与链。TCP 握手与挥手的原理见 [TCP 连接管理](../../basic-knowledge/network/tcp_handshake.mdx)。

## 1. 面试核心 {#core}

- 按层排查：`dig` 看解析，`ping`/`traceroute` 看三层可达，`nc -zv`/`telnet`/`curl` 看端口和应用。`ping` 通只说明 ICMP 可达，不代表业务端口通，防火墙可能只放行了 ICMP。[卡](#connectivity-check)
- `ss -lntp` 查看监听端口和对应进程，`ss -ant` 加 `awk`、`uniq -c` 统计各状态的连接数，`ss -s` 看汇总。`ss` 比 `netstat` 快，是现在的首选。[卡](#ports-connections)
- TIME_WAIT 出现在主动关闭的一方，持续 2MSL，过多通常是短连接太多，用连接复用（长连接、连接池）解决；CLOSE_WAIT 出现在被动关闭的一方，表示对方已关闭而本方程序没有调用 close，几乎总是程序的连接泄漏，要改代码。[卡](#time-wait-close-wait)
- tcpdump 抓包要指定网卡、过滤条件、不解析名称、写文件：`tcpdump -i eth0 -nn host 10.0.0.2 and port 8080 -w a.pcap`，再用 Wireshark 分析。[卡](#tcpdump)
- iptables 基于内核的 netfilter，在报文经过的五个挂载点（链）上按表（filter、nat、mangle、raw）执行规则；Kubernetes 的 Service 默认用 nat 表的 DNAT 把 Service IP 转换成 Pod IP。[卡](#iptables)

## 2. 分层确认连通性 {#layers}

| 层次 | 问题 | 工具 |
| --- | --- | --- |
| 解析 | 域名是否解析到正确的地址 | `dig example.com`、`dig +trace`、`cat /etc/resolv.conf` |
| 网络可达 | IP 能否到达、在哪一跳丢包 | `ping`（ICMP）、`traceroute`/`mtr`、`ip route` |
| 端口 | 能否建立 TCP 连接 | `nc -zv host 3389`、`telnet host port`、`curl -v telnet://host:port` |
| 应用 | 响应是否正确、各阶段耗时 | `curl -v`、`curl -w "%{time_connect} %{time_starttransfer} %{time_total}\n"` |
| 本机 | 服务是否在监听、防火墙是否放行 | `ss -lntp`、`iptables -L -n`、`firewall-cmd --list-all` |

**ping 的原理**：发送 ICMP Echo Request，目标回复 Echo Reply。输出中的 `icmp_seq` 是序号（不连续说明丢包），`ttl` 是剩余跳数（可以粗略判断经过几跳和对端系统），`time` 是往返时延，最后的统计给出丢包率和延迟的最小值、平均值、最大值、抖动。

ping 不通也不一定是网络故障：很多云主机和防火墙默认禁止 ICMP。反过来 ping 通、端口不通的常见原因有：服务没有监听（或只监听了 127.0.0.1）、主机防火墙或安全组没有放行该端口、中间设备拦截。

## 3. 端口与连接状态 {#connections}

```bash
ss -lntp                       # 监听中的 TCP 端口及进程（需要 root 才能看到其他用户的进程）
ss -lntp | grep 8080           # 哪个进程在监听 8080
lsof -i :8080                  # 同上，也能看到客户端连接
ss -s                          # 各类连接汇总
ss -ant | awk 'NR>1 {print $1}' | sort | uniq -c | sort -nr   # 按状态统计连接数
ss -ant state time-wait | wc -l
```

常见状态的含义：

| 状态 | 所在方 | 含义 |
| --- | --- | --- |
| LISTEN | 服务端 | 等待连接 |
| SYN-RECV | 服务端 | 收到 SYN，等待第三次握手；大量出现可能是 SYN 洪泛或半连接队列满 |
| ESTABLISHED | 双方 | 连接建立 |
| CLOSE-WAIT | 被动关闭方 | 对方已发 FIN，本方程序尚未关闭连接 |
| TIME-WAIT | 主动关闭方 | 等待 2MSL，确保对方收到最后的 ACK、旧报文过期 |

## 4. TIME_WAIT 与 CLOSE_WAIT 过多 {#wait-states}

**TIME_WAIT 过多**

- 原因：本机频繁主动关闭短连接。典型场景是 Nginx 作为反向代理，默认用 HTTP/1.0 短连接访问上游，每个请求都新建和关闭连接；或者客户端程序不复用连接。
- 影响：每个 TIME_WAIT 占用一个“本地 IP、本地端口、远端 IP、远端端口”组合。作为客户端频繁连接同一个目标时，可用的本地端口会被耗尽，新连接失败。服务端被动产生的 TIME_WAIT 主要占用少量内存，影响不大。
- 处理：首选复用连接，Nginx 配置 `upstream` 的 `keepalive`，并设置 `proxy_http_version 1.1` 和清空 `Connection` 头；应用使用连接池。其次调整内核参数：`net.ipv4.tcp_tw_reuse=1` 允许客户端发起新连接时复用 TIME_WAIT 端口，`net.ipv4.ip_local_port_range` 扩大本地端口范围。`tcp_tw_recycle` 在 NAT 环境下会丢弃正常连接，已在 Linux 4.12 中移除，不要使用。

**CLOSE_WAIT 过多**

- 原因：对方已经关闭，本方程序没有调用 `close`。常见于异常分支没有释放连接、连接池泄漏、线程阻塞在其他地方没有机会处理关闭。
- 处理：调参无效，要找到代码。用 `ss -antp state close-wait` 找到进程和对端地址，结合线程栈和代码检查连接的释放路径。

## 5. tcpdump {#tcpdump-usage}

```bash
tcpdump -i eth0 -nn host 10.0.0.2 and tcp port 8080 -w handshake.pcap
tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0' and port 443
tcpdump -i eth0 -nn -A port 80 -c 100          # 打印内容，只抓 100 个包
```

| 参数 | 作用 |
| --- | --- |
| `-i` | 指定网卡，`any` 表示全部 |
| `-nn` | 不解析主机名和端口名，避免 DNS 查询拖慢和干扰 |
| `host` / `port` / `src` / `dst` | 过滤条件，可以用 `and`、`or`、`not` 组合 |
| `-w` / `-r` | 写入和读取 pcap 文件，用 Wireshark 分析 |
| `-c` | 抓取指定数量后停止 |
| `-s 0` | 抓取完整报文（新版本默认） |

看握手时关注标志位 `[S]`、`[S.]`、`[.]`、`[F.]`、`[R]`，以及序列号、窗口大小和时间间隔。只有 SYN 没有 SYN+ACK，说明报文被丢弃或服务未监听；收到 RST 说明端口未监听或被主动拒绝；重传和较大的时间间隔说明链路丢包或对端处理慢。Pod 之间不通时，要在源和目标两端（以及节点网卡、隧道网卡上）分别抓包，确认报文在哪一段消失。

## 6. iptables {#iptables-chains}

iptables 是配置内核 netfilter 框架的工具。netfilter 在报文路径上提供五个挂载点（链）：

| 链 | 位置 |
| --- | --- |
| PREROUTING | 报文进入本机、路由判断之前 |
| INPUT | 发往本机进程 |
| FORWARD | 经本机转发 |
| OUTPUT | 本机进程发出 |
| POSTROUTING | 离开本机之前 |

规则按功能分在不同的表中：

| 表 | 用途 | 常见链 |
| --- | --- | --- |
| filter | 放行或拒绝（默认表） | INPUT、FORWARD、OUTPUT |
| nat | 地址转换：DNAT 改目的地址，SNAT/MASQUERADE 改源地址 | PREROUTING、OUTPUT、POSTROUTING |
| mangle | 修改报文标记、TTL 等 | 全部 |
| raw | 在连接跟踪之前处理，例如对某些流量关闭跟踪 | PREROUTING、OUTPUT |

iptables 主要工作在网络层，也能匹配传输层的端口和连接状态（依赖 conntrack 连接跟踪），所以常说它是三、四层的防火墙。

在 Kubernetes 中，kube-proxy 的 iptables 模式在 nat 表中为每个 Service 生成规则，访问 Service IP 时通过 DNAT 随机转发到某个 Pod；规则数量随 Service 增多线性增长，大集群改用 IPVS 模式或基于 eBPF 的方案。

**考察重点**

- 两个状态分别出现在主动关闭和被动关闭的一方。
- TIME_WAIT 用连接复用解决，CLOSE_WAIT 要修代码；`tcp_tw_recycle` 的风险。

<details>
<summary>参考回答</summary>

TIME_WAIT 是主动关闭方发出最后一个 ACK 后进入的状态，持续 2MSL（Linux 上固定 60 秒）。它有两个作用：如果最后的 ACK 丢失，对方会重发 FIN，本方还能重新确认；等待网络中这个连接的旧报文过期，避免被相同四元组的新连接误收。CLOSE_WAIT 是被动关闭方收到对方 FIN 之后、本方调用 close 之前的状态。

TIME_WAIT 过多说明本机频繁主动关闭短连接，例如 Nginx 默认用短连接访问上游，每个请求都关闭一次。作为客户端时，大量 TIME_WAIT 会占满本地端口，导致新连接失败。处理首选复用连接：Nginx 的 upstream 配置 keepalive，同时设置 `proxy_http_version 1.1` 并清空 Connection 头；应用使用连接池。辅助手段是开启 `tcp_tw_reuse`、扩大本地端口范围。`tcp_tw_recycle` 在 NAT 后会丢弃正常连接，新内核已经移除。

CLOSE_WAIT 过多几乎都是程序问题：对方关了，本方没有 close，常见于异常分支未释放连接或连接池泄漏。调内核参数没有用，要用 `ss -antp state close-wait` 找到进程和对端，结合代码检查释放逻辑。

</details>

iptables 是配置内核 netfilter 的用户态工具。netfilter 在报文经过的路径上设置了五个挂载点：PREROUTING（进入后路由前）、INPUT（发往本机）、FORWARD（转发）、OUTPUT（本机发出）、POSTROUTING（离开前）。规则按功能放在不同的表里：filter 负责放行和拒绝，nat 负责地址转换（DNAT 改目的地址、SNAT 和 MASQUERADE 改源地址），mangle 修改报文标记，raw 在连接跟踪之前处理。报文到达某条链时，依次执行各表中的规则，匹配后执行 ACCEPT、DROP、DNAT 等动作。

它主要工作在网络层，同时可以匹配端口和连接状态，所以通常说是三、四层防火墙。作为主机防火墙时关注：默认策略、按来源地址和端口放行、放行已建立连接的回包、规则的顺序。

Kubernetes 的 kube-proxy 在 iptables 模式下，为每个 Service 在 nat 表中生成规则，访问 Service 的 ClusterIP 时通过 DNAT 随机改写为某个 Pod 的 IP。规则是线性匹配的，Service 很多时性能下降，所以大集群使用 IPVS 模式，它用哈希表做四层负载均衡。路由表决定报文从哪个接口发往下一跳，与 iptables 的过滤和改写是不同的环节。
