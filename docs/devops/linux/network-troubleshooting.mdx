# Linux 网络排查

Linux 网络排查按解析、连接和应用响应逐层定位。本文负责命令、抓包证据与 netfilter 路径。TCP 状态原理见 [TCP 连接](../../basic-knowledge/network/tcp_handshake.mdx)。代理配置见 [Nginx 与负载均衡](../traffic/nginx-load-balancing.mdx)。

## 1. 面试核心 {#core}

- ping 检查 ICMP 回显，业务端口仍需独立验证。[卡](#connectivity-check)
- `ss -lntp` 查看 TCP 监听，`ss -Hant` 输出无表头连接列表。[卡](#ports-connections)
- TIME_WAIT 保留关闭状态，CLOSE_WAIT 等待本地应用关闭。[卡](#time-wait-close-wait)
- tcpdump 的双端抓包可缩小报文丢失范围。[卡](#tcpdump)
- conntrack 保存连接状态与 NAT 映射，路由表选择下一跳。[卡](#iptables)

## 2. 分层确认连通性 {#分层确认连通性}

| 层次 | 命令与证据 |
| --- | --- |
| DNS | `dig example.com`、`dig @解析器 example.com` |
| 路由 | `ip route get 目标IP` 查看出口与源地址 |
| 三层路径 | `ping`、`traceroute`、`mtr` |
| TCP 端口 | `nc -zv host 443` |
| TLS 与 HTTP | `curl -v https://example.com` |
| 本机监听 | `ss -lntp` 查看地址、端口与进程 |
| 防火墙 | 按实际后端检查 iptables 或 nftables 规则 |

ping 发送 Echo Request，并等待 Echo Reply。`time` 是往返时间，`ttl` 是响应包的剩余跳数。初始 TTL 未知时，无法精确推算路径跳数。

序号缺口需结合最终统计判断。抓取时尚未返回的响应也会形成暂时缺口。ICMP 被过滤时，业务 TCP 连接仍能正常工作。

TCP 连接还依赖监听地址、端口及路径策略。只监听 127.0.0.1 的服务只能接受本机回环访问。排查应按实际源地址与目的地址验证。

## 3. 端口与连接状态 {#端口与连接状态}

```bash
ss -lntp 'sport = :8080'
lsof -nP -iTCP:8080 -sTCP:LISTEN
ss -s
ss -Hant | awk '{print $1}' | sort | uniq -c | sort -nr
ss -Hant state time-wait | wc -l
```

精确端口过滤避免把 18080 等端口混入。`-H` 去掉表头，计数时只统计连接。查看其他用户的进程信息需要相应权限。

| 状态 | 排查方向 |
| --- | --- |
| LISTEN | 地址、端口与监听队列 |
| SYN-RECV | 握手未完成、丢包与 SYN 请求压力 |
| ESTABLISHED | 活跃连接及收发队列 |
| CLOSE-WAIT | 本地关闭路径与阻塞线程 |
| TIME-WAIT | 短连接速率、端口与内存压力 |

## 4. TIME_WAIT 与 CLOSE_WAIT 诊断 {#time_wait-与-close_wait-过多}

TIME_WAIT 的协议作用和复用条件见 [TCP 连接](../../basic-knowledge/network/tcp_handshake.mdx#time_wait-的资源压力与连接复用)。本篇只处理现场定位。

先确认主动关闭端、目标分布和连接创建速率。短连接多时，检查客户端连接池及代理上游复用。端口不足需结合临时端口范围和目标四元组判断。

Nginx 1.29.7 前默认代理 HTTP/1.0。1.29.7 起默认使用 HTTP/1.1。是否复用仍取决于 keepalive、请求头和对端行为。配置方式见 [Nginx 与负载均衡](../traffic/nginx-load-balancing.mdx#nginx-的结构与常用配置)。

持续 CLOSE_WAIT 表示本地发送方向尚未关闭。先用 `ss -antp state close-wait` 定位进程和对端。再检查异常分支、流关闭逻辑与线程栈。应用有意半关闭时，也需核对其业务期限。

## 5. tcpdump 抓包 {#tcpdump-抓包}

```bash
tcpdump -i eth0 -nn 'host 10.0.0.2 and tcp port 8080' -c 1000 -w a.pcap
tcpdump -i any -nn 'tcp port 443 and (tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0)'
tcpdump -nn -r a.pcap
```

`-i` 指定接口，`-nn` 关闭名称解析。`-c` 限制数量，`-w` 保存原始包。`-r` 读取已有文件。`-s` 控制截取长度，`-s 0` 使用工具支持的最大默认长度。

| 现象 | 证据边界 |
| --- | --- |
| 只有 SYN | 尚未看到应答，需继续查目标与回程 |
| 收到 RST | 对端或中间设备主动拒绝或复位 |
| SYN 重传 | 发送方等待确认，需区分去程与回程丢失 |
| 接收窗口趋近零 | 接收端提供的缓冲空间不足 |

单端抓包无法确认包在哪里丢失。双端对比能区分请求未达和响应未返。时间间隔还会受处理延迟、抓包丢失与卸载影响。应结合序列号、重传和工具丢包统计。

## 6. iptables 规则 {#iptables-规则}

iptables 配置 netfilter 规则。内核在网络路径中提供多个 hook。

| 内建链 | 主要路径位置 |
| --- | --- |
| PREROUTING | 入站后的路由判断前 |
| INPUT | 送往本机进程 |
| FORWARD | 经本机转发 |
| OUTPUT | 本机进程发包 |
| POSTROUTING | 出站前 |

| 表 | 作用 |
| --- | --- |
| filter | 过滤与放行 |
| nat | DNAT、SNAT 和 MASQUERADE |
| mangle | 修改标记、TTL 等字段 |
| raw | 在连接跟踪前处理 |
| security | 强制访问控制相关规则 |

同一 hook 的表按内核优先级执行。每条链内再按规则顺序匹配。`ACCEPT` 结束当前相关过滤处理。后续 hook 仍可丢弃报文。

NAT 规则主要为连接首包建立映射。后续包按 conntrack 保存的映射转换。修改 NAT 规则后，已有连接仍会使用旧映射。

kube-proxy 的 iptables 模式用 DNAT 选择后端。其他代理模式的数据路径不同。IPVS 模式自 Kubernetes 1.35 起弃用。模式选择和集群网络见 [工作负载、Service 与集群网络](../kubernetes/workloads-networking.mdx#集群网络)。

## 7. DNS、TLS 与 HTTP 耗时 {#dns-tls-与-http-耗时}

curl 的 time 字段多为从请求开始累计的时间。

```bash
curl -sS -o /dev/null --connect-timeout 3 --max-time 10 \
  -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}\n' \
  https://example.com/
curl --resolve example.com:443:192.0.2.10 https://example.com/
```

一次新的直连 HTTPS 请求可用相邻时间差定位阶段。TCP 时间用 time_connect 减 time_namelookup。TLS 时间用 time_appconnect 减 time_connect。首字节时间还包含请求传输与服务端处理。

重定向、代理和连接复用会改变解释方式。排查时应先固定访问路径。

`--resolve` 指定连接地址，并保留域名语义。HTTP Host、TLS SNI 与证书校验仍使用原域名。仅访问 IP 再修改 Host，会遗漏 TLS 名称差异。
