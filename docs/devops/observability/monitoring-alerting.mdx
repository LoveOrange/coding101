# 监控与告警

**监控**通过采集和分析指标了解系统状态，**告警**则在需要处理问题时通知负责人。设计时要同时回答两件事：这些指标能否反映用户遇到的问题，收到通知的人能否据此采取行动。Prometheus 的采集、聚合和告警规则，都要围绕这两个问题来设计。

## 1. 面试核心 {#core}

- **Prometheus 采集指标并计算规则，Alertmanager 组织和发送通知**，采集失败与通知失败要分别排查。[卡](#prometheus-architecture)
- **指标名称与完整标签集共同标识一条时间序列**，标签取值过多会增加存储和查询成本。
- 服务指标围绕**延迟、流量、错误和饱和度**组织，再结合资源指标解释原因。[卡](#what-to-monitor)
- **`for` 控制条件持续多久才触发，分组和抑制减少重复通知**。它们处理的是告警流程中的不同问题。[卡](#alert-design)
- Counter 要**先按序列计算速率，再跨实例求和**；整体分位数要合并分布后计算，不能平均各实例的 P99。[卡](#histogram-aggregation)

## 2. Prometheus 的组成 {#prometheus-的组成}

Prometheus 主要通过主动抓取获取指标：应用或 Exporter 暴露数据，Server 定期读取、存储并计算规则，触发的告警再交给 Alertmanager 处理。各组件的分工如下：

| 组件 | 分工 |
| --- | --- |
| Prometheus Server | 发现目标、抓取、存储、查询和计算规则 |
| 应用客户端库 | 在应用内记录并暴露指标 |
| Exporter | 将系统状态转换成可抓取指标 |
| Pushgateway | 为特定批处理任务保留推送指标 |
| Alertmanager | 分组、去重、抑制、静默和路由 |
| Grafana | 展示查询和看板 |
| 远程存储 | 支持长期保存或跨集群查询 |

**服务发现**负责提供需要抓取的目标，relabel 规则再筛选目标、改写标签。默认抓取路径是 `/metrics`，也可以按目标调整。Kubernetes 中可以发现 Pod、Service 和 EndpointSlice；使用 Prometheus Operator 时，可以通过 ServiceMonitor、PodMonitor 声明抓取配置。

`up == 0` 表示某个仍在发现结果中的目标抓取失败。如果目标已经从发现结果消失，原来的 `up` 序列也会消失，而不是一直保留一个 0。因此，只监控 `up == 0` 会漏掉目标缺失，还需要检查指标是否缺失，或核对实际目标数是否符合预期。

### 2.1 指标类型 {#指标类型}

指标类型要与记录的对象匹配。累计请求数、当前连接数和请求延迟分布表达的是不同信息：

| 类型 | 含义与用途 |
| --- | --- |
| Counter | 累计事件数，例如请求总数，可在重启时重置 |
| Gauge | 可升可降的当前值，例如当前连接数 |
| Histogram | 保存观测值的分布，可合并分布后计算分位数 |
| Summary | 提供观测值总和、数量，以及配置的预先计算分位数 |

**时间序列**是同一指标在不同时刻的采样值，由指标名称和完整标签集共同标识。每增加一种标签组合，就会形成独立序列。用户 ID、完整 URL 等标签有大量不同取值，这就是高基数，会扩大存储和查询成本。HTTP 路径可用 `/users/:id` 这样的模板值，把同一类接口聚合起来。

Zabbix 提供主机模板以及多种主动、被动采集方式；Prometheus 则用标签和查询语言 PromQL 组织时序分析。选择时要结合采集对象、服务发现方式和维护成本，判断哪一种更适合现有环境。

### 2.2 Pushgateway 与监控高可用 {#pushgateway-与监控高可用}

Pushgateway 适合服务级、短生命周期的批处理任务：任务可能在下一次抓取前就结束，因此先把指标推送到 Pushgateway，由它保留并供 Prometheus 抓取。数据会一直保留到显式删除，所以任务停止后，旧的成功指标仍可能被反复抓取。设计时既要记录任务完成时间，也要安排旧序列清理。

长期运行的服务可以直接暴露抓取端点。为了避免单个监控实例故障造成中断，多个 Prometheus 可以独立抓取同一目标，Alertmanager 集群协作去重通知。查询侧仍要处理重复采集的序列，具体做法取决于远程存储方案。

监控系统本身也需要检测。可以让外部心跳接收端检查通知是否按时到达，从而验证规则计算、通知发送和接收是否仍在工作。接收端要独立于被监控系统，否则两者同时故障时，检测也会失效。

## 3. 服务与资源指标 {#监控哪些指标}

服务指标先回答请求量有多大、请求是否变慢或失败，以及是否发生积压。这四类信息称为**黄金信号**：延迟、流量、错误和饱和度。其中，饱和度反映资源是否已经紧张到让工作排队等待。

延迟可以用分位数描述：P50 表示一半请求的耗时不超过这个值，P99 则表示 99% 的请求耗时不超过这个值。两者放在一起，可以区分整体变慢和少量请求特别慢。

| 黄金信号 | 示例 |
| --- | --- |
| 延迟 | 成功与失败请求分别统计 P50、P99 |
| 流量 | QPS、并发连接、新连接速率 |
| 错误 | 5xx、业务失败、超时比例 |
| 饱和度 | 队列积压、池等待、资源压力 |

**USE 方法**按使用率（Utilization）、饱和度（Saturation）和错误（Errors）检查每类资源。比如，CPU 使用率之外还要看运行队列和限流；内存要结合资源受阻时间 PSI、回收和内存不足导致的 OOM；磁盘则检查空间、inode、I/O 延迟和设备错误。

对代理服务，还要分别观察各上游的延迟和失败，避免总体指标掩盖某个后端的问题。TLS 证书期限、文件描述符和连接数也会影响接入。业务层补充交易成功率，用户侧通过外部拨测实际发起请求，确认用户能否完成操作。

## 4. 告警设计 {#告警设计}

需要立即响应的告警，应对应用户影响或明确风险，并写清负责人、影响范围和处置入口。资源指标不一定都要触发紧急通知：尚未影响用户、留有处理时间的容量问题，可以进入工单或容量规划。

| 机制 | 作用 |
| --- | --- |
| `for: 5m` | 条件持续成立 5 分钟后进入 firing 状态 |
| `keep_firing_for` | 条件消失后继续保留 firing 状态一段时间 |
| 分组 | 合并同服务或同事故的通知 |
| 抑制 | 已有上层故障时，抑制关联衍生告警 |
| 静默 | 按匹配器和时间窗口暂停通知 |
| 路由 | 根据标签选择接收人和通知渠道 |

配置了 `for` 的规则，在条件首次成立时进入 **pending**，也就是等待确认的状态；条件持续满足指定时间后，才进入 **firing**，表示告警已经触发。Alertmanager 收到告警后，`group_wait` 控制首批通知的聚合等待时间，`repeat_interval` 控制后续重复通知的间隔。`for` 决定何时触发，后两个参数决定怎样通知，不能互相替代。

**迟滞**是给告警设置不同的触发条件和恢复条件，避免指标在同一个阈值附近来回波动时反复告警。单独设置 `for` 只要求条件持续一段时间，没有提供双阈值；`keep_firing_for` 延迟恢复，也不等于双阈值迟滞。

按服务质量目标（SLO）设置错误预算消耗告警时，可以组合长短窗口，具体见 [SRE 的职责与工作方式](../incidents/sre-practice.mdx#错误预算策略与消耗速率)。磁盘增长趋势可以用 `predict_linear` 预测。无论采用哪种规则，流量很低或数据缺失时，都要检查计算结果是否仍有意义。

严重告警还需要值班人员确认，超时未处理则升级给其他负责人。这可以由外部值班系统实现，Alertmanager 的通知路由本身不提供人工确认流程。

## 5. 分位数聚合与速率 {#分位数聚合与速率}

多个实例的整体分位数，要先合并延迟分布，再计算分位数。单个实例的 P99 已经把分布压缩成一个值，直接平均这些值无法还原所有请求的 P99。

经典 Histogram 用一组累计桶记录分布，每个桶统计不超过其上界的观测值数量，`le` 标签保存这个上界。下面的查询先合并同一 `job` 下各实例的桶，再计算整体 P99：

```promql
histogram_quantile(
  0.99,
  sum by (job, le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
```

`rate` 先分别计算每条序列的增长速率，处理实例重启带来的计数重置；`sum by (job, le)` 再合并同一服务、相同边界的桶，最后由 `histogram_quantile` 计算 P99。参与合并的经典 Histogram 应使用一致的桶边界，才能把所有实例按同一标准统计的数量相加。

Summary 已经在实例内计算出的分位数，不能直接相加或平均成整体分位数。不过，它的 `sum` 和 `count` 分别保留观测值总和与数量，仍可以跨实例聚合后计算均值。

跨实例计算错误率，也要保留请求量的权重。用错误总速率除以请求总速率：

```promql
sum by (job) (rate(http_requests_total{status=~"5.."}[5m]))
/
sum by (job) (rate(http_requests_total[5m]))
```

这个计算按各实例的请求量加权。直接平均实例错误率，会把请求很少的实例与请求很多的实例看成同样重要，从而偏离用户实际遇到的错误比例。

实际规则还要处理零请求和错误序列尚未初始化的情况，避免把无数据误当成正常。`absent_over_time` 可以检查一段时间内是否缺少数据；对于动态服务，还需要独立维护预期目标信息，才能判断哪些目标本来应该存在。

## 6. 面试题 {#面试题}

### 6.1 Prometheus 的架构是怎样的？它怎样发现和抓取目标？与 Zabbix 有什么区别？ {#prometheus-architecture}

**考察重点**

- Server、Exporter、Pushgateway、Alertmanager 的分工和拉取模型。
- 服务发现与 relabel；指标类型；与 Zabbix 的定位差异。

**相关内容**：[Prometheus 的组成](#prometheus-的组成)。

<details>
<summary>参考回答</summary>

**Prometheus Server 发现并抓取目标，存储时序并计算规则。**

指标由应用客户端库或 Exporter 暴露，服务发现提供目标，relabel 规则筛选目标并改写标签。使用 Operator 时，可以通过 ServiceMonitor 或 PodMonitor 描述采集配置。特定的短生命周期批处理任务可以借助 Pushgateway 保留指标。

Prometheus 负责计算告警条件，Alertmanager 负责分组、去重、静默、抑制和通知。目标仍被发现但抓取失败时，`up` 为 0；目标消失还需要额外检测。

Zabbix 提供主机模板及主动、被动采集，Prometheus 通过标签和 PromQL 组织时序分析。选择取决于采集对象、服务发现、查询和维护需求。

</details>

### 6.2 如果要监控一个生产环境的服务（例如一台代理服务器），你会监控哪些指标？ {#what-to-monitor}

**考察重点**

- 用黄金信号、USE 方法组织指标，而不是罗列。
- 分层覆盖：资源、中间件、应用、业务、用户侧。

**相关内容**：[服务与资源指标](#监控哪些指标)。

<details>
<summary>参考回答</summary>

**服务应覆盖延迟、流量、错误和饱和度。**

先用这四类黄金信号确认请求质量，再用 USE 方法检查 CPU、内存、磁盘和网络的使用率、饱和度及错误，寻找原因。

代理服务要分别看各上游的延迟和失败，以及连接数、新建连接速率、文件描述符和证书期限。业务成功率与外部拨测则用于确认用户能否完成操作。

看板帮助定位原因，紧急告警触发明确处置。因此每条告警都要能对应影响、负责人和处理入口。

</details>

### 6.3 告警怎样设置才合理？一个指标在阈值附近反复触发、一天告警几百次，怎样降下来？告警怎样收敛和升级？ {#alert-design}

**考察重点**

- 告警关联用户影响，并给出可执行动作。
- 持续时间、迟滞、平滑、分组、抑制等降噪手段；分级与升级；告警系统自身的可用性。

**相关内容**：[告警设计](#告警设计)。

<details>
<summary>参考回答</summary>

**告警应对应用户影响或需要处理的容量风险。**

阈值结合 SLO、正常基线和处置时限设定。瞬时尖峰可以用 `for` 过滤，短暂恢复后又触发的抖动可以用 `keep_firing_for` 缓解；需要不同的进入、退出阈值时，要设计迟滞逻辑，`for` 本身无法实现。

通知侧按标签分组，把同一事故的相关告警合并；已有上层故障时，抑制关联衍生告警；计划维护则用静默。值班确认和超时升级交给外部值班系统，另用独立的外部心跳检测规则到通知的完整链路。

</details>

### 6.4 多个实例的 P99 能直接平均吗？错误率怎样跨实例聚合？ {#histogram-aggregation}

**考察重点**：分布合并、计数重置与流量加权。

**相关内容**：[分位数聚合与速率](#分位数聚合与速率)。

<details>
<summary>参考回答</summary>

**整体 P99 要从聚合后的 Histogram 计算，错误率要用错误总速率除以请求总速率。**

直接平均各实例 P99 会丢失请求数量和延迟分布信息。

经典 Histogram 先按序列计算 `rate`，再按 `job` 和 `le` 求和，最后用 `histogram_quantile` 计算分位数。Summary 的分位数无法这样合并，但 `sum` 和 `count` 可以聚合。

</details>

### 6.5 目标消失为什么不一定触发 up==0？Pushgateway 有什么生命周期问题？ {#missing-metrics-pushgateway}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：目标缺失、旧序列与独立检测。

**相关内容**：[Prometheus 的组成](#prometheus-的组成)、[Pushgateway 与监控高可用](#pushgateway-与监控高可用)。

<details>
<summary>参考回答</summary>

**`up == 0` 检测仍被发现但抓取失败的目标；目标消失后，序列也会消失。Pushgateway 则相反，会保留已经推送的旧指标。**

检测目标缺失，需要结合 `absent_over_time` 和预期目标信息。Pushgateway 中的旧成功指标会一直保留到显式删除，即使任务已经停止，也可能继续被抓取。因此要检查任务完成时间，并设计旧序列的清理方式。

</details>
