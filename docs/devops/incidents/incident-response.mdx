# 故障响应与排查

**故障响应**是在服务异常时组织排查、缓解和恢复，尽量缩短业务受损时间。处置时需要同时回答两个问题：现在怎样减少用户损失，以及哪些证据能解释故障。前者决定是否回滚、切流或降级，后者决定下一步查哪里；完整根因没有查清，也可以先采取有依据、可回退的恢复措施。

## 1. 面试核心 {#core}

- 响应需要**统一决策和共享记录**。事故负责人维护处置计划，执行人记录动作与结果，沟通人同步影响和进展。[卡](#incident-process)
- 止血先减少业务损失，根因修复再消除故障条件。**恢复动作不必等待完整根因结论**，但要明确适用条件、风险和撤回办法。[卡](#incident-process)
- 按地区、版本、入口等维度**确定受影响用户的共同特征**，再沿请求路径对照健康请求，缩小排查范围。[卡](#user-reported-slowness)
- **错误率下降不足以证明恢复**，还要核对请求量、业务成功率、延迟、积压和数据完整性。[卡](#recovery-validation)
- 复盘把影响、时间线和因果链转成**有负责人和验收条件的改进项**，后续还要验证效果。[卡](#postmortem)

## 2. 处置流程 {#处置流程}

处置从确认业务影响开始，再决定投入哪些人、采取什么动作。下面的阶段描述每一步需要得到的结果；止血和证据采集可以并行，不必等一项全部完成才开始下一项。

| 阶段 | 产出 |
| --- | --- |
| 确认 | 告警与业务探测相互印证 |
| 定级 | 受损功能、用户范围与损失估计 |
| 组织 | 事故负责人、执行人、沟通人和记录入口 |
| 止血 | 明确动作、预期收益、风险及撤回条件 |
| 定位 | 支持或排除假设的日志、指标和变更记录 |
| 修复 | 根因对应的修复与验证结果 |
| 恢复验证 | 核心功能、请求指标、积压和数据状态达到恢复标准 |
| 复盘 | 有负责人、截止时间和验收条件的改进项 |

事故负责人维护统一的处置计划，执行人把动作和结果写入共享记录，沟通人按约定节奏同步影响与进展。这样可以避免有人正在验证新配置，另一人却同时回滚，导致结果无法解释。交接时也要说明当前影响、已经做过的动作，以及仍待验证的假设。

最近的发布和配置变更是优先核对的线索，但发生时间接近还不足以认定因果关系。还要检查故障是否集中在变更覆盖的实例，以及变更能否解释异常机制。如果对不上，就继续检查容量、依赖和硬件等线索。

### 2.1 止血措施 {#止血措施}

**止血**是先减少当前故障造成的业务损失。选择措施时，要判断它能缓解什么问题，以及是否会把故障扩大到其他地方。

- 回滚适合新版本或新配置触发的故障，但要先确认旧版本仍兼容当前的数据格式和数据库结构。
- 切流把请求转向健康实例或机房，前提是接收端有足够容量，并满足数据一致性要求。
- 扩容用于增加处理能力；扩容完成前，可以通过限流保护核心请求，避免积压继续增长。
- 降级关闭非核心功能或对非核心依赖的调用，也可以返回业务允许的替代结果。
- 隔离用于摘除异常节点，并暂停仍在扩大影响的任务。

证据采集要考虑耗时和额外负载。关键日志、线程栈和变更记录可以与止血并行收集；堆转储等高成本操作则应先评估对故障实例的影响。如果已经有足够依据采取恢复动作，不需要为了凑齐所有材料而继续让用户等待。

## 3. 请求路径与影响范围 {#从用户反馈定位问题}

跨服务排查先确定影响范围，再沿受影响请求走过的路径寻找证据。收到“搜索打不开”这样的反馈时，先把它补充成三个可检查的问题：

1. 哪些用户受影响，是否集中于地区或版本。
2. 故障何时开始，与哪些变更同时发生。
3. 哪个功能异常，其他功能是否正常。

| 环节 | 核对证据 |
| --- | --- |
| 客户端 | 版本分布、DNS 与建连耗时、客户端错误 |
| DNS | 受影响地区的解析结果与缓存 TTL |
| CDN | 节点错误、回源状态与证书有效期 |
| 网关 | 状态码、上游地址、连接池与限流记录 |
| 应用 | 请求追踪、线程池、GC 和发布版本 |
| 依赖 | 数据库查询、缓存命中率、外部调用耗时 |

用同一个请求标识关联各段日志和追踪，才能判断延迟出现在哪一段。如果只有某个地区异常，可以对比故障地区与健康地区的拨测结果，检查解析和接入路径是否不同。如果只有部分用户异常，则按实例、分片和灰度批次对照，寻找这些请求共有的路由或版本。具体网络命令与抓包方法见 [Linux 网络排查](../linux/network-troubleshooting.mdx)。

## 4. 恢复验证与回切 {#恢复验证与回切}

服务恢复需要同时确认用户能完成操作，以及系统有能力继续承接请求。错误率下降时，要一起看请求量：如果受影响用户已经放弃访问，剩下的请求错误率可能很低，但原来的问题并没有解决。

因此，恢复验证既要实际探测下单等核心流程，也要看真实请求的成功率和延迟。队列积压、重试量和连接池占用应回到可控范围，否则积压释放后仍可能再次过载。有状态服务还要核对是否存在重复处理、记录丢失或副本延迟。

准备把流量切回原来的实例或机房时，先确认目标端的容量和数据可用性，再从少量流量开始，观察稳定后逐步扩大。每一步都要预先约定停止条件和撤回方案，避免一次性回切又触发同样的故障。

服务恢复和事故关闭也要分开记录。前者表示预先约定的业务指标已经满足，后者还要求后续修复、证据保存和交接责任都已明确。临时降级能让服务恢复，并不代表根因修复已经完成。

## 5. 复盘 {#复盘}

**复盘**是用故障证据还原事情怎样发生，并决定怎样降低再次发生的概率或影响。文档需要让没有参与处置的人也能理解以下内容：

1. 概要说明故障内容与持续时间。
2. 影响记录用户、请求、业务功能及数据损失。
3. 时间线区分触发、发现、响应、缓解和恢复。
4. 因果链区分触发条件、直接原因与防护缺口。
5. 处置评估记录有效动作、失败尝试和沟通问题。
6. 改进项明确负责人、优先级、截止时间和验收方法。

尚无足够证据支持的原因应标为待验证假设，不能为了写出一个根因而把猜测写成事实。**无责复盘**关注参与者当时掌握的信息、使用的工具和受到的系统约束，目的是解释为什么会做出那个选择；改进项仍然需要明确责任人。例如，“完善回滚”要落实为可演练的流程，并用恢复时间验收。更深入的复盘协作见 [事故复盘](../../system-design/leadership/incident-review-failed-designs-organizational-learning.mdx)。

## 6. 面试题 {#面试题}

### 6.1 一个高优先级的线上故障发生了，你的处置流程是什么？如果一个机房整体故障了怎么办？ {#incident-process}

**考察重点**

- 止血优先于根因；先查最近的变更。
- 定级、角色分工与沟通；机房故障的切流前提。

**相关内容**：[处置流程](#处置流程)、[灾难恢复](../../system-design/availability/high-availability-backup-rto-rpo.mdx)。

<details>
<summary>参考回答</summary>

**先确认影响并组织响应，再执行可回退的止血动作。**

先确定受损功能和用户范围，完成故障定级，再由事故负责人统一处置计划、沟通人定时同步，执行人记录动作、时间和结果。

优先核对最近的变更及其影响范围。回滚前验证数据兼容性，切流前验证容量和数据状态，再根据瓶颈选择扩容、限流或降级。证据采集与止血并行，避免高成本采集拖延恢复。

如果有 A、B、C 三个机房，B 整体故障，先确认 A、C 的剩余容量，再按预案分批接收 B 的流量。有状态服务还要确认副本进度和切主条件。恢复后核对业务指标、积压和数据完整性，继续跟进根因修复与复盘。

</details>

### 6.2 用户反馈某个功能很慢或打不开（例如某个地区搜索出了问题），你怎样从客户端到服务端定位？ {#user-reported-slowness}

**考察重点**

- 先确定影响范围、开始时间和功能，找出受影响用户的共同特征。
- 沿 DNS、CDN、接入层、应用、依赖逐段排查，每段说出检查方法。

**相关内容**：[请求路径与影响范围](#从用户反馈定位问题)、[Linux 网络排查](../linux/network-troubleshooting.mdx)。

<details>
<summary>参考回答</summary>

**先按地区、版本、功能和时间缩小范围。**

通过拨测和真实请求确认用户症状，把受影响用户与正常用户做对照，找出地区、接入点、实例或分片上的共同特征。

沿客户端、DNS、CDN、网关、应用和依赖逐段检查。客户端看解析、建连、TLS 和首包耗时，入口看解析结果、证书、状态码与上游地址。应用和依赖则用请求标识关联日志及追踪。

局部地区异常时优先比较接入路径，实例或分片异常时优先核对用户路由。找到可用的替代路径后，在容量允许的前提下切流，验证恢复效果，再继续修复原路径。

</details>

### 6.3 故障复盘应该包含哪些内容？怎样验证复盘改进的效果？ {#postmortem}

**考察重点**

- 复盘文档的结构：影响、时间线、根因、防线为什么失效、改进项。
- 改进项可跟踪；无责文化；按预防、发现、恢复、减小影响分类。

**相关内容**：[复盘](#复盘)、[事故复盘](../../system-design/leadership/incident-review-failed-designs-organizational-learning.mdx#release-incident-review)。

<details>
<summary>参考回答</summary>

**复盘应记录影响、时间线、因果链和可验收的改进项。**

因果链要说明什么触发了故障、它怎样造成业务损失，以及哪些防护没有起作用；尚未确认的原因标为待验证假设。

改进项可以分别针对预防故障、提前发现、加快恢复和缩小影响范围，每项写明负责人、截止时间和验收条件。例如，回滚改进要通过演练验证恢复时间。无责复盘如实记录当时的信息与约束，让改进落到系统和流程上。

</details>

### 6.4 错误率恢复正常后，怎样判断故障已经恢复？ {#recovery-validation}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：流量分母、积压、数据完整性和回切。

**相关内容**：[恢复验证与回切](#恢复验证与回切)。

<details>
<summary>参考回答</summary>

**还要核对请求量、核心交易、延迟与积压。**

受影响请求减少也可能使错误率下降，所以还要验证核心交易能够完成，延迟与积压回到可控范围。有状态故障需检查数据丢失和重复处理。在约定观察窗口内保持稳定后，再逐步回切；事故关闭前还要明确后续修复和交接责任。

</details>
