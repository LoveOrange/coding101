# SRE 的职责与工作方式

**SRE（站点可靠性工程）**用软件工程方法管理服务可靠性。它先明确用户需要怎样的服务，再用指标、自动化和故障复盘后的改进达到目标。准备这类岗位，需要能说明可靠性目标怎样影响发布决策，以及怎样把重复的人工操作变成持续有效的工程改进。

## 1. 面试核心 {#core}

- SRE 用 SLO 量化可靠性目标，再据此安排运行和工程工作，**把用户体验与工程投入联系起来**。[卡](#what-is-sre)
- toil 是重复、可自动化且缺少长期收益的运维工作。减少它，是为了**给持续改进留出时间**。
- 错误预算表示给定统计窗口内**可以接受的失败额度**，按请求数还是按时间计算，取决于 SLO 的口径。[卡](#error-budget-policy)
- burn rate 是**实际错误比例与允许错误比例的比值**，用来判断当前故障消耗预算有多快。[卡](#error-budget-policy)
- 混沌实验通过受控故障**检验预先提出的可靠性假设**，要限定影响范围，并验证停止和恢复流程。[卡](#chaos-engineering)

## 2. SRE 的核心实践 {#sre-的核心实践}

SRE 先定义可靠性目标，再决定监控什么、何时响应，以及优先改善哪里。这里有三个需要区分的概念：

- **SLI（服务等级指标）**是对服务表现的测量，例如请求成功率。
- **SLO（服务等级目标）**是指标在给定统计窗口内要达到的水平，例如 30 天请求成功率不低于 99.9%。
- **SLA（服务等级协议）**是对外约定，还包含未达标时的处理条款。内部 SLO 可以比 SLA 更严格，为发现和处置问题留出余量。

有了这些约定，日常工作就能围绕同一目标展开：

| 实践 | 具体工作 |
| --- | --- |
| 可靠性目标 | 明确用户结果、统计口径、窗口与 SLO |
| 错误预算策略 | 根据预算消耗调整发布和可靠性工作 |
| 减少 toil | 用自动化消除重复操作及人工协调 |
| 监控告警 | 根据业务症状与预算消耗触发响应 |
| 故障响应 | 定义角色、升级路径与恢复方案 |
| 无责复盘 | 找到系统缺口，并验证改进效果 |
| 容量与变更 | 压测、预留容量、灰度和回滚演练 |

**toil** 指手工、重复、可自动化，又很少带来持久改进的运维工作。例如，每次流量上涨都手工扩容，操作结束后下一次仍要再做；改造扩容机制则能减少以后的重复劳动。判断一项工作是不是 toil，要看它的性质，而不能把所有运维工作都算进去。

Google SRE 将运维性工作控制在总时间的 50% 内，是为了给工程改进保留时间。这是其组织实践，不是所有团队必须照搬的比例；关键在于避免重复操作占满时间，以至于一直无法消除这些操作。

SLO 的统计口径会直接影响失败额度。按 30 天的时间可用率计算，总时间是 `30 × 24 × 60 = 43200` 分钟，99.9% 允许其中的 0.1% 不可用，也就是 43.2 分钟；99.99% 则对应 4.32 分钟。如果目标是请求成功率，就应按失败请求数计算，不能直接套用这两个时间值。

监控需要把用户结果转成可响应的告警，具体实现见 [监控与告警](../observability/monitoring-alerting.mdx)；故障发生后的分工与恢复见 [故障响应与排查](./incident-response.mdx)；怎样为流量和故障预留资源，见 [容量规划](../../system-design/system-design/capacity-slo-failure-model.mdx)。

## 3. 相关岗位的区别 {#相关岗位的区别}

这些岗位会使用相似的工具，但组织工作的重点不同。比较时，要看一个岗位对什么结果负责，而不只是看它是否写代码。

| 岗位或方法 | 侧重 |
| --- | --- |
| 运维 | 部署、配置、资源维护和故障处理 |
| 运维开发 | 用代码建设发布、监控和管理工具 |
| SRE | 围绕可靠性目标组织运行与工程改进 |
| DevOps | 改善开发与运维协作及持续交付 |
| 平台工程 | 提供自助使用的内部开发平台 |

这些职责在不同团队中会重叠，运维岗位也可以高度自动化。SRE 的区别在于明确可靠性目标，并据此安排运行工作和工程投入。面试时应结合 JD 和自己的项目说明：衡量了什么、做了什么改进、结果怎样，而不是只背岗位名称的定义。

## 4. 错误预算策略与消耗速率 {#错误预算策略与消耗速率}

**错误预算**是 SLO 在给定统计窗口内允许的失败额度。它把“还能承受多少失败”变成可计算的数值，帮助团队决定继续发布，还是先投入可靠性改进。

预算策略应由开发与可靠性团队在事故前约定，包括统计窗口、计算口径和触发动作。预算充足时按计划发布，耗尽时可以暂停普通功能变更，但仍要保留安全修复和恢复性变更的路径。具体豁免也应事先明确，避免在事故中临时争论。预算恢复后，还要检查改进项和发布风险，再决定是否恢复正常发布。

假设一个 30 天窗口内有 100 万次请求，成功率目标为 99.9%，允许失败的比例就是 `1 - 99.9% = 0.1%`，对应 `1000000 × 0.1% = 1000` 次失败。

**预算消耗速率（burn rate）**是实际错误比例除以允许错误比例。当前错误率为 1% 时，burn rate 就是 `1% / 0.1% = 10`。如果请求速率稳定，并一直维持这个错误率，一份完整的 30 天预算约 3 天就会耗尽；已经花掉的预算和流量变化都会影响实际剩余时间。

告警可以同时检查长、短两个窗口：长窗口用于确认预算正在持续消耗，短窗口用于确认故障此刻仍在发生。这样可以把是否需要响应与预算消耗联系起来。

## 5. 故障注入与混沌工程 {#故障注入与混沌工程}

**故障注入**是主动制造延迟、节点失效等故障；**混沌工程**则通过受控实验，检验系统在这些故障下是否仍能达到预期。实验开始前，先定义反映正常业务表现的稳态指标，再提出可验证的假设，例如“一个缓存节点失效后，核心请求仍满足既定 SLO”。后续注入和观察都围绕这个假设进行。

1. 选择故障类型和最小实验范围。
2. 设置稳态指标、对照组和观测窗口。
3. 验证停止开关及恢复步骤。
4. 注入故障，并比较实际结果与假设。
5. 达到停止条件时恢复，记录设计缺口。

测试环境用于先验证注入工具、停止开关和恢复流程。生产实验的价值，是观察真实负载、配置和依赖共同作用下的表现，因此应在这些准备完成后，从少量实例或流量开始。

**爆炸半径**是一次实验可能影响的用户、实例和依赖范围。给请求加标记，可以限定哪些请求被注入故障，却不保证其他请求完全不受影响：实验请求仍可能占满共享线程池，或把压力传给同一个缓存和数据库。节点级故障还会影响该节点上的其他流量，所以隔离效果本身也要验证。

是否把实验流量单独统计和熔断，要看实验目标。如果只想验证某个调用方的处理，可以用独立统计控制波及范围；如果要验证全局熔断，就必须让故障进入真实的统计路径。把实验错误全部排除后，得到的结果就无法说明全局熔断是否有效。

有写入的实验可以使用影子数据或可识别的测试记录，避免与正常业务数据混淆。自动停止条件要观察真实用户指标，不能只看实验请求。停止注入后，还要确认积压和重试已经消退，才算完成恢复。

## 6. 面试题 {#面试题}

### 6.1 你怎么理解 SRE？它和传统运维、运维开发、DevOps 有什么区别？ {#what-is-sre}

**考察重点**

- 用工程方法保障可靠性：SLO、错误预算、消除琐事、故障响应、复盘。
- 与传统运维、运维开发、DevOps 的关系，并能结合岗位说明。

**相关内容**：[SRE 的核心实践](#sre-的核心实践)、[相关岗位的区别](#相关岗位的区别)。

<details>
<summary>参考回答</summary>

**SRE 用软件工程方法管理服务可靠性。**

它用 SLI 衡量用户结果，用 SLO 设定目标，再通过错误预算策略决定什么时候可以继续发布，什么时候应优先改善可靠性。

日常工作包括监控、值班、容量、变更和复盘，但还要持续用工程改进减少重复操作、缩短恢复时间。限制 toil 的目的，就是给这些改进留出时间。

运维侧重系统运行，运维开发侧重工具建设，SRE 围绕可靠性目标组织这些工作，DevOps 强调开发与运维协作及持续交付。它们的职责可能重叠，具体边界应结合目标团队的 JD 判断。

</details>

### 6.2 故障注入为什么要在线上做而不只在测试环境做？怎样控制爆炸半径，避免影响正常流量？ {#chaos-engineering}

**考察重点**

- 混沌实验的流程：稳态、假设、注入、观察、停止。
- 生产实验的理由；爆炸半径、流量标记、数据隔离、熔断统计隔离与自动停止。

**相关内容**：[故障注入与混沌工程](#故障注入与混沌工程)、[服务容错](../../system-design/reliability/circuit-breaker-degradation-bulkhead.mdx)。

<details>
<summary>参考回答</summary>

**生产实验用于检验真实负载与依赖下的容错表现。**

测试环境先验证注入工具、停止开关和恢复流程；这些准备完成后，生产实验从少量实例或流量开始，以覆盖测试环境难以完整重现的负载与依赖。

实验前定义稳态假设、对照组和停止条件。请求级故障可以用流量标记限定范围，但还要检查共享资源是否把影响传给正常用户；节点级故障则需按实例和依赖限制范围。

实验流量是否单独统计和熔断，取决于验证目标；要验证全局熔断，就应覆盖真实统计路径。写入数据应隔离或可识别，自动停止条件要观察真实用户指标，停止注入后还需确认积压和重试消退。

</details>

### 6.3 99.9% 的请求成功率目标怎样计算预算？预算耗尽后怎样处理？ {#error-budget-policy}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：统计口径、发布策略与 burn rate。

**相关内容**：[错误预算策略与消耗速率](#错误预算策略与消耗速率)。

<details>
<summary>参考回答</summary>

**99.9% 的成功率允许 0.1% 的请求失败，因此 100 万次请求对应 1000 次失败预算。**

如果当前错误率为 1%，burn rate 就是 `1% / 0.1% = 10`。在请求速率稳定、该错误率持续不变的前提下，一份完整的 30 天预算约 3 天耗尽。

预算耗尽后，按事先约定暂停普通功能变更，优先处理可靠性问题。安全修复和恢复性变更走预先约定的豁免路径。

</details>
