# Pod：生命周期、探针与资源

Pod 将紧密协作的容器作为一个整体调度。本文负责组成、状态、探针、资源与终止过程。组件创建链路见 [Kubernetes 架构](./architecture.mdx)。工作负载管理见 [工作负载、Service 与集群网络](./workloads-networking.mdx)。

## 1. 面试核心 {#core}

- Pod 内容器共享网络空间，并可挂载同一卷。[卡](#why-pod)
- CrashLoopBackOff 表示容器重启退避，Pending 是 Pod 阶段。[卡](#pod-troubleshooting)
- readiness 影响接流量，liveness 失败触发容器重启处理。[卡](#probes)
- requests 参与调度，CPU limit 通过配额实施限流。[卡](#scheduling-scaling)
- `preStop` 与应用退出共用终止宽限期。[卡](#graceful-termination)

## 2. Pod 的组成 {#pod-的组成}

同一 Pod 的容器共用网络 Namespace。它们通过 localhost 通信，需避免监听端口冲突。共享卷可用于交换文件。容器根文件系统各自独立。

Pod 内各容器调度到同一节点。Linux 运行时可用 pause 容器维持沙箱。默认配置下，各容器使用独立的进程视图。`shareProcessNamespace: true` 才显式共享进程空间。

普通 init 容器按顺序执行，并成功结束。随后，业务容器启动。sidecar 则长期提供代理、日志等辅助能力。

原生 sidecar 在 Kubernetes 1.33 达到稳定状态。它声明在 initContainers 中，使用 `restartPolicy: Always`。kubelet 确认它已启动后，再处理后续 init 容器。配置 startupProbe 时，启动确认还依赖该探针。正常终止时，原生 sidecar 在业务容器之后停止。

## 3. 状态与排查 {#状态与排查}

| Pod phase | 含义 |
| --- | --- |
| Pending | 已接受，部分容器尚未完成启动准备 |
| Running | 已绑定节点，容器已创建；至少一个在运行或启动重启中 |
| Succeeded | 所有容器成功结束，并且不再重启 |
| Failed | 所有容器结束，至少一个失败，并且不再重启 |
| Unknown | 无法取得 Pod 状态 |

`kubectl get pod` 的 STATUS 是展示信息。它还会显示容器等待原因及终止状态。

| 表现 | 重点证据 |
| --- | --- |
| 未调度 Pending | FailedScheduling、requests、约束与 PVC |
| ContainerCreating | 卷挂载、CNI 与镜像准备事件 |
| ImagePullBackOff | 镜像地址、凭据、网络与拉取事件 |
| CrashLoopBackOff | 上次退出原因、日志和探针事件 |
| OOMKilled | 内存限额、节点压力与内核 OOM 记录 |
| Terminating | preStop、存储卸载、finalizer 与节点状态 |

缺少必需 Secret 可阻止容器创建。程序读取配置后主动退出，则会进入重启流程。两者应按事件区分。

```bash
kubectl describe pod web
kubectl logs web -c app --previous
kubectl get events --sort-by=.lastTimestamp
```

describe 用于定位事件和上次容器状态。logs 的 `--previous` 读取上一个容器实例的日志。退出码 137 还需核对 OOMKilled 与终止记录。停止超时后的 SIGKILL 也能产生 137。

## 4. 探针 {#探针}

| 探针 | 失败达到阈值后的行为 |
| --- | --- |
| livenessProbe | kubelet 终止容器，再按重启策略处理 |
| readinessProbe | 标记未就绪，常规 Service 流量停止选用该端点 |
| startupProbe | 终止启动失败的容器，再按重启策略处理 |

startupProbe 成功前，另外两种探针暂缓执行。HTTP 探针接受 200—399 状态码。TCP 检查建连，exec 检查退出码 0。gRPC 探针检查健康服务响应。

```yaml
startupProbe:
  httpGet: {path: /healthz, port: 8080}
  periodSeconds: 5
  failureThreshold: 30
livenessProbe:
  httpGet: {path: /healthz, port: 8080}
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: {path: /ready, port: 8080}
  periodSeconds: 5
```

示例为启动预留约 150 秒的探测预算。实际时点还受单次超时与探测调度影响。liveness 用于识别重启能恢复的本地故障。将共享数据库故障纳入 liveness，会触发连锁重启。

readiness 应反映当前实例能否处理请求。共享依赖检查也要考虑全部副本同时摘流量的后果。探针失败不会主动断开所有已有连接。

## 5. 资源配置与 QoS {#资源请求限制与-qos}

以下使用容器级资源配置。

```yaml
resources:
  requests: {cpu: 500m, memory: 512Mi}
  limits: {cpu: "1", memory: 1Gi}
```

调度器按 requests 计算资源需求。CPU 超过配额会限流。内存达到上限且回收不足时，内核可触发 OOM。具体 cgroup 机制见 [容器原理](../containers/container-principles.mdx#cgroups)。

| QoS | 容器级配置下的条件 |
| --- | --- |
| Guaranteed | 每个容器都配置 CPU、内存；各自 request 等于 limit |
| BestEffort | 所有容器都未配置 CPU、内存的 request 和 limit |
| Burstable | 其他配置 |

节点压力驱逐按所需回收的资源排序。主要依据是是否超过 requests、Priority 和超出量。QoS 只是部分资源配置的归类。磁盘或 inode 压力还需按对应资源处理。

`kubectl drain` 默认通过 Eviction API 驱逐。该路径遵守 PodDisruptionBudget。节点压力驱逐与节点故障不受 PDB 保护。

## 6. 调度约束与弹性伸缩 {#调度约束与弹性伸缩}

| 机制 | 含义 |
| --- | --- |
| nodeSelector、required 亲和 | 硬性筛选节点 |
| preferred 亲和 | 为满足偏好的节点评分 |
| NoSchedule 污点 | 拒绝缺少容忍的新调度 |
| PreferNoSchedule 污点 | 尽量避开缺少容忍的 Pod |
| NoExecute 污点 | 还可驱逐未容忍的已有 Pod |
| 反亲和、拓扑分布 | 约束副本在节点或可用区的分布 |

容忍只是通过污点检查。它不会保证 Pod 被调度到该节点。

HPA 根据指标调整副本数。基本计算为 `ceil(当前副本数 × 当前指标 / 目标指标)`。CPU 利用率目标以 requests 为分母。使用 CPU 绝对值目标时，计算口径不同。

控制器还处理缺失指标、未就绪副本和容差。缩容稳定窗口用于减少抖动。VPA 调整资源请求，Cluster Autoscaler 调整节点。应用扩容需与节点容量配合。

## 7. 优雅终止与流量排空 {#优雅终止与流量排空}

正常删除 Pod 后，终止宽限期开始计时。默认 `terminationGracePeriodSeconds` 为 30 秒。kubelet 先运行 preStop，再请求运行时发送停止信号。默认信号为 SIGTERM，镜像或配置可以覆盖。

preStop 耗时计入同一个宽限期。应用应停止接收新请求，并完成在途工作。宽限期结束后，剩余进程会被强制终止。

端点更新与本地停止流程并行推进。终止端点会标记为未就绪，规则传播需要时间。应用需留出传播时间，并处理已有连接。固定 sleep 只能提供等待窗口。它的时长应结合入口传播和请求耗时验证。

强制删除会先移除 API 对象。它无法确认失联节点上的进程已经停止。有状态业务还需隔离旧实例，避免重复执行。

-->

**出现公司**：嘉银科技、影石、共济科技

**考察重点**

- 三种探针失败后的不同动作。
- 存活探针不检查下游；启动探针保护慢启动应用；探针与节点健康的区别。

**相关内容**：[探针](#探针)。

<details>
<summary>参考回答</summary>

readiness 控制接流量，liveness 判断是否需要重启。startup 为慢启动提供独立的探测预算。startup 成功前，另外两类探针暂缓执行。

liveness 失败达到阈值后，kubelet 终止容器。后续重启受 restartPolicy 约束。readiness 失败只改变就绪状态，已有连接仍需处理。

liveness 应检查重启能修复的本地故障。共享依赖故障放入该探针会造成连锁重启。超时和失败阈值应覆盖可接受的短暂抖动。

</details>
