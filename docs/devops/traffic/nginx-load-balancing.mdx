# Nginx 与负载均衡

Nginx 作为**反向代理**接收客户端请求，再把请求转给后端；通过**负载均衡**，它还可以把流量分配到多个后端。理解代理时，要分清客户端到 Nginx、Nginx 到上游这两侧的连接。连接容量、超时、重试和 502、504 排查，都要沿着这个请求过程判断。

## 1. 面试核心 {#core}

- Nginx worker 通过**事件循环和非阻塞网络 I/O**处理大量连接，Linux 下可使用 `epoll` 等待就绪事件。[卡](#nginx-architecture)
- 连接额度要同时考虑客户端和上游；**`keepalive` 只限制每个 worker 缓存的上游空闲连接数**，不限制所有活跃连接。[卡](#connection-capacity)
- **四层按连接分发，七层可以按 HTTP 域名、路径和头部路由**，选择时要结合需要的路由能力和报文路径。[卡](#l4-vs-l7)
- **502 表示上游通信异常，504 表示网关等待上游超时**。状态码还可能由上游返回，需要结合日志确认来源。[卡](#nginx-502-504)
- **`proxy_read_timeout` 限制相邻两次读取之间的等待**，不限制整个响应的总耗时；超时重试还要考虑请求是否已经产生业务效果。[卡](#proxy-timeout-retry)

## 2. Nginx 的结构与常用配置 {#nginx-的结构与常用配置}

Nginx 的 master 进程读取配置并管理 worker，worker 负责处理请求。worker 的**事件循环**会等待网络操作就绪，再执行相应的读写，因此不需要为每条空闲连接安排一个专门等待的线程。`worker_processes auto` 根据可用 CPU 自动设置 worker 数量。

非阻塞网络 I/O 让少量 worker 可以管理大量连接，但事件循环中的阻塞操作仍会拖慢其他请求。磁盘访问、复杂计算或阻塞模块都需要单独评估，文件 I/O 可以根据平台和配置使用异步机制或线程池。

Apache 通过多处理模块（MPM）选择请求处理模型，`prefork`、`worker` 和 `event` 的方式不同。因此比较 Nginx 与 Apache 的性能时，要说明具体 MPM、模块和工作负载，不能只按产品名称下结论。

下面的片段放在 `http` 上下文中。`upstream backend` 定义两个上游服务器，也就是 Nginx 要转发请求的后端：

```nginx
upstream backend {
    least_conn;
    server 10.0.0.11:8080 weight=2 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=10s;
    keepalive 64;
}
server {
    listen 8080;
    server_name example.com;

    location /static/ {
        root /data/www;
        expires 7d;
    }
    location /api/ {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;
    }
}
```

请求 `/static/a.css` 时，`root` 把请求路径接到 `/data/www` 后，得到 `/data/www/static/a.css`。请求 `/api/` 下的接口时，Nginx 把请求转给 `backend`，保留 `/api/` 前缀。代理侧显式使用 HTTP/1.1、清空 `Connection` 头，并配合上游 `keepalive` 复用连接。

Nginx 1.29.7 之前默认使用 HTTP/1.0 代理，1.29.7 起默认使用 HTTP/1.1。示例显式写出协议版本，避免配置含义依赖默认值。

修改配置后，先用 `nginx -t` 检查语法及引用文件，通过后再用 `nginx -s reload` 重载。master 成功应用新配置后启动新 worker，旧 worker 则在完成已有请求后退出。

### 2.1 连接容量 {#连接容量}

`worker_connections` 限制每个 worker 能处理的连接数，客户端连接和上游连接都占用这个额度。HTTP 反向代理处理一次活跃请求时，可能同时占用两侧连接，因此不能把连接额度直接当成请求并发数。

文件描述符上限也会限制实际容量。worker 数量乘以连接额度，只能给出连接数的粗略上界；HTTP/2 在同一连接上承载多个请求，上游连接也可能复用，所以请求数和连接数之间没有固定的一一对应关系。

示例中的 `keepalive 64` 表示每个 worker 最多缓存 64 条上游空闲连接，供后续请求复用。活跃上游连接可以超过这个数，所以它不是上游并发上限；要保护后端，还需要单独评估和配置并发控制。

## 3. 负载均衡 {#负载均衡}

负载均衡算法决定下一次请求交给哪个后端。选择时，要考虑后端能力、请求处理时间，以及同类请求是否需要落到同一个节点：

| 算法 | 配置 | 适用条件 |
| --- | --- | --- |
| 加权轮询 | `weight` | 按后端能力分配请求 |
| 最少连接 | `least_conn` | 请求占用时间差异较大 |
| IP 哈希 | `ip_hash` | 需要按地址粘滞，注意 NAT 聚集 |
| 一致性哈希 | `hash $request_uri consistent` | 缓存按键分布 |

**被动健康检查**根据实际请求中的失败判断后端是否可用。`max_fails=3 fail_timeout=10s` 表示在 10 秒内达到三次符合条件的失败后，把该后端视为不可用 10 秒。哪些情况计为失败，受 `proxy_next_upstream` 等配置影响。上游组只有一个后端时，`max_fails` 和 `fail_timeout` 会被忽略。

**四层负载均衡**依据连接、IP 地址和端口分发流量；**七层负载均衡**解析应用协议，可以按 HTTP 域名、路径和头部路由。Nginx 的 HTTP 代理属于后者，`stream` 模块也能提供四层代理。

同样是四层，实现路径也不同：全代理拆成客户端侧和后端侧两条连接，Linux Virtual Server（LVS）的 NAT、DR 模式则转发原连接。性能需要结合具体实现、TLS 和请求负载测试，不能仅由层次推断。LVS 的主要模式如下：

| LVS 模式 | 请求与响应路径 |
| --- | --- |
| NAT | 改写目的地址；响应也经调度器反向转换 |
| DR | 修改目的 MAC；后端直接响应客户端 |
| TUN | 封装转发；后端解封装后直接响应 |

DR 要求调度器和后端处于可直接到达的二层网络。后端需要配置供客户端访问的虚拟 IP（VIP），并限制对该 VIP 的 ARP 应答。TUN 则依赖隧道和底层网络可达性。这两种模式让后端直接向客户端发送响应，因此可以减轻调度器承载响应流量的带宽压力。

FULLNAT 属于特定 LVS 扩展实现，例如阿里 LVS，会同时改写源地址和目的地址。后端要取得原客户端地址，可以使用 TOA 等扩展传递信息，但需要两端配合，部署前要确认实现是否支持。

Keepalived 可以通过虚拟路由冗余协议（VRRP）协调 VIP 在主备之间切换，并通过健康检查维护 LVS 后端列表。接管 VIP 只解决入口地址由谁承接的问题，业务能否恢复，还要看接管节点的容量和连接状态。

## 4. 502 与 504 {#502-与-504}

502 和 504 都与代理访问上游有关，但指向不同的失败：502 表示上游通信异常，504 表示等待上游超时。排查前还要确认状态码由谁生成，因为上游应用返回的状态码也可能被直接传给客户端。

| 状态 | 解释与线索 |
| --- | --- |
| 500 | 当前响应方内部错误，可由应用或代理产生 |
| 502 | 上游连接失败、无有效响应或无可用后端 |
| 503 | 服务不可用；Nginx limit_req 默认拒绝码 |
| 504 | 网关等待上游超时 |
| 499 | Nginx 日志记录客户端提前关闭 |

`upstream_status`、Nginx 错误日志和应用日志可以帮助判断错误来源。比如错误日志中的 `no live upstreams` 表示没有可用上游，对应 502。定位时按请求阶段逐步检查：

1. 查看 `error.log`，确认建连、响应头或响应体读取阶段。
2. 对比 `upstream_addr`、`upstream_status` 与各阶段耗时。
3. 核对异常后端的监听、负载、线程池和依赖。
4. 检查超时、连接复用及重试配置。
5. 用用户请求成功率与延迟验证修复。

`Connection refused` 表示连接遭到明确拒绝，可能是目标进程没有监听，也可能是策略主动拒绝。`upstream timed out` 则说明发生了超时，还要看日志写的是建连、读取响应头还是读取响应内容阶段，才能决定下一步查哪里。

## 5. 代理超时与重试 {#代理超时与重试}

代理超时分别约束建连、发送和读取，不能统一理解成「请求最多执行多久」。`proxy_connect_timeout` 控制上游建连等待，`proxy_send_timeout` 控制相邻写操作之间的等待，`proxy_read_timeout` 控制相邻读操作之间的等待。

因此，配置 `proxy_read_timeout 30s` 后，只要上游持续返回数据、相邻读取间没有超时，整个响应仍可能超过 30 秒。

`proxy_next_upstream` 指定失败后换后端的条件，`proxy_next_upstream_tries` 限制尝试次数，`proxy_next_upstream_timeout` 限制允许换到下一个上游的时间窗口。响应一旦已经发给客户端，就不能靠换后端重新完成这次响应。

**非幂等请求**是重复执行可能产生额外业务效果的请求，例如重复提交一次创建操作。已经发给上游的 POST 等非幂等请求，默认不会在失败后换后端重试；`non_idempotent` 会放宽这个限制。启用前必须考虑业务幂等保护，例如用幂等键识别重复请求，因为代理看到超时时，上游也可能已经完成提交。

## 6. 路径映射与真实地址 {#路径映射与真实地址}

普通前缀 `location` 中，`proxy_pass` 是否带 URI，决定是否替换匹配到的路径前缀。下面的地址末尾带 `/`，这个 `/` 就是配置中的 URI 部分：

```nginx
location /api/ {
    proxy_pass http://backend/;
}
```

请求 `/api/users` 匹配 `/api/` 后，这段前缀被替换为 `/`，所以上游收到 `/users`。去掉 `backend` 后面的斜杠，`proxy_pass` 就不带 URI，上游保留 `/api/users`。这个推导适用于普通前缀 `location`，正则 `location` 和带变量配置需要按各自规则判断。

静态文件的 `root` 与 `alias` 也有不同含义：`root` 把 URI 拼到根目录后，`alias` 则用指定路径替换匹配的位置。排查文件找不到或无权访问时，先算出最终路径，再检查文件和沿途目录权限。

`X-Forwarded-For` 可以携带经过代理链的地址信息，但客户端也能自行填写这个头。因此，不能看到头里的地址就把它当成真实客户端。使用 `real_ip` 模块时，要通过 `set_real_ip_from` 指定可信代理；只有明确这些地址由谁提供，才能据此限流或审计。

## 7. 请求限流 {#请求限流}

请求限流控制的是单位时间内的请求数量。下面按客户端 IP 设置速率，并给短时突发保留一定额度，片段放在 `http` 上下文中：

```nginx
limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s;
server {
    listen 8081;
    location / {
        limit_req zone=perip burst=20 nodelay;
        limit_req_status 429;
        proxy_pass http://backend;
    }
}
```

`limit_req` 按漏桶方法控制速率：请求超过配置速率时，根据突发额度决定延迟处理还是拒绝。示例中的 `rate=10r/s` 设置每秒 10 个请求的速率，`burst=20` 提供超额请求额度，`nodelay` 让额度内的突发立即处理。超过可用额度的请求被拒绝，示例通过 `limit_req_status 429` 返回 429。

`limit_conn` 用于限制并发，与请求速率是不同维度。按 IP 限流时，还要考虑多个用户可能通过 NAT 共用一个出口地址，他们会共享这份额度。

## 8. 面试题 {#面试题}

### 8.1 Nginx 有什么作用？它为什么能支撑很高的并发？与 Apache 有什么区别？ {#nginx-architecture}

**考察重点**

- master/worker 进程模型与 epoll 事件驱动。
- 常用功能与动静分离；与 Apache 连接模型的差异。

**相关内容**：[Nginx 的结构与常用配置](#nginx-的结构与常用配置)、[I/O 多路复用](../../basic-knowledge/operating-system/io-multiplexing.mdx)。

<details>
<summary>参考回答</summary>

**Nginx 用事件循环和非阻塞网络 I/O 管理大量连接。**

master 负责配置和 worker 管理，worker 处理已经就绪的网络事件，Linux 下可以使用 `epoll`。连接等待数据时不需要独占一个线程，因此少量 worker 可以管理大量连接；但阻塞模块和复杂计算仍会影响同一 worker 上的其他请求。

Nginx 可以提供反向代理、静态文件、TLS、缓存和限流，实际容量还受连接数、文件描述符和上游能力限制。Apache 的 `prefork`、`worker`、`event` MPM 使用不同处理模型，比较时需要明确 MPM、模块和工作负载。

</details>

### 8.2 四层负载均衡和七层负载均衡有什么区别？Nginx 和 LVS 怎样选择？LVS 有哪几种模式？ {#l4-vs-l7}

**考察重点**

- 四层与七层的依据、能力和性能差异；Nginx 的负载均衡算法。
- LVS 各模式的报文路径与限制；Keepalived 的 VRRP。

**相关内容**：[负载均衡](#负载均衡)、[网络模型](../../basic-knowledge/network/network-models.mdx)。

<details>
<summary>参考回答</summary>

**四层按连接分发，七层可按应用内容路由。**

LVS 在内核中转发连接，Nginx HTTP 代理解析请求，适合需要按域名、路径或头部路由的场景；Nginx 的 `stream` 也可以承担四层代理。选择时还要结合容量、网络条件和运维复杂度测试。

LVS NAT 模式下，请求和响应都经过调度器；DR 修改目的 MAC，后端直接响应客户端；TUN 封装请求，后端解封装后直接响应。FULLNAT 属于特定扩展实现，会同时改写源、目的地址，需要确认具体支持情况。

Nginx 支持加权轮询、最少连接和哈希等算法。需要 VIP 主备切换时，可以由 Keepalived 使用 VRRP 协调，并配合后端健康检查。

</details>

### 8.3 Nginx 返回 502 和 504 分别是什么原因？怎样排查？和 500 有什么区别？ {#nginx-502-504}

**考察重点**

- 状态码由谁产生；502 与 504 的典型原因。
- 从 Nginx 错误日志和上游字段定位到具体后端；长连接复用导致的 502。

**相关内容**：[502 与 504](#502-与-504)、[Linux 网络排查](../linux/network-troubleshooting.mdx#端口与连接状态)。

<details>
<summary>参考回答</summary>

**502 表示上游通信异常，504 表示网关等待上游超时。**

500 表示响应方内部错误，可能由应用或代理产生；其他状态码也可能由上游透传，所以先确认错误来源。

查看 `error.log` 中失败发生在建连、响应头还是响应体读取阶段，再结合 `upstream_addr`、`upstream_status` 和耗时定位具体后端。之后检查监听、负载、池等待和依赖。如果复用连接被对端关闭，核对双方空闲超时；如果日志是 `no live upstreams`，则检查后端为何被判定为不可用。

超时处理还要结合业务期限和重试副作用，不能只增加 `proxy_read_timeout`，因为它限制的是相邻读取之间的等待，不是整个请求的期限。

</details>

### 8.4 worker_connections 与 keepalive 能直接算出业务并发上限吗？ {#connection-capacity}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：双侧连接、文件描述符与空闲缓存。

**相关内容**：[连接容量](#连接容量)。

<details>
<summary>参考回答</summary>

**不能直接算出。`worker_connections` 同时计入客户端和上游连接，`keepalive` 只限制上游空闲连接缓存。**

一个活跃代理请求可能占用两侧连接，而 HTTP/2 多路复用又让多个请求共用连接。实际容量还受文件描述符和业务处理能力限制。

`keepalive` 的数值按每个 worker 计算，活跃上游连接可以超过它，因此要单独评估上游并发，不能把空闲缓存大小当作业务并发上限。

</details>

### 8.5 proxy_read_timeout=30s 会限制总响应时间吗？POST 超时能否换后端重试？ {#proxy-timeout-retry}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：相邻读超时、重试窗口与幂等性。

**相关内容**：[代理超时与重试](#代理超时与重试)。

<details>
<summary>参考回答</summary>

**不会限制总响应时间，它限制相邻两次读取之间的等待；已发送给上游的 POST 等非幂等请求，默认不会换后端重试。**

只要上游持续返回数据、相邻读取间没有超时，响应就可以超过 30 秒。`non_idempotent` 可以放宽非幂等请求的重试限制，但原请求可能已经提交，必须有业务幂等保护。还要通过 `proxy_next_upstream_tries` 和 `proxy_next_upstream_timeout` 限制尝试次数及可重试的时间窗口。

</details>

### 8.6 proxy_pass 末尾斜杠有什么影响？怎样可信地取得客户端地址？ {#proxy-uri-realip}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：URI 替换规则与可信代理。

**相关内容**：[路径映射与真实地址](#路径映射与真实地址)。

<details>
<summary>参考回答</summary>

**普通前缀 `location` 中，`proxy_pass` 是否带 URI 决定是否替换匹配前缀；客户端地址则只能从可信代理提供的信息中取得。**

例如 `location /api/` 配合 `proxy_pass http://backend/` 时，`/api/users` 转为 `/users`；改成不带 URI 的 `proxy_pass http://backend` 时保留原路径。

客户端可伪造 `X-Forwarded-For`。配置 `real_ip` 时，只信任 `set_real_ip_from` 指定的代理。

</details>

### 8.7 limit_req 的 burst 与 nodelay 分别做什么？ {#request-rate-limit}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：平均速率、突发额度与拒绝行为。

**相关内容**：[请求限流](#请求限流)。

<details>
<summary>参考回答</summary>

**`burst` 提供超额请求额度，`nodelay` 让额度内的突发立即通过，而不按配置速率延迟处理。**

没有 `nodelay` 时，超额但未超过 `burst` 额度的请求会被延迟处理；超过可用额度仍会被拒绝。`limit_req_status` 可以把拒绝状态码设为 429。这控制的是请求速率，并发限制要通过 `limit_conn` 等机制另行配置。

</details>
