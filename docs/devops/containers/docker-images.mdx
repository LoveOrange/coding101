# Docker 镜像与 Dockerfile

**Docker 镜像**保存应用所需的文件系统层和运行配置，**Dockerfile** 则描述怎样构建这些内容。理解两者的关系，才能解释为什么只改源码可以复用依赖缓存、删除文件后镜像未必变小，以及哪些数据应该放到容器之外保存。

## 1. 面试核心 {#core}

- exec 格式的 `ENTRYPOINT` 指定入口程序，与它组合的 `CMD` 提供**可在运行时替换的默认参数**。[卡](#dockerfile-instructions)
- 镜像保存只读层与运行配置，容器另有**独立可写层**。分层可以复用相同内容，但后续层删除文件不会移除旧层中的数据。[卡](#image-layers-storage)
- 多阶段构建只把所需产物复制到运行阶段，**编译工具和中间文件可以留在构建阶段**。[卡](#image-optimization)
- 卷的生命周期**独立于容器**，适合保存需要在容器删除后继续保留的数据。[卡](#image-layers-storage)
- tag 可以指向新内容，**digest 固定镜像内容**；构建密钥通过临时 secret 挂载提供，避免写入镜像配置或文件层。[卡](#build-secrets-digests)

## 2. 常用指令 {#常用指令}

Dockerfile 同时描述构建时做什么，以及容器启动时运行什么。**构建上下文**是提供给构建器的输入文件集合，下面假设其中已有编译好的 `target/app.jar`：

```dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
ENV TZ=Asia/Shanghai
COPY target/app.jar app.jar
USER 10001:10001
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
CMD ["--spring.profiles.active=prod"]
```

用这个镜像启动容器后，会以 UID 10001 执行 `java -jar app.jar --spring.profiles.active=prod`。应用需要写文件时，对应目录必须允许这个用户写入。执行 `docker run image --server.port=9090` 会保留 Java 入口程序，把 `CMD` 中的默认参数替换为 `--server.port=9090`。

| 指令 | 行为 |
| --- | --- |
| `FROM` | 指定阶段的基础镜像 |
| `RUN` | 在构建阶段执行命令 |
| `WORKDIR` | 设置工作目录 |
| `COPY` | 复制构建上下文中的文件 |
| `COPY --from` | 从其他阶段、镜像或命名上下文复制 |
| `ADD` | 另支持远程 URL、Git 和本地 tar 解包 |
| `ARG` | 声明构建参数及作用域 |
| `ENV` | 将环境变量写入镜像配置 |
| `USER` | 设置后续运行使用的用户 |
| `EXPOSE` | 声明容器服务端口 |
| `HEALTHCHECK` | 声明运行时健康检查命令 |

`CMD` 单独使用时，可以指定完整的默认启动命令；与 exec 格式的 `ENTRYPOINT` 组合时，则提供默认参数。运行容器时追加的参数覆盖 `CMD`，要替换 `ENTRYPOINT` 指定的程序，则使用 `--entrypoint`。

示例中的 JSON 数组写法是 **exec 格式**，它直接启动程序，便于应用接收停止信号。shell 格式则经 `/bin/sh -c` 执行，应用与停止信号之间可能多一层 shell。需要入口脚本做初始化时，应在最后用 `exec` 把执行交给业务进程。信号处理与子进程回收见 [进程管理与信号](../linux/processes-signals.mdx#信号)。

`EXPOSE 8080` 只记录服务端口，不会自动把它开放到宿主机；使用 `docker run -p` 才会建立主机端口发布。`HEALTHCHECK` 也只是定义检查命令，命令需要的工具仍必须存在于镜像中。

### 2.1 构建镜像与进入容器 {#构建镜像与进入容器}

`docker build` 的最后一个路径指定构建上下文，`-f` 选择 Dockerfile，`-t` 给产物命名。假设项目根目录已有 `target/app.jar`，上面的 Dockerfile 放在 `docker/Dockerfile`，在项目根目录执行：

```bash
docker build -t interview-app:local -f docker/Dockerfile .
docker run -d --name interview-app interview-app:local
docker exec -it interview-app sh
```

这里的 `COPY target/app.jar app.jar` 从最后的 `.` 所指目录取文件，不是从 `docker/` 取。改成 `docker build -f docker/Dockerfile docker/` 后，构建器就不能从该上下文取得根目录下的 `target/app.jar`；被 `.dockerignore` 排除的文件也不能被普通 `COPY` 复制。

`docker exec` 在正在运行的容器中启动一个新进程；它不会创建新容器，也不会恢复已经退出的主进程。`-i` 保持标准输入打开，`-t` 分配伪终端，交互式 shell 通常一起使用。批处理执行 `docker exec interview-app java -version` 时不需要终端。镜像中必须有要执行的程序：精简镜像可能没有 `sh`，不能把这种失败当成容器没有运行。要执行管道、重定向或多条 shell 命令，需要明确调用 `sh -c`，不能把整段字符串当成可执行文件名。

### 2.2 用 stats 区分资源现象 {#用stats区分资源现象}

`docker stats` 展示容器资源统计，默认持续刷新；只取一次可以执行 `docker stats --no-stream interview-app`。它提供的是排查入口，不能只看某一列就断言应用存在泄漏或性能瓶颈。

| 字段 | 观察内容与边界 |
| --- | --- |
| `CPU %` | 采样间隔内的 CPU 使用量；多核并行时可以超过 100%，不直接等于请求耗时 |
| `MEM USAGE / LIMIT`、`MEM %` | 当前使用量、可用上限及比例；Linux CLI 会扣除相应文件缓存，不能和原始 API 数值不加转换地对比 |
| `NET I/O` | 网络接口累计接收与发送字节；比较间隔内的增量才有吞吐量意义 |
| `BLOCK I/O` | 块设备累计读写量，不等于应用每次文件调用的字节数，缓存会影响它 |
| `PIDS` | 内核任务数量，包含进程和线程；线程增多也可能使该列上升 |

Linux 的缓存扣除口径还取决于 cgroup 版本：v1 使用 `total_inactive_file`，v2 使用 `inactive_file`；原始 stats API 保留使用量和缓存字段，由客户端计算。宿主没有为容器设置独立内存限额时，显示的上限不能当作已经完成资源隔离。看到异常后，再结合进程、日志和时间趋势定位；例如查询非容器 MySQL 的监听端口，应使用 [Linux 端口与连接检查](../linux/performance-troubleshooting.mdx#连接与请求缺失)，而不是从 `stats` 推测端口。

### 2.3 容器互访的路径 {#容器互访的路径}

同一宿主上的两个容器互访，先确认网络模式，再确认名称、端口和服务监听地址。普通 bridge 容器各有自己的网络命名空间，容器 A 的 `127.0.0.1` 指向 A 自己，不能用它访问容器 B。`host` 模式共享宿主网络，`none` 模式没有普通外部网络连接，不能套用同一条地址判断。

自定义 bridge 为加入同一网络的容器提供名称或别名解析。假设 `client` 与 `api` 都在 `app-net` 上，服务监听 `api` 的 `0.0.0.0:8080`，`client` 应访问 `api:8080`，通常不需要发布宿主端口。默认 `bridge` 不提供同样的容器名自动解析。不同宿主的 bridge 也不会因网络名称相同就自动连通。

`-p 127.0.0.1:18080:8080` 另建宿主到容器的端口发布路径：宿主侧用 18080，容器间直接访问仍用 8080。发布端口不会替应用启动监听；如果服务只绑定容器自己的 `127.0.0.1:8080`，其他普通 bridge 容器仍不能通过该容器的网卡地址连接。

排查时把失败定位到具体一段：

1. 用 `docker ps -a`、`docker logs api` 确认进程是否仍在运行、是否启动完成，避免把应用退出当成网络故障。
2. 用 `docker inspect client api` 和 `docker network inspect app-net` 核对网络模式、共同网络、地址和别名。不要看到两个容器都在运行，就假定它们可以互访。
3. 从发起请求的容器检查目标名称解析；再按实际协议尝试目标 IP 和容器端口。名字失败而 IP 成功时，优先检查名称和 DNS；连接被拒绝时检查端口与监听；超时还要检查路由、防火墙和服务负载，不能只凭现象认定原因。
4. 在目标容器确认监听地址、端口及协议。工具不在镜像中时，使用已具备的诊断方式；TCP 连接成功只证明传输路径可达，HTTP 状态、TLS、鉴权和业务响应仍要分别核对。

## 3. 分层与构建缓存 {#分层与构建缓存}

镜像的文件系统由多个只读层组成，运行容器时再加上独立的可写层。这样，不同镜像或容器可以共享相同的只读内容，拉取镜像时也能复用本地已有的层。

构建缓存则根据指令和输入判断一个步骤能否复用。`COPY` 的输入改变后，依赖它的后续步骤需要重建，所以文件复制的顺序会影响缓存效果：

```dockerfile
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build
```

这里先复制依赖清单并执行 `npm ci`，再复制源码。只修改源码时，前面的依赖安装仍可命中缓存；如果 `package.json` 或 `package-lock.json` 改变，`npm ci` 就需要重新执行。`COPY` 的校验不使用文件的修改时间 `mtime`，因此只改变时间戳不会使缓存失效。多阶段构建中，构建器 BuildKit 按步骤之间的依赖关系处理缓存，无依赖的阶段可以独立复用。

普通 `RUN` 缓存不会主动检查远程软件仓库是否更新。即使仓库里已经有新包，只要该步骤仍命中缓存，安装命令就不会重新执行。需要更新依赖时，应调整固定版本或显式使缓存失效，之后可用 `docker history <image>` 查看构建历史和各层大小。

分层也解释了为什么删文件后镜像未必变小：后续层只能遮住早期层的文件，旧内容仍留在镜像中。因此，下载、安装和清理临时文件应放在同一个 `RUN` 中，避免把无需保留的内容写入已完成的层。具体机制见 [容器原理](./container-principles.mdx#联合文件系统)。

## 4. 体积与构建速度优化 {#体积与构建速度优化}

**多阶段构建**把编译环境与运行环境分开，最终镜像只从构建阶段取出运行需要的文件。例如，编译 Java 应用需要 Maven，运行应用却不一定需要它。下面假设 Maven 将产物命名为 `app.jar`：

```dockerfile
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline
COPY src ./src
RUN mvn -q package -DskipTests

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/target/app.jar app.jar
USER 10001:10001
ENTRYPOINT ["java", "-jar", "app.jar"]
```

`build` 阶段使用 Maven 编译，最终阶段以 JRE 镜像为基础，只复制 `app.jar`，不会把前一阶段的 Maven 和源码一并带进来。示例使用 `-DskipTests` 跳过了测试，发布前仍需在测试流程中完成验证。

镜像体积与构建速度需要分别优化：多阶段构建主要减少最终保留的内容，缓存主要减少重复工作。

| 方法 | 作用与条件 |
| --- | --- |
| 精简基础镜像 | 减少运行依赖；Alpine 的 musl 需做兼容验证 |
| 同层清理 | 避免将包管理缓存保留在旧层 |
| `.dockerignore` | 排除无关输入，保留构建必需的产物 |
| 依赖步骤前置 | 源码变化时复用依赖层 |
| BuildKit cache 挂载 | 在多次构建间复用下载缓存 |
| 远程构建缓存 | 在不同 CI 执行器间共享缓存 |

## 5. 容器的数据存储 {#容器的数据存储}

容器可写层会在停止容器后保留，但删除容器时会一起删除。需要独立于容器生命周期保存的数据，应使用卷或绑定挂载；只在容器运行期间使用的临时数据，可以考虑 tmpfs。

| 方式 | 示例 | 生命周期 |
| --- | --- | --- |
| 命名卷 | `--mount type=volume,src=data,dst=/data` | 独立于容器，由 Docker 管理 |
| 绑定挂载 | `--mount type=bind,src=/host/data,dst=/data` | 使用宿主路径中的数据 |
| tmpfs | `--tmpfs /tmp` | 停止容器后数据消失 |

命名卷由 Docker 管理，绑定挂载则直接使用指定的宿主路径，因此依赖宿主的目录布局和权限。只供读取的配置可以使用 `readonly` 挂载。tmpfs 使用内存，宿主配置允许时也可能进入 swap，不能据此假定数据绝不会落盘。

多个容器挂载同一卷后，可以访问同一份数据，但并发写入仍需由应用或文件系统协调。挂载本身不提供业务事务，不能因为两个容器看到了同一文件，就认为它们的更新不会冲突。

迁移 Docker 数据前，要先确认实际存储后端。经典存储布局与 containerd 镜像存储的目录安排不同：`data-root` 管理 Docker 数据目录，而 containerd 管理的镜像和快照还有独立目录。因此，不能只调整 `data-root` 就假定全部数据已经迁移。

## 6. 镜像标识与密钥 {#镜像标识与密钥}

**tag** 是可以重新指向其他内容的镜像名称，**digest** 则是按内容计算的摘要。同一个 tag 今天和下次构建时可能指向不同镜像；`FROM image@sha256:...` 才能固定所引用的基础镜像内容。要控制整个构建的输入，还需要固定应用依赖和远程下载内容。

构建时需要凭据，可以用 BuildKit 的 **secret 挂载**，在指定步骤中临时提供密钥文件。下面假设构建阶段已经安装 curl：

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=token,required=true \
    curl --config /run/secrets/token https://example.com/artifact -o artifact
```

构建时用 `--secret id=token,src=token.conf` 提供 curl 配置，当前 `RUN` 步骤通过 `/run/secrets/token` 读取它。这个挂载只对该步骤可见，但命令仍可能主动把密钥写进产物或日志，因此还要检查命令本身的行为。

`ARG` 和 `ENV` 可能把密钥暴露在构建信息或运行配置中，不适合用于传递密钥。另外，secret 的内容变化不会自动使构建缓存失效。如果更换凭据后需要重新拉取产物，还应显式调整缓存输入。

## 7. 面试题 {#面试题}

### 7.1 Dockerfile 有哪些常用指令？CMD 和 ENTRYPOINT、COPY 和 ADD 有什么区别？ {#dockerfile-instructions}

**考察重点**

- 常用指令的用途；构建期和运行期指令的区分。
- `CMD` 与 `ENTRYPOINT` 的组合规则、exec 格式与信号；`COPY` 与 `ADD`；`EXPOSE` 只是声明。

**相关内容**：[常用指令](#常用指令)。

<details>
<summary>参考回答</summary>

**Dockerfile 分别定义构建步骤、运行配置和启动命令；`COPY` 负责明确的文件复制，`ADD` 还提供远程来源和解包能力。**

- `FROM` 指定基础镜像，`RUN` 执行构建命令；`WORKDIR`、`ENV`、`USER` 设置工作目录、环境变量和用户。`EXPOSE` 只声明端口，发布主机端口还需 `-p`；`HEALTHCHECK` 定义运行时检查命令。
- `CMD` 单独使用时可以指定默认启动命令，与 exec 格式的 `ENTRYPOINT` 组合时提供默认参数。运行时参数覆盖 `CMD`，`--entrypoint` 可替换入口程序。入口脚本应使用 `exec`，让应用直接接收停止信号。
- `COPY --from` 可从其他阶段或镜像复制文件。`ADD` 还支持远程来源和本地 tar 解包；普通复制使用 `COPY`，输入行为更明确。

</details>

### 7.2 构建镜像时，怎样优化镜像体积和构建速度？ {#image-optimization}

**考察重点**

- 多阶段构建、精简基础镜像、同层清理、`.dockerignore`。
- 利用层缓存的指令顺序；删除文件不缩小镜像的原因。

**相关内容**：[体积与构建速度优化](#体积与构建速度优化)、[分层与构建缓存](#分层与构建缓存)。

<details>
<summary>参考回答</summary>

**多阶段构建减少运行镜像内容，缓存复用缩短构建时间。**

减小体积时，最终阶段使用满足运行要求的基础镜像，只复制所需产物；安装与清理放在同一步骤，避免旧层保留无需使用的缓存文件。

缩短构建时间时，先复制依赖清单、安装依赖，再复制源码，让源码修改不影响依赖层缓存。用 `.dockerignore` 排除无关输入，用 BuildKit cache 挂载复用下载内容；不同 CI 执行器之间还可以共享远程缓存。优化后用 `docker history` 检查镜像历史和大小。

</details>

### 7.3 镜像和容器有什么区别？镜像为什么要分层？两个容器怎样共享数据？ {#image-layers-storage}

**考察重点**

- 只读层与可写层、写时复制；分层带来的复用。
- 卷、绑定挂载与 tmpfs 的区别。

**相关内容**：[分层与构建缓存](#分层与构建缓存)、[容器的数据存储](#容器的数据存储)、[容器原理](./container-principles.mdx#联合文件系统)。

<details>
<summary>参考回答</summary>

**镜像是文件层与配置，容器是镜像的运行实例。**

运行时为容器增加独立可写层。停止后的容器仍保留该层，删除容器才移除它。

分层让镜像共享相同内容，拉取时可复用已有层。卷和绑定挂载可让多个容器访问同一份数据。卷独立于容器生命周期，绑定挂载直接使用宿主路径。tmpfs 的内容在容器停止后消失。共享写入仍需要应用协调。

</details>

</details>

### 7.5 怎样构建镜像并进入一个正在运行的容器？ {#build-and-exec}

**考察重点**：构建上下文与 Dockerfile 路径、运行实例、交互终端。

**相关内容**：[构建镜像与进入容器](#构建镜像与进入容器)。

<details>
<summary>参考回答</summary>

**先用 `docker build -t interview-app:local -f docker/Dockerfile .` 构建镜像，再对已经运行的容器执行 `docker exec -it interview-app sh`。** 最后的 `.` 决定普通 `COPY` 能读取哪些文件，`-f` 只选择 Dockerfile。`exec` 启动容器内的新进程；主进程已经退出、镜像没有 `sh`，或非交互环境不适合分配终端时，应分别处理，不能一律加 `-it`。

</details>

### 7.6 docker stats 是做什么的？ {#container-stats}

**考察重点**：容器资源指标与统计口径。

**相关内容**：[用 stats 区分资源现象](#用stats区分资源现象)。

<details>
<summary>参考回答</summary>

**`docker stats` 用来观察容器的 CPU、内存、网络、块设备 I/O 和任务数量，`--no-stream` 只取一次。** 网络与块 I/O 是累计量，吞吐要看增量；`PIDS` 包含线程。Linux CLI 会从内存使用量中扣除相应文件缓存，直接与原始 API 比较前要统一口径。指标异常只是线索，还要结合应用日志和进程行为判断原因。

</details>

### 7.7 两个 Docker 容器无法互访，怎样排查？ {#container-connectivity}

**题型**：综合题

**考察重点**：容器生命周期、网络命名空间、名称解析、监听与端口路径。

**相关内容**：[容器互访的路径](#容器互访的路径)、[常用指令](#常用指令)、[容器原理](./container-principles.mdx#namespace)。

<details>
<summary>参考回答</summary>

**先确认应用运行与监听，再从发起请求的一侧按网络、名称、端口、协议逐段定位。** 用 `inspect` 核对网络模式和共同网络；同一自定义 bridge 通常按容器名和容器端口访问，不必绕宿主发布端口。`localhost` 指向当前网络命名空间，不能把 A 的回环地址当成 B。

名称解析失败时对照目标 IP；连接失败时检查监听地址、容器端口、路由与防火墙。`-p` 是另一条宿主端口发布路径，不会替服务启动监听。传输连接成功后仍要核对 TLS、鉴权和业务响应。

</details>
