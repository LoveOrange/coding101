# 容器原理

**Linux 容器**是一组受隔离和资源约束的进程，它们仍由宿主的 Linux 内核调度。理解容器，需要分清三个问题：进程能看到什么、能使用多少资源，以及读写的是哪一层文件。这分别对应 Namespace、cgroup 和分层文件系统，也决定了容器与虚拟机的区别。

## 1. 面试核心 {#core}

- Linux 容器**共享宿主内核**，虚拟机则运行独立的客户内核。这一差别影响启动过程、资源开销和安全边界。[卡](#container-vs-vm)
- Namespace 隔离进程**能看到的资源**，cgroup 统计并约束进程**能使用的资源量**，两者解决的问题不同。[卡](#namespace-cgroups)
- cgroup v2 的 `cpu.max` 限制 CPU 时间配额，配额耗尽后会**限流**；`memory.max` 限制内存，回收不足时可能触发 **OOM**。
- OverlayFS 将只读下层和可写上层合并，**修改下层文件内容时先复制到上层**，原镜像内容得以保留。
- 容器共享内核，安全还需要**限制权限和系统调用**：capabilities 拆分特权，seccomp 过滤系统调用。[卡](#container-security-boundary)

## 2. 容器与虚拟机 {#容器与虚拟机}

容器直接运行在宿主内核上，虚拟机则先运行一个客户操作系统，再由客户内核管理应用。因此，容器省去了启动客户内核和系统服务的步骤，但隔离也依赖大家共用的内核。

| 维度 | Linux 容器 | 虚拟机 |
| --- | --- | --- |
| 运行对象 | 宿主内核调度的进程 | 虚拟硬件上的客户操作系统 |
| 内核 | 与宿主共享 | 客户系统独立运行 |
| 启动工作 | 创建隔离环境并启动程序 | 启动客户内核和系统服务 |
| 资源开销 | 进程和隔离机制的开销 | 另有客户操作系统的开销 |
| 安全边界 | 依赖共享内核和权限配置 | 依赖虚拟化边界及其实现 |
| 系统兼容 | 程序须兼容所用内核与架构 | 客户系统须适配虚拟硬件 |

这不代表任何容器都比虚拟机启动快。镜像拉取和应用初始化仍要花时间，虚拟机也可以通过快照缩短启动过程。比较启动耗时，要让两者运行相同的工作负载，并明确是否计入镜像下载。

Linux 容器在 macOS 上运行时，需要 Linux 虚拟机。容器共享的是该虚拟机的内核。

## 3. Namespace {#namespace}

**Namespace（命名空间）**让不同进程看到不同的资源视图。例如，两个容器使用不同的 Network Namespace 时，可以各自监听 8080 端口，而不会争用同一组端口。它隔离的是进程所见的环境，并不负责限制 CPU 或内存用量。

| 类型 | 隔离对象 |
| --- | --- |
| PID | 进程 ID 与可见进程范围 |
| Network | 网络设备、路由、协议栈和端口 |
| Mount | 挂载点 |
| UTS | 主机名和 NIS 域名 |
| IPC | System V IPC 与 POSIX 消息队列 |
| User | 用户、组 ID 和对应特权范围 |
| Cgroup | 可见的 cgroup 根路径 |
| Time | 单调时钟与启动时钟的偏移 |

隔离视图只是建立容器环境的一部分。Mount Namespace 隔离挂载视图后，运行时还要设置根目录和具体挂载；Network Namespace 提供独立网络视图后，还要通过 veth、网桥或路由建立网络连接。仅仅创建 Namespace，不会自动完成这些配置。

排查时，`ls -l /proc/<pid>/ns` 可以查看进程所属的 Namespace 标识，`nsenter -t <pid> -n ip addr` 则在目标进程的网络视图中查看地址。`docker exec` 也是让运行时新建一个容器内进程，并不会另建一台虚拟机。Linux 运行时可用 `setns()` 加入已有 Namespace；其中 PID Namespace 的加入对后续创建的子进程生效。

容器可以显式共享部分 Namespace。例如 `--network=host` 使用宿主网络视图。

## 4. Cgroups {#cgroups}

**cgroup（控制组）**把进程分组，按组统计和限制资源用量。即使某个容器看不到其他容器，它们仍可能争用同一台机器的 CPU 和内存，cgroup 就用来约束这种资源使用。下面的文件名以 cgroup v2 为准。

| 文件 | 含义 |
| --- | --- |
| `cpu.max` | 每个周期内可用的 CPU 时间 |
| `cpu.weight` | 竞争 CPU 时的相对权重 |
| `cpuset.cpus` | 允许使用的 CPU 集合 |
| `memory.max` | 内存硬上限 |
| `memory.current` | 当前内存用量 |
| `memory.events` | 内存压力、OOM 与 OOM kill 事件计数 |
| `io.max` | 指定块设备的带宽与 IOPS 上限 |
| `pids.max` | 任务数量上限，线程也计入 |

`cpu.max` 的两个数分别表示配额和周期，单位是微秒。`cpu.max=50000 100000` 表示组内任务每 100 ms 合计可用 50 ms 的 CPU 时间，相当于半个 CPU 的时间配额。配额用完后，任务要等待后续周期，所以宿主 CPU 还有空闲，容器也可能被限流。排查时可以查看 `cpu.stat` 中的 `nr_throttled`，确认是否发生了配额限流。

内存达到 `memory.max` 后，内核会先尝试回收；回收仍无法满足分配时，可能触发组内内存不足（OOM）处理。判断容器是否因此退出，要结合 `memory.events` 和运行时状态。退出码 137 通常表示进程收到了 SIGKILL，手工强杀、停止超时也能产生这个值，不能只凭它认定发生了 OOM。

cgroup v1 允许 CPU、内存等控制器使用不同的层级，v2 则使用统一层级，父级约束也会限制子级。v2 默认按进程分组，threaded 模式支持部分线程级控制。实际使用哪个版本，要看宿主系统的配置。

使用 Docker 时，可以通过 `--cpus=1.5` 和 `--memory=512m` 设置 CPU、内存限制，通过 `--pids-limit=100` 限制任务数量。这里的任务也包含线程，因此它不只是限制进程数。

## 5. 联合文件系统 {#联合文件系统}

**OverlayFS** 将多层目录合并成应用可见的一个文件系统视图。它让多个容器共享只读镜像内容，同时把各自的修改保存在独立的可写层。

- `lowerdir` 提供只读下层。
- `upperdir` 保存新增和修改后的文件。
- `merged` 是应用看到的挂载视图。

读取文件时，如果上下层存在同名文件，应用看到的是上层文件。修改下层文件内容时，会先把它复制到上层，再修改这份副本，这个过程叫 **copy-up**。因此，一个容器的修改不会直接改掉其他容器共享的镜像文件。仅修改元数据时，行为还取决于 `metacopy` 配置。

删除下层文件时，OverlayFS 会创建一个叫 **whiteout** 的删除标记，让应用看不到原文件，下层镜像中的内容仍然保留。因此，在容器里删除文件，不等于从镜像中移除了那部分数据。需要独立保存的持久数据应使用卷，具体方式见 [Docker 镜像与 Dockerfile](./docker-images.mdx#容器的数据存储)。

## 6. 容器安全边界 {#容器安全边界}

Namespace 隔离了资源视图，但容器进程仍然会调用宿主内核。要限制它能做什么，还需要控制权限、系统调用和宿主资源访问。

**capabilities** 将 root 权限拆成可以分别授予的能力，避免应用为一项特权操作获得全部 root 权限。**seccomp** 按策略过滤系统调用，AppArmor、SELinux 则进一步约束文件和资源访问。这些机制分别限制不同的操作范围，需要配合使用。

在容器内使用非 root 用户，可以降低应用进程的权限。User Namespace 还可以把容器 UID 映射到宿主的普通 UID；Docker rootless 模式则让守护进程也以非 root 身份运行。因此，容器里的用户不是 root，并不代表 Docker 守护进程也没有 root 权限。

`--privileged` 会显著扩大容器权限，挂载 Docker socket 也会向容器暴露守护进程的控制能力。评估安全边界时，要把这些配置一起考虑进去。运行不可信代码时，还需评估独立虚拟机等隔离方案。

## 7. 面试题 {#面试题}

### 7.1 容器和虚拟机有什么本质区别？ {#container-vs-vm}

**考察重点**

- 是否共享内核：容器是隔离的进程，虚拟机虚拟了硬件。
- 由此推出启动速度、开销、隔离强度和可运行系统的差异。

**相关内容**：[容器与虚拟机](#容器与虚拟机)、[Namespace](#namespace)、[Cgroups](#cgroups)。

<details>
<summary>参考回答</summary>

**Linux 容器共享宿主内核，虚拟机有独立的客户内核。**

容器通过 Namespace 隔离资源视图，通过 cgroup 限制资源用量，再由运行时设置根文件系统，应用本身仍是宿主内核调度的进程。

因此，容器省去了客户内核和系统服务的开销，但实际启动速度还取决于镜像拉取和应用初始化。虚拟机多了一层虚拟化安全边界，容器则依赖共享内核和权限策略；两者的隔离能力都要结合具体实现评估。

</details>

### 7.2 容器是怎样实现隔离和资源限制的？Namespace 和 Cgroups 分别解决什么问题？ {#namespace-cgroups}

**考察重点**

- 各类 Namespace 隔离的内容；Cgroups 的主要控制器。
- 内存超限与 CPU 限流的表现；v1 与 v2 的区别；`docker exec` 的原理。

**相关内容**：[Namespace](#namespace)、[Cgroups](#cgroups)、[联合文件系统](#联合文件系统)。

<details>
<summary>参考回答</summary>

**Namespace 隔离资源视图，cgroup 约束资源用量。**

PID、Network、Mount Namespace 分别隔离进程、网络和挂载视图。`docker exec` 让运行时在容器内启动新进程，运行时可以通过 `setns()` 加入已有 Namespace。

cgroup v2 的 `cpu.max` 按周期限制 CPU 时间，配额耗尽后会限流；内存达到 `memory.max` 时先尝试回收，回收不足可能触发 OOM。退出码 137 也可能来自其他 SIGKILL，需要结合 OOM 事件确认。`pids.max` 则限制包含线程在内的任务数。

v1 可以有多个控制器层级，v2 使用统一层级。父级的资源上限同样约束子级。

</details>

### 7.3 容器内使用非 root 用户后，还需要哪些安全限制？ {#container-security-boundary}

**考察重点**：用户映射、权限与系统调用边界。

**相关内容**：[容器安全边界](#容器安全边界)。

<details>
<summary>参考回答</summary>

**还需要限制 capabilities、系统调用和宿主资源访问。**

非 root 用户降低的是进程的用户权限，不能替代 seccomp 对系统调用的过滤，也不能替代安全模块对资源访问的限制。User Namespace 可以提供 UID 映射，rootless 模式还降低守护进程权限。由于容器仍共享内核，配置这些限制后也需要评估内核攻击面。

</details>
