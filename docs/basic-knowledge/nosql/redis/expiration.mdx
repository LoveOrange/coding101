# Redis 过期

**TTL**（Time to Live）是键的剩余有效时间。Redis 用过期机制让临时数据到期失效，但到期、实际清理和业务任务执行，并不是同一件事。理解 Redis 6、7 的过期机制，要能判断更新值会不会改变 TTL，也要能解释为什么过期通知不能保证订单准点取消。

## 1. 面试核心 {#core}

- `SET key value EX 60` **同时写入值和 60 秒有效期**，避免写值成功后没来得及设置期限。
- `TTL` 返回 **-1 表示键没有期限，-2 表示键不存在**。[卡](#ttl-update)
- 普通 `SET` 覆盖值会**清除原 TTL**，`SET ... KEEPTTL` 保留原期限；`INCR`、`HSET` 等内部更新不会清除整键 TTL。[卡](#ttl-update)
- Redis 通过**访问时检查和主动抽样**清理过期键，实际清理可能晚于到期时刻。[卡](#expired-key-cleanup)
- 过期通知在**实际处理过期删除时**产生，且 Pub/Sub 断线期间的消息会丢失，不能独自承担可靠任务调度。[卡](#expiration-notifications)

## 2. 写入值与 TTL {#写入值与-ttl}

写入有期限的数据时，用一条 `SET` 命令同时保存值和有效期。例如下面的键在写入后 60 秒到期：

```redis
SET demo:code 123456 EX 60
TTL demo:code
```

`TTL demo:code` 返回剩余秒数，所以结果会随查询时间递减。需要毫秒精度时用 `PTTL`。两者都有两个特殊返回值：-1 表示键存在但没设期限，-2 表示键不存在。

如果拆成 `SET` 和 `EXPIRE`，进程可能在写值成功后、设置期限前退出。这样原本只想保存 60 秒的数据，就变成了没有期限的键。

## 3. 更新与清理 {#更新与清理}

普通 `SET` 会替换键值，也会清除原有 TTL。接着上面的例子执行：

```redis
SET demo:code 654321
TTL demo:code
```

这次 `TTL` 返回 -1，`demo:code` 不再自动过期。Redis 6.0 起可以用 `SET ... KEEPTTL` 在替换值时保留原期限；如果希望从更新时重新计时，就明确使用 `EX` 或 `PX` 设置新期限。

`INCR`、`LPUSH` 和 `HSET` 修改键内数据时，会保留整键 TTL，不会因为一次递增或字段更新就重新计时。`PERSIST` 则专门用来清除期限。Redis 7.0 起，`EXPIRE` 还支持按条件修改期限：

| 条件 | 设置期限的条件 |
| --- | --- |
| NX | 当前没有期限。 |
| XX | 当前已有期限。 |
| GT | 新期限比当前更晚。 |
| LT | 新期限比当前更早。 |

`GT`、`LT` 比较时，把没有期限的键视为到期时间无限远。例如给已有期限的键执行 `EXPIRE key seconds GT`，只有新期限更晚才会成功，可以避免续期操作意外缩短有效期。

## 4. 过期清理与时钟 {#过期清理与时钟}

Redis 把访问检查和定期抽样结合起来清理过期键。**被动过期**，也叫惰性删除，是访问键时才检查并处理过期；**主动过期**则定期抽样检查带期限的键，把一直没人访问的过期数据也清掉。

主动清理有执行时间预算，不能一直占着执行线程。因此，键的有效期已经结束时，内存未必立即释放；到期失效和实际清理要分开理解。

Redis 保存的是绝对 Unix 到期时间，停机不会暂停计时。比如一个键还有 60 秒到期，Redis 停机两分钟后再载入，它已经过期，不能重新获得 60 秒有效期。同理，主机时钟发生跳变也会影响到期判断。

主从复制时，由主节点产生过期删除操作，再传播给副本并记录到 AOF。副本仍保留到期信息，等它被提升为主节点后，就能独立处理过期。

## 5. 过期通知与任务调度 {#过期通知与任务调度}

过期通知既不能保证准时，也不能保证一定收到。它属于通过 Pub/Sub 发布的键空间通知，产生时刻是 Redis 实际处理过期删除的时候；如果键还没被清理，通知就会延后。订阅客户端断线期间的消息也不会等重连后补发。

因此，可以用通知观察事件，或触发允许偶尔遗漏的刷新。订单到期取消这类任务则要持久化到期时间和任务状态：消费者按状态执行，失败后重试，再用定期扫描找出遗漏任务。这样即使通知丢失，任务也有恢复依据。

## 6. 使用边界 {#使用边界}

大量键集中失效会增加回源流量。TTL 抖动和加载合并见[缓存穿透、击穿、雪崩与热点 Key](./cache-penetration-stampede-avalanche-hotkeys.mdx)。

验证码等业务状态还应记录自己的有效期。键消失可能是到期，也可能是淘汰或故障恢复造成的，不能只凭「键不存在」判断业务发生了什么。需要到期执行的动作，应保留可重试的任务状态。

<summary>参考回答</summary>

**Redis 用访问检查和主动抽样清理过期键，实际删除可能晚于到期时刻，所以 TTL 不是精确的任务调度器。**

清理有执行预算，内存释放与通知可晚于到期时刻。TTL 定义键的有效期，业务调度还需确认和恢复机制。因此，可靠到期任务应持久化任务状态并补偿执行。
