# 缓存穿透、击穿、雪崩与热点 Key

缓存穿透、击穿和雪崩是三种让缓存挡不住请求的情况，结果都是流量集中打到数据库；热点 key 和大 key 则不一定穿过缓存，而是把单个 Redis 节点的 CPU、带宽或内存耗尽。区分它们的关键是看流量从哪来、影响多大范围：穿透查的是根本不存在的数据，击穿是一个热点 key 失效，雪崩是大量 key 或整个缓存同时失效。

穿透、击穿和雪崩都需要限制回源总量，保护数据库；热点 key 和大 key 还要控制 Redis 节点的资源开销。

## 1. 面试核心 {#core}

- 穿透是**持续查询不存在的数据**，用空值缓存和布隆过滤器减少回源。[卡](#penetration-breakdown-avalanche)
- 击穿是**单个热点 key 失效**引发并发加载，用 singleflight 把同一个 key 的加载合并成一次。
- 雪崩是**大量 key 同时到期或缓存节点故障**，用 TTL 随机抖动分散到期时间，用回源限流保护数据库。
- 热点 key 固定路由到**同一个分片**，命中率再高也受单节点资源限制，可以用本地缓存分担读取。
- Redis 4.0 起提供 `UNLINK`，把**键的摘除和值的内存回收分开**，减少删除大 key 时主线程的停顿。[卡](#big-key-unlink)

## 2. 缓存穿透 {#缓存穿透}

**缓存穿透**是请求的数据在缓存和数据库里都不存在，每次都查不到、也就没有东西可以缓存，于是请求一直落到数据库。无效 ID、随机生成的 key、已经删除的对象都会造成穿透；如果是有人刻意构造请求，数据库压力会持续上升。

处理的思路是在越靠前的地方拦下越好：

- 入口先检查参数格式、租户和访问权限，明显不合法的请求不往下走。
- 对确认不存在的对象，缓存一个短期的空值，也叫**负缓存**。
- 用布隆过滤器拦截「确定不在集合里」的 ID，见下一节。
- 对异常来源限流，并按查询结果（命中、空值、失败）分别监控回源量。

使用负缓存时，要区分「数据不存在」和「数据库查询失败」。如果查询超时也被当成空值缓存起来，真实存在的数据在这段时间里就会被当成不存在。另外，新增对象后要清掉对应的负缓存，否则新数据要等空值过期才能被读到。

## 3. 布隆过滤器维护 {#布隆过滤器维护}

**布隆过滤器**是一种用位数组判断「元素是否在集合里」的结构：加入一个元素时，用多个哈希函数算出几个位置并置为 1；查询时检查这几个位置，只要有一个是 0，元素就一定不在集合里。多个元素会共用一些位，所以一个从没加入过的元素，也可能恰好碰上全是 1 的位置，这就是误判。反过来，已加入元素的位只要都还在，查询就不会漏掉它。

这个「不会漏判」有前提：元素确实已经加进了过滤器。数据库新增一条记录、还没同步到过滤器时，过滤器会把这个 ID 判为不存在，新数据就查不到了。所以新增记录要同步写入过滤器；整体重建时，可以先构建新过滤器、补齐重建期间的增量，再切换过去，重建期间保留回源或双读策略。

普通布隆过滤器不支持删除。把一个元素对应的位清零，可能同时清掉其他元素共用的位，那些元素就会被漏判。需要删除能力时，选计数布隆过滤器等支持删除的结构。

Redis 6、7 里的 `BF.*` 命令来自 RedisBloom 模块，不属于核心 Redis。部署前要确认实例加载了这个模块。

## 4. 缓存击穿 {#缓存击穿}

**缓存击穿**是一个热点 key 失效的瞬间，大量并发请求同时发现未命中，同时去数据库加载同一份数据。查询本身没问题，问题在于同一个昂贵的查询被执行了成百上千次。

**singleflight** 是解决这个问题的常见做法：同一个 key 同一时间只允许一个请求回源，其他请求等待并共享它的结果。等待的请求要设置队列上限和超时，否则回源一慢，等待的请求会越积越多。要注意进程内的 singleflight 只能合并本实例的请求，有 100 个实例就可能有 100 次回源，多实例部署时还需要全局的回源限额或跨实例协调。

另一种做法是**逻辑过期**：Redis 里的 key 不设 TTL，把业务上的到期时间存进值里。读到已经逻辑过期的值时，先把旧值返回给调用方，同时启动后台刷新。这样，刷新期间仍有旧值可读，代价是调用方拿到的可能不是最新数据，所以只适合允许短暂读取旧数据的接口。冷启动时还没有旧值可返回，仍然需要合并加载和失败处理。

用分布式锁做互斥重建时，锁的租约边界见[分布式锁](./distributed-lock-conditions-boundaries.mdx)。

## 5. 缓存雪崩 {#缓存雪崩}

**缓存雪崩**是大量 key 在同一时间失效，或者缓存整体不可用，原本由缓存承接的请求一起落到数据库。前一种常见于同一批数据用相同的 TTL 写入，比如凌晨批量预热的数据会在同一时刻过期。

- 基础 TTL 加上随机抖动，让同一批 key 的到期时间分散开。
- 预热分批进行，限制每批的回源量。
- 对数据库回源设置并发和队列上限。
- 非关键接口返回可接受的旧值，或者明确的降级结果。
- 缓存和数据库分别做容量测试，知道数据库在没有缓存时能扛多少。

TTL 抖动只能解决集中到期，解决不了节点故障。Redis 节点挂掉时，要靠高可用部署和回源保护一起兜住。

## 6. 热点 key {#热点-key}

**热点 key** 是访问特别集中的 key，可能让负责它的节点先达到容量上限。Redis Cluster 里一个 key 只会路由到一个分片，即使命中率是 100%，这个分片的 CPU 和网络带宽也是上限。

判断热点要按业务 key 采样请求量，再结合各分片的 CPU 和网络流量看。读热点可以在应用进程里加本地缓存分担。也可以把一个热点 key 复制成多个副本 key，读取时随机选一个，但要确认这些副本落在不同的槽和节点上。

分散副本时还要看 key 的 hash tag，也就是 `{...}` 包起来的部分。存在有效 hash tag 时，Redis 只用这部分计算槽。只改 tag 外面的后缀，比如 `{item:1}:a` 和 `{item:1}:b`，它们仍在同一个槽里，热点并没有分散。副本 key 更新时，还要处理所有副本的失效和版本一致。

写热点如果可以合并，比如计数，可以拆成多个分片计数再汇总。要求全局严格顺序的写入拆不开，只能统一协调。

## 7. 大 key {#大-key}

**大 key** 是值特别大，或者集合元素特别多的 key。它会放大内存占用、网络传输、删除和集群迁移的成本。Redis 用单线程执行命令，对一个大集合做全量读取，会长时间占住执行线程，其他请求都要排队。

所以要控制单个值的大小和集合的元素数量。需要遍历时用 `SCAN` 家族命令分批取，并限制每次返回的规模，游标的语义见 [SCAN 游标遍历](./data_structure.mdx#scan-游标遍历)。

默认配置下，`DEL` 在主线程里同步释放值占用的内存。集合元素越多，释放时的停顿可能越长。Redis 4.0 起可以用 `UNLINK key`：主线程只把 key 从键空间里摘掉，真正的内存释放交给后台线程。值很小时，Redis 也可能直接在主线程释放。后台回收仍然要消耗 CPU 和内存带宽，批量删除大 key 时要控制速度。

## 8. 防护链路 {#防护链路}

无论什么原因造成缓存失效，都要限制回源总量，避免数据库随之过载。一个请求从进入到回源，可以依次经过这几层：

1. 校验参数和权限，拦截无效 key。
2. 按来源和业务 key 限制请求速率。
3. 用本地缓存或 Redis 承接命中的请求。
4. 合并同一个 key 的加载，并限制等待的请求数。
5. 用回源并发上限、连接池和查询超时控制数据库压力。
6. 失败时返回约定好的旧值、缺省结果或明确的错误。

每一层的等待时间加起来，不能超过接口的总超时预算。故障恢复时也一样，预热和重试都要限速。

## 9. 故障演练 {#故障演练}

这些保护措施是否有效，要靠演练验证。分别模拟热点 key 过期、大批 key 同时过期和 Redis 不可用，也要覆盖数据库变慢、客户端连接池耗尽的情况。

演练时观察回源 QPS、加载等待时间和各分片的 CPU、网络，再对照数据库的连接等待和接口尾延迟。恢复阶段尤其要限制预热速度，否则重建流量会再次把数据库压满。

## 10. 常见问题 {#常见问题}

### 10.1 热点 key 不设过期时间，就不需要重建了吗？ {#永久-key-与重建}

不设过期时间只能避免这个 key 因 TTL 到期而消失，不能保证它一直在。内存淘汰、节点故障和人为删除仍然会让 key 消失，高频数据本身也需要更新。所以永不过期的 key 仍要设计重建保护。

### 10.2 布隆过滤器判断「可能存在」后，还要查询数据源吗？ {#布隆过滤器的查询边界}

要。布隆过滤器没有保存对象内容，而且「可能存在」也可能是误判，仍需查询缓存或数据库。如果结果是「确定不存在」，则可以拦截请求，前提是过滤器已完整覆盖需要查询的数据。新增和重建时如何保证这一点，见[布隆过滤器维护](#布隆过滤器维护)。

## 11. 面试题 {#面试题}

### 11.1 缓存穿透、击穿和雪崩分别如何处理 {#penetration-breakdown-avalanche}



**考察重点**

- 三类问题的流量来源和影响范围。
- 负缓存、Bloom filter、合并加载和 TTL 抖动。
- 回源限流、降级与故障恢复。

**相关内容**：[缓存穿透](#缓存穿透)至[故障演练](#故障演练)。

<details>
<summary>参考回答</summary>

**穿透用参数校验、空值缓存和布隆过滤器减少无效回源；击穿用 singleflight 或互斥重建合并热点加载；雪崩用 TTL 抖动分散到期，并限制总回源量。**

穿透查的是不存在的数据，要在入口拦截，空值缓存要区分「不存在」和「查询失败」。击穿是单个热点 key 失效，多实例部署时还需要全局回源限额。雪崩如果是 Redis 整体故障，TTL 抖动无效，要靠高可用、降级和数据库容量保护。

热点 key 与大 key 要按分片 CPU、网络和命令延迟诊断。无论哪种问题，恢复阶段都要限制预热速度。

</details>

### 11.3 热点 key 和大 key 如何区分，UNLINK 能消除哪些删除成本？ {#big-key-unlink}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：访问频率、对象体积与异步释放。

**相关内容**：[热点 key](#热点-key)、[大 key](#大-key)。

<details>
<summary>参考回答</summary>

**热点 key 看访问频率，大 key 看值的大小和元素数量，一个 key 可以同时是两者。**

`UNLINK` 在主线程里只把 key 从键空间摘除，较重的内存释放交给后台线程，因此减少了主线程释放大对象时的停顿。但释放的成本并没有消失，后台回收仍然消耗 CPU 和内存带宽，批量删除时要限速。

</details>
