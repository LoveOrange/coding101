# 缓存一致性

**缓存一致性**说的是缓存里的副本和数据库里的权威数据之间有多大差异、差异能持续多久。缓存和数据库分别更新时，两步操作之间会有时间差，还可能有一步失败。设计缓存时，要明确旧值最多允许存在多久、故障后怎样恢复一致。

理解这件事要抓住三点：更新时为什么先提交数据库再删缓存，删完缓存为什么还会被旧值填回去，删除失败后靠什么继续重试。

## 1. 面试核心 {#core}

- Cache-aside 未命中时回源数据库，更新时**先提交数据库，再删除缓存**。[卡](#update-db-then-delete-cache)
- 缓存删除成功后，一个更早开始的慢读请求**仍可能把旧值回填进缓存**。[卡](#stale-refill-version)
- TTL 从缓存写入时开始计时，所以**旧值回填会让旧副本重新获得一整段 TTL**。[卡](#stale-refill-version)
- 删除失败要靠**持久化的失效事件**来重试；Redis Pub/Sub 断线期间的消息会丢，不能单独承担这件事。[卡](#durable-invalidation)
- 必须读到最新值时，到**数据库主库发起新查询**；MySQL RR 事务里已经建立的快照仍会返回旧版本。

## 2. 适合缓存的数据 {#适合缓存的数据}

适合放进缓存的，是读得多、并且允许短暂读到旧值的数据，比如商品详情、用户资料。回源越贵，缓存的收益越大。反过来，如果每次判断都必须基于当前最新状态，比如扣库存前检查余量，这个判断就应该交给数据库完成。

决定缓存一类数据之前，先把这几件事定下来：

- 数据库是权威来源，缓存只保存随时可以重建的副本。
- 接口能接受多久的旧值，要和业务方约定清楚。
- 每类 key 的大小、访问频率和 TTL 要有记录。
- 缓存整体丢失时，数据库能承受多大的重建流量，并且有办法限流。

明确这些条件后，才能判断 TTL、失效重试等措施是否满足业务要求。

## 3. Cache-aside {#cache-aside}

**Cache-aside**（旁路缓存）是由应用自己负责缓存和数据库读写的模式，缓存本身不知道数据库的存在：

```text
读取：查缓存 → 未命中时查数据库 → 回填缓存
更新：提交数据库 → 删除缓存
```

更新时删除缓存而不是直接写入新值，是因为删除之后，下一次读取会走统一的回源逻辑重建缓存，重建只有这一条路径。如果改成直接更新缓存，多个写入者到达缓存的顺序可能和它们提交数据库的顺序不同，就得额外协调顺序，[常见问题](#直接更新的乱序)里有具体例子。

TTL 给每个缓存副本设了寿命上限，即使后面讲的竞态让旧值留了下来，到期后也会被清掉。不过过期后回源的那次数据库查询，本身也要读到足够新的数据，否则只是把旧值换个时间再写一遍。

## 4. 更新顺序 {#更新顺序}

更新时应该先提交数据库，再删缓存。反过来先删缓存的话，数据库里还是旧值，这时有读请求进来，缓存未命中，就会从数据库读到旧值并回填；之后写事务才提交，缓存里留下的就是一份旧副本，要等 TTL 到期才会消失。

先提交再删除，可以避免回源发生时写事务尚未提交的问题。不过，回源查询仍可能受旧快照或副本延迟影响，见[强一致读取](#强一致读取)。另一种风险是数据库提交成功了，删除缓存却失败了，比如 Redis 超时。数据库提交和 Redis 删除是两个系统里的两步操作，本地数据库事务只能保证前一步，所以删除失败后必须有办法继续重试：

- 每个缓存副本都设置符合业务要求的 TTL，作为最后的兜底。
- 同步删除限制重试次数和耗时，不让写请求一直卡在缓存上。
- 用持久化的失效事件记下「这个 key 还需要删除」，供后续重试，做法见[可靠失效事件](#可靠失效事件)。
- 事件积压、缓存与数据库长期存在版本差异时，触发监控告警。

## 5. 并发竞态 {#并发竞态}

先提交再删除也不能完全避免旧值，因为读请求可能在删除之前就已经读到了旧值：

1. 读请求未命中缓存，从数据库读到旧值。
2. 写请求提交新值，随后删除缓存。
3. 读请求这时才恢复执行，把手里的旧值写进缓存。

第 3 步发生在删除之后，所以删除挡不住它。窗口有多大，取决于数据库查询有多慢、进程会不会暂停（比如 GC 停顿）。它的触发条件比「先删缓存」苛刻：读请求要在写请求提交之前读完数据库，又要在删除之后才写缓存。

怎么处理，取决于业务能接受多久的旧值：

- 短 TTL 缩短一份旧副本最多能留多久。
- 版本校验让已经落后的回填写不进去，见下一节。
- 热点 key 的加载合并成一个请求，减少同时在跑的旧查询。
- 余额、库存这类关键判断交给数据库，用一条语句原子完成检查和更新。

## 6. 旧值回填与版本水位 {#旧值回填与版本水位}

旧值回填的危害比看上去大，因为 TTL 从回填那一刻才开始计时。假设数据库更新后，一个持有旧结果的查询又暂停了 30 秒，恢复时用 60 秒的 TTL 回填。从数据库更新到这份旧副本过期，就经过了约 90 秒，超过了 TTL 本身。

直觉上的办法是在缓存值里带一个版本号，回填时比较版本，旧的不写。问题在于删除缓存时，版本号也跟着被删掉了。缓存里什么都没有，旧回填找不到可比较的新版本，照样能写进去。

所以版本信息要和缓存值分开存。**版本水位**是为每个 key 单独保存的最低可接受版本：失效事件在清除旧副本的同时，原子地把水位提高到新版本；回填用一段脚本先比较版本和水位，只有版本不低于水位的数据才写入。水位要保留足够久，直到所有可能还在跑的旧加载请求都已经结束。

这套方案要成立，还得限制单次加载最多能跑多久，并考虑失效事件本身的投递延迟。它是读写双方共同遵守的业务协议，不是给缓存值加一个 `version` 字段就能完成的。

## 7. 可靠失效事件 {#可靠失效事件}

删除失败后要能继续重试，前提是「需要删除这个 key」被持久化下来。常见做法是 **Outbox**：在同一个数据库事务里，同时写入业务数据和一条失效事件记录。事务提交后，消费者读取事件、删除缓存，成功后再确认事件。删除同一个 key 执行多少次结果都一样，所以消费者可以放心重试。

另一种做法是订阅数据库的 binlog，从数据变更里推导出要删除的 key。这时要保存消费位点，中断后能接着消费，并监控积压。事件可能乱序到达，维护版本水位时不能让旧事件把较新的水位改回去。

Redis Pub/Sub 不能单独承担这个角色。它是至多一次投递：订阅端断线期间发布的消息不会保留下来等它重连后补收，这段时间的失效通知就丢了。

## 8. Read-through 与 Write-through {#read-through-与-write-through}

Cache-aside 之外，还有几种把协调工作交给缓存组件的模式：

- **Read-through**：缓存组件在未命中时自己加载数据，应用只和缓存打交道。
- **Write-through**：写入缓存组件时，由它同步写入权威存储。
- **Write-behind**：缓存组件先接收更新，再异步写回权威存储。

这些模式把一致性的责任从应用代码移到了数据访问组件里，问题本身并没有消失。Write-behind 尤其要小心：更新在写回之前只存在于缓存中，需要持久化的队列、写入顺序控制和失败恢复。只有业务能接受数据异步落库时，才适合用它。

## 9. 多级缓存 {#多级缓存}

加上进程内缓存后，进程内缓存、Redis 和数据库就是三份状态。只删掉 Redis 里的 key，各个应用实例内存里的旧值还在，同样需要失效。

Redis 6.0 起提供服务端辅助的客户端缓存（client-side caching）：Redis 记录客户端读过哪些 key，这些 key 被修改时，向跟踪连接发送失效通知。跟踪连接断开后，客户端收不到这期间的通知，所以要清空相关的本地缓存，或者重新验证。

不用这项功能、自己维护本地缓存时，同样需要失效广播加 TTL。不管有几层，每一层都要有一条故障之后能重新收敛的路径。

## 10. 强一致读取 {#强一致读取}

必须读到刚提交的新值时，绕开缓存，到数据库主库发起一次新查询。这里有两个条件容易忽略：MySQL 在可重复读（RR）隔离级别下，一个事务里已经建立的快照会继续返回旧版本；从只读副本读取，又会受复制延迟影响。

库存或余额这类「先检查再更新」的操作，可以直接写成条件 `UPDATE`，让检查和更新在同一条数据库语句里完成，中间没有其他请求插进来的机会。

延迟双删、重试这些手段只能缩小部分缓存竞态。如果真要求缓存和数据库跨系统强一致，需要的是完整的一致性协议。

## 11. 缓存指标 {#缓存指标}

缓存指标要按接口和 key 前缀拆开看，整体数字会掩盖问题：

- 命中率与回源量，反映缓存带来了多少收益。
- TTL 与副本版本，反映旧值会保留多久。
- 加载耗时与并发量，反映重建时数据库的压力。
- 失效事件积压与失败次数，反映故障恢复的进度。
- 定期抽样比对缓存和数据库，发现长期不一致。

整体命中率很高时，个别接口仍可能一直在回源。做缓存故障演练时，要同时观察数据库能不能扛住。

## 12. 常见问题 {#常见问题}

### 12.1 为什么不在更新数据库后直接更新缓存？ {#直接更新的乱序}

更新时直接写缓存，可能让旧值覆盖新值，因为数据库提交顺序和缓存写入顺序可以不同。比如两个写请求在数据库里先提交 A、再提交 B，写缓存时却是 B 先到、A 后到，最后缓存里留下的是旧值 A。改成删除缓存后，新值统一由回源读取，写入者之间不需要再协调顺序。

### 12.2 延迟双删能彻底解决旧值回填吗？ {#延迟双删的适用范围}

不能。**延迟双删**是在更新数据库前后各删一次缓存，第二次删除延迟一段时间执行，用来清掉这段时间里回填的旧值。它只能覆盖一部分情况：旧查询耗时超过预设的延迟时，仍会在第二次删除之后回填。第二次删除也可能失败，所以它替代不了可靠失效事件和 TTL。

## 13. 面试题 {#面试题}

### 13.1 Cache-aside 为什么通常先更新数据库再删除缓存 {#update-db-then-delete-cache}



**考察重点**

- 权威数据、缓存副本与 TTL 的作用。
- 两种更新顺序的并发窗口。
- 删除失败、旧值回填和强一致边界。

**相关内容**：[Cache-aside](#cache-aside)至[强一致读取](#强一致读取)。

<details>
<summary>参考回答</summary>

**先提交数据库再删除缓存，可以避免先删缓存后、写事务尚未提交时，读请求回源并留下旧副本。**

如果先删缓存，写事务提交之前进来的读请求会从数据库读到旧值并回填，缓存里就留下一份旧副本。

先提交再删除也不是万无一失：删除可能失败，删除之前读到旧值的慢请求也可能在删除之后回填。TTL 限制一份副本的寿命，可靠的失效事件让删除失败后可以重试。一致性要求严格的判断应回到数据库完成，还要注意 RR 事务快照和只读副本的复制延迟都会返回旧数据。

</details>

### 13.2 删除缓存后，旧查询为何还能回填旧值，版本字段足够吗？ {#stale-refill-version}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：回填时序、TTL 起点和独立版本水位。

**相关内容**：[旧值回填与版本水位](#旧值回填与版本水位)。

<details>
<summary>参考回答</summary>

**旧查询在删除之前就读到了旧值，只是在删除之后才写入缓存，删除挡不住它。**

回填时 TTL 重新计时，旧值能存在的时间会超过 TTL 本身。只在缓存值里放版本字段不够：删除缓存时版本也一起被删了，旧回填没有可比较的对象。可以为每个 key 单独保存版本水位，失效时原子提高水位，回填时原子比较、拒绝更旧的值。同时还要约定单次加载的最长耗时，并考虑失效事件的投递延迟。

</details>

### 13.3 数据库已提交但缓存删除失败，如何保证后续还能重试？ {#durable-invalidation}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：Outbox、消费位点与幂等删除。

**相关内容**：[可靠失效事件](#可靠失效事件)。

<details>
<summary>参考回答</summary>

**把失效事件和业务数据放在同一个数据库事务里提交（Outbox），让「需要删除」和数据变更一起持久化。**

消费者根据持久化的事件删除缓存，成功后再确认；删除是幂等的，失败可以反复重试。也可以订阅 binlog，这时要保存消费位点并监控积压。Redis Pub/Sub 断线期间的消息会丢失，适合做通知，不能作为唯一的可靠依据。

</details>
