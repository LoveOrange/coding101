# Redis 持久化、复制与集群

Redis 持久化保存恢复数据，复制保留运行副本。Cluster 通过哈希槽将数据分布到多个主节点。本文以 Redis 6、7 为基线，负责恢复点、故障转移和分片边界。

## 1. 面试核心 {#core}

- **持久化方式。** RDB 保存时间点快照，AOF 记录恢复所需的写操作。[卡](#rdb-aof-replication-cluster)
- **AOF 同步。** `appendfsync everysec` 每秒同步 AOF，故障恢复依赖最近已持久化位置。[卡](#aof-rewrite)
- **AOF 文件组织。** Redis 7.0 起，AOF 使用基础文件、增量文件和 manifest。[卡](#aof-rewrite)
- **Sentinel 故障转移。** Sentinel 的 quorum 用于判定客观下线，故障转移授权还需多数票。[卡](#sentinel-quorum)
- **Cluster 分片。** Cluster 有 16384 个槽，MOVED 更新路由，ASK 只临时转发本次请求。[卡](#cluster-redirects)

## 2. RDB {#rdb}

RDB 保存某一时刻的数据集。SAVE 在主线程同步生成快照，会阻塞请求。BGSAVE 通过 fork 子进程在后台保存。

故障恢复到最后一份有效快照。该快照之后的修改缺少恢复依据。快照紧凑，适合备份与整库加载。

后台保存仍有 fork 停顿和写时复制成本。父进程修改共享页时，需要复制对应内存页。写入越密集、子进程运行越久，额外内存压力越大。

## 3. AOF {#aof}

设置 `appendonly yes` 后，Redis 记录 AOF。`appendfsync` 控制同步到磁盘的策略。

| 配置 | 同步方式与代价 |
| --- | --- |
| `always` | 每次写入批次同步，确认延迟受磁盘同步影响。 |
| `everysec` | 后台每秒同步，正常调度下约有一秒未同步窗口。 |
| `no` | 由操作系统安排同步，丢失窗口取决于系统刷盘。 |

磁盘阻塞和同步延期会影响实际落盘进度。因此，约一秒是正常运行窗口，不能视为任意故障下的硬上限。

AOF 重写根据当前数据生成更短的恢复表示。它保留恢复后的状态，省去重复的中间修改。重写期间仍需评估磁盘与内存容量。

## 4. AOF 重写与混合格式 {#aof-重写与混合格式}

Redis 6 重写 AOF 时，子进程生成新文件。父进程继续写旧 AOF，并保存重写期间的增量。新文件补齐增量后，替换旧文件。

Redis 7.0 起改用多文件 AOF。重写时，父进程写新的增量文件，子进程生成基础文件。完成后原子切换 manifest，恢复时按清单加载文件。

Redis 6、7 默认 `aof-use-rdb-preamble=yes`。重写结果以 RDB 保存基础数据，后续增量仍是 AOF 命令。它兼顾基础数据加载与新增操作记录。Redis 7 备份需保持清单及其引用文件一致。

## 5. RDB 与 AOF 恢复顺序 {#同时启用-rdb-与-aof}

两种持久化同时启用时，Redis 重启优先加载 AOF。独立 RDB 仍可作为时间点备份。

恢复演练需校验文件完整性与数据结果。备份应放到独立故障域，避免和运行实例一起损坏。Redis 7.x 备份 AOF 目录时，还需协调重写与 manifest 切换。

## 6. 主从复制 {#主从复制}

副本先同步数据，再消费主节点的命令流。主节点确认写入时，复制默认异步。因此，提升落后副本会丢失它尚未收到的写入。

PSYNC 使用复制 ID 与偏移量识别同步位置。复制历史匹配且 backlog 仍覆盖缺口时，可部分重同步。缺口超出保留范围时，需要全量同步。

全量同步传输数据集，再衔接后续命令流。大数据集会增加主节点、网络和副本加载压力。backlog 容量应结合写入速率与允许断连时长规划。

## 7. 复制确认与落盘确认 {#复制确认与落盘确认}

WAIT 等待本连接此前写入被指定数量副本确认。返回值是实际确认的副本数量。超时返回较小数量时，原写入仍保留结果。

Redis 7.2 起支持 WAITAOF。它等待本连接此前写入在本地或副本完成 AOF 同步。

```redis
SET demo:order paid
WAITAOF 1 1 1000
```

该例要求本地和一个副本同步，最多等待 1000 毫秒。相关节点需开启 AOF。返回两个计数，分别表示本地与副本的完成情况。

确认更多副本可减少丢失风险，但仍需约束提升对象和故障模型。WAIT 与 WAITAOF 都不自动提供强一致复制。

## 8. Sentinel {#sentinel}

Sentinel 监控主从组，并协调主节点故障转移。客户端据此发现新主节点。它管理可用性，数据仍受异步复制窗口影响。

单个 Sentinel 超时判断主节点不可达，标记主观下线。达到 quorum 个 Sentinel 同意后，形成客观下线。执行切换还需获得多数 Sentinel 授权。

例如部署 5 个 Sentinel，quorum 设置为 2。两个同意可判定下线，切换仍需至少 3 个授权。quorum 高于多数时，还需满足更高的 quorum 数量。

客户端应支持主节点地址刷新和连接切换。切换期间的超时与重试，还需业务幂等处理。

## 9. Cluster 与哈希槽 {#cluster-与哈希槽}

Cluster 用 `CRC16(key) mod 16384` 计算槽位。键包含有效 hash tag 时，使用花括号内的部分计算。槽再分配给主节点，主节点可配置副本。

`{user:42}:profile` 与 `{user:42}:orders` 使用相同 tag。因此它们落在同一槽，可参与要求同槽的多键操作。过度复用同一 tag，会把负载集中到一个节点。

MGET、事务和 Lua 的跨键访问需遵守同槽约束。客户端将跨槽读取拆成多次请求时，只获得多次独立操作。

## 10. MOVED 与 ASK 重定向 {#moved-与-ask-重定向}

MOVED 表示当前槽由另一个节点负责。客户端重发请求，并更新槽映射。

ASK 用于槽迁移期间的临时转发。客户端先向目标连接发送 ASKING，再执行原命令。它只处理这一次请求，长期槽映射保持原样。

迁移中多键操作还会遇到 TRYAGAIN 等暂时错误。客户端应使用支持 Cluster 的实现，并限制重试预算。

## 11. Cluster 与网络分区 {#cluster-与网络分区}

Cluster 的异步复制仍存在已确认写入丢失窗口。分区中的旧主可在故障检测生效前短暂接受写入。另一侧提升副本后，这些写入会被丢弃。

少数派一侧失去继续服务的条件。默认 `cluster-require-full-coverage=yes` 时，未覆盖槽会影响整个集群服务。设为 no 后，可继续服务仍被覆盖的槽。

客户端需区分拓扑变化、暂时不可用与业务执行结果未知。写入重试应带幂等依据，并限制总耗时。

## 12. 恢复目标与配置 {#按恢复目标选择配置}

RPO 表示允许丢失的数据量，常以时间衡量。RTO 表示允许的恢复耗时。配置还需考虑是否分片、是否读副本，以及故障域范围。

缓存可从数据库重建时，重点是重建容量和恢复速度。Redis 保存权威状态时，还需独立备份与结果核对。选定策略后，应演练进程、磁盘与主节点故障。

## 13. 常见问题 {#常见问题}

### 13.1 AOF 的恢复边界 {#aof-的恢复边界}

AOF 的恢复点由实际持久化位置决定。异步复制切换还受被提升副本的进度影响。文件损坏需由独立备份恢复，因此应同时规划 RPO 与恢复验证。

### 13.2 多键操作与槽位 {#多键操作与槽位}

Cluster 的多键事务和脚本要求键在同一槽。hash tag 可控制共槽，但会集中负载。客户端自行拆分跨槽操作后，结果分属多次请求。

### 14.4 5 个 Sentinel、quorum=2 时，两个节点能完成自动故障转移吗？ {#sentinel-quorum}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：客观下线与多数授权。

**相关内容**：[Sentinel](#sentinel)。

<details>
<summary>参考回答</summary>

**5 个 Sentinel 中只有两个能互通时，无法完成自动故障转移。**

`quorum=2` 允许这两个节点共同判定主节点客观下线，但切换仍需至少 3 个 Sentinel 的多数授权。quorum 负责故障判定，多数授权负责协调切换。

</details>
