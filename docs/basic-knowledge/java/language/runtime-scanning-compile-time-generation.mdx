# Java 注解处理器

Java 注解处理器在编译期校验程序并生成文件。本文负责处理轮次、生成接口和构建配置。保留策略见 [Java 注解](./annotations-retention-processing.mdx)。运行时调用规则见 [Java 反射](./reflection-method-handles.mdx)。

## 1. 面试核心 {#core}

- 处理器读取 `Element` 和 `TypeMirror`，通过 `Filer` 生成新文件。[卡](#compile-time-annotation)
- 生成的新类型进入后续处理轮次。
- `process` 返回 `true` 表示认领当前注解类型。
- Java 17、21 的 `javac` 默认搜索可用的注解处理器。[卡](#processor-discovery-rounds)
- IoC 容器管理对象创建与依赖，反射支持运行时调用。[卡](#ioc-reflection)

## 2. 运行时扫描 {#运行时扫描}

注解处理器能提前完成部分发现工作。下面以运行时路由注册为例，展示扫描步骤：

1. 确定需要扫描的包、模块或 classpath 位置。
2. 找出候选类并通过类加载器加载。
3. 使用反射读取类和方法上的运行时注解。
4. 校验方法签名、访问权限和配置冲突。
5. 创建对象并把调用信息放入注册表。

```java
for (Class<?> candidate : scanner.findClasses("com.example")) {
    for (Method method : candidate.getDeclaredMethods()) {
        Route route = method.getAnnotation(Route.class);
        if (route != null) {
            registry.register(route.value(), candidate, method);
        }
    }
}
```

框架可在启动时发现新增的标注类。应用只需遵循扫描范围与注解约定。

### 2.1 运行时扫描的成本 {#运行时扫描的成本}

- 启动时需要枚举资源、加载类并解析注解。
- 签名错误和重复配置直到启动才出现。
- classpath、模块和自定义类加载器会增加发现难度。
- 反射结果需要缓存，避免进入请求热路径后重复查找。
- 闭世界编译无法仅从静态调用关系得知所有反射目标，需要额外元数据。

扫描成本取决于候选范围和实现。先限制扫描范围，再评估编译期生成的收益。

## 3. 注解处理模型 {#注解处理模型}

标准注解处理 API 让处理器在编译阶段访问类型、方法、字段和注解。处理器看到的是 `Element`、`TypeMirror` 等语言模型，不需要加载并执行正在编译的业务类。

```java
@SupportedAnnotationTypes("com.example.GenerateMapper")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public final class MapperProcessor extends AbstractProcessor {
    @Override
    public boolean process(
        Set<? extends TypeElement> annotations,
        RoundEnvironment roundEnvironment
    ) {
        if (roundEnvironment.processingOver()) {
            return false;
        }
        TypeElement marker = processingEnv
            .getElementUtils()
            .getTypeElement("com.example.GenerateMapper");

        if (marker == null) {
            return false;
        }
        for (Element element : roundEnvironment.getElementsAnnotatedWith(marker)) {
            generateMapper((TypeElement) element);
        }
        return true;
    }
}
```

处理器由编译器调用，不应在业务代码中手动实例化。构建需要把处理器放到注解处理器路径，或显式指定要运行的处理器。

### 3.1 多轮处理 {#多轮处理}

新源码或 class 文件会触发后续处理轮次。仅生成普通资源文件不会触发新轮次。最后一轮可做汇总和诊断。

因此处理器需要：

- 能识别已经处理过的元素，避免重复生成。
- 不依赖多个处理器之间的执行顺序。
- 在最后一轮停止生成新的类型。
- 对相同输入产生稳定结果，便于增量构建和缓存。

`RoundEnvironment.processingOver()` 可以判断是否进入最后一轮，`errorRaised()` 可以判断此前是否报告过错误。

## 4. 代码生成 {#代码生成}

假设业务声明一个映射接口：

```java
@GenerateMapper
public interface UserMapper {
    UserDto toDto(User source);
}
```

处理器可以通过 `Filer` 生成实现类：

```java
JavaFileObject file = processingEnv
    .getFiler()
    .createSourceFile("com.example.UserMapperGenerated", sourceElement);

try (Writer writer = file.openWriter()) {
    writer.write("""
        package com.example;

        public final class UserMapperGenerated implements UserMapper {
            @Override
            public UserDto toDto(User source) {
                return new UserDto(source.id(), source.name());
            }
        }
        """);
}
```

生成类随后与业务源码一起编译。运行时调用它，与调用普通手写类相同：

```java
UserMapper mapper = new UserMapperGenerated();
UserDto dto = mapper.toDto(user);
```

标准处理器生成新文件，现有源码保持不变。修改编译器内部语法树会绑定具体实现。JDK 和 IDE 升级时需验证兼容性。

### 4.1 编译期报错 {#编译期报错}

处理器可以使用 `Messager` 把错误定位到具体程序元素：

```java
processingEnv.getMessager().printMessage(
    Diagnostic.Kind.ERROR,
    "mapper method must have exactly one parameter",
    methodElement
);
```

`Diagnostic.Kind.ERROR` 会让构建失败。开发者在编译阶段即可发现签名错误。

## 5. 运行时扫描与注解处理器的比较 {#运行时扫描与注解处理器的比较}

| 维度 | 运行时扫描 | 编译期生成 |
| --- | --- | --- |
| 发现时间 | 应用启动或首次使用 | 源码编译时 |
| 错误出现时间 | 启动或运行时 | 构建时 |
| 调用方式 | 常用反射、代理或动态分派 | 生成的普通类型和直接调用 |
| 扩展方式 | 放入运行时 classpath 即可发现 | 需要在编译阶段看到扩展源码或元数据 |
| 启动成本 | 扫描范围越大，成本越高 | 工作移到构建阶段 |
| 动态性 | 更适合运行时插件和未知类型 | 更适合闭世界和固定应用组成 |
| 调试重点 | 类加载、扫描条件、反射权限 | 生成源码、构建配置、处理轮次 |

编译期生成把部分运行工作移到构建阶段。项目还需管理处理器、生成文件和增量编译。

## 6. 混合方案 {#混合方案}

很多框架使用混合方案：

### 6.1 编译期索引与运行时装配 {#编译期索引与运行时装配}

处理器不生成完整调用代码，只生成候选类型清单或资源文件。运行时不再扫描整个 classpath，而是读取索引并加载少量明确类型。

### 6.2 构建分析与运行时扩展 {#构建分析与运行时扩展}

应用内部的 Bean、路由和序列化器在构建时固定。插件仍可通过 `ServiceLoader` 或指定目录发现。常规启动成本与动态扩展因此能分别管理。

### 6.3 生成工厂与运行时选择 {#生成工厂与运行时选择}

处理器生成类型安全的工厂或注册表，运行时仍根据配置选择具体实现。候选类型仍由生成结果限定。

构建时已知的类型可提前生成。部署后加入的插件需要运行时发现。选择应取决于类型何时确定。

## 7. Native Image 与 AOT {#native-image-与-aot}

闭世界编译需要在构建时确定可达代码。反射和动态加载的目标需通过静态分析或元数据表达。

将以下工作提前，有助于减少运行时配置：

- 根据注解生成直接调用代码。
- 生成序列化器、映射器和依赖注入工厂。
- 为仍需反射的成员生成精确注册元数据。
- 在构建阶段检查动态代理接口和资源文件。

启动成本较低且依赖动态插件时，运行时模型仍然适用。AOT 收益需结合构建成本与部署方式评估。

## 8. 处理器发现与认领规则 {#处理器发现与认领规则}

Java 17、21 的 `javac` 默认搜索注解处理器。未指定处理器路径时，会搜索普通 classpath。`-proc:none` 可禁用注解处理。也可显式指定处理器与路径：

```sh
javac --processor-path processor.jar \
  -processor com.example.MapperProcessor \
  -d out -s generated src/com/example/UserMapper.java
```

自动发现使用服务配置或模块的 `provides` 声明。classpath 服务文件名为 `META-INF/services/javax.annotation.processing.Processor`。文件内容是处理器的完整类名。

`process` 返回 `true` 表示认领传入的注解类型。后续处理器不再收到这些已认领类型。返回 `false` 允许后续处理器继续处理。该返回值与编译成功或失败无关。

同一轮次序列中重复创建同名文件会抛出 `FilerException`。生成器应记录已生成类型，避免重复创建。

## 9. 常见问题 {#常见问题}

### 9.1 标准处理器的修改边界 {#标准处理器的修改边界}

标准 API 支持读取语言模型、生成新文件和报告诊断。它没有修改既有 AST 的可移植接口。依赖内部 API 会增加编译器和 IDE 的兼容成本。

### 9.2 生成类型的可见轮次 {#生成类型的可见轮次}

`Filer` 创建的新源码会在后续轮次进入模型。当前轮无法立即查询完整的新类型。文件由编译器继续编译。

### 9.3 编译生成的性能成本 {#编译生成的性能成本}

生成代码省去部分运行时发现，并可使用直接调用。代价包括构建时间、代码体积与生成器维护。收益应结合启动频率和调用热度测量。

### 9.4 生成文件的版本管理 {#生成文件的版本管理}

可重复生成的文件放入构建目录。这样可避免源码与生成结果漂移。发布协议要求提交生成源码时，应增加一致性校验。

### 10.1 怎样实现一个编译期注解 {#compile-time-annotation}

**出现公司**：飞书

**考察重点**

- `SOURCE` 保留策略与注解处理器的关系。
- `Processor`、`RoundEnvironment`、`Filer` 和 `Messager` 的职责。
- 多轮处理、重复生成和编译期错误报告。

**相关内容**：[注解处理模型](#注解处理模型)、[代码生成](#代码生成)。

<details>
<summary>参考回答</summary>

编译期注解由注解类型与处理器共同实现。处理器继承 `AbstractProcessor`，读取 `Element` 和 `TypeMirror`。校验失败时通过 `Messager` 报告错误。

处理器通过 `Filer` 创建新源码或资源。新类型进入后续轮次，生成器需避免重复创建。处理器顺序不应成为业务依赖。构建还需显式配置处理器。

</details>

### 10.2 Java 为什么可以实现 IoC，反射在其中做了什么 {#ioc-reflection}

<!-- 面试来源：

-->

**出现公司**：网易

**考察重点**

- 配置、类加载与反射如何让容器发现用户类型。
- 容器怎样创建对象、注入依赖并保存注册关系。
- 运行时发现和编译期生成各自适合什么边界。

**相关内容**：[运行时扫描](#运行时扫描)、[运行时扫描与注解处理器的比较](#运行时扫描与注解处理器的比较)。

<details>
<summary>参考回答</summary>

IoC 容器管理对象创建、依赖注入和生命周期。反射让它在运行时读取构造器及成员并完成调用。候选类型可来自配置、扫描或显式注册。

反射提供类型检查和调用能力。依赖解析与生命周期由 IoC 容器负责。构建时固定的组成可提前生成，动态插件保留运行时发现。

</details>
