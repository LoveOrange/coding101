# 对象相等性

判断对象是否相等，需要区分两件事：两个引用是否指向同一个对象，以及两个对象是否在业务上表示相同的值。本文说明 `==`、`equals` 和 `hashCode` 的关系，再结合可变哈希键、数组和身份哈希，解释这些规则怎样影响比较与查找。

## 1. 面试核心 {#core}

- 基本类型的 `==` 比较值，引用类型的 `==` 判断是否为同一个对象。`Object.equals` 默认也比较对象身份。[卡](#equals-hashcode)
- 通过 `equals` 判断相等的对象，必须具有相同的 `hashCode`，哈希容器才能把它们放进同一个候选范围。反过来，哈希值相同不代表对象相等。
- 哈希冲突是允许的，最终是否相等仍要通过 `equals` 判断。
- 对象作为哈希键期间，参与 `equals` 和 `hashCode` 的字段需要保持稳定，否则可能影响查找。[卡](#mutable-map-keys)

## 2. 对象身份与逻辑相等 {#对象身份与逻辑相等}

基本类型的 `==` 比较值，引用类型的 `==` 则判断两个引用是否指向同一个对象，也就是比较**对象身份**。`Object.equals` 默认采用的也是身份比较，子类可以重写它来比较内容。例如，`String.equals` 比较的就是字符串内容：

```java
String first = new String("Java");
String second = new String("Java");
String alias = first;

System.out.println(first == second);      // false
System.out.println(first == alias);       // true
System.out.println(first.equals(second)); // true
```

`first` 和 `second` 指向两个分别创建的对象，所以 `==` 返回 `false`；两个对象的内容都是 `"Java"`，所以 `equals` 返回 `true`。`alias` 保存的是从 `first` 复制过来的引用，两者指向同一个对象，因此 `==` 返回 `true`。

字符串字面量可以共享对象，但内容比较仍应使用 `equals`。具体共享规则见 [String](./string-immutability-pool.mdx#字符串常量池)。

**值对象**用字段值表达业务含义，并根据这些字段判断两个对象是否表示相同的值，这称为**逻辑相等**。例如，两个订单编号只要编号文本相同，就表示同一个编号：

```java
public record OrderId(String value) {
    public OrderId {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("blank order id");
        }
    }
}
```

记录类（`record`）会根据所有组件生成 `equals` 和 `hashCode`。组件就是声明在记录类名称后面的字段，`OrderId` 只有 `value` 这一个组件。因此，两个 `OrderId` 只要 `value` 相同，就在逻辑上相等。记录类从 Java 16 起正式可用，适合由所有组件共同决定相等性的值对象。

## 3. `equals` 契约 {#equals-契约}

调用方和集合需要稳定的相等规则，才能正确查找和去重。对于非空对象，`equals` 需要遵守五项约定：

- 自反：`x.equals(x)` 返回 `true`。
- 对称：`x.equals(y)` 与 `y.equals(x)` 的结果相同。
- 传递：`x` 等于 `y`、`y` 等于 `z` 时，`x` 也等于 `z`。
- 一致：参与相等判断的字段没有变化时，多次调用的结果相同。
- 非空：`x.equals(null)` 返回 `false`。

继承可能让这些约定难以保持。如果父类只比较自身字段，子类又把额外字段加入比较，两边采用的规则就不一致，可能破坏对称性或传递性。

设计值对象时，可以用下面三种方式避免这种差异：

- 将类声明为 `final`，固定参与相等判断的字段。
- 使用记录类，让所有组件共同定义相等性。
- 通过组合保存附加信息，避免在继承关系中扩展相等规则。

类型检查的方式也会影响结果。用 `getClass()` 比较时，要求两个对象的运行时类型相同；用 `instanceof` 检查时，子类型也能通过。选择哪一种，要看业务是否允许父类对象与子类对象相等，同时确保双方遵守相同的约定。

## 4. `hashCode` 契约 {#hashcode-契约}

`HashMap` 和 `HashSet` 查找键时，先用 `hashCode` 定位候选桶，再用 `equals` 确认是否相等。这个查找过程要求：

> 如果两个对象通过 `equals` 判断相等，它们的 `hashCode` 必须相同。

不同对象得到相同的哈希值，称为**哈希冲突**。`hashCode` 返回的是 32 位整数，结果数量有限，无法给所有对象分配唯一编号。因此，遇到相同哈希值时，集合还要用 `equals` 确认是不是相等的键。

```java
OrderId first = new OrderId("ORDER-101");
OrderId second = new OrderId("ORDER-101");

System.out.println(first == second);                    // false
System.out.println(first.equals(second));               // true
System.out.println(first.hashCode() == second.hashCode()); // true
```

`first` 和 `second` 是两个不同的对象，但 `value` 都是 `"ORDER-101"`，因此 `equals` 返回 `true`，哈希值也相同。

如果只重写 `equals`，逻辑相等的对象可能得到不同的哈希值。集合按哈希值查找时，就可能把它们定位到不同位置，导致 `HashSet` 留下逻辑上重复的值，或 `HashMap` 找不到相等的键。所以，`equals` 和 `hashCode` 应根据同一组字段定义。

## 5. 可变哈希键 {#可变对象作为哈希键}

哈希集合保存条目时，用的是写入时的哈希值；后续查询时，会重新计算查询键的哈希值。如果修改字段让哈希值变了，查询就会按新的哈希值定位，而旧条目还留在原来的位置。因此，即使用原对象去查，也可能找不到它。

要让键保持稳定，需要注意三个条件：

- 构造后不再修改参与相等判断的字段。
- `equals` 和 `hashCode` 使用相同字段。
- 字段本身也具有稳定的相等性。

数据库实体还要考虑主键是什么时候生成的。例如，用主键判断相等时，如果持久化前主键为空，插入后才分配主键，前后的相等性就会发生变化。

对象关系映射（ORM）框架把对象映射到数据库记录，它生成的代理对象还会影响运行时类型。如果用 `getClass()` 判断相等，就需要考虑代理对象与原实体能否通过类型比较。因此，要结合实体在整个生命周期中的变化，以及集合的用法来确定相等规则，并保证对象作为键期间规则保持稳定。

## 6. 数组内容与身份哈希 {#数组内容与身份哈希}

数组继承了 `Object.equals`，直接调用它比较的是对象身份。要比较内容，单层数组用 `Arrays.equals`，嵌套数组用 `Arrays.deepEquals`：

```java
int[] first = {1, 2};
int[] second = {1, 2};
System.out.println(first.equals(second));         // false
System.out.println(Arrays.equals(first, second)); // true
```

`first` 和 `second` 是两个独立的数组，所以 `first.equals(second)` 返回 `false`。它们的元素值相同，因此 `Arrays.equals(first, second)` 返回 `true`。

如果对象的相等规则包含数组内容，哈希值也要根据数组内容计算：单层数组使用 `Arrays.hashCode`，嵌套数组使用 `Arrays.deepHashCode`。这样，内容相等的数组才会得到相同的哈希值。

如果需要绕过类重写的哈希逻辑，可以调用 `System.identityHashCode`。它按对象身份计算哈希值，采用的是 `Object.hashCode` 默认实现的规则。不过，这个哈希值仍然可能冲突，不能把它当成对象的唯一编号或内存地址。

## 7. 常见问题 {#常见问题}

### 7.1 哈希值不同，两个对象一定不相等吗？ {#不同哈希值与相等性}

如果实现符合契约，就一定不相等。因为相等对象必须有相同的哈希值，哈希值不同就能排除相等的情况。

### 7.2 哈希值相同，两个对象一定相等吗？ {#哈希冲突}

不一定。不同对象可以发生哈希冲突，所以还需要调用 `equals` 判断是否相等。

### 7.3 `Objects.equals(a, b)` 怎样处理空值？ {#空值相等比较}

`Objects.equals(a, b)` 可以直接比较可能为 `null` 的引用。只要对象遵守相等契约，结果就分为三种情况：

- 两者都为 `null` 时，返回 `true`。
- 只有一个为 `null` 时，返回 `false`。
- 两者都非空时，相同引用直接返回 `true`，否则调用第一个对象的 `equals`。

因此，它处理了空值，但非空对象怎样判断逻辑相等，仍由类自身的 `equals` 实现决定。

## 8. 面试题 {#面试题}

### 8.1 `==`、`equals` 和 `hashCode` 有什么关系 {#equals-hashcode}

**考察重点**

- 区分引用身份与逻辑相等，并解释各自的使用场景。
- 说明哈希集合为什么需要先定位候选位置，再确认键是否相等。

**相关内容**：[对象身份与逻辑相等](#对象身份与逻辑相等)、[`hashCode` 契约](#hashcode-契约)。

<details>
<summary>参考回答</summary>

对引用类型来说，`==` 判断两个引用是否指向同一个对象。

`Object.equals` 默认也比较对象身份，类可以通过重写它来定义逻辑相等。

哈希集合先通过 `hashCode` 定位候选位置，再通过 `equals` 确认是否相等。只要 `equals` 返回 `true`，哈希值就必须相同；哈希值相同则不能保证对象相等。因此，自定义逻辑相等时，应根据同一组字段同时重写 `equals` 和 `hashCode`。

</details>

### 8.2 可变对象能否作为 HashMap 的键 {#mutable-map-keys}

**考察重点**

- 说明写入和查找时分别怎样使用哈希值。
- 根据字段变化前后的定位过程，解释为什么会找不到原键。

**相关内容**：[可变哈希键](#可变对象作为哈希键)。

<details>
<summary>参考回答</summary>

可以，前提是对象作为键期间，参与 `equals` 和 `hashCode` 的字段保持稳定。

集合按写入时的哈希值保存条目。如果修改字段后算出的哈希值变了，查询就可能找不到还在原位置的条目。可以选择值对象作为键，让参与相等判断的字段在构造后保持不变，并让 `equals` 和 `hashCode` 使用同一组字段。

</details>
