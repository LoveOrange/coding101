# Java 异常

方法执行失败时，Java 用异常把失败原因交给调用方。处理异常绕不开三个问题：哪些异常编译器要求你处理，捕获之后该做什么，关闭资源时又失败了怎么办。本文按这个顺序展开，最后说明 `finally` 对返回值的影响。

## 1. 面试核心 {#core}

- `Error`、`RuntimeException` 及其子类属于**非受检异常**。[卡](#exception-hierarchy)
- 受检异常**必须捕获或声明**，这是编译器的要求。失败能否恢复，则要看具体的调用场景。
- 当前层**有恢复或转换策略时才捕获异常**。需要包装异常时，通过 `cause` 保留原始失败原因。[卡](#exception-handling)
- try-with-resources 会**按资源声明的逆序**关闭资源。[卡](#try-with-resources)
- `try` 主体与资源关闭都失败时，**向外传播的是主体异常**，关闭异常保存在它的 `suppressed` 列表中。

## 2. 异常体系 {#异常体系}

Java 里能被 `throw` 的对象都继承自 `Throwable`。一个异常要不要捕获或声明，看它在这棵继承树上的位置：

```text
Throwable
├── Error
└── Exception
    ├── RuntimeException
    └── 其他受检异常
```

`Error` 表示虚拟机层面的严重问题，比如 `OutOfMemoryError` 和链接错误。遇到这类问题，要根据具体原因决定是终止还是尝试恢复；用一个 `catch` 把所有 `Error` 都接住，反而可能把严重故障藏起来。

`RuntimeException` 是 `Exception` 的子类。`RuntimeException`、`Error` 以及它们的子类叫作**非受检异常**，编译器不要求捕获或声明。其余的异常类，包括 `Throwable` 本身，都是**受检异常**，编译器会检查调用方有没有处理：

```java
void load(Path path) throws IOException { // 受检异常需要声明或捕获
    Files.readString(path);
}

int parsePort(String value) {
    return Integer.parseInt(value);       // 可能抛非受检异常
}
```

`Files.readString` 会抛出受检异常 `IOException`，所以 `load` 要么捕获它，要么像示例这样写进 `throws`。`Integer.parseInt` 抛出的 `NumberFormatException` 是非受检异常，`parsePort` 不声明也能通过编译。

自己设计 API 时，如果希望调用方必须对某种失败做出反应，就用受检异常。参数错误、状态错误这类编程问题，或者不想让调用链每一层都跟着声明的失败，可以用非受检异常。受检还是非受检只由继承关系决定，和异常的名字、严重程度无关，也不说明它能不能恢复，能否恢复要看具体的调用场景。

## 3. 抛出、声明与捕获 {#抛出声明与捕获}

这里涉及三个关键字：`throw` 抛出一个异常对象，`throws` 在方法签名上声明可能抛出的异常，`catch` 接住匹配的异常，在当前层处理。下面的 `loadOrder` 捕获一个异常，再抛出另一个：

```java
Order loadOrder(long id) {
    try {
        return repository.find(id);
    } catch (SQLException cause) {
        throw new OrderStoreException("load order " + id, cause);
    }
}
```

数据库访问失败时，`loadOrder` 把 `SQLException` 换成应用自己定义的 `OrderStoreException` 再抛出去。这样调用方只需要处理 `OrderStoreException`，不用关心底层的数据库异常。原来的 `SQLException` 作为 `cause` 传给构造器，排查问题时还能顺着它看到数据库报了什么错。

什么时候该 `catch`，要看当前这一层能不能对失败做点什么。临时故障可以重试，但要限制次数和总耗时；业务允许的话，可以返回一个降级结果；当前层负责的资源和没做完的操作，要在这里清理；也可以像 `loadOrder` 那样补上订单编号这类信息，换个异常类型继续抛。这些都做不了，就让异常继续往上传。尤其不要捕获后返回 `null` 或空结果，调用方会把「执行失败」误当成「没有数据」。

一个 `try` 后面可以跟多个 `catch`，它们按书写顺序匹配，所以子类异常的 `catch` 必须写在父类前面。反过来写的话，父类分支会先接住所有子类异常，后面的子类分支永远执行不到，编译器会直接报错。这条规则对受检异常和非受检异常都一样。

多重捕获 `catch (A | B e)` 用同一段代码处理两种异常，但 `A` 和 `B` 不能有子类型关系，否则也会编译报错。比如 `IOException` 已经能接住它的子类 `FileNotFoundException`，两者就不能写在同一个多重捕获里。

### 3.1 错误边界 {#错误边界}

异常一层层往上传，总要有一个地方决定这次请求或任务最终怎么收场，这个地方叫作**错误边界**。Web 请求的入口、消息消费者和定时任务的入口，都可以是错误边界。

在错误边界上，异常会被转换成对外的结果，比如 HTTP 错误码、消息是否重试、任务状态。日志也在这里记录，并带上追踪标识（trace ID），这样才能把这次失败和对应的请求联系起来。中间层只负责补充业务信息、继续往上抛，不需要每一层都打印一遍完整堆栈。

## 4. 常见处理规则 {#常见处理规则}

空的 `catch` 块会把失败悄悄吞掉，所以 `catch` 里要明确做一件事：恢复、转换，或者继续抛出。转换异常时，把原异常作为 `cause` 传进去。循环结束、缓存未命中这类预期内的情况，用条件判断和正常返回值表达，不要用异常控制流程。

`finally` 用来做清理，它本身应该正常结束。在 `finally` 里 `return`，会覆盖前面的返回值或正在传播的异常，第 6 节会具体说明。

`InterruptedException` 要单独处理。捕获它之后，要么继续往外抛，要么像下面这样恢复中断标记：

```java
try {
    queue.take();
} catch (InterruptedException interrupted) {
    Thread.currentThread().interrupt();
    return;
}
```

`queue.take()` 被中断时，代码先调用 `Thread.currentThread().interrupt()` 把中断标记设回去，再结束当前操作。这样外层代码仍然能发现有人请求了取消。如果直接忽略中断，这个信号就丢了。

## 5. try-with-resources 与资源关闭 {#try-with-resources-与资源关闭}

文件、网络连接这类资源用完要关闭。try-with-resources 把使用和关闭写在一起：资源只要实现了 `AutoCloseable` 接口，不管 `try` 主体是正常执行完、中途 `return`，还是抛出了异常，离开时都会调用它的 `close()`。

```java
try (
    InputStream input = Files.newInputStream(source);
    OutputStream output = Files.newOutputStream(target)
) {
    input.transferTo(output);
}
```

这段代码先打开 `input`，再打开 `output`，然后复制数据。关闭时顺序反过来，先关 `output`，再关 `input`。如果打开 `output` 时就失败了，已经打开的 `input` 也会被关闭。

复制和关闭都失败时，向外抛出的是主体里的异常。关闭时的异常不会丢，它们作为**抑制异常**（suppressed exception）挂在主体异常上。下图假设复制和两次关闭都失败：

调用方可以通过 `getSuppressed()` 取出这些关闭失败，一起记到日志里：

```java
try {
    run();
} catch (Exception failure) {
    for (Throwable closeFailure : failure.getSuppressed()) {
        // 记录资源关闭失败
    }
}
```

### 5.1 资源所有权 {#资源所有权}

谁打开的资源，谁负责关闭。方法只关闭自己创建的，或者调用方明确交给它管理的资源。

如果流是调用方传进来的，调用方之后可能还要用它，只是借用它的方法就不应该关掉。另外，包装流关闭时会按自己的约定关闭底层流。所以 API 要写清楚，传进来的资源是借给方法用一下，还是连同关闭的责任一起交了出去。

## 6. finally 与返回值 {#finally-与返回值}

`finally` 里改了变量，返回值会不会跟着变？关键在于返回值是什么时候算出来的。执行 `return` 时，程序先把表达式的值算好，然后执行 `finally`，最后才真正返回：

```java
static int result() {
    int value = 1;
    try {
        return value;
    } finally {
        value = 2;
    }
}
System.out.println(result()); // 1
```

执行 `return value` 时，返回值 1 已经确定了。之后 `finally` 把 `value` 改成 2，改的只是局部变量，所以 `result()` 还是返回 1。

如果返回的是引用，提前确定的是引用值。`finally` 换不掉这个引用，但可以通过它修改对象的内容。

`finally` 自己 `return` 或抛出异常时，会直接覆盖前面的返回值或正在传播的异常，原来的结果就丢了。所以清理代码应该正常结束。

## 7. 多个资源的关闭失败 {#多个资源的关闭失败}

第 5 节说的是主体失败的情况。如果主体正常结束，只是关闭时出了错，那么第一个关闭异常会向外抛出，后面的关闭异常挂到它的 `suppressed` 列表里。

比如先声明资源 A，再声明资源 B。退出时先关 B、再关 A；两个都失败的话，B 的异常先发生，成为向外抛出的异常，A 的异常挂在它下面。如果主体已经抛出了异常，B 和 A 的关闭异常就都挂到主体异常上，也就是第 5 节图里的情况。

try-with-resources 从 Java 7 开始提供。从 Java 9 开始，括号里还可以直接引用外部的 `final` 或有效 `final` 资源变量。有效 `final` 指变量没有写 `final`，但赋值之后没有再被重新赋值。Java 17 和 21 都支持这些写法。

## 8. 常见问题 {#常见问题}

### 8.1 `finally` 一定会执行吗？ {#finally-的执行边界}

不一定。控制流离开 `try` 或 `catch` 时，不管是正常结束、`return` 还是异常，`finally` 都会执行。但 JVM 停止以后，线程没有机会再运行 Java 代码，`finally` 也就执行不了：

- 在 `try` 或 `catch` 中调用 `System.exit(status)`，并成功启动 JVM 关闭流程后，这个调用不会返回，外层的 `finally` 也不会执行。`Runtime.getRuntime().halt(status)` 直接终止 JVM，同样不会执行 `finally`。
- 所有非守护线程结束后，JVM 开始关闭。JVM 最终退出时，还在运行的守护线程会被直接终止，它们没执行到的 `finally` 也不会再执行。
- 进程被强制终止、JVM 崩溃或者机器断电时，清理代码可能还没开始，也可能执行到一半就被打断。

### 8.2 普通业务代码应该捕获 Throwable 吗？ {#throwable-的捕获范围}

不应该。`catch (Throwable)` 会把 `Error` 和 `Exception` 一起接住，严重的系统问题可能被当成普通的业务失败处理掉。业务代码只捕获自己能处理的具体异常类型。框架在边界上确实需要统一捕获时，要想清楚记录哪些信息，以及什么情况下应该终止执行。

### 8.3 同一个异常应该在哪一层记录日志？ {#异常日志的记录边界}

在[错误边界](#错误边界)记录一次完整堆栈就够了，那里有请求或任务的上下文。中间层保留 `cause`、补充业务信息后继续往上抛。这样既能追到最初的原因，同一次失败也不会打出好几份重复的堆栈。

## 9. 面试题 {#面试题}

### 9.1 Error、Exception、受检异常和运行时异常有什么关系 {#exception-hierarchy}

**考察重点**

- 说明 `Error`、`Exception` 和 `RuntimeException` 在继承体系中的位置。
- 根据继承关系判断异常是否需要捕获或声明。

**相关内容**：[异常体系](#异常体系)。

<details>
<summary>参考回答</summary>

**`Error`、`RuntimeException` 及其子类属于非受检异常，其余异常类属于受检异常。**

从继承关系看，`Error` 和 `Exception` 都属于 `Throwable` 体系，`RuntimeException` 则继承自 `Exception`。

编译器要求受检异常必须捕获或声明，对非受检异常没有这个要求。至于失败能否恢复，还要看具体调用场景。

</details>

### 9.2 项目中应该怎样处理异常 {#exception-handling}

**考察重点**

- 根据当前层能采取的行动，选择捕获、转换或继续传播。
- 说明怎样保留原始原因、记录日志，并形成稳定的对外错误结果。

**相关内容**：[抛出、声明与捕获](#抛出声明与捕获)、[常见处理规则](#常见处理规则)。

<details>
<summary>参考回答</summary>

**当前层能够恢复、清理或转换失败时，才捕获异常；否则，让异常继续向外传播。**

例如，遇到临时故障可以有限重试，业务允许时可以降级，未完成的操作则由负责它的层清理。基础设施异常传到应用层时，可以补充业务信息、转换异常类型，同时保留原始 `cause`。

异常到达 Web、消息或任务入口后，再统一转换为对外结果，并记录一次带追踪标识的完整日志。失败应沿异常路径传播，不要用 `null` 或空结果把它隐藏起来。

</details>

### 9.3 try-with-resources 怎样保证资源关闭 {#try-with-resources}

**考察重点**

- 解释 `AutoCloseable` 的作用，以及资源关闭顺序和初始化失败后的处理。
- 说明主体异常与关闭异常怎样同时保留。

**相关内容**：[try-with-resources 与资源关闭](#try-with-resources-与资源关闭)。

<details>
<summary>参考回答</summary>

**控制流离开 `try` 时，try-with-resources 会按资源声明的逆序，自动调用各个 `AutoCloseable` 资源的 `close()`。**

初始化中途失败时，已经创建成功的资源也会关闭。例如，输出流创建失败，之前打开的输入流仍然会被清理。

如果主体和 `close()` 都失败，向外传播的是主体异常，关闭异常放在它的 `suppressed` 列表中。调用方仍能查看两次失败的信息。

</details>

### 9.4 try 返回后 finally 修改局部变量，返回值会改变吗？ {#finally-return}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释返回表达式的求值时机，以及 `finally` 返回或抛异常怎样改变结果。

**相关内容**：[finally 与返回值](#finally-与返回值)。

<details>
<summary>参考回答</summary>

**如果返回的是基本类型值，就不会改变。返回值在进入 `finally` 前已经算出，之后修改局部变量不会影响它。**

例如，`try` 准备返回 1，`finally` 再把局部变量改成 2，最终仍返回 1。如果 `finally` 自己返回或抛出异常，就会覆盖原来的返回值或异常。返回引用时，引用值已经确定，但它指向的对象仍可能被 `finally` 修改。

</details>

### 9.5 主体成功但两个 close 都失败，哪个异常会向外传播？ {#close-failure-order}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：按关闭顺序判断哪个异常向外传播，以及其余异常保存在哪里。

**相关内容**：[多个资源的关闭失败](#多个资源的关闭失败)。

<details>
<summary>参考回答</summary>

**资源按声明的逆序关闭，最先发生的关闭异常向外传播。**

如果先声明 A、再声明 B，就会先关闭 B。因此，B 的异常成为主异常，A 的关闭异常保存在它的 `suppressed` 列表中。

</details>
