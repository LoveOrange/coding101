# Java 异常

Java 异常把正常返回与失败路径分开。异常类型说明失败属于哪一层，`throw` 负责产生失败，调用方则选择处理、转换或继续传播；错误边界决定一段代码应该负责到哪里。

## 1. Java 异常体系

所有能够被 Java 语句抛出的对象都属于 `Throwable` 体系，主要分为 `Error` 和 `Exception`：

```text
Throwable
├── Error
└── Exception
    └── RuntimeException
```

### 1.1 Error

`Error` 表示 Java 运行环境或资源层面的严重问题，例如 `OutOfMemoryError`、`StackOverflowError` 和类定义错误。业务代码通常无法在局部恢复到可靠状态，因此不应通过 `catch (Error)` 把它们统一吞掉。

这不代表任何 `Error` 都绝对无法观察或清理，也不代表捕获后进程一定立刻退出。关键是普通业务方法不应把处理 JVM 级故障当作自己的职责。

### 1.2 Exception

`Exception` 表示程序可以在 API 中声明和传播的失败。其中 `RuntimeException` 及其子类属于非受检异常，其他 `Exception` 子类通常属于受检异常。

常见示例：

- `IOException`：受检异常。
- `SQLException`：受检异常。
- `IllegalArgumentException`：非受检异常。
- `NullPointerException`：非受检异常。

受检与非受检是编译规则，不等同于“能够恢复”和“不能恢复”。网络文件暂时不可用可能可以重试，也可能必须终止请求；参数非法可能由调用方修正，也可能代表内部程序错误。恢复策略仍然要结合调用场景判断。

## 2. 受检异常与非受检异常

### 2.1 受检异常必须捕获或声明

如果方法体可能抛出受检异常，方法必须使用 `try-catch` 处理，或者在 `throws` 中声明：

```java
static String readConfig(Path path) throws IOException {
    return Files.readString(path);
}
```

`throws IOException` 把处理责任交给调用方。调用方可以重试、使用默认配置、向上继续传播，或者在更合适的边界转换异常。

受检异常适合调用方有合理处理机会，而且希望编译器强制其注意的失败。层层声明却没有任何一层能作出决策时，它也会增加 API 噪声。

### 2.2 非受检异常不要求显式声明

```java
static int percentage(int part, int total) {
    if (total <= 0) {
        throw new IllegalArgumentException("total must be positive");
    }
    return part * 100 / total;
}
```

调用方不需要在编译阶段捕获 `IllegalArgumentException`。这种异常适合表示违反方法前置条件、对象状态非法，或当前层无法合理恢复的错误。

不受编译器强制，不代表可以忽略。公开 API 仍然应在文档中说明重要的非受检异常，入口层也需要把它们映射为稳定的响应或任务结果。

## 3. throw、throws 与捕获

### 3.1 `throw` 抛出具体异常对象

```java
if (order == null) {
    throw new IllegalArgumentException("order must not be null");
}
```

`throw` 是语句，后面跟一个 `Throwable` 对象。执行后，当前正常控制流停止，运行时沿调用栈寻找匹配的处理器。

### 3.2 `throws` 声明方法可能传播的类型

```java
void importOrders(Path path) throws IOException {
    // ...
}
```

`throws` 写在方法签名中，描述调用者需要考虑的受检异常。它不负责创建异常，也不保证方法每次都会抛出。

### 3.3 catch 应尽量匹配能够处理的范围

```java
try {
    return Files.readString(path);
} catch (NoSuchFileException exception) {
    return defaultConfig;
}
```

这里的调用方明确知道“文件不存在”可以回退到默认配置。直接捕获 `Exception` 会把权限错误、解码错误和程序缺陷一起隐藏。

在 Web 请求入口、消息消费循环或任务调度器等顶层边界，捕获较宽类型可能是必要的：它们需要把失败转换为响应、拒绝消息或任务状态，并防止一个请求破坏整个处理循环。宽捕获应集中在这样的边界，而不是散落在每个业务方法中。

## 4. 在边界转换异常

基础设施异常不应无条件泄漏到业务和接口层。当前层理解失败含义时，可以转换为更稳定的异常，同时保留原始原因：

```java
public final class OrderLoadException extends RuntimeException {
    public OrderLoadException(String message, Throwable cause) {
        super(message, cause);
    }
}

public Order loadOrder(long orderId) {
    try {
        return repository.findById(orderId);
    } catch (SQLException exception) {
        throw new OrderLoadException(
            "failed to load order " + orderId,
            exception
        );
    }
}
```

`OrderLoadException` 告诉上层操作失败的业务上下文，`cause` 保留底层堆栈和数据库原因，便于诊断。

### 4.1 哪一层应该处理异常

一层代码只有能完成以下动作之一时，才适合捕获异常：

- 依据明确规则重试或降级。
- 补充当前层上下文后转换为更合适的类型。
- 回滚或清理当前层负责的状态。
- 在系统入口把失败映射为稳定的外部结果。

如果只能打印日志再原样抛出，通常会造成重复日志；如果捕获后返回 `null`，又会丢失失败原因。让异常继续传播到真正拥有处理策略的边界更清楚。

### 4.2 外部错误契约要保持稳定

内部异常类型和堆栈不应直接作为 HTTP 响应或 RPC 错误暴露。入口层可以统一映射为公开错误码、可理解的信息和追踪标识，同时在内部日志保留异常链。

业务拒绝也不一定都要用异常表达。批量校验、表单错误等需要同时返回多项结果时，明确的结果类型通常比抛出第一个异常更合适。

## 5. 异常处理的常见规则

### 5.1 不要丢失原始原因

```java
try {
    callRemoteService();
} catch (IOException exception) {
    throw new OrderLoadException("remote call failed", exception);
}
```

只传入新的消息而不保留 `exception`，会截断异常链，使排查只能看到转换位置。

### 5.2 不要用异常替代正常分支

可预期且频繁出现的条件，例如缓存未命中、用户输入校验失败列表或查找不到可选数据，可以使用条件、`Optional` 或结果类型表达。异常构造和堆栈处理有成本，更重要的是它会把正常业务状态写成失败控制流。

### 5.3 不要在 finally 中返回

```java
static int unsafe() {
    try {
        throw new IllegalStateException("failed");
    } finally {
        return 1; // 会压过正在传播的异常
    }
}
```

`finally` 用于必须执行的收尾逻辑，不应通过 `return` 或新的异常覆盖原始结果。资源关闭优先使用 try-with-resources，它还能记录关闭阶段产生的受抑制异常。

### 5.4 正确处理中断

捕获 `InterruptedException` 后，如果当前方法不能继续向上抛出，应恢复中断标记并尽快结束当前工作：

```java
try {
    queue.take();
} catch (InterruptedException exception) {
    Thread.currentThread().interrupt();
    return;
}
```

直接吞掉中断会让上层取消和关闭流程失效。

## 6. try-with-resources 与资源关闭 {#try-with-resources}

try-with-resources 在控制流离开代码块时自动关闭资源，包括正常返回和异常传播。它不仅减少 `finally` 样板代码，还定义了资源初始化失败、多个资源关闭和关闭异常的处理方式。

### 6.1 AutoCloseable

资源类型需要实现 `AutoCloseable`：

```java
public interface AutoCloseable {
    void close() throws Exception;
}
```

文件流、Socket、JDBC 连接、语句和结果集都实现了 `AutoCloseable` 或它的子接口 `Closeable`。

```java
static String read(Path path) throws IOException {
    try (BufferedReader reader = Files.newBufferedReader(path)) {
        return reader.readLine();
    }
}
```

无论 `readLine()` 正常返回还是抛出异常，`reader.close()` 都会在方法真正返回或异常继续传播前执行。已经声明的 `final` 或有效 final 变量也可以直接作为资源：

```java
BufferedReader reader = Files.newBufferedReader(path);

try (reader) {
    return reader.readLine();
}
```

资源块结束后，变量仍在词法作用域中，但对象已经关闭，不应再次使用。

### 6.2 多个资源按声明的逆序关闭

资源通常存在依赖关系，后创建的包装层依赖先创建的底层资源：

```java
try (
    InputStream file = Files.newInputStream(path);
    InputStream buffered = new BufferedInputStream(file);
    Reader decoded = new InputStreamReader(buffered, StandardCharsets.UTF_8)
) {
    // ...
}
```

退出时依次关闭 `decoded`、`buffered` 和 `file`。逆序关闭使上层包装器可以先刷新或完成自己的协议，再释放底层资源。如果某个资源初始化失败，已经成功创建的前序资源仍会关闭，尚未创建的资源不参与关闭。

JDBC 资源也应按依赖顺序声明：

```java
try (
    Connection connection = dataSource.getConnection();
    PreparedStatement statement = connection.prepareStatement(sql);
    ResultSet resultSet = statement.executeQuery()
) {
    while (resultSet.next()) {
        // ...
    }
}
```

退出时先关闭 `ResultSet`，再关闭 `PreparedStatement`，最后关闭或归还 `Connection`。

### 6.3 关闭异常作为受抑制异常保留

方法体和 `close()` 都可能失败。try-with-resources 会让方法体中的异常继续作为主要异常，并把关闭阶段的异常记录为受抑制异常：

```java
try (FailingResource resource = new FailingResource()) {
    throw new IllegalStateException("operation failed");
}
```

如果 `close()` 又抛出 `IOException("close failed")`，最终传播的仍是 `IllegalStateException`，关闭异常可以通过 `getSuppressed()` 读取：

```java
for (Throwable suppressed : exception.getSuppressed()) {
    logger.warn("resource close also failed", suppressed);
}
```

手写下面的 `finally` 无法提供相同语义：

```java
Resource resource = open();

try {
    resource.use();
} finally {
    resource.close();
}
```

如果 `use()` 和 `close()` 都失败，`finally` 中的关闭异常会覆盖原始业务异常。多个资源关闭失败时，最先发生的关闭异常成为主要异常，后续关闭异常加入它的 suppressed 列表；一个资源关闭失败也不会阻止其余资源继续尝试关闭。

### 6.4 catch 和 finally 在资源关闭后执行

```java
try (Resource resource = open()) {
    resource.use();
} catch (IOException exception) {
    handle(exception);
} finally {
    finishRequest();
}
```

执行顺序是：

1. 执行 try 主体。
2. 自动关闭资源。
3. 进入匹配的 `catch`。
4. 执行外层 `finally`。

因此 `catch` 看到的异常已经包含关闭阶段产生的受抑制异常。从 try 主体 `return` 也会先关闭资源，再完成返回；如果 `close()` 抛出异常，原本准备返回的值不会正常返回。

### 6.5 资源所有权

代码只应关闭自己创建或明确接管所有权的资源：

```java
void writeReport(OutputStream output) throws IOException {
    // output 由调用方传入，当前方法不擅自关闭
    output.write(reportBytes);
}
```

API 应明确资源关系：

- 方法只是借用资源，调用方继续拥有并负责关闭。
- 方法接管所有权，返回后资源一定关闭。
- 方法返回一个新资源，调用方成为所有者。

包装流的 `close()` 通常会继续关闭底层流。只希望完成编码或压缩但保留底层连接时，需要使用不会传播关闭的包装策略，或者重新划分所有权边界。

### 6.6 自定义 AutoCloseable

需要成对获取和释放的资源可以实现 `AutoCloseable`，让生命周期进入语法作用域：

```java
public final class LockGuard implements AutoCloseable {
    private final Lock lock;
    private boolean closed;

    private LockGuard(Lock lock) {
        this.lock = lock;
        lock.lock();
    }

    public static LockGuard acquire(Lock lock) {
        return new LockGuard(lock);
    }

    @Override
    public void close() {
        if (!closed) {
            closed = true;
            lock.unlock();
        }
    }
}

try (LockGuard ignored = LockGuard.acquire(lock)) {
    updateSharedState();
}
```

自定义关闭逻辑应说明是否允许重复调用、是否可能阻塞，以及失败时抛出什么异常。`AutoCloseable` 本身不要求 `close()` 幂等。

## 7. 常见问题

### 7.1 `finally` 一定会执行吗

在正常退出 `try` 或匹配的 `catch` 时，`finally` 通常会执行，包括方法准备返回或继续抛异常的情况。但如果 JVM 终止、进程被强制结束或执行永远无法离开 `try`，就不能保证。不要把关键持久化协议建立在“finally 绝对执行”上。

### 7.2 能否捕获 `Throwable`

语法允许，但普通业务代码不应这样做。它会同时捕获 `Exception` 和 `Error`，可能把虚拟机或链接层面的严重问题当作普通业务失败继续运行。只有框架最外层、诊断或清理代码在明确重新抛出和隔离策略时才可能需要。

### 7.3 自定义异常应该继承 Exception 还是 RuntimeException

如果调用方必须显式决定恢复策略，而且每个调用点都有现实处理机会，可以考虑受检异常。若异常表示违反前置条件、非法状态，或通常只能由统一边界处理，继承 `RuntimeException` 更合适。选择依据是 API 希望强制调用方承担什么责任，不是异常名称。

### 7.4 一个异常应该记录几次日志

通常在真正消费异常、生成外部结果或终止任务的边界记录一次完整日志。中间层如果只是补充上下文并继续抛出，优先把上下文放入异常消息或结构化字段，避免每层重复打印同一堆栈。

### 7.5 try-with-resources 是否等同于 finally 调用 close

不等同。两者都以释放资源为目标，但 try-with-resources 还处理资源初始化失败、逆序关闭和受抑制异常。只说“编译器增加了 finally”会遗漏它最重要的异常语义。

### 7.6 Closeable 与 AutoCloseable 有什么区别

`Closeable` 继承 `AutoCloseable`，其 `close()` 声明抛出 `IOException`，并要求资源已经关闭时再次调用没有效果。`AutoCloseable.close()` 可以声明更宽的 `Exception`，接口本身不要求幂等。

### 7.7 close 失败可以忽略吗

不一定。输出流关闭失败可能表示缓冲数据没有完整写出，数据库连接归还失败可能影响连接池。至少应让关闭异常进入现有错误处理与监控，不能统一使用空 `catch`。

### 7.8 为什么资源不能只交给 GC

文件描述符、Socket 和数据库连接是有限的外部资源，何时释放不能依赖对象何时被垃圾回收。GC 管理 Java 对象可达性，不提供及时的协议关闭、刷新或归还连接保证。

<summary>参考回答</summary>

通常只关闭当前方法创建或明确接管所有权的资源。调用方传入的流可能还要继续写入，方法擅自关闭会破坏更大的协议边界。API 应在命名或文档中说明资源是借用还是移交。

包装流关闭通常会继续关闭底层流，因此不能只看最外层对象。需要保留底层连接时，应调整所有权设计或使用明确不传播关闭的包装方案。
