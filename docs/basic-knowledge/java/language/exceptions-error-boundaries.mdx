# Java 异常

Java 异常把正常返回与失败路径分开。面试重点是异常体系、受检与非受检异常的区别、在哪一层处理，以及资源关闭时怎样保留原始失败。

:::tip 面试核心

- `Throwable` 的主要分支是 `Error` 和 `Exception`；`RuntimeException` 属于非受检异常。
- 受检与非受检的差异是编译器是否强制捕获或声明，不直接等于“可恢复”与“不可恢复”。
- 只在当前层能够重试、降级、清理、补充语义或转换外部结果时捕获异常。
- 转换异常时保留原始 `cause`，完整日志通常只在系统边界记录一次。
- try-with-resources 按声明的逆序关闭资源，主体异常优先，关闭异常进入 `suppressed` 列表。

:::

## 1. 异常体系

```text
Throwable
├── Error
└── Exception
    ├── RuntimeException
    └── 其他受检异常
```

`Error` 通常表示虚拟机、链接或严重资源问题，例如 `OutOfMemoryError`。业务代码一般不把捕获所有 Error 作为恢复策略。

`Exception` 表示程序可以描述的失败。`RuntimeException` 及其子类属于非受检异常，其他 Exception 通常属于受检异常。

```java
void load(Path path) throws IOException { // 受检异常需要声明或捕获
    Files.readString(path);
}

int parsePort(String value) {
    return Integer.parseInt(value);       // 可能抛非受检异常
}
```

受检异常要求调用者显式处理传播路径，适合调用者通常能够采取行动的失败。非受检异常适合参数、状态或编程错误，以及不希望每层重复声明的失败。最终选择取决于 API 契约，而不是错误是否“严重”。

## 2. 抛出、声明与捕获

- `throw` 抛出一个具体异常对象。
- `throws` 在方法签名中声明可能向外传播的受检异常。
- `catch` 只应该捕获当前层知道怎样处理的范围。

```java
Order loadOrder(long id) {
    try {
        return repository.find(id);
    } catch (SQLException cause) {
        throw new OrderStoreException("load order " + id, cause);
    }
}
```

这里的数据访问异常被转换为稳定的应用异常，同时保留原始原因。没有处理策略时，让异常继续传播比捕获后返回 `null` 或空结果更清楚。

### 2.1 错误边界

Web 入口、消息消费者和定时任务入口通常是错误边界。它们把内部异常转换为对外错误码、重试结果或任务状态，并记录追踪标识。

同一个异常不应在每一层重复打印完整堆栈。中间层负责补充语义并传播，边界层负责形成一次可诊断记录。

## 3. 常见处理规则

- 不要使用空 `catch` 隐藏失败。
- 转换异常时把原异常作为 `cause`。
- 不要用异常控制预期的普通分支，例如循环结束或缓存未命中。
- 不要在 `finally` 中 `return`，它可能覆盖 try 中的返回值或异常。
- 捕获 `InterruptedException` 后，如果不能继续向外抛出，通常要调用 `Thread.currentThread().interrupt()` 恢复中断状态。

```java
try {
    queue.take();
} catch (InterruptedException interrupted) {
    Thread.currentThread().interrupt();
    return;
}
```

## 4. try-with-resources {#try-with-resources}

实现 `AutoCloseable` 的资源可以放入 try-with-resources。无论 try 主体正常结束、返回还是抛异常，资源都会被关闭。

```java
try (
    InputStream input = Files.newInputStream(source);
    OutputStream output = Files.newOutputStream(target)
) {
    input.transferTo(output);
}
```

关闭规则包括：

1. 多个资源按声明的逆序关闭，这里先关闭 `output`，再关闭 `input`。
2. 初始化中途失败时，已经成功创建的资源仍会关闭。
3. try 主体和 `close()` 同时失败时，主体异常保留为主要异常，关闭异常可通过 `getSuppressed()` 取得。

```java
try {
    run();
} catch (Exception failure) {
    for (Throwable closeFailure : failure.getSuppressed()) {
        // 记录资源关闭失败
    }
}
```

### 4.1 资源所有权

通常只关闭当前方法创建或明确接管所有权的资源。调用方传入的流可能还会继续使用；包装流关闭时也常会继续关闭底层流，因此 API 需要明确资源是借用还是移交。

## 5. 常见问题

### 5.1 `finally` 一定会执行吗

不能绝对保证。进程被强制终止、JVM 崩溃或机器断电时不会执行；正常控制流中，finally 通常会在离开 try/catch 前执行。

### 5.2 应该捕获 `Throwable` 吗

普通业务代码不应该。它会同时捕获多数 `Error`，容易把系统级严重问题伪装成可继续运行的业务失败。框架边界即使需要兜底，也要定义清晰的记录和终止策略。

### 5.3 一个异常应该记录几次日志

通常在能够形成完整上下文的边界记录一次。中间层只转换并保留 cause，避免同一失败产生多份重复堆栈。

`Throwable` 的主要分支是 `Error` 和 `Exception`。`Exception` 中，`RuntimeException` 及其子类属于非受检异常，其他异常通常属于受检异常。

</details>

### 6.3 try-with-resources 怎样保证资源关闭

<!-- 面试来源：
- 蚂蚁金服：https://www.nowcoder.com/discuss/652926046165123072
-->

**出现公司**：蚂蚁金服

**考察重点**

- `AutoCloseable`、关闭顺序和初始化失败。
- 主体异常与关闭异常怎样同时保留。

**相关内容**：[try-with-resources](#try-with-resources)。

<details>
<summary>参考回答</summary>

try-with-resources 接收 `AutoCloseable` 资源。控制流离开 try 时，资源按声明的逆序关闭；初始化中途失败时，已经创建的资源也会关闭。

如果主体和 close 同时失败，主体异常保持为主要异常，关闭异常通过 `getSuppressed()` 保留，因此不会被 finally 中的新异常覆盖。

</details>
