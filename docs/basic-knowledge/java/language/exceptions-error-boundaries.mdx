# Java 异常

Java 异常表示方法执行失败，并把失败原因沿调用链传给调用方。处理异常时，需要知道哪些失败必须捕获或声明、当前层能采取什么行动，以及资源关闭时会发生什么。本文围绕这些问题，说明异常传播、`finally` 和多个异常同时出现时的执行结果。

## 1. 面试核心 {#core}

- `Error`、`RuntimeException` 及其子类属于非受检异常。[卡](#exception-hierarchy)
- 受检异常必须捕获或声明，这是编译器的要求。失败能否恢复，则要看具体的调用场景。
- 当前层有恢复或转换策略时才捕获异常。需要包装异常时，通过 `cause` 保留原始失败原因。[卡](#exception-handling)
- try-with-resources 会按资源声明的逆序关闭资源。[卡](#try-with-resources)
- `try` 主体与资源关闭都失败时，向外传播的是主体异常，关闭异常保存在它的 `suppressed` 列表中。

## 2. 异常体系 {#异常体系}

Java 中能被抛出的对象都属于 `Throwable` 体系。判断一个异常是否必须捕获或声明，要先看它的继承关系：

```text
Throwable
├── Error
└── Exception
    ├── RuntimeException
    └── 其他受检异常
```

`Error` 包括虚拟机错误、链接错误和严重的资源错误，例如 `OutOfMemoryError`。遇到这类问题，要根据具体原因决定终止还是恢复。如果统一捕获所有 `Error`，就可能掩盖严重故障。

`Exception` 是另一条分支，`RuntimeException` 也属于它。`RuntimeException`、`Error` 及其子类属于**非受检异常**，编译器不要求捕获或声明。其余异常类，包括 `Throwable` 自身，都属于**受检异常**，需要通过编译器的检查。

```java
void load(Path path) throws IOException { // 受检异常需要声明或捕获
    Files.readString(path);
}

int parsePort(String value) {
    return Integer.parseInt(value);       // 可能抛非受检异常
}
```

`Files.readString` 可能抛出受检异常 `IOException`，因此 `load` 必须捕获它，或像示例一样在方法签名中声明。`Integer.parseInt` 抛出的 `NumberFormatException` 属于非受检异常，所以 `parsePort` 可以不声明它。

设计 API 时，如果希望明确提醒调用方为某种失败采取行动，可以使用受检异常。非受检异常可以表示参数、状态或编程错误；如果不希望调用链每一层都重复声明某种失败，也可以使用非受检异常。两类异常的划分依据是继承关系，不能只看名称或严重程度来判断能否恢复。

## 3. 抛出、声明与捕获 {#抛出声明与捕获}

方法执行失败后，可以抛出异常，在当前层处理，或继续传给调用方。这里有三个作用不同的关键字：

- `throw` 抛出一个具体异常对象。
- `throws` 在方法签名中声明异常传播范围。
- `catch` 捕获匹配的异常，让当前层执行恢复或转换逻辑。

```java
Order loadOrder(long id) {
    try {
        return repository.find(id);
    } catch (SQLException cause) {
        throw new OrderStoreException("load order " + id, cause);
    }
}
```

`loadOrder` 把 `SQLException` 转换成应用定义的 `OrderStoreException`，让调用方依赖一个稳定的失败类型。传给构造器的 `cause` 保留了原始异常，排查时仍能看到数据库操作为什么失败。

决定捕获异常之前，先确认当前层能够做什么：

- 对临时失败重试，并限定次数和总耗时。
- 降级为业务允许的替代结果。
- 清理当前层负责的资源或未完成操作。
- 补充订单编号等信息，转换异常后继续传播。
- 将内部异常映射成调用方需要的错误结果。

如果当前层没有合适的处理策略，就让异常继续传播。捕获后直接返回 `null` 或空结果，会让调用方把执行失败误认为没有数据。

多个 `catch` 会按代码中的顺序匹配，因此子类异常的 `catch` 必须写在父类异常的 `catch` 前面。如果父类分支在前，它就能捕获这个子类的所有异常，后面的子类分支永远不会执行，编译器会报错。受检异常和非受检异常都遵守这条规则。

多重捕获 `catch (A | B e)` 可以用同一段逻辑处理两种异常，但 `A` 与 `B` 不能有子类型关系，否则也会编译报错。例如，`IOException` 已经包含了对其子类 `FileNotFoundException` 的捕获，所以不能把两者并列写在同一个多重捕获中。

### 3.1 错误边界 {#错误边界}

决定如何结束本次请求或任务的位置，称为**错误边界**。Web 请求、消息消费者和定时任务的入口，都可以承担这个职责。

异常传播到这些入口后，就会被转换为对外错误码、消息重试结果或任务状态。记录日志时还需要带上追踪标识，才能把这次失败与对应请求联系起来。

同一个异常不需要在每一层都打印完整堆栈。中间层补充必要的业务信息后继续传播，由边界层记录一次完整的诊断信息。

## 4. 常见处理规则 {#常见处理规则}

处理异常时，既要保留失败信息，也要让正常执行的分支清楚可读。可以按下面的规则检查代码：

- `catch` 中需要明确执行恢复、转换或传播。留空会直接隐藏失败。
- 转换异常时，把原异常作为 `cause` 保留下来。
- 循环结束、缓存未命中属于预期分支，用条件判断和正常返回值表达。
- 用 `finally` 清理资源时，让它正常结束。在其中执行 `return`，会覆盖此前的返回值或异常。
- 捕获 `InterruptedException` 后，继续传播异常，或用 `Thread.currentThread().interrupt()` 恢复中断标记。

```java
try {
    queue.take();
} catch (InterruptedException interrupted) {
    Thread.currentThread().interrupt();
    return;
}
```

`queue.take()` 被中断后，这段代码先调用 `Thread.currentThread().interrupt()` 恢复中断标记，再结束当前操作。这样，外层代码仍能识别取消请求；如果直接忽略中断，这个信号就会丢失。

## 5. try-with-resources 与资源关闭 {#try-with-resources-与资源关闭}

try-with-resources 把资源的使用和关闭写在同一个语法结构中。资源需要实现 `AutoCloseable` 接口，提供 `close()` 方法。无论 `try` 主体执行完毕，还是通过 `return` 或异常退出，都会调用资源的关闭方法。

```java
try (
    InputStream input = Files.newInputStream(source);
    OutputStream output = Files.newOutputStream(target)
) {
    input.transferTo(output);
}
```

示例先打开 `input` 和 `output`，再通过 `input.transferTo(output)` 复制数据。资源关闭有以下规则：

1. 多个资源按声明的逆序关闭，这里先关闭 `output`，再关闭 `input`。
2. 初始化中途失败时，已经成功创建的资源仍会关闭。
3. 主体与 `close()` 同时失败时，保留主体异常。关闭异常通过 `getSuppressed()` 读取。

这些附加的关闭异常称为**抑制异常**，保存在主体异常的 `suppressed` 列表中。向外传播的是主体异常，但关闭失败的信息也被保留下来，可以一起用于诊断：

```java
try {
    run();
} catch (Exception failure) {
    for (Throwable closeFailure : failure.getSuppressed()) {
        // 记录资源关闭失败
    }
}
```

### 5.1 资源所有权 {#资源所有权}

关闭资源之前，先确认由谁负责它的生命周期。当前方法只应关闭自己创建或明确接管的资源。

如果流是调用方传进来的，调用方后面可能还要使用它。只是借用这个流的方法，应把关闭职责留给所有者。另外，包装流还会按自身约定关闭底层流，所以 API 要说明传入资源是供当前方法借用，还是把所有权一起移交。

## 6. finally 与返回值 {#finally-与返回值}

`finally` 会不会改变返回值，取决于返回表达式什么时候求值。执行 `return` 时，程序先算出表达式的值，再执行 `finally`，最后才完成返回。因此，如果返回的是基本类型值，在 `finally` 中修改局部变量不会改变已经算出的值：

```java
static int result() {
    int value = 1;
    try {
        return value;
    } finally {
        value = 2;
    }
}
System.out.println(result()); // 1
```

执行 `return value` 时，已经得到返回值 1。随后 `finally` 把局部变量 `value` 改成 2，但这不会改变先前算出的结果，所以 `result()` 仍返回 1。

如果返回的是引用，提前确定的就是引用值，`finally` 仍可以通过这个引用修改对象内容。另一种情况是 `finally` 自己执行了 `return` 或抛出异常，这会覆盖此前的返回值或异常。因此，清理代码应正常结束，让原来的结果或失败原因继续传给调用方。

## 7. 多个资源的关闭失败 {#多个资源的关闭失败}

多个资源都关闭失败时，只会有一个主异常向外传播，其余失败也需要保留。try-with-resources 按资源声明的逆序关闭资源。如果主体正常结束，最先发生的关闭异常就成为主异常，后续关闭异常保存在它的 `suppressed` 列表中。

例如，先声明资源 A，再声明资源 B，退出时就先关闭 B，再关闭 A。如果两者关闭时都抛出异常，B 的异常先发生，会成为主异常，A 的异常则附加到它的 `suppressed` 列表中。如果主体已经抛出异常，B 和 A 的关闭异常都会附加到主体异常中。

try-with-resources 从 Java 7 开始提供。Java 9 起，还可以直接引用外部的 `final` 或有效 `final` 资源变量。有效 `final` 是指变量虽然没有写 `final`，但赋值后没有再次赋值。这些用法在 Java 17 和 21 中都可以使用。

## 8. 常见问题 {#常见问题}

### 8.1 `finally` 一定会执行吗？ {#finally-的执行边界}

不一定。正常执行完毕、返回或异常传播导致控制流离开 `try` / `catch` 时，会执行 `finally`。但 JVM 终止后，线程无法继续执行 Java 代码，这时就不能依赖 `finally` 完成清理：

- 在 `try` 或 `catch` 中调用 `System.exit(status)`，并成功启动 JVM 关闭流程后，这次调用不会返回，也不会进入外层的 `finally`。`Runtime.getRuntime().halt(status)` 会直接终止 JVM，同样不会执行 `finally`。
- 所有非守护线程结束后，JVM 会启动关闭流程。等到 JVM 最终退出，仍在运行的守护线程会被直接终止，它们尚未执行的 `finally` 也不会再执行。
- 进程被强制终止、JVM 崩溃或机器断电时，清理可能还没开始，也可能执行到一半就被打断。

### 8.2 普通业务代码应该捕获 Throwable 吗？ {#throwable-的捕获范围}

普通业务代码应捕获自己能够处理的具体异常类型。`catch (Throwable)` 会同时捕获 `Error` 和 `Exception`，可能把严重的系统问题当成可恢复的业务失败。如果框架边界需要统一捕获，就要明确哪些信息需要记录，以及什么情况下应该终止执行。

### 8.3 同一个异常应该在哪一层记录日志？ {#异常日志的记录边界}

在掌握请求或任务上下文的错误边界，记录一次完整堆栈。中间层保留 `cause`、补充业务信息后继续传播，这样既能追查原始原因，也不会为同一次失败重复打印堆栈。

## 9. 面试题 {#面试题}

### 9.1 Error、Exception、受检异常和运行时异常有什么关系 {#exception-hierarchy}

**考察重点**

- 说明 `Error`、`Exception` 和 `RuntimeException` 在继承体系中的位置。
- 根据继承关系判断异常是否需要捕获或声明。

**相关内容**：[异常体系](#异常体系)。

<details>
<summary>参考回答</summary>

`Error`、`RuntimeException` 及其子类属于非受检异常，其余异常类属于受检异常。

从继承关系看，`Error` 和 `Exception` 都属于 `Throwable` 体系，`RuntimeException` 则继承自 `Exception`。

编译器要求受检异常必须捕获或声明，对非受检异常没有这个要求。至于失败能否恢复，还要看具体调用场景。

</details>

### 9.2 项目中应该怎样处理异常 {#exception-handling}

**考察重点**

- 根据当前层能采取的行动，选择捕获、转换或继续传播。
- 说明怎样保留原始原因、记录日志，并形成稳定的对外错误结果。

**相关内容**：[抛出、声明与捕获](#抛出声明与捕获)、[常见处理规则](#常见处理规则)。

<details>
<summary>参考回答</summary>

当前层能够恢复、清理或转换失败时，才捕获异常；否则，让异常继续向外传播。

例如，遇到临时故障可以有限重试，业务允许时可以降级，未完成的操作则由负责它的层清理。基础设施异常传到应用层时，可以补充业务信息、转换异常类型，同时保留原始 `cause`。

异常到达 Web、消息或任务入口后，再统一转换为对外结果，并记录一次带追踪标识的完整日志。失败应沿异常路径传播，不要用 `null` 或空结果把它隐藏起来。

</details>

### 9.3 try-with-resources 怎样保证资源关闭 {#try-with-resources}

**考察重点**

- 解释 `AutoCloseable` 的作用，以及资源关闭顺序和初始化失败后的处理。
- 说明主体异常与关闭异常怎样同时保留。

**相关内容**：[try-with-resources 与资源关闭](#try-with-resources-与资源关闭)。

<details>
<summary>参考回答</summary>

控制流离开 `try` 时，try-with-resources 会按资源声明的逆序，自动调用各个 `AutoCloseable` 资源的 `close()`。

初始化中途失败时，已经创建成功的资源也会关闭。例如，输出流创建失败，之前打开的输入流仍然会被清理。

如果主体和 `close()` 都失败，向外传播的是主体异常，关闭异常放在它的 `suppressed` 列表中。调用方仍能查看两次失败的信息。

</details>

### 9.4 try 返回后 finally 修改局部变量，返回值会改变吗？ {#finally-return}

**考察重点**：解释返回表达式的求值时机，以及 `finally` 返回或抛异常怎样改变结果。

**相关内容**：[finally 与返回值](#finally-与返回值)。

<details>
<summary>参考回答</summary>

如果返回的是基本类型值，就不会改变。返回值在进入 `finally` 前已经算出，之后修改局部变量不会影响它。

例如，`try` 准备返回 1，`finally` 再把局部变量改成 2，最终仍返回 1。如果 `finally` 自己返回或抛出异常，就会覆盖原来的返回值或异常。返回引用时，引用值已经确定，但它指向的对象仍可能被 `finally` 修改。

</details>

### 9.5 主体成功但两个 close 都失败，哪个异常会向外传播？ {#close-failure-order}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：按关闭顺序判断哪个异常向外传播，以及其余异常保存在哪里。

**相关内容**：[多个资源的关闭失败](#多个资源的关闭失败)。

<details>
<summary>参考回答</summary>

资源按声明的逆序关闭，最先发生的关闭异常向外传播。

如果先声明 A、再声明 B，就会先关闭 B。因此，B 的异常成为主异常，A 的关闭异常保存在它的 `suppressed` 列表中。

</details>
