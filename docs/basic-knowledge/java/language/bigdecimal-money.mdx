# BigDecimal

`BigDecimal` 用整数值和小数位数表示十进制数，适合需要明确舍入规则的金额计算。但换成 `BigDecimal` 只是第一步，金额从哪里来、在哪一步舍入、怎样比较，都还要自己决定，其中任何一步处理不当，账就可能对不上。

## 1. 面试核心 {#core}

- `double` 只能用二进制浮点数**保存 `0.1` 的近似值**。金额可以从十进制文本构造 `BigDecimal`，避免先经过这种近似表示。[卡](#money-not-double)
- `BigDecimal` 的值等于 **`unscaledValue × 10^-scale`**。
- 不指定舍入策略的 `divide`，**在结果为无限循环小数时会抛出 `ArithmeticException`**。金额运算需要事先明确保留多少精度，以及采用什么舍入规则。
- `BigDecimal` 的运算**不会修改原对象**，调用方需要接收返回的结果。
- `equals` **同时比较数值和 `scale`**，`compareTo` **只比较数值**。[卡](#bigdecimal-equals-compareto)

## 2. double 的十进制误差 {#double-的十进制误差}

`double` 无法精确表示 `0.1` 这样的十进制小数，连续计算会出现误差。原因是 `double` 用二进制浮点数保存小数，十进制的 `0.1` 转成二进制后是无限循环小数，而存储空间有限，只能取最接近的可表示值。这种近似会影响后续计算：

```java
double result = 0.1 + 0.2;
System.out.println(result); // 0.30000000000000004
```

`result` 末尾出现的差异，来自二进制近似和运算中的舍入。允许误差的科学计算、图形处理和统计场景可以使用 `double`。金额与税率结算则需要控制十进制规则，可以使用 `BigDecimal`，也可以按最小货币单位保存整数。

## 3. BigDecimal 的表示 {#bigdecimal-的表示}

一个 `BigDecimal` 由任意精度的整数值和 `scale` 组成，两者共同确定它表示的数值：

```text
unscaledValue × 10^-scale
```

例如，`123.45` 可以写成 `12345 × 10^-2`：

```java
BigDecimal amount = new BigDecimal("123.45");

System.out.println(amount.unscaledValue()); // 12345
System.out.println(amount.scale());         // 2
System.out.println(amount.precision());     // 5
```

这里的三个方法分别描述数值的不同部分：

- `scale` 为非负数时，表示小数点右侧有多少位，`123.45` 的 `scale` 是 2。
- `precision` 表示有效数字的位数，这里是 5。
- `unscaledValue` 是公式中的整数系数，这里是 12345。

`BigDecimal` 是不可变对象。调用 `add`、`setScale` 时，原对象不会变化，运算结果通过返回值交给调用方：

```java
BigDecimal original = new BigDecimal("10.00");
BigDecimal updated = original.add(new BigDecimal("2.50"));

System.out.println(original); // 10.00
System.out.println(updated);  // 12.50
```

## 4. BigDecimal 构造 {#创建-bigdecimal}

创建 `BigDecimal` 时，要先看数据来源：拿到的是原始十进制数，还是已经舍入过的浮点数。如果已有十进制文本，可以直接用字符串构造：

```java
BigDecimal price = new BigDecimal("19.90");
BigDecimal taxRate = new BigDecimal("0.06");
```

如果来源是整数，可以直接使用 `valueOf(long)` 或对应的常量：

```java
BigDecimal count = BigDecimal.valueOf(3);
BigDecimal zero = BigDecimal.ZERO;
```

### 4.1 `new BigDecimal(double)` 的问题 {#new-bigdecimaldouble-的问题}

如果来源只能提供 `double`，就需要区分构造器与 `valueOf` 的转换方式。下面两种写法传入的都是 `0.1`，得到的结果却不同：

```java
BigDecimal unexpected = new BigDecimal(0.1);
System.out.println(unexpected);
// 0.1000000000000000055511151231257827021181583404541015625

BigDecimal value = BigDecimal.valueOf(0.1);
System.out.println(value); // 0.1
```

差别在于，它们转换的依据不同：

- `new BigDecimal(double)` 会精确转换传入的二进制浮点值。`0.1` 在传入前已经舍入，转换后的长串小数正是这个浮点值的十进制表示。
- `valueOf(double)` 先取得浮点数的规范字符串表示，再把它转成十进制数。这里得到的字符串是 `"0.1"`，所以结果为 `0.1`。

不过，`valueOf` 无法恢复数据转成 `double` 时已经丢失的精度。因此，金额应直接从文本、数据库 `DECIMAL` 或最小单位整数进入系统。

## 5. 运算与舍入 {#运算与舍入}

金额运算除了保存数值，还需要明确什么时候舍入。不传入 `MathContext` 时，加、减、乘会按精确值计算；传入后，则按其中配置的有效数字位数和舍入方式处理。先看不传入 `MathContext` 的乘法：

```java
BigDecimal subtotal = new BigDecimal("19.90")
    .multiply(BigDecimal.valueOf(3));

System.out.println(subtotal); // 59.70
```

精确除法要求结果能够表示为有限小数。`1/3` 是无限循环小数，无法满足这个要求，因此不带舍入参数的 `divide` 会抛出异常：

```java
BigDecimal one = BigDecimal.ONE;
BigDecimal three = BigDecimal.valueOf(3);

// one.divide(three); // ArithmeticException

BigDecimal result = one.divide(three, 2, RoundingMode.HALF_UP);
System.out.println(result); // 0.33
```

`one.divide(three, 2, RoundingMode.HALF_UP)` 指定保留两位小数，按 `HALF_UP` 舍入，得到 `0.33`。保留几位、怎样舍入，属于业务规则，要提前定下来：中间计算保留多少精度，在哪一步舍入，展示、结算和入账各用几位小数，正数和负数是否用同一种舍入方式。

### 5.1 小数位调整 {#setscale-返回新对象}

`setScale` 可以调整小数位数，但不会修改原对象，所以需要接收返回值：

```java
BigDecimal amount = new BigDecimal("12.345");
BigDecimal rounded = amount.setScale(2, RoundingMode.HALF_UP);

System.out.println(amount);  // 12.345
System.out.println(rounded); // 12.35
```

`rounded` 保存舍入后的 `12.35`，`amount` 仍然是 `12.345`。如果只调用 `amount.setScale(...)` 而不接收返回值，`amount` 不会改变。

### 5.2 MathContext {#mathcontext}

`MathContext` 控制的是有效数字个数和舍入方式，`setScale` 控制的则是小数位数。看下面这个乘法：

```java
MathContext context = new MathContext(4, RoundingMode.HALF_UP);
BigDecimal result = new BigDecimal("123.45")
    .multiply(new BigDecimal("6.789"), context);

System.out.println(result); // 838.1
```

`new MathContext(4, RoundingMode.HALF_UP)` 中的 4，表示整个结果保留四位有效数字。因此结果是 `838.1`，并不是保留四位小数。

金融结算需要按币种和业务规则控制小数位，高精度科学计算则会关注有效数字位数。配置 `setScale` 和 `MathContext` 时，要区分这两种用途，不能用一个全局精度替代所有规则。

## 6. `equals` 与 `compareTo` {#equals-与-compareto}

`equals` 同时比较数值和小数位数，`compareTo` 只比较数值，所以数值相同、小数位数不同的两个金额，用它们比较会得到不同的结果：

```java
BigDecimal first = new BigDecimal("2.0");
BigDecimal second = new BigDecimal("2.00");

System.out.println(first.equals(second)); // false
System.out.println(first.compareTo(second)); // 0
```

`first` 的 `scale` 是 1，`second` 的 `scale` 是 2，所以 `equals` 返回 `false`；两者的数值相同，所以 `compareTo` 返回 0。

如果只需要判断金额数值是否相等，可以使用 `compareTo(...) == 0`。集合也要按这个区别来看：`HashMap` 和 `HashSet` 通过 `equals` 与 `hashCode` 识别元素，所以 `2.0` 和 `2.00` 会被当成两个不同的键；使用自然排序的 `TreeSet` 通过 `compareTo` 判重，两者只会保留一个。

可以在创建领域对象时统一 `scale`，明确金额使用什么表示：

```java
public record Money(BigDecimal amount) {
    public Money {
        amount = amount.setScale(2, RoundingMode.UNNECESSARY);
    }
}
```

`Money` 的这段实现只适用于明确要求两位小数、并且不允许对输入舍入的业务。不同货币、不同业务不一定都保留两位小数，需要根据各自的规则决定。

## 7. 金额模型的选择 {#金额模型的选择}

金额有两种常见的保存方式：按元这样的主单位保存，或者换算成分这样的最小单位保存。选哪种，取决于币种和换算规则是否固定。

### 7.1 BigDecimal 主单位模型 {#用-bigdecimal-保存主单位}

用 `BigDecimal` 可以直接保存以元为单位的金额，便于对接数据库 `DECIMAL`。业务需要使用不同的小数位，或计算规则比较复杂时，也适合采用这种模型。

采用这种模型，数据进入系统时就要把表示方式统一下来：精度和舍入模式符合计算与结算的要求，数值的单位明确是元还是分，接口输出小数位和科学计数形式的格式保持一致。

### 7.2 long 最小单位模型 {#用-long-保存最小单位}

如果货币的最小单位固定，可以换算成整数，用 `long` 保存。例如，`19.90` 元换算成分后是：

```java
long amountInCents = 1990;
```

整数运算没有小数表示误差，类型也更轻量，但需要防止溢出。只有最小货币单位和换算规则固定时，这种表示才比较简单。计算涉及比例、税率或分摊时，仍然要规定余数怎样处理、结果怎样舍入。

无论选择哪种模型，都应把数值和币种放在一起。例如，人民币 100 元与美元 100 元需要先换算，再按业务规则计算，不能因为数字相同就把它们当成同一种金额。

## 8. 舍入方向与精确转换 {#舍入方向与精确转换}

舍入模式决定结果往哪个方向取，同一个数用不同模式可能得到不同结果。负数还能区分出「向零」和「向负无穷」这两种方向。下面都把 `-1.25` 保留到一位小数，比较四种舍入模式的结果：

```java
BigDecimal value = new BigDecimal("-1.25");
System.out.println(value.setScale(1, RoundingMode.HALF_UP));   // -1.3
System.out.println(value.setScale(1, RoundingMode.HALF_EVEN)); // -1.2
System.out.println(value.setScale(1, RoundingMode.DOWN));      // -1.2
System.out.println(value.setScale(1, RoundingMode.FLOOR));     // -1.3
```

按每种模式的规则，可以得到上面的结果：

- `HALF_UP` 选择最近的值，距离相等时远离零，因此结果是 `-1.3`。
- `HALF_EVEN` 也选择最近的值，距离相等时保留偶数末位，因此结果是 `-1.2`。
- `DOWN` 向零舍入，因此结果是 `-1.2`。
- `FLOOR` 向负无穷舍入，因此结果是 `-1.3`。

如果业务要求数值保持精确，可以使用 `UNNECESSARY`。这表示当前操作必须无需舍入就能完成，否则抛出异常。

转成整数时，也要明确是否允许丢失精度。`intValue()` 会截去小数，溢出时只保留低 32 位；`intValueExact()` 遇到非零小数或溢出则会抛出异常，让调用方知道这次转换无法保留原来的数值。

## 9. 常见问题 {#常见问题}

### 9.1 使用 BigDecimal 后，还需要定义哪些金额规则？ {#金额业务边界}

还需要明确币种、汇率、余数分配和舍入时机。`BigDecimal` 只负责十进制表示和精度控制，不能代替这些结算规则：

- 金额使用什么币种，按哪个时点的汇率换算。
- 分摊后有余数时，把余数分配给谁。
- 在哪一步舍入，以及遵循哪些会计规则。

`scale` 选得不合适，或每一步都重复舍入，都会影响最终金额。因此，使用 `BigDecimal` 后，仍然需要验证完整的计算过程。

### 9.2 `stripTrailingZeros()` 适合统一 scale 吗？ {#尾零移除与负-scale}

如果金额接口要求固定的小数位数，应使用 `setScale`。`stripTrailingZeros()` 会移除末尾的零，得到的 `scale` 可能是负数。

例如，`new BigDecimal("1000").stripTrailingZeros()` 得到的整数系数是 1，`scale` 是 -3。代入数值公式，结果仍然是 1000，但文本形式会变成 `1E+3`。因此，显示或持久化之前，要确认接口能否接受这种表示。

### 9.3 为什么不使用 double，再格式化为两位小数？ {#格式化与数值精度}

因为格式化只改变输出的文本，不改变参与计算的值。中间计算产生的二进制近似和舍入误差还在，后续运算会继续使用这些值，最后显示成两位小数也修复不了前面的计算。

## 10. 面试题 {#面试题}

### 10.1 金额为什么不适合直接使用 double {#money-not-double}

**考察重点**

- 解释十进制小数为什么会在二进制浮点表示中产生误差。
- 说明 `BigDecimal` 怎样保存数值和小数位。
- 区分精确表示数值与制定业务舍入规则各自解决的问题。

**相关内容**：[double 的十进制误差](#double-的十进制误差)、[BigDecimal 的表示](#bigdecimal-的表示)、[运算与舍入](#运算与舍入)。

<details>
<summary>参考回答</summary>

**`double` 无法精确表示许多十进制小数，只能保存近似值，连续计算时会出现尾差。**

`BigDecimal` 用整数系数和 `scale` 表示十进制数，可以精确保存十进制文本中的金额。

使用时仍要明确创建方式和舍入规则：从字符串、数据库 `DECIMAL` 或最小货币单位整数创建，避免使用 `new BigDecimal(double)`；除法和结算时，则由业务规则确定精度与 `RoundingMode`。

</details>

### 10.2 `BigDecimal` 的 equals 与 compareTo 有什么区别 {#bigdecimal-equals-compareto}

**考察重点**

- 区分数值相同与表示相同。
- 解释 `scale` 怎样影响 `equals`、`hashCode` 和哈希集合判重。
- 根据业务需要判断是否应统一小数位。

**相关内容**：[`equals` 与 `compareTo`](#equals-与-compareto)。

<details>
<summary>参考回答</summary>

**`equals` 同时比较数值和 `scale`，因此 `2.0` 与 `2.00` 不相等。`compareTo` 只比较数值大小，两者的比较结果为 0。**

只判断金额数值是否相等时，可以使用 `compareTo(...) == 0`。

如果用 `BigDecimal` 作为哈希键，集合会通过 `equals` 和 `hashCode` 判断，`scale` 不同就会形成不同的键。可以在构造领域对象时统一符合业务要求的小数位，让金额的表示保持一致。

</details>

### 10.3 负数的 HALF_UP、DOWN 和 FLOOR 有什么区别？ {#rounding-negative-exact}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：根据舍入方向推导负数的结果，并判断怎样发现精度丢失。

**相关内容**：[舍入方向与精确转换](#舍入方向与精确转换)。

<details>
<summary>参考回答</summary>

**`HALF_UP` 在两个候选值的中点选择远离零的一侧，`DOWN` 向零舍入，`FLOOR` 向负无穷舍入。**

因此，把 `-1.25` 保留到一位小数，三者依次得到 -1.3、-1.2、-1.3。如果要求操作保持精确，可以使用 `UNNECESSARY`。转成整数时，可以用 `intValueExact()` 这类精确转换方法，在无法保留原值时报错。

</details>
