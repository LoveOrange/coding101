# Spring Boot 自动配置

Spring Boot 自动配置按条件注册默认 Bean。本文以 Boot 3.5 为准，负责候选发现、条件与退让。Starter 模块设计见 [Spring Boot Starter](./custom-starter-boundaries.mdx)。

## 1. 面试核心 {#core}

- Boot 3.x 从 `AutoConfiguration.imports` 读取自动配置候选。[卡](#auto-configuration)
- `@ConditionalOnMissingBean` 根据已处理的 Bean 定义决定退让。
- `@ConditionalOnProperty` 默认匹配已存在且值不为 `false` 的属性。[卡](#property-condition-defaults)
- 自动配置的 `before`、`after` 控制定义顺序，实例顺序由依赖决定。
- `--debug` 输出条件报告，`conditions` 端点提供运行时查询。

## 2. 候选自动配置类 {#候选自动配置类}

自动配置候选登记在以下文件：

```text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

文件每行写一个配置类全限定名：

```text
com.example.payment.autoconfigure.PaymentAutoConfiguration
```

`@EnableAutoConfiguration` 通过导入选择器读取候选。候选经排除、排序和条件匹配后参与定义注册。自动配置类使用 `@AutoConfiguration` 声明。

自动配置放在专用包中，通过 imports 导入。内部依赖用明确的 `@Import` 组织，避免宽泛组件扫描。可用 `@SpringBootApplication(exclude=...)` 排除候选。配置文件也支持 `spring.autoconfigure.exclude`。

## 3. 条件注解 {#条件注解}

```java
@AutoConfiguration
@ConditionalOnClass(PaymentClient.class)
@EnableConfigurationProperties(PaymentProperties.class)
class PaymentAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    PaymentService paymentService(PaymentProperties properties) {
        return new PaymentService(properties.endpoint());
    }
}
```

示例要求类路径存在 `PaymentClient`。容器缺少 `PaymentService` 时，才注册默认实现。

| 注解 | 判断条件 |
| --- | --- |
| `@ConditionalOnClass` | 类路径包含指定类 |
| `@ConditionalOnBean` | 已处理定义中存在指定 Bean |
| `@ConditionalOnMissingBean` | 已处理定义中缺少指定 Bean |
| `@ConditionalOnProperty` | 属性存在且值匹配 |
| `@ConditionalOnWebApplication` | 应用属于指定 Web 类型 |

类级条件控制整组配置，方法级条件控制该 Bean。缺失依赖的类型隔离见 [Spring Boot Starter](./custom-starter-boundaries.mdx#可选依赖隔离)。

## 4. 用户配置优先 {#用户配置优先}

`@ConditionalOnMissingBean` 在已有用户 Bean 时退让。例如用户声明 `PaymentService` 后，示例跳过默认实现。两份同名定义相互覆盖属于另一种机制。

Bean 条件只看到评估时已处理的定义。自动配置在用户配置之后处理，便于按用户定义退让。自动配置之间可用 `before`、`after` 指定关系。

`@Bean` 方法返回类型需表达条件检查所需的类型。返回过宽的接口会丢失具体类型信息。实例创建顺序仍由依赖、`@DependsOn` 和懒加载设置决定。

## 5. 属性条件 {#属性条件}

```java
@Bean
@ConditionalOnProperty(
    prefix = "payment.retry",
    name = "enabled",
    havingValue = "true",
    matchIfMissing = false
)
RetryPolicy retryPolicy() {
    return new RetryPolicy();
}
```

示例只在 `payment.retry.enabled=true` 时启用。属性缺失时，`matchIfMissing=false` 使条件失败。

省略 `havingValue` 时，已存在且值不为 `false` 即匹配。因此 `enabled=foo` 也会命中默认规则。布尔开关应明确写 `havingValue="true"`。

同一注解声明多个 `name` 时，所有属性都需匹配。集合下标属性应使用专门条件，避免将其当作普通键判断。参数范围用 `@ConfigurationProperties` 校验。

## 6. 条件评估报告 {#条件评估报告}

`--debug` 或 Actuator `conditions` 可展示条件结果。诊断时先找到目标自动配置，再查看未匹配条件。

- 类条件失败时，检查运行时依赖树。
- Bean 条件失败时，查看已有定义和返回类型。
- 属性条件失败时，检查最终值与来源。
- Web 条件失败时，确认应用类型。

条件成立只说明允许注册。Bean 创建中的构造或初始化失败需继续查看异常链。

## 7. 启动副作用 {#启动副作用}

自动配置负责声明组件与装配关系。网络连接和后台任务应交给有生命周期的 Bean。

类加载和条件评估时访问网络会增加启动耗时。条件还会用于精简测试，因此应保持评估过程可重复。

## 8. 常见问题 {#常见问题}

### 8.1 自动配置注册的版本差异 {#自动配置注册的版本差异}

Boot 2.7 引入 `AutoConfiguration.imports`，并兼容旧登记。Boot 3.0 移除了 `spring.factories` 的自动配置候选登记。初始化器等其他扩展仍可使用 `spring.factories`。

### 8.2 MissingBean 条件诊断 {#missingbean-条件诊断}

先确认条件检查的类型、名称和搜索范围。再查看用户定义是否已注册、返回类型是否准确。自动配置顺序也会影响条件可见的定义。
