# Spring 事务

Spring 事务用拦截器和事务管理器控制资源提交。本文以 Spring 6.2 的 JDBC 本地事务为主。内容覆盖传播、回滚、隔离和提交后的处理。代理入口见 [Spring AOP](./aop-pointcut-interceptor-chain.mdx#代理边界)。

## 1. 面试核心 {#core}

- `TransactionInterceptor` 在调用前取得事务，退出时处理提交或回滚。[卡](#transactional-flow)
- JDBC 事务按线程绑定连接，同一数据源的参与操作复用连接。
- 默认回滚匹配 `RuntimeException` 与 `Error`，受检异常可用 `rollbackFor`。
- `REQUIRES_NEW` 创建独立事务，`NESTED` 使用当前事务的保存点。[卡](#requires-new-vs-nested)
- 内层 `REQUIRED` 标记 rollback-only 后，外层提交会抛 `UnexpectedRollbackException`。[卡](#unexpected-rollback)

## 2. 事务注解与代理 {#事务注解与代理}

```java
@Transactional
public Order create(CreateOrder command) {
    Order order = repository.save(command.toOrder());
    inventoryRepository.reserve(order.items());
    return order;
}
```

示例的两个 repository 使用同一受管数据源。外部调用进入事务代理后，两次写入参与同一事务。

注解可声明传播、隔离、超时、只读和回滚规则。事务管理器及底层资源决定具体支持范围。

## 3. 事务拦截器 {#事务拦截器}

```text
进入代理
  → 解析 TransactionAttribute
  → 选择 TransactionManager
  → 获取或加入事务
  → 执行目标方法
  → 正常返回：请求提交
  → 异常退出：按规则提交或回滚
  → 清理事务上下文与资源
```

新建事务的调用边界负责实际提交。加入已有事务时，内层方法返回只结束逻辑事务范围。

`PlatformTransactionManager` 用于命令式事务。响应式事务使用 `ReactiveTransactionManager` 与 Reactor Context。本文的线程绑定描述适用于 JDBC 路径。

## 4. 连接与事务上下文 {#连接与事务上下文}

JDBC 事务管理器把连接关联到当前线程和数据源。`JdbcTemplate` 等组件通过 Spring 获取该连接。事务结束后，管理器提交或回滚并释放资源。

直接调用普通 `DataSource.getConnection()` 会绕开 Spring 的资源查找。需要底层连接时，可使用 `DataSourceUtils`。事务感知数据源代理也可协调获取。

新线程有独立上下文，需通过事务入口建立自己的事务。多数据源可用 `@Transactional(transactionManager="ordersTxManager")` 明确选择。单个本地管理器只管理其负责的数据源。

## 5. 提交失败 {#提交失败}

目标方法正常返回后，事务仍需实际提交。JPA 的 flush、数据库约束或连接故障都可在此时失败。调用方应以事务代理的最终返回结果判断成功。

远程调用与本地提交分属不同资源。需要可靠发送消息时，可在本地事务写入 Outbox。后台发布器再投递，并用幂等键处理重复。

## 6. 事务边界 {#事务边界}

一次应用服务调用可承载需要共同提交的数据库操作。过大的事务长期占用连接和锁，也增加回滚成本。

耗时网络调用应移出本地事务。前后步骤通过可恢复状态连接，并明确重试和补偿责任。

## 7. 编程式事务 {#编程式事务}

逐批提交、局部事务或明确重试范围可使用 `TransactionTemplate`。

```java
return transactionTemplate.execute(status -> repository.save(order));
```

回调返回后，模板按规则提交；异常退出时处理回滚。传播方式仍由模板设置决定。它让事务边界直接出现在代码中。

## 8. 传播、隔离与回滚 {#传播隔离与回滚}

传播决定怎样处理已有事务。隔离控制数据库并发可见性。回滚规则决定异常是否触发回滚。三者分别配置。

### 8.1 `REQUIRED` {#required}

`REQUIRED` 有事务时加入，无事务时新建。内外方法有各自的逻辑边界，但共享物理事务。

内层代理收到匹配回滚的异常，会将共享事务标为 rollback-only。外层捕获该异常也无法清除标记。外层请求提交时，管理器回滚并抛出 `UnexpectedRollbackException`。

若异常在内层方法内部被捕获，拦截器只看到正常返回。没有其他回滚标记时，事务按正常路径提交。

### 8.2 `REQUIRES_NEW` {#requires_new}

`REQUIRES_NEW` 挂起外层事务，再开启独立事务。

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void recordAudit(AuditEvent event) {}
```

内层提交结果独立保留，外层回滚也会保留该记录。内层完成时释放自己的锁与连接。

外层挂起期间仍持有连接和锁。内层额外申请连接，并发时需预留池容量。若内层等待外层已持有的锁，还会形成跨事务等待。

### 8.3 `NESTED` {#nested}

`DataSourceTransactionManager` 可在已有 JDBC 事务中建立保存点。`NESTED` 内层失败时回滚到该保存点。外层处理异常后，可继续执行并尝试提交。

外层最终回滚时，内层写入也被撤销。没有外层事务时，`NESTED` 按 `REQUIRED` 新建事务。

保存点需 JDBC 驱动支持。JPA 持久化上下文中的对象状态还需单独考虑。应按具体事务管理器确认支持范围。

### 8.4 其他传播方式 {#其他传播方式}

| 传播方式 | 已有事务 | 没有事务 |
| --- | --- | --- |
| `SUPPORTS` | 加入 | 非事务执行 |
| `MANDATORY` | 加入 | 抛异常 |
| `NOT_SUPPORTED` | 挂起 | 非事务执行 |
| `NEVER` | 抛异常 | 非事务执行 |

挂起能力由事务管理器提供。非事务执行时，数据库写入仍需按连接的自动提交设置判断。

### 8.5 隔离级别 {#隔离级别}

`Isolation.DEFAULT` 沿用数据库默认隔离级别。显式隔离和超时应用于新建事务。加入已有事务时沿用外层设置。

`AbstractPlatformTransactionManager.setValidateExistingTransaction(true)` 开启严格校验。内层声明与外层隔离或只读状态冲突时，可提前拒绝参与。

`readOnly=true` 是资源优化提示。JDBC 管理器可用 `setEnforceReadOnly(true)` 加强只读执行。具体支持仍依赖数据库；权限约束应由数据库授权承担。

### 8.6 回滚规则 {#回滚规则}

默认对传出方法的 `RuntimeException` 和 `Error` 回滚。受检异常可显式声明：

```java
@Transactional(rollbackFor = PaymentException.class)
```

异常必须到达拦截器，或由业务显式设置 rollback-only。类型规则支持子类，`noRollbackFor` 可声明提交例外。匹配多个规则时，继承距离更近的规则优先。

Spring 6.2 可用 `@EnableTransactionManagement(rollbackOn=ALL_EXCEPTIONS)` 更改全局默认。该设置将受检异常也纳入默认回滚。局部规则仍可覆盖默认行为。

## 9. 提交后事件 {#提交后事件}

`@TransactionalEventListener` 默认在 `AFTER_COMMIT` 执行。它适合在提交成功后触发后续处理。无事务发布事件时，默认跳过监听器。`fallbackExecution=true` 可允许无事务执行。

提交后仍能访问绑定资源，但原事务已经结束。此时新增写入应通过另一个代理开启 `REQUIRES_NEW`。

普通事务事件保存在进程内存中。提交后进程崩溃会丢失尚未执行的通知。要求可靠投递时，应使用持久化 Outbox 等机制。

## 10. 常见问题 {#常见问题}

### 10.1 本地事务与远程写入 {#本地事务与远程写入}

本地事务只管理所属资源。远程服务已经完成的写入需用补偿或跨服务事务协议处理。

### 10.2 只读事务的约束 {#只读事务的约束}

`readOnly=true` 向资源传递优化意图。JDBC 的强制只读设置和数据库权限提供更明确的限制。

### 10.3 独立事务的回滚范围 {#独立事务的回滚范围}

内层 `REQUIRES_NEW` 提交后独立保留。外层回滚只撤销外层事务的写入。

### 10.4 保存点回滚后的外层事务 {#保存点回滚后的外层事务}

回到保存点后，外层可继续尝试提交。前提是异常已处理，且数据库事务仍可用。

### 11.1 `@Transactional` 从调用到提交经历什么 {#transactional-flow}

**出现公司**：美团、阿里云

**考察重点**：理解事务拦截、资源绑定与实际提交。

**相关内容**：[事务注解与代理](#事务注解与代理)至[事务边界](#事务边界)。

<details>
<summary>参考回答</summary>

事务拦截器解析属性并选择事务管理器。管理器新建或加入事务，再执行目标方法。JDBC 路径按线程绑定连接，参与操作复用该资源。

方法正常返回时请求提交，异常退出时按规则处理。实际提交仍会因约束或连接故障失败。事务结束后清理上下文并释放连接。

</details>

### 11.2 `REQUIRES_NEW` 与 `NESTED` 有什么区别 {#requires-new-vs-nested}

<!-- 面试来源：
- 阿里云：https://www.nowcoder.com/discuss/592128174994075648
- 美团：https://www.nowcoder.com/discuss/353158567966482432
-->

**出现公司**：阿里云、美团

**考察重点**：区分独立事务与保存点的回滚范围。

**相关内容**：[`REQUIRES_NEW`](#requires_new)和[`NESTED`](#nested)。

<details>
<summary>参考回答</summary>

`REQUIRES_NEW` 创建独立物理事务，内层提交独立保留。`NESTED` 在已有 JDBC 事务中建立保存点。外层回滚会撤销整个事务的写入，包括内层变化。

前者需额外连接，后者需事务管理器和驱动支持保存点。无外层事务时，两者都会新建事务。

</details>
