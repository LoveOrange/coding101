# Spring MVC 请求生命周期

一次 HTTP 请求进入 Spring MVC 应用，要依次经过 Servlet 容器、Filter 链和 DispatcherServlet，才调用到 Controller；Controller 返回之后，结果还要经过转换才写回客户端。Controller 方法只是这条链路中间的一段。

把链路顺序讲清楚，能回答两类问题：某段逻辑（鉴权、参数解析、序列化、异常处理）发生在哪个阶段；一个请求慢了，时间可能花在哪里。返回 `Callable` 或 `DeferredResult` 的异步请求，还会在结果就绪后再次派发；初始请求处理和结果写回可能由不同线程完成。

## 1. 面试核心 {#core}

- Servlet 容器接收 HTTP 请求，让它**先经过 Filter 链，再进入 DispatcherServlet**。
- DispatcherServlet 通过 **HandlerMapping 找到处理器和拦截器**，再由 **HandlerAdapter 解析参数并调用 Controller**。[卡](#request-to-controller)
- `@ResponseBody` 返回值由**消息转换器**按协商的媒体类型写出；视图名由 ViewResolver 解析后交给 View 渲染。
- MVC 异步会**释放初始请求线程**，结果就绪后通过 **ASYNC 派发**继续处理已有结果，Controller 方法不会再执行一次。[卡](#async-redispatch)
- 响应序列化发生在 Controller 返回之后，**也计入完整请求耗时**。

## 2. Servlet 容器 {#servlet-容器}

请求到达 MVC 之前，连接和 HTTP 报文已经由服务器处理好了。Tomcat、Jetty 这类服务器接受 TCP 连接，解析请求行和请求头，并提供读取请求体的入口。**Servlet 容器**再据此构造 request 和 response 对象，按自己的线程模型安排请求执行。

MVC 从这里接手，拿到的是 Servlet API 对象，只负责应用层的分派。这个分工在排查慢请求时很重要：请求可能还没进入应用，就在服务器入口排队了。所以要区分**服务器容量与应用容量**：

- 连接数限制服务器同时维护多少连接。
- accept 队列存放等待被接受的连接，请求太多时会在入口等待。
- 请求线程决定容器怎样安排请求执行，keep-alive 决定连接能否继续复用。
- 数据库连接池和业务执行器由应用自己配置，要单独观察使用量和等待时间。

## 3. Filter 链 {#filter-链}

容器按 URL 和派发类型选出要执行的 Filter，每个过滤器调用 `chain.doFilter()` 后，请求才进入下一项，最后到达 DispatcherServlet。Spring Security 也是通过这条 Servlet 过滤链接入的，所以安全检查发生在请求进入 MVC 之前。

请求包装、拒绝响应和返回后的清理见 [Spring 拦截机制](./filter-interceptor-aspect-boundaries.mdx#filter)。

## 4. DispatcherServlet {#dispatcherservlet}

**DispatcherServlet** 是 MVC 的前端控制器：它本身是一个 Servlet，接住请求后不自己处理业务，而是协调一组 MVC 组件完成调用。这里先说明两个名词：**handler** 是实际处理请求的对象，通常是一个 Controller 方法；**adapter**（HandlerAdapter）封装了怎样调用某一类 handler。DispatcherServlet 不需要知道 handler 的具体形态，交给能支持它的 adapter 去调用就行。

一次**同步请求**按下面的顺序完成：

1. HandlerMapping 根据请求找到 handler，以及匹配这个请求的拦截器。
2. DispatcherServlet 选出支持这个 handler 的 HandlerAdapter。
3. 拦截器执行 `preHandle`，决定是否继续。
4. 适配器用参数解析器、数据绑定和消息转换器准备好参数，再调用 Controller。
5. 返回值处理器写出响应正文，或者准备好视图和模型数据。
6. 拦截器执行 `postHandle`。
7. 有视图时渲染视图，随后调用 `afterCompletion` 完成清理。

映射、参数解析、Controller 调用这些阶段抛出的异常，会进入 `HandlerExceptionResolver` 异常解析链，解析器尝试把异常转换成错误响应。

各个策略组件的职责见 [DispatcherServlet](./dispatcherservlet-handler-mapping.mdx)。

## 5. 返回值处理 {#返回值处理}

Controller 返回的是 Java 对象，MVC 还要把它变成 HTTP 响应。下面的方法在 `@RestController` 里返回订单对象，所以返回值会被当成响应正文处理：

```java
@RestController
class OrderController {
    @GetMapping("/orders/{id}")
    OrderResponse get(@PathVariable long id) {
        return service.find(id);
    }
}
```

**消息转换器**（`HttpMessageConverter`）负责把 Java 对象和 HTTP 正文互相转换。返回值处理器按协商出的媒体类型选择转换器：协商结果是 JSON 时，对应的转换器把 `OrderResponse` 序列化成 JSON，写进响应体。

同样返回一个值，声明不同，含义也不同，要区分**视图名、响应正文和 ResponseEntity**：

- 普通 `@Controller` 方法返回 String 时，字符串可以被解释为视图名。
- 加了 `@ResponseBody`，或者在 `@RestController` 里，String 会作为正文写出。
- 返回 `ResponseEntity` 时，除了正文，还能指定状态码和响应头。

视图名交给 ViewResolver 解析，得到 View 后再渲染页面。JSON 序列化发生在 Controller 返回之后，仍属于 MVC 的返回值处理阶段。所以序列化失败时，只要响应还没提交，MVC 还能通过异常解析器生成错误响应。

## 6. 异步请求 {#异步请求}

Controller 要等一个耗时任务时，可以先返回一个异步结果对象，让初始请求线程先回到容器，结果好了再写回。`Callable` 和 `DeferredResult` 都能稍后提供一个结果，区别在于**由谁生产结果**：

| 返回类型 | 结果生产方式 |
| --- | --- |
| `Callable` | MVC 将任务交给配置的 AsyncTaskExecutor |
| `DeferredResult` | 应用从其他线程调用 `setResult` 或 `setErrorResult` |

两者背后都是 **Servlet async**，也就是 Servlet 的异步请求机制。过程分两段：

1. 第一段，Controller 返回异步结果，MVC 开启 Servlet async，初始请求线程返回容器，响应保持打开。
2. 第二段，结果准备好后，MVC 发起 **ASYNC 派发**，把同一个请求再交给容器处理。框架重新定位 handler，然后直接用已有结果继续返回值处理。Controller 方法不会再执行一次。

拦截器在这两段里收到的回调不同。第一段结束时，初始线程调用异步拦截器的 `afterConcurrentHandlingStarted`，跳过普通的 `postHandle` 和 `afterCompletion`；第二段的派发才进入完成流程。如果结果迟迟不来，发生超时，还需要对应的异步回调来处理超时结果。

因为请求换了线程，清理逻辑要覆盖每一次线程退出，具体规则见 [Spring 拦截机制](./filter-interceptor-aspect-boundaries.mdx#异步与-threadlocal)。

失败也走这条路：`Callable` 抛出异常，或者应用调用 `setErrorResult(exception)`，异常会随 ASYNC 派发进入 MVC 的异常解析。独立的 `@Async` 后台任务不一样，它和请求没有关系，失败通过 Future 等返回结果或异步异常处理器报告，要由调用方自己处理。

## 7. 请求日志与指标 {#请求日志与指标}

请求日志要能回答两件事：哪个请求慢了，慢在哪里。入口日志至少保留这些信息：

- 请求 ID，用来关联同一个请求的多条日志。
- HTTP 方法和路径模板，用来确定是哪个接口。
- 响应状态码，用来区分成功和失败。
- 完整耗时和响应大小，用来判断处理成本和写出成本。

**高基数**是指指标标签有大量不同的取值，会增加指标存储和查询的成本。例如，把每个用户 ID 都放进路径标签，会为不同用户产生不同的标签值。因此接口指标应使用 `/users/{id}` 这样的路径模板。

计时的位置决定了你看到的是哪一段。服务端处理耗时包含 Filter、参数读取、业务执行和响应序列化，异步请求还要算上等待结果的时间；只给 Controller 方法计时，看到的只是其中一段。

定位慢请求时，用调用追踪或性能分析把各阶段的耗时拆开。数据库等待单独观察；请求进入应用之前的连接等待，要结合客户端和容器的指标判断。这样才能分清是业务执行慢、排队慢，还是响应写出慢。

## 8. 异步执行容量 {#异步执行容量}

MVC 异步释放的只是 Servlet 请求线程，剩下的工作照样消耗资源：`Callable` 里的阻塞任务占着执行器线程，正在执行的数据库操作也继续占着连接。所以异步接口要同时约束**执行器、超时与下游容量**。

AsyncTaskExecutor 是 MVC 执行异步任务的执行器，要配置线程数、队列容量，以及任务过多时的拒绝策略。还要设置异步超时，并处理超时以后才返回的任务结果。注意 HTTP 超时只是结束了响应，后台任务不会自动停下，要单独取消或收尾，才能释放它占用的资源。

MVC 异步也不等于整条链路都变成非阻塞。MVC 写出消息仍然用阻塞 I/O。WebFlux 是另一套响应式执行模型，不走这条 Servlet DispatcherServlet 调用链。Java 21 的虚拟线程也可以承载传统 Servlet 同步代码和阻塞任务。选哪种，要看任务的阻塞特征和框架支持；无论选哪种，数据库连接这类下游容量都要单独限制。

## 9. 常见问题 {#常见问题}

### 9.1 Controller 是 Servlet 吗？ {#controller-与-servlet}

不是。注解 Controller 是由适配器调用的普通 Spring Bean。DispatcherServlet 才是 Servlet，它作为前端控制器接收容器分派的请求，再协调对 Controller 的调用。

### 9.2 一个请求一定只执行一次 Filter 吗？ {#请求与多次派发}

不一定。一个请求可以经历多次派发，Filter 也就可能再次执行。初始请求是 REQUEST 派发，之后还可能有 ASYNC、ERROR 或 FORWARD 派发，FORWARD 表示服务端把请求转发给另一个目标。

Filter 是否参与每次派发，由注册方式和过滤器自己的策略共同决定。`OncePerRequestFilter` 也提供了控制异步和错误派发的钩子，见 [Spring 拦截机制](./filter-interceptor-aspect-boundaries.mdx#异步与-threadlocal)。

## 10. 面试题 {#面试题}

### 10.1 一次 HTTP 请求在 Spring MVC 中怎样到达 Controller {#request-to-controller}

**考察重点**：按请求顺序说明容器与 MVC 组件的分工，并解释参数准备、返回值转换和异常解析发生在哪个阶段。

**相关内容**：[Servlet 容器](#servlet-容器)至[返回值处理](#返回值处理)。

<details>
<summary>参考回答</summary>

**请求由服务器解析，经 Servlet 容器安排执行，再通过 Filter 链进入 DispatcherServlet。**

DispatcherServlet 用 HandlerMapping 找到 handler 和拦截器，再选出支持它的 HandlerAdapter。

`preHandle` 放行后，适配器准备参数并调用 Controller，参数准备会用到参数解析器、数据绑定和消息转换器。方法返回后，返回值处理器写出正文或准备视图，随后执行后置回调、视图渲染和完成回调。

MVC 处理阶段的异常进入解析器链，异步结果通过后续派发继续处理。参数读取和响应序列化都要花时间，所以完整请求耗时要覆盖 Controller 方法之外的阶段。

</details>

### 10.2 Controller 返回 Callable 后，结果怎样写回，Controller 会再次执行吗？ {#async-redispatch}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释初始线程何时释放、结果由谁生成，以及异步派发怎样继续处理已有结果。

**相关内容**：[异步请求](#异步请求)。

<details>
<summary>参考回答</summary>

**Callable 的结果通过 ASYNC 派发交回 MVC，Controller 方法不会再次执行。**

MVC 开启 Servlet async 后，把 Callable 交给执行器，初始请求线程就可以返回容器。

任务完成后，MVC 保存结果并发起 ASYNC 派发。框架重新找到 handler，用已有结果继续返回值转换和响应写出。如果 Callable 抛出异常，异常也通过这次派发交给 MVC 的异常解析器。

</details>
