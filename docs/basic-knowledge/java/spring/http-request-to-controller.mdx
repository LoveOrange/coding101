# Spring MVC 请求生命周期

Spring MVC 请求从 Servlet 容器进入，再由框架调用 Controller。本文负责端到端顺序、返回值与异步续接。处理器策略见 [DispatcherServlet](./dispatcherservlet-handler-mapping.mdx)。参数绑定见 [Spring MVC 参数解析](./binding-validation-content-negotiation.mdx)。

## 1. 面试核心 {#core}

- Servlet 容器接收 HTTP 请求，Filter 链随后调用 DispatcherServlet。
- MVC 经处理器映射、参数解析和适配调用后，执行 Controller。[卡](#request-to-controller)
- `@ResponseBody` 交给消息转换器，视图名交给 ViewResolver 解析。
- MVC 异步释放初始线程，结果就绪后通过 ASYNC 派发续接。[卡](#async-redispatch)
- 序列化发生在 Controller 返回后，也计入完整请求耗时。

## 2. Servlet 容器 {#servlet-容器}

Tomcat、Jetty 等服务器处理 HTTP 协议。Servlet 容器构造 request/response，并安排请求执行。

MVC 接收 Servlet API 对象，负责应用层分派。连接数、accept 队列与请求线程由服务器管理。应用数据库连接池和业务执行器需单独观察。

## 3. Filter 链 {#filter-链}

Filter 按注册范围包装请求并控制是否继续，详见 [Spring 拦截机制](./filter-interceptor-aspect-boundaries.mdx#filter)。

## 4. DispatcherServlet {#dispatcherservlet}

同步成功路径按以下顺序执行：

1. 映射器查找处理器和拦截器。
2. DispatcherServlet 选择匹配的适配器。
3. 拦截器执行 `preHandle`。
4. 适配器解析参数并调用 Controller。
5. 返回值处理器写响应或准备视图。
6. 拦截器执行 `postHandle`。
7. 有视图时执行渲染，再调用 `afterCompletion`。

异常发生时进入解析分支。各策略职责见 [DispatcherServlet](./dispatcherservlet-handler-mapping.mdx)。

## 5. 返回值处理 {#返回值处理}

```java
@RestController
class OrderController {
    @GetMapping("/orders/{id}")
    OrderResponse get(@PathVariable long id) {
        return service.find(id);
    }
}
```

示例在 `@RestController` 中返回对象。返回值处理器选择消息转换器，将对象写为响应体。

`@Controller` 方法返回 String 时，可将其解释为视图名。`@ResponseBody` 或 `@RestController` 则将 String 作为正文。`ResponseEntity` 还可指定状态与响应头。

视图路径由 ViewResolver 解析，再由 View 渲染。JSON 序列化出错发生在 Controller 返回后。响应仍未提交时，可继续尝试 MVC 异常处理。

## 6. 异步请求 {#异步请求}

`Callable` 与 `DeferredResult` 支持单次异步结果。

| 返回类型 | 结果生产方式 |
| --- | --- |
| `Callable` | MVC 将任务交给配置的 AsyncTaskExecutor |
| `DeferredResult` | 应用从其他线程调用 `setResult` 或 `setErrorResult` |

两者都会开启 Servlet async，释放初始请求线程。结果准备好后，MVC 发起 ASYNC 派发。框架重新定位 handler，但用已有结果继续返回值处理。Controller 方法无需再执行一次。

初始线程执行 `afterConcurrentHandlingStarted`。此时跳过普通 `postHandle` 与 `afterCompletion`。最终派发再进入完成流程，超时还需相应异步回调。

`Callable` 抛错或 `setErrorResult(exception)` 会进入 MVC 异常解析。独立 `@Async` 后台任务的失败则由其结果协议处理。

## 7. 请求日志与指标 {#请求日志与指标}

请求日志记录 ID、方法、路径模板、状态与完整耗时。指标使用模板路径，避免用户 ID 形成高基数标签。

完整耗时包含 Filter、参数读取、业务执行和响应序列化。异步请求还需包含等待结果的时间。Controller 方法计时只反映其中一段。

## 8. 异步执行容量 {#异步执行容量}

MVC 异步释放 Servlet 请求线程，工作仍需执行资源。`Callable` 的阻塞任务占用业务执行器线程。数据库请求继续占用连接。

应配置 AsyncTaskExecutor 的容量与拒绝策略。还需设置异步超时，并处理超时后的任务结果。HTTP 超时结束响应时，后台任务仍需单独取消或收尾。

MVC 消息写出仍采用阻塞 I/O。WebFlux 的执行模型与此不同。虚拟线程可承载阻塞任务，但下游连接容量仍需限制。

## 9. 常见问题 {#常见问题}

### 9.1 Controller 与 Servlet {#controller-与-servlet}

注解 Controller 是 Spring Bean，由适配器调用。DispatcherServlet 才是 Servlet 前端控制器。

### 9.2 请求与多次派发 {#请求与多次派发}

一个请求可经历 REQUEST、ASYNC 或 ERROR 等派发。Filter 是否再次执行，由注册方式与过滤器策略决定。
