# JDK 动态代理与 CGLIB

JDK 动态代理和 CGLIB 是 Spring AOP 创建代理的两种方式。**代理**是放在目标对象前面的对象：外部调用先到代理，代理在业务方法前后加上事务、日志等增强逻辑，再把调用转给目标对象。

两者的根本区别在于代理怎样获得调用方需要的类型：JDK 代理实现和目标相同的接口，CGLIB 生成目标类的子类。这一个区别决定了代理能被当成什么类型注入、哪些方法能被拦截、`final` 会造成什么影响。本文以 Spring Framework 6.2 和 Spring Boot 3.5 为准，Boot 的默认选择和 Framework 不同，这一点也要能讲清楚。

## 1. 面试核心 {#core}

- JDK 动态代理**实现指定接口**，接口方法的调用交给 `InvocationHandler` 处理。[卡](#jdk-proxy-vs-cglib)
- CGLIB **生成目标类的子类**，通过覆盖方法拦截调用，所以可以代理没有业务接口的类，但**受 `final`、`private` 等继承规则限制**。
- Spring Framework 默认对有接口的目标用 JDK 代理；**Boot 3.5 的 AOP 自动配置默认使用类代理**，设置 `spring.aop.proxy-target-class=false` 后，有接口的目标改用 JDK 代理。
- Spring 6.0 起，类代理**默认支持在 `protected` 和包可见方法上使用 `@Transactional`**。
- 目标实现方法声明为 `final` 时，**JDK 代理仍能增强通过接口发起的调用**，因为它不需要覆盖目标方法。[卡](#final-interface-method)

## 2. JDK 动态代理 {#jdk-动态代理}

**JDK 动态代理**在运行时生成一个实现指定接口的类。调用代理的接口方法时，代理把方法对象和参数交给 **`InvocationHandler`**，这是 JDK 定义的调用处理接口，增强逻辑就写在它里面，转发给目标对象前后都可以执行。下面用它把支付接口的调用转发给目标对象：

```java
PaymentService target = new DefaultPaymentService();

PaymentService proxy = (PaymentService) Proxy.newProxyInstance(
        PaymentService.class.getClassLoader(),
        new Class<?>[] {PaymentService.class},
        (object, method, arguments) -> {
            try {
                return method.invoke(target, arguments);
            } catch (InvocationTargetException exception) {
                throw exception.getCause();
            }
        }
);
```

`proxy` 实现了 `PaymentService`，第三个参数里的 Lambda 就是调用处理器。调用 `proxy` 的任意接口方法，都会进入这个 Lambda，再由 `method.invoke(target, arguments)` 执行目标方法。

异常要多处理一步。目标方法抛出异常时，反射会把它包装成 `InvocationTargetException`，示例取出 `getCause()` 重新抛出，调用方看到的就是原始异常。如果原始异常是接口方法没有声明的受检异常，JDK 代理仍会把它包装成 `UndeclaredThrowableException`。

类型上要注意：代理和 `DefaultPaymentService` 都实现了 `PaymentService`，但两者之间没有继承关系。所以代理只能当成接口类型使用，不能强转成 `DefaultPaymentService`，接口里没有声明的方法也调用不到。

放到 Spring 里也是一样。如果 Bean 是 JDK 代理，按实现类 `DefaultPaymentService` 去注入或查找，就会遇到类型不匹配。依赖要按代理实现的接口声明。

## 3. CGLIB {#cglib}

**CGLIB** 通过生成目标类的子类来创建代理，所以目标没有业务接口也能代理。子类覆盖目标方法，为调用提供拦截入口。在 Spring AOP 中，调用从这个入口进入拦截链，再转给目标对象；代理实例和目标实例仍然是分开的。

既然靠继承和覆盖，能不能拦截一个方法，就由 Java 的继承和可见性规则决定：

| 成员 | 子类代理边界 |
| --- | --- |
| `final` 类 | 无法生成子类 |
| `final` 方法 | 无法覆盖 |
| `private` 方法 | 子类无法覆盖 |
| `static` 方法 | 属于类调用，无法通过实例覆盖 |
| 跨包不可见方法 | 受 Java 可见性约束 |

Spring 已经把 CGLIB 重新打包进 `spring-core`，使用 Spring AOP 时不需要单独引入 cglib 依赖。另外，Java 模块系统也控制包和成员能否被外部访问：模块没有开放所需的访问权限时，即使类允许继承，代理也可能生成不了。

子类代理还有一个问题：创建子类实例，按理要调用父类构造器，目标类的构造器就会多执行一次。Spring 用 Objenesis 创建类代理实例来避免这一点。Objenesis 能绕过构造器创建对象，在 JVM 支持时，目标类构造器只在创建目标实例时执行一次。如果 JVM 禁止绕过构造器，Spring 会退回到调用构造器来创建代理，这时目标类的构造器会额外执行一次。

Kotlin 的类和方法默认是 `final`，同样受这些继承限制。使用类代理时，要让目标类和方法可继承、可覆盖：可以显式写 `open`，也可以用 `kotlin-spring` 插件自动开放符合条件的组件。

## 4. Spring 的默认选择 {#spring-的默认选择}

实际用哪种代理，要分清 Framework 的默认规则和 Boot 的自动配置，两者不一样。

- **Spring Framework 6.2**：目标有接口时用 JDK 代理，没有接口时用 CGLIB；设置 `proxyTargetClass=true` 可以强制使用类代理。
- **Spring Boot 3.5**：AOP 自动配置默认启用类代理，也就是即使目标有接口，也用 CGLIB。设置 `spring.aop.proxy-target-class=false` 后，有接口的目标改用 JDK 代理，没有接口的目标仍然只能用类代理。Boot 2.7 的 AOP 自动配置也是这个默认策略。

多处代理配置会共同影响最终结果，所以排查时别靠推断，直接检查容器实际交付的对象：

```java
AopUtils.isAopProxy(bean);
AopUtils.isJdkDynamicProxy(bean);
AopUtils.isCglibProxy(bean);
```

三个方法分别判断对象是不是 Spring AOP 代理、JDK 代理和 CGLIB 代理，返回布尔值，可以用来核对配置是否生效。比如目标类明明实现了接口，只要有强制类代理的配置，结果也会是 CGLIB。

## 5. 自调用 {#自调用}

两种代理都只能拦截经过代理对象的调用。目标对象用 `this` 调用自己的方法时，调用直接发生在目标对象内部，不经过代理，增强就不会生效。原因和拆分 Bean 等处理方式见 [Spring AOP](./aop-pointcut-interceptor-chain.mdx#同类自调用)。

## 6. 代理类型与注解匹配 {#代理类型与注解匹配}

能拦截一个方法，不等于增强一定会作用在它上面。增强通常靠注解识别，而读注解要找到真正声明注解的类和方法。

先是类。对代理调用 `getClass()`，得到的是生成的代理类，不是目标类。所以自己写反射代码读注解时，要先识别代理，再定位目标类和它实际执行的方法。

再是方法。接口方法和实现方法是两个不同的反射对象，只检查其中一个，会漏掉写在另一处的注解。编译器还会为泛型重写等情况生成**桥接方法**，用来维持多态调用，读注解时也要找到它对应的业务方法。Spring 的事务属性解析器会处理这些对应关系。

方法可以被代理拦截之后，还要符合具体增强的识别规则。Spring 6.0 起，类代理的事务默认支持 `protected` 和包可见方法；JDK 代理的事务入口则必须是代理接口里声明的 `public` 方法。把事务属性解析器的 `publicMethodsOnly` 设为 `true`，识别范围会收窄到公开方法。

## 7. 性能 {#性能}

选代理类型时，先看调用方需要什么类型、哪些方法需要增强，性能通常不是决定因素。业务里有数据库或网络 I/O 时，代理调用的开销一般比这些等待和业务计算小得多。

分析代理耗时，可以把调用过程拆成三部分：

- 方法分派：把调用送到处理器或目标方法。
- 切点判断：确定当前方法要执行哪些增强。
- 拦截链：执行事务、日志等实际增强逻辑，这部分也要花时间。

调用频率高、方法体又很短时，代理开销才更容易影响总耗时。这时要用实际部署的 JDK、Spring 和 CGLIB 版本来测量，因为实现会随版本变化。可以先用 JMH 做微基准测试，再用性能剖析工具看真实调用链。测试要带上实际的增强逻辑，只测空代理反映不了业务里的成本。

## 8. final 实现方法与接口代理 {#final-实现方法与接口代理}

`final` 限制的是继承和覆盖，所以它对两种代理的影响不同。JDK 代理自己实现接口，再把调用转给目标对象，整个过程不需要继承目标类。下面的类和方法都声明为 `final`：

```java
interface PaymentService {
    void pay();
}

final class DefaultPaymentService implements PaymentService {
    public final void pay() {}
}
```

`DefaultPaymentService` 可以作为 JDK 代理的目标。通过代理接口调用 `pay()` 时，调用先进入 `InvocationHandler`，再由处理器执行目标方法，中间没有任何覆盖，所以目标实现上的 `final` 不影响接口调用的增强。

换成 CGLIB 结果就不同了。强制类代理时，`final` 类会让子类生成直接失败。把类改成非 `final`、只保留方法上的 `final`，子类能生成了，但 `pay()` 仍然覆盖不了，对这个方法的增强不会生效。

## 9. 常见问题 {#常见问题}

### 9.1 强制 CGLIB 后，非公开方法都能增强吗？ {#非公开方法的代理范围}

并非都能增强，方法要同时满足可覆盖和增强可识别这两项要求。`private` 方法无法被子类覆盖，因此会被排除。`protected` 和同包可见方法还要符合事务等增强的识别规则，具体见[代理类型与注解匹配](#代理类型与注解匹配)。

### 9.2 代理对象和目标对象是同一个实例吗？ {#代理引用与目标引用}

在本文的 Spring AOP 代理方式中，代理对象与目标对象是两个实例。代理通过 `TargetSource` 获取目标对象，再执行匹配当前方法的拦截链。`TargetSource` 是用于取得目标对象的 Spring 接口，链执行到底后才调用目标方法。

容器会把代理引用交给依赖它的其他 Bean。调用方使用这个引用，才能经过增强逻辑；直接持有目标对象并调用，会绕过代理。

## 10. 面试题 {#面试题}

### 10.1 JDK 动态代理与 CGLIB 有什么区别 {#jdk-proxy-vs-cglib}

**考察重点**：说明接口转发与子类覆盖怎样影响可调用的方法，并解释 `final`、`private` 和自调用的边界。能结合配置判断实际代理类型。

**相关内容**：[JDK 动态代理](#jdk-动态代理)至[自调用](#自调用)。

<details>
<summary>参考回答</summary>

**JDK 动态代理实现接口，把调用交给 `InvocationHandler`；CGLIB 继承目标类，通过覆盖方法拦截调用。**

- **JDK 代理按接口使用。** 它无需覆盖目标实现方法，所以接口暴露的方法即使实现为 `final`，仍可增强。
- **CGLIB 可代理无接口的类。** 目标类必须可继承，目标方法必须可覆盖，`final` 类以及 `final`、`private` 方法因此受限。

Spring Framework 默认对有接口的目标使用 JDK 代理；Boot 3.5 的 AOP 自动配置默认使用类代理，可用 `spring.aop.proxy-target-class=false` 切回接口优先。实际类型可用 `AopUtils` 核对。两者都要求调用经过代理，`this` 自调用会绕过增强。

</details>

### 10.2 目标实现方法是 final，JDK 动态代理还能增强它吗？ {#final-interface-method}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释 JDK 代理为何无需覆盖目标方法，以及 `final` 对接口转发和子类覆盖的不同影响。

**相关内容**：[final 实现方法与接口代理](#final-实现方法与接口代理)。

<details>
<summary>参考回答</summary>

**可以，前提是该方法由代理接口暴露，并且调用经过代理对象。**

JDK 代理实现的是接口，接到调用后先进入 `InvocationHandler`，再由处理器转发给目标对象。它无需覆盖目标方法，所以目标实现方法为 `final` 也能增强。

CGLIB 依靠子类覆盖目标方法，`final` 方法无法提供这种拦截入口。若目标类本身也是 `final`，子类代理连生成这一步都会失败。

</details>
