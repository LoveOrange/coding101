# Bean 生命周期

**Bean 生命周期**是 Spring 容器创建、初始化、交付和销毁一个对象的过程。理解各阶段的顺序，才能判断依赖何时可用、调用是否经过代理，以及应用关闭时资源由谁释放。例如，构造器执行时字段注入还没发生，在构造器里访问这类依赖就会拿到 `null`。

## 1. 面试核心 {#core}

- 普通 Bean 依次经过**实例化、填充依赖、Aware 回调、初始化前处理、初始化回调和初始化后处理**，然后才交给调用方。[卡](#bean-lifecycle)
- 同一个 Bean 声明了多种初始化方法时，按 **`@PostConstruct`、`afterPropertiesSet()`、自定义初始化方法**的顺序调用。
- `@PostConstruct` 由初始化前处理器调用，**发生在最终代理交付之前**，在里面自调用不会经过代理。
- 容器正常关闭时会**销毁它管理的 singleton**；prototype 交给使用者之后，清理由使用者负责。
- `SmartLifecycle` 的 **phase 越小，启动越早、停止越晚**。[卡](#smart-lifecycle-phase)

## 2. 实例化与依赖注入 {#实例化与依赖注入}

容器创建一个普通 Bean，要先得到对象，再把它需要的依赖填进去，最后才交给调用方。整个过程分六步：

1. 容器选择构造器或工厂方法，创建实例。
2. 注入处理器解析 `@Autowired`、`@Value` 等注解，填充字段和方法依赖。
3. 容器调用 `BeanNameAware`、`BeanFactoryAware` 等回调，把 Bean 名称或工厂交给需要这些信息的组件。
4. 初始化前处理器执行，`@PostConstruct` 方法就在这一步被调用。
5. 容器调用 `afterPropertiesSet()` 和自定义初始化方法。
6. 初始化后处理器可以把对象包装一层，容器把最终得到的引用作为可用 Bean 交给调用方。

**Aware 接口**是让组件接收容器信息的回调接口，比如拿到自己的 Bean 名称、所在的工厂或应用上下文。它们的执行位置不完全一样：`BeanNameAware`、`BeanFactoryAware` 在第 3 步直接回调，`ApplicationContextAware` 则由第 4 步的初始化前处理器回调。

第 1、2 步的先后决定了依赖什么时候可用。构造器参数在实例化时就解析好了，字段依赖要等实例创建出来才填充。所以在构造器里访问一个靠字段注入的依赖，拿到的还是 `null`。

## 3. 初始化回调 {#初始化回调}

**初始化回调**在依赖注入完成之后执行，用来检查对象是否具备工作条件，或者准备必要的资源。下面的 `@PostConstruct` 方法检查超时参数：

```java
@PostConstruct
void validateConfiguration() {
    if (timeout.isNegative() || timeout.isZero()) {
        throw new IllegalArgumentException("timeout must be positive");
    }
}
```

超时是零或负数时，`validateConfiguration` 抛出异常，Bean 创建失败。如果这是启动时创建的非懒加载单例，应用启动也会失败；懒加载 Bean 则可能到第一次获取时才暴露错误。初始化方法适合做这类本地校验和必要的资源准备；耗时的工作要设好超时和完成条件。

同一个 Bean 声明了多种初始化方法时，按下面的顺序执行：

1. `@PostConstruct` 方法。
2. `InitializingBean.afterPropertiesSet()`。
3. 自定义 `init-method`。

如果同一个方法被配置成了多种方式，它只会被调用一次。Spring 6 使用的是 `jakarta.annotation.PostConstruct`。业务类优先用这个注解或自定义初始化方法，少依赖 Spring 专用的 `InitializingBean` 接口。

## 4. BeanPostProcessor {#beanpostprocessor}

**`BeanPostProcessor`** 是在 Bean 初始化前后处理实例的扩展点。初始化前处理器负责生命周期注解等逻辑，初始化后处理器可以返回一个包装对象来代替原始实例。普通的 AOP 就是在初始化后这一步生成代理的，所以从容器拿到的引用可能和最初创建的实例不是同一个对象。循环依赖时还有一条提前生成代理的路径，见 [Spring 循环依赖](./circular-dependencies-scopes-early-exposure.mdx)。

在默认代理模式下，初始化方法里调用自己的事务方法，不会触发事务增强。初始化回调在原始对象上执行，`this` 调用没有经过代理。需要事务增强的预热工作，可以交给 Runner 调用另一个 Bean。**Runner** 是 Boot 在上下文刷新完成后执行的启动任务，这时它可以通过容器交付的代理调用目标方法。

`SmartInitializingSingleton` 在所有非懒加载单例创建完之后回调，适合检查这些单例能否配合工作。这个回调仍处在上下文刷新过程中，不代表整个应用已经就绪。需要等刷新完成再协调的工作，也可以监听上下文刷新事件，但仍要明确依赖和耗时。

## 5. 初始化与服务就绪 {#初始化与服务就绪}

对象初始化完成，不等于服务可以接收流量：连接可能还没建好，业务预热可能还没做完。如果把长任务放进构造器或 `@PostConstruct`，上下文刷新会被拖长，出错时也很难分清是哪个阶段失败的。启动工作可以这样分配：

- 本地配置校验放在初始化回调里，尽早发现错误。
- 必要资源在初始化阶段建立，并设置明确的连接超时。
- 必须在对外服务前完成的业务预热放在 Runner 里，完成后再允许接收流量。
- 非关键预热交给受管理的后台执行器，提供超时、指标和降级方式。

后台任务还要有停止机制，保证应用关闭时能结束。Readiness 状态表示服务是否就绪；非关键预热失败时，应该保留其余仍能提供的服务能力，而不是让整个应用不可用。

启动各阶段的分工见 [Spring Boot 启动](./spring-boot-startup.mdx#runner-与就绪)。

## 6. 销毁回调 {#销毁回调}

**销毁回调**用来释放 Bean 持有的资源。singleton 是容器里共享的单个实例，容器正常关闭时按下面的顺序调用它的销毁方法：

1. `@PreDestroy` 方法。
2. `DisposableBean.destroy()`。
3. 自定义 `destroy-method`。

Spring 6 使用 `jakarta.annotation.PreDestroy`。同一个方法配置了多次，也只调用一次。

线程池、客户端连接和文件句柄都要有明确的所有者负责关闭。清理过程要有时间上限，否则一个组件一直等下去，整个应用的优雅关闭都会被卡住。

prototype 是每次向容器请求都新建的实例。它会正常经过初始化，但交出去之后容器就不再跟踪它，也不会调用它的销毁回调，清理由使用者负责。进程被强制终止或崩溃时，不能保证销毁回调执行。关键的一致性操作不能只依赖关闭时的清理，还需要持久化状态和恢复机制。

## 7. 生命周期日志 {#生命周期日志}

排查启动慢或启动失败，要把异常和耗时对应到具体的 Bean 和它所处的生命周期阶段。日志里记录 Bean 名称、阶段、耗时和异常根因，再沿时间线找出是在哪里等待的。

启动步骤记录和 JFR 事件可以帮忙分析。JFR（Java Flight Recorder）是 JVM 自带的事件记录工具，能把初始化耗时和类加载、内存分配、GC 放在一起看。按问题有针对性地采集，比给每个 Bean 都打一堆普通日志噪声小得多。

诊断工具的配置见 [Spring Boot Actuator](./actuator-health-startup-diagnostics.mdx#启动阶段分析)。

## 8. SmartLifecycle 启停顺序 {#smartlifecycle-启停顺序}

消息消费者这类组件，除了创建和销毁，还要控制什么时候开始工作、什么时候停止接收任务。**`SmartLifecycle`** 就是管理这种启动和停止过程的接口。`isAutoStartup()` 返回 `true` 时，组件随上下文刷新自动启动。

**phase** 是决定启停顺序的阶段值：数值越小，启动越早、停止越晚。假设连接组件的 phase 是 0，消费者是 100。启动时连接先起来，消费者再开始工作；关闭时消费者先停，连接最后关。这样消费者在停止过程中还能用连接处理完手上的消息。如果组件之间声明了显式依赖，依赖关系优先于 phase。

异步停止通过 `stop(Runnable callback)` 协调。组件真正停下来之后，必须调用 `callback.run()`，通知生命周期处理器停止已经完成。漏掉这个通知会拖延上下文的关闭流程。

`stop()` 管的是组件还在不在工作，销毁回调负责最后释放资源。启动失败等异常关闭路径可能直接销毁 Bean，所以清理逻辑也要能处理组件从未启动的状态。

## 9. 常见问题 {#常见问题}

### 9.1 `@PostConstruct` 中调用自己的事务方法会生效吗？ {#初始化回调中的事务调用}

默认代理模式下不会。初始化回调中的 `this` 调用没有经过事务代理，拦截器就没有机会开启事务。可以用 `TransactionTemplate` 显式开启事务，或者把工作交给 Runner，让它通过代理调用另一个负责事务的 Bean。

### 9.2 `@PreDestroy` 一定会执行吗？ {#销毁回调的执行条件}

不一定。对象要在容器的销毁管理范围内，而且容器要正常走到销毁阶段，回调才会执行。进程被强制终止或崩溃时这类清理会被跳过，prototype 交付后也不归容器销毁。所以关键的一致性操作还需要持久化记录和恢复机制。

## 10. 面试题 {#面试题}

### 10.1 Spring Bean 从创建到销毁经历哪些关键阶段 {#bean-lifecycle}

**考察重点**：解释实例创建、依赖填充、Aware 和初始化前后处理的顺序，并说明代理发布与不同作用域的销毁边界。

**相关内容**：[实例化与依赖注入](#实例化与依赖注入)至[销毁回调](#销毁回调)。

<details>
<summary>参考回答</summary>

**Bean 先经过实例化、依赖注入和初始化，再发布给调用方，最后按容器管理范围执行销毁。**

容器按定义选择构造器或工厂方法，得到实例后填充字段和方法依赖。随后执行 Aware 回调，让需要容器信息的组件取得名称、工厂或上下文。

初始化前处理器会调用 `@PostConstruct`，之后依次执行 `afterPropertiesSet()` 和自定义初始化方法。初始化后处理器可返回代理，所以容器发布的是处理后的引用。

正常关闭时，容器为其管理的 singleton 执行销毁回调。顺序为 `@PreDestroy`、`DisposableBean.destroy()` 和自定义销毁方法。prototype 交付后的清理由使用者负责，强制退出也无法保证回调执行。

</details>

### 10.2 消费者依赖连接组件时，怎样安排启动和停止顺序？ {#smart-lifecycle-phase}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：用 phase 和显式依赖安排消费者与连接的启停顺序，并解释异步停止为何要通知生命周期处理器。

**相关内容**：[SmartLifecycle 启停顺序](#smartlifecycle-启停顺序)。

<details>
<summary>参考回答</summary>

**应让连接先启动、后停止，消费者后启动、先停止。**

可以把连接组件 phase 设为 0，消费者设为 100，让消费者启动和停止时都有可用连接。显式依赖关系优先于 phase，因此还要核对组件之间的依赖声明。

异步停止结束后，组件必须调用 `callback.run()`，通知生命周期处理器继续关闭。销毁回调则负责最终释放资源，也要兼容组件尚未成功启动的情况。

</details>
