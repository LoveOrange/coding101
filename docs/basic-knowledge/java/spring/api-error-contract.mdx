# API 错误契约

API 错误契约让客户端按稳定字段处理失败。本文负责异常映射、HTTP 状态和错误响应。参数绑定与校验见 [Spring MVC 参数解析](./binding-validation-content-negotiation.mdx)。

## 1. 面试核心 {#core}

- `@RestControllerAdvice` 通过 MVC 异常解析链集中映射错误。[卡](#global-exception-handling)
- Spring 6 的 `ProblemDetail` 表达标准问题字段，并支持扩展字段。
- 同一处理器内，异常类型匹配按继承深度选择。[卡](#exception-handler-selection)
- MVC 异步结果中的异常仍能进入 `@ExceptionHandler`。
- 响应已提交后，错误处理器无法重新设置完整响应。

## 2. 错误字段 {#错误字段}

`ProblemDetail` 提供 `type`、`title`、`status`、`detail` 和 `instance`。本文按 RFC 9457 说明字段语义。

```json
{
  "type": "https://coding101.dev/problems/order-state",
  "title": "Order state conflict",
  "status": 409,
  "detail": "The order has already been paid",
  "instance": "/orders/101",
  "code": "ORDER_ALREADY_PAID",
  "traceId": "..."
}
```

`code` 和 `traceId` 是业务扩展字段。客户端按状态、`type` 或稳定错误码分支。`detail` 用于展示，内容可随语言变化。

响应使用 `application/problem+json`。正文的 `status` 应与实际 HTTP 状态一致。Spring MVC 的消息转换器支持该格式。

## 3. 异常处理器 {#异常处理器}

```java
@RestControllerAdvice
class ApiExceptionHandler {
    @ExceptionHandler(OrderStateException.class)
    ResponseEntity<ProblemDetail> handle(OrderStateException exception) {
        ProblemDetail problem = ProblemDetail.forStatus(409);
        problem.setTitle("Order state conflict");
        problem.setProperty("code", "ORDER_STATE_CONFLICT");
        return ResponseEntity.status(409).body(problem);
    }
}
```

示例把订单状态冲突映射为 HTTP 409。异常类型承载失败分类，HTTP 状态表达协议语义。未知异常映射为 500，并在日志中保留根因。

`ResponseEntityExceptionHandler` 提供 MVC 标准异常处理基类。继承它可统一绑定错误、媒体类型错误等响应。

## 4. 状态码 {#状态码}

| 状态 | 语义 |
| --- | --- |
| 400 | 请求语法、参数或校验错误 |
| 401 | 缺少有效认证凭证；需返回 `WWW-Authenticate` |
| 403 | 服务端理解请求，但拒绝执行 |
| 404 | 资源不存在，或服务端拒绝披露其存在 |
| 409 | 操作与资源当前状态冲突 |
| 429 | 请求频率超过限制 |
| 500 | 服务端未预期错误 |
| 502 | 网关收到无效的上游响应 |
| 503 | 服务暂时无法处理请求 |
| 504 | 网关等待上游响应超时 |

客户端重试还需考虑幂等性和 `Retry-After`。依赖失败需根据服务角色映射，避免一律返回网关状态。

## 5. 日志与响应 {#日志与响应}

错误响应只保留公开错误字段。堆栈、SQL、密钥和内部路径留在受控诊断范围。

服务端日志记录 cause、trace ID 和必要业务标识。预期业务冲突可记录简要信息。未知异常在处理边界记录一次完整堆栈，避免重复日志。

## 6. ControllerAdvice 的处理范围 {#controlleradvice-的处理范围}

`ControllerAdvice` 参与 `DispatcherServlet` 的异常解析。Filter 在进入 MVC 前抛出的异常需由过滤链或容器处理。

MVC 的 `Callable` 抛错后会触发异步派发。`DeferredResult.setErrorResult(exception)` 也走该流程。异常随后交给 MVC resolver。独立后台任务的失败由任务结果或异常处理器承接。

响应提交后，状态与已写出的正文已经交付。此时应记录写出失败，并按连接状态结束处理。客户端断开造成的 I/O 错误应单独统计。

## 7. 字段校验错误 {#字段校验错误}

```json
{
  "code": "VALIDATION_FAILED",
  "errors": [
    {"field": "quantity", "code": "Positive"}
  ]
}
```

字段路径需约定数组和嵌套对象的表达方式。响应省略密码等敏感拒绝值。本地化消息与稳定错误码分别维护。

## 8. 契约测试 {#契约测试}

测试每类公开错误的状态、媒体类型和字段结构。用敏感值作为测试输入，检查响应是否泄露。

边界用例包括路由缺失、方法错误、校验失败和 Filter 拒绝。还需覆盖异步异常、下游超时与响应写出失败。

## 9. 异常处理器选择 {#异常处理器选择}

Controller 内的局部 `@ExceptionHandler` 优先于全局 Advice。多个 Advice 按 `Ordered` 或 `@Order` 排序。较小的值具有较高优先级。

同一 Controller 或 Advice 内，先匹配顶层异常。多个类型匹配时，选择继承距离更近的类型。顶层无匹配时再查 cause 链。Spring 5.3 起支持任意深度的 cause。

跨 Advice 时，优先级先决定查找顺序。高优先级 Advice 的 cause 匹配可先于低优先级的顶层匹配。将 `Exception` 兜底放在低优先级 Advice，避免提前截获错误。方法书写顺序不参与选择。

## 10. 常见问题 {#常见问题}

### 10.1 成功响应与错误响应 {#成功响应与错误响应}

成功响应可直接返回资源，错误响应采用稳定结构。团队使用统一包装时，也应保留正确的 HTTP 状态。

### 10.2 未知异常兜底 {#未知异常兜底}

边界可捕获 `Exception`，脱敏后返回 500。兜底 Advice 应设置较低优先级。响应已提交时，应保留原响应并记录失败。
