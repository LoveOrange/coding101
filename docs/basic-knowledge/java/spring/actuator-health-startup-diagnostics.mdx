# Spring Boot Actuator

Spring Boot Actuator 提供运行状态和诊断端点。本文以 Boot 3.5 为准，负责端点访问、探针和启动诊断。启动事件顺序见 [Spring Boot 启动](./spring-boot-startup.mdx)。

## 1. 面试核心 {#core}

- `management.endpoints.web.exposure.include` 决定 HTTP 暴露范围。
- Liveness 失败触发重启，readiness 失败停止流量。[卡](#health-checks)
- 默认 liveness 与 readiness 健康组只检查应用可用性状态。
- `BufferingApplicationStartup` 为 `startup` 端点采集启动步骤。
- 独立管理端口的探针成功只验证管理服务路径。[卡](#probe-main-port)

## 2. 常用端点 {#常用端点}

| 端点 | 信息 |
| --- | --- |
| `health` | 组件健康状态与健康组 |
| `metrics`、`prometheus` | 指标查询与 Prometheus 抓取 |
| `conditions` | 自动配置匹配报告 |
| `configprops`、`env` | 配置绑定与属性来源 |
| `beans`、`mappings` | Bean 与 Web 路由 |
| `startup` | 启动步骤 |
| `loggers` | 日志级别查询与调整 |
| `threaddump`、`heapdump` | 线程与堆诊断 |

`prometheus` 需要 `micrometer-registry-prometheus` 依赖。Boot 3.5 默认只通过 HTTP 暴露 `health`。端点操作权限、网络暴露和请求鉴权分别配置。

## 3. 端点暴露与访问控制 {#端点暴露与访问控制}

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  endpoint:
    health:
      show-details: when_authorized
```

`include` 只控制端点暴露。`show-details` 控制健康详情展示。认证与授权仍由安全过滤链负责。

Boot 3.5 用 `management.endpoint.<id>.access` 限制操作。可选值为 `none`、`read-only`、`unrestricted`。自定义 `SecurityFilterChain` 后，Boot 的管理端点安全配置退让。应用需要显式配置这些端点的访问规则。

生产环境按需开放监控端点。诊断端点放在受控管理网络，并配置认证。`env`、堆转储和线程栈包含内部信息。获取诊断材料前，应确认脱敏和访问权限。

## 4. Liveness 探针 {#liveness-探针}

Liveness 表示应用内部是否处于可恢复状态。平台在连续探测失败后重启实例。数据库、缓存和远程 API 的故障应交给依赖治理。重启本地进程无法恢复这些外部服务。

Boot 的 `LivenessStateHealthIndicator` 读取应用可用性状态。它没有自动检测线程死锁的能力。应用需主动发布状态变化，或增加对应检查。

## 5. Readiness 探针 {#readiness-探针}

Readiness 表示实例当前能否接收流量。失败后，平台停止向该实例转发请求。Boot 的默认 readiness 组只包含 `readinessState`。

外部依赖是否加入该组，要看服务的降级能力。所有请求都依赖数据库时，可加入数据库检查。服务仍能提供缓存读取时，应保留这部分服务能力。共享依赖故障会同时影响全部实例，配置时要评估全量摘流。

探针超时、周期和失败阈值需覆盖正常抖动。启动较慢时，可用平台的 startup probe 保护启动阶段。

## 6. 启动阶段分析 {#启动阶段分析}

为应用设置启动记录器：

```java
SpringApplication app = new SpringApplication(OrderApplication.class);
app.setApplicationStartup(new BufferingApplicationStartup(2048));
app.run(args);
```

再按需暴露 `startup` 端点，即可查看已采集步骤。JFR 场景可改用 `FlightRecorderApplicationStartup`。

诊断时分别观察配置加载、定义处理、Bean 创建和服务器启动。Runner 与自定义预热也要单独计时。步骤只覆盖实际记录的操作，业务耗时需自行补充。

## 7. 诊断端点选择 {#按问题选择端点}

- Bean 缺失时，查看 `conditions` 与 `beans`。
- 配置值异常时，查看 `env` 与 `configprops`。
- 路由缺失时，查看 `mappings`。
- 延迟上升时，结合指标、trace ID 和请求日志。
- 线程阻塞时，连续获取线程转储并比较调用栈。
- 内存持续增长时，先观察 GC，再按需获取堆转储。

堆转储会增加诊断开销，应在资源允许时执行。

## 8. 业务端口探针 {#业务端口探针}

独立管理端口拥有独立的连接与处理路径。管理端口响应成功时，业务端口仍可处于阻塞状态。

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true
        add-additional-paths: true
```

Boot 3.5 使用上述配置在主端口增加 `/livez` 与 `/readyz`。健康组原路径仍是 `/actuator/health/liveness` 和 `/actuator/health/readiness`。平台探测主端口，才能覆盖业务端口的接入路径。

健康状态为 `DOWN` 或 `OUT_OF_SERVICE` 时，默认返回 HTTP 503。自定义状态映射时，应保留这两个失败映射。

## 9. 常见问题 {#常见问题}

### 9.1 健康状态与业务指标 {#健康状态与业务指标}

`UP` 表示已注册检查通过。查询权限、数据延迟和业务规则仍需业务指标验证。可用低频合成请求覆盖关键业务路径。

### 9.2 健康检查的查询成本 {#健康检查的查询成本}

健康检查可执行有超时的轻量连通性查询。复杂校验放在低频合成监控中。探针应避免竞争业务关键锁。
