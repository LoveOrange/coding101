# Spring AOP

Spring AOP 在 Bean 外部放置代理，对匹配的方法调用执行一组拦截器。切点决定哪些调用需要增强，拦截链决定事务、鉴权、监控等逻辑以什么顺序包围目标方法。

## 1. Spring AOP 的连接点是方法执行

```java
@Aspect
@Component
class TimingAspect {
    @Around("@annotation(Measured)")
    Object measure(ProceedingJoinPoint point) throws Throwable {
        long start = System.nanoTime();
        try {
            return point.proceed();
        } finally {
            record(point.getSignature(), System.nanoTime() - start);
        }
    }
}
```

代理收到方法调用后，先判断 Advisor 的 Pointcut 是否匹配，再执行对应 Advice。Spring AOP 主要处理 Spring Bean 的方法执行；字段访问、构造器等更广泛连接点属于 AspectJ 编译或加载期织入的范围。

## 2. 常用概念对应不同职责

| 概念 | 职责 |
| --- | --- |
| Aspect | 一组相关横切规则 |
| Pointcut | 匹配目标方法 |
| Advice | 在匹配位置执行的逻辑 |
| Advisor | 将 Pointcut 与 Advice 组合 |
| Proxy | 接收外部调用 |
| MethodInterceptor | 拦截链中的统一调用节点 |

业务代码最需要判断的是：调用是否经过代理、切点是否匹配、链中有哪些拦截器。

## 3. 拦截链以嵌套调用执行

每个拦截器收到当前 invocation，执行自己的前置逻辑，再调用 `proceed()` 进入下一个节点；返回时执行后置逻辑：

```text
监控 before
  → 事务 before
    → 目标方法
  ← 事务 commit / rollback
← 监控 record
```

环绕通知如果不调用 `proceed()`，目标和后续拦截器都不会执行；调用多次则可能重复执行业务。拦截器必须清楚自己是否允许短路或重试。

## 4. 顺序会改变语义

事务与重试的相对顺序决定每次重试是否拥有独立事务；缓存位于事务外时，提交前后可见性也要确认。可以使用 `@Order` 或 `Ordered` 明确优先级，但数值含义应由测试验证，不能只凭注解位置猜测。

对于关键组合，写集成测试记录实际顺序、事务状态和异常结果。多个自动代理功能会共同参与一个代理创建过程，不应假定每个注解都套一层独立对象。

## 5. 切点应稳定且范围可控

基于包名的宽泛切点容易把框架配置、健康检查或内部任务一并拦截。业务语义明确时，使用专用注解或稳定接口，并在启动或测试阶段验证匹配集合。

高频方法上的参数序列化、远程审计等 Advice 会显著增加延迟。横切逻辑也属于生产代码，需要超时、异常和敏感数据策略。

## 6. 代理边界 {#proxy-boundaries}

`@Transactional`、`@Cacheable` 和 `@Async` 通常依赖 Spring 代理。注解没有产生预期行为时，应检查对象是否由容器管理、调用是否经过代理、方法能否被代理，以及异常和线程边界是否符合协议。

### 6.1 同类自调用绕过代理

```java
public void createOrder() {
    this.saveOrder();
}

@Transactional
public void saveOrder() {}
```

外部调用 `createOrder` 进入代理后，目标对象内部的 `this.saveOrder()` 直接调用自身。事务、缓存和异步拦截器都没有第二次进入机会。

优先把 `saveOrder` 的边界移动到另一个 Bean，或让外部入口方法本身承担完整语义。自注入或 `AopContext.currentProxy()` 会把结构问题变成运行时约束。

### 6.2 方法与类必须可被代理

- 对象必须由当前 Spring 容器创建或处理。
- JDK 代理只能从代理接口暴露调用。
- CGLIB 不能覆盖 final、private 方法。
- 方法上的注解要能被事务或缓存属性解析器找到。

当前 Spring 版本对受支持的方法可见性已有演进，不应只背“必须 public”。最稳妥的业务入口仍是可覆盖的公开方法，并用所部署版本的集成测试确认。

### 6.3 异常必须到达事务拦截器

```java
@Transactional
public void importData() {
    try {
        repository.saveAll(rows);
    } catch (DataAccessException exception) {
        log.warn("ignored", exception);
    }
}
```

方法正常返回时，代理会尝试提交。默认回滚规则也只自动匹配 RuntimeException 与 Error。不要通过吞异常伪造成功；需要转换异常时保留 cause 并让回滚规则匹配。

### 6.4 新线程没有原事务上下文

`@Async` 让方法在另一个执行器线程运行。调用线程的 JDBC 事务通常不会跟过去，异步方法若自己声明事务，会创建属于异步线程的新边界。

调用方已经返回后，异步失败也不能通过原调用栈传播。需要 Future、CompletableFuture、事件结果、重试和监控来承接。

### 6.5 缓存还受 key 与提交时机影响

`@Cacheable` 只在 key、condition 等规则匹配时读取或写入缓存。可变参数、不稳定 `toString()` 或租户字段遗漏会造成错误命中。

数据库事务尚未提交时就更新缓存，之后本地回滚会留下不存在的数据。可以在事务提交后失效或更新缓存，并明确失败重试；缓存注解的顺序需要从实际拦截链验证。

同类调用、非容器对象等代理边界同样会让缓存注解失效。

### 6.6 多事务管理器需要明确选择

应用含多个 DataSource 或事务技术时，默认 `TransactionManager` 可能不是目标资源。通过限定名称、类型或事务管理配置明确选择，并测试一条方法究竟绑定了哪些连接。

本地事务无法原子覆盖两个独立数据库，除非使用相应全局事务能力；多个 `@Transactional` 注解不会自动合并资源。

### 6.7 排查顺序

1. 用 `AopUtils` 确认注入对象是否为代理、是哪种代理。
2. 从调用入口确认是否经过代理，检查自调用。
3. 检查方法可见性、final、注解位置和切点匹配。
4. 打开事务、缓存或异步框架的诊断日志。
5. 记录线程名、事务状态、缓存 key 和实际 SQL。
6. 用集成测试复现成功、异常和并发路径。

## 7. 常见问题

### 7.1 `@After` 和 `@AfterReturning` 有什么区别

`@After` 类似 `finally`，正常与异常退出都会执行；`@AfterReturning` 只在正常返回后执行。异常路径使用 `@AfterThrowing`，完整控制优先用 `@Around`。

### 7.2 AOP 能拦截普通 `new` 出来的对象吗

默认不能。Spring AOP 代理由容器创建并交付，绕过容器得到的普通对象不会自动经过该代理。

**考察重点**

**相关内容**：[Spring AOP 的连接点是方法执行](#1-spring-aop-的连接点是方法执行)至[顺序会改变语义](#4-顺序会改变语义)。

<details>
<summary>参考回答</summary>

容器为匹配 Advisor 的 Bean 创建代理。外部方法调用进入代理后，代理按 Pointcut 选择 MethodInterceptor，并组成调用链；每个拦截器执行前置逻辑，调用 `proceed` 进入下一项，最后到目标方法，再逐层返回执行提交、记录等后置逻辑。

环绕通知可以短路或重复调用，所以必须控制 `proceed`。多个切面的顺序会改变事务与重试等实际边界，应显式排序并用集成测试验证。

</details>

**考察重点**

- 容器对象、代理入口和自调用。
- 方法可代理性与异常传播。
- 异步线程和事务管理器边界。

**相关内容**：[代理边界](#proxy-boundaries)。

<details>
<summary>参考回答</summary>

先看调用是否经过 Spring 管理的代理。同类 `this` 调用、手工 new 的对象、JDK 代理接口未暴露的方法，以及 CGLIB 无法覆盖的 final、private 方法，都可能绕过拦截。异常被方法内部吞掉或不匹配回滚规则时，代理也会按正常返回提交。

`@Async` 切到新线程后不会继承普通 JDBC 事务，多数据源还可能选错 TransactionManager。排查时确认代理类型和入口，记录线程、事务状态与 SQL，再用异常路径集成测试证明边界。
