# Spring AOP

**AOP**（面向切面编程）是把多个业务方法共有的逻辑集中到一处的方式。Spring AOP 通过代理实现它：调用先经过代理，由代理执行事务、鉴权或监控逻辑，再进入业务方法。

理解 AOP，关键是能沿一次调用说明增强在哪里执行。同一个方法加了事务和重试，谁在外层会改变事务范围；方法上写了注解，调用没有经过代理，增强也可能不生效。

## 1. 面试核心 {#core}

- Pointcut 决定**哪些方法需要增强**，Advice 决定**执行什么增强逻辑**，Advisor 把两者组合起来。
- 拦截器通过 `proceed()` 进入下一节点，结果或异常再**按嵌套顺序逐层返回**。[卡](#interceptor-chain)
- `@Order` 数值越小，切面**进入越早、退出越晚**；这个顺序会改变事务与重试的作用范围。[卡](#advice-order)
- 代理模式下，目标对象的 **`this` 自调用绕过增强**；即使沿用已有事务，内部方法的事务规则也不会重新生效。[卡](#transactional-pitfalls)
- `@After` 在**正常或异常退出时都执行**，`@AfterReturning` 只在正常返回时执行。

## 2. 常用概念 {#常用概念}

Spring AOP 把“选哪些方法”和“执行什么逻辑”分开描述。**切点**（Pointcut）是匹配方法的规则，**通知**（Advice）是匹配后执行的增强逻辑，**切面**（Aspect）则把相关规则与通知组织在一起。各个对象的分工如下：

| 概念 | 职责 |
| --- | --- |
| Aspect | 组织跨多个方法的共有逻辑 |
| Pointcut | 匹配目标方法 |
| Advice | 执行增强逻辑 |
| Advisor | 组合 Pointcut 与 Advice |
| Proxy | 接收外部方法调用 |
| MethodInterceptor | 执行拦截链节点 |

代理按 Advisor 选择匹配当前方法的增强，再把它们组成拦截链。带运行时参数条件的切点，还会在调用时检查实际参数。判断增强是否生效，可以沿着这条路径检查：

- 调用是否经过代理入口。
- 切点是否匹配当前方法和参数。
- 拦截链是否包含预期的增强。

## 3. 连接点与方法执行 {#连接点与方法执行}

**连接点**（join point）是可以插入增强逻辑的位置。Spring AOP 支持的是 Bean 的方法执行。下面的计时切面用切点选中 `OrderService` 的方法，再用环绕通知记录耗时：

```java
@Aspect
@Component
class TimingAspect {
    @Around("execution(* com.example.order.OrderService.*(..))")
    Object measure(ProceedingJoinPoint point) throws Throwable {
        long start = System.nanoTime();
        try {
            return point.proceed();
        } finally {
            System.out.println(System.nanoTime() - start);
        }
    }
}
```

`@Aspect` 声明切面，`@Around` 声明环绕通知，其中的 `execution` 表达式是匹配方法的切点。启用 AOP 后，外部调用先进入代理，再执行 `measure`。

`measure` 先记录开始时间，再调用 `point.proceed()` 继续执行后续调用，最后在 `finally` 中输出耗时。业务正常返回或抛出异常，都会经过 `finally`，所以两种结果都能记录时间。

字段访问和构造器连接点属于 AspectJ 织入的范围。织入是把增强逻辑加入字节码的过程，可以发生在编译或类加载阶段。

## 4. 拦截链 {#拦截链}

**拦截链**是按顺序组织的一组方法拦截器，多个增强通过它形成嵌套调用。每个拦截器收到当前调用的信息，执行前置逻辑后，通过 `proceed()` 进入下一节点。走到链末尾才调用目标方法，结果或异常随后逐层返回。

例如，监控包住事务，事务再包住业务方法，就会形成下面的顺序。事务提交或回滚完成后，外层监控才记录结果：

```text
监控 before
  → 事务 before
    → 目标方法
  ← 事务 commit / rollback
← 监控 record
```

**短路**是提前结束调用、跳过后续拦截器和目标方法的做法。环绕通知可以不调用 `proceed()`，直接返回缓存结果。反过来，环绕通知多次调用 `proceed()`，就会重复执行后续链和业务方法。因此，重试通知既要限制次数，也要确认重复执行不会造成重复扣款等副作用。

## 5. 拦截器顺序 {#拦截器顺序}

拦截器顺序决定哪个增强包住哪个增强，进而改变事务、重试和缓存的行为。不同切面用 `@Order` 或 `Ordered` 声明顺序。数值越小，优先级越高。高优先级切面进入较早，返回时较晚退出。

以重试和事务为例，先假设没有调用方传入的事务，事务传播方式是 `REQUIRED`，即有事务就加入、没有就新建：

- 重试在外层：每次尝试都会重新进入事务拦截器，因此每次都会创建新事务。
- 事务在外层：先建立事务，再进入重试逻辑，多次尝试共享这一个事务。

如果共享事务已被数据库或内层事务标记为 rollback-only，意味着它只能回滚，后续重试即使成功也无法正常提交。选择顺序前，必须先确定每次重试是否需要独立的事务。

事务 Advisor 的顺序可通过 `@EnableTransactionManagement(order=...)` 设置，切面上的 `@Order` 则控制该切面的通知顺序。两个不同切面优先级相同时，不要依赖它们偶然表现出的先后顺序。

关键组合要用集成测试记录实际顺序、事务状态和异常结果。缓存与事务的顺序还会影响提交前后的数据可见性，见[缓存 key 与提交时机](#缓存-key-与提交时机)。多个自动代理功能可以参与同一代理的创建，注解数量与代理层数并非一一对应。

## 6. 切点范围 {#切点范围}

切点决定增强应用到哪些方法。表达式看起来相近时，先确认它检查的是声明类型、代理类型还是实际参数。

| 表达式 | 匹配依据 |
| --- | --- |
| `execution(* com.example.service..*(..))` | 方法签名与包范围 |
| `within(com.example.service..*)` | 声明方法的类型范围 |
| `@annotation(com.example.Measured)` | 方法注解 |
| `args(java.io.Serializable)` | 实际参数的运行时类型 |
| `this(com.example.Service)` | 代理对象类型 |
| `target(com.example.Service)` | 目标对象类型 |

`execution` 看声明签名，`args` 看运行时实参。JDK 代理与目标类的类型不同，`this` 与 `target` 因此会有差异。

宽泛的包名切点容易同时拦截框架配置、健康检查和内部任务。业务范围明确时，可以用专用注解或稳定接口表达，再在启动或测试阶段核对实际匹配的方法。

高频 Advice 中的参数序列化和远程审计会增加请求耗时。增强逻辑也需要设置超时、处理异常，并对敏感参数脱敏。否则，共有的监控或审计逻辑会影响每一次业务调用。

## 7. 代理边界 {#代理边界}

在 Spring 的代理模式下，`@Transactional`、`@Cacheable` 和 `@Async` 都要求调用经过对应代理。只在方法上写注解还不够：对象要经过代理处理，调用方也要拿着代理引用发起调用。

### 7.1 同类自调用 {#同类自调用}

**同类自调用**是目标对象用 `this` 调用自己的另一个方法。即使外部调用先经过了代理，进入目标对象后，`this` 指向的仍是目标对象，内部调用不会再次绕到代理上。

```java
public void createOrder() {
    this.saveOrder();
}

@Transactional
public void saveOrder() {}
```

`this.saveOrder()` 在目标对象内部执行，绕过事务拦截器。若入口已有事务，内部方法仍在该事务内执行。只是内部注解声明的传播或回滚规则没有重新生效。

如果 `saveOrder` 需要独立的事务规则，可以把它移到另一个 Bean，通过那个 Bean 的代理调用。如果整个 `createOrder` 才是一次完整的事务，就把事务放在这个外部入口上。自注入或 `AopContext.currentProxy()` 也能取得代理，但会增加对象对代理机制的依赖，后者还要求暴露当前代理。缓存和异步注解同样受自调用影响。

### 7.2 可代理的方法与类 {#可代理的方法与类}

JDK 动态代理通过接口接收调用，CGLIB 则通过子类重写方法，所以两者的可拦截范围不同。尤其是 CGLIB，无法重写 `final`、`private` 方法，也就无法在这些方法上加入代理增强，具体见 [JDK 动态代理与 CGLIB](./jdk-proxy-cglib.mdx#cglib)。

方法能够被拦截之后，还要确认事务或缓存的属性解析器能找到注解。排查时要结合实际部署版本，验证真正被调用的入口。

### 7.3 异常与事务回滚 {#异常与事务回滚}

如果要靠异常触发回滚，异常必须传到事务拦截器，并匹配它的回滚规则，具体见 [Spring 事务](./declarative-transaction-execution.mdx#回滚规则)。例如，方法捕获异常后只打印日志、随后正常返回，拦截器就无法通过这次异常判断是否回滚。转换异常时要保留 `cause`，也就是原始异常，同时确认新异常符合回滚规则。

### 7.4 异步线程与事务上下文 {#异步线程与事务上下文}

异步调用需要同时考虑事务属于哪个线程，以及失败怎样通知调用方。JDBC 事务绑定当前线程，`@Async` 把方法交给执行器的另一个线程后，需要在该线程另建事务。异步方法通过代理进入时，异步与事务 Advisor 的组合决定具体执行边界。

调用方已经返回后，异步失败也无法沿原调用栈传播。返回 `Future` 或 `CompletableFuture` 的方法，可以通过结果对象承接失败。返回 `void` 时，则用 `AsyncUncaughtExceptionHandler` 处理未捕获异常。应用还可通过事件结果、重试和监控跟踪后续处理。

### 7.5 缓存 key 与提交时机 {#缓存-key-与提交时机}

**缓存 key** 是定位缓存项的键，应包含租户和资源 ID 等影响业务结果的参数。不同租户或资源如果误用了同一个 key，就可能读到别人的数据。设计时需要避免：

- 用可变参数作为键，写入后参数变化，使键与原结果失去对应关系。
- 自定义键使用不稳定的 `toString()`，导致同一业务对象在不同调用中得到不同键。
- 遗漏租户字段，让不同租户命中同一缓存项。

`condition` 控制是否应用缓存，`unless` 则可在方法执行后否决缓存写入。数据库提交前就写缓存，后续回滚会让缓存留下尚未生效的数据。可以在提交后失效或更新缓存，也可使用支持事务同步的缓存管理器延后变更。

数据库与远程缓存仍需分别处理失败，并明确缓存更新失败后的重试方式。最终时机要通过实际拦截链验证，因为切面顺序会改变执行位置。

### 7.6 多事务管理器 {#多事务管理器}

多个数据源或事务技术共存时，默认事务管理器未必管理当前访问的资源。可以通过 `@Transactional(transactionManager="ordersTxManager")` 显式指定，并在测试中核对实际绑定的连接。

本地事务只覆盖所属资源，多库原子性需要相应的全局事务支持，见 [Spring 事务](./declarative-transaction-execution.mdx#连接与事务上下文)。

### 7.7 代理诊断 {#排查顺序}

排查增强失效，要沿着实际调用路径检查，确认问题发生在代理入口、匹配规则还是执行过程中：

1. 用 `AopUtils` 确认代理类型。
2. 检查外部入口、自调用和切点匹配。
3. 确认方法可见性、`final` 与注解位置。
4. 开启事务、缓存或异步的诊断日志，记录拦截器顺序、线程名、事务状态和缓存 key。
5. 对照实际 SQL，用集成测试复现成功、异常和并发路径。

## 8. 常见问题 {#常见问题}

### 8.1 `@After` 和 `@AfterReturning` 有什么区别？ {#通知的退出语义}

`@After` 同时覆盖正常与异常退出，而 `@AfterReturning` 只在正常返回时执行。前者类似 `finally`，适合无论成功与否都要执行的清理。若只处理异常退出，可使用 `@AfterThrowing`。需要控制参数、返回结果或是否继续调用时，再使用 `@Around`。

### 8.2 AOP 能拦截手工 `new` 出来的对象吗？ {#手工对象与代理}

普通 `new` 得到的是原始对象，直接调用会绕过 Spring 代理。如果确实需要增强手工对象，可以用 `ProxyFactory` 为它创建代理。之后调用方要使用代理返回的引用，才能进入拦截链。

## 9. 面试题 {#面试题}

### 9.1 Spring AOP 的拦截链怎样执行 {#interceptor-chain}

**考察重点**：解释代理怎样按切点选择拦截器，以及 `proceed()` 怎样形成嵌套调用。说明顺序为何会影响事务、重试和缓存。

**相关内容**：[常用概念](#常用概念)至[拦截器顺序](#拦截器顺序)。

<details>
<summary>参考回答</summary>

**Spring AOP 通过代理选择匹配当前方法的拦截器，再按顺序嵌套执行。**

容器先为需要增强的 Bean 创建代理，外部调用进入代理后，再按 Advisor 的 Pointcut 匹配。

每个拦截器执行前置逻辑后，用 `proceed()` 进入下一项。到达目标方法后，结果或异常逐层返回，各层再执行提交、回滚或记录逻辑。环绕通知也可以直接返回，或多次调用后续链，所以要控制短路与重复执行。

`@Order` 数值较小的切面进入较早、退出较晚。这会改变每次重试的事务范围，也会影响缓存结果的可见时机，应通过集成测试确认。

</details>

### 9.2 `@Transactional` 常见的失效原因有哪些 {#transactional-pitfalls}

**考察重点**：根据代理入口、方法范围和异常传播，判断事务增强是否执行。说明线程切换与事务管理器选择怎样影响资源参与范围。

**相关内容**：[代理边界](#代理边界)。

<details>
<summary>参考回答</summary>

**排查 `@Transactional` 未生效，要检查调用是否经过代理、方法能否被拦截，以及异常、线程和资源是否符合事务约定。**

- **调用要经过代理。** 手工 `new` 和 `this` 自调用绕过增强；自调用仍可沿用外层已有事务。
- **方法要可拦截。** JDK 代理接口需暴露方法，CGLIB 则无法覆盖 `final`、`private` 方法。
- **异常要匹配回滚规则。** 默认处理 `RuntimeException` 与 `Error`；受检异常可用 `rollbackFor` 指定，吞掉异常会影响代理判断。
- **线程和资源要正确参与。** 原线程的 JDBC 事务不会自动进入异步线程，多数据源也需选对 `transactionManager`。

结合代理类型、线程、事务状态与 SQL 记录，再用异常路径测试验证回滚。

</details>

### 9.3 重试切面与事务切面的顺序怎样影响重试？ {#advice-order}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：根据切面的嵌套顺序，判断每次重试是重新开启事务，还是继续使用原事务。

**相关内容**：[拦截器顺序](#拦截器顺序)。

<details>
<summary>参考回答</summary>

**没有调用方事务且使用 `REQUIRED` 时，重试在事务外层会让每次尝试创建新事务；事务在重试外层，则让多次尝试共享同一个事务。**

原因是外层通知决定了内层会被执行几次。重试在外层，每次尝试都重新进入事务拦截器；事务在外层，则只建立一次事务，再执行里面的多次重试。

共享事务若已被标记为 rollback-only，后续重试也无法恢复正常提交。`@Order` 数值较小的切面位于外层，因此要明确排序，并用实际事务状态验证。

</details>
