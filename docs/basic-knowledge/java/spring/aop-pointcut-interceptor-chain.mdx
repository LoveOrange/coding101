# Spring AOP

Spring AOP 通过代理增强 Bean 的方法调用。本文负责切点、通知、拦截链与代理入口。代理类型见 [JDK 动态代理与 CGLIB](./jdk-proxy-cglib.mdx)。事务执行过程见 [Spring 事务](./declarative-transaction-execution.mdx)。

## 1. 面试核心 {#core}

- Pointcut 匹配方法，Advice 定义增强逻辑，Advisor 组合两者。
- `proceed()` 进入下一拦截器，返回时按嵌套顺序退出。[卡](#interceptor-chain)
- `@Order` 数值越小，切面进入越早、退出越晚。[卡](#advice-order)
- 代理模式下，目标对象的 `this` 自调用绕过增强。[卡](#transactional-pitfalls)
- `@After` 覆盖正常和异常退出，`@AfterReturning` 只覆盖正常返回。

## 2. 连接点与方法执行 {#连接点与方法执行}

```java
@Aspect
@Component
class TimingAspect {
    @Around("execution(* com.example.order.OrderService.*(..))")
    Object measure(ProceedingJoinPoint point) throws Throwable {
        long start = System.nanoTime();
        try {
            return point.proceed();
        } finally {
            System.out.println(System.nanoTime() - start);
        }
    }
}
```

示例匹配 `OrderService` 的方法执行，并输出耗时。启用 AOP 后，外部调用进入代理和计时通知。`finally` 同时覆盖成功与异常路径。

Spring AOP 的连接点是方法执行。字段访问和构造器连接点属于 AspectJ 织入的范围。

## 3. 常用概念 {#常用概念}

| 概念 | 职责 |
| --- | --- |
| Aspect | 组织相关横切规则 |
| Pointcut | 匹配目标方法 |
| Advice | 执行增强逻辑 |
| Advisor | 组合 Pointcut 与 Advice |
| Proxy | 接收外部方法调用 |
| MethodInterceptor | 执行拦截链节点 |

代理按 Advisor 构建当前方法的拦截链。带运行时参数条件的切点还会在调用时匹配。

## 4. 拦截链 {#拦截链}

拦截器通过 `proceed()` 进入下一节点。最后一个节点调用目标方法，结果再逐层返回。

```text
监控 before
  → 事务 before
    → 目标方法
  ← 事务 commit / rollback
← 监控 record
```

环绕通知可以省略 `proceed()`，直接返回缓存等结果。调用多次会重复执行后续链和业务方法。重试通知因此需要控制次数与副作用。

## 5. 拦截器顺序 {#拦截器顺序}

不同切面用 `@Order` 或 `Ordered` 声明顺序。数值越小，优先级越高。高优先级切面进入较早，返回时较晚退出。

重试在事务外层时，每次尝试都重新进入事务拦截器。在无外层事务且传播为 `REQUIRED` 时，每次尝试创建新事务。重试位于事务内层时，多次尝试共享该事务。若数据库或内层事务已标记 rollback-only，后续尝试仍受影响。

事务 advisor 可通过 `@EnableTransactionManagement(order=...)` 排序。切面上的 `@Order` 用于该切面的 advice。相同优先级的不同切面应避免依赖偶然顺序。

## 6. 切点范围 {#切点范围}

| 表达式 | 匹配依据 |
| --- | --- |
| `execution(* com.example.service..*(..))` | 方法签名与包范围 |
| `within(com.example.service..*)` | 声明方法的类型范围 |
| `@annotation(com.example.Measured)` | 方法注解 |
| `args(java.io.Serializable)` | 实际参数的运行时类型 |
| `this(com.example.Service)` | 代理对象类型 |
| `target(com.example.Service)` | 目标对象类型 |

`execution` 看声明签名，`args` 看运行时实参。JDK 代理与目标类的类型不同，`this` 与 `target` 因此会有差异。

切点应覆盖明确的业务范围。高频 Advice 中的序列化和远程调用会增加请求耗时。

## 7. 代理边界 {#代理边界}

以下按 Spring 的代理模式讨论。对象需交给代理基础设施处理，调用也需从代理入口进入。

### 7.1 同类自调用 {#同类自调用}

```java
public void createOrder() {
    this.saveOrder();
}

@Transactional
public void saveOrder() {}
```

`this.saveOrder()` 在目标对象内部执行，绕过事务拦截器。若入口已有事务，内部方法仍在该事务内执行。只是内部注解声明的传播或回滚规则没有重新生效。

可将 `saveOrder` 移至另一个 Bean，显式通过其代理调用。

### 7.2 可代理的方法与类 {#可代理的方法与类}

可拦截范围由接口与继承规则决定，见 [JDK 动态代理与 CGLIB](./jdk-proxy-cglib.mdx#cglib)。

### 7.3 异常与事务回滚 {#异常与事务回滚}

异常需到达事务拦截器并匹配回滚规则，见 [Spring 事务](./declarative-transaction-execution.mdx#回滚规则)。

### 7.4 异步线程与事务上下文 {#异步线程与事务上下文}

JDBC 事务绑定当前线程，切换到 `@Async` 执行线程后需另建事务。异步方法通过代理进入时，异步与事务 advisor 的组合决定执行边界。

返回 `Future` 的方法通过结果承接失败。返回 `void` 的异步方法用 `AsyncUncaughtExceptionHandler` 处理未捕获异常。

### 7.5 缓存 key 与提交时机 {#缓存-key-与提交时机}

缓存 key 应包含区分业务结果的参数，如租户和资源 ID。`condition` 控制是否应用缓存，`unless` 可在执行后否决缓存写入。

提交前写缓存会让后续数据库回滚留下旧结果。可使用支持事务同步的缓存管理器，将缓存变更延后到提交后。数据库与远程缓存仍需各自处理失败。

### 7.6 多事务管理器 {#多事务管理器}

通过 `@Transactional(transactionManager="ordersTxManager")` 指定管理器。资源参与范围见 [Spring 事务](./declarative-transaction-execution.mdx#连接与事务上下文)。

### 7.7 代理诊断 {#排查顺序}

1. 用 `AopUtils` 确认代理类型。
2. 检查外部入口、自调用和切点匹配。
3. 确认方法可见性、`final` 与注解位置。
4. 记录拦截器顺序、线程和事务状态。
5. 对照实际 SQL，并复现异常路径。

## 8. 常见问题 {#常见问题}

### 8.1 通知的退出语义 {#通知的退出语义}

`@After` 在正常与异常退出时执行，类似 `finally`。`@AfterReturning` 只在正常返回时执行。`@AfterThrowing` 匹配异常退出。`@Around` 可控制参数、结果和后续调用。

### 8.2 手工对象与代理 {#手工对象与代理}

普通 `new` 得到原始对象，直接调用它会绕过 Spring 代理。程序化使用 `ProxyFactory` 也能为手工对象创建代理。调用方需使用代理返回的引用。

<details>
<summary>参考回答</summary>

常见原因是代理入口、方法范围或回滚条件不符。先确认对象是否为代理，再检查自调用和方法可见性。自调用绕过内部注解，但仍可沿用外层事务。

再确认异常是否传出、是否匹配 `rollbackFor`。最后检查线程切换和 `transactionManager` 的选择。通过实际 SQL 与异常测试确认资源是否回滚。

</details>
