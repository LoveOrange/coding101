# Spring 拦截机制

Filter、Interceptor 和 AOP 分别拦截 Servlet、MVC 与 Bean 调用。本文负责层级选择、回调顺序与线程清理。MVC 分派见 [DispatcherServlet](./dispatcherservlet-handler-mapping.mdx)。AOP 链见 [Spring AOP](./aop-pointcut-interceptor-chain.mdx)。

## 1. 面试核心 {#core}

- Filter 按 URL 与 dispatcher type 注册，可包装请求和响应。[卡](#filter-interceptor-aop)
- `HandlerInterceptor` 在处理器映射后执行，可读取 `HandlerMethod`。
- 同步请求中，`preHandle` 正序执行，后置回调逆序执行。[卡](#interceptor-callback-order)
- `preHandle=false` 时，仅此前返回 true 的拦截器收到完成回调。
- `OncePerRequestFilter` 默认跳过后续 ASYNC 与 ERROR 派发。

## 2. Filter {#filter}

Filter 属于 Servlet 过滤链，可覆盖多个 Servlet。URL 与 dispatcher type 决定实际匹配范围。

编码、CORS、安全入口与请求包装适合放在这一层。调用 `chain.doFilter()` 后，请求才进入后续过滤器或 Servlet。提前返回可直接拒绝请求。

Filter 进入时尚未执行 MVC 的处理器映射。Controller 注解应在映射完成后读取。

## 3. HandlerInterceptor {#handlerinterceptor}

Interceptor 在 HandlerMapping 找到处理器后执行。

```java
if (handler instanceof HandlerMethod method) {
    RequiredTenant annotation =
            method.getMethodAnnotation(RequiredTenant.class);
}
```

示例先确认注解方法类型，再读取方法注解。静态资源等 handler 使用其他类型。

Interceptor 适合添加路由标签、区域设置和轻量审计。通用 Web 认证授权优先使用 Spring Security 过滤链。方法级授权可使用 Method Security。

## 4. AOP {#aop}

AOP 覆盖经过代理的 Bean 方法调用，具体机制见 [Spring AOP](./aop-pointcut-interceptor-chain.mdx)。

## 5. 分层协作 {#分层协作}

请求追踪可按信息来源分工：

- Filter 读取或生成请求 ID，并在继续执行前写响应头。
- Interceptor 添加路径模板和 handler 标签。
- 方法监控记录 service 调用耗时。
- 当前线程退出时，在 `finally` 中清理 MDC 等上下文。

响应头需在提交前写入。过滤链返回后的 `finally` 适合清理，此时需确认响应是否已提交。

## 6. 异常处理范围 {#异常处理范围}

MVC 的异常由 resolver 链处理，响应契约见 [API 错误契约](./api-error-contract.mdx#controlleradvice-的处理范围)。

Filter 自身抛错需由过滤链或 Servlet 错误机制处理。AOP 只能捕获其调用链内的异常。返回值序列化发生在 Controller 方法返回后，超出该方法切面的范围。

## 7. 异步与 ThreadLocal {#异步与-threadlocal}

Servlet 异步处理会释放初始线程，再通过 ASYNC 派发继续执行。ThreadLocal 按线程保存，后续线程需重新建立上下文。

`OncePerRequestFilter` 默认跳过 ASYNC 与 ERROR 派发。参与 ASYNC 需让 `shouldNotFilterAsyncDispatch()` 返回 false。参与 ERROR 需让 `shouldNotFilterErrorDispatch()` 返回 false。还需在注册时包含相应 dispatcher type，并启用异步支持。

允许 ASYNC 后，后续派发可再次执行过滤逻辑。每次执行都需清理当前线程的数据。请求全局完成另用异步完成回调观察。

## 8. 拦截器回调顺序 {#拦截器回调顺序}

同步正常路径中，A、B 按注册顺序执行：

```text
A.preHandle → B.preHandle → handler
→ B.postHandle → A.postHandle
→ 视图渲染 → B.afterCompletion → A.afterCompletion
```

`@ResponseBody` 的正文在 adapter 内写出，早于 `postHandle`。因此，修改响应体应使用 `ResponseBodyAdvice` 等返回值扩展点。

若 B 的 `preHandle` 返回 false，handler 与 `postHandle` 都跳过。只有 A 收到 `afterCompletion`。B 在拒绝路径中需自行释放刚取得的资源。

handler 抛错时，`postHandle` 跳过，异常交给 resolver。已成功进入的拦截器仍收到 `afterCompletion`。异常已被 resolver 处理时，完成回调中的异常参数可为 null。

开启 MVC 异步时，初始线程改调 `afterConcurrentHandlingStarted`。随后派发的回调过程见 [Spring MVC 请求生命周期](./http-request-to-controller.mdx#异步请求)。

## 9. 常见问题 {#常见问题}

### 9.1 入口认证与方法授权 {#入口认证与方法授权}

入口认证由安全过滤链处理。业务方法授权由 Method Security 等机制承担。Interceptor 可补充路由元数据校验。

### 9.2 Filter 与处理器注解 {#filter-与处理器注解}

Filter 进入时尚未完成 MVC 映射。需要读取处理器注解时，在 Interceptor 中检查 `HandlerMethod`。

<details>
<summary>参考回答</summary>

Filter 拦截 Servlet 请求，Interceptor 拦截 MVC 处理器。AOP 则围绕 Bean 的代理方法调用。

请求包装和通用 Web 安全适合 Filter。路由与 Controller 元数据适合 Interceptor。事务和方法监控适合 AOP。异步路径需按每次派发清理线程上下文。

</details>
