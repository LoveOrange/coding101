# Spring 循环依赖

循环依赖是 Bean 依赖图中的环。本文负责早期引用、三级缓存与作用域限制。Spring Boot 2.6 起默认禁止循环引用。注入候选选择见 [依赖注入](./dependency-injection-selection.mdx)。

## 1. 面试核心 {#core}

- 直接构造器循环在实例化前阻塞，早期引用无法解除它。
- 允许循环引用时，部分 singleton 属性循环可用早期引用完成。[卡](#three-level-cache)
- 三级缓存分别保存完整单例、早期引用和引用工厂。
- Boot 2.6 起 `spring.main.allow-circular-references` 默认为 `false`。
- singleton 直接注入 prototype 时，只解析一次该依赖。[卡](#prototype-in-singleton)

## 2. 构造器注入的循环 {#构造器注入的循环}

```java
@Service
class OrderService {
    OrderService(PaymentService paymentService) {}
}

@Service
class PaymentService {
    PaymentService(OrderService orderService) {}
}
```

创建 `OrderService` 前需先得到 `PaymentService`。后者又需先得到前者，双方都缺少可用实例。容器最终报告创建中的循环依赖。

注入点 `@Lazy` 可先注入延迟代理。`ObjectProvider` 可把查询推迟到实际使用时。若构造或初始化阶段立即获取目标，循环仍会出现。

## 3. 属性注入的循环 {#属性注入的循环}

以下假设 A、B 都是 singleton，且允许循环引用。

```text
实例化 A
  → 登记 A 的早期引用工厂
  → 为 A 注入 B，开始创建 B
  → 为 B 注入 A，取得 A 的早期引用
  → 完成 B 初始化
  → 将 B 注入 A
  → 完成 A 初始化
```

构造和属性填充分开，才有机会提前交付 A。B 获取 A 时，A 的属性与初始化尚未完成。B 在此阶段调用 A，仍会访问不完整状态。

## 4. 三级缓存 {#三级缓存}

Spring Framework 6.2.12 的单例注册表使用三个结构：

| 结构 | 内容 |
| --- | --- |
| `singletonObjects` | 完成创建的单例 |
| `earlySingletonObjects` | 已生成的早期引用 |
| `singletonFactories` | 按需生成早期引用的工厂 |

查询先检查完整单例，再检查早期引用。需要早期引用时，工厂调用 `getEarlyBeanReference()` 扩展点。结果进入早期引用缓存，工厂项随后移除。

自动代理创建器可在该扩展点返回代理。最终发布阶段复用这份早期代理，以保持引用一致。Bean 创建完成后进入完整单例缓存，并清理早期项。

工厂层将早期代理创建推迟到确有依赖请求时。简单属性循环可通过提前交付原始实例完成。涉及代理时，还需协调早期引用和最终包装结果。

## 5. Spring Boot 的默认行为 {#spring-boot-的默认行为}

Boot 2.6 起默认 `spring.main.allow-circular-references=false`。设置为 true 只允许容器尝试处理循环。

以下情况仍需分别处理：

- 直接构造器循环缺少可提前暴露的实例。
- prototype 循环没有单例早期缓存协议。
- 跨作用域依赖需满足目标作用域的上下文要求。
- 后处理器若产生不同代理，早期引用与最终引用会冲突。

优先拆分职责，可减少初始化阶段对半成品对象的依赖。

## 6. 作用域 {#作用域}

Spring singleton 按容器和 Bean 定义共享实例。prototype 在每次容器获取时创建实例。request 与 session 分别绑定 Web 请求和会话。

singleton 构造时直接注入 prototype，只获取当时那一份。后续方法调用继续使用相同引用。

```java
class ReportService {
    private final ObjectProvider<ReportBuilder> builders;

    ReportService(ObjectProvider<ReportBuilder> builders) {
        this.builders = builders;
    }

    Report create() {
        return builders.getObject().build();
    }
}
```

`ReportBuilder` 为 prototype 时，每次 `getObject()` 获取新实例。它的资源清理由使用方负责。

request Bean 可通过作用域代理注入 singleton。代理在有效请求上下文中取得目标。离开该上下文后应显式传递请求数据。

## 7. 循环依赖的职责拆分 {#拆解循环依赖}

上层编排服务可单向调用原来的两个服务。共同逻辑可提取为第三个组件。结果通知可使用事件或回调接口。

Provider 适合实际需要延迟获取的资源。用它隐藏直接依赖，只会把初始化错误推迟到使用阶段。

## 8. 常见问题 {#常见问题}

### 8.1 循环依赖的支持范围 {#循环依赖的支持范围}

允许循环引用时，容器可处理部分 singleton 属性循环。直接构造器循环和 prototype 循环会失败。

### 8.2 早期代理的一致性 {#早期代理的一致性}

若 B 持有原始 A，而容器发布代理 A，调用语义就会不同。早期引用工厂给自动代理创建器协调引用的机会。自定义后处理器仍需遵守该协议。

### 9.1 Spring 的三级缓存怎样处理循环依赖，有哪些限制 {#three-level-cache}

<details>
<summary>参考回答</summary>

三级缓存通过提前交付实例引用完成部分属性循环。A 实例化后登记引用工厂，B 注入 A 时按需获取早期引用。B 完成后再填回 A，最后发布完整单例。

工厂可生成早期代理，最终发布时复用该引用。此路径要求允许循环引用，且对象适用单例协议。直接构造器循环和 prototype 循环仍会失败。

</details>

### 9.2 singleton 注入 prototype 后，每次调用都会创建新对象吗？ {#prototype-in-singleton}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

<details>
<summary>参考回答</summary>

直接注入只在 singleton 创建时解析一次。每次需要新对象时，可调用 `ObjectProvider.getObject()`。目标为 prototype 时，每次容器获取才创建新实例。使用者负责产品实例的资源清理。
