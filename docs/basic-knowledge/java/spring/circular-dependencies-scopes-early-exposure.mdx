# Spring 循环依赖

**循环依赖**是 Bean 之间的依赖形成了环，比如 A 依赖 B，B 又依赖 A。容器创建 A 要先拿到 B，创建 B 又要先拿到 A，创建过程就可能无法继续。Spring 能通过提前交出尚未初始化完成的对象引用，处理其中一部分单例循环。理解这个机制，才能解释构造器循环为什么失败、三级缓存各保存什么，以及代理参与时怎样保证引用一致。

还要先记住一个前提：Spring Boot 2.6 起默认禁止循环引用，遇到依赖环直接启动失败。下文讲的处理过程，都假设已经显式允许了循环引用。

## 1. 面试核心 {#core}

- 直接的构造器循环里，双方都要先拿到对方的实例才能创建自己，**容器没有可以提前交出的对象**，所以必然失败。
- 允许循环引用时，容器可以**提前交出尚未初始化完成的引用**，以此处理部分 singleton 的属性注入循环。[卡](#three-level-cache)
- 三级缓存分别保存**完整单例、已生成的早期引用和早期引用工厂**；工厂可以按需生成早期代理。
- Boot 2.6 起 `spring.main.allow-circular-references` **默认为 `false`**。
- singleton 直接注入 prototype 时，这个依赖**只解析一次**，之后一直用同一个实例。[卡](#prototype-in-singleton)

## 2. 构造器注入的循环 {#构造器注入的循环}

构造器注入要求依赖先准备好，容器才能调用构造器创建当前对象。下面两个服务都要求对方先存在，就形成了直接的构造器循环：

```java
@Service
class OrderService {
    OrderService(PaymentService paymentService) {}
}

@Service
class PaymentService {
    PaymentService(OrderService orderService) {}
}
```

要创建 `OrderService`，先得有 `PaymentService`；要创建 `PaymentService`，又得先有 `OrderService`。两边都还没有实例，容器没有任何东西可以先交出去，只能报 `BeanCurrentlyInCreationException`，意思是遇到了一个正在创建中的依赖。

在注入点加 `@Lazy`，可以先注入一个延迟代理，等真正调用时再去取目标；`ObjectProvider` 则让代码自己决定什么时候向容器获取依赖。这两种做法都只是把获取往后推。如果在构造或初始化阶段就立即访问目标，仍可能触发同一个循环。两个服务在职责上互相依赖的问题，仍然需要另外拆开。

## 3. 属性注入的循环 {#属性注入的循环}

属性注入允许容器先创建对象，再填充字段或调用 Setter。**早期引用**就是对象已经实例化、但尚未完成初始化时，容器提前交给依赖方的引用。下面假设 A、B 都是 singleton（容器里共享的单个实例），并且已经允许循环引用：

```text
实例化 A
  → 登记 A 的早期引用工厂
  → 为 A 注入 B，开始创建 B
  → 为 B 注入 A，取得 A 的早期引用
  → 完成 B 初始化
  → 将 B 注入 A
  → 完成 A 初始化
```

B 拿到 A 的早期引用后，就能完成自己的注入和初始化。随后，容器把完整的 B 注入 A，再完成 A 的初始化。这样双方不必都等待对方完全创建好。

代价是 B 有一段时间持有一个还不能用的 A。如果 B 在自己的初始化方法里调用 A，就会碰到 A 还没填充的属性。所以这条路径更适合当作兼容机制，业务设计上仍然应该优先把依赖环拆开。

## 4. 三级缓存 {#三级缓存}

要实现上面的流程，容器得把「已经创建完的单例」和「供循环依赖提前使用的引用」分开存放。Spring Framework 6.2.12 的单例注册表用三个结构保存它们，这就是**三级缓存**：

| 结构 | 内容 |
| --- | --- |
| `singletonObjects` | 完成创建的单例 |
| `earlySingletonObjects` | 已生成的早期引用 |
| `singletonFactories` | 按需生成早期引用的工厂 |

获取一个单例时，容器先查 `singletonObjects`。没有找到，而且这个对象正在创建中，才继续查 `earlySingletonObjects`。如果仍没有早期引用，并且当前查找允许生成早期引用，容器就尝试从 `singletonFactories` 取出工厂来生成。

这个工厂是一个 `ObjectFactory`。它生成引用时会调用 `getEarlyBeanReference()` 扩展点，让后处理器有机会参与。生成的结果放进 `earlySingletonObjects`，对应的工厂从 `singletonFactories` 移除，之后再有依赖方来取就直接拿这份。

工厂这一层让容器可以按需生成早期代理。自动代理创建器能在 `getEarlyBeanReference()` 中返回 A 的代理，等 A 初始化完成后，容器复用这份代理作为最终结果。B 手里的引用和后续调用方拿到的引用因此一致。

如果没有依赖方提前请求 A，工厂就不必执行，代理仍可在初始化后生成。Bean 创建完成后，最终引用进入 `singletonObjects`，早期缓存项随之清理。

这些缓存字段是框架的实现细节，业务代码只通过容器获取 Bean。

## 5. Spring Boot 的默认行为 {#spring-boot-的默认行为}

底层容器有处理循环的能力，还要 Boot 允许它用这条路径。Boot 2.6 起默认 `spring.main.allow-circular-references=false`，遇到依赖环就启动失败；设为 `true` 后，容器才会尝试用早期引用处理循环。

即使打开了这个开关，下面几种情况仍然处理不了：

- 直接的构造器循环，没有能提前暴露的实例。
- prototype 之间的循环，prototype 不进单例缓存，没有早期引用这套机制。
- 跨作用域的依赖，需要满足目标作用域的上下文要求。
- 后处理器产生了不同的代理，早期引用和最终引用对不上，会冲突。

因此，这个开关只允许容器尝试处理部分循环，不能保证所有依赖环都能启动。拆开职责上的相互依赖，才能避免初始化时使用尚未准备好的对象。

## 6. 作用域 {#作用域}

**作用域**决定容器什么时候创建对象，以及哪些调用共享同一个对象。判断依赖要不要延迟获取，先要分清这四种作用域：

- singleton：同一个容器、同一个 Bean 定义只共享一个实例。
- prototype：每次向容器获取都新建一个实例。
- request：同一次 Web 请求内共享一个实例。
- session：同一个 Web 会话内共享一个实例。

singleton 在创建时直接注入一个 prototype，只会拿到那一刻创建的那一份。之后不管调用多少次方法，用的都是同一个引用，因为调用方法并不会再去向容器要对象。需要每次都拿到新对象，可以注入 `ObjectProvider`：

```java
class ReportService {
    private final ObjectProvider<ReportBuilder> builders;

    ReportService(ObjectProvider<ReportBuilder> builders) {
        this.builders = builders;
    }

    Report create() {
        return builders.getObject().build();
    }
}
```

`ReportBuilder` 是 prototype 时，每次调用 `create()`，`getObject()` 都会向容器要一次，于是每次都得到一个新实例。容器交出 prototype 后就不再管它，资源清理由使用方负责。方法注入或作用域代理也能把获取目标推迟到使用时。

request 作用域的 Bean 可以通过作用域代理注入到 singleton 里。**作用域代理**是一个中间对象，每次被调用时才去查找当前作用域里的真实目标，所以能随请求切换实际的实例。前提是调用发生在有效的请求上下文里。异步线程已经离开了这个上下文，再解析目标就会失败，这时应该把需要的请求数据显式传过去。

## 7. 循环依赖的职责拆分 {#拆解循环依赖}

拆循环依赖，先要搞清楚两个服务为什么非得互相调用，再调整调用方向。常见的拆法有这几种：

- 把双方共用的逻辑提取成第三个组件，两个服务各自依赖它。
- 由上层的应用服务编排流程，单向调用原来的两个服务。
- 状态变更后发布领域事件，由监听者处理后续工作。
- 重新定义接口，让服务只返回结果，由调用方决定下一步，或者通过明确的回调接口通知结果。

Provider 适合确实需要延迟获取的资源。如果只是拿它把直接依赖藏起来，初始化时的错误会被推迟到使用时才暴露，职责之间的环也依然存在。

## 8. 常见问题 {#常见问题}

### 8.1 打开循环引用开关后，构造器循环也能处理吗？ {#循环依赖的支持范围}

不能。开关允许使用早期引用，但直接的构造器循环中，双方都还没有实例，没有引用可以提前交出。prototype 之间的循环也不在单例缓存的处理范围内。

### 8.2 为什么不能先注入原始对象，最后再生成代理？ {#早期代理的一致性}

早期代理必须和最终交出的代理是同一个，各调用方才能得到相同的增强行为。假如 B 拿到的是原始的 A，而容器对外交出的是 A 的事务代理，那 B 调用 A 时就会绕过事务。早期引用工厂正是给自动代理创建器一个协调引用的机会，自定义的后处理器也要遵守这套约定。

## 9. 面试题 {#面试题}

### 9.1 Spring 的三级缓存怎样处理循环依赖，有哪些限制 {#three-level-cache}

**考察重点**：解释实例化与属性填充为何可以分开，并说明早期代理怎样保持引用一致。能结合构造器、作用域和 Boot 配置判断处理范围。

**相关内容**：[构造器注入的循环](#构造器注入的循环)至[Spring Boot 的默认行为](#spring-boot-的默认行为)。

<details>
<summary>参考回答</summary>

**允许循环引用时，三级缓存通过提前交付单例引用，完成部分 Setter 或字段注入循环。**

容器实例化 A 后登记引用工厂，创建 B、为 B 注入 A 时，再按需取得 A 的早期引用。B 完成初始化后被注入 A，容器最后完成 A 并发布完整单例。

完整单例、已生成的早期引用和引用工厂分别保存在三个缓存中。工厂还能生成早期代理，让最终发布结果复用同一引用，保证各调用方的增强行为一致。

这条路径要求对象可以先实例化，所以直接构造器循环和 prototype 循环仍会失败。Boot 2.6 起默认禁止循环引用，即使显式开启，也应优先用职责提取、上层编排或事件拆开依赖环。

</details>

### 9.2 singleton 注入 prototype 后，每次调用都会创建新对象吗？ {#prototype-in-singleton}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：区分方法调用与容器获取对象的时机，说明 Provider 怎样触发新建，以及 prototype 由谁清理。

**相关内容**：[作用域](#作用域)。

<details>
<summary>参考回答</summary>

**直接注入后，每次方法调用都会使用同一份 prototype 实例，因为依赖只在 singleton 创建时解析一次。**

若每次调用都需要新对象，可注入 `ObjectProvider`，再调用 `getObject()` 向容器获取。目标为 prototype 时，每次获取才会创建新实例，使用者负责实例的资源清理。

</details>
