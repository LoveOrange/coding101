# Spring Boot 启动

Spring Boot 启动从 `main` 方法开始，准备配置、创建 Spring 容器，让应用具备运行条件；Web 应用还会启动嵌入式服务器。它大致分三段：准备运行环境，刷新容器，执行启动任务。三段都成功以后，应用才被标为就绪。

这个顺序决定了很多实际问题的答案：某个配置为什么没生效，初始化代码该放在哪里，端口已经能连了为什么还不该接流量，启动慢该先查哪一段。本文以 Boot 3.5 为准。

## 1. 面试核心 {#core}

- `@SpringBootApplication` 组合了 `@SpringBootConfiguration`、`@EnableAutoConfiguration` 和 `@ComponentScan`，分别负责**应用配置、自动配置和组件扫描**。
- `SpringApplication` **先准备保存配置的 `Environment`，再创建并刷新 `ApplicationContext`**。[卡](#boot-startup)
- 嵌入式 Web 服务器**在 `refresh()` 阶段就启动了**，这时 Runner 启动任务还没执行，所以端口可连接不代表应用就绪。
- `ApplicationRunner` 和 `CommandLineRunner` **统一按 `Ordered` 或 `@Order` 排序**，数值越小越早执行，接口类型没有固定先后。[卡](#runner-ready-order)
- **所有 Runner 成功返回后**，Boot 才发布 `ApplicationReadyEvent`，随后把就绪状态设为 `ACCEPTING_TRAFFIC`。

## 2. 启动类与 `@SpringBootApplication` {#启动类与-springbootapplication}

启动类有两个作用：它是 Java 程序的入口，也告诉 Spring 从哪里开始读应用配置。下面的 `main` 方法把启动类和命令行参数一起交给 `SpringApplication.run()`：

```java
@SpringBootApplication
public class OrderApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderApplication.class, args);
    }
}
```

运行后，Boot 以 `OrderApplication` 为配置来源启动应用。类上这一个注解，组合了**应用配置、自动配置和组件扫描**三项职责：

- `@SpringBootConfiguration` 把当前类标记为应用配置来源。
- `@EnableAutoConfiguration` 导入自动配置候选，再按类路径、配置属性和已有的 Bean 判断每一项是否生效。
- `@ComponentScan` 默认扫描启动类所在的包及其子包，把找到的组件注册到容器。

扫描范围由启动类的位置决定，所以启动类应该放在业务根包。放得太深，同级包里的组件就扫不到，启动时会报找不到 Bean。反过来，放在没有 `package` 声明的默认包里，扫描会扩展到依赖中的大量类，既增加扫描成本，也容易把无关的类型带进容器。

## 3. 运行环境准备 {#准备运行环境}

容器要先知道应用是什么类型、配置是什么，才能创建对应的组件。这里有两个对象：**`Environment`** 汇总所有配置属性和它们的来源；**`ApplicationContext`** 是管理 Bean 和应用事件的 Spring 容器。环境准备阶段就是先把前者准备好，再创建后者。

从创建 `SpringApplication` 到刷新容器之前，主要有以下步骤：

1. 构造 `SpringApplication` 时，根据类路径推断应用类型，并加载初始化器和监听器。
2. 执行 `run()` 后，发布早期启动事件，让已经注册的监听器参与启动。
3. 读取命令行参数、环境变量和配置文件等来源，准备 `Environment`。
4. 绑定 `spring.main.*` 属性，用这些值调整启动行为。
5. 按确定的应用类型，创建对应的 `ApplicationContext`。
6. 执行初始化器，让它们在刷新之前定制上下文。

第 1 步推断的应用类型分三种：基于 Servlet 的 MVC 应用、基于响应式处理的 WebFlux 应用，以及非 Web 应用。类路径上 MVC 和 WebFlux 同时存在时，默认选 Servlet 应用；也可以用 `spring.main.web-application-type` 明确指定。非 Web 应用照样创建并刷新 Spring 容器，只是不启动 Web 服务器。

第 2 步的部分事件发生在 `ApplicationContext` 创建之前，这时声明为 `@Bean` 的监听器还没注册，收不到这些事件。需要接收时，可以在 `run()` 之前调用 `addListeners()` 注册监听器。

## 4. 容器刷新 {#容器刷新}

**容器刷新**是解析配置、处理 Bean 定义并创建所需组件的过程。Boot 先把启动类注册为配置来源，再调用 `refresh()`。刷新时，后处理器解析用户配置和自动配置，得到一组 `BeanDefinition`，它记录了对象的类型、依赖和创建方式。所以自动配置是在这一步才真正被解析和判断的。

刷新先处理定义，再批量创建普通业务 Bean。两类后处理器的顺序见 [BeanDefinition](./beandefinition-container-startup.mdx#beanpostprocessor)。非懒加载的单例在刷新阶段完成创建和初始化，回调过程见 [Bean 生命周期](./bean-creation-lifecycle.mdx)。

定义的注册顺序不等于实例的创建顺序。实例什么时候创建，还受**三类设置**影响：

- 依赖关系：创建当前 Bean 之前，要先拿到它依赖的对象。
- `@DependsOn`：指定某些 Bean 必须先完成初始化。
- 懒加载：把对象创建推迟到第一次需要它的时候。

所以先注册定义的 Bean，实例可能因为依赖或懒加载而更晚创建。刷新完成时，容器发布 `ContextRefreshedEvent`，通知监听器上下文已经刷新。

## 5. 嵌入式 Web 服务器 {#嵌入式-web-服务器}

Web 应用还要有一个接收 HTTP 请求的服务器，它也是在容器刷新期间启动的。Servlet 应用使用支持 Web 功能的 `WebApplicationContext`，容器里的 `WebServerFactory` 创建 Tomcat、Jetty 等嵌入式服务器，再由生命周期流程启动它。

同一阶段，Servlet、Filter 和 Web 监听器注册到 Servlet 容器；默认非懒加载时，Spring MVC 也会在刷新期间建立 Controller 的请求映射。前者准备好服务器的请求入口，后者准备好到业务方法的路由。

关键在于时间点：服务器开始监听时，Runner 这类启动任务还没执行。**Runner** 是容器刷新之后执行的应用初始化任务（第 6 节展开），**readiness**（就绪状态）表示应用是否已经可以接流量（第 7 节展开）。所以端口能连上，只说明服务器能接收连接，部署平台仍然应该等到就绪以后再转发业务流量。

服务器启动失败时，重点检查**端口、连接器、证书和服务器工厂**：

- 端口是否被其他进程占用。
- 连接器配置是否正确，服务器监听的地址和协议对不对。
- 启用 HTTPS 时，证书配置是否有效。
- 容器里是否有匹配当前 Web 类型的 `WebServerFactory`。

如果失败发生在 Bean 创建阶段，要沿着依赖链和异常的 `cause` 查找根本原因。`cause` 保存着被包装的原始异常，外层通常只是说「某个 Bean 创建失败」，真正的配置错误在里面。

## 6. Runner 与就绪 {#runner-与就绪}

Runner 用来放那些必须在容器刷新之后、应用标为就绪之前完成的初始化。Boot 提供两种接口，区别只在于怎样接收命令行参数：`ApplicationRunner` 接收解析好的 `ApplicationArguments`，能区分选项参数和普通参数；`CommandLineRunner` 直接接收原始的 `String[]` 数组。

两类 Runner 放在同一个集合里，按 `Ordered` 或 `@Order` 统一排序，数值越小越早执行。所以执行顺序只看排序值，接口类型没有固定的优先级。

Runner 的耗时会直接推迟应用就绪的时间。安排任务时，要控制**数据回填、重试和远程调用**带来的等待：

- 大批量数据回填会让启动时间随数据量增长，应该考虑独立的迁移流程或显式的运维操作。
- 无限重试会让启动任务一直结束不了，要限制重试次数或总时长。
- 远程调用要设置超时，否则一个迟迟不返回的请求就会卡住启动。

必须在接流量之前完成的任务，留在启动流程里，并给出明确的完成期限；不是必须的长任务，交给受管理的后台执行器。Runner 抛出异常会让启动失败，应用保持未就绪。

## 7. 启动、存活与就绪 {#启动存活与就绪}

「应用启动成功了吗」其实可以指四种不同的完成程度，从进程存在到可以接收流量：

| 阶段 | 含义 |
| --- | --- |
| JVM 运行 | 进程已存在 |
| refresh 完成 | 非懒加载单例等刷新工作已完成 |
| Liveness 正常 | 应用内部状态被标为 CORRECT |
| Readiness 正常 | 应用已标为 ACCEPTING_TRAFFIC |

后两种是部署平台最关心的。**Liveness**（存活状态）表示应用内部能否正常工作，或者出问题后能否自己恢复；**Readiness**（就绪状态）表示应用当前是否应该接收流量。平台根据前者决定要不要重启实例，根据后者决定要不要把请求转过来。

两者混用会出问题。比如共享数据库故障时，如果让它触发 liveness 失败，依赖这个数据库的所有实例都会被反复重启，而重启并不能修好数据库。设计原则见 [Spring Boot Actuator](./actuator-health-startup-diagnostics.mdx#liveness-探针)，健康组和平台探针的配置见 [Spring Boot Actuator](./actuator-health-startup-diagnostics.mdx#readiness-探针)。

## 8. 启动耗时分析 {#启动耗时分析}

排查启动慢，先记总耗时，再按前面讲的阶段拆开比较**各启动阶段的耗时**：

- 配置加载：配置文件读取和条件评估。
- 定义处理：扫描、配置类解析和后处理器执行。
- Bean 创建：构造器和初始化回调，连接池初始化和数据库迁移单独计时。
- 服务器启动：Web 服务器的创建和启动。
- Runner 执行：每个业务初始化任务单独计时。

哪个阶段访问了数据库或远程服务，还要把调用耗时和超时单独记下来，这样才能分清是本地计算慢，还是在等外部依赖。

`ApplicationStartup` 用来采集 Spring 的启动步骤，Actuator 和 JFR 可以查看或关联这些事件，配置见 [Spring Boot Actuator](./actuator-health-startup-diagnostics.mdx#启动阶段分析)。

`spring.main.lazy-initialization=true` 能把 Bean 创建推迟到需要时，启动阶段确实少做了一部分工作，但代价是首次请求要承担初始化成本，配置错误也要等到用的时候才暴露。所以先找到耗时来源，再判断是否只对少量 Bean 使用懒加载。必要的基础设施仍然应该在启动时校验，免得接到请求以后才发现关键配置写错了。

## 9. 启动事件顺序 {#启动事件顺序}

启动事件告诉监听器启动走到了哪一步。对照事件顺序，可以判断初始化代码该挂在哪里，也能解释某个监听器为什么收不到事件。Boot 3.5 的主要顺序如下：

```text
ApplicationStartingEvent
→ ApplicationEnvironmentPreparedEvent
→ ApplicationContextInitializedEvent
→ ApplicationPreparedEvent
→ refresh
→ ApplicationStartedEvent
→ LivenessState.CORRECT
→ 所有 Runner
→ ApplicationReadyEvent
→ ReadinessState.ACCEPTING_TRAFFIC
```

`ApplicationPreparedEvent` 的意思是启动类等初始定义已经加载、马上要刷新容器。完整的配置解析还在后面的 `refresh()` 里，所以这时全部业务定义并没有准备好。

事件监听器默认在发布事件的线程里同步执行，发布方要等监听器返回才继续往下走。所以，如果 `ApplicationReadyEvent` 的同步监听器迟迟不返回，后面的 readiness 更新也得等着。在这里直接跑长任务，就会推迟平台开始转发流量的时间。

启动过程中抛出异常时，Boot 发布 `ApplicationFailedEvent`。诊断日志要记下失败发生在哪个阶段，并保留原始异常链，这样才能从外层的启动失败一路追到最早的原因。

## 10. 常见问题 {#常见问题}

### 10.1 为什么 `@PropertySource` 中的早期配置没有生效？ {#早期配置与-propertysource}

因为 `@PropertySource` 加入属性的时间，晚于这些配置被读取的时间。它要到容器刷新时才把属性加进 `Environment`，而部分日志配置和 `spring.main.*` 属性在刷新之前就已经读过了。所以这些属性要放在**刷新前可用的配置来源**里：

- `application.properties` 或 `application.yaml` 等配置文件。
- 操作系统环境变量。
- Java 系统属性。
- 命令行参数。

### 10.2 `ApplicationReadyEvent` 适合执行长期任务吗？ {#就绪事件与长期任务}

不适合在监听器里直接阻塞执行。默认的同步监听器会推迟后面的 readiness 更新。可以在监听器里把任务交给受管理的执行器，或者干脆改成独立作业。

任务转到后台以后，还要让它具备**结束控制和状态查询**：

- 设置超时和重试上限，避免无限等待。
- 提供取消和关闭协议，应用停止时能结束任务。
- 暴露执行状态，让运维能判断任务是完成了还是失败了。

## 11. 面试题 {#面试题}

### 11.1 Spring Boot 从 main 方法到应用就绪经历了什么 {#boot-startup}

**考察重点**：解释环境准备、容器刷新与启动任务的先后关系。能指出自动配置、Bean 初始化和 Web 服务器启动分别发生在哪个阶段。

**相关内容**：[启动类与 `@SpringBootApplication`](#启动类与-springbootapplication)至[启动耗时分析](#启动耗时分析)。

<details>
<summary>参考回答</summary>

**Spring Boot 依次准备环境、刷新容器、执行 Runner，最后发布应用就绪状态。**

- **环境阶段准备配置。** `SpringApplication` 推断应用类型、加载初始化器和监听器，`run()` 准备 `Environment` 并创建 `ApplicationContext`。
- **刷新阶段建立应用。** 注册启动配置，调用 `refresh()` 解析用户配置与自动配置、注册 Bean 定义、创建并初始化非懒加载单例；Web 应用还会启动嵌入式服务器。
- **Runner 完成后才就绪。** 刷新后发布 `ApplicationStartedEvent` 并设为 `CORRECT`，再执行 Runner。全部成功后发布 `ApplicationReadyEvent`，随后设为 `ACCEPTING_TRAFFIC`。

所以端口已监听不代表启动任务已完成。启动失败时，按上述阶段沿异常链定位根因。

</details>

### 11.2 ApplicationRunner 一定先于 CommandLineRunner 执行吗？ {#runner-ready-order}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：说明两类 Runner 如何共同排序，以及它们与 `ApplicationStartedEvent`、`ApplicationReadyEvent` 的先后关系。

**相关内容**：[Runner 与就绪](#runner-与就绪)、[启动事件顺序](#启动事件顺序)。

<details>
<summary>参考回答</summary>

**不一定，两类 Runner 按 `Ordered` 或 `@Order` 统一排序。**

Boot 收集全部 Runner 后一起比较排序值，数值小的先执行。因此，顺序由排序值决定，接口类型没有固定优先级。

`ApplicationStartedEvent` 在 Runner 执行前发布。全部 Runner 成功返回后，Boot 才发布 `ApplicationReadyEvent`，随后更新 readiness。任意 Runner 抛出异常，都会使启动失败。

</details>
