# Spring Boot 启动

Spring Boot 启动依次准备环境、刷新容器并执行启动任务。本文以 Boot 3.5 为准，负责阶段顺序、事件与就绪。定义扩展见 [BeanDefinition](./beandefinition-container-startup.mdx)。条件选择见 [Spring Boot 自动配置](./auto-configuration-conditions.mdx)。

## 1. 面试核心 {#core}

- `@SpringBootApplication` 组合配置、自动配置和组件扫描。
- SpringApplication 先准备 Environment，再创建并刷新上下文。[卡](#boot-startup)
- 嵌入式 Web 服务器在 refresh 阶段启动，早于 Runner 完成。
- 两类 Runner 统一按 `Ordered` 或 `@Order` 排序。[卡](#runner-ready-order)
- Runner 完成后发布 `ApplicationReadyEvent`，随后更新 readiness。

## 2. 启动类与 `@SpringBootApplication` {#启动类与-springbootapplication}

```java
@SpringBootApplication
public class OrderApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderApplication.class, args);
    }
}
```

`@SpringBootConfiguration` 标记应用配置。`@EnableAutoConfiguration` 导入自动配置。`@ComponentScan` 默认扫描启动类所在包及子包。

启动类宜位于业务根包。位置过深会遗漏同级组件，使用默认包则会扩大扫描范围。

## 3. 运行环境准备 {#准备运行环境}

SpringApplication 构造时推断应用类型，并加载初始化器与监听器。执行 `run()` 后，先发布早期事件，再准备 Environment。

Boot 读取命令行、环境变量与配置数据。随后绑定 `spring.main.*`，创建相应上下文。初始化器在刷新前定制该上下文。

MVC 与 WebFlux 同时存在时，默认选择 Servlet 应用。可通过 `spring.main.web-application-type` 指定类型。非 Web 应用也会创建并刷新 Spring 容器。

早期事件发生在 Bean 注册之前。要接收它们，可在 run 前用 `addListeners()` 注册监听器。

## 4. 容器刷新 {#容器刷新}

Boot 注册启动配置来源后，调用 `refresh()`。容器在刷新中解析用户配置与自动配置。具体定义处理顺序见 [BeanDefinition](./beandefinition-container-startup.mdx#beanpostprocessor)。

非懒加载单例在此阶段创建。实例初始化见 [Bean 生命周期](./bean-creation-lifecycle.mdx)。刷新完成时，容器发布 `ContextRefreshedEvent`。

定义注册与实例创建有不同顺序。实例依赖、`@DependsOn` 和 lazy 设置决定创建时机。

## 5. 嵌入式 Web 服务器 {#嵌入式-web-服务器}

Servlet 应用使用专门的 WebApplicationContext。WebServerFactory 在刷新阶段创建服务器，生命周期流程随后启动它。

服务器开始监听时，Runner 尚未执行完毕。端口可连接只说明接入路径已经打开。部署平台应等待 readiness 后再转发业务流量。

服务器失败时检查端口、证书与连接器配置。Bean 创建失败时沿 cause 链定位首个业务原因。

## 6. Runner 与就绪 {#runner-与就绪}

两类 Runner 在上下文刷新后统一执行。`ApplicationRunner` 接收解析后的 `ApplicationArguments`。`CommandLineRunner` 接收原始 String 参数数组。

所有 Runner 放在同一集合中排序。`@Order` 数值越小，执行越早。接口类型没有固定的先后顺序。

Runner 适合必须完成且耗时有界的初始化。抛出异常会使启动失败，应用不会进入就绪状态。非必要长任务应交给受管理的后台执行器。

## 7. 启动、存活与就绪 {#启动存活与就绪}

| 阶段 | 含义 |
| --- | --- |
| JVM 运行 | 进程已存在 |
| refresh 完成 | 非懒加载单例等刷新工作已完成 |
| Liveness 正常 | 应用内部状态被标为 CORRECT |
| Readiness 正常 | 应用已标为 ACCEPTING_TRAFFIC |

健康组与平台探针配置见 [Spring Boot Actuator](./actuator-health-startup-diagnostics.mdx)。

## 8. 启动耗时分析 {#启动耗时分析}

先区分配置加载、定义处理、Bean 创建、服务器与 Runner 耗时。启动记录器配置见 [Spring Boot Actuator](./actuator-health-startup-diagnostics.mdx#启动阶段分析)。

`spring.main.lazy-initialization=true` 可延迟 Bean 创建。启动阶段会少做部分工作，首次访问则承担初始化成本。配置错误也随之延后暴露。必要基础设施应保留启动校验。

## 9. 启动事件顺序 {#启动事件顺序}

Boot 3.5 的主要事件顺序如下：

```text
ApplicationStartingEvent
→ ApplicationEnvironmentPreparedEvent
→ ApplicationContextInitializedEvent
→ ApplicationPreparedEvent
→ refresh
→ ApplicationStartedEvent
→ LivenessState.CORRECT
→ 所有 Runner
→ ApplicationReadyEvent
→ ReadinessState.ACCEPTING_TRAFFIC
```

`ApplicationPreparedEvent` 表示初始定义已加载，刷新即将开始。完整配置解析仍在 refresh 中进行。

默认事件监听器同步执行。`ApplicationReadyEvent` 的同步监听器未返回时，后续 readiness 更新仍需等待。长期任务直接放在该监听器中，会延迟接流量。

启动抛出异常时发布 `ApplicationFailedEvent`。诊断应记录异常所处阶段，保留最早的根因。

## 10. 常见问题 {#常见问题}

### 10.1 早期配置与 PropertySource {#早期配置与-propertysource}

`@PropertySource` 在刷新时才加入 Environment。部分日志和 `spring.main.*` 属性此前已读取。此类参数应放在配置数据或环境变量等早期来源中。

### 10.2 就绪事件与长期任务 {#就绪事件与长期任务}

默认同步监听器会阻塞后续 readiness 更新。长期任务应移至受管理执行器，并提供超时与停止协议。
