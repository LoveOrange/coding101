# DispatcherServlet

**DispatcherServlet** 是 Spring MVC 统一接收并分派请求的 Servlet，也叫前端控制器。它负责找到处理请求的对象，再协调调用、返回值处理和异常处理。理解这条分工，才能解释一个 URL 怎样匹配到 Controller 方法，以及请求为什么会在进入方法之前就失败。

## 1. 面试核心 {#core}

- `HandlerMapping` 负责**找到处理器**，把它与匹配的拦截器放进 `HandlerExecutionChain`。[卡](#mapping-vs-adapter)
- 不同方法注册了**完全相同的映射条件**，会在启动时发生冲突；条件只是部分重叠时，还要看请求阶段能否选出唯一的最优匹配。
- `HandlerAdapter` 负责**按处理器类型执行调用**，注解方法的适配器还负责参数解析和返回值处理。
- 404、405、415、406 分别帮助定位资源、HTTP 方法、请求媒体类型和响应媒体类型的问题，排查时还要确认**实际匹配了哪个处理器**。
- `HandlerExceptionResolver` 返回 **`null` 表示未处理**，返回**空 `ModelAndView` 表示已处理且无需渲染视图**。[卡](#resolver-result)

## 2. HandlerMapping {#handlermapping}

**处理器**是实际处理请求的对象，可以表示一个 Controller 方法，也可以是静态资源处理器。**`HandlerMapping`** 负责根据请求找到它。DispatcherServlet 按顺序询问已注册的映射器，采用首个非空结果。

结果用 `HandlerExecutionChain` 表示，其中包含处理器和当前请求匹配的拦截器：

```text
HandlerExecutionChain
  ├─ handler: HandlerMethod
  └─ interceptors: [locale, metrics]
```

注解控制器的映射由 `RequestMappingHandlerMapping` 在启动时建立。它读取 `@RequestMapping`、`@GetMapping` 等注解，登记方法及其匹配条件。上面的 `HandlerMethod` 就表示一个控制器方法；`locale`、`metrics` 表示与这次请求匹配的拦截器。

## 3. 映射条件 {#映射条件}

一个请求能否匹配 Controller 方法，要看整组条件，不能只比较 URL。注解控制器的映射可以同时约束：

- 路径模式和 HTTP 方法决定访问哪个地址、执行哪种操作。
- `params` 和 `headers` 分别约束请求参数与请求头。
- `consumes` 约束请求的 `Content-Type`，也就是请求正文的媒体类型。
- `produces` 声明能生成的响应媒体类型，并与客户端的 `Accept` 匹配。

不同方法注册完全相同的映射，会在启动时失败。不过，路径相同不一定冲突：一个处理 `GET /orders`，另一个处理 `POST /orders`，HTTP 方法就能把它们区分开。

路径模式相互重叠时，框架会在请求阶段比较匹配的具体程度。如果最优匹配仍有多个，就会报告歧义。因此，设计 API 时要让路径、方法和媒体类型等条件能明确区分请求。

`GET` 映射支持 `HEAD`，输出阶段省略正文。`OPTIONS` 可自动生成包含允许方法的 `Allow` 头。客户端仍应按明确的业务方法调用。

## 4. HandlerAdapter {#handleradapter}

**`HandlerAdapter`** 负责按处理器的类型执行调用。不同处理器没有统一的调用方式，例如 Controller 方法需要解析 Java 参数，静态资源处理器则负责读取资源。DispatcherServlet 不直接处理这些差异，而是选择 `supports(handler)` 返回 `true` 的适配器，把调用交给它。

注解方法由 `RequestMappingHandlerAdapter` 执行，主要经过下面几步：

1. 创建数据绑定和模型上下文，用来转换输入并保存视图数据。
2. 调用 `HandlerMethodArgumentResolver`，从请求中解析方法参数。
3. 使用解析好的参数调用 Controller 方法。
4. 调用 `HandlerMethodReturnValueHandler`，将返回值交给响应写出或视图处理。

例如，多个 Controller 都要接收当前用户对象，可以扩展参数解析器，统一从请求上下文取值。参数解析机制见 [Spring MVC 参数解析](./binding-validation-content-negotiation.mdx)。

## 5. Interceptor 回调 {#interceptor-回调}

拦截器在处理器调用前后执行回调，用来决定是否放行、处理同步结果和清理资源。

短路与异步回调的具体规则见 [Spring 拦截机制](./filter-interceptor-aspect-boundaries.mdx#拦截器回调顺序)。

## 6. 异常解析 {#异常解析}

**`HandlerExceptionResolver`** 是把 MVC 处理过程中的异常转换为响应或视图的扩展接口。参数解析、Controller 调用或返回值处理抛出异常后，DispatcherServlet 会依次交给这些解析器，直到有一个返回已处理的结果。默认链中的三类解析器分工如下：

| Resolver | 职责 |
| --- | --- |
| `ExceptionHandlerExceptionResolver` | 调用 `@ExceptionHandler` |
| `ResponseStatusExceptionResolver` | 处理 `@ResponseStatus` 和 `ResponseStatusException` |
| `DefaultHandlerExceptionResolver` | 将标准 MVC 异常映射为状态码 |

`@ExceptionHandler` 标记异常处理方法，由对应的解析器负责调用。Filter 在进入 DispatcherServlet 之前抛出的异常，由过滤链或 Servlet 错误机制处理。

API 错误字段与处理范围见 [API 错误契约](./api-error-contract.mdx)。

## 7. HTTP 错误状态诊断 {#排查-404405415-与-406}

状态码能帮助判断请求在哪个阶段失败。定位时，先按下表检查路径和媒体类型，再结合实际匹配的处理器确认原因。

| 状态 | 检查内容 |
| --- | --- |
| 404 | 上下文路径、Servlet 映射与资源存在性 |
| 405 | 路径允许的 HTTP 方法 |
| 415 | `Content-Type`、`consumes` 与消息读取器 |
| 406 | `Accept`、`produces` 与消息写出器 |

静态资源处理器也能返回 404，所以要检查实际匹配的 handler。打开 Spring MVC 的映射诊断日志，可以查看启动时注册的映射，以及请求的匹配过程。

参数内容读取失败与媒体类型错误的区别见 [Spring MVC 参数解析](./binding-validation-content-negotiation.mdx#content-type-与-accept)。

## 8. 异常解析返回值 {#异常解析返回值}

异常解析器是否处理成功，由返回值表达。**`ModelAndView`** 是保存模型数据和视图信息的对象，在异常解析中，它是否为 `null`、是否为空有不同含义：

- 返回 `null`，表示当前解析器未处理，继续尝试下一项。
- 返回空 `ModelAndView`，表示异常已处理，且无需渲染视图。
- 返回带视图信息的 `ModelAndView`，表示异常已处理，DispatcherServlet 继续渲染该视图。

如果所有解析器都返回 `null`，异常就继续向 Servlet 容器传播。容器可触发 ERROR 派发，也就是转入错误处理入口。自定义解析器写完响应后，应返回空 `ModelAndView`，让解析链结束。

响应已提交，表示状态码和响应头已经发送给客户端。此后发生错误，解析器无法重新生成完整响应，需要按已写出的内容处理连接和日志。

## 9. 常见问题 {#常见问题}

### 9.1 为什么需要 HandlerAdapter？ {#处理器适配的作用}

因为不同处理器的调用方式不同，HandlerAdapter 将这些差异封装起来。DispatcherServlet 只需选择合适的适配器，就能统一协调注解方法与其他处理器。

### 9.2 一个应用能有多个 DispatcherServlet 吗？ {#多-dispatcherservlet-与上下文}

可以。Boot MVC 应用默认使用一个 DispatcherServlet，Servlet 容器也允许注册多个实例并映射不同路径。每个实例可拥有自己的 WebApplicationContext，也就是管理 Web 组件的应用上下文。子上下文可读取父上下文的 Bean，父容器无法读取子容器的定义。

## 10. 面试题 {#面试题}

### 10.1 HandlerMapping 与 HandlerAdapter 分别负责什么 {#mapping-vs-adapter}

**考察重点**：说明映射器怎样找到处理器和拦截器，以及适配器怎样解析参数、调用方法并处理返回值。

**相关内容**：[HandlerMapping](#handlermapping)至[Interceptor 回调](#interceptor-回调)。

<details>
<summary>参考回答</summary>

**HandlerMapping 根据请求条件找到处理器，HandlerAdapter 负责按处理器类型执行调用。**

映射器将 handler 与匹配的拦截器一起放进 `HandlerExecutionChain`。

DispatcherServlet 再选择支持该 handler 的适配器。对于注解方法，适配器负责解析参数、执行方法和处理返回值。因此，DispatcherServlet 可以统一协调多种处理器。

</details>

### 10.2 异常解析器返回 null 和空 ModelAndView 有什么区别？ {#resolver-result}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释两种返回值怎样影响后续解析器，并说明所有解析器都未处理时异常会传到哪里。

**相关内容**：[异常解析返回值](#异常解析返回值)。

<details>
<summary>参考回答</summary>

**null 表示当前解析器未处理异常，空 `ModelAndView` 表示已处理且无需渲染视图。**

前者会让解析链继续，后者会结束解析链。

例如，自定义解析器已经写出错误响应，就应返回空 `ModelAndView`。如果全部解析器都返回 null，异常会继续传给 Servlet 容器，由容器进入错误处理流程。

</details>
