# IoC 容器

**Spring IoC 容器**根据配置创建对象、装配依赖，并管理对象的初始化和销毁。装配依赖，就是把一个对象需要的协作者交给它，比如把支付客户端交给订单服务。

容器带来的变化，是把「选哪个实现、用什么配置」从业务类移到统一装配的地方。业务类只声明自己需要什么，测试时也就能传入替代对象。理解 IoC，要分清容器负责的创建、装配和生命周期，以及业务代码仍需负责的状态管理：一个 Bean 被多个请求共享，并不意味着它线程安全。

## 1. 面试核心 {#core}

- IoC 把**对象创建和装配的控制权交给外部容器**，DI 是实现它的方式：通过构造器、工厂方法参数或属性**把依赖传给对象**。[卡](#ioc-di)
- BeanDefinition **描述对象怎样创建、怎样管理**，Bean 是容器按定义创建并管理的对象。
- 构造器注入**在签名里声明依赖**；Service Locator 则由业务对象**主动查询容器**，依赖藏在方法内部。
- 实体和值对象可以直接创建，**需要依赖注入、代理或生命周期管理的组件**才注册为 Bean。
- Spring singleton 按容器和 Bean 定义**共享实例**，并发修改业务状态**仍然需要同步**。[卡](#singleton-thread-safety)

## 2. 依赖创建与外部装配 {#在对象内部创建依赖}

业务对象要调用别的组件时，依赖可以自己创建，也可以由外部传进来。两种做法的区别在于：谁来决定用哪个具体实现。下面把同一个订单服务的两种写法放在一起比较：

```java
// 写法一：业务类内部创建依赖
public final class OrderService {
    private final PaymentClient paymentClient =
            new HttpPaymentClient("https://pay.example.com");
}

// 写法二：通过构造器接收依赖，与上面的写法分别使用
public final class OrderService {
    private final PaymentClient paymentClient;

    public OrderService(PaymentClient paymentClient) {
        this.paymentClient = paymentClient;
    }
}
```

- 写法一里，`OrderService` 同时决定了业务流程、客户端实现和支付地址。测试时想换成本地桩，或者生产环境要换地址，都得改业务代码。
- 写法二里，`OrderService` 只声明自己需要一个 `PaymentClient`。用哪种实现、连哪个地址，由调用构造器的一方决定。

两种写法都是通过 `PaymentClient` 调用支付能力，业务逻辑本身没变。变的是做出实现选择的位置：构造器注入把它移到了应用组装对象的地方，也就是**装配处**。

## 3. IoC 与 DI {#ioc-与-di}

**控制反转**（Inversion of Control，IoC）是指创建对象、装配协作关系的控制权，从业务对象手里转移到外部容器。上一节的写法二就是这样：`OrderService` 不再自己 `new` 依赖，而是等别人传进来。**依赖注入**（Dependency Injection，DI）是实现控制反转的具体方式：容器通过构造器、工厂方法参数或属性，把依赖传给对象。用 Setter 方法设置依赖，就是通过属性注入的一种写法。

所以两者是目标和手段的关系：IoC 说的是控制权交给谁，DI 说的是依赖怎么传进去。

业务类只声明需要什么，Spring 根据配置完成装配。具体来说，容器要做这些事：

- 从 Java 配置、组件扫描等来源读取对象定义。
- 根据类型、名称和限定符选择依赖。同一类型有多个实现时，用限定符指定要哪一个。
- 按作用域管理实例，并执行初始化和销毁回调。作用域决定哪些调用方共享同一个对象。
- 通过后处理器处理生命周期注解，或者为事务、异步、方法校验等功能加上代理。

## 4. BeanDefinition 与实例 {#beandefinition-与实例}

**BeanDefinition** 保存创建对象需要的类型、依赖和生命周期配置；**Bean** 是容器按定义创建并管理的实例。容器先注册定义，再按作用域创建实例，所以一个定义可能对应一个共享实例，也可能对应很多个实例。

定义里有哪些字段、实例什么时候创建，以及 `@Bean` 工厂方法的参数怎样注入，见 [BeanDefinition](./beandefinition-container-startup.mdx)。

## 5. 替换与测试 {#替换与测试}

依赖从外部传入以后，单元测试就能直接换掉它。**桩对象**（stub）用预设的结果代替真实服务，下面让支付调用总是返回成功：

```java
PaymentClient stub = request -> PaymentResult.approved();
OrderService service = new OrderService(stub);
```

测试通过构造器传入 `stub`，就能验证业务怎样处理支付结果，这个单元测试不需要启动 Spring。组件扫描、条件配置和代理是否生效，数据库等真实资源能否正常使用，交给集成测试检查。

集中装配也有代价：容器启动要花时间，出了问题也要到容器里去查。可以借助启动记录和诊断工具查看 **Bean 创建耗时、依赖关系和配置来源**：

- Bean 缺失时，检查它的定义来源，以及条件配置是否匹配。
- 同一个依赖有多个候选 Bean 时，检查它们在哪里注册、按什么规则选择。
- 依赖成环时，沿依赖关系检查各组件的职责是否划分合理。

这些问题发生在容器组装对象的时候，所以要看定义和装配信息；只盯着业务类里的 `new` 调用，找不到完整原因。

## 6. 容器管理范围 {#容器的使用边界}

交给容器管理的，应该是需要统一装配的组件，而且业务对象要通过清楚的接口声明依赖。**Service Locator**（服务定位）是由业务对象主动向容器查询依赖的模式，比如在方法里调用 `applicationContext.getBean(...)`。这样依赖藏在方法内部，从构造器签名上看不出来，测试时不好替换，静态分析也更难。

需要在运行时选择实现时，可以注入策略集合、`ObjectProvider` 或工厂接口，依赖仍然写在签名上：

- `Map<String, Strategy>` 一次提供多个策略，业务按名称选择。
- `ObjectProvider<T>` 按需获取依赖，适合延迟获取或可选依赖。
- 明确的工厂接口把创建或选择规则封装起来。

框架扩展和插件系统确实需要查询容器时，可以直接用容器 API。实体、值对象和方法内的临时对象直接 `new` 就行；需要装配、代理、作用域或生命周期管理的组件，才注册为 Bean。

## 7. 单例与线程安全 {#单例与线程安全}

Spring singleton 只说明实例被共享，不保证线程安全。这里要分清两件事：共享的范围有多大，共享的状态由谁保护。

先看范围。**Spring singleton** 是指在同一个容器里，一个 Bean 定义只对应一个共享实例。它和设计模式里「全局只有一个实例」不同：同一类型可以注册多个 Bean，多个容器也可以各自创建实例。

再看保护。容器会安全发布初始化结果，也就是保证拿到 Bean 的线程能看到初始化完成后的状态。之后对业务字段的并发修改，就要按 Java 并发规则自己保护了。比如 singleton Controller 的字段被所有并发请求共享，把当前用户写进字段，不同请求就会互相覆盖。

所以请求数据应该放在方法参数、局部变量或请求作用域的对象里。共享的计数、缓存和集合，要用锁、原子变量或合适的并发容器。

改成 prototype 作用域也不一定能解决问题。**prototype** 表示每次向容器获取时都创建新实例，但如果它被注入到一个 singleton 里并长期持有，之后所有请求用的还是那一个实例。所以改作用域以后，还要检查对象实际是怎样获取和持有的。

## 8. 常见问题 {#常见问题}

### 8.1 使用 Spring 后还可以直接 new 对象吗？ {#容器与手工对象}

可以。短生命周期的实体、值对象和方法内的临时对象，直接创建就行。只有需要容器注入、代理或生命周期回调的组件，才要交给容器管理，否则拿不到这些功能。

### 8.2 IoC 能消除对象之间的耦合吗？ {#依赖契约与实现替换}

不能完全消除。IoC 分开的是「选哪个实现」和「业务怎么处理」，业务对象仍然依赖协作者的接口契约。比如 `OrderService` 仍然要知道 `PaymentClient` 返回成功意味着什么。替换实现时必须保持这些语义，业务行为才能符合预期。

## 9. 面试题 {#面试题}

### 9.1 Spring IoC 和依赖注入分别是什么 {#ioc-di}

**考察重点**：区分对象创建和装配的控制权与依赖传入方式，并说明定义、实例和生命周期之间的关系。

**相关内容**：[依赖创建与外部装配](#在对象内部创建依赖)至[BeanDefinition 与实例](#beandefinition-与实例)。

<details>
<summary>参考回答</summary>

**IoC 把对象创建、实现选择和生命周期管理交给外部容器，DI 是容器把依赖传给对象的方式。**

注入可以通过构造器、工厂方法参数或属性完成，所以业务类只需要声明自己需要哪些协作者。

Spring 先读取并注册 BeanDefinition，再解析依赖、按作用域创建实例，并执行初始化等扩展点。实现选择集中到装配处以后，替换和测试都更容易。替换后的组件仍要遵守同样的业务契约；使用容器也会增加启动和诊断的成本。

</details>

### 9.2 Spring singleton Bean 是否天然线程安全？ {#singleton-thread-safety}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释 singleton 的共享范围，并区分初始化结果的可见性与运行时字段修改的线程安全。

**相关内容**：[单例与线程安全](#单例与线程安全)。

<details>
<summary>参考回答</summary>

**不是。Spring singleton Bean 的业务字段会被多个请求共享，并发修改要由业务代码自己保护。**

容器只负责安全发布初始化结果，让拿到 Bean 的线程看到初始化完成后的状态；之后的字段修改不在它的保证范围内。

让 Bean 保持无状态，把请求数据放进参数和局部变量，可以避免共享状态。确实要共享计数或集合时，按实际操作使用锁、原子变量或并发数据结构。

</details>
