# 零拷贝

**零拷贝**（zero copy）是指减少 I/O 路径上由 CPU 完成的数据复制，尤其是数据在内核与应用之间的来回搬运。它省掉的是特定环节的副本；文件尚未缓存时仍要从存储设备读取，发送到网络也仍需设备传输。

Java 中可以通过 `FileChannel.transferTo` 利用平台的高效通道传输，通过 `FileChannel.map` 访问映射的文件区域，也可以用直接 `ByteBuffer` 减少本地 I/O 的中间复制。三者优化的环节不同。回答这类问题，要先指出省掉了哪一步，再说明部分传输、页面访问和内存释放带来的约束。

## 1. 面试核心 {#core}

- `FileChannel.transferTo` 在平台支持时可以利用 `sendfile`，**省去数据经过 Java 堆缓冲区的那一份副本**。[卡](#java-zero-copy)
- `FileChannel.map` 把文件区域**映射到进程地址空间**，适合随机访问；第一次访问不在内存里的页时，仍要等缺页和磁盘读取。
- `allocateDirect` 分配的数据位于**堆外**，可减少本地 I/O 的中间复制；在 HotSpot 中，自动释放仍然**依赖相关 Java 对象的可达性和 GC 清理时机**。[卡](#direct-memory-tradeoffs)
- `transferTo` **返回本次实际传输的字节数**，可能少于请求量，要保存进度、循环继续。
- `MappedByteBuffer` 的**生命周期独立于文件通道**，关闭通道后，已有映射仍然有效。[卡](#mapping-lifetime)

## 2. 普通文件传输的复制过程 {#普通文件传输的复制过程}

普通文件发送会让同一批数据先进入应用，再交回内核网络栈。应用用堆数组读文件、再写入 Socket 时，数据路径可以简化成：

```text
存储设备 → 内核页缓存 → Java 堆缓冲区 → 内核 Socket 缓冲区 → 网卡
```

**页缓存**（page cache）是操作系统在内存里缓存文件内容的区域，读文件时数据先到这里。Java 堆缓冲区在用户空间，是应用自己能访问的内存。中间两个箭头，一个把数据从内核复制到用户空间，一个再从用户空间复制回内核。实际路径还取决于操作系统、文件系统、驱动和 JVM，这里只看主干。

除了中间复制，分开的读取和写入还需要系统调用，增加用户态与内核态之间切换的开销。

如果只是原样发送文件，应用不需要检查或修改字节，就可以考虑省去数据经过用户缓冲区的步骤。

## 3. FileChannel.transferTo {#filechanneltransferto}

`FileChannel.transferTo` 把文件的指定区域直接传给目标通道，应用不经手数据，通道实现就可以选择更省复制的方式：

```java
try (
    FileChannel source = FileChannel.open(path, StandardOpenOption.READ);
    SocketChannel target = SocketChannel.open(address)
) {
    long position = 0;
    long size = source.size();

    while (position < size) {
        long transferred = source.transferTo(
            position,
            size - position,
            target
        );
        if (transferred == 0) {
            throw new IOException("transfer made no progress at " + position);
        }
        position += transferred;
    }
}
```

循环每次从 `position` 开始传输，用返回值推进位置，直到传完最初记录的 `size`。在 Linux 等支持的平台和目标通道上，`transferTo` 可以利用 `sendfile` 在内核中传输，省去数据进入 Java 堆缓冲区、再交回内核的步骤，也可能减少系统调用。

### 3.1 部分传输 {#部分传输}

`transferTo` 返回的是本次实际传输的字节数，可能小于请求的量，甚至是 0。目标暂时写不进去，或者操作系统限制了单次传输量（例如 Linux 的 `sendfile` 一次最多约 2 GB），都会出现这种情况。所以不能假设调用一次就传完，要像示例那样循环，并记住已经完成到了哪个位置。

示例的目标是阻塞的 `SocketChannel`，正常情况下每次至少传出一些字节；如果返回 0，说明没有进展，就抛出异常，让调用方知道文件没有发完，而不是死循环。非阻塞目标返回 0 是正常的，这时要保存当前位置，等 Selector 通知可写再继续（见 [Java NIO](./buffer-channel-selector.mdx#op_write-的注册时机)）。整个传输完成前，两个通道都要保持打开。

### 3.2 平台差异 {#平台差异}

`transferTo` 不保证使用 `sendfile`。API 规定传输行为，具体路径由通道实现和操作系统决定；不能使用直接传输时，也可能采用映射或普通读写。因此，要在目标环境观察系统调用、CPU 使用率和吞吐量，确认实际获得了什么收益。

文件直接传到 Socket 的这条路径，适合不需要应用处理字节的场景。要在用户态压缩、加密、改写协议内容或逐字节解析时，数据仍需由应用访问；不需要处理的部分，例如静态文件响应体，才可以单独考虑直接传输。

## 4. 内存映射 {#内存映射}

**内存映射**（memory-mapped file）是把文件区域映射到进程地址空间，让应用通过内存访问读取内容；能否修改、修改是否写回文件，则取决于映射模式。`FileChannel.map` 建立映射，返回的 `MappedByteBuffer` 是访问入口：

```java
try (FileChannel channel = FileChannel.open(path, StandardOpenOption.READ)) {
    MappedByteBuffer mapped = channel.map(
        FileChannel.MapMode.READ_ONLY,
        0,
        Math.min(channel.size(), 1024L * 1024)
    );

    while (mapped.hasRemaining()) {
        consume(mapped.get());
    }
}
```

这里只映射文件开头最多 1 MiB，再通过 `mapped.get()` 读取字节并交给 `consume`。在常见的文件映射实现中，进程直接访问映射的文件页，不必先把整块内容复制到 Java 堆数组。

建立映射不保证文件内容已经驻留在内存中。**缺页**（page fault）是访问页面时，操作系统需要补齐页面映射或调入内容的情况。如果访问的文件页尚未在内存中，操作系统还要读取存储设备，当前的 `get()` 就需要等待。因此，映射减少了中间复制，却不会消除冷数据的读取延迟；等待只是发生在内存访问时。

### 4.1 内存映射的适用场景 {#内存映射的适用场景}

内存映射适合按位置访问文件，以及反复访问已经读进内存的文件页，比如：

- 需要随机读取大文件中的不同区域。
- 多个进程需要读取同一份文件页。
- 索引、日志或数据文件采用固定布局，可以按偏移找到内容。
- 希望减少用户态复制，并让操作系统管理页面换入换出。

只是顺序读一个小文件的话，缓冲流或 `FileChannel.read` 更简单，也更容易控制资源释放。

### 4.2 内存映射的边界 {#内存映射的限制}

映射省掉了复制，代价是程序要承担页面管理和文件共享的成本：

- 映射占用进程的虚拟地址空间，也需要页表记录地址对应关系。映射区域越大，这些管理成本越需要关注。
- 首次访问冷页会等待缺页处理，因此单次访问延迟会升高。
- 大范围随机访问会反复换入文件页，把其他常用数据挤出缓存，造成缓存抖动。
- 映射有独立的生命周期，关闭文件通道后仍然保留。长期使用大量映射时，需要管理它们的引用和占用。
- 文件被其他进程截断或并发修改时，需要约定读写顺序和一致性协议。

写入方面，`READ_WRITE` 模式的映射，修改会写回文件，但写回时机由操作系统决定。对本地文件调用 `force()`，可以保证它返回前修改已经写入存储设备；网络文件系统等非本地存储没有同样的保证。

`PRIVATE` 模式是**写时复制**：修改某一页时，操作系统先为这个进程复制一份私有的页，修改只发生在副本上，不会写回文件，`force()` 对它也没有效果。另外，`force()` 只保证写回，不保证多处修改要么都成功、要么都不成功，这需要应用自己设计协议（见[常见问题](#写回与事务语义)）。

## 5. 直接 ByteBuffer {#直接-bytebuffer}

**直接缓冲区**是数据位于 Java 堆之外的 `ByteBuffer`，操作系统做 I/O 时可以直接使用这块内存。下面分配一个 64 KiB 的直接缓冲区：

```java
ByteBuffer direct = ByteBuffer.allocateDirect(64 * 1024);

System.out.println(direct.isDirect()); // true
```

`isDirect()` 返回 `true`，说明这是直接缓冲区。操作系统执行 I/O 时需要稳定的内存区域，而 GC 可能移动堆对象。HotSpot 用堆缓冲区进行通道写入时，会先复制到临时直接缓冲区；读取时则先读进临时直接缓冲区，再复制回堆。直接使用可复用的直接缓冲区，可以省去堆缓冲区与临时缓冲区之间的复制。

堆外数据仍通过 Java `ByteBuffer` 对象访问。相关对象不再能由程序通过有效引用访问时，称为**不可达**。在 HotSpot 中，自动分配的本地内存还要等 GC 清理机制处理后才能释放，所以不再使用缓冲区，并不代表内存已经归还。

### 5.1 直接内存的代价 {#直接内存的代价}

直接内存只减少 I/O 的中间复制，分配和使用本身都有代价：

- 分配与释放涉及本地内存管理，通常比普通堆缓冲区更贵。因此，它更适合分配后长期复用。
- 数据不计入普通 Java 堆占用，但仍占用进程内存，并受 JVM 直接内存上限约束。
- 大量短命缓冲区会在清理完成前积压，持续占用直接内存额度。
- 纯 Java 代码随机调用 `get`、`put` 时，没有本地 I/O 中间复制可省，性能需要与堆数组实测比较。
- 直接内存额度耗尽时，即使 Java 堆还有空间，也会发生 `OutOfMemoryError`。

因此，排查这类 OOM 时，不能只看 Java 堆是否还有空间。复用直接缓冲区可以降低分配频率，但缓冲池本身也要限制容量，并约定用完后如何归还；一直借出不还，同样会耗尽池中的资源。

## 6. 三种机制的比较 {#三种机制的比较}

三种机制优化的是不同环节，最简单的区分方法是看数据需不需要经过应用处理：

| 机制 | 主要目标 | 数据是否进入 Java 堆 | 适合场景 | 主要风险 |
| --- | --- | --- | --- | --- |
| `transferTo` / `transferFrom` | 在通道间直接传输 | 可省去应用堆副本 | 文件原样发送 | 平台差异、部分传输 |
| `MappedByteBuffer` | 将文件页映射到地址空间 | 不需要普通堆数组副本 | 大文件随机访问、固定布局 | 缺页延迟、映射生命周期 |
| 直接 `ByteBuffer` | 为本地 I/O 提供直接数据区域 | 数据在堆外 | 高频网络或文件 I/O 缓冲 | 分配成本、堆外 OOM |

文件原样发送，用通道传输；按位置访问文件，考虑映射；应用要处理字节、又有大量 I/O，考虑复用直接缓冲区。它们可以组合使用。不管选哪个，都要结合数据量和生命周期，确认省下的复制成本确实超过了新增的管理成本。

## 7. 性能验证指标 {#验证收益}

验证零拷贝的效果，要同时确认两件事：复制确实减少了，内存和延迟也没有因此变差。只看平均耗时不够，还要观察：

- 比较吞吐量与尾延迟，也就是单位时间完成的工作量和最慢一部分请求的耗时。
- 记录 CPU 使用率和系统调用次数，判断数据搬运与跨内核调用是否减少。
- 记录上下文切换与缺页次数，判断等待和页面换入是否增加。
- 分别记录 Java 堆、直接内存和进程 RSS。RSS 表示进程当前驻留在物理内存中的页面总量。
- 记录 GC 停顿和缓冲区分配速率，判断缓冲复用是否减少了分配压力。
- 检查文件页缓存是否挤出了其他常用数据，导致系统其他部分变慢。

测试的数据量和访问方式要接近真实负载，并分别测量冷缓存与热缓存：前者需要从存储设备读取文件页，后者已经有可用的内存缓存。各方案的 JIT 预热程度也应一致，避免把缓存和编译状态的差异误当成机制本身的收益。

## 8. 映射大小与释放时机 {#映射大小与释放时机}

处理大文件时，要分别管两件事：每段映射多大，以及它活多久。

先说大小。返回 `MappedByteBuffer` 的 `map` 重载最多映射 `Integer.MAX_VALUE` 字节，也就是约 2 GB，因为 `ByteBuffer` 的下标是 `int`。更大的文件要分成多段，分别映射。

再说释放。关闭 `FileChannel` 并不会解除映射，已有的 `MappedByteBuffer` 还能继续读写。Java 17、21 的 `MappedByteBuffer` 没有公开的 `close()` 方法，解除映射要等 GC：映射对象和从它创建的所有视图（比如 `slice()` 出来的缓冲区）都不可达、并被回收之后，映射才会解除。因此不能通过关闭通道控制映射释放时间。

在 Windows 等环境中，尚未解除的映射还可能妨碍文件删除或替换，文件轮换流程要考虑这一点。

还要注意统计口径。HotSpot 的 `-XX:MaxDirectMemorySize` 只限制直接缓冲区的分配，文件映射不计入这个额度。排查内存时，要分别看直接缓冲区（direct）、文件映射（mapped）和进程的 RSS，才知道内存到底被谁占了。

## 9. 常见问题 {#常见问题}

### 9.1 零拷贝真的完全没有数据复制吗？ {#设备传输与内存复制}

不是。数据仍需在设备与内存之间传输。**DMA** 是让设备直接访问内存的机制，可减少 CPU 逐字节搬运数据的工作，但传输的发起和管理仍有开销。零拷贝所说的减少复制，要落实到具体路径，例如省去文件内容从内核复制到应用缓冲区的那一步。

### 9.2 直接内存受垃圾回收影响吗？ {#直接内存与垃圾回收}

受影响。`allocateDirect` 分配的数据虽然在堆外，但 HotSpot 的自动释放依赖相关 Java 对象不可达并被清理。已经不用、尚未清理的缓冲区仍会占用额度，所以 Java 堆空闲不代表直接内存也充足。需要同时观察直接内存占用、分配速率和清理情况。

### 9.3 内存映射一定比 read 快吗？ {#映射与读取的成本}

不一定，取决于访问方式。映射省掉了显式的读调用和中间复制，但多了缺页、页表管理和映射生命周期的成本。小文件顺序读、一次性扫描，或者需要明确控制资源何时释放的场景，先用缓冲 I/O，有疑问再测量比较。

### 9.4 `force()` 等于事务提交吗？ {#写回与事务语义}

不等于。对本地文件的读写映射，`MappedByteBuffer.force()` 保证相关修改写回存储设备，但不提供事务原子性。假设一次业务更新要修改两处，程序可能在写完第一处后就崩溃；已经写回的部分不会自动撤销。多处更新或多个文件之间的一致性，需要应用用写入顺序、预写日志、校验和或临时文件替换等协议保证。

<summary>参考回答</summary>

**Java 可以用通道传输或内存映射减少文件 I/O 中的中间复制。**

</details>

### 10.2 直接内存有什么收益和风险 {#direct-memory-tradeoffs}

**考察重点**

- 解释直接缓冲区怎样减少本地 I/O 的中间复制。
- 说明堆外数据何时能够释放，以及 Java Buffer 对象的引用如何影响它。
- 比较分配成本、内存上限与缓冲池复用带来的收益。

**相关内容**：[直接 ByteBuffer](#直接-bytebuffer)。

<details>
<summary>参考回答</summary>

**直接缓冲区可以减少本地 I/O 的中间复制，代价是分配释放更贵，还要单独管理堆外内存。**

HotSpot 用堆缓冲区做通道 I/O 时，需要临时直接缓冲区：写入前把堆内数据复制进去，读取后再把数据复制回堆。直接缓冲区可以省去这一步中间复制，因此适合评估长期复用的网络和文件 I/O 场景。

风险有三点。一是分配和释放比堆缓冲区贵，频繁创建短命的直接缓冲区得不偿失。二是释放要等堆上的 `ByteBuffer` 对象不可达、被 GC 处理，短命缓冲区会在清理前积压。三是直接内存受 `-XX:MaxDirectMemorySize` 等上限约束，耗尽时即使堆还有空闲也会 OOM。缓冲池可以降低分配频率，但池也要限制容量并管理归还。

</details>

**关闭 `FileChannel` 后，已有映射仍然有效，大文件则需要按单段大小上限分段映射。**

返回 `MappedByteBuffer` 的 `map` 重载最多映射 `Integer.MAX_VALUE` 字节（约 2 GB），更大的文件要分成多段映射。

映射的生命周期和通道是分开的。Java 17、21 的 `MappedByteBuffer` 没有公开的 `close()`，解除映射依赖 GC：只有映射对象和从它创建的视图都不再被引用、并被回收以后，映射才会解除。所以关闭通道的时间和映射释放的时间要分别管理。

</details>
