# Java 序列化

Java 原生序列化把对象图写入字节流并恢复对象。本文负责字段、构造规则、版本兼容和输入过滤。流的资源关闭见 [Java 异常](../language/exceptions-error-boundaries.mdx#try-with-resources-与资源关闭)。

## 1. 面试核心 {#core}

- 默认序列化保存实例字段，排除 `static` 与 `transient`。[卡](#serialization-uid)
- 普通可序列化类恢复时跳过自身构造器。
- 普通类的 `serialVersionUID` 不匹配时抛出 `InvalidClassException`。
- `ObjectInputFilter` 可限制类型、深度、引用数和数组长度。[卡](#untrusted-deserialization)
- 同一对象流通过句柄复用已写出的对象。[卡](#serialization-handles)

## 2. Serializable {#serializable}

类实现标记接口 `Serializable` 后，可以交给 `ObjectOutputStream`：

```java
public final class UserProfile implements Serializable {
    @Serial
    private static final long serialVersionUID = 1L;

    private final long userId;
    private final String displayName;

    public UserProfile(long userId, String displayName) {
        this.userId = userId;
        this.displayName = displayName;
    }
}
```

写入对象：

```java
try (ObjectOutputStream output = new ObjectOutputStream(
    Files.newOutputStream(path)
)) {
    output.writeObject(profile);
}
```

读取对象：

```java
try (ObjectInputStream input = new ObjectInputStream(
    Files.newInputStream(path)
)) {
    UserProfile profile = (UserProfile) input.readObject();
}
```

默认序列化沿引用关系处理对象图。非瞬态字段指向不可序列化对象时，会抛出 `NotSerializableException`。

### 2.1 默认序列化的字段范围 {#不参与默认序列化的字段}

- `static` 字段属于类，不属于单个对象状态。
- `transient` 字段被默认序列化机制忽略。

```java
private transient String accessToken;
```

`transient` 可以避免写入临时缓存、文件句柄或敏感派生值，但不是完整安全策略。其他字段、嵌套对象和自定义写入方法仍可能泄漏信息。

### 2.2 反序列化与构造方法 {#反序列化与构造方法}

普通 `Serializable` 类恢复时，跳过自身构造器和字段初始化。第一个不可序列化父类的可访问无参构造器会执行。随后恢复序列化字段。

因此不能只依赖可序列化类构造器维护不变量。读取外部数据时，还需要在反序列化钩子中校验状态。

## 3. serialVersionUID {#serialversionuid}

普通可序列化类反序列化时，会比较流与本地类的版本标识。不匹配会抛出 `InvalidClassException`。record 和枚举另有专门规则。

```java
@Serial
private static final long serialVersionUID = 1L;
```

未显式声明时，运行时按类结构计算默认 UID。结构变化会改变结果。需要兼容旧数据时应显式声明，并验证演进规则。

### 3.1 UID 与语义兼容 {#uid-与语义兼容}

`serialVersionUID` 只通过一个标识控制是否尝试反序列化，不会自动迁移业务语义：

- 原始类型字段改变类型属于不兼容变化。
- 新增字段读取旧流时得到默认值，业务需校验该值。
- 删除字段会丢失旧数据中的信息。
- 类层次与自定义钩子的变化也需检查兼容性。

保持 UID 不变，意味着开发者承诺新类能够合理读取旧数据。做不到时应改变 UID 并明确拒绝，或者提供独立迁移工具。

### 3.2 长期数据的模式版本 {#长期数据的模式版本}

长期数据需要独立的字段兼容、版本迁移和跨语言规则。`serialVersionUID` 只解决其中的类版本匹配。

JSON、Protocol Buffers、Avro 可将传输模式与 Java 实现分开。协议应按兼容需求选择，并定义输入校验。

## 4. 自定义序列化 {#自定义序列化}

类可以声明特定签名的私有方法参与读写：

```java
@Serial
private void writeObject(ObjectOutputStream output) throws IOException {
    output.defaultWriteObject();
}

@Serial
private void readObject(ObjectInputStream input)
        throws IOException, ClassNotFoundException {
    input.defaultReadObject();

    if (userId <= 0 || displayName == null || displayName.isBlank()) {
        throw new InvalidObjectException("invalid user profile");
    }
}
```

`defaultReadObject` 恢复默认字段，后续校验防止构造器未执行时产生非法对象。

其他扩展点还包括：

- `writeReplace`：写入前替换对象。
- `readResolve`：读取后替换恢复结果，常用于保持单例或规范对象。
- `Externalizable`：由类完全控制读写格式和对象恢复流程。

这些钩子增加了兼容和安全复杂度。自定义协议应有明确的兼容或状态恢复需求。

## 5. 不可信输入风险 {#反序列化不可信数据}

`ObjectInputStream` 按类型信息恢复对象图，执行过程包括：

- `readObject`、`readResolve` 等自定义钩子。
- 集合重建过程中的比较、哈希和其他类型行为。
- 大数组、深层对象图和大量引用分配。
- classpath 中可被组合利用的危险调用链。

攻击者可组合 classpath 中现有类型触发危险行为。副作用能在业务字段校验之前发生。

:::danger 不要默认反序列化不可信 Java 对象流

网络、上传文件和外部可修改的数据都属于不可信输入。外部协议应只构造预期 DTO，并执行字段校验。必须使用原生流时，应先配置类型与规模限制。

:::

## 6. 反序列化过滤器 {#反序列化过滤器}

必须兼容原生流时，可用 `ObjectInputFilter` 检查类型与规模：

```java
try (ObjectInputStream input = new ObjectInputStream(source)) {
    ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
        "maxdepth=10;maxrefs=1000;maxarray=10000;maxbytes=1048576;"
            + "com.example.UserProfile;!*"
    );
    input.setObjectInputFilter(filter);

    UserProfile profile = (UserProfile) input.readObject();
}
```

过滤器可以限制：

- 允许或拒绝的类与包。
- 对象图最大深度。
- 引用数量。
- 数组长度。
- 输入字节数量。

类型允许列表应覆盖合法对象图，并测试历史版本。示例仅允许 `UserProfile`，字符串内容仍需业务校验。宽泛放行整个包会扩大可构造类型范围。

具体编码的字符串和基本值不会逐项触发过滤。`maxbytes` 在过滤回调时检查，并非输入流的硬字节上限。外层还需限制消息大小，字段内容由业务校验。

## 7. 适用范围 {#适用范围}

适用场景应同时满足：

- 写入方与读取方由同一应用和发布流程控制。
- 数据生命周期短，不需要多年兼容。
- 输入无法被不可信主体替换。
- 对象图类型范围小，并配置了过滤器。
- 性能、体积和跨语言不是主要约束。

常见的不适用场景：

- 对外 HTTP、RPC 或消息协议。
- 长期归档和数据库字段。
- 浏览器、移动端或其他语言需要读取的数据。
- 插件可任意扩展 classpath 的系统。
- 无法确认历史字节来源是否可信的缓存。

## 8. 对象句柄与特殊构造规则 {#对象句柄与特殊构造规则}

同一输出流首次写入对象时分配句柄。再次写入同一对象时写出句柄引用。对象在两次写入之间被修改，也不会自动重写状态。

```java
List<String> values = new ArrayList<>();
values.add("A");
output.writeObject(values);
values.add("B");
output.writeObject(values); // 引用首次写出的列表
output.reset();
output.writeObject(values); // 新快照包含 A、B
```

`reset()` 清除流中的对象记录。接收方前两次读取得到同一对象，第三次得到新快照。句柄机制也能表示循环引用。

`Externalizable` 恢复时调用公开无参构造器，再执行 `readExternal`。record 在 Java 16 成为正式特性。可序列化 record 恢复时调用规范构造器。其 `readObject` 等定制钩子被忽略，UID 匹配要求也被豁免。

枚举按名称恢复为已有枚举常量，其 UID 固定为 0。普通类、record 和枚举应分别讨论构造与兼容规则。

## 9. 常见问题 {#常见问题}

### 9.1 标记接口 {#标记接口}

`Serializable` 用类型关系启用对象序列化。实际读写由对象流和类的可选钩子完成。

### 9.2 对象图的恢复边界 {#对象图的恢复边界}

循环引用由句柄处理，对象图规模仍需限制。钩子执行失败或类演进不兼容，也会阻止恢复。可序列化资格只是机制入口。

### 9.3 瞬态字段的恢复值 {#瞬态字段的恢复值}

普通可序列化类的瞬态字段保留 Java 默认值。引用为 `null`，整数为 0。派生状态可在读取钩子或首次使用时重建。

### 9.4 类版本演进 {#类版本演进}

能够保持反序列化兼容并正确处理新增默认值时可以保持不变；旧数据无法被新类可靠解释时应改变并拒绝读取。改变前还要决定历史数据是迁移、清除还是由旧版本读取。

**考察重点**

<details>
<summary>参考回答</summary>

`ObjectOutputStream` 沿引用关系写出默认实例状态。`ObjectInputStream` 根据类信息恢复对象图。普通可序列化类会跳过自身构造器，因此还需校验不变量。

普通类的 UID 不匹配会抛出 `InvalidClassException`。显式声明可稳定版本标识。字段与业务语义的兼容性仍需单独验证。

</details>

### 10.2 为什么不应该反序列化不可信的 Java 对象流 {#untrusted-deserialization}

**出现公司**：奇安信

**考察重点**

- 反序列化为什么会执行类型相关逻辑。
- 对象图资源消耗和 gadget chain 风险。
- `ObjectInputFilter` 能限制什么，不能替代什么。

**相关内容**：[不可信输入风险](#反序列化不可信数据)、[反序列化过滤器](#反序列化过滤器)。

<details>
<summary>参考回答</summary>

对象流恢复会触发类型相关逻辑，并分配对象图。危险类型组合可引发副作用，过大对象图可耗尽资源。

外部协议应只构造预期 DTO，再校验字段。必须兼容原生流时，用 `ObjectInputFilter` 限制类型与规模。字段含义和授权仍由业务校验。

</details>

### 10.3 同一对象修改后再次 writeObject，为什么读不到新状态？ {#serialization-handles}

</details>
