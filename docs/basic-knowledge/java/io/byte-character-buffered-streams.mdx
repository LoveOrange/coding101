# Java 流式 I/O

字节流读写原始字节，字符流读写字符序列。本文负责编码转换、部分读取、缓冲与刷新。非阻塞通道见 [Java NIO](./buffer-channel-selector.mdx)。

## 1. 面试核心 {#core}

- `InputStream` 读字节，`Reader` 读字符，转换流负责字符集解码。[卡](#byte-vs-char-streams)
- `InputStreamReader` 和 `OutputStreamWriter` 连接字节与字符表示。
- `read(byte[])` 返回实际读取量，-1 表示结束。[卡](#read-return-value)
- 缓冲流聚合小读写，减少底层调用。
- `flush` 推送缓冲数据，文件持久化由 `force` 等机制处理。

## 2. 字节流 {#字节流}

`InputStream` 和 `OutputStream` 是阻塞式字节流的基础抽象。图片、压缩包、加密数据和未知格式文件都应按字节处理：

```java
Path source = Path.of("avatar.png");
Path target = Path.of("avatar-copy.png");

try (
    InputStream input = Files.newInputStream(source);
    OutputStream output = Files.newOutputStream(target)
) {
    input.transferTo(output);
}
```

字节流不解释内容。值 `0x41` 是字符 `A`、图片数据还是压缩格式的一部分，由上层协议决定。

### 2.1 部分读取 {#部分读取}

一次 `read(byte[])` 不保证填满整个数组，只返回本次实际读取的字节数。返回 `-1` 表示到达流末尾：

```java
byte[] buffer = new byte[8192];
int count;

while ((count = input.read(buffer)) != -1) {
    output.write(buffer, 0, count);
}
```

最后一块可只占数组的一部分。写出时使用实际 `count`，否则会带出未覆盖的旧数据。

`available()` 只表示当前无需阻塞即可读取的估计字节数，不是整个流的总长度。网络输入尤其不能用它判断消息是否已经完整到达。

## 3. 字符流 {#字符流}

`Reader` 和 `Writer` 处理字符序列。连接字节源时，由转换流执行字符集编解码：

```java
Path path = Path.of("article.md");

try (BufferedReader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    String firstLine = reader.readLine();
    System.out.println(firstLine);
}
```

写出时同样指定编码：

```java
try (BufferedWriter writer = Files.newBufferedWriter(path, StandardCharsets.UTF_8)) {
    writer.write("欢迎来到 Coding 101");
    writer.newLine();
}
```

如果读写两端使用不同字符集，同一组字节会被解释成错误字符。协议、文件格式和数据库连接都应明确字符集，不依赖进程默认值。

### 3.1 InputStreamReader 与 OutputStreamWriter {#inputstreamreader-与-outputstreamwriter}

已有字节流时，可以显式增加解码层：

```java
Reader reader = new InputStreamReader(
    socket.getInputStream(),
    StandardCharsets.UTF_8
);
```

反向写出使用 `OutputStreamWriter`：

```java
Writer writer = new OutputStreamWriter(
    socket.getOutputStream(),
    StandardCharsets.UTF_8
);
```

字符与字节之间需要字符集。已解码的字符若需重新输出字节，应按目标字符集编码。

### 3.2 char 与用户可见字符 {#char-与用户可见字符}

Java 字符流以 UTF-16 代码单元工作。码点与用户可见字符的区别见 [String](../language/string-immutability-pool.mdx#字符串存储与字符计数)。

## 4. 缓冲流 {#缓冲流}

逐字节读写会增加方法调用。底层直接访问设备时，还会增加 I/O 次数。缓冲流一次读取较大数据块放入内存，再满足后续小读取：

```java
try (
    InputStream input = new BufferedInputStream(Files.newInputStream(source));
    OutputStream output = new BufferedOutputStream(Files.newOutputStream(target))
) {
    input.transferTo(output);
}
```

字符缓冲还提供 `readLine()` 和 `newLine()` 等按文本组织的操作。

缓冲聚合小调用，减少底层往返。`Files.copy`、`transferTo` 等 API 已能按块处理。额外包装的收益需按实际调用方式验证。

### 4.1 缓冲区大小 {#缓冲区大小}

扩大缓冲可减少调用次数，也会增加常驻内存。连接数较多时，单连接容量会放大总占用。

先使用默认容量。确认调用粒度是瓶颈后，再按数据量、并发数和延迟调整。

## 5. 装饰器组合 {#装饰器组合}

Java I/O 经常通过包装组合能力：

```java
try (
    InputStream file = Files.newInputStream(Path.of("data.gz"));
    InputStream buffered = new BufferedInputStream(file);
    InputStream decompressed = new GZIPInputStream(buffered);
    Reader decoded = new InputStreamReader(decompressed, StandardCharsets.UTF_8);
    BufferedReader lines = new BufferedReader(decoded)
) {
    lines.lines().forEach(System.out::println);
}
```

数据依次经过文件读取、缓冲、解压和 UTF-8 解码，最后按行消费。每一层只负责一种转换。

包装顺序应匹配文件格式。写入时先编码再压缩，读取时先解压再解码。例中关闭最外层流会沿包装链关闭底层流。

## 6. flush 与持久化 {#flush-与持久化}

`flush()` 要求把 Java 层已经缓冲的输出继续交给底层流：

```java
writer.write("event\n");
writer.flush();
```

它常用于长连接协议，需要在不关闭连接的情况下及时发送一批数据。`BufferedWriter.close()` 会先刷新，再关闭底层流。

`flush` 推送 Java 缓冲，底层系统仍可缓存数据。文件持久化使用 `FileChannel.force` 等机制。映射写回边界见 [零拷贝](./file-mapping-zero-copy-direct-memory.mdx#内存映射)。

频繁刷新会削弱缓冲效果。刷新时机应由消息边界、交互延迟或持久化协议确定。

## 7. API 选择 {#api-选择}

1. **二进制数据**：使用 `InputStream`、`OutputStream` 或字节 `Channel`。
2. **文本数据**：使用 `Reader`、`Writer` 或 `Files` 的带字符集方法。
3. **大量小读写**：使用缓冲或显式块读取。
4. **一次性文件复制**：优先查看 `Files.copy`、`InputStream.transferTo` 或 `FileChannel.transferTo`。
5. **随机访问、内存映射或多路复用**：进入 NIO 的 `Channel`、`Buffer` 和 `Selector` 模型。

不要因为字符流 API 更方便，就用它复制任意文件。二进制内容经过错误解码再编码，字节序列会被破坏。

## 8. 跨块解码与错误处理 {#跨块解码与错误处理}

UTF-8 字符可占多个字节，一次读取可截断字符。每块直接 `new String(bytes, UTF_8)` 会丢失跨块解码状态。`InputStreamReader` 会保留未完成的字节序列。

需要拒绝损坏文本时，显式配置解码器：

```java
CharsetDecoder decoder = StandardCharsets.UTF_8.newDecoder()
    .onMalformedInput(CodingErrorAction.REPORT)
    .onUnmappableCharacter(CodingErrorAction.REPORT);
try (Reader reader = new InputStreamReader(input, decoder)) {
    char[] chars = new char[1024];
    int count;
    while ((count = reader.read(chars)) != -1) {
        consume(chars, 0, count); // 只处理本次字符；格式损坏时读取抛异常。
    }
}
```

Java 17 的默认字符集取决于运行环境。Java 21 默认使用 UTF-8，允许兼容配置。协议仍应显式写出字符集。`DataInputStream.readFully` 适合读取固定长度字段。不足指定长度即遇 EOF 时，它抛出 `EOFException`。

## 9. 常见问题 {#常见问题}

### 9.1 字符流的成本 {#字符流的成本}

字符流增加编解码工作，性能取决于字符集、缓冲及设备。文本按字符处理，二进制内容按字节保留。

### 9.2 单字节读取的返回类型 {#单字节读取的返回类型}

它需要同时表示 `0` 到 `255` 的所有字节值和流末尾 `-1`。如果返回 `byte`，`-1` 会与合法的 `0xFF` 无法区分。

### 9.3 行内容与终止符 {#行内容与终止符}

`readLine()` 返回内容并移除行终止符。原文件可混用不同换行形式。需要保留原字节时，采用字节复制。

### 9.4 默认字符集 {#默认字符集}

默认字符集仅适合明确依赖环境的输入。跨机器文件与网络协议应显式使用约定字符集，例如 UTF-8。

### 10.1 字节流和字符流有什么区别，怎样选择 {#byte-vs-char-streams}

**出现公司**：饿了么、网易、美团、金山云

**考察重点**

- 字节数据与文本字符之间是否需要编解码。
- `InputStreamReader` 和 `OutputStreamWriter` 的作用。
- 缓冲解决了什么调用粒度问题。

**相关内容**：[字节流](#字节流)、[字符流](#字符流)、[缓冲流](#缓冲流)。

<details>
<summary>参考回答</summary>

字节流读写原始字节，适合图片、压缩包和任意二进制协议。字符流在底层字节流上增加字符集编解码，适合文本；`InputStreamReader` 和 `OutputStreamWriter` 就是两种表示之间的转换边界。

字符流还需编解码，速度应按具体路径比较。大量小读写可增加缓冲。文本需先确定字符集，再评估调用粒度。

</details>

### 10.2 读取流时为什么必须使用 read 的返回值 {#read-return-value}

<!-- 面试来源：
- 美团：https://www.nowcoder.com/discuss/353156832904552448
-->

**出现公司**：美团

**考察重点**

- 一次读取为什么不保证填满缓冲区。
- `-1` 与有效字节值怎样区分。
- 最后一个数据块怎样避免写入旧内容。

**相关内容**：[部分读取](#部分读取)。

<details>
<summary>参考回答</summary>

`read(byte[])` 返回本次实际读到的字节数，不保证填满数组，返回 `-1` 才表示流结束。最后一次读取常常只有部分数据，因此写出时必须使用 `write(buffer, 0, count)`。

总写完整数组会带出本次未覆盖的旧数据。结果就会重复或损坏。

</details>

### 10.3 为什么不能把每次 read 的字节块分别转成 UTF-8 字符串？ {#incremental-decoding}
