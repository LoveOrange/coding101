# Java 流式 I/O

Java 流式 I/O 分两类：**字节流**读写原始字节，用于图片、压缩包这类二进制数据；**字符流**读写字符，用于文本。文件、Socket 在底层传的都是字节，字符流是在字节流之上，按某个字符集把字节解码成字符、把字符编码成字节。

选择流时，先判断要原样保留字节，还是要解释文本。用字符流复制图片可能破坏原始字节，读写两端字符集不一致则可能产生乱码。读写循环还要处理三个边界：一次 `read` 未必读满，缓冲只减少特定调用的成本，`flush()` 也不等于数据已经持久化。

## 1. 面试核心 {#core}

- 字节流读写**原始字节**，适合二进制数据；字符流读写**字符序列**，适合文本，读写时都要明确字符集。[卡](#byte-vs-char-streams)
- `InputStreamReader` 按指定字符集**把字节解码为字符**，`OutputStreamWriter` 反过来**把字符编码为字节**。
- `read(byte[])` **返回本次实际读到的字节数**，可能少于数组长度，`-1` 才表示流结束；写出时只能写这么多。[卡](#read-return-value)
- 缓冲流把**多次小读写合并成大块操作**，减少对底层流和操作系统的调用次数。
- `flush()` 只是**把 Java 缓冲区里的数据交给底层流**，要保证落到磁盘，还需要 `FileChannel.force` 等机制。

## 2. 字节流 {#字节流}

字节流的两个基类是 `InputStream` 和 `OutputStream`，一个读字节，一个写字节，不对内容做任何解释。图片、压缩包、加密数据都必须原样保留每个字节，格式未知的文件也应该按字节处理。比如复制一张图片：

```java
Path source = Path.of("avatar.png");
Path target = Path.of("avatar-copy.png");

try (
    InputStream input = Files.newInputStream(source);
    OutputStream output = Files.newOutputStream(target)
) {
    input.transferTo(output);
}
```

`transferTo` 把输入流的字节原样搬到输出流，不解释内容。例如，`0x41` 在 UTF-8 文本里表示 `A`，在图片文件里却要按图片格式解释。字节流只保证搬运字节，具体含义由使用它的代码决定。

流打开后要关闭，否则会泄漏文件句柄。谁创建流（或明确接管了流），就由谁关闭，优先用 try-with-resources。关闭顺序和异常处理见 [Java 异常](../language/exceptions-error-boundaries.mdx#try-with-resources-与资源关闭)。

### 2.1 部分读取 {#部分读取}

`read(byte[])` 的返回值表示本次实际读到的字节数，不保证等于数组长度。数组非空时，读取会等待数据、流结束或异常；成功读取可能只填满数组的一部分，返回 `-1` 才表示流结束。读写循环因此要用返回值确定有效范围：

```java
byte[] buffer = new byte[8192];
int count;

while ((count = input.read(buffer)) != -1) {
    output.write(buffer, 0, count);
}
```

假设这一轮只读到 100 个字节，`count` 就是 100，只有 `buffer[0]` 到 `buffer[99]` 是本轮的数据。`write(buffer, 0, count)` 恰好写出这部分；若调用 `output.write(buffer)`，会把整个 8192 字节数组写出，未被本轮覆盖的旧内容也会混进结果。

读协议里固定长度的字段时，比如一个 4 字节的长度头，可以用 `DataInputStream.readFully`。它会一直读到填满指定长度为止，中途遇到流末尾就抛出 `EOFException`。

还有一个容易误用的方法是 `available()`，它返回的是「现在不阻塞就能读到的字节数」的估计值，不是流的总长度，也不能用来判断一条网络消息是否已经收全。消息到哪结束，要靠协议里的长度字段或结束标记。

## 3. 字符流 {#字符流}

字符流的两个基类是 `Reader` 和 `Writer`，读写的单位是字符。字符和字节之间怎样对应，由**字符集**决定，比如 UTF-8 里「欢」是三个字节 `E6 AC A2`。读取时把字节转换为字符叫**解码**，写入时把字符转换为字节叫**编码**。

下面的读取和写入都明确指定了 UTF-8：

```java
Path path = Path.of("article.md");

try (BufferedReader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    String firstLine = reader.readLine();
    System.out.println(firstLine);
}

try (BufferedWriter writer = Files.newBufferedWriter(path, StandardCharsets.UTF_8)) {
    writer.write("欢迎来到 Coding 101");
    writer.newLine();
}
```

第一段读取并打印首行；第二段重新打开同一路径写入，会覆盖原文件，再写入文本和换行符。这是两个读写用法的示例，并不是保留原文件内容的更新操作。

读写双方的字符集需要一致。例如，按 UTF-8 写入的「欢」若用 GBK 解码，就无法按原来的规则还原字符，可能出现乱码或解码错误。所以协议和文件格式应明确约定字符集。

### 3.1 InputStreamReader 与 OutputStreamWriter {#inputstreamreader-与-outputstreamwriter}

手里已经有一个字节流，比如 Socket 的输入输出流，又想按文本处理时，就用**转换流**把它包成字符流。`InputStreamReader` 负责解码，`OutputStreamWriter` 负责编码：

```java
Reader reader = new InputStreamReader(
    socket.getInputStream(),
    StandardCharsets.UTF_8
);

Writer writer = new OutputStreamWriter(
    socket.getOutputStream(),
    StandardCharsets.UTF_8
);
```

`reader` 把 Socket 收到的 UTF-8 字节解码成字符，`writer` 把写入的字符编码成 UTF-8 字节，再交给 Socket。注意 `Reader` 只交出解码后的字符，不保留原始字节；字符要重新变回字节，必须再选一次目标字符集。

### 3.2 char 与用户可见字符 {#char-与用户可见字符}

字符流读出来的 `char` 是一个 **UTF-16 代码单元**，也就是一个 16 位的编码值，并不总等于用户看到的一个字符。比如 emoji「😀」要用两个 `char`（一个代理对）表示。所以按字符计数或截断文本时，不能直接数 `char` 的个数。

码点、代理对和组合字符的区别见 [String](../language/string-immutability-pool.mdx#字符串存储与字符计数)。

## 4. 缓冲流 {#缓冲流}

**缓冲流**在内存里放一块缓冲区，把很多次小读写合并成少数几次大块读写。没有缓冲时，每次 `read()` 读一个字节，`FileInputStream` 就要发起一次系统调用；读一个 1 MB 的文件就是约一百万次。加了缓冲以后，读取时一次从底层读一大块（`BufferedInputStream` 默认 8192 字节），后续的小读取直接从内存里拿；写入时先在内存里攒着，攒满了再一次交给底层流：

```java
try (
    InputStream input = new BufferedInputStream(Files.newInputStream(source));
    OutputStream output = new BufferedOutputStream(Files.newOutputStream(target))
) {
    input.transferTo(output);
}
```

这里用包装的方式给输入和输出都加了缓冲。字符流的 `BufferedReader`、`BufferedWriter` 是同样的思路，还额外提供了 `readLine()`、`newLine()` 这类按行处理的方法。

如果代码已经按大块读写，再包装缓冲流未必能进一步减少底层调用。`transferTo` 和 `Files.copy` 的具体路径还取决于流实现与平台，不能只凭「多包一层」判断更快。应先看原来的读写粒度，再测量是否需要缓冲。

### 4.1 缓冲区大小 {#缓冲区大小}

增大缓冲区可能减少底层调用，也会增加每个流占用的内存。并发连接多时，单个缓冲区的小幅增长也会累积：每个连接多用 64 KB，一万个连接就多用约 640 MB。调用次数能否继续减少，还取决于每次实际读写多少数据。

所以先用默认大小。性能分析确认小粒度 I/O 是瓶颈之后，再结合数据量、并发连接数和延迟要求调整。

## 5. 装饰器组合 {#装饰器组合}

**装饰器模式**是在保留原接口的前提下，用包装对象增加能力。`BufferedInputStream` 包装一个 `InputStream`，对调用方仍是 `InputStream`，但增加了缓冲。转换流则负责衔接字节与字符这两种接口。把它们组合起来，就能完成缓冲、解压、解码和按行读取：

```java
try (
    InputStream file = Files.newInputStream(Path.of("data.gz"));
    InputStream buffered = new BufferedInputStream(file);
    InputStream decompressed = new GZIPInputStream(buffered);
    Reader decoded = new InputStreamReader(decompressed, StandardCharsets.UTF_8);
    BufferedReader lines = new BufferedReader(decoded)
) {
    lines.lines().forEach(System.out::println);
}
```

读取时，调用从外层向内层请求数据，数据处理结果再逐层向外返回：`file` 提供压缩字节，`buffered` 缓冲这些字节，`decompressed` 解压出 UTF-8 字节，`decoded` 解码为字符，最后由 `lines` 按行交给调用方。每层的输入输出类型必须与相邻层对应。

还原数据时，要反过来撤销写入时的转换。这个文件先将文本编码成 UTF-8 字节、再压缩，读取就要先解压、再解码。若直接解码压缩字节，得到的不会是原文，还可能发生解码错误。

关闭也要注意。这些包装类关闭时会顺带关闭被包装的流，所以只关最外层也能释放文件。本例把每一层都声明成资源，好处是如果某一层的构造方法抛出异常（比如文件不是合法的 gzip 格式，`GZIPInputStream` 构造时就会报错），已经打开的内层流仍会被关闭。换用其他包装类时，要看它的文档，确认关闭时会不会关闭底层流。

## 6. flush 与持久化 {#flush-与持久化}

`flush()` 要求输出流把已缓冲的数据交给下层。使用输出缓冲时，`write` 返回并不代表数据已经离开 Java 缓冲区；需要及时提交这一批数据时，可以显式刷新：

```java
writer.write("event\n");
writer.flush();
```

写完事件后刷新，可以避免它继续滞留在 Java 缓冲区，但不保证对方立即收到或处理完。连接可以保持打开，下一条消息继续写入。`BufferedWriter.close()` 也会尝试刷新缓冲内容；关闭过程若发生 I/O 错误，仍需处理异常。没有刷新或关闭就异常退出，尚在 Java 缓冲区中的数据可能丢失。

`flush()` 不提供磁盘持久化保证。写文件时，数据可能只是进入操作系统的页缓存，尚未写到存储设备。需要崩溃后仍能恢复数据时，要使用 `FileChannel.force` 等写回机制，并确认文件系统和硬件提供的保证。

映射文件的写回范围见 [零拷贝](./file-mapping-zero-copy-direct-memory.mdx#内存映射)。

每次刷新都会提前结束当前这一批，刷得越勤，缓冲省下的调用就越少。什么时候刷新，应该由消息边界、交互延迟要求或持久化协议决定，而不是每写一次就刷一次。

## 7. API 选择 {#api-选择}

选 API 先看数据是文本还是二进制，再看读写方式：

1. **二进制数据**：使用 `InputStream`、`OutputStream` 或字节 `Channel`。
2. **文本数据**：使用 `Reader`、`Writer` 或 `Files` 的带字符集方法。
3. **大量小读写**：使用缓冲或显式块读取。
4. **一次性文件复制**：优先查看 `Files.copy`、`InputStream.transferTo` 或 `FileChannel.transferTo`。
5. **随机访问、内存映射或多路复用**：进入 NIO 的 `Channel`、`Buffer` 和 `Selector` 模型。

二进制文件必须按字节复制，因为解码再编码未必能还原原始字节。例如，图片中出现了不合法的 UTF-8 字节序列，而解码器采用替换策略时，会生成替换字符 U+FFFD；重新编码成 UTF-8 后，得到的是 `EF BF BD`，原始字节已经丢失。采用报错策略则会中断读取，同样无法完成原样复制。

## 8. 跨块解码与错误处理 {#跨块解码与错误处理}

分块读取文本时，解码状态必须跨读取保留，因为字节块的边界未必是字符的边界。例如，「欢」在 UTF-8 中是三个字节 `E6 AC A2`。一次 `read` 只得到 `E6 AC` 时，单独用 `new String(bytes, UTF_8)` 解码，会把残缺序列替换掉；下一块开头的 `A2` 也无法独立还原这个字。

`InputStreamReader` 会保留还没有拼完整的字节，等后续读取补齐后再解码。因此它能处理跨块字符，不要求每次 `read` 都恰好停在字符末尾。

输入本身损坏时，处理方式取决于所用 API 和错误策略。`new String(byte[], Charset)` 会替换错误输入，而新建的 `CharsetDecoder` 默认采用 `REPORT`，报告错误。下面显式写出两类错误的策略：格式错误（malformed）和无法映射（unmappable）都拒绝继续解码。

```java
CharsetDecoder decoder = StandardCharsets.UTF_8.newDecoder()
    .onMalformedInput(CodingErrorAction.REPORT)
    .onUnmappableCharacter(CodingErrorAction.REPORT);
try (Reader reader = new InputStreamReader(input, decoder)) {
    char[] chars = new char[1024];
    int count;
    while ((count = reader.read(chars)) != -1) {
        consume(chars, 0, count); // 只处理本次字符；格式损坏时读取抛异常。
    }
}
```

和字节读取一样，这里也只把本次读到的 `count` 个字符交给 `consume`。遇到损坏的文本，`read` 会抛出 `MalformedInputException`（`IOException` 的子类），调用方就能拒绝这份输入，而不是带着替换字符继续处理。

默认字符集还受 JDK 版本和运行环境影响。Java 17 的默认值取决于操作系统和区域设置；Java 21 默认使用 UTF-8，但可以通过 `-Dfile.encoding=COMPAT` 采用兼容旧环境的选择方式。API 若使用平台默认字符集，同一份代码换环境后就可能得到不同结果，所以协议和文件格式应显式指定字符集。

## 9. 常见问题 {#常见问题}

### 9.1 字符流一定比字节流快吗？ {#字符流的成本}

不一定，字符流在字节流的基础上还多了编解码这一步。实际快慢取决于字符集、缓冲方式、数据量和底层设备。选择时先看数据是不是文本，性能问题再按实际读写方式测量。

### 9.2 为什么 `InputStream.read()` 返回 int？ {#单字节读取的返回类型}

因为它要同时表示 256 种字节值和一个结束标记。`int` 返回 `0` 到 `255` 表示读到的字节，`-1` 表示流结束。如果返回 `byte`，它的取值范围是 `-128` 到 `127`，合法字节 `0xFF` 正好就是 `-1`，和结束标记分不开。所以拿到返回值后，要先判断是否为 `-1`，再转成 `byte`。

### 9.3 `readLine()` 会保留换行符吗？ {#行内容与终止符}

不会，`readLine()` 返回的内容去掉了行终止符，而且 `\n`、`\r\n`、`\r` 都当作行终止符。原文件用的是哪种换行、是否混用，读完以后就不知道了；再用 `newLine()` 统一补回去，换行字节可能就变了，文件末尾有没有换行也可能变。需要原样保留文件时，用字节复制。

### 9.4 什么时候可以使用默认字符集？ {#默认字符集}

只有数据格式明确约定跟随运行环境，而且读写双方对该默认值的理解一致时，才适合使用。跨机器传输的文件、网络协议和长期保存的文本，应按格式指定字符集。控制台也要按它自身的编码约定处理，不能直接假定与平台默认字符集相同。

## 10. 面试题 {#面试题}

### 10.1 字节流和字符流有什么区别，怎样选择 {#byte-vs-char-streams}

**考察重点**

- 说明字节和字符的区别，并判断数据是否需要编解码。
- 解释 `InputStreamReader` 和 `OutputStreamWriter` 各自转换的方向。
- 说明缓冲怎样合并小读写，以及它为什么能减少底层调用。

**相关内容**：[字节流](#字节流)、[字符流](#字符流)、[缓冲流](#缓冲流)。

<details>
<summary>参考回答</summary>

**字节流处理原始字节，适合二进制数据，字符流处理字符序列，适合文本。**

图片和压缩包必须原样保留每个字节，用字节流；文本要按约定的字符集解码或编码，用字符流。两者之间靠转换流衔接：`InputStreamReader` 把字节解码为字符，`OutputStreamWriter` 把字符编码为字节，所以使用文本 API 时要明确字符集。用字符流处理二进制数据，可能因非法编码而报错，也可能因替换字节而损坏文件。

选择时先按数据的含义选流，再按读写粒度决定要不要缓冲。大量小读写包一层缓冲流，可以合并成块操作，减少底层调用。

</details>

### 10.2 读取流时为什么必须使用 read 的返回值 {#read-return-value}

**考察重点**

- 解释一次读取为什么可以只填充数组的一部分。
- 区分 `read(byte[])` 返回的数量与 `read()` 返回的单字节值。
- 说明如何识别流末尾，并避免把上次残留的数据写出去。

**相关内容**：[部分读取](#部分读取)。

<details>
<summary>参考回答</summary>

**`read(byte[])` 的返回值决定本次有效数据的范围，因此写出时必须使用它。**

一次读取可以只填充数组的一部分，返回 `-1` 才表示流结束。比如，最后一块少于数组容量时，写入应使用 `write(buffer, 0, count)`。如果总是写完整数组，本次未覆盖的区域就会带出旧数据，造成输出重复或损坏。

</details>

### 10.3 为什么不能把每次 read 的字节块分别转成 UTF-8 字符串？ {#incremental-decoding}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释字节块为何会截断字符，以及解码器怎样保留剩余字节和处理损坏输入。

**相关内容**：[跨块解码与错误处理](#跨块解码与错误处理)。

<details>
<summary>参考回答</summary>

**一次读取可以截断一个 UTF-8 多字节字符，所以每块独立解码会把残缺字节当作错误输入。**

例如，「欢」的 UTF-8 字节是 `E6 AC A2`。一次读取只拿到前两个字节，直接构造字符串会替换掉残缺序列；下一块的 `A2` 也无法单独恢复这个字，原文因此被改变。`InputStreamReader` 这样的转换流会保留还没拼完的字节序列，等下一块到达后继续解码，读取边界就不必和字符边界对齐。

需要拒绝真正损坏的输入时，使用 `CharsetDecoder` 的 `CodingErrorAction.REPORT` 策略，让读取报告异常；不能依赖会自动替换错误输入的字符串构造方法。

</details>
