# 并行流

并行流将数据拆分处理，再合并结果。本文负责拆分、调度、顺序和共享资源边界。归约契约见 [Collector](./collectors-grouping-reduction.mdx)。

## 1. 面试核心 {#core}

- `Spliterator.trySplit` 为并行计算划分数据范围。
- Fork/Join 通过工作窃取平衡待执行任务。[卡](#work-stealing)
- 有序并行流可保留结果顺序，但各元素计算仍可并发。
- OpenJDK 21 的公共池由多个任务来源共享。
- 阻塞 I/O、共享状态和调度成本会削弱并行流收益。[卡](#parallel-stream-checklist)

## 2. Spliterator 拆分 {#spliterator-拆分}

Stream 通过 `Spliterator` 遍历和拆分数据源。并行流水线会尝试调用 `trySplit()`，把一个数据范围分成更小的范围：

```text
[0 ................ 15]
         /                 \
[0 ...... 7]          [8 ...... 15]
   /       \             /        \
[0..3]   [4..7]       [8..11]   [12..15]
```

数组和 `ArrayList` 可按索引均匀拆分。链式结构和 I/O 来源的拆分更复杂。单项耗时不均也会降低负载均衡效果。

`Spliterator` 特征描述顺序、大小和元素互异性。实现据此选择拆分策略，数据源结构仍影响成本。

## 3. ForkJoinPool {#forkjoinpool}

OpenJDK 21 中，普通线程发起的并行流使用公共池。调用线程也可参与处理。Fork/Join 工作线程内启动的任务可使用所在池。Stream API 未提供指定执行器的参数。Fork/Join 流程如下：

1. 大任务递归拆成较小任务。
2. Worker 优先处理自己的任务队列。
3. 空闲 Worker 从其他队列窃取任务。
4. 子任务结果按终止操作的规则合并。

工作窃取平衡待执行任务。难以拆分的数据和长期阻塞仍会限制并行收益。

```java
long total = orders.parallelStream()
    .filter(Order::confirmed)
    .mapToLong(Order::amountInCents)
    .sum();
```

示例的过滤与金额计算应独立、无共享副作用。计算量需足以覆盖调度和合并成本，进程也需有可用 CPU。

## 4. 执行顺序 {#执行顺序}

有遇到顺序的数据源，不等于每个操作都按这个顺序执行：

```java
List.of(1, 2, 3, 4)
    .parallelStream()
    .forEach(System.out::println);
```

输出顺序不确定。`forEachOrdered` 可以按遇到顺序提交结果，但会增加协调并限制并行空间。

有序流的 `findFirst` 保留遇到顺序。`findAny` 可返回任意结果。业务无顺序要求时，可用 `unordered()` 放宽约束。

## 5. 外部可变状态 {#外部可变状态}

下面的代码不安全：

```java
List<String> names = new ArrayList<>();

users.parallelStream()
    .map(User::displayName)
    .forEach(names::add);
```

多个任务并发修改 `ArrayList`，可导致数据丢失或异常。同步列表会让写入竞争同一把锁。直接收集为列表可由框架管理结果：

```java
List<String> names = users.parallelStream()
    .map(User::displayName)
    .toList();
```

收集器可隔离分区结果，再合并。具体契约见 [Collector](./collectors-grouping-reduction.mdx#归约单位元与并发收集)。

Lambda 还应避免依赖：

- 请求线程中的 `ThreadLocal` 上下文。
- 绑定当前线程的事务或安全上下文。
- 非线程安全客户端和格式化器。
- 需要严格调用顺序的外部系统。

任务可由调用线程或 Worker 执行，线程本地状态不会自动传播。

## 6. 阻塞 I/O {#阻塞-io}

```java
List<Profile> profiles = userIds.parallelStream()
    .map(profileClient::load)
    .toList();
```

`load` 阻塞时会占用 Worker。其他公共池任务因此需要等待。请求量增大后，资源竞争会放大尾延迟。

需要并发 I/O 时，应该显式控制：

- 最大并发数。
- 连接池容量。
- 每次调用与端到端超时。
- 取消和异常传播。
- 不同请求或业务的资源隔离。

并发 I/O 可使用虚拟线程、有界执行器或异步客户端。实现仍需显式限制并发、超时及排队规模。

## 7. commonPool 竞争 {#commonpool-竞争}

公共 ForkJoinPool 是 JVM 进程内的共享资源。一个模块提交大量长任务，会影响其他使用者。只调整 `java.util.concurrent.ForkJoinPool.common.parallelism` 也是进程级配置，无法为每个接口建立独立预算。

如果业务必须隔离执行资源，使用显式执行器和明确的任务编排。把并行 Stream 包在自建 `ForkJoinPool.submit` 中的行为不应作为跨实现的资源隔离契约；即使当前 JDK 达到预期，也要通过升级测试验证。

:::warning 服务端使用前先确认

并行流没有队列长度、拒绝策略、业务优先级和请求级并发上限这些接口。需要过载保护与隔离时，线程池或任务框架应当由业务显式拥有。

:::

## 8. 适用条件 {#适用条件}

并行流的有利条件包括：

- 数据规模足够大，拆分近似均匀。
- 每个元素执行独立的 CPU 计算。
- 没有外部可变状态和线程绑定上下文。
- 合并操作满足结合律，合并成本较低。
- 机器有空闲核心，应用允许这项计算使用它们。

不利因素包括：

- 元素很少或单个操作过轻，调度成本占主导。
- 数据源难以拆分，例如链式结构或串行 I/O。
- 大量装箱、分配和全局排序。
- 有序短路操作限制任务协作。
- 运行环境已经 CPU 饱和。
- 流水线包含数据库、网络或文件阻塞。

用接近生产的数据量、核心数和并发背景做测试。JMH 或端到端压测可帮助比较吞吐与尾延迟。单次计时会混入类加载、JIT 和 GC 开销。

## 9. 异常与取消 {#异常与取消}

某任务抛异常会使终止操作失败。已启动的其他任务仍可继续运行。Stream 没有请求级超时和外部副作用补偿协议。

需要超时、部分成功或逐项错误时，使用显式任务模型。统一吞异常并返回 `null` 会混淆失败与缺失。

## 10. 并行标志与结果顺序 {#并行标志与结果顺序}

`parallel()` 和 `sequential()` 修改整条流水线的执行模式。执行时以最后设置的模式为准。它们不会把前后阶段分配到不同线程池。

```java
List<Integer> values = IntStream.range(0, 1000)
    .parallel()
    .map(i -> i * 2)
    .sequential()
    .boxed()
    .toList();
```

这条流水线以串行模式执行。有序并行流的 `toList()` 仍按遇到顺序组织结果。`forEachOrdered` 约束终端动作顺序，其上游计算仍可并发。

`unordered()` 取消顺序要求，不执行随机打乱。并行短路也会有已启动的额外计算，应避免依赖精确调用次数。

## 11. 常见问题 {#常见问题}

### 11.1 并行度与活动线程 {#并行度与活动线程}

OpenJDK 21 中，公共池并行度影响工作线程数量。调用线程也可参与计算。阻塞与嵌套任务会改变活动线程数，因此它不是业务并发上限。

### 11.2 线程安全容器与业务状态 {#线程安全容器与业务状态}

线程安全容器只保证自身操作契约。跨容器更新或检查后写入仍需协调。锁竞争也会削弱收益，优先采用分区隔离的收集过程。

### 11.3 并行模式与执行资源 {#并行模式与执行资源}

不会。它只把 Stream 的并行标志设为 true，终止操作执行时再按并行模型处理。它也不会异步返回，调用终止操作的线程仍然等待最终结果。

### 11.4 嵌套并行流 {#嵌套并行流}

嵌套并行增加拆分和合并工作，内外层还会共享执行资源。应先选择一个并行维度，再验证收益。

**考察重点**

- 阻塞任务为什么会降低 Fork/Join 的利用率。

<details>
<summary>参考回答</summary>

Fork/Join 将大任务拆成小任务。Worker 优先处理自身队列，空闲时窃取其他队列任务。子任务完成后按归约规则合并结果。

它适合可拆分的 CPU 计算。任务阻塞会占用工作线程，公共池其他使用者也会排队。工作窃取只重新分配任务，不增加外部资源容量。

</details>

公共池由多个模块共享。阻塞 I/O 需要明确并发上限、超时和隔离，宜用显式任务模型。在实际并发背景下比较串行与并行的吞吐及尾延迟。
