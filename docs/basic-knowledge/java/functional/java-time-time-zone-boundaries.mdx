# java.time

`java.time` 区分瞬间、本地时间、偏移量和地区时区。本文负责类型选择、夏令时、日期运算和格式解析。

## 1. 面试核心 {#core}

- `Instant` 表示瞬间，`LocalDateTime` 只保存本地日期时间。
- `ZoneOffset` 是固定偏移，地区 `ZoneId` 按规则计算偏移。
- 按当地日历执行的任务需保存本地规则和 `ZoneId`。[卡](#cross-timezone-jobs)
- `DateTimeFormatter` 不可变且线程安全。[卡](#simpledateformat-thread-safety)
- `Duration` 表示秒与纳秒时长，`Period` 表示年月日数量。

## 2. Instant {#instant}

`Instant` 表示 UTC 时间线上的一个点，适合记录已经发生的事件：

```java
Instant createdAt = Instant.now();
```

订单创建、消息发送和审计时间都可用瞬间记录。两个系统只要使用同一时间尺度，就能比较先后和计算经过时长。

`Instant` 不包含用户所在地区，也不能直接回答“当地是星期几”。展示时需要应用时区：

```java
ZoneId shanghai = ZoneId.of("Asia/Shanghai");
ZonedDateTime localView = createdAt.atZone(shanghai);
```

同一个 `Instant` 在上海和纽约会显示不同的本地日期时间，但仍是同一个瞬间。

## 3. LocalDateTime {#localdatetime}

`LocalDate`、`LocalTime` 和 `LocalDateTime` 表示 ISO 日历中的本地字段：

```java
LocalDate date = LocalDate.of(2026, 8, 30);
LocalTime time = LocalTime.of(9, 30);
LocalDateTime meeting = LocalDateTime.of(date, time);
```

`2026-08-30 09:30` 没有说明在哪个地区，不能唯一对应时间线上的瞬间。它适合表示：

- 生日等只关心日历日期的数据。
- 每天 09:30 开门等本地规则。
- 用户刚输入、尚未选择时区的日期时间。

输入的 `LocalDateTime` 需要明确的地区或偏移。隐式使用服务器时区，会让部署环境改变解析结果。

## 4. OffsetDateTime 与 ZonedDateTime {#offsetdatetime-与-zoneddatetime}

`OffsetDateTime` 包含固定 UTC 偏移量：

```java
OffsetDateTime value = OffsetDateTime.parse("2026-08-30T09:30:00+08:00");
```

`+08:00` 能确定一个瞬间，但没有说明偏移量来自哪个地区规则。

`ZonedDateTime` 包含 `ZoneId`，例如 `Asia/Shanghai` 或 `Europe/Paris`：

```java
ZonedDateTime parisMeeting = ZonedDateTime.of(
    LocalDateTime.of(2026, 10, 25, 2, 30),
    ZoneId.of("Europe/Paris")
);
```

地区时区包含偏移变化规则。每月按纽约当地时间执行时，应保存日历规则和 `America/New_York`。当前偏移只描述特定时点，无法表达后续规则。

### 4.1 ZoneOffset 与 ZoneId {#zoneoffset-与-zoneid}

`ZoneOffset.ofHours(8)` 固定为 `+08:00`。巴黎地区的偏移随日期与规则变化。固定偏移适合明确的协议值，地区时区适合当地日程。

## 5. 本地时间解析 {#本地时间转换为瞬间}

```java
LocalDateTime local = LocalDateTime.parse(
    "2026-03-29 02:30",
    DateTimeFormatter.ofPattern("uuuu-MM-dd HH:mm")
);

ZonedDateTime zoned = local.atZone(ZoneId.of("Europe/Paris"));
Instant instant = zoned.toInstant();
```

夏令时向前或向后调整分别产生：

- **间隙**：某段本地时间不存在，时钟直接向前跳。
- **重叠**：某段本地时间出现两次，对应两个不同瞬间。

`atZone` 遇到间隙时按间隙长度向后推移。遇到重叠时默认选择较早偏移。业务可明确拒绝间隙，或改选较晚偏移。

可以通过 `ZoneRules.getValidOffsets(localDateTime)` 检查一个本地时间对应零个、一个还是两个有效偏移。

## 6. 时区转换 {#时区转换}

保持同一瞬间切换显示地区：

```java
ZonedDateTime shanghai = instant.atZone(ZoneId.of("Asia/Shanghai"));
ZonedDateTime newYork = shanghai.withZoneSameInstant(
    ZoneId.of("America/New_York")
);
```

两者的本地时钟不同，`toInstant()` 相同。

`withZoneSameLocal` 尽量保留本地字段，并在目标时区解析。目标时区存在间隙时，本地时间会被调整。普通展示转换应使用 `withZoneSameInstant`。

## 7. Duration 与 Period {#duration-与-period}

`Duration` 按秒和纳秒计算时间线上的时长：

```java
Duration elapsed = Duration.between(startInstant, endInstant);
```

`Period` 按年、月、日表示日历差异：

```java
Period age = Period.between(birthDate, today);
```

跨夏令时切换时，日历一天可为 23 或 25 小时。固定时长使用 `Duration.ofHours(24)`。当地明天同一时刻使用 `plusDays(1)`。

## 8. DateTimeFormatter {#datetimeformatter}

```java
private static final DateTimeFormatter ORDER_TIME =
    DateTimeFormatter.ofPattern("uuuu-MM-dd HH:mm:ss")
        .withResolverStyle(ResolverStyle.STRICT);
```

`DateTimeFormatter` 可以安全共享。`SimpleDateFormat` 维护可变解析状态，共享时需同步。

严格解析能拒绝 2 月 30 日等非法日期。`uuuu` 表示连续年份，`yyyy` 表示纪元内年份。`YYYY` 表示基于周的年份，年末年初可与日历年不同。

协议优先使用 ISO 8601 格式，例如：

```java
String encoded = DateTimeFormatter.ISO_INSTANT.format(createdAt);
Instant decoded = Instant.parse(encoded);
```

自定义展示格式属于界面或集成边界，不应成为系统内部唯一时间语义。

## 9. Clock 与时间测试 {#用-clock-测试当前时间}

直接在业务方法中调用 `Instant.now()` 会让测试依赖真实时钟。可以注入 `Clock`：

```java
final class ExpirationPolicy {
    private final Clock clock;

    ExpirationPolicy(Clock clock) {
        this.clock = clock;
    }

    boolean expired(Instant deadline) {
        return !Instant.now(clock).isBefore(deadline);
    }
}
```

测试使用固定时钟：

```java
Clock clock = Clock.fixed(
    Instant.parse("2026-08-30T01:30:00Z"),
    ZoneOffset.UTC
);
```

固定时钟可稳定测试到期、跨日和夏令时边界。测试无需等待真实时间。

## 10. 存储与接口 {#存储与接口}

### 10.1 已发生事件 {#已发生事件}

保存 `Instant` 或具有明确 UTC 语义的数据库时间戳。API 输出带 `Z` 或显式偏移量，展示时再按用户时区转换。

### 10.2 未来日程 {#未来日程}

如果要求“每周一纽约时间 09:00 执行”，保存：

- 本地日期或重复规则。
- 本地时间。
- 地区 `ZoneId`。
- 对间隙和重叠的处理策略。

重复日程应保留本地规则和时区。只存一个 UTC 瞬间，会丢失下一次执行所需的日历意图。已算好的瞬间本身仍表示固定时点。

### 10.3 数据库字段 {#数据库字段}

数据库时间类型与 JDBC 的时区语义依产品而异。应核对驱动、连接、会话时区及 ORM 映射。跨时区往返测试可验证保存与读取是否一致。

:::tip 一个简单判断

已发生事件优先使用 `Instant`；只有本地日期或时间含义时使用 `LocalDate`、`LocalTime`；未来安排需要遵循某地规则时，保留 `ZoneId`。

:::

## 11. 夏令时解析与日历运算 {#夏令时解析与日历运算}

以下示例使用 `Europe/Paris` 的 2026 年规则：

```java
ZoneId paris = ZoneId.of("Europe/Paris");
ZonedDateTime gap = LocalDateTime.of(2026, 3, 29, 2, 30).atZone(paris);
System.out.println(gap); // 2026-03-29T03:30+02:00[Europe/Paris]
ZonedDateTime overlap = LocalDateTime.of(2026, 10, 25, 2, 30).atZone(paris);
System.out.println(overlap.getOffset()); // +02:00
System.out.println(overlap.withLaterOffsetAtOverlap().getOffset()); // +01:00
```

间隙中的 02:30 被推至 03:30。重叠中的 02:30 对应两个瞬间。严格校验可先调用 `getValidOffsets`，再按业务选择。

`plusDays(1)` 按本地日期前进，跨夏令时可相差 23 或 25 小时。`plus(Duration.ofHours(24))` 沿时间线增加 24 小时。`LocalDate.of(2026, 1, 31).plusMonths(1)` 则得到 2 月 28 日。月末会调整到目标月最后一个有效日期。

## 12. 常见问题 {#常见问题}

### 12.1 时间戳的转换边界 {#时间戳的转换边界}

epoch 值表示瞬间，展示需要时区。输入解析和数据库转换也应明确时区。无时区文本需要补足语义后再转为时间戳。

### 12.2 本地时间的适用范围 {#本地时间的适用范围}

`LocalDateTime` 适合本地日历字段。确定瞬间还需时区或偏移。重叠时间也需选择具体偏移。

### 12.3 服务器默认时区 {#服务器默认时区}

只有系统明确约定并持续验证时才可以。容器基础镜像、JVM 参数和部署地区都可能改变默认时区。核心业务应使用显式 `ZoneId` 或 `Clock`，不要让环境默认值悄悄决定结果。

### 12.4 时间精度转换 {#时间精度转换}

`Instant` 支持纳秒，转为 epoch 毫秒会丢失更细精度。数据库与协议也各有精度上限。比较或去重时应明确采用的精度。

## 13. 面试题 {#面试题}

### 13.1 SimpleDateFormat 为什么线程不安全，应该怎样替代 {#simpledateformat-thread-safety}

**出现公司**：CVTE、三七互娱

**考察重点**

- 共享可变解析状态如何产生数据竞争。
- 加锁、每次新建、ThreadLocal 与 DateTimeFormatter 的差异。
- 新代码为何优先使用不可变的 java.time API。

**相关内容**：[DateTimeFormatter](#datetimeformatter)。

<details>
<summary>参考回答</summary>

`SimpleDateFormat` 的解析状态可变，共享时会发生竞争。可通过每次创建、加锁或线程隔离处理。三者分别增加分配、竞争或生命周期管理成本。

新代码可共享 `DateTimeFormatter`。事件时间用 `Instant`，本地日期用 `LocalDate`。遵循地区规则的时间用 `ZonedDateTime`。

</details>

### 13.2 跨时区定时任务怎样保证执行时间正确 {#cross-timezone-jobs}

**出现公司**：蚂蚁集团

**考察重点**

- 固定瞬间与本地日程的区别。
- ZoneId、夏令时间隙和重叠。
- 时区规则更新、幂等与错过执行的恢复。

**相关内容**：[OffsetDateTime 与 ZonedDateTime](#offsetdatetime-与-zoneddatetime)、[本地时间解析](#本地时间转换为瞬间)、[存储与接口](#存储与接口)。

<details>
<summary>参考回答</summary>

固定执行时点保存 `Instant`。按当地日历重复执行时，保存本地规则与 `ZoneId`。每次按时区规则计算下一执行瞬间。

间隙与重叠都应有明确处理规则。调度状态需持久化，执行需幂等。停机恢复后按业务规则补跑，并记录计划与实际时间。

</details>
