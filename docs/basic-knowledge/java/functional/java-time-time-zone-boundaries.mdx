# java.time

`java.time` 用不同的类型区分几种不同的「时间」：时间线上的一个瞬间、某地日历和钟表上的日期时间、带固定偏移量的时间，以及遵循某个地区时区规则的时间。

处理时间时，最容易出问题的地方是选错类型，把「全世界同一时刻」和「某地墙上挂钟显示的时间」混为一谈。所以选类型之前，先问一句：这个数据表示的是全球同一时刻，还是某地日历上的时间？分清这一点，夏令时、跨时区接口和定时任务的问题都能顺着推出来。

## 1. 面试核心 {#core}

- `Instant` 表示**时间线上的一个瞬间**；`LocalDateTime` 只保存本地日期时间，**要确定是哪个瞬间，还需要偏移量或时区**。
- `ZoneOffset` 是**固定的偏移量**；地区 `ZoneId` 会**按日期和时区规则确定当时的偏移量**，所以能处理夏令时。
- `Duration` 用**秒和纳秒表示时间线上经过的时长**，`Period` 用**年、月、日表示日历上的间隔**；跨夏令时切换时，「加一天」和「加 24 小时」结果不同。
- `SimpleDateFormat` 共享可变的解析状态，多线程共享会产生数据竞争；**`DateTimeFormatter` 不可变且线程安全**。[卡](#simpledateformat-thread-safety)
- 按当地日历重复执行的任务，要**保存本地规则和 `ZoneId`**，每次据此算出执行的瞬间，而不是只存一个算好的 UTC 时刻。[卡](#cross-timezone-jobs)

## 2. Instant {#instant}

`Instant` 表示 UTC 时间线上的一个点，适合记录已经发生的事件：

```java
Instant createdAt = Instant.now();
```

`createdAt` 记录的是调用这一刻的瞬间。订单创建时间、消息发送时间、审计日志时间都适合这样保存。不同系统只要都用这个时间尺度，就能直接比较事件的先后，计算经过了多久。

`Instant` 只记录瞬间，不知道「当地是星期几、几点」。要展示给用户看，需要用户所在的时区，把它转换成当地日期时间：

```java
ZoneId shanghai = ZoneId.of("Asia/Shanghai");
ZonedDateTime localView = createdAt.atZone(shanghai);
```

同一个 `Instant` 在上海和纽约显示的本地日期时间不同，但它们仍然是同一个瞬间。

## 3. LocalDateTime {#localdatetime}

生日、营业时间、用户在表单里输入的日期，关心的是日历或钟表上的数值，而不是时间线上的某个点。`LocalDate` 保存年月日，`LocalTime` 保存时分秒，`LocalDateTime` 两者都有：

```java
LocalDate date = LocalDate.of(2026, 8, 30);
LocalTime time = LocalTime.of(9, 30);
LocalDateTime meeting = LocalDateTime.of(date, time);
```

`meeting` 表示 `2026-08-30 09:30`（ISO 日历），但没有时区。上海和纽约都有这个本地时间，对应的却是两个不同的瞬间。三种类型各自适合：

- 生日这类只关心日历日期的数据，用 `LocalDate`。
- 「每天 09:30 开门」这类本地规则，用 `LocalTime` 表示钟表时间。
- 用户刚输入、还没确定时区的日期时间，可以暂存为 `LocalDateTime`。

把 `LocalDateTime` 转成瞬间时，必须明确用哪个地区或偏移量。擅自把它当作 UTC，会曲解用户的输入；隐式使用服务器时区，换个地区部署，转换结果就变了。

## 4. OffsetDateTime 与 ZonedDateTime {#offsetdatetime-与-zoneddatetime}

本地日期时间加上 UTC 偏移量，就能确定一个瞬间。**偏移量**是当地时间比 UTC 快或慢多少，`OffsetDateTime` 把两者存在一起：

```java
OffsetDateTime value = OffsetDateTime.parse("2026-08-30T09:30:00+08:00");
```

`+08:00` 表示比 UTC 快 8 小时，所以这条记录对应 UTC 的 01:30。偏移量说明了当时的时差，但没有记录它来自哪个地区。

`ZonedDateTime` 则带着一个地区 `ZoneId`，例如 `Asia/Shanghai` 或 `Europe/Paris`：

```java
ZonedDateTime parisMeeting = ZonedDateTime.of(
    LocalDateTime.of(2026, 10, 25, 2, 30),
    ZoneId.of("Europe/Paris")
);
```

`parisMeeting` 除了日期时间，还保留了「巴黎」这个地区。地区时区背后是一套规则，包含历史上的偏移变化和已知的未来变化，夏令时就靠它处理。

这个区别在重复任务上最明显。比如每月按纽约当地时间执行的任务，夏令时切换后，纽约和 UTC 的时差会从 5 小时变成 4 小时（或反过来）。如果只存了一个偏移量 `-05:00`，切换之后算出的时间就差了一小时；保存 `America/New_York`，才能每次按当时的规则重新计算。

### 4.1 ZoneOffset 与 ZoneId {#zoneoffset-与-zoneid}

固定偏移量适合协议里约定好的明确时差，地区时区适合遵循当地日历的安排。`ZoneOffset.ofHours(8)` 永远是 `+08:00`；`ZoneId.of("Europe/Paris")` 则根据日期查时区数据库的规则来确定偏移量，冬天和夏天可以不同。

## 5. 本地时间解析 {#本地时间转换为瞬间}

把本地时间转换成瞬间，要先按地区规则确定当时的偏移量。麻烦在于，夏令时会让时钟跳过或重复一段时间，所以一个本地时间不一定唯一对应一个瞬间：

```java
LocalDateTime local = LocalDateTime.parse(
    "2026-03-29 02:30",
    DateTimeFormatter.ofPattern("uuuu-MM-dd HH:mm")
);

ZonedDateTime zoned = local.atZone(ZoneId.of("Europe/Paris"));
Instant instant = zoned.toInstant();
```

夏令时切换会产生两种情况：

- **间隙**（gap）：进入夏令时那天，时钟直接往前跳，某段本地时间根本不存在。
- **重叠**（overlap）：退出夏令时那天，时钟往回拨，某段本地时间出现两次，对应两个不同的瞬间。

`atZone` 遇到间隙时，会把本地时间往后推一个间隙的长度，所以上面巴黎的 02:30 会被调整成 03:30。遇到重叠时，它默认选回拨之前的偏移，也就是两个候选瞬间里较早的那个。

这个默认行为不一定适合你的业务。支付截止、航班、定时任务都要明确自己的策略：间隙里的时间可以往后推，也可以直接拒绝，让用户改选一个有效时间；如果业务只关心一个固定的执行时刻，可以直接约定一个 `Instant`。重叠的时间则要明确选较早还是较晚的偏移。

需要自己判断时，可以调用 `ZoneRules.getValidOffsets(localDateTime)`，看返回几个有效偏移：

- 0 个：输入落在间隙里。
- 1 个：可以唯一确定瞬间。
- 2 个：输入落在重叠区间，需要选其中一个。

## 6. 时区转换 {#时区转换}

给不同地区的用户展示同一个事件，应该保留瞬间，只换显示的时区，用的是 `withZoneSameInstant`：

```java
ZonedDateTime shanghai = instant.atZone(ZoneId.of("Asia/Shanghai"));
ZonedDateTime newYork = shanghai.withZoneSameInstant(
    ZoneId.of("America/New_York")
);
```

`shanghai` 和 `newYork` 显示的本地日期时间不同，但 `toInstant()` 相同，事件发生的时刻没变。

`withZoneSameLocal` 正好相反：它尽量保留原来的年月日和时分秒，换成目标时区来解释。两个时区的偏移不同时，对应的瞬间就变了；目标本地时间落在间隙里，还会按间隙规则调整。

所以普通的展示转换用 `withZoneSameInstant`。只有在修正时区标错的数据，或者明确要保留当地钟表时间时，才考虑 `withZoneSameLocal`。

## 7. Duration 与 Period {#duration-与-period}

「两个事件相隔多久」和「生日到今天相隔几年」要用不同的单位来算。`Duration` 用秒和纳秒表示时间线上经过的时长：

```java
Duration elapsed = Duration.between(startInstant, endInstant);
```

`elapsed` 是两个瞬间之间实际经过的时间。`Period` 则按年、月、日表示日历上的差异，比如从生日到今天：

```java
Period age = Period.between(birthDate, today);
```

`age` 保存的是年、月、日的数量，适合按日历理解年龄。

两者的差别在夏令时切换那天最明显：那天的日历一天只有 23 小时或者有 25 小时。所以「24 小时后」要用 `Duration.ofHours(24)`；「当地明天的同一时刻」要在带时区的时间上用 `plusDays(1)`，结果落在间隙里时再按规则调整。下一节用巴黎的例子验证这一点。

## 8. 夏令时解析与日历运算 {#夏令时解析与日历运算}

用巴黎 2026 年的夏令时切换验证前面的规则（`Europe/Paris` 在 3 月 29 日进入夏令时，10 月 25 日退出）：

```java
ZoneId paris = ZoneId.of("Europe/Paris");
ZonedDateTime gap = LocalDateTime.of(2026, 3, 29, 2, 30).atZone(paris);
System.out.println(gap); // 2026-03-29T03:30+02:00[Europe/Paris]
ZonedDateTime overlap = LocalDateTime.of(2026, 10, 25, 2, 30).atZone(paris);
System.out.println(overlap.getOffset()); // +02:00
System.out.println(overlap.withLaterOffsetAtOverlap().getOffset()); // +01:00
```

- 3 月 29 日的 02:30 落在间隙里，被推到 03:30，偏移已经是夏令时的 `+02:00`。
- 10 月 25 日的 02:30 出现两次，默认选回拨前的 `+02:00`。
- `withLaterOffsetAtOverlap()` 改选回拨后的 `+01:00`，对应晚一小时的那个瞬间。

需要拒绝输入或让用户选择的场景，先调用 `getValidOffsets` 判断，再执行业务约定的策略。

日期运算也会碰到同样的边界。`plusDays(1)` 按本地日期前进，在巴黎跨过上面两个切换日时，实际经过的时长是 23 或 25 小时；`plus(Duration.ofHours(24))` 沿时间线加整整 24 小时，所以当地钟表上的时间会差一小时。

月份运算还要处理目标日期不存在的情况。`LocalDate.of(2026, 1, 31).plusMonths(1)` 得到 2 月 28 日：2 月没有 31 日，API 会把结果调整到目标月份的最后一个有效日期。

## 9. DateTimeFormatter {#datetimeformatter}

处理时间文本，要同时约定格式和非法日期怎么处理。下面的格式器使用严格解析，会拒绝 2 月 30 日这类日期：

```java
private static final DateTimeFormatter ORDER_TIME =
    DateTimeFormatter.ofPattern("uuuu-MM-dd HH:mm:ss")
        .withResolverStyle(ResolverStyle.STRICT);
```

`DateTimeFormatter` 不可变且线程安全，所以可以像上面这样作为静态常量共享。`SimpleDateFormat` 则不同：它内部持有一个 `Calendar` 对象，每次解析和格式化都会修改它。多个线程共享同一个实例时，会互相覆盖对方的中间状态，得到错误结果甚至抛异常，所以必须同步或者不共享。

写格式时要分清三种年份符号：

- `uuuu`：连续的年份，包含 0 和负数年份，适合直接解析完整日期。
- `yyyy`：纪元内的年份，要结合公元前、公元后的纪元信息才能确定。所以用 STRICT 解析 `yyyy-MM-dd` 时，因为文本里没有纪元字段，日期无法确定，解析会失败；这也是上例用 `uuuu` 的原因。
- `YYYY`：基于周的年份，在年末年初可能和日历年不同（比如 12 月 31 日可能已经算作下一年的第 1 周），普通日期格式不要用它。

协议里优先使用 ISO 8601 格式，例如：

```java
String encoded = DateTimeFormatter.ISO_INSTANT.format(createdAt);
Instant decoded = Instant.parse(encoded);
```

编码保留了瞬间，解析回来得到和 `createdAt` 相等的值。界面上可以用自定义的展示格式，但系统内部始终保留含义明确的时间类型，这样换一种显示格式，也不影响比较和计算。

## 10. Clock 与时间测试 {#用-clock-测试当前时间}

判断是否到期需要读取当前时间，但测试需要稳定地重现某个时刻。`Clock` 是一个可替换的时间来源，业务代码和测试可以用不同的时钟：

```java
final class ExpirationPolicy {
    private final Clock clock;

    ExpirationPolicy(Clock clock) {
        this.clock = clock;
    }

    boolean expired(Instant deadline) {
        return !Instant.now(clock).isBefore(deadline);
    }
}
```

当前时间达到或超过截止时刻时，`expired` 返回 true。它通过传进来的 `Clock` 读时间，所以测试时可以换成固定时钟：

```java
Clock clock = Clock.fixed(
    Instant.parse("2026-08-30T01:30:00Z"),
    ZoneOffset.UTC
);
```

这个时钟永远返回同一个瞬间。把它设在刚好到期、跨日或夏令时切换的前后，就能稳定地验证边界，既不用等真实时间流逝，也不用修改系统时间。

## 11. 存储与接口 {#存储与接口}

时间存进数据库或传给其他系统以后，原来的业务含义不能丢。已发生的事件和未来的日程关心的东西不同，存法也不同。

### 11.1 已发生事件 {#已发生事件}

已发生的事件需要记录一个确定的时刻，适合保存 `Instant`，或者具有明确 UTC 语义的数据库时间戳。API 输出时带上 `Z`（表示 UTC）或显式的偏移量，展示时再按用户时区转换，这样各个系统指向的都是同一个时刻。

### 11.2 未来日程 {#未来日程}

未来的日程需要保留当地日历上的约定。比如「每周一纽约时间 09:00 执行」，需要保存：

- 本地日期或重复规则：在哪些日历日期执行。
- 本地时间：当天几点执行。
- 地区 `ZoneId`：用来取得当地的时区规则。
- 间隙和重叠的处理策略：特殊日期怎样选出瞬间。

每次计算下一次执行时间，都要结合本地规则和地区时区。如果只保存一次算出来的 UTC 瞬间，「每周一 09:00」这个约定就丢了，夏令时一切换，执行时间就偏了一小时。另外，已经算好的未来瞬间是固定的时点，如果时区规则后来更新了（某些国家会调整夏令时政策），要重新检查它是否还符合原来的当地日程。

### 11.3 数据库字段 {#数据库字段}

`TIMESTAMP`、`DATETIME` 和它们的 JDBC 映射在时区语义上因数据库产品而异，光看字段类型的名字定不了转换规则。保存和读取时，要逐个核对这些环节：

- JDBC 驱动怎样映射 Java 时间类型。
- 连接配置用的是哪个时区。
- 数据库会话用的是哪个时区。
- ORM（对象关系映射框架）怎样读写这个字段。

最后用不同时区的连接做一次往返测试，确认读回来的值仍然表示原来的瞬间或本地时间。

:::tip 一个简单判断

- 已发生事件优先使用 `Instant`。
- 只有本地日期或时间含义时，使用 `LocalDate`、`LocalTime`。
- 未来安排需要遵循某地规则时，保留 `ZoneId`。

:::

## 12. 常见问题 {#常见问题}

### 12.1 使用时间戳后还需要处理时区吗？ {#时间戳的转换边界}

需要。时间戳本身没问题，问题在进出的环节：解析输入、数据库转换和界面展示都要明确时区。epoch 值记录的是距离纪元起点（通常是 `1970-01-01T00:00:00Z`）经过的时间，它能确定瞬间；但用户输入的「2026-08-30 09:30」这种不带时区的文本，要先补上地区或偏移量，才能转成正确的时间戳。

### 12.2 可以统一使用 LocalDateTime 吗？ {#本地时间的适用范围}

不可以。`LocalDateTime` 只表达本地日历上的日期时间，它分不清上海的 09:30 和纽约的 09:30，也分不清夏令时重叠里的两个瞬间。记录事件时，要补上偏移量或时区、明确重叠时选哪个，再转成 `Instant`。

### 12.3 服务器默认时区可以作为业务时区吗？ {#服务器默认时区}

只有系统明确约定了默认时区，并且持续验证它没被改掉时才可以。容器基础镜像、JVM 参数和部署地区都可能改变默认时区。核心业务显式传入 `ZoneId` 或 `Clock`，转换依据就清楚地写在代码或配置里，而不是依赖环境。

### 12.4 转成 epoch 毫秒会丢失精度吗？ {#时间精度转换}

会。`Instant` 支持纳秒精度，转成 epoch 毫秒会截掉不足一毫秒的部分。数据库和协议也各有精度上限，比如微秒或毫秒。所以比较或去重之前，要先统一到所有环节都能保留的精度，否则同一个时刻经过一次往返，数值就对不上了。

## 13. 面试题 {#面试题}

### 13.1 SimpleDateFormat 为什么线程不安全，应该怎样替代 {#simpledateformat-thread-safety}

**考察重点**

- 解释多个线程怎样互相覆盖同一个格式器的可变解析状态。
- 比较加锁、每次新建和 `ThreadLocal` 隔离实例的成本。
- 说明 `DateTimeFormatter` 为什么能够安全共享。

**相关内容**：[DateTimeFormatter](#datetimeformatter)。

<details>
<summary>参考回答</summary>

**`SimpleDateFormat` 在解析和格式化时会修改内部状态，多线程共享同一个实例会互相覆盖，所以新代码优先改用 `DateTimeFormatter`。**

旧代码可以通过隔离实例或同步来处理：

- 每次调用都新建实例，各用各的状态，代价是多了对象分配。
- 用锁保护共享实例，调用依次执行，代价是串行等待和锁竞争。
- 用 `ThreadLocal` 为每个线程保存一个实例，但要管理线程复用时的清理和实例生命周期。

`DateTimeFormatter` 不可变且线程安全，可以直接共享。从 `Date`、`Calendar` 迁移时，还要按数据含义选类型：事件时间用 `Instant`，本地日期用 `LocalDate`，遵循地区规则的日期时间用 `ZonedDateTime`。

</details>

### 13.2 跨时区定时任务怎样保证执行时间正确 {#cross-timezone-jobs}

**考察重点**

- 区分固定瞬间执行与按当地日历重复执行。
- 解释 `ZoneId` 怎样参与计算，并明确夏令时间隙和重叠的处理策略。
- 说明时区规则更新或进程停机后，怎样重新计算并避免重复执行业务。

**相关内容**：[OffsetDateTime 与 ZonedDateTime](#offsetdatetime-与-zoneddatetime)、[本地时间解析](#本地时间转换为瞬间)、[存储与接口](#存储与接口)。

<details>
<summary>参考回答</summary>

**在固定时点执行的任务保存 `Instant`；按当地日历重复执行的任务保存本地时间、重复规则和地区 `ZoneId`。**

重复任务每次都按时区数据库的规则算出下一次执行的瞬间。间隙里的时间是推迟还是拒绝、重叠时选哪个偏移，都要由业务约定。时区规则更新后，还要重新核对已经算好的未来计划。

调度系统要持久化任务状态，记录计划时间和实际执行时间。执行要保证幂等，也就是同一任务被重复触发时，只产生一次预期的业务效果。进程停机恢复后，再按业务规则决定跳过还是补跑错过的任务。

</details>

### 13.3 夏令时切换时，atZone 和增加一天分别怎样处理？ {#dst-resolution-arithmetic}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释 `atZone` 怎样处理间隙和重叠，并说明增加一个日历日为何会与增加 24 小时不同。

**相关内容**：[夏令时解析与日历运算](#夏令时解析与日历运算)。

<details>
<summary>参考回答</summary>

**`atZone` 遇到间隙时把本地时间往后推一个间隙长度，遇到重叠时默认选回拨前的偏移；增加一天按本地日历走，增加 24 小时按时间线走。**

以 `Europe/Paris` 的 2026 年规则为例：3 月 29 日的 02:30 落在间隙里，`atZone` 把它调整为 03:30；10 月 25 日的 02:30 出现两次，默认选 `+02:00`，也可以用 `withLaterOffsetAtOverlap()` 改选 `+01:00`。

`plusDays(1)` 跨过一小时的夏令时切换时，实际经过的时长是 23 或 25 小时；`plus(Duration.ofHours(24))` 始终加 24 小时，所以得到的当地钟表时间会差一小时。

</details>
