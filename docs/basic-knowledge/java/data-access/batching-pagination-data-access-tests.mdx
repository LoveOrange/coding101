# 批处理与分页

批处理减少写入往返，分页限定单次读取范围。本文负责执行批次、事务边界、游标与数据访问测试。示例采用 JDBC、MySQL 8.4 和 Hibernate ORM 7.1。

实体状态见 [JPA](./jpa-entity-states-dirty-checking-lazy-loading.mdx)。关联抓取与父对象分页见 [N+1 查询](./n-plus-one-fetch-strategies.mdx)。

## 1. 面试核心 {#core}

- JDBC batch 合并执行，整批原子性由事务保证。[卡](#batch-results)
- `flush()` 同步待写变化，随后 `clear()` 才能安全解除实体管理。[卡](#flush-clear)
- 深 offset 需跳过前方记录，覆盖索引只减少取列成本。[卡](#deep-pagination)
- Keyset 依赖唯一稳定排序，精确导出还需固定快照。[卡](#keyset-consistency)
- Hibernate 7.1 的 `hibernate.jdbc.batch_size=50` 设置单批语句上限。[卡](#batch-size-commit-boundary)

## 2. JDBC 批处理 {#1-jdbc-批处理复用语句结构}

```java
try (PreparedStatement statement = connection.prepareStatement(SQL)) {
    for (OrderRow row : rows) {
        statement.setLong(1, row.id());
        statement.setBigDecimal(2, row.amount());
        statement.addBatch();
    }
    int[] counts = statement.executeBatch();
}
```

PreparedStatement 把同一 SQL 的多组参数交给驱动。驱动根据协议和配置发送或改写语句。实际往返次数与生成键行为需结合驱动验证。

## 3. 批大小与事务范围 {#2-批大小决定内存与失败范围}

执行批大小与提交频率是两个参数。前者控制单次提交给驱动的语句量，后者控制事务范围。

批次太小，往返节省有限。批次太大，会增加参数内存与单次失败排查成本。锁持有时间、日志保留和回滚范围还受提交频率影响。

BatchUpdateException 提供已执行命令的更新计数。驱动可在失败处停止，也可继续执行剩余命令。处理规则见后文事务示例。

## 4. MyBatis 与 JPA 的本地状态 {#3-mybatis-与-jpa-还要处理本地状态}

MyBatis 的 BATCH 执行器延迟执行更新。结果获取时机见 [MyBatis](./mybatis-mapping-executor-plugins.mdx)。

JPA 的 flush 同步修改，clear 解除实体管理。实体生命周期见 [JPA](./jpa-entity-states-dirty-checking-lazy-loading.mdx)。批量导入应按块 flush、clear，限制上下文保留量。

## 5. Offset 分页成本 {#4-offset-分页的成本随偏移增长}

```sql
select id, created_at
from orders
order by created_at desc, id desc
limit 20 offset 1000000;
```

MySQL 8.4 需从排序结果中跳过前一百万行。匹配索引可减少排序，覆盖索引可减少回表。偏移对应的跳过成本仍存在。

并发插入或删除会移动分页位置，造成重复或遗漏。需要任意跳页时可用 offset。持续下拉与顺序扫描适合 Keyset。

## 6. Keyset 分页 {#5-keyset-分页从最后一条继续}

```sql
select id, created_at
from orders
where (created_at, id) < (:lastCreatedAt, :lastId)
order by created_at desc, id desc
limit 20;
```

排序键需唯一且稳定，时间字段后可补主键。索引设计需同时考虑过滤与排序。

游标保存末行排序值、方向和查询条件。服务端应校验参数，并绑定当前查询范围。条件改变时，重新从第一页开始。

Keyset 需要已知游标，适合连续翻页。任意跳页和精确总页数需额外查询或索引。

## 7. 批处理结果与事务示例 {#批处理结果与事务示例}

下例使用新获取的独立连接，整批共同提交。Spring 管理的连接应由 Spring 控制事务：

```java
try (Connection connection = dataSource.getConnection()) {
    connection.setAutoCommit(false);
    try {
        // 使用该连接 addBatch / executeBatch，核对更新计数。
        connection.commit();
    } catch (SQLException e) {
        try { connection.rollback(); }
        catch (SQLException rollbackFailure) { e.addSuppressed(rollbackFailure); }
        throw e;
    }
}
```

`SUCCESS_NO_INFO=-2` 表示执行成功，行数未知。`EXECUTE_FAILED=-3` 表示该命令失败。驱动继续执行时，失败项由后者标记。驱动中止时，数组只包含中止前的成功结果。

提交阶段断线会留下结果未知的状态。重试前应按业务唯一键核对。可确认未提交且已回滚时，再重试整个业务单元。

## 8. 游标与一致性边界 {#游标与一致性边界}

上例要求 created_at 与 id 非空，组合排序唯一。倒序下一页使用严格小于。只记录时间会漏掉同时间的剩余记录。

MySQL 8.4 的元组比较需检查执行计划。可与下面的等价条件比较：

```sql
created_at < :t OR (created_at = :t AND id < :id)
```

Keyset 隔离前方插入造成的偏移移动。排序字段更新仍会让记录跨过游标。精确导出需固定事务快照或冻结业务版本。固定最大 ID 仅限定新增范围，已有字段仍可变化。

## 9. 关联分页的结果规模 {#6-分页关联数据要控制结果规模}

一对多关联会展开父行，直接 LIMIT 会截断展开结果。父 ID 分页与第二阶段抓取见 [N+1 查询](./n-plus-one-fetch-strategies.mdx#7-集合抓取与分页要分两步考虑)。

## 10. 目标数据库的访问测试 {#7-数据访问测试使用目标数据库}

关键 Repository/Mapper 测试应运行目标数据库版本。H2 可测试通用逻辑，方言与锁行为需单独验证。Testcontainers 可为测试创建隔离数据库。

测试至少覆盖：

- 参数绑定与空值、枚举、时间类型。
- 唯一约束、外键和事务回滚。
- 动态 SQL、排序字段白名单和分页边界。
- N+1 查询数量及批处理实际执行。
- 并发更新、锁等待和超时。
- 数据库迁移脚本与旧数据兼容。

自动回滚的测试覆盖不到提交后行为。验证提交后事件或可见性时，应显式完成 commit。之后用新事务读取，并检查实际结果。

## 11. 性能与结果验证 {#8-性能验证同时记录结果正确性}

测试需记录批大小、行宽、索引、驱动配置与提交频率。比较吞吐与 P99 时，同时核对影响行数和重复记录。分页还需核对遗漏、顺序与并发修改后的结果。

## 12. Hibernate 批次与提交频率 {#hibernate-批次与提交频率}

Hibernate ORM 7.1 默认 `hibernate.jdbc.batch_size=0`。设为正数可启用有状态 Session 的 JDBC 批处理。

```properties
hibernate.jdbc.batch_size=50
hibernate.order_inserts=true
hibernate.order_updates=true
```

batch_size 控制提交给驱动的单批语句上限。两个 order 配置调整执行顺序，增加相同 SQL 的合批机会。排序也有成本，需按负载验证。IDENTITY 主键策略会关闭 JDBC 插入合批。

每 50 条 flush、clear，可限制受管实体数量。若一万条只在末尾 commit，仍属于一个大事务。缩短事务需分批 commit，并接受已提交批次独立成功。

### 13.3 JPA 批量插入为什么要先 flush 再 clear？ {#flush-clear}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**

- 说明同步和实体保留。
- 说明主键生成与合批。

**相关内容**：[本地状态](#3-mybatis-与-jpa-还要处理本地状态)、[批处理事务](#批处理结果与事务示例)。

<details>
<summary>参考回答</summary>

flush 先同步待写变化，clear 再解除实体管理。反过来执行，会丢弃尚未同步的修改。flush 只发送 SQL，最终提交仍由事务控制。

Hibernate 7.1 的 IDENTITY 插入关闭 JDBC 合批。是否合批还受 batch_size 与 SQL 形态影响。

</details>

### 13.4 Keyset 分页能保证并发修改下完全不重不漏吗？ {#keyset-consistency}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**

- 说明唯一排序和边界。
- 说明快照与固定截止点。

**相关内容**：[Keyset](#5-keyset-分页从最后一条继续)、[一致性边界](#游标与一致性边界)。

唯一稳定排序解决同值边界。精确导出还需事务快照或业务版本。固定最大 ID 只约束新增范围。

</details>

### 13.5 hibernate.jdbc.batch_size=50 是否表示每 50 条自动提交？ {#batch-size-commit-boundary}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：执行批次、上下文清理与事务边界。

**相关内容**：[Hibernate 批次与提交频率](#hibernate-批次与提交频率)。

<details>
<summary>参考回答</summary>

它只设置单批语句上限，事务提交仍由 commit 控制。flush、clear 也不会自动提交。每 50 条提交需显式划分事务，并处理部分批次已成功的情况。

</details>
