# 批处理与分页

**批处理**是把多条结构相同的写入攒成一批交给数据库，减少逐条发送的往返；**分页**是限定一次读取多少数据。两者都是常见的性能手段，但都有容易混淆的边界：一批语句执行完不等于已经提交，换成游标分页也不等于结果不重不漏。

批次大小和事务大小是两回事；Offset 分页越往后越慢，Keyset 分页从上一页末尾继续。这些优化最后都要在目标数据库和真实数据规模下验证。文中的示例基于 JDBC、MySQL 8.0 和 Hibernate ORM 5.6/6.2。

## 1. 面试核心 {#core}

- JDBC batch 只是把多组参数交给驱动批量执行，**整批共同成功或回滚要靠事务保证**。`executeBatch()` 失败后，要结合更新计数和事务状态决定重试范围。[卡](#batch-results)
- JPA 分批写入时，**先 `flush()` 把待写变化同步到数据库，再 `clear()` 解除实体管理**；顺序反过来会丢掉尚未同步的修改。[卡](#flush-clear)
- `hibernate.jdbc.batch_size=50` 只把**单批语句上限设为 50**，什么时候提交仍由 commit 决定。[卡](#batch-size-commit-boundary)
- 深 Offset 分页**仍要扫描并跳过前面的记录**。覆盖索引能减少回表，但消除不了偏移扫描。[卡](#deep-pagination)
- Keyset 分页依赖**唯一且稳定的排序**；游标只记录位置，不冻结数据，精确导出还需要固定快照或业务版本。[卡](#keyset-consistency)

## 2. JDBC 批处理 {#1-jdbc-批处理复用语句结构}

多行数据用同一种 SQL 结构写入时，可以先把每行的参数收集起来，再一次交给驱动执行，省去逐条发送语句的开销：

```java
try (PreparedStatement statement = connection.prepareStatement(SQL)) {
    for (OrderRow row : rows) {
        statement.setLong(1, row.id());
        statement.setBigDecimal(2, row.amount());
        statement.addBatch();
    }
    int[] counts = statement.executeBatch();
}
```

`PreparedStatement` 保存带占位符的 SQL，每次 `addBatch()` 把当前这组参数加进批次。循环结束后，`executeBatch()` 把攒下的命令交给驱动执行，返回的 `counts` 是每条命令的更新计数。

驱动拿到批次后怎么发，取决于数据库协议和驱动配置：可能合并发送，也可能改写成一条多值语句。实际往返了几次、单批最多支持多少条、生成的主键怎样返回，都要针对你用的驱动验证，可以看 JDBC 日志和数据库指标确认批处理真的发生了。

## 3. 批大小与事务范围 {#2-批大小决定内存与失败范围}

批大小决定一次交给驱动多少条语句，提交频率决定多少次写入属于同一个事务，这是两个独立的旋钮。比如导入一百万行，可以每 500 条执行一次批次，再按一致性要求决定多久提交一次。

两个旋钮各有代价：

- 批次太小，减少网络往返的收益有限。
- 批次太大，参数占用的内存增加，一旦失败，定位和重试的成本也更高。
- 事务太大，锁持有时间变长、日志保留量增加，回滚范围也随之扩大。

批处理失败时会抛出 `BatchUpdateException`，它带着更新计数。驱动可以在失败处停下，也可以继续执行剩下的命令，所以重试范围要结合事务状态来定（下一节展开）。如果写入涉及唯一约束，先要保证**幂等**，也就是同一笔业务重复执行仍能得到正确结果，然后再考虑增大批量。

## 4. 批处理结果与事务示例 {#批处理结果与事务示例}

更新计数告诉你哪些命令执行过，事务状态才决定哪些结果真正提交了。需要整批一起成功时，可以像下面这样，在新获取的独立连接上关闭自动提交，执行完再提交：

```java
try (Connection connection = dataSource.getConnection()) {
    connection.setAutoCommit(false);
    try {
        // 使用该连接 addBatch / executeBatch，核对更新计数。
        connection.commit();
    } catch (SQLException e) {
        try { connection.rollback(); }
        catch (SQLException rollbackFailure) { e.addSuppressed(rollbackFailure); }
        throw e;
    }
}
```

批量执行成功就 `commit()`，遇到 `SQLException` 就尝试 `rollback()`；如果回滚也失败，回滚异常会作为 suppressed 异常附在原异常上，不会把原因盖掉。如果连接由 Spring 管理，就不要这样手动提交，而是让内部代码沿用 Spring 的事务边界。

读更新计数（update counts）时，要区分三种值：

- 非负数：该命令成功，数值是影响的行数。
- `SUCCESS_NO_INFO=-2`：执行成功，但驱动没有给出精确行数。
- `EXECUTE_FAILED=-3`：该命令失败。只有驱动在失败后继续执行剩余命令时才会出现。

如果驱动在失败处中止，数组里只有中止前那些成功命令的结果。所以负数各有含义，不能统一当成「影响了零行」。

决定重试之前，还要确认 autoCommit 配置和事务有没有提交。自动提交模式下，失败前的命令可能已经各自提交；如果在提交阶段断线，调用方根本无法直接知道最终结果。这时只能按业务唯一键去数据库核对，看哪些操作已经生效。只有确认没有提交、并且已经回滚，才能重试整个业务单元。

## 5. MyBatis 与 JPA 的本地状态 {#3-mybatis-与-jpa-还要处理本地状态}

用框架批量写入时，除了数据库那边的执行，内存里还压着待执行的语句和被跟踪的实体，控制批大小时要把这些本地状态一起管住。

MyBatis 的 `ExecutorType.BATCH` 会把更新延迟到刷新批次时才执行，所以最终影响行数要从刷新后的结果里读。执行时机和返回值见 [MyBatis](./mybatis-mapping-executor-plugins.mdx#3-executor-决定语句复用与批处理方式)。

JPA 的持久化上下文会保留**受管实体**，也就是框架正在跟踪变化的对象。导入一万条数据时，如果一直不清理，上下文里就会攒下一万个实体。所以要按块处理：先 `flush()` 把待写变化同步到数据库，再 `clear()` 解除管理。顺序不能反，先 `clear()` 的话，还没同步的修改就直接丢了。语句最终能不能合批，还取决于主键策略、实体关系和 Hibernate 的批处理配置。

反过来，用批量 DML 直接改数据库时，已经加载的实体不会跟着变，仍然是旧值，需要在明确的边界上清理或刷新。处理顺序见 [JPA](./jpa-entity-states-dirty-checking-lazy-loading.mdx#批量修改与上下文同步)。

## 6. Hibernate 批次与提交频率 {#hibernate-批次与提交频率}

Hibernate 的批处理配置只决定语句怎样交给驱动，事务仍由外层的提交边界决定。Hibernate ORM 5.6/6.2 默认 `hibernate.jdbc.batch_size=0`，设成正数才会为有状态 Session 启用 JDBC 批处理：

```properties
hibernate.jdbc.batch_size=50
hibernate.order_inserts=true
hibernate.order_updates=true
```

`batch_size` 把单批交给驱动的语句上限设为 50。两个 `order_*` 配置会调整插入和更新的执行顺序，让相同的 SQL 排在一起，更容易进入同一批次；排序本身也有成本，要按实际负载验证。另外，使用 IDENTITY 主键策略时，Hibernate 5.6/6.2 会关闭 JDBC 插入合批，因为每插一行都要立刻拿回数据库生成的主键。

每 50 条调用一次 `flush()`、`clear()`，限制的是上下文里的实体数量。如果一万条数据只在最后 commit 一次，它们仍然是一个大事务。想缩短事务就要分批 commit，同时接受一个事实：已经提交的批次是独立成功的，后面的批次失败时，需要单独设计恢复方式。

## 7. Offset 分页成本 {#4-offset-分页的成本随偏移增长}

Offset 分页先跳过指定数量的记录，再返回一页，所以页码越靠后，要跳过的记录越多：

```sql
select id, created_at
from orders
order by created_at desc, id desc
limit 20 offset 1000000;
```

这条 MySQL 8.0 查询只返回 20 行，却要先沿排序结果跳过前一百万行。有匹配排序的索引，可以省掉排序；有**覆盖索引**（索引里包含查询需要的全部列），可以省掉回表取列。但扫描并跳过大量索引项这一步，怎么都省不掉。

Offset 还有正确性问题：翻页期间有人插入或删除数据，后面的记录位置就会整体移动，相邻两页可能出现重复或遗漏。后台管理页面偶尔跳到某一页，用 Offset 没问题；持续下拉或顺序批量扫描，更适合从上一页最后一行接着查。

## 8. Keyset 分页 {#5-keyset-分页从最后一条继续}

**Keyset 分页**用上一页最后一条记录的排序值定位下一页，这组值叫**游标**。查询直接从游标之后开始，不用从头跳过大量记录：

```sql
select id, created_at
from orders
where (created_at, id) < (:lastCreatedAt, :lastId)
order by created_at desc, id desc
limit 20;
```

`created_at` 可能重复，如果只按时间排序，同一时刻的多条记录分在两页时，就分不清哪些已经返回过。所以示例在后面补上主键 `id`，让组合排序唯一。排序键还要稳定，记录才会一直待在游标的同一侧。建索引时，过滤条件和排序顺序要一起考虑。

游标里要保存或编码这些定位信息：

- 上一页末行的排序值，例如 `created_at` 和 `id`。
- 翻页方向，以及和方向匹配的比较规则。
- 查询条件或它的摘要，让游标只对当前这次查询有效。

服务端要校验这些参数，也可以给游标签名，防止客户端篡改。筛选条件变了，就从第一页重新开始。

Keyset 适合拿着上一页游标连续往后翻。它不擅长任意跳页和精确统计总页数，这些都要额外查询，所以选哪种分页方式，要看页面是否需要这些能力。

## 9. 游标与一致性边界 {#游标与一致性边界}

游标解决的是从哪里接着读，至于读出来的结果完不完整，还取决于边界条件和数据变化。上一节的查询要求 `created_at` 和 `id` 都非空，并且组合排序唯一。倒序翻页时下一页用严格小于；如果游标只记时间，同一时刻还没返回的记录就会被漏掉。

`(created_at, id) < (...)` 这种把多个字段作为一组比较的写法叫**元组比较**（行构造器比较）。MySQL 8.0 能不能用好索引，要看执行计划，也可以和下面的等价条件对比：

```sql
created_at < :t OR (created_at = :t AND id < :id)
```

Keyset 能避免前面插入数据导致的位置移动，但它不是数据库快照。记录的排序字段被更新，就可能跨过游标；删除也会改变后续结果，所以重复和遗漏仍然可能出现。

需要精确导出时，就得固定事务快照、冻结数据集，或者按固定的业务版本读取。按单调递增主键扫描时，还可以在开始时记下当前最大 ID 作为截止点，只限制本次扫描不读后来新增的行。已有行的内容仍然可能被修改，这个截止点管不到。

## 10. 关联分页的结果规模 {#6-分页关联数据要控制结果规模}

关联分页先要想清楚：一页的单位是父对象，还是 join 展开以后的结果行。一对多关联会让一个父对象占好几行，直接加 LIMIT 截的是展开后的行，结果是每页的父对象数量忽多忽少，最后一个父对象的子集合还可能不完整。

做法是分两步：先分页查出本页的父 ID，再抓取这些父对象的关联数据，并恢复第一步的顺序，这样每页父对象的数量就稳定了。两次读取之间数据会不会变，取决于事务隔离级别或业务版本，具体过程见 [N+1 查询](./n-plus-one-fetch-strategies.mdx#7-集合抓取与分页要分两步考虑)。

## 11. 目标数据库的访问测试 {#7-数据访问测试使用目标数据库}

数据访问测试要验证的是最终 SQL 在目标数据库上怎样执行，所以要用目标数据库来测。H2 可以测少量通用逻辑，但 MySQL 8.0 的方言、锁、索引、时区和执行计划，只能在同版本上验证。关键的 Repository 或 Mapper 测试，可以用 Testcontainers 启动一个隔离的数据库容器。

测试至少要覆盖这些正确性和执行行为：

- 参数绑定是否正确，包括空值、枚举和时间类型。
- 唯一约束、外键，以及失败后事务回滚的结果。
- 动态 SQL、排序字段白名单和分页边界。
- 关联查询的次数（发现 N+1），以及写入是否真的走了批处理。
- 并发更新、锁等待和超时后的处理结果。
- 数据库迁移脚本能否兼容已有数据。

有一类问题自动回滚的测试发现不了：测试执行到回滚就结束了，提交之后的行为根本没跑到。需要验证提交后的缓存、事件或数据可见性时，要显式 commit，再开一个新事务读取检查。有些约束数据库是在提交时才检查的，这类测试也要走到真实提交。

## 12. 性能与结果验证 {#8-性能验证同时记录结果正确性}

性能验证要同时证明两件事：执行更快了，结果仍然正确，而且数据规模要接近实际使用。为了能和其他方案比较，记录下面这些内容：

- 批大小、行宽、索引、驱动配置和提交频率，保证不同测试的条件可比。
- 吞吐、P99、重试次数和数据库资源消耗，判断加速是不是只是把成本转移到了别处。
- 影响行数、重复键、遗漏记录和返回顺序，以及并发修改后的分页结果。

只有性能和结果都达标，才换用新的批处理或分页方案。

### 13.1 `limit 1000000, 20` 为什么慢，怎样改进 {#deep-pagination}

**考察重点**

- 解释为什么只返回 20 行，仍要扫描并跳过大量记录。
- 区分覆盖索引、先查主键再关联详情，以及 Keyset 各自减少的成本。
- 说明稳定排序和并发插入、删除怎样影响分页结果。

**相关内容**：[Offset 成本](#4-offset-分页的成本随偏移增长)、[Keyset](#5-keyset-分页从最后一条继续)、[游标边界](#游标与一致性边界)。

<details>
<summary>参考回答</summary>

**它慢在 MySQL 仍需沿排序结果跳过前一百万行，才能返回后面的 20 行。**

如果查询列不能由索引覆盖，被跳过的行还可能产生回表成本。

需要任意跳页时，可以保留 Offset，但先用覆盖索引查出本页主键，再关联取详情，减少回表量。连续翻页则改用 Keyset：用 `created_at` 加 `id` 组成唯一游标，并建立匹配的索引，每次从上一页末尾继续。

改完要在目标数据库和实际数据量下比较执行计划、扫描行数与接口延迟，还要检查并发插入、删除后有没有重复和遗漏。

</details>

**考察重点**

<summary>参考回答</summary>

**不能凭猜测的失败位置继续，因为驱动可能在失败处停下，也可能继续执行了后面的命令。**

### 13.3 JPA 批量插入为什么要先 flush 再 clear？ {#flush-clear}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 解释 flush 怎样同步待写变化，以及 clear 怎样减少上下文保留的实体。
- 说明主键生成策略和批处理配置怎样影响插入合批。

**相关内容**：[本地状态](#3-mybatis-与-jpa-还要处理本地状态)、[批处理事务](#批处理结果与事务示例)。

<details>
<summary>参考回答</summary>

**先 flush 把待写变化同步到数据库，再 clear 解除实体管理，这样既不丢修改，又能限制上下文里的实体数量。**

反过来先 clear，尚未同步的修改会被直接丢弃。按块处理减少的是持久化上下文的内存占用，最终提交仍由事务控制。

语句能否合批还取决于 SQL 形态、实体关系、主键生成策略和 `hibernate.jdbc.batch_size`。例如 Hibernate 5.6/6.2 使用 IDENTITY 策略时，会关闭 JDBC 插入合批。

</details>

**考察重点**

- 解释唯一排序、非空字段和严格比较怎样处理页边界。
- 区分固定快照与最大 ID 截止点，并说明排序字段修改的影响。

**相关内容**：[Keyset](#5-keyset-分页从最后一条继续)、[一致性边界](#游标与一致性边界)。

<details>
<summary>参考回答</summary>

**不能。游标只记录读到了哪里，没有冻结数据版本。**

记录的排序字段被修改，可能跨到游标另一侧；删除也会改变后续结果，所以仍可能重复或遗漏。

Keyset 能做到的是处理好页边界：排序唯一且稳定，字段非空，按方向使用严格比较，并规定好翻页方向和查询条件。要精确导出，就得固定事务快照、冻结数据集或按业务版本读取。记录最大 ID 作为截止点只能排除新增行，已有行的内容仍可能变化。

</details>

### 13.5 hibernate.jdbc.batch_size=50 是否表示每 50 条自动提交？ {#batch-size-commit-boundary}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：区分单批语句上限、上下文清理和事务提交，并说明分批提交后的失败范围。

**相关内容**：[Hibernate 批次与提交频率](#hibernate-批次与提交频率)。

<details>
<summary>参考回答</summary>

**不是。`hibernate.jdbc.batch_size=50` 只设置单批语句上限，事务什么时候提交仍由 commit 决定。**

即使每 50 条 flush、clear 一次，一万条数据也可以都在同一个事务里。

如果要求每 50 条提交，就要显式划分事务。这样后面的批次失败时，前面已提交的批次仍然有效，恢复和重试要按这个范围设计。

</details>
