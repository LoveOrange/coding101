# JPA

JPA 通过持久化上下文管理实体身份与变化。本文负责状态转换、脏检查、关联写入和乐观锁。采用 Jakarta Persistence 3.2，示例实现为 Hibernate ORM 7.1。

抓取优化见 [N+1 查询](./n-plus-one-fetch-strategies.mdx)。批量执行与分页见 [批处理与分页](./batching-pagination-data-access-tests.mdx)。

## 1. 面试核心 {#core}

- managed 实体在 flush 时同步变化，事务在 commit 时提交。[卡](#dirty-checking)
- merge 复制 detached 对象状态，返回受管实例，原对象仍脱管。[卡](#merge-identity)
- LAZY 是加载提示，EAGER 是加载要求，均未指定 SQL 形态。[卡](#fetch-cascade)
- `@Version` 通过版本校验检测并发覆盖。[卡](#bulk-version)
- AUTO 模式确保查询考虑相关待写变化，COMMIT 模式的查询效果未指定。[卡](#flush-mode-query)

## 2. 持久化上下文与实体身份 {#1-持久化上下文维护实体身份}

EntityManager 关联持久化上下文。同一上下文中，一个持久化身份对应一个受管实例：

```java
Order first = entityManager.find(Order.class, 101L);
Order second = entityManager.find(Order.class, 101L);

assert first == second;
```

身份映射复用已加载实例，并支持脏检查。上下文结束后，原对象脱管。EntityManager 面向单线程使用，共享访问需避免。

## 3. 实体状态 {#2-实体有四种主要状态}

- **new**：刚创建，尚未与持久化上下文关联。
- **managed** 实体由当前上下文管理，变化在同步时写入数据库。
- **detached**：有持久化身份，但已离开当前上下文。
- **removed**：已标记删除，将在同步时执行删除。

persist 让新实体进入 managed。find 或实体查询返回受管对象。detach、clear 或上下文关闭会让对象脱管。remove 把受管实体标记为 removed。

## 4. merge 的状态复制与返回值 {#3-merge-返回新的受管实例}

```java
Order detached = previousOrder; // 来自已关闭的上下文
Order managed = entityManager.merge(detached);
```

merge 把 detached 状态复制到受管目标，并返回目标。原 detached 对象仍脱管，后续应修改返回对象。目标可复用上下文中的实例，也可由提供者新建。传入 managed 对象时，返回该受管对象。

事务内修改受管实体，flush 时即可同步。每次 setter 后无需额外调用 merge。

## 5. 脏检查与 flush {#4-脏检查在-flush-时同步变化}

```java
@Transactional
public void rename(long id, String name) {
    Customer customer = entityManager.find(Customer.class, id);
    customer.rename(name);
}
```

提供者跟踪受管实体，flush 时检测变化并生成 SQL。Hibernate 可使用快照比较或字节码增强。

flush 把变化同步给数据库，事务仍可回滚。SQL 执行时间还受主键生成与查询模式影响。

## 6. 事务与上下文边界 {#5-事务边界决定状态管理范围}

关闭 OSIV 且使用事务范围上下文时，事务结束后关闭上下文。实体随后成为 detached。扩展上下文则可跨越多个事务。

回滚后的 Java 字段没有自动恢复保证。重试需开启新事务，重新读取并执行业务判断。长期保存脱管实体，会让版本与关联加载难以管理。

## 7. 懒加载与上下文 {#6-懒加载需要可用的持久化上下文}

Hibernate 可用代理或持久化集合承载 LAZY 关联。访问尚未初始化的内容时触发加载：

```java
Order order = repository.findById(id).orElseThrow();
return order.getItems().size();
```

默认配置下，关闭 Session 后初始化代理会抛出异常。异常类型是 LazyInitializationException。已加载字段则可继续访问。

服务层按用例抓取并映射 DTO，可固定查询边界。具体抓取方式见 [N+1 查询](./n-plus-one-fetch-strategies.mdx)。

## 8. OSIV 的上下文范围 {#7-osiv-延长的是上下文不是业务事务}

OSIV 让持久化上下文覆盖 Web 响应阶段。序列化因此仍可触发懒加载，但原业务事务已结束。

API 服务可在服务事务内完成查询与 DTO 映射。测试应覆盖真实序列化过程，确认额外查询的位置和数量。

## 9. 乐观锁与版本校验 {#8-乐观锁处理并发覆盖}

```java
@Version
private long version;
```

`@Version` 让更新检查读取时的版本，并推进版本。版本不匹配时抛出乐观锁异常。脏检查负责发现变化，版本校验负责检测并发覆盖。

重试应重新读取，并执行完整业务判断。

## 10. 关联所有权、级联与抓取 {#关联所有权级联与抓取}

双向关系由 owning side 决定关系写入。mappedBy 指向拥有方字段。只修改反向集合时，外键更新由拥有方状态决定。应用应同时维护两侧对象关系。

cascade 控制 persist、merge、remove 等操作传播。fetch 控制关联加载要求，两者职责独立。

Persistence 3.2 的 ManyToOne、OneToOne 默认 EAGER。OneToMany、ManyToMany 默认 LAZY。LAZY 允许提供者提前加载，EAGER 也可用次级查询实现。

orphanRemoval 适用于 OneToOne 与 OneToMany。受管子实体移出关系后，会在 flush 时被删除。它适合父对象私有的子实体。共享对象的删除需单独定义生命周期。

## 11. 批量修改与上下文同步 {#批量修改与上下文同步}

JPQL bulk DML 直接作用于数据库。已加载对象保持原状态，普通实体版本校验也被绕过。批量 SQL 需自行声明版本条件与版本递增。

已有修改先 flush，再执行批量 DML，随后 clear 或 refresh。提前 clear 会丢弃待同步变化。

版本冲突可在 flush 或 commit 时暴露。异常后结束事务，在新上下文读取并重试。

## 12. FlushMode 与查询可见性 {#flushmode-与查询可见性}

事务已加入上下文时，默认 AUTO 模式考虑相关待写变化。查询结果必须反映会影响它的受管实体更新。提供者可通过 flush 或其他方式满足要求。

COMMIT 模式在提交时 flush。提交前，内存修改对查询结果的影响未指定。提供者也允许在其他时机提前 flush。

```java
entityManager.setFlushMode(FlushModeType.COMMIT);
customer.rename("new-name");
entityManager.flush();
```

显式 flush 让待写变化先同步到数据库。事务仍需 commit，且后续仍可回滚。
