# 数据库连接池

数据库连接池复用物理连接，并限制应用同时占用数据库的连接数量。本文以 HikariCP 为例，讲解连接复用、容量、超时与泄漏诊断。内容也包括池内部的性能机制。容量选择同时受应用并发和数据库承载能力约束。

## 1. 面试核心 {#core}

- 池复用物理连接，业务关闭代理连接表示归还；异常路径和事务管理必须保证资源释放。[卡](#connection-pool-config)
- `maximumPoolSize` 限制池内连接总数，所有实例的池上限之和构成数据库连接容量预算。[卡](#pool-capacity)
- `connectionTimeout` 限制取连接的等待。`Statement.setQueryTimeout` 限制语句执行时间。两者分别消耗请求预算。[卡](#timeout-budget)
- `maxLifetime` 控制连接轮换，使用中的连接归还后才淘汰。`keepaliveTime` 只作用于空闲连接。
- `leakDetectionThreshold` 在借用超过阈值时记录堆栈。连接仍由业务或事务管理器归还。[卡](#pool-exhaustion)

## 2. 代理连接与资源归还 {#1-close-把代理连接归还池中}

```java
try (Connection connection = dataSource.getConnection()) {
    // execute SQL
}
```

HikariCP 返回代理 Connection。业务调用 `close()` 后，代理重置必要状态。然后，它将可复用的物理连接归还池中。手动通过 DataSource 借连接时，try-with-resources 仍然是正确写法。若使用 Spring/JdbcTemplate/MyBatis-Spring 管理事务，应让框架管理连接。框架按事务边界获取和释放连接。应用应避免绕过绑定资源另借连接。

DataSource 和连接池应作为长生命周期组件管理。每次请求新建一个池，会失去复用能力。并发请求还会因此创建大量物理连接。

## 3. 连接池容量 {#2-maximumpoolsize-是并发上限}

HikariCP 的 `maximumPoolSize` 包含空闲和正在使用的连接。当池已达到上限且没有可用连接时，新的 `getConnection()` 会等待。等待超过 `connectionTimeout` 后，它会抛出异常。

池大小至少要考虑三项因素：

- 确认数据库允许多少连接，以及能高效处理多少并发连接。
- 确认单实例数据库操作的并发量，以及每次持有连接的时间。
- 统计共享同一数据库的应用实例数量。

例如 20 个实例各设 100，连接总上限为 2000；吞吐由数据库锁、I/O、CPU 和内存瓶颈决定。

## 4. 容量验证指标 {#3-用等待与吞吐验证容量}

初始容量应通过压测和生产指标校准。需要观察以下指标：

- 观察 active、idle、pending 连接数。
- 记录获取连接的等待时间与超时数。
- 记录 SQL 执行和事务持有时间。
- 观察数据库 CPU、I/O、锁等待及最大连接使用量。
- 统计应用实例扩缩容后的总连接数。

若 active 长期满且数据库仍有余量，可以评估增加容量；若数据库已经饱和，扩池会让更多慢查询同时进入数据库。先优化查询、缩短事务或限制上游并发。

## 5. 超时预算 {#4-超时要形成递减预算}

- `connectionTimeout`：它限制从池中等待可用连接的最长时间。
- JDBC 查询超时：它限制一条语句的执行时间。
- 事务超时：它限制整个数据库工作单元的持续时间。
- 请求超时：它限制调用方等待整个接口的时间。

各阶段预算应从请求剩余时间分配，并为回滚和释放资源预留时间。一次事务内多条 SQL 的时间会累积，重试也要消耗同一总预算。若只设置连接获取超时，未结束的慢 SQL 仍会占用连接。还需要设置查询与事务超时。

## 6. 连接生命周期 {#5-连接生命周期配合基础设施}

`maxLifetime` 限制物理连接的使用寿命。数据库、代理或网络若有连接寿命上限，该值应比上限略短。使用中的连接不会在执行期间被强行关闭，归还后才会淘汰。

`keepaliveTime` 可以在空闲连接上执行保活检查，并且必须短于 maxLifetime。JDBC 4 驱动优先使用 `Connection.isValid()`；没有必要时不要额外设置 validation query。

`minimumIdle` 未单独设置时，HikariCP 默认将它设为 maximumPoolSize。这会形成固定容量池。动态缩减是否有价值，要根据资源成本和流量模式决定。

## 7. 连接泄漏检测 {#6-泄漏检测提供线索}

连接长时间未归还的常见原因包括：

- 应用在异常路径上没有调用 close。
- 事务包含远程调用、文件处理或长时间计算。
- 流式 ResultSet 尚未关闭。
- 异步任务或线程切换破坏了资源边界。
- 数据库阻塞让连接看起来长期未归还。

HikariCP 用 `leakDetectionThreshold` 检测疑似泄漏。连接离池超过该阈值时，HikariCP 会记录借用堆栈。业务仍负责归还连接。长事务和慢 SQL 超过同一阈值时也会触发告警。

## 8. 连接池耗尽的排查顺序 {#7-连接池耗尽的排查顺序}

1. 确认 pending、active 和获取超时是否同步上升。
2. 查看占用连接最长的调用栈、事务和 SQL。
3. 在数据库侧检查运行语句、锁等待和连接状态。
4. 判断是连接未归还、查询变慢，还是流量超过容量。
5. 修复根因后重新压测池大小和超时，不直接永久扩容。

## 9. 容量估算与多连接占用 {#容量估算与多连接占用}

稳定负载下，可粗略估算平均同时借出的连接数。估算公式为“每秒借用次数 × 平均持有秒数”。例如每秒 400 次借用，每次 50ms，平均约占用 20 个连接。这是平均占用量，容量还需为峰值与长尾预留余量。还要看峰值、长尾、等待目标和数据库饱和点。

多实例部署要计算所有池的总上限。还要为管理、迁移和其他服务预留连接。扩容应用实例会放大总连接数，需同步核对数据库容量。

请求持有连接再申请第二个连接，会增加池内资源等待的风险。例如外层事务挂起，但仍占有连接。内层 `REQUIRES_NEW` 又申请新连接。当池中连接都被这类外层事务占用时，内层事务只能等待。这就形成了池内资源等待。应优先减少嵌套持有。再根据最坏同时占用量与数据库容量评估池大小。

## 10. 超时取消与连接轮换 {#超时取消与连接轮换}

`connectionTimeout` 约束取连接等待，SQL 执行由查询超时管理。JDBC `Statement.setQueryTimeout` 约束语句执行。驱动如何取消、网络异常多久返回，需要按驱动与数据库验证。还要验证数据库是否终止工作。事务超时还取决于事务管理器如何传递到语句。

例如请求总预算为 1s，连接等待已经用了 300ms。这时，执行、回滚、释放和响应合计只剩 700ms。外层 HTTP 超时后，查询仍需由线程或驱动取消。若查询没有真正取消，连接仍处于占用状态。

`maxLifetime` 管理连接轮换；使用中的连接会等到归还后再淘汰。因此，事务执行时间需要单独限制。这能避免事务超过基础设施的连接时限。处理空闲连接超时，应结合 keepalive、池的空闲管理与基础设施策略。不要把所有超时都折算成一个连接寿命值。

### 10.1 HikariCP 的内部性能机制 {#hikaricp-的内部性能机制}

HikariCP 优化了连接交接、代理调用和小型集合等高频操作：

- **ConcurrentBag**：它优先从 ThreadLocal 缓存寻找可复用连接。它还通过共享集合、跨线程获取和直接交接服务等待者。这些机制减少竞争与交接延迟。CAS 用于协调借出状态。
- **字节码与 JIT 内联**：HikariCP 缩短热点方法，并简化继承层次。这能减少类型转换和调用开销，使关键路径更适合 JIT 内联。
- **FastList**：连接代理用它记录打开的 Statement。内部逻辑已保证下标有效，因此它去掉了下标范围检查。删除时，它从尾部开始查找。后创建的 Statement 通常先关闭，这样更容易找到目标。

这些优化降低池自身借还与代理管理的开销；端到端延迟仍取决于 SQL、锁等待、网络和连接持有时间。比较性能时，应保持驱动、池容量和负载相同。再比较等待时间与吞吐。

**考察重点**

- 理解告警阈值与借用栈。
- 理解数据库阻塞、应用持有与最终归还。

**相关内容**：[连接泄漏检测](#6-泄漏检测提供线索)、[连接池耗尽的排查顺序](#7-连接池耗尽的排查顺序)。

<details>
<summary>参考回答</summary>

泄漏告警只说明借出时间超过阈值。沿借用栈检查异常路径和 close。再关联事务、正在执行的 SQL、数据库锁等待与远程调用。若工作结束后正常归还连接，应查看连接持有时间花在哪里。若主要花在慢 SQL 或锁等待上，就应按慢事务处理。如果代码失去连接引用且未归还，才有明确泄漏证据。泄漏检测只记录线索。要恢复资源归还，仍需修复 close 或事务结束路径。

</details>
