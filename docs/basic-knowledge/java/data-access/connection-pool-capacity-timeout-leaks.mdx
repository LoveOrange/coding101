# 数据库连接池

数据库连接池复用物理连接，并限制应用同时占用数据库的连接数量。连接池容量配置要同时服从应用并发和数据库承载能力；本文以 HikariCP 为配置示例：数据库有余量时扩池可能提高吞吐，数据库已饱和时扩池可能加剧争用，不能只看应用侧排队。

## 1. 面试核心 {#core}

- 池复用物理连接，业务关闭代理连接表示归还；异常路径和事务管理必须保证资源释放。[卡](#connection-pool-config)
- 容量受实例总数、连接持有时间和数据库承载能力共同约束，扩池是否有效要看瓶颈。[卡](#pool-capacity)
- 获取连接、SQL 执行、事务与请求是不同超时范围；外层超时不保证内层工作已经取消。[卡](#timeout-budget)
- maxLifetime 用于连接轮换，使用中的连接归还后才淘汰；keepalive 只检查空闲连接。
- leakDetectionThreshold 报告疑似长时间借用，不会强行回收；耗尽时要区分泄漏、慢 SQL、锁等待和流量过载。[卡](#pool-exhaustion)

## 2. close 把代理连接归还池中 {#1-close-把代理连接归还池中}

```java
try (Connection connection = dataSource.getConnection()) {
    // execute SQL
}
```

池返回的通常是代理 Connection。调用 `close()` 会重置必要状态并归还物理连接，而不是每次断开 TCP。手动通过 DataSource 借连接时，try-with-resources 仍然是正确写法。若使用 Spring/JdbcTemplate/MyBatis-Spring 管理事务，应让框架按事务边界获取和释放连接，避免绕过绑定资源另借连接。

DataSource 和连接池应作为长生命周期组件管理。每次请求新建一个池，会失去复用能力，并可能同时创建大量物理连接。

## 3. maximumPoolSize 是并发上限 {#2-maximumpoolsize-是并发上限}

HikariCP 的 `maximumPoolSize` 包含空闲和正在使用的连接。当池已达到上限且没有可用连接时，新的 `getConnection()` 会等待，超过 `connectionTimeout` 后抛出异常。

池大小至少受三项约束：

- 数据库允许并能高效处理的并发连接。
- 单实例数据库操作的并发量和持有时间。
- 共享同一数据库的应用实例数量。

例如 20 个实例各设 100，不代表系统获得 2000 份吞吐；数据库可能先在锁、I/O、CPU 和内存上进入竞争。

## 4. 用等待与吞吐验证容量 {#3-用等待与吞吐验证容量}

初始容量应通过压测和生产指标校准。观察：

- active、idle、pending 连接数。
- 获取连接的等待时间与超时数。
- SQL 执行和事务持有时间。
- 数据库 CPU、I/O、锁等待及最大连接使用量。
- 应用实例扩缩容后的总连接数。

若 active 长期满且数据库仍有余量，可以评估增加容量；若数据库已经饱和，继续扩池只会让更多慢查询同时进入数据库。先优化查询、缩短事务或限制上游并发。

## 5. 超时预算 {#4-超时要形成递减预算}

- `connectionTimeout`：从池中等待可用连接的最长时间。
- JDBC 查询超时：一条语句允许执行多久。
- 事务超时：整个数据库工作单元允许持续多久。
- 请求超时：调用方等待整个接口的预算。

需要按请求剩余时间分配获取连接、执行与清理预算，不能仅让三个配置数字递减。一次事务内多条 SQL 的时间会累积，重试也要消耗同一总预算。只有连接获取超时，没有查询与事务超时，连接仍可能被慢 SQL 长期占用。

## 6. 连接生命周期配合基础设施 {#5-连接生命周期配合基础设施}

`maxLifetime` 限制物理连接的使用寿命，通常设置得比数据库、代理或网络设备的连接时限略短。使用中的连接不会在执行期间被强行关闭，归还后才会淘汰。

`keepaliveTime` 可以在空闲连接上执行保活检查，并且必须短于 maxLifetime。JDBC 4 驱动优先使用 `Connection.isValid()`；没有必要时不要额外设置 validation query。

`minimumIdle` 未单独设置时，HikariCP 默认与 maximumPoolSize 相同，形成固定容量池。动态缩减是否有价值，要根据资源成本和流量模式决定。

## 7. 泄漏检测提供线索 {#6-泄漏检测提供线索}

连接泄漏的常见原因包括：

- 异常路径没有 close。
- 事务范围包住远程调用、文件处理或长时间计算。
- 流式 ResultSet 尚未关闭。
- 异步任务或线程切换破坏资源边界。
- 数据库阻塞让连接看起来长期未归还。

HikariCP 的 `leakDetectionThreshold` 会在连接离池超过阈值时记录可能的泄漏堆栈。它只记录诊断信号，不会强行回收正在使用的连接，也不能证明连接永久丢失；合法的长事务和慢 SQL 也可能触发。

## 8. 连接池耗尽的排查顺序 {#7-连接池耗尽的排查顺序}

1. 确认 pending、active 和获取超时是否同步上升。
2. 查看占用连接最长的调用栈、事务和 SQL。
3. 在数据库侧检查运行语句、锁等待和连接状态。
4. 判断是连接未归还、查询变慢，还是流量超过容量。
5. 修复根因后重新压测池大小和超时，不直接永久扩容。

## 9. 容量估算与多连接占用 {#capacity-example}

在稳定负载下，平均同时借出的连接数可以粗略估算为“每秒借用次数 × 平均持有秒数”。例如每秒 400 次借用，每次 50ms，平均约占用 20 个连接；这是占用量估计，不是建议直接把池设成 20。还要看峰值、长尾、等待目标和数据库饱和点。

多实例部署要计算所有池的总上限，并为管理、迁移和其他服务预留连接。扩容应用实例可能放大总连接数，单实例配置没变也可能压垮数据库。

一个请求持有连接再申请第二个连接时，可能在池内形成资源等待。典型例子是外层事务挂起但仍占有连接，内层 `REQUIRES_NEW` 又申请新连接。多个线程都持有一条再等待第二条时，数据库侧甚至没有锁冲突也可能卡住。优先减少嵌套持有，再根据最坏同时占用量与数据库容量评估池大小。

## 10. 超时取消与连接轮换 {#timeout-cancellation}

`connectionTimeout` 只约束从池中取连接的等待，不能限制已开始的 SQL。JDBC `Statement.setQueryTimeout` 约束语句执行，但驱动如何取消、网络异常多久返回，以及数据库是否终止工作，需要按驱动与数据库验证；事务超时还取决于事务管理器如何传递到语句。

例如请求总预算 1s，连接等待已经用了 300ms，就不能再给每条 SQL 各 900ms。应使用剩余预算，留出回滚、释放与响应时间。外层 HTTP 超时后，若线程或驱动没有真正取消查询，连接仍可能被占用。

maxLifetime 管理的是连接轮换，不是 SQL 超时。数据库或代理在使用途中强行断开连接时，较短的 maxLifetime 也不能保护一条无限长的事务。对空闲连接超时可结合 keepalive、池的空闲管理与基础设施策略；不要把所有超时都折算成一个连接寿命值。

<summary>参考回答</summary>

</details>

**考察重点**

- 告警阈值与借用栈。
- 数据库阻塞、应用持有与最终归还。

**相关内容**：[泄漏检测提供线索](#6-泄漏检测提供线索)、[连接池耗尽的排查顺序](#7-连接池耗尽的排查顺序)。

<details>
<summary>参考回答</summary>

泄漏告警只说明借出时间超过阈值。沿借用栈检查异常路径和 close，再关联事务、正在执行的 SQL、数据库锁等待与远程调用。若工作结束后正常归还，可能是慢事务；如果代码失去连接引用且未归还，才有明确泄漏证据。泄漏检测不会强制回收，单纯降低 maxLifetime 或扩池不能修复根因。

</details>
