# N+1 查询

N+1 查询指列表查询后，又逐项查询关联数据。本文负责定位证据、抓取策略与关联分页。采用 Jakarta Persistence 3.2 和 Hibernate ORM 7.1。

实体与懒加载边界见 [JPA](./jpa-entity-states-dirty-checking-lazy-loading.mdx)。游标条件见 [批处理与分页](./batching-pagination-data-access-tests.mdx)。

## 1. 面试核心 {#core}

- N+1 的查询量随未加载关联增长，缓存与批抓取会改变实际次数。[卡](#n-plus-one)
- EAGER 和 EntityGraph 声明加载要求，SQL 形态由提供者决定。[卡](#eager-query-count)
- 同时 join 多个一对多集合，会产生集合基数的乘积行。[卡](#join-explosion)
- 父 ID 分页后再抓取关联，可保持父对象页大小。[卡](#collection-pagination)
- Hibernate 的 `@BatchSize(size=16)` 合批读取待加载关联。[卡](#batch-fetch-vs-jdbc-batch)

## 2. 列表访问与关联查询 {#1-一次列表访问怎样变成-n1}

```java
List<Order> orders = orderRepository.findAll(); // 1 次

for (Order order : orders) {
    render(order.getCustomer().getName());       // 最多 N 次
}
```

假设首次查询仅加载 Order，customer 尚未初始化。循环访问不同 customer 时，Hibernate 继续发 SQL。关联越多，往返开销越大。

循环内逐项调用 Mapper、RPC 或缓存，也会产生相同结构。

## 3. SQL 与指标证据 {#2-先用-sql-与指标确认问题}

排查一条列表接口时，至少记录：

- 一次请求的 SQL 总数和重复 SQL 模板。
- 每条 SQL 的耗时、返回行数和扫描行数。
- 数据库连接占用时间与等待时间。
- 页面大小变化时，SQL 数量是否按比例增长。

开发环境可用 SQL 日志定位。生产环境结合采样追踪、查询统计与慢查询。记录模板即可，敏感参数需脱敏。

## 4. Join Fetch 关联抓取 {#3-join-fetch-一次取回已知关联}

```java
select o
from Order o
join fetch o.customer
where o.status = :status
```

join fetch 可在本次 SQL 中加载指定关联。to-one 每个父行最多对应一个目标。可空关联使用 left join fetch，可保留无关联的父行。

to-many 会展开父行，同时抓取多个集合会放大行数。Hibernate 6 起自动去除 fetch join 的重复根实体。子行仍需传输与物化，distinct 无法消除这部分成本。

## 5. EntityGraph 加载范围 {#4-entitygraph-按用例选择加载范围}

EntityGraph 为某次查询声明所需属性。可用 NamedEntityGraph 或动态创建图。不同接口因此可以指定不同的加载范围。

fetchgraph 中列出的属性按 EAGER 处理。其余属性按 LAZY 处理，提供者仍可额外加载。loadgraph 对图外属性保留映射中的抓取设置。两种图都需核对实际 SQL 数量。

## 6. 关联批量抓取 {#5-批量抓取减少往返次数}

Hibernate batch fetching 合并待加载实体或集合。它按关联主键组织 IN 查询，减少逐项往返。

这种方式适合 join 会放大结果集的用例。查询次数仍受批大小、缓存与访问顺序影响。手写查询也可收集外键，批量读取后按键回填。

## 7. DTO 投影 {#6-dto-投影只读取接口需要的数据}

列表接口若只显示订单号、客户名和金额，可以直接查询 DTO：

```java
select new com.example.OrderRow(o.id, c.name, o.amount)
from Order o
join o.customer c
where o.status = :status
```

这个 DTO 只保存标量字段，序列化时无需继续抓取关联。结果服务于当前用例，修改 DTO 不会触发实体脏检查。

## 8. 集合抓取与父对象分页 {#7-集合抓取与分页要分两步考虑}

to-many join fetch 会让同一父记录重复多次。按 SQL 行分页会切断集合；Hibernate 可退回内存分页。父对象分页可以分两阶段：

1. 先按稳定排序分页查询父对象 ID。
2. 再按这一页 ID 抓取详情和关联。
3. 在内存中按第一页的顺序组装结果。

两阶段限定父对象范围，关联仍可分批加载。IN 查询结果需恢复第一阶段的顺序，空 ID 页直接返回。两次读取的一致性取决于事务隔离与版本协议。

## 9. 抓取范围与结果基数 {#抓取范围与结果基数}

20 个订单都引用同一客户时，上下文可复用该客户。首次加载后，剩余访问无需再次查询。EAGER 也可通过次级查询实现，注解无法直接给出次数。

一个订单有 10 个商品和 8 个标签。同时 join 两个集合时，该订单展开为 80 行。分别查询则按各集合规模读取。多个 bag 集合的同时抓取还会触发 Hibernate 的限制。

Hibernate 7.1 可设置：

```properties
hibernate.query.fail_on_pagination_over_collection_fetch=true
```

这样遇到集合抓取分页会直接失败。测试可尽早暴露内存分页，再改为两阶段查询。

## 10. 查询回归验证 {#8-防止问题再次出现}

- 为关键接口添加 SQL 数量上限或查询统计断言。
- 用真实页面大小测试，不只查一条数据。
- 代码评审检查循环内 Repository/Mapper 调用和实体序列化。
- 压测同时观察连接池等待、数据库 CPU 和返回行数。
- 新增关联字段时重新检查查询策略。

## 11. 批量抓取与写入合批 {#批量抓取与写入合批}

Hibernate 7.1 可用 `@BatchSize(size=16)` 配置读取合批。注解可用于实体类型或集合属性。全局设置为 `hibernate.default_batch_fetch_size=16`。

触发一次懒加载时，Hibernate 收集同上下文中的候选项。例如一批未初始化的同类实体代理，会被合并查询。候选数量不足、缓存命中或锁模式变化时，实际批次会变化。

`hibernate.jdbc.batch_size` 则控制写入语句合批。它不会消除逐条关联 SELECT。写入配置见 [批处理与分页](./batching-pagination-data-access-tests.mdx#hibernate-批次与提交频率)。

### 12.3 一条 SQL 同时抓两个集合，为什么可能比三条 SQL 更慢？ {#join-explosion}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**

- 说明笛卡尔放大。
- 说明传输与物化成本。

**相关内容**：[Join Fetch](#3-join-fetch-一次取回已知关联)、[结果基数](#抓取范围与结果基数)。

<details>
<summary>参考回答</summary>

两个一对多集合会展开为乘积行。父实体去重后，已发生的传输与物化成本仍存在。分别抓取可减少结果行数，但增加往返。应比较总行数、行宽与延迟。

</details>

### 12.4 带一对多详情的分页接口怎样保持页大小和顺序？ {#collection-pagination}

- 说明父记录分页与关联展开。
- 说明两次读取的一致性。

**相关内容**：[集合分页](#7-集合抓取与分页要分两步考虑)。

<details>
<summary>参考回答</summary>

Hibernate 7.1 可将集合抓取分页配置为失败。参数是 `hibernate.query.fail_on_pagination_over_collection_fetch=true`。两阶段之间的并发变化仍需事务或版本协议处理。

</details>
