# N+1 查询

N+1 查询是先查出 N 个主对象，再为每个对象分别查询关联数据，最终产生 1+N 次数据库往返。它通常由循环内查询或 ORM 懒加载触发，只有观察实际 SQL 数量才能确认。

## 1. 面试核心 {#core}

- N+1 要用 SQL 数量与重复模板证明，次数也受关联去重、缓存及批抓取影响。[卡](#n-plus-one)
- EAGER 仍可能发次级查询，EntityGraph 也不保证只有一条 SQL。[卡](#eager-query-count)
- to-one 抓取与多个 to-many 抓取的行数放大不同，不能只数 SQL 条数。[卡](#join-explosion)
- 集合 fetch join 与分页可能导致内存分页，优先先取父 ID，再抓需要的数据。[卡](#collection-pagination)
- 回归测试同时观察查询数、返回行数、连接占用和分页正确性。[卡](#n-plus-one)

## 2. 一次列表访问怎样变成 N+1 {#1-一次列表访问怎样变成-n1}

```java
List<Order> orders = orderRepository.findAll(); // 1 次

for (Order order : orders) {
    render(order.getCustomer().getName());       // 最多 N 次
}
```

第一次查询只加载 Order。循环访问未加载的 customer 时，Hibernate 为每个不同关联继续发 SQL。小数据集看不出问题，分页数量或延迟上升后，往返成本会线性放大。

N+1 并不限于 ORM：在循环中手工调用 Mapper、RPC 或缓存，也会形成相同结构。

## 3. 先用 SQL 与指标确认问题 {#2-先用-sql-与指标确认问题}

排查一条列表接口时，至少记录：

- 一次请求的 SQL 总数和重复 SQL 模板。
- 每条 SQL 的耗时、返回行数和扫描行数。
- 数据库连接占用时间与等待时间。
- 页面大小变化时，SQL 数量是否按比例增长。

开发环境打开 SQL 日志只能帮助定位，生产环境更适合使用低开销指标、采样追踪和慢查询。不要把完整参数和敏感字段长期写入日志。

## 4. Join Fetch 一次取回已知关联 {#3-join-fetch-一次取回已知关联}

```java
select o
from Order o
join fetch o.customer
where o.status = :status
```

对 to-one 关联，join fetch 通常能直接消除额外查询。对 to-many 集合，SQL 会产生父行与子行的组合，结果集可能显著膨胀；同时抓取多个集合还可能形成笛卡尔积。

Hibernate 6/7 会在物化后自动去除 join fetch 产生的重复根实体，通常无需为了该目的添加 distinct。SQL 层去重与父实体去重不是同一过程；子行不同仍会占据结果集，不能据 distinct 断言传输量减少。选择 join fetch 前要估算关联基数和返回列宽。

## 5. EntityGraph 按用例选择加载范围 {#4-entitygraph-按用例选择加载范围}

`@NamedEntityGraph` 或动态 EntityGraph 可以在不改实体默认抓取设置的前提下，为某次查询声明所需关联。它适合多个接口对同一实体需要不同视图的情况。

EntityGraph 描述要抓取什么，具体 SQL 形态仍由提供者决定。需要通过实际 SQL 和查询计划验证，不能把声明当作“一定只有一条 SQL”的承诺。

## 6. 批量抓取减少往返次数 {#5-批量抓取减少往返次数}

Hibernate batch fetching 会收集一批待加载关联的主键，用 `where id in (...)` 等形式分批查询。它可以把 N 次降为若干次，适合 join 会产生巨大结果集、又无法提前确定每个关联是否都会访问的情况。

批量抓取缓解了 N+1，但查询数量仍取决于批大小和访问模式。IN 参数上限、执行计划与结果集大小也需要压测。

手写数据访问可以先收集所有外键，批量查询后按 key 分组回填，原理相同。

## 7. DTO 投影只读取接口需要的数据 {#6-dto-投影只读取接口需要的数据}

列表接口若只显示订单号、客户名和金额，可以直接查询 DTO：

```java
select new com.example.OrderRow(o.id, c.name, o.amount)
from Order o
join o.customer c
where o.status = :status
```

投影避免构造完整实体图，也不会在序列化阶段继续懒加载。代价是查询结果面向具体用例，不能作为受管实体直接修改。

## 8. 集合抓取与分页要分两步考虑 {#7-集合抓取与分页要分两步考虑}

对 to-many 集合使用 join fetch 后，数据库结果中的一条父记录会重复多次。此时直接分页可能切断集合、得到错误页大小，或让 ORM 在内存中分页。

稳定方案通常是：

1. 先按稳定排序分页查询父对象 ID。
2. 再按这一页 ID 抓取详情和关联。
3. 在内存中按第一页的顺序组装结果。

这两阶段限制的是父对象范围；关联可能仍分批加载，所以总数不必恰好为两条。两次读取之间若有并发修改，需要按隔离级别决定接受最新数据、维持事务快照还是做版本校验。空 ID 列表直接返回，IN 查询不会自动保留第一阶段顺序。

## 9. 抓取范围与结果基数 {#fetch-cost}

同一页 20 个订单若都引用同一个客户，在同一持久化上下文中可能只额外加载一次客户，并非必然 21 次。反过来，EAGER 关联也可能为每个对象执行次级查询，单看注解不足以判断。

若一个父对象有 10 个商品和 8 个标签，同时 join 两个集合，可能产生 80 行组合。即使 Hibernate 去掉重复父实体，传输和物化成本仍存在；某些多 bag 抓取组合还会被实现拒绝。按用途分别批量查询，往往能降低总数据量。

Hibernate 7.1 可通过 `hibernate.query.fail_on_pagination_over_collection_fetch=true` 让集合抓取分页直接报错，帮助测试尽早暴露问题。该设置不替代正确的两阶段查询和并发一致性设计。

## 10. 防止问题再次出现 {#8-防止问题再次出现}

- 为关键接口添加 SQL 数量上限或查询统计断言。
- 用真实页面大小测试，不只查一条数据。
- 代码评审检查循环内 Repository/Mapper 调用和实体序列化。
- 压测同时观察连接池等待、数据库 CPU 和返回行数。
- 新增关联字段时重新检查查询策略。

<details>
<summary>参考回答</summary>

先统计一次请求的 SQL 数量和重复模板，确认查询数是否随页面 N 线性增长，再定位是懒加载还是循环内手工查询。已知且基数可控的关联可以 join fetch 或用 EntityGraph；join 会放大结果集时，可使用批量抓取或收集外键后一次查询。只读列表也可以直接 DTO 投影。

to-many join fetch 不能直接假定能正确分页，常见做法是先分页查父 ID，再按这一页 ID 抓取关联。修复后应断言查询数量，并在真实页大小下观察返回行数、连接池等待和数据库负载。

</details>

### 11.3 一条 SQL 同时抓两个集合，为什么可能比三条 SQL 更慢？ {#join-explosion}

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**

- 笛卡尔放大。
- 传输与物化成本。

**相关内容**：[Join Fetch](#3-join-fetch-一次取回已知关联)、[结果基数](#fetch-cost)。

<details>
<summary>参考回答</summary>

两个集合会产生乘积行，去重父实体无法消除已传输的数据。分别抓取可以把乘积规模降为各集合规模之和，但增加往返；应比较总行数、行宽、延迟和内存，而不是只追求 SQL 条数最少。

</details>

### 11.4 带一对多详情的分页接口怎样保持页大小和顺序？ {#collection-pagination}

<!-- 面试来源：本站自测：依据本文机制与官方资料设计，无已核验的公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**

- 父记录分页与关联展开。
- 两次读取的一致性。

**相关内容**：[集合分页](#7-集合抓取与分页要分两步考虑)。

<details>
<summary>参考回答</summary>

先按唯一稳定顺序分页父 ID，再按本页 ID 获取关联，最后恢复 ID 顺序。空页不发无条件查询；同时定义两个阶段之间数据变化的处理。Hibernate 对集合 fetch join 可能内存分页，可在测试启用失败检查，不能以去重后的 List 长度替代正确分页。

</details>
