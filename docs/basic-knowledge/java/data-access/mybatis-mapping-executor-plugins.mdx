# MyBatis

**MyBatis** 是一个把 Mapper 接口方法和 SQL 关联起来的持久层框架：你写接口和 SQL，它负责参数绑定、执行和把结果映射成 Java 对象。和 JPA 不同，它不跟踪对象的变化，SQL 写什么就执行什么。

要讲清 MyBatis，关键是能沿着一次查询把链路走一遍：Mapper 代理怎样找到 SQL，`Executor` 怎样组织执行，参数和结果在哪里转换。缓存、批处理、插件和分页都挂在这条链路的某一环上，链路清楚了，它们在哪里生效、边界在哪也就清楚了。本文以 MyBatis 3 和 MyBatis-Spring 为范围。

## 1. 面试核心 {#core}

- Mapper 代理定位 `MappedStatement`，再经 `SqlSession` 和 `Executor` 执行，**缓存命中时可以跳过 JDBC 查询**。[卡](#mybatis-query-flow)
- `#{}` **通过 PreparedStatement 绑定数据值**，`${}` **直接替换 SQL 文本**；动态列名、排序方向这类标识符要从固定白名单里选。[卡](#parameter-binding)
- BATCH 执行器下，Mapper 更新只是加入批次，**`flushStatements()` 才执行批次并返回 `BatchResult`，commit 才提交事务**。[卡](#batch-flush)
- **一级缓存属于 `SqlSession`，二级缓存按 namespace 配置**；跨 namespace 或外部系统的写入，需要单独处理缓存失效。[卡](#cache-boundaries)
- 插件**只能拦截 `Executor` 等四类组件的指定方法**，PageHelper 就是通过拦截 `Executor.query` 改写分页 SQL 的。[卡](#plugin-boundaries) [卡](#pagehelper-rewrite)

## 2. MappedStatement 与 Mapper 代理 {#1-映射配置形成-mappedstatement}

Mapper 方法执行哪条 SQL，由启动时加载的映射配置决定。MyBatis 读取 XML 或注解，把 SQL 及其动态片段、参数类型、结果映射和缓存配置都保存到 `Configuration`，也就是 MyBatis 的全局配置对象里。

每条映射语句对应一个 **`MappedStatement`**，里面记录了执行这条语句所需的全部配置。语句用 `namespace + id` 唯一标识，namespace 是映射器的命名空间。下面这条查询的 id 是 `findById`：

```xml
<select id="findById" resultMap="orderResultMap">
  select id, user_id, status
  from orders
  where id = #{id}
</select>
```

使用 Mapper 接口时，namespace 就是接口的全限定名，语句 id 就是方法名。调用 `orderMapper.findById(id)` 时，MyBatis 生成的动态代理按「接口名 + 方法名」找到这条映射语句，再把参数交给 **`SqlSession`**（一次数据库工作的会话入口）。所以接口方法不需要你手写实现。

## 3. 查询执行链路 {#2-一次查询经过多个处理组件}

找到映射语句以后，还要绑定参数、执行 SQL、构造返回对象。下面是一次使用 PreparedStatement、且没有命中缓存的查询经过的阶段。箭头表示处理顺序，组件之间实际还有委托关系：

```text
Mapper proxy
  → SqlSession
  → Executor
  → StatementHandler
  → ParameterHandler
  → JDBC PreparedStatement
  → ResultSetHandler
  → Java result
```

链路里的四类处理组件各管一段：

- **`Executor`**（执行器）：组织查询或更新，管理本地缓存和事务相关操作。配置了二级缓存时，外面还包着一层 `CachingExecutor`，先查 namespace 缓存，没命中再进入实际执行器的本地缓存和查询路径。
- **`StatementHandler`**：创建 JDBC Statement、设置参数并执行。
- **`ParameterHandler`**：借助 `TypeHandler`（负责 Java 类型和 JDBC 类型之间的转换）把 Java 参数绑定到 JDBC。
- **`ResultSetHandler`**：读取 JDBC 返回的 `ResultSet`，按 `ResultMap`（描述数据库列怎样对应 Java 字段或关联）或结果类型构造对象。

出了问题，可以按 SQL、参数、结果三段定位：

- SQL 生成错了，检查动态 SQL 和 `BoundSql`。`BoundSql` 保存本次执行实际生成的 SQL、参数映射和附加参数。
- 参数类型不对，检查 `ParameterHandler` 和 `TypeHandler`，看 Java 值是怎样绑定到 JDBC 的。
- 列映射错了，检查 `ResultMap` 和 `ResultSetHandler`，看返回列是怎样写进对象的。

## 4. 参数占位符与字符串替换 {#4-参数占位符与字符串替换用途不同}

参数有两种用途：作为普通的数据值，或者决定 SQL 的结构（比如用哪个列排序），这两种要分开处理。

`#{value}` 会生成 JDBC 的 `?` 占位符，再由 PreparedStatement 绑定数据值。绑定进去的内容始终被当作数据，不会改变 SQL 的结构，所以用户输入的普通参数都用 `#{}`。

`${column}` 则是把文本原样拼进 SQL，拼进去的内容会参与 SQL 语法解析。表名、列名和排序方向属于语法，没法用 `#{}` 这种值占位符表达，只能用 `${}`。但如果把请求里的任意字符串直接放进 `${}`，比如有人传入 `id; drop table orders`，它就会成为 SQL 的一部分，这就是 SQL 注入。所以需要动态选择时，要在代码里映射到固定的白名单。

下面的 Java 17 示例假定 `sort` 是已经校验过的枚举，结果只能是两个固定列名之一：

```java
String orderBy = switch (sort) {
    case CREATED_AT -> "created_at";
    case AMOUNT -> "amount";
};
```

请求只能决定选哪个枚举值，最终拼进 SQL 的文本始终是代码里写死的列名。

## 5. 动态 SQL 与结果映射 {#动态-sql-与结果映射}

查询条件随输入变化时，**动态 SQL** 会根据参数生成本次执行的 `BoundSql`。常用的几个标签：

- `<if>`：按条件决定是否加入一段 SQL。
- `<where>`：需要时加上 WHERE，并去掉开头多余的 AND 或 OR。
- `<foreach>`：展开集合，生成 IN 条件这类列表参数。

用动态 SQL 时，业务要先定清楚空集合、空字符串和 null 分别代表什么。缺少必需的筛选条件时应该拒绝执行，否则一次本该只改几行的 update，可能因为所有 `<if>` 都不成立而变成全表更新。

读取结果时，`resultType` 适合简单结果的自动映射；`resultMap` 则显式描述列映射和构造器，还能用 `association` 表达单个关联、用 `collection` 表达集合。一对多映射要明确对象标识（`<id>`），否则同一条主记录会在展开的多行里被反复创建。多参数的 Mapper 方法可以用 `@Param` 给参数起稳定的名字，不依赖编译器是否保留参数名。

如果列表里每一项都通过嵌套 select 去查关联，就会产生 N+1 次查询。延迟加载只是把这些查询推迟到访问属性时，查询总数不一定变少，要看日志确认。关联访问频繁时，可以用 join 或批量加载减少查询，选择方法见 [N+1 查询](./n-plus-one-fetch-strategies.mdx)。

### 5.1 关联属性的延迟加载 {#关联属性的延迟加载}

延迟加载要记住还没执行的关联查询，等访问属性时再执行。MyBatis 3.5.19 会为带延迟关联的结果对象创建代理，默认 `proxyFactory=JAVASSIST`。`association` 或 `collection` 的每个嵌套 select 对应一个 `ResultLoader`，保存在代理持有的 `ResultLoaderMap` 里。读取属性时，代理执行对应的关联查询，再把结果写回这个属性。

```xml
<association property="user" column="user_id"
             select="findUserById" fetchType="lazy"/>
```

这段配置放在订单的 resultMap 里，`findUserById` 用 `user_id` 查询用户。主查询返回订单后，第一次调用 `order.getUser()` 才会触发 user 的加载，之后再访问用的就是已经填充的属性。

关联什么时候执行查询，由这几项配置决定：

- `lazyLoadingEnabled` 默认 false，设为 true 才启用延迟关联。
- 单个关联上的 `fetchType="lazy"` 或 `"eager"` 会覆盖全局设置。
- `aggressiveLazyLoading=false` 时按属性加载；设为 true 时，调用对象的任意方法都会触发全部待加载属性。
- 默认的 `lazyLoadTriggerMethods=equals,clone,hashCode,toString`，调用这些方法会触发全部待加载属性。

所以打印对象（`toString`）或者序列化时调用 getter，都可能提前发出 SQL。

还有一个事务边界的问题：如果原来的 `Executor` 已经关闭，或者加载发生在另一个线程，`ResultLoader` 会用配置好的 Environment/DataSource 新建一个 `Executor` 来执行查询，这次查询就不在原来的事务里了。如果关联数据需要和主数据在同一事务内保持一致，就要在事务结束前完成加载。列表逐项访问关联造成的 N+1，则要用批量加载或 join 处理。

## 6. Executor 与批处理 {#3-executor-决定语句复用与批处理方式}

执行器决定 Statement 是否复用，以及更新什么时候交给驱动。MyBatis 有三种执行器类型：

- `SIMPLE`：每次执行都创建新的 Statement，这是默认值。
- `REUSE`：在当前执行器范围内，复用相同 SQL 的 PreparedStatement。
- `BATCH`：把更新语句攒起来，批量交给 JDBC 驱动。

使用 BATCH 时，Mapper 的更新方法只是把操作加入 JDBC 批次，返回的是一个占位值，并不是真实的影响行数。调用 `flushStatements()` 后，驱动才执行攒下的批次，结果通过 `BatchResult` 返回，实际影响行数要从这里读。

flush 之后事务仍然要 commit 才提交，执行失败则按事务边界回滚。还有一个容易忽略的点：BATCH 执行器在执行查询（`BatchExecutor.doQuery`）前，会先刷新待执行的批次，所以批处理中途插一条查询，会改变批次的执行时机。验证批处理时，还要检查驱动是否真正支持、生成键怎样返回、出错时能否定位到具体语句，并测试事务大小对性能的影响。

## 7. 一级缓存与二级缓存 {#5-一级缓存属于-sqlsession}

缓存决定一次查询要不要再访问数据库。**一级缓存**属于单个 `SqlSession`，**二级缓存**则让不同会话复用同一 namespace 下的查询结果。

每个 `SqlSession` 都有本地缓存，也就是一级缓存，默认范围是 `localCacheScope=SESSION`。缓存键由语句 id、分页参数、实际执行的 SQL 和参数值等组成，同一个会话里这些都相同的查询，第二次直接返回缓存的结果。执行 update、commit、rollback 和 close 时，本地缓存会被清空。

SESSION 范围的本地缓存返回的是同一个对象引用。如果你修改了查询返回的对象，同一会话里下一次命中缓存时，拿到的就是这个被改过的对象。所以 Session 的生命周期要短，也不要随意修改查询结果。

二级缓存按 Mapper namespace 配置，要用 `<cache/>` 或 `@CacheNamespace` 显式声明，同时全局 `cacheEnabled` 和语句上的 `useCache` 也要允许。默认情况下，查询语句使用已配置的缓存，写语句会刷新所属 namespace 的缓存。查询结果不会立刻对其他会话可见，要等当前会话的事务完成（commit 或 close）时才写入二级缓存，之后其他会话才能复用。

二级缓存的边界在于：同一张表可能被多个 namespace 或其他服务更新，而某个 namespace 的缓存只知道自己 namespace 里的写语句。比如 `OrderMapper` 缓存了订单查询，`OrderAdminMapper` 修改了同一张表，`OrderMapper` 的缓存不会被刷新，读到的就是旧数据。这种情况可以用 `<cache-ref>` 让相关 namespace 共享缓存，或者干脆不用结果缓存。

两级缓存的开关也是分开的：`localCacheScope=STATEMENT` 把一级缓存缩短到单条语句，查询上的 `useCache=false` 只控制二级缓存。

## 8. Spring 事务与 SqlSession {#7-与-spring-事务共用同一-sqlsession}

在 Spring 事务里，多次 Mapper 调用应该共享同一个数据库工作范围。MyBatis-Spring 通过 Spring 的事务同步机制管理 `SqlSession` 的创建、复用和提交。创建会话的 `SqlSessionFactory` 必须和事务管理器使用同一个 `DataSource`。这样，同一事务内经同一个 `SqlSessionFactory` 的 Mapper 调用，用的都是绑定在事务上的那个 Session。如果你手工另开一个 Session，它就脱离了当前事务，也不共享一级缓存。

`DefaultSqlSession` 不是线程安全的，应该按单次工作单元使用。`SqlSessionTemplate` 是线程安全的入口，每次调用时根据当前事务找到实际的 Session。所以模板可以在多线程间共享，由它为各个事务选择各自的会话。

不在事务里时，每次 Mapper 调用都会单独打开并关闭一个 Session，一级缓存也随之结束，两次调用之间不会命中。

Mapper 方法返回后，外层事务还可能继续执行或回滚。缓存什么时候可见、批处理什么时候 flush、连接什么时候释放，都要结合外层事务边界来判断。

## 9. 插件扩展点 {#6-插件只拦截指定扩展点}

MyBatis **插件**通过代理包装链路上的组件，在指定方法前后加入自己的逻辑。能包装的只有前面链路里的四类组件：

- `Executor`：查询、更新和事务操作的执行入口。
- `StatementHandler`：JDBC Statement 的创建与执行。
- `ParameterHandler`：参数绑定。
- `ResultSetHandler`：读取并映射结果。

分页、审计或租户条件这类插件，应该选能完成任务的最小扩展点。如果插件改写了 `BoundSql` 里的 SQL，还要同步改参数映射和缓存键：新增了 `?` 却没加参数映射，驱动就会绑错参数；查询条件变了却还用旧的缓存键，就可能命中不对应的结果。SQL 语法还取决于数据库方言；嵌套查询会多出查询路径，也要验证插件是否在预期的位置生效。

多个插件之间的顺序也会影响结果。两个插件都改写 SQL 或参数时，谁包在外层、谁先执行，结果可能不同，要用集成测试确认代理的嵌套顺序和最终 SQL。

### 9.1 PageHelper 分页 SQL 改写 {#pagehelper-分页-sql-改写}

PageHelper 在执行前改写 SQL，让数据库只返回需要的那一页。以 PageHelper 6.1.1 为例，它的 `PageInterceptor` 拦截 `Executor.query` 的四参数和六参数两个重载。`PageHelper.startPage(2, 10)` 把页码和页大小放进当前线程的分页上下文，紧接着执行的 Mapper 查询进入拦截器后，依次完成计数和分页查询：

1. 拦截器取得 `MappedStatement`、参数、`BoundSql` 和 `CacheKey`，据此判断是否要分页。
2. 启用了 count 时，先执行一条计数查询，再通过数据库方言生成分页 SQL。
3. MySQL 方言为第 2 页、每页 10 条生成 `LIMIT ?, ?`，绑定 offset=10、pageSize=10，同时同步参数映射、动态 SQL 的附加参数和缓存键。
4. 拦截器用新的 `BoundSql` 调用 `Executor` 执行分页查询，返回分页结果，并在 finally 里清理分页上下文。

比如 `SELECT id FROM orders ORDER BY id` 在 JDBC 执行前就变成了带 LIMIT 的 SQL。传给后续执行器的是 `RowBounds.DEFAULT`，分页完全由改写后的 SQL 完成，而不是在内存里截取。

因为分页参数放在线程上下文里，`startPage` 之后要立即执行目标查询。如果某个分支跳过了查询，或者进入拦截器之前就抛了异常，上下文不会被清理，要手动调用 `PageHelper.clearPage()`。否则线程被线程池复用时，下一次无关的查询会意外地被分页。

## 10. 常见问题 {#8-常见问题}

### 10.1 一级缓存中的旧值属于脏读吗？ {#81-mybatis-一级缓存会导致脏读吗}

不属于。缓存返回旧值是数据新鲜度的问题，而脏读专指读到另一个事务尚未提交的修改。一级缓存命中时，MyBatis 根本没有访问数据库，直接返回了 `SqlSession` 里已有的对象，这和数据库的隔离级别无关。

排查时，先确认 Session 的范围、期间有没有更新操作、这次查询是否命中缓存，再去核对数据库的隔离级别，这样才能分清值是来自本地缓存还是数据库。

### 10.2 插件可以拦截任意 MyBatis 方法吗？ {#82-插件可以拦截任意-mybatis-方法吗}

不能。官方插件机制只支持 `Executor`、`StatementHandler`、`ParameterHandler`、`ResultSetHandler` 上规定的方法。需要改其他行为时，应该用明确的扩展点或自己封装一层，而不是依赖内部类碰巧的实现。

## 11. 面试题 {#9-面试题}

### 11.1 MyBatis 的一次查询是怎样执行的 {#mybatis-query-flow}

**考察重点**：说明 Mapper 代理怎样定位映射语句，以及执行器如何组织 JDBC 查询。能指出缓存、插件和 Spring 事务分别在哪一步生效。

**相关内容**：[MappedStatement 与 Mapper 代理](#1-映射配置形成-mappedstatement)、[查询执行链路](#2-一次查询经过多个处理组件)、[Spring 事务与 SqlSession](#7-与-spring-事务共用同一-sqlsession)。

<details>
<summary>参考回答</summary>

**Mapper 调用经 SqlSession 和 Executor 执行映射语句，缓存未命中时进入 JDBC，最后把结果映射成 Java 对象。**

启动时，XML 或注解被解析成 `MappedStatement`。调用时，Mapper 代理按接口名和方法名定位语句，由 Executor 先检查缓存，再组织执行。

进入 JDBC 后，StatementHandler 创建 Statement，ParameterHandler 借助 TypeHandler 绑定参数；SQL 执行完，ResultSetHandler 按 ResultMap 构造返回对象。插件包装的就是这几类组件。MyBatis-Spring 让 SqlSession 和外层事务同步，所以连接和一级缓存的生命周期也受事务边界影响。

</details>

### 11.2 MyBatis 的 `#{}` 和 `${}` 有什么区别，动态排序字段应该怎样传入？ {#parameter-binding}

**考察重点**：区分数据值绑定与 SQL 文本替换，并说明动态标识符为什么需要白名单、多参数方法怎样命名。

**相关内容**：[参数占位符与字符串替换](#4-参数占位符与字符串替换用途不同)。

<details>
<summary>参考回答</summary>

**`#{}` 通过占位符绑定数据值，`${}` 把内容直接替换进 SQL 文本。**

绑定的值始终是数据，不会改变 SQL 结构；替换的文本会参与语法解析。列名和排序方向属于 SQL 语法，只能用 `${}`，所以要先从枚举或固定映射中选出列名再放进去。把请求里的任意字符串直接拼入，就是 SQL 注入入口。多个方法参数可以用 `@Param` 明确命名，不依赖编译器是否保留参数名。

</details>

### 11.3 MyBatis 一级缓存和二级缓存的作用范围、失效条件有什么区别？ {#cache-boundaries}

**考察重点**：比较 SqlSession 与 namespace 的缓存范围，说明结果发布和失效时机。能解释跨 Mapper 或外部写入为什么需要单独处理一致性。

**相关内容**：[一级缓存与二级缓存](#5-一级缓存属于-sqlsession)、[Spring 事务与 SqlSession](#7-与-spring-事务共用同一-sqlsession)。

<details>
<summary>参考回答</summary>

**一级缓存属于单个 SqlSession；二级缓存按 namespace 配置，可以跨会话复用结果。**

- **一级缓存默认在 Session 内复用。** `localCacheScope=SESSION` 时，update、commit、rollback 和 close 会清空它。缓存返回的是对象引用，修改返回对象会影响后续命中的结果。
- **二级缓存需要显式配置。** 由 `cacheEnabled` 和 `useCache` 控制，结果在会话事务完成时才写入，默认写语句刷新所属 namespace。其他 namespace 或外部系统的写入，它感知不到，需要额外的失效策略。

`useCache=false` 不会关闭一级缓存，一级缓存由 `localCacheScope` 控制。在 Spring 事务之外，每次调用各自开关 Session，一级缓存随之结束。

</details>

### 11.4 使用 BATCH 时，flushStatements、Mapper 返回和事务提交分别代表什么？ {#batch-flush}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：区分操作加入批次、驱动执行与事务提交，说明怎样读取影响行数并处理失败回滚。

**相关内容**：[Executor 与批处理](#3-executor-决定语句复用与批处理方式)。

<details>
<summary>参考回答</summary>

**BATCH 下，Mapper 更新返回只表示操作已加入批次，`flushStatements()` 才执行批次，commit 才提交事务。**

Mapper 返回的是占位值，实际影响行数要从 BatchResult 里读驱动给出的结果。flush 会暴露执行结果或异常，这时事务仍然可以回滚。执行查询（`BatchExecutor.doQuery`）前也会先刷新待执行的批次，所以要同时留意中途的查询和提交时机。

批处理效果依赖驱动能力，执行失败要按事务边界回滚，并核对生成键和错误定位结果。

</details>

### 11.5 MyBatis 插件能拦截哪些组件，为什么只修改 SQL 文本可能出错？ {#plugin-boundaries}

**考察重点**：说明插件能包装哪些接口，以及代理顺序怎样影响 SQL。能解释参数映射和缓存键为何要随 SQL 同步变化。

**相关内容**：[插件扩展点](#6-插件只拦截指定扩展点)。

<details>
<summary>参考回答</summary>

**插件只能包装 Executor、StatementHandler、ParameterHandler 和 ResultSetHandler 的指定方法；改写 SQL 时，参数映射和缓存键也要一起改。**

新增了占位符却没同步参数映射，驱动就会绑错参数。查询条件变了却还用旧的缓存键，就可能命中不对应的结果。多个插件按代理嵌套顺序执行，所以要用集成测试检查最终的 BoundSql、参数和缓存命中情况。

</details>

### 11.6 PageHelper 怎样让 Mapper 查询变成数据库分页？ {#pagehelper-rewrite}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释 Executor 拦截怎样把分页上下文转换为方言 SQL，并同步参数映射与缓存键。

**相关内容**：[PageHelper 分页 SQL 改写](#pagehelper-分页-sql-改写)。

<details>
<summary>参考回答</summary>

**PageHelper 拦截 `Executor.query`，按数据库方言生成分页 SQL，并同步参数映射和缓存键。**

`startPage` 把页码和页大小放进线程上下文。PageInterceptor 读到后，按配置先执行 count，再生成新的 BoundSql 和分页用的 CacheKey。MySQL 下 `startPage(2,10)` 对应 `offset=10`、`pageSize=10` 的 LIMIT，后续传 `RowBounds.DEFAULT`，分页由 SQL 完成。

拦截器会在 `finally` 里清理上下文；如果分支跳过了查询，或进入拦截器前就发生异常，需要自己调用 `clearPage()`，避免线程复用时影响下一次查询。

</details>

### 11.7 MyBatis 延迟加载怎样实现，哪些调用会触发关联 SQL？ {#lazy-loading-triggers}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：说明结果代理如何保存并执行 ResultLoader，以及哪些方法调用会提前触发关联查询。

**相关内容**：[关联属性的延迟加载](#关联属性的延迟加载)。

<details>
<summary>参考回答</summary>

**MyBatis 为结果对象创建代理，代理里保存着关联查询的 ResultLoader，访问未加载的属性时执行查询，再把结果写回属性。**

- **按属性触发需要关闭激进加载。** `aggressiveLazyLoading=false` 时按属性加载，但默认的 `equals`、`clone`、`hashCode`、`toString` 仍会触发全部待加载属性；设为 true 后，任意方法调用都会触发全部加载。
- **日志和序列化也可能发出 SQL。** 它们会调用 `toString` 或 getter；列表逐项访问关联仍然会产生 N+1。
- **事务结束后加载可能不在原事务里。** 原 Executor 关闭或换了线程后，ResultLoader 会新建 Executor 执行查询。需要和原事务保持一致时，应提前加载。

这套机制通过 `lazyLoadingEnabled=true` 或关联上的 `fetchType="lazy"` 启用。

</details>
