# MyBatis

本文以 MyBatis 3 与 MyBatis-Spring 的常规用法为范围。MyBatis 把 Mapper 方法和 SQL 映射为 `MappedStatement`。它再通过 SqlSession、Executor 和 JDBC 处理一次数据库访问。本文负责执行链路、缓存、分页插件与延迟加载；连接资源的容量和超时见 [数据库连接池](./connection-pool-capacity-timeout-leaks.mdx)。

## 1. 面试核心 {#core}

- Mapper 代理定位 MappedStatement，经 SqlSession、Executor 到 JDBC；缓存命中时可以不执行后续 JDBC 路径。[卡](#mybatis-query-flow)
- `#{}` 通过 PreparedStatement 绑定值，`${}` 替换 SQL 文本，动态标识符需由固定白名单映射。[卡](#parameter-binding)
- 一级缓存绑定 SqlSession，二级缓存按 namespace 显式配置；跨 namespace 或外部写入不会自动让全部二级缓存失效。[卡](#cache-boundaries)
- BATCH 的 `flushStatements()` 执行 JDBC 批处理。影响行数来自 BatchResult，事务通过 commit 提交。[卡](#batch-flush)
- 插件拦截 Executor、StatementHandler、ParameterHandler 和 ResultSetHandler。PageHelper 在 Executor.query 处改写分页 SQL。[卡](#plugin-boundaries) [卡](#pagehelper-rewrite)

## 2. MappedStatement 与 Mapper 代理 {#1-映射配置形成-mappedstatement}

应用启动时，MyBatis 读取 XML 或注解中的配置。内容包括 statement、动态 SQL、参数类型、ResultMap 和缓存配置。MyBatis 将这些配置保存到 `Configuration`。每条语句使用 `namespace + id` 作为标识，对应一个 `MappedStatement`。

```xml
<select id="findById" resultMap="orderResultMap">
  select id, user_id, status
  from orders
  where id = #{id}
</select>
```

Mapper 接口由动态代理实现。调用 `orderMapper.findById(id)` 时，代理根据接口与方法找到 statement id。然后，代理把参数交给 SqlSession。接口方法本身不包含查询实现。

## 3. 查询执行链路 {#2-一次查询经过多个处理组件}

以下查询采用 PreparedStatement，且未命中缓存。链路按组件职责顺序展示：

```text
Mapper proxy
  → SqlSession
  → Executor
  → StatementHandler
  → ParameterHandler
  → JDBC PreparedStatement
  → ResultSetHandler
  → Java result
```

- **Executor**：组织查询或更新，管理本地缓存和事务相关操作。配置二级缓存时，CachingExecutor 会先处理 namespace 缓存。之后，它再进入实际执行器的本地缓存与查询路径。
- **StatementHandler**：创建、参数化并执行 JDBC Statement。
- **ParameterHandler**：使用 TypeHandler 把 Java 参数设置到 JDBC。
- **ResultSetHandler**：读取 ResultSet，并按 ResultMap 或结果类型构造对象。

排查时应按组件职责定位问题。SQL 没有生成正确，先看动态 SQL 与 BoundSql；参数类型错误看 ParameterHandler 和 TypeHandler；列映射错误看 ResultMap 与 ResultSetHandler。

## 4. Executor 与批处理 {#3-executor-决定语句复用与批处理方式}

MyBatis 提供三种主要 ExecutorType：

- `SIMPLE`：每次执行创建新的 Statement，是默认方式。
- `REUSE`：在当前执行器范围复用相同 SQL 的 PreparedStatement。
- `BATCH`：积累更新语句并批量提交给 JDBC 驱动。

`BATCH` 将更新积累到 JDBC 批次。`flushStatements()` 执行批次并返回 BatchResult。事务仍由 commit 提交。Mapper 更新返回的是批处理占位值。实际影响行数需读取 BatchResult/驱动结果。查询进入 BatchExecutor.doQuery 时会先刷新待执行批次。批量执行的错误定位、生成键和事务大小都要单独测试。

## 5. 参数占位符与字符串替换 {#4-参数占位符与字符串替换用途不同}

`#{value}` 会生成 JDBC `?` 占位符，再由 PreparedStatement 绑定值。它适用于普通数据参数。

`${column}` 会把文本原样替换进 SQL，无法通过 PreparedStatement 绑定。表名、列名和排序方向属于 SQL 语法。使用时，应在代码中映射到固定白名单：

以下 Java 17+ 片段假定 `sort` 是已校验的枚举；只输出固定 SQL 标识符：

```java
String orderBy = switch (sort) {
    case CREATED_AT -> "created_at";
    case AMOUNT -> "amount";
};
```

请求中的任意字符串直接进入 `${}` 会形成 SQL 注入入口。示例通过枚举到固定文本的映射限制输入。

## 6. 一级缓存与二级缓存 {#5-一级缓存属于-sqlsession}

每个 SqlSession 都有本地缓存。默认配置为 `localCacheScope=SESSION`。statement、参数和分页条件相同的查询可以复用结果。update、commit、rollback、close 等操作会清理缓存。

默认 SESSION 范围的本地缓存保存并返回对象引用。在同一 Session 内，应用可以修改查询结果对象。后续命中缓存时，应用会看到同一对象被修改后的值。应缩短 Session 生命周期，并避免随意修改查询结果。这样比依赖缓存副本更稳妥。

二级缓存按 Mapper namespace 配置。它需要 `<cache/>`、`@CacheNamespace` 等显式声明。全局 `cacheEnabled` 和语句 `useCache` 也会控制二级缓存。默认查询会使用已配置缓存。写语句默认触发所属 namespace 缓存刷新。缓存结果在会话的事务完成阶段按规则发布。

同一张表可以由多个 namespace 或其他服务更新。某个 namespace 的缓存不会自动获知全部写入。可按依赖共享缓存配置或避免使用这种结果缓存。`localCacheScope=STATEMENT` 缩短一级缓存共享范围；查询的 `useCache=false` 控制二级缓存，两级缓存分别控制。

## 7. 插件扩展点 {#6-插件只拦截指定扩展点}

MyBatis 插件可以包装四类组件的指定方法。它们是 Executor、StatementHandler、ParameterHandler 和 ResultSetHandler。

分页、审计或租户条件插件需要选择最窄的扩展点。拦截器修改 BoundSql 时，也要处理参数映射和缓存键。数据库方言和嵌套查询同样需要处理。

插件顺序会改变行为。若两个插件都重写 SQL 或参数，嵌套顺序就会影响结果。应通过集成测试确认代理嵌套顺序和最终 SQL。

### 7.1 PageHelper 分页 SQL 改写 {#pagehelper-分页-sql-改写}

以 PageHelper 6.1.1 为例，`PageInterceptor` 拦截 `Executor.query` 的四参数和六参数重载。`PageHelper.startPage(2, 10)` 将页码、页大小放入当前线程的分页上下文。紧随其后的 Mapper 查询进入拦截器：

1. 拦截器取得 `MappedStatement`、参数、`BoundSql` 和 `CacheKey`。它据此判断是否启用分页。
2. 启用 count 时，拦截器执行计数查询。随后，拦截器通过数据库方言生成分页 SQL。
3. MySQL 方言为第二页、每页 10 条生成 `LIMIT ?, ?`。它绑定 offset=10、pageSize=10。它还处理参数映射、动态 SQL 附加参数与分页缓存键。
4. 拦截器用新的 BoundSql 调用 Executor，执行数据库分页。它返回分页结果，并在 finally 路径清理分页上下文。

例如 `SELECT id FROM orders ORDER BY id` 会在 JDBC 执行前变为带 LIMIT 的 SQL。`RowBounds.DEFAULT` 传给后续执行器，分页工作由改写后的 SQL 完成。`startPage` 后应立即执行目标查询；若分支跳过查询，或进入拦截器前发生异常，就需手动清理。此时应调用 `PageHelper.clearPage()` 清理线程上下文。这能避免线程复用影响下一次查询。

## 8. Spring 事务与 SqlSession {#7-与-spring-事务共用同一-sqlsession}

MyBatis-Spring 可以通过 Spring 事务同步管理 SqlSession。前提是事务管理器与 SqlSessionFactory 使用同一 DataSource。管理范围包括 SqlSession 的创建、复用和提交。同一事务内，经同一 SqlSessionFactory 的 Mapper 调用使用绑定的 Session。直接手工创建另一个 Session 会脱离当前事务和一级缓存范围。

DefaultSqlSession 不是线程安全对象。应用应按单次工作单元管理它。线程安全的 SqlSessionTemplate 根据当前事务取得实际 Session。事务外的多次 Mapper 调用各自完成会话生命周期。一级缓存随各次 Session 结束。

Mapper 返回后，外层事务仍可继续执行或回滚。缓存可见性、批处理 flush 和连接释放都要结合外层事务边界判断。

## 9. 动态 SQL 与结果映射 {#动态-sql-与结果映射}

动态 SQL 在运行时根据参数生成 BoundSql。`<if>` 决定片段是否存在。`<where>` 处理 WHERE 及开头连接词。`<foreach>` 生成列表参数。业务必须明确空集合、空字符串和 null 的语义。缺少必需筛选条件时，应拒绝执行全表操作。

`resultType` 适合简单结果自动映射；`resultMap` 用于显式列映射、构造器、association 与 collection 等复杂结构。一对多映射应明确对象标识，避免把同一主记录反复创建。多参数 Mapper 可用 `@Param` 给出稳定名称，避免依赖编译器参数名设置。

列表查询逐项触发嵌套 select 会形成 N+1 次访问；延迟加载将关联查询推迟到访问属性时。关联访问频繁时，可通过 join 或批量加载减少查询次数。

### 9.1 关联属性的延迟加载 {#关联属性的延迟加载}

MyBatis 3.5.19 为带延迟关联的结果对象创建代理，默认 `proxyFactory=JAVASSIST`。`association` 或 `collection` 的嵌套 select 对应一个 `ResultLoader`。这个加载器保存在 `ResultLoaderMap` 中。触发属性读取时，代理执行关联查询并写回该属性。

```xml
<association property="user" column="user_id"
             select="findUserById" fetchType="lazy"/>
```

此片段放在订单的 resultMap 中，`findUserById` 接收 `user_id` 查询用户。主查询返回订单后，`order.getUser()` 触发尚未完成的 user 加载。后续访问使用已填充的属性。

全局 `lazyLoadingEnabled` 默认 false。将它配置为 true，可启用延迟关联。单个关联的 `fetchType="lazy"` 或 `"eager"` 覆盖全局设置。`aggressiveLazyLoading=false` 时，代理按属性加载。默认 `lazyLoadTriggerMethods=equals,clone,hashCode,toString` 中的方法会触发全部待加载属性。将 `aggressiveLazyLoading` 设置为 true 时，普通方法调用也会触发全部加载。打印对象或序列化调用 getter 都能提前触发 SQL。

若原 Executor 已关闭，或加载发生在其他线程，`ResultLoader` 会创建新 Executor。它使用已配置的 Environment/DataSource 执行查询。事务范围也随之改变。若关联数据需要事务内一致性，应在事务结束前完成加载。逐项访问列表关联的 N+1 查询应通过批量加载或 join 处理。

## 10. 常见问题 {#8-常见问题}

### 10.1 缓存旧值与脏读 {#81-mybatis-一级缓存会导致脏读吗}

一级缓存命中时，会返回 SqlSession 中已有的对象。此时会跳过数据库查询，形成数据新鲜度问题。数据库脏读则专指读取另一事务尚未提交的修改。排查时先确认 Session 范围、更新和缓存命中情况。再核对数据库隔离级别。

### 10.2 插件拦截范围 {#82-插件可以拦截任意-mybatis-方法吗}

官方插件机制支持 Executor、StatementHandler、ParameterHandler、ResultSetHandler 的规定方法。需要修改其他行为时，应使用明确扩展点或封装层。这样能避免依赖内部类的偶然实现。

<details>

</details>

<summary>参考回答</summary>
