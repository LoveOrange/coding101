# MyBatis

本文以 MyBatis 3 与 MyBatis-Spring 的常规用法为范围。MyBatis 把 Mapper 方法和 SQL 映射为 `MappedStatement`，再通过 SqlSession、Executor 和 JDBC 处理一次数据库访问。掌握这条执行路径，才能判断缓存、插件、参数绑定和事务分别在哪一层生效。

## 1. 面试核心 {#core}

- Mapper 代理定位 MappedStatement，经 SqlSession、Executor 到 JDBC；缓存命中时可以不执行后续 JDBC 路径。[卡](#mybatis-query-flow)
- `#{}` 绑定值，`${}` 替换文本；动态标识符只能来自受控白名单，不能直接拼接请求参数。[卡](#parameter-binding)
- 一级缓存绑定 SqlSession，二级缓存按 namespace 显式配置；跨 namespace 或外部写入不会自动全面失效。[卡](#cache-boundaries)
- BATCH 的 flush 是执行批处理，commit 才是提交事务；Mapper 返回值不能直接当作真实影响行数。[卡](#batch-flush)
- 插件只有四类接口扩展点；Spring 的 SqlSessionTemplate 可共享，不代表底层 DefaultSqlSession 可被多线程共享。[卡](#plugin-boundaries)

## 2. 映射配置形成 MappedStatement {#1-映射配置形成-mappedstatement}

应用启动时，MyBatis 读取 XML 或注解中的 statement、动态 SQL、参数类型、ResultMap 和缓存配置，并保存到 `Configuration`。每条语句使用 `namespace + id` 作为标识，对应一个 `MappedStatement`。

```xml
<select id="findById" resultMap="orderResultMap">
  select id, user_id, status
  from orders
  where id = #{id}
</select>
```

Mapper 接口通常由动态代理实现。调用 `orderMapper.findById(id)` 时，代理根据接口与方法找到 statement id，再把参数交给 SqlSession。接口方法本身不包含查询实现。

## 3. 一次查询经过多个处理组件 {#2-一次查询经过多个处理组件}

以下是未命中缓存、采用 PreparedStatement 的常规查询路径；它是职责顺序，不是所有调用之间的直接调用关系：

```text
Mapper proxy
  → SqlSession
  → Executor
  → StatementHandler
  → ParameterHandler
  → JDBC PreparedStatement
  → ResultSetHandler
  → Java result
```

- **Executor**：组织查询或更新，管理本地缓存和事务相关操作。配置二级缓存时，CachingExecutor 会先处理 namespace 缓存，再进入实际执行器的本地缓存与查询路径。
- **StatementHandler**：创建、参数化并执行 JDBC Statement。
- **ParameterHandler**：使用 TypeHandler 把 Java 参数设置到 JDBC。
- **ResultSetHandler**：读取 ResultSet，并按 ResultMap 或结果类型构造对象。

理解职责比背类名更重要。SQL 没有生成正确，先看动态 SQL 与 BoundSql；参数类型错误看 ParameterHandler 和 TypeHandler；列映射错误看 ResultMap 与 ResultSetHandler。

## 4. Executor 决定语句复用与批处理方式 {#3-executor-决定语句复用与批处理方式}

MyBatis 提供三种主要 ExecutorType：

- `SIMPLE`：每次执行创建新的 Statement，是默认方式。
- `REUSE`：在当前执行器范围复用相同 SQL 的 PreparedStatement。
- `BATCH`：积累更新语句并批量提交给 JDBC 驱动。

`BATCH` 并不表示 Mapper 方法返回时数据库一定已经执行。`flushStatements()` 把积累的语句交给驱动执行并返回批处理结果；它本身不提交事务。实际行数应看 BatchResult/驱动返回值，不能把每次 Mapper 更新调用的返回值当成已完成影响行数。需要在 flush 或事务提交时检查批处理结果；中间查询也可能触发待执行语句刷新。批量执行的错误定位、生成键和事务大小都要单独测试。

## 5. 参数占位符与字符串替换用途不同 {#4-参数占位符与字符串替换用途不同}

`#{value}` 会生成 JDBC `?` 占位符，再由 PreparedStatement 绑定值。它适用于普通数据参数。

`${column}` 会把文本原样替换进 SQL，无法通过 PreparedStatement 绑定。表名、列名和排序方向确实不能作为普通值参数时，应在代码中映射到固定白名单：

以下 Java 17+ 片段假定 `sort` 是已校验的枚举；只输出固定 SQL 标识符：

```java
String orderBy = switch (sort) {
    case CREATED_AT -> "created_at";
    case AMOUNT -> "amount";
};
```

不能把请求中的字符串直接传给 `${}`，否则会形成 SQL 注入入口。

## 6. 一级缓存属于 SqlSession {#5-一级缓存属于-sqlsession}

每个 SqlSession 都有本地缓存。默认 `localCacheScope=SESSION` 时，相同 statement、参数和分页条件的查询可以复用结果；update、commit、rollback、close 等操作会清理缓存。

默认 SESSION 范围的本地缓存保存并返回对象引用。在同一 Session 内修改查询结果对象，后续缓存命中可能看到修改后的值。缩短 Session 生命周期、不随意修改查询结果，比依赖缓存副本更稳妥。

二级缓存按 Mapper namespace 配置，需要 `<cache/>`、`@CacheNamespace` 等显式声明，也受全局 `cacheEnabled` 和语句 `useCache` 控制。默认查询会使用已配置缓存，写语句默认触发所属 namespace 缓存刷新；缓存结果在会话的事务完成阶段按规则发布，不能认为查询返回时就对其他会话可见。

同一张表若由多个 namespace 或其他服务更新，某个 namespace 的缓存不会自动获知全部写入。可按依赖共享缓存配置或避免使用这种结果缓存。`localCacheScope=STATEMENT` 缩短一级缓存共享范围；查询的 `useCache=false` 控制二级缓存，不能据此断言一级缓存也关闭。

## 7. 插件只拦截指定扩展点 {#6-插件只拦截指定扩展点}

MyBatis 插件可以包装以下四类组件的指定方法：

- Executor
- StatementHandler
- ParameterHandler
- ResultSetHandler

分页、审计或租户条件插件需要选择最窄的扩展点。拦截器修改 BoundSql 时，要同时处理参数映射、缓存键、数据库方言和嵌套查询，不能只拼一段字符串。

插件顺序会改变行为。两个插件都重写 SQL 或参数时，应通过集成测试确认代理嵌套顺序和最终 SQL，而不是依赖注册代码的表面阅读。

## 8. 与 Spring 事务共用同一 SqlSession {#7-与-spring-事务共用同一-sqlsession}

使用 MyBatis-Spring 且事务管理器与 SqlSessionFactory 使用同一 DataSource 时，SqlSession 的创建、复用和提交由 Spring 事务同步管理。同一事务内的 Mapper 调用通常使用绑定到当前线程的 Session；直接手工创建另一个 Session 会脱离当前事务和一级缓存范围。

DefaultSqlSession 不是线程安全对象，应按单次工作单元管理；线程安全的 SqlSessionTemplate 根据当前事务取得实际 Session。事务外多次 Mapper 调用通常各自完成会话生命周期，不应期待跨调用命中同一个一级缓存。

Mapper 方法正常返回不等于外层事务已经提交。缓存可见性、批处理 flush 和连接释放都要结合外层事务边界判断。

## 9. 动态 SQL 与结果映射 {#动态-sql-与结果映射}

动态 SQL 在运行时根据参数生成 BoundSql。`<if>` 决定片段是否存在，`<where>` 处理 WHERE 及开头连接词，`<foreach>` 生成列表参数。空集合、空字符串和 null 的语义必须由业务明确，不能让“没有筛选条件”意外变成全表操作。

`resultType` 适合简单结果自动映射；`resultMap` 用于显式列映射、构造器、association 与 collection 等复杂结构。一对多映射应明确对象标识，避免把同一主记录反复创建。多参数 Mapper 可用 `@Param` 给出稳定名称，避免依赖编译器参数名设置。

嵌套 select 可能把一次列表查询变成 N+1 次访问；延迟加载只是推迟触发，不会消除查询数量。对照实际 SQL 日志决定 join、批量加载或分页策略，不能只看 Mapper 方法调用次数。

## 10. 常见问题 {#8-常见问题}

### 10.1 MyBatis 一级缓存会导致脏读吗 {#81-mybatis-一级缓存会导致脏读吗}

一级缓存可能让同一 SqlSession 重复读取到旧的本地对象，而没有再次访问数据库；这属于缓存与数据库之间的数据新鲜度问题。数据库“脏读”专指读取另一个事务尚未提交的修改，不能把缓存旧值直接称为脏读。排查时先确认 Session 范围、更新和缓存命中情况，再核对数据库隔离级别。

### 10.2 插件可以拦截任意 MyBatis 方法吗 {#82-插件可以拦截任意-mybatis-方法吗}

不能。官方插件机制只支持规定的四类接口及其方法。需要修改其他行为时，应使用明确扩展点或封装层，避免依赖内部类的偶然实现。

</details>

### 11.3 MyBatis 一级缓存和二级缓存的作用范围、失效条件有什么区别？ {#cache-boundaries}

<!-- 面试来源：金山云：https://www.nowcoder.com/discuss/800822936729894912；2026-10-13 核验一面第 26—29 项；这里只标注原帖明确覆盖的考点。 -->

**出现公司**：金山云

**考察重点**

- Session 与 namespace。
- 事务发布、跨 Mapper 写入和外部更新。

**相关内容**：[一级缓存属于 SqlSession](#5-一级缓存属于-sqlsession)、[与 Spring 事务共用同一 SqlSession](#7-与-spring-事务共用同一-sqlsession)。

<details>
<summary>参考回答</summary>

一级缓存随 SqlSession，默认可跨该 Session 的语句共享，更新、提交、回滚、关闭等会清理。二级缓存需按 namespace 配置，可在会话事务完成后供其他会话复用，默认写语句刷新所属缓存。它不按所有数据库表变化自动失效，跨 namespace 和外部写入都要单独设计一致性策略。Spring 事务外的多次调用也不能按一个长 Session 理解。

</details>

</details>
