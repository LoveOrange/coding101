# JUnit

JUnit 是 Java 的测试框架，用可重复执行的测试验证程序行为。一个测试要能发现它所检查的错误，就需要明确的前置状态、目标动作，以及能区分正确和错误结果的断言。

例如，金额构造器应拒绝负数，测试就要确认它确实抛出了约定的异常。除了检查结果，还要让测试互不干扰，并控制时间、随机数和异步执行，避免代码没变、测试却偶发失败。示例采用 JUnit Jupiter 5.13.4。

## 1. 面试核心 {#core}

- 每个测试**从独立的前置状态执行目标动作，再用断言检查**返回值、状态变化或失败结果。[卡](#junit-usage)
- `assertThrows` **接受指定异常类型及其子类**，`assertThrowsExactly` 要求抛出的异常类型完全匹配。
- `@ParameterizedTest` 为同一规则的**每组输入与期望结果分别执行一次**测试。[卡](#parameterized-tests)
- JUnit Jupiter 默认使用 `PER_METHOD` 生命周期，**为每次测试创建新的测试类实例**。
- `assertTimeout` **在当前线程执行，等调用结束后才判断超时**；`assertTimeoutPreemptively` 在另一个线程执行，并尝试中断超时的调用。[卡](#timeout-thread-boundary)

## 2. 测试结构 {#测试结构}

**AAA 结构**（Arrange-Act-Assert）是把测试组织为准备、执行和验证三部分的写法。下面用 `Money` 类型演示，它的构造方法约定拒绝负数金额：

```java
@Test
void rejectsNegativeAmount() {
    IllegalArgumentException exception = assertThrows(
        IllegalArgumentException.class,
        () -> new Money(new BigDecimal("-1.00"), CNY)
    );

    assertEquals("amount must be >= 0", exception.getMessage());
}
```

这三个部分在示例中分别是：

- Arrange（准备）：准备负数金额和币种。
- Act（执行）：调用 `Money` 构造方法。
- Assert（验证）：验证异常类型和可观察信息。

这几部分在代码里容易辨认就行，要不要加分段注释看复杂度。一个测试只覆盖一个行为条件，但可以用多条断言共同说明这个行为的结果，比如这里既检查异常类型，也检查异常消息。

检查消息意味着把它当作稳定契约：以后有人改了措辞，测试就会失败。如果消息只是给人看的诊断信息，只验证异常类型和业务字段即可。

## 3. 断言 {#断言}

**断言**判断执行结果是否符合预期，失败时让测试失败。比较方式要跟结果的含义匹配，比如相等、布尔条件、空值或集合元素：

```java
assertEquals(expected, actual);
assertTrue(result.isValid());
assertNull(repository.findRaw(id));
assertIterableEquals(expectedItems, actualItems);
```

断言越宽松，能发现的错误越少。比如只断言结果不为 `null`，金额算错、状态不对，测试照样通过。期望值 `expected` 的来源也有讲究：它应该来自明确的常量、小规模的手算结果，或者一个独立成立的性质。如果照着生产代码的算法再算一遍期望值，生产代码错了，测试也跟着错，断言就失去了区分能力。

断言还可以带一条失败消息，说明这次检查的是哪个业务条件，失败时更容易定位：

```java
assertEquals(expected, actual, "discount for first-time customer");
```

## 4. 异常与多个结果的断言 {#异常与多个结果的断言}

异常也是方法的可观察结果，测试要检查异常类型，也要检查它携带的业务信息。`assertThrows` 接受指定的异常类型及其子类，`assertThrowsExactly` 则要求类型完全一致。两者都会返回捕获到的异常，可以继续检查它的字段：

```java
DuplicateOrder exception = assertThrowsExactly(
    DuplicateOrder.class,
    () -> service.create(command)
);

assertEquals(command.idempotencyKey(), exception.key());
```

这里验证重复创建订单时抛出的正好是 `DuplicateOrder`，并且异常里的幂等键对应当前这次请求。

一个行为同时改变多个相关字段时，可以用 `assertAll` 汇总断言失败。这样，前一个字段不符合预期时，后面的字段仍会被检查，报告能一次列出多处不符：

```java
assertAll(
    () -> assertEquals(PAID, order.status()),
    () -> assertEquals(paymentId, order.paymentId()),
    () -> assertEquals(paidAt, order.paidAt())
);
```

`assertAll` 适合检查同一个行为的多个结果。互相独立的场景要拆成独立测试，否则一个场景的前置动作失败了，后面的断言会跟着一起失败，干扰定位。

## 5. 参数化测试 {#参数化测试}

**参数化测试**用同一段测试逻辑跑多组数据，每组只替换输入和期望结果。适用的前提是这些数据遵循同一条规则。下面用一个方法检查十进制整数的位数：

```java
@ParameterizedTest
@CsvSource({
    "0, 1",
    "1, 1",
    "10, 2",
    "99, 2"
})
void countsDecimalDigits(int input, int expectedDigits) {
    assertEquals(expectedDigits, DecimalDigits.count(input));
}
```

`@CsvSource` 里的四组参数会分别运行一次：0 和 1 期望 1 位，10 和 99 期望 2 位。某一组失败时，报告会指出是哪一组输入。

挑数据时，可以先划分等价类，再补充边界值。**等价类**是按同一规则处理的一组输入，可以从每组挑选代表，避免堆积重复案例。**边界值**是规则切换附近的值，比如位数从 1 变成 2 的 9 和 10，用它们可以检查分界条件有没有写错。上面的示例已经包含 10，还可以补上 9，形成直接对照。数据来源按数据的形态选：

- `@ValueSource` 提供简单的单参数数据，例如一组整数。
- `@NullSource`、`@EmptySource` 分别提供空引用和空内容，用于检查缺失或空输入。
- `@CsvSource`、`@CsvFileSource` 从内联 CSV 或文件提供多列数据。
- `@EnumSource` 提供枚举值，适合遍历状态或选项。
- `@MethodSource` 由工厂方法生成参数，适合复杂对象和需要清楚命名的案例。
- 自定义 `ArgumentsProvider` 可以封装需要自行生成的参数。

参数是复杂对象时，用 `@MethodSource` 写比一长串 CSV 好读。工厂方法要不要 `static`，取决于测试实例的生命周期（第 6 节）：默认的 `PER_METHOD` 下，本类的工厂方法必须是 `static`；`PER_CLASS` 复用同一个测试实例，所以允许本类的非静态工厂方法。放在外部类里的工厂方法始终要 `static`。

## 6. 生命周期与隔离 {#生命周期与隔离}

测试要从可重复的状态开始，换一种执行顺序也应该得到同样的结果。JUnit Jupiter 默认为每个测试方法创建一个新的测试类实例，这叫 `PER_METHOD` 生命周期；`@BeforeEach` 方法则在每个测试之前执行，用来准备依赖：

```java
@BeforeEach
void setUp() {
    repository = new InMemoryOrderRepository();
    service = new OrderService(repository, fixedClock);
}
```

`setUp` 每次都新建一个内存版的 `repository`，也就是保存和读取订单的对象。前一个测试写入的订单，后一个测试就看不到。新实例只能隔离实例字段，静态状态和数据库里的残留数据还得单独清理；`fixedClock` 则避免了真实时钟让结果随执行时间变化（第 7 节）。

创建代价高的资源可以放到 `@BeforeAll` 里只建一次，但每个测试仍要重置业务数据。改用 `PER_CLASS` 后，所有测试共用一个测试类实例，实例字段也需要清理。参数化测试的每次调用都会单独执行 `@BeforeEach`，所以每组数据都有独立的起点。

## 7. 时间、随机与并发 {#时间随机与并发}

测试如果依赖真实时间、随机数或外部资源，就可能在代码未变时偶发失败。要让结果可重复，需要控制这些依赖：

- 注入 `Clock`，让被测代码通过它读取时间，测试时固定当前时间。
- 注入随机源并使用固定种子，让重复运行得到同样的随机序列。
- 用 `@TempDir` 提供临时目录，隔离测试文件。
- 由测试环境分配端口，减少端口被其他进程占用造成的失败。

以时间为例，被测代码不直接调用 `Instant.now()`，而是从注入的 `Clock` 读取，测试里传入一个固定时钟：

```java
Clock clock = Clock.fixed(
    Instant.parse("2026-08-30T00:00:00Z"),
    ZoneOffset.UTC
);
```

被测代码通过这个 `clock` 读到的永远是示例指定的时间点。

并发测试要等一个明确的完成信号，比如用 `Future` 取任务结果，用 `CountDownLatch` 等任务完成，或者用 Awaitility 轮询条件是否满足并设置等待上限。单纯 `sleep` 一段时间，只是在猜任务什么时候完成，机器一慢就会偶发失败。

测试里的超时断言用来检查操作是否在约定时间内完成，测量性能则需要专门的基准测试。`assertTimeout` 会等调用结束再检查耗时，因此不能中止永久阻塞的调用；它和抢占式超时的区别见[超时执行与线程边界](#超时执行与线程边界)。

## 8. 测试命名 {#测试命名}

测试失败时，名字应该直接告诉你是什么条件下、期望什么结果。下面这个名字说明，支付已取消的订单应该被拒绝：

```java
@Test
void payingCancelledOrderIsRejected() {}
```

和 `testPay1` 相比，它把条件、行为和结果都写了出来。还可以用 `@Nested` 按方法或状态把测试分组，用 `@DisplayName` 补充业务描述。不过方法名本身也要保留明确的含义，方便搜索和定位失败用例。

## 9. 超时执行与线程边界 {#超时执行与线程边界}

两种超时断言的区别在于被测代码在哪个线程执行。这决定了测试什么时候失败，也决定了被测代码能用到哪个线程上的上下文。

`assertTimeout` 在当前线程执行被测代码，等代码返回后再比较耗时。所以代码要是永久阻塞，这个断言也会一直等下去。

`assertTimeoutPreemptively` 在另一个线程执行被测代码，到达上限后测试可以提前失败。JUnit 会尝试中断执行线程，但被测代码必须响应中断，才能及时停下来。

换线程的副作用在事务测试里最明显。Spring 的测试事务通过 `ThreadLocal` 绑定在当前线程上，也就是把事务信息存在当前线程里。抢占式断言换了执行线程，里面的数据库操作就脱离了原来的测试事务。如果这些操作在自己的事务里提交了，测试结束时外层回滚也撤销不了它们，数据就留在了数据库里。

所以需要沿用当前线程的事务时，用同线程的 `assertTimeout`。确实需要抢占式超时，就要单独设计执行线程上的事务和中断处理。

## 10. 常见问题 {#常见问题}

### 10.1 一个测试只能有一条断言吗？ {#行为与断言数量}

不是。一个行为可以有多条相关断言，比如同时检查订单状态和支付时间。要拆开的是独立的动作或不同的前置条件，因为它们各有各的失败原因。

### 10.2 私有方法怎样测试？ {#私有方法的测试入口}

通过公开行为覆盖私有实现，测试只停留在调用方能观察到的范围内。私有方法里有独立且复杂的规则时，可以把它提取成一个有明确包级或公开契约的对象。这样规则能单独验证，也不用通过反射去绑定私有实现。

### 10.3 参数化测试能替代普通测试吗？ {#参数化与独立场景}

不能。参数化测试适合同一个行为的多组数据，独立场景仍然用普通测试。准备过程、目标动作或失败路径明显不同时，分开写更清楚。针对某个具体故障的回归测试也可以单独保留，一看就知道它防的是哪个问题。

### 10.4 抢占式超时为什么会影响线程上下文？ {#抢占式超时的使用边界}

因为它在另一个线程执行，而普通 `ThreadLocal` 里的数据属于原来的线程，新线程读不到。测试事务这类上下文要按新线程重新设计，超时后还要确认被测代码会响应中断。对事务的具体影响见[超时执行与线程边界](#超时执行与线程边界)。

## 11. 面试题 {#面试题}

### 11.1 平时怎样使用 JUnit 编写单元测试 {#junit-usage}

**考察重点**

- 说明怎样为测试建立独立状态，以及断言如何区分正确与错误结果。
- 说明时间、随机和外部依赖怎样变得可控。
- 说明单元测试与启动完整 Spring 环境的区别。

**相关内容**：[测试结构](#测试结构)至[测试命名](#测试命名)。

<details>
<summary>参考回答</summary>

**JUnit 测试从独立、可重复的状态执行目标行为，再用断言验证可观察结果。**

每个测试都要明确准备、执行和验证三部分。整组用例分别覆盖正常结果、边界与失败后的状态。期望结果使用常量、手算结果或独立性质，避免复制生产算法。

时间通过固定 `Clock` 控制，随机源使用固定种子，测试顺序也应保持独立。纯业务规则可以直接构造对象，并通过窄接口替换外部依赖，无需启动 Spring 容器。数据库映射、事务和 Bean 配置则由使用真实组件的集成测试验证。

</details>

### 11.2 什么情况下使用参数化测试 {#parameterized-tests}

**考察重点**

- 说明怎样为同一规则选择等价类与边界值。
- 说明数据源和测试逻辑如何保持可读。
- 说明复杂场景为什么仍需要独立测试。

**相关内容**：[参数化测试](#参数化测试)。

<details>
<summary>参考回答</summary>

**同一条规则只改变输入和期望结果时，适合使用参数化测试。**

例如金额边界、日期解析与状态枚举，都可以用多组数据验证。

简单值使用 `@ValueSource` 或 `@CsvSource`，复杂对象和需要清楚命名的案例使用 `@MethodSource`。每组数据都应有明确的期望结果，失败时能直接定位对应输入。准备、动作或断言路径明显不同的场景，则拆成独立测试。

</details>

### 11.3 assertTimeout 会中止慢调用吗，抢占式超时为何会影响事务测试？ {#timeout-thread-boundary}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：区分两种超时断言的执行线程，并解释中断处理和线程绑定事务对测试结果的影响。

**相关内容**：[超时执行与线程边界](#超时执行与线程边界)。

<details>
<summary>参考回答</summary>

**`assertTimeout` 会等代码结束后才判断超时，因此不会中止慢调用。**

`assertTimeoutPreemptively` 在另一线程执行，到达上限后可提前失败，并尝试中断执行线程。被测代码要响应中断，才能及时结束。

Spring 测试事务绑定原线程，新线程无法自动沿用该事务。所以，抢占式断言中的数据库操作会脱离外层回滚范围。它们若已在自己的事务中提交，外层回滚也无法撤销。事务测试应让执行线程与事务的作用范围保持一致。

</details>
