# 测试金字塔

测试金字塔按验证范围组织测试组合。本文负责层级选择、契约、覆盖率与回归策略。

单元测试写法见 [JUnit](./junit-assertions-parameterized-tests.mdx)。数据库行为验证见 [批处理与分页](../data-access/batching-pagination-data-access-tests.mdx)。

## 1. 面试核心 {#core}

- 单元测试验证局部规则，集成测试验证真实组件协作。[卡](#test-levels)
- 契约测试验证消费方依赖与提供方实现，端到端测试验证完整流程。[卡](#contract-provider-verification)
- JaCoCo 行覆盖率记录指令执行，分支覆盖率记录条件分支执行。[卡](#high-coverage-regressions)
- 回归测试保留缺陷触发条件，并验证修复后的可观察行为。
- 变异测试修改条件或返回值，检测断言能否识别错误。[卡](#mutation-survivors)

## 2. 测试范围 {#测试范围}

| 类型 | 主要证据 | 常见盲区 |
| --- | --- | --- |
| 单元测试 | 一个行为单元的规则与边界 | 框架配置、真实协议、数据库 |
| 组件或切片测试 | Web、数据访问等局部集成 | 完整部署与跨服务链路 |
| 集成测试 | 真实数据库、消息或客户端协作 | 全系统用户流程 |
| 契约测试 | 提供方与消费方接口兼容 | 服务内部正确性、真实容量 |
| 端到端测试 | 部署环境中的关键业务路径 | 细粒度失败定位、所有组合 |

金额舍入用单元测试，数据库精度用集成测试。回调字段用契约测试，下单主路径用端到端测试。各层分别覆盖不同失败原因。

## 3. 底层测试的数量 {#底层测试的数量}

单元测试运行快、失败定位清楚，适合覆盖大量分支和边界。端到端测试跨进程、网络、数据和异步任务：

- 环境更难建立。
- 运行时间更长。
- 失败原因更多。
- 测试数据更易冲突。
- 重试可能掩盖真实不稳定。

测试分布由风险决定。纯规则多的系统适合大量单元测试。数据库逻辑集中的系统需要更多集成测试。

## 4. 真实依赖 {#真实依赖}

真实数据库测试可固定目标版本。下面按 Testcontainers 1.21.3 的 API 写法示意：

```java
@Testcontainers
class OrderRepositoryTest {
    @Container
    static PostgreSQLContainer<?> database =
        new PostgreSQLContainer<>("postgres:18");
}
```

容器化依赖可以固定镜像版本，并为 CI 创建隔离环境。测试仍要管理：

- schema 迁移。
- 每个用例的数据清理。
- 启动和复用策略。
- ARM/x86 与生产插件差异。
- 外部镜像获取和供应链安全。

容器固定依赖环境，生产插件、参数与数据规模仍需核对。数据访问的具体测试范围见 [批处理与分页](../data-access/batching-pagination-data-access-tests.mdx#7-数据访问测试使用目标数据库)。

## 5. 契约测试 {#契约测试}

服务独立测试通过后，接口仍可因字段变化而不兼容。契约测试记录消费方真实依赖：

```json
{
  "status": "PAID",
  "amount": {
    "value": "10.00",
    "currency": "CNY"
  }
}
```

消费方验证客户端能处理契约样例，提供方验证当前实现能满足该契约。它可以发现：

- 删除或重命名字段。
- 类型与可空性变化。
- 状态码和错误体变化。
- 消费方依赖的枚举值变化。

真实网络容量、认证设施与长链路结果需另行验证。

## 6. 回归测试 {#回归测试}

修复 bug 时先保留能稳定失败的最小用例，再修改实现。这个用例记录的是：

- 哪个输入触发问题。
- 哪条外部行为必须保持。
- 修复后未来变更不能再次破坏什么。

用例应保留触发条件，并删除无关数据。涉及集成路径的缺陷，还需在对应层级验证修复。

## 7. 覆盖率的含义 {#覆盖率的含义}

JaCoCo 把至少一条指令执行过的行标为已覆盖。分支计数覆盖 if 和 switch 的分支。异常处理不计入它的分支覆盖率。

覆盖率衡量执行范围。行覆盖率达到 100%，仍会漏掉分支与输入组合。即使分支全覆盖，错误结果也能通过薄弱断言。

覆盖率适合寻找未执行区域。断言质量还需结合边界用例、真实集成与变异测试检查。

## 8. 不稳定测试 {#不稳定测试}

常见 flaky 来源：

- 依赖真实时间和 sleep。
- 测试执行顺序和共享数据。
- 未等待的异步任务。
- 随机端口、网络和第三方服务。
- 并发断言没有同步条件。
- 数据库清理与事务边界错误。

重跑可收集失败频率与环境证据。测试仍需修复共享状态、时间或等待条件。临时隔离时，应记录恢复条件并补足关键覆盖。

## 9. 风险与测试层级 {#按风险分配测试层级}

可以对每项变化问：

1. 错误影响多大？
2. 最便宜的哪一层能可靠发现它？
3. 哪些真实组件行为不能被替身模拟？
4. 哪个边界由其他团队或服务维护？
5. 失败后能否快速定位和重放？

例如支付适配器：

- 单元：金额、幂等键和错误映射。
- 契约：请求字段、签名输入和响应结构。
- 集成：HTTP 客户端超时、TLS 与序列化。
- 端到端：沙箱中一条成功和一条失败主流程。

## 10. 消费方契约与服务端验证 {#消费方契约与服务端验证}

Pact 消费方测试让真实客户端请求模拟提供方。测试通过后生成交互契约。提供方验证再把同一交互回放给实际实现。

每项交互需要独立的 provider state。例如先准备“订单存在”，再验证查询响应。交互之间应相互独立，避免依赖执行顺序。

只有模拟服务测试通过，还缺少提供方验证。发布检查应使用活跃消费者版本对应的契约结果。

## 11. 变异测试结果 {#变异测试结果}

PIT 会临时改变条件、运算或返回值，再运行相关测试。测试因此失败，称为杀死该变异。测试仍通过，则该变异存活。

存活变异可提示缺少边界输入或结果断言。也存在等价变异：代码形式改变，外部行为仍相同。分析时需区分无覆盖、存活与等价情况。

例如把金额校验 `< 0` 改成 `<= 0`。零金额合法的测试应失败，从而发现边界被改坏。

## 12. 常见问题 {#常见问题}

### 12.1 端到端与单元测试 {#端到端与单元测试}

端到端测试与单元测试应组合使用。端到端验证完整路径，单元测试低成本覆盖规则边界。两者分别帮助发现集成与局部逻辑错误。

### 12.2 H2 与目标数据库 {#h2-与目标数据库}

H2 可覆盖共享的 SQL 与 JDBC 逻辑。目标数据库的锁、方言、索引与时间类型需单独验证。

### 12.3 契约测试与接口文档 {#契约测试与接口文档}

契约测试执行消费方交互，并验证提供方实现。接口文档校验只覆盖描述层。契约版本也需跟随活跃消费方维护。

### 12.4 测试代码的复用范围 {#测试代码的复用范围}

环境建立和对象工厂可以抽取。关键输入与期望结果应保留在用例附近，便于定位失败。

测试应放在能可靠发现该问题的最小范围。更高层保留关键集成与业务流程验证。

### 13.2 为什么高覆盖率仍然可能发生严重回归 {#high-coverage-regressions}

<!-- 面试来源：
- 腾讯、字节跳动、快手、滴滴：https://www.nowcoder.com/discuss/586632
-->

**出现公司**：腾讯、字节跳动、快手、滴滴

**考察重点**

- 说明执行过代码与验证正确结果的区别。
- 说明组合、协议、并发和时序盲区。
- 说明覆盖率怎样作为诊断指标而非目标。

**相关内容**：[回归测试](#回归测试)、[覆盖率的含义](#覆盖率的含义)。

<details>
<summary>参考回答</summary>

覆盖率衡量执行范围，无法衡量断言是否识别错误。行已执行仍可漏掉分支，分支已执行仍可漏掉组合。并发时序与外部协议也需专门用例。

可结合边界测试、真实集成和历史回归检查风险。变异测试进一步检查断言对代码错误的敏感度。

</details>

### 13.3 消费方对模拟服务测试通过，为什么还要验证提供方？ {#contract-provider-verification}

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：契约生成、回放与 provider state。

**相关内容**：[消费方契约与服务端验证](#消费方契约与服务端验证)。

<details>
<summary>参考回答</summary>

模拟服务测试只验证客户端符合约定交互。提供方验证回放同一契约，检查实际实现是否满足它。provider state 为每项交互准备独立前置数据。

</details>
