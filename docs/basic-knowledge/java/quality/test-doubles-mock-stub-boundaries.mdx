# 测试替身

测试替身用可控对象替换协作者。本文负责 Stub、Mock、Fake、Spy 的用途与交互验证。代码采用 Mockito 5.20.0。

断言与生命周期见 [JUnit](./junit-assertions-parameterized-tests.mdx)。真实集成覆盖见 [测试金字塔](./test-pyramid-contract-regression.mdx)。

## 1. 面试核心 {#core}

- Stub 提供预设结果，Mock 验证协作者交互。[卡](#mock-vs-stub)
- Fake 是可运行的简化实现，Mockito Spy 默认执行真实方法。
- Mock 验证调用意图，真实 SQL、映射与约束由集成测试验证。
- 验证内部调用图会让等价重构破坏测试。[卡](#over-mocking)
- `doReturn(...).when(spy)` 在配置阶段避开真实方法执行。[卡](#spy-stubbing)

## 2. 测试替身的种类 {#测试替身的种类}

| 类型 | 主要作用 | 示例 |
| --- | --- | --- |
| Dummy | 只填充参数，不参与行为 | 未使用的回调对象 |
| Stub | 为测试场景返回预设结果 | 固定汇率提供者 |
| Fake | 有可运行的简化实现 | 内存 Repository |
| Spy | 记录真实或包装对象的调用 | 记录发送次数 |
| Mock | 按期望验证交互 | 验证消息网关收到命令 |

这些名称描述测试用途。Mockito 创建的对象只返回预设值时，承担 Stub 角色。

## 3. Stub {#stub}

```java
ExchangeRateProvider rates = mock(ExchangeRateProvider.class);
when(rates.rate(USD, CNY, at))
    .thenReturn(new ExchangeRate("7.20"));

Price result = service.convert(price, CNY, at);

assertEquals(expected, result);
```

测试重点是转换结果，Stub 只提供所需汇率。它避免真实网络波动，也能稳定构造超时、缺失和异常等难以复现条件。

真实协议、序列化与客户端配置需用集成或契约测试验证。

## 4. Mock {#mock}

```java
PaymentGateway gateway = mock(PaymentGateway.class);

service.pay(command);

verify(gateway).charge(command.idempotencyKey(), command.amount());
```

适合验证：

- 必须发送一次支付命令。
- 拒绝请求时不应发送消息。
- 重试使用同一个幂等键。
- 业务流程先登记事件，再交给发布端口。

verify 适合约束有业务意义的外部调用。真实事务提交后的发布时机，需用集成测试验证。

## 5. 状态断言与交互断言 {#状态断言与交互断言}

状态断言检查结果：

```java
assertEquals(PAID, order.status());
```

交互断言检查协作者调用：

```java
verify(eventPublisher).publish(any(PaymentAccepted.class));
```

纯计算和值对象优先验证状态。外部副作用可通过端口交互检查。两者可组合，分别验证结果与调用意图。

## 6. 替换的边界 {#替换的边界}

可替换的边界包括：

- 时钟与随机源。
- 支付、邮件、对象存储等外部客户端。
- Repository 接口。
- 消息发布端口。
- 昂贵或不可稳定复现的系统依赖。

不值得 Mock：

- String、Money 等值对象。
- 当前类内部的私有方法。
- 简单数据结构。
- 被测对象本身。
- 只有一行转发、且 Mock 后没有真实逻辑剩余的组件。

一个类需要十几个 Mock 时，应检查职责是否过多。也应检查接口能否按业务能力集中表达。

## 7. Fake {#fake}

内存 Repository 可以真实执行保存和查询：

```java
final class InMemoryOrderRepository implements OrderRepository {
    private final Map<OrderId, Order> orders = new HashMap<>();

    @Override
    public void save(Order order) {
        orders.put(order.id(), order);
    }
}
```

Fake 让多个操作共享可控状态。上例只是写入方法片段，查询需按接口补齐。真实数据库的约束、事务、排序与锁需集成测试覆盖。

## 8. Spy 与部分 Mock {#spy-与部分-mock}

Spy 默认调用真实方法，同时允许局部替换。它适合观测遗留对象，但容易形成“部分真实、部分虚假”的难懂状态。

```java
List<String> spy = spy(new ArrayList<>());
```

大量部分替换会增加理解成本。有独立职责时，可提取明确协作者。

## 9. 过度严格的交互验证 {#过度严格的交互验证}

以下测试对重构很脆弱：

- 验证每个内部调用恰好一次。
- 使用 `inOrder` 固定无业务意义的顺序。
- 对所有参数使用 `any()`，实际什么都没验证。
- 对所有调用使用精确对象匹配，连无关字段也固定。
- 使用 `verifyNoMoreInteractions` 阻止新增遥测等无害行为。

交互验证应围绕公共契约。检查目标端口、业务参数、重试次数与失败处理。

## 10. Spy 的配置阶段调用 {#spy-的配置阶段调用}

Mockito Spy 默认调用真实方法。`when(spy.get(0))` 会先求值，因此配置时就访问列表。

```java
List<String> values = spy(new ArrayList<String>());
// when(values.get(0)).thenReturn("A"); // 运行时越界
doReturn("A").when(values).get(0);
assertEquals("A", values.get(0));
```

doReturn 让配置阶段避开真实 get 调用。它适合已有 Spy 的副作用方法。普通 Mock 仍可使用更直观的 when/thenReturn。

## 11. 参数匹配与捕获 {#参数匹配与捕获}

同一次调用使用匹配器时，每个参数都需使用匹配器。固定值可用 eq 包装，空值用 isNull 匹配。

```java
verify(gateway).charge(eq(key), any(Money.class));
```

any(Money.class) 只检查非空类型。需要验证金额内容时，可用 ArgumentCaptor 捕获参数：

```java
ArgumentCaptor<Money> amount = ArgumentCaptor.forClass(Money.class);
verify(gateway).charge(eq(key), amount.capture());
assertEquals(expectedAmount, amount.getValue());
```

捕获后的断言检查业务字段。测试因此能发现类型正确但金额错误的调用。

## 12. 常见问题 {#常见问题}

### 12.1 Repository 替身与数据库测试 {#repository-替身与数据库测试}

Mock Repository 验证上层如何响应预设结果。真实 SQL、约束与事务需数据库集成测试。

### 12.2 Mockito 与私有方法 {#mockito-与私有方法}

Mockito 的常规 API 不支持 Mock 私有方法。应通过公开行为测试，或提取独立协作者。

### 12.3 调用次数的业务约束 {#调用次数的业务约束}

次数有业务含义时验证。例如同一流程只发一次支付请求，通知最多重试三次。内部 helper 的调用次数可由实现调整。

### 12.4 测试替身与测试层级 {#测试替身与测试层级}

测试层级取决于验证范围和真实运行依赖。使用 Mock 的测试仍可启动完整容器并跨多个组件。

## 13. 面试题 {#面试题}

### 13.1 Mock 与 Stub 有什么区别，分别什么时候使用 {#mock-vs-stub}

**出现公司**：招银网络、爱客科技

**考察重点**

- 说明预设输入与验证交互的区别。
- 说明状态断言和交互断言的选择。
- 说明替身不能证明真实集成行为。

<details>
<summary>参考回答</summary>

Stub 提供预设结果，Mock 验证协作者调用。纯计算适合结果断言，外部副作用适合交互断言。

替身可隔离时钟、Repository 与远程网关。真实协议、序列化和数据库约束需集成或契约测试补充。

</details>

### 13.2 过度 Mock 会带来什么问题 {#over-mocking}

<!-- 面试来源：
- 阿里巴巴：https://www.nowcoder.com/discuss/353156377390555136
-->

**出现公司**：阿里巴巴

**考察重点**

- 说明测试绑定实现调用图后为何难以重构。
- 说明全部依赖被替换后留下了哪些盲区。
- 说明大量 Mock 是否暴露职责过多。

**相关内容**：[替换的边界](#替换的边界)、[过度严格的交互验证](#过度严格的交互验证)。

<details>
<summary>参考回答</summary>

过度 Mock 会把内部调用图固定成测试契约。等价重构也会让测试失败，真实集成行为却仍缺乏覆盖。

测试应验证公开结果与关键外部交互。大量替身还提示需要检查职责边界。

</details>

### 13.3 给空列表 Spy 配置 get(0)，为什么 when 写法会直接抛异常？ {#spy-stubbing}

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：实参求值、真实调用与 doReturn。

**相关内容**：[Spy 的配置阶段调用](#spy-的配置阶段调用)。

<details>
<summary>参考回答</summary>

when 的实参先求值，因此真实 get(0) 在配置时执行。空列表随即抛出越界异常。`doReturn("A").when(spy).get(0)` 可避开配置阶段的真实调用。

</details>

### 13.4 any 匹配的测试为何会漏掉错误金额，怎样验证实际参数？ {#mock-argument-capture}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：匹配器与业务字段断言。

**相关内容**：[参数匹配与捕获](#参数匹配与捕获)。

<details>
<summary>参考回答</summary>

any 只约束匹配范围，无法检查具体金额。可用 ArgumentCaptor 捕获参数，再断言金额与币种。同次调用用了匹配器时，其他参数也需用 eq 等匹配器。

</details>
