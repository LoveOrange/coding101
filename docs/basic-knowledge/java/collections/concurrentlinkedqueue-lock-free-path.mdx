# ConcurrentLinkedQueue

`ConcurrentLinkedQueue` 是无界 FIFO 并发队列。本文负责 OpenJDK 26 的 CAS 入队、出队与进展保证。

容量和阻塞等待见 [BlockingQueue](./blockingqueue-producer-consumer.mdx)。遍历视图见 [迭代一致性](./concurrent-collection-iteration-consistency.mdx)。

## 1. 面试核心 {#core}

- ConcurrentLinkedQueue 是无界 FIFO 队列，offer 与 poll 使用 CAS 协调。[卡](#cas-enqueue-dequeue)
- 入队以链接 next 的成功 CAS 生效，出队以清空 item 的成功 CAS 生效。[卡](#cas-enqueue-dequeue)
- lock-free 保证整体进展，单个线程仍会因竞争重试。
- `size()` 需遍历节点，并发更新时只能反映观察值。
- `poll()` 在空队列返回 null，条件等待需用 BlockingQueue。[卡](#clq-vs-lbq)

## 2. 头尾指针 {#头尾指针}

队列保存 head、tail 和节点的 next 链接。head 与 tail 允许暂时落后。线程沿链接查找有效位置，再协助推进。

```text
head                             tail
 ↓                                ↓
[removed] -> [A] -> [B] -> [C] -> null
```

允许指针落后可减少强制 CAS 次数。后续线程查找位置时可协助推进。线程暂停也无需等待它释放队列锁。

## 3. offer 入队 {#offer-入队}

入队的大致逻辑：

1. 创建 item 为新元素、next 为 null 的节点。
2. 从观察到的尾部向后寻找实际末端。
3. 对末端节点的 next 执行 CAS，把 null 改为新节点。
4. 视情况推进 tail；失败也不影响元素已经成功链接。

多个生产者竞争同一末端时，只有一个 CAS 成功。失败者重新查找并重试。lock-free 保证系统整体取得进展。单个线程仍会因持续竞争而长时间重试。

## 4. poll 出队 {#poll-出队}

poll 从 head 向后查找首个 item 非 null 的节点。它通过 CAS 把 item 改为 null。CAS 成功的消费者获得该元素，其他消费者继续查找。

逻辑删除后，线程再尝试推进 head。旧头节点还可自链接，用于标记脱离主链。线程遇到这种标记时，从当前 head 重新查找。

## 5. 竞争下的重试成本 {#竞争下的重试成本}

offer 与 poll 使用无锁算法。高竞争时仍需承担这些成本：

- CAS 失败和重试。
- 同一缓存行在核心间传递。
- 节点分配与 GC。
- 遍历 next 链寻找有效节点。

无锁算法减少对持锁线程进度的依赖。吞吐还受竞争、分配和消费速度影响。选择时应按真实负载比较。

## 6. size 的成本 {#size-的成本}

```java
int pending = queue.size();
```

OpenJDK 26 的 size 通过遍历统计有效节点，成本为 O(n)。并发入队与出队会影响统计结果。

因此不要写：

```java
if (queue.size() < limit) {
    queue.offer(job);
}
```

检查和入队是两个操作，线程会在中间交错。需要容量限制时，使用有界 BlockingQueue。

## 7. 弱一致迭代 {#弱一致迭代}

ConcurrentLinkedQueue 的迭代器采用弱一致语义。适用范围与消费操作的区别见 [迭代一致性](./concurrent-collection-iteration-consistency.mdx#并发队列的迭代)。

## 8. 适用场景 {#适用场景}

适合：

- 多生产者、多消费者的进程内 FIFO。
- 不需要阻塞等待、容量限制和严格快照。
- 调用方能自行处理空队列轮询策略。

不适合：

- 必须通过容量向上游施加背压。
- 消费者希望在队列为空时睡眠等待；此时 BlockingQueue 更合适。
- 任务必须持久化或跨进程。
- 需要按优先级、延迟或严格公平处理。

`poll` 返回 null 表示当前观察不到元素，因此队列禁止保存 null。

## 9. 空值与对象发布 {#空值与对象发布}

ConcurrentLinkedQueue 拒绝 null，因为 poll 用它表示队空。生产者入队前的写入，对取得该元素的线程可见。入队后继续修改元素时，仍需独立同步。

成功 poll 只表示当前消费者取得一个元素。处理失败后的重试与重复副作用由业务协议管理。进程崩溃后的任务恢复需要持久存储。

## 10. 常见问题 {#常见问题}

### 10.1 lock-free 与 wait-free {#lock-free-与-wait-free}

lock-free 保证系统整体取得进展。某个线程仍可反复重试。wait-free 还要求每个操作在有界步骤内完成。

### 10.2 空队列等待策略 {#空队列等待策略}

条件等待应使用 BlockingQueue。持续自旋占用 CPU，固定 sleep 增加延迟。已有唤醒机制的事件循环可使用非阻塞队列。

### 10.3 isEmpty 与 poll 的时序 {#isempty-与-poll-的时序}

直接调用 poll 并处理 null 即可。isEmpty 与 poll 之间仍可发生并发出队。

### 10.4 FIFO 与线程公平性 {#fifo-与线程公平性}

FIFO 约束元素的取出顺序。线程执行机会仍由调度与 CAS 竞争决定。

### 11.1 ConcurrentLinkedQueue 怎样用 CAS 完成入队和出队 {#cas-enqueue-dequeue}

**出现公司**：快手、蚂蚁集团

**考察重点**

- 说明节点链接与逻辑删除分别使用什么 CAS。
- 说明head、tail 为什么允许暂时落后。
- 说明lock-free 与 wait-free 的区别。

**相关内容**：[头尾指针](#头尾指针)至[竞争下的重试成本](#竞争下的重试成本)。

<details>
<summary>参考回答</summary>

入队通过 CAS 把末端 next 从 null 改为新节点。出队通过 CAS 把首个有效节点的 item 改为 null。两处成功 CAS 分别确定入队与领取结果。

head、tail 可稍后推进，其他线程能协助完成。整体算法提供 lock-free 进展，单线程仍可持续重试。

</details>

### 11.2 ConcurrentLinkedQueue 与 LinkedBlockingQueue 怎样选择 {#clq-vs-lbq}

**出现公司**：快手

**考察重点**

- 说明非阻塞无界队列与可阻塞有界队列的协议差异。
- 说明size、背压和消费者等待。
- 说明CAS 重试与锁条件等待各自的成本。

**相关内容**：[size 的成本](#size-的成本)、[适用场景](#适用场景)。

<details>
<summary>参考回答</summary>

已有唤醒机制且无需容量限制时，可用 ConcurrentLinkedQueue。poll 在空队列立即返回 null。

需要缓冲上限和条件等待时，使用有界 LinkedBlockingQueue。它提供 put、take 和限时操作。选择取决于交接协议与实际负载。

</details>

### 11.3 无锁队列怎样保证入队前的字段写入对消费者可见？ {#clq-publication}

<details>
<summary>参考回答</summary>
