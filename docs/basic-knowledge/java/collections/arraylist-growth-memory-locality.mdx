# ArrayList

<ReviewReading plan={javaCollectionsReview} stepId="collections-arraylist" />

`ArrayList` 用连续引用数组保存元素。本文负责容量管理、扩容、搬移和视图成本。实现细节以 OpenJDK 26 为准。

链表定位成本见 [LinkedList](./linkedlist-semantics-cost.mdx)。固定大小与只读列表见 [集合迭代器](./iterator-fail-fast-immutable.mdx)。

## 1. 面试核心 {#core}

- `ArrayList` 的 `get`、`set` 按下标访问，成本为 O(1)。
- OpenJDK 26 的扩容首选增量是旧容量的一半。[卡](#arraylist-growth)
- 尾部追加摊销 O(1)，单次扩容复制为 O(n)。[卡](#arraylist-growth)
- 中间插入和删除搬移后续引用，最坏为 O(n)。[卡](#arraylist-vs-linkedlist)
- `subList` 共享原列表，复制子列表才能隔离结构变化。[卡](#sublist-retention)

## 2. size 与 capacity {#size-与-capacity}

`size` 是当前元素数量。capacity 是内部数组长度：

```java
List<String> values = new ArrayList<>(100);
System.out.println(values.size()); // 0
```

构造参数 `100` 预留 100 个引用槽，`size` 仍是 0。此时调用 `get(0)` 会抛出 `IndexOutOfBoundsException`。

数组连续保存对象引用。元素对象位于各自的堆位置。

## 3. 随机访问 {#随机访问}

读取第 `i` 个元素时，ArrayList 先检查 `0 <= i < size`，再读取内部数组对应位置：

```java
User user = users.get(i);
```

下标直接定位数组槽，因此 `get` 和 `set` 是常数时间。顺序遍历连续读取引用，有利于缓存和预取。

O(n) 描述增长趋势。连续数组复制与链表跳转的实际耗时仍有差异。性能比较还需固定数据规模和访问方式。

## 4. 尾部追加与扩容 {#尾部追加与扩容}

只要内部数组还有空位，尾部 `add` 就把引用写到 `elementData[size]`，再增加 size：

```java
users.add(user);
```

容量不足时，OpenJDK 26 会：

1. 根据最小需要容量计算新容量。
2. 首选增加旧容量的一半，并满足最小所需容量。
3. 申请新的引用数组。
4. 复制现有元素引用。
5. 把内部字段指向新数组。

增长比例属于 OpenJDK 实现细节。API 保证尾部追加具有摊销常数时间。单次扩容需要线性复制。

### 4.1 摊销复杂度 {#摊销复杂度}

连续追加时，多数操作只写入一个数组槽。少数操作需要分配数组并复制引用。几何增长让累计复制量随追加数量线性增长。因此，每次追加的摊销成本是 O(1)。

单次大数组复制仍会增加该次调用延迟。延迟敏感的路径可以提前预留容量。

## 5. 初始容量 {#初始容量}

已知大致元素数量时，可以预留容量：

```java
List<OrderLine> lines = new ArrayList<>(expectedLineCount);
```

预留容量可以减少数组分配与引用复制。旧数组等待 GC 造成的短期峰值也会减少。

预留容量应参考元素数量分布。大量小列表使用大数组，会长期保留空槽。

追加大量元素前，可以调用 `ensureCapacity`。元素减少后，`trimToSize` 可缩小数组。缩容也要复制引用，适合长期保留且已稳定的列表。

## 6. 中间插入与删除 {#中间插入与删除}

在索引位置插入元素时，后面的引用需要整体向右移动：

```java
users.add(0, user);
```

删除后，后续引用向左移动。最后一个旧位置置为 `null`，释放多余引用。对象的其他引用也消失后，GC 才能回收它。

因此：

- 尾部追加摊销 O(1)。
- 中间插入、删除最坏为 O(n)。
- 按值删除先线性查找，再搬移后续引用。

倒序删除可避免索引错位，却仍会反复搬移。OpenJDK 26 的 `removeIf` 会集中压缩保留元素。

## 7. subList 视图 {#sublist-视图}

```java
List<User> page = users.subList(from, to);
```

`subList` 与原列表共享数据。通过视图修改元素，会影响原列表。原列表在视图之外发生结构修改后，视图语义未定义。OpenJDK 的修改计数检查会尽力检测此类错误。

需要独立快照时显式复制：

```java
List<User> page = new ArrayList<>(users.subList(from, to));
```

子列表还会保留根列表，内存影响见 [子列表的内存保留](#子列表的内存保留)。

</details>

## 8. 线程安全 {#线程安全}

ArrayList 不提供并发修改保证。下面的复合操作不是原子的：

```java
if (!users.contains(user)) {
    users.add(user);
}
```

两个线程都通过检查后，会分别追加元素。共享可变列表需要统一的同步协议。`synchronizedList` 的遍历与复合操作需另加同步。具体迭代规则见 [集合迭代器](./iterator-fail-fast-immutable.mdx)。

## 9. 子列表的内存保留 {#子列表的内存保留}

OpenJDK 26 的 `SubList` 保存 `root`、`parent` 和偏移量。只保留一个小视图，也会保留根列表及其数组。根列表中的其他元素引用因此仍可达。

需要长期保存一页结果时，可复制这一页：

```java
List<String> page = new ArrayList<>(all.subList(0, 10));
```

新列表仅保存这 10 个元素引用。复制后的元素仍是原对象；可变元素需要单独管理。

## 10. 常见问题 {#常见问题}

### 10.1 默认容量与延迟分配 {#默认容量与延迟分配}

OpenJDK 26 的无参构造先使用共享空数组。首次单元素 `add` 分配容量 10。显式指定容量 0 时，首次单元素 `add` 分配容量 1。

### 10.2 Arrays.asList 的列表类型 {#arrays.aslist-的列表类型}

它是数组支持的固定大小列表。替换元素会写回原数组，改变长度会抛异常。示例见 [集合迭代器](./iterator-fail-fast-immutable.mdx#arraysaslist-的固定大小列表)。

### 10.3 Integer 列表的删除重载 {#integer-列表的删除重载}

`remove(1)` 选择的是接收 `int` 索引的重载，删除下标 1。删除值为 1 的元素应写 `remove(Integer.valueOf(1))`。重载选择发生在编译阶段。

### 10.4 ArrayList 与数组的开销 {#arraylist-与数组的开销}

ArrayList 需要管理容量，基本类型元素还需装箱。Java 数组访问本身也有边界检查。JIT 优化效果取决于具体代码。固定长度的基本类型计算适合数组。需要动态增删的序列适合 List。

**考察重点**

<details>
<summary>参考回答</summary>

ArrayList 容量不足时分配新数组并复制引用。OpenJDK 26 首选增加旧容量的一半。最小所需容量更大时，按所需容量增长。

连续追加的摊销成本是 O(1)，单次扩容为 O(n)。指定初始容量可减少分配和复制。预留过大则让空槽长期占用内存。

</details>

### 11.2 ArrayList 与 LinkedList 应该怎样选择 {#arraylist-vs-linkedlist}

<!-- 面试来源：
- 字节跳动、阿里巴巴：https://www.nowcoder.com/discuss/353147579288461312
- 美团：https://www.nowcoder.com/discuss/400870/
-->

**出现公司**：字节跳动、阿里巴巴、美团

**考察重点**

- 说明随机访问、定位和节点修改的不同成本。
- 说明引用数组的缓存局部性与链表的节点开销。
- 说明“插入多就用 LinkedList”为什么缺少前提。

**相关内容**：[随机访问](#随机访问)、[中间插入与删除](#中间插入与删除)。

<details>
<summary>参考回答</summary>

按索引读取或尾部追加时，优先考虑 ArrayList。它的随机访问为 O(1)，尾部追加摊销 O(1)。连续引用数组也减少了节点跳转。

LinkedList 按索引定位为 O(n)。已有迭代位置时，局部插入删除为 O(1)。选择链表还需衡量节点分配和实际访问模式。

</details>

### 11.3 只保留一个很小的 subList，为什么仍会占用大量内存？ {#sublist-retention}

<details>

</details>
