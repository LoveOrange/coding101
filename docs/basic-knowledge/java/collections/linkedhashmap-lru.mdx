# LinkedHashMap

`LinkedHashMap` 用双向链表记录条目顺序，同时保留 HashMap 按键查找的能力。本文以 Java 21 为准，先区分插入顺序和访问顺序，再讲解简单 LRU 缓存的实现与成本。LRU 指优先淘汰最久未访问条目的策略。

## 1. 面试核心 {#core}

- **结构分工。** LinkedHashMap 用哈希桶定位条目，用双向链表记录遍历顺序。
- **遍历顺序。** LinkedHashMap 默认保留插入顺序，设置 `accessOrder=true` 后按访问顺序排列，链首是最久未访问条目。[卡](#access-order)
- **LRU 淘汰。** 访问顺序模式中，让 `removeEldestEntry` 返回 `size() > maximumSize`，可以实现按条目数限制的 LRU 缓存。[卡](#lru-cache)
- **读取与同步。** 访问顺序模式的 `get` 命中非尾条目时会重排链表，因此多线程读取也需要同步。
- **访问顺序的触发条件。** `containsKey` 和集合视图遍历都不会刷新访问顺序。[卡](#lru-access-methods)

## 2. 哈希表与顺序链 {#哈希表与顺序链}

按键查找和按顺序遍历需要两套连接关系。LinkedHashMap 用 HashMap 的桶结构定位条目，再将所有条目接入一条双向链表，记录遍历次序：

```text
table buckets                     encounter order
0 -> [B]                           [A] ⇄ [B] ⇄ [C]
1 -> [A] -> [C]
```

图中，`A`、`C` 位于同一个哈希桶，但遍历时沿顺序链依次访问 `A`、`B`、`C`。也就是说，每个条目同时属于一个桶和一条全局顺序链。哈希分布合理时，`get`、`put` 平均为 O(1)，代价是额外保存前后引用，并在重排时维护链接。

## 3. 插入顺序 {#插入顺序}

默认构造保留键首次插入的顺序：

```java
Map<String, Integer> counts = new LinkedHashMap<>();
counts.put("A", 1);
counts.put("B", 2);
counts.put("A", 3);

System.out.println(counts.keySet()); // [A, B]
```

再次写入 `A` 只替换值，因此输出仍为 `[A, B]`。这种**插入顺序**适合以下需求：

- 稳定输出配置和聚合结果。
- 去重后保留输入顺序。
- API 需要可预测遍历顺序。

如果只需要保留插入顺序，就可以使用 LinkedHashMap，省去 TreeMap 按键排序所需的对数级比较。

## 4. 访问顺序 {#访问顺序}

缓存常需要知道哪些条目最近被使用过。构造时将 `accessOrder` 设为 `true`，`get` 等访问操作就会把命中的条目移到链尾：

```java
Map<String, String> cache = new LinkedHashMap<>(16, 0.75f, true);
cache.put("A", "value-a");
cache.put("B", "value-b");

cache.get("A");
System.out.println(cache.keySet()); // [B, A]
```

示例访问 `A` 后，顺序从 `[A, B]` 变成 `[B, A]`。因此，链首是最久未访问条目，链尾是最近访问条目。具体哪些方法会刷新访问顺序，见后文的方法表。

`get` 命中非尾条目时，会调整双向链接。这属于结构修改，已有迭代器发现修改计数变化时，会抛出 `ConcurrentModificationException`，简称 CME。跨线程访问也需要同步，即使多个线程只调用 `get`。

这种修改检测称为 fail-fast，具体机制见[集合迭代器](./iterator-fail-fast-immutable.mdx#结构修改与-fail-fast)。

## 5. removeEldestEntry 与 LRU {#用-removeeldestentry-实现-lru}

有了访问顺序，再加上容量上限，就能实现简单 LRU。`removeEldestEntry` 是容器在新增条目后调用的方法，可以通过重写它决定是否淘汰链首：

```java
public final class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maximumSize;

    public LruCache(int maximumSize) {
        super(Math.max(16, maximumSize), 0.75f, true);
        if (maximumSize < 0) {
            throw new IllegalArgumentException("maximumSize must be >= 0");
        }
        this.maximumSize = maximumSize;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maximumSize;
    }
}
```

`put` 新增条目后会调用 `removeEldestEntry`。示例在条目数超过 `maximumSize` 时返回 `true`，容器便移除链首，也就是最久未访问的条目。上限为 0 时，每次新增条目都会立即被移除；负数上限则由构造器拒绝。

### 5.1 简单 LRU 的局限 {#简单-lru-的局限}

这个实现只限制条目数，并按访问顺序淘汰。业务如果还有以下**缓存管理需求**，就需要额外机制：

- 多个线程同时读写时，需要控制并发访问。
- 条目大小差异明显时，需要按内存占用等权重限制容量。
- 数据会过时时，需要设置过期时间或刷新内容。
- 多个请求同时未命中时，需要合并加载，避免它们同时查询数据库等数据源。
- 需要监控命中率和淘汰次数，判断缓存是否有效。
- 淘汰时若执行额外回调，需要隔离回调失败的影响。

把同一个键的并发加载合并称为加载去重，用于缓解大量未命中请求同时访问数据源的缓存击穿问题。这个简单实现适合教学、小规模局部缓存和约束简单的工具。需要上述能力时，可以使用 Caffeine 等专门缓存组件，或远程缓存系统。

## 6. LRU 与其他淘汰策略 {#lru-与其他淘汰策略}

LRU 根据最近访问时间选择淘汰对象，依据是最近用过的数据更有机会再次被使用。如果一次扫描访问大量不同键，它们都会成为最近访问项，从而挤出反复使用的热点条目。因此，访问模式会直接影响 LRU 的命中率。

比较缓存策略时，还需要区分以下**淘汰与过期方式**：

- FIFO 按写入顺序淘汰最早加入的条目，访问次数和时间都不影响顺序。
- LFU 按访问频率选择，倾向保留被多次访问的条目。
- 混合策略结合近期访问窗口与频率估计，同时考虑最近使用和长期热点。
- TTL 表示条目的生存时间，到期后按过期规则处理。它可以与容量淘汰同时使用。

选择时要结合访问分布和对象大小，还要明确业务能接受数据旧到什么程度。容量淘汰控制缓存占用，TTL 则控制数据有效期，两者解决的问题不同。

## 7. 迭代与内存成本 {#迭代与内存成本}

LinkedHashMap 沿顺序链遍历，成本为 O(size)，只与实际条目数有关。HashMap 则还要扫描桶数组，所以容量预留较大且频繁完整遍历时，顺序链可以减少空桶扫描。

这个收益需要用额外内存换取：每个条目都增加两个顺序链接。访问顺序模式中，`get` 命中非尾条目时还要修改这些链接。因此，内存敏感时要按实际对象布局和数据量测量，性能评估也要包含重排成本。

## 8. 访问重排的方法范围 {#访问重排的方法范围}

读取或更新条目是否刷新 LRU 次序，取决于调用的方法。在**访问顺序模式**中，各方法的效果如下：

| 方法 | 访问重排 |
| --- | --- |
| get、getOrDefault | 命中时移到链尾 |
| put、putIfAbsent、compute 系列、merge | 调用完成后条目仍存在时，构成访问 |
| replace | 成功替换值时，构成访问 |
| containsKey、keySet/entrySet 遍历 | 保持访问顺序 |

因此，用 `containsKey` 检查缓存是否存在，只会得到存在性结果，访问顺序保持不变。遍历 `keySet` 时再调用 `get`，却会在命中非尾条目时触发重排。若需要同时读取键和值，直接遍历 `entrySet` 就能避免这次额外访问。

## 9. 常见问题 {#常见问题}

### 9.1 get 与迭代器冲突 {#get-与迭代器冲突}

访问顺序模式中，`get` 命中非尾节点会重排，修改计数也随之变化。已有迭代器检查到计数不一致时，就会抛出 CME。插入顺序模式的 `get` 保持原顺序，因此没有这种访问重排冲突。

### 9.2 淘汰钩子的触发时机 {#淘汰钩子的触发时机}

`put` 或 `putAll` 新增条目后，会调用 `removeEldestEntry` 判断是否淘汰最旧条目。这个方法由新增操作触发，时间流逝本身不会让它执行。因此，实现 TTL 还需要在读取时检查过期时间，或增加定时清理机制。

### 9.3 访问顺序与线程安全 {#访问顺序与线程安全}

多个线程共享并更新 LinkedHashMap 时，需要同步保护。访问顺序模式的 `get` 也会修改链表，所以只有读取方法也需要同步。使用同步包装时，整个遍历还需锁住包装对象，复杂并发缓存则适合使用专门实现。

### 9.4 条目容量与权重容量 {#条目容量与权重容量}

条目大小接近时，按数量设置上限简单有效。大小差异明显时，一个大值就能占用大部分内存，条目数很少也会耗尽空间。这时应按权重估算容量，并监控实际堆占用。

## 10. 面试题 {#面试题}

### 10.1 怎样使用 HashMap 和双向链表实现 LRU {#lru-cache}



**考察重点**

- 解释如何用 HashMap 平均 O(1) 定位节点，再用双向链表 O(1) 调整顺序。
- 说明读取、写入和淘汰如何维护头尾节点，并处理容量为零的情况。
- 说明 LinkedHashMap 的访问顺序模式提供了哪些能力，还需补充哪些缓存机制。

**相关内容**：[哈希表与顺序链](#哈希表与顺序链)至[用 removeEldestEntry 实现 LRU](#用-removeeldestentry-实现-lru)。

<details>
<summary>参考回答</summary>

**用 HashMap 按键定位节点，再用双向链表维护访问顺序，就能实现平均 O(1) 的 LRU 操作。**

链首表示最久未访问，链尾表示最近访问，各操作按以下**访问与淘汰规则**维护节点：

- `get` 命中后，把节点移到链尾。
- `put` 更新已有节点时，也将它移到链尾。
- 新增节点放在链尾，超过上限就移除链首，并删除 HashMap 中对应的映射。

移动和删除时都要维护头尾边界，容量为 0 时则每次新增都会被淘汰。LinkedHashMap 的 `accessOrder=true` 已提供这种组合，再重写 `removeEldestEntry` 即可限制条目数。并发控制、TTL 和按权重淘汰仍需额外机制。

</details>

### 10.2 LinkedHashMap 的插入顺序与访问顺序有什么区别 {#access-order}



**考察重点**

- 说明更新已有键是否改变插入顺序。
- 说明哪些访问会在 accessOrder 模式中重排。
- 说明读取修改结构对迭代和并发有什么影响。

**相关内容**：[插入顺序](#插入顺序)、[访问顺序](#访问顺序)。

<details>
<summary>参考回答</summary>

**插入顺序按键首次插入的位置排列，访问顺序则把最近访问的条目移到链尾。**

默认模式使用插入顺序，更新已有键的值时保留原位置。设置 `accessOrder=true` 后，`get` 等操作命中条目就会刷新其访问位置，因此链首可用于 LRU 淘汰。

访问重排会修改结构，已有迭代器会检测到冲突，多线程读取也需要同步。`containsKey` 和集合视图遍历则保持原顺序。

</details>

### 10.3 containsKey 或遍历 entrySet 会刷新 LRU 访问顺序吗？ {#lru-access-methods}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：区分会刷新访问顺序的方法，并解释遍历时调用 `get` 为什么会造成修改冲突。

**相关内容**：[访问重排的方法范围](#访问重排的方法范围)。

<details>
<summary>参考回答</summary>

**`containsKey` 和 `entrySet` 遍历都保持原访问顺序，因此不会刷新 LRU 次序。**

`get` 属于访问操作，命中非尾条目时会把它移到链尾。遍历期间直接读取 entry 的值，就能避免因额外调用 `get` 触发重排。

</details>
