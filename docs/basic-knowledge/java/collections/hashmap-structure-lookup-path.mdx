# HashMap

<ReviewReading plan={javaCollectionsReview} stepId="collections-hashmap" />

HashMap 先用哈希值找到键值对所在的位置，再确认键是否相等。它平均 O(1) 的读写成本、对 `equals` 和 `hashCode` 的要求、树化和扩容的时机，都来自这条查找路径。只要能顺着一次 `get` 和 `put` 讲清楚每一步在做什么，冲突、树化、容量这些追问都能推出来。下文的阈值和容量计算以 OpenJDK 21 为准。

## 1. 面试核心 {#core}

- HashMap **先用哈希定位桶，再用键引用或 `equals` 确认匹配**；`get` 和 `put` 走的是同一条路径。[卡](#put-get-path)
- 哈希分布合理时，每个桶只有少量节点，所以 `get` 与 `put` 的**平均成本是 O(1)**。
- OpenJDK 21 中，普通 `put` **向链表追加第 9 项时请求树化**。[卡](#treeify)
- 树化还要求**桶数组容量至少为 64**，小表先扩容，让冲突的节点有机会分散开。[卡](#treeify)
- 容量翻倍后，每个节点**要么留在原索引，要么移到原索引加旧容量的位置**。[卡](#power-of-two-capacity)

## 2. 结构与查找路径 {#结构与查找路径}

HashMap 的做法是先把候选键缩小到一个桶里，再在桶内逐个确认。**桶**是底层数组中的一个位置，哈希值决定键落进哪个桶。空桶里没有节点；不同的键落进同一个桶，叫作**哈希冲突**，冲突的节点用链表或红黑树串起来。

`get(key)` 的**查找路径**分四步：

1. 计算哈希。非空键先调用 `hashCode()`，再把高 16 位异或到低 16 位上，这一步叫扰动。桶下标只取哈希的低位，扰动让高位也能影响落点。null 键的哈希固定为 0。
2. 用当前容量算出桶下标。
3. 在桶内先比较节点保存的哈希，相同再比较键引用，引用不同才调用 `equals`。
4. 找到相等的键就返回值，找不到返回 `null`。

`put(key, value)` 沿同一条路径查找。找到相等的键就替换旧值；找不到就插入新节点，然后判断要不要树化或扩容。

```java
Map<Long, User> users = new HashMap<>();
users.put(7L, new User("Lin"));
User user = users.get(7L);
```

`get(7L)` 算出的哈希和 `put` 时相同，所以会进入同一个桶，再通过 `equals` 认出这个键，拿到之前保存的 `User`。哈希分布合理时，每个桶只需要检查很少的节点，`get` 与 `put` 的平均成本就是 O(1)。冲突严重时，大量键挤在同一个桶里，桶内查找就会变慢。

这个 O(1) 是把 `hashCode` 和 `equals` 当作常数成本算的。如果键的哈希计算或相等比较本身很贵，比如很长的字符串或复杂对象，这部分耗时也要算进去。

## 3. `equals` 与 `hashCode` {#equals-与-hashcode}

HashMap 靠 `hashCode` 找桶、靠 `equals` 认键，两者必须配合：**相等的键必须产生相同的哈希**，而哈希相同的键不一定相等。所以自定义键要同时正确实现这两个方法，参与比较的字段在键放进 Map 之后也不能再改。

```java
record UserId(long value) {}

Map<UserId, String> names = new HashMap<>();
names.put(new UserId(7), "Lin");
System.out.println(names.get(new UserId(7))); // Lin
```

两个 `UserId(7)` 是不同的对象，但 record 会根据字段自动生成 `equals` 和 `hashCode`，所以它们被识别为同一个键。如果只重写了 `equals` 而没重写 `hashCode`，两个对象的哈希大概率不同，`get` 会去另一个桶里找，返回 `null`。

键放进 Map 之后，如果修改了参与哈希的字段，再算出的哈希就变了。查找要么进入另一个桶，要么在原桶里因为哈希和节点保存的值对不上而直接跳过。结果是即使传入同一个对象引用，也找不到它。

HashMap 允许一个 null 键和多个 null 值，所以 `get` 返回 `null` 有两种可能：键不存在，或者键存在但值是 `null`。单线程下可以用 `containsKey` 区分，也可以在业务上约定只保存非空值。

## 4. 冲突与树化 {#冲突与树化}

**树化**是把桶里的链表换成红黑树，用来降低严重冲突时的查找成本。红黑树是一种自平衡的二叉搜索树，插入和删除后能把树高控制在 O(log n)。节点少的时候链表更简单、更省空间；节点持续变多时，才值得为每个节点多存颜色、父子指针这些字段，换来更快的查找。

OpenJDK 21 的**树化与退化条件**要按操作区分：

- `TREEIFY_THRESHOLD` 为 8。普通 `put` 向已经有 8 项的链表追加第 9 项时，请求树化。
- 桶数组容量达到 64 才真正树化。容量更小时先扩容：扩容让更多哈希位参与定位，原本挤在一起的长链有机会分到不同的桶。
- `computeIfAbsent`、`compute` 和 `merge` 数的是桶里已有的节点：已有 7 个、再加入第 8 个时就请求树化，比普通 `put` 早一项。
- 扩容拆分树桶时，拆出的某一侧节点数不超过 6，就转回链表。
- 普通 `remove` 删除树节点后，会看根节点附近的形状，树小到一定程度就转回链表，源码注释说大约在 2 到 6 个节点之间。通过迭代器删除时不做这项检查，树桶会一直保留到下次扩容拆分。

这些数字是 OpenJDK 21 的实现细节，`Map` 接口并没有要求所有实现使用相同的阈值。

树化后查找不一定就是 O(log n)，前提是能判断要找的键在树的哪一侧。`Comparable` 是对象声明自身比较顺序的接口。哈希相同、键又没有可用的 `Comparable` 顺序时，查找只能把两侧子树都搜一遍，最坏情况仍要线性检查候选键。

## 5. 容量与扩容 {#容量与扩容}

容量决定桶的数量，进而影响冲突概率和扩容频率。讨论扩容前，先分清**四个概念**：

- `size` 是当前保存的键值对数量。
- `capacity` 是桶数组的长度。
- `loadFactor` 是负载因子，默认 0.75，用来在空间占用和冲突概率之间取舍。
- `threshold` 是触发扩容的条目数上限，通常是 `capacity × loadFactor` 取整数部分。`size` 超过它就扩容。

HashMap 的容量总是 2 的幂，这样 `capacity - 1` 的二进制低位全是 1。拿它做位掩码（用来选出特定几位的数），一次按位与就能得到桶下标：

```java
index = (capacity - 1) & hash;
```

比如容量 16 时，`capacity - 1` 是二进制 `1111`，下标就是哈希的低 4 位。容量翻倍到 32，掩码变成 `11111`，多了一位参与定位。所以旧桶里的节点只有两个去向，看的就是新增的那一位：

```text
(hash & oldCapacity) == 0  -> 原索引
(hash & oldCapacity) != 0  -> 原索引 + oldCapacity
```

迁移时直接使用节点里保存的哈希，不用重新调用每个键的 `hashCode()`。但它仍然要分配新数组、扫描所有旧桶、调整节点链接，成本随旧容量和节点数增长；负载因子固定、表已经接近满的时候，可以记为 O(n)。

大 Map 扩容时新旧数组会短暂同时存在，内存占用上升，触发扩容的那次 `put` 也会明显变慢。已知条目数时，提前算好初始容量可以避免反复扩容；但容量预留过大会浪费内存，遍历时也要多扫描空桶。

## 6. 使用边界 {#使用边界}

选 HashMap 时还要看两件事：需不需要固定的遍历顺序，会不会被多个线程同时修改。

HashMap 的遍历要扫描整个桶数组，成本与容量加 `size` 成正比，而且遍历顺序没有保证。需要保留插入顺序可以用 [LinkedHashMap](./linkedhashmap-lru.mdx)，需要按键排序则用 [TreeMap 与 TreeSet](./treemap-treeset-ordered-query.mdx)。

多个线程不加同步地修改 HashMap，可能丢失更新，也可能读到修改到一半的结构，所以共享的可变 HashMap 需要外部同步。换成并发 Map 也不能先 `containsKey` 再 `put`，两步之间仍有竞态，应该按需求用 `putIfAbsent` 或 `compute` 这类原子方法。

复合操作的实现与边界见 [ConcurrentHashMap](./concurrenthashmap-atomic-compound-operations.mdx)。

## 7. 预期条目数与初始容量 {#预期条目数与初始容量}

预估初始容量时，要把「打算放多少条」换算成「需要多少个桶」。`new HashMap<>(100)` 里的 100 是桶容量的提示，不是能容纳的条目数。OpenJDK 21 首次分配时会把它向上取整到 2 的幂 128，再乘默认负载因子 0.75，得到阈值 96。所以插入第 97 个不同的键时就会扩容。

Java 21 可以直接用 `HashMap.newHashMap(expectedMappings)`，它按预期条目数和默认负载因子算出合适的容量。Java 17 没有这个方法，可以自己把条目数除以 0.75 再向上取整，传给构造器，构造器会再按 2 的幂调整。

## 8. 常见问题 {#常见问题}

### 8.1 hash 与 equals 的比较顺序 {#hash-与-equals-的比较顺序}

先比哈希，因为比较两个整数很便宜，哈希不同的键可以直接排除，省掉一次 `equals`。哈希相同可能只是冲突，所以还要比较键引用，引用不同再调用 `equals` 确认。

### 8.2 遍历顺序的约定 {#遍历顺序的约定}

HashMap 不保证遍历顺序。同样的键在同样的环境下，结果有时看起来很稳定，但扩容、键的哈希变化或 JDK 实现调整都会改变顺序。业务需要固定顺序时，应该换用有顺序约定的 Map。

### 8.3 链表长度与树化条件 {#链表长度与树化条件}

OpenJDK 21 的普通 `put` 向链表追加第 9 项时请求树化，但不一定真的树化：桶数组容量小于 64 时先扩容，达到 64 才把链表转成树桶。

## 9. 面试题 {#面试题}

<ReviewQuestionAnchor />

### 9.1 说明 HashMap 的 put 和 get 路径 {#put-get-path}

**考察重点**

- 说明桶定位、哈希比较和 `equals` 比较的顺序。
- 说明覆盖旧值、插入新值和触发结构变化的边界。

**相关内容**：[结构与查找路径](#结构与查找路径)、[`equals` 与 `hashCode`](#equals-与-hashcode)。

<details>
<summary>参考回答</summary>

**`get` 与 `put` 都先用扰动后的哈希定位桶，再在桶内确认键是否匹配。**

桶内的节点用链表或红黑树组织。查找时先比较节点保存的哈希，再比较键引用或调用 `equals`。`get` 找到就返回值，找不到返回 `null`。

`put` 沿同一条路径查找，命中已有的键就覆盖旧值，没有命中就插入新节点。插入后 `size` 超过阈值会扩容；如果桶内形成了长链，还会根据当前表容量决定是树化还是先扩容。平均 O(1) 的前提是哈希分布均匀、容量合理。

</details>

### 9.2 HashMap 什么时候树化，为什么小容量时先扩容 {#treeify}

**考察重点**

- 说明树化阈值与最小表容量的协作。
- 说明扩容分散普通碰撞与树处理持续碰撞的区别。

**相关内容**：[冲突与树化](#冲突与树化)。

<details>
<summary>参考回答</summary>

**OpenJDK 21 的普通 `put` 向链表追加第 9 项时请求树化，但桶数组容量不到 64 时会先扩容。**

相关的两个常量是 `TREEIFY_THRESHOLD = 8` 和最小树化容量 64。

小表出现长链，原因可能只是桶太少。扩容让更多哈希位参与定位，节点就有机会分散开，不需要付出树节点的额外空间和维护成本。容量已经足够、冲突仍然集中在一个桶时，才说明这些键真的难以分散，这时再树化。扩容拆分树桶后，某一侧不超过 6 项会退回链表。这些阈值都属于实现细节。

</details>

### 9.3 HashMap 为什么使用 2 的幂作为容量 {#power-of-two-capacity}

**考察重点**

- 说明位掩码怎样定位桶。
- 说明容量翻倍后节点为什么只有两个候选位置。

**相关内容**：[容量与扩容](#容量与扩容)。

<details>
<summary>参考回答</summary>

**容量取 2 的幂，就能用 `hash & (capacity - 1)` 代替取模来定位桶，扩容拆分也更简单。**

`capacity - 1` 的低位全是 1，按位与正好取出哈希的低几位作为下标。容量翻倍只多出一个定位位：这一位为 0 的节点留在原索引，为 1 的移到原索引加旧容量的位置，不需要逐个重新计算。

</details>

### 9.4 预存 100 个键时，`new HashMap<>(100)` 能避免扩容吗？ {#hashmap-expected-size}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释初始容量如何取整，以及负载因子怎样决定扩容前能容纳的条目数。

**相关内容**：[预期条目数与初始容量](#预期条目数与初始容量)。

<details>
<summary>参考回答</summary>

**不能。OpenJDK 21 首次分配 128 个桶，默认阈值只有 96，插入第 97 个不同的键时就会扩容。**

构造器参数是桶容量的提示，不是条目数。要放下 100 个键，Java 21 可以用 `HashMap.newHashMap(100)`，由它按条目数算容量。Java 17 可以把 100 除以 0.75 后向上取整，传入 134，实际桶数会取整为 256。

</details>
