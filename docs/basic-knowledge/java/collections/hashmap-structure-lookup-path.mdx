# HashMap

<ReviewReading plan={javaCollectionsReview} stepId="collections-hashmap" />

HashMap 用桶数组组织键值对。哈希定位桶，equals 确认键相等。本文负责 OpenJDK 21 的查找、冲突处理和扩容。

并发更新见 [ConcurrentHashMap](./concurrenthashmap-atomic-compound-operations.mdx)。遇到顺序见 [LinkedHashMap](./linkedhashmap-lru.mdx)。

## 1. 面试核心 {#core}

- HashMap 用哈希定位桶，再用键引用或 equals 确认匹配。[卡](#put-get-path)
- 哈希分布合理时，get 与 put 的平均成本为 O(1)。
- OpenJDK 21 的 put 在链表第 9 项插入时请求树化。[卡](#treeify)
- 树化要求表容量至少 64，小表先扩容。[卡](#treeify)
- 容量翻倍后，节点留在原索引或移到原索引加旧容量。[卡](#power-of-two-capacity)

## 2. 结构与查找路径 {#结构与查找路径}

HashMap 的核心结构是一组桶。冲突元素存入同一个桶，以链表或红黑树组织。

`get(key)` 的主要步骤是：

1. 非空键的 `hashCode()` 经扰动后参与桶定位。null 键使用哈希值 0。
2. 使用当前容量计算桶下标。
3. 先比较保存的哈希，再比较键引用或调用 `equals`。
4. 在链表或树中找到相等键后返回值；找不到则返回 `null`。

`put(key, value)` 沿相同路径查找。相等键会替换旧值；没有相等键时插入新节点，随后判断是否需要树化或扩容。

```java
Map<Long, User> users = new HashMap<>();
users.put(7L, new User("Lin"));
User user = users.get(7L);
```

平均 O(1) 要求哈希分布合理。这个分析还把 hashCode 与 equals 视为常数成本。复杂键的计算和比较需另行计入。

## 3. `equals` 与 `hashCode` {#equals-与-hashcode}

相等键必须产生相同哈希。相同哈希仍可对应不同键。自定义键需同时实现 equals 与 hashCode。参与比较的字段在入表后应保持稳定。

```java
record UserId(long value) {}

Map<UserId, String> names = new HashMap<>();
names.put(new UserId(7), "Lin");
System.out.println(names.get(new UserId(7))); // Lin
```

修改键的哈希字段，会改变后续查找路径。即使对象引用相同，也会因保存的哈希不匹配而查找失败。

HashMap 允许一个 null 键和多个 null 值。get 返回 null 可表示缺失，也可表示值为空。单线程下可用 containsKey 区分。

## 4. 冲突与树化 {#冲突与树化}

不同键进入同一桶时，链表逐项检查候选键。树桶增加颜色、父子链接等字段，以换取树形查找。

OpenJDK 21 的 `TREEIFY_THRESHOLD` 为 8。普通 put 向已有 8 项的链表追加第 9 项时，请求树化。表容量达到 64 才执行树化，小表先扩容。compute 系列的计数路径不同，应按调用路径分析。

扩容拆分树桶时，某侧节点数不超过 6 会转回链表。普通 remove 则根据树形判断，迭代删除还有额外条件。退化时机应区分扩容与删除。

树高为 O(log n)，但任意键查找仍有边界。哈希相同且缺少可用的 Comparable 顺序时，查找会搜索子树。此时最坏仍需线性检查候选键。

## 5. 容量与扩容 {#容量与扩容}

需要区分四个概念：

- `size`：键值对数量。
- `capacity`：桶数组长度。
- `loadFactor`：控制空间与冲突概率的比例，默认是 0.75。
- `threshold` 是扩容边界，已分配表中按容量和负载因子计算。

容量是 2 的幂时，可以用位掩码定位桶：

```java
index = (capacity - 1) & hash;
```

容量翻倍新增一个定位位，旧桶节点只有两个去向：

```text
(hash & oldCapacity) == 0  -> 原索引
(hash & oldCapacity) != 0  -> 原索引 + oldCapacity
```

迁移复用保存的哈希，并分配新表和调整链接。成本随旧容量与节点数量增长。负载因子固定且表较满时，可记为 O(n)。过大容量还会增加空桶扫描与内存成本。

## 6. 使用边界 {#使用边界}

HashMap 的迭代成本与容量加 size 成正比。需要顺序时，使用 [LinkedHashMap](./linkedhashmap-lru.mdx) 或 [TreeMap 与 TreeSet](./treemap-treeset-ordered-query.mdx)。

并发修改需要外部同步，或使用 [ConcurrentHashMap](./concurrenthashmap-atomic-compound-operations.mdx)。

## 7. 预期条目数与初始容量 {#预期条目数与初始容量}

`new HashMap<>(100)` 表达桶容量提示，未表达 100 条映射。OpenJDK 21 首次分配 128 个桶，默认阈值为 96。插入第 97 个不同键时，就会触发容量扩展。

Java 21 可用 `HashMap.newHashMap(expectedMappings)`。它根据预期条目数与默认负载因子估算容量。Java 17 可按条目数除以 0.75 预估，再考虑容量取整。

## 8. 常见问题 {#常见问题}

### 8.1 hash 与 equals 的比较顺序 {#hash-与-equals-的比较顺序}

哈希不同可直接排除。哈希相同再用键引用或 equals 确认，减少相等比较。

### 8.2 遍历顺序的约定 {#遍历顺序的约定}

HashMap 的遍历顺序未指定。扩容、键哈希和实现变化都会影响次序。

### 8.3 链表长度与树化条件 {#链表长度与树化条件}

OpenJDK 21 的普通 put 在追加第 9 项时请求树化。表容量小于 64 时，改为扩容。

<details>
<summary>参考回答</summary>

2 的幂容量可用 `hash & (capacity - 1)` 定位桶。翻倍时只新增一个定位位。该位为 0 的节点留在原索引，为 1 的移到原索引加旧容量。

</details>
