# HashMap

HashMap 使用桶数组保存键值对，通过键的哈希定位桶，再用 `equals` 确认键是否相等。面试重点是 `put`/`get` 路径、冲突处理、扩容和线程安全边界。

:::tip 面试核心

- 哈希先定位桶，哈希相同仍要用 `equals` 判断键是否相等。
- 哈希分布合理时，`get` 和 `put` 平均接近 O(1)；严重冲突会增加桶内查找成本。
- 当前 OpenJDK 使用短链表处理普通冲突，表足够大且桶持续过长时才树化。
- 容量通常是 2 的幂，扩容翻倍后节点只会留在原索引或移动到“原索引 + 旧容量”。
- HashMap 不保证遍历顺序，也不支持无同步的并发写。

:::

## 1. 结构与查找路径

HashMap 的核心结构是一组桶。桶为空时没有节点；发生冲突时，桶内可能是链表或红黑树。

`get(key)` 的主要步骤是：

1. 取得 `key.hashCode()` 并做扰动，让高位也参与桶定位。
2. 使用当前容量计算桶下标。
3. 先比较保存的哈希，再比较键引用或调用 `equals`。
4. 在链表或树中找到相等键后返回值；找不到则返回 `null`。

`put(key, value)` 沿相同路径查找。相等键会替换旧值；没有相等键时插入新节点，随后判断是否需要树化或扩容。

```java
Map<Long, User> users = new HashMap<>();
users.put(7L, new User("Lin"));
User user = users.get(7L);
```

平均 O(1) 依赖两个条件：哈希分布合理，且 `hashCode`、`equals` 本身足够便宜。复杂的相等比较仍会成为真实成本。

## 2. `equals` 与 `hashCode`

相等键必须产生相同哈希；相同哈希的键不一定相等。自定义键应同时正确实现 `equals` 和 `hashCode`，并且参与比较的字段在键存入 Map 后保持稳定。

```java
record UserId(long value) {}

Map<UserId, String> names = new HashMap<>();
names.put(new UserId(7), "Lin");
System.out.println(names.get(new UserId(7))); // Lin
```

如果键在存入后改变了参与哈希的字段，后续查找会从另一个桶开始，逻辑上相同的对象也可能找不到原条目。

HashMap 允许一个 `null` 键和多个 `null` 值。`get` 返回 `null` 时无法区分“键不存在”和“值就是 null”，需要时使用 `containsKey` 或避免保存 null 值。

## 3. 冲突与树化 {#hashmap-treeification}

不同键进入同一桶是正常现象。短链表结构简单，节点少时通常比红黑树更合适；只有冲突持续严重时，树的对数查找才值得额外字段和维护成本。

当前 OpenJDK 的关键边界是：

- 桶内节点达到树化阈值 8。
- table 容量至少为 64；容量较小时优先扩容，让更多哈希位参与定位。
- 树桶拆分后节点较少时，可以退化回链表，相关阈值为 6。

这些数字是当前实现细节，不是 Map 接口契约。面试回答应先说明取舍：短桶保持简单，小表先扩容，足够大的表仍有长桶时再用树限制退化。

## 4. 容量与扩容 {#hashmap-resize}

需要区分四个概念：

- `size`：键值对数量。
- `capacity`：桶数组长度。
- `loadFactor`：控制空间与冲突概率的比例，默认是 0.75。
- `threshold`：触发扩容的元素数量边界，通常约为 `capacity × loadFactor`。

容量是 2 的幂时，可以用位掩码定位桶：

```java
index = (capacity - 1) & hash;
```

容量翻倍只增加一个参与定位的哈希位，所以旧桶中的节点只有两个去向：

```text
(hash & oldCapacity) == 0  -> 原索引
(hash & oldCapacity) != 0  -> 原索引 + oldCapacity
```

实现不必重新调用每个键的 `hashCode()`，但仍要分配新数组并迁移节点链接，因此扩容整体是 O(n)，大 Map 还会产生短时内存和延迟压力。已知元素数量时可以预估初始容量，避免明显的重复扩容；盲目预留过大数组会浪费内存并增加遍历空桶的成本。

## 5. 使用边界

- **遍历顺序**：HashMap 没有顺序保证。需要插入顺序使用 LinkedHashMap，需要按键排序使用 TreeMap。
- **并发访问**：并发写可能丢失更新或观察到不一致状态。共享可变 Map 应使用 ConcurrentHashMap 的原子方法，或在更高层建立锁。
- **复合操作**：即使换成并发 Map，`containsKey` 后再 `put` 仍不是一个原子动作，应使用 `putIfAbsent`、`compute` 等复合方法。

## 6. 常见问题

### 6.1 为什么先比较 hash 再比较 equals

哈希不同可以直接排除，哈希相同仍可能只是冲突，需要 `equals` 确认。这个顺序减少了需要执行相等比较的候选数量。

### 6.2 HashMap 的顺序有时看起来固定，可以依赖吗

不可以。同一组键和同一运行环境下结果可能暂时稳定，但扩容、键哈希或实现版本变化都可能改变顺序。

### 6.3 链表达到 8 个节点就一定树化吗

不一定。table 容量小于 64 时当前实现优先扩容；只有扩容后冲突仍集中并满足条件才树化。

**考察重点**

<details>
<summary>参考回答</summary>

HashMap 先取得键的哈希并做扰动，再按容量定位桶。`get` 在桶内先比较保存的哈希，再通过键引用或 `equals` 确认相等；桶可能使用链表或红黑树。

`put` 沿同一路径查找，相等键会替换值；不存在时新增节点。桶持续过长时可能树化，新增映射使 size 越过阈值后会扩容。平均 O(1) 的前提是哈希分布和容量合理。

</details>

<details>
<summary>参考回答</summary>

当前 OpenJDK 在桶链达到树化阈值，并且 table 容量至少为 64 时才考虑转为红黑树。容量较小时先扩容，因为长链可能只是桶太少，扩容能让新的哈希位参与定位并分散节点。

具体数字属于实现细节。核心取舍是少量冲突使用简单链表，小表优先扩容，足够大的表仍有严重冲突时再使用树。

</details>

### 7.3 HashMap 为什么使用 2 的幂作为容量

**出现公司**：一嗨租车、上海卫瓴信息科技

**考察重点**

- 位掩码怎样定位桶。
- 容量翻倍后节点为什么只有两个候选位置。

**相关内容**：第 4 节“容量与扩容”。

<details>
<summary>参考回答</summary>

容量是 2 的幂时，`capacity - 1` 的低位全是 1，可以通过按位与取得桶下标。容量翻倍只新增一个参与定位的哈希位，因此旧桶节点要么留在原索引，要么移动到原索引加旧容量，扩容拆分更直接。

</details>
