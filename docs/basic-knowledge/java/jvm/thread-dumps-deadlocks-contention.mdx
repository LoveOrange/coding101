# 线程转储

**线程转储**（thread dump）是线程调用栈、状态和部分锁关系的记录，用来判断线程正在执行什么、在等什么。服务卡住或请求超时时，可以从这些信息中查找死锁、锁竞争和线程池饥饿的线索。具体能看到哪些线程和锁，取决于采集命令。

单份转储只反映采集时的状态，不能说明线程已经等了多久、用了多少 CPU。要判断等待是否持续，需要对比多份转储；要量化等待时间，可以结合 JVM 自带的运行事件记录工具 Java Flight Recorder（JFR）。

## 1. 面试核心 {#core}

- 线程转储记录的是**采集时刻**的调用栈和状态，间隔几秒**采集多份**，才能判断等待是否持续。
- `BLOCKED` 表示**等待进入 `synchronized` 的监视器**；`ReentrantLock` 通过 `park` 等待时，状态可能是 **`WAITING`**。
- 锁引起的死锁是线程**互相持有对方等待的锁**，按锁标识把持有者和等待者连起来，能看到**循环等待**。[卡](#dump-deadlock)
- 空闲工作线程等任务时也是 `WAITING`；父任务占满线程池后**同步等待同一个池里的子任务**，会造成线程池饥饿。[卡](#waiting-threads)
- `Thread.dump_to_file` **可以包含虚拟线程**，但**不做自动死锁检测**。[卡](#virtual-thread-dump)

## 2. 采集线程转储 {#采集线程转储}

服务卡住时，先把线程当时在做什么保存下来，再和业务指标对照。平台线程可以这样采集：

```bash
jcmd <pid> Thread.print -l > thread-01.txt
```

只采一份不够。第一份之后，间隔几秒再采 2—4 份，同时记下这段时间的线程池和请求指标：

- 线程池的线程总数，以及 active，也就是正在执行任务的工作线程数。
- queue，也就是排队等待执行的任务数。
- 同一时间段的 CPU 使用率和请求延迟。

`-l` 会额外输出 ownable synchronizer 信息。**ownable synchronizer** 是有独占持有者的同步器，比如 `ReentrantLock` 内部用的同步器。这些信息能帮助我们找到锁的持有者。采集的开销随线程数量增加，线程很多时要留意对应用的影响。

`Thread.print` 在 Java 21 中主要用来观察平台线程，虚拟线程要用 `Thread.dump_to_file`（见第 8 节）。不同命令覆盖的线程和锁信息不一样，保存结果时注明用的是哪个命令。具体选项可以用 `jcmd <pid> help Thread.dump_to_file` 查看。

## 3. 线程状态与栈 {#线程状态与栈}

线程状态告诉你 JVM 认为线程处于哪一类活动，调用栈告诉你它具体停在哪段代码。只看其中一个容易误判。

| 状态 | 含义与例子 |
| --- | --- |
| `RUNNABLE` | 执行或可运行，也可处于部分 native I/O |
| `BLOCKED` | 等待进入或重新进入 synchronized monitor |
| `WAITING` | 无期限 wait、join 或 park |
| `TIMED_WAITING` | 带期限 wait、sleep 或 park |
| `NEW` / `TERMINATED` | 尚未启动 / 已结束 |

表里的 **monitor** 是 `synchronized` 使用的监视器，同一时刻只有持有它的线程才能进入受它保护的临界区。`park` 用来挂起线程，`ReentrantLock` 等并发工具靠它实现等待。拿到许可、中断或虚假唤醒都可能使 `park` 返回，所以返回后仍需检查等待条件。

同样是 `WAITING`，意义可能完全不同。空闲工作线程在任务队列上 park，是正常等待。但如果队列和请求等待一直在增长，就要从栈里确认线程在等什么：锁、数据库连接，还是某个 Future，以及该由谁来唤醒它。对 `TIMED_WAITING`，还要检查超时时间和任务期限是否匹配。

`ReentrantLock` 通过 `park` 等待时，线程可能显示为 `WAITING`；带超时的等待也可能是 `TIMED_WAITING`。所以排查锁竞争时，只数 `BLOCKED` 线程会漏掉这类等待，要同时看调用栈和锁对象。`NEW` 和 `TERMINATED` 的线程没有在处理请求，可以先放一边。

## 4. 死锁 {#死锁}

锁引起的**死锁**是多个线程互相等待对方持有的锁，谁都无法继续。比如一个线程按 L1、L2 的顺序进入嵌套 `synchronized`，另一个按 L2、L1 的顺序进入，就可能出现：

```text
线程 A 持有锁 L1，等待锁 L2
线程 B 持有锁 L2，等待锁 L1
```

在转储里找死锁，就是按锁标识把等待者和持有者连起来，看是否成环。monitor 相关的栈里，`locked` 表示已经持有的锁，`waiting to lock` 表示正在等的锁。

`ReentrantLock` 使用的 AQS 是 Java 并发工具管理同步状态和等待队列的基础框架。这类锁要把 `park` 等待栈与 ownable synchronizer 的持有信息对应起来，才能找到谁在等谁。

`jstack -l <pid>` 或 `jcmd <pid> Thread.print -l` 能自动发现部分 monitor 和同步器死锁，报告里会出现 `Found one Java-level deadlock` 并列出相关线程。但等待 `Future`、等待外部资源形成的环，JVM 识别不了，要结合业务上的依赖关系自己判断。

修复的关键是改变造成循环等待的拿锁方式：

- 统一各条代码路径的获取顺序，所有线程都按同一顺序拿锁。
- 减少嵌套持锁，或者把需要一起保护的临界区合并，让所有权关系更简单。
- 用 `tryLock(timeout, unit)` 给拿锁设一个失败出口，失败时释放已经持有的锁，再有限次重试。

重启能暂时恢复服务，但造成循环等待的代码不改，问题还会再出现。

## 5. 锁竞争 {#锁竞争}

**锁竞争**是多个线程争用同一把锁。和死锁不同，持有者最终能完成工作并释放锁，队列会向前推进，只是等待者要排队，吞吐下降、请求长尾变长。下面的代码把远程调用放在了锁里：

```java
synchronized void record(Metric metric) {
    remoteClient.send(metric);
}
```

`record` 持有 monitor 时调用 `remoteClient.send`。远程服务响应慢，持有者就迟迟不释放锁，其他调用 `record` 的线程都在 monitor 上排队。

在转储里，它的样子是：多份转储都显示同一个持有者停在远程调用里，后面跟着大量 `BLOCKED` 等待者。要量化等了多久，可以用 JFR：`jdk.JavaMonitorEnter` 记录 monitor 竞争，`jdk.ThreadPark` 记录 park 等待，启用这些事件后能看到等待时长和等待对象。async-profiler 的 lock 模式也能从采样角度展示锁竞争。

优化要围绕共享状态和持锁时间展开：

- 把 I/O 等慢操作移出锁，缩短临界区。
- 把彼此独立的状态拆开，各用各的锁，减少无关请求互相等待。
- 用不可变快照、并发集合或消息传递改变共享方式，同时验证数据一致性。
- 按热点 key 分片时，检查请求是否还是集中在少数分片上，否则竞争只是换了个地方。

## 6. 线程池饥饿 {#线程池饥饿}

**线程池饥饿**是工作线程被长期占用，导致排队的任务拿不到线程执行。父任务等待同池的子任务就是一种情况：它不需要形成 monitor 锁环，也能让任务停止推进。看下面这段在池内父任务中执行的代码：

```java
Future<Result> child = executor.submit(task);
return child.get();
```

假设线程池大小固定，所有工作线程都在执行这样的父任务。每个父任务把子任务提交到同一个池，再调用 `get()` 同步等结果。子任务只能在队列里排着，因为所有工作线程都被等待中的父任务占着，没有线程来执行它们，父任务也就永远等不到结果。

排查时要把线程总数、active、queue 和任务的提交关系放在一起看。active 等于池容量、queue 持续积压，而且工作线程的栈都停在子任务的 `Future.get()` 上，就是这种情况。

修复的思路是不在池内同步等待：改成子任务完成后再触发后续操作，也就是非阻塞编排。也可以让子任务使用单独的执行器，但仍要控制队列大小和下游容量，否则等待只是转移到了数据库等资源上。

## 7. 活锁与饥饿 {#活锁与饥饿}

线程一直在动，任务却完不成，可能是活锁，也可能是饥饿。**活锁**是线程不断改变状态或重试，却始终完成不了工作，密集重试时 CPU 使用率还会升高。**饥饿**是特定任务长期拿不到锁、许可或调度机会，而其他任务照常有进展。

单份 `RUNNABLE` 的栈分不清线程是在正常计算还是在反复重试。要结合任务完成数、重试次数、锁获取延迟和连续采样，判断线程是否一直在活动却没有完成任务，JFR 可以补充这段时间的运行事件。

CPU 排查见 [CPU 使用率](./cpu-high-diagnosis.mdx)。

## 8. 虚拟线程的线程转储 {#虚拟线程的线程转储}

Java 21 的虚拟线程让大量阻塞任务共享少量平台线程。要看这些任务的业务栈，可以导出 JSON 格式的线程转储：

```bash
jcmd <pid> Thread.dump_to_file -format=json /safe/path/threads.json
```

这条命令同时包含平台线程和虚拟线程，但有两个限制：它逐个线程采集，得到的不是同一时刻的一致快照；它也不做自动死锁检测。`ThreadMXBean.findDeadlockedThreads()` 只检测平台线程之间的锁环，涉及虚拟线程的等待环不在它的结果里。

承载虚拟线程运行的平台线程称为 **carrier**。在 Java 21 中，虚拟线程在 synchronized 块里阻塞时，会被固定在 carrier 上无法卸载，这称为 **pinning**；执行 native 方法期间也会固定。长时间固定会让能运行其他虚拟线程的 carrier 变少，进而影响吞吐。

虚拟线程便宜，但它们等的数据库连接和共享锁并不会变多。诊断时要分别看这几处资源：

- 从业务栈确认虚拟线程在等哪把锁或哪个资源池。
- 查看 carrier 的 CPU 使用率，判断承载线程是否饱和。
- 检查 pinning 持续多久，以及它是否真的影响了任务吞吐。
- 对照数据库连接池和下游服务的容量，确认请求是否积压在外部资源上。

## 9. 常见问题 {#常见问题}

### 9.1 sleep 和 wait 都会释放锁吗？ {#sleep-与-wait-的锁行为}

`sleep` 不释放已持有的锁，`Object.wait` 只释放调用对象的 monitor。线程在 `synchronized` 里调用 `sleep`，其他线程仍然无法进入同一个 monitor 保护的临界区。`Object.wait` 返回前会重新获取调用对象的 monitor；线程持有的其他锁不受这次等待影响。

### 9.2 换成 ReentrantLock 就能避免死锁吗？ {#reentrantlock-的死锁条件}

不能，换成 `ReentrantLock` 不会自动破坏死锁所需的互斥、持有并等待、不可强制剥夺和循环等待四个条件。线程拿着一把锁去等另一把锁，对方也这样做，就可能谁都无法继续。带超时的 `tryLock` 提供了失败出口，但调用方失败后还必须释放已经持有的锁，其他线程才能继续。

### 9.3 怎样区分线程池在空闲，还是任务已经卡住？ {#线程池空闲与积压}

两种情况下工作线程都可能是 `WAITING`，区别在队列和等待目标。空闲时，队列为空，工作线程在等新任务，业务指标正常。卡住时，请求等待或队列持续增长，工作线程却都在等某把锁、某个连接池或子 Future。所以要同时看队列、等待目标和任务完成情况。

## 10. 面试题 {#面试题}

### 10.1 怎样从线程转储定位 Java 死锁 {#dump-deadlock}

**考察重点**：根据锁标识连接持有者与等待者，区分 monitor 和同步器信息，并理解自动死锁检测的范围。

**相关内容**：[采集线程转储](#采集线程转储)、[死锁](#死锁)。

<details>
<summary>参考回答</summary>

**定位锁引起的死锁，需要把转储中的锁持有者和等待者连接起来，确认是否构成循环等待。**

先用 `jcmd <pid> Thread.print -l` 采集线程与锁信息，查看 JVM 的自动报告。再根据 `locked`、`waiting to lock` 和同步器持有信息核对关系。比如 A 持有 L1、等待 L2，B 持有 L2、等待 L1，就形成环。

保存多份转储确认等待持续，再映射到代码中的锁顺序。修复可以统一获取顺序、减少嵌套，或设计超时后释放锁的协议。修复后重新验证，自动检测范围之外的 Future 等依赖还需结合业务任务关系分析。

</details>

### 10.2 大量线程处于 WAITING，为什么系统仍然可能故障 {#waiting-threads}

**考察重点**：结合等待对象、active 和任务队列区分空闲与积压，解释同池父子任务为什么会互相等待。

**相关内容**：[线程状态与栈](#线程状态与栈)、[线程池饥饿](#线程池饥饿)。

<details>
<summary>参考回答</summary>

**因为 `WAITING` 既能表示空闲线程在等任务，也能表示业务线程长期等不到锁、连接或子任务结果。**

需要从栈中确认等待目标，再结合 active、queue 和请求延迟判断是否积压。比如，父任务占满固定大小线程池后，把子任务提交到同一池，再同步等待子 Future。所有工作线程都被父任务占用，排队的子任务就没有执行者，形成线程池饥饿。

这种依赖会让业务停止推进，但未必形成 JVM 能自动报告的 monitor 或同步器死锁。

</details>
