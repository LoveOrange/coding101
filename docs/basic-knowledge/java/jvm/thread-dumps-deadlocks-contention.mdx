# 线程转储

线程转储记录采集时刻的线程栈、状态和部分锁关系。本文负责锁等待、死锁、线程池饥饿与采集边界。CPU 热点定位见 [CPU 使用率](./cpu-high-diagnosis.mdx)。等待持续时间需要结合 JFR 等事件。

## 1. 面试核心 {#core}

- 线程转储记录瞬时状态，多份栈能帮助判断持续等待。
- 死锁由持有与等待关系构成环，锁编号可用于连接相关线程。[卡](#dump-deadlock)
- `BLOCKED` 表示等待 monitor，ReentrantLock 的等待可表现为 `WAITING`。
- 工作线程等待任务时也会 `WAITING`，故障判断还需任务队列和请求指标。[卡](#waiting-threads)
- `Thread.dump_to_file` 可包含虚拟线程，但不会自动检测死锁。[卡](#virtual-thread-dump)

## 2. 采集线程转储 {#采集线程转储}

```bash
jcmd <pid> Thread.print -l > thread-01.txt
```

隔几秒采集多份，并记录 CPU、请求延迟和队列长度。`-l` 增加 ownable synchronizer 信息，如 ReentrantLock。

Java 21 的 `Thread.print` 主要用于观察平台线程。虚拟线程使用 `Thread.dump_to_file` 观察。各命令的采集口径应分别记录。

## 3. 线程状态与栈 {#线程状态与栈}

| 状态 | 含义与例子 |
| --- | --- |
| `RUNNABLE` | 执行或可运行，也可处于部分 native I/O |
| `BLOCKED` | 等待进入或重新进入 synchronized monitor |
| `WAITING` | 无期限 wait、join 或 park |
| `TIMED_WAITING` | 带期限 wait、sleep 或 park |
| `NEW` / `TERMINATED` | 尚未启动 / 已结束 |

状态只描述 JVM 视角。空闲工作线程在任务队列中 park，属于正常等待。队列增长而工作线程都等外部资源时，才需分析阻塞。

ReentrantLock 通过 park 等待时，状态可为 WAITING。定位锁竞争需要同时查看栈与锁对象。

## 4. 死锁 {#死锁}

```text
线程 A 持有锁 L1，等待锁 L2
线程 B 持有锁 L2，等待锁 L1
```

按锁标识连接等待者与持有者，即可得到等待环。monitor 转储可出现 `locked` 和 `waiting to lock`。AQS 锁还需结合 ownable synchronizer 的持有信息。

JVM 能自动报告部分 monitor 与同步器死锁。Future 依赖和外部资源等待需要补充业务关系。

修复可统一获取顺序，或减少嵌套持锁。`tryLock(timeout)` 需要配套释放、失败和重试协议。单独重启只恢复当前进程。

## 5. 锁竞争 {#锁竞争}

```java
synchronized void record(Metric metric) {
    remoteClient.send(metric);
}
```

示例持锁执行远程调用。远程响应慢时，其他调用者会等待该 monitor。只要持有者最终退出，队列仍能向前推进。

多份栈可确认持有者是否停在慢路径。JFR 的 `jdk.JavaMonitorEnter` 记录 monitor 竞争。`jdk.ThreadPark` 则提供 park 等待事件。

优化可移出锁内 I/O，或拆分独立状态。改用并发结构后，仍需验证共享状态的一致性。

## 6. 线程池饥饿 {#线程池饥饿}

```java
Future<Result> child = executor.submit(task);
return child.get();
```

假设父任务已占满固定大小线程池。每个父任务都把子任务提交到同一池，再同步等待。子任务留在队列中，全部工作线程却都在等待。

排查需对齐 active、queue 和提交关系。可采用非阻塞编排，或让子任务使用独立执行器。修复还需控制队列和下游容量。

## 7. 活锁与饥饿 {#活锁与饥饿}

活锁指线程不断改变状态或重试，却未完成工作。饥饿指特定任务长期得不到资源，其他任务仍有进展。

单份 RUNNABLE 栈难以区分正常计算与重试。结合完成数、重试数和连续采样判断。CPU 排查见 [CPU 使用率](./cpu-high-diagnosis.mdx)。

## 8. 虚拟线程的线程转储 {#虚拟线程的线程转储}

以 JDK 21 为例，可导出 JSON 线程栈：

```bash
jcmd <pid> Thread.dump_to_file -format=json /safe/path/threads.json
```

该命令包含平台线程和虚拟线程。它逐线程采集，并非同一时刻的一致快照。命令也不执行自动死锁检测。

`ThreadMXBean.findDeadlockedThreads()` 检测平台线程的锁环。其结果不覆盖涉及虚拟线程的等待环。

虚拟线程仍会争用数据库连接和共享锁。诊断时要查看业务栈、carrier CPU 与下游容量。Java 21 在 synchronized 内阻塞时会发生 pinning。native 方法执行期间也会固定 carrier。长时间固定会降低可用 carrier 数量。

## 9. 常见问题 {#常见问题}

### 9.1 sleep 与 wait 的锁行为 {#sleep-与-wait-的锁行为}

sleep 保留当前持有的 monitor。Object.wait 释放调用对象的 monitor，返回前重新获取。线程持有的其他锁仍需单独管理。

### 9.2 ReentrantLock 的死锁条件 {#reentrantlock-的死锁条件}

ReentrantLock 也能形成循环等待。超时获取提供失败出口，但调用方必须释放已持有的锁。

### 9.3 线程池空闲与积压 {#线程池空闲与积压}

空闲时队列为空，工作线程等待新任务。故障时请求或队列持续增长，线程却在等锁或资源。

<summary>参考回答</summary>

先用 `jcmd <pid> Thread.print -l` 采集锁信息。查看自动报告，再按锁标识连接持有者与等待者。A 持 L1 等 L2，B 持 L2 等 L1，即构成环。对照代码确认锁顺序，修复后再次验证。自动报告未覆盖的依赖需结合任务关系分析。

</details>

### 10.2 大量线程处于 WAITING，为什么系统仍然可能故障 {#waiting-threads}

<!-- 面试来源：
- 阿里巴巴：https://www.nowcoder.com/discuss/353148456472616960
-->

**出现公司**：阿里巴巴

**考察重点**：等待对象、任务队列与线程池饥饿。

**相关内容**：[线程状态与栈](#线程状态与栈)、[线程池饥饿](#线程池饥饿)。

<details>
<summary>参考回答</summary>

WAITING 只说明等待条件，空闲与故障都可出现。空闲线程等待新任务，故障线程可等待锁或子 Future。若父任务占满同一线程池，子任务会排队。父任务又等待子任务时，就会发生线程池饥饿。

</details>
