# CPU 使用率

CPU 使用率表示进程消耗处理器时间的程度。本文负责从进程、线程到调用路径定位高 CPU。诊断工具的选择见[JVM 诊断](./diagnostic-tools-evidence.mdx)。

## 1. 面试核心 {#core}

- Linux 平台线程的 TID 对应线程转储中的十六进制 `nid`。[卡](#high-cpu-to-code)
- CPU profile 的样本占比反映调用路径的 CPU 消耗分布。[卡](#high-cpu-no-loop)
- cgroup v2 的 `cpu.max` 用配额与周期约束 CPU 带宽。[卡](#cpu-quota-throttling)
- Java `RUNNABLE` 状态包括计算与部分 native I/O。

## 2. CPU 饱和程度 {#确认范围与饱和程度}

先确认受影响实例、吞吐与延迟。再对照流量、发布和定时任务的时间。

处理器指标要区分 user、system 与 iowait。容器还需结合 CPU 配额和 throttling。按单核计数时，100% 表示占用一个逻辑核。

### 2.1 容器配额与节流 {#容器配额与节流}

Linux cgroup v2 的 `cpu.max` 格式为配额与周期。两个值以微秒计：

```text
200000 100000
```

这表示每 100ms 最多使用 200ms CPU 时间。对应平均 2 个 CPU 的带宽。多个线程能提前用完配额，随后进入节流。

在目标 cgroup 目录读取 `cpu.stat`。比较 `nr_throttled` 与 `throttled_usec` 的区间增量。主机仍有空闲核时，容器也可因自身配额受限。

配额不足时应减少每请求 CPU，或评估扩容。增加业务线程会加剧配额竞争。

## 3. 高 CPU 线程 {#定位高-cpu-线程}

Linux 平台线程可用以下命令观察：

```bash
top -H -p <pid>
pidstat -t -p <pid> 1
```

记录持续高 CPU 的 TID，再转换为十六进制：

```bash
printf '%x\n' <tid>
jcmd <pid> Thread.print -l > threads.txt
```

在转储中匹配 `nid=0x...`。TID 与转储需来自同一 PID 命名空间。还应在相近时间采集，避免线程退出或 ID 复用。

虚拟线程会在载体线程之间切换。一个 OS TID 无法固定对应一个虚拟线程。此时应结合支持虚拟线程的 JFR 与分析工具。

## 4. 多份线程栈 {#多份线程栈}

间隔 3—10 秒采集数份线程栈。检查同一线程是否持续计算，或只偶然经过某方法。

相同栈帧反复出现是热点线索。持续计算也可在多个方法间推进。因此，确认 CPU 占比还需采样 profile。

GC Worker、CompilerThread 与业务线程应分开统计。线程状态需与 OS 线程 CPU 一起解释。

## 5. CPU profile {#cpu-profile}

使用 async-profiler 采样 30 秒：

```bash
asprof -e cpu -d 30 -f cpu.html <pid>
```

火焰图宽度表示采样占比。叶子表示采样时的执行位置，父节点包含子调用成本。应沿热点路径定位请求或任务入口。

典型热点包括排序、压缩、序列化与正则回溯。异常堆栈填充和 CAS 重试也会消耗 CPU。CPU profile 的宽度不表示单次调用耗时。

## 6. GC 与分配 {#gc-与分配}

GC 线程消耗高时，应检查分配率与存活对象量：

```bash
jstat -gcutil <pid> 1000
jcmd <pid> JFR.start name=cpu settings=profile duration=60s filename=cpu.jfr
```

分配峰值会增加回收工作。无界保留则增加复制、标记与空间压力。阶段诊断见[GC 停顿分析](./gc-logs-jfr-pauses.mdx)。

## 7. JIT、类加载与 native 时间 {#jit类加载与-native-时间}

发布后的预热会产生 JIT 和类加载工作。可用 JFR 编译事件与 `jcmd <pid> Compiler.queue` 核对。

system CPU 高时，继续检查系统调用与上下文切换。缺页、线程创建和 native 库也需纳入分析。async-profiler 的 native/kernel 栈依赖平台权限与符号。

Java 栈中的一个 native 方法可包含大量本地工作。展开本地栈后，才能继续区分实际热点。

## 8. 修复验证 {#修复验证}

修复前后应使用相近流量与请求分布。比较每请求 CPU、吞吐、P99 和错误率。再检查分配率、GC CPU 与 throttling。

若使用缓存减少计算，还需验证容量和一致性。仅瞬时 CPU 下降不足以证明修复有效。

## 9. 常见问题 {#常见问题}

### 9.1 Load Average 与 CPU 使用率 {#load-average-与-cpu-使用率}

Linux Load Average 包含可运行与不可中断等待任务。高 Load 需结合 CPU、运行队列和 I/O 判断。

### 9.2 线程数量与 CPU 消耗 {#线程数量与-cpu-消耗}

WAITING 线程主要占用栈等资源。大量可运行线程会增加调度与切换成本。应比较线程 CPU 时间和状态。

### 9.3 RUNNABLE 与实际计算 {#runnable-与实际计算}

Java RUNNABLE 包含部分 native I/O。需要结合 OS 线程 CPU 和调用栈判断。耗时路径还可通过 wall-clock profile 分析。

### 10.3 主机 CPU 仍有空闲，容器为何出现节流和长尾？ {#cpu-quota-throttling}

<details>
<summary>参考回答</summary>

容器可因自己的 CPU 配额用尽而被节流。`cpu.max` 为 `200000 100000` 时，平均带宽为 2 个 CPU。并发线程可在周期前段用完配额。应比较 `cpu.stat` 的节流增量与请求长尾。随后评估每请求计算量和配额容量。

</details>
