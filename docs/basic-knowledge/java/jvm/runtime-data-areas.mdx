# JVM 运行时数据区域

**JVM 运行时数据区域**是 JVM 规范为运行中的程序划分的几块逻辑内存。每个线程有自己的程序计数器、虚拟机栈和本地方法栈，所有线程共享堆和方法区。

这些划分帮助我们解释方法调用时数据存在哪里、方法结束后对象为什么还能存在。但规范描述的是各区域的职责，不是实际的内存布局。理解这一点，才能把堆、栈、元空间和操作系统看到的进程内存联系起来。

## 1. 面试核心 {#core}

- 程序计数器、JVM 栈和本地方法栈**由各线程独有**，堆和方法区**由所有线程共享**。[卡](#runtime-areas)
- 栈帧**随方法调用创建、随方法结束销毁**，保存局部变量、操作数栈和调用状态。
- 按规范的逻辑划分，堆管理对象与数组，栈帧中的引用变量保存的是**引用值，不是对象本身**。[卡](#heap-vs-stack)
- `long` 和 `double` **占两个局部变量槽位**，实例方法的**槽位 0 保存 `this`**。[卡](#frame-slots)
- 方法区是规范中的逻辑区域，HotSpot 自 JDK 8 起用**本地内存中的 Metaspace** 管理类元数据。

## 2. 程序计数器 {#程序计数器}

**程序计数器**记录当前线程正在执行的 JVM 指令位置，每个线程各有一个。线程被切换出去再切回来时，靠它知道从哪条指令接着执行。

它只对 Java 方法有意义。执行 `native` 方法（用 C、C++ 等语言实现的方法）时，程序计数器的值在规范中是未定义的。程序计数器保存的信息很少，JVM 规范也没有为它规定内存溢出异常。

光有指令位置还不够接着算下去：线程恢复执行时，JVM 还要恢复它的栈帧等调用状态，这就是下一节的虚拟机栈。

## 3. 虚拟机栈 {#虚拟机栈}

**JVM 栈**保存一个线程的方法调用状态，它由一个个栈帧组成。**栈帧**是保存一次方法调用所需数据的结构：每调用一次方法，JVM 就压入一个新栈帧；方法正常返回或异常退出，这个栈帧就销毁。

栈帧主要保存四类数据：

- **局部变量表**保存方法参数和局部变量。
- **操作数栈**保存指令计算时用到的值和中间结果。
- 指向当前类运行时常量池的引用，用于动态链接，也就是把方法里的符号引用关联到运行时的目标（[运行时常量池](#运行时常量池)一节会说明符号引用是什么）。
- 调用状态，用于方法返回和异常处理，让执行能回到调用方，或者转入异常处理代码。

栈的深度有限。递归过深时，栈帧放不下，就会抛出 `StackOverflowError`。另一种失败和线程数量有关：大量创建平台线程时，每个线程都要一块栈，系统给不出来就会报 `OutOfMemoryError: unable to create native thread`。这时要结合进程内存、系统线程数限制和容器配额一起判断，单看堆是找不到原因的。

具体诊断见 [OutOfMemoryError 与 StackOverflowError](./oom-stack-overflow.mdx)。

### 3.1 局部变量槽位与操作数栈 {#局部变量槽位与操作数栈}

**槽位**是局部变量表存放值的逻辑单位。下面用一次加法看参数、局部变量和中间结果分别放在哪里：

```java
static long sum(int left, int right) {
    long result = (long) left + right;
    return result;
}
```

`sum` 是静态方法，没有 `this`，所以 `left`、`right` 分别占槽位 0、1，`long` 类型的 `result` 占槽位 2、3。执行时，指令先把参数从局部变量表读到操作数栈，转换成 `long` 后相加，再把结果存回 `result` 的槽位，最后返回。可以看到，相加这一步在操作数栈上完成，局部变量表只负责保存变量的值。

如果是实例方法，槽位 0 先留给 `this`，显式参数从槽位 1 开始。`long` 和 `double` 各占两个槽位，引用占一个。槽位描述的是逻辑容量，一个槽位具体占多少字节由 JVM 决定。

这两块结构的大小在编译时就确定了：Class 文件的 Code 属性用 `max_locals` 记录局部变量表需要多少槽位，用 `max_stack` 记录操作数栈的最大深度。到了运行时，即时编译器（JIT）会把热点代码编译成机器码，这时变量的值可以放进寄存器，不再使用的位置也可以复用，不一定真的按槽位排在内存里。

## 4. 堆 {#堆}

**堆**保存对象和数组，由所有线程共享，也是垃圾收集器（GC）管理的主要区域。方法返回后，栈帧销毁，方法创建的对象却未必能回收：如果其他正在使用的对象仍然持有它，它就可能继续存活。判断对象能否回收，要看可达性，不能只看创建它的方法是否结束。

规范允许堆在物理上不连续，是否分代、用哪种收集器，都由实现决定。

「对象都在堆上」也有例外：JIT 可以在不改变程序可观察行为的前提下，消除某些对象的整体分配。原理见 [逃逸分析与标量替换](./escape-analysis-scalar-replacement.mdx)。

HotSpot 用 `-Xms` 设置初始堆大小，用 `-Xmx` 设置最大堆。看内存统计时，要分清三种容量：

- **reserved** 是保留下来、供以后使用的虚拟地址范围。
- **committed** 是已经承诺给 JVM 使用的内存。
- **used** 是当前实际用掉的空间。

比如堆的 reserved 可以等于 `-Xmx`，committed 只有其中一部分，used 又小于 committed。三个数字回答的是不同问题，不能拿一个代替另一个。

## 5. 方法区 {#方法区}

**方法区**保存类和接口在运行时需要的结构，包括字段和方法信息、方法代码以及运行时常量池，由所有线程共享。规范只规定它要保存什么，物理布局和回收策略由 JVM 实现自己选。

所以方法区和元空间不是一个层次的概念。方法区是规范中的逻辑区域；HotSpot 在 JDK 8 移除了永久代，改用**元空间**（Metaspace）在本地内存中管理类元数据，这是实现层面的存储机制。

与类相关的数据实际上分散在多个地方。静态字段属于类的状态，随这个类及其定义加载器的生命周期存在。在 HotSpot 17、21 中，静态字段的值随堆中的 Class 镜像存放，Class 镜像就是 Java 代码里拿到的那个 `Class` 对象；类元数据则放在元空间。

## 6. 运行时常量池 {#运行时常量池}

**运行时常量池**是每个类或接口在运行时的一张常量表，类执行时从这里取得常量，并找到要用的其他类型和成员。它由 Class 文件里的常量池构造而来，属于方法区。

表里保存字面量，以及类、字段和方法的符号引用。**符号引用**用名称和类型描述目标，比如「`java/lang/String` 类的 `length` 方法，返回 `int`」。解析之后，它才关联到运行时真正的目标。解析过程见 [类加载](./class-loading-stages.mdx#解析)。

有三个名字相近的东西要分开：

- Class 文件常量池是 Class 文件里的一张表。
- 运行时常量池是每个运行时类型各有一份的结构，由前者构造。
- 字符串驻留池是 `String.intern()` 用来查找内容相同字符串的地方，它让内容相同的字符串可以复用同一个规范实例，也就是同一个字符串对象。

## 7. 本地方法栈 {#本地方法栈}

**本地方法栈**为本地方法调用服务：Java 调用本地方法时，本地函数的参数和调用状态需要有地方存放。规范把它和 JVM 栈的职责分开，但实现可以合并物理存储，HotSpot 就让 Java 调用和本地调用共用底层的线程栈。

Java 调用本地代码的接口是 JNI。调用过程中还会用到本地堆、对象句柄和本地库自己的状态，这些分配都计入进程内存。

## 8. 进程内存的其他组成 {#规范以外的进程内存}

操作系统统计 Java 进程时，看到的内存远不止 Java 堆。除了堆，进程还要为这些部分留出空间：

- 元空间与压缩类空间，保存类元数据。
- Code Cache，保存 JIT 生成的机器码。
- GC 数据结构，记录对象的存活和引用关系。
- 平台线程栈，保存各线程的调用状态。
- DirectByteBuffer 与 JNI 分配，使用本地内存。
- 内存映射文件与动态链接库，占用进程地址空间。

比如 `-Xmx4g` 只把 Java 堆限制在 4 GiB，进程的总内存还要加上上面这些。如果容器内存限制也设成 4 GiB，进程很可能因为超出配额被杀掉，所以配置容器容量时要给它们和 JVM 自身的开销留出余量。

各区域的统计和容量关系见 [Java 直接内存](./direct-native-memory.mdx)。

## 9. 常见问题 {#常见问题}

### 9.1 局部变量一定存放在栈内存里吗？ {#局部变量的物理位置}

不一定在一块固定的栈内存里。规范用栈帧槽位描述局部变量，实际执行时值也可以放在寄存器中，JIT 还能把无用的计算整个消掉。另外，局部引用变量保存的只是访问对象的引用值，对象本身存在哪里要另外判断。

### 9.2 方法区就是元空间吗？ {#方法区的实现差异}

不能直接画等号。方法区规定的是类型数据的逻辑职责，元空间是 HotSpot 保存类元数据的实现方案。其他 JVM 可以选择不同的存储结构，所以讨论方法区时，要先说明是在讲规范还是具体实现。

### 9.3 NIO 直接缓冲区占用哪一块内存？ {#直接内存的归属}

NIO 直接缓冲区的存储在 Java 堆外，不属于 JVMS 列出的任何一个运行时数据区域。但它仍然计入进程内存，排查进程内存增长时要检查这部分分配。

具体管理见 [Java 直接内存](./direct-native-memory.mdx)。

## 10. 面试题 {#面试题}

### 10.1 JVM 有哪些运行时数据区域，哪些在线程间共享 {#runtime-areas}

**考察重点**：说明各区域保存什么、由哪些线程共享，并区分方法区的规范职责与元空间的实现。

**相关内容**：[程序计数器](#程序计数器)、[方法区](#方法区)。

<details>
<summary>参考回答</summary>

**程序计数器、JVM 栈和本地方法栈由各线程独有，堆和方法区在线程之间共享。**

方法调用会创建栈帧，用来保存参数、局部变量和调用状态。堆保存对象与数组，方法区保存类型的运行时结构。每个类或接口还有一份运行时常量池，它属于方法区。

这些是规范中的逻辑区域，HotSpot 用元空间管理类元数据。进程内存还包含 Code Cache、直接内存等部分，所以 `-Xmx` 只限制堆的容量。

</details>

### 10.2 堆和栈的区别是什么 {#heap-vs-stack}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：比较堆和栈的生命周期、共享范围与内存管理方式，并区分引用变量和对象本身。

**相关内容**：[虚拟机栈](#虚拟机栈)、[堆](#堆)。

<details>
<summary>参考回答</summary>

**JVM 栈由各线程独有，保存方法调用状态；堆由线程共享，保存 GC 管理的对象和数组。**

栈帧随方法调用创建，在方法返回或异常退出后销毁。堆中对象则按可达性回收，可以在创建它的方法结束后继续存在。栈帧中的引用值用于访问对象，基本类型字段也会随对象存放，因此位置取决于数据所属的结构。

递归超过栈深限制时会报 `StackOverflowError`。堆无法为新对象提供空间时，会报 `OutOfMemoryError: Java heap space`。JIT 还可以把值放进寄存器或消除完整对象分配，实际物理布局需要结合实现判断。

</details>

### 10.3 long 局部变量占几个槽位，实例方法的槽位 0 保存什么？ {#frame-slots}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：说明 `long`、引用和 `this` 怎样使用槽位，并区分逻辑容量与实际机器布局。

**相关内容**：[局部变量槽位与操作数栈](#局部变量槽位与操作数栈)。

<details>
<summary>参考回答</summary>

**`long` 占两个局部变量槽位，实例方法的槽位 0 保存 `this`。**

显式参数从后续槽位开始排列，`double` 同样占两个槽位，引用值占一个。槽位表示规范中的逻辑容量，所以一个槽位并不对应所有 JVM 上固定的字节数。实际机器布局由 JVM 决定。

</details>
