# GC 停顿分析

GC 停顿分析定位回收工作与业务延迟的关系。本文负责日志解读、JFR 关联和调优验证。收集过程见[G1](./g1-regions-rset-collection-set.mdx)。安全点机制见[分代回收](./generational-barriers-safepoints.mdx)。

## 1. 面试核心 {#core}

- `-Xlog:gc*,safepoint` 可同时记录 GC 与安全点事件。
- GC 日志中的堆容量是当前容量，并非必然等于 `-Xmx`。[卡](#gc-log-capacity)
- GC 后 live set 持续增长是保留量增长的线索。[卡](#frequent-full-gc)
- JFR 可将 GC、分配样本与线程事件放入同一时间线。[卡](#jfr-vs-gc-log)

## 2. Unified Logging 配置 {#unified-logging-配置}

JDK 9 及以后使用 Unified Logging：

```bash
java \
  -Xlog:gc*,safepoint:file=/logs/gc.log:time,uptime,level,tags:filecount=10,filesize=100m \
  -jar app.jar
```

time 与 uptime 用于对齐业务时间与进程运行时间。filecount 和 filesize 控制日志轮转。目标 JVM 可用 `java -Xlog:help` 查看支持项。

需要阶段细节时，可短期开启 `gc+phases=debug`。排查结束后应恢复已验证的日志级别。

## 3. GC 事件信息 {#gc-事件的四类信息}

读一条 GC 事件时，先确认以下内容：

1. 确认收集器和事件类型。
2. 确认触发原因与 GC ID。
3. 比较回收前后占用及当前容量。
4. 查看暂停时间与最慢阶段。

回收后降得多、随后快速上涨，是高分配的线索。回收后仍高，应继续检查存活对象与回收范围。Young GC 后老年代仍高，不能直接判为泄漏。

### 3.1 堆容量与 CPU 时间 {#堆容量与-cpu-时间}

以下为格式示意：

```text
GC(12) Pause Young (Normal) (G1 Evacuation Pause) 800M->200M(1024M) 20.000ms
GC(12) User=0.06s Sys=0.01s Real=0.02s
```

800M 与 200M 是此次 GC 前后的堆占用。1024M 是当前堆容量，最大堆需另查 `-Xmx`。20ms 是该暂停事件的耗时。

User 与 Sys 记录该区间内的进程 CPU 时间。Real 是经过的墙钟时间。并行工作时，User 加 Sys 可以超过 Real。

Real 明显偏高时，应关联调度、节流与缺页证据。CPU 时间相加也无法直接推出业务损失。

## 4. GC 类型与回收范围 {#gc-类型与回收范围}

Minor、Major 和 Full 的含义依收集器而定。报告应使用实际日志事件名，并写清回收范围。

G1 Mixed 回收年轻代与部分老 Region。ZGC 的并发 cycle 则包含自己的代与阶段。并发周期总时长也不同于 STW 总时长。

## 5. GC 停顿、安全点与系统停顿 {#gc-停顿安全点与系统停顿}

业务长尾可来自安全点进入、GC 工作与系统等待。CPU 节流、换页、锁竞争和 I/O 都需关联。

安全点日志区分到达安全状态与停顿内工作。某段 GC phase 很短时，还需查看该事件的总时间。若 GC 与长尾不在同一窗口，应继续检查其他原因。

## 6. JFR 关联分析 {#jfr-关联分析}

采集与故障窗口一致的记录：

```bash
jcmd <pid> JFR.start name=latency settings=profile duration=5m filename=/logs/latency.jfr
```

在 JMC 中对齐 GC pause、CPU 和业务线程。再查看分配样本、Monitor Blocked 与 Thread Park。编译事件可帮助判断预热成本。

`ObjectAllocationInNewTLAB` 记录触发新 TLAB 的分配。`ObjectAllocationOutsideTLAB` 记录 TLAB 外分配。前者并未记录 TLAB 内的每个对象。

`ObjectAllocationSample` 用采样表示分配压力。估计总量需使用样本权重，而非直接数事件条数。事件缺失时，应先检查 recording settings。

Old Object Sample 可提供存活对象线索。对象保留路径仍需结合堆分析核实。

## 7. 常见原因 {#常见原因}

### 7.1 分配压力 {#分配压力}

请求或批次增大，会推高每秒分配量。年轻代因此更快填满，GC 频率上升。分配 profile 可定位创建位置，再优化中间对象和批次大小。

### 7.2 存活对象与堆余量 {#存活对象与堆余量}

回收后 live set 接近上限时，疏散余量缩小。需要区分业务容量增长与意外持有。容量合理时评估扩堆，持有错误时修复生命周期。

### 7.3 安全点到达延迟 {#安全点到达延迟}

日志中的 Reaching safepoint 高，表示协调耗时较长。应检查线程状态、编译代码和系统调度。收集器暂停目标主要约束回收工作预算。

### 7.4 显式回收与元数据阈值 {#显式回收与元数据阈值}

`System.gc()` 与诊断命令也能发起回收。G1 下可评估 `-XX:+ExplicitGCInvokesConcurrent`。它让显式 GC 走并发路径。`-XX:+DisableExplicitGC` 则忽略应用显式 GC 请求。

诊断工具仍可请求回收，需检查采集记录。相关影响见[JVM 诊断](./diagnostic-tools-evidence.mdx#堆转储与显式回收)。

Metadata GC Threshold 指向元数据分配压力。应检查加载器数量与类增长。这个原因本身不足以证明 Java 堆泄漏。

## 8. 调优步骤 {#调优步骤}

1. 明确业务延迟、吞吐与资源目标。
2. 建立日志、JFR 和负载基线。
3. 修复异常分配与无界持有。
4. 确认堆、容器内存和 CPU 配额有余量。
5. 每次只改一类参数，并回放相同负载。
6. 比较暂停分位、GC CPU、吞吐和 RSS。

参数变更应能对应已观察到的原因。收集器默认自适应配置应作为比较基线。

## 9. 常见问题 {#常见问题}

### 9.1 Young GC 频率 {#young-gc-频率}

频率需与暂停、CPU 和业务目标一起判断。短暂停且成本可接受时，高频回收也可正常。

### 9.2 Full GC 的触发原因 {#full-gc-的触发原因}

空间不足、显式 GC 和诊断操作都可触发 Full GC。应分别记录原因、耗时与重复频率。

### 9.3 JFR 的记录开销 {#jfr-的记录开销}

JFR 的开销随事件、阈值与堆栈深度变化。default 适合持续记录，profile 适合短时分析。修改配置后应在目标负载测量。

## 10. 面试题 {#面试题}

### 10.1 线上 Full GC 频繁，怎样排查 {#frequent-full-gc}

<!-- 面试来源：
- 阿里云：https://www.nowcoder.com/discuss/401459816646942720
-->

**出现公司**：阿里云

**考察重点**：区分分配压力、保留增长、元数据与显式回收。

**相关内容**：[Unified Logging 配置](#unified-logging-配置)至[调优步骤](#调优步骤)。

<details>
<summary>参考回答</summary>

先读取每次 Full GC 的 cause、回收范围与前后占用。再对照分配率、live set、Metaspace 和 Humongous 数量。显式 GC 与诊断操作需单独核对。

回收后持续高，继续分析持有链与业务容量。迅速涨回，检查分配热点与批次峰值。元数据原因则查类加载器增长。修复后用同一负载比较吞吐、暂停和 RSS。

</details>

### 10.2 JFR 和 GC 日志各自能回答什么 {#jfr-vs-gc-log}

<!-- 面试来源：
- 阿里云：https://www.nowcoder.com/discuss/401459816646942720
-->

**出现公司**：阿里云

**考察重点**：关联回收阶段、容量变化与同时发生的运行事件。

**相关内容**：[Unified Logging 配置](#unified-logging-配置)至[JFR 关联分析](#jfr-关联分析)。

<details>
<summary>参考回答</summary>

GC 日志说明回收类型、原因、容量变化与阶段耗时。JFR 关联 GC、分配样本、CPU、线程与编译事件。

两者需按时间、uptime 和实例对齐。日志定位回收成本，JFR 补充同时发生的应用活动。

</details>

### 10.4 能直接用 JFR 分配事件条数计算对象总量吗？ {#allocation-event-count}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：TLAB 事件与采样权重。

**相关内容**：[JFR 关联分析](#jfr-关联分析)。

<details>
<summary>参考回答</summary>
