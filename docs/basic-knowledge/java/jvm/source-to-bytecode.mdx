# Java 字节码

**Java 字节码**是 JVM 执行的指令格式。`javac` 把源码编译成字节码，连同类型信息一起写进 Class 文件，再由目标平台的 JVM 执行。

源码中的泛型、装箱和 Lambda，编译后不一定保留原来的写法。读懂 Class 文件，才能确认编译器做了哪些转换。不过，字节码还会经过解释执行或即时编译，不能直接把它当成 CPU 最终执行的机器码。

## 1. 面试核心 {#core}

- `javac` 完成语法与类型检查，把**泛型擦除、语法糖展开后的程序**写入与处理器无关的 Class 文件。[卡](#source-to-run)
- Class 文件保存**版本、常量池、字段、方法和属性**，方法的字节码用**局部变量表与操作数栈**计算。
- 方法描述符记录**擦除后的参数与返回类型**，泛型信息可以保存在 Signature 属性中。
- 用 **`javap -v -c -p`** 可以检查常量池、描述符和字节码。[卡](#inspect-bytecode)
- `javac --release 8` **同时约束语言、Class 版本和可用的平台 API**。[卡](#release-compatibility)

## 2. javac 编译 {#javac-编译}

`javac` 把合法的 Java 源码转换成 JVM 能读取的 Class 文件。先编译一个乘法方法，再用 `javap` 看生成的指令：

```java
public final class Price {
    public static int total(int unitPrice, int quantity) {
        return unitPrice * quantity;
    }
}
```

```bash
javac Price.java
javap -c -p Price.class
```

编译成功后得到 `Price.class`。在这个过程中，`javac` 解析语法、检查类型，还会做一系列转换：擦除泛型、插入装箱调用、展开语法糖。编译器也会折叠部分常量表达式，也就是把编译时就能算出来的结果提前算好。

源文件和 Class 文件不是一一对应的。成员类、匿名类和编译器生成的辅助类型都会单独产生 Class 文件，一个源文件编译出好几个 Class 文件很正常。

Class 文件里存的是 JVM 指令和类型信息，不是某种 CPU 的机器码，所以它与处理器无关。CPU 最终执行的仍然是机器码：JVM 要么解释执行这些指令，要么把热点方法编译成当前平台的机器码。

## 3. Class 文件的结构 {#class-文件的结构}

Class 文件不只保存指令，还保存 JVM 理解这些指令需要的类型信息。按顺序读，主要有这几部分：

- 文件以魔数 `0xCAFEBABE` 开头，用来识别这是 Class 格式。紧跟着的 minor、major 分别是次版本号和主版本号。
- **常量池**保存字符串等常量，以及类、字段和方法的符号引用。**符号引用**用名称和描述符说明要访问的目标，到解析阶段才关联到运行时的实际目标。
- 类型信息记录访问标志、当前类、父类和接口，然后列出字段和方法。
- **属性**补充代码、调试和验证需要的信息。方法的 Code 属性包含字节码和异常表，还用 `max_stack`、`max_locals` 记录操作数栈和局部变量表的容量。

Code 属性里还可以有行号表和栈映射帧。**行号表**把指令位置对应到源码行，异常堆栈里的行号就来自这里；**栈映射帧**记录某些指令位置上局部变量和操作数栈的类型，供字节码验证使用。`abstract` 和 `native` 方法没有 Code 属性，因为 Class 文件里没有它们的 Java 字节码实现。

下面的命令可以查看这些结构：

```bash
javap -v Price.class
```

`-v` 会输出版本、常量池和属性；再加上 `-p`，可以显示包括 `private` 在内的所有成员。

## 4. 操作数栈与局部变量表 {#操作数栈与局部变量表}

**局部变量表**保存方法参数和局部变量，**操作数栈**保存指令计算时用到的值和中间结果。两者都属于当前方法调用的栈帧，每次调用各有一份。`Price.total` 的核心字节码如下：

```text
iload_0
iload_1
imul
ireturn
```

`total` 是静态方法，两个参数分别在局部变量表的 0 号和 1 号位置。`iload_0` 和 `iload_1` 把 `unitPrice`、`quantity` 依次压入操作数栈；`imul` 弹出这两个整数，相乘后把乘积压回栈顶；`ireturn` 再弹出乘积作为返回值。指令名开头的 `i` 表示操作的是 `int`。

栈帧槽位与共享范围见 [JVM 运行时数据区域](./runtime-data-areas.mdx#局部变量槽位与操作数栈)。

## 5. 方法描述符 {#方法描述符}

**方法描述符**用一串字符记录方法的参数类型和返回类型，JVM 靠它匹配要调用的方法。比如下面这个方法签名接收 `long` 参数，返回 `List<String>`：

```java
List<String> find(long userId)
```

擦除后的描述符为：

```text
(J)Ljava/util/List;
```

括号里是参数，括号后面是返回类型。`J` 表示 `long`，`L...;` 表示类或接口类型。可以看到，`<String>` 已经不在描述符里了。

泛型擦除后，方法调用就按这个描述符匹配。`List<String>` 中的 `String` 这类泛型信息可以另外保存在 Signature 属性中，供反射等工具读取。桥接方法、装箱和增强 for 也都是编译时转换出来的，具体生成了什么结构，以 Class 文件为准。

### 5.1 方法调用指令 {#方法调用指令}

描述符说明了要调用的方法长什么样，调用指令则决定怎样找到要执行的那个方法。不同指令对应不同的查找和分派方式：

| 指令 | 主要用途 |
| --- | --- |
| `invokestatic` | 调用静态方法 |
| `invokevirtual` | 按接收者类型进行虚方法调用 |
| `invokeinterface` | 通过接口类型调用方法 |
| `invokespecial` | 构造器、父类调用等特殊调用 |
| `invokedynamic` | 通过 bootstrap method 链接动态调用点 |

**接收者**是调用实例方法的那个对象，虚方法分派会根据它的实际类型选择具体实现。**bootstrap method**（引导方法）负责为 `invokedynamic` 建立调用点，也就是在第一次执行时决定这条动态调用指令具体调用什么。

从 JDK 9 开始，`javac` 可以用 `invokedynamic` 实现字符串拼接，Lambda 也会用到这条指令。某段语法具体生成哪种指令，以目标 JDK 的编译产物为准。另外，字节码里的调用指令不等于机器码里一定有一次调用：即时编译器（JIT）内联方法后，会把方法体直接并入调用处。

## 6. 字节码验证 {#字节码验证}

JVM 不信任收到的 Class 文件，加载时会先验证它能安全执行。Class 文件不一定来自 `javac`：Kotlin、Scala 等语言的编译器也会生成 Class 文件，字节码工具还可以在编译后修改类。所以 JVM 在读取和链接时，会检查文件格式、类型约束、指令操作数和控制流。操作数非法或者类型不兼容，验证就会失败，这样非法字节码就没有机会破坏运行时状态。

验证过程见 [类加载](./class-loading-stages.mdx#验证)。

### 6.1 Class 版本与目标平台 {#class-版本与目标平台}

Class 文件与处理器无关，但运行它的 JVM 必须支持它的版本。比如 Java 8 的 major 版本是 52，Java 17 是 61；用 Java 8 运行 major 为 61 的 Class 文件，会抛出 `UnsupportedClassVersionError`。

为旧平台编译时，可以用 `--release` 同时约束语言、Class 版本和平台 API：

```bash
javac --release 8 Price.java
javap -v Price.class
```

在支持这个目标的 JDK 上，输出的 major version 是 52。`--release 8` 还限制源码只能用 Java 8 的语法和平台 API。

只写 `-source 8 -target 8` 是不够的：它们约束了语法和 Class 版本，但编译时用的平台 API 仍然来自当前 JDK。代码里不小心用了 Java 8 没有的 API，编译能通过，到旧环境运行时才报链接错误。第三方依赖也要单独确认支持目标版本。

## 7. 字节码执行 {#从字节码到执行}

Class 文件交给 JVM 后，要先变成运行时的类型，才能执行里面的方法。类加载器找到字节并定义类型，JVM 完成验证、准备等链接工作，再在满足使用条件时触发初始化；解析可以推迟到真正用到符号引用时再做。详见 [类加载](./class-loading-stages.mdx)。

执行阶段，HotSpot 先解释字节码，同时收集方法调用频率、实际对象类型等运行信息，这些信息称为**运行时画像**。根据画像，热点方法会被编译成机器码。执行层级与循环中途切换到编译代码的过程见 [分层编译](./interpreter-tiered-compilation.mdx)。

编译优化依赖画像中的假设，比如「这里的对象总是某个类型」。假设失效时，已编译的代码会去优化，退回能够正确执行的较低层级。原理见 [方法内联与去优化](./inlining-deoptimization.mdx)。

## 8. 常见问题 {#常见问题}

### 8.1 javac 和 JIT 都是编译器，有什么区别？ {#javac-与-jit}

两者的工作时机和目标不同。`javac` 在程序运行前把源码编译成 Class 文件，产物可以在支持相应 Class 版本和所需 API 的 JVM 上运行。即时编译器（JIT）在程序运行时工作，利用调用和类型画像，把热点代码编译成当前平台的机器码。

### 8.2 反编译能还原原来的源码吗？ {#反编译结果与源码}

不能保证。反编译器只能根据 Class 文件重建近似的源码。到 Class 文件这一步，泛型擦除、桥接方法生成、装箱调用插入和语法糖转换都已经发生，所以重建结果反映的是编译后的结构，原来的变量名和写法不一定能恢复。

### 8.3 能从字节码直接判断性能吗？ {#字节码与实际性能}

不能从字节码直接判断性能。同样的字节码，在不同的 JDK 版本、JVM 实现、运行参数、输入数据和硬件上，会编译出不同的机器码，解释执行、内联和垃圾回收的开销也不一样。性能要在目标环境里实测。

## 9. 面试题 {#面试题}

### 9.1 Java 程序从源码到运行经历了哪些过程 {#source-to-run}

**考察重点**：区分源码编译、类加载与运行时执行，说明字节码与机器码的关系，以及解释器和 JIT 怎样配合。

**相关内容**：[javac 编译](#javac-编译)、[字节码执行](#从字节码到执行)。

<details>
<summary>参考回答</summary>

**Java 程序先由 `javac` 编译为 Class 文件，再由 JVM 加载、链接并执行。**

`javac` 完成语法和类型检查，生成与处理器无关的字节码。JVM 根据 Class 文件中的字节创建运行时类型，完成验证与准备，再按使用条件触发初始化，解析可以延迟。HotSpot 解释字节码并收集运行时画像，再把热点代码编译为当前平台的机器码。

优化假设失效时，已编译代码还会去优化。整个过程把源语言检查、运行时类型创建和热点优化分开，CPU 最终执行的是机器码。

</details>

### 9.2 怎样确认一段 Java 语法最终生成了什么 {#inspect-bytecode}

**考察重点**：用一致的编译参数和 javap 检查泛型擦除、桥接方法与调用指令，并区分编译产物和运行时优化。

**相关内容**：[Class 文件的结构](#class-文件的结构)、[方法描述符](#方法描述符)。

<details>
<summary>参考回答</summary>

**用相同 JDK 和编译参数生成 Class 文件，再运行 `javap -v -c -p` 查看实际产物。**

输出包含版本、常量池、描述符、属性和指令，可以据此确认泛型擦除或语法糖的编译结果。若要继续确认运行时加载了哪个类、方法是否内联，还需结合类加载日志、JIT 日志或 JFR 记录。字节码只描述编译产物，后续优化要通过运行时证据判断。

</details>

### 9.3 为什么编译给 Java 8 使用时，应选 --release 8？ {#release-compatibility}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释 Class 版本与平台 API 是两项兼容要求，说明 `--release` 怎样同时约束它们。

**相关内容**：[Class 版本与目标平台](#class-版本与目标平台)。

<details>
<summary>参考回答</summary>

**`--release 8` 同时限定 Java 8 语法、Class 版本和 Java 8 平台 API。**

单独设置 `-source 8 -target 8` 时，编译器仍可读取当前 JDK 的新 API。这样生成的 Class 虽然能被 Java 8 读取，调用旧平台缺少的方法时却会链接失败。`--release 8` 能在编译时发现这类平台 API 误用，第三方依赖的目标版本仍需单独检查。

</details>

### 9.4 invokevirtual、invokespecial 与 invokedynamic 各负责什么？ {#bytecode-invocations}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：说明三条指令各怎样确定调用目标，并解释引导方法在动态链接中的作用。

**相关内容**：[方法调用指令](#方法调用指令)。

<details>
<summary>参考回答</summary>

**`invokevirtual` 按对象的实际类型分派虚方法，`invokespecial` 处理构造器和父类方法等特殊调用，`invokedynamic` 交给引导方法建立调用点。**

前两者由 JVM 按固定规则选择方法。`invokedynamic` 把调用点怎样链接交给引导方法决定，所以能用来实现 Lambda 和字符串拼接。调用点确定后，JIT 仍可继续内联和优化，最终机器码中未必保留独立调用。

</details>
