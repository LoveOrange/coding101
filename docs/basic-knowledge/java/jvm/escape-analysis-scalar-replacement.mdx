# 逃逸分析与标量替换

逃逸分析确定对象的可见范围。HotSpot C2 用分析结果支持分配消除与锁消除。本文负责这两类优化及其验证边界。内联机制见[方法内联与去优化](./inlining-deoptimization.mdx)。

## 1. 面试核心 {#core}

- 逃逸分析依据内联后的调用图判断对象可见范围。
- 标量替换将字段拆为独立值，并消除对象分配。[卡](#heap-allocation)
- 线程私有对象的 monitor 可由 C2 消除。[卡](#escape-analysis-optimizations)
- JDK 21 C2 的流不敏感分析会合并不同分支的逃逸结果。[卡](#conditional-escape)

## 2. 对象逃逸的判断 {#对象逃逸的判断}

对象返回给外部、写入共享字段后，会扩大可见范围。未知调用也会使分析变得保守。

```java
record Point(int x, int y) {}

static long distance(int x1, int y1, int x2, int y2) {
    Point left = new Point(x1, y1);
    Point right = new Point(x2, y2);
    return Math.abs((long) left.x() - right.x())
         + Math.abs((long) left.y() - right.y());
}
```

本例只返回计算结果，两个 Point 都留在局部调用中。内联后，C2 可以进一步分析这两次分配。减法前转为 long，避免 int 差值溢出。

参数传递也可以继续分析。若被调用方法已内联，对象仍可证明不逃逸。

## 3. 标量替换 {#标量替换}

标量替换将对象字段拆成独立的编译器值。本例的 Point 可拆成坐标值，再直接计算距离。

```text
分配 Point → 读取坐标 → 计算
                 ↓
          直接使用坐标计算
```

分配消除后，运行时无需保留完整对象头与字段布局。寄存器或栈槽可保存需要的独立值。去优化需要对象时，JVM 可根据元数据重新物化。

## 4. 锁消除 {#锁消除}

线程私有对象上的同步可省去 monitor 操作：

```java
String format(int id, int status) {
    StringBuffer buffer = new StringBuffer();
    buffer.append(id).append(':').append(status);
    return buffer.toString();
}
```

buffer 只在当前调用中使用。C2 能证明线程私有时，可以消除相关锁。源码仍可直接选择语义匹配的 StringBuilder。

锁粗化将相邻同步区间合并，减少重复进入退出。它与基于线程私有性的锁消除属于不同优化。

## 5. 优化条件 {#优化的限制条件}

不逃逸是优化依据，完整分配消除还需满足其他条件。未知调用、对象身份操作和复杂控制流会限制分析。解释执行与编译预算也会影响结果。

### 5.1 条件逃逸 {#条件逃逸}

JDK 21 C2 使用流不敏感逃逸分析。某个分支将对象写入全局字段，就会影响整个分配点：

```java
static Point saved;

static int compute(boolean publish, int x) {
    Point p = new Point(x, 1);
    if (publish) {
        saved = p;
    }
    return p.x();
}
```

若发布分支保留在编译图中，p 被判为全局逃逸。即使大多数调用传 false，也会限制分配消除。其他编译器的部分逃逸分析需按具体实现判断。

## 6. 栈上分配 {#栈上分配的说法}

JDK 21 HotSpot C2 主要通过标量替换消除分配。它并未将所有不逃逸对象整体搬到线程栈。

保留的对象分配仍属于堆分配。TLAB 是堆内线程私有分配区，见[Java 对象布局](./object-creation-layout.mdx)。

## 7. 分配数据验证 {#用分配数据验证}

JMH 的 GC profiler 可测每次操作的分配量：

```bash
java -jar target/benchmarks.jar EscapeBenchmark -prof gc
java -jar target/benchmarks.jar EscapeBenchmark -prof gc -jvmArgsAppend -XX:-DoEscapeAnalysis
```

第二组关闭逃逸分析，作为独立 fork 的对照。比较 `gc.alloc.rate.norm`，并确认两组预热充分。该参数用于实验，不能由结果直接推成生产配置。

基准应返回标量结果，避免死代码消除。把整个待测对象返回或交给外部，还会改变逃逸条件。基准设计见[JMH](./jmh-correct-benchmarks.mdx)。

JFR 分配事件和 async-profiler 可用于定位分配热点。采样量与全部对象数量需要区分。线上验证应比较每请求分配量、GC CPU 与吞吐。

## 8. 常见问题 {#常见问题}

### 8.1 局部对象与堆分配 {#局部对象与堆分配}

局部可见对象也可保留堆分配。C2 需要成功完成分析与标量替换。源代码中的局部变量范围无法保证优化结果。

### 8.2 临时集合的优化边界 {#临时集合的优化边界}

扩容数组与复杂调用会增加标量替换难度。临时集合仍应优先通过算法减少创建。

### 8.3 对象数量与分配成本 {#对象数量与分配成本}

TLAB 缩短分配路径。对象初始化、内存带宽和后续 GC 仍有成本。应根据分配热点决定优化范围。

## 9. 面试题 {#面试题}

### 9.1 Java 对象一定分配在堆上吗 {#heap-allocation}

<!-- 面试来源：
- 字节跳动：https://www.nowcoder.com/discuss/353158260289118208
- 美团、高德等：https://www.nowcoder.com/discuss/606575623565242368
-->

**出现公司**：字节跳动、美团、高德

**考察重点**：区分规范中的对象存储与 C2 分配消除。

**相关内容**：[对象逃逸的判断](#对象逃逸的判断)至[栈上分配](#栈上分配的说法)。

<details>
<summary>参考回答</summary>

JVM 规范将对象存储归入堆，但 JIT 可消除对象分配。C2 成功完成标量替换后，只保留计算所需的独立值。因此运行时可不存在完整的堆对象。

这与把完整对象搬到线程栈不同。是否消除取决于逃逸结果、内联和控制流。应使用分配数据验证。

</details>

### 9.2 逃逸分析可能带来哪些优化 {#escape-analysis-optimizations}

<!-- 面试来源：
- 满帮：https://www.nowcoder.com/discuss/353158686027751424
-->

**出现公司**：满帮

**考察重点**：理解分析结果对标量替换和锁消除的作用。

**相关内容**：[标量替换](#标量替换)至[优化条件](#优化的限制条件)。

<details>
<summary>参考回答</summary>

逃逸分析支持标量替换、分配消除和锁消除。标量替换拆开字段，分配消除省去完整对象。线程私有对象还可省去 monitor 操作。

分析结果只是优化依据。编译器还需满足内联、控制流和对象身份等条件。

</details>

### 9.3 对象只在极少数分支发布，其他调用就能消除分配吗？ {#conditional-escape}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：C2 流不敏感分析与保留的发布分支。

**相关内容**：[条件逃逸](#条件逃逸)。

<details>
<summary>参考回答</summary>

JDK 21 C2 会合并保留分支的逃逸结果。若同一分配点在一个分支写入全局字段，就会被判为全局逃逸。分支很少执行，并不足以保证分配消除。需要确认编译图中的分支与实际分配数据。

</details>
