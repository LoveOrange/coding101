# G1

**G1** 是把堆划分为等大小区域、分批回收的垃圾收集器。它保留年轻代和老年代，但每一代都由多个区域组成，回收时可以只处理选中的一部分区域。

理解 G1，要能回答两个问题：只回收部分区域，怎样避免漏掉仍被外部引用的对象；每次处理的工作量，又怎样影响停顿和吞吐。这也决定了排查时应该看引用扫描、存活对象复制，还是可用空间。本文以 Java 17、21 的 HotSpot 为范围。

## 1. 面试核心 {#core}

- G1 将堆划分为**等大小的 Region**。年轻代和老年代各由一组 Region 组成，区域的角色可以随回收和分配改变。
- RSet 记录**其他区域指向当前 Region 的引用摘要**，局部回收时据此查找外部引用，无需遍历全部未回收区域。[卡](#g1-partial-collection)
- Young GC 回收年轻代；Mixed GC 会再加入**部分候选老年代 Region**，候选区域来自并发标记的结果。
- 自适应 IHOP 根据标记耗时、老年代分配速率和预留空间，**调整并发标记的启动阈值**，并非始终使用初始值 45%。[卡](#adaptive-ihop)
- `-XX:MaxGCPauseMillis=200` 设置的是 **200ms 的软暂停目标**。G1 按历史数据预测工作量，实际停顿仍受存活量、扫描成本和调度影响。[卡](#g1-pause-goal)

## 2. Region {#region}

**Region** 是 G1 分配和回收堆空间的基本区域，大小在 JVM 启动时确定。除了空闲区域，各个 Region 可以承担以下角色：

- Eden 存放新分配的普通对象。
- Survivor 存放年轻代回收后继续留在年轻代的对象。
- Old 存放晋升等路径进入老年代的对象。
- Humongous 存放达到大对象阈值的对象。

```text
[Eden][Old][Free][Survivor][Old][Humongous][Humongous][Free]
```

示意中的 Eden 和 Survivor 属于年轻代，Old 和 Humongous 属于老年代，Free 表示空闲区域。各代不必占据一整块连续地址。G1 可以调整年轻代包含的 Region 数量，适应当前负载和暂停目标。

### 2.1 Humongous 对象 {#humongous-对象}

**Humongous 对象**是达到 G1 大对象判定条件的对象。在 JDK 21 HotSpot 中，这个条件是对象大小严格大于半个 Region，计算时包含对象头和对齐填充。这类对象直接分配到老年代，占用一个或多个连续 Region。

大对象的成本不只是它自身的大小。最后一个 Region 中剩下的空间，要等整个对象回收后才能复用。比如一个对象略大于半个 Region，就会占用整个 Region，尾部接近一半的空间暂时不能分配给别的对象。需要多个 Region 时，还必须找到连续的空闲区域；空闲总量足够但位置分散，仍可能分配失败。

大对象并不都要等到 Full GC 才能回收。G1 可以在标记后回收已经无用的大对象，部分满足条件的对象还可以在回收暂停中提前回收。

增大 `G1HeapRegionSize` 会提高大对象阈值，让一部分对象改走普通分配路径，但每次选择回收区域的粒度也会变粗。因此，要先看对象的实际尺寸和日志中的 Humongous Region 数量，再判断调整是否有收益。

## 3. Remembered Set {#remembered-set}

**记忆集**（Remembered Set，RSet）记录其他区域指向当前 Region 的引用摘要，用来缩小局部回收时的扫描范围。

假设这次回收 Region A，Region B 中的一个对象仍然引用 A 中的对象。即使 B 不参与回收，这条引用也必须检查，否则 A 中仍被使用的对象就可能被漏掉。除了扫描 GC Roots，也就是线程栈等可达性分析的起点，G1 还要根据 A 的 RSet 找到这些外部引用。

RSet 不会保存一份完整对象图。堆被划成更小的地址段，称为**卡片**；**卡表**记录这些地址段的状态。引用更新时，**写屏障**会执行额外的记录逻辑，G1 再通过卡片处理维护引用摘要。回收时扫描摘要指向的卡片，才能找到具体引用，因此不必遍历全部未回收 Region。

缩小回收时的扫描范围，需要付出其他成本：

- 引用写入需要执行额外的屏障逻辑。
- 后台线程需要处理卡片更新。
- RSet 本身需要占用内存。
- 跨 Region 引用密集时，合并摘要与扫描卡片的工作量会增加。

## 4. Young GC {#young-gc}

**Young GC** 主要回收年轻代，为后续分配腾出空间。G1 先把要回收的年轻 Region 加入**回收集合**（collection set），也就是本次回收要处理的区域集合。

应用线程暂停后，G1 找出集合中的存活对象，把它们复制到 Survivor 或 Old，这个过程叫**疏散**（evacuation）。复制完成后，原 Region 中的存活对象已经搬走，垃圾对象无需逐个释放，整个 Region 就可以重新使用。存活对象在目标区域集中存放，也减少了区域内碎片。

复制需要预先留出目标空间。如果没有足够的空间容纳存活对象，就会发生**疏散失败**（evacuation failure）。没有成功搬走对象的区域不能整体释放，需要保留这些对象，交给后续回收处理。

CMS 正常周期采用标记清除，会留下空闲碎片，具体对比见[Serial、Parallel 与 CMS](./serial-parallel-cms.mdx#碎片与浮动垃圾)。

## 5. 并发标记与 Mixed GC {#并发标记与-mixed-gc}

**并发标记**用来识别存活对象，为选择老年代回收区域提供依据。G1 达到启动条件后开始标记，其中大部分工作与应用同时执行，但并非全程没有停顿。例如 Remark 阶段需要暂停应用，完成剩余标记工作。

**Mixed GC** 是把年轻代与部分候选老年代 Region 一起回收。标记结束后，G1 根据存活情况确定候选老区域，再分批将它们加入回收集合。每次选择既要看能腾出多少空间，也要估算扫描和复制需要多少时间。

“Garbage First”表示优先选择回收收益较高的区域，但收益不只看垃圾比例。某个区域垃圾多，如果跨区域引用的扫描成本也很高，就未必是当前最合适的选择。候选范围、必须完成的工作和暂停预算都会影响结果。

### 5.1 IHOP 与启动时机 {#ihop-与启动时机}

**IHOP**（Initiating Heap Occupancy Percent）是判断何时启动并发标记的占用阈值。标记和后续回收都需要时间，如果等空间快耗尽了才开始，老年代可能在回收完成之前就被填满。

JDK 21 默认启用 `G1UseAdaptiveIHOP`，根据标记耗时、老年代分配速率和预留空间调整阈值。例如，标记期间进入老年代的对象变多了，就需要在预测中为这些新增对象留出更多空间。

`InitiatingHeapOccupancyPercent=45` 提供默认初始阈值。收集到足够样本后，G1 改用自适应计算结果，因此不能用 45% 判断每一次并发标记的启动时机。

若要手动设定阈值，需要关闭自适应：

```text
-XX:-G1UseAdaptiveIHOP -XX:InitiatingHeapOccupancyPercent=30
```

这组参数关闭自适应，并把阈值固定为 30%。它用于说明手动模式的写法；实际排查应先观察默认自适应策略下的标记耗时和分配增长，再决定是否调整。

## 6. 暂停目标 {#暂停目标}

暂停目标是 G1 预测和安排回收工作量的依据，并不保证每次停顿都小于这个值。以下参数把目标设为 200ms：

```bash
java -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -jar app.jar
```

G1 根据历史统计估算扫描、复制等工作的成本，再选择回收集合。实际执行时，条件可能已经变化：

- 存活对象突然增多，需要复制更多数据。
- RSet 与根扫描的工作量高于预测。
- 大对象改变空间布局，增加回收压力。
- 机器负载和系统调度延迟使 GC 线程难以及时执行。

降低目标也有代价。G1 可以缩小年轻代，减少一次需要处理的对象，但年轻代变小后会更快填满，回收可能更频繁。如果 GC 因此消耗了更多 CPU，应用吞吐就会下降。调整前应先确认 GC 是否主导业务延迟，调整后一起比较停顿、CPU 和吞吐。

## 7. G1 的 Full GC {#g1-的-full-gc}

**Full GC** 是对全堆进行回收和整理的操作，停顿代价较高。分配失败且正常回收无法及时腾出空间时，G1 会尝试这条路径。显式 GC 请求与诊断命令也可能触发它。

排查时先看日志中的 cause，也就是本次回收的触发原因。若原因是空间不足，继续检查：

- 并发标记是否启动太晚，导致 Mixed GC 来不及回收老年代。
- live set 是否接近最大堆。live set 指回收后仍需保留的存活对象总量。
- 分配或晋升速率是否突然升高。
- Humongous 对象是否缺少连续 Region。
- 疏散时是否缺少存放复制对象的目标空间。

确认有缓存无界增长、异常的大量分配等问题时，先修复这些来源，再评估堆余量和并发周期是否来得及完成。需要调整 IHOP 等参数时，一次只改少量相关参数，便于判断效果。

## 8. G1 日志 {#阅读-g1-日志}

G1 日志可以把停顿时间对应到具体的回收类型和阶段。使用统一日志，记录 Region 数量和回收过程：

```bash
java -Xlog:gc*,gc+heap=debug:file=gc.log:time,uptime,level,tags -jar app.jar
```

分析时，把这些信息放到同一时间线上：

1. 确认 Young、Mixed、Concurrent Cycle 或 Full 的事件类型与触发原因。
2. 比较 Eden、Survivor、Old 和 Humongous Region 的数量变化。
3. 查看 Evacuate、Merge/Scan Heap Roots 和 Reference Processing 等阶段耗时。它们分别涉及疏散、合并或扫描堆根，以及特殊引用处理。
4. 对照暂停前后的堆占用，计算此次回收腾出了多少空间。
5. 关联同期分配率、请求延迟和 CPU，判断回收对业务的影响。

例如，复制阶段耗时高，先检查需要搬走的存活对象有多少；扫描阶段耗时高，则检查跨区域引用。只有知道时间花在哪一步，才能判断扩大堆或减少引用扫描是否有帮助。把这些阶段与请求延迟关联的方法，见[GC 停顿分析](./gc-logs-jfr-pauses.mdx)。

## 9. 常见问题 {#常见问题}

### 9.1 G1 还分年轻代和老年代吗？ {#g1-的分代布局}

分。G1 的年轻代和老年代各由一组 Region 组成，不要求各自连续。Region 可以在释放后重新分配角色，因此各代容量也可以动态变化。

### 9.2 RSet 保存的是完整对象图吗？ {#rset-的记录粒度}

不是，它记录的是跨 Region 引用的摘要。卡片只定位一段地址范围，不直接给出其中所有对象的引用关系，所以回收时还要扫描卡片，找到具体引用。

### 9.3 Mixed GC 和 Full GC 有什么区别？ {#mixed-gc-与-full-gc}

Mixed GC 在正常疏散过程中回收年轻代与部分候选老 Region。Full GC 则处理全堆，用于正常回收无法及时提供空间或显式请求等情况。两者的回收范围、触发原因与停顿成本都不同。

## 10. 面试题 {#面试题}

### 10.1 G1 怎样通过 Region 和 RSet 完成局部回收 {#g1-partial-collection}

**考察重点**：理解 RSet、回收集合与疏散复制的配合。

**相关内容**：[Region](#region)至[并发标记与 Mixed GC](#并发标记与-mixed-gc)。

<details>
<summary>参考回答</summary>

**G1 选择一组 Region 作为回收集合，再用 RSet 找到集合外指向集合内的引用。**

暂停时，G1 扫描 GC Roots 和相关卡片，把存活对象复制到其他 Region。成功疏散后，原区域就能整体释放。

这种方式用写屏障、后台卡片处理和 RSet 内存，换取较小的扫描范围。跨 Region 引用越密集，合并与扫描摘要的成本也越高。

</details>

### 10.2 G1 的暂停目标为什么不是保证 {#g1-pause-goal}

**考察重点**：理解暂停预测的依据、偏差与吞吐代价。

**相关内容**：[暂停目标](#暂停目标)至[G1 日志](#阅读-g1-日志)。

<details>
<summary>参考回答</summary>

**`MaxGCPauseMillis` 是软目标，因为 G1 按历史数据预测耗时，实际工作量仍会变化。**

比如，存活量、RSet 扫描或大对象压力突然增加，系统调度也会延迟 GC 线程执行。

目标过低可能让 G1 缩小年轻代，并更频繁地收集。单次工作量减少后，GC 的总 CPU 开销却可能上升，影响吞吐。因此，要先找出停顿超出目标的具体阶段，再用相同负载比较延迟、CPU 和吞吐。

</details>

### 10.3 G1 总在堆占用达到 45% 时启动并发标记吗？ {#adaptive-ihop}

<details>

**45% 是默认初始阈值，G1 收集到足够样本后会自适应调整它。**

预测结合标记耗时、老年代分配速率与预留空间，目的是及时启动标记。

手动固定阈值时，需要用 `-XX:-G1UseAdaptiveIHOP` 关闭自适应。例如，再配合 `-XX:InitiatingHeapOccupancyPercent=30`，才是固定为 30% 的模式。

</details>

### 10.4 G1 总空闲空间充足，为何大对象仍会分配失败？ {#humongous-fragmentation}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释分散的空闲 Region 为什么无法满足大对象分配，以及尾部浪费怎样影响可用空间。

<details>
<summary>参考回答</summary>

此外，对象末尾 Region 的剩余空间要等对象回收后才能复用。分析时应同时检查对象实际尺寸、所需 Region 数量与连续空间。

</details>
