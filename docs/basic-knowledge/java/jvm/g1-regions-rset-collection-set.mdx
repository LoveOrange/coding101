# G1

G1 通过 Region 和疏散复制完成局部回收。本文负责回收集合、Mixed GC、大对象和暂停目标。通用屏障与安全点见[分代回收](./generational-barriers-safepoints.mdx)。

## 1. 面试核心 {#core}

- G1 将堆划分为等大小 Region，按需分配各代角色。
- RSet 记录跨 Region 的入向引用摘要。[卡](#g1-partial-collection)
- Mixed GC 回收年轻 Region 与部分老年代 Region。
- `-XX:MaxGCPauseMillis=200` 设置 200ms 的软暂停目标。[卡](#g1-pause-goal)
- 自适应 IHOP 根据标记耗时与分配速率预测启动时机。[卡](#adaptive-ihop)

## 2. Region {#region}

G1 用等大小 Region 管理堆空间。Region 在当前时刻可作为 Eden、Survivor、Old 或 Humongous。

```text
[Eden][Old][Free][Survivor][Old][Humongous][Humongous][Free]
```

年轻代和老年代分别由一组 Region 组成。年轻代容量可随暂停目标动态调整。

### 2.1 Humongous 对象 {#humongous-对象}

Humongous 对象按连续 Region 分配，并直接归入老年代。判定使用对齐后的对象大小，含对象头。JDK 21 HotSpot 的阈值为严格大于半个 Region。

最后一个 Region 剩余空间在对象回收前无法复用。因此，大对象会同时增加连续空间需求和尾部浪费。总空闲空间充足时，也会因缺少连续 Region 分配失败。

G1 可在标记后回收无用的大对象。部分满足条件的大对象还可在暂停中提前回收。大对象并非都要等到 Full GC。

增大 `G1HeapRegionSize` 可改变大对象判定范围。代价是 Region 粒度变粗。应先检查对象尺寸与 Humongous Region 数量。

## 3. Remembered Set {#remembered-set}

局部回收需要知道集合外哪些位置指向集合内。G1 通过写屏障、卡表和 RSet 维护这些信息。

RSet 可理解为 Region 的入向引用摘要。GC 扫描相关卡片，找到指向回收集合的对象引用。卡片记录的是地址范围，精度比单条对象边更粗。

维护这些摘要需要屏障、后台处理和额外内存。跨 Region 引用密集时，扫描成本也会增加。

## 4. Young GC {#young-gc}

Young GC 将年轻 Region 放入 collection set。应用线程暂停后，存活对象被复制到 Survivor 或 Old。成功疏散的原 Region 整体释放。

复制需要足够的目标空间。空间不足会发生 evacuation failure。疏散失败的 Region 需在后续回收继续处理。

## 5. 并发标记与 Mixed GC {#并发标记与-mixed-gc}

G1 并发标记统计老年代对象的存活情况。并发周期仍包含 Remark 等停顿阶段。完成标记后，G1 选出值得回收的老 Region。

Mixed GC 将部分候选 Old Region 与年轻代一起回收。选择依据包括可回收空间、预计成本和暂停预算。它既有空间收益约束，也有时间约束。

### 5.1 IHOP 与启动时机 {#ihop-与启动时机}

IHOP 决定何时发起并发标记。JDK 21 默认启用 `G1UseAdaptiveIHOP`。预测会结合标记耗时、老年代分配速率与预留空间。

`InitiatingHeapOccupancyPercent=45` 是默认初始阈值。收集到足够样本后，由自适应结果决定阈值。因此，固定 45% 无法描述整个运行期。

若要手动设定阈值，需要关闭自适应：

```text
-XX:-G1UseAdaptiveIHOP -XX:InitiatingHeapOccupancyPercent=30
```

这组参数仅展示手动模式。实际调整应以标记耗时和分配增长为依据。默认自适应仍应作为基线。

## 6. 暂停目标 {#暂停目标}

G1 的暂停目标可通过以下参数设置：

```bash
java -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -jar app.jar
```

G1 根据历史统计预测 collection set 的成本。突增的存活量、根扫描或调度延迟会超出预测。因此，200ms 是软目标。

更低目标会缩小单次工作预算，并增加回收频率。其代价需结合 GC CPU、吞吐与业务延迟判断。

## 7. G1 的 Full GC {#g1-的-full-gc}

分配失败且正常回收无法腾出空间时，G1 会尝试 Full GC。其路径在全堆上执行整理，停顿代价较高。显式 GC 与诊断命令也可触发 Full GC。

应按日志中的 cause 区分处理。空间问题需检查 live set、分配速率与疏散余量。大对象还需检查连续 Region。

先减少无界保留与异常分配，再评估堆余量。并发标记过晚时，继续核对 IHOP 预测。

## 8. G1 日志 {#阅读-g1-日志}

开启统一日志，观察 Region 与回收集合：

```bash
java -Xlog:gc*,gc+heap=debug:file=gc.log:time,uptime,level,tags -jar app.jar
```

重点对照 Young、Mixed、Concurrent Cycle 与 Full。再看各类 Region 数量、回收后占用和阶段耗时。跨事件时间线分析见[GC 停顿分析](./gc-logs-jfr-pauses.mdx)。

## 9. 常见问题 {#常见问题}

### 9.1 G1 的分代布局 {#g1-的分代布局}

G1 保留年轻代和老年代。各代由离散 Region 组成，容量可以动态变化。

### 9.2 RSet 的记录粒度 {#rset-的记录粒度}

RSet 保存局部回收所需的跨 Region 引用摘要。它通过卡片定位需要继续扫描的地址范围。

### 9.3 Mixed GC 与 Full GC {#mixed-gc-与-full-gc}

Mixed GC 只加入部分候选老 Region。Full GC 则走全堆处理路径。两者的范围与触发原因不同。

## 10. 面试题 {#面试题}

### 10.1 G1 怎样通过 Region 和 RSet 完成局部回收 {#g1-partial-collection}

<!-- 面试来源：
- 阿里巴巴：https://www.nowcoder.com/discuss/353157613372252160
- 某云原生企业：https://www.nowcoder.com/discuss/732685882523758592
-->

**出现公司**：阿里巴巴、某云原生企业

**考察重点**：理解 RSet、回收集合与疏散复制的配合。

**相关内容**：[Region](#region)至[并发标记与 Mixed GC](#并发标记与-mixed-gc)。

<details>
<summary>参考回答</summary>

G1 用 RSet 定位回收集合之外的入向引用。暂停时扫描根和相关卡片，再复制集合内存活对象。成功疏散后，原 Region 可整体释放。

这种方式省去全堆扫描，但需要维护跨区引用。成本包括写屏障、RSet 内存与扫描工作。

</details>

### 10.2 G1 的暂停目标为什么不是保证 {#g1-pause-goal}

<!-- 面试来源：
- 阿里云：https://www.nowcoder.com/discuss/401459816646942720
-->

**出现公司**：阿里云

**考察重点**：理解暂停预测的依据、偏差与吞吐代价。

**相关内容**：[暂停目标](#暂停目标)至[G1 日志](#阅读-g1-日志)。

<details>
<summary>参考回答</summary>

`MaxGCPauseMillis` 是按历史数据预测的软目标。实际存活量、根扫描与系统调度可偏离预测。G1 因此无法保证每次暂停都低于设定值。

过低目标会增加回收频率。调整时应一起比较 GC CPU、吞吐与端到端延迟。

</details>

### 10.4 G1 总空闲空间充足，为何大对象仍会分配失败？ {#humongous-fragmentation}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：连续 Region 与尾部空间浪费。

**相关内容**：[Humongous 对象](#humongous-对象)。

<details>
<summary>参考回答</summary>

Humongous 分配要求足够的连续 Region。分散的空闲 Region 无法满足这一条件。对象末尾 Region 的剩余空间也无法复用。应检查大对象尺寸、连续空间和 Region 数量。

</details>
