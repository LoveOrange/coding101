# JVM 诊断

JVM 诊断通过快照与时间序列定位运行问题。本文负责工具选择、证据范围和采集影响。CPU 定位见[CPU 使用率](./cpu-high-diagnosis.mdx)。对象引用分析见[堆转储](./heap-dumps-memory-leaks.mdx)。

## 1. 面试核心 {#core}

- 线程转储记录调用与等待，堆转储记录对象引用。[卡](#diagnostic-tools)
- GC 日志记录回收过程，JFR 关联运行期事件。
- 多份线程转储可区分持续停留与偶然经过。[卡](#single-thread-dump)
- JDK 21 的 `GC.heap_dump` 默认请求 Full GC。[卡](#heap-dump-impact)

## 2. 故障时间线 {#故障时间线}

采集前先确认错误、延迟或退出的发生时间。记录受影响实例、接口与发布版本。再关联流量、下游状态和资源指标。

证据需要来自同一实例与时间窗口。正常等待、大对象与 GC 事件都需结合症状解释。

## 3. `jcmd` {#jcmd}

先查看目标 JVM 支持的命令：

```bash
jcmd -l
jcmd <pid> help
jcmd <pid> VM.version
jcmd <pid> VM.command_line
jcmd <pid> VM.flags
```

命令集合由 JDK 版本与实现决定。采集工具应与目标 JDK 匹配。`jcmd` Attach 要求同机及相同有效用户和组。

容器的 PID 命名空间会影响目标识别。`-XX:+DisableAttachMechanism` 会关闭 Attach。连接失败时，应先核对这些条件。

## 4. 症状与首选证据 {#症状与首选证据}

| 症状 | 首选证据 | 后续证据 |
| --- | --- | --- |
| CPU 高 | OS 线程 CPU 与 CPU profile。 | GC、JIT 和线程栈。 |
| 请求卡住 | 多份线程栈与 wall-clock profile。 | 锁、队列与下游指标。 |
| 堆增长 | GC 后 live set 与类直方图。 | 堆转储中的保留关系。 |
| RSS 高、堆稳定 | NMT、BufferPool 与线程数。 | smaps 与 native profiler。 |
| GC 停顿 | GC 日志与 JFR。 | 分配样本和对象图。 |
| 进程崩溃 | hs_err_pid 与系统退出记录。 | core dump 与本地符号。 |
| 类冲突 | 类加载日志与实际来源。 | 依赖树与加载器统计。 |

症状决定所需证据。CPU 高优先采线程 CPU 与调用路径。堆转储适合回答对象由谁持有。

## 5. 快照与时间序列 {#快照与时间序列}

一份线程转储只描述采集瞬间。间隔几秒采集 3—5 份，可以观察状态是否推进。CPU 占比仍需结合线程统计或采样结果。

堆转储显示某一时刻的引用图。连续指标用于确认增长，再用引用图定位持有者。

## 6. JFR {#jfr}

短时记录可使用 profile 配置：

```bash
jcmd <pid> JFR.start name=incident settings=profile duration=2m filename=/logs/incident.jfr
```

JFR 关联 CPU、分配、锁、GC、编译与 I/O 事件。实际事件与阈值由配置决定。持续记录可用 default 配置，并限制年龄和大小：

```bash
jcmd <pid> JFR.start name=continuous settings=default maxage=30m maxsize=256m
jcmd <pid> JFR.dump name=continuous filename=/logs/incident.jfr
```

第二条命令导出已有记录，记录本身继续运行。路径由目标 JVM 写入，需有权限与可用空间。暂停关联分析见[GC 停顿分析](./gc-logs-jfr-pauses.mdx)。

## 7. async-profiler {#async-profiler}

CPU 与 wall-clock 使用不同采样目标：

```bash
asprof -e cpu -d 30 -f cpu.html <pid>
asprof -e wall -d 30 -f wall.html <pid>
```

CPU profile 定位处理器消耗。wall-clock profile 还包含等待和睡眠线程。因此，后者适合分析锁、I/O 与延迟。

采样是统计结果。频率、时长、平台权限和符号都会影响解释。

## 8. 采集动作的影响 {#采集动作的风险}

已有日志与指标适合先建立故障范围。线程转储、JFR 和 profile 用于补充时间维度。类直方图和堆转储涉及堆遍历，应评估停顿。

执行前查看命令影响：

```bash
jcmd <pid> help GC.class_histogram
jcmd <pid> help GC.heap_dump
```

JDK 21 将这两项命令标为 High impact。影响与堆大小、对象数量和落盘速度有关。

### 8.1 堆转储与显式回收 {#堆转储与显式回收}

JDK 21 的 `GC.heap_dump` 默认请求 Full GC。添加 `-all` 后包含不可达对象，并省去该回收请求：

```bash
jcmd <pid> GC.heap_dump /logs/live.hprof
jcmd <pid> GC.heap_dump -all /logs/all.hprof
```

以上是两种采集方式，按目标选一种执行。`-all` 仍需遍历堆并写出文件。它不保证无停顿，文件还会包含待回收对象。

转储前需确认磁盘空间和可接受停顿。分析时记录采集选项，避免混淆存活与不可达对象。

## 9. 证据的环境信息 {#证据的环境信息}

每份证据应记录采集时间、进程 uptime 和实例标识。还需包含 JDK 版本、启动参数与发布版本。

保留采集命令、持续时间和对应监控区间。这些信息用于确认不同证据是否来自同一现场。

## 10. 常见问题 {#常见问题}

### 10.1 传统工具的适用范围 {#传统工具的适用范围}

目标 JDK 支持时，`jstack` 与 `jmap` 仍可使用。`jcmd` 提供统一入口，并能查询命令影响。

### 10.2 在线诊断与堆分析 {#在线诊断与堆分析}

在线调用诊断用于观察具体执行路径。JFR 提供事件时间线，堆转储提供完整引用图。三者按症状组合。

### 10.3 诊断动作与故障现场 {#诊断动作与故障现场}

堆遍历与大文件写入会增加进程负担。先通过指标和事件确定需要回答的问题。再选择能提供所需证据的采集动作。

### 11.2 为什么只采一份线程转储经常无法定位问题 {#single-thread-dump}

<!-- 面试来源：
- 阿里巴巴：https://www.nowcoder.com/discuss/353148456472616960
-->

**出现公司**：阿里巴巴

**考察重点**：区分瞬时状态、持续停留与实际时间占比。

**相关内容**：[快照与时间序列](#快照与时间序列)。

<details>
<summary>参考回答</summary>

单份转储只显示线程采集瞬间的位置。线程恰好经过某个方法，也会出现在栈中。连续快照能显示它是否长期停留或持续推进。

实际热点还需对照线程 CPU 与采样占比。等待栈则需结合请求延迟和队列变化。

</details>

### 11.3 GC.heap_dump 的 -all 选项会消除停顿吗？ {#heap-dump-impact}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：Full GC 请求、堆遍历与不可达对象。

**相关内容**：[堆转储与显式回收](#堆转储与显式回收)。

<details>
<summary>参考回答</summary>

`-all` 省去默认的 Full GC 请求，但仍需遍历堆。它同时导出可达与不可达对象。堆遍历和文件写入仍会造成影响。选择该选项后，分析时也需区分待回收对象。

</details>
