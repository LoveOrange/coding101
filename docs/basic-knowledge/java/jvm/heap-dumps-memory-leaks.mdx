# 堆转储

堆转储记录某一时刻的堆对象和引用关系。本文负责采集成本、对象持有关系与泄漏验证。GC Roots 的类型见 [GC Roots](./gc-roots-reachability.mdx)。堆外问题见 [Java 直接内存](./direct-native-memory.mdx)。

## 1. 面试核心 {#core}

- GC 后存活占用持续增长是泄漏线索，业务生命周期决定对象是否无用。[卡](#cache-growth-vs-leak)
- `GC.class_histogram` 按类统计对象数量和浅大小。
- JDK 21 的 `GC.heap_dump` 默认请求 Full GC，`-all` 包含不可达对象。[卡](#heap-dump-all)
- 浅大小只计算对象自身，保留大小包含其支配的对象图。[卡](#shallow-vs-retained)
- Dominator Tree 表达支配关系，GC Roots 路径解释对象的持有来源。

## 2. 泄漏、容量不足与分配峰值 {#泄漏容量不足与分配峰值}

泄漏是无用对象仍被强引用持有。容量不足是必需的工作集超过可用堆。分配峰值则是短期需求超过回收供给。

普通 used heap 会随分配上升。判断时应对齐负载和 GC 后存活占用。还要检查缓存上限、过期时间与队列长度。有限缓存填满后稳定，属于预期增长。过期条目持续滞留，才指向生命周期问题。

## 3. 类直方图 {#类直方图}

```bash
jcmd <pid> GC.class_histogram > histogram.txt
```

直方图按类汇总数量与浅大小。`[B` 表示 `byte[]`。数组的业务归属仍需沿引用链查找。

该命令需要遍历堆，采集会影响业务。输出文件小，也仍有采集成本。采集前用 `jcmd <pid> help GC.class_histogram` 确认选项。

## 4. 堆转储的成本 {#堆转储的成本}

```bash
jcmd <pid> GC.heap_dump /safe/path/heap.hprof
```

转储涉及堆遍历、停顿和磁盘写入。文件大小取决于对象与格式，须预留足够磁盘。线上采集应选择允许暂停的窗口。可摘流的实例优先摘流后采集。

HPROF 会包含对象字段中的业务数据。文件按敏感数据控制访问、传输和留存。

### 4.1 存活对象与全量对象 {#存活对象与全量对象}

JDK 21 的默认命令会请求 Full GC。添加 `-all` 后，命令包含不可达对象。该选项省去命令主动请求的 Full GC。堆遍历与写文件仍有停顿成本。

```bash
jcmd <pid> GC.heap_dump -all /safe/path/heap-all.hprof
```

不可达对象等待回收，不属于强引用泄漏。比较两份转储时，应使用相同采集口径。

## 5. Histogram 与 Dominator Tree {#histogram-与-dominator-tree}

Histogram 按类型聚合，适合寻找增长对象。Dominator Tree 按支配关系聚合，适合寻找持有者。

若从 GC Roots 到 B 的每条路径都经过 A，A 就支配 B。A 的保留大小包含这些被支配对象。支配树的父子关系与直接引用关系不同。

例如小型缓存管理器能保留大量数组。若另有绕过管理器的路径，数组就不受它单独支配。删除缓存中的引用也未必释放该数组。

定位时先看 retained size。再用 Path to GC Roots 找静态字段、线程或队列。OQL 可按实例字段继续筛选。

## 6. 常见泄漏来源 {#常见泄漏来源}

### 6.1 无界缓存和队列 {#无界缓存和队列}

缓存缺少容量或过期机制，会持续积累键值。消费速度长期落后时，队列也会保留请求。

### 6.2 监听器和回调 {#监听器和回调}

长生命周期发布者会持有订阅者。订阅结束后需要注销回调。

### 6.3 ThreadLocal 与线程池 {#threadlocal-与线程池}

池中线程长期存活，会保留任务留下的值。任务结束时应在 `finally` 中调用 `remove()`。

### 6.4 类加载器泄漏 {#类加载器泄漏}

线程或静态注册表持有旧加载器，会阻碍卸载。卸载条件见 [类加载器](./classloaders-spi-isolation.mdx#类的卸载)。

### 6.5 未完成任务 {#未完成任务}

Future 和重试队列会持有请求上下文。下游卡住且任务没有超时，会延长持有时间。

## 7. 多个时间点的对比 {#多个时间点的对比}

GC 日志用于建立存活占用趋势。业务指标用于判断缓存与队列增长。JFR Old Object Sample 提供老对象采样线索。采样遗漏的对象仍需结合完整转储分析。

先确定增长时段，再选择代表性时刻采集。比较时保持负载、采集选项与 GC 阶段一致。

## 8. 修复方式 {#修复方式}

修复应落实对象的释放责任。缓存设置容量和有效过期策略。队列设置上限，并处理消费落后。监听器、任务和 ThreadLocal 补齐结束时的清理。

修复后运行同等长稳负载。确认 GC 后存活占用与对象数量稳定。还要验证缓存命中、请求结果和取消行为。

## 9. 常见问题 {#常见问题}

### 9.1 大对象与泄漏来源 {#大对象与泄漏来源}

大对象既能是合理工作集，也能是意外持有。判断依据是增长趋势、保留大小和业务生命周期。

### 9.2 字节数组的持有来源 {#字节数组的持有来源}

沿支配者和 GC Roots 路径分组。再检查数组属于缓存、网络缓冲还是请求上下文。

### 9.3 连续转储的采集成本 {#连续转储的采集成本}

每次采集都会增加堆遍历与写盘成本。先用监控和 JFR 定位增长时段，再采代表性转储。

## 10. 面试题 {#面试题}

### 10.1 堆使用率持续升高，怎样判断缓存增长还是内存泄漏 {#cache-growth-vs-leak}

<!-- 面试来源：
- 阿里、腾讯：https://www.nowcoder.com/discuss/353158121138888704
-->

**出现公司**：阿里、腾讯

**考察重点**：存活占用、引用链与业务上限。

**相关内容**：[泄漏、容量不足与分配峰值](#泄漏容量不足与分配峰值)。

<details>
<summary>参考回答</summary>

先对齐稳定负载和多次 GC 后的存活占用。再用直方图定位增长类型，用转储追查持有者。缓存达到约定上限后稳定，属于预期工作集。失效条目仍被强引用持有，则属于泄漏。修复后用同等负载确认增长停止。

</details>

### 10.2 堆转储分析时为什么既要看 shallow size，也要看 retained size {#shallow-vs-retained}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：对象自身大小与支配关系。

**相关内容**：[Histogram 与 Dominator Tree](#histogram-与-dominator-tree)。

<details>
<summary>参考回答</summary>

浅大小计算对象自身，保留大小计算其支配的对象图。缓存管理器虽小，也能保留大量元素。其他根共享的元素不计入它独占的保留大小。分析时还需沿 GC Roots 路径确认持有来源。

</details>
