# 堆转储

**堆转储**（heap dump）是记录某一时刻 Java 堆中对象及其引用关系的快照。它能回答两个问题：谁占用了内存，谁还在持有这些对象。

一份转储只记录一个时刻，无法单独说明内存是否持续增长。排查时先用监控和多次 GC 后的占用确认增长趋势，再用转储找到持有者，结合业务生命周期判断是否泄漏。采集转储本身会暂停应用，并写出可能包含敏感数据的大文件，因此还要评估采集成本。

## 1. 面试核心 {#core}

- 稳定负载下，**多次 GC 后的存活占用持续增长**是泄漏的线索；对象到底有没有用，还要按业务生命周期判断。[卡](#cache-growth-vs-leak)
- `GC.class_histogram` **按类统计实例数量和对象自身占用**，适合先找出数量异常或持续增长的类型。
- JDK 21 的 `GC.heap_dump` **默认会请求一次 Full GC**，只转储存活对象；加 `-all` 则包含不可达对象，并省去这次请求。[卡](#heap-dump-all)
- **浅大小**只算对象自身，**保留大小**还包括它失去可达性后能连带回收的对象。[卡](#shallow-vs-retained)
- Dominator Tree 展示对象之间的**支配关系**，通向 GC Roots 的路径解释对象**为什么仍被持有**。

## 2. 泄漏、容量不足与分配峰值 {#泄漏容量不足与分配峰值}

堆占用上升只说明空间在被使用，不说明有问题。动手处理之前，先判断这些对象是不是还有用。三种常见情况的处理方式完全不同：

- **泄漏**：业务上已经没用的对象仍被强引用持有，存活占用随时间增长。要修的是对象的生命周期。
- **容量不足**：对象都还有用，只是稳定运行需要的工作集超过了可用堆。要评估的是堆大小。
- **分配峰值**：短时间内创建大量对象，GC 或堆扩容来不及腾出空间。要查的是批次和突发流量。

区分它们，不能只看 used heap（当前堆占用）曲线，因为对象分配会让曲线上升，回收又会让它下降。要在负载相近、回收范围一致的前提下，比较多次 GC 后的占用。这个值持续上升，说明回收后留下的对象越来越多，但是否泄漏还要看它们有没有业务用途。

同时还要看缓存容量、过期时间和队列长度。一个有上限的缓存逐渐填满、然后稳定下来，属于预期的工作集增长；已经过期的条目一直留着不走，才说明生命周期有问题。

## 3. 类直方图 {#类直方图}

**类直方图**按类型汇总对象数量和自身占用，适合在采集完整转储之前，先确定是哪些类型在增长。采集命令如下：

```bash
jcmd <pid> GC.class_histogram > histogram.txt
```

直方图里的大小是浅大小，只算对象自身（第 5 节会解释它和保留大小的区别）。它能帮你发现 `byte[]`、Map 节点或业务 DTO（传递业务数据的对象）数量异常。比如类名 `[B` 表示 `byte[]`，但这些数组属于缓存还是请求内容，直方图看不出来，还得沿引用链去查。

直方图需要遍历整个堆，即使输出文件很小，采集过程也会影响业务。JDK 21 默认只统计存活对象，为此还会请求一次 GC。采集前用 `jcmd <pid> help GC.class_histogram` 确认可用选项，并挑一个业务能接受的时间窗口。

## 4. 堆转储的成本 {#堆转储的成本}

直方图只能定位到类型，要看到具体的对象和持有关系，就需要完整的堆转储。下面的命令把快照写成 HPROF 文件：

```bash
jcmd <pid> GC.heap_dump /safe/path/heap.hprof
```

转储要遍历整个堆、暂停应用，还要写出大量数据，堆越大成本越高。文件大小取决于实际对象和格式，磁盘空间要按堆的规模提前留好。执行前确认下面几项：

- 目标路径所在的持久存储有足够的空闲空间。
- 当前时间窗口能接受采集带来的业务暂停。
- 能摘流的实例先摘流（暂停接收新请求），再采集。
- HPROF 里保存着对象字段的实际内容，可能有密码、令牌或个人数据，要限制访问。
- 文件怎样下载、存储、传输、保留和销毁，已经事先定好。

如果启动参数里配了 `-XX:+HeapDumpOnOutOfMemoryError`，也要提前验证输出目录和磁盘容量，否则真到 OOM 时可能留不下能分析的快照。

### 4.1 存活对象与全量对象 {#存活对象与全量对象}

比较两份转储之前，要先确认它们是不是都只包含存活对象。JDK 21 的默认命令会先请求一次 Full GC，再转储存活对象。加上 `-all` 后，转储会把还没被回收的不可达对象也写进去，同时省掉命令主动请求的那次 Full GC；不过遍历堆和写文件的停顿成本还在。

```bash
jcmd <pid> GC.heap_dump -all /safe/path/heap-all.hprof
```

`-all` 里多出来的不可达对象只是还没被回收，已经没有强引用路径持有它们，所以不能算作强引用泄漏。比较两份转储时，采集选项要保持一致，不然会把记录范围的差别误当成对象在增长。

## 5. Histogram 与 Dominator Tree {#histogram-与-dominator-tree}

知道是哪种类型占得多之后，还要找到是哪个对象在持有它们。MAT（Eclipse Memory Analyzer）是常用的堆分析工具，可以用下面四种视图逐步缩小范围：

| 视图 | 能回答的问题 |
| --- | --- |
| Histogram | 某种类型有多少实例，对象自身总共占用多少空间？ |
| Dominator Tree | 哪个对象独自保留了大量对象，释放它能带来多大收益？ |
| Path to GC Roots | 对象沿哪些路径仍能连接到根，持有者是谁？ |
| OQL | 哪些具体实例满足给定类型或字段条件？ |

读这些视图要先分清两种大小。**浅大小**（shallow size）只算对象自身，它引用的其他对象另算。**保留大小**（retained size）是这个对象变得不可达后，可以释放的总空间，包括它自身，以及随之不可达的其他对象。哪些对象会随它一起释放，取决于支配关系。

**支配关系**是指从 GC Roots 到对象 B 的每一条路径都必须经过对象 A，这时就说 A 支配 B。A 一旦不可达，B 也没有来自根的路径了。所以支配树里的父子关系表示可达路径上的依赖，不一定是直接的字段引用。

举个例子，一个缓存管理器自身只有几百字节，却可能支配着几个 GB 的值对象和数组，只看浅大小完全发现不了它。反过来，如果某些数组还有一条绕过管理器的强引用路径，管理器就不支配它们；删掉缓存引用之后，这些数组仍会被那条路径留住。

实际定位时，先按保留大小找到突出的对象，再看它的 Path to GC Roots。常见的持有者有静态字段、线程、`ThreadLocal`、队列和类加载器。需要细分具体实例时，再用 OQL 按字段筛选，比如只查已经过期的缓存条目。

## 6. 常见泄漏来源 {#常见泄漏来源}

泄漏通常出现在「长生命周期的对象持有短期数据」的地方。顺着引用链找到持有者后，可以对照下面几类，检查释放的责任有没有落实。

### 6.1 无界缓存和队列 {#无界缓存和队列}

缓存没有容量上限或有效的过期机制时，新的业务键会不断积累。队列的消费速度长期低于生产速度时，也会积压越来越多的请求。两者都要检查数量上限，以及达到上限后怎么处理。

### 6.2 监听器和回调 {#监听器和回调}

发布者通过监听器或回调持有订阅者。如果发布者活得很久，订阅结束后又没有注销回调，本该短期存在的订阅者就会一直活着。所以每一次注册都要有对应的注销。

### 6.3 ThreadLocal 与线程池 {#threadlocal-与线程池}

线程池里的平台线程可以在任务结束后继续存活，留在 `ThreadLocalMap` 里的值也可能继续被线程持有。如果 `ThreadLocal` 保存的是当前任务的数据，就应该在 `finally` 里调用 `remove()`，让任务正常结束或异常退出时都能清理。

### 6.4 类加载器泄漏 {#类加载器泄漏}

热部署之后，如果旧的类加载器还被某个线程或外部注册表持有，整组类和它们的静态状态都卸载不掉。常见要查的地方有 JDBC Driver 注册、MBean 注册和父加载器里的静态集合。

具体卸载条件见 [类加载器](./classloaders-spi-isolation.mdx#类的卸载)。

### 6.5 未完成任务 {#未完成任务}

`Future`、响应聚合器和重试队列会保留请求上下文。下游卡住、任务又没有超时或取消逻辑时，这些上下文就会长期存活。所以既要检查任务怎样算完成，也要检查失败退出时有没有清理。

## 7. 多个时间点的对比 {#多个时间点的对比}

一份转储能解释持有关系，但要说明增长，需要多个时间点的数据。建立趋势时，可以组合下面几类信息：

- 周期性的类直方图：比较各类型的数量和浅大小。它每次都要遍历堆，采集频率要考虑这个成本。
- JFR 的 Old Object Sample 和堆统计：找长期存活的样本和增长较快的类型。
- GC 日志里回收后的存活占用：判断实际保留量是否在上升。
- 缓存条目数、队列长度和业务键数量：判断增长是否符合业务预期。

先用这些数据缩小增长发生的时段，再挑有代表性的时刻采集完整转储。Old Object Sample 只是采样线索，会有遗漏，最终还要结合完整的堆分析。比较不同时间点时，采集选项要一致，负载和所处的 GC 阶段也要可比，避免把采集范围或负载差异当成泄漏。

## 8. 修复方式 {#修复方式}

找到持有者之后，修复的关键是明确由谁负责结束对象的生命周期。可以用下面几个问题检查代码：

- 谁创建对象，谁负责删除引用或关闭资源？
- 数量、总字节数和存活时间，分别最多允许到多少？
- 消费者变慢时，生产者怎样限速、背压或丢弃请求？**背压**指把消费能力不足反馈给生产方，让它放慢。
- 缓存键是否有界，过期条目是否真的被删除了？
- 任务取消、超时和应用停止时，清理是否都会执行？

据此补上缓存容量、队列上限、监听器注销这类规则。临时调用一次 `clear()` 能让占用降下来，但只要生产者还在持续放入对象，增长很快会再出现。

修复之后，在同等负载下运行足够长的时间，确认 GC 后的存活占用和对象数量都稳定了。同时检查缓存命中率、请求结果和取消行为，别让内存降下来了，业务却出了问题。

## 9. 常见问题 {#常见问题}

### 9.1 堆里最大的对象就是泄漏源吗？ {#大对象与泄漏来源}

不一定。最大的对象可能属于合理的工作集，比如有上限的缓存、类数据相关的数组或当前正在处理的大请求。判断泄漏要结合保留大小、增长趋势和业务上限，而真正需要修复的持有者，自身往往可以很小。

### 9.2 byte[] 很多时怎样定位来源？ {#字节数组的持有来源}

先按支配者和通向 GC Roots 的路径分组，再确认它们的业务用途。`byte[]` 可能来自下面几类对象：

- 字符串或类数据。
- 网络缓冲和压缩结果。
- 缓存值或请求上下文。

确定持有者后，再结合分配热点和业务键分析。这样既知道数组是谁创建的，也知道它为什么还没被释放。

### 9.3 线上可以连续采集多份转储吗？ {#连续转储的采集成本}

技术上可以，但每一份都会带来堆遍历、停顿和写盘的成本。应该先评估堆大小和磁盘余量，用监控、直方图或 JFR 确定增长时段。确实需要多份转储时，优先在摘流的实例或可控的副本上采集有代表性的快照。

## 10. 面试题 {#面试题}

### 10.1 堆使用率持续升高，怎样判断缓存增长还是内存泄漏 {#cache-growth-vs-leak}

**考察重点**：结合 GC 后的存活占用、持有链和业务上限，区分预期的缓存增长和无用对象滞留。

**相关内容**：[泄漏、容量不足与分配峰值](#泄漏容量不足与分配峰值)至[修复方式](#修复方式)。

<details>
<summary>参考回答</summary>

**看两点：稳定负载下 GC 后的存活占用趋势，以及被保留的对象是否还在业务有效期内。**

可以分三步检查：

1. 比较多次 GC 后的存活占用，同时对照缓存条目数、队列长度和业务键数量。
2. 用直方图找出增长的类型，必要时用堆转储的支配树和 GC Roots 路径找到持有者。
3. 核对缓存的上限、命中收益和过期策略。达到明确上限后稳定下来，属于预期工作集；失效的条目仍被静态 Map、`ThreadLocal` 或未完成任务强引用着，就是泄漏。

修复后用同等负载长时间运行，确认存活占用稳定，并验证业务结果没有受影响。

</details>

### 10.2 堆转储分析时为什么既要看 shallow size，也要看 retained size {#shallow-vs-retained}

**考察重点**：区分对象自身大小和它独占保留的对象图，并说明共享引用怎样影响保留大小。

**相关内容**：[Histogram 与 Dominator Tree](#histogram-与-dominator-tree)。

<details>
<summary>参考回答</summary>

**浅大小说明对象自身占多少空间，保留大小说明它失去可达性后能连带释放多少空间。**

一个缓存管理器自身很小，却可能独自保留大量值对象，只看浅大小就会漏掉这个关键持有者。

如果某个元素还有一条绕过管理器的根路径，它就不算在管理器的保留大小里。分析时先找保留大小突出的对象，再沿 GC Roots 路径确认持有来源。

</details>
