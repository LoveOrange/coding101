# 方法内联与去优化

**方法内联**是即时编译器（JIT）把被调用方法的代码直接放进调用点，让调用者和被调用者能当作一段代码一起优化。**去优化**是它的另一面：JIT 的很多优化建立在「运行时一直是这样」的假设上，假设失效时，JVM 把执行状态退回解释器，保证程序仍然按 Java 语义运行。

理解这两个机制，才能解释动态分派的代码为什么也能被充分优化，以及输入类型变化为什么可能带来性能波动。分析这些现象时，要看内联扩大了哪些优化机会、编译器依赖了什么假设，以及假设失效后怎样恢复执行。

## 1. 面试核心 {#core}

- 内联的主要价值是**扩大优化范围**，让常量传播、分支消除等优化跨过方法边界，省掉一次调用只是附带的收益。
- HotSpot 根据**调用点热度、方法字节码大小和内联深度**决定是否内联，用来控制机器码膨胀。[卡](#inlining-conditions)
- 虚方法调用点的接收者类型稳定时，JIT 可以根据类型画像生成**带类型检查的内联代码**。
- 去优化用编译时保存的元数据**重建解释器栈帧**，让程序继续按 Java 语义执行。[卡](#deoptimization)
- 去优化还能**重新创建被标量替换消除掉的对象**。[卡](#deopt-state-reconstruction)

## 2. 内联的收益 {#内联的收益}

内联让编译器同时看到调用前后的计算，从而利用调用方提供的信息优化被调用方法。下面的 `price` 调用 `discount` 时，折扣比例固定为 10：

```java
int price(int subtotal) {
    return discount(subtotal, 10);
}

int discount(int subtotal, int rate) {
    return subtotal - subtotal * rate / 100;
}
```

不内联时，编译 `discount` 只能把 `rate` 当成任意整数。把 `discount` 内联进 `price` 之后，编译器在调用点就能看到 `rate` 恒为 10，可以直接把这个常量代进计算，这叫**常量传播**。常量确定了，后面的计算往往还能继续化简。

调用者和被调用者能放在一起分析时，还能做更多跨方法的优化：

- 消除条件已经确定为假的分支，去掉永远不会执行的代码。
- 判断临时对象会不会被外部用到，从而整个省掉这次对象分配。
- 能证明下标安全时，去掉重复的数组边界检查。
- 把循环里始终不变的计算移到循环外面。
- 继续内联更下层的调用，让更多代码一起参与优化。

所以一个小 getter 内联后，独立的调用开销就没了。但具体收益取决于调用位置和最终生成的机器码，Java 语言本身也不保证任何方法一定会被内联。

## 3. 内联条件 {#内联的限制}

内联要在优化收益和代码体积之间取舍。同一个方法被内联到多个调用点，就会被复制多份，机器码随之变大。机器码越多，编译越耗时，指令缓存（CPU 用来暂存待执行指令的高速存储）的压力也越大，反而可能拖慢执行。

所以 HotSpot 会综合考虑下面几项：

- 调用点的热度：执行得越频繁，内联省下的重复成本越多。
- 方法字节码的大小：越大，内联后代码膨胀越多。
- 内联深度和递归深度：决定还能往下展开几层调用。
- 异常路径和历史画像：帮助判断哪些路径值得展开。
- 总代码预算：限制一次编译最多能膨胀到多大。

`static`、`private`、`final` 方法的调用目标是确定的，这对内联有帮助；但普通虚方法也能借助画像内联（见下一节）。所以，只为了内联就把公共 API 全改成 `final`，并没有充分的依据。反过来，调用目标再明确，方法也还得满足上面的预算条件。

## 4. 投机内联 {#投机内联}

**接收者**是方法调用作用的对象，比如 `obj.encode()` 里的 `obj`。虚方法实际执行哪个实现，取决于接收者的运行时类型。**类型画像**记录调用点实际遇到过的接收者类型，由解释器和较低编译层级收集。源码中的声明类型不足以确定调用目标时，JIT 可以参考这份记录。

假设 `Codec` 接口的 `encode` 方法接收 `Message`、返回编码后的字节数组，而某个调用点长期只遇到 `JsonCodec`。JIT 可以按这个类型生成带检查的内联代码：类型匹配就执行内联后的 `encode`，不匹配就走回退路径。

```text
if (receiver 的类型是 JsonCodec) {
    执行内联后的 encode
} else {
    执行通用调用或触发去优化
}
```

这里的检查叫**类型守卫**，它保证内联代码只会用在匹配的类型上。调用点只有少数几种稳定类型时，也可以为每种类型各生成一个内联分支；类型再多下去，检查分支和代码体积都会膨胀，这时保留普通的间接调用更合适。

投机的另一个依据是**类层级分析**：编译器根据当前已经加载的类，判断一个方法实际有哪几种实现。比如某个接口目前只有一个实现类，就可以直接内联它。之后如果新加载的类推翻了这个判断，JVM 就要让依赖它的编译代码失效。

## 5. 去优化 {#去优化}

投机优化让常见情况跑得更快，去优化负责在假设落空之后继续正确执行。编译器依赖的**运行时假设**通常有这几类：

- 调用点长期只有一种接收者类型。
- 某个分支几乎不会执行。
- 当前类层级里只有一个可用的方法实现。
- 某个值在当前优化依赖的条件下可以当作常量。

类型守卫失败、走进了被认为罕见的分支，或者编译依赖失效，都可能触发去优化。JVM 根据编译时保存的信息，恢复出解释器能继续执行的栈帧，然后在解释器里接着跑，同时继续收集类型和分支画像，之后再按策略编译出新的版本。

不过，出现新类型不一定就会去优化。如果编译代码保留了通用的回退路径，新类型直接走普通调用就行。新加载一个类，也只会影响依赖了被推翻假设的那部分代码。

去优化本身是正常机制，但频繁的去优化和重新编译会消耗 CPU，带来延迟波动。排查这类问题时，要把流量分布、类加载和编译事件放到同一条时间线上比较。

### 5.1 栈帧与对象恢复 {#栈帧与对象恢复}

去优化需要恢复每个方法的执行位置、局部变量和对象。经过内联的一段机器码，在 Java 语义上可能对应好几个方法。为此，HotSpot 在编译时记录字节码位置，以及恢复局部变量、锁状态等所需的信息。去优化时，JVM 结合这些元数据和当时的运行状态，展开出多个解释器栈帧，让每个方法都回到对应的位置。

**标量替换**是把对象的字段拆成独立的值参与计算，从而消除完整对象分配的优化。如果去优化后需要恢复这样一个对象，JVM 就重新分配它，并把可恢复的字段值填回去。程序随后从对应的字节码位置继续执行，所以已经完成的写入等副作用不会从头再做一遍。

标量替换的具体机制见 [逃逸分析与标量替换](./escape-analysis-scalar-replacement.mdx)。

## 6. uncommon trap {#uncommon-trap}

**uncommon trap** 是 JIT 处理「几乎不会执行的路径」的方式：编译时不为这部分逻辑生成完整的机器码，而是放一个陷阱，真的走到这里时就触发去优化，交给解释器执行。这样常见路径的代码更紧凑。

问题出在画像和真实情况不一致的时候。比如压测只用了正常输入，校验失败的分支看起来就很冷，被编译成了 uncommon trap。上线后突然来了大量无效输入，这个陷阱就会被频繁触发，带来恢复和重新编译的成本。HotSpot 会根据新的画像调整编译结果，但这段时间的性能会受影响。所以测试数据应该包含真实的类型分布和分支比例。

## 7. 编译日志 {#用日志确认}

一个方法到底有没有被内联，要看实际的编译结果。在诊断环境里，可以打开下面的日志：

```bash
java -XX:+UnlockDiagnosticVMOptions \
  -XX:+PrintCompilation -XX:+PrintInlining -jar app.jar
```

`PrintInlining` 输出每个调用点的内联结果和拒绝原因，`PrintCompilation` 显示编译层级和编译版本的状态。需要完整的编译日志时，可以再加上 `-XX:+LogCompilation`，配合 JITWatch 等工具阅读。JFR（Java Flight Recorder，JVM 的运行事件记录工具）里的编译、去优化和 Code Cache 事件，也能帮你建立时间线；Code Cache 是 JVM 保存编译代码的内存区域。

分析时可以按这个顺序确认：

1. 用性能采样确认目标调用点确实消耗了较多 CPU。
2. 看目标方法有没有编译到预期的层级。
3. 检查内联的拒绝原因，判断限制来自类型还是代码预算。
4. 把去优化事件和流量、类加载、输入变化对应起来。
5. 改完之后先用 JMH 检查局部收益，再用业务负载验证整体效果。

这些日志选项属于 HotSpot 的诊断接口，输出格式会随 JDK 版本变化，升级后要重新核对日志和工具的解析结果。

## 8. 常见问题 {#常见问题}

### 8.1 方法很小就一定会被内联吗？ {#小方法的内联条件}

不一定。小方法同样要满足热度、代码预算和调用类型等条件。方法体小只是让内联的膨胀代价更低，递归深度和编译层级仍然会影响决策。

### 8.2 方法被内联后，异常栈还准确吗？ {#内联后的逻辑栈}

准确。内联后，异常栈仍然反映 Java 语义上的方法调用关系。HotSpot 会保留被内联方法的调试信息，栈回溯时据此重建出逻辑上的调用栈。

### 8.3 线上出现去优化，说明代码有问题吗？ {#去优化与性能波动}

不一定。去优化是投机编译的正常恢复机制，保证假设失效后程序仍然正确。只有它频繁发生、并且和延迟波动对得上时，才需要检查输入画像是否稳定，以及代码为什么反复失效。

## 9. 面试题 {#面试题}

### 9.1 JVM 在什么情况下会进行方法内联 {#inlining-conditions}

**考察重点**：解释调用热度、代码预算和类型画像怎样影响内联，以及内联为什么能扩大优化范围。

**相关内容**：[内联条件](#内联的限制)。

<details>
<summary>参考回答</summary>

**HotSpot 综合调用点热度、方法大小、内联深度和代码预算，决定是否内联。**

静态、私有或 `final` 方法的调用目标是确定的，更容易内联。普通虚方法如果长期只遇到少数几种类型，也能根据类型画像生成带类型守卫的内联代码。

内联让编译器能同时分析调用前后的计算，从而做常量传播、分支消除和逃逸分析，省掉调用开销只是其中一项收益。实际有没有内联，可以用 `PrintInlining` 核对。

</details>

### 9.2 什么是去优化，为什么优化后的代码还要退回去 {#deoptimization}

**考察重点**：解释优化依赖哪些假设、哪些变化会让假设失效，以及 JVM 怎样恢复到解释执行。

**相关内容**：[去优化](#去优化)。

<details>
<summary>参考回答</summary>

**去优化是投机假设失效时，把编译代码的执行状态恢复成解释器状态的过程。**

JIT 的很多优化基于运行时观察到的假设，比如调用点只有一种类型、某个分支不会执行。一旦调用点出现了之前没见过的类型，或者新加载的类让类层级依赖失效，继续沿用原来的优化就会违反语义。所以 HotSpot 用编译时保存的元数据重建栈帧，从对应位置接着解释执行。

如果编译代码保留了通用回退路径，新类型也可以直接走回退调用，不必去优化。之后 JVM 会根据更新的画像重新编译。频繁的恢复和重编译会消耗 CPU，造成延迟波动。

</details>

### 9.3 方法已内联、对象已被消除，去优化怎样继续执行？ {#deopt-state-reconstruction}

**考察重点**：说明内联方法的栈帧和被消除的对象怎样重建，以及为什么不需要重做已经完成的副作用。

**相关内容**：[栈帧与对象恢复](#栈帧与对象恢复)。

<details>
<summary>参考回答</summary>

**HotSpot 根据编译时保存的元数据，重建解释器栈帧和被消除的对象。**

一个机器码栈帧里内联了多个方法时，要分别恢复每个方法的执行位置、局部变量和锁状态，展开成多个解释器栈帧。

如果后续执行需要一个被标量替换消除掉的对象，JVM 会重新分配它并回填字段。程序随后从对应的字节码位置继续，所以已经发生的业务副作用不会从方法开头重做。

</details>
