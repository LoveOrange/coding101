# 方法内联与去优化

方法内联把被调用方法的代码纳入调用点。去优化在投机假设失效时恢复解释执行。本文负责内联条件、假设检查和状态恢复。编译层级见 [分层编译](./interpreter-tiered-compilation.mdx)。

## 1. 面试核心 {#core}

- 内联扩大优化范围，使常量传播和分支消除跨越方法边界。
- HotSpot 按热度、方法大小和内联深度控制代码膨胀。[卡](#inlining-conditions)
- 虚方法可根据接收者类型画像进行投机内联。
- 去优化用编译元数据重建解释器栈帧，以继续执行 Java 语义。[卡](#deoptimization)
- 去优化能重新创建被标量替换消除的对象。[卡](#deopt-state-reconstruction)

## 2. 内联的收益 {#内联的收益}

```java
int price(int subtotal) {
    return discount(subtotal, 10);
}

int discount(int subtotal, int rate) {
    return subtotal - subtotal * rate / 100;
}
```

内联后，编译器在调用点能看到 `rate` 恒为 10。后续优化据此传播常量并简化计算。内联也为临时对象消除和循环优化提供机会。

getter 内联后可省去独立调用。实际收益由编译结果和调用位置决定。

## 3. 内联条件 {#内联的限制}

内联会增加调用者的机器码大小。代码膨胀会增加编译时间和指令缓存压力。因此 HotSpot 控制字节码大小、深度与总预算。

`static`、`private`、`final` 有助于确定调用目标。普通虚方法也能依赖画像内联。目标确定与满足内联预算是两个条件。

## 4. 投机内联 {#投机内联}

若接口调用点长期只接收 `JsonCodec`，编译器可生成类型检查。匹配时执行内联代码，否则进入回退路径。

```text
if (receiver 的类型是 JsonCodec) {
    执行内联后的 encode
} else {
    执行通用调用或触发去优化
}
```

这段伪代码表达类型守卫。少量稳定类型也可形成多个内联分支。类型增多后，间接调用能避免过多分支与代码膨胀。

类层级分析还可依赖当前已加载的类型。新类使依赖失效时，JVM 会处理受影响的编译代码。

## 5. 去优化 {#去优化}

去优化把已编译帧恢复为解释器可执行的状态。触发原因包括类型守卫失败、罕见分支和依赖失效。JVM 随后继续收集画像，并按策略重新编译。

某次新类型调用若已有通用回退路径，可直接回退。新类加载也只影响依赖该假设的代码。

频繁去优化和重编译会消耗 CPU。排查时应对齐流量分布、类加载和编译事件。

### 5.1 栈帧与对象恢复 {#栈帧与对象恢复}

一次内联机器码执行可包含多个逻辑方法。HotSpot 保留字节码位置、局部值和锁状态等元数据。去优化据此展开解释器栈帧，并恢复执行位置。

被标量替换消除的对象也可重新分配。JVM 将保留的字段值写回新对象。恢复从对应字节码位置继续，避免重做已完成的副作用。标量替换机制见 [逃逸分析与标量替换](./escape-analysis-scalar-replacement.mdx)。

## 6. uncommon trap {#uncommon-trap}

uncommon trap 把罕见路径交给解释器处理。JIT 因此可以缩小常见路径的机器码。

输入分布变化后，原罕见路径会变热。HotSpot 可据新画像重新编译。测试数据应包含真实类型和分支分布。

## 7. 编译日志 {#用日志确认}

```bash
java -XX:+UnlockDiagnosticVMOptions \
  -XX:+PrintCompilation -XX:+PrintInlining -jar app.jar
```

`PrintInlining` 输出内联结果和拒绝原因。`PrintCompilation` 显示方法编译与版本状态。JFR 的 Compilation 和 Deoptimization 事件可建立时间线。

先用 profile 确认目标调用点确为热点。再看内联拒绝原因与去优化频率。修改后通过 JMH 和业务负载验证收益。

## 8. 常见问题 {#常见问题}

### 8.1 小方法的内联条件 {#小方法的内联条件}

方法小只减少代码预算压力。热度、编译层级和调用类型分布仍参与决策。

### 8.2 内联后的逻辑栈 {#内联后的逻辑栈}

HotSpot 保留内联方法的调试信息。栈回溯工具可据此重建逻辑调用关系。

### 8.3 去优化与性能波动 {#去优化与性能波动}

去优化是投机编译的正常恢复机制。频繁发生且与延迟波动对应时，才需定位原因。

## 9. 面试题 {#面试题}

### 9.1 JVM 在什么情况下会进行方法内联 {#inlining-conditions}

-->

**出现公司**：京东数科

**考察重点**：热度、代码预算和类型画像。

**相关内容**：[内联条件](#内联的限制)。

<details>
<summary>参考回答</summary>

HotSpot 按调用热度、方法大小和内联深度决定内联。目标明确的调用更容易分析。虚方法也能根据类型画像，带守卫进行内联。内联扩大优化范围，进而支持常量传播等优化。具体结果可用 `PrintInlining` 核对。

</details>

### 9.2 什么是去优化，为什么优化后的代码还要退回去 {#deoptimization}

<!-- 面试来源：
- 京东数科：https://www.nowcoder.com/discuss/353156055045709824
-->

**出现公司**：京东数科

**考察重点**：投机假设、失效范围和解释器恢复。

**相关内容**：[去优化](#去优化)。

<details>
<summary>参考回答</summary>

去优化是在投机假设失效时恢复解释执行。HotSpot 用编译元数据重建逻辑栈帧与局部状态。类型守卫失败或类层级依赖失效可触发它。有通用回退路径时，也能直接执行回退调用。后续编译会使用更新后的画像。

</details>

### 9.3 方法已内联、对象已被消除，去优化怎样继续执行？ {#deopt-state-reconstruction}
