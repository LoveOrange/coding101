# 双亲委派模型

**双亲委派模型**是 `ClassLoader` 默认采用的查找规则：先检查已加载的类，再交给父加载器查找，父加载器找不到时，才由当前加载器自己查找。这样，多个加载器就能复用上层定义的平台类和公共接口。

理解这条规则，需要分清「谁发起查找」和「谁最终定义了类」。它们不一定是同一个加载器，而后者直接影响运行时类型身份：同名类为什么无法转换、插件怎样隔离依赖，都要从这里解释。

## 1. 面试核心 {#core}

- `loadClass` 默认按**已加载记录、父加载器、当前加载器**的顺序查找，分别对应 `findLoadedClass`、父加载器的 `loadClass` 和自己的 `findClass`。[卡](#delegation-flow)
- 父优先让多个子加载器**复用同一份平台类和公共 API**。共享接口由共同的父加载器定义，宿主与插件就能围绕同一种接口类型交互。
- JVM 用**二进制名称和定义加载器**共同标识类。名称和字节码相同、定义加载器不同，仍然是不同类型。[卡](#same-class-cast-failure)
- 发起加载器可以通过委派取得类，定义加载器才负责创建类型。`findLoadedClass` 查的是**发起加载记录**，`Class.getClassLoader()` 返回的是**定义加载器**。[卡](#initiating-defining-loader)
- JDK 17、21 使用启动、平台和应用加载器。加载器的父子关系通过**对象引用**建立，表示请求交给谁，不是实现类之间的继承关系。
- 插件可以优先加载私有依赖，但**平台类和宿主 API 仍需共享**。线程上下文加载器则让平台代码能找到应用提供的实现，改变的是查找入口。

## 2. 委派流程 {#委派流程}

`ClassLoader.loadClass` 默认先复用已有类型，找不到时才继续查找。它按下面的顺序处理请求：

1. `findLoadedClass` 查询当前加载器的发起加载记录。已有记录时，直接复用对应的类。
2. 尚未加载时，当前加载器委派给父加载器。父加载器为 `null` 时，尝试启动类加载器。
3. 父加载器抛出 `ClassNotFoundException` 后，当前加载器调用自己的 `findClass`。
4. 找到类后，如果调用参数 `resolve` 为 `true`，再调用 `resolveClass` 链接该类。

这里要区分三个方法的职责：`loadClass` 组织查找流程，`findClass` 负责当前加载器自己的查找，`defineClass` 把找到的字节转换为运行时类型。

自定义加载器如果只是换一个地方读取字节码，重写 `findClass` 就够了。例如，从插件目录读取字节，再调用 `defineClass` 创建类。`loadClass` 仍负责先向父加载器查找，也保留默认的并发加载同步逻辑。

覆盖 `loadClass` 会改变整个搜索流程。这时需要明确哪些包父优先、哪些包子优先，以及怎样协调并发加载。默认流程只在父加载器报告查找失败时转入本地查找。如果父加载阶段发生链接错误，就应传播错误，避免把版本不兼容误当成类不存在。

## 3. 委派的作用 {#委派的作用}

父优先让多个子加载器复用同一个平台类或公共 API。比如，应用请求 `java.lang.String` 时，默认委派会先取得启动类加载器定义的类型。

插件之间也需要这种共享。父加载器定义 `api.Service` 接口，子加载器分别定义插件实现。宿主和插件看到的是同一个接口类型，所以宿主能把插件实例转换为该接口，再调用它的方法。

子加载器仍可各自定义同名业务类，因为 JVM 判断类型身份时，同时看类的二进制名称和定义加载器。**二进制名称**是类在运行时使用的名称，例如 `com.example.User`。两个加载器分别定义这个类时，即使读到的字节相同，也会得到两个不同类型。

因此，插件的私有实现可以分别加载，共享 API 则应由宿主和插件共同可见的加载器定义。仅仅把同一份接口 JAR 分别放进两个插件，并不能保证它们共享同一种类型。

### 3.1 发起加载器与定义加载器 {#发起加载器与定义加载器}

**发起加载器**是 JVM 借助它发起某个类的加载请求、并记录了这次加载关系的加载器。它可以自己定义类，也可以委派其他加载器取得类。**定义加载器**则是实际把字节码转换成这个运行时类型的加载器。前者描述请求经过谁，后者决定类型由谁创建。

假设 JVM 通过子加载器请求 `api.Service`，最后由父加载器定义该类。JVM 会把子加载器记录为这个类的发起加载器，父加载器则是定义加载器。调用 `Service.class.getClassLoader()`，得到的是父加载器。

`findLoadedClass` 查询 JVM 记录的发起加载关系，所以也能返回经委派取得的类。不过，只有 JVM 自己经这个加载器发起的加载才会留下记录，比如解析子加载器所定义类里的符号引用。Java 代码直接调用 `child.loadClass("api.Service")`、由父加载器完成定义后，HotSpot 不会记录这次关系，`child.findLoadedClass("api.Service")` 仍然返回 `null`。判断类型身份时则要看定义加载器，不能只看请求从哪个加载器进入。

## 4. 内置类加载器 {#内置类加载器}

JDK 17、21 的内置加载器分为三类。它们分担平台类与应用类的加载工作：

| 加载器 | 职责 |
| --- | --- |
| Bootstrap | 加载核心平台类，Java API 中以 `null` 表示 |
| Platform | 加载其他平台模块，JDK 9 起替代扩展加载器 |
| Application/System | 加载应用类路径、模块路径等内容 |

默认应用加载器以平台加载器为父加载器。JDK 9 引入模块系统后，加载类还要考虑类属于哪个模块，以及模块之间是否允许访问。因此，内置加载器在模块场景下也会根据模块归属跨层委派。

应用服务器、构建工具和插件系统可以增加自定义加载器，形成更复杂的加载器关系。

双亲委派是 `ClassLoader` 的默认协议。JVM 规范允许自定义加载策略。

## 5. 父加载器与类继承 {#父加载器与类继承}

加载器的父子关系由对象引用建立。`getParent()` 返回父加载器对象，当前加载器通过这个引用把请求交给它。这里的「父」表示委派给谁，与加载器实现类 `extends` 哪个类无关。

“双亲”是传统名称，一条默认委派链只有一个直接父节点。

## 6. 改变委派顺序的场景 {#改变委派顺序的场景}

**子优先加载**（child-first）是在检查已有加载记录后，先查自己的类，再按规则委派父加载器。它可以让不同应用或插件使用各自版本的私有依赖。还有些需求改变的是发起查找的加载器，或用新加载器定义新版类，需要分别看待：

- 应用服务器让不同应用使用各自版本的业务依赖。
- 插件系统让插件优先使用私有的第三方库。
- SPI（服务提供者机制）由平台代码发起，通过线程上下文加载器发现应用提供的实现。
- 热部署用新加载器定义新版业务类，并为旧加载器卸载创造条件。

改变顺序时，要保留平台类和宿主接口的共享关系。跨加载器调用涉及的日志门面、用于传递数据的类型，也要确定由谁统一定义。否则，两边即使用着同名的类，也可能无法转换，或各自维护一份静态状态。热部署还要解除线程和静态注册表对旧加载器的引用，否则旧版本无法释放。

SPI 的发现流程见 [类加载器](./classloaders-spi-isolation.mdx#线程上下文类加载器)。该文也介绍热部署时的隔离与卸载条件。

## 7. 加载结果观察 {#观察实际加载结果}

排查同名类冲突时，需要同时确认类从哪里读取、最终由谁定义。以下命令分别提供类加载日志、加载器关系与统计信息：

```bash
java -Xlog:class+load=info -jar app.jar
jcmd <pid> VM.classloaders
jcmd <pid> VM.classloader_stats
```

统一日志可以显示类的来源。下面两行分别查看 `value` 的实际类型和 `Service` 接口由谁定义：

```java
System.out.println(value.getClass().getClassLoader());
System.out.println(Service.class.getClassLoader());
```

插件实现类和共享接口可以由不同加载器定义，所以这两行输出不同，本身不代表类型冲突。要排查同名类型冲突，应进一步比较两份同名类或接口的定义加载器。

JAR 路径说明字节从哪里来，定义加载器参与决定它是什么类型。一个加载器可以从多个 JAR 查找类，同一个 JAR 也可以被多个加载器分别读取。因此，文件路径相同并不保证得到的是同一个类型。

## 8. 常见问题 {#常见问题}

### 8.1 自己定义 java.lang.String，能替换 JDK 的 String 吗？ {#平台类的定义保护}

普通应用加载器无法这样替换。默认委派会先取得启动类加载器定义的 `String`，当前加载器直接复用它。即使改变委派顺序，JDK 21 的 `defineClass` 也对 `java.*` 包有保护：只有平台加载器及其祖先可以定义这些类，其他加载器会被拒绝。

### 8.2 双亲委派能解决依赖版本冲突吗？ {#依赖冲突与委派范围}

双亲委派只确定搜索顺序，依赖版本仍需匹配。旧版本的类先被找到后，代码若调用新版本才有的方法，仍会链接失败。不同子加载器重复定义共享类型，或资源文件的查找顺序与预期不同，也会引起冲突。

### 8.3 插件怎样隔离依赖，又共享宿主接口？ {#选择性子优先}

child-first 可以只应用于插件私有包，平台类与共享接口继续父优先。这样，插件能使用自己的依赖版本，宿主仍能通过同一份公共接口调用插件。

## 9. 面试题 {#面试题}

### 9.1 双亲委派的加载流程和作用是什么 {#delegation-flow}

**考察重点**：解释已加载检查、父委派与本地查找的顺序，以及它怎样让多个加载器共享平台类和公共 API。

**相关内容**：[委派流程](#委派流程)。

<details>
<summary>参考回答</summary>

**双亲委派先检查已加载记录，再委派父加载器，父加载器找不到时才由当前加载器查找；这样可以优先共享上层定义的平台类和公共接口。**

默认实现依次使用 `findLoadedClass`、父加载器的 `loadClass` 和当前加载器的 `findClass`。父加载器报告 `ClassNotFoundException` 后，才进入当前加载器的查找。

例如，宿主和插件复用父加载器定义的 `api.Service`，看到的就是同一种接口类型，宿主可以通过它调用插件实现。

插件或容器可以调整私有依赖的查找顺序，但平台包和宿主 API 仍应共享。隔离的子加载器也仍可分别定义同名业务类。

</details>

### 9.2 为什么同名同字节码的两个类仍可能无法强制转换 {#same-class-cast-failure}

**考察重点**：说明二进制名称和定义加载器怎样共同确定类型，并解释插件接口为什么需要共享。

**相关内容**：[委派的作用](#委派的作用)。

<details>
<summary>参考回答</summary>

**因为类的运行时身份同时包含二进制名称和定义加载器。**

两个加载器分别定义 `com.example.User`，即使字节码完全相同，也会得到两个不同类型，两份类的实例无法互相强制转换。

插件场景应让公共接口由共同的父加载器定义，只隔离实现和私有依赖。这样宿主才能把插件实例转换为共享接口并调用它。

</details>

### 9.3 findLoadedClass 返回的类一定由当前加载器定义吗？ {#initiating-defining-loader}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：区分发起加载记录与类型定义，说明为什么参与加载的加载器与定义加载器可以不同。

**相关内容**：[发起加载器与定义加载器](#发起加载器与定义加载器)。

<details>
<summary>参考回答</summary>

**不一定，它查询的是 JVM 记录的发起加载关系。**

当前加载器可以通过委派取得一个由父加载器定义的类。如果这次加载由 JVM 经当前加载器发起，JVM 会记下发起关系，`findLoadedClass` 也能返回这个类；Java 代码直接调用 `loadClass` 委派成功，则不会留下这条记录。

`Class.getClassLoader()` 返回的才是定义加载器。判断运行时类型身份，应把定义加载器和类的二进制名称一起比较。

</details>
