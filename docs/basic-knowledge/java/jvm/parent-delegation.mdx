# 双亲委派模型

双亲委派规定类加载请求的默认查找顺序。本文负责委派流程、内置加载器和运行时类型身份。SPI 与插件实践见 [类加载器](./classloaders-spi-isolation.mdx)。加载后的链接与初始化见 [类加载](./class-loading-stages.mdx)。

## 1. 面试核心 {#core}

- `ClassLoader.loadClass` 默认先查已加载记录，再委派父加载器。[卡](#delegation-flow)
- 父加载器查找失败后，默认流程调用当前加载器的 `findClass`。
- 类的运行时身份由二进制名称和定义加载器共同确定。[卡](#same-class-cast-failure)
- 发起加载器能通过委派取得类，定义加载器负责创建该运行时类型。[卡](#initiating-defining-loader)
- JDK 9 起，内置加载器分为启动、平台和应用加载器。

## 2. 委派流程 {#委派流程}

`ClassLoader.loadClass` 的默认流程如下：

1. `findLoadedClass` 查询当前加载器的发起加载记录。
2. 当前加载器委派给父加载器。父为 `null` 时，尝试启动类加载器。
3. 父加载器抛出 `ClassNotFoundException` 后，调用当前 `findClass`。
4. `resolve` 为 `true` 时，调用 `resolveClass`。

自定义字节码来源可重写 `findClass`。它读取字节后调用 `defineClass` 创建类型。这样能保留默认委派和加载同步逻辑。

覆盖 `loadClass` 则需自行维护查找协议。父加载阶段的链接错误应按错误处理。默认流程只对查找失败转入本地查找。

## 3. 委派的作用 {#委派的作用}

父优先让子加载器复用平台类与公共 API。多个插件共同实现父加载器定义的接口，宿主即可按同一接口调用。

隔离的子加载器仍可各自定义同名业务类。因此共享 API 需要放在共同可见的加载器中。

### 3.1 发起加载器与定义加载器 {#发起加载器与定义加载器}

发起加载器参与某个类型的加载请求。定义加载器将字节表示创建为运行时类型。

假设子加载器请求 `api.Service`，父加载器定义该类。子加载器可被记录为发起加载器，父加载器是定义加载器。`Service.class.getClassLoader()` 返回定义加载器。

`findLoadedClass` 查询的是发起加载记录。因此它也能返回经委派取得的类。判断类型身份时，应使用定义加载器。

## 4. 内置类加载器 {#内置类加载器}

| 加载器 | 职责 |
| --- | --- |
| Bootstrap | 加载核心平台类，Java API 中以 `null` 表示 |
| Platform | 加载其他平台模块，JDK 9 起替代扩展加载器 |
| Application/System | 加载应用类路径、模块路径等内容 |

默认应用加载器以平台加载器为父加载器。模块加载还涉及模块归属与可读关系。内置加载器在模块场景下也有跨层委派机制。

双亲委派是 `ClassLoader` 的默认协议。JVM 规范允许自定义加载策略。

## 5. 父加载器与类继承 {#父加载器与类继承}

`getParent()` 表达委派关系。子加载器通过对象引用调用父加载器。这种关系由组合建立，与加载器实现类的继承关系分开。

“双亲”是传统名称，一条默认委派链只有一个直接父节点。

## 6. 改变委派顺序的场景 {#改变委派顺序的场景}

child-first 可让应用或插件优先使用私有依赖。平台类和宿主接口仍需保持共享边界。否则同名接口也会成为不同类型。

SPI 用线程上下文加载器发现应用提供者，见 [类加载器](./classloaders-spi-isolation.mdx#线程上下文类加载器)。热部署的隔离与卸载也由该文负责。

## 7. 加载结果观察 {#观察实际加载结果}

```bash
java -Xlog:class+load=info -jar app.jar
jcmd <pid> VM.classloaders
jcmd <pid> VM.classloader_stats
```

JDK 9 起可用统一日志观察类来源。定位类型冲突时，也可比较定义加载器：

```java
System.out.println(value.getClass().getClassLoader());
System.out.println(Service.class.getClassLoader());
```

JAR 路径说明字节来源，定义加载器说明类型身份。同一个 JAR 可由多个加载器分别读取。

## 8. 常见问题 {#常见问题}

### 8.1 平台类的定义保护 {#平台类的定义保护}

默认委派会先返回平台的 `String`。JDK 26 的 `defineClass` 还保护 `java.*` 包。平台加载器及其祖先之外的加载器定义时会被拒绝。

### 8.2 依赖冲突与委派范围 {#依赖冲突与委派范围}

委派确定搜索顺序，依赖版本仍需匹配。某个旧版本先被找到后，调用新方法仍会链接失败。

### 8.3 选择性子优先 {#选择性子优先}

child-first 可只覆盖插件私有包。共享接口继续父优先，能让隔离实现与宿主交互。

默认流程先查 `findLoadedClass`，再委派父加载器。父查找失败后，当前加载器执行 `findClass`。该顺序复用上层平台类和公共接口。自定义加载器可调整协议，但需要保留共享类型边界。

</details>

### 9.2 为什么同名同字节码的两个类仍可能无法强制转换 {#same-class-cast-failure}

<!-- 面试来源：
- 字节跳动：https://www.nowcoder.com/discuss/353158260289118208
-->

**出现公司**：字节跳动

**考察重点**：二进制名称和定义加载器。

**相关内容**：[委派的作用](#委派的作用)。

<details>
<summary>参考回答</summary>

定义加载器不同，同名同字节码的类仍是不同类型。两份类的实例无法仅凭名称互相转换。插件应共享父加载器定义的接口，再隔离实现与私有依赖。

</details>
