# Java 直接内存

Java 直接内存用于在堆外保存 I/O 缓冲内容。本文负责直接缓冲区、文件映射与本地内存诊断。堆内持有关系见[堆转储](./heap-dumps-memory-leaks.mdx)。

## 1. 面试核心 {#core}

- `ByteBuffer.allocateDirect` 在堆外分配内容，在堆内保留管理对象。[卡](#direct-memory-usage)
- `-XX:MaxDirectMemorySize` 限制 NIO 直接缓冲区容量。[卡](#direct-limit-scope)
- 直接缓冲区的管理对象不可达后，清理机制释放底层内存。
- NMT 的 baseline 与 diff 用于比较 HotSpot 内存类别。[卡](#native-memory-growth)

## 2. 直接缓冲区 {#直接缓冲区}

HotSpot 将直接缓冲区内容分配在 Java 堆外：

```java
ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024);
```

Java 堆上仍有 ByteBuffer 管理对象。原生 I/O 可直接使用其内容，减少堆与本地缓冲区复制。直接内存不等于所有 I/O 路径都实现零拷贝。

这类缓冲区适合反复参与 I/O 的大块数据。分配和清理需要额外成本，应评估复用策略。池化后，实际释放还取决于池的生命周期。

普通直接缓冲区在管理对象不可达后由清理机制释放。GC 影响清理触发时机，因此释放可晚于业务使用结束。

### 2.1 直接内存上限与池统计 {#直接内存上限与池统计}

在 HotSpot JDK 21 中，`MaxDirectMemorySize` 限制容量总和。未显式设置时，上限取 `Runtime.maxMemory()`。容量计数与实际 native 分配字节数可以不同。

该参数并非整个进程堆外内存的总上限。JNI 分配和文件映射有各自生命周期。应分别为它们留出进程预算。

`BufferPoolMXBean` 提供 direct 与 mapped 池统计：

```java
for (BufferPoolMXBean pool :
        ManagementFactory.getPlatformMXBeans(BufferPoolMXBean.class)) {
    System.out.printf("%s count=%d capacity=%d used=%d%n",
        pool.getName(), pool.getCount(),
        pool.getTotalCapacity(), pool.getMemoryUsed());
}
```

容量表示缓冲区可容纳的字节总数。used 还受对齐与分配器影响。`slice()` 和 `duplicate()` 共享底层内容。长期保留小视图也会延长整块区域的生命周期。

## 3. 直接缓冲区的生命周期 {#ffm-api}

Java 17、21 的 `ByteBuffer` 没有公开的释放方法。HotSpot 用清理机制释放不可达缓冲区的本地内存。释放时机受 GC 和清理进度影响。

共享视图会持有底层缓冲区。归还缓冲池后，池仍可保留它供后续复用。业务使用结束与本地内存释放需要分别判断。

## 4. 文件映射 {#文件映射}

文件映射将文件区域关联到虚拟地址。页面由操作系统按需调入，脏页按映射规则回写。映射长度与实际驻留内存需要分别观察。

Java 17、21 使用 `MappedByteBuffer` 访问映射：

```java
try (FileChannel channel = FileChannel.open(path, READ)) {
    MappedByteBuffer mapped = channel.map(READ_ONLY, 0, channel.size());
    // 读取 mapped，单段大小最多为 Integer.MAX_VALUE 字节。
}
```

映射的生命周期依赖可达性。关闭 FileChannel 本身不会立即解除映射。

## 5. HotSpot 本地内存的来源 {#hotspot-本地内存的来源}

进程内存还包括类元数据、线程栈和 Code Cache。GC 的卡表、记忆集与标记位图也需要内存。JNI 库可通过自己的分配器申请区域。

`-Xmx` 只限制 Java 堆。线程增长、动态类生成或 native 泄漏仍可耗尽容器。

## 6. Native Memory Tracking {#native-memory-tracking}

NMT 必须在启动时开启：

```bash
java -XX:NativeMemoryTracking=summary -jar app.jar
```

建立基线后比较增长：

```bash
jcmd <pid> VM.native_memory baseline
jcmd <pid> VM.native_memory summary.diff
```

NMT 按 Class、Thread、Code、GC 等类别记录 HotSpot 分配。`detail` 还提供调用点信息。启动未开启时，无法用 jcmd 补开历史跟踪。

reserved 是保留的虚拟地址区间。committed 是已承诺可用的内存，两者均不同于 RSS。RSS 还受实际驻留页面与共享映射影响。

NMT 覆盖范围之外的 native 分配需由系统工具补充。可对照 `/proc/<pid>/smaps`、`pmap` 与 native profiler。

## 7. Direct buffer OOM {#direct-buffer-oom}

容量计数达到上限后，分配会等待清理并尝试重试。HotSpot JDK 21 重试失败时抛出直接缓冲区 OOM。

先比较 direct 池容量与 `MaxDirectMemorySize`。再检查无界池、排队请求和未完成 I/O。若视图长期存活，还需检查它持有的原始区域。

上限充足时，native 分配仍会受进程与系统资源约束。扩大上限只适合已确认的容量不足。引用泄漏需修复持有链。

## 8. 容器内存预算 {#容器内存预算}

进程预算需要包含堆与全部非堆区域：

```text
进程峰值 ≈ 堆 + 类元数据 + Code Cache + GC 结构
         + 线程栈 + direct / JNI
         + 映射与动态库 + 余量
```

应按稳定负载与故障峰值测量。堆接近容器上限时，非堆正常增长也会触发 OOM Kill。操作系统终止进程时，JVM 可来不及写出 Java OOM。

## 9. 常见问题 {#常见问题}

### 9.1 堆外区域的释放方式 {#堆外区域的释放方式}

普通直接缓冲区依赖管理对象的可达性清理。native 库按自身 API 管理资源。

### 9.2 reserved 与泄漏 {#reserved-与泄漏}

大 reserved 表示保留了较多虚拟地址。判断泄漏需看同负载下的增长趋势与持有原因。还需分开观察 committed 和 RSS。

### 9.3 堆转储的证据范围 {#堆转储的证据范围}

堆转储能显示缓冲区包装对象与持有链。堆外内容和全部本地分配需由 NMT 与系统工具补充。
