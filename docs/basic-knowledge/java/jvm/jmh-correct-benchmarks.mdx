# JMH

JMH 用于构建 Java 微基准。本文负责测量边界、状态、预热和结果消费。JIT 的执行层级见 [分层编译](./interpreter-tiered-compilation.mdx)。基准结果还需与业务负载对照。

## 1. 面试核心 {#core}

- JMH 用预热与独立 fork 控制编译状态和进程间隔离。[卡](#trustworthy-benchmark)
- 基准返回结果或使用 `Blackhole`，可防止结果无用导致的消除。
- 可变输入放在 `@State` 中，可降低常量折叠对测试的干扰。
- `Scope.Thread` 每线程独立，`Scope.Benchmark` 在测试线程间共享。
- 每个 fork 启动新的 JVM，隔离前次测试的画像和静态状态。[卡](#fork-jvm)

## 2. 测量模式 {#测量模式}

| 模式 | 测量对象 |
| --- | --- |
| `Throughput` | 单位时间操作数 |
| `AverageTime` | 每次操作平均耗时 |
| `SampleTime` | 采样得到的耗时分布 |
| `SingleShotTime` | 一次方法调用或指定批次的耗时 |

```java
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
public class ParserBenchmark {
    // 基准方法使用 @Benchmark 标记。
}
```

纳秒是输出单位，精度还受计时器与样本影响。报告应保留迭代、fork、误差与环境参数。

## 3. 死代码消除 {#死代码消除}

以下片段中的计算结果无人使用：

```java
@Benchmark
public void wrong() {
    Math.sqrt(123.0);
}
```

JIT 可删除没有可观察副作用的计算。正确做法是使用可变输入，并返回结果：

```java
@State(Scope.Thread)
public static class Input {
    public double value = 123.0;
}

@Benchmark
public double sqrt(Input input) {
    return Math.sqrt(input.value);
}
```

JMH 会消费返回值。多个结果可分别传给 `Blackhole.consume()`。副作用仍可被观察时，方法即使无返回值也会保留工作。日志与断言应放在测量路径之外。

## 4. 常量折叠与 State {#常量折叠与-state}

```java
@State(Scope.Thread)
public static class Input {
    @Param({"16", "256", "4096"})
    public int size;
    public byte[] data;

    @Setup(Level.Trial)
    public void setup() {
        data = new byte[size];
    }
}
```

`@Param` 让输入规模成为实验维度。`@State` 字段向基准提供运行时数据。若数据仍可静态推导，JIT 仍能简化计算。

| Setup 层级 | 执行时机 |
| --- | --- |
| `Trial` | 每次 trial 开始前，对各状态实例执行 |
| `Iteration` | 每轮预热和测量迭代前 |
| `Invocation` | 每次基准方法调用前 |

Invocation 需要逐次计时，会引入额外成本。它只适合足够长的调用，并需验证干扰。

### 4.1 可变输入的重置 {#可变输入的重置}

排序基准会修改原数组。若只在 Trial 创建随机数组，后续调用会处理有序数组。测试问题因此从随机排序变成有序输入排序。

可以每次复制原数组，再排序副本。此时测量包含复制成本，需在结果中说明。若用 Invocation 重置，应验证计时和缓存干扰。仅把准备过程移出计时区，仍会改变缓存状态。

## 5. 预热与 fork {#预热与-fork}

```java
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 8, time = 1)
@Fork(3)
```

该配置使用 5 轮预热和 8 轮测量，并启动 3 个 JVM。每轮设置的时间为 1 秒。预热轮次应根据稳态变化调整。

fork 隔离 JIT 画像、Code Cache 与静态状态。多个进程样本还能暴露进程间波动。

SingleShotTime 测的是基准调用，未包含 JVM 启动。测完整进程冷启动时，要用外部计时包住进程。

## 6. 基准方法中的循环 {#基准方法中的循环}

手写大循环会改变优化条件。JIT 可展开、向量化或合并循环中的计算。除以循环次数得到的数值只对应该批处理程序。

JMH 自身会重复调用基准方法。业务确有批处理时，可以保留批内循环。`@OperationsPerInvocation` 用于按逻辑操作数归一化。它只改变结果换算，无法撤销循环优化。

## 7. State 的 Scope {#state-的-scope}

`Scope.Thread` 为每个工作线程创建独立状态。`Scope.Benchmark` 让参与测试的线程共享状态。`Scope.Group` 让同组线程共享状态。

测共享容器竞争时，应采用 Benchmark 或 Group。误用 Thread 会让各线程操作各自的容器。线程数也应显式配置，例如 `@Threads(4)`。仅声明共享状态不会自动形成并发。

## 8. Profiler 与测量证据 {#用-profiler-解释差异}

```bash
java -jar target/benchmarks.jar ParserBenchmark -prof gc
```

`gc.alloc.rate.norm` 表示每次操作的分配字节数。CPU 或汇编分析可解释内联和循环优化。额外 profiler 的可用性取决于安装环境。

同时检查误差、CPU 频率、后台负载和容器限流。均值变小只说明观察到差异，原因还需证据。

## 9. 微基准与系统压测 {#微基准与系统压测}

微基准适合拆解解析、集合与序列化成本。真实服务还包含网络、数据库与排队。

局部优化应先确认输入分布和热点占比。再用服务负载检查吞吐、长尾与资源占用。局部节省的时间决定了整体收益上限。

## 10. 常见问题 {#常见问题}

### 10.1 手写计时循环的干扰 {#手写计时循环的干扰}

预热、结果消除和循环优化都会改变被测工作。JMH 提供实验框架，输入和工作量仍需正确设计。

### 10.2 结果消费方式 {#结果消费方式}

单个结果可直接返回，多个结果可使用 Blackhole。两种方式都应保留被测计算的可观察结果。

### 10.3 微基准结果的应用范围 {#微基准结果的应用范围}

基准结论对应指定 JDK、硬件、输入与线程数。生产改动还需验证正确性和业务性能。

<details>
<summary>参考回答</summary>

先明确吞吐、稳态耗时或首次调用耗时。使用 JMH 配置预热、测量轮次与多个 fork。输入放入合适 Scope 的 State，并覆盖真实规模。结果返回或交给 Blackhole。可变输入在每次操作前恢复所需状态。最后结合误差与 profiler 解释结果。

</details>

### 11.2 为什么微基准需要 fork 新的 JVM {#fork-jvm}

<!-- 面试来源：
- 京东数科：https://www.nowcoder.com/discuss/353156055045709824
-->

**出现公司**：京东数科

**考察重点**：进程隔离与环境噪声。

**相关内容**：[预热与 fork](#预热与-fork)。

<details>
<summary>参考回答</summary>

fork 用新 JVM 隔离此前基准的编译画像和静态状态。同进程复用会让结果依赖测试顺序。多个 fork 提供独立进程样本。CPU 频率和后台任务仍需控制，测试环境也需记录。

</details>

### 11.3 排序基准只在 Trial 生成随机数组，会测到什么？ {#mutable-benchmark-input}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：输入状态变化与准备成本。

**相关内容**：[可变输入的重置](#可变输入的重置)。

<details>
<summary>参考回答</summary>

首次调用排序随机数组，后续调用处理已排序数组。若目标是随机输入排序，就需每次恢复随机数据。复制后排序会把复制成本计入结果。Invocation 重置会增加计时与缓存干扰，需要验证。

</details>
