# GC Roots

GC Roots 是垃圾回收遍历对象图的起点。本文负责可达性、引用强度与资源清理边界。引用链诊断方法见[堆转储](./heap-dumps-memory-leaks.mdx)。

## 1. 面试核心 {#core}

- HotSpot 从 GC Roots 遍历对象图，孤立引用环可回收。[卡](#reachability)
- 业务无用对象仍被强可达链持有时，会形成内存泄漏。
- GC 发现对象弱可达时，会清除相应弱引用。[卡](#reference-types)
- WeakHashMap 的 value 是强引用，反向持有 key 会阻止回收。[卡](#weak-map-value-cycle)
- 虚引用入队表示进入清理通知阶段，并非内存已释放。

## 2. 引用计数与循环引用 {#引用计数与循环引用}

两个对象可以互相引用：

```java
final class Node {
    Node next;
}

Node left = new Node();
Node right = new Node();
left.next = right;
right.next = left;

left = null;
right = null;
```

清除外部引用后，整个环从 GC Roots 不可达。可达性分析因此能将它们一并回收。单纯引用计数则仍会看到环内的非零计数。

## 3. GC Roots 的来源 {#gc-roots-的来源}

根来源包括活动线程的引用、JNI 引用与 JVM 内部引用。线程栈扫描需使用运行时的有效引用信息。局部变量的源码作用域与实际存活期可以不同。

可达类的静态字段也是常见持有路径。静态字段属于该类的对象图。类加载器整体失去外部根后，静态字段不会使其永久存活。

实际分析应找到对象到根的具体路径。根的显示名称与分类会随 JVM 和分析工具变化。

## 4. 可达对象与内存泄漏 {#可达对象与内存泄漏}

无界静态 Map 会长期持有业务对象：

```java
private static final Map<String, Session> SESSIONS = new HashMap<>();
```

只要该类仍可达，Map 中的 Session 就被保留。GC 仅处理可达性，业务过期需由应用删除。

队列、监听器和 ThreadLocal 也能形成持有链。业务已无用途的对象持续被保留，就构成泄漏。修复应落在持有者的生命周期。

## 5. 强、软、弱、虚引用 {#强软弱虚引用}

### 5.1 强引用 {#强引用}

普通字段和局部引用形成强引用。只有从根出发的强可达关系才会保留对象。孤立对象内部的强引用环仍可回收。

### 5.2 软引用 {#软引用}

GC 可按内存压力与实现策略清除软引用。在抛出 OOM 前，软可达对象的软引用会被清除。它仍无法替代业务缓存的容量与过期策略。

### 5.3 弱引用 {#弱引用}

GC 确定对象弱可达时，会清除相应弱引用。已注册的引用会在同时或稍后入队。触发时机取决于该对象被哪次收集发现。

### 5.4 虚引用 {#虚引用}

`PhantomReference.get()` 始终返回 `null`。对象达到虚可达状态后，GC 会清除对应虚引用。引用对象在同时或稍后入队，供程序处理清理动作。

入队通知并不证明对象内存已经释放。程序也无法通过虚引用取得原对象。

### 5.5 弱键与值的反向引用 {#弱键与值的反向引用}

`WeakHashMap` 使用弱键，但 value 被强引用。若 value 又强引用 key，就形成仍可达的路径：

```text
可达的 WeakHashMap → value → key
```

此时 key 仍强可达，弱键清理条件不成立。value 也可经其他 value 间接持有 key。设计弱关联时，应检查整个对象图。

## 6. ReferenceQueue {#referencequeue}

引用队列用于接收已注册引用的处理通知：

```java
ReferenceQueue<ResourceOwner> queue = new ReferenceQueue<>();
PhantomReference<ResourceOwner> ref =
    new PhantomReference<>(owner, queue);
```

应用需保留 ref，以便识别后续通知。清理状态应独立保存，避免再次强引用 owner。队列消费者还需明确停止条件。

### 6.1 Cleaner 与显式关闭 {#cleaner-与显式关闭}

资源有明确作用域时，优先使用 try-with-resources。Cleaner 可作为遗漏关闭时的补充机制。它基于虚引用，执行时机由可达性与调度决定。

清理 Runnable 应只持有清理所需状态。若它捕获目标对象的 `this`，目标就会一直被持有。静态嵌套状态类可避免隐式捕获。

JDK 18 的 JEP 421 将 finalization 标记为待移除。新资源管理代码应使用显式关闭与必要的 Cleaner。

## 7. 类卸载 {#类卸载}

普通类的卸载要求定义加载器可被回收，见[类加载器](./classloaders-spi-isolation.mdx#类的卸载)。热部署排查应关注旧加载器到 GC Roots 的路径。

## 8. 堆转储中的引用链 {#在堆转储中查看引用链}

先用直方图定位数量与大小异常的类型。再用 Dominator Tree 找保留量大的对象。对具体实例查看 Path to GC Roots。

强持有链与软、弱、虚引用路径需分别判断。一个对象也可由多条路径持有。修复后，应确认同负载下的 live set 趋势。

## 9. 常见问题 {#常见问题}

### 9.1 循环引用与泄漏 {#循环引用与泄漏}

孤立引用环可回收。仍从 GC Roots 可达的环会继续保留。判断取决于外部持有关系。

### 9.2 软引用与 OOM {#软引用与-oom}

软引用只影响 referent 的保留策略。缓存索引、强引用和其他内存仍可耗尽资源。业务缓存应有明确容量与过期规则。

### 9.3 finalize 与资源释放 {#finalize-与资源释放}

finalize 的执行时机不确定，并会延长生命周期。JDK 18 起已弃用并计划移除。明确作用域的资源应显式关闭。

### 10.1 JVM 怎样判断一个对象可以回收 {#reachability}

**出现公司**：阿里巴巴、美团

**考察重点**：理解根遍历、孤立引用环与业务泄漏。

**相关内容**：[引用计数与循环引用](#引用计数与循环引用)至[可达对象与内存泄漏](#可达对象与内存泄漏)。

<details>
<summary>参考回答</summary>

HotSpot 从 GC Roots 遍历对象图。孤立且没有特殊引用处理要求的对象具备回收条件。对象之间只有内部循环引用时，整个环仍可回收。

业务过期但仍被强可达链持有的对象会继续存活。缓存、队列与监听器应及时解除无用引用。

</details>

### 10.2 强、软、弱、虚引用分别适合什么场景 {#reference-types}

<!-- 面试来源：
- 阿里巴巴：https://www.nowcoder.com/discuss/353157613372252160
-->

**出现公司**：阿里巴巴

**考察重点**：区分引用清除、队列通知与显式资源管理。

**相关内容**：[强、软、弱、虚引用](#强软弱虚引用)和[ReferenceQueue](#referencequeue)。

<details>
<summary>参考回答</summary>

强引用用于正常持有对象，软引用按内存策略清理。弱引用适合避免关联结构延长对象生命周期。虚引用配合队列用于清理通知，其 get 始终返回 null。

弱引用清除以 GC 发现弱可达为条件。虚引用入队也不表示物理内存已释放。文件和连接仍应按明确作用域关闭。

</details>

### 10.3 WeakHashMap 的 value 引用 key 时，key 还能自动回收吗？ {#weak-map-value-cycle}

**相关内容**：[弱键与值的反向引用](#弱键与值的反向引用)。

<details>
<summary>参考回答</summary>

只要 Map 可达且 value 强引用 key，key 就仍然强可达。路径为 Map 到 value，再到 key。弱键机制无法解除这条强引用路径。需要改变 value 的持有关系。

</details>
