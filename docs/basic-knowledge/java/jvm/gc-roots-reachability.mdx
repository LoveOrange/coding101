# GC Roots

**GC Roots** 是垃圾回收器遍历对象引用关系的起点。**可达性分析**就是从这些根出发，沿引用查找对象，判断哪些对象还需要保留。只要有一条从根出发的强引用链能找到对象，GC 就不会回收它；软、弱、虚引用则按各自的规则处理。

这套规则决定了两件和日常开发直接相关的事：两个对象互相引用，不会仅因此泄漏；一个早就没用的对象，只要仍被可达的静态 Map 强引用，就无法回收。理解引用链，才能解释对象为什么还活着，以及应该由谁解除引用。

## 1. 面试核心 {#core}

- HotSpot 从 GC Roots 出发遍历对象图，**根到不了的对象就能回收**，所以只有内部循环引用、没有外部路径的对象照样会被回收。[卡](#reachability)
- Java 里的内存泄漏，是业务上已经没用的对象**仍被一条从根出发的强引用链持有**。
- 对象只剩弱引用可达时，GC 会**清除指向它的弱引用**。[卡](#reference-types)
- `WeakHashMap` 可达、它强引用的 value 又强引用 key 时，**key 仍然强可达，不会被清理**。[卡](#weak-map-value-cycle)
- 虚引用入队是一个**清理通知**，程序可以据此做清理，但不能据此断定目标对象的内存已经释放。

## 2. 引用计数与循环引用 {#引用计数与循环引用}

判断一个对象能不能回收，看的是程序还能不能从根找到它，而不是它被引用了几次。**引用计数**是另一种思路：给每个对象记一个被引用的次数，次数归零就回收。它的问题出在互相引用上，看下面两个对象：

```java
final class Node {
    Node next;
}

Node left = new Node();
Node right = new Node();
left.next = right;
right.next = left;

left = null;
right = null;
```

把 `left` 和 `right` 设为 `null` 之后，程序已经没有任何办法再访问这两个 `Node`，但它们还互相引用着。按引用计数，每个对象的计数都是 1，永远回收不掉。按可达性分析，从 GC Roots 出发已经走不到它们，所以整个孤立的环可以一起回收。HotSpot 用的是后者。

## 3. GC Roots 的来源 {#gc-roots-的来源}

GC Roots 来自线程和 JVM 运行时需要保留的引用。排查时既要看根，也要看从根延伸出来的持有路径，例如：

- 活动线程栈帧里还在用的局部引用，以及线程执行需要的其他引用。
- 可达类的静态字段，业务对象可以通过它挂在类的对象图上。
- JNI（Java 和本地代码交互的接口）持有的局部引用和全局引用。
- JVM 自己运行需要的引用，比如线程正在同步使用的对象。

线程栈上的引用，GC 按运行时实际还在用的信息来扫描，而不是按源码里的作用域。JIT 优化后，一个局部变量在源码里还没出作用域，实际上可能已经不再被使用，也就不再把对象留住。

静态字段也不是永久的根。静态字段属于类，而类本身有生命周期：当一个类加载器连同它加载的类和对象整体都失去外部引用时，里面的静态引用也留不住这些对象。根的名称和分类在不同 JVM、不同分析工具里写法不一样，所以诊断时与其纠结根的类型，不如追踪具体的持有路径。

## 4. 可达对象与内存泄漏 {#可达对象与内存泄漏}

GC 只能判断对象是否可达，判断不了它在业务上还有没有用。比如下面这个静态 Map，如果不停往里放会话却从来不删：

```java
private static final Map<String, Session> SESSIONS = new HashMap<>();
```

只要这个类还可达，Map 里的每个 `Session` 都能沿着静态字段 `SESSIONS` 找到。会话哪怕早就过期，对 GC 来说依然可达，于是一直留在堆里，越积越多。GC 帮不了这个忙，应用必须自己删除失效的条目。

队列、监听器、`ThreadLocal` 和类加载器都能造成同样的持有链。它们的共同点是：持有者活得比业务对象该活的时间更长。修复时要先找到谁负责解除引用，再在删除、注销或任务结束的地方补上清理。

## 5. 强、软、弱、虚引用 {#强软弱虚引用}

引用的强度决定了对象还被引用着的时候，GC 能怎样处理它。普通代码用的都是强引用；`java.lang.ref` 包另外提供了软、弱、虚三种引用，对应不同的生命周期需求。从强到弱，GC 对对象的保护依次减弱。

### 5.1 强引用 {#强引用}

**强引用**就是普通的引用，字段和局部变量都是。从根出发、全程只经过强引用就能到达的对象叫强可达对象，即使内存紧张，GC 也不会回收它。前面那个孤立的 `Node` 环里也全是强引用，但根到不了这个环，所以它照样可以回收。

### 5.2 软引用 {#软引用}

**软引用**允许 GC 在内存紧张时清掉对象，适合放能重新创建的辅助数据。一个对象只能通过软引用这类路径到达时，GC 会根据内存压力和自己的策略决定要不要清除这条软引用；在抛出 OOM 之前，所有软可达对象的软引用都会被清除。

清理的时机完全由 JVM 决定，业务没法据此得到稳定的容量、过期时间或命中率。所以业务缓存不能只靠软引用，仍然要有明确的容量上限和过期策略。

### 5.3 弱引用 {#弱引用}

**弱引用**用来维护一种关联，同时不让这份关联本身延长对象的寿命。一个对象失去了所有强引用和软引用路径、只剩弱引用这类路径时，就是弱可达的。GC 一旦发现对象弱可达，就会清除指向它的弱引用。

如果弱引用注册了队列，引用对象会在被清除时或稍后进入队列。具体哪次 GC 发现它，取决于那次回收的范围，所以不能假设「下一次 GC 就一定清掉」。

### 5.4 虚引用 {#虚引用}

**虚引用**是用于跟踪对象回收状态、接收清理通知的一种引用，不能用来访问目标对象。目标对象变成虚可达后，GC 会清除对应的虚引用，引用对象同时或稍后进入队列。程序收到通知后，再处理单独保存的资源状态。

`PhantomReference.get()` 永远返回 `null`，所以程序没办法通过虚引用重新拿到或「复活」目标对象。入队只说明收到了清理通知，不代表目标对象的内存已经释放。

### 5.5 弱键与值的反向引用 {#弱键与值的反向引用}

`WeakHashMap` 的键是弱引用，适合这样一种关联：键在别处的所有者都消失后，Map 里的这一条也应该能被清理。但要注意，Map 对 value 是强引用。如果 value 又强引用了 key，就多出一条路径：

```text
可达的 WeakHashMap → value → key
```

这条路径上全是强引用，所以 key 仍然强可达，弱键的清理条件永远不成立，这个条目就一直留在 Map 里。value 也可能经过别的 value 间接引用到 key，所以只检查当前 value 的直接字段是不够的，设计弱关联时要检查整条持有链。

## 6. ReferenceQueue {#referencequeue}

**ReferenceQueue** 是接收引用处理通知的队列。GC 处理已注册的软、弱、虚引用后，可以把引用对象放进队列，程序再据此清理相关状态。队列里放的是引用对象本身，不是它指向的目标对象。下面把一个虚引用注册到队列：

```java
ReferenceQueue<ResourceOwner> queue = new ReferenceQueue<>();
PhantomReference<ResourceOwner> ref =
    new PhantomReference<>(owner, queue);
```

要用好这个通知，有三件事要注意：

- 应用要让 `ref` 本身保持可达，队列不会替应用保留尚未入队的引用对象。还要把 `ref` 和清理状态关联起来，取出它时才知道该清理什么。
- 清理状态要独立保存，比如只保留待释放资源的句柄。如果清理状态又强引用了 `owner`，`owner` 就永远到不了虚可达，通知也永远不会来。
- 消费队列的线程要有明确的停止条件，应用关闭时才能正常退出。

### 6.1 Cleaner 与显式关闭 {#cleaner-与显式关闭}

文件、连接这类需要及时释放的资源，首选实现 `AutoCloseable`，用 try-with-resources 显式关闭。`Cleaner` 基于虚引用实现，可以在调用方忘记关闭时兜底。它什么时候执行取决于可达性判断和线程调度，所以只能用来补充清理，不能指望它及时释放。

注册给 `Cleaner` 的清理任务（一个 `Runnable`）只应保存释放资源需要的状态。如果它捕获了目标对象的 `this`，`Cleaner` 持有任务，任务又持有目标对象，目标就永远不会变成虚可达，自动清理也就不会触发。常见写法是把清理状态放进静态嵌套类，静态嵌套类不会隐式捕获外部对象。

finalization 在 Java 17 已经是弃用状态，Java 21 进一步把它标记为待移除。新写的资源管理代码应该用显式关闭，必要时加上 `Cleaner`。

## 7. 类卸载 {#类卸载}

普通类能卸载的前提，是定义它的类加载器可以被回收。只是某个 `Class` 引用消失了，并不说明加载器已经失去所有外部引用。热部署之后，存放类元数据的 Metaspace 持续增长，就要去查旧类加载器到 GC Roots 的路径。

具体的卸载条件，以及线程、驱动注册这类常见持有来源，见[类加载器](./classloaders-spi-isolation.mdx#类的卸载)。

## 8. 堆转储中的引用链 {#在堆转储中查看引用链}

堆转储能把「这个对象怎么还在」变成一条能追踪的持有关系。分析具体实例时，可以按下面的顺序：

1. 用 Histogram（类直方图）找数量或自身大小异常的类型。
2. 用 Dominator Tree（支配树）找独自保留了大量内存的持有者。
3. 用 Path to GC Roots 追踪具体实例通向根的引用路径。
4. 区分强引用路径和软、弱、虚引用路径，判断哪些路径真的会把对象留住。
5. 把持有者对应回缓存、队列、线程或类加载器，检查它们的生命周期。

一个对象可能同时被多条路径持有，工具展示的最短路径只是其中一条，切断它不一定就够了。修复之后，还要在相同负载下比较 live set（GC 后仍存活的对象总量），确认保留量已经稳定下来。

## 9. 常见问题 {#常见问题}

### 9.1 两个对象循环引用会泄漏吗？ {#循环引用与泄漏}

不会因为循环引用本身泄漏。孤立的引用环可以回收；如果这个环还能从 GC Roots 到达，GC 就会继续保留它。只有对象在业务上已经没用、却仍被外部持有时，才算泄漏。

### 9.2 把缓存值改成软引用就能避免 OOM 吗？ {#软引用与-oom}

不能保证。软引用只影响它所指向的那个对象怎么保留，缓存的索引结构和其他强可达对象照样占着内存。业务缓存还是要控制容量、过期时间和并发加载量，并评估软引用被清掉后命中率会降到多少。

### 9.3 finalize 适合用来释放资源吗？ {#finalize-与资源释放}

不适合。`finalize` 什么时候执行没有保证，还会延长对象的生命周期，Java 21 已经把它标记为待移除。有明确作用域的资源应该显式关闭；需要兜底时，用独立保存资源状态的 `Cleaner`。

## 10. 面试题 {#面试题}

### 10.1 JVM 怎样判断一个对象可以回收 {#reachability}

**考察重点**：理解从根遍历的判断方式、孤立引用环和业务泄漏的区别。

**相关内容**：[引用计数与循环引用](#引用计数与循环引用)至[可达对象与内存泄漏](#可达对象与内存泄漏)。

<details>
<summary>参考回答</summary>

**HotSpot 用可达性分析：从 GC Roots 出发遍历对象图，根到不了的对象就可以回收。**

根包括线程栈上的引用、JNI 引用和 JVM 内部引用等。根无法到达、也没有特殊引用处理要求的对象可以回收，所以孤立的循环引用会被整体回收，这一点和引用计数不同。

反过来，业务上已经过期、但仍被强引用链持有的对象会一直存活。比如会话还留在静态缓存里，GC 就会保留它。这需要应用在缓存、队列或监听器用完对象时主动解除引用。

</details>

### 10.2 强、软、弱、虚引用分别适合什么场景 {#reference-types}

**考察重点**：区分引用被清除的条件、队列通知和显式资源管理。

**相关内容**：[强、软、弱、虚引用](#强软弱虚引用)和[ReferenceQueue](#referencequeue)。

<details>
<summary>参考回答</summary>

**强引用用于正常持有对象，软引用用于可以重新创建的数据，弱引用用于不延长寿命的关联，虚引用用于清理通知。**

四种引用的处理方式分别是：

- 强可达对象会一直保留，适合普通业务对象。
- 软引用由 GC 根据内存压力和自身策略清理，所以业务缓存仍要自己控制容量和过期。
- 弱引用在 GC 发现目标弱可达后就被清除，适合不希望关联结构单独延长目标寿命的场景。
- 虚引用配合 ReferenceQueue 发出清理通知，`get()` 永远返回 `null`，入队也不代表目标内存已经释放。

文件和连接需要及时释放，仍然应该用显式关闭或 try-with-resources 管理。

</details>

### 10.3 WeakHashMap 的 value 引用 key 时，key 还能自动回收吗？ {#weak-map-value-cycle}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：找出弱键之外的强引用路径，解释 value 反向持有 key 为什么会阻止清理。

**相关内容**：[弱键与值的反向引用](#弱键与值的反向引用)。

<details>
<summary>参考回答</summary>

**不能。只要 Map 可达、value 又强引用 key，这个 key 就不会按弱键机制被回收。**

Map 强引用 value，value 强引用 key，这就形成了一条绕过弱键的强引用路径，key 一直是强可达的。要让 key 能被清理，就得改掉 value 对 key 的强引用，包括经过其他对象的间接引用。

</details>

### 10.4 Cleaner 的清理任务为何应避免捕获 this？ {#cleaner-capture-owner}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释清理任务持有目标对象时为什么触发不了自动清理，并区分清理状态和目标对象。

**相关内容**：[Cleaner 与显式关闭](#cleaner-与显式关闭)。

<details>
<summary>参考回答</summary>

**清理任务捕获 `this` 后会强引用目标对象，目标永远到不了触发清理的可达性状态。**

`Cleaner` 持有清理任务，任务又持有目标对象，这条强引用链让目标一直可达，自动清理也就不会发生。

正确做法是把释放资源需要的状态放进独立的静态嵌套类，让任务只持有这些状态。资源有明确作用域时，仍应优先显式关闭。

</details>
