# 低延迟垃圾收集器

ZGC 与 Shenandoah 是以缩短停顿为目标的垃圾收集器。它们让标记和移动对象等耗时工作与应用并发执行，尽量减少堆大小和存活对象数量对停顿的影响，代价是 CPU、内存带宽和额外的堆空间。

理解这类收集器，要能解释对象移动时应用怎样继续访问它，以及回收期间为什么必须留出分配空间。选型时还要区分 GC 暂停和请求延迟：暂停变短，并不保证业务响应也变快。

## 1. 面试核心 {#core}

- ZGC 与 Shenandoah **让应用在对象移动期间继续运行**，通过**引用屏障**找到对象的正确位置。
- G1 的主要疏散**在 STW 中完成**，ZGC **并发重定位**对象。[卡](#g1-vs-zgc)
- Java 21 的 ZGC **默认不分代**，加 **`-XX:+ZGenerational`** 才开启分代。
- 分代 ZGC 用**加载屏障修正对象移动后的引用**，用**存储屏障处理标记并记录跨代引用**。[卡](#generational-zgc-barriers)
- 并发回收跟不上分配时，ZGC 的分配线程会**等待可用空间**，这就是 allocation stall。[卡](#allocation-stall)

## 2. 并发重定位 {#并发重定位}

**重定位**是把存活对象搬到新的内存位置，好把原来的区域整块腾出来回收。G1 也要搬对象，它称之为疏散（evacuation），但主要的疏散工作在 **Stop-The-World**（STW，暂停全部应用线程）期间完成，存活对象越多，要搬的越多，暂停就越长。低延迟收集器的做法是让应用在搬运期间照常运行，把主要耗时工作挪到并发阶段。

对象搬走后，应用手里的引用可能还指向旧位置。**引用屏障**是在读写引用时执行的一小段检查和处理逻辑，用来协调应用访问与 GC 工作。应用遇到旧引用时，收集器借助屏障找到对象的新位置。

两个收集器配合屏障使用的机制不同。ZGC 的**染色指针**是在引用中附带标记等状态的表示方式，屏障据此判断引用是否需要处理。Shenandoah 则利用转发信息记录对象搬到了哪里，再通过引用屏障找到它。

工作并发执行，不等于工作消失了，它变成了这些成本：

- 应用在需要屏障的引用读写位置，要执行额外检查。
- GC 并发线程消耗 CPU 和内存带宽，和业务计算抢资源。
- 堆要为回收期间的新分配和重定位预留空间。
- 某些阶段仍然要短暂 STW，用来处理根集合或切换阶段。

正常并发周期仍有短暂的协调暂停；资源不足时，还可能出现后文讨论的分配等待或退化回收。

## 3. 分代 ZGC {#分代-zgc}

**分代 ZGC** 把新创建的对象和长寿命对象分开回收。它是否默认启用取决于 JDK 版本，Java 17、21 的配置如下：

| JDK 版本 | ZGC 模式 |
| --- | --- |
| 17 | `-XX:+UseZGC` 启用非分代 ZGC。 |
| 21 | `-XX:+UseZGC` 默认不分代，另加 `-XX:+ZGenerational` 启用分代。 |

Java 21 启用分代 ZGC 的命令如下：

```bash
java -XX:+UseZGC -XX:+ZGenerational -jar app.jar
```

分代的依据是：新创建的对象里，有很多很快就不再被引用。分代 ZGC 可以更频繁地回收年轻代，把长寿命对象留在老年代，这样就不用每次都反复扫描那些老对象。ZGC 能用于各种大小的堆，但适不适合，仍然要按分配模式和资源预算实测。

### 3.1 加载屏障与存储屏障 {#加载屏障与存储屏障}

分代 ZGC 的屏障既要处理对象移动，也要支持标记和跨代引用追踪。加载屏障主要解决「对象搬走后去哪里访问」，存储屏障则处理标记并记录老年代指向年轻代的引用。

**加载屏障**（load barrier）在读取引用时检查引用里的元数据。如果对象已经被移动，它就取得新地址，让应用继续访问的还是同一个对象。

**存储屏障**（store barrier）在写入引用字段时执行，承担标记工作，并记录需要追踪的跨代引用。有了这些记录，年轻代回收就能直接找到老年代对年轻代对象的引用，不必为了找它们扫描全部老对象。

两种屏障都靠染色指针里保存的阶段状态快速判断：大多数情况下引用已经是最新的，屏障直接放行，只有少数情况才需要进一步处理。

## 4. Shenandoah {#shenandoah}

Shenandoah 同样通过并发标记和并发移动对象来缩短停顿，由 OpenJDK 社区开发。它不一定在你的 JDK 里：是否包含取决于发行版、平台和具体构建，Oracle JDK 与某些 OpenJDK 发行版提供的收集器就有差异，所以要核对实际安装的构建。

Java 17、21 的 Shenandoah 是非分代的，默认模式为 `satb`。SATB 指「开始时快照」（snapshot-at-the-beginning），它通过记录标记期间的引用变化，保证标记开始时可达的对象都会被保留。在支持的构建上，这样启用：

```bash
java -XX:+UseShenandoahGC -jar app.jar
```

如果 JVM 启动时不认识 `UseShenandoahGC`，说明当前构建没有提供这个收集器。只看 Java 主版本号判断不了，要以构建本身和具体报错为准。

## 5. 分配余量 {#分配余量}

并发回收期间，应用还在不停创建对象，所以堆必须撑得住回收完成之前的这些新分配。设**分配率**为 A，也就是单位时间分配的字节数，一次并发周期耗时为 T，那么这段时间的新分配量大约是 `A × T`。这个估算假设分配率稳定，并且周期内还没有空间被回收出来。

**存活工作集**（live set）是回收后仍然要保留的对象集合。堆除了装下它，还要装下周期内的新分配和重定位，所以需要满足这些条件：

- 最大堆在稳定的存活工作集之外，为并发周期内的新对象留出空间。
- GC 并发线程有足够的 CPU 配额，否则周期变长，`A × T` 也跟着变大。
- 流量突发和巨型对象会突然吃掉更多空间，要控制突发分配，并留出波动余量。
- 并发周期要及时启动，让回收在剩余空间耗尽之前完成。

比如堆只比存活工作集大一点，应用很快就会把剩余空间用完，并发回收还没结束就没有余量了。

空间不够时，两个收集器的退路不同。ZGC 会出现 **allocation stall**（分配停滞），也就是分配对象的线程停下来，等 GC 腾出空间。Shenandoah 可以进入 Degenerated GC，在 STW 中把当前周期做完；空间仍然不够时，还会执行 Full GC。两者的失败路径要分别看各自的日志。

## 6. 吞吐、CPU 与内存的代价 {#吞吐cpu-与内存的代价}

更短的 GC 暂停是否值得，要看业务收益能否覆盖并发回收的资源成本。对象布局、压缩指针支持和平台限制也会随收集器和版本变化，所以和 G1 或 Parallel 比较时，要在相同负载下测量这些指标：

- 吞吐量，即单位时间完成多少请求。
- P99、P999，分别表示 99%、99.9% 的请求延迟不超过这个值，用来观察长尾。
- GC CPU，即回收占用了多少处理器资源。
- RSS，即进程当前驻留在物理内存中的大小，用来检查容器内存压力。
- 分配停滞，看应用有没有因为等可用空间而停下。

GC 暂停很短，请求延迟照样可能很高。CPU 饱和、应用自己的锁、I/O、限流和缺页都会拉长请求延迟；缺页是指访问的页面还没准备好，要等操作系统补上映射或读取数据。比如屏障和 GC 线程把 CPU 吃满后，请求在排队上花的时间可能比省下的暂停还多。所以 GC 暂停和端到端请求延迟要分开观察。

### 6.1 软堆上限与最大堆 {#软堆上限与最大堆}

ZGC 允许设一个软目标和一个硬上限：平时尽量把堆控制在较小的大小，遇到分配突发时又能用到更多空间。

```bash
java -XX:+UseZGC -Xmx5g -XX:SoftMaxHeapSize=4g -jar app.jar
```

这项配置让 ZGC 尽量以 4 GiB 作为堆大小的目标。为了避免分配停滞，它仍然可以使用更多空间，最多到 `-Xmx` 指定的 5 GiB。软目标管日常的堆大小，硬上限决定堆最多能用多少。

注意 `SoftMaxHeapSize` 不是进程内存上限，容器预算还要覆盖堆外内存。

## 7. 收集器的选择 {#收集器的选择}

选收集器要把暂停目标和资源预算放在一起看。可以从这四个候选开始比较：

- **G1** 可以作为通用服务的基线，在吞吐、内存占用和暂停之间取得平衡。业务能接受数百毫秒以内的暂停时，可以先从 G1 开始验证实际的暂停分布。
- **ZGC** 适合评估暂停目标严格或堆很大的场景，同时要验证并发回收的成本。
- **Shenandoah** 是另一种低停顿选择，前提是目标发行版和平台支持它。
- **Parallel** 适合吞吐优先、能接受集中暂停的批处理任务。

如果 G1 已经满足业务的暂停目标，吞吐、内存占用和团队现有的运维经验都是继续用它的理由。比较其他收集器时，要保持相同的 JDK、容器限制和请求回放，用端到端效果判断收益。

## 8. 迁移验证 {#迁移验证清单}

迁移验证要回答两个问题：新收集器有没有改善业务指标，内存紧张时还能不能满足要求。验证时负载和资源限制要保持可比较：

1. 记录原配置的存活工作集、分配率、暂停分布和 GC CPU，作为比较基线。
2. 确认目标构建、平台和监控工具都支持新收集器，清理旧收集器的专用参数。先只切换收集器，堆配置保持简单。
3. 在相同的资源限制下，分别压测稳定流量、突发流量和内存接近上限的情况。
4. 检查 allocation stall、退化回收和 GC CPU，确认回收能及时腾出可用空间。
5. 对比端到端请求长尾、吞吐和容器 RSS，判断更短的暂停是否真的转化成了业务收益。

GC 日志与 JFR 的时间线分析见 [GC 停顿分析](./gc-logs-jfr-pauses.mdx)。

## 9. 常见问题 {#常见问题}

### 9.1 ZGC 能保证每次暂停都不超过某个时限吗？ {#停顿目标与实时保证}

ZGC 的低停顿是设计目标，不是硬实时保证。它通过并发执行主要工作，避免暂停随堆大小线性增长，但实际暂停仍受根集合大小、线程数量、系统调度和实现细节影响，资源争抢还会进一步拉长业务延迟。

### 9.2 换成低延迟收集器，就不用规划堆容量了吗？ {#低延迟收集器的容量}

换成低延迟收集器，堆容量照样要规划，而且要为存活工作集、并发期间的新分配和波动都留出余量。堆太小，分配线程会等回收；堆太大，又占用了本可以留给其他进程的资源。配置完还要用 RSS 检查整个进程是否在容器预算内。

### 9.3 ZGC 和 Shenandoah 哪个更快？ {#zgc-与-shenandoah-的性能比较}

没有固定的快慢顺序，取决于工作负载。JDK 版本、对象之间的引用关系、分配率、CPU、堆大小和发行版实现都会影响结果，应该在目标环境里比较吞吐、请求长尾和资源占用。

## 10. 面试题 {#面试题}

### 10.1 G1 和 ZGC 的主要差异是什么，什么情况下适合继续使用 G1 {#g1-vs-zgc}

**考察重点**：解释 G1 的暂停疏散与 ZGC 的并发重定位，并结合吞吐、内存和运维经验说明选择依据。

**相关内容**：[并发重定位](#并发重定位)、[收集器的选择](#收集器的选择)。

<details>
<summary>参考回答</summary>

**G1 的主要对象疏散在 STW 中完成，ZGC 则并发移动对象；G1 已满足暂停目标时，服务可以继续使用它。**

G1 能并发标记，但把存活对象搬出回收区域的主要工作仍需暂停应用。ZGC 用引用屏障帮助应用在移动期间找到正确位置，因此把更多工作移出了暂停阶段。代价是屏障、并发 GC 的资源消耗，以及回收所需的堆余量。

如果 G1 已满足业务延迟目标，吞吐、内存占用和现有运维经验都可以成为保留它的理由。迁移应在同一环境比较端到端长尾、吞吐和 RSS，再判断收益。

</details>

### 10.2 低延迟收集器为什么仍可能发生分配停滞 {#allocation-stall}

**考察重点**：说明存活工作集、分配率、周期时间与堆余量的关系，以及 CPU 不足怎样加大分配压力。

**相关内容**：[分配余量](#分配余量)。

<details>
<summary>参考回答</summary>

**因为应用在并发回收期间仍会分配对象，回收完成前若耗尽可用空间，分配线程就需要等待。**

存活工作集大时，堆中可腾出的空间有限。高分配率会更快消耗空闲空间，CPU 不足或周期启动太晚又会推迟回收完成。因此，堆要为一个并发周期内的新分配、对象重定位和流量波动留出余量。

ZGC 用 allocation stall 表示这类分配等待。诊断时应同时比较堆余量、GC CPU 和周期时长；Shenandoah 的退化回收则要按它自己的日志判断。

</details>

<details>

**加载屏障负责取得对象移动后的正确地址，存储屏障负责标记与跨代引用记录。**

### 10.4 ZGC 的 SoftMaxHeapSize 与 Xmx 有什么区别？ {#soft-max-heap}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：区分 ZGC 的软堆目标与最大堆，并说明容器为什么还需为堆外内存留余量。

**相关内容**：[软堆上限与最大堆](#软堆上限与最大堆)。

<details>
<summary>参考回答</summary>

**`SoftMaxHeapSize` 是 ZGC 尽量遵守的软目标，`-Xmx` 才是堆的硬上限。**

配置 4 GiB 软目标、5 GiB 最大堆时，ZGC 会尽量以 4 GiB 为目标运行。为避免分配停滞，它仍可使用额外空间，最多扩展到 5 GiB。进程还包含线程栈、元空间等堆外内存，因此容器容量需要在最大堆之外继续预留。

</details>
