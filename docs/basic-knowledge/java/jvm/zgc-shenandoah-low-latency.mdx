# 低延迟垃圾收集器

ZGC 与 Shenandoah 通过并发标记和移动对象缩短停顿。本文负责并发访问机制、版本配置和分配余量。G1 的区域回收见 [G1](./g1-regions-rset-collection-set.mdx)。GC 暂停与请求延迟需要分别观察。

## 1. 面试核心 {#core}

- ZGC 与 Shenandoah 将对象移动放入并发阶段，用引用屏障维持访问正确性。
- JDK 23 的 ZGC 默认使用分代模式，JDK 24 移除非分代模式。
- 分代 ZGC 用加载屏障修正引用，用存储屏障处理标记与跨代记录。[卡](#generational-zgc-barriers)
- G1 的主要疏散在 STW 中完成，ZGC 并发重定位对象。[卡](#g1-vs-zgc)
- 并发回收跟不上分配时，ZGC 的分配线程会等待可用空间。[卡](#allocation-stall)

## 2. 并发重定位 {#并发重定位}

并发重定位允许 GC 移动对象时，应用继续访问对象。应用引用中仍会暂存旧位置，因此需要屏障纠正访问。

ZGC 用染色指针记录元数据，并通过引用屏障处理。Shenandoah 用转发信息与引用屏障找到新位置。具体编码属于各收集器的实现。

并发线程消耗 CPU 与内存带宽。应用访问也要承担屏障成本。收集器仍保留短暂 STW 阶段，以协调阶段切换。

## 3. 分代 ZGC {#分代-zgc}

| JDK 版本 | ZGC 模式 |
| --- | --- |
| 21—22 | `UseZGC` 选择非分代，另加 `ZGenerational` 选择分代 |
| 23 | 分代默认，非分代弃用 |
| 24 起 | 只保留分代，旧模式开关退出使用 |

JDK 24—26 可直接启用：

```bash
java -XX:+UseZGC -jar app.jar
```

分代 ZGC 把新对象与长寿命对象分开处理。年轻代可更频繁回收，减少反复扫描老对象。

### 3.1 加载屏障与存储屏障 {#加载屏障与存储屏障}

加载屏障检查引用中的位置元数据。对象已移动时，屏障获得正确地址。

存储屏障处理引用字段写入。它承担标记工作，并记录需要追踪的跨代引用。年轻代回收据此处理老年代对年轻代的引用。

染色指针承载不同阶段的状态，供屏障快速判断。分代模式同时使用 load barrier 和 store barrier。

## 4. Shenandoah {#shenandoah}

Shenandoah 也并发标记和移动对象。目标 JDK 是否包含它，取决于发行版与构建。

分代 Shenandoah 在 JDK 24 作为实验功能交付。JDK 25 将它产品化，但默认仍为单代。OpenJDK 26 默认模式也为 `satb`。

JDK 25—26 的支持构建中，可显式选择分代：

```bash
java -XX:+UseShenandoahGC \
  -XX:ShenandoahGCMode=generational -jar app.jar
```

JDK 24 还需 `-XX:+UnlockExperimentalVMOptions`。启动失败时应核对构建支持与错误内容。

## 5. 分配余量 {#分配余量}

并发 GC 期间，应用仍在分配。若分配率为 A、周期耗时为 T，新分配量约为 `A × T`。该估算假设速率稳定，且暂未回收空间。

实际容量还需覆盖存活对象、重定位和流量突发。CPU 配额不足会拉长周期，使分配压力进一步积累。

ZGC 缺少空间时会出现 allocation stall。Shenandoah 可进入 Degenerated GC，在 STW 中继续当前周期。空间仍不足时，它还可执行 Full GC。两者的故障路径应分别看日志。

## 6. 吞吐、CPU 与内存的代价 {#吞吐cpu-与内存的代价}

低停顿来自把工作移到并发阶段。屏障和 GC 线程会与业务代码竞争资源。具体吞吐与内存差异需要同负载测量。

同时比较 P99/P999、GC CPU、RSS 和分配停滞。短 GC pause 与高请求延迟可同时出现。锁等待、限流和缺页都属于额外延迟来源。

### 6.1 软堆上限与最大堆 {#软堆上限与最大堆}

```bash
java -XX:+UseZGC -Xmx5g -XX:SoftMaxHeapSize=4g -jar app.jar
```

ZGC 以 4 GiB 作为软目标。为避免分配停滞，它仍可扩展到 5 GiB。`-Xmx` 才是该配置的堆硬上限。

容器预算仍需覆盖堆外内存。`SoftMaxHeapSize` 并非进程内存上限。

## 7. 收集器的选择 {#收集器的选择}

G1 可作为通用服务的比较基线。严格停顿目标或大堆场景可评估 ZGC。Shenandoah 适用于目标发行版支持的低停顿场景。吞吐优先的批处理还可比较 Parallel。

选择需以业务吞吐、端到端延迟和资源预算为标准。同一 JDK、容器限制和请求回放才能形成有效对照。

## 8. 迁移验证 {#迁移验证清单}

1. 记录原配置的存活工作集、分配率与暂停分布。
2. 确认目标构建支持，清理旧收集器参数。
3. 在相同资源限制下，比较稳定与突发流量。
4. 检查分配停滞、退化回收和 GC CPU。
5. 对比请求长尾、吞吐与进程内存。

GC 日志与 JFR 的时间线分析见 [GC 停顿分析](./gc-logs-jfr-pauses.mdx)。

## 9. 常见问题 {#常见问题}

### 9.1 停顿目标与实时保证 {#停顿目标与实时保证}

ZGC 将主要工作并发执行，以降低暂停。操作系统调度和资源争抢仍会影响实际延迟。低停顿目标不构成硬实时上限。

### 9.2 低延迟收集器的容量 {#低延迟收集器的容量}

堆需覆盖存活工作集、并发新分配和波动余量。过小的堆会使分配线程等待回收。

### 9.3 ZGC 与 Shenandoah 的性能比较 {#zgc-与-shenandoah-的性能比较}

不同版本、对象图和分配率会改变结果。应在目标环境比较吞吐、长尾和资源占用。

## 10. 面试题 {#面试题}

### 10.1 G1 和 ZGC 的主要差异是什么，为什么不少服务仍使用 G1 {#g1-vs-zgc}

<!-- 面试来源：
- 某云原生企业：https://www.nowcoder.com/discuss/732685882523758592
-->

**出现公司**：某云原生企业

**考察重点**：STW 疏散、并发重定位与资源取舍。

**相关内容**：[并发重定位](#并发重定位)、[收集器的选择](#收集器的选择)。

<details>
<summary>参考回答</summary>

G1 的主要疏散工作在 STW 中完成，ZGC 并发移动对象。ZGC 通过引用屏障维持访问正确性，以缩短暂停。屏障和并发回收会消耗资源。G1 已满足暂停目标时，还可依据吞吐与内存占用保留它。最终应对比同环境下的吞吐、长尾和 RSS。

</details>

### 10.2 低延迟收集器为什么仍可能发生分配停滞 {#allocation-stall}

<!-- 面试来源：
- 阿里云：https://www.nowcoder.com/discuss/401459816646942720
-->

**出现公司**：阿里云

**考察重点**：分配率、周期时间与可用空间。

**相关内容**：[分配余量](#分配余量)。

<details>
<summary>参考回答</summary>

并发回收期间应用继续分配，可用空间会先于回收完成而耗尽。ZGC 的分配线程此时需要等待空间。高分配率、大工作集和 CPU 不足都会增加风险。应同时评估堆余量、周期时长和 allocation stall。Shenandoah 的退化回收需按其日志另行分析。

</details>

### 10.4 ZGC 的 SoftMaxHeapSize 与 Xmx 有什么区别？ {#soft-max-heap}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：软目标、硬上限与进程预算。

**相关内容**：[软堆上限与最大堆](#软堆上限与最大堆)。

<details>
<summary>参考回答</summary>

SoftMaxHeapSize 是 ZGC 尽量遵守的软目标，Xmx 是最大堆。配置 4 GiB 软目标、5 GiB 最大堆时，堆可超过 4 GiB。额外空间用于降低分配停滞。进程还包含堆外内存，容器容量需另行预留。

</details>
