# 压缩指针与对象对齐

Java 对象的内存占用由对象头、字段和对齐填充组成。压缩指针会影响其中一部分大小：在 Java 17、21 的 64 位 HotSpot 上，开启压缩对象指针时，堆中的引用槽位占 4 字节，关闭时占 8 字节。

几千万个集合节点中，每个引用多占 4 字节，就会明显改变堆占用和缓存利用率。因此，评估容量不能只看 `-Xmx`：如果扩大堆后压缩指针关闭了，新增的空间有一部分会被更宽的引用占用。理解引用宽度、对象布局和保留关系，才能解释一个业务对象实际带来了多少内存成本。

## 1. 面试核心 {#core}

- HotSpot 的压缩对象指针**用 32 位编码表示堆内引用**，访问时结合堆基址和移位恢复出真实地址，从而让每个引用只占 4 字节。[卡](#compressed-oops)
- 默认 **8 字节对齐让 32 位编码理论上能覆盖 32 GiB** 的堆，实际能否启用还要检查目标 JVM 的配置。
- 压缩对象指针表示堆内对象的地址，压缩类指针表示类元数据的地址，**两者可以分别启用**。[卡](#oop-klass-independence)
- Java 17、21 的 64 位 HotSpot 上，类指针压缩时**普通对象头占 12 字节**。加上字段后，还要按对齐粒度向上取整。
- **浅大小**只算对象自身的占用；**保留大小**还包括这个对象变得不可达后，能跟着一起释放的其他对象。[卡](#object-memory-cost)

## 2. 压缩对象指针 {#压缩对象指针}

**压缩对象指针**（Compressed Oops）用比 64 位更窄的编码来表示对象地址，目的是减少引用占用的空间。一个 64 位地址要 8 字节，字段和数组里引用越多，这部分开销就越大。

开启 `UseCompressedOops` 时，对象字段和对象数组中的引用槽位占 4 字节；关闭后占 8 字节。4 字节存不下完整的 64 位地址，所以 JVM 访问对象时，要结合堆基址和移位把地址算回来：

```text
对象地址 = 堆基址 + (编码值 << 移位位数)
```

这里能移位，靠的是对齐。默认 8 字节对齐时，所有对象地址都是 8 的倍数，最低 3 位永远是 0，不需要存。于是编码值可以按 8 倍缩放，也就是左移 3 位，32 位编码的理论范围就成了 `2^32 × 8 = 32 GiB`。

32 GiB 只是理解编码时的理论上限。实际能不能启用，还受堆放在内存中的位置、保留空间和 JVM 的实现策略影响，部署时要检查进程参数和启动日志。查看 Java 17、21 的相关选项：

```bash
java -XX:+PrintFlagsFinal -version | rg 'UseCompressedOops|UseCompressedClassPointers|ObjectAlignmentInBytes'
```

这条命令显示当前 JVM 的选项值。验证部署配置时，要带上实际使用的收集器和启动参数，因为它们会影响结果。ZGC 使用自己的引用编码，要按它的实现单独分析。

### 2.1 对象引用与类指针 {#对象引用与类指针}

**对象引用**用于找到堆中的对象，比如对象字段或数组元素保存的引用。**类指针**位于对象头中，指向描述对象所属类型的类元数据。估算对象大小时，要分别检查两者的宽度。

两者的编码范围和管理机制不同，压缩与否也是分开的。所以堆调大导致压缩对象引用关闭后，类指针仍然可以保持压缩。Java 17、21 用 `UseCompressedClassPointers` 控制类指针压缩，而引用数组每个元素的宽度，取决于对象引用用的是哪种方案。

## 3. 对象头布局 {#compact-object-headers}

Java 17、21 的 64 位 HotSpot 上，普通对象头由标记字和类指针组成。**标记字**（mark word）是保存锁状态、哈希码等信息的部分，占 8 字节；压缩类指针占 4 字节，所以普通对象头一共 12 字节。关闭类指针压缩后，对象头是 16 字节。

数组对象头后面还有 4 字节的长度字段。对象最终的大小是对象头加上实例数据，再按对齐粒度向上取整。比如一个只有一个 `int` 字段的对象，12 字节对象头加 4 字节字段，正好 16 字节，不需要填充。

## 4. 对象对齐 {#对象对齐}

对象实际占用的大小，要算上对齐带来的填充。默认 `ObjectAlignmentInBytes=8`，对象大小会向上取整到 8 的倍数，比如对象头加字段一共 22 字节，最终占 24 字节。

字段之间也可能出现空洞。比如下面这个类包含宽度不同的字段：

```java
final class Entry {
    byte state;
    long timestamp;
    Object value;
}
```

`long` 需要按 8 字节对齐，如果严格按声明顺序摆放，`state` 后面就会空出几个字节。HotSpot 可以重排字段，用较小的字段填补这些空洞，所以源码里的声明顺序并不能直接告诉你最终的偏移。继承层级、对象头方案和 JVM 的布局算法都会影响结果，要在目标 JVM 上实际测量。

调大对齐值可以扩大压缩引用能覆盖的范围：16 字节对齐时，理论范围变成 64 GiB。但每个对象的尾部填充也可能变多。调整前要看对象大小的分布：小对象越多，多出来的填充越容易把引用压缩省下的空间吃掉。

## 5. 浅大小与保留大小 {#浅大小与保留大小}

**浅大小**（shallow size）是对象自身的占用，包括对象头、字段和填充。**保留大小**（retained size）还包括这个对象变得不可达后，能跟着一起释放的其他对象。前者回答「它自己有多大」，后者回答「释放它能回收多少内存」。

比如一个 `ArrayList` 对象本身只存了数组引用、大小这些字段，浅大小很小，但它内部的数组和元素可能占了大量内存。不过，如果某个元素同时还被别的 GC Root（垃圾回收查找存活对象的起点）引用着，这个列表没了它也不会被释放，它就不算在列表的保留大小里。

JOL（Java Object Layout）可以测量对象布局，也能统计从一个对象出发能到达的对象图大小。不过，共享对象也会计入可达图，所以这个结果不等于保留大小。

分析保留关系要用堆转储里的**支配树**（Dominator Tree），它按对象之间的支配关系组织：从 GC Root 到对象 Y 的所有路径都经过 X，就说 X 支配 Y。X 的保留大小包括它自身和它支配的所有对象，因为一旦 X 不可达，这些对象也就失去了来自 GC Root 的引用路径。

## 6. 数组与集合节点的开销 {#数组与集合节点的开销}

估算数组或集合的成本时，要顺着引用把内部结构都算进去。对象数组除了对象头和长度字段，还要为每个元素存一个引用；基本类型数组则直接存值。

所以同样存 100 万个整数，`int[]` 和 `Integer[]` 的成本差别很大。`int[]` 每个元素 4 字节；`Integer[]` 每个元素先要一个引用槽位，再加上装箱出来的 `Integer` 对象本身。如果多个位置共用缓存里的同一个 `Integer`，这个对象只算一次。

双向链表还要给每个元素额外加一个节点对象，以及指向前后节点的引用。数组省掉了这些节点，而且值或引用在内存里连续排列，顺序访问时更有利于利用 CPU 缓存。不过，选数据结构不能只看内存，还要结合元素规模和操作模式，比较插入、删除和扩容的成本。

## 7. 字段类型与内存密度 {#字段类型与内存密度}

内存优化先从数量多、存活时间长的记录下手。字段的取值范围允许时，用基本类型可以省掉装箱对象，也省掉一次通过引用访问对象的开销：

```java
record Metric(long timestamp, double value, int status) {}
```

这个 record 仍然是一个普通对象，但字段直接存基本类型的值，不需要额外的包装对象。如果每条记录都用好几个包装类型、字符串或 Map 字段，每条就要多出若干个对象和引用。

改成基本类型之前，要保住原来的取值范围和可空语义。比如包装类型的 `null` 原本表示「尚未采集」，改成 `double` 后就得另外想一个表示方式。动手之前先用堆直方图看各个类的实例数量和占用，再挑占用高、长期存活的结构评估收益。

## 8. 压缩指针失效后的容量变化 {#压缩指针失效后的容量变化}

堆调大到压缩对象指针无法启用时，每个引用从 4 字节变成 8 字节，引用密集的结构会整体变大。所以加大 `-Xmx` 之后，能装下的业务对象数量不一定按比例增加，多出来的堆可能有一大部分被更宽的引用占掉了。类指针是否还压缩，要另外确认。

比较两组配置时，要同时验证对象密度和运行成本：

1. 记录压缩相关选项的实际值，以及对象头方案。
2. 用 JOL 比较核心对象和数组的实际布局。
3. 在相同负载下比较 live set、分配率、GC CPU 和吞吐。live set 指回收后仍然存活的对象总量。
4. 把 RSS 和容器内存上限纳入容量评估。RSS 是进程实际驻留在物理内存里的页面总量。

这样才能看出新增的堆空间带来了多少有效容量，以及 GC 和进程总内存为此付出了什么代价。

## 9. 常见问题 {#常见问题}

### 9.1 Java 引用一定占 8 字节吗？ {#java-引用的字节数}

不一定。在本文讨论的 64 位 HotSpot 上，压缩的堆内对象引用占 4 字节，关闭压缩后占 8 字节。这个结论适用于对象字段和对象数组里的引用槽位，实际状态要结合进程参数和 JOL 验证。

### 9.2 调整字段声明顺序就能让对象变小吗？ {#字段顺序与对象大小}

只调整源码里的字段顺序，并不能保证对象变小，因为 HotSpot 会按自己的布局规则摆放字段。改完之后要重新测量实际偏移。如果主要成本来自大量包装对象或集合节点，减少装箱和节点数量更值得先验证。

### 9.3 对齐粒度越大，性能就越好吗？ {#对齐粒度与性能}

不是。调大对齐粒度能扩大压缩编码的范围，但也可能增加尾部填充，收益取决于对象大小的分布和引用的数量。先保留默认值，再通过目标 JVM 上的布局测量和负载基准判断是否需要调整。

## 10. 面试题 {#面试题}

### 10.1 压缩对象指针解决什么问题 {#compressed-oops}

**考察重点**：解释压缩编码如何减少引用占用，以及对齐、堆放置和 JVM 配置怎样影响寻址范围。

**相关内容**：[压缩对象指针](#压缩对象指针)和[压缩指针失效后的容量变化](#压缩指针失效后的容量变化)。

<details>
<summary>参考回答</summary>

**压缩对象指针减少了对象字段和对象数组里引用占用的空间，让每个引用从 8 字节降到 4 字节。**

64 位 HotSpot 用 32 位编码表示对象地址，访问时再结合堆基址和移位恢复真实地址。引用变窄后，同样大小的缓存也能装下更多引用。

默认 8 字节对齐时，对象地址的低 3 位总是 0，编码可以左移 3 位，理论上覆盖 32 GiB；实际能否启用还受堆的放置位置和 JVM 配置影响。对象头里的类指针单独表示类元数据地址，压缩状态要分别检查。

</details>

### 10.2 怎样评估一个 Java 对象的真实内存成本 {#object-memory-cost}

**考察重点**：区分浅大小、可达图大小与保留大小，并解释实例数量如何放大单个对象的成本。

<summary>参考回答</summary>

**要同时看对象自身的浅大小、它保留的对象图，以及同类实例的数量。**

浅大小由对象头、字段和填充组成；集合还要算上内部数组、节点和元素。

在目标 JVM 上用 JOL 测量布局，用堆直方图确认实例数量，用 Dominator Tree 判断保留关系。共享对象即使能从当前对象到达，也不一定由它保留，所以可达图大小和保留大小要分开解释。

优化先针对数量大、存活时间长的结构，再通过 live set、分配率和 GC 结果验证收益。

</details>

### 10.3 扩大堆关闭压缩对象指针后，类指针也会变宽吗？ {#oop-klass-independence}

**考察重点**：说明对象引用和类指针指向什么，以及为何需要分别检查压缩状态。

**相关内容**：[对象引用与类指针](#对象引用与类指针)。

<details>
<summary>参考回答</summary>

所以要分别检查 `UseCompressedOops` 和 `UseCompressedClassPointers`。计算对象大小时，再结合对象头布局和对齐粒度实际测量。
