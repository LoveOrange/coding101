# 类加载故障

类加载故障包括查找失败、链接冲突与初始化失败。本文负责按异常和线程状态定位原因。正常阶段与触发条件见[类加载](./class-loading-stages.mdx)。

## 1. 面试核心 {#core}

- `ClassNotFoundException` 表示显式类查找失败。[卡](#cnfe-vs-ncdfe)
- 初始化失败后，再次主动使用会抛 `NoClassDefFoundError`。[卡](#initialization-failure-retry)
- `NoSuchMethodError` 表示解析时找不到目标方法描述符。[卡](#no-such-method-error)
- 跨线程的循环初始化依赖可以造成死锁。[卡](#initialization-deadlock)

## 2. 类初始化锁 {#类初始化锁}

JVM 为每个类或接口维护初始化锁。一个线程执行初始化，其他首次使用者等待结果。正常完成后，静态初始化结果对后续使用者可见。

```java
final class Registry {
    static final Map<String, Handler> HANDLERS = loadFromRemote();
}
```

若 `loadFromRemote()` 等待网络，首次使用者也会等待。外部 I/O 应放入显式生命周期步骤。静态初始化适合建立短小的内存状态。

## 3. 类初始化死锁 {#类初始化死锁}

两个线程分别初始化 A 和 B，再请求对方完成，就会形成等待环：

```java
final class A {
    static final Object VALUE = B.VALUE;
}

final class B {
    static final Object VALUE = A.VALUE;
}
```

该代码需要特定并发时序才会死锁。单线程访问会递归请求已在初始化的类。JVM 允许同一线程继续，因此本例读到 `null`。

初始化线程在执行 `<clinit>` 时已释放初始化锁。死锁来自“等待另一线程完成初始化”的依赖环。线程转储中应查找 `<clinit>` 和初始化等待。

Java monitor 死锁检测未必直接报告这种等待。应对照多个线程栈，还原类初始化依赖。移除双向静态依赖可消除本例的等待环。

## 4. 初始化失败与缺少类定义 {#初始化失败与缺少类定义}

首次初始化抛出非 `Error` 异常时，JVM 会包装异常。包装类型是 `ExceptionInInitializerError`：

```text
ExceptionInInitializerError
Caused by: IllegalStateException: missing endpoint
```

若原异常已经是 `Error`，首次调用直接传播它。包装异常分配失败时，还可抛出 `OutOfMemoryError`。失败后的类会进入错误状态。

后续主动使用同一 `Class` 会得到：

```text
NoClassDefFoundError: Could not initialize class com.example.Config
```

此时 Class 文件可以仍然存在。定位应回到最早异常与完整 cause chain。同一 `Class` 的初始化不会自动重试。

显式 API 找不到类会抛 `ClassNotFoundException`。JVM 加载依赖失败也会抛 `NoClassDefFoundError`。需要结合消息与首次异常区分两种原因。

## 5. 二进制版本冲突 {#二进制版本冲突}

应用按一个版本编译，运行时加载另一版本，就会产生链接风险。

| 错误 | 含义 |
| --- | --- |
| `NoSuchMethodError` | 解析时找不到目标方法描述符。 |
| `NoSuchFieldError` | 解析时找不到目标字段。 |
| `AbstractMethodError` | 调用到缺少有效具体实现的方法。 |
| `IncompatibleClassChangeError` | 类、接口或成员形态发生不兼容变化。 |
| `UnsupportedClassVersionError` | 运行 JDK 不支持该 Class 版本。 |

方法描述符包含参数类型与返回类型。只比较方法名会遗漏返回类型冲突。修复需要统一运行时依赖，或恢复二进制兼容。

## 6. 类来源证据 {#确认类的来源}

JDK 9 及以后可记录类加载来源：

```bash
java -Xlog:class+load=info -jar app.jar
jcmd <pid> VM.classloaders
jcmd <pid> VM.classloader_stats
```

代码中可查看目标类信息：

```java
Class<?> type = SomeLibrary.class;
System.out.println(type.getProtectionDomain().getCodeSource());
System.out.println(type.getClassLoader());
```

代码来源可为空，需结合加载日志判断。再对照依赖树与最终产物：

```bash
mvn dependency:tree
./gradlew dependencies
```

依赖图说明构建选择，加载日志说明运行结果。服务器共享库、容器挂载和 shaded JAR 都需检查。

## 7. 加载器类型冲突 {#加载器冲突导致的-classcastexception}

“X cannot be cast to X”可由同名类型的加载器差异引起。应分别打印两边类型的加载器、模块和来源：

```java
static void describe(Class<?> type) {
    System.out.printf("%s loader=%s module=%s source=%s%n",
        type.getName(),
        type.getClassLoader(),
        type.getModule(),
        type.getProtectionDomain().getCodeSource());
}
```

共享 API 需由共同父加载器定义，见[类加载器](./classloaders-spi-isolation.mdx#插件隔离)。

## 8. 排查顺序 {#排查顺序}

1. 保留最早异常和完整 cause chain。
2. 判断故障处于查找、链接、初始化还是等待阶段。
3. 记录目标类的加载器、模块和代码来源。
4. 对照类加载日志、依赖图和最终产物。
5. 检查启动脚本、容器挂载与共享库。
6. 修复后验证冷启动和热部署路径。

## 9. 常见问题 {#常见问题}

### 9.1 重启与故障时序 {#重启与故障时序}

重启会清除旧加载器，并改变首次访问顺序。并发初始化的触发时序也会变化。重启前应保留线程转储、首个异常与类加载日志。

### 9.2 依赖树与运行时来源 {#依赖树与运行时来源}

依赖树只描述构建依赖。服务器共享目录、手工 JAR 和 Java Agent 可引入额外定义。定位以实际加载来源为准。

### 9.3 初始化失败后的恢复 {#初始化失败后的恢复}

同一 `Class` 进入错误状态后，主动使用持续失败。可重试业务应采用显式初始化方法。插件架构也可创建新加载器，重新定义类型。

## 10. 面试题 {#面试题}

### 10.1 `ClassNotFoundException` 与 `NoClassDefFoundError` 有什么区别 {#cnfe-vs-ncdfe}

<!-- 面试来源：
- 字节跳动：https://www.nowcoder.com/discuss/366687810131165184
- 阿里巴巴：https://www.nowcoder.com/discuss/353156165536260096
-->

**出现公司**：字节跳动、阿里巴巴

**考察重点**：区分类查找失败、依赖缺失与初始化错误。

**相关内容**：[初始化失败与缺少类定义](#初始化失败与缺少类定义)和[二进制版本冲突](#二进制版本冲突)。

<details>
<summary>参考回答</summary>

`ClassNotFoundException` 表示显式加载 API 找不到类。`NoClassDefFoundError` 是 JVM 使用类定义失败的错误。运行时缺少依赖与之前初始化失败都能触发后者。

看到 `Could not initialize class`，先找最早初始化异常。再用类加载日志确认来源，区分缺类与失败状态。

</details>

### 10.2 线上出现 `NoSuchMethodError` 应该怎样排查 {#no-such-method-error}

<!-- 面试来源：
- 阿里巴巴：https://www.nowcoder.com/discuss/353157613372252160
-->

**出现公司**：阿里巴巴

**考察重点**：根据方法描述符与实际加载来源定位版本冲突。

**相关内容**：[二进制版本冲突](#二进制版本冲突)至[排查顺序](#排查顺序)。

<details>
<summary>参考回答</summary>

先确认运行时目标类中缺失的方法描述符。描述符包含参数和返回类型。记录报错中的签名、实际 JAR 与加载器。

用 `-Xlog:class+load=info` 确认来源。再对照依赖树、打包产物和启动脚本。修复版本后，重新验证发生错误的调用路径。

</details>

<details>

</details>

### 10.4 两个类互相引用静态字段，为何单线程成功而并发死锁？ {#initialization-deadlock}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：递归初始化与跨线程等待环。

**相关内容**：[类初始化死锁](#类初始化死锁)。

<details>
<summary>参考回答</summary>

同一线程递归请求初始化时，JVM 允许它继续执行。因此它可读到尚未赋值的静态字段零值。两个线程分别负责两个类时，会等待对方完成。若依赖构成环，初始化就无法推进。

</details>
