# 分代回收

分代回收按对象寿命组织回收工作。本文负责分代假设、引用屏障、并发标记和安全点。G1 的回收集合见[G1](./g1-regions-rset-collection-set.mdx)。

## 1. 面试核心 {#core}

- 分代收集依据多数对象短命的经验，优先处理年轻对象。
- 写屏障与卡表记录跨代引用，支持年轻代局部回收。[卡](#write-barrier-rset)
- G1 的 SATB 前置写屏障记录被覆盖的旧引用。[卡](#satb-floating-garbage)
- 安全点协调可扫描的线程状态，handshake 可只针对部分线程。[卡](#safepoints)

## 2. 分代假设 {#分代假设}

多数临时对象很快失效，少量对象会长期存活。分代收集据此频繁回收年轻对象，减少老对象扫描。

新对象主要进入年轻代，存活对象再按策略晋升。大对象等分配路径由具体收集器决定。Java 语言本身未要求堆必须分代。

日志中的 Minor、Major、Full 也需结合收集器解释。诊断时应使用具体事件名与回收范围。

## 3. 跨代引用与写屏障 {#跨代引用与写屏障}

老对象可以持有新对象：

```java
oldOrder.latestEvent = new Event();
```

年轻代回收需要发现这条外部引用。否则，新对象会被误判为不可达。

GC 写屏障在引用更新周围执行辅助逻辑。卡表用一个条目表示一段堆地址是否需要扫描。脏卡是引用变化的摘要，还需扫描区域才能找到对象。

Remembered Set 组织局部回收所需的外部引用信息。卡表与 RSet 的具体关系依收集器实现。代价包括屏障执行、摘要内存和后续扫描。

## 4. 并发标记与对象图变化 {#并发标记与对象图变化}

并发标记期间，应用还在新增和删除引用。收集器需要处理遍历过程中发生的变化。三色模型可帮助说明漏标风险：

- 白色表示尚未发现的对象。
- 灰色表示已发现、尚未扫描完引用的对象。
- 黑色表示引用已扫描完的对象。

若黑对象新增到白对象的引用，标记需要处理这条新边。原有到白对象的路径同时被删除时，会产生漏标风险。

### 4.1 SATB 与增量更新 {#satb-与增量更新}

G1 使用 SATB，保留标记开始时的存活快照。覆盖引用前，前置写屏障记录旧引用。标记线程之后继续处理这些记录。

增量更新则关注新增引用。它记录或重新扫描变化，防止已扫描对象隐藏新边。两类算法分别维护自己的标记不变量。

SATB 保留快照时存活、后来失去用途的对象。这类浮动垃圾留到后续回收再判断。并发标记因此需要为新增分配与浮动垃圾留余量。

### 4.2 引用屏障的分工 {#引用屏障的分工}

G1 的 SATB 前置屏障用于并发标记。后置屏障处理更新后的跨 Region 引用信息。RSet 支持局部回收，SATB 维护并发标记正确性。

GC 屏障与 JMM 内存屏障用途不同。前者维护引用信息，后者约束跨线程内存顺序。某些实现可同时需要相关机器指令。

## 5. 安全点 {#安全点}

安全点允许 JVM 准确解释线程状态与引用位置。全局操作需要线程进入可协调状态。编译代码在指定位置执行安全点轮询。

Java 线程阻塞或执行 native 代码时，可处于可安全扫描状态。它返回 Java 执行前还需检查协调状态。因此，native 方法耗时长并不必然拖延安全点。

### 5.1 全局安全点与线程握手 {#全局安全点与线程握手}

全局安全点协调所有相关 Java 线程。JDK 10 的 thread-local handshake 可只协调指定线程。部分操作因此无需等待所有线程共同暂停。

应把等待进入安全状态与停顿内工作分开观察：

```text
安全点总时间 = 到达安全状态的时间 + 停顿内工作时间
```

诊断时先看具体 VM 操作与耗时。日志解读见[GC 停顿分析](./gc-logs-jfr-pauses.mdx#gc-停顿安全点与系统停顿)。

## 6. Stop-The-World 阶段 {#stop-the-world-阶段}

Serial 与 Parallel 的主要回收工作在停顿内完成。G1、ZGC 和 Shenandoah 将部分工作与应用并发执行。它们仍保留用于协调状态的 STW 阶段。

比较收集器应同时观察暂停、吞吐与 GC CPU。并发工作还需要 CPU 和堆余量。低暂停目标也需结合分配停滞与失败路径评估。

## 7. 晋升与分配失败 {#晋升与分配失败}

复制或晋升需要目标空间。空间不足时，收集器可进入失败处理或更重的回收路径。实际名称和恢复方式依实现而定。

存活量增大与突发分配都会压缩余量。并发周期完成过晚也会使空闲空间耗尽。G1 的疏散与大对象条件见[G1](./g1-regions-rset-collection-set.mdx#young-gc)。

调优需先确认存活量、分配速率和周期耗时。降低暂停目标无法直接增加可用空间。

## 8. 回收日志 {#从日志观察回收过程}

JDK 9 及以后可同时记录 GC 与安全点：

```bash
java -Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags -jar app.jar
```

日志应与分配率、吞吐和请求延迟对齐。先区分安全点到达时间与回收工作时间。再按收集器分析回收范围与空间变化。

## 9. 常见问题 {#常见问题}

### 9.1 GC 写屏障与内存屏障 {#gc-写屏障与内存屏障}

GC 写屏障维护引用摘要或标记不变量。JMM 内存屏障约束读写顺序与可见性。两者的正确性目标不同。

### 9.2 安全点的触发来源 {#安全点的触发来源}

GC、类重定义与部分诊断操作会请求全局协调。部分线程操作也可通过 handshake 完成。具体原因应看安全点事件名称。

### 9.3 年轻代容量与性能 {#年轻代容量与性能}

年轻代增大会延长填满时间，但增加单次存活对象处理量。固定总堆下，老年代可用空间也会减少。应根据分配率、存活率和延迟目标验证。

## 10. 面试题 {#面试题}

### 10.1 为什么分代收集需要写屏障和 Remembered Set {#write-barrier-rset}

<!-- 面试来源：
- 阿里巴巴：https://www.nowcoder.com/discuss/353157613372252160
-->

**出现公司**：阿里巴巴

**考察重点**：区分局部回收的外部引用与并发标记的变化记录。

**相关内容**：[分代假设](#分代假设)至[并发标记与对象图变化](#并发标记与对象图变化)。

<details>
<summary>参考回答</summary>

年轻代局部回收需要发现老对象持有的年轻对象。写屏障记录引用变化，卡表或 RSet 缩小扫描范围。回收时只需扫描相关外部区域。

并发标记还有另一项要求：正确处理标记中的引用变化。G1 的 SATB 前置屏障为此记录旧引用。两项职责需分别解释。

</details>

### 10.2 什么是安全点，GC 为什么需要它 {#safepoints}

<!-- 面试来源：
- 阿里云：https://www.nowcoder.com/discuss/401459816646942720
-->

**出现公司**：阿里云

**考察重点**：区分安全点到达、停顿内工作与线程握手。

**相关内容**：[安全点](#安全点)和[Stop-The-World 阶段](#stop-the-world-阶段)。

<details>
<summary>参考回答</summary>

安全点让 JVM 能准确解释线程状态与引用位置。GC 的特定阶段需要稳定状态，因此发起全局协调。等待进入安全状态的时间也影响应用停顿。

并发收集器仍有 STW 阶段。JDK 10 引入的 handshake 可只协调部分线程。诊断时应区分全局安全点与线程局部操作。

</details>

### 10.3 G1 的 SATB 为何记录旧引用，还会留下浮动垃圾？ {#satb-floating-garbage}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：开始快照、前置屏障与存活余量。

**相关内容**：[SATB 与增量更新](#satb-与增量更新)。

<details>
<summary>参考回答</summary>

SATB 要保留标记开始时可达的对象。前置屏障记录被覆盖的旧引用，供标记继续追踪。对象即使后来失去用途，也可因开始快照被保留。它会留到后续回收重新判断，因此需要预留空间。

</details>
