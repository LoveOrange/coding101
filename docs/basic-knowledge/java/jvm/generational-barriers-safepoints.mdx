# 分代回收

**分代回收**是按对象的存活时间，把年轻对象和长期存活对象分开处理的策略。典型的分代堆把大部分新对象放进年轻代并频繁回收，再把满足条件的存活对象移到老年代，减少对它们的反复扫描。这样做依据的是一个经验：多数对象创建后很快就不再被使用。

理解分代回收，需要先讲清只回收年轻代时，怎样找到来自老年代的引用。收集器与应用并发运行、需要暂停线程时，还会遇到引用变化和线程协调的问题。这几类问题分别关系到写屏障与记忆集、并发标记和安全点，不能混为同一种机制。

## 1. 面试核心 {#core}

- 分代收集依据的是**多数对象很快失效**的经验：频繁回收年轻代，减少对长期存活对象的反复扫描。
- 写屏障配合卡表或 RSet **记录跨代引用**，让年轻代回收不用扫描整个老年代，也能找到被老对象持有的年轻对象。[卡](#write-barrier-rset)
- G1 的 SATB 前置写屏障**记录被覆盖的旧引用**，让并发标记仍能追踪到标记开始时可达的对象，代价是留下浮动垃圾。[卡](#satb-floating-garbage)
- **安全点**让 JVM 能准确知道线程的状态和引用位置；线程握手则可以**只协调指定线程**，不必让所有线程一起停下。[卡](#safepoints)

## 2. 分代假设 {#分代假设}

分代要省掉的，是反复扫描长期存活对象的成本。在临时对象很多的服务里，大部分新对象创建后很快就不再被引用，只有少数对象会长期存活。既然如此，频繁回收年轻对象、少去碰老对象，每次回收就能用较少的工作腾出较多的空间。

典型的分代堆会把新对象放进年轻代，对象熬过若干轮回收后，再按策略移到老年代，这一步叫**晋升**。大对象等特殊情况怎么分配，由具体收集器决定。要注意，分代只是收集器的设计选择，Java 语言规范和 JVM 规范都没有要求堆必须分代。

不同收集器的分代方式、区域划分和晋升策略都不一样，Minor、Major、Full 这些词的含义也要结合实现来解释。诊断时应写出收集器和具体的事件名，再确认回收了哪些区域、有没有暂停应用线程。

## 3. 跨代引用与写屏障 {#跨代引用与写屏障}

只回收年轻代时，收集器必须知道有哪些老对象正在引用年轻对象，否则会把还在用的对象当成垃圾。比如下面这行赋值，让一个老对象持有了一个刚创建的对象：

```java
oldOrder.latestEvent = new Event();
```

如果只从线程根和年轻代内部查找，又没有记下这条来自老年代的引用，就可能漏掉仍被 `oldOrder.latestEvent` 持有的 `Event`。把整个老年代扫一遍当然能找到它，但那样就失去了分代回收减少扫描范围的收益。

解决办法是在引用写入时顺手做个记录。**GC 写屏障**是 JVM 在引用更新前后插入的一小段辅助代码，比如上面这次赋值发生时，它会把 `oldOrder` 所在的那段堆地址记到卡表里。**卡表**把堆按固定大小切成一张张「卡」，每个条目对应一段地址；被标为脏的卡表示这段地址里可能有需要检查的引用。回收时只扫描脏卡对应的区域，就能找到具体的引用。

**Remembered Set**（RSet，记忆集）是为局部回收整理好的外部引用信息，记录「哪些区域引用了我」。卡表和 RSet 具体怎么配合，取决于收集器。这些结构的代价是屏障执行时间、额外的内存和扫描摘要的工作，换来的是每次回收只需处理较小的范围。

## 4. 并发标记与对象图变化 {#并发标记与对象图变化}

**并发标记**是收集器在应用继续运行的同时，查找并标记存活对象的过程。应用在这期间会删除、覆盖或新增引用，收集器看到的对象图一直在变。不把关键的变化记下来，就可能漏标仍然存活的对象。**三色模型**用三种状态描述标记进度：

- 白色：还没被发现的对象。
- 灰色：已经发现，但它的引用还没扫描完的对象。
- 黑色：引用已经全部扫描完的对象。

漏标是这样发生的：应用让一个黑色对象新增了一条指向白色对象的引用。黑色对象已经扫描过，收集器不会再回头检查它。如果同时，原本通向这个白色对象、还没被扫描到的旧路径被删掉了，收集器就再也找不到它，一个仍在使用的对象会被当成垃圾回收。只要阻止这两个条件之一，就能避免漏标。

### 4.1 SATB 与增量更新 {#satb-与增量更新}

SATB 保留被删除的旧引用线索，增量更新记录新增的引用，两者都能避免上面的漏标。

**SATB**（Snapshot-At-The-Beginning，开始时快照）是 G1 的做法：以标记开始时的对象图为准，开始时可达的对象本轮都算存活。应用覆盖一个引用之前，前置写屏障先把旧引用记下来，标记线程随后会继续追踪它。这样即使原来的路径被删掉，收集器手里仍有线索找到目标对象。

**增量更新**关注的是新增的引用：应用让已扫描的对象指向未扫描的对象时，收集器记下这次变化，或者安排重新扫描。两种算法维护的都是「存活对象不能漏标」，只是一个盯删除，一个盯新增。

**浮动垃圾**是在并发标记期间已经变得不可达、本轮却仍被保留的对象。SATB 按标记开始时的可达性保留对象，所以会留下这类垃圾，留到后续回收再判断。应用在标记期间还会不断创建新对象，因此并发周期必须为新分配和浮动垃圾都预留空间。

### 4.2 引用屏障的分工 {#引用屏障的分工}

同一次引用更新，可能同时要为两件事做记录。在 G1 里，前置屏障记录旧引用，服务于并发标记；后置屏障处理更新后的跨 Region 引用，服务于 RSet。换句话说，RSet 解决的是「局部回收时去哪里找外部引用」，SATB 解决的是「标记过程中怎么不漏标」。

其他收集器会按自己的算法使用读屏障、写屏障或两者组合。**读屏障**是在读取引用时执行的辅助代码，它把一部分成本放到了读取路径上。理解任何一种屏障，都先问它在维护哪一条正确性条件。

还要注意，GC 屏障和 Java 内存模型（JMM）里的内存屏障是两回事。GC 屏障维护收集器需要的引用信息，内存屏障约束跨线程的内存访问顺序。两者都可能带来额外的机器指令，但要保证的正确性完全不同。

## 5. 安全点 {#安全点}

GC 的某些阶段需要线程状态稳定下来，才能准确找到栈上的对象引用。**安全点**就是这样一种状态：线程停在这里时，JVM 能准确解释它的执行状态和引用所在的位置，可以安全地做全局操作。编译后的代码会在特定位置检查有没有收到安全点请求，收到了就配合 JVM 暂停。

阻塞中的 Java 线程，或者正在执行 native 本地代码的线程，本身就处于可以安全扫描的状态，JVM 不必等它们。这类线程返回 Java 代码之前，会先检查 JVM 是不是正在做全局操作，是的话就等操作结束再继续。所以一个本地方法执行很久，并不会因此拖慢安全点。

### 5.1 全局安全点与线程握手 {#全局安全点与线程握手}

不同操作涉及的线程范围不同，协调方式也可以不同。全局安全点要让所有相关的 Java 线程都停下来。Java 17、21 支持 thread-local handshake（**线程握手**），可以只协调指定的线程，所以有些只针对单个线程的操作，不需要等所有线程一起暂停。

看安全点耗时，要把两段时间分开：

```text
安全点总时间 = 到达安全状态的时间 + 停顿内工作时间
```

即使某个 GC 阶段本身很短，等所有线程到达安全状态的时间也会把总时间拉长。停顿内除了 GC，还可能有引用处理、类卸载等工作，所以要看完整的事件，而不是只看一个阶段。

具体日志解读见[GC 停顿分析](./gc-logs-jfr-pauses.mdx#gc-停顿安全点与系统停顿)。

## 6. Stop-The-World 阶段 {#stop-the-world-阶段}

**Stop-The-World**（STW）指暂停所有应用线程，让 JVM 执行回收或其他全局工作。Serial 和 Parallel 收集器的主要回收工作都在 STW 内完成。G1、ZGC 和 Shenandoah 把一部分标记、整理或重定位工作放到和应用并发执行的阶段，但仍保留用于协调状态的 STW 阶段。

并发并不是免费的：并发工作占用的 CPU 本来可以给应用用，而且回收完成之前，堆还得装得下应用新分配的对象。所以比较收集器时，要把下面几组指标放在一起看：

- 暂停次数和暂停时长的分位数。
- GC 和屏障消耗的 CPU。
- 相同负载下应用的吞吐。
- 并发周期需要预留的堆空间。
- 分配停顿和退化回收的次数与耗时。

暂停变短只是收益的一部分，还要确认吞吐和资源成本符合目标。

## 7. 晋升与分配失败 {#晋升与分配失败}

年轻对象熬过回收后，需要有地方放下被复制或晋升的对象。目标空间不够时，收集器就会进入失败处理，日志里会出现 evacuation failure（疏散失败）、promotion failure（晋升失败）或分配停顿之类的信号，具体名称和恢复方式因收集器而异。

排查这类失败时，先检查空间需求和回收速度：

- 回收后的存活对象总量已经接近堆上限，留给新分配的空间太少。
- 分配或晋升速率突然升高，目标空间很快被用完。
- 大对象增多，对连续空间的需求增加。
- 并发周期启动太晚或执行太久，还没回收完，空闲空间就已经耗尽。

跨代引用增多也会增加扫描成本，但它不直接代表目标空间被占满。要结合阶段耗时，判断是否因为回收变慢而来不及释放空间。

G1 的疏散与大对象处理见[G1](./g1-regions-rset-collection-set.mdx#young-gc)。

调优前先确认存活量、分配速率和周期耗时。调低暂停目标并不能解决空间问题：它会减少每次回收允许安排的工作量，回收变得更频繁，反而可能加重并发周期的压力。空间不足的问题，仍然要从对象保留量和可用余量入手。

## 8. 回收日志 {#从日志观察回收过程}

日志能把前面讲的机制对应到实际的耗时和空间变化。Java 17、21 可以用统一日志同时记录 GC 和安全点：

```bash
java -Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags -jar app.jar
```

先用常规级别的日志建立时间线，再把下面这些信息对起来：

- GC 的触发原因、事件类型和回收范围。
- 各阶段的耗时，确定主要成本在哪里。
- 回收前后的占用和当前容量，以及相同回收范围下存活量的变化。
- 并发周期有没有在可用空间耗尽之前完成。
- 到达安全点的时间和停顿内工作的时间。
- 同一时段的分配率、应用吞吐和请求延迟。

常规日志解释不了问题时，再短期打开对应的详细标签。这样既能拿到需要的阶段信息，也不会让调试日志一直大量写入。

## 9. 常见问题 {#常见问题}

### 9.1 GC 写屏障和 volatile 的内存屏障是一回事吗？ {#gc-写屏障与内存屏障}

不是。GC 写屏障记录引用变化，让局部扫描和并发标记保持正确；`volatile` 涉及的内存屏障约束跨线程读写的顺序和可见性。即使在实现上都表现为额外的指令，也要按各自的目的区分。

### 9.2 安全点只由 GC 触发吗？ {#安全点的触发来源}

不是。除了 GC，类重定义、部分涉及去优化的 VM 操作和某些诊断命令也会请求全局协调；只影响部分线程的操作还可以通过线程握手完成。诊断时应查看安全点日志或 JFR 里的具体事件名称。

### 9.3 年轻代越大，性能越好吗？ {#年轻代容量与性能}

不一定。年轻代变大，填满所需的时间变长，回收频率会下降，但每次要扫描和复制的工作量也会变化：存活对象较多时，单次暂停会变长。总堆大小固定时，年轻代变大还会挤占老年代的余量。所以要结合分配率、存活率和延迟目标实测验证。

## 10. 面试题 {#面试题}

### 10.1 为什么分代收集需要写屏障和 Remembered Set {#write-barrier-rset}

**考察重点**：区分局部回收要找的外部引用，和并发标记要记录的对象图变化。

**相关内容**：[分代假设](#分代假设)至[并发标记与对象图变化](#并发标记与对象图变化)。

<details>
<summary>参考回答</summary>

**写屏障和 RSet 让年轻代回收能找到老对象对年轻对象的引用，又不用遍历整个老年代。**

老对象写入一个指向年轻对象的引用时，写屏障记下这次变化，卡表或 RSet 保存对应的摘要。回收时只扫描这些记录指向的区域，就能把仍被老对象使用的年轻对象保留下来。

代价是屏障的执行时间和摘要占用的内存。并发标记还有另一项需求，就是处理标记期间对象图的变化：G1 用 SATB 前置屏障记录旧引用，其他收集器按各自算法使用增量更新、读屏障或写屏障。这两类职责要分开说明。

</details>

### 10.2 什么是安全点，GC 为什么需要它 {#safepoints}

**考察重点**：区分到达安全点的等待、停顿内的工作和线程握手。

**相关内容**：[安全点](#安全点)和[Stop-The-World 阶段](#stop-the-world-阶段)。

<details>
<summary>参考回答</summary>

**安全点是 JVM 能准确解释线程状态和引用位置、可以安全协调全局操作的状态。**

GC 的部分阶段需要稳定的根集合，或者要更新全局结构，所以必须让线程进入安全状态。等所有线程到达的这段时间，同样会算进应用感受到的停顿。

并发收集器把大量工作移到了并发阶段，但仍保留用于协调的 STW 阶段。只影响部分线程的操作可以用线程握手完成。诊断时既要区分全局协调和线程局部操作，也要把到达时间和停顿内工作时间分开看。

</details>

### 10.3 G1 的 SATB 为何记录旧引用，还会留下浮动垃圾？ {#satb-floating-garbage}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释旧引用怎样维持标记开始时的可达性，以及浮动垃圾为什么需要额外空间。

**相关内容**：[SATB 与增量更新](#satb-与增量更新)。

<details>
<summary>参考回答</summary>

**SATB 记录旧引用，是为了引用被覆盖之后，仍能追踪到标记开始时可达的对象。**

前置屏障在覆盖前把旧引用保存下来，标记线程随后继续处理，这样删除引用就不会导致漏标。

同样因为以开始时的快照为准，对象即使在标记期间变得不可达，本轮也会被保留，这就是浮动垃圾，要等下一轮回收再判断。并发周期中应用还在创建新对象，所以堆里要为这两部分预留空间。

</details>
