# 类加载器

类加载器确定 SPI 的发现范围与插件类型边界。本文负责服务发现、依赖隔离和卸载条件。默认加载流程见[双亲委派模型](./parent-delegation.mdx)。

## 1. 面试核心 {#core}

- `ServiceLoader.load(service)` 使用线程上下文类加载器。[卡](#spi-context-classloader)
- `ServiceLoader` 按需发现并实例化提供者。[卡](#spi-lazy-failure)
- 共享 API 由共同父加载器定义，私有依赖按插件隔离。[卡](#plugin-isolation)
- 普通类的卸载要求其定义加载器可被回收。

## 2. `ServiceLoader` {#serviceloader}

SPI 让调用方依赖服务接口，再发现实现：

```java
public interface PaymentProvider {
    String name();
    PaymentResult charge(PaymentCommand command);
}
```

```java
for (PaymentProvider provider : ServiceLoader.load(PaymentProvider.class)) {
    providers.put(provider.name(), provider);
}
```

类路径中的声明文件位于 `META-INF/services/<接口全名>`。文件按行列出提供者全名，并使用 UTF-8。此部署方式要求提供者有公开无参构造器。

命名模块通过 `uses` 和 `provides ... with ...` 声明服务。显式模块还支持公开静态无参的 `provider()` 方法。它返回的对象需满足服务类型。自动模块仍采用构造器方式。

服务接口、参数和返回类型需要共同可见。提供者实例由迭代过程按需创建。

### 2.1 懒加载与发现失败 {#懒加载与发现失败}

`ServiceLoader.load()` 成功只说明创建了加载器对象。迭代器的 `hasNext()` 或 `next()` 才可触发发现错误。错误类型为 `ServiceConfigurationError`。

配置格式、类可见性和构造器异常都需检查。`stream()` 可先访问 Provider 的类型信息。`Provider.get()` 再取得服务实例。

`ServiceLoader` 会缓存已发现的提供者。`reload()` 清除其缓存，但已有服务实例仍由调用方管理。ServiceLoader 对象本身不支持多线程并发访问。

## 3. 线程上下文类加载器 {#线程上下文类加载器}

框架由父加载器定义，实现却可位于应用层。`ServiceLoader.load(service)` 使用线程上下文加载器。因此，调用方能指定服务的发现范围。

```java
ClassLoader original = Thread.currentThread().getContextClassLoader();
try {
    Thread.currentThread().setContextClassLoader(pluginLoader);
    ServiceLoader<PaymentProvider> loader =
        ServiceLoader.load(PaymentProvider.class);
    // 在此范围内使用 loader。
} finally {
    Thread.currentThread().setContextClassLoader(original);
}
```

线程池任务结束时应恢复原值。否则后续任务会沿用错误的发现范围。长期存活线程还会持有插件加载器。

也可直接调用 `ServiceLoader.load(service, loader)`。这种方式无需修改线程状态。

## 4. 插件隔离 {#插件隔离}

宿主与插件共享 API，私有实现分别加载：

```text
共同父加载器：插件 API、公共协议模型
├── 插件 A 加载器：A 实现与私有依赖
└── 插件 B 加载器：B 实现与私有依赖
```

私有依赖可用 child-first，以允许版本共存。共享 API 与 Java 平台类型保持父优先。若插件再次定义 API，同名接口就会成为另一个类型。

跨边界传参需要使用共享类型。JNI 库、系统属性与文件仍属于进程共享资源。

## 5. JPMS 模块层 {#jpms-模块层}

JPMS 描述模块可读关系和包导出。`ModuleLayer` 建立模块图，并配合加载器定义类型：

```java
ServiceLoader<PaymentProvider> providers =
    ServiceLoader.load(layer, PaymentProvider.class);
```

这条调用在指定层及其父层中发现服务。模块访问规则与加载器类型身份分别生效。

## 6. 资源查找 {#资源查找}

服务声明与配置文件也需要匹配加载策略：

```java
Enumeration<URL> resources =
    loader.getResources("META-INF/services/com.example.PaymentProvider");
```

`getResource()` 返回一个匹配项。`getResources()` 可以枚举多个 JAR 中的同名资源。类与资源使用不同优先级时，会混用不同版本配置。

## 7. 类的卸载 {#类的卸载}

普通类的卸载要求定义加载器可被回收。插件实例、Class 对象与活动调用都会影响可达性。

常见持有来源包括线程上下文加载器、ThreadLocal 和全局注册。停止插件时需取消任务、注销注册，再释放相关引用。`URLClassLoader.close()` 关闭文件资源，并不立即卸载类。

JDK 15 引入的隐藏类有特殊生命周期。默认弱关联隐藏类可早于定义加载器卸载。`ClassOption.STRONG` 则将生命周期关联到加载器。插件普通类按前述加载器条件分析。

## 8. 常见问题 {#常见问题}

### 8.1 服务接口与实现的可见范围 {#服务接口与实现的可见范围}

接口的加载器只看得到它的可见范围。应用层实现可由 TCCL 或显式 loader 参数查找。

### 8.2 提供者的实例化时机 {#提供者的实例化时机}

迭代会按需发现并实例化提供者。`stream()` 支持先检查类型，再调用 `get()`。构造器应避免耗时外部操作。

### 8.3 类隔离与进程资源 {#类隔离与进程资源}

类加载器隔离类型与私有依赖。端口、文件、native 库和系统属性还需单独管理。

### 9.1 Java SPI 为什么常使用线程上下文类加载器 {#spi-context-classloader}

**出现公司**：阿里巴巴、字节跳动

**考察重点**：理解服务接口与实现的可见范围，并管理 TCCL。

**相关内容**：[`ServiceLoader`](#serviceloader)和[线程上下文类加载器](#线程上下文类加载器)。

<details>
<summary>参考回答</summary>

TCCL 让框架按调用方的可见范围发现实现。框架和接口可由父加载器定义，实现则位于应用层。`ServiceLoader.load(service)` 使用当前线程的 TCCL。

临时修改 TCCL 后应在 `finally` 中恢复。否则线程池后续任务会继承错误范围。也可直接向 `ServiceLoader.load(service, loader)` 传入加载器。

</details>

### 9.2 插件系统怎样允许不同版本依赖共存 {#plugin-isolation}

<!-- 面试来源：
- 阿里巴巴：https://www.nowcoder.com/discuss/353157613372252160
-->

**出现公司**：阿里巴巴

**考察重点**：划分共享 API 与私有依赖，并清理加载器持有链。

**相关内容**：[插件隔离](#插件隔离)至[类的卸载](#类的卸载)。

<details>
<summary>参考回答</summary>

每个插件用独立加载器定义实现与私有依赖。私有包可采用子优先。共享 API、协议模型与平台类型保持父优先。

资源查找应采用对应的优先级策略。插件停止时需取消任务并注销全局引用。普通插件类的卸载还要求定义加载器可被回收。

</details>

<details>
<summary>参考回答</summary>

</details>
