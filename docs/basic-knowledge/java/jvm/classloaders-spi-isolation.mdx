# 类加载器

**类加载器**负责查找类的字节流，并将它交给 JVM 定义为运行时类型。使用哪个加载器，会影响框架能发现哪些服务实现，也会影响宿主和插件能否共享同一个类型。

服务发现要解决的是「去哪里找实现」，插件隔离要解决的是「哪些类型共用、哪些各自定义」。插件停止时还要检查哪些引用没有释放，否则加载器和它定义的类会一直留在内存里。这些问题都需要结合加载器之间的关系判断。

## 1. 面试核心 {#core}

- `ServiceLoader` **在遍历时才按需发现和实例化**提供者，所以 `load()` 成功之后，发现错误仍可能在遍历时才出现。[卡](#spi-lazy-failure)
- `ServiceLoader.load(service)` **使用当前线程的上下文类加载器**查找实现，让定义在上层的框架能按应用的可见范围发现下层的服务实现。[卡](#spi-context-classloader)
- 插件系统里，宿主和插件共享的 API **由共同的父加载器定义**，每个插件用**独立的加载器**定义自己的实现和私有依赖。[卡](#plugin-isolation)
- 普通类要卸载，**它的定义加载器必须能被回收**。线程上下文、静态集合或其他长寿命引用还持有这个加载器时，这批类都释放不了。

## 2. `ServiceLoader` {#serviceloader}

**SPI**（Service Provider Interface，服务提供者接口）是一种约定：调用方只依赖一个接口，具体实现在运行时再去发现。负责提供实现的类称为**提供者**。比如支付框架先定义统一的接口：

```java
public interface PaymentProvider {
    String name();
    PaymentResult charge(PaymentCommand command);
}
```

调用方通过 `ServiceLoader` 遍历所有提供者，按名称登记：

```java
for (PaymentProvider provider : ServiceLoader.load(PaymentProvider.class)) {
    providers.put(provider.name(), provider);
}
```

提供者怎样被找到，取决于部署方式。类路径部署时，提供者要写进 `META-INF/services/<接口全名>` 文件，这是一个 UTF-8 文件，每行一个提供者的全名，`ServiceLoader` 按它去找实现类，再用公开的无参构造器创建实例，所以提供者必须有这样的构造器。

模块化部署时，使用方在模块描述符里用 `uses` 声明服务接口，提供方用 `provides ... with ...` 声明实现。显式模块还可以提供一个公开的静态无参方法 `provider()`，由它返回服务对象；自动模块仍然走构造器。

无论哪种方式，调用方和提供者都要共享同一份服务接口、参数类型和返回类型，才能互相调用。第 4 节会看到，这一点在插件隔离时尤其要注意。

### 2.1 懒加载与发现失败 {#懒加载与发现失败}

**懒加载**是把查找和创建推迟到实际使用时。`ServiceLoader` 按这种方式发现提供者，所以 `load()` 成功只说明创建了服务加载对象，并不说明所有实现都没问题。

真正的查找发生在调用迭代器的 `hasNext()` 或 `next()` 时。这时配置文件格式错误、实现类不可见、构造器抛异常，都会以 `ServiceConfigurationError` 报出来，具体原因要看它的异常链。上面的 `for` 循环里，前两个提供者可能已经登记成功，第三个才失败。

如果想先筛选类型、再决定要不要实例化，可以用 `stream()` 拿到 `Provider`，先看它的类型信息，合适了再调用 `Provider.get()` 创建实例。

`ServiceLoader` 会缓存已经加载的提供者。`reload()` 清掉的是它内部的缓存，调用方自己保存的实例（比如上面的 `providers`）仍要自己管理。另外，同一个 `ServiceLoader` 对象不支持多线程并发使用。

## 3. 线程上下文类加载器 {#线程上下文类加载器}

父加载器不会反过来搜索子加载器里的类。假设服务接口和框架代码由父加载器定义，提供者只在应用或插件的子加载器中可见，框架用自己的加载器就找不到这些提供者。子加载器可以向父加载器委派查找，但父委派不会自动建立反方向的查找关系。

**线程上下文类加载器**（TCCL，Thread Context ClassLoader）是保存在当前线程上的一个类加载器，用来解决这个问题。`ServiceLoader.load(service)` 用它来查找服务，框架因此能按应用或插件的可见范围发现实现：

```java
ClassLoader original = Thread.currentThread().getContextClassLoader();
try {
    Thread.currentThread().setContextClassLoader(pluginLoader);
    ServiceLoader<PaymentProvider> loader =
        ServiceLoader.load(PaymentProvider.class);
    // 在此范围内使用 loader。
} finally {
    Thread.currentThread().setContextClassLoader(original);
}
```

这段代码在 `finally` 里把 TCCL 恢复成原来的值，因为 TCCL 是线程上的可变状态。如果不恢复，线程池里的下一个任务复用这个线程时，就会拿着上一个插件的加载器去找类，找到错误应用的类。长期存活的线程还会一直持有插件加载器，让插件卸载不掉。

如果手里已经有明确的加载器，也可以直接调用 `ServiceLoader.load(service, loader)`，这样就不用改线程状态。

## 4. 插件隔离 {#插件隔离}

插件需要使用不同版本的依赖时，可以给每个插件建一个独立的类加载器。宿主和插件之间传递的 API 和协议模型，则由它们共同的父加载器定义：

```text
共同父加载器：插件 API、公共协议模型
├── 插件 A 加载器：A 实现与私有依赖
└── 插件 B 加载器：B 实现与私有依赖
```

私有依赖可以采用 **child-first**（子优先），也就是先在插件自己的路径里找，找不到再委派给父加载器。这样插件 A 和 B 就能各自使用自己的依赖版本。共享 API 和 Java 平台类型则保持父优先，保证双方用的是同一个类型。

为什么共享 API 不能也子优先？因为 JVM 用「类名加定义加载器」区分类型。如果插件自己又定义了一份 `PaymentProvider`，它在 JVM 看来就是另一个类型。插件的实现类实现的是插件自己的那个接口，宿主把它转换成宿主的 `PaymentProvider` 时就会抛 `ClassCastException`。所以跨边界传递的参数也都要使用共享类型。

类隔离只隔离类型和依赖。JNI 库（Java 调用本地代码时加载的库）、系统属性这些进程级资源仍然是共享的，要统一管理，见[类隔离与进程资源](#类隔离与进程资源)。

## 5. JPMS 模块层 {#jpms-模块层}

**JPMS**（Java Platform Module System，Java 平台模块系统）用来声明模块之间的依赖和包的可见性：哪些模块可以读取哪些模块，哪些包允许外部访问。

`ModuleLayer` 表示一组模块和它们之间的依赖关系，可以搭配一个或多个类加载器来定义类型。需要按模块层发现服务时，可以这样调用：

```java
ServiceLoader<PaymentProvider> providers =
    ServiceLoader.load(layer, PaymentProvider.class);
```

它在指定的层和它的父层里发现服务。注意模块规则和类加载器是两套规则：模块规则控制能不能访问，类加载器决定由谁查找和定义类型，两者都满足才能用。

## 6. 资源查找 {#资源查找}

框架除了加载类，还会读配置文件、模板和服务声明。多个 JAR 可能包含同名资源，所以要分清「找一个」和「找全部」：

```java
Enumeration<URL> resources =
    loader.getResources("META-INF/services/com.example.PaymentProvider");
```

`getResource()` 只返回一个匹配项，`getResources()` 会枚举当前加载器可见的同名资源。这个例子可以用来检查查找范围内有哪些 JAR 提供了支付服务的声明。

自己实现 child-first 时，资源查找和类查找要用同样的优先级。否则会出现类来自插件的私有库、配置却来自父加载器里另一个版本的情况，两者对不上。

## 7. 类的卸载 {#类的卸载}

普通插件类要卸载，前提是定义它的加载器能被垃圾回收。而加载器是否可达，不只看你有没有清空保存它的变量：插件对象、`Class` 对象、正在执行的调用，都会通过「对象 → 类 → 加载器」这条链让它保持可达。

卸载失败时，要检查哪些长期存活的对象还持有插件引用：

- 长期存活的线程，以及它们的 TCCL，会持有插件加载器。
- 没停止的执行器、定时任务和驱动线程，还在使用插件对象。
- 父加载器中某个类的静态集合，保存了插件实例或 `Class` 对象。
- `ThreadLocal` 值、日志缓存、MBean 和 JDBC Driver 注册，保留了插件引用。MBean 是注册给监控管理系统使用的对象。

所以停止插件时，要取消任务、停止线程、注销全局注册，再清理上下文和其他引用。`URLClassLoader.close()` 只关闭加载器打开的 JAR 文件等资源，并不会卸载类，类的卸载仍要等回收条件满足。

类元数据保存在 Metaspace 里。如果每次热部署后 Metaspace 都在增长，就同时观察加载器的数量，确认旧的加载器是不是还被持有。

Java 17、21 里的**隐藏类**是例外，它们由框架在运行时生成和使用，生命周期有自己的规则。默认情况下，隐藏类和定义加载器是弱关联的，可以比加载器更早卸载；用 `ClassOption.STRONG` 定义时，生命周期才和加载器绑定在一起。普通插件类仍然按前面的条件分析。

## 8. 常见问题 {#常见问题}

### 8.1 为什么用接口的类加载器找不到实现？ {#服务接口与实现的可见范围}

接口由父加载器定义、实现在应用层时，只用接口的加载器是看不到下层实现的。所以调用方要通过 TCCL，或者显式传入 `loader` 参数，指定在哪个范围里发现服务。

### 8.2 提供者的构造器适合执行耗时的外部操作吗？ {#提供者的实例化时机}

不适合。构造器在遍历、创建提供者时执行，外部操作一旦卡住，服务发现也会一起停下来。构造器应保持轻量，把耗时操作放到可单独控制的步骤里。一个提供者创建失败时，还要决定如何处理已经创建的实例，避免服务只登记了一部分却被当作完整结果使用。

### 8.3 独立的类加载器能隔离插件的全部资源吗？ {#类隔离与进程资源}

不能。类加载器隔离的是类型和私有依赖，插件仍在同一个进程里。端口、文件、线程、本地库和系统属性要单独管理。由宿主保存的进程级单例，也要明确哪些插件可以共用、由谁负责释放。

## 9. 面试题 {#面试题}

### 9.1 Java SPI 为什么常使用线程上下文类加载器 {#spi-context-classloader}

**考察重点**：解释父加载器为何看不到应用层实现，以及线程池任务为何需要恢复 TCCL。

**相关内容**：[`ServiceLoader`](#serviceloader)和[线程上下文类加载器](#线程上下文类加载器)。

<details>
<summary>参考回答</summary>

**TCCL 让框架能按调用方的可见范围查找服务实现。**

框架和接口由父加载器定义、实现在应用层时，父加载器不会反向搜索应用的子加载器。`ServiceLoader.load(service)` 使用当前线程的 TCCL；只要这个加载器能看到提供者，框架就能在该范围内发现实现。

临时修改 TCCL 后要在 `finally` 里恢复，否则线程池里的后续任务会拿着错误的加载器找类，线程也会长期持有插件加载器。调用方如果已经有明确的加载器，也可以直接传给 `ServiceLoader.load(service, loader)`。

</details>

### 9.2 插件系统怎样允许不同版本依赖共存 {#plugin-isolation}

**考察重点**：说明共享 API 与私有依赖分别由谁定义，以及卸载时需要清理哪些引用。

**相关内容**：[插件隔离](#插件隔离)至[类的卸载](#类的卸载)。

<details>
<summary>参考回答</summary>

**每个插件用独立的加载器定义自己的实现和私有依赖，不同版本的依赖就能共存。**

私有包采用子优先，宿主 API、协议模型和平台类型保持父优先。这样既隔离了依赖，又保证跨边界传参时双方用的是同一个类型。

配置和服务声明的查找也要采用同样的策略，防止类和配置来自不同版本。插件停止时，要停止线程和定时任务，注销驱动、MBean 和静态注册，并恢复 TCCL。这些引用都释放后，定义加载器才可能被回收，普通插件类才能卸载。

</details>

### 9.3 ServiceLoader.load 成功后，为何遍历仍会失败？ {#spi-lazy-failure}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释懒发现为何让错误延后到遍历阶段，并根据异常链区分配置与实例化失败。

**相关内容**：[懒加载与发现失败](#懒加载与发现失败)。

<details>
<summary>参考回答</summary>

**因为提供者要到遍历时才按需发现和创建，`load()` 成功时还没有验证任何实现。**

遍历过程中遇到配置错误、实现类不可见或构造器异常，都会抛出 `ServiceConfigurationError`。

排查时保留完整的异常链，再核对服务声明、使用的加载器和提供者的构造器。如果只想先筛选实现类型，可以用 `stream()`，把实例化推迟到 `Provider.get()`。

</details>
