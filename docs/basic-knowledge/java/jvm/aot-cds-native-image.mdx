# Java 启动优化

Java 启动优化可以复用类信息，也可以提前编译代码。本文比较 Java 17、21 的 CDS、JIT 与 Native Image。运行期编译机制见[分层编译](./interpreter-tiered-compilation.mdx)。

## 1. 面试核心 {#core}

- CDS 复用预处理类信息，运行进程仍使用 HotSpot。
- JIT 在运行时编译热点代码，Native Image 在构建时生成机器码。[卡](#jit-vs-aot)
- Native Image 用闭世界分析生成原生程序。[卡](#native-image-fit)
- 构建期初始化的静态状态会进入 Native Image 产物。[卡](#native-initialization)

## 2. CDS {#cds}

CDS 将预处理类信息写入共享归档。HotSpot 启动时映射归档，减少重复处理。同机多个 JVM 可以共享只读页面。

Application CDS 将应用类纳入归档。Java 17、21 可在应用运行后生成动态归档：

```bash
java -XX:ArchiveClassesAtExit=app.jsa -cp app.jar com.example.Main
java -XX:SharedArchiveFile=app.jsa -Xlog:cds=info -cp app.jar com.example.Main
```

第一条命令在正常退出时生成归档。第二条命令加载归档，并输出加载情况。应用仍保留动态类加载、反射和 JIT。

CDS 的收益集中在启动与共享内存。长时间服务还需单独测量稳定吞吐。

## 3. CDS 归档兼容性 {#jdk-aot-cache}

Java 17、21 的 CDS 归档依赖生成时的运行环境。生成与加载归档应使用相同 JDK 构建。应用 JAR、类路径或关键选项变化时，应重新生成归档。

默认 `-Xshare:auto` 允许归档失效时继续启动。验证归档可用性可用 `-Xshare:on`；加载失败时 JVM 会退出。

## 4. CDS 与 JIT {#aot-cache-与-jit}

CDS 减少类信息的重复处理。热点机器码仍由 JIT 根据本次运行画像生成。优化假设失效后，JIT 代码也可以去优化。

这种组合适合保留 HotSpot 部署方式的服务。额外成本是归档生成、存储和兼容性验证。

## 5. GraalVM Native Image {#graalvm-native-image}

Native Image 从入口分析静态可达代码。构建产物包含可达代码和所需运行时：

```bash
native-image -jar app.jar
```

产物以原生程序启动，自带所需的内存管理机制。CLI、函数计算和频繁冷启动服务重视这类收益。构建耗时、RSS 和稳定吞吐需在目标负载下测量。

## 6. 闭世界假设 {#闭世界假设}

构建时需要确定运行所需的代码与资源。静态分析难以发现的动态访问需补充元数据。常见项目包括反射、JNI、代理和资源文件。

GraalVM for JDK 21 用 `reflect-config.json` 声明反射访问：

```json
[
  {
    "name": "com.example.PaymentHandler",
    "allDeclaredConstructors": true
  }
]
```

构建时用 `-H:ReflectionConfigurationFiles=reflect-config.json` 加载文件。框架可以生成部分反射配置。Tracing Agent 也能记录测试中发生的动态访问。未执行的分支仍需单独覆盖。

任意新字节码的运行期加载超出闭世界边界。插件清单和动态生成机制需在迁移时逐项验证。

## 7. 构建期初始化 {#构建期初始化}

Native Image 可在构建时执行类初始化。初始化产生的对象会进入 image heap。读取环境变量或路径的静态字段也会保存当时结果。

环境相关类应在运行时初始化：

```bash
native-image --initialize-at-run-time=com.example.EnvironmentConfig -jar app.jar
```

纯计算类可评估 `--initialize-at-build-time`。配置要使用明确类名或包范围。部署前应更换环境值，验证产物读取的是运行环境。

## 8. 三种方案的比较 {#三种方案的比较}

| 方案 | 运行形态 | 主要收益 | 额外成本 |
| --- | --- | --- | --- |
| HotSpot JIT | 运行时编译热点代码。 | 根据运行画像优化。 | 启动后的预热与编译。 |
| CDS 与 JIT | HotSpot 与共享归档。 | 减少类处理，共享只读页面。 | 归档兼容性验证。 |
| Native Image | 独立原生程序。 | 减少冷启动工作。 | 闭世界适配与构建。 |

对比应覆盖 ready 时间、首批请求与稳定吞吐。还需记录 P99、RSS、构建时间和诊断成本。

## 9. 常见问题 {#常见问题}

### 9.1 AOT 与 JIT 的性能比较 {#aot-与-jit-的性能比较}

AOT 在运行前编译代码，JIT 利用本次运行画像。短任务更重视启动，长时间服务更重视稳定吞吐。Java 17、21 可用 CDS 减少类处理，并保留 JIT。

### 9.2 Native Image 的反射支持 {#native-image-的反射支持}

Native Image 支持构建时已知的反射目标。目标由静态分析识别，或通过元数据补充。

### 9.3 CDS 归档的版本兼容性 {#aot-cache-的版本兼容性}

归档随应用和运行环境一起管理。应用、JDK 或关键选项改变时，应重新生成归档。使用 `-Xlog:cds=info` 验证实际加载结果。

## 10. 面试题 {#面试题}

### 10.1 JIT 和 AOT 有什么区别 {#jit-vs-aot}

**出现公司**：去哪儿、淘天、拼多多

**考察重点**：区分运行期编译、类信息归档与原生编译产物。

**相关内容**：[CDS](#cds)至[闭世界假设](#闭世界假设)。

<details>
<summary>参考回答</summary>

JIT 在运行时编译代码，AOT 在运行前编译代码。JIT 能利用本次负载的类型和分支画像。AOT 则以构建成本换取启动收益。

Java 17、21 的 CDS 归档类信息，机器码仍由 JIT 生成。Native Image 通过闭世界分析生成原生程序。反射等动态访问需在构建时被发现或声明。

</details>

选择依据应包括真实请求下的启动与稳定性能。还需比较构建耗时、RSS 和诊断能力。

</details>

### 10.3 Native Image 为何会读到构建机的配置，怎样处理？ {#native-initialization}

<details>
<summary>参考回答</summary>

</details>
