# Java 启动优化

Java 启动优化可以复用类信息，也可以提前编译代码。本文比较 CDS、JDK 24—26 AOT Cache 与 Native Image。运行期编译机制见[分层编译](./interpreter-tiered-compilation.mdx)。

## 1. 面试核心 {#core}

- CDS 复用预处理类信息，运行进程仍使用 HotSpot。
- JDK 24 的 AOT Cache 缓存类加载与链接结果。[卡](#jit-vs-aot)
- JDK 25 的 JEP 515 将方法画像加入 AOT Cache。
- Native Image 用闭世界分析生成原生程序。[卡](#native-image-fit)
- 构建期初始化的静态状态会进入 Native Image 产物。[卡](#native-initialization)

## 2. CDS {#cds}

CDS 将预处理类信息写入共享归档。HotSpot 启动时映射归档，减少重复处理。同机多个 JVM 可以共享只读页面。

Application CDS 将应用类纳入归档。JDK 17 可用动态归档训练应用：

```bash
java -XX:ArchiveClassesAtExit=app.jsa -cp app.jar com.example.Main
java -XX:SharedArchiveFile=app.jsa -Xlog:cds=info -cp app.jar com.example.Main
```

第一条命令在正常退出时生成归档。第二条命令加载归档，并输出加载情况。应用仍保留动态类加载、反射和 JIT。

CDS 的收益集中在启动与共享内存。长时间服务还需单独测量稳定吞吐。

## 3. JDK AOT Cache {#jdk-aot-cache}

AOT Cache 的能力按 JDK 版本增加：

| 版本 | 功能 |
| --- | --- |
| JDK 24，JEP 483 | 缓存类加载与链接结果。 |
| JDK 25，JEP 514 | 用单条训练命令生成缓存。 |
| JDK 25，JEP 515 | 复用训练得到的方法画像。 |
| JDK 26，JEP 516 | 支持与收集器无关的对象缓存格式。 |

JDK 25—26 可使用以下命令：

```bash
java -XX:AOTCacheOutput=app.aot -cp app.jar com.example.Main
java -XX:AOTCache=app.aot -Xlog:aot=info -cp app.jar com.example.Main
```

训练结束后，JVM 生成缓存。生产启动日志用于确认缓存是否成功加载。训练应覆盖真实启动路径，并使用隔离的外部依赖。

缓存要求兼容的应用、JDK、CPU 架构和操作系统。关键 JVM 选项变化也会影响兼容性。发布流程应同步生成、验证和替换缓存。

JDK 26 的 JEP 516 让 ZGC 也能使用对象缓存。JDK 24—26 的这些功能仍由 JIT 生成热点机器码。

## 4. AOT Cache 与 JIT {#aot-cache-与-jit}

AOT Cache 减少类加载、链接和画像收集的重复工作。JIT 继续根据本次负载编译代码。它也可以在优化假设失效后去优化。

这种组合适合保留 HotSpot 部署方式的服务。额外成本是训练时间、缓存空间和兼容性验证。

## 5. GraalVM Native Image {#graalvm-native-image}

Native Image 从入口分析静态可达代码。构建产物包含可达代码和所需运行时：

```bash
native-image -jar app.jar
```

产物以原生程序启动，自带所需的内存管理机制。CLI、函数计算和频繁冷启动服务重视这类收益。构建耗时、RSS 和稳定吞吐需在目标负载下测量。

## 6. 闭世界假设 {#闭世界假设}

构建时需要确定运行所需的代码与资源。静态分析难以发现的动态访问需补充元数据。常见项目包括反射、JNI、代理和资源文件。

以下元数据声明反射访问的构造器：

```json
{
  "reflection": [
    {
      "type": "com.example.PaymentHandler",
      "allDeclaredConstructors": true
    }
  ]
}
```

框架可以生成部分 Reachability Metadata。Tracing Agent 也能记录测试中发生的动态访问。未执行的分支仍需单独覆盖。

任意新字节码的运行期加载超出闭世界边界。插件清单和动态生成机制需在迁移时逐项验证。

## 7. 构建期初始化 {#构建期初始化}

Native Image 可在构建时执行类初始化。初始化产生的对象会进入 image heap。读取环境变量或路径的静态字段也会保存当时结果。

环境相关类应在运行时初始化：

```bash
native-image --initialize-at-run-time=com.example.EnvironmentConfig -jar app.jar
```

纯计算类可评估 `--initialize-at-build-time`。配置要使用明确类名或包范围。部署前应更换环境值，验证产物读取的是运行环境。

## 8. 三种方案的比较 {#三种方案的比较}

| 方案 | 运行形态 | 主要收益 | 额外成本 |
| --- | --- | --- | --- |
| CDS | HotSpot 与共享归档。 | 减少类处理，共享只读页面。 | 归档兼容性验证。 |
| JDK AOT Cache | HotSpot 与训练缓存。 | 减少启动与预热工作。 | 训练与缓存管理。 |
| Native Image | 独立原生程序。 | 减少冷启动工作。 | 闭世界适配与构建。 |

对比应覆盖 ready 时间、首批请求与稳定吞吐。还需记录 P99、RSS、构建时间和诊断成本。

## 9. 常见问题 {#常见问题}

### 9.1 AOT 与 JIT 的性能比较 {#aot-与-jit-的性能比较}

AOT 提前完成部分工作，JIT 利用本次运行画像。短任务更重视启动，长时间服务更重视稳定吞吐。AOT Cache 可以与 JIT 共同使用。

### 9.2 Native Image 的反射支持 {#native-image-的反射支持}

Native Image 支持构建时已知的反射目标。目标由静态分析识别，或通过元数据补充。

### 9.3 AOT Cache 的版本兼容性 {#aot-cache-的版本兼容性}

缓存随应用和运行环境一起管理。应用、JDK 或关键选项改变时，应重新生成缓存。使用 `-Xlog:aot=info` 验证实际加载结果。

## 10. 面试题 {#面试题}

### 10.1 JIT 和 AOT 有什么区别 {#jit-vs-aot}

**出现公司**：去哪儿、淘天、拼多多

**考察重点**：区分运行期编译、训练缓存与原生编译产物。

**相关内容**：[CDS](#cds)至[闭世界假设](#闭世界假设)。

<details>
<summary>参考回答</summary>

JIT 在运行时编译代码，AOT 将工作提前到运行前。JIT 能利用本次负载的类型和分支画像。AOT 则以构建或训练成本换取启动收益。

JDK 24—26 的 AOT Cache 保留 HotSpot 与 JIT。Native Image 通过闭世界分析生成原生程序。反射等动态访问需在构建时被发现或声明。

</details>

选择依据应包括真实请求下的启动与稳定性能。还需比较构建耗时、RSS 和诊断能力。

</details>

### 10.3 Native Image 为何会读到构建机的配置，怎样处理？ {#native-initialization}

<details>
<summary>参考回答</summary>

构建期初始化会将静态状态写入 image heap。若静态字段读取环境变量，产物就会保留构建时的值。可用 `--initialize-at-run-time=com.example.EnvironmentConfig` 延后初始化。随后在不同环境中验证配置读取结果。

</details>
