# Java 启动优化

Java 启动优化可以把一部分运行时工作提前完成：CDS 保存处理过的类信息，供后续启动复用；GraalVM Native Image 则在构建时编译代码，产出独立运行的原生程序。它们减少的工作不同，也有不同的适用条件。

启动时间和预热时间也要分开看。应用开始接收请求后，JIT 仍可能继续编译热点代码，逐渐改善性能。CDS 保留这套运行方式；Native Image 把编译提前，但要求运行时需要的代码在构建时就已确定，反射、动态代理和初始化逻辑都要检查。面试中比较这些方案，要说明省掉了哪些工作、增加了哪些限制。本文的范围是 Java 17 和 21。

## 1. 面试核心 {#core}

- CDS 把预处理过的类信息保存为共享归档，HotSpot 启动时**直接映射复用**，同一台机器上的多个 JVM 还能共享其中的只读页面。
- JIT 在运行时**根据本次运行的类型和分支信息**编译热点代码；AOT 在**运行之前**就生成机器码。[卡](#jit-vs-aot)
- Native Image 在构建时分析可达代码并生成原生程序，**适合重视冷启动和初始内存的短生命周期应用**。[卡](#native-image-fit)
- Native Image 用到的反射等动态访问目标，**必须在构建时被静态分析发现，或者通过元数据声明**。
- Native Image 构建期初始化产生的静态状态**会进入产物**，和环境有关的配置要留到运行期再读。[卡](#native-initialization)

## 2. CDS {#cds}

**CDS**（Class Data Sharing，类数据共享）把预处理后的类信息写进一个共享归档文件，HotSpot 启动时通过内存映射直接使用它，不用每次都重新解析这些类。

每个 JVM 启动时都要加载 `java.lang.String`、`java.util.HashMap` 这样一大批基础类，而且每次处理的结果都一样。CDS 把这份结果存下来，启动时就省掉了重复的解析工作。归档里的只读部分映射进内存后，同一台机器上的多个 JVM 还能共享这些页面，节省内存。Oracle JDK 17、21 自带一份默认 CDS 归档，里面是一组核心类，不需要额外配置。

**AppCDS**（Application CDS）把应用自己的类也放进归档。Java 17、21 支持在应用退出时生成动态归档，供之后的启动使用：

```bash
java -XX:ArchiveClassesAtExit=app.jsa -cp app.jar com.example.Main
java -XX:SharedArchiveFile=app.jsa -Xlog:cds=info -cp app.jar com.example.Main
```

第一条命令正常运行应用，并在应用正常退出时生成 `app.jsa`。第二条命令加载这份归档，`-Xlog:cds=info` 输出归档的实际加载情况。动态归档只记录这次运行中加载过的应用类，所以生成时要把真实的启动过程走完整；同时因为它会真的运行应用，应该放在隔离的测试环境里做。

CDS 不改变程序的运行方式：应用仍然由完整的 HotSpot JVM 运行，动态类加载、反射和 JIT 都照常可用。收益大小取决于应用规模，以及启动时有多少时间花在处理类上。启动时间的改善不能直接代表稳定期吞吐的改善，后者需要单独测量。

## 3. CDS 归档兼容性 {#jdk-aot-cache}

CDS 归档和生成它的应用、JDK 是配套的，发布时要当作一个整体管理。生成和加载归档要用同一个 JDK 构建，操作系统和 CPU 架构也要兼容；应用 JAR、类路径或影响归档的 JVM 选项变了，就要重新生成。

归档无法使用时，默认的 `-Xshare:auto` 允许 JVM 不使用归档继续启动。因此，应用能启动不代表归档生效了，还要看 `-Xlog:cds=info` 的日志。测试归档能否使用时，可以改用 `-Xshare:on`，让加载失败直接导致 JVM 退出。

## 4. CDS 与 JIT {#aot-cache-与-jit}

CDS 和 JIT 处理的是不同阶段的工作，可以同时使用：CDS 减少类信息的重复处理，JIT 负责在运行时编译热点代码。

**JIT**（Just-In-Time，即时编译）在程序运行过程中，把执行频繁、值得优化的热点代码编译成机器码。它会收集本次运行的类型和分支信息，这些信息称为**运行画像**（profile），再据此生成适合当前负载的机器码。比如某个接口调用点在实际运行中总是同一个实现类，JIT 就可以按这个实现类做内联。如果后来出现了别的实现类，优化的假设就不成立了，JVM 会退出这段优化代码，回到解释执行，这个过程叫**去优化**（deoptimization），之后再按新的运行信息重新编译。

所以 CDS 加 JIT 的组合，既减少了启动时的类处理，又保留了针对真实负载的优化能力。代价是启动后的预热和编译开销依然存在，另外还要承担归档的生成、存储和兼容性验证。

## 5. GraalVM Native Image {#graalvm-native-image}

**AOT**（Ahead-Of-Time，提前编译）是在程序运行之前就把代码编译成机器码。GraalVM Native Image 就是一种 AOT 方案：它从程序入口出发，追踪所有能调用到的代码，把这些代码和所需的运行时一起编译进一个原生可执行文件：

```bash
native-image -jar app.jar
```

生成的产物作为独立的原生程序启动，不需要另行启动 HotSpot，内存管理等运行时机制也编在里面。**冷启动**是新进程从启动到开始服务的过程。Native Image 把类处理、编译等工作提前到构建阶段，可以减少冷启动的工作量和初始内存占用。

短生命周期或频繁启动的应用更值得评估这些收益：

- 命令行工具（CLI）通常执行一次任务就退出，启动时间在总耗时里占比很高。
- 函数计算会频繁创建新实例，启动时间直接算进请求延迟。
- 按需伸缩的服务需要快速加实例，新实例的首批请求体验很重要。

迁移到 Native Image 后，构建时间、产物体积和调试方式都会变。稳定期吞吐也要用目标负载实测，再判断启动收益值不值得这些成本。

## 6. 闭世界假设 {#闭世界假设}

**闭世界假设**是指 Native Image 在构建时就要确定运行所需的代码，运行时不能再任意加载新的类。需要随程序打包的资源，也要在构建时纳入产物。

动态访问会让这一步变得困难。代码里写了 `new PaymentHandler()`，分析器可以直接发现目标；但 `Class.forName(name)` 里的 `name` 如果来自运行时配置，分析器就无法仅凭这段代码确定目标。这时需要补充**元数据**，也就是声明运行时要访问哪些类、成员或资源的配置。如果目标没有通过其他途径被发现或声明，运行时访问就可能失败。

迁移时要逐一检查这些动态访问目标：

- 反射和按名称加载的类，要明确实际访问哪些类和成员。
- 动态代理要明确代理的接口。JNI（Java 与本地代码交互的接口）要声明本地代码会访问的 Java 元素。
- 序列化要声明运行时需要恢复的对象类型。
- 需要从类路径读取的配置文件、模板等资源，要打进构建产物。

GraalVM for JDK 21 用 `reflect-config.json` 声明反射访问：

```json
[
  {
    "name": "com.example.PaymentHandler",
    "allDeclaredConstructors": true
  }
]
```

这份配置声明 `PaymentHandler` 的所有已声明构造器都可以通过反射调用。构建时用 `-H:ReflectionConfigurationFiles=reflect-config.json` 加载它。

这些配置不必全部手写。框架可以生成一部分；Tracing Agent 能在应用运行时记录实际发生的动态访问。但它只能记录测试真正走过的分支，没走到的分支还要靠补充测试或手写配置。因此，构建成功也不能证明反射配置完整，遗漏可能直到部署后第一次访问目标时才暴露。

运行期加载任意新字节码，本身就超出了闭世界的边界。所以自定义类扫描、插件机制、运行时字节码生成，以及第三方库里的动态行为，都要在迁移时逐项验证。

## 7. 构建期初始化 {#构建期初始化}

Native Image 可以在构建时执行一部分类的初始化，以减少启动工作。**image heap** 是保存进原生程序的初始堆对象集合，构建期初始化留下的对象可以进入其中，供程序启动后使用。

如果静态字段在构建期初始化时读取环境变量，读到的就是构建机上的值。这个值随对象保存进产物后，即使部署环境已经改变，程序仍可能使用构建机的配置。

检查初始化代码时，要特别注意这些和环境有关的状态：

- 时区和环境变量会随部署环境变化。
- 证书内容和机器上的路径，可能只在构建机上有效。
- 随机数如果在构建时生成并作为普通数值保存，每次运行都会用同一个值。

这样的类应该放到运行时初始化。例如下面把 `EnvironmentConfig` 推迟到程序运行时：

```bash
native-image --initialize-at-run-time=com.example.EnvironmentConfig -jar app.jar
```

这样 `EnvironmentConfig` 里的环境读取就发生在部署机器上，而不是构建时。反过来，纯计算、结果和环境无关的类，可以评估用 `--initialize-at-build-time` 提前初始化。

配置时写清楚类名或包的范围，明确哪些类提前初始化、哪些推迟。部署前用同一个产物在不同环境里运行，改一改配置值，确认程序读到的是当前环境的值。

## 8. 三种方案的比较 {#三种方案的比较}

选方案时，先看应用更在意启动速度还是长期吞吐，再比较部署方式和适配成本：

| 方案 | 运行形态 | 主要收益 | 额外成本 |
| --- | --- | --- | --- |
| HotSpot JIT | 运行时编译热点代码。 | 根据运行画像优化。 | 启动后的预热与编译。 |
| CDS 与 JIT | HotSpot 与共享归档。 | 减少类处理，共享只读页面。 | 归档兼容性验证。 |
| Native Image | 独立原生程序。 | 减少冷启动工作。 | 闭世界适配与构建。 |

性能验证要用目标框架和真实请求，分别记录运行和交付指标：

- 进程启动到 ready 的时间，也就是服务能接收请求之前的等待时间。
- 首批请求的耗时，看初始化和预热对它们的影响。
- 稳定期吞吐和 P99 延迟。P99 表示 99% 的请求耗时都不超过这个值。
- RSS，也就是进程驻留在物理内存中的页面总量。
- 构建耗时、产物体积和发布复杂度，判断交付成本能否接受。
- 日志、性能分析和故障诊断方式，确认出问题时能拿到需要的证据。

一个简单 Hello World 的启动时间只反映很小一段执行过程，最终选择要以真实应用的测量结果为准。

## 9. 常见问题 {#常见问题}

### 9.1 AOT 一定比 JIT 快吗？ {#aot-与-jit-的性能比较}

不一定，要看应用运行多久、负载是否稳定。AOT 提前编译，省掉了运行时的准备工作；JIT 能利用本次运行真实的类型和分支信息做优化。短任务更看重启动，长期服务还要比较稳定期吞吐。在 Java 17、21 上，也可以用 CDS 减少类处理，同时保留 JIT 的运行期优化。

### 9.2 Native Image 支持反射吗？ {#native-image-的反射支持}

支持，但只支持构建时已知的反射目标。目标可以由静态分析识别，也可以通过元数据声明。如果要访问的类或成员到运行时才从任意外部配置里确定，就得先把所有允许的目标列出来，纳入构建。

### 9.3 CDS 归档能跨 JDK 版本复用吗？ {#aot-cache-的版本兼容性}

不能直接复用。CDS 归档要和生成它时的 JDK 构建匹配，所以应该和应用、运行环境一起管理。应用、JDK、操作系统、CPU 架构或关键 JVM 选项变了，都要重新验证并按需重新生成。部署时用 `-Xlog:cds=info` 确认归档实际是否加载。

## 10. 面试题 {#面试题}

### 10.1 JIT 和 AOT 有什么区别 {#jit-vs-aot}

**考察重点**：解释编译发生的时机，以及运行画像如何影响启动和稳定性能。区分类信息归档与原生编译产物。

**相关内容**：[CDS](#cds)至[闭世界假设](#闭世界假设)。

<details>
<summary>参考回答</summary>

**JIT 在程序运行时编译热点代码，AOT 在运行前编译代码，两者能利用的信息不同，承担编译成本的时机也不同。**

JIT 能收集真实的执行热度、类型和分支信息，据此优化，代价是预热时间和运行期的编译资源。AOT 把编译提前到构建阶段，减少了启动准备，但它依据的静态分析未必能代表实际负载。

Java 17、21 的 CDS 归档保存的是类信息，不是机器码，热点代码仍由 JIT 编译。Native Image 则通过闭世界分析生成原生程序，它用到的反射目标、资源和其他动态访问，必须在构建时被发现或声明。

</details>

### 10.2 什么应用适合 Native Image {#native-image-fit}

**考察重点**：根据进程生命周期和扩缩容要求判断启动收益，并评估动态特性、第三方库与诊断能力的适配成本。

**相关内容**：[GraalVM Native Image](#graalvm-native-image)至[三种方案的比较](#三种方案的比较)。

<details>
<summary>参考回答</summary>

**CLI、函数计算、频繁冷启动或需要快速扩缩容的服务适合评估 Native Image，因为这些场景里启动时间和初始内存占比高。**

如果应用依赖运行时插件、动态生成类，或者反射目标难以枚举，适配工作量就会很大。第三方库也要逐个验证，确认它们的动态访问能在构建时声明。

决定之前，用目标框架和真实请求测量启动到 ready 的时间、首批请求耗时和稳定期吞吐，再比较 P99、RSS、构建和发布成本，并确认故障诊断手段够用。

</details>
