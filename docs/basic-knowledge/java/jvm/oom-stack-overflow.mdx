# OutOfMemoryError 与 StackOverflowError

OutOfMemoryError 表示一次资源申请失败。StackOverflowError 表示线程调用栈深度超限。本文负责错误分类、证据选择与恢复边界。堆内引用分析见 [堆转储](./heap-dumps-memory-leaks.mdx)。

## 1. 面试核心 {#core}

- `Java heap space` 指堆分配失败，`Metaspace` 指类元数据分配失败。[卡](#oom-types)
- `unable to create native thread` 指平台线程资源申请失败。
- `StackOverflowError` 表示线程请求的调用栈深度超出允许范围。
- `-XX:+HeapDumpOnOutOfMemoryError` 可在 HotSpot 支持的 OOM 路径导出堆。[卡](#locate-oom)
- 操作系统 OOM Kill 可直接终止进程，JVM 来不及生成堆转储。[卡](#oom-kill-vs-java)

## 2. Java heap space {#java-heap-space}

```java
List<byte[]> retained = new ArrayList<>();
while (true) {
    retained.add(new byte[1024 * 1024]);
}
```

示例持续强引用新数组，堆耗尽后抛出 OOM。实际故障还包括必需工作集过大或突发分配。

泄漏要结合对象生命周期判断，见 [堆转储](./heap-dumps-memory-leaks.mdx#泄漏容量不足与分配峰值)。`Requested array size exceeds VM limit` 则指数组超出实现上限。增大堆也无法解除该数组长度限制。

## 3. GC overhead limit exceeded {#gc-overhead-limit-exceeded}

该消息表示 GC 占用大量时间，却释放极少空间。它描述回收进展，未新增一种内存区域。

以 Java 17、21 的 Parallel 默认策略为例：GC 时间超过约 98%，回收空间低于约 2%。持续满足条件后会触发保护。此规则应结合收集器和版本解释。

`-XX:-UseGCOverheadLimit` 可关闭该保护。工作集和可用空间问题仍需处理。应结合 GC 后存活占用、分配率和吞吐判断。

## 4. 元空间与压缩类空间 {#元空间与压缩类空间}

动态生成类、加载器滞留和容量配置都可导致故障。`-XX:MaxMetaspaceSize` 管理元空间上限。`-XX:CompressedClassSpaceSize` 配置压缩类空间大小。

```bash
jcmd <pid> VM.classloader_stats
jcmd <pid> VM.metaspace
```

先检查加载器数量与类数量的变化。旧加载器应卸载却持续存活时，再查持有链。空间不足时，也需核对正常业务的类规模。

## 5. 直接内存与本地分配失败 {#直接内存与本地分配失败}

直接缓冲区受限可抛出 `Direct buffer memory`。其他本地分配失败也可表现为 native OOM 或崩溃。此时 Java 堆仍可很小。

BufferPool 指标用于观察直接缓冲区。NMT 追踪 HotSpot 管理的本地内存。第三方 native 分配还需操作系统映射等证据。工具范围见 [Java 直接内存](./direct-native-memory.mdx)。

## 6. 平台线程创建失败 {#平台线程创建失败}

平台线程需要本地结构和栈空间。线程无限增长会耗尽内存或线程数配额。容器 PID 限制也会导致创建失败。

```bash
jcmd <pid> Thread.print -l
```

结合线程增长、OS 线程限制和容器事件排查。`-Xss` 影响平台线程栈容量。减小它可降低单线程栈预算，也会降低可承受调用深度。控制并发和任务积压仍是必要处理。

## 7. StackOverflowError {#stackoverflowerror}

```java
static void recurse() {
    recurse();
}
```

无限递归会持续增加栈帧，最终超过栈容量。循环调用的 `toString`、`equals` 也会触发同类问题。

先根据重复栈帧定位调用环。无终止递归应修正终止条件。输入决定的深递归可改为迭代和显式栈。深度已知且内存预算允许时，再调整 `-Xss`。

## 8. 按错误类型选择证据 {#按错误类型选择证据}

| 错误或现象 | 主要证据 |
| --- | --- |
| `Java heap space` | GC 日志、直方图、堆转储 |
| `Metaspace` | 加载器统计、类卸载趋势 |
| `Direct buffer memory` | BufferPool、NMT 与系统内存 |
| `unable to create native thread` | 线程数、栈预算、OS 与 PID 配额 |
| `StackOverflowError` | 重复调用栈帧 |
| 操作系统 OOM Kill | 内核或容器事件、进程内存趋势 |

首先保留完整错误消息与首次发生时间。再关联启动参数、负载和容器限制。

```bash
java -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/safe/path -jar app.jar
```

启动前验证路径可写，并为转储预留磁盘。该开关覆盖部分 HotSpot OOM 路径。应用手动抛出的 OOM 和线程创建失败等不保证产出。

### 8.1 操作系统 OOM Kill {#操作系统-oom-kill}

容器内存包含 Java 堆、线程栈和其他本地内存。即使堆未到 `-Xmx`，进程仍可超过容器限额。内核此时可直接杀死进程。

SIGKILL 没有给 JVM 留下清理窗口。退出码 137 只说明 SIGKILL，需要核对 OOM 事件。已配置的 heap dump 和 shutdown hook 也无法据此保证执行。

## 9. 常见问题 {#常见问题}

### 9.1 泄漏与溢出 {#泄漏与溢出}

泄漏是无用资源仍被持有，溢出是资源申请失败。合理工作集超过容量也会溢出。

### 9.2 OOM 后的进程状态 {#oom-后的进程状态}

未捕获的 OOM 可终止当前线程。其他线程仍能运行，但进程资源已经紧张。恢复策略应由外部健康检查和监督机制配合。

### 9.3 显式 GC 与容量 {#显式-gc-与容量}

`System.gc()` 只是 GC 请求。仍被强引用持有的对象会继续存活。释放责任和容量配置需要分别修正。

### 10.1 `StackOverflowError` 和不同 OOM 分别怎样产生 {#oom-types}

**出现公司**：腾讯

**考察重点**：调用栈与不同资源的分配失败。

**相关内容**：[Java heap space](#java-heap-space)、[StackOverflowError](#stackoverflowerror)。

<details>
<summary>参考回答</summary>

`StackOverflowError` 表示调用栈深度超限。OOM 根据消息区分资源。`Java heap space` 对应堆，`Metaspace` 对应类元数据。`Direct buffer memory` 对应直接缓冲区。`unable to create native thread` 对应平台线程申请。

</details>

**出现公司**：高德

**考察重点**：错误分类、首次证据和采集成本。

**相关内容**：[按错误类型选择证据](#按错误类型选择证据)。

<details>
<summary>参考回答</summary>

先保存完整错误、首次时间和容器事件，再按资源分类。堆问题看 GC 趋势和堆转储。元空间看类与加载器，直接内存看 BufferPool。线程失败看线程数、栈预算和系统限制。预配 `-XX:+HeapDumpOnOutOfMemoryError` 并验证路径。采集时还要评估停顿与磁盘。

</details>

### 10.3 堆未达到 Xmx，进程为何被杀死且没有 heap dump？ {#oom-kill-vs-java}

</details>
