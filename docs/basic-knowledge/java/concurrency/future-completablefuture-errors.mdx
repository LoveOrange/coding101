# CompletableFuture

`CompletableFuture` 用完成阶段组织异步结果，以及结果之间的依赖。一个完成阶段表示一次计算及其结果，计算结束后再触发依赖它的后续阶段。本文以 Java 17/21 为准，从 Future 的结果读取入手，再讲阶段组合与回调线程。之后说明异常怎样传播，以及超时、取消和聚合完成的边界。

## 1. 面试核心 {#core}

- **异步阶段组合。** `thenCompose` 将回调返回的异步阶段展平为一层结果，`thenCombine` 等两个阶段正常完成后合并结果。
- **默认执行器。** Java 17/21 的 CompletableFuture 异步方法默认使用公共池，并行度小于 2 时为每个任务新建线程。[卡](#completablefuture-errors-executor)
- **回调失败。** 原阶段成功时，`whenComplete` 回调抛错会使它返回的新阶段异常完成。[卡](#completion-observer-failure)
- **聚合完成。** `allOf` 等待全部输入阶段完成后报告结果，其中任一阶段失败，聚合结果就会失败。[卡](#allof-anyof-failure)
- **取消边界。** `CompletableFuture.cancel(true)` 通过异常完成表达取消，底层任务仍需自己的退出机制。

## 2. Future 的结果与异常 {#future-的结果与异常}

Future 表示异步计算的结果，计算结束前也可以先取得这个对象。它提供结果读取、超时等待和取消等操作。调用 `get` 时，调用线程会等待计算完成：

```java
Future<Profile> future = executor.submit(() -> loadProfile(id));

try {
    Profile profile = future.get(300, TimeUnit.MILLISECONDS);
} catch (ExecutionException exception) {
    Throwable cause = exception.getCause();
    handleFailure(cause);
}
```

示例最多等待 300 毫秒，成功时返回 Profile。任务自身抛错时，`get` 用 `ExecutionException` 包装异常，代码通过 `getCause()` 取得原始原因。等待被中断或超时则分别抛出 `InterruptedException`、`TimeoutException`，外围方法还需处理或声明它们。

`submit` 会把任务失败记录到返回的 Future 中。如果提交方丢弃这个对象，又没有其他失败记录，异常就会缺少读取和处理的入口。

FutureTask 的 `cancel(true)` 会尝试中断任务，任务退出仍取决于是否响应中断。具体行为见 [任务取消](./interruption-timeout-cancellation.mdx#futurecanceltrue-的效果)。

## 3. CompletionStage 的依赖组合 {#completionstage-的依赖组合}

CompletionStage 描述计算完成后要继续做什么，CompletableFuture 实现了这个接口。这样就能直接连接计算结果之间的依赖，无需调用线程逐步等待。

订单和客户数据互相独立时，可以并行加载，再合并为订单视图：

```java
CompletableFuture<OrderView> view =
        CompletableFuture.supplyAsync(() -> loadOrder(id), ioExecutor)
                .thenCombine(
                        CompletableFuture.supplyAsync(
                                () -> loadCustomer(id), ioExecutor),
                        OrderView::new
                );
```

示例把两个加载任务提交给 `ioExecutor`。只有两者都正常完成，才会调用 `OrderView::new`，生成最终视图。

组织依赖时，需要区分以下**三种组合方式**：

- `thenApply` 把一个结果值转换为另一个值，适合普通结果映射。
- `thenCompose` 接收回调返回的另一个异步阶段，并展平嵌套结果，适合依赖上一步的异步调用。
- `thenCombine` 等待两个阶段正常完成后合并结果，适合汇合独立任务。

需要前一步输出的任务，应在前一步成功后沿依赖关系启动。独立任务才适合像示例这样直接并行提交。

## 4. 回调的执行线程 {#回调的执行线程}

异步阶段描述了执行顺序，还需要明确每个回调由谁执行。否则，一段慢回调就会占住完成上一步的网络线程或调用方线程。

非 `Async` 回调可由完成当前阶段的线程执行，其他调用完成方法的线程也能执行它。在已经完成的阶段上注册回调时，注册回调的线程也可直接执行。

带 `Async` 且未显式传入 Executor 时，Java 17/21 默认使用 `ForkJoinPool.commonPool()`。这是不同业务共享的公共线程池，其并行度小于 2 时，每个异步任务会新建一个线程。子类还可通过 `defaultExecutor()` 改写实例方法的默认执行器。显式传入 Executor 时，任务交给指定的执行器。

慢 I/O 会长时间占用线程，不同业务共用公共池时就会互相影响。需要隔离的依赖应使用专用执行器，并设置容量限制、监控排队与拒绝情况。

执行器的容量与拒绝规则见 [Java 线程池](./threadpoolexecutor-execution-path.mdx)。

## 5. 异常恢复与观察 {#异常恢复与观察}

阶段失败后，业务需要决定是恢复为可用结果，还是继续传播异常。下面的**三种回调**承担不同职责：

- `exceptionally` 只在失败时计算替代结果，适合业务允许的降级。
- `handle` 在成功或失败时都转换结果，适合统一处理两种完成状态。
- `whenComplete` 接收结果和异常，用于记录日志或指标，正常返回时保留原有结果。

```java
future.whenComplete((value, error) -> metrics.record(error));
```

示例用 `whenComplete` 记录失败指标。它返回一个新阶段，指标回调自身抛错也会影响这个阶段，因此要处理指标代码的失败。

`exceptionally` 和 `handle` 的回调正常返回时，后续阶段会得到成功结果。也就是说，返回默认值会把原来的失败恢复为成功。只有业务允许降级时才这样做，并保留错误指标；否则应让异常继续传播，在业务边界处理。回调自身抛错时，后续阶段仍会失败。

读取结果时，还要区分以下**异常类型**：

- `get()` 用受检的 `ExecutionException` 包装计算异常，调用方需要捕获或声明它。
- `join()` 对异常完成抛出非受检的 `CompletionException`。
- 直接取消后的 Future 在调用 `get()` 或 `join()` 时，会抛出 `CancellationException`。

记录或去重日志时，应解开包装异常，并保留原始 cause，才能看到真正失败的调用。

## 6. 超时与取消的作用范围 {#超时与取消的作用范围}

结果等待结束后，产生结果的网络或数据库调用仍有自己的生命周期。因此，设置超时和取消时，要分别处理 Future 状态与底层任务。

Java 17/21 中，`orTimeout` 在期限到达且当前结果尚未完成时，使它以超时异常完成。`completeOnTimeout` 则用默认值正常完成。两者都修改并返回当前 CompletableFuture，底层外部调用仍需独立设置超时。

`cancel` 将当前结果标为取消，但 `mayInterruptIfRunning` 参数在 CompletableFuture 中无效。它通过异常完成表达取消，任务是否退出取决于外部调用自己的取消机制。

组合多个调用时，需要明确以下**超时与取消策略**：

- 从请求入口传递截止时间，让后续阶段知道还剩多少可用时间。
- 为每个外部调用设置超时，并安排底层任务的退出方式。
- 一个阶段失败后，决定其他兄弟任务是取消、继续等待，还是保留已取得的结果。

## 7. 观察回调的异常 {#观察回调的异常}

观察结果的代码也会失败，所以需要区分原阶段异常和回调异常。`whenComplete` 的回调正常返回时，新阶段保留原结果。原阶段成功、回调抛错时，新阶段异常完成。如果两者都失败，则优先保留原阶段异常。

下面让成功结果的观察回调主动抛错：

```java
CompletableFuture<Integer> next =
        CompletableFuture.completedFuture(1)
                .whenComplete((value, error) -> {
                    throw new IllegalStateException("metrics failed");
                });
```

调用 `next.join()` 会抛出 `CompletionException`，其 cause 是回调抛出的 `IllegalStateException`。原来的已完成 Future 仍保持成功，失败的是 `whenComplete` 返回的新阶段。

## 8. allOf 与 anyOf 的完成条件 {#allof-与-anyof-的完成条件}

同时启动多个任务后，聚合阶段何时结束，取决于使用的组合方法。`allOf` 等待所有输入阶段完成，只要其中有异常，聚合结果就异常完成。因此，即使一个任务很早失败，它仍会等待其他任务结束。

`anyOf` 随任一输入完成而完成。最先完成的输入即使失败，也会使聚合结果失败，所以它不会专门等待首个成功结果。需要“首个成功”策略时，要额外记录成功结果和失败数量，全部失败时再报告失败。

这两个方法都保留其他任务的运行状态。需要停止剩余任务时，由调用方安排取消。输入为空时，`allOf` 立即正常完成，而 `anyOf` 保持未完成。

## 9. 常见问题 {#常见问题}

### 9.1 thenApply 与 thenCompose {#thenapply-与-thencompose}

回调返回普通值时用 `thenApply`，返回另一个 CompletionStage 时用 `thenCompose`。如果异步回调交给 `thenApply`，结果类型会嵌套为 `CompletableFuture<CompletableFuture<T>>`。`thenCompose` 会展平它，让调用方直接等待最终的 T。

### 9.2 allOf 的结果类型 {#allof-的结果类型}

`allOf` 表示一组阶段全部完成，返回类型是 `CompletableFuture<Void>`。它没有收集各个计算结果，所以调用方需要保留原 Future 列表。聚合正常完成后，可以逐个读取结果；存在失败时，则按业务规则决定整体报错还是保留部分结果。

- **Future 超时不等于底层 I/O 停止。** `orTimeout` 改变完成状态，网络和数据库调用仍需截止时间、超时与退出机制。
