# Java 原子类

Java 原子类负责独立状态的原子读改写。本文比较精确计数、分散累加和读取成本。CAS 重试与 ABA 见 [CAS](./cas-aba-versioning.mdx)。

## 1. 面试核心 {#core}

- `AtomicLong.incrementAndGet()` 原子递增并返回新值。
- 检查余额与扣减余额需要组合为一次条件更新。
- `LongAdder` 将热点更新分散到 `base` 和多个 Cell。[卡](#atomiclong-vs-longadder)
- 并发更新期间，`LongAdder.sum()` 缺少原子快照语义。
- `sumThenReset()` 适合在无并发更新时读取并清零。[卡](#adder-reset-boundary)

## 2. 原子类与 CAS 循环 {#原子类与-cas-循环}

```java
private final AtomicLong sequence = new AtomicLong();

long nextId() {
    return sequence.incrementAndGet();
}
```

每次调用都执行原子递增，并返回新值。序列号还需处理 `long` 溢出和进程重启。

```java
if (stock.get() > 0) {
    stock.decrementAndGet();
}
```

第二段把检查与扣减分成两次操作。两个线程可同时检查到库存大于零。因此，库存扣减应采用 [CAS 条件更新](./cas-aba-versioning.mdx#cas-的条件更新)。

## 3. 单变量的竞争成本 {#单变量的竞争成本}

多个核心更新同一原子变量时，会争夺缓存行。CAS 循环还要承担失败重试成本。原子加法的底层指令取决于 JVM 与处理器。

`AtomicLong` 的 API 承诺原子读改写。一次方法调用并不等于一次 CAS 指令。性能评估要结合更新频率和竞争强度。

## 4. `LongAdder` 的分段累加 {#longadder-的分段累加}

```java
private final LongAdder requests = new LongAdder();

void recordRequest() {
    requests.increment();
}

long observedRequests() {
    return requests.sum();
}
```

OpenJDK 26 的实现使用 `base` 和 Cell 数组。低竞争时可以直接更新 `base`。竞争发生后，更新分散到不同 Cell。`sum()` 读取 `base` 并累加各 Cell。

分散更新减少单点竞争，也增加空间开销。读取成本随 Cell 数量增加。示例适合请求统计，返回值用于观测。

## 5. `sum()` 的读取语义 {#sum-的读取语义}

并发更新时，`sum()` 依次读取各分量。分量的采样时刻各不相同。因此，返回值缺少整体原子快照语义。

所有更新停止且对读取线程可见后，求和结果精确。指标统计可以使用该接口。序列号和精确阈值转换应选择原子读改写。跨字段一致性则需要统一的状态转换协议。

## 6. AtomicReference 与不可变状态 {#用-atomicreference-更新多字段状态}

以下示例使用 Java 16 起正式支持的 record：

```java
record State(int available, long version) {}

AtomicReference<State> state =
        new AtomicReference<>(new State(10, 0));
```

一次 CAS 替换整个不可变对象引用。读取方保留一次 `get()` 的结果，再访问各字段。由此，字段属于同一状态版本。

读者若对每个字段分别调用 `get()`，仍会混用版本。更新函数的重试约束见 [CAS](./cas-aba-versioning.mdx#重试函数与副作用)。

## 7. 统计窗口与清零 {#统计窗口与清零}

`LongAdder.reset()` 要求避开并发更新。`sumThenReset()` 也缺少整个操作的原子快照。写线程与清零交错时，窗口边界难以精确划分。

若要求单计数器原子切换窗口，可用 `AtomicLong.getAndSet(0)`。并发递增会按该交换点落入前后窗口。多个计数器组成的快照仍需统一协调。

## 8. 常见问题 {#常见问题}

### 8.1 LongAdder 的性能条件 {#longadder-的性能条件}

`LongAdder` 适合高竞争且累加远多于读取的负载。`AtomicLong` 的空间和读取成本更低。应按线程数与读写比例测量两者。

### 8.2 原子类的同步范围 {#原子类的同步范围}

原子类负责其 API 定义的状态转换。多个字段、条件等待或业务副作用仍需统一协调。锁能直接覆盖多步临界区。

<details>
<summary>参考回答</summary>

精确发号或条件更新应选择 `AtomicLong`。高竞争统计累加可以选择 `LongAdder`。后者用分散更新降低热点竞争。

`sum()` 在并发写入时缺少整体原子快照。`LongAdder` 还需要更多空间和求和开销。选择应依据读写比例与实测吞吐。

</details>

### 9.2 怎样精确切分并发计数窗口，sumThenReset 适合吗？ {#adder-reset-boundary}

<summary>参考回答</summary>

</details>
