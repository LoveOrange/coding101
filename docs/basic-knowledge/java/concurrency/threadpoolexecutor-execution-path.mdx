# Java 线程池

Java 线程池复用 Worker，并管理任务接收与过载。本文负责 ThreadPoolExecutor 的执行路径、容量和关闭。异步结果组合见 [CompletableFuture](./future-completablefuture-errors.mdx)。

## 1. 面试核心 {#core}

- 运行中的池依次尝试核心 Worker、队列和最大线程。[卡](#execute-flow)
- 无界队列在核心 Worker 创建后持续接收积压任务。[卡](#queue-expansion-policy)
- I/O 线程数同时受等待比例、下游并发和内存限制。[卡](#io-pool-size)
- 池关闭或容量耗尽时会调用拒绝策略。[卡](#saturation-handling)
- `shutdownNow()` 尝试中断在执行任务，并返回排队任务。[卡](#pool-shutdown-states)

## 2. 构造参数 {#构造参数}

`ThreadPoolExecutor` 有七个主要构造参数：

| 范围 | 参数 | 作用 |
| --- | --- | --- |
| 线程数量 | `corePoolSize`、`maximumPoolSize` | 核心阈值与线程上限 |
| 空闲回收 | `keepAliveTime`、`unit` | 空闲等待期限 |
| 排队 | `workQueue` | 保存待执行任务 |
| 创建 | `threadFactory` | 创建和命名 Worker 线程 |
| 拒绝 | `handler` | 处理拒绝任务 |

```java
ExecutorService executor = new ThreadPoolExecutor(
    8,
    16,
    30,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),
    new ThreadPoolExecutor.AbortPolicy()
);
```

示例使用六参数重载，采用默认 ThreadFactory。队列容量为 200，核心阈值为 8，上限为 16。饱和后，AbortPolicy 抛出拒绝异常。

自定义 ThreadFactory 可指定业务线程名。参数应与队列类型一起解释。

## 3. execute 接收流程 {#execute-的处理流程}

运行中的线程池按以下顺序接收任务：

1. Worker 少于 `corePoolSize` 时，尝试创建 Worker。
2. 否则尝试入队，并复查运行状态。
3. 入队失败时，尝试扩展至 `maximumPoolSize`。
4. 关闭或容量耗尽时，执行拒绝策略。

入队后若池已关闭，且成功移除该任务，则拒绝它。池仍可消费任务但 Worker 为零时，要补建消费者。

Worker 完成任务后继续从队列取任务。超过核心阈值的空闲 Worker 可超时退出。`allowCoreThreadTimeOut(true)` 也允许核心数量内回收。此时 `keepAliveTime` 必须大于零。

### 3.1 execute 与 submit 的异常 {#execute-与-submit-的异常}

`execute` 的任务抛出未捕获异常时，Worker 会异常退出。异常会交给线程的未捕获异常处理器。线程池可按状态和容量补建 Worker。

`submit` 把任务包装为 FutureTask。任务异常保存在 Future 中，`get()` 抛出 `ExecutionException`。因此，丢弃 Future 会失去处理任务失败的入口。

`afterExecute` 的 Throwable 参数也有区别。FutureTask 捕获了异常时，该参数可为 null。自定义监控需进一步检查已完成 Future。

## 4. 线程池容量 {#线程池容量}

CPU 密集任务持续占用核心。并行度增加到计算容量上限后，更多线程会争抢 CPU。I/O 任务在等待期间释放 CPU，但仍占下游资源。

可用以下关系估算压测起点：

```text
线程数 ≈ CPU 核数 × 目标利用率 × (1 + 等待时间 / 计算时间)
在途任务数 ≈ 目标吞吐 × 平均响应时间
```

第二条是稳定系统下的 Little 定律。第一条依赖计算与等待时间的估算。两者都需结合资源上限验证。

- 数据库连接数限制同时查询数量。
- 下游配额限制并发调用数量。
- 内存限制线程栈和在途任务数量。
- 延迟预算限制排队时间。

逐步增加并发，观察吞吐和 p99。吞吐持平而长尾上升时，应停止继续加线程。

## 5. 过载保护 {#过载保护}

| 策略 | 行为 |
| --- | --- |
| `AbortPolicy` | 抛出 `RejectedExecutionException` |
| `CallerRunsPolicy` | 池未关闭时由提交线程执行，否则丢弃 |
| `DiscardPolicy` | 静默丢弃当前任务 |
| `DiscardOldestPolicy` | 池未关闭时移除队头，再尝试提交 |

拒绝结果应映射到业务响应。可选择返回繁忙、有限重试或降级。允许丢弃的任务也需有明确指标。

`CallerRunsPolicy` 会占用提交者。若提交者是事件循环或持锁线程，就会扩大阻塞。其反压效果取决于提交链路。

## 6. 饱和与堆积诊断 {#饱和与堆积诊断}

队列长期增长，说明完成速率低于到达速率。排查时可按以下顺序收集证据：

1. 查看 active、池大小、队列年龄和拒绝数。
2. 比较提交、完成速率及任务耗时。
3. 采集多份栈，检查锁、I/O 和连接等待。
4. 检查父任务是否等待同池子任务。
5. 限制新任务并清理已过期工作，再评估扩容。

同池等待的原因见 [并发活跃性](./liveness-deadlock-livelock-starvation.mdx#线程池的资源等待环)。CPU 低且线程多时，应先定位等待对象。

## 7. 队列类型与扩容 {#队列类型与扩容}

| 队列 | 接收特点 | 对扩容的影响 |
| --- | --- | --- |
| 无界 `LinkedBlockingQueue` | 持续保存等待任务 | 核心数后优先积压 |
| 有界 `ArrayBlockingQueue` | 容量固定 | 满后才扩展 Worker |
| `SynchronousQueue` | 容量为零，直接交接 | 无接收者时尝试增线程 |

无界队列使 `maximumPoolSize` 缺少触发扩容的机会。直接交接队列则要求及时提供消费者。默认 cached pool 使用直接交接，并给出很高线程上限。

需要队列缓冲时，容量应由任务预算决定。任务过期后还应避免继续执行无效工作。

## 8. 线程池关闭与终止 {#线程池关闭与终止}

OpenJDK 26 用五种状态管理线程池：

| 状态 | 行为 |
| --- | --- |
| `RUNNING` | 接收新任务，处理队列 |
| `SHUTDOWN` | 拒绝新任务，继续处理队列 |
| `STOP` | 拒绝新任务，停止取队列并尝试中断运行任务 |
| `TIDYING` | Worker 已归零，执行终止钩子 |
| `TERMINATED` | 终止钩子执行完成 |

`shutdown()` 进入有序关闭。`shutdownNow()` 尝试中断，并返回尚未执行的排队任务。`awaitTermination` 用于在期限内等待终止。

```java
pool.shutdown();
if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
    List<Runnable> pending = pool.shutdownNow();
    handlePending(pending);
}
```

片段需处理或声明 `InterruptedException`。运行任务忽略中断时，线程池仍会等待其结束。返回的排队 FutureTask 也需调用方安排取消或接管。

## 9. 静默拒绝与悬空 Future {#静默拒绝与悬空-future}

`submit` 创建 FutureTask 后调用 `execute`。拒绝策略若静默丢弃，该 FutureTask 就不会执行。它也未被自动标为完成，`get()` 会持续等待。

`DiscardPolicy` 会出现这个结果。关闭后的 `CallerRunsPolicy` 同样直接丢弃。`DiscardOldestPolicy` 还会遗留被移除任务的 Future。

需要结果的任务应采用显式拒绝。自定义处理器也可取消被丢弃的 Future，并记录失败。调用者据此得到可结束的结果状态。

## 10. 常见问题 {#常见问题}

### 10.1 核心线程的预启动 {#核心线程的预启动}

核心 Worker 默认按需创建。`prestartCoreThread()` 可预启动一个。`prestartAllCoreThreads()` 可预启动全部核心 Worker。

### 10.2 固定线程池的排队边界 {#固定线程池的排队边界}

`Executors.newFixedThreadPool` 使用无界队列。持续过载会增加排队延迟和内存占用。需要明确容量时，可显式构造有界线程池。

### 10.3 队列容量与延迟预算 {#队列容量与延迟预算}

队列可吸收短时突发。持续积压时，更大队列会延长排队并保留过期任务。容量应结合单任务内存和可接受等待时间。

### 11.5 shutdown、shutdownNow 和 awaitTermination 有什么区别？ {#pool-shutdown-states}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：理解关闭状态、排队任务和实际终止。

**相关内容**：[线程池关闭与终止](#线程池关闭与终止)。

<details>
<summary>参考回答</summary>

shutdown 拒绝新任务，但继续执行已接受任务。shutdownNow 停止取队列，并尝试中断运行任务。awaitTermination 在期限内等待线程池真正终止。

shutdownNow 返回排队任务，供调用方处理。运行任务仍需响应中断，才能完成退出。

</details>
