# Java 线程池

Java 线程池复用工作线程并限制同时执行的任务数量。面试重点是 `ThreadPoolExecutor` 的接收顺序、线程与队列怎样共同形成容量边界，以及过载后如何拒绝和排查。

:::tip 面试核心

- 提交任务时依次尝试核心线程、工作队列、最大线程，最后执行拒绝策略。
- 无界队列通常让线程数无法增长到 `maximumPoolSize`，过载会表现为队列和延迟持续增加。
- 线程数不能只按 CPU 核数套公式，还受任务等待时间、目标吞吐、下游容量和内存限制。
- 有界队列和明确拒绝让过载可见；大队列只是延后失败，并增加过期任务和内存占用。
- 排查堆积时先比较提交速率与完成速率，再用线程栈和下游指标解释任务为什么变慢。

:::

## 1. 构造参数形成四类约束

`ThreadPoolExecutor` 的七个主要参数可以分成四组：

| 约束 | 参数 | 作用 |
| --- | --- | --- |
| 线程数量 | `corePoolSize`、`maximumPoolSize` | 控制常态与峰值工作线程 |
| 空闲回收 | `keepAliveTime`、`unit` | 回收超过核心数的空闲线程 |
| 等待空间 | `workQueue` | 保存尚未执行的任务 |
| 创建与过载 | `threadFactory`、`handler` | 命名线程并定义拒绝结果 |

```java
ExecutorService executor = new ThreadPoolExecutor(
    8,
    16,
    30,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),
    new ThreadPoolExecutor.AbortPolicy()
);
```

参数必须放在一起解释。最大线程数很大但队列无界时，任务通常一直入队；队列很小则更早扩展线程或拒绝。

## 2. `execute` 的任务接收顺序

运行中的线程池接收任务时主要经过四步：

1. 工作线程少于 `corePoolSize` 时，尝试创建核心 Worker 执行任务。
2. 否则尝试把任务放入队列，并在入队后复查线程池状态。
3. 队列无法接收时，尝试创建非核心 Worker，直到 `maximumPoolSize`。
4. 线程池不再运行，或线程和队列都没有容量时，调用拒绝策略。

入队后复查很重要：提交期间线程池可能已经关闭；如果池中没有 Worker，还需要创建一个线程消费已经入队的任务。

Worker 完成初始任务后会继续从队列取任务。超过核心数量的线程空闲达到 `keepAliveTime` 后可以退出；启用 `allowCoreThreadTimeOut(true)` 后，核心线程也可以超时回收。

### 2.1 `execute` 与 `submit` 的异常

`execute` 执行的 Runnable 抛出未捕获异常时，异常会到达线程的未捕获异常处理器。`submit` 会把异常保存在 Future 中，调用 `get()` 时通过 `ExecutionException` 交给调用方；如果从不读取 Future，失败很容易被忽略。

## 3. 线程池容量 {#thread-pool-sizing}

CPU 密集任务持续占用核心，线程数接近可用核心数通常已经接近吞吐上限。I/O 密集任务会等待数据库或网络，可以有更多线程，但有效并发仍受下游限制。

估算可以从两个关系开始：

```text
线程数 ≈ CPU 核数 × 目标利用率 × (1 + 等待时间 / 计算时间)
在途任务数 ≈ 目标吞吐 × 平均响应时间
```

它们只提供实验起点。最终上限还要取以下约束中的较小值：

- 数据库连接池和下游允许的并发。
- 每个任务占用的内存与线程栈。
- 容器 CPU 配额和可用核心数。
- 目标延迟、超时与允许的排队时间。

逐步增加并发压测，观察吞吐、P95/P99、队列、拒绝、CPU、上下文切换和下游等待。吞吐不再增长而长尾继续变差时，继续增加线程已经没有收益。

## 4. 过载保护 {#thread-pool-overload}

有界队列让等待任务数和内存上限可计算。四种内置拒绝策略表达不同结果：

- `AbortPolicy`：抛出异常，让失败显式暴露。
- `CallerRunsPolicy`：由提交线程执行，可能降低提交速度。
- `DiscardPolicy`：静默丢弃当前任务。
- `DiscardOldestPolicy`：丢弃队头任务后重试提交。

生产系统不能只选择一个类名，还要定义业务结果：请求返回繁忙、有限重试、降级、合并还是允许丢弃。任务还需要幂等、截止时间和拒绝指标。

`CallerRunsPolicy` 只在部分同步调用链中形成有限反压。如果提交者是 I/O 线程、事件循环或持锁线程，它可能扩大故障，应先确认调用上下文。

## 5. 饱和与堆积诊断 {#thread-pool-saturation}

队列持续增长说明任务到达速率长期高于完成速率。排查顺序是：

1. 查看 active、pool size、队列长度、最老任务年龄、完成数和拒绝数。
2. 比较提交速率、完成速率和任务耗时，区分流量增加与单个任务变慢。
3. 采集多份线程栈，检查数据库连接等待、下游调用、锁和 CPU 热点。
4. 检查池内任务是否同步等待同一个池提交的子任务，这会造成线程饥饿。
5. 先限制新任务、隔离慢依赖并放弃已过期任务，再评估是否需要扩容。

线程数很多而 CPU 不高，通常说明线程在等待锁、I/O、连接池或子任务，不足以证明“线程还不够”。

## 6. 常见问题

### 6.1 创建线程池会立即创建所有核心线程吗

默认不会。通常在任务到来时逐步创建，也可以调用 `prestartCoreThread` 或 `prestartAllCoreThreads` 预启动。

### 6.2 为什么不直接使用 `Executors.newFixedThreadPool`

它使用无界 `LinkedBlockingQueue`。流量持续超过处理能力时，任务会不断排队，延迟和内存占用缺少明确上限。显式构造 ThreadPoolExecutor 更容易表达容量与拒绝结果。

### 6.3 队列越大越能抗突发吗

队列可以吸收短时波动，但过大会延长等待时间、保存更多已经过期的任务，并推迟过载信号。容量应来自可接受排队时间和任务内存，而不是越大越好。

### 7.1 `ThreadPoolExecutor.execute` 的任务处理流程是什么

**出现公司**：阿里巴巴、美团

**考察重点**

- 核心线程、队列和最大线程的先后关系。

**相关内容**：第 1 节“构造参数形成四类约束”、第 2 节“`execute` 的任务接收顺序”。

<details>
<summary>参考回答</summary>

提交任务时，先在工作线程少于 core 时尝试创建 Worker；否则尝试入队，并在入队后复查运行状态和是否存在消费者。队列满时再尝试扩展到 maximum；仍无法接收或线程池不再运行时执行拒绝策略。

因此参数必须和队列一起解释。无界队列通常不会触发 maximum 扩容，过载会表现为队列和延迟持续增长。

</details>

<details>

先测任务的计算时间、等待时间和目标吞吐，用核数与等待/计算比得到实验区间，也可以用 Little 定律检查目标吞吐对应的在途量。然后取数据库连接、对端并发和内存等约束中的更小上限。

逐步增加线程压测吞吐和 P99，同时观察队列、拒绝、CPU、切换与下游等待。吞吐停止增长而长尾变差的位置说明继续加线程无效。

</details>

### 7.3 队列满或任务持续堆积时应该怎样处理

<!-- 面试来源：
- 美团：https://www.nowcoder.com/discuss/363477877092876288
- 阿里巴巴：https://www.nowcoder.com/discuss/461925
-->

**出现公司**：美团、阿里巴巴

**考察重点**

- 拒绝策略的业务结果。
- 提交速率、完成速率、线程栈和下游等待。

**相关内容**：第 4 节“过载保护”、第 5 节“饱和与堆积诊断”。

<details>
<summary>参考回答</summary>

队列满后先尝试扩展到最大线程，仍无法接收才执行拒绝。系统应让失败显式可见，再按业务选择返回繁忙、有限重试、降级或允许丢弃，并监控队列年龄和拒绝数。

持续堆积时比较提交与完成速率，再用多份线程栈和数据库、下游、锁、CPU 时间线判断是流量增加还是任务变慢。恢复时先阻止继续恶化，只有证据表明确实缺少可用计算容量时才扩池。

</details>
