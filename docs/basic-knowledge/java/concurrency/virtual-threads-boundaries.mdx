# 虚拟线程

虚拟线程以较低线程成本承载大量阻塞任务。本文负责 Java 21 的运行模型、容量边界及 pinning。线程局部上下文见 [ThreadLocal](./threadlocal-leaks-context.mdx)。

## 1. 面试核心 {#core}

- 虚拟线程自 JDK 21 正式提供，按任务创建使用。
- 支持卸载的阻塞操作可释放 carrier，供其他任务运行。
- 虚拟线程适合大量阻塞 I/O，CPU 吞吐仍受核心数限制。[卡](#virtual-thread-fit)
- Java 21 中，持有 monitor 时阻塞会导致 pinning。[卡](#pinning-version-boundary)
- 虚拟线程是守护线程，退出前需显式等待任务完成。[卡](#virtual-thread-observation)

## 2. 虚拟线程与 carrier 线程 {#虚拟线程与-carrier-线程}

```java
try (ExecutorService executor =
             Executors.newVirtualThreadPerTaskExecutor()) {
    Future<Response> response = executor.submit(() -> client.call());
    return response.get();
}
```

示例使用 Java 21。执行器为每个任务创建一个虚拟线程。`get()` 取得调用结果，退出作用域时关闭执行器。

虚拟线程挂载在 carrier 平台线程上执行。支持卸载的等待会释放 carrier。等待结束后，虚拟线程重新排队等待挂载。

虚拟线程保留 Java 的栈、异常和中断模型。`Thread.currentThread()` 返回当前虚拟线程对象。

## 3. 虚拟线程与线程池 {#虚拟线程与线程池}

平台线程池通过复用降低创建成本。虚拟线程按任务创建，用完即结束。`newVirtualThreadPerTaskExecutor()` 对线程数没有固定池上限。

稀缺资源应单独限定并发：

```java
Semaphore dbPermits = new Semaphore(30);

dbPermits.acquire();
try {
    return repository.query();
} finally {
    dbPermits.release();
}
```

示例在成功取得许可后归还。所有调用都遵守此协议时，最多 30 个查询进入。入口还需限制总在途任务，避免大量等待占用内存。

## 4. 适用场景 {#适用场景}

大量独立网络请求适合使用虚拟线程。JDK 的网络阻塞操作支持卸载 carrier。并发等待数量增加后，I/O 服务可提高吞吐。

CPU 计算仍要占用处理器时间。增加虚拟线程数量会增加竞争，单次计算时长仍受算力限制。

文件 I/O 和第三方 native 调用应逐项确认。部分阻塞操作会保留 carrier，需要实际压测。

## 5. pinning 与 JDK 版本 {#pinning-与-jdk-版本}

pinning 表示虚拟线程在阻塞时仍绑定 carrier。平台线程随之被占用，影响其他虚拟线程调度。

Java 21 中，持有 monitor 时阻塞会导致 pinning。频繁在 synchronized 内执行慢 I/O，会长期占用 carrier。此类代码可改用 ReentrantLock，让阻塞时可以卸载。

native 调用也有绑定边界。例如 native 回调 Java 后发生阻塞，会产生 pinning。

## 6. ThreadLocal 与上下文传播 {#threadlocal-与上下文传播}

虚拟线程支持 ThreadLocal，且每个线程有自己的值。给每个线程缓存昂贵资源，会增加总内存。

跨线程任务需显式传递必要上下文。清理与恢复规则见 [ThreadLocal](./threadlocal-leaks-context.mdx#用-finally-清理)。

## 7. 迁移验证 {#迁移验证}

压测应同时记录吞吐、p99、CPU 和内存。再检查 carrier 数量、pinning 与连接等待。

数据库只有 30 个连接时，大量任务仍会等待连接。虚拟线程降低承载等待的成本，容量约束仍由连接池决定。

客户端、驱动和观测工具需按实际版本验证。性能评估还应包含过载、超时和任务退出。

## 8. pinning 的版本诊断 {#pinning-的版本诊断}

Java 21 可用 `-Djdk.tracePinnedThreads=full` 查看部分 pinning。该参数覆盖持 monitor 时发生的阻塞。它对等待进入 monitor 等情况有观测限制。

JFR 的 `jdk.VirtualThreadPinned` 记录超过阈值的 pinning。Java 21 默认启用该事件，阈值为 20 毫秒。

短小的内存操作可继续使用 synchronized。替换锁应由持锁阻塞的频率和时长决定。

## 9. 虚拟线程的观测与退出 {#虚拟线程的观测与退出}

Java 21 的 ThreadMXBean 只覆盖平台线程。查看虚拟线程可使用专门转储：

```sh
jcmd <pid> Thread.dump_to_file -format=json threads.json
```

命令输出包含平台与虚拟线程的结构化转储。它用于查看线程栈，与传统完整锁信息转储分工不同。

虚拟线程始终为守护线程。仅剩守护线程时，JVM 可以开始退出。程序应通过 `join`、Future 或执行器关闭等待任务。

`ExecutorService.close()` 会等待执行器终止。请求需要总超时时，仍应显式安排取消和退出期限。

## 10. 常见问题 {#常见问题}

### 10.1 单任务延迟与并发吞吐 {#单任务延迟与并发吞吐}

虚拟线程主要降低线程承载成本。它适合让大量 I/O 任务同时等待。单次网络响应和 CPU 计算仍需相应的执行时间。

### 10.2 资源池与执行器 {#资源池与执行器}

虚拟线程无需通过固定 Worker 复用。连接池、限流器和 CPU 执行器仍有各自职责。资源容量应在实际使用入口控制。
