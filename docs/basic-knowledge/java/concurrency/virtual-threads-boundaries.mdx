# 虚拟线程

虚拟线程由 JVM 调度，以较低的线程成本承载大量阻塞任务。本文以 Java 21 为范围，先解释虚拟线程怎样运行，再说明适用场景、资源限制和阻塞时的绑定问题。最后介绍迁移验证、观测与退出。

## 1. 面试核心 {#core}

- **任务与线程。** 虚拟线程自 JDK 21 正式提供，每个任务创建一个线程，任务结束后线程随之结束。
- **阻塞卸载。** 虚拟线程遇到支持卸载的阻塞操作时，会让出承载它的平台线程，供其他虚拟线程运行。
- **适用负载。** 虚拟线程适合用同步代码承载大量阻塞 I/O，CPU 计算的吞吐仍受可用核心数限制。[卡](#virtual-thread-fit)
- **Java 21 的 pinning。** Java 21 中，虚拟线程持有 monitor 时阻塞会导致 pinning，使承载它的平台线程一起被占用。[卡](#pinning-version-boundary)
- **任务完成等待。** 虚拟线程始终是守护线程，程序应在退出前通过 `join`、Future 或关闭执行器等待任务完成。[卡](#virtual-thread-observation)

## 2. 虚拟线程与 carrier 线程 {#虚拟线程与-carrier-线程}

虚拟线程仍要借助平台线程执行代码。承载它的平台线程称为 **carrier 线程**，也叫载体线程。应用可以继续使用同步调用，由 JVM 管理挂载和等待：

```java
try (ExecutorService executor =
             Executors.newVirtualThreadPerTaskExecutor()) {
    Future<Response> response = executor.submit(() -> client.call());
    return response.get();
}
```

示例使用 Java 21，执行器为每个任务创建一个虚拟线程。`get()` 等待并取得调用结果，退出作用域时关闭执行器。

JVM 把大量虚拟线程调度到较少的 carrier 上。虚拟线程占用 carrier 执行代码，称为挂载。遇到支持卸载的等待时，它会让出 carrier，使后者可以运行其他虚拟线程。等待结束后，原虚拟线程重新排队，等待再次挂载。

虚拟线程保留 Java 的调用栈、异常和中断模型，常用的 Thread API 仍然适用。`Thread.currentThread()` 返回的是当前虚拟线程对象。因此，应用可以保留一个请求对应一个线程的同步代码。

## 3. 虚拟线程与线程池 {#虚拟线程与线程池}

平台线程的创建和栈内存成本较高，所以线程池通过复用与数量限制管理它们。虚拟线程则按任务创建，用完即结束。若把虚拟线程固定为少量 Worker，任务又会在池前排队，限制它承载大量等待的能力。

`newVirtualThreadPerTaskExecutor()` 对线程数没有固定池上限。因此，应在**稀缺资源的入口**单独限定并发，例如限制同时查询数据库的任务数：

```java
Semaphore dbPermits = new Semaphore(30);

dbPermits.acquire();
try {
    return repository.query();
} finally {
    dbPermits.release();
}
```

`Semaphore` 是按许可数量限制并发的信号量。所有查询都使用同一个信号量并遵守上述协议时，最多有 30 个查询进入。只有成功取得许可后才进入 `try`，退出时在 `finally` 中归还。

许可只限制正在查询的数量，等待许可的任务仍占内存。所以，入口还需限制总在途任务，也就是已接收但尚未完成的任务。

## 4. 适用场景 {#适用场景}

虚拟线程适合数量大、彼此独立，且大部分时间等待 I/O 的任务。例如，服务需要同时发起大量 HTTP 请求或 JDBC 查询。JDK 的网络阻塞操作支持卸载 carrier，所以同一台机器可以承载更多等待中的任务。

CPU 计算则持续占用处理器时间。大量虚拟线程同时计算时，仍在争夺相同的核心，因此长期计算任务应限制并行度。

文件 I/O、JDBC 驱动和第三方 native 调用需要按实际实现验证。native 指调用本地机器代码的方法。部分阻塞操作会继续占用 carrier，所以要通过压测确认扩展能力。

## 5. pinning 与 JDK 版本 {#pinning-与-jdk-版本}

**pinning** 指虚拟线程被绑定到 carrier，阻塞时也无法卸载。这样，等待中的虚拟线程会占住一个平台线程，其他虚拟线程可用的执行资源就会减少。它影响并发扩展能力，线程语义仍然成立。

Java 21 中，虚拟线程持有 monitor，也就是 `synchronized` 使用的对象监视器锁时，阻塞会导致 pinning。频繁在锁内执行慢 I/O，就会长期占用 carrier。对此，可以用 `ReentrantLock` 替换，让原来由 monitor 导致的阻塞能够卸载。

native 调用也会造成绑定。例如，native 方法回调 Java 后发生阻塞，虚拟线程仍会被 pin 在 carrier 上。

## 6. ThreadLocal 与上下文传播 {#threadlocal-与上下文传播}

虚拟线程支持 `ThreadLocal`，每个线程都能保存自己的值。但虚拟线程数量可以很大，给每个线程缓存昂贵对象，会显著增加总内存。按任务创建的线程也失去了固定 Worker 跨任务复用缓存的机会。

外部资源应在明确的作用域内获取和释放，跨线程任务则显式传递必要上下文。清理与恢复规则见 [ThreadLocal](./threadlocal-leaks-context.mdx#用-finally-清理)。

## 7. 迁移验证 {#迁移验证}

迁移验证要确认吞吐是否提高，以及瓶颈是否转移到了下游。数据库只有 30 个连接时，即使创建更多虚拟线程，也只是让更多任务排在连接池前。

压测应记录以下**性能与资源指标**：

- 吞吐与 P99，确认完成量和较慢请求的耗时。
- CPU 与内存，确认计算和在途任务的成本。
- carrier 数量与 pinning，确认平台线程是否被持续占住。
- 数据库连接等待，确认请求是否卡在下游资源入口。

JDBC 驱动、客户端和观测工具还需按实际版本验证。测试应覆盖过载、超时和任务退出，才能确认取消后资源会按预期释放。

## 8. pinning 的版本诊断 {#pinning-的版本诊断}

定位 pinning 时，需要找到持续占用 carrier 的阻塞栈，再判断是否值得替换锁。Java 21 可用 `-Djdk.tracePinnedThreads=full` 输出部分 pinning 的栈。该参数覆盖持有 monitor 时发生的阻塞，但对等待进入 monitor 等情况有观测限制。

JFR 是 JDK 的运行事件记录工具。它的 `jdk.VirtualThreadPinned` 事件记录超过阈值的 pinning；Java 21 默认启用该事件，阈值为 20 毫秒。

短小的内存操作可以继续使用 `synchronized`。是否替换锁，应由持锁阻塞的频率、时长及其对吞吐的影响决定。

## 9. 虚拟线程的观测与退出 {#虚拟线程的观测与退出}

迁移后，需要同时检查观测工具的范围和程序退出方式。Java 21 的 `ThreadMXBean` 只覆盖平台线程，因此查看虚拟线程要使用专门的转储命令：

```sh
jcmd <pid> Thread.dump_to_file -format=json threads.json
```

命令会把平台线程和虚拟线程的栈写入 JSON 文件。它便于查看大量线程，但不会包含传统转储中的完整锁信息等内容。

虚拟线程始终是守护线程。守护线程本身不会阻止 JVM 退出，所以仅剩守护线程时，JVM 可以开始退出。程序应通过 `join`、Future 或关闭执行器等待任务完成。

`ExecutorService.close()` 会等待执行器终止，因此开篇示例退出作用域时也会等待。请求需要总超时时，仍应安排明确的取消和退出期限。

## 10. 常见问题 {#常见问题}

### 10.1 虚拟线程会让单个任务更快吗？ {#单任务延迟与并发吞吐}

虚拟线程主要降低的是线程承载成本，单次网络响应和 CPU 计算仍需原有的执行时间。它的收益来自让大量 I/O 任务同时等待，从而提高服务吞吐，并保留容易理解的同步代码。

### 10.2 使用虚拟线程以后还需要线程池吗？ {#资源池与执行器}

虚拟线程按任务创建即可，平台线程执行器、定时任务和 CPU 并行计算仍可以使用池。连接池与限流器也继续负责限制稀缺资源，容量应在资源的实际使用入口控制。

## 11. 面试题 {#面试题}

### 11.1 虚拟线程适合哪些场景，有哪些边界 {#virtual-thread-fit}



**考察重点**

- 解释一个任务对应一个虚拟线程，怎样帮助服务承载大量阻塞 I/O。
- 说明 CPU、下游容量和每线程缓存为什么仍会限制吞吐与内存。
- 解释 Java 21 中持有 monitor 时阻塞，为什么会占住 carrier。

**相关内容**：[虚拟线程与 carrier 线程](#虚拟线程与-carrier-线程)至[迁移验证](#迁移验证)。

<details>
<summary>参考回答</summary>

**虚拟线程适合数量大、彼此独立，且大部分时间阻塞等待 I/O 的任务。**

支持卸载的等待会让出 carrier，所以能用较少平台线程承载更多并发请求，并继续使用同步代码。CPU 计算和数据库连接仍受自身容量限制。

每个任务创建一个虚拟线程即可，连接和接口并发用信号量或资源池单独限流。每个线程缓存昂贵对象仍会增加内存，所以 ThreadLocal 也要控制大小和生命周期。Java 21 中，持有 monitor 时阻塞会导致 pinning；native 调用也要结合实际阻塞栈验证。

</details>

<summary>参考回答</summary>

**Java 21 中，频繁在 `synchronized` 内执行慢 I/O 时，可以考虑换成 `ReentrantLock`。**

原因是持有 monitor 时阻塞会 pin 住 carrier，减少其他虚拟线程可用的执行资源。短小的内存操作则可以保留 `synchronized`。

可用 `-Djdk.tracePinnedThreads=full` 定位部分阻塞栈，再结合 JFR 的 `jdk.VirtualThreadPinned` 事件判断持续时间。该事件默认阈值为 20 毫秒，替换应以实际吞吐影响为依据。
