# ReentrantLock

`ReentrantLock` 是支持重入的显式互斥锁。本文负责获取方式、公平策略和 Condition 使用。等待节点的内部组织见 [AQS](./aqs-state-wait-queue.mdx)。

## 1. 面试核心 {#core}

- `ReentrantLock` 支持可中断获取、超时获取和多个 Condition。
- 每次成功加锁都应有一次对应的 `unlock()`。
- 公平获取优先服务排队者，无超时 `tryLock()` 允许插队。[卡](#fair-lock-throughput)
- `await()` 完全释放关联锁，返回前恢复原持有次数。[卡](#condition-recheck)
- 带时限的条件等待应在循环中递减剩余预算。[卡](#condition-time-budget)

## 2. 加锁与释放 {#加锁与释放的写法}

```java
private final ReentrantLock lock = new ReentrantLock();

void update() {
    lock.lock();
    try {
        updateState();
    } finally {
        lock.unlock();
    }
}
```

获取成功后，代码才进入 `try`。`finally` 在正常与异常路径释放锁。可中断获取若抛异常，流程会跳过该临界区。

同一线程可重复获取同一把锁。重入次数降至零时，其他线程才能取得锁。

## 3. 可中断获取与超时获取 {#可中断获取与超时获取}

```java
if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {
    try {
        updateState();
    } finally {
        lock.unlock();
    }
} else {
    rejectBusyRequest();
}
```

`tryLock(timeout, unit)` 在期限内尝试获取。超时返回 `false`，示例据此拒绝繁忙请求。它还会通过 `InterruptedException` 响应中断。

`lockInterruptibly()` 等待时也可响应中断。`lock()` 则继续等待获取，保留中断状态。无超时 `tryLock()` 立即返回获取结果。

## 4. 公平锁与非公平锁 {#公平锁与非公平锁}

`new ReentrantLock(true)` 启用公平策略。竞争时，排队最久者优先获取。当前所有者的重入仍可直接成功。

非公平锁允许正在运行的线程插队。插队成功时可减少等待唤醒带来的空档。公平锁更严格的排队约束会影响吞吐。

无超时 `tryLock()` 会忽略公平策略。需要遵守公平顺序的立即尝试，可用 `tryLock(0, unit)`。后者还会响应中断。操作系统的线程调度仍独立于锁的公平性。

## 5. Condition 等待 {#condition-等待}

```java
private final Condition notEmpty = lock.newCondition();

Item take() throws InterruptedException {
    lock.lockInterruptibly();
    try {
        while (queue.isEmpty()) {
            notEmpty.await();
        }
        return queue.removeFirst();
    } finally {
        lock.unlock();
    }
}
```

示例在同一把锁下检查队列并进入等待。`await()` 完全释放关联锁，等待通知。返回前，它重新加锁并恢复原持有次数。

等待后必须用 `while` 重查条件。线程可虚假唤醒，也可在重获锁前被其他消费者抢先。只有队列确实非空，才执行删除。

持有的其他锁仍由当前线程保留。设计等待协议时，也要检查这些锁是否阻碍生产者。

## 6. `signal` 与 `signalAll` {#signal-与-signalall}

```java
lock.lock();
try {
    queue.addLast(item);
    notEmpty.signal();
} finally {
    lock.unlock();
}
```

示例在持锁状态下更新队列并通知等待者。通知后，生产者继续持有锁直到 `unlock()`。消费者重获锁后才能返回。

`signal()` 选择一个等待者。`signalAll()` 通知全部等待者，大家仍需重新检查条件。不同条件可使用不同的 Condition，减少无关唤醒。

## 7. 条件重查与通知时机 {#条件重查与通知时机}

条件变量的通知只表示值得再次检查状态。等待还允许虚假唤醒，此时也需重新验证条件。

例如两个消费者都等待队列非空。生产者加入一条数据并唤醒它们。第一个消费者取走数据后，第二个应再次等待。

用 `if` 只检查一次，会让第二个消费者操作空队列。用 `while` 可在每次恢复持锁后验证条件。

## 8. 条件等待的剩余预算 {#条件等待的剩余预算}

`awaitNanos` 返回估算的剩余纳秒数。重复等待时应使用该余额：

```java
long remaining = timeoutNanos;
while (queue.isEmpty()) {
    if (remaining <= 0L) {
        return false;
    }
    remaining = notEmpty.awaitNanos(remaining);
}
return true;
```

本片段在持锁的 `try` 内执行，外围 `finally` 解锁。若每轮都传原始超时，反复唤醒就会重启等待预算。包含获取锁的总期限，需从调用入口统一计算。

## 9. 常见问题 {#常见问题}

### 9.1 ReentrantLock 与 synchronized {#reentrantlock-与-synchronized}

两者都提供互斥和锁释放后的可见性。需要超时、中断获取或多个条件队列时，可选 `ReentrantLock`。性能取决于 JVM、竞争强度和临界区成本。

### 9.2 Condition 的锁关联 {#condition-的锁关联}

`ReentrantLock` 的 Condition 与创建它的锁关联。`await`、`signal` 和 `signalAll` 都要求持有该锁。缺少所有权时会抛出 `IllegalMonitorStateException`。

### 10.1 公平锁为什么通常吞吐更低 {#fair-lock-throughput}

**出现公司**：蚂蚁集团、美团

**考察重点**

- 理解插队、排队与唤醒成本。
- 理解公平锁和线程调度公平的区别。
- 理解 `tryLock()` 的特殊行为。

**相关内容**：[可中断获取与超时获取](#可中断获取与超时获取)和[公平锁与非公平锁](#公平锁与非公平锁)。

<details>
<summary>参考回答</summary>

公平锁约束插队，会增加排队者唤醒后的交接等待。非公平锁允许运行中的线程直接利用空闲锁。持续竞争时，这会影响吞吐和等待时间分布。

公平锁仍受操作系统调度影响。无超时 `tryLock()` 也允许插队。应同时测量吞吐与等待分位数，再决定策略。

</details>
