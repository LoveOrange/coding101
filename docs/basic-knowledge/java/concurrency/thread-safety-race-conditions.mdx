# 线程安全

**线程安全**是指多个线程同时访问一个对象时，不管它们怎样交错执行，对象都仍然满足约定的正确性要求。反过来，多个线程共享可变状态却没有约定读写规则，程序就会丢失更新、读到改到一半的状态，或者根据过期的数据做决定。检查一段代码时，可以从被共享和修改的状态入手，确定哪些操作必须作为一个整体完成，再检查所有访问路径是否遵守同一套同步规则。

## 1. 面试核心 {#core}

- 多个线程访问同一份可变状态、且至少一个线程写入时，**各条访问路径要遵守同一套同步规则**。
- `count++` 包含读、计算和写三步，**并发交错会丢失更新**。
- `volatile` 保证单次读写的可见性和顺序，**复合更新的原子性需要锁或原子操作保证**。
- 临界区要**覆盖维护业务不变量的完整过程**，包括条件检查和状态更新。[卡](#judge-thread-safety)
- **多个线程安全操作组合在一起，仍可能存在竞态**。[卡](#compound-thread-safe-operations)

## 2. 竞态条件 {#竞态条件}

**竞态条件**是指程序结果是否正确，取决于多个线程执行的先后顺序。最简单的例子是计数器：

```java
public final class Counter {
    private int value;

    public void increment() {
        value++;
    }

    public int get() {
        return value;
    }
}
```

`value++` 看起来是一条语句，实际要分三步：读取旧值、计算新值、写回。两个线程同时递增时，可能都读到 10，各自算出 11 再写回，结果两次递增只加了一次。这种情况叫**丢失更新**。结果取决于两个线程的三步怎样交错，所以是竞态条件。

还有一个相关但不同的概念。两个线程访问同一个变量、且至少一个是写，这两个访问就是**冲突**的；冲突的普通访问之间如果没有 happens-before 关系，就构成**数据竞争**。happens-before 是 Java 内存模型（JMM）定义的顺序关系，前一个操作的结果保证对后一个操作可见。计数器的例子既有数据竞争，也有竞态条件；第 7 节会看到，消除了数据竞争，竞态条件仍可能存在。

## 3. 原子性、可见性与有序性 {#原子性可见性与有序性}

分析并发错误时，可以从**原子性、可见性和有序性**三个角度看。它们分别问：操作能不能被别的线程从中间插入，一个线程的写入另一个线程什么时候能看到，以及另一个线程观察到的读写顺序要满足什么约束：

| 性质 | 关注点 | 典型问题 |
| --- | --- | --- |
| 原子性 | 操作能否作为整体生效 | 检查与更新被穿插 |
| 可见性 | 写入何时对另一线程可见 | 停止标志读取过期 |
| 有序性 | 跨线程观察应满足的先后约束 | 发布引用与数据写入缺少顺序 |

计数器丢失更新是原子性问题。可见性问题的典型例子是：工作线程循环读一个普通的 `stop` 字段，另一个线程把它改成 `true` 后，工作线程可能一直看不到。有序性问题出现在发布对象时：写对象字段和写引用在另一个线程看来可能颠倒，读者拿到了引用，字段却还没初始化，详见 [安全发布](./safe-publication-escape-final.mdx)。

`volatile` 能解决单次读写的可见性和顺序问题，但解决不了原子性：`volatile int` 上的 `value++` 仍然是三步，仍会被其他线程插入。具体推演见 [volatile](./volatile-barriers-visibility.mdx#复合更新)。

## 4. 不变量与临界区 {#不变量与临界区}

决定加锁范围之前，先写出**业务不变量**，也就是每次操作前后都必须成立的条件。比如扣款要求余额始终非负：

```java
if (balance >= amount) {
    balance -= amount;
}
```

假设 `amount > 0`。这段代码靠「先检查、再扣减」维护余额非负。余额 100 时，两个线程各扣 80，都可能先通过检查，再先后扣减，余额变成 -60。

所以锁要同时覆盖检查和扣减。被锁保护、必须作为整体执行的这段代码叫**临界区**。如果只把扣减换成原子操作，检查和扣减之间仍然有空隙，问题还在。

不用锁也可以，用带条件的 CAS 循环完成整个更新。**CAS**（compare-and-swap）比较当前值和预期值，相同才写入新值；失败说明有别的线程改过，就重新读取余额、重新检查条件，再试一次。

不变量也可能跨多个字段。比如区间对象要求 `lower <= upper`，两个字段要一起更新。把它们分别声明为 `volatile` 只能保证各自的可见性，另一个线程仍可能看到新的 `lower` 和旧的 `upper`，所以需要用锁整体更新，或者把两个值放进一个不可变对象里整体替换。

## 5. 同步策略 {#同步策略}

选择同步方式时，先问状态是不是真的必须共享、必须修改。常用的**四种策略**是：

- **不共享**：状态留在任务内部，或者只交给一个线程访问。这种限制访问线程的方式叫线程封闭。
- **不可变**：对象或快照正确发布后内容不再变化，多个线程可以放心读取。判断是否不可变时，还要看字段引用的对象会不会变。
- **单一所有者**：只由一个线程修改状态，其他线程通过消息提交操作，见 [消息传递](./shared-state-message-passing.mdx)。
- **受控共享**：多个线程必须直接修改状态时，用锁、原子类或并发容器保护。

工具要和状态的变化方式对应。独立的计数适合 `AtomicLong`；多个字段要一起变化，适合用锁；持续到来的事件，可以用队列交给单一消费者依次处理。

## 6. synchronized 状态转换 {#用-synchronized-保护状态转换}

下面用 `synchronized` 修复前面的计数器。读和写两个方法都获取同一个对象的锁：

```java
public final class Counter {
    private int value;

    public synchronized void increment() {
        value++;
    }

    public synchronized int get() {
        return value;
    }
}
```

两个实例同步方法锁的都是当前对象的 monitor（对象监视器）。同一时刻只有一个线程能执行其中任意一个方法，所以一次递增的三步之间不会插入另一次递增。

`get()` 也要加锁，这一点容易漏掉。锁除了互斥，还保证一次解锁之前的写入，对随后获取同一把锁的线程可见。`get()` 不加锁，就和 `increment()` 之间没有这条关系，可能读到旧值。其他访问 `value` 的路径也都要遵守这套规则。机制细节见 [synchronized](./synchronized-monitor-optimizations.mdx)。

## 7. 线程安全操作的组合 {#线程安全操作的组合}

用了线程安全容器，还要检查多次调用之间的空隙。并发 Map 的每个方法单独调用都是线程安全的，但下面的写法一是两次独立调用：

```java
// 写法一：分别检查和插入。
if (!map.containsKey(key)) {
    map.put(key, value);
}

// 写法二：用原子接口替代上面的组合。
Value previous = map.putIfAbsent(key, value);
```

两种写法的区别在于**检查与插入是否原子地完成**：

- 写法一中，两个线程可能都通过 `containsKey` 检查，再先后执行 `put`，后一次写入覆盖前一次的结果。
- 写法二用 `putIfAbsent` 一次完成检查和插入。返回非 null 表示已经有值，这次没有覆盖它。

业务要求第一次写入生效时，用写法二。如果业务条件涉及多个键或多个对象，单个原子方法就不够了，需要为整个操作设计共同的同步。

写法一里没有数据竞争，`ConcurrentMap` 的每次调用内部都做了同步，但它仍然有竞态条件。这就是两个概念要分开的原因：数据竞争看的是单次内存访问有没有同步，竞态条件看的是业务操作整体是否正确。

## 8. 常见问题 {#常见问题}

### 8.1 方法里只有局部变量就一定线程安全吗？ {#局部引用与共享对象}

不一定。局部变量本身属于当前这次方法调用，别的线程碰不到；但它可能指向一个共享对象。比如局部变量引用了一个多个线程都能访问的列表，通过它调用 `add` 时仍然需要同步。所以要看的不只是变量，还有它引用的对象。

### 8.2 压力测试一直通过，能证明线程安全吗？ {#压力测试与正确性}

不能。压力测试只能发现实际执行到的那些交错，覆盖不了所有可能；JIT 编译优化、线程调度和硬件差异，都会让线上的执行方式和测试时不同。测试的作用是寻找反例，正确性仍然要根据业务不变量和同步关系推导出来。

## 9. 面试题 {#面试题}

### 9.1 怎样判断一段代码是否线程安全 {#judge-thread-safety}

**考察重点**

- 找出哪些状态被多个线程共享，以及哪些访问会修改它们。
- 说明哪些字段或操作共同维护业务不变量，并据此确定临界区。
- 区分 `volatile` 的单次访问保证与完整状态转换的要求。

**相关内容**：[竞态条件](#竞态条件)至[同步策略](#同步策略)。

<details>
<summary>参考回答</summary>

**判断标准是多个线程访问对象时，所有操作仍能保持业务不变量。**

这个判断要覆盖**共享状态、原子性和可见性**：

- 共享状态包括多个线程访问的对象，也包括局部引用指向的共享对象。
- 原子性要求保护完整的状态转换，例如余额检查和扣减，以及多个字段的共同变化。
- 可见性要求所有访问遵守同一同步规则，并能用 happens-before 证明写入对读者可见。

状态只在任务内使用、正确发布后保持不可变，或由单一线程负责时，可以减少加锁需求。需要共享修改时，再按不变量选择锁、原子操作或并发容器。压力测试用于寻找反例，正确性仍需上述推导。

</details>

### 9.2 多个线程安全方法组合后，整体一定线程安全吗？ {#compound-thread-safe-operations}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：说明单个方法为什么安全，以及多个调用之间的空隙怎样破坏业务条件。

**相关内容**：[线程安全操作的组合](#线程安全操作的组合)。

<details>
<summary>参考回答</summary>

**多个线程安全方法组合后，整体仍可能存在竞态。**

每个方法内部的同步只保证这一次调用完整执行，两次调用之间的空隙不受保护。比如两个线程都通过 `containsKey` 检查，再分别执行 `put`，后一次写入就会覆盖前一次结果。

若要求首次写入生效，应使用 `putIfAbsent`，将检查与插入合成一次原子操作。如果业务条件跨越多个键，则还要为这些键设计共同的同步规则。

</details>
