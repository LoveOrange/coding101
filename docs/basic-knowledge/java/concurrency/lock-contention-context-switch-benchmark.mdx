# 锁竞争

锁竞争会增加排队时间，并消耗调度与同步资源。本文负责线程转储、JFR 和基准测试的证据链。死锁等进度问题见 [并发活跃性](./liveness-deadlock-livelock-starvation.mdx)。

## 1. 面试核心 {#core}

- 线程转储反映采样时刻的栈和锁等待关系。
- `jdk.JavaMonitorEnter` 记录 monitor 获取等待事件。
- `jdk.ThreadPark` 覆盖锁、条件和队列等 park 等待。
- JFR 事件阈值会过滤短于阈值的等待。[卡](#jfr-threshold-evidence)
- 同负载下等待下降且吞吐改善，可支持锁热点判断。[卡](#prove-lock-contention)

## 2. 症状时间线 {#症状时间线}

先记录吞吐、p95/p99、超时和错误的变化。再对齐以下数据：

- 观察进程与线程 CPU。
- 观察 monitor 等待与 park 事件。
- 观察运行线程、阻塞线程和队列数量。
- 观察连接池与下游耗时。
- 观察上下文切换与运行队列。

锁内慢 I/O 会使其他线程一起排队。该场景的修复点是缩短持锁期间的 I/O 等待。线程数量只表示现象，原因需由栈和时间线确认。

## 3. 线程转储 {#线程转储}

连续采集 3—5 份线程转储，按等待栈分组。再沿锁地址找到持有者，并检查其执行位置。

```sh
jcmd <pid> Thread.print -l
```

命令适合查看平台线程及锁信息。相同等待关系持续存在时，再与业务延迟对齐。线程名称应能映射到具体执行器和业务。

虚拟线程使用专门的转储方式。具体边界见 [虚拟线程](./virtual-threads-boundaries.mdx#虚拟线程的观测与退出)。

## 4. JFR 等待事件 {#jfr-等待事件}

Java 26 中可重点查看三类事件：

| 事件 | 等待类型 |
| --- | --- |
| `jdk.JavaMonitorEnter` | 进入 monitor 的竞争等待 |
| `jdk.JavaMonitorWait` | `Object.wait()` 条件等待 |
| `jdk.ThreadPark` | `LockSupport.park` 等待 |

park 事件可来自锁、队列或空闲 Worker。分析时应结合事件栈识别等待原因。monitor enter 的时长反映获取等待。完整持锁时长还需结合持有方的采样和业务埋点。

## 5. 上下文切换 {#上下文切换}

上下文切换需要保存和恢复执行状态。线程被唤醒后，还会受到 CPU 调度和缓存局部性影响。

大量可运行线程会竞争 CPU。频繁阻塞与唤醒也会增加调度次数。诊断时应同时观察系统切换率和业务进展。

优化方向包括减少线程、批处理和缩短临界区。按独立状态分片也能减少共享竞争。

## 6. 并发基准测试 {#并发基准测试}

JMH 基准应覆盖不同竞争条件：

- 改变线程数和读写比例。
- 分别测试均匀 key 与热点 key。
- 保留临界区内有代表性的计算量。
- 同时观察吞吐和延迟分布。
- 使用预热、多个 fork，并消费计算结果。

服务压测还要包含 GC、连接池和下游调用。微基准只比较局部机制。并发正确性需结合模型推导与专门测试。

## 7. 优化结果验证 {#优化结果验证}

复测应保持请求量、并发度和数据分布相同。除吞吐与 p99 外，还要检查业务结果。

锁等待下降后，检查队列和下游等待是否上升。观察 CPU、分配率及拒绝情况。故障负载下还需验证任务能超时并恢复。

## 8. JFR 阈值与采样边界 {#jfr-阈值与采样边界}

JFR 仅记录已启用且满足阈值的持续时间事件。短于阈值的等待会被过滤。把事件时长相加，得到的是已记录事件的总时长。

```sh
jcmd <pid> JFR.start name=locks settings=profile duration=60s filename=locks.jfr
jfr print --events jdk.JavaMonitorEnter,jdk.JavaMonitorWait,jdk.ThreadPark locks.jfr
```

第一条命令采集一分钟，结束后生成文件。第二条输出指定事件。诊断短等待时，应核对实际配置并调整阈值。更多事件会增加采集和分析成本。

缺少事件时，还需检查录制时段和栈采集设置。事件记录为空本身不足以排除竞争。

## 9. 常见问题 {#常见问题}

### 9.1 WAITING 与正常空闲 {#waiting-与正常空闲}

空闲 Worker 会等待队列中的任务。`WAITING` 数量高时，应先根据线程栈区分用途。调度开销需通过上下文切换和 CPU 数据确认。

### 9.2 锁粒度与不变量 {#锁粒度与不变量}

锁分片适合相互独立的状态。涉及跨分片不变量时，需要额外协调和锁顺序。应依据热点数据决定拆分范围。

<details>
<summary>参考回答</summary>

锁等待与业务退化的时间关联，是诊断的起点。先对齐吞吐、长尾和 CPU，再连续采集线程栈。找出持续出现的等待者与持有者。

用 JFR 区分 monitor 竞争、park 和正常空闲。结合持有方栈识别慢 I/O 或热点状态。修改后用相同负载比较等待、吞吐和 p99。业务结果正确且相关等待下降，才支持修复结论。

</details>
