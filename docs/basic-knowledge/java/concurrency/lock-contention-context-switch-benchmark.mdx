# 锁竞争

**锁竞争**是多个线程同时争用同一把锁，于是排队等待、产生额外同步开销的现象。它常常是服务吞吐上不去、长尾延迟变高的原因，但也常常被误判：线程多、`BLOCKED` 多，不一定就是锁的问题。

要说「性能问题来自锁竞争」，需要一条证据链：先确定服务从什么时候开始变慢，再用线程转储看线程在哪里等，用 JFR 看等了多久，最后在相同负载下复测，证明改动之后等待减少了、服务也确实变好了。

## 1. 面试核心 {#core}

- 单份**线程转储只反映采集那一刻**的调用栈和锁等待关系，连续采集多份才能识别持续的等待。
- JFR 的 `jdk.JavaMonitorEnter` 记录**获取 monitor 时的竞争等待**，不包含完整的持锁时长。
- JFR 的 `jdk.ThreadPark` 记录线程挂起等待，它的来源**不只是锁竞争**，还包括条件等待和队列空闲。
- JFR 会**过滤短于阈值的等待**，所以记录下来的时长只覆盖满足配置的事件。[卡](#jfr-threshold-evidence)
- 在相同负载下，**锁等待下降、吞吐和长尾延迟改善，并且业务结果正确**，才能支持「锁热点已缓解」的判断。[卡](#prove-lock-contention)

## 2. 症状时间线 {#症状时间线}

排查的第一步是确定服务什么时候开始变慢，再看同一时段线程在做什么。先记下吞吐、p95/p99、超时和错误开始变化的时刻。p95 和 p99 分别表示 95% 和 99% 的请求延迟低于这个值，用来观察慢请求。

然后把下面这些运行指标对齐到同一段时间：

- 进程和线程的 CPU。
- monitor 等待、park 事件，以及锁持有者的调用栈。
- 运行线程、阻塞线程和队列的数量。
- GC、连接池等待和下游调用耗时。
- 上下文切换和运行队列。

对齐的意义在于找因果。比如锁内有一次 HTTP 调用，下游接口变慢，持锁线程的持锁时间就跟着变长，其他线程全在后面排队。这时锁等待和下游耗时会同时上升，根因在下游和「锁里做 I/O」这个写法。在保证业务一致的前提下，可以把 I/O 移到锁外，或者缩短锁内的等待。

反过来，线程多或 `BLOCKED` 多，只说明值得往下查等待原因。锁是不是瓶颈，还要结合调用栈和业务延迟的变化来确认。

## 3. 线程转储 {#线程转储}

**线程转储**是某一时刻所有线程调用栈和状态的快照。单份快照可能恰好拍到一次正常的短暂等待，所以要连续采集 3 到 5 份，把相同的等待栈归为一组。再顺着锁的地址找到持有者，看它正在执行什么代码。

```sh
jcmd <pid> Thread.print -l
```

这条命令打印平台线程的调用栈和锁信息，`-l` 会额外列出线程持有的 JUC 锁。如果几份转储里都出现同一个持有栈，等待线程的数量和业务延迟又一起在涨，这个位置就值得重点检查。

线程名要能对应到具体的执行器和业务。如果只有 `pool-3-thread-7` 这样的名字，还得先去追查它属于哪个线程池，定位会慢很多。

虚拟线程要用专门的转储方式，见 [虚拟线程](./virtual-threads-boundaries.mdx#虚拟线程的观测与退出)。

## 4. JFR 等待事件 {#jfr-等待事件}

**JFR**（Java Flight Recorder）是 JVM 内置的运行事件记录工具，可以记录等待、CPU、对象分配等活动。线程转储告诉你线程「在哪里等」，JFR 则帮你量化「等了多久」。Java 21 中重点看这三类等待事件：

| 事件 | 等待类型 |
| --- | --- |
| `jdk.JavaMonitorEnter` | 进入 monitor 的竞争等待 |
| `jdk.JavaMonitorWait` | `Object.wait()` 条件等待 |
| `jdk.ThreadPark` | `LockSupport.park` 等待 |

monitor 是 `synchronized` 使用的对象监视器，争不到 monitor 的线程处于 `BLOCKED`，对应 `JavaMonitorEnter`。`ReentrantLock` 这类 JUC 锁则通过 park 挂起等待的线程，所以 JUC 锁的等待表现为 `WAITING`，对应 `ThreadPark`。但 park 还可能来自 `Condition` 条件队列、阻塞队列，或者没活干的空闲工作线程，必须结合事件的调用栈区分。

分析时重点比较这几项：

- 已记录事件的累计等待时间，判断总成本集中在哪里。
- 单次最长等待时间，找出拖慢长尾请求的操作。
- 热点锁对象和等待栈，定位大量线程争用的共享状态。
- 持有者的调用栈，判断锁内是否有慢 I/O 或过多计算。

注意，`JavaMonitorEnter` 的时长是拿到锁之前等了多久，不是持锁多久。完整的持锁时长，要结合持有方的采样和业务埋点。同时也可以看 JFR 的 CPU 和对象分配事件，确认成本是不是其实来自别的工作。

### 4.1 JFR 阈值与采样边界 {#jfr-阈值与采样边界}

解读 JFR 之前，先确认这次录制覆盖了哪些等待。对于有持续时间的事件，JFR 只记录已经启用、并且时长达到阈值的那些。短于阈值的等待会被过滤掉，所以把记录的时长加起来，得到的只是「已记录事件」的总时长，不是全部等待。

```sh
jcmd <pid> JFR.start name=locks settings=profile duration=60s filename=locks.jfr
jfr print --events jdk.JavaMonitorEnter,jdk.JavaMonitorWait,jdk.ThreadPark locks.jfr
```

第一条命令用 `profile` 配置录制 60 秒，结束后生成 `locks.jfr`；第二条命令打印其中的三类等待事件。如果要诊断短而频繁的等待，先核对实际配置里的阈值，再按需要调低。阈值越低，保留的短事件越多，采集和分析的成本也越高。

事件很少或者没有调用栈时，还要检查录制是否覆盖了故障时段，以及这些事件有没有开启栈采集。记录为空不能排除锁竞争，要结合连续的线程转储和业务指标判断。

## 5. 上下文切换 {#上下文切换}

**上下文切换**是 CPU 从执行一个线程转去执行另一个线程的过程。它要保存和恢复执行状态，这是直接成本。间接成本来自缓存局部性：线程反复访问同一批或相邻的数据时，缓存命中率高；切到新线程后，它的数据可能还不在缓存里，需要重新加载。

切换分两种：

- **自愿切换**：线程因为等锁或等 I/O 主动阻塞。频繁地阻塞和唤醒，会增加调度次数，锁竞争激烈时就是这样。
- **非自愿切换**：线程本来还能运行，但时间片用完或被抢占了。可运行的线程远多于 CPU 核心时，它们会互相争抢执行机会。

所以切换率升高时，要同时看 CPU、等待时长和业务完成量，判断是哪一种。优化可以从减少线程数、批量处理或缩短**临界区**（被锁保护的那段代码）入手；按互相独立的状态分片、减少共享，也能降低竞争频率。只调整调度参数，业务里的热点仍然在。

## 6. 并发基准测试 {#并发基准测试}

**JMH** 是 JVM 上的微基准测试工具，适合比较一小段并发操作的成本，比如两种锁写法的吞吐。要让测试接近真实竞争，需要覆盖这些条件：

- 改变线程数和读写比例，看并发度提高后性能怎样变化。
- 分别测试均匀 key 和热点 key，区分分散访问和集中争用。
- 临界区里保留有代表性的计算量，否则只测到了空锁的成本。
- 同时用吞吐模式和采样时间模式，分别看成功操作量和延迟分布。
- 做预热，并使用多个 fork（启动多个独立的 JVM 分别运行），降低单次运行的偶然影响。
- 返回或消费计算结果，防止优化器把没用到的计算整个删掉。

微基准只比较局部机制，服务压测还要把请求处理的其他成本带进来：

- 序列化会消耗 CPU，并产生临时对象。
- GC 会影响运行时间和延迟。
- 连接池和下游调用会引入排队与外部等待。

性能数据好看不代表代码正确，正确性还要通过内存模型推导、代码审查和专门的并发测试验证。JMH 的具体写法见 [JMH](../jvm/jmh-correct-benchmarks.mdx)。

## 7. 优化结果验证 {#优化结果验证}

复测要证明改动改善了整个服务，而不只是让某个指标变好看。保持请求量、并发度和数据分布不变，比较这几项：

- 吞吐和 p99 是否改善，业务结果是否仍然正确。
- 锁等待是否下降，队列或下游等待有没有随之上升。
- CPU 和对象分配率是否增加，有没有引入新的成本。
- 高峰和故障负载下，任务能否按预期拒绝、超时，并在故障解除后恢复。

几个指标要一起看。平均延迟下降但 p99 上升，说明慢请求反而更慢了；吞吐提高却出现业务错误，也不能算优化成功。锁等待下降了，下游等待却上升，可能只是把排队从锁上挪到了别处。所以验收要同时满足正确性、吞吐和长尾延迟的要求。

## 8. 常见问题 {#常见问题}

### 8.1 WAITING 线程多，就说明上下文切换多吗？ {#waiting-与正常空闲}

不能这样判断。空闲的工作线程会在队列上等待新任务，长期停在 `WAITING` 是正常状态，并不消耗 CPU。应该先用调用栈区分空闲等待和业务等待，再结合系统的切换率、CPU 和连续的事件记录，确认有没有调度开销。

### 8.2 把锁拆得越细越好吗？ {#锁粒度与不变量}

不是。锁应该按互相独立的状态拆分，粒度根据实际热点决定。拆得更细能减少一部分竞争，但也会增加跨锁协调和加锁顺序的复杂度。

如果多个分片之间有必须共同满足的业务约束，就需要额外的同步来维护它。比如把账户按 ID 分片加锁之后，跨分片的转账仍然要同时锁住两个账户，才能保证总余额不变，还得按统一顺序加锁防止死锁。拆分后仍要通过性能分析和正确性检查验证收益。

## 9. 面试题 {#面试题}

### 9.1 怎样证明 Java 服务的性能问题来自锁竞争 {#prove-lock-contention}

**考察重点**

- 能把连续线程转储、JFR 等待事件与业务变慢的时间对齐。
- 能通过调用栈区分 monitor 竞争、JUC 锁等待和线程池空闲。
- 能在相同负载下复测，确认等待减少且业务结果正确。

**相关内容**：[症状时间线](#症状时间线)至[优化结果验证](#优化结果验证)。

<details>
<summary>参考回答</summary>

**需要证明锁等待和服务变慢同时发生，并通过相同负载下的优化复测来验证。**

可以按这个顺序收集证据：

1. 对齐吞吐、长尾延迟、活跃线程、队列和 CPU，确定故障时段。
2. 连续采集线程转储，找出反复出现的等待者和持有者，检查锁内是否有慢 I/O 或大量计算。
3. 用 JFR 量化已记录的等待，结合调用栈区分 monitor 竞争、JUC 锁、`Condition` 和正常的线程池空闲。
4. 修改后保持并发度和数据分布一致，复测吞吐、p99、等待时间、CPU 和业务结果。

相关等待下降、服务表现改善，才支持「锁热点已缓解」的结论。还要确认队列和下游等待没有增加，否则可能只是把成本转移到了别处。

</details>

### 9.2 JFR 没有锁等待事件，就能排除锁竞争吗？ {#jfr-threshold-evidence}

**考察重点**：能解释事件启用状态、时长阈值和录制时段怎样影响 JFR 的记录范围。

**相关内容**：[JFR 阈值与采样边界](#jfr-阈值与采样边界)。

<details>
<summary>参考回答</summary>

**不能排除，因为 JFR 只记录符合本次录制配置的事件。**

应该依次确认：事件是否启用，时长阈值是否过高，录制是否覆盖了故障时段。缺少调用栈时，还要检查栈采集设置。

短而频繁的等待会被阈值过滤掉，可以调低阈值后重新录制观察。已记录的时长只覆盖满足配置的事件，所以还要结合连续的线程转储，以及相同负载下的复测来判断。

</details>
