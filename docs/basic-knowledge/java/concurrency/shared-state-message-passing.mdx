# 消息传递

消息传递通过交接命令协调状态变更。本文负责单一所有者、消息边界和过载处理。底层队列的交接可见性见 [Java 内存模型](./jmm-happens-before.mdx#juc-组件的交接语义)。

## 1. 面试核心 {#core}

- 单一所有者串行修改状态，其他线程通过消息提交操作。[卡](#reduce-shared-state)
- 发送后继续修改消息对象，会重新引入共享竞态。
- 有界队列用固定容量限制待处理消息数量。
- 结果通道可用 `CompletableFuture` 返回成功或异常。
- 毒丸终止协议要求先停止生产，再处理剩余消息。[卡](#mailbox-shutdown-failure)

## 2. 共享对象的同步范围 {#共享对象的同步范围}

```java
public final class OrderBook {
    private final Map<Long, Order> orders = new HashMap<>();

    public void cancel(long id) {
        orders.remove(id);
    }
}
```

多个线程直接修改 orders 时，需要共同的锁协议。协议应覆盖 map 与订单状态的组合不变量。

也可由单个消费者持有整个 `OrderBook`：

```java
BlockingQueue<Command> mailbox = new LinkedBlockingQueue<>(1_000);

void eventLoop() throws InterruptedException {
    while (!Thread.currentThread().isInterrupted()) {
        Command command = mailbox.take();
        command.apply(orderBook);
    }
}
```

示例使用容量为 1000 的 FIFO 队列。单消费者按出队顺序执行命令。其他线程应通过消息访问状态，避免直接调用对象。命令异常的处理方式见后文。

## 3. 消息与状态所有权 {#消息与状态所有权}

消息应包含一次状态转换所需的信息：

```java
record CancelOrder(long orderId) implements Command {
    public void apply(OrderBook book) {
        book.cancel(orderId);
    }
}
```

示例使用 Java 16 起正式支持的 record。命令只携带订单 ID，由所有者执行取消。基本值和不可变字符串适合跨线程交接。

集合消息可用副本或不可变值传递。引用槽位固定后，可变元素仍需限制访问。队列交接保证入队前写入的可见性。

## 4. 结果通道 {#结果通道}

```java
record CreateOrder(Order order, CompletableFuture<Long> reply) {}
```

示例展示结果通道字段。所有者成功时调用 `reply.complete(id)`。命令失败时，应调用 `completeExceptionally(error)`。

调用方等待应有截止时间。回复 Future 超时后，已入队命令仍可被执行。状态查询和重试需使用稳定的业务标识。

## 5. 有界队列与过载 {#有界队列与过载}

消费者每秒处理 1000 条，生产者持续提交 2000 条，积压就会增长。

有界队列容量用尽后，提交方必须处理结果。`put` 会等待，`offer` 可立即失败。带超时 `offer` 可把排队纳入请求预算。

订单命令应明确返回拒绝或超时。统计类消息可按业务合并。刷新通知可只保留最新请求。

## 6. 共享状态的适用场景 {#共享状态的适用场景}

消息传递引入排队延迟和异步错误处理。单个所有者也会成为热点。

独立计数器可直接使用原子类。配置读取可使用不可变快照。低竞争且需要同步结果的短操作可使用锁。

按 key 分片时，同一 key 应稳定路由到同一所有者。跨分片不变量仍需协调协议。

## 7. 消费者异常与关闭协议 {#消费者异常与关闭协议}

`BlockingQueue` 没有统一的关闭方法。可由业务定义停止接收、排空或取消的协议。

毒丸是一种特殊终止消息。使用 FIFO 队列时，应先停止并协调所有生产者。再把毒丸放到已接受消息之后。多消费者还要安排足够的终止通知。

单条命令异常应通知对应结果通道。若处理状态已失去一致性，应停止并恢复状态。若选择继续消费，也需先确保状态仍可用。

直接中断消费者可结束等待。队列里尚未处理的消息需另行拒绝或接管。

## 8. 常见问题 {#常见问题}

### 8.1 消息对象的竞态边界 {#消息对象的竞态边界}

消息中的可变对象若仍被发送者修改，就存在共享访问。多个消费者直接修改同一状态时，也需同步。所有权约束覆盖对象及其可达状态。

### 8.2 消息顺序与业务顺序 {#消息顺序与业务顺序}

FIFO 队列保证其定义的入队顺序。并发发送者的真实业务先后，还需序列号或其他协议。多个消费者的完成顺序也会受执行时长影响。
