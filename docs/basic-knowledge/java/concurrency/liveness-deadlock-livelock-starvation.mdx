# 并发活跃性

**活跃性**关心的是任务能不能持续取得进展、最终把工作做完。线程安全保证「不出错」，活跃性保证「不卡住」。违反活跃性的三种典型情况是死锁、活锁和饥饿：死锁是互相等、谁也动不了，活锁是一直在忙却做不成，饥饿是整体在推进、个别任务一直轮不到。

这三种情况在监控上可能长得很像：请求不返回、队列积压。要分清它们，看线程状态和 CPU 不够，还得看业务完成量，以及每个任务到底在等谁。线程池里父任务等子任务，也会悄悄形成一个等待环。

## 1. 面试核心 {#core}

- **死锁**是多个参与者各自持有资源、又等待对方释放，**等待关系连成环**，谁都无法继续。
- 所有线程**遵守统一的加锁顺序**，就能破坏锁之间的循环等待。
- **活锁**中的线程**一直在改变状态**，却因为反复让步和冲突，任务始终完成不了。
- **饥饿**是**整体有进展，个别任务长期得不到资源**。[卡](#deadlock-livelock-starvation)
- 父任务占满线程池的工作线程，再**同步等待同一个池里排队的子任务**，会形成资源等待环。[卡](#executor-starvation-cycle)

## 2. 死锁 {#死锁}

理解死锁，要看「谁占着资源，谁在等它」。多个线程的等待关系连成一个环，每个线程都在等别人先释放，就全部停住了。转账是最常见的例子：

```java
void transfer(Account from, Account to, Money amount) {
    synchronized (from) {
        synchronized (to) {
            move(from, to, amount);
        }
    }
}
```

`transfer` 先锁转出账户，再锁转入账户。线程甲从账户 1 转到账户 2，先锁住账户 1；同时线程乙从账户 2 转到账户 1，先锁住账户 2。接下来甲要等账户 2 的锁，乙要等账户 1 的锁，两人都不会放手，就永远等下去了。

死锁要同时满足**四个条件**：

- 资源由线程互斥占用。
- 线程持有资源的同时，还在等待其他资源。
- 已经占有的资源不能被外部强行剥夺。
- 多个参与者形成循环等待。

破坏其中任何一个，就能避免这类死锁。业务里最常用的是破坏循环等待：统一加锁顺序，所有线程都先锁排序靠前的账户。

```java
Account first = smallerId(from, to);
Account second = first == from ? to : from;
```

这段代码按账户 ID 决定顺序，之后依次锁住 `first` 和 `second`。这样甲和乙都会先去抢账户 1 的锁，抢不到的一方在第一把锁上等，不会出现各拿一把的情况。

排序键要用唯一、稳定的账户 ID，`from` 和 `to` 是同一个账户的情况也要单独处理。如果用哈希值这类可能碰撞的排序键，两个账户的键相同时就分不出先后，这时可以引入一把额外的 **tie lock**：排序键相同的操作先拿这把公共锁，串行执行。

## 3. 超时获取锁 {#超时获取锁}

另一种思路是给等待设个上限，为循环等待留一条退路。`ReentrantLock.tryLock(timeout, unit)` 在指定时间内拿不到锁就返回 `false`，这时调用方应先释放已经持有的第一把锁，再决定要不要重试。

但如果所有线程失败后都立即重试，很可能又同时拿到第一把锁、又同时等第二把，从死锁变成了下一节的活锁。所以还需要三样东西：

- **总截止时间**，限制多次尝试加起来花的时间。
- **退避**，即重试前先等一段时间，把竞争者错开。
- **重试上限**，达到上限或截止时间就返回明确的失败，交给调用方处理。

中断的传播和退出时的清理见 [任务取消](./interruption-timeout-cancellation.mdx)。

## 4. 活锁 {#活锁}

活锁中的线程一直在执行，但做的工作不断作废。比如两个线程发现冲突后，同时撤销自己的操作，又同时重试；每一轮都再次冲突，于是一直忙着让步，却没有一个任务完成。这就像两个人在走廊里相遇，同时往同一边让，又同时往另一边让。

忙着重试时，线程处于 `RUNNABLE` 状态，CPU 使用率和重试次数都很高。但如果退避里有睡眠或阻塞，CPU 也可能不高。所以判断活锁要看成功完成量，只看线程是不是在运行，判断不了业务有没有进展。

降低反复冲突的概率，可以从这几方面入手：

- **随机退避**：每个线程等待的时间随机，重试时间自然错开。
- **指数退避**：连续失败后逐步拉长等待间隔。
- 给其中一方确定的优先级，避免双方同时让步。
- 缩短每次尝试占用资源的时间，减少冲突的机会。

这些办法同样要配合截止时间和重试上限，达到上限就返回失败，免得无效的尝试一直占着资源。

## 5. 饥饿 {#饥饿}

饥饿时系统整体仍在完成工作，只是部分任务长期拿不到需要的资源。它们等的可以是锁、许可、CPU，也可以是线程池里的执行机会。常见的来源有：

- 非公平竞争中，新来的线程不断插队，等了很久的线程一直抢不到。
- 高优先级任务持续占满同一个队列，低优先级任务一直排队。
- 读锁不断被新来的读者拿到，写者很难进入。
- 调度器总是先执行短任务，大任务被反复推后。

公平锁可以改善这把锁的获取顺序，但多出来的排队约束会牺牲吞吐量；而 CPU 怎样分配，仍然由操作系统的线程调度决定。需要隔离不同业务时，可以拆分队列、设置资源配额，或者限制单个租户能占用的资源。

## 6. 进度指标与诊断 {#进度指标与诊断}

诊断要回答两个问题：哪些任务没完成，它们在等谁。把下面这些数据放到同一条时间线上看：

- 成功完成率，以及最早进入、还没完成的任务已经等了多久。
- 重试、超时和取消的次数。
- 锁等待、队列长度和线程栈。
- CPU、上下文切换和下游响应时间。

三种情况的特征不同。死锁是一个稳定的等待环，阻塞的线程处于 `BLOCKED` 或 `WAITING`，自身几乎不耗 CPU，连续几次线程栈都一样。活锁是反复尝试，重试次数高，却没有有效完成。整体仍有吞吐量，只有部分任务的等待时间越来越长，就该查饥饿。

## 7. 线程池的资源等待环 {#线程池的资源等待环}

线程池的工作线程也是一种有限资源，任务之间的依赖可能把它耗尽。假设一个固定线程池只有两个 **Worker**（执行任务的工作线程）。两个父任务各占一个 Worker，各自向同一个池提交子任务，然后同步等待子任务的 Future。

这时子任务排在队列里，需要空闲的 Worker 才能执行；父任务却要等子任务完成才会释放 Worker。双方形成资源等待环。线程都处于 `WAITING`，没有一个锁环，整个池却停住了。

一种改法是组合异步结果：父任务不阻塞等待，而是在子任务完成后再安排后续逻辑，这样父任务能先释放 Worker。另一种是让有依赖关系的任务使用不同的执行器，并分别约束容量。只是把池调大并不能根治，还要验证最大嵌套并发，否则负载更高时还会再次耗尽线程。

## 8. 死锁检测的覆盖范围 {#死锁检测的覆盖范围}

JVM 的死锁检测能帮你找到锁环，但完整的业务等待关系还得自己补全。对平台线程，可以用 `jcmd <pid> Thread.print -l` 打印线程栈和锁信息。连续采集几次线程转储，核对持有者和等待者是不是一直在互相等。

`ThreadMXBean.findDeadlockedThreads()` 检测平台线程之间的锁环，覆盖 monitor（`synchronized` 用的锁）和受支持的 **ownable synchronizer**。后者是能记录独占持有线程的同步器，比如 `ReentrantLock` 内部使用的同步器。

数据库锁、HTTP 调用和 Future 依赖，也能和线程等待连成环；连接池的容量限制还会让任务等待可用连接。这些关系 JVM 看不到，要结合业务调用补全，它无法自动重建跨进程的依赖图。

另外，Java 21 的 `ThreadMXBean` 只支持平台线程，不覆盖虚拟线程。所以 `findDeadlockedThreads()` 返回 `null`，只说明这次没有在它支持的范围内发现锁环。

## 9. 常见问题 {#常见问题}

### 9.1 使用 ConcurrentHashMap 就能避免死锁吗？ {#并发容器与等待环}

不能，仍然要检查业务的等待关系。`ConcurrentHashMap` 只保证它自己定义的操作线程安全，你传进去的业务回调却可能获取外部锁或者等待 Future。多个组件按相反顺序访问这些资源时，照样会形成等待环。

### 9.2 随机退避能保证任务最终完成吗？ {#随机退避的保证范围}

不能保证。随机退避只是降低反复冲突的概率，任务能不能完成还取决于调度和竞争协议，它不能单独证明算法一定有进展。实现时仍然要限制总时间和重试次数，并给耗尽预算的任务一条失败路径。

## 10. 面试题 {#面试题}

### 10.1 死锁、活锁和饥饿怎样区分 {#deadlock-livelock-starvation}

**考察重点**

- 能区分循环等待、反复冲突和部分任务长期等待。
- 能结合业务完成量解释线程状态，避免仅凭 CPU 或状态名称判断故障。
- 能说明统一锁顺序、退避和资源配额分别解决什么问题。

**相关内容**：[死锁](#死锁)至[进度指标与诊断](#进度指标与诊断)。

<details>
<summary>参考回答</summary>

**死锁是参与者互相等待资源、谁都无法继续；活锁是线程一直在改变状态，却因反复冲突完成不了任务；饥饿是整体有进展，但部分任务长期得不到资源。**

处理死锁，可以统一加锁顺序，或者超时获取锁、失败时释放已持有的锁，打破等待环。活锁可以用随机或指数退避、确定优先级来减少冲突，再用重试上限结束失败的尝试。饥饿则要检查获取顺序、资源配额和任务隔离。

诊断时把线程栈和完成率、重试次数、等待时间对齐。线程状态和 CPU 只能辅助判断，比如死锁线程几乎不耗 CPU，活锁线程可能很忙，最终还是要确认具体任务有没有进展。

</details>

### 10.2 线程都在等待 Future，为什么线程池仍会停滞？ {#executor-starvation-cycle}

**考察重点**：能说明父子任务怎样争用有限的工作线程，以及怎样消除这种循环依赖。

**相关内容**：[线程池的资源等待环](#线程池的资源等待环)。

<details>
<summary>参考回答</summary>

**父任务占满了工作线程，又在等同一个池里排队的子任务，形成了资源等待环。**

子任务要等父任务释放线程才能执行，父任务却要等子任务先完成，双方都无法推进。这里没有锁环，所以线程都在 `WAITING`。

可以改成组合异步结果，让父任务不阻塞等待，在子任务完成后再继续后续逻辑。也可以把父子任务放到不同的执行器，并按最大嵌套并发约束容量。

</details>

### 10.3 findDeadlockedThreads 返回 null 能排除死锁吗？ {#deadlock-detection-scope}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：能说明 JVM 自动检测哪些锁环，以及哪些任务和资源依赖需要人工补充。

**相关内容**：[死锁检测的覆盖范围](#死锁检测的覆盖范围)。

<details>
<summary>参考回答</summary>

**不能排除。**

返回 `null` 只表示这次没有发现它支持的锁环。这个接口检测平台线程之间的 monitor 和受支持的独占同步器，Java 21 中也不覆盖虚拟线程。

Future 依赖、连接池容量和跨进程调用，同样可以形成等待环，JVM 检测不到。所以还要根据任务在等什么、资源被谁占着，补全业务的等待关系图。

</details>
