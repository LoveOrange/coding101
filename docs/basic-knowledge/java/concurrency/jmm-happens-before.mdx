# Java 内存模型

Java 内存模型规定跨线程读写允许出现的结果。本文负责 happens-before 规则及可见性推导。对象构造与逸出见 [安全发布](./safe-publication-escape-final.mdx)。

## 1. 面试核心 {#core}

- happens-before 是可传递的内存顺序关系。[卡](#happens-before-rules)
- 同一 monitor 的解锁先于后续加锁。
- 同一 volatile 字段的写先于同步顺序中的后续读。
- 线程的动作先于另一线程成功检测到其终止。
- `sleep` 和 `yield` 只影响调度，缺少同步语义。[卡](#sleep-no-publication)

## 2. 跨线程可见性问题 {#跨线程可见性问题}

```java
int value;
boolean ready;

// Thread A
value = 42;
ready = true;

// Thread B
if (ready) {
    System.out.println(value);
}
```

本例的两个普通字段缺少跨线程同步。B 即使读到 `ready == true`，也可读到 `value == 0`。写标志与读标志之间缺少 happens-before 关系。

JMM 约束合法执行结果。编译器和处理器可在这些约束内重排执行。只按源代码顺序推演，会遗漏允许的结果。

## 3. happens-before 规则 {#happens-before-规则}

happens-before 规定动作之间的可见性和顺序。常用规则如下：

- 同一线程中，前面的动作先于后面的动作。
- 同一 monitor 的解锁先于后续加锁。
- volatile 写先于同步顺序中该字段的后续读。
- `start()` 调用先于新线程的全部动作。
- 线程动作先于另一线程成功检测到其终止。
- 对线程的中断先于其他线程检测到该中断。

这里的“先于”均表示 happens-before。检测终止可通过成功等待结束的 `join()` 完成。默认初始化也先于程序中的后续动作。

该关系具有传递性。若 A 先于 B、B 先于 C，则 A 先于 C。它约束可观察结果，无需对应逐条机器指令的时间顺序。

## 4. volatile 发布链 {#用-volatile-发布数据}

```java
private int value;
private volatile boolean ready;

public void publish() {
    value = 42;
    ready = true;
}

public int consume() {
    if (!ready) {
        throw new IllegalStateException("not ready");
    }
    return value;
}
```

本例只发布一次，且发布后保持 `value` 不变。`value = 42` 先于 volatile 写。读到 `ready == true` 后，消费者再读 `value`。传递性使消费者得到 42。

volatile 的复合更新边界见 [volatile](./volatile-barriers-visibility.mdx)。

## 5. JUC 组件的交接语义 {#juc-组件的交接语义}

JUC 组件为交接定义内存顺序：

- 提交前的动作先于 Executor 中的任务动作。
- 异步计算中的动作先于成功 `Future.get()` 后的动作。
- 入队前的动作先于另一线程取出该元素后的动作。
- 计数归零前，`countDown()` 前的动作先于成功 `await()` 后的动作。
- `release()` 前的动作先于成功 `acquire()` 后的动作。

这些规则覆盖各 API 规定的交接方向。入队后继续修改消息内容，仍需额外同步。

## 6. 数据竞争与顺序一致性 {#数据竞争与顺序一致性}

冲突的普通内存访问若缺少 happens-before 排序，就存在数据竞争。其中至少一个访问是写入。

正确同步的程序保证顺序一致性。可以按保持线程内顺序的某种交错理解结果。存在数据竞争时，还需考虑模型允许的重排序。

顺序一致性仍允许多个线程交错。业务检查与更新若分开同步，仍可产生竞态。具体例子见 [线程安全](./thread-safety-race-conditions.mdx#线程安全操作的组合)。

## 7. sleep 与 join 的同步边界 {#sleep-与-join-的同步边界}

`Thread.sleep()` 和 `yield()` 都没有同步语义。让读线程晚几秒执行，也无法建立发布关系。

对已启动线程，无超时 `join()` 正常返回表示已终止。带超时的 `join(long)` 返回时，目标线程仍可存活。未启动线程的 `join()` 会直接返回。需要确认线程已结束，才能使用终止检测规则。

```java
worker.start();
worker.join(100);
if (worker.isAlive()) {
    throw new IllegalStateException("still running");
}
System.out.println(result);
```

示例用 `isAlive()` 确认终止后读取结果。假设 `result` 仅由 worker 写入，读者可见其最终写入。

## 8. 常见问题 {#常见问题}

### 8.1 happens-before 与时间先后 {#happens-before-与时间先后}

happens-before 表达内存顺序。两个动作之间可以夹着大量其他动作。观察到现实时间先后，还需同步关系才能推导可见性。

### 8.2 内存模型与缓存实现 {#内存模型与缓存实现}

JMM 规定允许观察到的读写结果。JVM 与处理器通过屏障和缓存一致性实现约束。推导正确性应使用同步关系。

<details>
<summary>参考回答</summary>

happens-before 是 JMM 定义的偏序关系。它约束跨线程可见性，并具有传递性。规则包括程序顺序、monitor 解锁与后续加锁。还包括 volatile 写读、线程启动和终止检测。

普通数据写入可先于 volatile 发布标记。消费者读到标记后，再读取普通数据。这条传递链使发布前的数据对消费者可见。

</details>
