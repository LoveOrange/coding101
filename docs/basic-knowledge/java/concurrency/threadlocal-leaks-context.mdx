# ThreadLocal

`ThreadLocal` 为每个线程提供独立的值槽位。本文负责值的生命周期、泄漏和跨任务上下文。虚拟线程的承载模型见 [虚拟线程](./virtual-threads-boundaries.mdx)。

## 1. 面试核心 {#core}

- OpenJDK 21 在 Thread 的 ThreadLocalMap 中保存值。
- ThreadLocalMap 的 entry 使用弱 key 和强 value。[卡](#threadlocal-leak)
- `remove()` 删除当前线程的 entry，后续 get 可重新初始化。
- `InheritableThreadLocal` 在创建子线程时传递初始值。[卡](#inheritable-pool-context)
- 嵌套上下文应在 finally 恢复外层值。[卡](#threadlocal-nested-restore)

## 2. ThreadLocalMap 的结构 {#threadlocalmap-的结构}

```java
private static final ThreadLocal<RequestContext> CONTEXT =
        new ThreadLocal<>();
```

OpenJDK 21 的 Thread 持有自己的 ThreadLocalMap。ThreadLocal 实例作为 key 定位该线程的值。不同线程因此可以关联不同的 RequestContext。

隔离的是槽位。若多个线程放入同一个可变对象，对象仍由它们共享。对象内部访问还需同步。

## 3. 弱引用 key 与 value 保留 {#弱引用-key-与-value-保留}

entry 的 key 是弱引用，value 是强引用。key 没有其他强引用时可被回收。其 value 仍被线程的 map 持有。

后续部分 map 操作会清理陈旧 entry。线程结束后，也可释放对应存储。线程池 Worker 长期存活时，值会被意外保留。

静态 ThreadLocal 的 key 持续存活时，旧请求值也会一直占据槽位。值的清理需要跟随业务作用域。

## 4. finally 清理 {#用-finally-清理}

```java
CONTEXT.set(context);
try {
    handleRequest();
} finally {
    CONTEXT.remove();
}
```

此处假设每次请求独占该作用域。`remove()` 删除 entry，后续 `get()` 会重新走初始化。`set(null)` 则保留值为 null 的 entry。

线程复用时，遗漏清理会造成上下文污染。下一任务若未设置值，就会读到旧用户或租户。嵌套调用还需恢复外层绑定，见下文。

## 5. 跨线程的上下文传递 {#跨线程的上下文传递}

已有 Worker 使用自己的 ThreadLocalMap。提交任务时，普通 ThreadLocal 的值留在提交线程。

任务包装器可捕获必要的不可变上下文。Worker 开始时绑定，结束时恢复原状态。包装器还需覆盖异常和调用者执行的路径。

传播数据应限制在租户、trace 等必要字段。整个请求对象会延长大量关联数据的生命周期。

## 6. 虚拟线程与 ThreadLocal {#虚拟线程与-threadlocal}

Java 21 可为每个任务创建一个虚拟线程。线程结束时释放其局部状态。每个线程缓存昂贵对象，仍会造成内存压力。

跨线程任务需显式传递上下文。局部绑定仍按业务作用域清理，嵌套调用恢复外层值。

## 7. 内存保留与上下文诊断 {#诊断内存保留与上下文污染}

- 在堆转储中检查 Worker 到 entry 和 value 的引用链。
- 在任务边界检查上下文是否残留。
- 复用同一 Worker，验证异常后的清理结果。
- 同时观察线程数量和单任务内存。

诊断日志只记录是否存在残留，避免输出上下文敏感值。还应区分合法缓存和超出作用域的请求对象。

## 8. 子线程继承与线程池复用 {#子线程继承与线程池复用}

`InheritableThreadLocal` 在创建子线程时初始化子值。默认 `childValue` 返回父值引用。父子线程因此可共享同一可变对象。

线程池按任务复用已经创建的 Worker。新任务提交时，Worker 不会重新继承提交者上下文。若首次建线程时继承旧用户信息，还会污染后续任务。

应按任务捕获不可变快照，并在执行边界绑定和恢复。

## 9. 嵌套作用域的恢复 {#嵌套作用域的恢复}

内层调用覆盖上下文后，退出时应恢复外层值：

```java
RequestContext previous = CONTEXT.get();
CONTEXT.set(inner);
try {
    invokeNested();
} finally {
    if (previous == null) {
        CONTEXT.remove();
    } else {
        CONTEXT.set(previous);
    }
}
```

本例约定 null 表示未绑定，且使用默认初始化。内层直接 remove 会丢掉外层上下文。保存并恢复能保持嵌套调用的作用域。

提交任务也应考虑 `CallerRunsPolicy`。任务有机会在提交线程执行，此时更需要恢复原值。

## 10. 常见问题 {#常见问题}

### 10.1 弱 key 的清理边界 {#弱-key-的清理边界}

弱引用允许 ThreadLocal 在失去强引用后被回收。entry 中的 value 仍需 map 清理。业务应通过 `remove()` 明确结束值的生命周期。

### 10.2 数据库连接的线程绑定 {#数据库连接的线程绑定}

事务框架可在线程上临时绑定连接。框架必须完整管理获取、解绑和归还。异步切换线程时，还需重新确认事务边界。

## 11. 面试题 {#面试题}

### 11.1 ThreadLocal 为什么可能发生内存泄漏，怎样避免 {#threadlocal-leak}

**出现公司**：美团、某云原生企业

**考察重点**

- 理解 ThreadLocalMap 的弱 key 与强 value。
- 理解线程池长生命周期和上下文污染。
- 理解 `finally` 中 `remove` 与显式传播。

**相关内容**：[ThreadLocalMap 的结构](#threadlocalmap-的结构)至[跨线程的上下文传递](#跨线程的上下文传递)。

<details>
<summary>参考回答</summary>

长期存活的线程会通过 ThreadLocalMap 保留 value。entry 的 key 是弱引用，value 是强引用。key 被回收后，陈旧 entry 仍会保留值直到清理。

独立请求应在 `finally` 中 `remove()`。嵌套作用域则恢复先前绑定。跨线程任务需显式捕获并设置必要上下文。

</details>

### 11.3 嵌套调用设置 ThreadLocal 后，直接 remove 有什么问题？ {#threadlocal-nested-restore}

<details>
<summary>参考回答</summary>

</details>
