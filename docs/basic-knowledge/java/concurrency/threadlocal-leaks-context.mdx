# ThreadLocal

`ThreadLocal` 让同一个变量在每个线程里各有一份值，常用来保存当前请求的用户、租户、trace 标识这类调用上下文，免得一层层当参数传。它的问题都出在生命周期上：值跟着线程活，而线程池里的线程几乎不死，所以值会比请求活得久，造成内存保留，或者让下一个任务读到上一个任务的数据。用好它要清楚三件事：值存在哪里、为什么不会自动释放，以及在请求结束、跨线程和嵌套调用时分别怎样清理和恢复。

## 1. 面试核心 {#core}

- OpenJDK 21 把值保存在**当前 `Thread` 的 `ThreadLocalMap` 中**，用 `ThreadLocal` 实例作为查找键。
- `ThreadLocalMap` 的**键是弱引用、值是强引用**，长期存活的线程会保留尚未清理的值。[卡](#threadlocal-leak)
- 独立请求**在 `finally` 中调用 `remove()`**，删除当前线程的条目，避免后续任务读到旧值。
- `InheritableThreadLocal` **只在创建子线程时传递初始值**，线程池复用 Worker 时不会重新传递。[卡](#inheritable-pool-context)
- 嵌套调用覆盖上下文后，应**在 `finally` 中恢复外层值**，而不是直接删除。[卡](#threadlocal-nested-restore)

## 2. ThreadLocalMap 的结构 {#threadlocalmap-的结构}

同一个 `ThreadLocal` 实例，不同线程读到的是各自的值。原因在于值并不存在 `ThreadLocal` 对象里：

```java
private static final ThreadLocal<RequestContext> CONTEXT =
        new ThreadLocal<>();
```

OpenJDK 21 中，每个 `Thread` 对象持有自己的 `ThreadLocalMap`。这张表以 `ThreadLocal` 实例为键，保存这个线程关联的值。调用 `CONTEXT.get()` 时，先取出当前线程的表，再用 `CONTEXT` 作键去查。所以 `CONTEXT` 只是一把钥匙，同一把钥匙在不同线程的表里对应不同的 `RequestContext`。

隔离的只是「每个线程把引用存在哪里」。如果多个线程放进去的是同一个可变对象，它们访问的仍然是同一份数据，对象内部的并发读写照样需要同步。

## 3. 弱引用 key 与 value 保留 {#弱引用-key-与-value-保留}

`ThreadLocalMap` 的每个条目（entry）对键和值用了不同的引用方式，这是理解泄漏的关键。

条目的 key 是**弱引用**：弱引用不阻止垃圾回收，外部不再强引用某个 `ThreadLocal` 实例后，它就可以被回收，条目的 key 变成 null。value 则是**强引用**，由线程的表一直持有。引用链是「线程 → `ThreadLocalMap` → 条目 → value」，只要线程还活着，value 就回收不了。

表的部分操作（比如 `set`、`get` 时碰到 key 为 null 的条目）会顺带清理这些失效条目，线程结束时整张表也会释放。但线程池的工作线程（Worker）会反复执行任务，可能和进程活得一样长。清理如果迟迟没有发生，请求对象、大对象，甚至它们关联的类加载器，都会被一直保留。

更常见的情况是 `ThreadLocal` 声明为 `static final`，就像上面的 `CONTEXT`。这时键一直有强引用，根本不会变成 null，顺带清理也就无从发生，上一次请求放进去的值会一直留到被下一次 `set` 覆盖。所以清理不能指望垃圾回收，要跟着请求或调用的结束主动做。

## 4. finally 清理 {#用-finally-清理}

请求结束时，要同时清掉它留在线程上的上下文。把设置和清理放在同一个作用域，并用 `finally`，正常返回和抛出异常都能覆盖：

```java
CONTEXT.set(context);
try {
    handleRequest();
} finally {
    CONTEXT.remove();
}
```

这里假设这次请求独占这段作用域。`remove()` 删除当前线程的条目，之后再 `get()` 会重新调用初始化方法得到初始值。`set(null)` 则不同，它保留条目、只把值设为 null，之后 `get()` 直接返回 null。

线程复用时漏掉清理，除了内存问题，还会造成**上下文污染**：新任务读到了旧任务的数据。比如下一个请求因为某个分支没有设置上下文，就会读到上一个用户的身份、租户或 trace 信息（trace 信息用来把一次请求经过的多个服务调用串起来）。身份串了是安全问题，trace 串了会让排查找错请求。嵌套调用的情况不能直接 `remove()`，第 9 节单独说明。

## 5. 跨线程的上下文传递 {#跨线程的上下文传递}

提交任务的线程和执行任务的 Worker 各有自己的表。所以把任务交给线程池时，提交线程里的 `ThreadLocal` 值不会跟着过去，Worker 里读到的是它自己表里的东西。

需要传递时，用任务包装器完成**上下文的捕获、绑定与恢复**：

1. 提交任务时，在提交线程里捕获需要的不可变上下文。
2. 执行任务前，在执行线程里保存它原来的值，再绑定捕获的上下文。
3. 任务结束时，在 `finally` 中恢复执行线程原来的状态，正常返回和异常都覆盖。

日志框架和可观测性库通常自带上下文传播机制，可以按所用框架接入。传递的内容只限租户、trace 这类必要字段。如果把整个请求对象捕获进去，后台任务会延长它和它关联数据的生命周期。

第 2 步先保存原值、第 3 步再恢复，而不是直接 `remove()`，是因为任务有时会在提交线程自己身上执行，第 9 节说明这种情况。

## 6. 虚拟线程与 ThreadLocal {#虚拟线程与-threadlocal}

Java 21 可以为每个任务创建一个虚拟线程，任务结束线程就结束。线程不再跨任务复用，上下文污染的问题随之减少，线程结束时它的局部存储也会释放。

但虚拟线程的数量可以达到数百万。如果每个线程都在 `ThreadLocal` 里缓存一个昂贵对象（比如一个格式化器或缓冲区），原本在线程池里只有几十份，现在就有几百万份，总内存会显著增长。所以在虚拟线程中，仍然要按业务作用域清理绑定，跨线程任务显式传递必要上下文，嵌套调用恢复外层值；按线程缓存昂贵对象的做法则需要重新评估。

## 7. 内存保留与上下文诊断 {#诊断内存保留与上下文污染}

诊断要分别回答两个问题：对象为什么还在内存里，以及新任务有没有读到旧上下文。可以收集以下**四项证据**：

- 在堆转储中，沿 Worker、`ThreadLocalMap$Entry` 到可疑 value 查看引用链，确认是哪个线程保留了对象。
- 在任务开始和结束处检查上下文是否残留；日志只记录有没有残留，不输出敏感值本身。
- 在测试中让同一个 Worker 连续执行任务，确认前一个任务抛异常后，下一个任务仍然读不到旧上下文。
- 同时观察线程数量和单个任务的内存，区分合理的缓存增长和请求对象超出作用域的保留。

## 8. 子线程继承与线程池复用 {#子线程继承与线程池复用}

`InheritableThreadLocal` 解决的是创建子线程时的初始值传递：父线程创建子线程那一刻，子线程复制一份父线程的绑定。默认的 `childValue` 直接返回父值的引用，所以父子线程引用的是同一个对象，对象可变的话，双方的修改会互相影响。

问题在于继承只在线程创建时发生一次。线程池把后续任务交给已经创建好的 Worker，提交任务时不会再复制上下文。比如 Worker 是在处理用户 A 的请求时被创建的，它继承了 A 的信息；之后用户 B 的任务交给这个 Worker，读到的仍然是 A。

所以线程池场景应该按任务捕获不可变快照，在任务开始时绑定、结束时恢复，也就是第 5 节的包装器做法。

## 9. 嵌套作用域的恢复 {#嵌套作用域的恢复}

嵌套调用结束后，外层代码还要继续用自己的上下文。所以内层设置新值之前先保存原值，退出时恢复：

```java
RequestContext previous = CONTEXT.get();
CONTEXT.set(inner);
try {
    invokeNested();
} finally {
    if (previous == null) {
        CONTEXT.remove();
    } else {
        CONTEXT.set(previous);
    }
}
```

这个例子用默认初始化，约定 null 表示还没有绑定。如果内层退出时直接 `remove()`，外层的上下文会被一起删掉，外层后续代码就读不到它了。保存 `previous` 之后，内层退出时能把外层的值放回去；只有原来就没绑定时，才删除条目。

线程池也会出现这种嵌套。拒绝策略是 `CallerRunsPolicy` 时，线程池未关闭且已经饱和，任务会直接在提交线程上执行。这相当于在提交者的调用里嵌套执行任务，包装器如果在结束时直接 `remove()`，就会把提交线程自己的上下文删掉。所以包装器也要保存并恢复原值。

## 10. 常见问题 {#常见问题}

### 10.1 key 已经是弱引用，为什么还要 remove？ {#弱-key-的清理边界}

因为弱引用只让 `ThreadLocal` 键可以被回收，value 仍然被表强引用着。value 要等后续的表操作碰巧清理到它，或者线程结束，才会释放，而这个时间无法确定；键是静态字段时，甚至永远不会被回收。所以独立请求结束时要调用 `remove()`，明确结束这次绑定。

### 10.2 ThreadLocal 能用来保存数据库连接吗？ {#数据库连接的线程绑定}

可以临时绑定，但必须有人完整管理它的生命周期。事务框架会在事务范围内把连接绑定到当前线程，并负责获取、解绑和归还。如果应用只是把连接长期放进 `ThreadLocal`，就容易出现连接泄漏，或者下一个任务用上了上一个事务的连接。切换到异步任务或虚拟线程时，执行线程可能变了，还要确认事务边界，连接应该由明确的资源作用域管理。

## 11. 面试题 {#面试题}

### 11.1 ThreadLocal 为什么可能发生内存泄漏，怎样避免 {#threadlocal-leak}

**考察重点**

- 说明键被回收后，线程为什么仍能通过 `ThreadLocalMap` 保留值。
- 解释 Worker 长期存活怎样导致内存保留和上下文污染。
- 区分独立请求清理、嵌套恢复与跨线程传播。

**相关内容**：[ThreadLocalMap 的结构](#threadlocalmap-的结构)至[跨线程的上下文传递](#跨线程的上下文传递)。

<details>
<summary>参考回答</summary>

**长期存活的线程会通过 `ThreadLocalMap` 保留已超出业务作用域的 value，造成内存泄漏。**

条目的 key 是弱引用，value 是强引用。因此，即使 key 被回收，值仍要等到条目清理或线程结束才会释放；`ThreadLocal` 是静态字段时，key 不会被回收，值会一直留到被覆盖。线程池复用 Worker 时，未清理的旧值还会污染下一任务。

独立请求应在设置值的同一作用域内，用 `finally` 调用 `remove()`。嵌套调用则保存并恢复先前绑定。跨线程任务只捕获必要的不可变上下文，再在执行边界绑定和恢复。

</details>

### 11.2 InheritableThreadLocal 为什么不适合直接传播线程池任务上下文？ {#inheritable-pool-context}

**考察重点**：区分线程创建与任务提交的时机，并解释默认继承为什么会共享对象引用。

**相关内容**：[子线程继承与线程池复用](#子线程继承与线程池复用)。

<details>
<summary>参考回答</summary>

**`InheritableThreadLocal` 只在线程创建时继承值，而线程池会让已有 Worker 执行新任务。**

因此，后续提交任务时，Worker 仍持有最初继承的上下文。默认继承还会共享同一个值引用，可变对象的修改会相互影响。

按任务显式传递不可变上下文，才能让每次执行对应正确的请求。任务结束时还应恢复执行线程原来的绑定。

</details>

### 11.3 嵌套调用设置 ThreadLocal 后，直接 remove 有什么问题？ {#threadlocal-nested-restore}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：说明内层清理怎样影响外层绑定，以及任务在提交线程执行时为什么也需要恢复。

**相关内容**：[嵌套作用域的恢复](#嵌套作用域的恢复)。

<details>
<summary>参考回答</summary>

**直接 `remove()` 会丢失外层仍需使用的上下文。**

内层进入前应保存原值，在 `finally` 中恢复，只有原先未绑定时才删除条目。

线程池未关闭且已饱和时，`CallerRunsPolicy` 会让任务在提交线程执行。这时任务与提交者共用一个线程，所以也应恢复原值，让提交者继续使用自己的上下文。

</details>
