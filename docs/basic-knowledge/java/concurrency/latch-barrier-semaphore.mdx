# Java 并发同步器

**同步器**是用来协调多个线程「什么时候可以继续往下走」的组件。JUC 里最常用的三个，各自回答一个不同的问题：`CountDownLatch` 等一组事件做完，`CyclicBarrier` 让一组参与者每一轮都到齐了再一起走，`Semaphore` 限制同时占用某种资源的线程数。

选哪个，先看线程在等什么：等事件、等同伴，还是等名额。答好这类问题，还要讲清它们在失败时的行为：任务抛了异常或超时了，计数谁来减，屏障怎么恢复，许可谁来还。

## 1. 面试核心 {#core}

- `CountDownLatch` **计数归零后永久放行**等待者，适合等待一组事件完成；同一个实例**不能重置复用**。
- `CyclicBarrier` 让**固定数量的参与者逐轮会合**，每轮成功后自动开始下一轮。[卡](#latch-barrier-semaphore)
- `Semaphore` 用**可以反复获取和归还的许可**，限制同时占用资源的任务数量。
- `CyclicBarrier` 的等待者**中断或超时，会破坏本轮屏障**，其他等待者收到 `BrokenBarrierException`；参与者在进入 `await` 之前就退出，屏障**感知不到**。[卡](#barrier-broken-boundary)
- 即使在公平模式下，**`Semaphore.tryAcquire()` 也允许插队**。

## 2. CountDownLatch {#countdownlatch}

`CountDownLatch` 是一个一次性的倒计数器，适合「等一组任务都结束」的场景。完成方每次把计数减一，等待方一直等到计数归零再继续：

```java
CountDownLatch done = new CountDownLatch(tasks.size());

for (Task task : tasks) {
    executor.execute(() -> {
        try {
            task.run();
        } finally {
            done.countDown();
        }
    });
}

if (!done.await(2, TimeUnit.SECONDS)) {
    handleTimeout();
}
```

计数的初始值是任务数，每个任务结束时调用一次 `countDown()`。可以有一个或多个线程调用 `await()` 等待。计数归零后，正在等的线程全部放行，之后再调用 `await()` 也会立即返回。计数只减不增，所以要等下一批任务时，得新建一个实例。

`countDown()` 写在 `finally` 里，是为了保证任务抛异常时也会减计数，否则计数永远到不了零，等待方只能等到超时。但有一种情况 `finally` 也救不了：任务被执行器拒绝，根本没运行，`finally` 自然也不会执行。调用方要处理提交失败，要么自己替它减掉这次计数，要么直接结束这次等待。

示例最多等 2 秒，超时后 `await()` 返回 `false`。这时还要取消或接管剩下的任务，不能让它们在后台无人管理。还要注意，计数归零只说明完成信号收齐了，每个任务是成功还是失败，结果和异常需要另外收集。

## 3. CyclicBarrier {#cyclicbarrier}

`CyclicBarrier`（循环屏障）让固定数量的线程在每一轮结束时互相等待，全部到齐再一起进入下一轮。比如并行迭代计算，每个线程算完本轮自己那部分后，要等所有线程都算完，汇总结果，才能开始下一轮。

```java
CyclicBarrier barrier = new CyclicBarrier(workers, this::mergeRound);
```

每个参与者做完本阶段的工作后调用 `await()`。最后一个到达的线程会执行可选的 **barrier action**，也就是放行前的汇总动作，这里是 `mergeRound`。它成功结束后，本轮所有参与者一起放行。

和 latch 不同，屏障在成功会合后自动开始下一轮，可以反复使用。如果参与者数量会动态变化，可以改用 `Phaser`，它支持注册和注销参与者。

### 3.1 屏障的破坏与恢复 {#屏障的破坏与恢复}

屏障要等所有参与者到齐，所以一个参与者出问题，整轮都会受影响。等待中的线程被中断或等待超时，会**破坏**本轮屏障：出问题的那个线程收到 `InterruptedException` 或 `TimeoutException`，其他正在等的线程收到 `BrokenBarrierException`。barrier action 抛出异常，同样会破坏屏障。

更麻烦的是参与者在调用 `await` 之前就因业务异常退出了。屏障不知道它出了事，其他线程会一直等这个缺席者。所以参与者要用带超时的 `await`，并配合统一的取消协议结束本轮。

`reset()` 会打断当前正在等待的线程，让屏障回到初始状态，开始新一轮。重置之前，要先协调上一轮的参与者退出，否则旧线程会混进新一轮：人数凑齐了，但它们处理的已经不是同一个阶段。

## 4. Semaphore {#semaphore}

`Semaphore`（信号量）通过许可数量限制并发容量。一个许可代表一个可占用的资源名额，常用来限制连接数、调用外部接口的并发数，或者保护昂贵的设备。

```java
Semaphore permits = new Semaphore(20);

permits.acquire();
try {
    callDownstream();
} finally {
    permits.release();
}
```

`acquire()` 拿走一个许可，没有许可时就等待。示例在拿到许可之后才进入 `try`，再在 `finally` 里归还。只要所有调用都遵守这种配对写法，同时调用 `callDownstream()` 的线程最多就是 20 个。

`Semaphore` 不记录许可是哪个线程拿的，所以许可可以由另一个线程归还。这也带来风险：多调用一次 `release()` 就会凭空多出一个许可，总数甚至可以超过初始的 20，限流就失效了。所以业务要明确每个许可由谁释放，并保证只还一次。

## 5. 三者的选择 {#三者的选择}

选同步器，先问线程在等什么：

| 需求 | 组件 |
| --- | --- |
| 等待 N 个完成事件 | `CountDownLatch` |
| 固定参与者逐轮会合 | `CyclicBarrier` |
| 动态参与者逐阶段会合 | `Phaser` |
| 限制同时占用资源的数量 | `Semaphore` |

比如主线程等 N 个任务结束，用 latch 记录还没完成的事件数。要求最多 N 个任务同时调用接口，就需要 semaphore 管理可以反复使用的名额。如果误用 latch 去限流，计数归零之后就永久放行，再也限制不了容量。

## 6. 超时与业务失败 {#超时中断与业务失败处理}

同步器只协调 JVM 内的线程，业务结果仍然要调用方自己管理。设计失败路径时，要分别处理三类情况：

- 等待超时以后，决定迟到的结果还要不要，以及由谁取消或接管剩下的任务。
- 拿到许可后发生异常或中断，要在清理路径上归还许可，让后续任务还能进来。
- 屏障被破坏后，让所有参与者统一结束本轮，或者协调好之后重新开始。

这些计数都在内存里，进程一退出就没了。重启后要恢复业务进度，需要持久化记录；跨进程的协调要交给数据库、消息系统或分布式协调服务，由它们提供一致性保证。

## 7. 常见问题 {#常见问题}

### 7.1 CountDownLatch 能重复使用吗？ {#countdownlatch-的生命周期}

不能。`CountDownLatch` 的计数只会减到零，没有重置的方法，归零后的等待都会直接通过。固定参与者需要反复会合，用 `CyclicBarrier`；参与者会动态变化，用 `Phaser`。

### 7.2 公平 Semaphore 会严格按请求顺序完成任务吗？ {#semaphore-的公平性}

不会。公平模式约束的是许可的分配顺序，任务什么时候完成还取决于调度和各自的执行时长。而且它按线程到达内部排队点的先后分配许可，不是按外部请求到达的时刻。

另外，不带超时的 `tryAcquire()` 在公平模式下仍然允许插队，一次获取多个许可的重载也一样。批量获取还会影响等待时间：排在前面的任务一次要多个许可，后面的任务都得等它凑够数量。所以用公平模式时，也要考虑每个任务各要多少许可。

## 8. 面试题 {#面试题}

### 8.1 `CountDownLatch`、`CyclicBarrier` 和 `Semaphore` 有什么区别 {#latch-barrier-semaphore}

**考察重点**

- 能根据等待的对象，区分事件完成、阶段会合和资源容量。
- 能解释 latch 为什么是一次性的，以及 barrier 怎样逐轮复用。
- 能说明超时或异常后由谁结束任务、处理屏障和归还许可。

**相关内容**：[CountDownLatch](#countdownlatch)至[三者的选择](#三者的选择)。

<details>
<summary>参考回答</summary>

**`CountDownLatch` 等待一组事件完成，`CyclicBarrier` 让固定参与者逐轮会合，`Semaphore` 限制同时占用资源的数量。**

latch 的计数只减不增，归零后永久放行，所以适合一次性等待一批任务。barrier 在每轮参与者到齐后放行，再自动开始下一轮。semaphore 反复发放和回收许可，让资源名额可以持续复用。

失败路径也各不相同。latch 要在 `finally` 里递减计数，业务结果另外保存。barrier 要协调本轮参与者一起退出或恢复。semaphore 要在成功拿到许可后负责归还，并且只还一次，避免名额泄漏或凭空变多。

</details>

### 8.2 参与者业务失败会自动打破 CyclicBarrier 吗？ {#barrier-broken-boundary}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：能区分进入 await 前的业务失败和等待中的失败，并解释重置前为何要协调参与者。

**相关内容**：[屏障的破坏与恢复](#屏障的破坏与恢复)。

<details>
<summary>参考回答</summary>

**不会。参与者在进入 `await()` 之前因业务异常退出，屏障感知不到。**

其余线程会一直等这个缺席者，所以业务需要带超时的等待和统一的取消协议。

能触发破坏的是等待中的失败：线程在 `await` 中被中断或超时，或者 barrier action 抛出异常。这时其他等待者收到 `BrokenBarrierException`。要用 `reset()` 重建屏障，应先协调旧参与者退出，避免新旧两轮的线程混在一起。

</details>
