# 任务取消

**任务取消**是调用方通知后台任务「不用再做了」，并让任务及时退出、释放资源的过程。它由三样东西配合完成：**超时**限定调用方最多等多久，**中断**把停止请求传给执行任务的线程，**取消**把 Future 的结果状态标记为已取消。

这三者各管一段，最容易出错的就是把它们当成一回事：`get` 超时了以为任务停了，Future 取消了以为扣款请求没发出去。要答好这类问题，关键是分清每一步改变的是等待者、执行线程，还是结果状态，以及外部副作用由谁确认。

## 1. 面试核心 {#core}

- 调用链在入口**计算统一的截止时间**，后续每一步只使用剩余预算。
- `Future.get(timeout, unit)` 超时**只结束这一次等待**，任务可以继续运行；要终止任务，还得发出取消请求，并由任务响应。
- `FutureTask.cancel(true)` 成功后**把结果标为取消，并尝试中断正在执行的任务**。
- Future 进入取消状态后，**已经发出的网络请求仍可能在下游产生副作用**。[卡](#timeout-cancellable-task)
- `FutureTask.cancel(false)` 成功后，**已经开始的计算可以继续运行，但返回值会被丢弃**。[卡](#cancel-false-running)

## 2. 截止时间与剩余预算 {#截止时间与剩余预算}

一条调用链应该共用一个等待上限。如果三个步骤各自等 1 秒，最坏情况下总共要等将近 3 秒，调用方原本只愿意等 1 秒。做法是在入口算出一个统一的**截止时间**，后面每一步只用还没消耗掉的时间：

```java
Result awaitResult(long deadline)
        throws InterruptedException, ExecutionException, TimeoutException {
    long remaining = deadline - System.nanoTime();
    if (remaining <= 0) {
        throw new TimeoutException();
    }
    return future.get(remaining, TimeUnit.NANOSECONDS);
}
```

入口用 `System.nanoTime() + budgetNanos` 算出 `deadline`。每次等待之前，`awaitResult` 用它减去当前时间，得到剩余预算 `remaining`。预算已经用完就立即抛出 `TimeoutException`，否则把剩余时间交给 `future.get()`。这样每一层的等待消耗的都是同一份预算。

这里用 `nanoTime()` 而不是系统时间，是因为它专门用来测量时间间隔，不受修改系统日期或时间校准的影响。`nanoTime()` 的读数只有相减才有意义，而且相加时可能溢出：`TimeUnit` 把超大时长换算成纳秒会封顶为 `Long.MAX_VALUE`，再加上当前读数，`deadline` 就变成负数。所以判断是否超时要像示例这样看差值 `deadline - System.nanoTime()`，差值不受溢出影响；直接比较 `System.nanoTime() > deadline`，溢出后会把还没用完的预算误判为已经过期。

## 3. 中断与可中断等待 {#中断与可中断等待}

**中断**是一种协作式的停止信号：它只是在目标线程上设置一个标志，线程要不要停、什么时候停，由任务自己决定。`sleep`、`wait`、`join` 这类阻塞方法收到中断会提前结束等待，并抛出 `InterruptedException`。

任务捕获到 `InterruptedException` 后有两个选择：继续往外抛给调用方；或者在需要返回业务结果的任务边界上，恢复中断标志，再结束当前任务：

```java
catch (InterruptedException exception) {
    Thread.currentThread().interrupt();
    return Result.cancelled();
}
```

抛出 `InterruptedException` 时，线程的中断标志已经被清掉了，所以这里先调用 `interrupt()` 把标志设回去，再返回取消结果。这样上层代码仍然能看到有人请求过中断，当前任务也及时退出了。如果恢复标志之后还继续长时间执行业务，就会拖慢线程池关闭或请求取消。各个阻塞 API 对中断的具体响应见 [Java 线程](./thread-lifecycle-interruption.mdx#协作式中断)。

## 4. FutureTask 的中断取消 {#futurecanceltrue-的效果}

`FutureTask.cancel(true)` 同时作用于结果状态和执行线程。取消成功后，Future 的结果被标为取消；如果计算还没开始，它就不会再执行；如果正在运行，执行它的线程会收到中断请求。

但中断只是请求。任务忽略了中断，或者正阻塞在不响应中断的外部调用上，计算就会继续进行。所以数据库和网络客户端还要配置连接、读取和请求超时，保证这些调用迟早会返回。

取消也不会撤销已经发生的事。比如扣款请求已经发给支付服务，Future 被取消并不会让这笔扣款回滚。调用方需要用**幂等键**（标识这一次业务操作的唯一编号）去查询操作的实际状态，再决定重试还是补偿。

`CompletableFuture` 的取消行为不同，它不会中断执行线程，只是以取消异常完成，见 [CompletableFuture](./future-completablefuture-errors.mdx#超时与取消的作用范围)。

### 4.1 非中断取消与任务状态 {#非中断取消与任务状态}

`FutureTask.cancel(false)` 只取消结果，不打扰正在执行的计算，这里的 `false` 表示这次取消不请求中断。

计算还没开始时，成功取消会阻止它执行，这和 `cancel(true)` 一样。计算已经开始时，执行线程不会被中断，任务会按原逻辑跑完，但它最终返回的值不会成为 Future 的正常结果。只要取消先完成了状态转换，之后调用 `get()` 就会抛出 `CancellationException`。

还要注意 `isDone()`：正常完成、异常完成和取消，它都返回 `true`，所以它只说明 Future 已经结束，不说明底层计算已经停下。需要确认计算和资源清理都结束了，要由任务自己另外发出完成信号。

## 5. 资源清理 {#资源清理}

任务退出时，要释放已经取得的锁、许可和连接，而且正常完成、异常、中断和超时都要走同一条清理路径：

```java
Permit permit = pool.acquire();
try {
    return doWork();
} finally {
    permit.close();
}
```

`acquire()` 成功之后才进入 `try`，所以不管 `doWork()` 正常返回还是抛出异常，`finally` 都会释放许可。如果 `acquire()` 本身失败了，比如等待时被中断，代码不会进入 `try`，也就不会去归还一个根本没拿到的许可。

任务只拿到了部分资源时，也只释放已经拿到的那部分。每个资源都要明确由谁负责清理，否则不是漏还，就是重复归还。

有些操作必须完成一组更新，业务状态才是一致的，比如扣库存和写订单。这时可以先记下取消请求，等这组更新做完再退出。取消协议还应约定最迟多久响应，让调用方知道还要等多长时间。

## 6. 完成与取消的竞争 {#完成与取消的竞争}

任务恰好完成的时候，调用方也可能正在调用 `cancel()`。两者都想改变 Future 的状态，谁先完成状态转换，Future 最终就保存谁的结果：正常结果，或者取消状态。所以调用方要检查 `cancel()` 的返回值和 Future 的最终状态，再决定后续处理，不能假设调用了 `cancel()` 就一定取消成功。

竞争还会导致同一个任务被通知两次，比如完成回调和取消处理都触发了，所以回调、指标和业务状态更新要去重。结果状态和外部副作用也要分开确认：Future 显示已取消，扣款请求仍可能已经提交，这时应通过幂等键查询扣款结果，再决定是否重试。

## 7. 常见问题 {#常见问题}

### 7.1 get 超时后，任务会自动停止吗？ {#等待超时与任务退出}

不会。`get` 超时只是向等待者抛出 `TimeoutException`，调用方不再等了，后台任务仍然可以继续运行。需要停止任务时，要显式调用取消，并确认任务会响应中断或客户端超时。

### 7.2 为什么要单独处理 InterruptedException？ {#中断异常的传播}

因为它传递的是线程的取消信号。把它和普通异常一起捕获后吞掉，上层就再也不知道有人请求过取消。比如线程池已经在关闭，任务却还在继续执行业务。正确的做法是继续抛出，或者恢复中断标志后结束当前任务。

## 8. 面试题 {#面试题}

### 8.1 怎样设计一个支持超时和取消的并发任务 {#timeout-cancellable-task}

**考察重点**

- 能说明每一步怎样计算剩余预算，避免各层超时累加。
- 能解释中断怎样传递，以及 Future 取消后任务为什么仍会运行。
- 能说明退出时怎样释放资源，以及如何确认外部操作的结果。

**相关内容**：[截止时间与剩余预算](#截止时间与剩余预算)至[完成与取消的竞争](#完成与取消的竞争)。

<details>
<summary>参考回答</summary>

**任务共用一个截止时间，通过中断响应取消，并在所有退出路径上释放资源。**

入口先算出截止时间，每次阻塞前再计算剩余预算，避免各层超时累加。计算循环定期检查中断标志，阻塞等待则使用可中断、带超时的 API。

超时后，调用方用 `FutureTask.cancel(true)` 发出取消请求，任务在能保持业务一致的位置退出。捕获 `InterruptedException` 后，要么继续抛出，要么恢复中断标志再结束任务。

资源通过 `finally` 或自动关闭机制释放，底层客户端另外配置连接、读取和请求超时，因为中断不一定能打断它们。需要确认清理已经结束时，由任务发送独立的完成信号。对于已经发出的外部请求，取消不会撤销它，还要用幂等键查询结果，必要时补偿。

</details>

### 8.2 运行中的 FutureTask 执行 cancel(false) 会发生什么？ {#cancel-false-running}

之后调用 `get()` 会抛出 `CancellationException`，任务返回的值被丢弃。`isDone()` 为 `true` 也只说明 Future 已经结束，不说明计算已经停下。要确认计算和资源清理都已完成，需要任务另外发送完成信号。
