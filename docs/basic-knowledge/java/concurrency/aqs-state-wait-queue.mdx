# AQS

`AbstractQueuedSynchronizer`（AQS）是 JUC 里实现阻塞锁和同步器的基础框架，`ReentrantLock`、`CountDownLatch`、`Semaphore` 都建立在它上面。它把同步器拆成两半：子类只回答「这次能不能拿到资源」，AQS 负责回答「拿不到怎么办」，也就是排队、阻塞、唤醒和取消。

理解 AQS，关键是分清这两半各管什么。抓住一个整数 `state`、一条等待队列和 `park/unpark` 的许可，就能推出锁、闭锁和信号量的获取与释放流程，也能解释为什么被唤醒不等于拿到了锁。下文以 Java 17 和 21 为准。

## 1. 面试核心 {#core}

- AQS 用一个 **`int state` 表示同步状态**，它代表重入次数、剩余计数还是可用许可，由子类决定。
- 子类尝试获取失败后，**由 AQS 负责排队、阻塞和取消**，资源释放后再唤醒有效后继；被唤醒的线程要**重新尝试获取**。[卡](#aqs-wait-queue)
- `tryAcquireShared` **返回负数表示失败，零表示本次成功但后续无法成功，正数表示后续仍有成功机会**。[卡](#shared-acquire-result)
- `LockSupport` 为每个线程维护**至多一个许可**：`unpark` 提供许可，`park` 消耗许可或等待，所以先 `unpark` 再 `park` 不会丢失唤醒。[卡](#park-unpark-permit)
- `Condition` 的等待者先进入**条件队列**，被 `signal` 后转入同步队列，**重新取得锁后**才从 `await` 返回。

## 2. 同步状态 `state` {#同步状态-state}

**同步状态**是 AQS 里的一个 `int state` 字段，记录资源当前是否可用、还剩多少。子类通过下面三个方法读写它：

```java
getState();
setState(next);
compareAndSetState(expected, next);
```

`getState()` 和 `setState()` 具有 volatile 读写的可见性和顺序语义，一个线程写入的状态，其他线程随后读取时能看到。`compareAndSetState()` 是一次原子的比较并更新：只有当前值仍等于 `expected` 时才写入 `next`。没有它的话，两个线程可能都读到「还剩 1 个许可」，再各自写回 0，结果两个线程都以为自己拿到了。

同一个整数在不同同步器里含义不同：

- `ReentrantLock` 用它记录持有次数。0 表示没人持有，同一线程再次获取时加一，释放到 0 才算真正释放。
- `CountDownLatch` 用它记录剩余计数，归零后等待线程才能继续。
- `Semaphore` 用它记录可用许可，线程取得许可后才能使用受限资源。

子类通过 `tryAcquire`、`tryRelease`（共享模式是 `tryAcquireShared`、`tryReleaseShared`）定义状态怎样转换。AQS 的模板方法，比如 `acquire`，决定整体流程：先调用子类的 `tryAcquire`，失败了再安排线程排队。子类不用关心排队，AQS 也不用关心 `state` 代表什么。

## 3. park 与 unpark 的许可 {#park-与-unpark-的许可}

AQS 让等待线程暂停、再把它叫醒，用的是 `LockSupport.park` 和 `LockSupport.unpark`。讲队列之前，先把这两个方法弄清楚。

`LockSupport` 为每个线程维护**至多一个许可**。`unpark(thread)` 给目标线程一个许可，它已经有许可时，仍然只保留一个，不会累加。线程调用 `park` 时，如果有许可，就消耗掉并立即返回；没有许可，就进入等待。

许可的好处是唤醒可以先于等待发生。释放方可能在等待线程真正调用 `park` 之前就调用了 `unpark`，这时许可被留下来，等待线程随后调用 `park` 会直接返回，不会一直睡下去。前提是目标线程已经启动，并且这个许可还没被别的 `park` 消耗掉。

`park` 还可能因为中断或**虚假唤醒**返回。虚假唤醒是指没有对应的 `unpark`，等待也自行结束。`park` 返回时不会清除中断标志，也不告诉你是因为什么返回的，所以等待代码要放在循环里：每次返回都重新检查条件，确认资源可用了再继续。

## 4. FIFO 等待队列 {#fifo-等待队列}

资源暂时不可用时，AQS 把等待线程放进一条 FIFO 队列，也就是先进入的节点排在前面。以独占获取为例，流程如下：

1. 调用子类的 `tryAcquire` 尝试获取。成功就直接返回，不进入队列。
2. 获取失败，线程被包装成节点加入等待队列。
3. 节点排到合适的位置后再次尝试获取；暂时还拿不到，就通过 `LockSupport.park` 暂停。
4. 释放方调用 `tryRelease` 更新状态，满足唤醒条件时用 `unpark` 唤醒**有效后继**，也就是排在后面、还没取消的等待者。
5. 后继恢复执行，回到第 3 步重新尝试获取。

注意第 1 步：线程在入队之前就会先试一次。所以队列虽然是 FIFO，刚来的线程仍可能在排队者被唤醒的间隙抢先拿到资源，这就是非公平获取。公平与否取决于子类的 `tryAcquire`：公平实现会先调用 `hasQueuedPredecessors()` 检查是否已有线程排在前面，有的话就不抢。

第 5 步也要注意：被唤醒只是得到了再试一次的机会，真正拿到资源，要等 `tryAcquire` 成功返回。

## 5. 独占模式与共享模式 {#独占模式与共享模式}

**独占模式**一次只允许一个持有者，比如互斥锁；**共享模式**允许多个线程在条件满足时同时获取成功，比如闭锁和信号量。两种模式的等待者排在同一条同步队列里。

共享模式多了一步**共享传播**：一个节点共享获取成功后，AQS 会继续唤醒后继，让它也检查能不能获取。`CountDownLatch` 计数归零后，正是靠传播让所有等待者依次醒来继续执行。`Semaphore(3)` 一开始有三个许可，每个线程占一个，最多三个线程同时使用资源；传播到后继时，它能否成功仍取决于剩下的许可够不够。

### 5.1 共享获取的返回值 {#共享获取的返回值}

传播要靠 `tryAcquireShared(arg)` 的返回值判断：它既要告诉 AQS 本次是否成功，还要说明后面的线程有没有机会。返回值分三个区间：

| 返回值 | 含义 |
| --- | --- |
| 负数 | 本次获取失败 |
| 零 | 本次成功，后续共享获取无法成功 |
| 正数 | 本次成功，后续共享获取仍有成功机会 |

返回零时，AQS 不必再去唤醒后继；返回正数时，才值得继续传播。正数只表示「还有机会」，具体数值不必等于剩余许可数。后继真正执行时，其他线程也在竞争，所以它仍要重新检查状态。释放一侧，`tryReleaseShared` 返回 `true` 表示这次释放可能让等待者获取成功，AQS 据此唤醒后续等待者。

## 6. 中断、超时与取消 {#中断超时与取消}

等待资源时，调用方还要决定两件事：收到中断要不要退出，最多愿意等多久。AQS 为此提供三类获取方法：

- `acquire` 不响应中断，收到中断也继续等待。获取成功返回时，它会保留或恢复中断标志，让调用方之后还能发现中断。
- `acquireInterruptibly` 响应中断，退出等待并抛出 `InterruptedException`。
- `tryAcquireNanos` 同时支持中断和超时，超时仍未取得资源时返回 `false`。

等待者因中断或超时放弃后，它的节点就成了**取消节点**。取消节点还留在队列里，释放方唤醒后继时要跳过它们，找到仍在等待的有效后继；否则唤醒信号会落在一个已经离开的线程上，真正排队的线程反而一直睡着。

排队和取消都在并发发生，所以 `getQueueLength()` 只返回等待线程数的估计值。用它做监控时，看多次采样的趋势来判断积压，不要依赖单次读数。

## 7. Condition 条件队列 {#condition-条件队列}

等锁和等业务条件是两种不同的等待。比如消费者已经拿到锁，却发现队列是空的，它要等的是生产者放入元素，而不是等锁。AQS 的 `ConditionObject` 用一条独立的**条件队列**保存这类等待者，过程如下：

1. 线程调用 `await` 后，节点进入条件队列，并完全释放已持有的同步状态。重入了三次的锁，会一次释放干净，否则生产者永远拿不到锁。
2. 另一个线程持有同一把锁时调用 `signal`，把等待节点从条件队列转入同步队列。
3. 等待线程在同步队列里重新取得同步状态，并恢复原来的持有次数，才从 `await` 返回。

所以 `signal` 只是通知，被通知的线程仍要和其他线程一起重新竞争锁。为了支持这套流程，子类要能判断当前线程是否独占持有（`isHeldExclusively`），也要能完全释放再恢复原有的持有状态。

一把 `ReentrantLock` 可以创建多个 `Condition`，比如分别等待「非空」和「未满」，这样生产者只唤醒消费者，减少无关唤醒。具体用法见 [ReentrantLock](./reentrantlock-fairness-condition.mdx#condition-等待)。

## 8. AQS 的适用范围 {#aqs-的适用范围}

AQS 适合这样的组件：同步状态能用一个 `int` 表达，获取失败后需要排队阻塞。子类可以维护锁的所有者这类辅助字段，但 AQS 跟踪的同步状态始终是这个整数。子类实现的 `tryAcquire`、`tryRelease` 这些方法要短小、线程安全，并且不能阻塞，因为 AQS 会在排队流程中反复调用它们。

业务代码一般直接使用 JUC（`java.util.concurrent` 包）现成的组件：互斥用 `ReentrantLock`，限制并发数用 `Semaphore`，等待计数归零用 `CountDownLatch`。

确实要自己扩展 AQS 时，需要验证这些边界：

- 状态转换是否始终满足资源的使用规则。
- 获取和释放是否正确检查所有权，比如非持有者不能释放锁。
- 中断、超时与取消是否让等待者正确退出。
- 序列化后能否恢复可用状态。AQS 自身只序列化同步状态，反序列化后的等待队列为空。

## 9. 常见问题 {#常见问题}

### 9.1 AQS 与 CLH 队列是什么关系？ {#aqs-与-clh-队列}

AQS 的等待队列借鉴了 CLH 队列锁组织等待者的方式。经典 CLH 是自旋锁，每个等待者反复读取前驱节点的状态，判断自己能不能继续。AQS 保留了「按前驱排队」的思路，但把自旋换成了 `park/unpark` 阻塞等待，还加上了取消、独占和共享传播。所以回答 AQS 原理时，只说「CLH 变体」不够，还要讲清这些等待协议。

### 9.2 被 unpark 唤醒就等于拿到锁了吗？ {#唤醒与锁获取}

不等于。`unpark` 只是让等待线程获得继续执行的机会。线程恢复后要重新调用子类的获取方法，因为这时资源可能已经被新来的线程抢走了。只有获取方法成功返回，它才真正取得资源；失败的话，会再次 `park`。

## 10. 面试题 {#面试题}

### 10.1 AQS 如何组织获取失败的线程 {#aqs-wait-queue}

**考察重点**

- 说明子类怎样定义 `state`，以及获取和释放的条件。
- 解释获取失败的线程怎样排队、暂停，并在唤醒后重试。
- 区分独占与共享获取，并说明取消节点为何需要被跳过。

**相关内容**：[同步状态 `state`](#同步状态-state)至[中断、超时与取消](#中断超时与取消)。

<details>
<summary>参考回答</summary>

**AQS 把获取失败的线程加入 FIFO 等待队列，并负责重试、阻塞和唤醒。**

子类先通过 `tryAcquire` 等方法尝试获取资源，失败后线程进入队列。排到合适位置时再试一次，仍然拿不到就通过 `park` 等待。释放方更新状态并唤醒有效后继，后继恢复后再次竞争资源，成功了才算获取。

子类定义 `state` 的含义和转换条件，AQS 管理独占与共享两种等待；共享获取成功后还会把唤醒传播给后继。可中断和超时获取让等待者能够退出，队列随后跳过这些取消节点，保证唤醒落到仍在等待的线程上。公平策略由子类实现，比如先检查是否有前驱在排队，因为新线程在入队前也会尝试获取。

</details>

### 10.2 `tryAcquireShared` 的三个返回区间分别表示什么？ {#shared-acquire-result}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：区分本次获取成功与后继仍可获取，并解释后继为何需要重新检查状态。

**相关内容**：[共享获取的返回值](#共享获取的返回值)。

<details>
<summary>参考回答</summary>

**负数表示本次失败，零表示本次成功但后续无法成功，正数表示本次成功且后续仍有成功机会。**

AQS 根据这个区间决定是否继续唤醒后继：返回零就不必传播，返回正数才值得让后继再试。正数只说明还有获取机会，数值不必等于剩余许可数。后继执行时，资源还会被其他线程竞争，所以它必须重新检查状态。

</details>

### 10.3 先调用 unpark 再调用 park 会丢失唤醒吗？ {#park-unpark-permit}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释许可为何最多积累一个，以及中断和虚假唤醒为何要求循环检查条件。

**相关内容**：[park 与 unpark 的许可](#park-与-unpark-的许可)。

<details>
<summary>参考回答</summary>

**不会。目标线程已启动且许可未被消耗时，先调用 `unpark` 会把许可留下来。**

下一次 `park` 消耗这个许可后直接返回，所以唤醒可以先于等待发生。

许可最多只有一个，连续两次 `unpark` 也只能让一次 `park` 直接返回。另外，`park` 会因中断或虚假唤醒返回，而且不说明返回原因，所以返回后仍要在循环里检查资源条件。

</details>
