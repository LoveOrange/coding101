# Java 线程

Java 线程是程序中独立执行任务的单元，一个 `Thread` 对象从创建到结束会经过一组明确的状态。排查线程卡住、编写可以取消的任务，都要用到两类知识：线程处在什么状态、为什么停在那里；以及怎样让一个正在运行的线程停下来。后者的答案是**中断**，但中断只是一个协作请求，线程何时退出，取决于它正在执行的代码和调用的 API。

## 1. 面试核心 {#core}

- `start()` **启动新线程**，直接调用平台线程的 `run()` 则**在当前线程里执行任务**。
- 线程状态有六种：`NEW`、`RUNNABLE`、`BLOCKED`、`WAITING`、`TIMED_WAITING` 和 `TERMINATED`，它们是 **JVM 层面的状态，与操作系统线程状态不一一对应**。
- `isInterrupted()` 只查询标志，`Thread.interrupted()` **读取并清除当前线程的中断标志**。[卡](#interrupt-status-methods)
- `sleep`、`wait`、`join` 和 JUC 的可中断阻塞方法响应中断时，**会清除标志并抛出 `InterruptedException`**，捕获后要继续抛出或恢复标志。
- 任务**通过检查中断或调用可中断 API 协作退出**，并在退出前释放资源。[卡](#stop-thread)

## 2. `start()` 与 `run()` {#start-与-run}

创建 `Thread` 对象只是把任务准备好，调用 `start()` 才会真正启动一个新线程。下面的代码启动工作线程，然后等它执行结束：

```java
Thread worker = new Thread(() -> loadData());
worker.start();
worker.join();
```

这里创建的是**平台线程**，也就是由一个操作系统线程承载执行的线程。对象刚创建时处于 `NEW` 状态。调用 `start()` 后，新线程交给调度器，调用者和它并发运行；随后调用者执行 `join()`，等工作线程结束再继续。

如果把 `start()` 换成 `worker.run()`，`loadData()` 会在当前线程里执行。这只是一次普通的方法调用，没有新线程，执行完当前线程才走到下一行。

一个 `Thread` 只能启动一次，再次调用 `start()` 会抛出 `IllegalThreadStateException`。`run()` 正常返回，或者抛出的未捕获异常处理完之后，线程进入 `TERMINATED`。之后还要执行任务，就创建新线程或者交给线程池。

Java 21 还提供了由 JVM 调度的虚拟线程，它同样要通过启动才会执行；直接调用虚拟线程对象的 `run()` 什么也不做。虚拟线程的调度方式见 [虚拟线程](./virtual-threads-boundaries.mdx)。

## 3. 线程的六种状态 {#线程的六种状态}

`Thread.State` 枚举描述线程在 JVM 中的状态。看懂它，就能判断线程是在等锁、在等某个条件，还是已经结束：

| 状态 | 含义 |
| --- | --- |
| `NEW` | 尚未启动 |
| `RUNNABLE` | 可运行或正在执行，也包含部分系统资源等待 |
| `BLOCKED` | 等待进入或重新进入 monitor |
| `WAITING` | 无期限等待，如 `wait()`、`join()`、`park()` |
| `TIMED_WAITING` | 有期限等待，如 `sleep()` 或定时等待 |
| `TERMINATED` | 执行已结束 |

`BLOCKED` 专指等 `synchronized` 的 monitor：进入同步区域时等锁，或者从 `wait()` 醒来后重新拿锁。等 `ReentrantLock` 的线程底层用的是 `park()`，显示为 `WAITING` 或 `TIMED_WAITING`。

这些状态属于 JVM 层，和操作系统的线程状态并不一一对应。最容易误判的是 `RUNNABLE`：它既可能是正在 CPU 上运行，也可能是在等调度，还可能是阻塞在 native I/O（通过本地系统调用进行的输入输出，比如读 socket）上。所以看到一堆 `RUNNABLE` 线程，不能直接断定它们在消耗 CPU。

诊断时要把**三类信息**放在一起看：

- 线程栈：线程正在执行或等待的是哪个方法。
- 相关队列：任务有没有积压，线程是没活干还是在等别的东西。
- CPU 使用情况：区分是计算繁忙，还是在等系统资源。

## 4. 协作式中断 {#协作式中断}

`interrupt()` 向目标线程发出中断请求，最基本的效果是设置它的**中断标志**，至于怎样结束工作，由任务自己决定。之所以采用协作的方式，是因为外部不知道线程执行到了哪一步，强行停下可能留下改到一半的状态（第 6 节的 `Thread.stop()` 就是反例）。

普通计算代码不会被中断打断，要主动检查标志，才能在合适的位置退出：

```java
while (!Thread.currentThread().isInterrupted()) {
    processNextBatch();
}
```

循环在每批工作开始前检查标志。如果中断在某一批执行中途到达，这一批会先做完，到下一次检查时才退出。所以批次越长，任务响应取消越慢。

检查标志有两个方法，区别在于查谁、清不清除。实例方法 `isInterrupted()` 查询目标线程的标志，不改变它，适合上面这种循环检查。静态方法 `Thread.interrupted()` 查询的是当前线程，并且会清除标志，适合「读到中断、并且由我来处理它」的代码；只想查询时用它，会把中断信号吞掉。第 7 节用一个例子演示两者的差别。

线程阻塞在某个 API 里时，被中断后是返回、抛异常还是继续等，由这个 API 决定。下一节说明常见的可中断阻塞方法。

## 5. InterruptedException 的传播 {#处理-interruptedexception}

`sleep`、`wait`、`join` 以及 `BlockingQueue.take()` 这类方法，阻塞时被中断会抛出 `InterruptedException`。抛出之前，它们会先清除中断标志。也就是说，这时异常是中断请求的唯一载体，捕获它的代码有责任把请求继续传下去。

当前方法可以声明受检异常时，最简单的做法是直接向上抛：

```java
public Result load() throws InterruptedException {
    return queue.take(); // 继续向上抛出
}
```

调用方通过异常知道等待被中断了，可以接着做取消处理。如果当前方法实现的接口不允许声明 `InterruptedException`，就先恢复标志，再转换成业务异常：

```java
try {
    return queue.take();
} catch (InterruptedException exception) {
    Thread.currentThread().interrupt();
    throw new TaskCancelledException(exception);
}
```

这里假设业务定义了 `TaskCancelledException`。调用 `Thread.currentThread().interrupt()` 把标志设回去之后，上层既能捕获业务异常，也能通过线程的中断状态发现取消请求。如果捕获后只打一行日志就继续执行，异常被吞掉，标志也已经清除，上层发出的关闭或取消请求就彻底丢了。

## 6. 安全终止线程 {#安全终止线程}

安全终止是指让任务在状态一致的位置退出，并释放已经取得的资源。任务可以检查中断标志，也可以检查自定义的停止标志；后者要用 `volatile` 或锁保护，修改才对工作线程可见。只设置停止标志叫不醒已经阻塞的调用，阻塞中的线程还要靠中断、关闭资源或超时来结束等待。

清理工作放在 `finally` 或 try-with-resources 里完成，比如解锁、归还连接、关闭资源。调用方按以下顺序进行**协作关闭**：

1. 停止接收新任务，避免关闭期间还在增加工作。
2. 发出中断请求，或者设置受同步保护的停止标志。
3. 在一个期限内等已有任务退出，超时后再处理仍未完成的任务。

关闭流程和资源清理的完整说明见 [任务取消](./interruption-timeout-cancellation.mdx)。

为什么不直接用 `Thread.stop()`？Java 17 中，它会强制终止线程，并释放线程持有的所有 monitor。如果线程刚改完一组相关字段中的一部分，其他线程拿到锁后就会读到不一致的状态，所以这个方法早已弃用。Java 21 中，调用它总是抛出 `UnsupportedOperationException`。

线程池的关闭同样遵循协作原则。`ExecutorService.shutdown()` 开始有序关闭，不再接收新任务；超时后可以按业务需要调用 `shutdownNow()`，它会尝试中断正在运行的任务，并返回还没开始的任务。运行中的任务能不能真正停下，仍然取决于任务是否响应中断。排队任务的处理见 [Java 线程池](./threadpoolexecutor-execution-path.mdx#线程池关闭与终止)。

## 7. 中断状态的读取与清除 {#中断状态的读取与清除}

区分两个查询方法，要同时看查的是哪个线程、会不会清除标志。下面先中断当前线程，再连续读取三次：

```java
Thread.currentThread().interrupt();
System.out.println(Thread.currentThread().isInterrupted());
System.out.println(Thread.interrupted());
System.out.println(Thread.interrupted());
```

没有其他中断的话，输出依次是 `true`、`true`、`false`。第一次 `isInterrupted()` 读到标志，但保留它，所以第二次 `Thread.interrupted()` 仍然返回 `true`；这次静态调用同时清除了标志，第三次读取就返回 `false`。

## 8. park 与中断返回 {#park-与中断返回}

`LockSupport.park()` 用来暂停当前线程，它响应中断的方式和 `sleep` 不同：检测到中断时直接返回，不抛异常，也不清除中断标志。另外，`park()` 也可能在没人唤醒的情况下返回，所以调用者总要在循环里重新检查等待条件和中断状态。

问题出在循环忽略中断的时候。标志一直保持着，下一次 `park()` 又会立即返回，循环就一圈一圈地跑，看起来在等待，实际上在空转消耗 CPU。`sleep` 则相反：它抛出异常并清除标志，调用方在异常路径上处理取消。

`park` 的许可，以及先 `unpark` 后 `park` 的行为，见 [AQS](./aqs-state-wait-queue.mdx#park-与-unpark-的许可)。

## 9. 常见问题 {#常见问题}

### 9.1 sleep 和 wait 都会释放锁吗？ {#sleep-与-wait}

不是。`sleep` 不释放当前线程持有的任何 monitor，`wait` 会释放目标对象的 monitor。两者用途也不同：`sleep` 是 `Thread` 提供的定时暂停，`wait` 是对象上的条件等待。调用 `wait` 前必须持有目标 monitor，返回前还要重新获取它。

条件等待的完整机制见 [synchronized](./synchronized-monitor-optimizations.mdx#monitor-的等待与通知)。

### 9.2 中断一定能结束网络 I/O 吗？ {#网络-i/o-的中断边界}

不一定，取决于具体 API。线程阻塞在 `InterruptibleChannel`（NIO 的可中断通道）的 I/O 操作上时，中断会关闭这个通道，阻塞的调用随后抛出 `ClosedByInterruptException`，中断标志保持设置状态。

传统 Socket、各种客户端库和本地调用各有自己的行为，要按对应 API 配置关闭方式和超时。给外部调用设置超时，才能保证对方长期没有响应时，线程最终能结束等待。

## 10. 面试题 {#面试题}

### 10.1 Java 中怎样正确停止一个线程 {#stop-thread}

**考察重点**

- 说明任务为什么需要主动响应中断请求。
- 区分计算循环和阻塞 API 响应中断的方式。
- 解释退出前怎样清理资源，以及调用方怎样限制等待时间。

**相关内容**：[协作式中断](#协作式中断)至[安全终止线程](#安全终止线程)。

<details>
<summary>参考回答</summary>

**调用方通过 `interrupt()` 发出请求，任务响应后在状态一致的位置协作退出。**

计算循环用 `isInterrupted()` 检查，阻塞等待则选择可中断 API。捕获 `InterruptedException` 后继续抛出，或恢复中断标志并退出当前任务。

任务在 `finally` 或资源作用域中完成清理，调用方在期限内等待结束。线程池先调用 `shutdown()`，等待超时后再按业务需要调用 `shutdownNow()`。中断只发出请求，任务仍需执行取消逻辑。不能用 `Thread.stop()` 强行终止，它会留下改到一半的状态，Java 21 中调用它直接抛出异常。

已经发生的外部操作需要查询结果，重试时用幂等规则避免重复执行，必要时进行补偿。

</details>

### 10.2 isInterrupted 和 Thread.interrupted 有什么区别？ {#interrupt-status-methods}

**考察重点**：说明两个方法分别查询哪个线程，以及连续查询时清除标志会怎样影响结果。

**相关内容**：[中断状态的读取与清除](#中断状态的读取与清除)。

<details>
<summary>参考回答</summary>

**`isInterrupted()` 查询目标线程并保留标志，`Thread.interrupted()` 查询当前线程并清除标志。**

如果当前线程已被中断，而且之后没有新的中断请求，连续两次静态查询会依次得到 `true` 和 `false`，因为第一次调用已经把标志清除了。

</details>

### 10.3 线程中断后，为什么 park 循环会持续空转？ {#park-interrupt-spin}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释保留中断标志为什么会让后续 `park()` 立即返回，以及循环应如何处理取消。

**相关内容**：[park 与中断返回](#park-与中断返回)。

<details>
<summary>参考回答</summary>

**`park()` 响应中断后保留标志，循环如果忽略它，后续调用就会一直立即返回。**

循环因此不停执行、消耗 CPU，却没有真正等待。循环每轮都要检查中断：按取消协议退出，或者由明确的协议处理这个中断后，再决定是否继续等待。

</details>
