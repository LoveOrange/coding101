# 锁与无锁

锁与无锁算法都用于协调共享状态。本文比较进度保证、竞争成本与选择条件。CAS 原语和 ABA 见 [CAS](./cas-aba-versioning.mdx)。

## 1. 面试核心 {#core}

- 锁通过互斥保护临界区，等待者依赖持有者释放。
- CAS 失败会增加重新读取、计算和缓存竞争成本。[卡](#lock-free-under-contention)
- lock-free 保证整体进展，wait-free 保证单次操作步数有界。[卡](#progress-guarantees)
- 分片和批处理可降低共享状态的竞争频率。
- 伪共享来自不同变量占用同一缓存行。[卡](#false-sharing-cost)

## 2. 锁的竞争成本 {#锁的竞争成本}

```java
lock.lock();
try {
    updateState();
} finally {
    lock.unlock();
}
```

示例把一次状态变更放在锁内。`finally` 确保正常与异常路径都释放锁。

低竞争时，锁可沿快速路径获取。持续竞争时，等待者会自旋或挂起。相关成本包括原子操作、缓存迁移和线程调度。

锁能覆盖多个字段和多步状态变化。它还能配合条件队列等待资源就绪。

## 3. 无锁更新的重试成本 {#无锁更新的重试成本}

```java
while (true) {
    State current = state.get();
    State next = current.advance();
    if (state.compareAndSet(current, next)) {
        return;
    }
}
```

本例要求 `State` 不可变，`advance()` 无副作用。CAS 失败后，计算出的 `next` 被丢弃。线程重新读取状态并计算。

竞争越密集，失败计算和缓存竞争越多。`advance()` 昂贵时，重复计算会消耗大量 CPU。ABA 与更新函数约束见 [CAS](./cas-aba-versioning.mdx)。

## 4. 两类方案的常见错误 {#两类方案的常见错误}

| 方案 | 需要处理的风险 |
| --- | --- |
| 锁 | 锁顺序、持锁 I/O、忘记释放、等待超时 |
| 无锁算法 | 失败重试、局部饥饿、ABA、重复副作用 |

维护成本也影响选择。业务多字段更新适合短临界区。自行实现无锁结构，还需证明所有允许的交错。

## 5. 降低竞争的方法 {#降低竞争的方法}

减少共享可降低同步频率：

- 将统计分片，再定期聚合。
- 按 key 分配状态所有权。
- 批量提交，减少同步次数。
- 发布不可变快照供读者使用。
- 使用成熟并发容器管理单项操作。

方案还需满足业务一致性。例如，分片统计要接受聚合时刻的读取边界。

## 6. 竞争曲线基准 {#竞争曲线基准}

线程数至少覆盖单线程、核心数和超额订阅。数据应包含均匀 key 与热点 key。还要改变临界区长度和读写比例。

记录成功吞吐、p99、CPU 和分配率。再结合 CAS 失败数、锁等待与切换解释曲线。具体采集方法见 [锁竞争](./lock-contention-context-switch-benchmark.mdx)。

## 7. 无锁算法的进度保证 {#无锁算法的进度保证}

进度保证描述线程持续获得执行机会时的完成性质：

| 性质 | 保证范围 |
| --- | --- |
| obstruction-free | 一个操作独自执行足够久时可以完成 |
| lock-free | 并发执行中，系统整体持续有操作完成 |
| wait-free | 每个操作在自身有界步数内完成 |

lock-free 允许某个线程反复失败而饥饿。wait-free 还约束每个操作的完成步数。这些性质均有算法与调度前提。

单次 CAS 是原子操作。完整循环里若等待锁或执行无界工作，进度性质也会改变。

## 8. 伪共享与缓存行竞争 {#伪共享与缓存行竞争}

若变量位于同一缓存行，独立写入也会相互干扰。缓存一致性按缓存行协调写入。这种无业务共享的缓存竞争称为伪共享。

OpenJDK 21 的 `Striped64.Cell` 使用 `@Contended` 填充。填充把热点单元分隔，降低相互干扰。代价是增加对象占用。

JMH 的 FalseSharing 示例比较相邻字段与填充方案。实际收益需在目标处理器和对象布局下测量。

## 9. 常见问题 {#常见问题}

### 9.1 自旋等待的使用条件 {#自旋等待的使用条件}

自旋适合预计很短且 CPU 容量充足的等待。持有者被调度出去时，自旋线程会空耗 CPU。业务同步优先使用 JVM 或 JUC 的既有机制。

### 9.2 公平性与吞吐 {#公平性与吞吐}

公平获取减少插队，增加队列顺序约束。需要控制等待分布时，应同时测量吞吐代价。获取策略见 [ReentrantLock](./reentrantlock-fairness-condition.mdx#公平锁与非公平锁)。

### 10.1 为什么无锁方案在高竞争下可能比锁更慢 {#lock-free-under-contention}

- 阿里巴巴：https://www.nowcoder.com/discuss/461925
- 美团：https://www.nowcoder.com/discuss/383727207275933696

**出现公司**：阿里巴巴、美团

**考察重点**

- 理解 CAS 失败重试与缓存行迁移。
- 理解阻塞成本和临界区长度。
- 理解竞争曲线与方案选择的关系。

**相关内容**：[锁的竞争成本](#锁的竞争成本)至[竞争曲线基准](#竞争曲线基准)。

<details>
<summary>参考回答</summary>

高竞争会使无锁更新反复重算，并争夺缓存行。失败越多，有效业务计算占比越低。锁能让等待者挂起，减少持续空转。

两者的性能取决于临界区成本和线程数。应比较成功吞吐、p99、CPU 及分配率。最终选择还要考虑正确性与维护成本。

</details>
