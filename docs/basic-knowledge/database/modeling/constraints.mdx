# 数据约束

**数据约束**是写在表结构里的规则，限制数据库允许保存什么样的数据：哪些列不能为空，哪些值不能重复，数值要落在什么范围，引用的记录必须存在。违反约束的写入会被数据库直接拒绝。

约束的价值在于它守在最后一道门上。无论数据来自哪个服务、哪段脚本，还是有人手工执行的 SQL，都要经过它；应用里的校验只能管住走应用代码的那条路，而且在并发下还可能漏掉。理解约束要抓住三点：每种约束拦的是什么，NULL 怎样绕过检查，以及为什么应用里先查一下不能代替唯一约束。下文以 MySQL 8.0 InnoDB 为准。

## 1. 面试核心 {#core}

- 主键**唯一且非空**，普通唯一索引则**允许多个 NULL**。[卡](#check-null)
- 唯一约束**在写入时拒绝重复值**。应用先查询再插入，两步之间有并发窗口，所以**预查不能代替数据库约束**。[卡](#unique-constraint)
- MySQL 8.0.16 起才真正执行 CHECK，表达式结果为 **TRUE 或 UNKNOWN 时都算通过**，所以 CHECK 拦不住 NULL。[卡](#check-null)
- InnoDB **立即检查外键**引用关系，不能推迟到提交时，`NO ACTION` 和 `RESTRICT` 的效果相同。[卡](#foreign-key-actions)

## 2. 表级规则 {#在表结构中表达规则}

先看一张账户表，它要求邮箱非空且不重复，余额非空且不能为负：

```sql
CREATE TABLE accounts (
  id BIGINT PRIMARY KEY,
  email VARCHAR(200) NOT NULL UNIQUE,
  balance DECIMAL(12,2) NOT NULL,
  CHECK (balance >= 0)
) ENGINE=InnoDB;
```

三条规则各管一件事：插入重复的邮箱会违反 `UNIQUE`，邮箱为空会违反 `NOT NULL`，余额为负会违反 `CHECK`。这三种写入都会报错，数据不会进表。

`CHECK` 有版本差异。MySQL 8.0.16 起才真正执行 CHECK 约束；更早的版本能解析部分 CHECK 语法，但直接忽略，写进去的负余额照样能存。8.0.16 起还可以给约束加上 `NOT ENFORCED`，表示只声明不检查。本例没有写这个选项，所以会实际检查。

## 3. NULL 与 CHECK {#null-与-check}

NULL 表示「值未知」，它和任何值比较的结果都是 UNKNOWN，而不是 TRUE 或 FALSE。约束遇到 NULL 时的行为都从这一点推出来。

唯一索引判断重复时，两个 NULL 并不算相等，所以 MySQL 的唯一索引允许多个 NULL。联合唯一键也一样：只要某一列是 NULL，即使其他列完全相同，这样的组合也能重复插入。业务上要求「完整的值必须唯一」时，就要把每个组成列都声明为 `NOT NULL`。

CHECK 只拒绝表达式结果为 FALSE 的行。`balance` 为 NULL 时，`balance >= 0` 的结果是 UNKNOWN，不是 FALSE，所以只有 CHECK 的话，这一行可以写进去。真正拦住空余额的是 `NOT NULL`。

默认值也不能代替非空约束。`DEFAULT` 只在插入时省略这一列，或者显式写 `DEFAULT` 时才生效；如果语句明确写入 NULL，默认值不起作用，要靠 `NOT NULL` 拒绝。

## 4. 并发与引用完整性 {#并发与引用完整性}

应用注册前先查一下邮箱是否已存在，看起来就够了，但在并发下不够。两个请求可以同时查到「邮箱不存在」，然后各自插入。查询结束到插入之间，其他事务随时可能插入同一个邮箱，查询结果在插入时已经过期了。

唯一约束在实际写入时判断冲突，两个插入里只有一个能成功，另一个会收到重复键错误。应用要处理这个错误：返回「邮箱已被注册」这样的明确结果，或者在幂等场景下按幂等键读出已有记录。

外键同样只保证一件具体的事：子表引用的父记录存在。客户有没有资格下单、订单总额对不对，这些业务规则外键管不了。多条语句之间怎样一起提交或回滚，见[数据库事务](../transaction/index.mdx)。

## 5. 外键动作与检查时机 {#外键动作与检查时机}

外键可以为父记录的删除或键更新指定**引用动作**，也就是子表还在引用时怎么处理：

| 动作 | 子表存在引用时的行为 |
| --- | --- |
| `RESTRICT` / `NO ACTION` | InnoDB 立即拒绝父记录变更。 |
| `CASCADE` | 将删除或键更新传播到子表。 |
| `SET NULL` | 将子表外键列置空，要求这些列可空。 |

在标准 SQL 里，`NO ACTION` 可以推迟到语句结束再检查；InnoDB 不支持推迟检查，每一行写入时立即检查外键，所以两者效果相同。这也意味着顺序很重要：同一个事务里先插子行、后插父行，第一步就会失败，必须先插父行。外键列允许为空时，取 NULL 的子行不需要匹配任何父记录。

```sql
CREATE TABLE account_items (
  id BIGINT PRIMARY KEY,
  account_id BIGINT NOT NULL,
  FOREIGN KEY (account_id) REFERENCES accounts(id) ON DELETE RESTRICT
) ENGINE=InnoDB;
```

在这张明细表上，只要还有明细引用某个账户，删除这个账户就会被拒绝。外键对索引也有要求：子表的外键列要作为某个索引的前缀，并且顺序一致，子表没有这样的索引时 InnoDB 会自动创建；父表被引用的列通常是主键或唯一键。

## 6. 使用边界 {#使用边界}

文本的唯一性取决于列的排序规则（collation）。在忽略大小写的排序规则下，`Alice@example.com` 和 `alice@example.com` 会被视为相同，唯一约束会拒绝第二个。邮箱这类业务标识，要先想清楚大小写是否算同一个值，再选排序规则。

数据库约束和应用校验各有分工。约束保护所有写入入口，应用校验用来提前给用户友好的错误提示；即使应用已经校验过，也仍然要处理数据库返回的约束冲突。

### 7.2 CHECK(balance >= 0) 能拒绝 NULL 吗，唯一索引又如何处理 NULL？ {#check-null}

**考察重点**：三值逻辑、非空与唯一性。

<summary>参考回答</summary>

**不能。CHECK 只拒绝结果为 FALSE 的行，`balance` 为 NULL 时表达式结果是 UNKNOWN，这一行可以通过。**

要拒绝 NULL，需要另加 `NOT NULL`。唯一索引判断重复时两个 NULL 不算相等，所以 MySQL 唯一索引允许多个 NULL。要求业务值完整且唯一时，需要同时使用 `UNIQUE` 和 `NOT NULL`。

### 7.3 InnoDB 外键的 RESTRICT、CASCADE、SET NULL 有何区别？ {#foreign-key-actions}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：引用动作、可空性和即时检查。

**相关内容**：[外键动作与检查时机](#外键动作与检查时机)。

<details>
<summary>参考回答</summary>

**三者的区别在于父记录仍被引用时怎么处理：RESTRICT 拒绝变更，CASCADE 把变更传播到子表，SET NULL 把子表引用列置空。**

`CASCADE` 会让删除父记录时一起删掉子记录，更新父键时一起更新子表的外键列。`SET NULL` 要求子表外键列允许为空。InnoDB 立即检查外键，不支持推迟检查，所以 `NO ACTION` 与 `RESTRICT` 效果相同。

</details>
