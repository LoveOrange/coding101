# 数据建模

**数据建模**是把业务对象、对象之间的关系和必须成立的规则，转换成数据结构的过程。关系数据库中，首先要回答一行代表什么、怎样唯一标识它、哪些字段可以变化，再决定表、键和约束。

面试介绍项目表设计时，要能把一条业务规则对应到具体字段或约束，并说明这个设计怎样支持读写。只列出几张表名，还不能解释为什么这样拆。

## 1. 面试核心 {#core}

- 每张表先确定**一行的业务含义与唯一标识**；当前状态和历史事件有不同的行粒度。[卡](#table-design)
- 一对多关系通常在**多的一侧保存关联键**；多对多关系用关联表，每行表示一次关系。[卡](#many-to-many)
- 评论表用 **`parent_id` 保存直接回复关系**，查询顺序、所属内容和删除规则要一起确定。[卡](#comment-parent-model)
- 代理主键方便标识行，但**不能替代业务唯一约束**；有自增 ID 仍可能重复预约。[卡](#surrogate-business-key)
- 第一到第三范式逐步处理**重复组、部分依赖和传递依赖**，拆表是为了减少插入、更新和删除异常。[卡](#normalization-online-change)
- 规范化减少同一事实的重复保存；保留订单成交价这类**历史事实是业务语义，不能用当前价格覆盖**。
- 索引服务于访问路径，事务保护跨行变化；**表结构、约束、索引和事务要一起解释**，各自不能替代其他机制。

- 修改行中的值用 **`UPDATE`，修改列定义用 `ALTER TABLE`**；线上变更还要检查数据转换、锁和新旧程序兼容性。[卡](#modify-column-command)

## 2. 实体与行粒度 {#实体与行粒度}

**实体**是业务中需要单独识别和保存信息的对象，例如学生和课程。**行粒度**是一条记录代表的最小业务单位：课程表的一行可以代表一门课程，而开课表的一行代表某学期的一次开设，两者不能混用。

假设课程可以跨学期重开，学生每次开课只能报名一次。若只保存 `(student_id, course_id)`，就无法区分学生今年和明年的报名。更准确的模型是课程定义、开课实例和报名关系：报名指向具体的 `offering_id`。命名和主键都应服从这个业务含义。

再看报名状态。若表中一行保存当前报名，取消就是修改状态；若需要完整审计，可以另存状态变化事件，每行记录一次变化。不能一边把表理解为当前状态，一边把重复插入当作历史而不修改唯一规则。

## 3. 关系与关联表 {#关系与关联表}

**一对多**表示一个对象可以关联多个另一个对象，例如一次开课有多条报名。多的一侧保存外键，就能找到它归属的对象。**多对多**表示两侧都可以关联多个对象，例如学生可以报名多次开课，每次开课也允许多个学生报名。

多对多关系用独立关联表表示。下面以 MySQL 8.0、InnoDB 为例，省略与关系无关的课程名称等字段：

```sql
CREATE TABLE students (
  id BIGINT PRIMARY KEY,
  name VARCHAR(50) NOT NULL
) ENGINE=InnoDB;

CREATE TABLE offerings (
  id BIGINT PRIMARY KEY,
  title VARCHAR(100) NOT NULL
) ENGINE=InnoDB;

CREATE TABLE enrollments (
  student_id BIGINT NOT NULL,
  offering_id BIGINT NOT NULL,
  enrolled_at DATETIME NOT NULL,
  PRIMARY KEY (student_id, offering_id),
  FOREIGN KEY (student_id) REFERENCES students(id),
  FOREIGN KEY (offering_id) REFERENCES offerings(id)
) ENGINE=InnoDB;

INSERT INTO students VALUES (1, 'Lin'), (2, 'Ming');
INSERT INTO offerings VALUES (10, '数据库'), (20, '网络');
INSERT INTO enrollments VALUES
  (1, 10, '2026-01-01 10:00:00'),
  (1, 20, '2026-01-01 10:05:00'),
  (2, 10, '2026-01-02 09:00:00');

SELECT s.name, o.title
FROM enrollments e
JOIN students s ON s.id = e.student_id
JOIN offerings o ON o.id = e.offering_id
ORDER BY s.id, o.id;
```

结果是 Lin 对应数据库和网络，Ming 对应数据库。联合主键禁止重复的 `(student_id, offering_id)`；外键要求学生和开课记录存在。这里一行是一个学生与一次开课的报名关系，`enrolled_at` 属于这段关系，放在学生表里就无法表达同一个学生的多次报名时间。

不要把多个课程 ID 拼成逗号字符串放在学生的一列里：数据库无法把每一项分别作为外键约束，查询和删除关系也要额外解析字符串。连接、筛选与未匹配行的处理见 [SQL 连接](../sql/joins.mdx)。

### 3.1 评论与回复关系 {#评论与回复关系}

**评论关系**可以用一张自关联表表示：一行是一条评论，`parent_id` 指向被直接回复的评论。以下以一篇内容下的多级回复为教学场景，原题若只要求两层展示，可以限制允许回复的层级，不必增加无限层级的产品功能。

| 字段 | 含义与约定 |
| --- | --- |
| `id` | 评论唯一 ID，发布后不变 |
| `content_id` | 评论所属的视频或文章 |
| `author_id` | 发布者 |
| `parent_id` | 直接父评论 ID；顶层评论为 `NULL` |
| `body` | 评论正文 |
| `status` | 例如 `visible`、`deleted`，区分可展示内容与删除占位 |
| `created_at` | 发布时间 |

例如评论 100 属于内容 7，评论 101 回复 100，评论 102 回复 101，则它们的 `parent_id` 分别是 `NULL`、100、101。仅用一个“回复用户 ID”无法恢复这条父子链，因为同一用户可能在多处发言。

读取时先明确是查顶层评论、某条评论的直接回复，还是整条讨论链。下面约定按不可变的 `id` 降序展示顶层评论，按 `id` 升序展示直接回复；这只是稳定的 ID 顺序，不承诺严格的事务提交时间顺序。示例是后续页，游标取自上一页最后一条记录：

```sql
-- 内容 7 的顶层评论，上一页最后一个 ID 为 100
SELECT id, author_id, body
FROM comments
WHERE content_id = 7 AND parent_id IS NULL
  AND status = 'visible' AND id < 100
ORDER BY id DESC LIMIT 20;

-- 评论 100 的直接回复，上一页最后一个 ID 为 101
SELECT id, author_id, body
FROM comments
WHERE content_id = 7 AND parent_id = 100
  AND status = 'visible' AND id > 101
ORDER BY id ASC LIMIT 20;
```

首屏去掉游标条件即可。索引可以按这两类条件考虑 `(content_id, parent_id, status, id)`，再用执行计划核对。游标分页不依赖前面有多少行，但它不提供跨请求的一致快照；期间新增、删除或状态变化仍可能影响可见结果。

写入时要检查父评论存在、父子属于同一 `content_id`，并规定父关系发布后不可修改。只允许回复已存在的评论，且插入时禁止自引用，可以避免构造环；自引用外键本身不能表达所有这些规则。检查和插入应在事务中完成，并按并发删除策略锁定或约束父记录，不能只在事务外查一次。

删除父评论时，可以清除正文并保留 `deleted` 占位和父子关系，让已有回复仍可定位；此时讨论详情需要能展示删除占位，不能只用上面的可见评论列表恢复整棵树。是否级联删除是业务选择，要明确说明。若主要查询是“某条顶层评论下的全部回复”，可以额外保存 `root_id`，在写入时从父评论继承顶层 ID；它是查询冗余，不能替代 `parent_id` 的直接回复含义。

## 4. 键与业务规则 {#键与业务规则}

**候选键**是能够唯一确定一行的最小字段组合，主键是从中选出的主要标识。**代理键**是额外分配、主要用于标识行的值，例如自增 ID。使用代理键以后，业务唯一性仍要单独表达。

例如把 `enrollments` 改成自增 `id` 主键，并不自动阻止同一学生重复报名；仍需要 `UNIQUE(student_id, offering_id)`。如果允许取消后再次报名并保留多次历史，则应重新确定一行代表报名关系还是报名尝试，并为当前有效关系设计明确约束，不能直接沿用原来的唯一规则。

约束还应回答这些问题：字段能否未知或暂未提供，引用对象删除后如何处理，金额是否允许为负。金额需要精确计算时，可以用定义好单位的整数或 `DECIMAL`，避免用浮点近似代替精确金额。整数范围、小数精度、字符串长度与时间类型的选择见 [MySQL 数据类型](./data-types.mdx)。`NULL`、唯一性、外键和检查约束的执行细节见 [数据约束](./constraints.mdx)。

同一课程不能超额报名是跨行或多表规则，仅靠报名关系的唯一键还不够。要把名额检查、扣减和报名记录写入放进合适的[数据库事务](../transaction/index.mdx)，并处理并发竞争。

## 5. 规范化与历史事实 {#规范化与历史事实}

**规范化**是按数据之间的依赖关系组织表，减少同一事实重复保存造成的不一致。学生姓名属于学生，不必在每条报名中维护一份“当前姓名”。否则一次改名要修改许多记录，漏改就出现多个当前姓名。

但有些看起来重复的字段表达不同事实。订单行保存下单时的商品名称和成交价，是为了保留交易发生时的约定；商品表保存当前名称和售价。两者允许不同，不应把历史成交价随商品价格一起更新。

为了提高读取效率，也可以保存汇总或冗余数据，但要明确谁是依据、何时更新、失败后如何修复。面试中先说明查询瓶颈和一致性要求，再解释为什么接受这份维护成本；不能只用“减少连接”作为所有反规范化的理由。

### 5.1 第一范式到第三范式 {#第一范式到第三范式}

**函数依赖**描述字段间的确定关系：若一个 `student_id` 只对应一个当前姓名，就写作 `student_id → name`。这里的“确定”来自业务规则，不能因为几条样例数据恰好不同，就推断字段具有唯一性。

**第一范式**（1NF）要求每个位置保存所属域中的一个值，避免把多次报名塞成一组重复字段或可变长度的嵌套记录。前面的报名表把一个学生的一次报名拆成一行，新增报名不需要再加“课程 4”字段。“原子”取决于数据如何使用，不意味着所有字符串都必须拆成字符。

**第二范式**（2NF）在 1NF 上要求每个非主属性完全依赖每个候选键，不依赖候选键的真子集。非主属性是没有出现在任何候选键中的属性。假设报名表唯一的候选键是 `(student_id, offering_id)`，若还存当前学生姓名，姓名只依赖 `student_id`，就是部分依赖。把姓名放回学生表后，报名表保留属于整次报名的 `enrolled_at`。

**第三范式**（3NF）进一步限制依赖：对于非平凡函数依赖 `X → A`（`A` 不属于 `X`），`X` 应是超键，或 `A` 是主属性。超键是能唯一确定一行的字段集合，主属性是出现在某个候选键中的属性。基础例子可以理解为消除非主属性对候选键的传递依赖：假设学生表的唯一候选键为 `student_id`，每名学生属于一个院系，`department_id` 决定院系名称，则 `student_id → department_id → department_name`。把院系名称放入院系表，学生表只保存院系 ID。

这些拆分解决的是具体的数据异常：院系改名不必修改每个学生，新增院系不必先虚构一个学生，删除最后一个学生也不会丢失院系信息。范式以业务依赖为依据；如果字段表达的是下单时的历史名称，不能直接拿“当前名称”的依赖替代它。

## 6. 访问路径与生命周期 {#访问路径与生命周期}

表设计完成后，要用实际查询检验它。例如报名联合主键以 `student_id` 开头，适合按学生查看报名；按开课列出全部学生还需要相应索引。外键关联与查询索引的职责不同，具体访问计划见 [数据库索引](../indices/index.mdx)。

数据保留也影响模型：哪些记录可以删除，哪些需要归档，历史查询是否仍要关联已删除实体。冷热拆分和分片属于规模与访问路径的设计，先检查普通索引和归档是否已满足需求，再讨论 [数据拆分](../../../system-design/system-design/read-write-paths-hotspots-sharding.mdx)。

### 6.1 列定义与线上变更 {#列定义与线上变更}

**`UPDATE` 修改行中的值，`ALTER TABLE` 修改表结构**。例如，下面先修改课程标题的值，再把标题列的最大长度扩大；这是一个独立的 MySQL 8.0 示例：

```sql
CREATE TABLE course_titles (
  id BIGINT PRIMARY KEY,
  title VARCHAR(100) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci
    NOT NULL DEFAULT '' COMMENT '课程标题'
) ENGINE=InnoDB;
INSERT INTO course_titles (id, title) VALUES (1, '数据库');
UPDATE course_titles SET title = '数据库基础' WHERE id = 1;
ALTER TABLE course_titles
  MODIFY COLUMN title VARCHAR(200)
    CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci
    NOT NULL DEFAULT '' COMMENT '课程标题';
SHOW CREATE TABLE course_titles;
```

执行后，ID 为 1 的标题是“数据库基础”，列定义允许最多 200 个字符。`MODIFY COLUMN` 需要写出要保留的完整列定义；原有的非空、默认值、注释、字符集和排序规则等不能靠省略来保留。主键、普通索引等索引属性另有定义规则，不需要在这里重写。改之前先查看 `SHOW CREATE TABLE`，避免只写新类型时顺带改变其他属性。

线上改列还要检查三个问题：

- **已有数据能否转换。** 缩短字符串、缩小数字范围、改变字符集或增加非空要求，都可能失败或改变数据。先检查真实数据，在严格 SQL 模式下验证转换结果，不能只在空表试语法。
- **执行期间会占用什么资源。** MySQL 8.0 的不同变更可能使用 `INSTANT`、`INPLACE` 或 `COPY`，是否重建表、允许并发写入取决于具体操作和条件。扩展 `VARCHAR` 也受长度存储字节等条件影响，不能把所有扩列都说成瞬间完成。应确认算法、临时空间、复制延迟和锁等待；在线 DDL 也仍需要[元数据锁](../transaction/long-transactions-hot-updates-boundaries.mdx#元数据锁与-ddl)。
- **新旧应用能否共存。** 直接改名、删列或改变含义，可能让仍在运行的旧程序失败。需要分阶段时，先新增兼容字段，再迁移和校验存量数据，切换读写并确认旧程序退出，最后删除旧字段；这就是[扩展、迁移与收缩](../../../system-design/leadership/compatibility-migration-canary-exit-criteria.mdx#扩展迁移收缩)的用途。

先在接近实际数据规模的环境验证，并明确发布期间的观察与停止条件。修改结构成功只说明 DDL 已执行，不代表历史数据、新旧代码和回退路径都已验证。

## 7. 面试题 {#面试题}

### 7.1 介绍项目数据库设计时，应怎样说明表和字段的依据？ {#table-design}

**考察重点**：业务规则、行粒度、标识、关系、访问方式与事务边界。

**相关内容**：[实体与行粒度](#实体与行粒度)、[键与业务规则](#键与业务规则)、[访问路径与生命周期](#访问路径与生命周期)。

<details>
<summary>参考回答</summary>

**先说明一行代表什么，再解释键、关系、规则和主要读写。** 从一条真实请求出发，指出涉及哪些表、凭什么定位行、哪项约束阻止非法状态；涉及多条记录共同变化时，说明事务与并发控制。

最后给出主要查询和索引依据，以及删除、归档与历史数据的处理。表设计应当能对应实际业务要求，而不是只列字段名称。

</details>

### 7.2 学生与课程的多对多关系怎样建表和查询？ {#many-to-many}

**考察重点**：关联表的行含义、关系属性、联合唯一性与连接。

**相关内容**：[关系与关联表](#关系与关联表)。

<details>
<summary>参考回答</summary>

**分别保存学生和具体开课实例，用报名表连接两者。** 报名表一行代表一个学生报名一次开课，保存两个关联键及报名时间；按业务规则用联合主键或唯一约束防止重复。

查询时沿学生、报名、开课做连接。若课程可重复开设，报名应关联开课实例，避免把不同学期当成同一次报名。不要把多个课程 ID 拼进一个字符串字段。

</details>

### 7.3 已有自增主键，为什么仍需要业务唯一约束？ {#surrogate-business-key}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：行标识与业务唯一性的不同职责。

**相关内容**：[键与业务规则](#键与业务规则)。

<details>
<summary>参考回答</summary>

**自增主键只保证每行 ID 不同，不能防止两行代表同一次业务关系。** 两条重复报名可以获得不同 ID，所以还要约束学生与开课的组合。若业务允许重复尝试，必须先区分尝试记录和有效报名，再确定各自的唯一范围。

</details>

### 7.4 数据库前三个范式是什么，线上改表还要考虑什么？ {#normalization-online-change}

**题型**：综合题

**考察重点**：规范化与数据异常、线上结构变更的兼容性。

**相关内容**：[第一范式到第三范式](#第一范式到第三范式)、[列定义与线上变更](#列定义与线上变更)。

<details>
<summary>参考回答</summary>

**1NF 处理单值与重复组，2NF 消除非主属性对候选键的部分依赖，3NF 进一步限制传递依赖。** 例如姓名属于学生、院系名称属于院系，不应在每条报名里重复维护当前值。

线上改表还要检查数据转换、DDL 算法、资源和元数据锁，并验证新旧程序共存。不能因为模型更规范，就直接在有流量的表上改名或删列。

</details>

### 7.5 评论表如何表示多级回复，并支持查询和删除？ {#comment-parent-model}

**题型**：综合题

**考察重点**：评论粒度、直接父关系、访问路径和完整性。

**相关内容**：[评论与回复关系](#评论与回复关系)、[键与业务规则](#键与业务规则)。

<details>
<summary>参考回答</summary>

**每行保存一条评论，用 `content_id` 确定所属内容，用 `parent_id` 表示直接回复。** 顶层评论的父 ID 为空；需要按整条讨论查询时，可以增加由父关系维护的 `root_id`。

先明确查询顶层、直接回复还是全部后代，再设计索引和稳定游标。写入时检查父记录、所属内容和无环规则，结合事务处理并发删除。父评论删除可以保留占位，让已有回复仍可定位；具体层级和删除策略取决于业务。

</details>

### 7.6 MySQL 修改字段用什么命令？ {#modify-column-command}

**考察重点**：行值更新与列定义变更的区别。

**相关内容**：[列定义与线上变更](#列定义与线上变更)。

<details>
<summary>参考回答</summary>

**修改某行字段的值用 `UPDATE ... SET ... WHERE ...`；修改列类型或属性用 `ALTER TABLE ... MODIFY COLUMN ...`。** `MODIFY` 要写全需要保留的列属性。执行前查看原始定义、检查已有数据能否转换，并确认线上锁与兼容性影响。

</details>
