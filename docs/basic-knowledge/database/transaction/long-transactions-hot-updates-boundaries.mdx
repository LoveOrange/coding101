# 长事务

本文以 MySQL 8.4 InnoDB 为例。长事务可能延长锁和历史版本的持有时间，热点更新则让大量请求竞争同一小组记录。两者叠加时，连接池、undo、复制延迟和接口尾延迟都可能同时恶化。

## 1. 面试核心 {#core}

- 长事务可能长期持有行锁或旧快照，阻碍相关 undo 清理并占用连接；影响取决于隔离级别和实际 SQL。[卡](#long-transactions-hot-rows)
- 事务中不要调用远程接口，网络延迟会直接变成持锁时间，远程结果也不会随回滚撤销。
- 回填、迁移等批量任务按游标拆成小事务，每批更新与进度在同一事务提交，并允许安全重放。[卡](#batch-checkpoint)
- 热点行让并发更新串行执行，吞吐上限由单次持锁时间决定；可以拆分子行、合并请求或排队处理。
- 结合事务年龄、锁等待链和 history list length 诊断；后者不是 undo 字节数。[卡](#readonly-snapshot)

## 2. 事务持续时间与资源 {#事务持续时间与资源}

应用事务边界从显式开启或框架进入事务方法开始，到提交或回滚结束；InnoDB 的实际事务状态与 Read View 建立时机还取决于执行了什么 SQL。仅执行 `BEGIN` 不代表已经创建一致性读快照。期间可能持有：

- 已取得的记录锁和区间锁。
- 数据库连接。
- 未提交修改对应的 undo 与 redo 状态。
- Read View 对旧版本的可见需求。
- 应用线程和上游请求预算。

一条 SQL 很快，不代表事务很短。SQL 之间的业务计算、网络调用、人工等待或错误的自动重试都可能让事务长时间保持打开。

## 3. 长事务与 purge {#长事务与-purge}

默认 RR 下，第一次普通一致性读建立的快照通常沿用到事务结束；RC 下普通一致性读每条语句获取新快照。单次长查询也可能延长快照的有效时间。

活跃快照仍可能读取旧版本时，InnoDB 不能清理相关 undo 历史。更新持续发生会让历史版本积累，增加存储和一致性读沿版本链查找的成本。

写事务持有的锁还会让其他更新排队。等待请求占用连接后，应用连接池可能耗尽，原本只影响一行的阻塞逐步扩散到整个服务。

大事务提交还会形成较大的日志和复制工作单元，回滚也需要按修改量执行，失败恢复时间不可忽略。

## 4. 事务中的远程调用 {#事务中的远程调用}

```text
开启事务 → 更新订单 → 调用支付服务 → 写流水 → 提交
```

支付调用的网络延迟会直接变成数据库持锁时间。远程结果不受本地数据库事务控制，即使数据库随后回滚，支付也可能已经成功。

更清晰的设计是先用短事务记录可恢复的状态和待发送事件，再由 Outbox 或任务处理器调用外部系统。回调或结果通知通过幂等状态转换推进下一步，而不是让数据库事务跨越网络。

## 5. 批量任务拆分 {#批量任务拆分}

回填、迁移和清理任务应按稳定游标分批处理，每批独立提交，并保存进度。批次大小要根据单批耗时、日志量、锁影响和失败重做成本校准。

使用 `LIMIT ... OFFSET` 扫描持续变化的大表，可能越来越慢并产生遗漏或重复。更适合使用主键或稳定业务键作为 seek 游标，例如 `WHERE id > ? ORDER BY id LIMIT ?`。

分批不等于忽略整体正确性。任务要明确可重复执行规则、完成标记和中途失败后的恢复方式。同一数据库内，把本批数据变更与 checkpoint 放在同一事务提交；跨系统副作用要另用幂等键或 Outbox。只在内存推进游标会丢失恢复依据，先提交进度再提交数据则可能漏处理。

## 6. 热点行 {#热点行}

库存、余额、全局计数器和单一任务状态经常集中更新一行。即使每次更新只用几毫秒，所有请求仍要依次取得同一记录锁，吞吐上限由临界区耗时决定。

先确认业务不变量是否可以用单条条件更新表达：

```sql
UPDATE inventory
SET available = available - 1
WHERE sku_id = ? AND available > 0;
```

受影响行数可以判断扣减是否成功，避免“先查询、再计算、再更新”的竞争窗口。它减少往返与持锁时间，但同一行的写入依然串行。

## 7. 拆分热点 {#拆分热点}

当单行已达到瓶颈，可以考虑：

- **分片计数**：把可合并的统计值写入多个分片，读取时聚合。
- **按业务键分区**：让不同商品、账户或租户由不同执行单元处理。
- **串行消费者**：把同一键的命令路由到同一分区，显式控制顺序。
- **预分配额度**：把总资源拆给多个节点，再异步汇总剩余量。
- **乐观条件更新**：低冲突时使用版本号比较并有限重试。

这些方案会改变实时可见性、故障恢复或资源超卖边界。选择前要写清必须保持的业务不变量，而不是只追求数据库 TPS。

## 8. 监控 {#监控}

生产环境应观察：

- 活跃事务的最大和分位持续时间。
- history list、undo 空间和 purge 进度。
- 行锁等待时间、等待事务数和死锁率。
- 连接池 active、pending 与获取超时。
- 单一业务键或索引范围的冲突分布。
- 批任务单批耗时、进度和失败重试。

`SHOW ENGINE INNODB STATUS` 的 history list length 反映待清理的历史 undo 日志数量，不是行数、字节数或业务事务数量的精确等价物。结合 `information_schema.innodb_trx` 的事务起始时间，以及 Performance Schema 的锁等待关系判断。

发现长事务后，先定位会话和完整调用链，再决定终止、等待或修复。贸然杀掉修改量很大的事务也会触发长时间回滚，需要评估业务影响。

## 9. 常见问题 {#9-常见问题}

### 9.1 只读事务是否不会造成影响 {#91-只读事务是否不会造成影响}

长时间只读事务仍可能持有旧快照，阻止相关历史版本被 purge。它通常不阻塞普通写入取得记录锁，但会增加 undo 保留与旧版本读取成本。

### 9.2 把热点更新放进 Redis 是否就解决了 {#92-把热点更新放进-redis-是否就解决了}

Redis 可以提高某些计数操作吞吐，但会引入持久化、故障转移和数据库同步问题。若库存或余额要求严格不超额，需要先定义 Redis 故障时的权威状态、恢复协议和核对方式。

## 10. 面试题 {#10-面试题}

### 10.1 如何治理长事务和热点行更新 {#long-transactions-hot-rows}

- 腾讯：https://www.nowcoder.com/discuss/353155207712415744
- 招银科技：https://www.nowcoder.com/discuss/741956212241051648
-->

**出现公司**：腾讯、招银科技

**考察重点**

- 锁、连接、undo 历史与复制成本。
- 事务内远程调用和大批量工作的拆分。
- 条件更新、分片、串行化与业务不变量。

**相关内容**：[事务持续时间与资源](#事务持续时间与资源)至[监控](#监控)。

<details>
<summary>参考回答</summary>

长事务会长时间占用连接和锁，旧 Read View 还会阻止相关 undo 版本清理；大事务的提交、复制和回滚成本也更高。先从活跃事务年龄、锁等待、连接池和 undo 历史定位完整调用链，再把远程调用移出事务，把批处理按稳定游标拆成可恢复的小事务。

热点行会让并发更新在同一记录锁上串行。可以先用单条条件 UPDATE 缩短临界区；达到单行上限后，根据业务一致性要求选择分片计数、按键分区、串行消费者或额度预分配。无论采用哪种方式，都要保留幂等、失败恢复和核对机制，不能只把状态换到另一个组件。

</details>

### 10.3 分批回填时数据提交成功但进度未保存，如何保证恢复正确？ {#batch-checkpoint}

- 批次原子性
- 稳定游标与幂等

**相关内容**：[批量任务拆分](#批量任务拆分)。

<details>
<summary>参考回答</summary>

同一数据库内将本批数据变更和持久化进度一起提交，失败一起回滚。重放仍需幂等条件，扫描使用稳定排序键，并明确并发新增和更新是否属于本轮任务。涉及外部系统时，单库事务不能原子覆盖对方，应记录可恢复事件并去重处理。

</details>
