# 数据库事务

数据库事务把一组读写放进同一个提交边界，并规定失败恢复、并发可见性和提交后的持久性。本文以 MySQL 8.4 InnoDB 为例，负责 ACID、隔离级别、事务边界与提交持久性；版本可见性见 [MVCC](./mvcc-read-view-consistent-read.mdx)，记录与间隙的加锁规则见 [InnoDB 锁](./innodb-locking-ranges.mdx)。

## 1. 面试核心 {#core}

- ACID 描述原子性、一致性、隔离性和持久性，业务不变量通过约束、SQL 与事务边界维护。[卡](#acid-isolation-levels)
- InnoDB 的 RC 为每次一致性读创建快照，RR 复用首次一致性读的快照，Serializable 要求结果等价于串行执行。[卡](#acid-isolation-levels)
- `SET quantity = quantity - 1 WHERE quantity > 0` 根据当前记录完成库存判断和扣减，避免基于旧值覆盖写造成丢失更新。[卡](#lost-update)
- `innodb_rollback_on_timeout=OFF` 时锁等待超时回滚当前语句，死锁检测选中的受害事务整体回滚。[卡](#transaction-failure)
- `innodb_flush_log_at_trx_commit=1` 和 `sync_binlog=1` 让 redo 与 binlog 在提交成功返回前刷盘。[卡](#commit-durability) [卡](#double-one-durability)

## 2. 事务边界 {#1-事务保护一组相关状态变化}

账户转账至少包含扣减付款方余额与增加收款方余额。如果其中一步提交、另一步失败，数据就会进入不符合业务规则的状态。把两步放进一个本地数据库事务，可以让它们共同提交或共同回滚。

下面展示成功路径；两个更新之间必须由应用检查影响行数，失败时执行 `ROLLBACK` 并停止后续语句：

```sql
START TRANSACTION;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1 AND balance >= 100;
-- 应用检查影响行数为 1；否则 ROLLBACK 并结束。

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;
-- 应用检查影响行数为 1；否则 ROLLBACK 并结束。

COMMIT;
```

事务边界还要检查两条更新是否各影响一行，并通过约束防止非法余额。事务只能覆盖同一数据库能够协调的操作；HTTP 调用、消息发送和另一个数据库不会自动加入这次提交。

## 3. ACID {#2-acid-描述四类保证}

### 3.1 原子性 Atomicity {#21-原子性-atomicity}

事务中的修改要么提交，要么在失败时不对外生效。InnoDB 使用 undo log 等机制保存回滚所需信息。应用遇到异常时应结束失败事务，使未提交修改通过回滚撤销。

### 3.2 一致性 Consistency {#22-一致性-consistency}

事务执行前后应满足数据库约束和业务不变量。数据库可以强制主键、唯一键、外键和检查约束；“账户总额不变”等跨行业务规则还需要应用正确读取、加锁和更新。

### 3.3 隔离性 Isolation {#23-隔离性-isolation}

并发事务的中间状态按照隔离级别受到限制。隔离越强，允许观察到的并发结果越少；事务冲突时，锁实现会等待，冲突检测实现会回滚。

### 3.4 持久性 Durability {#24-持久性-durability}

数据库确认提交后，即使进程或机器随后故障，已提交结果仍应按系统承诺恢复。InnoDB 依赖 redo log、刷盘策略和恢复流程；复制副本与备份用于覆盖机器损毁等更大范围的故障。

## 4. 并发异常 {#3-并发读写会产生多种异常}

- **脏读**：读取了另一个事务尚未提交的修改。
- **不可重复读**：同一事务再次读取同一行时，看到其他事务已提交的新值。
- **幻读**：同一事务再次执行范围条件时，结果集合出现新增或删除的行。
- **丢失更新**：多个事务基于旧值计算并写回，后一次写入覆盖前一次结果。
- **写偏差**：两个事务读取共同约束的不同数据，再分别更新，单行都合法但组合后破坏业务不变量。

前三个名称常用于介绍 SQL 标准隔离级别，并发正确性还涉及丢失更新和写偏差。设计时要写出事务的读集合、写集合和业务约束，再检查特定数据库在目标隔离级别下允许什么执行结果。

## 5. 隔离级别 {#4-四种隔离级别限制不同可见性}

### 5.1 Read Uncommitted {#read-uncommitted}

读未提交允许事务读取其他事务尚未提交的修改，因此允许脏读。实际系统很少需要这种隔离级别。

### 5.2 Read Committed {#read-committed}

读已提交只读取已经提交的版本。在 InnoDB 中，每次普通一致性读建立新视图，可以看到期间刚提交的新值。PostgreSQL 默认使用 Read Committed。

### 5.3 Repeatable Read {#repeatable-read}

可重复读要求事务中的重复读取保持稳定；InnoDB 默认采用 Repeatable Read，快照时机与混合读写的可见性见 [MVCC](./mvcc-read-view-consistent-read.mdx#4-可重复读复用第一次一致性读的快照)。

### 5.4 Serializable {#serializable}

串行化要求并发结果等价于某种串行执行顺序。实现可以通过锁、序列化冲突检测或两者结合完成，允许在维持串行等价性的前提下并发执行。冲突时的代价是等待、死锁或序列化失败，应用必须能够处理回滚和重试。

:::note 数据库实现差异

SQL 标准给出隔离语义，数据库采用 MVCC、锁和冲突检测实现。MySQL 与 PostgreSQL 对 Repeatable Read、Serializable 和只读快照的具体行为并不完全一致，结论必须限定数据库、版本、语句类型和是否显式加锁。

:::

### 5.5 默认 RR 与 statement binlog 的历史背景 {#默认-rr-与-statement-binlog-的历史背景}

InnoDB 默认 RR 的历史背景与早期 statement 格式 binlog 的重放一致性有关。MySQL 5.7.7 之前默认 `binlog_format=STATEMENT`，副本通过重新执行 SQL 还原变更；RR 的 next-key 锁能约束并发插入，使范围写入和 `INSERT ... SELECT` 等语句的读写范围在重放时保持一致。

例如 A 的范围更新尚未提交，B 向该范围插入并先提交；若 A 在源库执行时没处理 B 的新行，副本按 B、A 的提交顺序重放 SQL 时却处理了该行，就会出现差异。范围锁使 B 的插入等待 A 结束，约束这种执行顺序。

这是根据官方格式历史与锁机制说明解释的兼容性背景；官方资料并未将它列为选择默认 RR 的唯一原因。MySQL 8.4 默认 `binlog_format=ROW`，记录行变更，RC/RU 的 InnoDB 写入也要求 row 格式；选择隔离级别仍需依据业务读写语义。

## 6. InnoDB 并发控制 {#5-innodb-同时使用-mvcc-与锁}

InnoDB 在 RC/RR 下通过 [MVCC](./mvcc-read-view-consistent-read.mdx) 提供普通一致性读，通过 [InnoDB 锁](./innodb-locking-ranges.mdx) 协调锁定读和写操作。

业务不变量还需要条件更新、唯一约束或锁定读保护，并处理死锁重试；具体选择取决于读写集合和需要共同成立的约束。

## 7. 事务范围与持续时间 {#6-事务边界要尽量短且完整}

事务范围与持续时间按以下原则设计：

1. 在进入事务前完成不依赖数据库快照的参数校验。
2. 事务内只保留维护不变量所需的查询与更新。
3. 按稳定顺序访问热点记录，缩短持锁时间。
4. 不在持锁期间等待用户输入或执行不受控的远程调用。
5. 使用唯一约束、版本号或条件更新保护并发结果。
6. 对死锁和序列化失败进行有界重试，并保证业务操作幂等。
7. 通过 outbox 等模式把事务结果可靠地交给异步消息流程。

事务过长会保留旧版本、占用连接和锁，增加回滚成本。拆分边界时仍需保持原本必须共同成立的业务不变量。

## 8. 条件更新与丢失更新 {#条件更新与丢失更新}

假设库存为 10，两个事务都先读取 10，再执行 `SET quantity = 9`，两次写入后最终只扣减一次。即使每条 `UPDATE` 都会取得排他锁，应用已经算好的旧结果仍会覆盖前一次更新。

把判断与修改放在同一条语句中：

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE sku_id = 100 AND quantity > 0;
```

两个事务更新同一行时会在写入处协调；后执行者根据可更新的当前记录判断剩余库存。影响行数为 0 表示本次扣减未成功，应用应按扣减失败处理。涉及多个表或跨行约束时，仍需完整事务、锁定读或约束设计。

另一种做法是 `WHERE id = ? AND version = ?`，同时递增版本号；影响行数为 0 时重新读取并决定重试。与把旧值直接覆盖回去相比，它能检测并发修改。MVCC 的实现细节见 [MVCC](./mvcc-read-view-consistent-read.mdx)，锁定范围见 [InnoDB 锁](./innodb-locking-ranges.mdx)。

## 9. 自动提交与失败边界 {#自动提交与失败边界}

MySQL 默认启用 autocommit，独立语句各自提交。需要多条 DML 共同成功时，用显式事务或事务管理器绑定同一连接。嵌套调用的提交范围由事务管理器决定；保存点用于事务内的局部回滚，最终提交仍由外层事务完成。

| 情况 | InnoDB 的典型行为 | 应用需要做什么 |
| --- | --- | --- |
| 普通重复键错误 | 回滚当前语句，事务继续有效 | 判断业务是否还能成立，按需回滚整个事务 |
| 检测到死锁 | 选择一个事务整体回滚 | 重开事务，有界重试完整业务单元 |
| 锁等待超时 | `innodb_rollback_on_timeout=OFF` 时回滚当前语句，`ON` 时回滚整个事务 | 明确回滚或恢复策略，避免半完成业务继续提交 |
| `CREATE TABLE`、`ALTER TABLE` 等 DDL | 多数会引发隐式提交 | 不把 DDL 与普通 DML 当成同一个可回滚单元 |

配置了相应回滚规则的框架会在异常后把事务标为仅回滚；数据库回滚范围与框架策略需要分别确认。捕获异常后显式终止失败事务，可以避免提交部分业务结果。

## 10. 提交持久性与结果确认 {#提交持久性与结果确认}

redo 保存崩溃恢复信息，undo 支持回滚与历史版本，binlog 记录用于复制和按时间点恢复的变更。

### 10.1 双 1 配置 {#双-1-配置}

“双 1”指 `innodb_flush_log_at_trx_commit=1` 和 `sync_binlog=1`：前者要求提交时写出并刷盘 redo，后者要求每组 binlog 提交在提交事务前同步到磁盘。组提交可以让多个事务共享一次同步，成功响应前仍须完成相应日志的持久化。

| 配置 | 写出与刷盘时机 | 故障边界 |
| --- | --- | --- |
| `innodb_flush_log_at_trx_commit=1` | 每次提交写出并刷盘 redo | 依赖操作系统和存储兑现刷盘 |
| `innodb_flush_log_at_trx_commit=2` | 每次提交写到操作系统缓存，按后台周期刷盘 | 操作系统崩溃或掉电可丢失尚未刷盘的提交 |
| `innodb_flush_log_at_trx_commit=0` | 后台按周期写出并刷盘 redo | mysqld 崩溃也可丢失仍在日志缓冲区的提交 |
| `sync_binlog=1` | 每组 binlog 提交同步磁盘 | 与 redo 的提交刷盘配合保护日志一致性 |
| `sync_binlog=0` | 由操作系统决定 binlog 刷盘时间 | 掉电可丢失尚未落盘的 binlog |

后台周期由 `innodb_flush_log_at_timeout` 控制，默认 1 秒；调度会影响实际间隔。“双 1”的持久性以可靠存储为前提；异步复制仍有复制延迟，整机或磁盘永久损毁需要副本与备份覆盖。

### 10.2 提交结果确认 {#提交结果确认}

提交阶段断线会让客户端失去结果确认：数据库已经提交而响应丢失时，直接重试会重复扣款或创建订单。使用业务唯一标识查询提交结果，并以唯一约束防止重复执行，再决定重试或对账。

## 11. 常见问题 {#7-常见问题}

### 11.1 可重复读的并发边界 {#71-可重复读能解决所有并发问题吗}

RR 的重复读取保证覆盖可见性；跨行不变量仍需锁、约束或串行化策略。例如两个事务分别更新不同记录时，写偏差会破坏它们共同依赖的业务约束。

### 11.2 本地事务与跨资源操作 {#72-方法加了-transactional-就能覆盖远程调用吗}

本地数据库事务只管理所绑定数据库连接上的提交与回滚。跨资源流程需要幂等、outbox、Saga、对账或专门的分布式事务协议。
