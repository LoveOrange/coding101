# MVCC

本文以 MySQL 8.4 的 RC/RR 一致性读为范围。MVCC 让 InnoDB 的普通读取可以访问符合事务快照的历史版本，从而减少读写之间的阻塞。版本链负责保留行的变化，Read View 决定当前事务可以看到哪些版本。

## 1. 面试核心 {#core}

- MVCC 通过事务信息、undo 历史版本与 Read View 判断可见性，写写冲突仍需要锁。[卡](#mvcc-repeatable-read)
- RC 每次一致性读取得新快照；RR 通常复用首次一致性读的快照，单独 `BEGIN` 不代表快照已建立。[卡](#snapshot-timing)
- 当前事务自己的修改可见；其他事务对快照不可见的修改，要沿版本链寻找旧值。[卡](#mvcc-repeatable-read)
- 快照读与锁定读可能读到不同结果；RR 的快照稳定不代表所有后续写操作都基于旧快照。[卡](#snapshot-current-read)
- 长期不结束的快照可能阻碍 purge 清理旧版本；导出分批提交也会改变一致性范围。[卡](#long-snapshot)

## 2. 行版本通过事务信息连接 {#1-行版本通过事务信息连接}

InnoDB 会为聚簇索引记录维护创建或最后修改该版本的事务信息，并通过回滚指针关联 undo log 中的旧版本。关键字段是 `DB_TRX_ID` 和 `DB_ROLL_PTR`；没有合适聚簇键时使用的隐藏行 ID 不是判断版本可见性的依据。更新一行时，新值写入当前记录，旧值可以通过 undo 信息重建。

版本链不是永久历史。没有活跃事务需要旧版本后，purge 才能清理相应 undo 记录。长时间持有快照的事务会延迟清理。

## 3. Read View 描述快照建立时的事务状态 {#2-read-view-描述快照建立时的事务状态}

Read View 会记录创建快照时尚未完成的事务范围。判断一个行版本是否可见时，可以按以下原则理解：

- 当前事务自己的修改可见。
- 快照建立前已经提交的事务版本可见。
- 快照建立时仍活跃的事务版本不可见。
- 建快照时尚未分配事务 ID 的后续写事务，其版本不可见。

若最新版本不可见，InnoDB 沿 undo 版本链查找更早的版本，直到找到可见版本或确认记录不存在。

源码中的 `ReadView::changes_visible` 可以用下面的顺序理解。先单独处理当前事务，再判断其他事务的版本：

| 条件 | 可见性 |
| --- | --- |
| 版本事务 ID 等于创建者 `m_creator_trx_id` | 自己的修改可见 |
| 小于 `m_up_limit_id` | 早于活跃事务下界，可见 |
| 大于等于 `m_low_limit_id` | 超出快照的事务 ID 上界，不可见 |
| 位于两个边界之间 | 在建快照时的活跃读写事务集合 `m_ids` 中则不可见，否则可见 |

例如创建者为 100，其他活跃事务为 101、103，上界为 105，则 99 可见，101 不可见，102 可见，105 不可见。101 后来提交也不会修改这张旧视图。字段命名中的 up/low 容易与数值上下界直觉相反，面试时先说明比较关系和活跃集合，比只背字段名更可靠。

## 4. 读已提交每条语句取得新快照 {#3-读已提交每条语句取得新快照}

在 Read Committed 隔离级别下，同一事务中的每次普通一致性读都会取得新的 Read View。另一事务在两次查询之间提交后，后一次查询可以看到新的结果，因此可能发生不可重复读。

它的优点是更快释放对旧版本的可见需求，并减少部分锁竞争；代价是事务内多次查询不再共享同一个时间点。

## 5. 可重复读复用第一次一致性读的快照 {#4-可重复读复用第一次一致性读的快照}

在 Repeatable Read 下，事务的第一次普通一致性读建立快照，后续一致性读通常继续使用它。因此，其他事务之后提交的新增或修改不会出现在这些快照读中。

```sql
START TRANSACTION;
SELECT * FROM orders WHERE id = 100; -- 在这里建立快照
```

仅执行 `START TRANSACTION` 通常不等于已经创建 Read View。若需要立即建立一致快照，在 RR 下可使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。MySQL 8.4 只在 RR 下支持这项快照语义，其他隔离级别会忽略该子句并产生警告。

同一事务自己的写入仍然可见，所以事务中混合“读取旧快照”和“修改最新状态”时，结果可能不适合用单一时间点直觉解释。业务应避免依靠含混的读写组合维持不变量。

## 6. 快照读和当前读服务不同目的 {#5-快照读和当前读服务不同目的}

RC/RR 下普通 `SELECT` 一般是快照读，从版本链中寻找可见版本。以下操作需要读取当前版本并参与并发控制：

- `SELECT ... FOR SHARE`
- `SELECT ... FOR UPDATE`
- `UPDATE`
- `DELETE`

这些当前读会读取当前可用状态并加锁；若目标被未提交事务持有不兼容锁，需要等待或按 NOWAIT 等选项失败，不能理解为直接读取未提交数据。如果业务要先检查余额再扣减，单纯使用旧快照不能防止并发修改；应使用锁定读、条件更新或其他原子约束。

## 7. 可重复读对幻读的处理分为两条路径 {#6-可重复读对幻读的处理分为两条路径}

对于普通一致性读，同一个 Read View 让后续查询看不到快照建立后提交的新行，因此结果集在快照维度保持稳定。

对于锁定读和写操作，InnoDB 需要面对当前数据。可重复读通常通过 next-key lock 锁住扫描到的记录和索引间隙，阻止其他事务插入会进入该范围的新记录。

因此，讨论“如何避免幻读”时要先区分快照读与当前读。两者使用的机制不同。

## 8. 长快照会增加版本保留成本 {#7-长快照会增加版本保留成本}

只读事务虽然不修改数据，也可能长时间持有旧 Read View。其他事务持续更新时，undo 版本不能及时清理，历史列表增长，并增加读取旧版本和存储的成本。

批处理、导出和管理脚本应设置运行时限，并监控活跃事务年龄与 undo 历史。允许跨批次看到新数据时可以分批提交；要求全量导出来自同一快照时，分批提交会破坏该保证，应控制快照持续时间与负载，或使用专门的备份方案。不要让一个无人关注的会话长期保持事务打开。

## 9. 双会话可见性推演 {#双会话可见性推演}

先创建独立的练习表：

```sql
CREATE TABLE mvcc_demo (id INT PRIMARY KEY, amount INT) ENGINE=InnoDB;
INSERT INTO mvcc_demo VALUES (1, 100);
```

以下步骤按表格从上到下执行，B 使用默认自动提交，A 显式设为 RR：

| 步骤 | 会话 A | 会话 B | A 的读取结果 |
| --- | --- | --- | --- |
| 1 | `SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ; START TRANSACTION;` | — | 尚未创建普通一致性读快照 |
| 2 | — | `UPDATE mvcc_demo SET amount=110 WHERE id=1;` | — |
| 3 | `SELECT amount FROM mvcc_demo WHERE id=1;` | — | 110，首次一致性读建立快照 |
| 4 | — | `UPDATE mvcc_demo SET amount=120 WHERE id=1;` | — |
| 5 | 再执行第 3 步查询 | — | 仍为 110 |
| 6 | `SELECT amount FROM mvcc_demo WHERE id=1 FOR UPDATE;` | — | 120，锁定读访问当前已提交记录 |
| 7 | `COMMIT;` 后再次普通查询 | — | 120，旧事务已结束 |

若 A 改为 RC，第 5 步会读到 120。第 6 步不会把 RR 原有 Read View 更新成新快照；当前读看到新值与后续普通查询仍看旧快照可以同时发生。

再考虑快照建立时一个修改事务尚未提交：即使它稍后提交，RR 仍不会因为它变成“已提交”而把版本纳入旧 Read View。可见性判断依据的是建快照时的事务状态，不能只比较当前是否提交。

## 10. 常见问题 {#8-常见问题}

### 10.1 MVCC 是否完全不需要锁 {#81-mvcc-是否完全不需要锁}

不是。MVCC 主要减少普通读取与写入之间的阻塞。写写冲突、锁定读、唯一约束和外键检查等操作仍需要锁。事务能看到哪个版本与能否修改当前记录是两个问题。

### 10.2 undo log 是否只用于事务回滚 {#82-undo-log-是否只用于事务回滚}

undo 信息既用于回滚未提交修改，也用于构造一致性读需要的历史版本。活跃快照持续时间会影响这些历史版本何时可以被清理。

**考察重点**

- 快照读、当前读和 next-key lock 的边界。

**相关内容**：[行版本通过事务信息连接](#1-行版本通过事务信息连接)、[Read View 描述快照建立时的事务状态](#2-read-view-描述快照建立时的事务状态)、[可重复读复用第一次一致性读的快照](#4-可重复读复用第一次一致性读的快照)。

<details>
<summary>参考回答</summary>

InnoDB 更新行时会保留事务信息，并通过 undo 记录连接旧版本。普通一致性读创建 Read View，根据快照建立时已经提交、仍活跃和后来开始的事务判断版本是否可见；最新版本不可见时，就沿版本链查找更早版本。

Read Committed 通常每条一致性读语句创建新快照，所以能看到其间新提交的数据。Repeatable Read 在第一次一致性读时建立快照，并在后续快照读中复用，因此结果保持在同一可见范围。锁定读和更新需要读取当前版本，并通过记录锁或 next-key lock 控制并发，不能把 MVCC 理解为所有操作都不加锁。

</details>

<details>
<summary>参考回答</summary>

</details>

**考察重点**

- 锁等待、自己的写入和幻读边界。

**相关内容**：[快照读和当前读服务不同目的](#5-快照读和当前读服务不同目的)、[双会话可见性推演](#双会话可见性推演)。

<details>
<summary>参考回答</summary>

普通查询沿旧 Read View 找可见版本，FOR UPDATE 根据当前记录取得锁，可能读到后来已提交的版本；有冲突的未提交写入时仍要等待。锁定读不会刷新原有快照，自己的更新又对自己可见，所以不能把混合读写看成一个固定历史时间点。并发不变量应使用原子更新或明确的锁协议。

</details>

### 11.4 为什么只读事务也可能让 undo 历史持续增长？ {#long-snapshot}

**相关内容**：[长快照会增加版本保留成本](#7-长快照会增加版本保留成本)。

<summary>参考回答</summary>

</details>
