# MVCC

**MVCC**（Multi-Version Concurrency Control，多版本并发控制）是 InnoDB 让读和写互不阻塞的机制：一行数据被修改时，旧版本不会立即消失，正在读的事务可以继续读它该看到的那个版本，不必等写事务提交。

它解释了几个看起来矛盾的现象：为什么另一个事务已经提交了修改，你的查询还是读到旧值；为什么同一个事务里，普通 `SELECT` 和 `SELECT ... FOR UPDATE` 会返回不同的结果；为什么一个什么都没改的只读事务，也能让 undo 空间不断增长。解释这些现象，要先理解旧版本怎样保存成版本链，再看 **Read View** 怎样判断哪个版本可见，并区分读已提交（RC）和可重复读（RR）建立快照的时机。下文以 MySQL 8.0 InnoDB 为准。

## 1. 面试核心 {#core}

- MVCC 用**行上的事务信息、undo 里的历史版本和 Read View** 一起判断可见性；它只解决读写冲突，**写写冲突仍然要靠锁**。[卡](#mvcc-repeatable-read)
- **当前事务自己的修改总是可见**；其他事务的修改对快照不可见时，InnoDB **沿版本链往回找更早的版本**。[卡](#mvcc-repeatable-read)
- RC **每次一致性读都创建新的 Read View**，RR **复用事务里第一次一致性读创建的 Read View**；`START TRANSACTION WITH CONSISTENT SNAPSHOT` 能让 RR 在事务开始时就建立快照。[卡](#snapshot-timing)
- RR 的普通 `SELECT` **读旧快照**，`FOR UPDATE` 和 `UPDATE` **读当前最新的记录**；事务自己改过的行，后续普通 `SELECT` 也能看到。[卡](#snapshot-current-read) [卡](#rr-update-new-row)
- 活跃的 Read View **需要的旧版本不能被 purge 清理**，长时间存活的快照会让 undo 历史持续增长；导出任务分批提交时，每批会换成新快照。[卡](#long-snapshot)

## 2. 行版本与 undo 链 {#1-行版本通过事务信息连接}

要让不同事务读到不同版本，首先得把旧版本留下来。InnoDB 在每条聚簇索引记录上保存两个隐藏字段：`DB_TRX_ID` 记录最后修改这个版本的事务 ID，`DB_ROLL_PTR` 是回滚指针，指向 undo log 里这一行修改前的信息。

更新一行时，新值直接写到当前记录上，旧值的信息写进 undo log。旧版本里也有自己的回滚指针，指向更早的版本，这样一行数据的所有版本就串成了一条**版本链**：最新的版本在记录本身，越往后越旧。

旧版本不会一直保留。后台的 purge 线程会清理已经没有任何活跃事务需要的 undo 记录。只要还有事务的快照可能用到某个旧版本，它就要留着，所以长时间持有快照的事务会延迟清理。

## 3. Read View 与版本可见性 {#2-read-view-描述快照建立时的事务状态}

有了版本链，还需要规则决定一个事务该读哪个版本。**Read View** 就是这套规则所依据的快照：它在创建的那一刻，记录下哪些事务还没有提交。之后判断某个行版本是否可见时，看的是修改这个版本的事务在快照那一刻是什么状态：

- 当前事务自己的修改可见。
- 快照建立前已经提交的事务版本可见。
- 快照建立时仍活跃的事务版本不可见。
- 建快照时尚未分配事务 ID 的后续写事务，其版本不可见。

简单说，快照只认那一刻已经提交的结果，加上自己的修改。如果记录的最新版本不可见，InnoDB 就沿版本链往回找，直到找到一个可见的版本；如果整条链上都没有可见版本，说明这一行对当前快照来说不存在。

源码里这个判断在 `ReadView::changes_visible` 中，先单独处理当前事务自己，再判断其他事务的版本：

| 条件 | 可见性 |
| --- | --- |
| 版本事务 ID 等于创建者 `m_creator_trx_id` | 自己的修改可见 |
| 小于 `m_up_limit_id` | 早于活跃事务下界，可见 |
| 大于等于 `m_low_limit_id` | 超出快照的事务 ID 上界，不可见 |
| 位于两个边界之间 | 在建快照时的活跃读写事务集合 `m_ids` 中则不可见，否则可见 |

举个例子：创建快照的事务是 100，此时其他活跃事务是 101 和 103，下一个将要分配的事务 ID 是 105。那么 99 修改的版本可见，它在快照前就提交了；102 在两个边界之间，但不在活跃集合里，说明快照时已经提交，也可见；101 在活跃集合里，不可见；105 是快照之后才开始的事务，不可见。即使 101 后来提交了，这张已经创建的 Read View 也不会改变，101 的修改对它仍然不可见。

注意字段名的 up/low 和数值大小的直觉正好相反：`m_up_limit_id` 是较小的那个边界，`m_low_limit_id` 是较大的那个。讲解时说清楚比较关系和活跃集合就够了，不必死记字段名。

## 4. RC 的语句级快照 {#3-读已提交每条语句取得新快照}

RC 和 RR 用的是同一套可见性规则，区别只在于 Read View 什么时候创建。

在读已提交下，每次普通的一致性读都会创建一个新的 Read View，同一个事务里的多次读取也是如此。所以另一个事务在两次查询之间提交了修改，后一次查询就能看到新值。同一个事务里两次读同一行结果不同，这就是**不可重复读**。

RC 的好处是每条语句结束后就不再需要旧快照，旧版本能更快被清理，配合 RC 下更少的间隙锁，锁竞争也更少。代价是事务内的多次查询不再基于同一个时间点。

## 5. RR 的事务级快照 {#4-可重复读复用第一次一致性读的快照}

在可重复读下，事务的第一次普通一致性读创建 Read View，之后的一致性读都复用它。因此，其他事务在这之后提交的新增或修改，都不会出现在这个事务的普通查询里，多次读取的结果保持一致。

```sql
START TRANSACTION;
SELECT * FROM orders WHERE id = 100; -- 在这里建立快照
```

注意快照是在第一次读的时候建立的，而不是在 `START TRANSACTION` 执行时。从开启事务到第一次查询之间，别的事务提交的修改，第一次查询仍然能看到。如果需要在事务开始的那一刻就固定快照，在 RR 下可以用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。MySQL 8.0 只在 RR 下支持这项语义，其他隔离级别会忽略这个子句并给出警告。

快照固定之后，事务自己的写入仍然可见。所以一个事务可以一边读旧快照，一边修改最新的数据，查询结果里会同时出现自己写的新版本和其他行的旧版本。具体例子见[混合读写与新行可见性](#混合读写与新行可见性)。

## 6. 快照读与当前读 {#5-快照读和当前读服务不同目的}

RC 和 RR 下，普通 `SELECT` 是**快照读**：按 Read View 从版本链里找可见的版本，不加锁。但修改数据时不能这样做，如果按旧快照的值去更新，就会覆盖掉别人已经提交的修改。所以 `SELECT ... FOR SHARE`、`SELECT ... FOR UPDATE`、`UPDATE` 和 `DELETE` 都是**当前读**：读取记录当前最新的已提交版本，并加锁，和其他写入协调冲突。

当前读遇到别人还没提交的修改时要等待，具体规则见 [InnoDB 锁](./innodb-locking-ranges.mdx#nowait-与-skip-locked)。这对业务逻辑很重要。比如扣余额时先用普通 `SELECT` 查余额是否足够，再 `UPDATE`，查到的可能是旧快照，检查结果已经过期了。要让检查结果在修改时仍然成立，可以用锁定读，或者像 `UPDATE ... WHERE balance >= ?` 这样把检查放进条件更新里。

## 7. 快照可见性与范围锁 {#6-可重复读对幻读的处理分为两条路径}

RR 下防止幻读，靠的是快照读和当前读两条不同的路径。

普通一致性读复用同一个 Read View，可见范围保持稳定，快照建立后别的事务提交的新行，后续快照查询都看不到，所以纯快照读不会出现幻读。

当前读读的是最新数据，快照帮不上忙，要靠锁：锁定读和写操作会锁住扫描到的记录和间隙，阻止别的事务往这个范围里插入新行。具体机制见 [InnoDB 锁](./innodb-locking-ranges.mdx#3-next-key-lock-同时保护记录和前方间隙)。

## 8. 长快照与版本保留 {#7-长快照会增加版本保留成本}

MVCC 的代价是要保留旧版本。只读事务也能长时间持有一个旧的 Read View，在它结束之前，别的事务持续更新产生的 undo 历史，只要这个视图可能用到，purge 就不能清理。结果是 undo 占用的空间越来越大，版本链越来越长，读旧版本的查询也越来越慢。

所以批处理、导出和管理脚本要设置运行时限，同时监控活跃事务的持续时间和 undo 历史的长度。导出数据时要先想清楚一致性要求：如果允许不同批次看到不同时间点的数据，就分批提交，每批用新的快照；如果全量导出必须来自同一个快照，就不能分批提交，这时要控制快照的持续时间和负载，或者改用专门的备份工具。最常见的问题是一个没人管的会话开着事务一直不关，这种情况要避免。

## 9. 双会话可见性推演 {#双会话可见性推演}

下面用两个会话把快照的建立时机和当前读亲手验证一遍。先创建独立的练习表：

```sql
CREATE TABLE mvcc_demo (id INT PRIMARY KEY, amount INT) ENGINE=InnoDB;
INSERT INTO mvcc_demo VALUES (1, 100);
```

以下步骤按表格从上到下执行，B 使用默认自动提交，A 显式设为 RR：

| 步骤 | 会话 A | 会话 B | A 的读取结果 |
| --- | --- | --- | --- |
| 1 | `SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ; START TRANSACTION;` | — | 尚未创建普通一致性读快照 |
| 2 | — | `UPDATE mvcc_demo SET amount=110 WHERE id=1;` | — |
| 3 | `SELECT amount FROM mvcc_demo WHERE id=1;` | — | 110，首次一致性读建立快照 |
| 4 | — | `UPDATE mvcc_demo SET amount=120 WHERE id=1;` | — |
| 5 | 再执行第 3 步查询 | — | 仍为 110 |
| 6 | `SELECT amount FROM mvcc_demo WHERE id=1 FOR UPDATE;` | — | 120，锁定读访问当前已提交记录 |
| 7 | `COMMIT;` 后再次普通查询 | — | 120，旧事务已结束 |

第 3 步能读到 110，是因为 `START TRANSACTION` 并没有建立快照，第一次查询时才建立，那时 B 的修改已经提交了。第 5 步仍然是 110，因为 A 复用了第 3 步的快照，B 在第 4 步的修改对它不可见。第 6 步是当前读，直接读最新的已提交记录，所以是 120。

如果 A 改用 RC，第 5 步就会读到 120，因为每次查询都新建快照。另外，第 6 步的当前读不会把 RR 原来的 Read View 刷新成新快照，如果在第 6 步之后、提交之前再做一次普通查询，读到的仍然是 110。

再考虑另一种情况：快照建立时，有一个修改事务还没提交。即使它稍后提交了，RR 也不会把它的版本纳入已经创建的 Read View，因为可见性依据的是建快照那一刻的事务状态。

### 9.1 混合读写与新行可见性 {#混合读写与新行可见性}

快照读和当前读混在一起时，会出现一个乍看违反「可重复读」的现象：RR 事务的快照里看不到的新行，它可以更新；更新之后，这一行就出现在它的普通查询里了。继续使用前面的 `mvcc_demo`，先确保表中只有 `(1, 100)`，两个会话都结束了上一轮事务，B 使用自动提交：

| 步骤 | 会话 A（RR） | 会话 B | A 的结果 |
| --- | --- | --- | --- |
| 1 | `START TRANSACTION; SELECT * FROM mvcc_demo WHERE id >= 2;` | — | 空，建立快照 |
| 2 | — | `INSERT INTO mvcc_demo VALUES (2, 200);` | B 提交新行 |
| 3 | `SELECT * FROM mvcc_demo WHERE id >= 2;` | — | 仍为空 |
| 4 | `UPDATE mvcc_demo SET amount=amount+1 WHERE id=2;` | — | 影响 1 行 |
| 5 | `SELECT * FROM mvcc_demo WHERE id >= 2;` | — | 返回 `(2, 201)` |
| 6 | `ROLLBACK;` | — | 撤销 A 的更新，B 插入的行仍保留 |

第 3 步看不到 B 插入的行，符合快照的规则。第 4 步的 `UPDATE` 是当前读，读的是最新数据，所以能找到 B 已经提交的 `id=2`，并把它改成了 A 自己的版本 201。第 5 步的普通查询仍然用原来的 Read View，但这一行的最新版本是 A 自己写的，适用「自己的修改可见」，于是返回 `(2, 201)`。

整个过程中 Read View 并没有变。这一行出现，是因为 A 自己写了它。混合使用快照读和当前读时，这种现象也被称为幻读；如果事务只做快照读、自己不写，可见范围就一直不变。

## 10. 常见问题 {#8-常见问题}

### 10.1 MVCC 与锁的分工 {#81-mvcc-是否完全不需要锁}

不是。MVCC 解决的是普通读取和写入之间的阻塞，写写冲突、锁定读、唯一约束检查和外键检查仍然需要锁。可以把它们看成两个问题：事务能看到哪个版本，由 MVCC 决定；能不能修改当前记录，由锁决定。

### 10.2 undo log 的用途 {#82-undo-log-是否只用于事务回滚}

不是。undo 信息有两个用途：一是事务回滚时，用它撤销未提交的修改；二是一致性读时，用它构造快照需要的历史版本。第二个用途决定了，即使事务早已提交，它的 undo 记录也要保留到没有活跃快照需要为止，所以快照的持续时间会影响这些历史版本何时能被清理。

<details>
<summary>参考回答</summary>

**InnoDB 用 undo 版本链保存历史值，用 Read View 判断哪些版本可见；RR 事务内复用 Read View，实现可重复读。**

一致性读按快照建立时的事务状态判断可见性，最新版本不可见时，沿 undo 链寻找更早版本。RC 每次一致性读创建新快照，RR 则复用首次一致性读的快照，因此后者保持相同的外部版本可见范围。

本事务自己的修改仍可见。锁定读和更新使用当前记录，写入冲突由[索引锁](./innodb-locking-ranges.mdx)控制，不按旧快照直接决定修改结果。

</details>

### 11.2 执行 BEGIN 后，另一个事务提交的修改还能被第一次查询看到吗？ {#snapshot-timing}

**考察重点**

- 理解 RR 快照建立时间。
- 理解 RC 与 WITH CONSISTENT SNAPSHOT 的区别。

**相关内容**：[RR 的事务级快照](#4-可重复读复用第一次一致性读的快照)、[双会话可见性推演](#双会话可见性推演)。

<details>
<summary>参考回答</summary>

**可以。RR 下，普通的显式事务不是在 `BEGIN` 时建立快照，而是在第一次一致性读时才创建 Read View。**

所以 `BEGIN` 之后、第一次查询之前别的事务提交的修改，第一次查询能看到；之后再提交的修改，同一事务里的普通查询就看不到了。如果用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`，RR 会在事务开始时就建立快照，这时第一次查询也看不到。RC 则每次一致性读都获取新快照，每次都能看到最新提交的值。

</details>

### 11.3 同一个 RR 事务里，普通 SELECT 与 FOR UPDATE 为什么可能返回不同值？ {#snapshot-current-read}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 理解快照可见性与当前读。
- 理解锁等待、自己的写入和幻读边界。

**相关内容**：[快照读与当前读](#5-快照读和当前读服务不同目的)、[双会话可见性推演](#双会话可见性推演)。

<details>
<summary>参考回答</summary>

**普通 `SELECT` 是快照读，按事务第一次读时建立的 Read View 取版本；`FOR UPDATE` 是当前读，读取记录最新的已提交版本并加锁。**

快照之后别的事务提交的修改，普通 `SELECT` 看不到，`FOR UPDATE` 能看到，两者就会不同。如果有未提交的冲突写入，`FOR UPDATE` 还要等待。锁定读不会刷新原来的快照，而自己的更新又对自己可见，所以混合读写时，结果里会同时有自己写的新版本和其他行的旧版本。需要保证并发不变量时，应该用原子的条件更新或明确的加锁协议，不能依赖普通 `SELECT` 的检查结果。

</details>

### 11.4 为什么只读事务也可能让 undo 历史持续增长？ {#long-snapshot}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 理解旧版本保留条件。
- 理解导出一致性与分批提交的取舍。

**相关内容**：[长快照与版本保留](#7-长快照会增加版本保留成本)。

<details>
<summary>参考回答</summary>

**只读事务也持有 Read View，只要它还活着，它可能需要的旧版本就不能被 purge 清理。**

这期间其他事务持续更新，产生的 undo 历史就会不断累积。缩短快照的持续时间、控制导出负载，都能降低保留成本。导出任务改成分批提交，每批会用新的快照，旧版本就能及时清理，但前提是业务能接受不同批次看到不同时间点的数据。

</details>

### 11.5 RR 事务更新另一事务新插入的行后，为什么普通 SELECT 能看到它？ {#rr-update-new-row}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：当前读、自身写入可见性与 Read View 的稳定性。

**相关内容**：[混合读写与新行可见性](#混合读写与新行可见性)。

<details>
<summary>参考回答</summary>

**因为 `UPDATE` 是当前读，能找到另一事务已提交的新行并修改它；修改之后，这一行的最新版本是本事务自己写的，而自己的修改总是可见。**

以正文的 `id=2` 为例：旧快照里没有这一行，普通 `SELECT` 先返回空。`UPDATE` 读取最新数据，把 B 插入的 200 改成 201，之后普通 `SELECT` 返回 201。整个过程中原来的 Read View 没有变化，这一行之所以可见，是因为它来自本事务自己的写入。

</details>
