# InnoDB 锁

InnoDB 通过索引记录锁和索引区间锁约束并发写入。本文讲解 MySQL 8.0 的锁类型、扫描范围和双会话验证。

## 1. 面试核心 {#core}

- **行级锁类型。** record lock 锁定索引记录，gap lock 阻止间隙插入。next-key lock 组合记录与前方间隙。[卡](#row-lock-ranges)
- **唯一等值查找。** RR 下，完整唯一键等值锁定读命中已有记录时只加记录锁。未命中时，它锁住目标键所在间隙。[卡](#unique-missing)
- **非唯一与范围查找。** RR 下，非唯一索引等值锁定读保护匹配记录及相邻间隙。范围锁定读按索引扫描路径加锁。[卡](#secondary-range-locks)
- **RC 的间隙锁边界。** RC 的普通搜索和索引扫描使用记录锁。外键与重复键检查仍可使用间隙锁。
- **失败与重试。** `innodb_rollback_on_timeout=OFF` 时，锁超时回滚当前语句。死锁检测选中的受害事务整体回滚。[卡](#deadlock-timeout)

## 2. 记录锁 {#1-记录锁锁住索引记录}

记录锁作用于索引记录。事务通过二级索引更新一行时，会锁住访问到的二级索引记录。它还会锁住对应的聚簇索引记录。

```sql
UPDATE orders SET status = 'PAID' WHERE id = 100;
```

如果 `id` 是唯一主键，查询又精确命中一行，就只对该索引记录加锁。

## 3. 间隙锁 {#2-间隙锁阻止区间内插入}

间隙锁作用于相邻索引记录之间的开区间。它阻止其他事务在该区间插入新索引记录。

例如索引中已有 10 和 20，查询锁住 `(10, 20)` 的间隙。此时，其他事务插入 15 会等待。10 和 20 的更新是否等待，由端点记录上的锁决定。

不同事务的 gap lock 可以共存于同一间隙，它们共同抑制插入；gap lock 的 S/X 标记在兼容性上没有区别。

## 4. Next-key lock {#3-next-key-lock-同时保护记录和前方间隙}

Next-key lock 是记录锁与该记录前方间隙锁的组合。在可重复读下，范围锁定读或更新常用 next-key lock。它覆盖扫描区间，防止其他事务在该范围插入新记录。

假设索引值为 10、20、30。next-key 锁按 `(-∞, 10]`、`(10, 20]`、`(20, 30]` 等区间组织。真实边界仍取决于查询条件与优化器选择的访问路径。

完整唯一索引的等值查找，若命中已有记录且确认唯一，只需记录锁。联合唯一索引的部分键查询按非唯一范围处理；唯一等值查询未命中时，RR 锁住目标值所在间隙以阻止插入。

## 5. 插入意向锁 {#4-插入意向锁协调同一间隙中的插入}

事务准备向某个间隙插入时，会先取得插入意向锁。多个事务可以并发插入同一间隙中的不同位置。若其他事务持有目标位置或间隙的不兼容锁，插入就需要等待。

插入意向锁属于间隙锁的一种，用来表达具体插入位置。

## 6. 意向锁 {#5-意向锁协调表锁与行锁}

InnoDB 在取得行级共享锁前，会在表级取得意向共享锁。取得行级排他锁前，则会在表级取得意向排他锁。表锁请求通过意向锁，能快速判断是否存在不兼容的行锁。因此，它可以省去遍历所有记录锁的步骤。

行记录上，S 与 S 兼容，S 与 X、X 与 X 不兼容；表级 IS/IX 表示已有或计划取得的行锁，它们彼此兼容。分析业务锁等待时，主要仍要找到实际的记录锁、间隙锁和持有事务。

## 7. 隔离级别与间隙锁 {#6-隔离级别影响间隙保护}

在可重复读下，范围更新、删除和锁定读会锁扫描到的记录。它们使用 next-key lock 或边界 gap lock，也保护相应间隙。普通一致性读的可见版本由 [MVCC](./mvcc-read-view-consistent-read.mdx) 决定。

在读已提交下，普通搜索和索引扫描只锁匹配的索引记录；外键约束检查和重复键检查仍可使用间隙锁。减少间隙锁能提高并发。同一事务的两次查询也可以看到新提交的记录。

## 8. 扫描路径与锁范围 {#7-扫描路径决定实际加锁范围}

```sql
SELECT *
FROM orders
WHERE tenant_id = 10 AND created_at >= '2026-08-01'
FOR UPDATE;
```

若存在 `(tenant_id, created_at)` 索引，InnoDB 可以锁住对应的连续索引范围。缺少合适索引时，执行计划可能采用全表扫描。锁范围也随扫描范围扩大，实际影响会远大于最终返回的行数。

过宽的访问路径会取得大量索引记录锁。为锁定读设计索引时，需要同时考虑查询性能和锁范围。

## 9. 锁等待的诊断证据 {#8-用数据库证据查看锁等待}

排查锁等待时可以组合使用：

- 使用 `performance_schema.data_locks` 查看当前持有或等待的锁。
- 使用 `performance_schema.data_lock_waits` 查看阻塞关系。
- 使用 `SHOW ENGINE INNODB STATUS` 查看最近死锁和事务信息。
- 通过执行计划确认所用索引与预计扫描记录数。

先找到等待事务、阻塞事务和锁定索引。再检查对应的 SQL 与事务边界。在阻塞尚未解除时增加锁等待超时，会延长连接占用。

## 10. 唯一键命中与未命中的双会话实验 {#唯一键命中与未命中的双会话实验}

在独立练习库初始化：

```sql
CREATE TABLE lock_demo (id INT PRIMARY KEY, value INT) ENGINE=InnoDB;
INSERT INTO lock_demo VALUES (10, 1), (20, 1);
```

会话 A 先执行：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM lock_demo WHERE id = 15 FOR UPDATE;
```

查询结果为空。在该数据布局下，15 位于 `(10, 20)` 间隙。会话 B 执行 `INSERT INTO lock_demo VALUES (15, 1)` 会等待 A 结束事务；A `COMMIT` 后 B 才能继续。若 A 改查已有主键 10，则保护的是 10 的记录，B 仍可插入 15。

每轮实验结束后提交或回滚两个会话，再恢复表数据。用 `data_locks` 与 `data_lock_waits` 对照锁模式和索引；换成二级索引、非唯一条件或 RC 时，结论要重新核对。

### 10.1 二级索引等值与范围锁实验 {#二级索引等值与范围锁实验}

以下实验适用于 MySQL 8.0 及以上。会话 A 使用 RR、升序扫描和 `FOR UPDATE`。它通过 `FORCE INDEX` 固定访问路径。每条查询单独开启事务。观察完成后执行 `ROLLBACK`，再进行下一条。

```sql
CREATE TABLE range_demo (
  id INT PRIMARY KEY,
  u INT NOT NULL,
  k INT NOT NULL,
  value INT,
  UNIQUE KEY uk (u),
  KEY nk (k)
) ENGINE=InnoDB;
INSERT INTO range_demo VALUES
  (5,5,5,0), (10,10,10,0), (15,15,15,0), (20,20,20,0);

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM range_demo FORCE INDEX (nk) WHERE k=10 FOR UPDATE;
-- 保持事务打开，在另一会话查询 data_locks。
-- 观察结束后 ROLLBACK，再分别执行下表其他查询。
```

下表按索引列值表示区间。本例每个值只有一条记录。`uk` 与 `nk` 都是二级索引，叶子中的定位键还包含主键 `id`。

| 查询（省略相同 SELECT 前缀） | 访问索引上的锁 | 聚簇索引上的锁 |
| --- | --- | --- |
| `FORCE INDEX (nk) WHERE k=10 FOR UPDATE` | 10 上的 next-key `(5,10]`，15 前的 gap `(10,15)` | 主键 10 的记录锁 |
| `FORCE INDEX (uk) WHERE u>5 AND u<15 FOR UPDATE` | 10、15 上的 next-key，即 `(5,10]`、`(10,15]` | 主键 10 的记录锁 |
| `FORCE INDEX (nk) WHERE k>5 AND k<15 FOR UPDATE` | 10、15 上的 next-key，即 `(5,10]`、`(10,15]` | 主键 10 的记录锁 |
| `FORCE INDEX (PRIMARY) WHERE id>5 AND id<15 FOR UPDATE` | 10 上的 next-key `(5,10]`，15 前的 gap `(10,15)` | 同一棵主键索引，无额外二级索引锁 |

非唯一等值查找必须继续确认等值组的结束位置。因此，它会保护末个匹配项之后的间隙。若 `k=10` 有多条记录，锁范围应按 `(k,id)` 的完整顺序推导。范围包括所有匹配记录和组内间隙。两侧扫描到的间隙也需要计入。

唯一索引只有完整唯一键等值命中才适用记录锁优化；范围查询仍需间隙保护。本例中，15 不在二级索引范围查询的返回结果中。但扫描仍在 15 上保留 next-key 锁。主键范围扫描能在该上界只保留 gap lock。实际锁会受上界是否命中、扫描方向、索引类型和执行计划影响。任一条件改变时，都应重新观察锁。

### 10.2 data_locks 与阻塞验证 {#data_locks-与阻塞验证}

在会话 B 查询锁，`DATABASE()` 要与实验表所在数据库一致：

```sql
SELECT INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA, LOCK_STATUS
FROM performance_schema.data_locks
WHERE OBJECT_SCHEMA = DATABASE() AND OBJECT_NAME = 'range_demo'
ORDER BY INDEX_NAME, LOCK_DATA;
```

- `LOCK_TYPE=TABLE`、`LOCK_MODE=IX` 是表级意向锁。
- 对本例的 `RECORD` 锁，`X,REC_NOT_GAP` 表示纯记录锁。`X,GAP` 表示 `LOCK_DATA` 所列记录前的间隙。`X` 表示 next-key 锁。
- 非唯一等值查询显示三项锁：`nk / X / 10, 10`、`nk / X,GAP / 15, 15`、`PRIMARY / X,REC_NOT_GAP / 10`。它们分别对应上表三处保护。

保持 A 的事务打开。B 执行 `SET SESSION innodb_lock_wait_timeout=1; START TRANSACTION; INSERT INTO range_demo VALUES (12,12,12,0);`。由于 `(10,15)` 受保护，B 应超时，随后执行 `ROLLBACK`。另起一轮，B 执行 `SELECT * FROM range_demo FORCE INDEX (nk) WHERE k=15 FOR UPDATE`。A 持有非唯一等值查询的锁时，B 可以锁定 15。A 持有非唯一范围查询的锁时，B 等待。验证唯一二级索引范围时，B 改用 `FORCE INDEX (uk) WHERE u=15`。观察活动等待可在第三个会话查询 `performance_schema.data_lock_waits`。

每轮最后回滚 A 与 B；用 `EXPLAIN` 确认访问索引。再对照锁模式、完整索引键和冲突操作，结合三项验证区间。

## 11. 死锁、超时与重试 {#死锁超时与重试}

两个事务按相反顺序占有并请求记录锁，会形成循环等待。例如 A 先锁 10 再等 20，B 先锁 20 再等 10。普通等待可随持锁方释放而结束；死锁需要打破等待环。InnoDB 默认启用死锁检测，选择受害事务回滚；`innodb_deadlock_detect=OFF` 时依赖 `innodb_lock_wait_timeout` 超时处理。

死锁检测会回滚整个受害事务；`innodb_rollback_on_timeout=OFF` 时，锁等待超时只回滚当前语句。`ON` 时，超时会回滚整个事务。完整失败语义见 [数据库事务](./index.mdx#自动提交与失败边界)。需要共同成立的业务操作应结束失败事务后整体重试。

统一访问顺序、缩短事务可以减少循环等待。为过滤条件建合适索引也有同样作用。有界退避重试应放在新事务中，并以幂等标识约束副作用。

## 12. NOWAIT 与 SKIP LOCKED {#nowait-与-skip-locked}

`FOR UPDATE NOWAIT` 遇到需要等待的行锁时直接报错；`FOR UPDATE SKIP LOCKED` 从结果中跳过被锁定的行。它们分别提供立即失败和跳过忙碌记录的处理方式。

多个消费者抢取任务时，可以用 SKIP LOCKED 跳过忙碌记录。选取与状态更新要在同一事务中完成。提交后再处理耗时任务，并另行设计失败重试与租约。SKIP LOCKED 返回的集合会跳过被锁行。因此，使用它的任务领取等场景需要允许结果不完整。

这些选项作用于行级锁等待，元数据锁等其他等待仍需单独处理。

## 13. 常见问题 {#9-常见问题}

### 13.1 普通 SELECT 与行锁 {#91-普通-select-会加行锁吗}

在 RC/RR 下，InnoDB 的普通一致性读通过 [MVCC](./mvcc-read-view-consistent-read.mdx) 读取可见版本；SERIALIZABLE 且 `autocommit=0` 时，普通 SELECT 隐式转为共享锁定读。`SELECT ... FOR SHARE`、`SELECT ... FOR UPDATE` 属于锁定读。它们与更新、删除操作都会根据访问范围加锁。

### 13.2 行锁的粒度与数量 {#92-行锁是否一定只影响一行}

“行锁”描述粒度，一条语句取得的锁数量由扫描范围决定。范围查询、非唯一条件或全表扫描会锁住多个索引记录与间隙。

### 14.5 非唯一等值、唯一范围与非唯一范围查询分别锁哪些区间？ {#secondary-range-locks}

<details>
<summary>参考回答</summary>

**RR 下，非唯一等值查找保护匹配记录及相邻间隙；唯一与非唯一范围查找都需要间隙保护，具体边界取决于扫描路径。**

- `k=10` 保护 `(5,10]` 和 `(10,15)`。
- `u>5 AND u<15` 与 `k>5 AND k<15` 保护 `(5,10]`、`(10,15]`。
- 这些查询还给返回行的主键 10 加记录锁；改为主键范围扫描时，上界 15 在该实验中只保留 gap lock。

完整唯一键等值命中才适用单记录优化。数据分布、扫描方向或索引改变后，应结合执行计划与 `data_locks` 重新核对。

</details>
