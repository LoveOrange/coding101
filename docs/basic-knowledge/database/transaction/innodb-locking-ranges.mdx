# InnoDB 锁

InnoDB 的行锁加在**索引**上，而不是直接加在「行」上：它锁住的是索引记录，或者两条索引记录之间的区间。所以一条 SQL 会锁住什么，取决于它用哪个索引、沿索引扫描了哪一段，而不只取决于最终返回了几行。

这一点决定了你能不能解释线上的锁等待：为什么一条只更新一行的语句挡住了别人的插入，为什么没有索引的更新会让整张表的写入排队。要讲清楚，抓住三点：几种锁各自保护什么，隔离级别和索引类型怎样改变加锁范围，以及怎样用 `performance_schema.data_locks` 验证推断。下文以 MySQL 8.0 为准，未特别说明时隔离级别是默认的可重复读（RR）。

## 1. 面试核心 {#core}

- 记录锁（record lock）**锁住一条索引记录**，间隙锁（gap lock）**阻止在两条记录之间插入**，next-key lock 是**记录锁加上它前面的间隙**。[卡](#row-lock-ranges)
- RR 下，用完整唯一键做等值锁定读，**命中已有记录时只加记录锁，没命中时锁住目标值所在的间隙**。[卡](#unique-missing)
- RR 下，非唯一索引的等值锁定读**保护匹配记录及其相邻间隙**，范围锁定读**按索引扫描路径加锁**。[卡](#secondary-range-locks)
- 读已提交（RC）下，普通的搜索和索引扫描**只加记录锁**，但外键检查和重复键检查仍会用间隙锁。
- 死锁检测选中的受害事务**整体回滚**；`innodb_rollback_on_timeout=OFF` 时，锁等待超时**只回滚当前语句**。[卡](#deadlock-timeout)

## 2. 记录锁 {#1-记录锁锁住索引记录}

**记录锁**锁住一条索引记录，其他事务不能再对这条记录加冲突的锁，比如同时修改它。因为锁在索引上，事务通过二级索引更新一行时，既会锁住访问到的二级索引记录，也会锁住对应的聚簇索引记录，也就是主键索引上的那一行。

```sql
UPDATE orders SET status = 'PAID' WHERE id = 100;
```

`id` 是主键，条件精确命中一行时，这条语句只对主键索引上 `id = 100` 这条记录加记录锁，是加锁范围最小的情况。

## 3. 间隙锁 {#2-间隙锁阻止区间内插入}

只锁记录有一个漏洞：锁不住还不存在的行。事务按范围查询并加锁后，别的事务仍然可以往这个范围里插入新行，再查一次就会多出来，这就是**幻读**。**间隙锁**就是为此设计的，它锁住两条相邻索引记录之间的开区间，阻止其他事务往这个区间插入新记录。

例如索引中已有 10 和 20，某个查询锁住了 `(10, 20)` 这个间隙。这时其他事务插入 15 会等待。间隙锁不包含两端的记录本身，10 和 20 能不能被更新，要看这两条记录上有没有记录锁。

间隙锁的唯一作用是阻止插入，所以它们之间不冲突：不同事务可以同时持有同一个间隙上的间隙锁，共同挡住插入。间隙锁也有共享（S）和排他（X）之分，但这个标记不影响兼容性。

## 4. Next-key lock {#3-next-key-lock-同时保护记录和前方间隙}

**Next-key lock** 是一条记录的记录锁，加上这条记录前面那个间隙的间隙锁。可重复读下，范围锁定读和范围更新默认使用 next-key lock：扫描经过的每条记录连同它前面的间隙一起锁住，整个扫描区间既不能被修改，也不能被插入。

假设索引值为 10、20、30，next-key lock 对应的区间就是 `(-∞, 10]`、`(10, 20]`、`(20, 30]`，以及最后一条记录之后的 `(30, +∞)`。左开右闭，每段包含右端的那条记录。一条查询实际锁住哪几段，取决于查询条件和优化器选择的访问路径。

有两种情况可以缩小范围。一是用完整的唯一索引做等值查找并且命中：唯一性保证了不会再插入一条相同的值，所以只需要记录锁，前面的间隙不必锁。二是唯一等值查找没有命中：这时没有记录可锁，RR 只锁住目标值所在的间隙，阻止别人把它插进来。注意「完整」二字，联合唯一索引只给出部分列时，不能保证唯一，按非唯一的范围查找处理。

## 5. 插入意向锁 {#4-插入意向锁协调同一间隙中的插入}

**插入意向锁**是插入之前要取得的一种特殊间隙锁，表示「我要往这个间隙的某个位置插入」。插入意向锁之间互不冲突，所以多个事务可以同时往同一个间隙的不同位置插入，比如一个插 12、一个插 15，互不等待。但如果别的事务已经在这个间隙上持有间隙锁或 next-key lock，插入意向锁就要等待，前面「插入 15 会等待」说的正是这一步。

## 6. 意向锁 {#5-意向锁协调表锁与行锁}

**意向锁**是表级的锁，用来告诉别人「这张表里有行被锁了」。InnoDB 在给某行加共享锁（S）之前，先在表上加意向共享锁（IS）；给某行加排他锁（X）之前，先在表上加意向排他锁（IX）。

它解决的是表锁和行锁之间的协调问题。有人要给整张表加锁时，如果没有意向锁，就得遍历所有记录，检查有没有冲突的行锁；有了意向锁，看一眼表上的 IS/IX 就知道了。

行锁之间，S 和 S 兼容，S 和 X、X 和 X 都不兼容。意向锁只是声明，IS 和 IX 彼此兼容，不同事务锁不同的行不会因为意向锁而互相等待。所以分析业务里的锁等待时，意向锁通常不是原因，要找的还是实际的记录锁、间隙锁和持有它们的事务。

## 7. 隔离级别与间隙锁 {#6-隔离级别影响间隙保护}

间隙锁是为了防止幻读，所以要不要用它，取决于隔离级别是否要求防止幻读。

可重复读下，范围更新、删除和锁定读会锁住扫描到的记录，并通过 next-key lock 或边界上的间隙锁保护相应的间隙。不加锁的普通 `SELECT` 不走这套机制，它读到哪个版本由 [MVCC](./mvcc-read-view-consistent-read.mdx) 决定。

读已提交下，普通的搜索和索引扫描只锁匹配的索引记录，不锁间隙；只有外键约束检查和重复键检查仍会用间隙锁。少了间隙锁，插入被挡住的情况大大减少，并发更高；代价是同一事务里两次查询之间，别的事务可以插入并提交新记录，后一次查询会看到它们。

## 8. 扫描路径与锁范围 {#7-扫描路径决定实际加锁范围}

```sql
SELECT *
FROM orders
WHERE tenant_id = 10 AND created_at >= '2026-08-01'
FOR UPDATE;
```

锁是沿着扫描路径加的，扫到哪里锁到哪里。有 `(tenant_id, created_at)` 索引时，InnoDB 只扫描并锁住这段连续的索引范围。缺少合适的索引时，执行计划可能退化成全表扫描，InnoDB 会锁住扫描到的每一条记录和间隙，影响范围远大于最终返回的行数，其他事务对这张表的更新和插入都可能被挡住。

所以给锁定读和更新语句设计索引时，不只是为了查询快，也是为了把锁的范围收窄。

## 9. 锁等待的诊断证据 {#8-用数据库证据查看锁等待}

排查锁等待时可以组合使用：

- 使用 `performance_schema.data_locks` 查看当前持有或等待的锁。
- 使用 `performance_schema.data_lock_waits` 查看阻塞关系。
- 使用 `SHOW ENGINE INNODB STATUS` 查看最近死锁和事务信息。
- 通过执行计划确认所用索引与预计扫描记录数。

排查的顺序是先找到谁在等、被谁挡住、锁在哪个索引的哪条记录上，再回到代码检查对应的 SQL 和事务边界，比如持锁的事务是不是迟迟没有提交。阻塞的根因没解决之前，调大锁等待超时只会让请求等得更久、占着连接更久。

## 10. 唯一键命中与未命中的双会话实验 {#唯一键命中与未命中的双会话实验}

前面的规则可以用两个会话亲手验证。先看最简单的唯一主键。在独立练习库初始化：

```sql
CREATE TABLE lock_demo (id INT PRIMARY KEY, value INT) ENGINE=InnoDB;
INSERT INTO lock_demo VALUES (10, 1), (20, 1);
```

会话 A 先执行：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM lock_demo WHERE id = 15 FOR UPDATE;
```

查询结果为空，因为表里没有 15。但 A 并非什么都没锁：15 落在 10 和 20 之间，RR 下 A 锁住了 `(10, 20)` 这个间隙。这时会话 B 执行 `INSERT INTO lock_demo VALUES (15, 1)` 会一直等待，直到 A `COMMIT` 之后 B 才能继续。

换一种做法，让 A 查询已有的主键 10。这是唯一键等值命中，A 只锁住 10 这条记录，B 插入 15 不受影响。

每轮实验结束后，提交或回滚两个会话，再恢复表数据。观察时用 `data_locks` 和 `data_lock_waits` 对照锁模式和索引。这里的结论只针对唯一主键和 RR，换成二级索引、非唯一条件或 RC 时要重新核对，下一节就是二级索引的情况。

### 10.1 二级索引等值与范围锁实验 {#二级索引等值与范围锁实验}

二级索引和范围查询的加锁范围更复杂，最好用实验对照。以下实验适用于 MySQL 8.0 及以上：会话 A 使用 RR、升序扫描和 `FOR UPDATE`，用 `FORCE INDEX` 固定访问路径，避免优化器换索引干扰结论。每条查询单独开一个事务，观察完执行 `ROLLBACK`，再做下一条。

```sql
CREATE TABLE range_demo (
  id INT PRIMARY KEY,
  u INT NOT NULL,
  k INT NOT NULL,
  value INT,
  UNIQUE KEY uk (u),
  KEY nk (k)
) ENGINE=InnoDB;
INSERT INTO range_demo VALUES
  (5,5,5,0), (10,10,10,0), (15,15,15,0), (20,20,20,0);

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM range_demo FORCE INDEX (nk) WHERE k=10 FOR UPDATE;
-- 保持事务打开，在另一会话查询 data_locks。
-- 观察结束后 ROLLBACK，再分别执行下表其他查询。
```

下表中的区间按索引列的值表示。本例每个值只有一条记录，并且 `u`、`k`、`id` 的值相同，便于对照。`uk` 和 `nk` 都是二级索引，叶子记录里除了索引列，还带着主键 `id`。

| 查询（省略相同 SELECT 前缀） | 访问索引上的锁 | 聚簇索引上的锁 |
| --- | --- | --- |
| `FORCE INDEX (nk) WHERE k=10 FOR UPDATE` | 10 上的 next-key `(5,10]`，15 前的 gap `(10,15)` | 主键 10 的记录锁 |
| `FORCE INDEX (uk) WHERE u>5 AND u<15 FOR UPDATE` | 10、15 上的 next-key，即 `(5,10]`、`(10,15]` | 主键 10 的记录锁 |
| `FORCE INDEX (nk) WHERE k>5 AND k<15 FOR UPDATE` | 10、15 上的 next-key，即 `(5,10]`、`(10,15]` | 主键 10 的记录锁 |
| `FORCE INDEX (PRIMARY) WHERE id>5 AND id<15 FOR UPDATE` | 10 上的 next-key `(5,10]`，15 前的 gap `(10,15)` | 同一棵主键索引，无额外二级索引锁 |

先看第一行。`nk` 不是唯一索引，找到 `k=10` 之后，InnoDB 不知道后面还有没有另一条 `k=10`，必须继续往后读，读到 15 才确认等值组结束了。所以它除了锁住 10 本身和前面的间隙 `(5,10]`，还要锁住 10 和 15 之间的间隙 `(10,15)`，否则别人可以再插入一条 `k=10`。15 这条记录本身不匹配，不加记录锁。如果 `k=10` 有多条记录，要按 `(k, id)` 的完整顺序推导：所有匹配记录、它们之间的间隙，以及两侧扫描到的间隙都要算进去。

再看范围查询。唯一索引只有在完整唯一键等值命中时才能只加记录锁，范围查询仍然要保护间隙，所以 `uk` 和 `nk` 的范围查询结果相同。本例中，15 并不在返回结果里，但二级索引的范围扫描读到 15 才知道该停，并在 15 上留下了 next-key lock；主键范围扫描在同样的上界只留下间隙锁。

这些结论和实验条件绑定：上界是否命中、扫描方向、索引类型和执行计划，任何一个改变，锁的范围都可能不同，都应该重新观察。

### 10.2 data_locks 与阻塞验证 {#data_locks-与阻塞验证}

在会话 B 查询锁，`DATABASE()` 要与实验表所在数据库一致：

```sql
SELECT INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA, LOCK_STATUS
FROM performance_schema.data_locks
WHERE OBJECT_SCHEMA = DATABASE() AND OBJECT_NAME = 'range_demo'
ORDER BY INDEX_NAME, LOCK_DATA;
```

- `LOCK_TYPE=TABLE`、`LOCK_MODE=IX` 是表级意向锁。
- 对本例的 `RECORD` 锁，`X,REC_NOT_GAP` 表示纯记录锁。`X,GAP` 表示 `LOCK_DATA` 所列记录前的间隙。`X` 表示 next-key 锁。
- 非唯一等值查询 `k=10` 会显示三项行锁：`nk / X / 10, 10`、`nk / X,GAP / 15, 15`、`PRIMARY / X,REC_NOT_GAP / 10`，分别对应上表里的 next-key `(5,10]`、间隙 `(10,15)` 和主键 10 的记录锁。二级索引的 `LOCK_DATA` 显示为「索引列值, 主键值」。

看到锁之后，再用冲突操作确认它确实挡住了什么：

1. 保持 A 的事务打开。B 执行 `SET SESSION innodb_lock_wait_timeout=1; START TRANSACTION; INSERT INTO range_demo VALUES (12,12,12,0);`。12 落在受保护的 `(10,15)` 里，B 应该在 1 秒后超时，随后执行 `ROLLBACK`。
2. 另起一轮，B 执行 `SELECT * FROM range_demo FORCE INDEX (nk) WHERE k=15 FOR UPDATE`。A 持有的是非唯一等值查询的锁时，15 上只有间隙锁，B 可以锁定 15；A 持有的是非唯一范围查询的锁时，15 上有 next-key lock，B 要等待。
3. 验证唯一二级索引的范围查询时，B 改用 `FORCE INDEX (uk) WHERE u=15`。

等待期间，可以在第三个会话查询 `performance_schema.data_lock_waits` 看到阻塞关系。每轮最后回滚 A 和 B，并用 `EXPLAIN` 确认实际访问的索引。锁模式、完整的索引键和冲突操作的结果三者对得上，才能确认推导出的区间。

## 11. 死锁、超时与重试 {#死锁超时与重试}

锁等待有两种结局。普通等待只要持锁方提交或回滚就会结束；但如果两个事务按相反顺序加锁，比如 A 先锁 10 再等 20、B 先锁 20 再等 10，就形成了循环等待，也就是死锁，双方都等不到对方释放。InnoDB 默认开启死锁检测，发现等待环后选一个受害事务回滚；`innodb_deadlock_detect=OFF` 时，只能等 `innodb_lock_wait_timeout` 超时。

两种失败的回滚范围不同：死锁检测回滚整个受害事务；锁等待超时在默认的 `innodb_rollback_on_timeout=OFF` 下只回滚当前语句，事务还开着，设为 `ON` 时才回滚整个事务。完整的失败语义见 [数据库事务](./index.mdx#自动提交与失败边界)。几个需要一起成功的操作，应该先结束失败的事务，再整体重试。

减少死锁的办法是统一访问顺序、缩短事务，以及给过滤条件建合适的索引来缩小加锁范围。重试要放在新事务里，限制次数并退避，用幂等标识防止副作用重复执行。

## 12. NOWAIT 与 SKIP LOCKED {#nowait-与-skip-locked}

默认情况下，锁定读遇到被别人锁住的行会一直等。MySQL 8.0 提供了两个选项改变这个行为：`FOR UPDATE NOWAIT` 遇到需要等待的行锁时立即报错，`FOR UPDATE SKIP LOCKED` 直接从结果中跳过被锁住的行。前者适合宁可快速失败、也不想排队的请求；后者适合「拿走任意几条空闲记录」的场景。

典型的例子是多个消费者从任务表里领取任务。每个消费者用 `SKIP LOCKED` 选出几条没被别人锁住的任务，在同一个事务里把它们的状态改为「处理中」并提交，再去执行耗时的处理。这样消费者之间不会互相等待，也不会领到同一个任务。处理失败怎么办，要另外设计重试和租约，比如超过一定时间没完成就允许别人重新领取。要注意 `SKIP LOCKED` 返回的结果本来就不完整，只能用在允许这一点的场景，不能用于需要准确结果的查询。

这两个选项只作用于行锁的等待，元数据锁等其他等待不受影响。

## 13. 常见问题 {#9-常见问题}

### 13.1 普通 SELECT 与行锁 {#91-普通-select-会加行锁吗}

在 RC 和 RR 下不会。普通的 `SELECT` 是一致性读，通过 [MVCC](./mvcc-read-view-consistent-read.mdx) 读取可见的版本，不加行锁，也不会被行锁挡住。例外是 SERIALIZABLE 且 `autocommit=0` 时，普通 `SELECT` 会被隐式转换成共享锁定读。显式写 `SELECT ... FOR SHARE`、`SELECT ... FOR UPDATE` 的是锁定读，它们和 `UPDATE`、`DELETE` 一样，按访问范围加锁。

### 13.2 行锁的粒度与数量 {#92-行锁是否一定只影响一行}

不是。「行锁」说的是锁的粒度是单条索引记录，而不是一条语句只锁一行。一条语句取得多少锁，由它扫描的范围决定：范围查询、非唯一条件或全表扫描，都会锁住多条索引记录和间隙。

## 14. 面试题 {#10-面试题}

### 14.1 InnoDB 有哪些行级锁，如何判断一条 SQL 的加锁范围 {#row-lock-ranges}

**考察重点**

- 理解 record、gap、next-key 与 insert intention lock。
- 理解唯一等值查询和范围查询的差异。
- 理解隔离级别、索引访问路径与实际锁范围。

**相关内容**：[记录锁](#1-记录锁锁住索引记录)、[间隙锁](#2-间隙锁阻止区间内插入)、[Next-key lock](#3-next-key-lock-同时保护记录和前方间隙)、[扫描路径与锁范围](#7-扫描路径决定实际加锁范围)。

<details>
<summary>参考回答</summary>

**InnoDB 的行级锁有记录锁、间隙锁、next-key lock 和插入意向锁，它们都加在索引上，加锁范围由隔离级别和索引扫描路径决定。**

记录锁锁住一条索引记录；gap lock 锁住两条记录之间的开区间，阻止插入；next-key lock 是记录锁加上前面的间隙锁。插入前要取得 insert intention lock，它会被已有的间隙锁挡住。另外还有表级的意向锁，用于协调表锁与行锁。

判断加锁范围要看隔离级别和执行计划。RR 下范围更新和锁定读按扫描路径使用 next-key lock 或边界 gap lock；完整唯一索引精确查找命中时只需记录锁，未命中时锁目标间隙。缺少合适索引时，访问路径会过宽。语句因此需要扫描并锁住大量索引记录。排查时应结合 data_locks、阻塞关系和实际执行计划。

</details>

### 14.2 唯一索引等值查询没有找到记录，还会阻止其他事务插入吗？ {#unique-missing}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 理解命中记录与不存在记录的差异。
- 理解 RR 间隙锁与双会话验证。

**相关内容**：[唯一键命中与未命中的双会话实验](#唯一键命中与未命中的双会话实验)。

<details>
<summary>参考回答</summary>

**会。RR 下，唯一键等值锁定读没有命中时，没有记录可锁，InnoDB 会锁住目标值所在的间隙，阻止别人把这个值插进来。**

例如表里已有 10 和 20，事务锁定查询 15，就锁住了 `(10, 20)`，另一个事务插入 15 会等待，直到前一个事务结束。对比之下，用完整唯一键查询命中 10，只锁 10 这条记录，插入 15 不受影响。验证时还要确认事务没有提前提交，以及实际使用的索引和隔离级别。

</details>

### 14.3 死锁和锁等待超时有什么区别，失败后怎样重试？ {#deadlock-timeout}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 理解等待环与超时阈值。
- 理解回滚范围与新事务重试。

**相关内容**：[死锁、超时与重试](#死锁超时与重试)、[锁等待的诊断证据](#8-用数据库证据查看锁等待)。

<details>
<summary>参考回答</summary>

**死锁是循环等待，锁等待超时是等待超过 `innodb_lock_wait_timeout`；死锁检测回滚受害事务，`innodb_rollback_on_timeout=OFF` 时超时只回滚当前语句。**

超时后事务还开着，前面语句的修改还在，不能当作什么都没发生直接提交。处理时先记录阻塞关系，确认事务状态，再回滚。需要整体重试时，开启新事务重新执行完整的业务单元，限制重试次数，并用幂等处理防止副作用重复。

</details>

### 14.4 FOR UPDATE 的 NOWAIT 和 SKIP LOCKED 分别适合什么场景？ {#skip-locked}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 理解立即失败与跳过记录。
- 理解任务领取与不完整结果集。

**相关内容**：[NOWAIT 与 SKIP LOCKED](#nowait-与-skip-locked)。

<details>
<summary>参考回答</summary>

**NOWAIT 把行锁等待变成立即报错，适合宁可快速失败也不想排队的请求；SKIP LOCKED 跳过已被锁住的行，适合多个消费者并发领取不同的任务。**

SKIP LOCKED 的结果会遗漏此刻被别人锁住的记录，所以只能用在允许结果不完整的场景。领取任务时，选取和标记「处理中」要在同一个事务里完成，提交后再执行耗时的处理；执行失败时仍需要租约或补偿机制，任务唯一标识和幂等处理用来防止重复副作用。

</details>

### 14.5 非唯一等值、唯一范围与非唯一范围查询分别锁哪些区间？ {#secondary-range-locks}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：二级索引扫描、边界记录、间隙与 data_locks 验证。

**相关内容**：[二级索引等值与范围锁实验](#二级索引等值与范围锁实验)、[data_locks 与阻塞验证](#data_locks-与阻塞验证)。

<details>
<summary>参考回答</summary>

**RR 下，非唯一等值查找保护匹配记录及相邻间隙；唯一与非唯一范围查找都需要间隙保护，具体边界取决于扫描路径。**

以正文 MySQL 8.0 实验为例，`u`、`k` 的值均为 5、10、15、20，每个值只有一条记录，并固定升序二级索引扫描：

- `k=10` 保护 `(5,10]` 和 `(10,15)`。
- `u>5 AND u<15` 与 `k>5 AND k<15` 保护 `(5,10]`、`(10,15]`。
- 这些查询还给返回行的主键 10 加记录锁；改为主键范围扫描时，上界 15 在该实验中只保留 gap lock。

完整唯一键等值命中才适用单记录优化。数据分布、扫描方向或索引改变后，应结合执行计划与 `data_locks` 重新核对。

</details>
