# InnoDB 锁

本文以 MySQL 8.4 InnoDB 为范围。InnoDB 通过索引记录锁和索引区间锁约束并发写入。分析一条 SQL 会锁住什么，不能只看 `WHERE` 条件，还要结合隔离级别、访问索引和实际扫描范围。

## 1. 面试核心 {#core}

- 记录锁保护索引记录，gap lock 阻止间隙插入，next-key lock 组合记录与前方间隙。[卡](#row-lock-ranges)
- RR 下完整唯一键等值查询命中记录时通常只锁记录；未命中、范围查询和唯一键部分条件要另行判断。[卡](#unique-missing)
- 加锁范围依赖隔离级别、索引与扫描路径，缺索引导致广泛锁定不等于自动升级表锁。[卡](#row-lock-ranges)
- RC 普通扫描通常减少 gap lock，外键和重复键检查仍有例外；普通快照读与锁定读不能混用同一套结论。
- 锁超时与死锁的回滚范围可能不同；NOWAIT 报错，SKIP LOCKED 跳过锁定记录，都需要明确业务处理。[卡](#deadlock-timeout) [卡](#skip-locked)

## 2. 记录锁锁住索引记录 {#1-记录锁锁住索引记录}

记录锁作用于索引记录。事务通过二级索引更新一行时，通常既要锁住访问到的二级索引记录，也要锁住对应的聚簇索引记录。

```sql
UPDATE orders SET status = 'PAID' WHERE id = 100;
```

如果 `id` 是唯一主键，并且查询能精确命中一行，InnoDB 可以只对该索引记录加锁。锁的是索引记录，不是 Java 对象，也不是抽象的业务条件。

## 3. 间隙锁阻止区间内插入 {#2-间隙锁阻止区间内插入}

间隙锁作用于相邻索引记录之间的区间，本身不锁定某条已有记录。它的主要作用是阻止其他事务在该区间插入新索引记录。

例如索引中已有 10 和 20，查询锁住 `(10, 20)` 的间隙后，其他事务不能在其中插入 15，但仍可能更新 10 或 20，具体要看记录上是否另有锁。

不同事务可以在同一间隙持有看起来冲突的 gap lock，因为它们的目的都是阻止插入，并不是互相排斥地修改一条现有记录。

## 4. Next-key lock 同时保护记录和前方间隙 {#3-next-key-lock-同时保护记录和前方间隙}

Next-key lock 是记录锁与该记录前方间隙锁的组合。InnoDB 在可重复读下执行范围锁定读或更新时，常用 next-key lock 覆盖扫描区间，防止其他事务插入会落入该范围的新记录。

假设索引值为 10、20、30，锁定范围可能按 `(-∞, 10]`、`(10, 20]`、`(20, 30]` 等 next-key 区间组织。真实边界仍取决于查询条件与优化器选择的访问路径。

对完整唯一索引进行等值查找时，如果命中已有记录且能确认其唯一，通常只需记录锁，不再锁住前方间隙。只使用联合唯一索引的一部分，并不具备这个条件。唯一等值查询未命中时，RR 可能锁住目标值所在间隙以阻止插入，不能套用“只加记录锁”。

## 5. 插入意向锁协调同一间隙中的插入 {#4-插入意向锁协调同一间隙中的插入}

事务准备向某个间隙插入时，会先取得插入意向锁。多个事务插入同一间隙中的不同位置时，可以并发进行；若目标位置或间隙被其他事务以不兼容方式锁住，则需要等待。

插入意向锁不是表级的“准备写入”标记。它属于间隙锁的一种，用来表达具体插入位置。

## 6. 意向锁协调表锁与行锁 {#5-意向锁协调表锁与行锁}

InnoDB 在取得行级共享锁或排他锁前，会在表级取得意向共享锁或意向排他锁。它让表锁请求可以快速判断表中是否存在不兼容的行锁，而不必遍历所有记录锁。

行记录上，S 与 S 兼容，S 与 X、X 与 X 不兼容；表级 IS/IX 表示已有或计划取得的行锁，不等于锁住全部行。普通行级操作之间通常不会因为意向锁彼此阻塞。分析业务锁等待时，主要仍要找到实际的记录锁、间隙锁和持有事务。

## 7. 隔离级别影响间隙保护 {#6-隔离级别影响间隙保护}

在可重复读下，范围更新、删除和锁定读通常使用 next-key lock，既锁扫描到的记录，也保护相应间隙。普通一致性读使用 MVCC，不会为了读取快照而给这些记录加行锁。

在读已提交下，普通搜索和索引扫描通常不使用间隙锁，只锁匹配的索引记录；外键约束检查和重复键检查等场景仍可能使用间隙锁。更少的间隙锁能提高并发，也允许同一事务的两次查询看到新提交的记录。

## 8. 扫描路径决定实际加锁范围 {#7-扫描路径决定实际加锁范围}

```sql
SELECT *
FROM orders
WHERE tenant_id = 10 AND created_at >= '2026-08-01'
FOR UPDATE;
```

若存在 `(tenant_id, created_at)` 索引，InnoDB 可以锁住对应的连续索引范围。若缺少合适索引，执行计划可能扫描大量记录，并对扫描过程中不能立即排除的记录加锁，实际影响远大于最终返回的行数。

这不等于 InnoDB 自动把行锁升级成表锁。问题在于访问路径太宽，导致大量索引记录被锁住。为锁定读设计索引时，需要同时考虑查询性能和锁范围。

## 9. 用数据库证据查看锁等待 {#8-用数据库证据查看锁等待}

排查锁等待时可以组合使用：

- `performance_schema.data_locks` 查看当前持有或等待的锁。
- `performance_schema.data_lock_waits` 查看阻塞关系。
- `SHOW ENGINE INNODB STATUS` 查看最近死锁和事务信息。
- 执行计划确认语句使用了什么索引、预计扫描多少记录。

先找到等待事务、阻塞事务和锁定索引，再回到 SQL 与事务边界。只看到“Lock wait timeout”就增加超时，通常会让连接占用更久。

## 10. 唯一键命中与未命中的双会话实验 {#unique-lock-example}

在独立练习库初始化：

```sql
CREATE TABLE lock_demo (id INT PRIMARY KEY, value INT) ENGINE=InnoDB;
INSERT INTO lock_demo VALUES (10, 1), (20, 1);
```

会话 A 先执行：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM lock_demo WHERE id = 15 FOR UPDATE;
```

查询结果为空，但在该数据布局下，15 位于 `(10, 20)` 间隙。会话 B 执行 `INSERT INTO lock_demo VALUES (15, 1)` 会等待 A 结束事务；A `COMMIT` 后 B 才能继续。若 A 改查已有主键 10，则保护的是 10 的记录，不能据此推断插入 15 也会被阻塞。

每轮实验结束后提交或回滚两个会话，再恢复表数据。用 `data_locks` 与 `data_lock_waits` 对照锁模式和索引；换成二级索引、非唯一条件或 RC 时，结论要重新核对。

## 11. 死锁、超时与重试 {#deadlock-handling}

两个事务按相反顺序占有记录，就可能形成循环等待。例如 A 先锁 10 再等 20，B 先锁 20 再等 10。正常等待可能最终被持锁方释放；死锁必须打破等待环。InnoDB 默认启用死锁检测，选择受害事务回滚；关闭检测后可能依赖超时处理。

死锁通常回滚整个受害事务，默认锁等待超时通常只回滚当前语句。应用必须确认剩余事务状态；需要共同成立的业务操作可显式回滚后整体重试，不能只无条件重试最后一条 SQL。

统一访问顺序、缩短事务、为过滤条件建合适索引可以降低概率，但不能承诺彻底消灭死锁。有界退避重试应放在新事务中，并以幂等标识约束副作用。

## 12. NOWAIT 与 SKIP LOCKED {#locking-options}

`FOR UPDATE NOWAIT` 遇到需要等待的行锁时直接报错；`FOR UPDATE SKIP LOCKED` 从结果中跳过被锁定的行。它们控制的是锁等待处理，不会让两个事务同时安全地修改同一行。

SKIP LOCKED 适合多个消费者抢取任务这类允许跳过忙碌记录的场景。选取与状态更新要在同一事务中完成，提交后再处理耗时任务，并另行设计失败重试与租约。它返回的集合不完整，不能直接用来做余额汇总、库存是否存在等要求完整性的判断。

这些选项只适用于行级锁，不能保证绕过元数据锁等其他等待。

## 13. 常见问题 {#9-常见问题}

### 13.1 普通 `SELECT` 会加行锁吗 {#91-普通-select-会加行锁吗}

在 RC/RR 下，InnoDB 的普通一致性读通常通过 MVCC 读取可见版本，不加记录锁。SERIALIZABLE 且关闭 autocommit 时，普通 SELECT 会隐式转为共享锁定读，不能套用此结论。`SELECT ... FOR SHARE`、`SELECT ... FOR UPDATE` 以及更新、删除属于锁定或写操作，会根据访问范围加锁。

### 13.2 行锁是否一定只影响一行 {#92-行锁是否一定只影响一行}

不一定。“行锁”描述锁的粒度，不代表一条语句只取得一个锁。范围查询、非唯一条件或缺少合适索引时，一条语句可能锁住很多索引记录和间隙。
