# 数据库死锁

**死锁**是两个或多个事务互相等待对方持有的锁，形成一个环，谁也无法继续。它和普通的锁等待不同：普通等待只要对方提交就能结束，死锁里没有任何一方能先提交。

死锁在并发系统里无法完全避免，真正要掌握的是它发生后怎么办：数据库怎样发现并打破它，应用收到错误后事务处于什么状态，以及重试时怎样不把外部操作重复执行一遍。下文以 MySQL 8.0 InnoDB 为准。

## 1. 面试核心 {#core}

- 事务**各自持有锁、又等待对方的锁**时，就形成了死锁的等待环。[卡](#handle-deadlock)
- `innodb_deadlock_detect=ON`（默认）时，InnoDB **发现等待环后会选一个事务回滚**，让其他事务继续。
- 死锁错误 1213 **回滚整个事务**；锁等待超时错误 1205 在默认的 `innodb_rollback_on_timeout=OFF` 下**只回滚当前语句**。[卡](#deadlock-timeout-retry)
- 关闭死锁检测后，**只能等锁等待超时来解除死锁**，延长超时也消除不了循环依赖。[卡](#deadlock-detection-off)
- 数据库回滚**只撤销数据库里的修改**，已经发出的 HTTP 请求、支付等外部调用不会被撤销，重试时要靠幂等控制。

## 2. 死锁的形成 {#死锁的形成}

最典型的死锁来自加锁顺序相反。事务 A 先锁住订单 1，再去锁订单 2；事务 B 先锁住订单 2，再去锁订单 1。两边都拿着对方要的锁不放，又都在等对方释放：

```text
事务 A：持有 order:1 → 等待 order:2
事务 B：持有 order:2 → 等待 order:1
```

实际业务里的死锁往往没这么直观。除了显式更新的行，通过二级索引访问、检查外键、遇到唯一键冲突时，InnoDB 也会加锁，这些锁在 SQL 里看不出来。所以排查时要还原整个事务执行过的所有语句，弄清每一步在哪些索引记录上加了锁。

## 3. InnoDB 死锁检测 {#innodb-死锁检测}

MySQL 8.0 默认开启 `innodb_deadlock_detect`。事务要等待一把锁时，InnoDB 会检查等待关系里有没有环；发现环后，从中选一个事务回滚，这个事务叫**受害事务**（victim）。它释放的锁让环上的其他事务得以继续。InnoDB 倾向于选择较小的事务回滚，事务的大小按插入、更新、删除的行数衡量，这样撤销的工作最少。

受害事务之前做的修改全部撤销，应用会收到错误码 1213。这时整个事务已经不存在了，应用要开一个新事务，把整个业务操作从头再做一遍。各种锁的具体类型和加锁范围见 [InnoDB 锁](./innodb-locking-ranges.mdx)。

## 4. 锁等待超时与死锁 {#锁等待超时与死锁}

**锁等待超时**是指一个事务等锁的时间超过了 `innodb_lock_wait_timeout`（默认 50 秒）。它不需要有环：持锁的事务只是执行得很慢，或者开着事务忘了提交，等待方也会超时。死锁则一定存在循环依赖，不管等多久都解不开。

两者对事务的影响也不同。MySQL 8.0 默认 `innodb_rollback_on_timeout=OFF`，超时只回滚等锁的那条语句，事务里之前的修改还在，事务也还开着。这是一个容易踩的坑：应用如果捕获错误后直接提交，会把一个只完成了一半的业务操作提交进去。正确做法是显式 `ROLLBACK`，再按完整的业务单元重试。

把超时调长不能解决死锁。它只是让等待方多等一会儿，同时更久地占着连接，等待环本身还在。

## 5. 错误码与配置 {#错误码与配置}

| 情况 | 错误码 | 回滚范围 |
| --- | --- | --- |
| 检测到死锁 | 1213 | 整个受害事务。 |
| 行锁等待超时，`innodb_rollback_on_timeout=OFF` | 1205 | 当前语句。 |
| 行锁等待超时，`innodb_rollback_on_timeout=ON` | 1205 | 整个事务。 |

死锁检测本身也有成本：大量事务同时争抢同一把锁时，每次等待都要检查等待关系，检测会变得很慢。这种场景下可以关闭 `innodb_deadlock_detect`，改由锁等待超时来解除阻塞。代价是一旦真发生死锁，环上的事务要一直等到超时，再由应用结束失败的事务；所以关闭后通常要把 `innodb_lock_wait_timeout` 调小。

几个超时参数管的不是同一件事：`innodb_lock_wait_timeout` 控制 InnoDB 行锁的等待；元数据锁（比如执行 DDL 时等待表上的锁）用 `lock_wait_timeout`；网络读写超时则由客户端和相关的网络参数控制。

## 6. 双会话死锁复现 {#双会话死锁复现}

用两个客户端会话就能复现死锁。先在独立的练习库里建表并插入两行：

```sql
CREATE TABLE deadlock_demo (id INT PRIMARY KEY, n INT) ENGINE=InnoDB;
INSERT INTO deadlock_demo VALUES (1,0),(2,0);
```

然后按下表顺序在两个会话里交替执行。第 3 步会卡住等待，保持它，再到会话 B 执行第 4 步：

| 步骤 | 会话 A | 会话 B |
| --- | --- | --- |
| 1 | `START TRANSACTION; UPDATE deadlock_demo SET n=n+1 WHERE id=1;` | |
| 2 | | `START TRANSACTION; UPDATE deadlock_demo SET n=n+1 WHERE id=2;` |
| 3 | `UPDATE deadlock_demo SET n=n+1 WHERE id=2;` | |
| 4 | | `UPDATE deadlock_demo SET n=n+1 WHERE id=1;` |

第 3 步时，A 持有行 1、等待 B 持有的行 2；第 4 步 B 又去等 A 持有的行 1，环就形成了。检测开启时，其中一个会话立即收到 1213，它的事务被整个回滚，另一个会话卡住的更新随即完成。哪个会话被选为受害事务由检测器决定，实验时以两边实际的输出为准。最后两个会话都执行 `ROLLBACK`，清理实验状态。

作为对照，可以构造一个没有环的普通等待：让 B 单独开事务更新行 1 并保持不提交，A 执行 `SET innodb_lock_wait_timeout=1` 后也去更新行 1。A 只是在等 B，没有循环依赖，1 秒后收到的是 1205 而不是 1213。实验结束同样两边都显式回滚。

## 7. 完整事务重试 {#重试完整事务}

死锁是瞬时的并发冲突，重试一次通常就能成功，所以适合有限次数的重试。重试的单位必须是整个事务，每次都重新读数据、重新判断业务前置条件：

1. 结束失败事务，必要时显式 ROLLBACK。
2. 在事务外按退避与随机抖动等待。
3. 新建事务，从业务入口重新执行。
4. 达到次数上限或总 deadline 时停止。

退避和随机抖动是为了让冲突的几个事务错开时间，否则它们同时重试，很可能再次死锁。使用框架的声明式事务时，要确认重试逻辑包在事务外面，每次重试都会开一个新事务。

只重放报错的那一条 SQL 是错误的。收到 1213 时整个事务已经回滚，前面语句的修改都没了，只补最后一条会得到一个残缺的结果。而且前面的语句可能是根据当时读到的数据做的判断，比如库存是否足够，这些判断也要基于新数据重新做。

## 8. 事务外的副作用 {#事务外的副作用}

重试整个事务还有一个前提：事务里只有数据库操作。数据库回滚只能撤销它自己管理的修改，事务里已经成功发出的 HTTP 请求、已经扣款的第三方支付不会跟着撤销。直接重试整个方法，这些操作会再执行一遍，比如用户被扣两次款。

所以远程调用要移出持锁的事务。事务里只在数据库中记录状态和待发送的事件，提交之后再异步执行外部调用；同时用幂等键和状态条件保证同一个操作即使执行多次，效果也只有一次。事务拆分的设计见[事务中的远程调用](./long-transactions-hot-updates-boundaries.mdx#事务中的远程调用)。

## 9. 死锁预防 {#减少死锁}

死锁的根源是循环等待，最有效的预防是统一加锁顺序。例如所有更新同一组记录的事务都按主键升序操作，A 和 B 都先锁订单 1 再锁订单 2，后来的只会排队等待，不会形成环。其他手段则是减少锁的数量和持有时间：

- 合适索引减少扫描与锁定范围。
- 短事务减少锁的占用时间。
- 小批量提交缩小单次竞争范围。
- 同一热点键可使用受控队列串行处理。

即使做了这些，索引内部的访问顺序仍可能带来意料之外的锁竞争，死锁不能完全杜绝。应用仍然要保留有限重试和幂等处理。

## 10. 死锁日志与诊断 {#分析死锁日志}

排查死锁有三个信息来源：`SHOW ENGINE INNODB STATUS` 的输出里保留最近一次死锁的详情；开启 `innodb_print_all_deadlocks=ON` 后，每次死锁都会写入错误日志，适合偶发问题；`performance_schema` 中的 `data_locks` 和 `data_lock_waits` 表展示当前持有的锁和等待关系，适合观察正在发生的阻塞。拿到日志后，按下面的步骤分析：

1. 找到每个事务持有和等待的锁。
2. 确认索引、记录或间隙范围。
3. 回到应用代码，还原事务内 SQL 顺序。
4. 对照执行计划，检查扫描范围。
5. 用并发用例验证调整后的死锁率和延迟。

注意，死锁日志里每个事务显示的通常只是当时正在执行的那条 SQL，事务前面执行过的语句不会列出来，而它们加的锁往往才是形成环的另一半。所以第 3 步回到代码还原完整的事务很关键。

## 11. 常见问题 {#9-常见问题}

### 11.1 死锁与数据库状态 {#91-发生死锁是否说明数据库有故障}

不说明。只要允许事务等待锁，就有可能出现循环等待，死锁是并发执行的正常结果之一。数据库检测并回滚受害事务，正是它从死锁中恢复的机制。偶发死锁靠重试处理即可；死锁频繁时，再检查访问顺序、事务长度和热点数据。

### 11.2 悲观锁与循环等待 {#92-使用悲观锁能否避免死锁}

不能。悲观锁（比如 `SELECT ... FOR UPDATE`）的作用是让事务在冲突资源上排队等待，而死锁恰恰发生在等待中：不同事务按相反的顺序锁多行，照样会形成环。统一加锁顺序和缩短持锁时间才能减少死锁。

## 12. 面试题 {#10-面试题}

### 12.1 数据库发生死锁后应该如何定位和处理 {#handle-deadlock}

**考察重点**

- 循环等待、死锁检测和 victim 回滚。
- 死锁与锁等待超时的区别。
- 完整事务重试、幂等和事务外副作用。

**相关内容**：[死锁的形成](#死锁的形成)至[死锁日志与诊断](#分析死锁日志)。

<details>
<summary>参考回答</summary>

**定位死锁要还原参与事务的持锁与等待关系；处理上打破等待环，并在新事务中有界重试。**

用 `SHOW ENGINE INNODB STATUS` 查看最近死锁，需要完整记录时开启 `innodb_print_all_deadlocks=ON`。核对全部 SQL 和索引扫描路径，再通过统一访问顺序、缩短事务和缩小扫描范围减少冲突。

收到 1213 时整个事务已经回滚，应重新执行完整业务单元，并使用退避、次数上限和幂等控制重复副作用。

</details>

### 12.2 1213 与 1205 的回滚范围有何区别，能否直接重试最后一条 SQL？ {#deadlock-timeout-retry}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 语句回滚与事务回滚
- 新事务与业务前置条件

**相关内容**：[错误码与配置](#错误码与配置)、[完整事务重试](#重试完整事务)。

<details>
<summary>参考回答</summary>

**1213 回滚整个事务；1205 在默认的 `innodb_rollback_on_timeout=OFF` 下只回滚当前语句，参数为 ON 时回滚整个事务。两种情况都不能只重试最后一条 SQL。**

收到 1213 时，前面语句的修改已经全部撤销，只重放最后一条会得到残缺的结果。收到 1205 时事务还开着，前面的修改还在，直接提交会留下只做了一半的操作。正确做法是结束原事务（1205 时显式 `ROLLBACK`），在新事务里重新执行整个业务单元，并基于新读到的数据重新判断前置条件。

</details>

### 12.3 关闭死锁检测或延长锁等待时间，能否避免死锁？ {#deadlock-detection-off}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 等待环与超时
- 检测开销和恢复代价

**相关内容**：[InnoDB 死锁检测](#innodb-死锁检测)、[错误码与配置](#错误码与配置)。

<details>
<summary>参考回答</summary>

**都不能。死锁来自循环依赖，关闭检测或延长等待时间都不改变加锁顺序，等待环依然会形成。**

`innodb_deadlock_detect=OFF` 后，死锁只能靠锁等待超时解除，环上的事务要一直等到超时。它的好处是在大量事务争抢同一把锁时省掉检测开销，代价是死锁的恢复被推迟。是否关闭要基于热点负载测试，应用也仍然要处理超时、结束失败的事务。延长等待时间只会让死锁等得更久、占用连接更久。

</details>

### 12.4 如何用两个会话构造死锁，并与普通锁等待超时区分？ {#reproduce-deadlock}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：相反加锁顺序、错误码和清理。

**相关内容**：[双会话死锁复现](#双会话死锁复现)。

<details>
<summary>参考回答</summary>

**让两个会话按相反顺序更新两行：A 先更新行 1，B 先更新行 2，两边都不提交。**

接着 A 更新行 2，进入等待；B 再更新行 1，此时 A 等 B、B 等 A，形成环。检测开启时，一个事务立即收到 1213 并整体回滚。区分普通锁等待超时的方法是去掉环：只让 B 持有行 1，A 去更新行 1，这时 A 只是单向等待 B，超过 `innodb_lock_wait_timeout` 后收到的是 1205。实验结束后两边都显式回滚。

</details>
