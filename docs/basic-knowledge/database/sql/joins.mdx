# SQL 连接

**连接**（JOIN）是按条件把两张表的行配对，每一个满足条件的配对输出一行。客户表和订单表按客户 ID 连接，得到的就是「每个客户的每笔订单」。

连接写错时通常不报错，只是行数不对：没有订单的客户消失了，或者一个客户的金额被算了好几遍。外连接怎样给没匹配上的行补 NULL？条件写在 `ON` 和 `WHERE` 里有什么不同？一对多连接又会怎样放大明细？下文以 MySQL 8.0 为准。

## 1. 面试核心 {#core}

- `INNER JOIN` **只返回匹配上的行**，`LEFT JOIN` **还会保留没匹配上的左表行，右表列补 NULL**。[卡](#left-join-where)
- 一对多连接**为每个匹配对输出一行**，左表的一行会重复出现，直接对左表金额求和会被放大。
- 在 `WHERE` 里对右表列写比较条件，**会把 `LEFT JOIN` 补出来的 NULL 行过滤掉**，外连接就退化成了内连接。[卡](#left-join-where)
- `EXISTS` **只判断有没有匹配**，不会因为匹配多行而重复输出；`NOT EXISTS` 选出完全没有匹配的行。[卡](#exists-anti-join)
- 连接多张明细表时，**先把每张明细聚合到目标粒度再连接**，才能避免重复求和。[卡](#join-fanout)

## 2. 匹配与补空 {#匹配与补空}

下面三个客户中，Lin 有两笔购买，Ming 有一笔，Yu 没有。用 `LEFT JOIN` 把客户和购买记录连起来：

```sql
CREATE TABLE customers (id INTEGER PRIMARY KEY, name VARCHAR(20));
CREATE TABLE purchases (
  id INTEGER PRIMARY KEY, customer_id INTEGER, amount INTEGER
);
INSERT INTO customers VALUES (1, 'Lin'), (2, 'Ming'), (3, 'Yu');
INSERT INTO purchases VALUES (10, 1, 50), (11, 1, 80), (12, 2, 20);

SELECT c.id, p.id AS purchase_id
FROM customers c
LEFT JOIN purchases p ON p.customer_id = c.id
ORDER BY c.id, p.id;
```

结果是 `(1,10)、(1,11)、(2,12)、(3,NULL)`。Lin 匹配到两笔购买，所以出现两行，这就是一对多连接让左表行重复的原因。Yu 没有任何匹配，`LEFT JOIN` 仍然保留他，右表的列全部补 NULL，这一行叫**补空行**。

换成 `INNER JOIN`，结果只剩前三行，没有匹配的 Yu 不会出现。

## 3. ON 与 WHERE {#on-与-where}

`LEFT JOIN` 的条件放在 `ON` 还是 `WHERE`，结果可能完全不同。关键在于两者生效的时机：`ON` 在连接时决定右表哪些行能和左表配对，配不上的左表行照样保留并补空；`WHERE` 在连接完成之后，对整个结果过滤，补空行也要接受检查。

先把金额条件放在 `ON` 里：

```sql
SELECT c.id, p.id AS purchase_id FROM customers c
LEFT JOIN purchases p
  ON p.customer_id = c.id AND p.amount >= 50
ORDER BY c.id, p.id;
```

结果是 `(1,10)、(1,11)、(2,NULL)、(3,NULL)`。金额条件只限制了哪些购买记录能参与配对：Ming 唯一的一笔 20 配不上，于是 Ming 和 Yu 一样变成补空行，三个客户仍然全部保留。

如果把条件移到连接之后，写成 `WHERE p.amount >= 50`，结果只剩 Lin 的两行。Ming 的购买金额 20 不满足条件；Yu 的补空行里 `p.amount` 是 NULL，`NULL >= 50` 的结果是 UNKNOWN，`WHERE` 只保留结果为 TRUE 的行，所以也被去掉。这时 `LEFT JOIN` 的效果和 `INNER JOIN` 一样了。

所以规则是：想限制「哪些右表行参与匹配」，条件写在 `ON`；想过滤「最终输出哪些行」，才写在 `WHERE`。

## 4. 存在性与反连接 {#存在性与反连接}

有时只想知道客户有没有购买记录，不需要购买的明细。这时用 `EXISTS` 更直接：它对每个客户检查子查询是否至少返回一行，有就保留这个客户，不关心有几行。

```sql
SELECT c.id FROM customers c
WHERE EXISTS (SELECT 1 FROM purchases p WHERE p.customer_id=c.id)
ORDER BY c.id;
SELECT c.id FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM purchases p WHERE p.customer_id=c.id)
ORDER BY c.id;
```

第一条返回 1、2，Lin 虽然有两笔购买，也只出现一次。第二条只返回 3。和 `JOIN` 不同，右表匹配多少行都不会让 `EXISTS` 的结果变多。

第二条这种「选出没有匹配的行」的查询叫**反连接**。它也可以写成 `LEFT JOIN` 再加 `WHERE p.id IS NULL`，利用的正是补空行。这时要检查右表中保证非空的列，比如主键；如果检查一个本来就可能为 NULL 的列，真实数据里的 NULL 会被误当成「没有匹配」。用 `NOT IN` 写反连接也有空值问题，见 [NOT IN 与 NULL](./query.mdx#not-in-与-null)。

## 5. 多明细连接与重复统计 {#多明细连接与重复统计}

一对多连接会让左表行重复，同时连接两张一对多的明细表，问题会更严重。假设一个客户有 2 个订单和 3 个标签，两张明细表都按客户 ID 连接，这个客户会得到 2 × 3 = 6 行，每个订单和每个标签都配对一次。每笔订单金额重复出现 3 次，直接 `SUM` 就把总额放大了 3 倍。

解决办法是先把每张明细表聚合到客户粒度，一个客户一行，再拿去连接。例如购买总额可以先算好：

```sql
SELECT c.id, COALESCE(p.total, 0) AS total
FROM customers c
LEFT JOIN (
  SELECT customer_id, SUM(amount) AS total
  FROM purchases GROUP BY customer_id
) p ON p.customer_id=c.id
ORDER BY c.id;
```

结果为 `(1,130)、(2,20)、(3,0)`。子查询先把购买记录压成每个客户一行，再连接时就不会有重复；Yu 没有购买，`COALESCE` 把补空的 NULL 换成 0。标签等其他明细也同样先聚合到一人一行，再加入连接。

用 `SUM(DISTINCT amount)` 去掉重复看起来也行，但它去重的依据是金额的值，不是订单。两笔不同的订单金额恰好相同时，也会被合并成一笔，结果反而少算。所以它修不了粒度错误。

## 6. 连接算法 {#连接算法}

前面讲的是连接的结果，这一节讲数据库怎样算出这个结果。

**嵌套循环连接**是最基本的算法：对外层表（驱动表）的每一行，到内层表里找匹配的行。内层表的连接列有索引时，每次查找只需要一次索引定位；没有索引就要扫描内层表。所以成本大致是「外层行数 × 每次内层查找的成本」。选驱动表时要看的是过滤之后剩下的行数，而不是表本身有多少行：一张大表经过 `WHERE` 过滤后只剩几行，就适合放在外层。

MySQL 8.0.18 起，适合的连接可以使用 **hash join**：先用其中一张表的连接键建一个内存哈希表，再逐行扫描另一张表，用键去哈希表里查匹配。它不依赖内层索引，适合等值连接；哈希表放不进内存时，要分批写到磁盘上处理，成本会上升。实际用了哪种算法、内层循环了多少次，见[执行计划](../indices/execution-plan.mdx)。

## 7. 使用边界 {#使用边界}

`ON` 里的普通等值比较匹配不了两个 NULL，因为 `NULL = NULL` 的结果是 UNKNOWN。确实需要把空值当成相等时，MySQL 提供了 NULL 安全的比较运算符 `<=>`。但这会让所有空值互相匹配，用之前要确认业务上确实是这个意思。

几种特殊的连接也值得知道：`CROSS JOIN` 不加条件时，产生两张表所有行的组合，也就是笛卡尔积；自连接是同一张表用两个别名参与匹配，比如员工表连接自己找到每个人的上级。另外，内连接的顺序可以由优化器重排，SQL 里先写哪张表，不代表执行时先读哪张表。

### 8.1 LEFT JOIN 后在 WHERE 中过滤右表字段，会有什么影响？ {#left-join-where}

**相关内容**：[面试核心](#core)、[匹配与补空](#匹配与补空)、[使用边界](#使用边界)。

<details>
<summary>参考回答</summary>

**会把没有匹配的左表行过滤掉，`LEFT JOIN` 退化成 `INNER JOIN` 的效果。**

`LEFT JOIN` 先给没匹配上的左表行补出右表 NULL，`WHERE` 再对连接结果过滤。`p.amount >= 50` 这类普通比较遇到 NULL 得到 UNKNOWN，补空行就被去掉了。要保留所有左表行、只限制哪些右表行参与匹配，应该把条件写在 `ON` 里。`WHERE p.id IS NULL` 则是反过来利用补空行，专门选出没有匹配的左表行。

</details>

### 8.2 只查有订单或没有订单的客户，为什么可以用 EXISTS 和 NOT EXISTS？ {#exists-anti-join}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：存在性、反连接与行数。

**相关内容**：[存在性与反连接](#存在性与反连接)。

<details>
<summary>参考回答</summary>

**因为这两个问题问的都是「有没有」，而 `EXISTS` 正是判断是否至少有一个匹配行，`NOT EXISTS` 判断是否完全没有匹配行。**

它们只是按条件筛选客户，不把订单明细带进结果，所以客户有多个订单也只出现一次，不需要再去重。用 `LEFT JOIN ... WHERE 右表列 IS NULL` 也能写反连接，但要检查右表中保证非空的列，比如主键，否则真实的 NULL 会被误判为没有匹配。

</details>

### 8.3 订单与标签同时连接后金额翻倍，为什么 DISTINCT 未必能修复？ {#join-fanout}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：多对多组合和统计粒度。

**相关内容**：[多明细连接与重复统计](#多明细连接与重复统计)。

<details>
<summary>参考回答</summary>

**金额翻倍是因为两张明细表按客户两两组合，每笔订单随标签数重复出现；`DISTINCT` 按值去重，会把金额相同的不同订单也合并掉。**

一个客户有 2 个订单、3 个标签时，连接后有 6 行，每笔订单金额出现 3 次。`SUM(DISTINCT amount)` 去重的是金额值，不是订单，两笔金额相同的订单会被算成一笔。正确的做法是先把订单和标签分别聚合到客户粒度，每个客户一行，再连接结果。

</details>

### 8.4 MySQL 连接一定由小表驱动大表吗，连接算法如何影响成本？ {#join-algorithms}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：过滤后基数、索引探测与哈希构建。

**相关内容**：[连接算法](#连接算法)。

<details>
<summary>参考回答</summary>

**不一定。连接成本取决于过滤后的行数和内层每次访问的成本，「小表」应该按过滤后的行数算，而不是按表的总行数。**

嵌套循环的成本大致是外层行数乘以每次内层查找的成本，内层连接列有索引时每次查找很便宜。Hash join 用一张表建哈希表、另一张表去探测，要比较建表、探测和内存成本，内存不够时还要分批落盘。MySQL 8.0 由优化器在候选计划中选择驱动顺序和算法，结论要用实际执行计划验证。

</details>
