# 联合索引与覆盖索引

**联合索引**是按多列建立的索引，索引项先按第一列排序，第一列相同再按第二列排序，依此类推。**覆盖索引**不是一种单独的索引，而是指某个索引已经包含一次查询要用到的全部列，查询不必再去读完整的行。

这两个概念决定了一条查询走索引时到底读了多少数据：联合索引的列顺序决定能圈出多小的扫描范围，覆盖与否决定圈出来的每条记录还要不要再回聚簇索引取一次行。要讲清楚它们，抓住三点：索引项怎样逐级排序，二级索引缺列时怎样回表，以及排序和 `LIMIT` 怎样借用索引顺序。下文以 MySQL 8.0 InnoDB 为准。

## 1. 面试核心 {#core}

- 联合索引 `(a,b,c)` **先按 a 排序，a 相同再按 b，a、b 都相同才按 c**，所以 `a=1 AND b>10` 能圈出一段连续的扫描范围。[卡](#left-prefix-range)
- 范围条件之后的索引列**不再缩小扫描区间，但仍能参与 ICP 过滤或覆盖取列**，例如 `a=1 AND b>10 AND c=5` 中的 c。[卡](#icp-vs-covering)
- 二级索引缺少查询要的列时，要**拿主键回聚簇索引读完整行**，这一步叫回表；索引已包含所需列时，查询可以直接从索引取值。[卡](#covering-index)
- 前导列被等值条件固定后，**剩下的索引列顺序可以直接满足排序**：`(tenant_id,status,created_at,id)` 固定前两列后，可按后两列满足 `ORDER BY created_at DESC,id DESC`。[卡](#index-order-limit)
- 为了覆盖而往索引里加列，会**让索引变宽，写入、存储和缓存成本都跟着上升**。

## 2. 联合索引的键顺序 {#1-联合索引先按第一列排序}

联合索引里的记录像电话簿一样逐级排序。以索引 `(tenant_id, status, created_at)` 为例：索引项先按 `tenant_id` 排；`tenant_id` 相同的，再按 `status` 排；前两列都相同的，才按 `created_at` 排。

所以下面这个条件可以在索引里找到一段连续的区间：先定位到 `tenant_id = 10`，在其中定位 `status = 'PAID'`，再从 `2026-08-01` 开始往后读。

```sql
WHERE tenant_id = 10
  AND status = 'PAID'
  AND created_at >= '2026-08-01'
```

反过来，如果只给出 `status`，同一个状态的记录分散在每个 tenant 的分组里，在整棵索引中并不连续，没法直接定位成一个区间。这就是**最左前缀**：只有从第一列开始、连续给出的那几列，才能用来圈定扫描范围。

## 3. 等值、范围与排序列 {#2-等值列范围列和排序共同决定列顺序}

决定列顺序时，三类列各有分工：等值列固定前缀，范围列划出扫描区间，排序列要和剩下的键顺序对上。完整的设计流程见 [索引设计](./index-review.mdx#6-从一条查询决定索引怎么建)。

关键在于范围列之后的列不再有序可用。比如 `(tenant_id, created_at, status)` 能按 tenant 和时间扫描，但条件是 `created_at > '2026-08-01'` 时，区间里不同时间点的记录交错排列，`status` 只能在扫描过程中逐条过滤，没法再缩小区间。如果主要查询是按 tenant、status 等值过滤再按时间翻页，就应该把 `status` 放到时间前面，用 `(tenant_id, status, created_at)`。

跳跃扫描、索引条件下推和索引合并能让一些不满足最左前缀的查询也用上索引，但它们各有适用条件，实际走哪条路径以执行计划为准。

## 4. 二级索引与回表 {#3-二级索引叶子节点保存主键}

InnoDB 的二级索引不直接保存整行，而是保存索引列加上聚簇键（通常就是主键），靠聚簇键找到完整的行。存储组织见 [聚簇索引](./clustered_index/index.mdx#聚簇索引)。

所以用二级索引查询一个不在索引里的列时，要分两步：

1. 在二级索引里找到符合条件的记录，拿到它们的主键。
2. 用主键去聚簇索引读完整的行，取出需要的列。

第二步就是**回表**。命中的记录少时，回表开销不明显；命中成千上万条时，每条都要按主键到聚簇索引里单独查一次，这些访问往往分散在不同的页上，回表就会成为主要成本。

## 5. 覆盖索引 {#4-覆盖索引让查询直接从索引返回}

如果一个索引同时包含查询的过滤列和返回列，它就覆盖了这次查询，第 2 步回表可以省掉：

```sql
SELECT created_at
FROM orders
WHERE tenant_id = 10 AND status = 'PAID';
```

这条查询只用到 `tenant_id`、`status` 和 `created_at`，索引 `(tenant_id, status, created_at)` 里都有，所以可以直接从索引取值。`EXPLAIN` 的 Extra 列会显示 `Using index`。

覆盖查询也不是完全不碰聚簇索引。二级索引记录本身不带版本信息，MVCC 判断可见性时有时要回到聚簇记录：二级索引记录带有删除标记时会这样；修改过该索引页的事务对当前读视图来说较新时，也会这样。必要时，InnoDB 还会通过 undo 重建可见的旧版本。

覆盖是一个索引和一条具体查询之间的关系，换一条要多返回一列的查询，同一个索引就不再覆盖。把所有返回列都塞进索引，会增加空间、缓存压力和写放大，所以只为高频、性能敏感、返回列少的查询考虑覆盖。

## 6. 主键宽度与索引成本 {#5-主键宽度会影响全部二级索引}

每条二级索引记录都带着聚簇键，主键越宽，所有二级索引的空间和缓存开销都越大。机制和选择条件见 [聚簇索引](./clustered_index/index.mdx#主键宽度)。

## 7. 索引访问的执行证据 {#6-sql-使用索引仍然可能很慢}

用上了索引不等于查询就快，还要看扫描了多少行、回表多少次、有没有额外排序。判断时看哪些证据字段见 [数据库索引](./index.mdx#执行计划的判断层次)，实测审查流程见[索引设计](./index-review.mdx#7-用-explain-检查推断)。

## 8. 范围定位、下推过滤与覆盖 {#范围定位下推过滤与覆盖}

范围之后的索引列虽然不能缩小区间，但还能在回表之前帮忙过滤。下面用一张独立的示意表说明，优化器最终选不选这条索引，仍取决于数据量和统计信息：

```sql
CREATE TABLE index_demo (
  id BIGINT PRIMARY KEY,
  tenant_id BIGINT NOT NULL,
  status VARCHAR(16) NOT NULL,
  created_at DATETIME NOT NULL,
  payload VARCHAR(200),
  KEY idx_tenant_time_status (tenant_id, created_at, status)
) ENGINE=InnoDB;

EXPLAIN SELECT payload FROM index_demo
WHERE tenant_id = 10 AND created_at > '2026-08-01'
  AND status = 'PAID';
```

`tenant_id` 等值加 `created_at` 范围，定位出一段连续的索引区间。`status` 不能再缩小这段区间，但它就在索引项里。**索引条件下推**（Index Condition Pushdown，ICP）是指存储引擎在扫描索引时，先用索引里已有的列检查条件，不满足的记录直接跳过，不去回表。这里引擎先用 `status = 'PAID'` 过滤，只为剩下的记录回表读 `payload`。`EXPLAIN` 显示的 `Using index condition` 就是这个机制。

如果把返回列改成 `id, created_at, status`，过滤和返回要的列都在索引项里（`id` 是聚簇键，二级索引本来就带着），查询就被覆盖了，Extra 显示 `Using index`。两者回答的是不同问题：`Using index` 说的是索引里的数据够不够用，`Using index condition` 说的是过滤在回表前还是回表后做。

前缀索引是个例外。`name(10)` 这样的索引只保存前 10 个字符，查询要返回完整的 `name` 时，索引里的内容不够，仍然要回表。

## 9. 排序、LIMIT 与列顺序 {#排序limit-与列顺序}

索引本身就是有序的，排序列和索引顺序对上时，数据库可以按索引顺序读，读够 `LIMIT` 条就停，不必先把所有结果取出来再排序。假设主要查询是某租户已支付订单的最新列表：

```sql
SELECT id, created_at
FROM orders
WHERE tenant_id = 10 AND status = 'PAID'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

在索引 `(tenant_id, status, created_at, id)` 上，前两列被等值条件固定后，剩下的记录正好按 `created_at, id` 排列，从末尾反向扫描就是 `DESC` 顺序，读到 20 条即可停止。这里显式写出 `id`，是为了让排序稳定、便于分析；实际设计时要记得 InnoDB 二级索引已经带着主键，避免定义出没有意义的冗余列。

如果查询去掉 `status` 条件，情况就变了。索引里的记录先按状态分组，每个状态组内部按时间有序，但把几组直接拼起来并不是全局的时间顺序。执行计划沿这条索引取出所有状态的结果后，就需要额外排序。要避免排序，可以针对这条查询另建 `(tenant_id, created_at, id)`。排序方向混合（一列升序、一列降序）时，还要核对索引各列定义的升降序。

`LIMIT 20` 限制的是返回行数，不是扫描行数。如果扫描过程中大量记录被其他条件过滤掉，就要读更多索引项才能凑够 20 条；大 `OFFSET` 也要先读过前面被跳过的那些记录。所以实际成本要看执行计划里的扫描量。

## 10. 常见问题 {#7-常见问题}

### 10.1 字符串前缀匹配 {#71-like-abc-会破坏左前缀吗}

不会。对可以直接比较的字符串索引列，`LIKE 'abc%'` 相当于「大于等于 `abc`、小于下一个前缀」的范围，可以在索引上定位。它之后的列能不能继续用，和普通范围条件一样，取决于生成的访问区间。`LIKE '%abc'` 没有固定前缀，以 `abc` 结尾的值分散在整个索引里，只能扫描后逐条过滤。

### 10.2 联合索引与单列访问 {#72-联合索引是否能替代所有单列索引}

不能一概而论。联合索引能用于和它有序前缀匹配的范围定位，也能用于全索引扫描、覆盖查询和满足条件的跳跃扫描。某一列经常被单独查询时，先看现有联合索引给出的扫描范围；范围过宽，再评估单列索引或另一组联合索引。最终要结合读写成本和真实查询频率取舍。

## 11. 面试题 {#8-面试题}

### 11.1 什么是覆盖索引和回表，如何减少回表成本 {#covering-index}

**考察重点**

- 理解 InnoDB 聚簇索引与二级索引的叶子内容。
- 结合具体查询判断索引是否覆盖。
- 理解回表次数、索引宽度和写入成本的权衡。

**相关内容**：[二级索引与回表](#3-二级索引叶子节点保存主键)、[覆盖索引](#4-覆盖索引让查询直接从索引返回)、[主键宽度与索引成本](#5-主键宽度会影响全部二级索引)。

<details>
<summary>参考回答</summary>

**覆盖索引包含查询所需的列；二级索引缺少结果列时，要通过聚簇键读取完整行，这个过程称为回表。**

通过调整联合索引列顺序，或加入少量高频返回列，可以减少扫描和取列回表。覆盖查询仍可能因 MVCC 可见性检查访问聚簇记录，例如二级索引记录有删除标记或页面被较新事务修改时。

索引越宽，存储、缓存和写入成本越高，因此要结合查询频率与实际执行计划判断收益。

</details>

### 11.2 联合索引 (a, b, c) 遇到 a=1、b>10、c=5，哪些列还起作用？ {#left-prefix-range}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 理解复合键的有序区间。
- 理解范围边界与剩余列过滤。

**相关内容**：[联合索引的键顺序](#1-联合索引先按第一列排序)、[范围定位、下推过滤与覆盖](#范围定位下推过滤与覆盖)。

<details>
<summary>参考回答</summary>

**a 的等值与 b 的范围构造扫描区间，c 可用于 ICP 过滤或覆盖取列。**

在 a=1 的分组里，b>10 对应一段连续区间，但区间内的记录先按 b 排，不同 b 值下的 c=5 分散在各处，所以 c 不能再缩小区间。c 仍在索引项里，可以在回表前过滤掉不满足的记录，查询所需列都在索引中时还能直接取值。实际是否这样执行以执行计划为准；把条件写成 c、b、a 的顺序也不会改变索引本身的顺序。

</details>

### 11.3 Using index 和 Using index condition 有什么区别？ {#icp-vs-covering}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 理解覆盖取列与 ICP。
- 理解回表与 MVCC 的边界。

**相关内容**：[范围定位、下推过滤与覆盖](#范围定位下推过滤与覆盖)、[覆盖索引](#4-覆盖索引让查询直接从索引返回)。

<details>
<summary>参考回答</summary>

**`Using index` 表示从索引取得查询所需列。**

`Using index condition` 表示用到了索引条件下推：引擎在取完整行之前，先用索引里的列过滤记录，减少需要回表的记录数。前者回答索引里的数据够不够，后者回答过滤在回表前还是回表后做。覆盖查询在 MVCC 可见性检查需要时，仍可能访问聚簇记录。

</details>

### 11.4 同一个联合索引，为什么加上或去掉一个等值条件会改变排序成本？ {#index-order-limit}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 理解固定前缀后的顺序。
- 理解 LIMIT 与实际扫描量。

**相关内容**：[排序、LIMIT 与列顺序](#排序limit-与列顺序)。

<details>
<summary>参考回答</summary>

**联合索引按列逐级分组，只有前导等值列固定后，后续列的顺序才能直接满足目标排序。**

对 `(tenant_id,status,created_at,id)`，`tenant_id` 和 `status` 都固定时，可直接按后两列取最近记录。去掉 `status` 条件后，各状态组内部有序，直接串接却不保证全局时间顺序。

用执行计划确认是否出现 `filesort`，再决定是否增加适合主要查询的索引；过滤条件和大 `OFFSET` 仍可能增加返回 `LIMIT` 行之前的扫描量。

</details>
