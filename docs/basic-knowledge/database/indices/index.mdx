# 数据库索引

数据库索引通过额外的数据结构缩小读取范围，并为排序和取列提供有序访问路径。本文负责 MySQL 8.4 InnoDB 的索引分类、读取成本和优化器选择；结构细节见 [B+ 树](./b_plus_tree/index.mdx)与[聚簇索引](./clustered_index/index.mdx)，查询推演见[联合索引与覆盖索引](./composite-covering-back-table.mdx)，审查流程见[索引设计](./index-review.mdx)。

## 1. 面试核心 {#core}

- B+ 树通过高扇出减少导航层数，有序叶子支持范围扫描。[卡](#btree-cost)
- InnoDB 的二级索引携带聚簇键，主键越宽，二级索引的空间成本越高。[卡](#cluster-key)
- 联合索引按定义的列顺序排列，`WHERE` 条件的书写顺序独立于索引键顺序。
- MySQL 按扫描、回表和排序成本选择访问路径，低选择性二级索引加大量回表时，全表扫描也能成为最优计划。[卡](#index-not-used)
- `EXPLAIN` 的 `rows` 是估算扫描量，`EXPLAIN ANALYZE` 通过实际执行提供行数、循环次数与耗时。[卡](#index-not-used)

## 2. 索引收益与维护成本 {#1-索引减少需要读取的数据页}

没有可用索引时，数据库需要扫描表中的记录，再逐行判断条件。索引按一个或多个键组织记录位置，使执行引擎可以先定位到目标键或键值范围，再读取相关数据。

数据库以磁盘或缓冲池中的数据页组织数据，减少随机读取、扫描页数、排序和回表次数，才会转化为实际延迟下降。

索引同时带来成本：

- 占用额外存储与缓冲池空间。
- `INSERT`、`UPDATE` 和 `DELETE` 需要维护相关索引。
- 页分裂、日志写入和缓存压力会增加。
- 多个相似索引会提高优化器选择和运维成本。

因此，索引要围绕真实查询及其读取收益创建。

## 3. B+ 树索引 {#2-innodb-常规索引使用-b-树}

InnoDB 的聚簇索引和普通二级索引使用 B+ 树，高扇出减少导航层数，有序叶子支持范围扫描，结构与再平衡机制见 [B+ 树](./b_plus_tree/index.mdx)。

## 4. 索引分类 {#3-索引名称描述不同维度}

索引名称分别表达约束、列组成和存储结构：

- **主键索引**：保证主键唯一且非空；在 InnoDB 中承担聚簇索引。
- **唯一索引**：约束非 NULL 键值唯一，MySQL 8.4 允许多个 `NULL`。
- **普通索引**：不附加唯一性约束。
- **联合索引**：索引键由多列组成，按定义顺序逐级排列。
- **聚簇索引**：叶子记录直接包含完整行数据。
- **二级索引**：InnoDB 叶子记录包含二级索引列和聚簇索引键。
- **覆盖索引**：当前查询需要的列都能从某个索引获得，是查询与索引之间的关系。

一个索引可以同时是唯一索引、联合索引和二级索引；所需列齐全的查询可以被它覆盖。

## 5. 回表与覆盖索引 {#4-二级索引查询可能需要回表}

InnoDB 二级索引查询缺失列时按聚簇键回表，覆盖查询可省去取列回表，查询示例与 MVCC 边界见 [联合索引与覆盖索引](./composite-covering-back-table.mdx#4-覆盖索引让查询直接从索引返回)。

## 6. 联合索引的列顺序 {#5-联合索引按照定义顺序排列}

联合索引按定义的列顺序逐级排列，等值前缀和范围条件共同确定扫描区间，具体推演见 [联合索引与覆盖索引](./composite-covering-back-table.mdx#1-联合索引先按第一列排序)。

## 7. 访问路径与成本估算 {#6-优化器按成本选择访问路径}

创建索引只提供一条候选路径，MySQL 会根据统计信息估算读取页数、结果行数、回表与排序成本。以下因素会影响范围构造或全表扫描与索引访问的成本比较：

1. 对索引列应用函数，而没有匹配的函数索引。
2. 字符串条件以通配符开头，例如 `LIKE '%example.com'`。
3. 联合索引缺少必要的左侧列。
4. 隐式类型转换或排序规则转换改变了可比较方式。
5. 条件选择性很低，二级索引会命中并回表读取大部分记录。
6. `OR` 的某个分支没有合适索引，合并多条路径的成本过高。

范围查询、`!=` 和 `IS NULL` 都具备使用索引的条件，最终选择由数据分布和访问成本决定。应通过 `EXPLAIN` 查看实际访问方式、选中索引和预计扫描行数，再在安全环境使用 `EXPLAIN ANALYZE` 对照实测。

## 8. 索引设计依据 {#7-从查询反推索引}

索引设计依据过滤、关联、排序、返回列与调用频率，完整审查步骤和写入成本评估见 [索引设计](./index-review.mdx#6-从一条查询决定索引怎么建)。

## 9. 聚簇键的选择与维护代价 {#聚簇键的选择与维护代价}

InnoDB 按“主键、第一个全部列非空的唯一索引、隐藏行 ID”选择聚簇键，键宽会放大所有二级索引的开销，选择机制和维护成本见 [聚簇索引](./clustered_index/index.mdx#没有主键时的聚簇索引)。

## 10. 执行计划的判断层次 {#执行计划的判断层次}

| 证据 | 能说明什么 | 解读边界 |
| --- | --- | --- |
| `possible_keys` | 候选查找索引 | 一定使用这些索引 |
| `key` 与 `type` | 选中的索引及访问方式 | 命中索引就很快；`index` 表示全索引扫描 |
| `rows`、`filtered` | 优化器估计的扫描量与过滤比例 | 等于实际行数；统计信息有估算误差 |
| `Using index` | 查询有覆盖访问条件 | 所有并发情况下绝不访问聚簇记录 |
| `Using index condition` | 用索引列先过滤再决定是否取完整行 | 已经覆盖全部返回列 |
| `Using filesort` | 排序不能完全由当前索引顺序提供 | 一定落盘排序 |

`EXPLAIN ANALYZE` 会实际执行受支持的语句并报告迭代器的行数、循环次数和时间，因此应在可控数据量与负载下使用。索引已被使用但仍慢时，继续检查扫描与返回行数的差距、回表次数、排序、锁等待和缓存状态。完整字段解释见 [执行计划](./execution-plan.mdx)。

## 11. 常见问题 {#8-常见问题}

### 11.1 索引数量与维护成本 {#81-索引越多查询就越快吗}

增加索引会增加候选路径，同时增加写放大、磁盘和缓冲池压力；只有新增路径成本更低时，查询才会受益。应保留能稳定改善重要查询的索引。

### 11.2 索引访问与查询耗时 {#82-explain-中出现索引名就说明查询很快吗}

索引名说明选中的访问路径；`type = index` 表示全索引扫描，`rows` 很大也说明仍要读取大量记录。还要看回表、额外排序、临时表和实际执行时间。

### 12.2 B+ 树为什么适合数据库索引，哈希索引能完全替代它吗？ {#btree-cost}

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**

- 页、扇出与树高。
- 等值、范围和排序的访问差异。

**相关内容**：[B+ 树索引](#2-innodb-常规索引使用-b-树)。

<details>
<summary>参考回答</summary>

数据库以页读写，B+ 树内部页集中保存导航项，较高扇出有利于减少定位需要访问的层数；叶子有序，定位后可以继续范围扫描。哈希适合等值定位，却不直接保留键顺序，无法通用地替代范围、排序访问。缓存、键宽、选择性和回表还会改变实际成本。

</details>

### 12.3 InnoDB 没有主键时怎样组织数据，为什么宽主键会增加索引成本？ {#cluster-key}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**

- 聚簇键选择顺序。
- 二级索引携带聚簇键。

**相关内容**：[聚簇键的选择与维护代价](#聚簇键的选择与维护代价)。

<details>
<summary>参考回答</summary>

InnoDB 没有主键时，选择第一个全部列非空的唯一索引，仍不存在时使用隐藏键；宽主键通过二级索引携带的聚簇键增加空间成本。二级索引通过聚簇键定位行，键越宽，二级索引占用的空间越大，可缓存的记录越少。因此主键选择需要同时考虑稳定性、大小、插入分布和唯一性要求。

</details>
