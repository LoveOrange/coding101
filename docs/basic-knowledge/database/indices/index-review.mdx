# 索引设计

**索引设计**是根据真实的查询负载，决定在哪些列上建索引、列按什么顺序排、要不要把返回列也放进去。索引不是越多越好：每多一个索引，写入时就多维护一棵树，读查询的收益要和这笔持续的写入成本放在一起比较。

评估一个索引方案，可以先问：查询条件能不能用上索引的有序性，索引过滤掉的数据够不够多？改完之后，还要用执行计划和实测证明它确实更好。下文以 MySQL 8.0 InnoDB 为准。

## 1. 面试核心 {#core}

- 联合索引里**等值列固定前缀后，紧跟的范围列能同时用于范围过滤和排序**。[卡](#workload-index)
- 查询要返回表中大部分行时，**二级索引加大量回表的成本可能高于直接扫描聚簇索引**，优化器会因此放弃索引。[卡](#explain-slow-sql)
- 前缀索引**只保存字符串的前一段**，查询要返回完整字符串时仍然要回表取行。[卡](#prefix-index-design)
- 不可见索引**默认不参与优化器选择，但写入时照常维护，唯一约束也照常生效**。[卡](#invisible-index)

<span id="1-索引解决了什么问题"></span>

## 2. 索引的作用 {#1-索引解决了什么问题}

索引用额外的空间和写入维护，换来读取时更小的扫描范围。下文都用这张用户表演示查询条件和候选索引：

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  email VARCHAR(255) NOT NULL,
  status TINYINT NOT NULL,
  created_at DATETIME NOT NULL
) ENGINE = InnoDB;
CREATE INDEX idx_users_email ON users(email);
```

有了 `idx_users_email`，按邮箱查用户时就不用扫全表。索引的基本成本见[数据库索引](./index.mdx#1-索引减少需要读取的数据页)。

<span id="2-innodb-怎样通过索引找到一行数据"></span>

## 3. 聚簇键与行定位 {#2-innodb-怎样通过索引找到一行数据}

InnoDB 的完整行存在聚簇索引里，二级索引只保存索引列和聚簇键，查到聚簇键后再回聚簇索引取整行。存储方式见[聚簇索引](./clustered_index/index.mdx)。

<span id="3-为什么常规索引使用-b-树"></span>

## 4. B+ 树索引 {#3-为什么常规索引使用-b-树}

常规索引用 B+ 树组织：上层节点多路分叉，几次查找就能到达叶子；叶子按键值有序并相互链接，适合范围访问。结构与页面调整见 [B+ 树](./b_plus_tree/index.mdx)。

<span id="4-联合索引为什么有最左前缀"></span>

## 5. 联合索引与最左前缀 {#4-联合索引为什么有最左前缀}

联合索引按定义的列顺序逐级排列：先按第一列，第一列相同再按第二列。所以只有从第一列开始连续给出的条件，才能圈出连续的扫描范围。范围、覆盖和 ICP 的推演见[联合索引与覆盖索引](./composite-covering-back-table.mdx)。

<span id="5-有索引为什么没有被选中"></span>

## 6. 索引选择与查询条件 {#5-有索引为什么没有被选中}

建了索引不等于一定会用。优化器会估算每条候选访问路径的总成本，选最便宜的那条，而这些估算依赖统计信息和直方图。索引没被选中，通常是下面三种情况之一：查询条件让索引的有序性用不上，查询没有确定的起点，或者索引过滤不掉多少数据、回表成本反而更高。

### 6.1 函数条件与范围改写 {#51-索引里没有计算结果}

普通索引里存的是列的原始值，不是函数计算后的结果。假设 `created_at` 上有普通索引：

```sql
SELECT * FROM users WHERE YEAR(created_at) = 2026;
```

索引按 `created_at` 原始值排序，`YEAR(created_at)` 的结果并不在索引里，优化器没法用它定位。把条件改写成原始列上的范围，查找边界就直接对应到索引上了：

```sql
SELECT * FROM users
WHERE created_at >= '2026-01-01'
  AND created_at < '2027-01-01';
```

如果工作负载确实需要按表达式查找，MySQL 8.0.13 起支持函数索引，可以显式建立：

```sql
CREATE INDEX idx_users_created_year ON users ((YEAR(created_at)));
```

这个索引保存的是表达式的计算结果，每次写入都要多算一次、多维护一棵树，这部分写入成本也要算进去。

### 6.2 前导通配符 {#52-左侧通配符没有确定的起点}

字符串索引按字符从左到右比较排序，就像字典按首字母排列。

```sql
SELECT * FROM users WHERE email LIKE '%@example.com';
```

前导 `%` 意味着开头可以是任何字符，以 `@example.com` 结尾的邮箱分散在索引各处，找不到扫描的起点。`LIKE 'hello%'` 则有固定的前缀，可以定位到以 `hello` 开头的那一段。如果按后缀检索很频繁，可以把域名单独存成一列，再给这一列建索引。

### 6.3 数据分布与选择性 {#53-索引过滤不掉多少数据}

假设表有 100 万行，其中 90 万行满足 `status=1`。

```sql
SELECT * FROM users WHERE status = 1;
```

走 `status` 上的二级索引，要先找到 90 万个主键，再逐个回聚簇索引取完整行，这些访问分散在各个页上。直接扫描聚簇索引则是顺着叶子一页页读下去。优化器比较两条路径的总成本，很可能选择全表扫描。

不过「很可能」不等于一定，因为成本是按估算的行数算的。在 MySQL 8.4 上用 20 万行、`status=1` 占 90% 的表实测：优化器估计 `status=1` 只有约 10 万行，选了 `status` 索引，实际读了 18 万行，耗时 87ms，强制全表扫描只要 29ms。给 `status` 建直方图也没有改变估算，因为列上有索引时，优化器优先用索引下探（index dive）得到的行数。所以低选择性条件要看 `EXPLAIN ANALYZE` 的实际行数，必要时用 `IGNORE INDEX` 对比两条路径。

同一个索引对 `status=0` 却可能很有效，因为它只对应少量记录。所以验证索引时，测试参数既要有热点值，也要有低频值，只测一种会得出片面的结论。

<span id="6-从一条查询决定索引怎么建"></span>

## 7. 字符串前缀索引 {#字符串前缀索引}

**前缀索引**只对字符串的前若干个字符建索引，用来缩小长字符串列的索引体积：

```sql
CREATE INDEX idx_users_email_prefix ON users(email(20));
```

它节省了键空间，代价是前 20 个字符相同的记录在索引里区分不开，还要回表比较完整值。前缀越短，需要继续检查的候选记录越多。选长度时，可以比较前缀和完整值各自的去重比例，前缀的去重比例接近完整值时，再用实际扫描量验证。

因为索引里没有完整值，前缀索引还有三个限制：查询要返回完整 `email` 时它不能覆盖，按完整字符串排序时它不能单独提供顺序，建成唯一索引时约束的是前缀本身唯一。最后一点最容易踩坑：两个不同的邮箱只要前 20 个字符相同，第二个就插不进去。

## 8. 索引设计步骤 {#6-从一条查询决定索引怎么建}

设计索引要从具体查询出发。假设现在要查最近创建的 20 个正常用户：

```sql
CREATE INDEX idx_users_status_created ON users(status, created_at);
SELECT id, email FROM users
WHERE status = 1 AND created_at >= '2026-01-01'
ORDER BY created_at DESC LIMIT 20;
```

`status = 1` 固定了索引第一列，这一段记录按 `created_at` 排列，于是 `created_at >= '2026-01-01'` 对应一段连续区间，`ORDER BY created_at DESC` 也能直接从区间末尾倒序扫描，拿到 20 条就停。区间内不足 20 行时，扫到区间开头为止。

要不要把 `email` 也加进去做成覆盖索引？加了能省掉回表，但这条查询最多只回表 20 次，收益有限，而索引变宽的写入成本每次插入和更新都要付。这种情况下通常不值得。

这个索引只服务于「先按状态、再按时间」的查询。如果另有查询只按日期过滤，用不上 `status` 前缀，需要单独评估日期索引。几个等值列谁放前面，要看哪些查询需要复用这段前缀；列的基数高低只是参考因素之一。

<span id="7-用-explain-检查推断"></span>

## 9. 执行计划验证 {#7-用-explain-检查推断}

推断完要用执行计划验证，而且要用相同的 SQL 和实际的参数值：

```sql
EXPLAIN SELECT id, email FROM users
WHERE status = 1 AND created_at >= '2026-01-01'
ORDER BY created_at DESC LIMIT 20;
```

重点比较扫描行数、回表行数、有没有额外排序，以及响应时间。字段含义和实际计时的读法见[执行计划](./execution-plan.mdx)。

### 9.1 慢查询验证步骤 {#71-从慢查询得到一个可以验证的结论}

1. 记录实际 SQL、参数、数据规模和调用频率。
2. 用 EXPLAIN 确认索引、扫描范围和排序。
3. 在受控环境用 `EXPLAIN ANALYZE` 记录实际统计。
4. 调整 SQL 或索引后，按相同条件对照测试。
5. 同时比较写入延迟、索引空间和其他高频查询。

计划变了不代表变好了，最后要用实际扫描量和延迟说话，并且热点参数和普通参数都要测到。

## 10. 工作负载与索引维护 {#工作负载与索引维护}

一个索引通常要服务一组查询，而不是一条。设计时把相关查询的过滤列、排序列、返回列和调用频率列出来，看哪些查询能复用同一段前缀，再比较读收益和写成本。

查询参数的类型也要和列一致。字符串列用数字去比较时，MySQL 会把列值转换成数字再比，而 `'1'`、`'01'`、`'1abc'` 这些不同的字符串都能转换成 1，索引里的顺序就对不上了，没法按等值定位。

索引的删除同样需要验证。**不可见索引**（invisible index）是 MySQL 8.0 提供的一种状态：优化器默认忽略它，但写入时照常维护，唯一约束也照常生效。想删一个索引时，可以先把它设为不可见，观察有没有查询变慢；有问题随时改回可见，不用重建。真正删除前，还要确认它没有承担唯一约束，并观察一个完整的业务周期，比如月底才跑的报表。

<span id="8-常见问题"></span>

## 11. 常见问题 {#8-常见问题}

### 11.1 冗余索引的判断 {#冗余索引的判断}

普通索引 `(a)` 通常是冗余的，因为 `(a,b)` 的前缀已经能支持按 `a` 查找；但 `(a)` 更窄，删除前仍要比较两者的实际查询成本。唯一索引不能这样推：唯一索引 `(a)` 要求 `a` 本身不重复，唯一索引 `(a,b)` 只要求 `a`、`b` 组合不重复，允许相同的 `a` 搭配不同的 `b`，所以前者不能被后者替换。

### 11.2 低基数列的索引位置 {#低基数列的索引位置}

可以。低基数列单独建索引过滤效果差，但放在联合索引前面时，它的作用是固定前缀，让后面的列有序可用。例如第 8 节的 `(status, created_at)`，状态固定后按时间倒序取 20 行。是否合适，取决于查询的过滤和排序组合，以及其他查询能不能复用这段前缀。

## 12. 面试题 {#9-面试题}

### 12.1 给定一条慢 SQL，怎样用 EXPLAIN 判断索引是否有效 {#explain-slow-sql}

**考察重点**

- 真实 SQL、参数、数据分布和访问路径。
- `type`、`key`、`rows`、`filtered` 与 `Extra`。
- 联合索引、范围、回表和实测验证。

**相关内容**：[索引选择与查询条件](#5-有索引为什么没有被选中)至[执行计划验证](#7-用-explain-检查推断)。

<details>
<summary>参考回答</summary>

**索引是否有效，要看它是否减少了实际扫描、回表和排序成本，而不能只看 `key` 是否非空。**

先取得真实 SQL、绑定参数和数据分布，用 `EXPLAIN` 核对实际 `key`、估计 `rows`、覆盖和下推情况。再在受控环境用 `EXPLAIN ANALYZE` 检查实际统计。

调整后比较同一负载下的扫描量与延迟，并检查写入成本和其他高频查询，确认整体收益。

</details>

### 12.2 如何为等值、范围和排序同时存在的查询设计联合索引？ {#workload-index}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 键顺序与可复用前缀
- 读写成本和实际计划

**相关内容**：[联合索引与最左前缀](#4-联合索引为什么有最左前缀)、[工作负载与索引维护](#工作负载与索引维护)。

<details>
<summary>参考回答</summary>

**等值列放在前面固定前缀，范围列紧跟其后，同时承担范围扫描和与之兼容的排序。**

例如查询 `status = 1 AND created_at >= ? ORDER BY created_at DESC LIMIT 20`，用 `(status, created_at)` 可以在状态固定后按时间倒序扫描，拿够 20 行就停。范围列之后的列不再有序可用，所以不要把排序列放在范围列后面。要不要加入覆盖列，取决于回表次数和索引变宽的写入成本。其他查询能否复用前缀，也会影响列的顺序，最后用执行计划确认。

</details>

### 12.3 把索引设为不可见，是否会停止维护它并取消唯一约束？ {#invisible-index}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**

- 优化器可用性
- 写入维护与唯一性

**相关内容**：[工作负载与索引维护](#工作负载与索引维护)。

<details>
<summary>参考回答</summary>

**不可见索引仍被维护，唯一约束也仍然生效。**

不可见只影响优化器：它默认不再考虑这个索引，但每次写入仍然要维护它。所以把索引设为不可见，适合用来观察删除它后查询会不会变慢，有问题可以立即改回可见。确认没有退化后，还要核对它是否承担唯一约束，再决定删除。

</details>

<span id="10-扩展阅读"></span>

### 12.4 邮箱前缀索引能覆盖完整邮箱查询并保证完整值唯一吗？ {#prefix-index-design}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：前缀选择性、覆盖能力和唯一性。

**相关内容**：[字符串前缀索引](#字符串前缀索引)。

<details>
<summary>参考回答</summary>

**都不能。前缀索引只保存邮箱的前一段，返回完整值仍要回表取行。**

普通前缀索引不带唯一性约束。唯一前缀索引约束的是前缀唯一，比完整邮箱唯一更严格：两个不同的邮箱只要前缀相同，后插入的就会被拒绝。要保证完整邮箱唯一，应该在完整列上建唯一索引。

</details>
