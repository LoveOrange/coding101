# 执行计划

执行计划描述数据库为查询选择的访问路径与操作顺序。本文以 MySQL 8.4 为例，用 EXPLAIN 判断扫描、连接和排序，再用实际运行证据验证估计。

## 1. 面试核心 {#core}

- `possible_keys` 是候选索引，`key` 是实际选中的索引；全索引扫描也可能很慢。[卡](#slow-indexed-query)
- `rows`、`filtered` 为估计；行数偏差应结合统计信息和数据倾斜判断。[卡](#estimate-statistics)
- `EXPLAIN ANALYZE` 实际执行语句，`actual time` 包括子节点耗时；多次循环显示每次平均值。[卡](#actual-loops)
- `Using filesort` 表示额外排序，不保证落盘；`Using index` 与索引条件下推含义不同。

## 2. 从查询条件到访问路径 {#从查询条件到访问路径}

```sql
CREATE TABLE orders_plan (
  id BIGINT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  created_at TIMESTAMP NOT NULL,
  amount DECIMAL(10,2) NOT NULL
);
CREATE INDEX idx_user_created ON orders_plan(user_id, created_at);

EXPLAIN SELECT id, created_at
FROM orders_plan
WHERE user_id = 7
ORDER BY created_at
LIMIT 20;
```

先按 user_id 定位，再按 created_at 读取，符合该联合索引的排列顺序。InnoDB 二级索引还包含主键 id，因此这个查询具有覆盖索引的可能。是否实际选择它，仍取决于数据规模、分布与优化器成本，不能预先编造固定 EXPLAIN 输出。

## 3. 阅读计划与验证 {#3-阅读计划与验证}

先检查实际选用的 key 和访问类型，再看 rows、filtered 估计留下多少行，最后检查排序、临时表与回表相关信息。传统输出中 `type=index` 可能表示全索引扫描，不代表只定位到少量目标。

`Using index` 常表示查询所需信息可由索引提供；`Using index condition` 表示利用索引条件下推过滤，两者不同。`Using filesort` 表示使用额外排序过程，不等于一定把排序写到磁盘。

对可控只读查询，可进一步用 EXPLAIN ANALYZE 检查实际行数、循环次数与时间，比较估计偏差。慢查询的等待、锁竞争和网络传输还需要其他运行指标配合。

## 4. 实际统计与估算偏差 {#实际统计与估算偏差}

MySQL 8.4 的 `EXPLAIN ANALYZE FORMAT=TREE` 展示迭代器执行树。`actual time=a..b` 分别表示取得首行和完成该迭代器的时间，单位毫秒；存在多次循环时按循环取平均。父节点时间包含子节点，不应把整棵树所有时间相加。内层单次很快但 `loops` 很大，也会使连接昂贵；实际行数与循环数应一起阅读。

`EXPLAIN ANALYZE` 会真正运行语句，支持的多表 UPDATE/DELETE 也可能修改数据。面试和实验优先用受控只读查询，不把它当成普通 EXPLAIN 的无执行模式。

估算明显偏离实测时，检查采样统计是否过时、参数是否命中倾斜热点、列之间是否相关。`ANALYZE TABLE` 更新统计信息，与执行查询并采集时间的 `EXPLAIN ANALYZE` 是不同操作；直方图等统计手段也不能保证所有相关列估算准确。

## 5. 使用边界 {#使用边界}

小表全表扫描可能比索引访问更便宜；索引命中但返回大量行也可能很慢。判断优化时应比较同样参数、数据规模和缓存条件下的实际延迟，而不是只追求计划中的索引名称。

修改索引后还要考虑写入成本、存储和其他查询。存在估计偏差时，先核对统计信息和数据倾斜，避免直接强制索引掩盖根因。
