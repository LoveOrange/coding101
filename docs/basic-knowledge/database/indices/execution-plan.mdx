# 执行计划

**执行计划**是优化器为一条查询选定的执行方式：先读哪张表、用哪个索引、预计扫描多少行、要不要额外排序或建临时表。MySQL 用 `EXPLAIN` 展示这个计划，用 `EXPLAIN ANALYZE` 真正执行一次并给出实际耗时和行数。

查询慢的时候，执行计划是最直接的证据。「用了索引」只说明选中了某个索引，至于扫了多少行、循环了多少次、估算准不准，都要从计划里读出来。读懂它要抓住三点：关键字段和访问类型各说明什么，估计值和实际值怎样对照，以及哪些成本计划本身看不到。下文以 MySQL 8.0 为准。

## 1. 面试核心 {#core}

- `possible_keys` 是**候选索引**，`key` 才是**优化器实际选中的索引**。[卡](#slow-indexed-query)
- `rows × filtered / 100` 估计的是**这一步传给后续连接的行数**。[卡](#estimate-statistics)
- `EXPLAIN ANALYZE` 会**真正执行语句**；一个节点被多次循环调用时，显示的时间和行数是**每次循环的平均值**。[卡](#actual-loops)
- `Using filesort` 表示**当前访问路径的顺序用不上，需要额外排序**。排序数据可以留在内存里，名字里的 file 不代表一定写磁盘。
- `eq_ref` 对每个外层行组合**至多匹配一行**，`ref` **可以匹配多行**。[卡](#access-types)

## 2. 查询条件与访问路径 {#从查询条件到访问路径}

看计划之前，先根据查询条件推一推它应该怎么走，再拿计划来对照。下面的查询按用户过滤，再取最早的 20 条记录：

```sql
CREATE TABLE orders_plan (
  id BIGINT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  created_at TIMESTAMP NOT NULL,
  amount DECIMAL(10,2) NOT NULL,
  KEY idx_user_created (user_id, created_at)
);
EXPLAIN SELECT id, created_at FROM orders_plan
WHERE user_id = 7 ORDER BY created_at LIMIT 20;
```

`user_id = 7` 固定了索引 `idx_user_created` 的第一列，这一段记录正好按 `created_at` 排好，所以可以顺着索引读前 20 条，不用额外排序。二级索引还带着主键 `id`，`SELECT` 要的两列都在索引里，也不用回表。这是理想情况；优化器实际选哪条路径，还取决于数据分布、统计信息和成本估算，所以要看计划确认。

## 3. 执行计划字段 {#3-阅读计划与验证}

读传统 `EXPLAIN` 输出时，按这个顺序看比较省力：先看实际用了哪个索引、用什么方式访问，再用行数估计判断扫描范围，最后看 `Extra` 里有没有额外操作。

| 字段 | 含义 |
| --- | --- |
| `possible_keys` | 能参与查找的候选索引。 |
| `key` | 优化器实际选择的索引。 |
| `key_len` | 所用索引键的最大长度，单位为字节。 |
| `rows` | 单次访问预计检查的行数。 |
| `filtered` | 表条件过滤后预计保留的百分比。 |
| `Extra` | 覆盖、下推、排序和临时表等信息。 |

`key_len` 可以帮你判断联合索引用到了前几列，但要结合列类型、字符集和是否可空来算，可空列还要多算 NULL 标记的开销。它只说明用了哪些键列，扫描了多少行还得看 `rows`。

`Extra` 里最常见的几项：

- `Using index`：查询需要的信息都能从索引拿到，不用回表。
- `Using index condition`：在索引层先过滤，再按需回表取行。两者的执行区别见[联合索引与覆盖索引](./composite-covering-back-table.mdx)。
- `Using filesort`：需要额外排序。内存够用时，排序可以全部在内存中完成。
- `Using temporary`：需要内部临时表。它同样不一定落盘，要结合实际的内存和落盘指标判断。

## 4. 访问类型 {#访问类型}

`EXPLAIN` 的 `type` 列是**访问类型**，描述这张表的行是怎样取到的。下表大致从高效到低效排列，但成本最终还要看扫描量：

| 类型 | 访问方式 |
| --- | --- |
| `const` | 通过主键或非空唯一键与常量比较，至多取得一行。 |
| `eq_ref` | 每个外层行组合通过完整唯一键，至多匹配一行。 |
| `ref` | 按非唯一键或索引前缀等值查找，可匹配多行。 |
| `range` | 扫描索引中的一个或多个范围。 |
| `index` | 扫描索引树，仍需检查大量条目。 |
| `ALL` | 扫描整张表。 |

`index` 容易被误读成「用上了索引所以很快」，其实它是把整棵索引树扫一遍。如果是覆盖查询，它比 `ALL` 少读一些列，但仍然要遍历全部条目。另外在连接里，内层表的访问次数等于外层传过来的行数，即使内层是 `ref`，外层行很多时总成本也会被放大。

## 5. 实际统计与估算偏差 {#实际统计与估算偏差}

传统 `EXPLAIN` 里的行数都是估计值，要知道实际情况，就用 `EXPLAIN ANALYZE`。它从 MySQL 8.0.18 开始提供，会真正执行查询，并以树的形式展示每个迭代器的实际统计；8.0.21 起可以显式写 `FORMAT=TREE`。

读这棵树时注意几点：

- `actual time=a..b` 的单位是毫秒，`a` 是返回第一行的时间，`b` 是这个迭代器全部执行完的时间。
- 一个节点被循环调用多次时，显示的时间和行数是**每次循环的平均值**，`loops` 是调用次数。单次 0.1ms 的内层查找循环 10000 次，就累积到 1 秒左右。用 `rows × loops` 可以估出总输出行数。
- 父节点的时间已经包含子节点，把整棵树各节点的时间加起来会重复计算。

因为会真正执行，`EXPLAIN ANALYZE` 要小心使用。MySQL 8.0 还支持用它分析多表 `UPDATE` 和 `DELETE`，这些语句会实际修改数据，实验应该在独立的练习库里做。

估计行数和实际行数差得很远时，优化器可能因此选错索引或连接顺序。排查时先看实际参数和数据倾斜：同一条 SQL 换一个热点值，命中行数可能差几个数量级。再看统计信息是不是过时了，过滤列之间是否相关。`ANALYZE TABLE` 用来更新表的统计信息，和执行查询并计时的 `EXPLAIN ANALYZE` 是两回事。

直方图可以补充单列的值分布，但多列之间的相关性它表达不了，仍然要用实际查询验证。

## 6. 使用边界 {#使用边界}

计划里出现全表扫描不一定是问题。小表全表扫描省去了索引定位的开销；查询要返回大部分行时，顺序扫描也比逐条回表便宜。比较优化前后的效果，要用相同的参数、数据规模和缓存条件。

执行计划解释的是数据库内部怎样访问数据。锁等待、客户端取数和网络传输的耗时它看不到，要结合运行指标查。新增索引对写入的代价，由[索引设计](./index-review.mdx)来评估。

**考察重点**

- 迭代器循环次数
- 包含关系与平均时间

**相关内容**：[实际统计与估算偏差](#实际统计与估算偏差)。

<details>
<summary>参考回答</summary>

**显示的是每次循环的平均耗时，内层迭代器被反复调用时，总耗时要乘以调用次数。**

`loops` 表示调用次数，单次 0.1ms 循环 10000 次就是 1 秒左右。父节点的时间已经包含子节点，要按包含关系读，不能把各节点相加。减少外层传入的行数，就能直接减少内层调用次数。

</details>

### 7.4 EXPLAIN 的 eq_ref、ref、range、index 和 ALL 有何区别？ {#access-types}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：访问方式、唯一键与扫描范围。

**相关内容**：[访问类型](#访问类型)。

<details>
<summary>参考回答</summary>

**这些访问类型描述定位和扫描记录的方式，成本还要结合扫描量、覆盖情况与循环次数判断。**

- **`eq_ref` 是通过完整唯一键的等值查找**，每个外层行组合至多匹配一行。
- **`ref` 是非唯一键或索引前缀的等值查找**，每个外层行组合可以匹配多行。
- **`range` 扫描索引中选定的范围**，只访问这些区间。
- **`index` 和 `ALL` 分别扫描整棵索引树和整张表**。`index` 是否更省，取决于索引宽度和是否覆盖查询。

</details>
