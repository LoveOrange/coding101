# I/O 模型

**I/O 模型**描述调用者如何等待数据、发起读写并取得结果。以 Linux socket 为例，非阻塞读取在没有数据时会立即返回，但应用仍要自己再次调用读取；异步 I/O 则先提交操作，之后再取得完成结果。理解这一区别，才能解释非阻塞为什么不等于异步，以及事件通知之后还需要做什么。

## 1. 面试核心 {#core}

- socket 没有数据可读时，阻塞读取会等待，非阻塞读取则以 `EAGAIN` 等错误返回，**由应用稍后重试**。[卡](#blocking-vs-nonblocking)
- **就绪通知后还要执行读写**；完成通知则交付此前已提交操作的结果，两者处在不同阶段。
- 对正长度的 TCP `recv`，正数表示读到的字节数，**0 表示对端已关闭发送方向且数据已读完**，`EAGAIN` 只表示暂时没数据。[卡](#socket-read-results)
- `send` 可能只接受一部分字节，应用要**保留尚未发送的部分**，等可写后继续发送。

## 2. 等待数据与执行读取 {#等待数据与执行读取}

一次网络读取要分清两件事：数据是否已经进入接收缓冲区，以及应用是否已经把字节读出来。网络数据经协议栈进入缓冲区后，应用还要调用 `read` 或 `recv` 才能取得它。

**阻塞 I/O** 允许调用在数据暂不可用时等待，让线程停在这次读取上。**非阻塞 I/O** 则不等待数据到来：socket 设置 `O_NONBLOCK` 后，如果当前没有数据，就返回暂不可用的错误。

非阻塞改变的是没数据时的行为。真正读到数据时，结果仍由本次系统调用返回，而且一次读取可能只拿到应用所需数据的一部分。

TCP 的消息拆分由应用协议负责，见 [RPC](../network/rpc-serialization-netty-event-loop.mdx#半包与粘包)。

## 3. 就绪与完成 {#就绪与完成}

**就绪通知**告诉应用现在可以尝试读写，操作还要由应用发起；**完成通知**则告诉应用，之前提交的操作已经结束，可以查看结果。两种流程的区别如下：

```text
就绪模型：等待可读 → 调用 recv → 使用返回字节
完成模型：提交读取 → 获取完成结果 → 使用结果缓冲区
```

| 模型 | 调用者行为 |
| --- | --- |
| 阻塞 I/O | 调用时等待数据与操作结果。 |
| 非阻塞 I/O | 暂不可用时返回，调用者稍后重试。 |
| I/O 多路复用 | 等待多个对象就绪，再执行读写。 |
| 信号驱动 I/O | 通过信号获知 I/O 就绪，再执行读写。 |
| 异步 I/O | 提交操作，再通过完成机制取得结果。 |

**Reactor** 是分派就绪事件的模型，事件处理器收到通知后调用读写接口。**Proactor** 分派的是操作完成结果，处理器接手结果继续工作。

这描述的是应用看到的接口：一个库也可以让线程池执行阻塞操作，完成后再通知调用方。因此，看到回调或异步接口，还不能据此认定内核采用了哪种 I/O 方式。

Linux `io_uring` 通过提交队列接收操作，通过完成队列交付结果。应用提交读取后，操作可能还在使用缓冲区，所以必须让缓冲区保持有效，收到对应完成结果后才能安全复用。

## 4. 读取结果与部分写入 {#读取结果与部分写入}

判断一次读取发生了什么，要看返回值和错误码。下面针对请求读取长度大于 0 的 TCP `recv`：

| 返回值 | 含义与处理 |
| --- | --- |
| 大于 0 | 取得部分或全部可读字节，交给协议缓冲区。 |
| 等于 0 | 对端有序关闭发送方向，且此前数据已读完。 |
| -1，EAGAIN / EWOULDBLOCK | 当前无可读数据，回到事件等待。 |
| -1，EINTR | 操作在返回数据前被信号中断，可按取消策略重试。 |
| 其他错误 | 按具体错误清理或恢复连接。 |

表中的 0 不能直接套到 UDP 上。UDP 允许零长度数据报，`recv` 返回 0 也可能只是收到了一个空数据报，并不表示连接结束。解释返回值前，要先明确 socket 类型。

写入也要检查实际接受了多少字节。例如准备发送 1000 字节，非阻塞 `send` 返回 300，表示内核只接受了前 300 字节，剩余 700 字节要保留，等可写后继续发送。如果返回 `EAGAIN`，则保留全部尚未发送的数据。

## 5. 使用边界 {#使用边界}

没有数据时不断重试 `EAGAIN`，线程仍会占着 CPU 做无用检查。用事件等待可以让它在没有工作时休眠，有就绪事件再继续。事件循环中的处理也应保持短小，慢业务交给其他执行资源，否则一个处理器就会拖住其他连接。

socket 的非阻塞规则不能直接套用到普通文件。Linux 普通文件上的 `O_NONBLOCK` 不会消除磁盘等待，读写需要等待设备时仍可能阻塞。因此，讨论非阻塞必须说明操作对象和系统调用。

## 6. 面试题 {#面试题}

### 6.1 阻塞和非阻塞 I/O 有什么区别，非阻塞是否就等于异步？ {#blocking-vs-nonblocking}



**考察重点**：暂不可用时的返回行为、就绪通知与异步完成的区别。

**相关内容**：[面试核心](#core)、[等待数据与执行读取](#等待数据与执行读取)、[使用边界](#使用边界)。

<details>
<summary>参考回答</summary>

**阻塞读取会等待数据，非阻塞读取在暂不可用时返回；非阻塞不等于异步。**

非阻塞 `recv` 返回 `EAGAIN` 后，应用还要稍后再次调用它，成功时也是通过这次调用取得字节。异步 I/O 则先提交读取，之后取得该操作的完成结果。区别在于暂时无法完成时如何返回，以及最终结果通过什么方式交付。

</details>

### 6.2 非阻塞 recv 返回 0、EAGAIN 和部分数据时分别怎样处理？ {#socket-read-results}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：TCP EOF、暂不可用与协议缓冲。

**相关内容**：[读取结果与部分写入](#读取结果与部分写入)。

<details>
<summary>参考回答</summary>

**对正长度 TCP `recv`，0 表示对端已关闭发送方向且此前数据已读完；`EAGAIN` 表示暂时没数据；正数表示本次读到的字节数。**

遇到 0，应按协议处理 EOF，不能继续当作「稍后会有数据」等待。遇到 `EAGAIN`，回到事件等待；读到部分字节时，先放进协议缓冲区，再判断是否已组成完整消息。UDP 的空数据报也会返回 0，需要另行区分。

</details>

### 6.3 Reactor 与 Proactor 的事件分别表示什么？ {#reactor-proactor}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：就绪分派和操作完成。

**相关内容**：[就绪与完成](#就绪与完成)。

<details>
<summary>参考回答</summary>

**Reactor 分派就绪事件，处理器随后执行读写；Proactor 分派已完成 I/O 的结果。**

前者收到通知时仍需调用读取接口，后者接手的是操作结果。异步操作使用的缓冲区必须保持有效，直到操作完成。库也可以用线程池包装阻塞 I/O，向外提供异步接口，因此接口形式和内核执行方式要分开判断。

</details>
