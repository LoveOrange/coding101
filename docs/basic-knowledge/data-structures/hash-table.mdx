# 哈希表

**哈希表**是一种按键存取的结构：先用键的哈希值算出它应该放在数组的哪个位置，再在这个位置上比较键是否相等。分布均匀时，一次查询只需要检查很少几个候选，期望时间是 O(1)。

O(1) 是有条件的。不同的键落到同一位置（冲突）时怎么办，什么时候扩容、扩容为什么要迁移所有条目，都影响着哈希表的成本。键的哈希和相等关系还必须满足一定的约定，否则存进去的东西会再也找不到。

## 1. 面试核心 {#core}

- 哈希分布均匀、负载受控时，哈希表**查询的期望时间是 O(1)**；所有键挤在一起时，最坏会退化到 O(n)。[卡](#lookup-complexity)
- 处理冲突有两种主要方式：**链地址法**把冲突的条目放在同一个桶里，**开放寻址**沿着预定的探测序列寻找其他空位。
- 线性探测删除条目时，**不能直接把位置标空**，要用墓碑保留探测路径，或者重新整理后面的条目。[卡](#open-addressing-delete)
- 手写链式哈希表时，**覆盖不增计数，扩容按新容量重新定位**；迁移节点前保存旧后继，才能保留碰撞链的所有条目。[卡](#implement-chained-map)
- **相等的键必须有相同的哈希值**，而且参与哈希和相等判断的字段，在键存放期间**必须保持不变**。[卡](#mutable-hash-key)

## 2. 哈希函数与定位 {#哈希函数与定位}

**哈希函数**把键转换成一个整数，称为哈希值。哈希值的范围通常远大于数组的容量，所以还要结合容量把它压缩成一个合法的下标：

```text
index = compress(hash(key), capacity)
```

在同一张表的存续期间，键的相等状态没有改变时，哈希结果应保持一致，否则存进去和查出来会去不同的位置。这不意味着不同进程或不同次运行必须得到相同哈希值。哈希值分布越均匀，每个位置上的条目越少，查询时需要比较或探测的次数也越少。

由于数组的位置有限，而可能的键要多得多，总会有不同的键被映射到同一个位置，这叫**哈希冲突**。冲突是正常情况，哈希表的设计就是要妥善处理它。

## 3. 冲突处理 {#冲突处理}

### 3.1 链地址法 {#链地址法}

**链地址法**让数组的每个位置关联一个桶，冲突的条目都放进同一个桶里。查询时先定位到桶，再在桶里逐个比较键是否相等。

```text
0 → [A]
1 → [B] → [C]
2 → 空
```

上图中 B 和 C 的位置都是 1，它们在同一个桶里，查 C 时要先比较 B 再比较 C。桶可以用链表、动态数组甚至树来实现。链式节点除了条目本身，还要额外存储链接和对象头，占用更多空间。有些容器会在桶里条目过多时把链表转成树，具体在什么条件下转换属于容器实现的细节，还和键能否比较大小有关。

### 3.2 开放寻址 {#开放寻址}

**开放寻址**不使用额外的桶，所有条目都放在同一个数组里。目标位置被占用时，就按预定的**探测序列**检查下一个位置，直到找到空位。最简单的**线性探测**每次往后走一格，缺点是冲突的条目容易连成一片，后来的键要走更长的路。

删除是开放寻址的难点。假设 A 和 B 的起始位置相同，A 先插入，B 因为冲突被放在 A 后面一格。如果删除 A 时直接把它的位置标为空，之后查询 B 时，会从起始位置出发，看到空位就以为 B 不存在，提前结束。

解决方法有两种。一种是放一个**墓碑**，表示「这里删过东西，查询要继续往后找」，插入时可以复用这个位置。另一种是删除后把后面受影响的条目重新插入一遍，恢复正确的布局。墓碑的代价是它会让探测路径越来越长，所以扩容或重建时要清理掉墓碑，只重新放置有效的条目。

## 4. 负载因子与扩容 {#负载因子与扩容}

**负载因子**是 `α=元素数量/槽位数量`，衡量表有多满。链地址法的桶能装多个条目，所以 α 可以大于 1；开放寻址的条目都在数组里，α 不会超过 1。前面这种遇到空位才结束的查询，需要保留真正的空位；如果允许表满，就必须另外限制探测次数等，保证查找不存在的键时也能停止。实际实现会控制负载，避免探测接近扫描整张表。

α 越高，冲突越多，桶越长或探测越远，所以哈希表会在 α 超过阈值时扩容。扩容不能只把旧数组复制过去：下标的计算用到了容量，容量一变，同一个键算出的位置也变了，所有条目都要按新容量重新定位。单次扩容是 O(n)，但和动态数组一样，容量倍增时累计的迁移成本平均到每次插入上是常数，可以按摊销来分析。

### 4.1 最小链式哈希表实现 {#最小链式哈希表实现}

**手写哈希表要把定位、键比较、链接修改和扩容接成一条完整的执行路径。** 下面用 Java 实现一张单线程的 `int → int` 表，冲突时使用单链表。键和值的类型是教学选择，不要求把生产容器的所有接口都实现出来。

先约定返回值，避免用 0 同时表示“键不存在”和“值恰好为 0”：

| 方法 | 返回约定 |
| --- | --- |
| `get(key)` | 返回当前值；不存在返回 `null` |
| `put(key, value)` | 覆盖时返回旧值；新键返回 `null` |
| `remove(key)` | 删除成功返回旧值；不存在返回 `null` |
| `size()` | 返回当前键的数量，覆盖不增加数量 |

方法返回 `Integer` 是为了容纳缺失标记 `null`，实际存储的值仍是 `int`，不接受空值。键按整数值相等判断，负数和整数两端也都是合法键。

```java
static final class IntMap {
    private static final class Entry {
        final int key;
        int value;
        Entry next;
        Entry(int key, int value, Entry next) {
            this.key = key;
            this.value = value;
            this.next = next;
        }
    }

    private Entry[] buckets = new Entry[4];
    private int size;

    int size() { return size; }

    private static int index(int key, int capacity) {
        int hash = key ^ (key >>> 16);
        return hash & (capacity - 1);
    }

    Integer get(int key) {
        for (Entry e = buckets[index(key, buckets.length)]; e != null; e = e.next) {
            if (e.key == key) return e.value;
        }
        return null;
    }

    Integer put(int key, int value) {
        int i = index(key, buckets.length);
        for (Entry e = buckets[i]; e != null; e = e.next) {
            if (e.key == key) {
                int previous = e.value;
                e.value = value;
                return previous;
            }
        }
        if (size >= buckets.length - buckets.length / 4) {
            grow();
            i = index(key, buckets.length);
        }
        buckets[i] = new Entry(key, value, buckets[i]);
        size++;
        return null;
    }

    Integer remove(int key) {
        int i = index(key, buckets.length);
        Entry previous = null;
        for (Entry e = buckets[i]; e != null; e = e.next) {
            if (e.key == key) {
                if (previous == null) buckets[i] = e.next;
                else previous.next = e.next;
                e.next = null;
                size--;
                return e.value;
            }
            previous = e;
        }
        return null;
    }

    private void grow() {
        if (buckets.length == (1 << 30)) {
            throw new IllegalStateException("capacity limit");
        }
        Entry[] expanded = new Entry[buckets.length * 2];
        for (Entry head : buckets) {
            for (Entry e = head; e != null; ) {
                Entry next = e.next;
                int i = index(e.key, expanded.length);
                e.next = expanded[i];
                expanded[i] = e;
                e = next;
            }
        }
        buckets = expanded;
    }
}
```

`buckets` 初始长度为 4，每次翻倍，所以容量一直是 2 的幂。`hash & (capacity - 1)` 保留对应的低位，得到合法的非负下标，不需要对负哈希取绝对值。`key ^ (key >>> 16)` 把部分高位信息混入低位，避免完全只看原键的最低几位；它并不能保证任意输入分布均匀，也不提供对恶意碰撞的保护。

`put` 先沿桶比较键。找到旧键就只更新 `value`，不增加 `size`，也不因为覆盖而扩容。没找到才准备插入新节点。这里把最大负载设为 0.75：容量为 4 时已有 3 个键，插第 4 个之前先扩成 8；扩容后必须重新计算这个新键的下标，不能继续使用旧容量下的 `i`。

`get` 和 `remove` 也必须比较完整键，不能认为落入同一桶就相等。例如依次插入键 0、4、8，在初始容量 4 时，它们都会进入桶 0，头插后形成 `8 → 4 → 0`。删除 4 只让 8 的 `next` 跳过 4，0 仍可访问；删除 8 则要更新桶头。删除不存在的键不改变链接和数量。链地址法不依赖“空槽结束后续探测”的规则，因此这里不需要开放寻址的墓碑。

扩容时，`grow` 逐个把旧节点接入新桶，不创建另一套键值条目，也不改变 `size`。迁移前先保存 `next`，因为接入新桶会覆盖 `e.next`；忘记保存就会丢失旧链的剩余部分。以 0、4、8 为例，容量从 4 变成 8 后，4 移到桶 4，0 和 8 留在桶 0，不能只把原桶链表整体复制到新数组。

扩容扫描旧桶和全部条目。由于本实现只在负载达到阈值、准备增加新键时扩容，此时容量与条目数同阶，一次迁移为 O(n)；倍增迁移的累计成本可以摊还到插入上。查询、覆盖和删除仍受桶长影响，所有键冲突时最坏 O(n)。固定的混合函数不等于随机哈希，不能脱离输入分布直接保证每次常数时间。

这份实现不缩容，空间为 O(容量+n)；大量删除后，空桶数组仍会保留。容量到 `1 << 30` 后，下一次需要增长的插入会报错，防止翻倍发生整数溢出，这不是对可用内存的承诺，实际分配可能更早失败。它也没有迭代器、并发控制或树化桶。验证重点是每个键恰好出现一次、都在当前容量算出的桶中、链表无环、`size` 与节点数一致，以及多轮扩容后旧键值仍然可查。

## 5. 复杂度 {#复杂度}

查询期望 O(1) 依赖三个前提：哈希分布均匀，负载因子受控，以及计算哈希和比较键本身是常数成本。如果所有键都落进同一个用链表实现的桶，查询就要逐个比较，最坏是 O(n)。开放寻址里很长的探测序列也会造成线性成本。

键本身的成本也要算进去。比如长度为 k 的字符串，第一次计算哈希要扫描全部 k 个字符，是 O(k)；比较两个键是否相等同样可能需要 O(k)。遍历的成本也不只看元素数：Java 21 的 `HashMap` 文档说明，遍历它的时间与容量和元素数之和成正比，所以初始容量设得过大会拖慢遍历。

## 6. 键的相等关系 {#键的相等关系}

哈希表靠两步找到条目：用哈希值定位，再用相等判断确认。所以两者必须一致：**相等的键必须产生相同的哈希值**，否则两个相等的键会被放到不同位置，查询时找不到。反过来，哈希值相同的键不一定相等，仍然要比较内容。

键放进表以后，参与哈希或相等判断的字段不能再改。假设用一个对象当键，存进去之后修改了它参与哈希的字段，再用它查询时，会按新的哈希值去新的位置找；而条目还留在按旧哈希值算出的位置，于是查找失败，这个条目也很难再被删除。用不可变对象作为键，可以从根本上避免这个问题。

## 7. 使用场景 {#使用场景}

哈希表适合按键查值、去重、计数和分组。它的位置由哈希值决定，和键的大小无关，所以不提供任何顺序。需要范围查询或按大小遍历时，用有序树；需要保留插入顺序时，可以额外用链表维护顺序。

哈希表本身不保证并发安全，也不保证「先查再写」这类多步操作的原子性。这些要靠具体容器的实现（比如并发容器）和调用方遵守的协议来保证。

## 8. 常见问题 {#常见问题}

### 8.1 哈希冲突 {#哈希冲突}

哈希冲突会导致数据出错吗？不会。冲突只表示不同的键被映射到了同一个位置，哈希表仍然会通过相等判断区分它们，结果是正确的。冲突影响的是性能：冲突越多，比较和探测的次数越多。哈希函数的稳定性决定结果是否正确，分布质量决定性能好坏。

### 8.2 范围查询 {#范围查询}

哈希表为什么不适合范围查询？因为条目按哈希值定位，键的大小和它所在的位置没有关系，相邻的键可能分散在数组的任何地方。要找一个区间内的键，只能扫描全部条目。有序树按键的大小组织，可以直接跳过区间外的子树。

### 8.3 扩容迁移 {#扩容迁移}

扩容时为什么不能直接复制旧数组？因为新容量改变了下标的计算规则，旧条目在新数组里的位置和原来不同，必须重新分布。迁移时是否需要重新计算哈希值，取决于实现是否缓存了哈希值。

### 9.1 哈希查询为何期望 O(1)，最坏却为 O(n)？ {#lookup-complexity}

**相关内容**：[复杂度](#复杂度)。

<details>
<summary>参考回答</summary>

**哈希分布均匀、负载因子受控时，每次查询期望只需检查常数个候选，所以是 O(1)。**

这个结论依赖分布假设。如果 n 个键都落进同一个线性结构的桶，查询就要逐个比较，需要 O(n) 次；开放寻址的探测序列过长也一样。另外，键本身的哈希计算和相等比较也有成本，比如长字符串键需要按长度另算。

</details>

### 9.2 线性探测删除条目为何要保留墓碑或整理条目？ {#open-addressing-delete}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：探测路径与查询终止。

**相关内容**：[开放寻址](#开放寻址)。

<details>
<summary>参考回答</summary>

**直接标空会截断后面冲突键的探测路径，让查询提前结束。**

线性探测的查询遇到空位就停止。如果 B 因为和 A 冲突而放在 A 后面，删除 A 时把位置标空，再查 B 就会在这里停下，误以为 B 不存在。墓碑告诉查询继续往后找；另一种做法是把后面受影响的条目重新插入，恢复从起始位置可达的布局。墓碑积累多了会拉长探测路径，需要在重建时清理。

</details>

### 9.3 修改已入表键的字段，为何会查找失败？ {#mutable-hash-key}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：哈希值、相等关系与存储位置。

**相关内容**：[键的相等关系](#键的相等关系)。

<details>
<summary>参考回答</summary>

**参与哈希的字段改变后，查询会按新的哈希值去新的位置找，而条目还留在旧位置。**

条目的位置是插入时按当时的哈希值决定的，之后不会自动移动。所以修改键以后，用它查询会定位到别处，查找失败。作为键使用期间，参与哈希和相等判断的字段应保持不变，最好直接使用不可变对象作为键。

</details>

### 9.4 怎样实现一个支持查询、写入、删除和扩容的哈希表？ {#implement-chained-map}

**考察重点**：桶定位、键比较、碰撞链修改、返回约定和扩容迁移。

**相关内容**：[链地址法](#链地址法)、[最小链式哈希表实现](#最小链式哈希表实现)。

<details>
<summary>参考回答</summary>

**用桶数组定位，用桶内链表区分冲突键，达到负载阈值时重新分配所有条目的位置。** 查询沿桶比较键；写入已有键时只覆盖值，新键才接入链并增加计数；删除时维护前驱，目标在链首则更新桶头。

扩容改变了下标计算所用的容量，必须逐条迁移，并先保存旧后继再重接节点。迁移不改变键值和数量。正文使用整数键值、以 `null` 表示缺失，负载上限 0.75，不提供并发和缩容；这些是示例约定，不是所有哈希表的统一规范。

边界验证应覆盖碰撞、覆盖已有值、缺失键、删除链首中尾、空表与整数极值，还要在多次扩容后检查所有键值和计数，不能只测没有冲突的插入。

</details>
