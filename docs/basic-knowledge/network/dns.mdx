# DNS

**DNS**（Domain Name System）是把域名翻译成 IP 地址等信息的查询系统。它按名称层级分工：各个区域的服务器维护自己的记录，上级通过委派告诉解析器下一步该去问谁。

实际工作里，DNS 带来的典型问题是：改了 DNS 记录，为什么还有人访问旧地址；新加了域名，为什么还是查不到。要答好这些问题，需要抓住三点：一次解析会经过哪些服务器，每一层缓存能保留多久，以及解析成功之后连接层面还会发生什么。

## 1. 面试核心 {#core}

- A 和 AAAA 记录分别提供 **IPv4 和 IPv6 地址**，CNAME 记录提供的是**另一个名称**，解析器还要接着查这个名称。
- 客户端把问题交给递归解析器，递归解析器**先查缓存，缺少答案时沿委派查询权威服务器**，最后把完整答案交回客户端。[卡](#dns-resolution)
- TTL 决定一条记录**通常可以缓存多久**。改记录之后，各级缓存仍可能在剩余 TTL 内返回旧值；已经建立的连接也不会因为 DNS 变了就断开。
- NXDOMAIN 表示**名称不存在**，NODATA 表示**名称存在但没有所查类型的记录**，两种否定答案都可以被缓存，时长由 SOA 记录决定。[卡](#dns-negative-cache)
- DNS 同时使用 UDP 和 TCP。UDP 响应**被截断（TC 位）时改用 TCP 重查**，超过 512 字节不等于必须走 TCP，EDNS 可以声明更大的 UDP 报文。[卡](#dns-tcp-fallback)

## 2. 资源记录 {#资源记录}

**资源记录**（resource record）是 DNS 保存的一条数据，包含名称、类型、TTL 和具体内容。**TTL** 是记录的缓存期限，以秒为单位。查询时，客户端同时说明要查哪个名称和哪种类型。常见类型如下：

| 类型 | 含义 |
| --- | --- |
| A / AAAA | 名称对应的 IPv4 / IPv6 地址。 |
| CNAME | 名称的别名目标，解析器继续查询目标记录。 |
| NS | 区域的权威服务器。 |
| MX | 邮件服务器及其优先级。 |
| SOA | 区域管理信息，包括负缓存所需参数。 |

CNAME 的目标是另一个名称，而不是地址。比如 `www.example.com` 的 CNAME 指向 `example.cdn-provider.net`，解析器拿到这个名称后，还要继续查它的 A 或 AAAA 记录才能得到地址。别名记录和目标记录各有自己的 TTL，分别缓存、分别过期。

## 3. 递归与迭代查询 {#递归与迭代查询}

一次完整的解析分两段：客户端向递归解析器发起递归查询，递归解析器再向各级权威服务器做迭代查询。

应用通常不直接发 DNS 报文，而是调用操作系统的解析接口。系统先按自己的配置检查 hosts 文件和本地缓存，确实需要查询时，才把问题发给配置好的**递归解析器**，比如运营商或公司内网提供的 DNS 服务器。客户端对它的要求是「把最终答案给我」，这叫**递归查询**。

递归解析器先看自己的缓存，有有效记录就直接返回。没有可用的答案或委派缓存时，它从根开始一层层问下去：

```text
客户端 → 递归解析器
           → 根：返回顶级域的委派
           → 顶级域：返回目标区域的委派
           → 权威服务器：返回记录或别名
```

这里的**委派**是指上一层告诉你「这一段归哪些服务器管」，也就是返回下一层的 NS 记录。根服务器不知道 `www.example.com` 的地址，但知道 `.com` 归谁管；`.com` 的服务器也不知道最终地址，但知道 `example.com` 的权威服务器是谁。**迭代查询**是解析器逐个询问服务器：对方有答案就返回答案，没有答案就返回下一步该问的服务器。解析器自己继续查询，直到拿到结果。

委派信息本身也会被缓存。递归解析器已经知道 `.com` 和 `example.com` 的权威服务器时，下次就可以跳过根和顶级域，直接问权威服务器。所以实际的查询往往比上图短得多。

## 4. 缓存与服务切换 {#缓存与服务切换}

改 DNS 记录不会立刻对所有人生效：各级缓存可能在剩余 TTL 内继续返回旧记录，已经建立的连接也会继续用旧地址。

假设旧地址的 TTL 是 300 秒。权威服务器改成新地址的那一刻，某个递归解析器可能刚刚缓存了旧值，它会在接下来最多 300 秒里继续返回旧地址。如果想让切换更快，可以提前把 TTL 调低，比如调到 60 秒。但调低本身也要生效：已经缓存的旧记录还带着 300 秒的 TTL，所以至少要等旧 TTL 过完，再改地址。

即使解析已经返回新地址，连接池里建好的连接仍然连着旧实例。复用这些连接时，不会因为 DNS 记录改变就自动切到新地址。因此切流时还要考虑连接的最长寿命，让旧实例逐步排空，并让新旧两组端点同时服务一段时间，直到旧实例上不再有流量。

## 5. 负缓存 {#负缓存}

「查不到」的结果也会被缓存，这叫**负缓存**。否定答案有两种，需要分开看。

- **NXDOMAIN** 表示查询的名称根本不存在。
- **NODATA** 表示名称存在，但没有请求的那种记录。

比如某个名称只配了 A 记录，没有 AAAA 记录。客户端查 AAAA 时得到的是 NODATA，这只说明它没有 IPv6 地址，不能理解成整个名称不存在。

负缓存能保留多久，由区域的 SOA 记录决定。RFC 2308 规定取 SOA 记录自身的 TTL 与 SOA 中 MINIMUM 字段的较小值，解析器还可以再加一个本地上限。所以新增域名之后可能仍然查不到：如果在此之前有人查过它，解析器缓存了 NXDOMAIN，那么在负缓存到期之前，这个解析器仍然会告诉客户端名称不存在。

## 6. DNS 传输 {#dns-传输}

传统 DNS 在 UDP 和 TCP 上都使用 53 端口，平时的查询走 UDP，答案放不下时再改用 TCP。

UDP 查询只需要一来一回，开销小，所以是默认选择。但 UDP 报文的大小有限制：没有使用 EDNS 时，DNS 消息不能超过 512 字节。**EDNS** 是 DNS 的扩展机制，客户端可以通过它声明自己能接收更大的 UDP 报文。所以「超过 512 字节就必须改用 TCP」并不准确，客户端通过 EDNS 声明了更大的接收上限、服务端也能支持时，答案仍然可以走 UDP。

答案仍然放不下时，服务器会在 UDP 响应里设置 **TC 位**（truncated），表示响应被截断了。客户端看到 TC 位，再用 TCP 重新查询，取得完整答案。另外，区域传送 AXFR 一直使用 TCP。RFC 7766 要求完整的 DNS 实现必须支持 TCP，所以防火墙只放行 UDP 53 会导致大响应查询失败。

## 7. 使用边界 {#使用边界}

DNS 的安全扩展分两类，各管一件事。**DNSSEC** 给记录加签名，让解析器能验证记录确实来自区域的所有者、中途没被篡改。**DoT**（DNS over TLS）和 **DoH**（DNS over HTTPS）加密客户端到解析服务之间的传输，防止路上的人看到或改动查询。加密通道只保护传输过程，解析服务本身给的答案是否可信，还得靠 DNSSEC 或者对解析服务的信任。

还要记住，解析成功只完成了地址发现。例如通过 HTTP/1.1 访问 HTTPS 站点，拿到地址后还要建立 TCP 连接、完成 [TLS](./tls.mdx) 握手、发送 HTTP 请求，任何一步都可能失败。排查「访问不了」时，先确认是解析失败，还是解析成功但后续连接失败，两者的方向完全不同。

## 8. 面试题 {#面试题}

### 8.1 访问域名时 DNS 如何解析，修改记录后为什么可能仍访问旧地址？ {#dns-resolution}

**考察重点**：递归解析、权威委派和缓存 TTL 对地址变更的影响。

**相关内容**：[面试核心](#core)、[递归与迭代查询](#递归与迭代查询)、[使用边界](#使用边界)。

<details>
<summary>参考回答</summary>

**客户端把查询交给递归解析器，递归解析器先查缓存，再沿已有委派或从根开始查询权威服务器；改记录后，各级缓存仍可能在剩余 TTL 内返回旧值。**

解析过程：应用调用系统解析接口，系统检查 hosts 和本地缓存后，向递归解析器发起递归查询。递归解析器没有可用缓存时，依次询问根、顶级域和目标区域的权威服务器，前两步取得委派，最后取得记录。委派信息也会被缓存，所以很多查询不必从根开始。

仍访问旧地址的原因有两层。一是缓存：客户端、系统和递归解析器都可能在剩余 TTL 内返回旧值。二是连接：连接池里已经建立的连接不受 DNS 变化影响，会继续连着旧实例。所以切换前要提前调低 TTL，并至少等旧 TTL 过完；切换后让旧实例逐步排空，新旧端点同时服务一段时间。

</details>

### 8.2 新增域名后仍收到 NXDOMAIN，应检查什么？ {#dns-negative-cache}

**考察重点**：负缓存类型、SOA 参数和缓存层次。

**相关内容**：[负缓存](#负缓存)。

<details>
<summary>参考回答</summary>

**先检查递归解析器和客户端里是否还缓存着之前的 NXDOMAIN。**

如果在添加记录之前有人查过这个名称，解析器会把「不存在」缓存下来，权威服务器上已经有了记录，它也要等负缓存到期才会重新查询。负缓存时长取 SOA 记录的 TTL 与 MINIMUM 字段的较小值，解析器还可能有本地上限。

另外要确认收到的到底是 NXDOMAIN 还是 NODATA。如果名称已经存在、只是缺少所查的类型（比如只有 A 没有 AAAA），得到的是 NODATA，问题在于记录类型，而不是名称不存在。

</details>

### 8.3 DNS 什么时候使用 TCP，超过 512 字节就必须切换吗？ {#dns-tcp-fallback}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：TC 位、EDNS 与 TCP 支持。

**相关内容**：[DNS 传输](#dns-传输)。

<details>
<summary>参考回答</summary>

**UDP 响应被截断（设置了 TC 位）时，客户端改用 TCP 重查；区域传送 AXFR 也使用 TCP。超过 512 字节不一定要切换。**

512 字节是没有使用 EDNS 时 UDP DNS 消息的上限。客户端通过 EDNS 声明了更大的接收上限、服务端也能支持时，更大的答案仍可以走 UDP。因此，遇到截断响应时应根据 TC 位改用 TCP，不能只看答案是否超过 512 字节。因为完整的 DNS 实现必须支持 TCP，网络上也要放行 TCP 53，否则大响应会查询失败。

</details>

### 8.4 DNSSEC 与 DoH、DoT 分别提供什么保护？ {#dnssec-encrypted-dns}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：记录验证与传输加密的边界。

**相关内容**：[使用边界](#使用边界)。

<details>
<summary>参考回答</summary>

**DNSSEC 用签名验证记录的来源和完整性，DoH、DoT 加密客户端到解析服务之间的传输。**

DNSSEC 保证的是「这条记录确实是区域所有者发布的、没被改过」，但查询本身仍然可能被看到。DoH 和 DoT 让路上的人看不到、改不了查询和响应，但解析服务返回什么，客户端就收到什么，答案是否可信仍需要 DNSSEC 验证或对解析服务的信任。两者解决的是不同问题，可以同时使用。

</details>
