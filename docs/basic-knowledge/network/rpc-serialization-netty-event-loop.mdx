# RPC

**RPC**（Remote Procedure Call，远程过程调用）把发往另一个进程的请求封装成方法调用接口。调用方看起来在调用一个方法，底层却要完成参数编码、网络传输、远端执行和结果返回，其中任何一步都可能失败或超时。

理解 RPC，需要能把一次调用还原成这条链路：响应怎样找到原来的请求，字节流怎样拆成消息，耗时业务为什么不能阻塞网络线程。下面以 Netty 4.2 的 NIO 执行模型说明这些问题。

## 1. 面试核心 {#core}

- 多个请求共用连接时，响应可能乱序返回，客户端靠**请求 ID 找到对应的 `Future` 或回调**。
- Protobuf 靠**字段编号识别字段**，删除字段后应使用 `reserved` 保留编号，避免旧数据被解释成新含义。[卡](#protobuf-field-evolution)
- TCP 不保留应用消息边界，需要协议自己定义。`LengthFieldBasedFrameDecoder` 可以**按长度字段拆出完整消息帧**。[卡](#netty-connections-framing)
- NIO 中一个 `EventLoop` 可以管理多个 `Channel`，**阻塞其中一个处理器会拖延同一线程上的其他连接**，耗时业务应交给有界线程池。
- `ByteBuf` 交给异步任务前，需要明确谁持有、谁释放引用。**需要延长生命周期时调用 `retain()`，使用结束后配对 `release()`**。[卡](#bytebuf-async-lifetime)

## 2. RPC 调用链 {#rpc-调用链}

RPC 要把本地调用转换成远程消息，再把响应交回原来的调用方。一次调用可以分为六步：

1. 客户端代理根据服务名选择实例。
2. 把方法、参数、请求 ID 和元数据编码成字节。
3. 取得连接，发送消息。
4. 服务端解码、鉴权，再交给对应的业务方法。
5. 服务端把执行结果编码成响应并发回。
6. 客户端根据请求 ID 找到原来的调用，交付结果。

**请求 ID** 是一次调用的标识，用来把响应与等待结果的 `Future` 或回调对应起来。比如同一条连接发出请求 A、B，B 先执行完、先返回，客户端也能按 ID 把结果交给 B，而不会误交给先发送的 A。

调用超时或取消时，要删除对应的等待记录，避免它一直占着内存。之后收到迟到的响应，应按已结束的调用处理，不能再次交付结果。统计耗时时同样要覆盖整条链路，只看服务端业务方法，会漏掉连接池、队列和网络中的等待。

## 3. 序列化协议 {#序列化协议}

**序列化**是把对象转换成协议约定的字节，接收方再通过反序列化还原数据。双方除了约定字段类型和缺省值，还要限制消息大小、嵌套深度和集合长度，避免异常输入消耗过多资源。

Protobuf 在二进制消息里用字段编号识别字段，字段改名并不会改变这个编号的含义。删除字段后，应通过 `reserved` 保留退役编号。例如，原来的编号 2 表示用户编号，后来把它改用作订单编号，旧消息中的用户编号就可能被当成订单编号读取。即使两者的底层编码类型（wire type）相同，业务含义也已经不兼容。

下例使用 Protobuf 3.15+，其 proto3 `optional` 已默认启用：

```protobuf
syntax = "proto3";
message Query {
  reserved 2;
  string request_id = 1;
  optional int32 limit = 3;
}
```

`reserved 2` 阻止后续字段再次使用编号 2。`limit` 声明为 `optional`，接收方就能区分「没有提供 `limit`」和「明确提供了 0」；两者可以对应不同的业务处理。

proto3 还可以保留收到的未知字段，并在重新序列化时继续输出，因此旧程序可以转发自己不认识的新字段。但转成 JSON 或只逐个复制已知字段时，这些信息会丢失。修改协议后，需要验证旧客户端与新服务端能否一起工作，不能只检查新版本之间能否通信。

## 4. 半包与粘包 {#半包与粘包}

TCP 传的是字节流，不知道应用把哪些字节看作一条消息。一次读取只得到消息的一部分，叫**半包**；一次读取包含多条消息，叫**粘包**。这都是正常的流式读取结果，不是 TCP 把数据传错了。

应用协议必须告诉接收方在哪里切开消息，常见方式如下：

| 方案 | 处理条件 |
| --- | --- |
| 固定长度 | 每条消息占固定字节数，累计够这些字节后再处理。 |
| 分隔符 | 遇到约定的分隔符结束一条消息，需要处理转义并限制长度。 |
| 长度字段 | 先读取头部给出的长度，再累计对应数量的消息体字节。 |

Netty 的 `LengthFieldBasedFrameDecoder` 按长度字段拆帧。配置时要说明长度字段从哪里开始、占几个字节，以及字段值是否包含头部等长度调整规则。`maxFrameLength` 则限制整帧的最大长度，避免接收方按异常长度不断分配内存或等待数据。

## 5. EventLoop {#eventloop}

**事件循环**负责反复处理 I/O 事件和任务。在 Netty 的 NIO 模型中，`EventLoop` 使用一个线程，可以服务多个 `Channel`；`Channel` 是 Netty 对网络通道的抽象，可以代表监听 socket，也可以代表已建立的连接。

服务端通常把两类工作分给不同的组：接收组处理监听 `Channel`，工作组处理已建立的连接。每个 `Channel` 注册到一个 `EventLoop`，由它按序处理该通道的 I/O 事件。

这也意味着，在 `EventLoop` 线程中执行的处理器不能长时间阻塞。例如，一个连接的处理器等待数据库返回时，同一线程上的其他连接也无法及时处理 I/O。慢数据库调用应交给有界业务线程池，`EventLoop` 继续处理网络事件。

业务转到其他线程后，完成顺序可能变化。需要按请求顺序处理的业务，要自行协调顺序和共享状态；`Channel` 的有序 I/O 不会自动让所有业务任务串行执行。

## 6. ChannelPipeline {#channelpipeline}

`ChannelPipeline` 是一个 `Channel` 上的处理器链，每个处理器（handler）负责一项工作，例如 TLS、拆帧、解码、鉴权或业务分派。入站事件按添加顺序经过入站处理器，出站操作则沿相反方向经过出站处理器。

写数据的入口会影响经过哪些处理器。`channel.write(...)` 从管线尾端开始向前传播，`ctx.write(...)` 则从当前处理器所在的上下文向前寻找出站处理器。如果编码器位于当前处理器之后，调用 `ctx.write(...)` 就会跳过它。因此，安排处理器顺序时，还要一起考虑从哪里发起写操作。

同一个 handler 实例要在多个通道中共享，必须自身满足线程安全要求。`@Sharable` 表示该实例可以安全复用，注解本身不会给共享状态加锁。

## 7. ByteBuf 引用计数 {#bytebuf-引用计数}

`ByteBuf` 是 Netty 的字节缓冲区，用引用计数管理底层内存的生命周期。`retain()` 增加计数，`release()` 减少计数，计数降到 0 后，底层资源就可以释放或归还池中。把消息继续交给下一个处理器时，也要明确把释放责任交给谁。

`SimpleChannelInboundHandler` 默认在处理结束后自动释放收到的消息。如果把同一个 `ByteBuf` 交给异步任务，处理器可能先返回，缓冲区随之被释放，而异步任务还没开始读取。因此，要在原引用释放前调用 `retain()`，为异步任务保留一份引用；任务结束后在 `finally` 中调用 `release()`。任务提交失败时，也必须释放刚才增加的引用。

`slice()` 和 `duplicate()` 产生的视图共享底层数据，并不会增加引用计数。需要让视图跨过异步调用继续存活时，可以用 `retainedSlice()` 或 `retainedDuplicate()`。这些方法只延长生命周期，没有复制数据，所以也不能隔离不同线程对内容的修改。

## 8. deadline 传递 {#deadline-传递}

**deadline** 是一次调用最晚应结束的时间。RPC 把剩余预算传给下游，各层才不会重新开始计时。例如，上游只剩 200ms，下游就不能再按完整的 1 秒预算执行。

gRPC 会把 deadline 转换为剩余超时再传递。截止时间到了以后，服务端处理器还要响应取消，停止已经没有必要继续执行的任务。

取消等待不会撤销已经提交的外部业务。例如订单已创建，只是响应没有及时到达，客户端取消后订单仍然存在。结果不明的写操作需要幂等键和结果查询，重试约束见 [HTTP](./http-versions-connection-reuse-timeouts.mdx#重试)。

## 9. 背压 {#背压}

**背压**是下游处理不过来时，让上游放慢生产和发送。RPC 服务需要限制在途请求、业务队列和待发送字节，否则请求只会越积越多，最终耗尽内存或全部超时。

Netty 用写缓冲水位反馈发送压力：待发送数据超过高水位后，`isWritable()` 返回 `false`；降到低水位以下时，重新返回 `true`。这只是信号，不会禁止应用继续 `write`。处理器需要监听可写状态变化，主动暂停生产，再在恢复可写后继续。

如果压力来自接收和业务处理，可以临时关闭 `autoRead`，暂停自动读取，待容量恢复后再开启。背压只能延缓上游发送，长期容量不足仍需要限流或拒绝请求，无限扩大队列只会增加内存占用和等待时间。

## 10. 常见问题 {#常见问题}

### 10.1 为什么大量连接不需要同样多的线程？ {#连接与线程数量}

因为连接在等待数据时，不需要各占一个线程。`EventLoop` 根据就绪事件处理当前能读写的连接，同一个线程可以轮流服务多个通道。这个模型要求 I/O 处理器短小；耗时业务要使用独立的执行资源，否则会阻塞同一线程负责的其他连接。

### 10.2 RPC 超时后直接重试，会不会重复执行业务？ {#rpc-重试与业务副作用}

会有这种可能。服务端已经提交业务、但响应丢失时，客户端也会看到超时。重试会再次发送同一请求，因此写操作需要稳定的幂等键，并持久化处理结果，让服务端能够识别重复请求、返回之前的结果。

## 11. 面试题 {#面试题}

### 11.1 Netty 如何处理连接、粘包和耗时业务 {#netty-connections-framing}

**考察重点**

- EventLoop 与 Channel 的线程关系。
- TCP 字节流和应用消息边界。
- ByteBuf 所有权、业务线程池与背压。

**相关内容**：[半包与粘包](#半包与粘包)至[背压](#背压)。

<details>
<summary>参考回答</summary>

**Netty 用 `EventLoop` 处理多个连接的 I/O，用解码器按协议规则拆帧；耗时业务需要由应用转交有界线程池。**

TCP 不保留消息边界，长度字段解码器需要先读长度，再等待完整消息，不能把一次读取当成一个请求。`EventLoop` 线程上执行阻塞业务，会拖延它管理的其他连接。

把 `ByteBuf` 交给异步任务时，还要配对管理 `retain()` 和 `release()`。队列、在途请求和待发送数据都应有上限；写缓冲水位只是压力信号，应用需要主动暂停生产。

</details>

### 11.2 Protobuf 删除字段后为什么要保留编号？ {#protobuf-field-evolution}

**考察重点**：字段编号、历史数据与缺省值。

**相关内容**：[序列化协议](#序列化协议)。

<details>

**二进制消息按编号识别字段，复用旧编号会把历史数据解释成新字段。**

删除后应使用 `reserved` 保留该编号，防止后续误用。即使新旧字段的编码类型相同，业务含义不同也会破坏兼容性。还要区分字段是否出现与字段的默认值；需要知道调用方是否明确填写时，可使用 proto3 `optional`。

</details>

### 11.3 把 ByteBuf 交给异步线程时，怎样避免提前释放？ {#bytebuf-async-lifetime}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：自动释放、引用计数与共享内存。

**相关内容**：[ByteBuf 引用计数](#bytebuf-引用计数)。

<details>
<summary>参考回答</summary>

**在当前引用释放前，为异步任务调用一次 `retain()`，任务结束后配对调用 `release()`。**

这样，即使 `SimpleChannelInboundHandler` 返回后自动释放了原引用，异步任务的引用仍能让缓冲区存活。任务正常结束、抛异常或提交失败时，都要释放自己持有的引用。

普通 `slice()` 只生成共享内存的视图，不增加计数。`retainedSlice()` 可以保留引用，但数据仍然共享，不能因此省去并发访问的协调。

</details>
