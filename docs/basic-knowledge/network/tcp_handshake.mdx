# TCP 连接

TCP 通过三次握手同步连接状态与初始序列号，通过两个方向分别关闭来释放全双工连接。

## 1. 面试核心 {#core}

- 握手同步双方初始序列号和连接状态；SYN 占用序列号，第三次 ACK 完成服务端对确认的接收。[卡](#three-way-handshake-time-wait)
- 客户端发出第三次 ACK 时可进入 ESTABLISHED，服务端收到有效 ACK 后才进入；连接状态不是双方同时变化。[卡](#lost-handshake-ack)
- FIN 只关闭发送方向并占用序列号；两个方向分别关闭，ACK 与 FIN 可以合并。[卡](#half-close-reset)
- TIME_WAIT 服务于可靠终止与旧报文隔离，通常由主动关闭方承担，同时关闭也可能两端都进入。[卡](#three-way-handshake-time-wait)
- 持续 CLOSE_WAIT 应检查应用关闭路径，TIME_WAIT 多则先看短连接与资源压力，不能统一当作泄漏。[卡](#connection-states)

## 2. TCP 连接保存双方状态 {#1-tcp-连接保存双方状态}

TCP 向应用提供可靠、有序的字节流。通信双方需要维护序列号、确认号、接收窗口和连接状态，后续数据才能被确认、重传并按顺序交付。

建立连接时需要完成两件事：

1. 确认客户端到服务端、服务端到客户端的通信路径可用。
2. 交换双方的初始序列号，避免新连接把网络中迟到的旧报文当成当前数据。

连接是全双工的，两个方向可以独立发送数据，也可以独立结束发送。这一点决定了关闭过程通常需要分别处理两个方向。

## 3. 三次握手同步初始序列号 {#2-三次握手同步初始序列号}

```mermaid
sequenceDiagram
    participant C as 客户端
    participant S as 服务端
    C->>S: SYN seq=x
    Note over C: SYN-SENT
    S->>C: SYN+ACK seq=y, ack=x+1
    Note over S: SYN-RECEIVED
    C->>S: ACK seq=x+1, ack=y+1
    Note over C: 发出确认后<br/>ESTABLISHED
    Note over S: 收到确认后<br/>ESTABLISHED
```

假设客户端初始序列号为 `x`，服务端初始序列号为 `y`：

1. 客户端发送 `SYN`，序列号为 `x`，进入 `SYN-SENT`。
2. 服务端回复 `SYN + ACK`，序列号为 `y`，确认号为 `x + 1`，进入 `SYN-RECEIVED`。
3. 客户端回复 `ACK`，确认号为 `y + 1`，客户端进入 `ESTABLISHED`；服务端收到有效 ACK 后才进入 `ESTABLISHED`。

`SYN` 会占用一个序列号，因此确认号在对方序列号基础上加一。不带数据的 ACK 不占序列号。第三个报文可以同时携带应用数据，但服务端必须收到该 ACK，才能确认客户端已经接收自己的 SYN 和初始序列号。

## 4. 第三次握手的作用 {#3-两次交互无法完成双方确认}

如果只有客户端的 `SYN` 和服务端的 `SYN + ACK`，客户端能够确认服务端收到了自己的请求，服务端却不知道自己的回复是否到达客户端。服务端也就无法判断对方是否接受了本次连接参数。

第三次 ACK 完成服务端方向的确认。它还可以帮助服务端区分有效的新连接与网络中迟到的旧 SYN，避免仅凭一个历史请求就进入已建立状态并分配完整连接资源。

三次握手仍不能证明未来的数据一定到达。它只建立当前连接状态，后续可靠性继续依赖序列号、确认、超时重传和拥塞控制。

## 5. 四次挥手分别关闭两个方向 {#4-四次挥手分别关闭两个方向}

```mermaid
sequenceDiagram
    participant A as 主动关闭方
    participant B as 被动关闭方
    A->>B: FIN
    Note over A: FIN-WAIT-1
    B->>A: ACK
    Note over B: CLOSE-WAIT
    Note over A: FIN-WAIT-2
    B->>A: 剩余数据（如果有）
    B->>A: FIN
    Note over B: LAST-ACK
    A->>B: ACK
    Note over A: TIME-WAIT<br/>等待 2MSL
    Note over B: 收到 ACK 后<br/>CLOSED
    Note over A: 等待结束后<br/>CLOSED
```

以客户端主动关闭为例：

1. 客户端发送 `FIN`，表示客户端已经没有更多数据发送，进入 `FIN-WAIT-1`。
2. 服务端确认该 `FIN`，进入 `CLOSE-WAIT`；客户端收到 ACK 后进入 `FIN-WAIT-2`。此时服务端仍可以继续发送剩余数据。
3. 服务端应用完成发送并关闭连接后，服务端发送自己的 `FIN`，进入 `LAST-ACK`。
4. 客户端确认服务端的 `FIN`，进入 `TIME-WAIT`；服务端收到最后的 ACK 后关闭连接。

第二步的 ACK 与第三步的 FIN 可以在同一个报文中发送，因此抓包时不一定总能看到四个独立报文。“四次挥手”描述的是两个方向各自发送 FIN 并获得确认的逻辑过程。

## 6. TIME_WAIT 与 CLOSE_WAIT 指向不同问题 {#5-time_wait-与-close_wait-指向不同问题}

常规单方主动关闭过程中，主动关闭者在自己的 FIN 已被确认、又收到对端 FIN 并回复 ACK 后进入 `TIME-WAIT`，等待 `2MSL`。MSL 是报文最大生存时间，不是一次往返的 RTT；具体计时值与实现有关。这段时间允许它在最后 ACK 丢失、对方重传 FIN 时再次回复，也让旧连接中的迟到报文从网络中消失，避免污染随后复用相同四元组的连接。

被动关闭的一方收到 FIN 后进入 `CLOSE-WAIT`。这个状态表示对端已经停止发送，本地应用还没有关闭自己的方向。少量、短暂的 `CLOSE-WAIT` 属于正常过渡；持续堆积通常说明应用没有及时关闭 socket，或相关线程被阻塞。

双方同时关闭时，可能各自经过 `CLOSING` 后进入 `TIME-WAIT`，因此不能用“只有客户端才有 TIME_WAIT”判断连接状态。

大量 `TIME-WAIT` 不等于连接泄漏。应先确认谁在主动关闭、连接是否缺少复用，以及端口范围、并发量和持续时间是否已经造成实际资源压力。

## 7. 握手丢包与半连接 {#握手丢包与半连接}

| 丢失位置 | 典型状态与恢复 | 排查关注点 |
| --- | --- | --- |
| 初始 SYN | 客户端仍在 SYN-SENT，等待重传或超时 | 网络可达性、监听端口、防火墙 |
| SYN+ACK | 客户端还未收到应答，双方可能各自重传对应 SYN 报文 | 返回路径、半连接积压 |
| 第三次 ACK | 客户端可能已建立，服务端仍在 SYN-RECEIVED；服务端重传 SYN+ACK，客户端再次确认 | 不能因客户端 connect 返回就断定服务端已经完成握手 |

纯 ACK 通常没有独立的重传定时器；通过对方重传 SYN+ACK 或后续携带有效确认的数据恢复。重试次数、退避和最终超时属于协议实现及配置，不应背成跨系统的固定常量。

SYN flood 会让服务端不断处理难以完成的连接请求。SYN cookies、限制速率和合理配置队列可降低状态分配压力；它们不能解决带宽被耗尽的问题。半连接等待握手完成，与握手完成后等待应用 accept 是两个阶段，排障时要结合操作系统队列和指标。

## 8. 半关闭、复位与业务完成 {#半关闭复位与业务完成}

`shutdown(SHUT_WR)` 可以结束本端发送方向，仍保留接收方向；对端读完此前数据后读取到 EOF，但仍可返回结果。`FIN` 表示有序结束这一方向，`RST` 则用于复位连接，接收应用可能看到连接错误，不能按正常 EOF 处理。

TCP ACK 表示对端协议栈接收了对应字节，不代表对端应用已执行请求或持久化数据；FIN 也不表示业务成功。需要端到端成功语义时，协议必须定义业务响应、超时、请求标识和重试规则。

## 9. 常见问题 {#6-常见问题}

### 9.1 为什么建立连接通常是三次，关闭通常是四次 {#61-为什么建立连接通常是三次关闭通常是四次}

建立连接时，服务端可以把对客户端 SYN 的 ACK 与自己的 SYN 合并，所以三个报文能够完成双方初始序列号确认。关闭时，一方收到 FIN 后可能还有数据要发送，只能先 ACK，等应用完成发送后再发自己的 FIN，因此通常表现为四个报文。

### 9.2 收到 FIN 是否表示连接中的数据都处理完了 {#62-收到-fin-是否表示连接中的数据都处理完了}

FIN 表示发送方不会再发送新的字节，它在序列空间中位于此前数据之后。接收端协议栈会按序交付，但这不代表应用已经完成业务处理；应用仍需读取剩余数据并正确关闭资源。
