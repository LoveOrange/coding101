# IP

**IP**（Internet Protocol）负责根据目标地址把数据报送向目标主机，既支持同一网络内通信，也支持跨网络转发。它不建立连接，每个数据报都带着目标地址，沿途的路由器各自查表，决定交给下一跳，一跳一跳地转发过去。

理解 IP，能帮你把「网络不通」拆成几个更具体的问题：地址和路由对不对，包是不是太大被丢了，诊断工具的结果到底说明了什么。数据报逐跳转发的过程、路由表的选路规则，以及包超过路径 MTU 时的处理方式，是判断这些问题的依据。

## 1. 面试核心 {#core}

- IP 只提供**尽力而为**的交付：数据报可能丢失、重复或乱序，可靠性要靠上层协议（比如 TCP）补上。
- 路由表按**最长前缀匹配**选路，前缀越长，描述的范围越具体，也越优先；默认路由的前缀长度为 0，只在没有更具体的路由时使用。
- IP 地址负责**找到主机并转发**，端口负责**在主机上区分服务和连接**，域名是给人用的名称，要通过 DNS 查出地址。[卡](#ip-port-domain)
- 包超过下一跳 MTU 时，IPv4 在允许分片时由路由器分片，否则丢包并回 ICMP 错误；IPv6 路由器**从不分片，直接丢包并回复 Packet Too Big**。[卡](#path-mtu-fragmentation)

## 2. 地址与逐跳转发 {#地址与逐跳转发}

IP 地址决定数据报的最终目标，路由表决定当前这一步交给谁。**下一跳**就是本次转发直接交付数据报的节点。

主机发包前先查本地路由表，确定从哪个网卡发出、下一跳是谁。目标就在直连的网络里时，下一跳就是目标本身；否则交给匹配路由指定的网关，通常就是默认网关。

找到下一跳的 IP 之后，还要知道它在链路上的地址才能真正发出去。在以太网上，IPv4 用 ARP 查询下一跳的 MAC 地址，IPv6 用邻居发现完成同样的事。主机只需要知道下一跳的 MAC，远端服务器的 MAC 不会也不需要跨过路由器传过来。

路由器收到包后重复这个过程：根据目标 IP 查表选出口，再用下一跳的链路地址重新封装成帧。所以经过路由器转发后，链路帧中的 MAC 地址会按下一跳重新填写；源 IP 和目标 IP 则保持不变，除非中途经过了 NAT 这类地址转换。

## 3. 子网与路由选择 {#子网与路由选择}

**网络前缀**是地址开头固定的那几位，用来描述一段地址。一条路由通常用网络地址和前缀长度说明它覆盖的范围。`192.0.2.0/24` 表示前 24 位固定、后 8 位可变，也就是 `192.0.2.0` 到 `192.0.2.255` 这一段。

目标地址同时匹配多条路由时，选前缀最长的那条，因为它描述得最具体。比如路由表里同时有 `192.0.2.0/24` 和 `/0` 默认路由，发往 `192.0.2.10` 的包走 `/24` 路由。默认路由能匹配所有地址，但前缀长度是 0，只有别的路由都匹配不上时才轮到它。

IPv4 地址有 32 位，IPv6 地址有 128 位。以 `192.0.2.0/24` 为例，它有 256 个地址，其中网络地址（`.0`）和广播地址（`.255`）不能分给主机，所以可分配 254 个。点对点链路常用的 /31 是例外，RFC 3021 允许它的两个地址都分给两端使用。

IP 地址只能把包送到主机，主机上跑着很多服务，区分它们靠的是传输层的**端口**。同一个 IP 上，443 端口和 8080 端口可以是完全不同的服务。NAT 会改写数据报里的地址，NAPT 还会改写端口，让多台内网主机共用一个公网地址；回来的流量要靠设备里记录的转换映射才能找回原来的主机和端口。

## 4. 路径 MTU 与分片 {#路径-mtu-与分片}

**MTU**（Maximum Transmission Unit，最大传输单元）是链路一次能承载的最大网络层数据长度；在这里就是整个 IP 包的长度。**路径 MTU** 是从源到目标所有链路 MTU 中的最小值。包超过下一跳 MTU 时，要么被分片，要么被丢弃，IPv4 和 IPv6 的处理不同。

IPv4 看包头里的 DF（Don't Fragment）位：

- DF 为 0 时，路由器可以把包分成几片继续转发。
- DF 为 1 时，路由器丢弃这个包，并向源端返回 ICMP 错误，告诉它需要分片以及下一跳的 MTU。

IPv6 路由器从不分片。包太大时，路由器直接丢弃，并返回 ICMPv6 Packet Too Big。如果确实需要分片，只能由源端自己完成。

无论哪种情况，分片都只在目标主机上重组，中途的路由器不会拼回去。任何一片丢了，整个数据报都作废，所以分片会放大丢包的影响。用 UDP 的应用应该控制好数据报大小，尽量不要依赖分片。

TCP 里还有一个相关的概念 **MSS**（Maximum Segment Size），它限制的是一个 TCP 段里数据部分的长度。MTU 限制的是整个 IP 包，两者相差 IP 头和 TCP 头的长度。比如以太网 MTU 是 1500 字节，IPv4 和 TCP 头各 20 字节（不带选项）时，MSS 就是 1460 字节。

## 5. ICMP 与路径诊断 {#icmp-与路径诊断}

**ICMP** 是 IP 用来报告错误和做诊断的控制报文协议，前面说的「需要分片」和 Packet Too Big 都是 ICMP 报文，ping 和 traceroute 也建立在它上面。

IPv4 包头有 TTL，IPv6 包头有对应的 Hop Limit，每经过一个路由器减 1，减到 0 时路由器丢弃这个包并返回超时错误。这个机制的本意是防止路由环路里的包一直转下去。

ping 发送 ICMP 回显请求，等对方回显响应。traceroute 利用 TTL 超时：先发 TTL 为 1 的探测包，第一跳路由器回超时错误，再发 TTL 为 2 的，依次发现路径上的每一跳。很多网络设备会过滤或限速 ICMP，这时 traceroute 结果里会出现空缺的跳，ping 也可能不通，但不代表路径断了。反过来，ping 通也只说明 ICMP 能来回，服务端口能不能连、HTTP 能不能响应，仍然要实际访问才知道。

传统的路径 MTU 探测同样依赖 ICMP：发送端靠「需要分片」或 Packet Too Big 才知道要把包变小。如果防火墙把这些报文也屏蔽了，发送端收不到反馈，大包会一直被静默丢弃。表现是连接能建立、小请求正常，一到大响应就卡住超时。遇到这种「小包正常、大包超时」的现象，值得优先检查路径 MTU 和 ICMP 过滤。

## 6. 使用边界 {#使用边界}

IP 地址标识的是网络接口和它在路由上的位置，不等于某个服务，也不等于某个域名：一个域名可以解析出多个地址，一个地址上也可以运行多个服务。要区分一条连接，需要传输协议、源地址、源端口、目标地址和目标端口一起确定。

## 7. 面试题 {#面试题}

### 7.1 访问服务器时，IP 地址、端口与域名分别起什么作用？ {#ip-port-domain}

**相关内容**：[面试核心](#core)、[地址与逐跳转发](#地址与逐跳转发)、[使用边界](#使用边界)。

<details>
<summary>参考回答</summary>

**域名用来查出地址，IP 地址用来寻址和逐跳转发，端口用来在主机上区分服务和连接。**

访问 `example.com` 时，客户端先通过 DNS 查到它的 IP 地址。数据报带着这个目标 IP，由路由器按路由表一跳一跳转发到目标主机。到了主机之后，传输层根据目标端口把数据交给对应的服务，比如 443 是 HTTPS 服务。三者不是一一对应：同一个域名可以对应多个 IP，一个 IP 上也可以通过不同端口承载多个服务。一条连接由协议加上源、目标的地址和端口共同标识。

</details>

### 7.2 IPv4 和 IPv6 遇到超过路径 MTU 的包怎样处理？ {#path-mtu-fragmentation}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：DF、源端分片与 ICMP 反馈。

**相关内容**：[路径 MTU 与分片](#路径-mtu-与分片)。

<details>
<summary>参考回答</summary>

**IPv4 在 DF 为 0 时允许路由器分片，DF 为 1 时丢包并回 ICMP 错误；IPv6 路由器从不分片，直接丢包并回复 Packet Too Big。**

收到 ICMP 反馈后，发送端据此缩小包的大小；IPv6 下如果确实需要分片，只能由源端执行。分片只在目标主机重组，缺少任何一片都无法重组出完整数据报，因此应用通常尽量避免分片。是否重传由上层协议决定，IP 不负责重传。这套机制依赖 ICMP 反馈，如果中间的防火墙屏蔽了这些报文，发送端不知道要缩小包，就会出现小包正常、大包一直超时的现象。

</details>

### 7.3 ping 不通能说明 HTTP 服务不可用吗？ {#icmp-service-reachability}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：ICMP 探测与应用端口访问。

**相关内容**：[ICMP 与路径诊断](#icmp-与路径诊断)。

<details>
<summary>参考回答</summary>

**不能。ping 失败只说明没有收到预期的 ICMP 回显响应。**

ping 用的是 ICMP，HTTP/1.1 和 HTTP/2 通常通过 TCP 服务端口通信，HTTP/3 则使用 UDP 上的 QUIC；它们与 ICMP 的处理规则不同。很多设备会过滤 ICMP，这时 TCP 连接和 HTTP 请求仍然可以成功。判断服务是否可用，应该直接测试目标端口能否建立连接、应用能否正常响应。反过来，ping 成功也只验证了 ICMP 能来回，不能说明服务端口是通的。

</details>
