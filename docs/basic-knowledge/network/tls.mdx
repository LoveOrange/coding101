# TLS

**TLS**（Transport Layer Security）是在通信双方之间建立安全通道的协议。它通过加密保护内容，用完整性校验检测篡改，并验证通信端点的身份。HTTPS 就是在 TLS 保护下传输 HTTP。`http` 与 `https` URI 的默认端口分别是 **80 和 443**，也可以显式指定其他端口；端口号本身不能证明连接受到 TLS 保护。

理解 TLS，要分清身份验证、密钥协商和数据加密各自负责什么：证书说明对方是谁，握手让双方得到用于加密的密钥，后续业务数据再用这些密钥保护。本文以 TLS 1.3 的证书握手为主。

## 1. 面试核心 {#core}

- 证书把身份与公钥关联起来，客户端要验证**信任链、有效期和目标主机名**；只确认签发者可信还不够。
- TLS 1.3 的证书握手用**临时密钥交换派生密钥**，证书对应的私钥用于证明身份，不直接加密业务数据。[卡](#https-roles)
- 在典型 TLS 1.2 完整握手中，双方交替发送**四批消息**；这不是所有 TLS 版本都固定发送四个消息或 TCP 包。[卡](#tls12-handshake-flights)
- SNI 提供**目标服务器名称**，用于选择站点配置和证书；ALPN **协商应用协议**，例如 HTTP/2 的 `h2`。[卡](#sni-alpn)
- 应用数据由**对称 AEAD 算法同时保护机密性和完整性**，双方使用协商派生的流量密钥处理。
- 临时密钥交换提供前向保密；但 **0-RTT 早期数据缺少前向保密，还可能被重放**，业务必须限制重复执行的影响。[卡](#tls-forward-secrecy-replay)

## 2. 证书与握手 {#证书与握手}

TLS 1.3 的完整证书握手同时完成两件事：让双方得到共享密钥，并让客户端确认对方确实是要访问的服务器。这里使用临时 **(EC)DHE** 密钥交换，双方交换公开参数（key share），各自结合本地临时私钥算出相同的共享秘密，再从中派生密钥，无需把私钥传给对方。

忽略可选分支，主要过程如下：

1. 客户端发送 `ClientHello`，提供支持的算法和 key share。
2. 服务端返回 `ServerHello`，选择算法并提供自己的 key share。
3. 双方根据密钥交换结果派生握手密钥，用来保护后续握手消息。
4. 服务端发送证书、`CertificateVerify` 和 `Finished`。
5. 客户端验证证书和握手证明，再返回自己的 `Finished`。

**证书**是把身份与公钥绑定起来的签名凭据。拿到一份证书还不能证明对方持有私钥，所以服务端还要发送 `CertificateVerify`：用证书对应的私钥对握手内容签名。客户端用证书里的公钥验证签名，确认当前对端持有该私钥。`Finished` 则用于校验握手上下文，确认双方看到的握手过程没有被篡改。

客户端还必须检查证书的信任链、有效期和目标名称。**SAN**（Subject Alternative Name）是证书中声明身份的字段，主机名校验以它为依据。例如，访问 `shop.example.com` 时，仅知道证书由可信 CA（证书颁发机构）签发还不够，证书里的身份也必须能匹配这个名称，否则认证的可能是另一个站点。

### 2.1 密钥建立与数据加密 {#密钥建立与数据加密}

**混合密码方案**把密钥建立、身份认证与大量数据的加密分开处理。对称加密适合高效处理网页、图片等业务内容，但双方必须先持有相应的共享秘密。第一次访问一个没有预先共享密钥的站点时，不能把秘密直接明文发给对方；只交换未经认证的公钥或密钥参数，也可能遭到中间人替换。

TLS 的证书握手结合身份认证与密钥交换建立可信的安全通道。这里的公钥密码不只是“用公钥加密”：在前面的 TLS 1.3 流程中，临时 (EC)DHE 用于协商秘密，证书私钥用于签名认证。大量业务数据随后交给对称算法处理，避免把代价较高的公钥运算用于整个数据流。

所以，“全程只用对称加密”的问题是初始密钥从哪里安全地来，而不是对称加密天然容易被窃取。如果双方已经通过可信方式配置了 PSK，也可以使用相应的 TLS 握手模式；这仍然依赖预先建立的秘密和信任。

### 2.2 TLS 1.2 完整握手 {#tls-12-完整握手}

TLS 1.2 的典型完整握手可以按发送方向分成四批消息。下面选择**服务端用证书认证、使用 ECDHE_RSA、没有客户端证书、不做会话恢复**的情况。ECDHE 用来协商临时秘密，RSA 在这个套件中用于签名认证；这个例子不采用静态 RSA 密钥传输。

| 批次 | 方向与消息 | 作用 |
| --- | --- | --- |
| 1 | 客户端 → 服务端：`ClientHello` | 提供版本、密码套件、客户端随机数等参数 |
| 2 | 服务端 → 客户端：`ServerHello`、`Certificate`、`ServerKeyExchange`、`ServerHelloDone` | 选择参数，发送证书以及经过签名的临时 ECDH 参数，并结束这一批协商消息 |
| 3 | 客户端 → 服务端：`ClientKeyExchange`、`ChangeCipherSpec`、`Finished` | 客户端完成证书和签名校验后发送自己的临时公钥；双方据共享秘密等材料派生密钥，客户端切换发送保护状态并证明握手内容一致 |
| 4 | 服务端 → 客户端：`ChangeCipherSpec`、`Finished` | 服务端校验客户端的 `Finished`，再切换发送保护状态并给出自己的握手证明 |

`ChangeCipherSpec` 用来启用协商好的记录保护状态，它属于独立的协议消息，**不是 Handshake 协议中的握手消息**。`Finished` 在切换后的状态下受到保护。这里的“四批”是交互分组，不等于四条协议消息，更不等于四个 TCP 包；客户端认证等可选步骤还会改变消息组成。

不采用提前发送应用数据的 False Start 时，上述完整握手通常需要 **2-RTT**，客户端验证服务端的 `Finished` 后再发送应用数据，不包含 TCP 建连。TLS 1.2 成功恢复已有会话时可以缩短为 `ClientHello` → 服务端的 `ServerHello`、`ChangeCipherSpec`、`Finished` → 客户端的 `ChangeCipherSpec`、`Finished`，通常只需 1-RTT；恢复被拒绝时仍要走完整握手。

TLS 1.3 把临时密钥交换参数放进 Hello 阶段，后续握手消息也得到加密保护，典型完整握手降为 1-RTT。它不再沿用 TLS 1.2 的 `ServerHelloDone` 流程，也移除了静态 RSA 密钥传输。因此，回答握手次数时应先说明版本和是否恢复会话。

## 3. SNI 与 ALPN {#sni-与-alpn}

**SNI** 是客户端在 `ClientHello` 中提供目标服务器名称的扩展。多个 HTTPS 站点共用一个 IP 时，服务端可以根据这个名称选择站点配置和证书。

**ALPN** 用来协商接下来使用哪种应用协议。例如双方选择 `h2`，后续就按 HTTP/2 解释应用数据。SNI 说明想访问哪个站点，ALPN 说明双方用什么协议交流。

这两步都发生在 HTTP 请求之前，所以服务端不能等看到 HTTP `Host` 头后才决定握手时发送哪张证书。普通 `ClientHello` 中的 SNI 也没有被后续的 HTTP 加密所隐藏，链路上的观察者可以看到它。

## 4. 记录加密与会话恢复 {#记录加密与会话恢复}

握手建立密钥之后，TLS 把应用数据组织成记录，用流量密钥保护。**AEAD** 是同时提供加密和完整性验证的对称加密方式，TLS 1.3 用它处理应用记录。因此，证书公钥参与身份验证，真正大量传输的业务数据则使用对称密码。

**会话恢复**让再次连接的双方利用此前会话派生的预共享密钥（PSK），减少重新认证的成本。恢复需要管理相应的会话票据、有效期和密钥轮换，不能把旧会话信息无限期地复用。

不使用早期数据时，典型的 TLS 1.3 完整握手需要一次往返（1-RTT），客户端才能开始发送应用数据。如果服务端要求 `HelloRetryRequest`，让客户端重新提供合适的握手参数，还会增加一次往返。这里计算的是 TLS 握手时间，不包含 TCP 建连。

## 5. 前向保密与早期数据 {#前向保密与早期数据}

**前向保密**是指长期认证私钥事后泄露，也不能据此解密过去录下的会话数据。临时 (EC)DHE 能提供这一性质，因为每次握手的共享秘密还依赖当次临时私钥；只拿到服务器证书私钥，无法还原过去的共享秘密，前提是临时秘密已经安全删除。

TLS 1.3 移除了静态 RSA 密钥传输，但不能因此认为所有 TLS 1.3 数据都具有相同的前向保密保证。PSK 恢复可以加入一次新的 DHE 交换，也可以只使用 PSK；纯 PSK 模式就缺少临时 DHE 带来的保护。

**0-RTT 早期数据**允许客户端在恢复握手时，不等待服务端本次回复就发送应用数据。它使用的密钥尚未加入本次 DHE 的结果，因此缺少前向保密。同时，攻击者可能把录下的早期数据再次发给服务端，这叫**重放**；即使攻击者读不懂密文，业务仍可能被重复执行。

扣款等操作不能因为数据已加密就允许早期执行。这类请求应等握手完成后再发送，或提供应用级防重放机制。服务端拒绝早期数据后，客户端还要结合操作是否允许重复，决定要不要在握手完成后重发。

## 6. 使用边界 {#使用边界}

TLS 保护的是两个端点之间的一段通信，终止 TLS 的端点能够读取明文。例如，浏览器与网关建立 TLS，网关解密后再访问后端，浏览器到网关、网关到后端就是两个独立区段。前一段加密，不代表后一段也自动加密；每一段都需要明确加密配置和证书验证。

TLS 验证通信端点的身份，不决定某个用户能否查看订单、修改账户。登录和资源权限仍由应用处理，见[认证与授权](../../system-design/security/authentication-authorization-trust-boundaries.mdx)。

### 6.1 多副本服务的证书部署 {#多副本服务的证书部署}

**证书签发、证书部署和连接中的证书验证是三件事。** 签发时，CA 按相应规则确认申请的身份并签名；部署时，把证书及对应私钥配置到实际终止 TLS 的端点。建立证书握手连接时，对端根据已信任的根、收到的证书链和握手证明进行验证，不是服务端每接一个连接就向 CA 重新申请一张证书。证书状态检查或缺失材料的获取可能涉及联网，不能据此把验证过程说成绝对不访问外部服务。

Pod 数量增加，也不自动意味着每个 Pod 都要向 CA 独立申请证书。先看 TLS 在哪里终止，以及客户端验证的是什么身份：

| 部署方式 | 证书放在哪里、验证什么 |
| --- | --- |
| 浏览器到 Ingress／网关终止 TLS，后端 Pod 接收明文请求 | 网关持有对应域名的证书和私钥；这些后端 Pod 不参与这一段 TLS 握手，但网关到 Pod 的通信也没有因此获得加密 |
| 网关再与后端 Pod 建立 TLS，或客户端直接访问 Pod 的 TLS 端点 | 实际后端 TLS 端点需要可用的证书和私钥；调用方按约定的服务名称或其他身份验证，不能只接受任意受信任证书 |

证书与服务身份对应，不要求与副本数机械地一一对应。同一服务身份的多个副本可以使用为该身份签发的证书，但私钥共享范围越大，泄露后的影响范围也越大；也可以采用按实例签发的方案。选择哪一种，都要管理私钥访问权限、证书更新和轮换，不能把“能挂载同一份证书”当作完整的密钥管理方案。

## 7. 面试题 {#面试题}

### 7.1 HTTPS 中证书、密钥交换和对称加密分别负责什么，为什么要配合使用？ {#https-roles}

**考察重点**：证书身份验证、初始共享秘密的建立、批量加密成本与应用权限检查的边界。

**相关内容**：[证书与握手](#证书与握手)、[密钥建立与数据加密](#密钥建立与数据加密)、[使用边界](#使用边界)。

<details>
<summary>参考回答</summary>

**证书和握手签名验证服务器身份，密钥交换让双方派生共享密钥，对称加密保护后续应用数据。**

以 TLS 1.3 证书握手为例，客户端核验信任链、有效期和主机名，再验证对端确实持有证书私钥。双方通过临时密钥交换派生密钥，后续用对称 AEAD 同时加密数据、检测篡改。证书私钥不直接加密业务内容，用户的业务权限也仍需由应用检查。

没有预共享密钥时，对称加密本身不能解决初始秘密如何安全建立的问题；公钥密码配合证书验证完成认证和密钥建立，但大量数据都交给公钥运算会增加成本。因此用对称算法处理后续数据。已通过可信方式配置 PSK 是另一种前提，不能省略它的安全配置条件。

</details>

### 7.2 TLS 1.3 的前向保密与 0-RTT 重放风险是什么关系？ {#tls-forward-secrecy-replay}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：临时密钥、PSK 和早期数据边界。

**相关内容**：[前向保密与早期数据](#前向保密与早期数据)。

<details>
<summary>参考回答</summary>

**前向保密限制密钥事后泄露的影响，防重放则避免旧消息被再次执行；0-RTT 早期数据缺少前者，也不能自动保证后者。**

使用临时 DHE 后，仅凭事后泄露的证书私钥无法还原过去的会话密钥，前提是临时秘密已经安全删除。0-RTT 在收到本次握手回复之前发送，早期密钥尚未加入本次 DHE 结果，因此不具备这种保护。攻击者还可能复制早期数据再次发送，所以有副作用的操作需要防重放机制，或等握手完成后再发送。

</details>

### 7.3 同一 IP 上的 HTTPS 服务怎样选择证书和 HTTP 版本？ {#sni-alpn}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：SNI、ALPN 与 HTTP Host 的时机。

**相关内容**：[SNI 与 ALPN](#sni-与-alpn)。

<details>
<summary>参考回答</summary>

**服务端按 SNI 中的目标名称选择站点配置和证书，再通过 ALPN 协商 `h2` 等应用协议。**

SNI 和 ALPN 都参与 TLS 握手。HTTP `Host` 头属于后续的应用请求，出现得比证书选择晚，所以不能代替 SNI 完成握手时的站点选择。

</details>

### 7.4 服务扩容为很多 Pod，是否每个都要向 CA 申请认证？ {#pod-certificates}

**考察重点**：证书生命周期、TLS 终止位置与服务身份。

**相关内容**：[证书与握手](#证书与握手)、[多副本服务的证书部署](#多副本服务的证书部署)。

<details>
<summary>参考回答</summary>

**不由 Pod 数量决定，要区分证书签发与连接验证，并确认 TLS 在哪里终止。** 如果 TLS 在网关终止，网关提供域名证书，后端明文 Pod 不参与这段握手；如果 Pod 自己终止 TLS，它就需要配置对应身份的证书和私钥，由调用方验证。

一次证书握手不要求服务端重新向 CA 申请证书。多个副本可代表同一服务身份，证书数量不必等于 Pod 数量，但仍需控制私钥分发、访问和轮换；实际部署采用哪种方式，要以项目配置为准。

</details>

### 7.5 TLS 的“四次握手”指什么？TLS 1.3 也一样吗？ {#tls12-handshake-flights}

**考察重点**：TLS 版本、完整握手的消息分组、会话恢复与往返次数。

**相关内容**：[TLS 1.2 完整握手](#tls-12-完整握手)、[记录加密与会话恢复](#记录加密与会话恢复)。

<details>
<summary>参考回答</summary>

**“四次”通常指 TLS 1.2 典型完整握手的四批交互，不是所有 TLS 都固定四次。** 以服务端证书认证的 ECDHE_RSA 为例，依次是客户端 Hello；服务端 Hello、证书、签名的临时密钥参数和 `ServerHelloDone`；客户端密钥参数、`ChangeCipherSpec` 和 `Finished`；服务端 `ChangeCipherSpec` 和 `Finished`。

`ChangeCipherSpec` 不属于 Handshake 消息，交互批次也不等于 TCP 包数。不使用 False Start 时，该完整握手通常为 2-RTT；TLS 1.2 成功会话恢复通常为 1-RTT。TLS 1.3 典型完整握手也为 1-RTT，但消息流程已经改变；遇到 `HelloRetryRequest` 还会多一次往返。这些数值不包含 TCP 建连。

</details>
