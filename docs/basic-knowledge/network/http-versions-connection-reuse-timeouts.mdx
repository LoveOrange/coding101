# HTTP

**HTTP** 定义了客户端和服务器之间请求与响应的语义：方法、状态码、头部和消息体的含义。各个版本的语义基本一致，区别主要在于怎样把多个请求放到连接上传输。

理解版本差异，才能解释多个请求为什么会互相等待。到了客户端实现，还要考虑连接池是否有空位、每个阶段能等多久，以及失败后能否重试：协议支持并发，不代表一次调用就不会排队或超时。

## 1. 面试核心 {#core}

- HTTP/1.1 **默认使用持久连接**，多个请求可以复用一条连接，但响应**必须按请求顺序返回**，前一个慢了后面都要等。
- HTTP/2 把一条连接拆成多个 stream **交错传输**，消除了响应必须按请求顺序返回的限制，但底层 TCP 丢包时**所有 stream 仍然一起等待重传**。[卡](#http-concurrency)
- HTTP/3 基于 QUIC，**一个流等待重传时，其他流可继续交付已完整收到的数据**，但所有流仍然共享同一条连接的拥塞控制。
- 读写超时只约束**某一个阶段**，deadline（调用截止时间）约束**整个调用的总时间**，包括排队、建连和所有重试。[卡](#deadline-and-retry)
- GET、PUT 和 DELETE 具有**幂等语义**，允许重复执行而不增加预期副作用；POST 等不保证幂等的操作，需要用**业务幂等键等机制**约束重复效果。

## 2. HTTP/1.1 持久连接 {#http11-持久连接}

HTTP/1.1 默认复用 TCP 连接：一个请求完成后，连接不关闭，下一个请求接着用，省去了重复建连和 TLS 握手。

能复用的前提是双方知道每条消息在哪里结束。HTTP/1.1 通过 `Content-Length` 或分块传输等规则确定响应体的边界。这带来一个使用上的要求：客户端要么把响应体读完，要么关闭这条连接。如果连接池在响应体尚未读完、也未被正确丢弃时就复用连接，剩余数据可能被误当成下一个请求的响应。具体客户端通常会通过读取、丢弃或关闭连接来处理这种情况。

HTTP/1.1 还定义了**流水线**（pipelining）：客户端不等响应回来，就在同一条连接上连续发出多个请求。问题在于服务器必须按请求的顺序返回响应。第一个请求处理得慢，后面已经算好的响应也只能排在后面，这叫 HTTP 层的**队头阻塞**。所以实际中客户端通常不依赖流水线，而是同时开多条连接来并发发请求。

## 3. HTTP/2 多路复用 {#http2-多路复用}

**多路复用**是让多个请求共享一条连接，并交错传输各自的数据。HTTP/2 用它消除响应必须按请求顺序返回的限制。

做法是把每个消息拆成二进制**帧**（frame），每个请求和它的响应属于一个**流**（stream），也就是连接中可独立传输的一组消息，帧上带着流编号。不同 stream 的帧可以交错发送，接收端按编号重新拼起来。一个响应慢，不会挡住其他 stream 的帧。头部字段则用 HPACK 压缩，它用静态表和动态表记住出现过的字段，重复的头部只需要发一个索引。

但多路复用只消除了响应必须按请求顺序返回的限制。所有 stream 仍然跑在同一条 TCP 连接上，而 TCP 只认字节顺序，不知道哪些字节属于哪个 stream。某个包丢了，它后面的字节即使已经到达，也要等丢失的那部分重传回来才能交给 HTTP/2。于是一个丢包会让这条连接上所有的 stream 一起等待，这是 TCP 层的队头阻塞。

除了丢包，HTTP/2 的发送还受两个限制：

- **流量控制**。DATA 帧同时受 stream 级和连接级两个窗口约束，流窗口用完会暂停该流的数据发送，连接窗口用完则影响整条连接的 DATA 帧，需要等接收端发 `WINDOW_UPDATE` 补充窗口。
- **并发流上限**。对端通过 `SETTINGS_MAX_CONCURRENT_STREAMS` 限制同时打开的 stream 数量，达到上限后，新请求要等已有 stream 结束。

## 4. HTTP/3 与 QUIC {#http3-与-quic}

HTTP/3 用 QUIC 替代 TCP，避免一个流的数据缺口阻止其他流交付数据。

**QUIC** 是运行在 UDP 之上的传输协议，自己实现了可靠、有序的流。和 TCP 不同，QUIC 知道每个字节属于哪个流，并且分别保证每个流内部的顺序。一个流缺了字节，只有这个流要等重传，其他流已经完整到达的数据可以继续交给应用。头部压缩改用 QPACK，它在 HPACK 的思路上做了调整，以适应流之间乱序到达。

HTTP/3 并没有让流之间完全独立。所有流仍然共享连接的带宽和拥塞控制，丢包引起的拥塞反应会降低整条连接的发送速度。QPACK 的动态表也带来一种依赖：如果某个头部引用了还没收到的动态表条目，解码这个头部就要等待。

QUIC 还把 TLS 1.3 握手集成到了自己的握手里，减少建连的往返次数。它用**连接 ID** 而不是 IP 和端口来识别连接，所以手机从 Wi-Fi 切到蜂窝网络、地址变了之后，连接有机会继续使用。不过迁移是否成功，还取决于对端的策略和对新路径的验证。

## 5. 连接池 {#连接池}

**连接池**是客户端保存、复用连接的组件，它限制同时使用的连接数，以及请求为了拿到连接最多等多久。对 HTTP/2 和 HTTP/3 来说，一条连接能承载多个流，所以还要限制每条连接上的并发流数。池里的连接或流名额都被占满时，新请求先在客户端排队。

连接也不能一直留着。空闲超时决定没有请求的连接多久后关闭，最大寿命决定一条连接最多用多久。连接存活太久会带来问题：服务端实例已经下线摘流，或者中间的负载均衡、NAT 设备早已因空闲把连接清掉，客户端再用它发请求就会失败。反过来，连接开得太多也有代价，每条连接都占客户端和服务端的内存，还会给服务端带来额外压力。

池的大小没有通用答案，要结合请求耗时、并发量和服务端能承受的连接数，通过压测确定。上线后再用[分段耗时指标](#分段耗时指标)观察请求是否大量卡在池等待上。

## 6. 超时设置 {#超时设置}

一次 HTTP 调用会经过好几个阶段，每个阶段的超时只管自己那一段：

| 超时 | 约束范围 |
| --- | --- |
| 连接池等待 | 等待可用连接或并发流名额。 |
| 连接建立 | 建立传输连接。 |
| TLS 握手 | 协商密钥与验证端点。 |
| 读取或写入 | 客户端定义的单次或阶段等待。 |
| 空闲超时 | 连接连续没有活动的时间。 |
| deadline | 包含排队和重试的总时间预算。 |

不同客户端对同一个名字的定义可能不一样。比如 DNS 解析和 TLS 握手算不算在 connect timeout 里，读取超时指的是单次 `read` 没有数据的时间，还是读完整个响应的时间，都要看所用客户端的文档。配置之前先核对这些语义，否则设了 800ms 读取超时，调用仍然可能远远超过 800ms。

**deadline** 是一次调用最晚应结束的时间。调用开始到这个时刻之间的时间是总预算，所有阶段和重试都要从里面扣。假设总预算是 800ms，请求在连接池里排队用了 200ms，第一次尝试又用了 400ms，那么后面的重试连同退避等待最多只剩 200ms。如果每次重试都重新获得一个完整的 800ms，调用方实际等待的时间就会远超预期。

## 7. 重试 {#重试}

请求失败后能不能重试，取决于重复执行会不会产生额外的副作用。

**幂等**是指同一个请求执行一次和执行多次，对服务端的预期效果相同。GET 是**安全方法**，也就是客户端不通过它请求改变资源状态；PUT 和 DELETE 会改变状态，但它们也是幂等的：把资源设成同一个值两次，结果一样；删除同一个资源两次，资源都不存在。第二次 DELETE 可能返回 404，响应不同，但服务端状态没有区别，仍然满足幂等语义。

超时只说明客户端没及时收到结果，不能证明服务端没有执行请求。幂等请求允许在结果不明时重试，但仍要受剩余预算和重试次数限制。POST 本身不保证幂等，重复发送可能扣两次款、建两个订单。常见的处理是让客户端生成一个稳定的**业务幂等键**，每次重试都带上同一个键，服务端发现已经处理过就直接返回之前的结果。重试还要求请求体能再发一次，比如流式上传的数据如果已经读完了，就没法重发。

所以可以按请求的状态区分：

- 确认请求根本没发出去（比如在连接池里就超时了），重试不会重复执行业务，但还要判断剩余预算是否足够。
- 结果不明的请求，只有幂等语义或幂等键能保证安全，否则要先查询结果再决定。

重试本身也要克制：限制次数，每次之间加入退避和随机抖动，避免大量客户端同时重试把服务端压垮。调用链上只在选定的一层重试。如果三层调用每层都最多尝试 3 次，一次失败最多会让最底层的服务收到 27 倍的请求。

## 8. 分段耗时指标 {#分段耗时指标}

调用变慢时，只看总耗时无法判断慢在哪里，需要按阶段分别记录：连接池等待、DNS 解析、建连、TLS 握手、首字节时间、读取响应的时间，以及重试次数和服务端自己记录的处理耗时。用 HTTP/2 时，再观察活动流数和流量控制窗口。

有了这些指标就能定位方向。客户端看到的耗时很长，服务端处理却很快，问题就在两者之间：先看是否在连接池排队或者频繁新建连接，再检查网络重传、代理等待和重试。服务端处理本身就慢，才需要去看业务逻辑。

## 9. 常见问题 {#常见问题}

### 9.1 HTTP/2 客户端只需要一条连接吗？ {#http2-的连接数量}

HTTP/2 一条连接能承载很多流，但不代表一个客户端只会有一条连接。目标地址不同、代理策略要求分开，或者单连接的并发流上限不够用时，都会出现多条连接。一条连接出问题会影响上面所有的流，所以连接数量也要考虑故障隔离，而不是越少越好。

### 9.2 有了读取超时，为什么还需要调用截止时间？ {#读取超时与调用截止时间}

读取超时只约束客户端定义的读取阶段，具体范围看客户端实现；deadline 限制的是整个调用最晚什么时候结束。调用方把剩余预算传给下游，下游就知道自己还有多少时间，超过截止时间的工作应该及时取消，而不是继续算出一个没人要的结果。

## 10. 面试题 {#面试题}

### 10.1 HTTP/1.1、HTTP/2 和 HTTP/3 如何处理并发请求 {#http-concurrency}

**考察重点**

- 持久连接、多路复用和 stream 的关系。
- HTTP/2 的 TCP 队头阻塞与 HTTP/3 的改进。
- 协议能力与连接池、超时、重试之间的边界。

**相关内容**：[HTTP/1.1 持久连接](#http11-持久连接)至[重试](#重试)。

<details>
<summary>参考回答</summary>

**HTTP/1.1 的响应按请求顺序返回；HTTP/2 允许多路复用，但受 TCP 队头阻塞影响；HTTP/3 用 QUIC 分别处理各流的有序交付。**

- HTTP/1.1 通过持久连接复用 TCP。即使用流水线连续发请求，响应也必须按请求顺序返回，前一个慢了后面都要等，所以客户端一般开多条连接并发。
- HTTP/2 把消息拆成带 stream 编号的帧交错发送，响应不必按请求顺序返回。但底层是一条 TCP 连接，丢一个包，后面所有 stream 的数据都要等重传。
- HTTP/3 用 QUIC 分别保证每个流的顺序，一个流丢包不挡其他流。不过所有流仍共享拥塞控制，QPACK 的动态表引用也可能让头部解码等待。

无论哪个版本，实际并发能力还受连接池容量、并发流上限和调用总 deadline 约束。

</details>

### 10.2 设置 800ms 读取超时后，为什么调用还能超过 800ms？ {#deadline-and-retry}

**考察重点**：局部超时、总预算和安全重试。

**相关内容**：[超时设置](#超时设置)、[重试](#重试)。

<details>
<summary>参考回答</summary>

**读取超时只覆盖客户端定义的读取等待，不是连接池排队、建连、握手和重试共用的总预算。**

比如排队 200ms、建连和握手 100ms、读取 700ms 没超时，总耗时已经是 1 秒；如果第一次失败后再重试，时间还会叠加。要限制调用方的等待时间，应该设置 800ms 的总 deadline，每次尝试之前扣掉已经用掉的时间，剩余时间不够就不再重试。重试的如果是结果不明的写请求，还需要幂等键或者先查询结果，避免重复执行。

</details>

### 10.3 HTTP/2 已经多路复用，为什么发送仍会等待？ {#http2-flow-control}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：双层流量窗口与并发限制。

**相关内容**：[HTTP/2 多路复用](#http2-多路复用)。

<details>
<summary>参考回答</summary>

**多路复用只让 stream 之间不必按顺序排队，发送仍然受流量控制、并发流上限和底层 TCP 的约束。**

DATA 帧同时受 stream 窗口和连接窗口限制，任何一个用完，相关数据就要等对端发 `WINDOW_UPDATE`。对端设置的 `SETTINGS_MAX_CONCURRENT_STREAMS` 限制同时打开的 stream 数，达到上限后新请求要等。此外 TCP 的拥塞控制和按字节顺序交付仍然生效，丢包时整条连接上的 stream 都会等待重传。

</details>
