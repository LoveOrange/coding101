# Go 逃逸分析

**逃逸分析**是编译器沿引用和赋值关系，判断对象能否安全放在栈上的分析。对象的引用如果可能比当前栈上的存储活得更久，就需要安排足够长的生命周期。Go 允许返回局部变量的指针，正是因为存储位置不会仅由源码中的声明位置决定。

面试中判断是否逃逸，要看对象交给了谁、调用方还能保留多久，以及编译器掌握了多少信息。看到 `&`、接口或闭包就直接判定堆分配，会漏掉内联和数据流分析的作用。本文使用 Go 1.22.12；栈、堆和分配器的职责见 [Go 内存分配](memory-allocation.mdx#栈堆与变量)。

## 1. 面试核心 {#core}

- **逃逸分析发生在编译期，负责保护对象的生命周期**。它需要避免堆对象留下不安全的栈指针，也要避免一个引用继续使用已经结束或被复用的栈存储。[卡](#escape-purpose)
- **返回局部变量指针是安全的，但不能仅凭这个写法断定每次调用都发生堆分配**。内联可能把函数体纳入调用方，让编译器看到这个对象没有继续向外流出。[卡](#returned-pointer)
- **参数流向返回值，不等于参数指向的对象已经逃逸到堆**。要结合调用方怎么使用结果，区分 `leaking param ... to result`、`moved to heap` 和实际分配次数。[卡](#escape-report)
- **编译器信息不足、对象过大或切片空间无法静态确定，也会影响栈分配**。接口调用和闭包是需要检查的场景，不是可以脱离上下文使用的判定口诀。[卡](#escape-purpose)
- **堆分配会带来分配、保留和 GC 成本，但逃逸本身不是内存泄漏或程序错误**。先找真实的分配热点，再保持语义不变地优化，并用分配统计与业务指标验证。[卡](#allocation-cost)

## 2. 生命周期与数据流 {#生命周期与数据流}

### 2.1 编译器要保证什么 {#编译器要保证什么}

一个函数的栈帧不会永久保留。函数返回后，对应空间可以用于其他调用；循环中的存储也可能被后续迭代复用。编译器必须保证一个仍然有效的 Go 引用，不会指向已经结束其生命周期的旧对象存储。

Go 1.22.12 的逃逸分析把变量、隐式创建的对象和赋值关系组织成数据流图，检查地址可能流向哪里。除了当前函数，它还记录参数向堆、向返回值流动的信息，供能够确定目标的调用位置使用。

因此，判断时应沿着具体路径看：局部对象的地址只是交给一个临时读取它的函数，还是存入了全局变量、可能在调用结束后继续存在的对象，或者被返回给调用方？这些路径有不同的生命周期要求。

编译器分析也有精度边界。它不会执行程序来证明某次运行的所有分支，而会在无法排除较长生命周期时采取保守处理。源码中“我知道这里不会保存它”，并不等于编译器已经得到这份信息。

### 2.2 编译期决策与运行时存储 {#编译期决策与运行时存储}

编译期判断需要堆存储后，生成的代码会按相应路径创建对象。一般不是程序先把对象放在栈上，等函数准备返回时再临时把它搬到堆上。

这与 goroutine 栈增长时复制栈内容是两件事，也与 GC 判断堆对象是否仍可达是两件事。逃逸分析决定如何满足存储生命周期，GC 处理堆对象后续的回收，见 [Go 垃圾回收](garbage-collection.mdx#可达性)。

“没有逃逸”也不能直接翻译成“必定占用了几个栈字节”。后续优化可能把值放在寄存器中、只保留其中的字段，或者消除不需要的对象。

## 3. 返回指针与内联 {#返回指针与内联}

**内联**是把被调用函数的代码展开到调用位置的编译优化。它能改变编译器看到的分析范围，使原本跨函数边界的引用流动变成同一段代码里的局部使用。

下面两个函数都返回局部变量的地址，其中一个允许正常内联，另一个用 `//go:noinline` 固定函数边界：

```go
package main

import (
	"fmt"
	"testing"
)

var result int

func square(n int) *int {
	x := n * n
	return &x
}

//go:noinline
func squareSeparate(n int) *int {
	x := n * n
	return &x
}

func main() {
	a := testing.AllocsPerRun(1000, func() { result = *square(7) })
	b := testing.AllocsPerRun(1000, func() { result = *squareSeparate(7) })
	fmt.Println(a, b, result)
}
```

在 Go 1.22.12、darwin/arm64、默认优化下，输出为 `0 1 49`。内联后的 `square(7)` 只在当前调用方读取结果，不需要把这个整数作为独立堆对象保留下来。`squareSeparate` 保留函数边界，返回的指针需要引用函数返回后仍有效的存储，观察到一次堆分配。

两种写法都安全。差异在于生成代码是否需要堆对象，不在于其中一个会产生悬空指针。`//go:noinline` 只是用于对照分析条件，不是推荐给业务代码的性能开关。

如果对整个示例使用 `go run -gcflags=-l main.go` 关闭内联，这个版本下输出会变为 `1 1 49`。因此，不能用关闭内联后的结果代表默认构建，也不能把某次得到的零次分配当作语言保证。

## 4. 编译器报告 {#编译器报告}

### 4.1 查看分析结果 {#查看分析结果}

在独立目录保存示例为 `main.go` 后，使用 `go build -gcflags=-m=2 main.go` 可以查看较详细的优化和逃逸报告。`-m` 输出优化判断，多次指定或使用 `-m=2` 会提供更多信息；`-l` 则是关闭内联，只有需要对照时再加。

报告描述的是编译器看到的表达式和流向，不能仅搜索一个 `escapes` 就给整个函数下结论：

| 报告片段 | 主要含义 | 仍需检查什么 |
| --- | --- | --- |
| `moved to heap: x` | 这个分析位置的 `x` 需要堆存储 | 是否另有内联后的调用位置；最终执行了哪条路径 |
| `new(T) escapes to heap` | 这个创建表达式被判为需要堆分配 | 运行时是否确实执行、对象是否为零大小等条件 |
| `does not escape` | 该表达式未被分析为向外逃逸 | 后续优化和实际代码生成，不能据此断言固定栈布局 |
| `leaking param: p to result ~r0 level=0` | 参数指针本身流到返回值 | 调用方是否继续保存返回的指针 |
| `leaking param content` | 参数指向的内容通过相应路径向外流动 | 具体间接引用关系，不能直接说参数变量自身被搬到堆 |

前面的 `square` 原函数可能出现 `x` 需要堆存储的报告，但内联到具体调用位置后，编译器还能重新处理那个局部实例。报告中可能同时出现原函数和内联位置的信息，这并不与实际观察到零次分配矛盾。

### 4.2 参数流向返回值 {#参数流向返回值}

把传入的指针原样返回，不会自动让调用方的对象进入堆。下面保留函数边界，分别比较返回参数和保存参数：

```go
package main

import (
	"fmt"
	"testing"
)

var saved *int
var result int

//go:noinline
func identity(p *int) *int { return p }

//go:noinline
func save(p *int) { saved = p }

func main() {
	a := testing.AllocsPerRun(1000, func() {
		x := 7
		result = *identity(&x)
	})
	b := testing.AllocsPerRun(1000, func() {
		x := 7
		save(&x)
	})
	fmt.Println(a, b, result, *saved)
}
```

输出为 `0 1 7 7`。`identity` 的参数流向返回值，但调用方只是立即解引用读取 `x`，没有继续保存指针。`save` 把指针交给全局变量 `saved`，`x` 需要在本次调用结束后仍有效。

对应报告中，`identity` 会说明 `p` 流向返回值；`save` 的参数则流向堆。关注的是 `p` 指向的对象需要活多久，不是“函数有一个指针参数，所以参数变量一定在堆上”。

`fmt.Println` 自己也可能让用于输出的接口参数出现在报告里。本例把输出放在 `AllocsPerRun` 测量之后，避免把打印的分配混进待比较的代码。报告里的某个值向接口流动，也不表示整个被访问的对象都以同一种方式逃逸。

## 5. 影响判断的其他条件 {#影响判断的其他条件}

### 5.1 接口调用与目标信息 {#接口调用与目标信息}

接口类型本身不是逃逸开关。编译器能确定具体调用目标时，可以利用被调用函数的信息；如果只能看到一个可能有不同实现的接口调用，就可能需要保守地认为参数会被保存。

```go
package main

import (
	"fmt"
	"testing"
)

type Reader interface{ Read([]byte) }
type Fill struct{}

func (Fill) Read(b []byte) { b[0] = 7 }

var result byte

//go:noinline
func known() byte {
	var b [8]byte
	Fill{}.Read(b[:])
	return b[0]
}

//go:noinline
func throughInterface(r Reader) byte {
	var b [8]byte
	r.Read(b[:])
	return b[0]
}

func main() {
	a := testing.AllocsPerRun(1000, func() { result = known() })
	b := testing.AllocsPerRun(1000, func() { result = throughInterface(Fill{}) })
	fmt.Println(a, b, result)
}
```

Go 1.22.12 下输出为 `0 1 7`。`known` 中，编译器看得到 `Fill.Read` 不保留切片；`throughInterface` 保留了接口调用边界，不能在它的函数体里假定所有 `Reader` 都与 `Fill` 一样，因此把局部数组 `b` 按需要更长生命周期处理。

这不证明接口调用永远分配，也不证明接口转换本身在此分配了一份 8 字节数组。原因是参数所指的数组通过无法静态确定目标的调用流出；内联、去虚拟化或代码组织变化后，需要重新检查。接口的类型关系见 [Go 接口](../language/interfaces.mdx)。

### 5.2 大小与动态空间 {#大小与动态空间}

即使引用没有离开当前函数，编译器也不会无条件把任意大小的对象塞进栈。Go 1.22.12 默认实现对显式变量有 10 MiB 的大小限制，对 `new`、切片底层数组等隐式对象有 64 KiB 的限制，还会检查对齐条件。这些是实现策略，不能作为未来版本的语言承诺。

例如，常量大小且满足其他条件的 `make([]byte, 16)` 可以不在堆上分配。若分析时只能看到 `make([]byte, n)`，无法把 `n` 化成合适的编译期常量，会报告 `non-constant size`，采用堆分配路径。即使运行时传入的恰好是 16，也不等于编译时已经知道这个值。

大小检查的 `too large for stack` 和引用流出是不同原因。阅读报告时先确认具体原因，不能把所有堆分配都解释成“函数返回了它”。运行时执行零长度或零大小创建等特殊情况时，也不能仅凭编译期选择的路径推断一定发生非零空间分配。

### 5.3 闭包与 goroutine {#闭包与goroutine}

闭包需要保留它使用的外部变量，但是否需要堆存储，还取决于闭包和被捕获变量的使用范围。立即执行、没有向外保存的闭包，可以在当前调用内完成；返回或长期保存闭包，则需要让被捕获的状态活得足够久。

启动 goroutine 还会带来独立的执行生命周期。即使代码随后等待它结束，Go 1.22.12 的编译器也不会把任意业务同步过程都证明为“被引用对象只需留在原调用栈上”。要看具体报告，不能根据自己知道的执行顺序直接改判。

同样，按值捕获与捕获共享变量是语义差异，不能为了减少分配随意替换。相关示例见 [Go 函数](../language/functions.mdx#闭包与变量捕获)。

## 6. 分配优化 {#分配优化}

堆分配需要取得和初始化存储，存活对象还会影响 GC 的扫描与保留成本。高频路径重复创建短命对象，可能因此增加 CPU 或内存压力；但对象确实需要跨调用存活时，堆分配就是满足正确语义的一部分。

优化时先固定输入和构建条件，再把编译器报告与实际分配联系起来：

1. 找到频繁创建的对象，确认报告描述的是哪个表达式、哪条调用路径。
2. 使用 `testing.AllocsPerRun` 或基准测试的分配指标，确认实际执行是否分配；别把打印、准备数据或全局测试干扰算进待比较逻辑。
3. 在保持所有权、别名关系和生命周期不变的前提下，减少无必要的中间对象、复制或重复分配。
4. 再检查耗时、存活内存和业务表现，避免只降低分配次数却长期保留过大的缓冲区。

`AllocsPerRun` 的预热、单 P 和整数平均边界见 [Go 内存分配](memory-allocation.mdx#new和make不指定栈或堆)。零次堆分配不能证明代码一定更快，使用指针也不自动比传值更省成本：小值复制可能很便宜，指针则可能延长对象生命周期或增加间接访问。

不要通过不安全地址转换来让编译器“看不到引用”，也不要依赖某个对象碰巧逃逸来保证并发安全。逃逸分析保护存储生命周期，不能替代 [Go 内存模型](../concurrency/memory-model.mdx) 中的同步关系。

## 7. 面试题 {#面试题}

### 7.1 Go 逃逸分析做什么，哪些条件会影响结果？ {#escape-purpose}

**考察重点**：编译期数据流、生命周期约束、调用信息与存储大小条件。

**相关内容**：[生命周期与数据流](#生命周期与数据流)、[影响判断的其他条件](#影响判断的其他条件)

<details>
<summary>参考回答</summary>

**逃逸分析在编译期判断对象能否安全放在栈上，避免引用使用已经失效或被复用的栈存储。**

编译器沿赋值、参数和返回值等关系分析地址流向。对象被交给全局存储或其他可能长期保留它的路径时，通常需要堆存储；内联和已知调用目标提供更多信息，可能改变具体位置的判断。

对象过大、对齐要求或无法静态确定的切片空间，也会影响栈分配。没有逃逸不保证对象一定保留在栈上，后续优化还可能把它消除或放入寄存器。

</details>

### 7.2 返回局部变量的指针安全吗？一定会有一次堆分配吗？ {#returned-pointer}

**考察重点**：引用有效性、原函数与内联位置的区别；语义保证和实现优化的区别。

**相关内容**：[返回指针与内联](#返回指针与内联)

<details>
<summary>参考回答</summary>

**安全，但不能单凭这个写法保证每次调用都产生堆分配。** 编译器会让被返回指针引用的对象保持足够长的生命周期。

保留函数边界时，创建于函数内、又被返回指针引用的对象通常需要堆存储；内联后，编译器可能看到调用方只短暂使用它，进而避免堆分配。原函数的逃逸报告与内联位置的判断需要分别看。

要确认实际分配，固定版本和编译条件，结合报告与分配统计验证，不能把关闭内联的实验当作默认构建结果。

</details>

### 7.3 leaking param to result 和 moved to heap 有什么区别？ {#escape-report}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：参数流向、对象存储位置和实际执行分配之间的关系。

**相关内容**：[编译器报告](#编译器报告)

<details>
<summary>参考回答</summary>

**前者描述参数向返回值的数据流，后者描述具体分析位置的变量需要堆存储，不能互相替代。**

例如 `identity(p *int) *int` 原样返回 `p`，会把参数流向结果记录下来。调用方若只立即读取结果，它原来的局部对象仍可能不分配到堆；如果把结果保存到全局位置，就有不同的生命周期要求。

报告也不是实际分配计数。内联位置、运行时分支、零大小对象和后续优化等都需要区分，再用可重复的分配测量确认。

</details>

### 7.4 结构体逃逸到堆有什么代价？怎样验证分配优化？ {#allocation-cost}

**考察重点**：分配与 GC 成本、生命周期合理性、保持语义的优化与测量。

**相关内容**：[分配优化](#分配优化)

<details>
<summary>参考回答</summary>

**逃逸到堆可能增加分配和 GC 成本，但不是内存泄漏，也不必然意味着设计有错。** 跨调用存活的对象需要合适的存储，不能为了少一次分配破坏引用和生命周期。

先确认热点和对象流向，再考虑减少无必要的中间对象、复制或重复创建。固定版本、输入和编译条件，用逃逸报告解释原因，用分配次数和字节验证变化，再检查耗时与存活内存。

不能把所有指针改成值来追求“无逃逸”，也不能仅凭零次分配断言更快；复制大小、别名语义和保留容量都会影响结果。

</details>
