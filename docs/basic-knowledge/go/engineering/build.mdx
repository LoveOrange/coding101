# Go 构建

**Go 构建**是根据目标平台和构建条件选择源码，解析依赖，再编译、链接得到目标产物的过程。对一个 `main` 包执行 `go build`，通常得到可以直接启动的可执行文件。

本地编译通过，只能说明这组源码在当前构建条件下可以生成产物。把程序交给另一台服务器，还要确认操作系统、CPU 架构、动态库和运行配置。面试中解释交叉编译与部署问题，重点就在这些条件如何影响构建结果。本文以 Go 1.22.12 的标准工具链为准。

## 1. 面试核心 {#core}

- **`go build` 负责构建，`go run` 先构建再运行，`go test` 构建并运行测试程序**。构建通过不代表测试通过，也不代表目标环境能启动。[卡](#build-run-test)
- **构建以包为单位，并按目标平台、文件名和构建约束选择源码**。直接列出 `.go` 文件，可能漏掉同包的其他文件，也会绕开这些文件上的构建约束。[卡](#source-selection)
- **交叉编译是在当前机器上生成另一种目标平台的程序**。`GOOS` 决定目标操作系统，`GOARCH` 决定目标架构；它们改变生成的代码和平台实现，不会把目标程序变成当前机器可以执行的程序。[卡](#cross-compilation)
- **使用 cgo 的交叉编译还需要目标平台的 C 工具链及相关头文件、库**。关闭 cgo 可能选择纯 Go 实现，也可能使依赖无法构建，不能一概当成修复办法。[卡](#cgo-boundary)
- **交付要同时确认二进制身份和运行依赖**。构建版本、目标平台、配置、证书与动态库等条件都可能影响启动和运行；单文件并不等于不需要运行环境。[卡](#binary-delivery)
- **Linux 的程序装载、Go runtime 初始化和业务代码执行是不同阶段**。系统调用由具体平台实现和程序行为决定，不能把一次观察到的调用列表当成所有 Go 程序的固定顺序。[卡](#linux-execution)

## 2. 构建命令与产物 {#构建命令与产物}

### 2.1 包与可执行程序 {#包与可执行程序}

一个普通包提供可以被其他包导入的代码；一个 `main` 包提供程序入口。构建可执行程序时，工具链不仅编译 `main` 包，还会处理它依赖的包，并把需要的代码与 Go runtime 链接进产物。

例如在已经包含 `go.mod` 的模块中，创建 `cmd/hello/main.go`：

```go
package main

import (
    "fmt"
    "runtime"
)

func main() {
    fmt.Printf("hello %s/%s %s\n", runtime.GOOS, runtime.GOARCH, runtime.Version())
}
```

在模块根目录执行：

```sh
go build -o ./bin/hello ./cmd/hello
./bin/hello
```

使用本文工具链在 macOS ARM64 上构建并运行，输出 `hello darwin/arm64 go1.22.12`。`runtime.GOOS` 和 `runtime.GOARCH` 表示构建目标，因此同一份源码构建成 Linux ARM64 程序后，在相应环境运行会输出 `linux/arm64`。

没有指定 `-o` 时，构建单个 `main` 包通常按导入路径末尾的名称生成可执行文件，Windows 目标还会加上 `.exe`。构建普通非 `main` 包或多个包时，默认行为主要用于确认这些包可以构建，不会为每个包都在当前目录生成可执行文件。`-o` 可以显式指定产物位置。

### 2.2 build、run、test 与 install {#构建运行测试与安装}

| 命令 | 主要作用 | 需要区分的边界 |
| --- | --- | --- |
| `go build ./cmd/hello` | 构建指定程序 | 不运行程序，也不运行 `_test.go` 中的测试 |
| `go run ./cmd/hello` | 构建并运行程序 | 使用临时构建产物，不是逐行解释执行，也不提供固定位置的交付文件 |
| `go test ./...` | 构建并测试当前模块内匹配的包 | 只覆盖实际选择并执行的测试，默认不会越过嵌套模块边界 |
| `go test -c -o ./bin/hello.test ./cmd/hello` | 编译该包的测试二进制 | 不执行测试；可用于在相应目标环境中运行测试 |
| `go install ./cmd/hello` | 构建并安装命令 | 命令安装到 `GOBIN`，未设置时通常是 `GOPATH/bin`，不等于配置好服务器服务 |

`go build` 会忽略 `_test.go` 文件。假如一个测试包含错误断言，业务源码仍可能正常构建，随后 `go test` 才会失败；测试文件本身有编译错误，也不会由普通 `go build` 自动发现。

跨平台执行 `go test` 还涉及运行测试二进制。如果宿主机无法执行生成的目标程序，测试不能直接运行；需要相应目标环境，或明确配置能够执行它的工具。`go test -c` 只完成编译，不能据此报告测试通过。

## 3. 源码选择与编译链接 {#源码选择与编译链接}

### 3.1 构建约束 {#构建约束}

**构建约束**决定一个源码文件是否进入当前包的构建。平台相关实现可以放在不同文件里，让工具链按目标条件选取。

例如下面两个文件位于同一个包中，分别提供 Linux 与其他平台的实现：

```go title="platform_linux.go"
package main

func platformLabel() string {
    return "linux"
}
```

```go title="platform_other.go"
//go:build !linux

package main

func platformLabel() string {
    return "other"
}
```

`platform_linux.go` 的 `_linux` 文件名后缀隐含 Linux 构建条件；`platform_other.go` 的 `_other` 不是已定义的目标系统后缀，因此用 `//go:build !linux` 明确条件。两份实现互斥，构建 Linux 目标时选择第一份，在 macOS 上选择第二份。

`//go:build` 放在文件开头、`package` 之前，并与包声明用空行分隔。表达式可以组合目标系统、架构、`cgo` 和自定义标签。例如 `//go:build linux && integration` 要求同时满足 Linux 目标与 `integration` 标签，构建时可通过 `-tags=integration` 添加后者。只把标签命名为 `production`，不会自动启用优化或赋予代码额外权限。

以包路径执行 `go build ./cmd/hello` 时，工具链选择这个包符合条件的文件。如果改为显式列出 `go build main.go`，工具链只把指定文件组成一个包，忽略这些指定文件上的构建约束。这样既可能漏掉 `platformLabel` 的定义，也可能把原本只适用于其他平台的文件送入编译。实际项目优先按包构建。

### 3.2 依赖、编译与链接 {#依赖编译与链接}

依赖解析先确定需要哪些包及模块版本，再对选中的源码进行语法和类型检查、优化与机器代码生成，最后链接出产物。模块版本规则见 [Go Modules](./modules.mdx#版本选择)；`go.mod` 中的 Go 版本要求与本次实际使用的工具链也要分开确认。

Go 的构建缓存可以复用已完成的工作，所以一次 `go build` 不一定重新编译所有依赖。观察构建过程可以使用：

```sh
go version
go env GOOS GOARCH CGO_ENABLED GOTOOLCHAIN GOWORK
go build -x -o ./bin/hello ./cmd/hello
```

`-x` 打印实际执行的构建命令。命中缓存时，输出中可能没有预期的某次编译动作，这不能说明编译步骤不存在。需要分析缓存时，应先确认输入、工具链、构建参数和相关环境，不要把清空缓存当成解释问题的替代品。

链接解决各部分代码和数据之间的引用，并生成目标格式的文件，例如 Linux 上的 ELF、Windows 上的 PE、macOS 上的 Mach-O。Go runtime 会随应用构建进入产物，负责调度、内存管理等工作；通常不需要在运行机器上再安装 Go 编译器。

## 4. 目标平台与交叉编译 {#目标平台与交叉编译}

### 4.1 GOOS 与 GOARCH {#目标系统与架构}

**交叉编译**是在一种宿主环境中生成另一种目标环境的程序。编译器本身运行在宿主机，但按目标平台选择源码、指令集、调用约定和可执行文件格式。

以没有 cgo 依赖的 `hello` 为例，在 macOS 的 shell 中执行：

```sh
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -o ./bin/hello-linux-arm64 ./cmd/hello
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -o ./bin/hello-windows-amd64.exe ./cmd/hello
go version -m ./bin/hello-linux-arm64
```

第一条命令生成 Linux ARM64 文件，第二条生成 Windows AMD64 文件。`go version -m` 可以查看产物中的工具链、模块和构建设置，包含这里的 `GOOS`、`GOARCH` 与 `CGO_ENABLED`。

第一份产物在 Linux ARM64 环境中运行会输出 `hello linux/arm64 go1.22.12`。把它放回 macOS 直接启动，并不会因为两台机器都是 ARM64 就变成 macOS 程序；操作系统接口和文件格式仍然不同。交叉编译提供生成目标程序的能力，运行和测试需要目标环境或合适的兼容、仿真设施。

可以使用 `go tool dist list` 查看当前工具链支持的系统与架构组合。支持某个组合也不代表它适用于任意旧内核、任意 CPU 特性或所有第三方库；这些仍受工具链最低要求、架构选项和依赖实现约束。

### 4.2 cgo 的额外条件 {#cgo的额外条件}

**cgo** 让 Go 包可以调用 C 代码。包含 `import "C"` 的文件会参与 cgo 处理，需要相应的 C 编译工具和依赖。

例如下面的独立程序调用一个最小 C 函数：

```go
package main

/*
static int add(int a, int b) { return a + b; }
*/
import "C"

import "fmt"

func main() {
    fmt.Println(C.add(2, 3))
}
```

在已安装本机 C 编译器、且启用 cgo 的环境中构建并运行，输出 `5`。如果关闭 cgo，包含 `import "C"` 的文件会被排除；这个包只有这一份源码，因而无法构建。设置 `CGO_ENABLED=0` 并不会把 C 函数自动改写成 Go。

交叉编译默认关闭 cgo。需要它时，应显式启用，并通过 `CC` 等配置指定面向目标系统和架构的 C 编译器；相关头文件、目标库和链接环境也必须匹配。只有本机 macOS 的 C 编译器，不等于已经具备构建 Linux C 依赖的完整条件。

某些包同时提供 cgo 与纯 Go 实现，关闭 cgo 后可以继续构建，但行为或能力可能变化；另一些包没有替代实现，会直接失败。因此应先检查依赖和需求，再决定是否关闭 cgo。

### 4.3 静态链接与动态依赖 {#静态链接与动态依赖}

**静态链接**把所需库代码包含在最终产物中；**动态链接**让程序在运行时依赖外部共享库。本文关闭 cgo 的 Linux `hello` 可构建成静态链接文件，但不能把这个结果推广成“所有 Go 程序都是静态链接”。

使用 cgo 的程序可能依赖 libc 或其他共享库，具体情况取决于构建模式、工具链和链接配置；cgo 也不意味着只能动态链接。交付到 Linux 时，应确认产物需要的动态装载器和共享库是否存在、版本及架构是否匹配。基于 glibc 的产物不能仅凭“都是 Linux”就认定能够在只有 musl 的环境中运行。

即使二进制本身是静态链接，业务仍可能读取配置、TLS 根证书、时区数据或外部资源。单文件解决的是一部分代码交付问题，没有消除这些运行需求。

## 5. 构建记录与程序交付 {#构建记录与程序交付}

交付一个可执行程序时，先建立产物与源码之间的对应关系，再验证目标环境中的行为。可以按下面的顺序准备：

1. 固定源码提交、工具链版本与依赖，明确是否启用工作区、本地替换或 vendor。
2. 运行适用的测试，并明确哪些测试是在宿主环境执行、哪些需要目标平台执行。
3. 用明确的目标系统、架构和构建参数生成产物，记录校验值及版本信息。
4. 在目标环境确认启动、配置读取、外部依赖连接和关键业务行为，再交给相应的进程管理或容器运行方式。

`go version -m` 能帮助检查二进制中的构建信息，但这些信息不是可信签名，也不能代替产物校验与来源记录。某些信息是否嵌入还受构建方式影响，不能假定任意二进制都有完整的 Git 提交与依赖信息。

`-trimpath` 可以去掉构建结果中记录的本机文件系统路径，使调试信息等使用模块或导入路径。它有助于减少机器差异，但相同命令并不足以保证相同字节的产物：源码、依赖、实际工具链、构建参数、版本控制元数据，以及使用 cgo 时的外部工具和库，都可能成为输入。

程序启动失败时，先观察失败发生在哪一层：

| 现象 | 优先核对 |
| --- | --- |
| 可执行格式错误 | 操作系统、CPU 架构和文件是否完整 |
| 文件存在却提示无法找到，或装载器报错 | 动态装载器路径、共享库、架构与权限；也要检查实际启动路径 |
| 启动后立刻退出 | 程序日志、参数、配置、端口与外部服务 |
| `go run` 在开发机成功，交付程序失败 | 两次构建的源码、依赖、环境变量、目标条件和工作目录是否一致 |

构建命令不负责注册系统服务、准备数据库、注入配置或设置健康检查。这些属于运行部署的工作，需要和产物一起验证。

## 6. Linux 上的执行过程 {#Linux上的执行过程}

Linux 启动一个已经构建好的 Go 程序，不需要重新解释 Go 源码。调用方请求内核执行文件，内核建立新的程序映像，之后才进入程序自己的启动代码。

### 6.1 程序装载 {#程序装载}

`execve` 用指定程序替换当前进程的程序映像，并传入参数与环境。它本身不创建一个新 PID；shell 或进程管理程序可能先创建子进程，再由子进程执行它，具体实现不能简单固定成某一组调用。

内核识别 ELF 等文件格式，安排程序的内存映射与初始执行环境。动态链接 ELF 还会用文件中声明的解释器路径启动动态装载器，由它处理所需共享库。这里的“映射可执行文件”不能直接等同于“业务程序自己调用了一次 `mmap`”：其中有内核装载工作，也可能有用户态装载器发起的调用。

### 6.2 runtime 与业务代码 {#运行时与业务代码}

Go 启动代码初始化 runtime，随后按依赖顺序初始化包，最后调用 `main.main`。包内变量与 `init` 的顺序见 [Go 包初始化](../language/packages-initialization.mdx#从依赖包到main)。

在 Linux 上，运行过程中可能涉及用于内存管理的 `mmap`、用于线程创建的 `clone`、用于线程等待唤醒的 `futex`，以及信号相关调用。业务访问文件、网络或输出时，又会需要对应的文件与网络接口。具体名称、参数和出现顺序依赖目标架构、Go 版本、调度过程与业务行为，某些操作还可能通过 vDSO 等方式完成，并非每次都触发系统调用。

例如上述 `hello` 会向标准输出写入文本，但仅凭它调用了 `fmt.Printf`，不能推出任意 Go 输出语句都恰好对应一次固定形式的系统调用。上层函数、缓冲与底层接口之间的关系见 [系统调用](../../operating-system/system-calls.mdx#库函数与系统调用)。

若需要回答某个具体程序的执行细节，可以在 Linux 上对已知程序使用 `strace -f`，观察它及其线程、子进程发生的系统调用；同时区分跟踪的是 `go build`、`go run`，还是最终的二进制。跟踪 `go run` 看到的编译器进程和临时文件操作，不应算成业务程序每次启动都必经的步骤。

**相关内容**：[目标系统与架构](#目标系统与架构)、[cgo 的额外条件](#cgo的额外条件)。

<details>
<summary>参考回答</summary>

**编译器在宿主机运行，但根据 `GOOS`、`GOARCH` 等目标条件选择平台实现，并生成目标机器代码与可执行文件格式。** 它不要求宿主机能够直接执行生成的程序。

纯 Go 依赖通常可以直接指定目标平台构建；使用 cgo 时还要准备目标 C 工具链、头文件和库。生成成功之后，仍需在能够执行目标程序的环境中测试。

</details>

**考察重点**：cgo 源码选择、静态链接、目标兼容性与外部资源。

**相关内容**：[cgo 的额外条件](#cgo的额外条件)、[静态链接与动态依赖](#静态链接与动态依赖)。

<details>
<summary>参考回答</summary>

**不能。关闭 cgo 可能让依赖改用纯 Go 实现，也可能直接使构建失败；成功生成产物后仍受目标平台和运行条件约束。**

需要确认架构、CPU 特性与工具链支持的系统要求。即使产物没有动态库依赖，业务仍可能需要配置、证书和其他文件。使用 cgo 时则要进一步核对目标动态装载器与共享库，不能只看系统名称都是 Linux。

</details>

### 7.5 Go 程序如何生成可执行文件并交付给服务器？ {#binary-delivery}

**题型**：综合题

**考察重点**：构建入口、产物身份、目标平台与运行验证。

**相关内容**：[包与可执行程序](#包与可执行程序)、[构建记录与程序交付](#构建记录与程序交付)。

<details>
<summary>参考回答</summary>

**对程序的 `main` 包运行 `go build -o` 生成产物，并按服务器的系统、架构和依赖条件构建、验证和交付。**

先固定源码、工具链和依赖并执行测试，再明确 `GOOS`、`GOARCH` 与 cgo 条件。交付时记录版本与校验值，准备配置及外部依赖，在目标环境验证启动和关键业务。通常无需安装 Go 编译器，但动态库、证书和其他运行资源仍要按实际需求准备。

</details>

### 7.6 编译后的 Go 程序在 Linux 上执行，会涉及哪些系统调用？ {#linux-execution}

**考察重点**：构建与运行的区分、exec 装载、runtime 与业务调用。

**相关内容**：[Linux 上的执行过程](#Linux上的执行过程)。

<details>
<summary>参考回答</summary>

**应先区分程序装载、Go runtime 初始化和业务执行，具体调用集合由平台与程序行为决定。** 调用方可通过 `execve` 替换进程映像；动态链接产物还需要动态装载器处理共享库。

Linux 上的 Go runtime 可能使用 `mmap`、`clone`、`futex` 及信号相关调用；业务文件、网络与输出又会引入相应接口。它们不是每个程序都严格遵循的固定调用顺序。要确认某个程序，应跟踪最终二进制，并把 `go build` 或 `go run` 的编译过程与程序本身分开。

</details>
