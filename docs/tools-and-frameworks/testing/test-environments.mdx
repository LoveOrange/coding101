# 测试环境

**测试环境**是执行测试时被测程序及其依赖、配置、数据和运行资源的集合。同一份代码在两个环境得到不同结果，可能来自数据库版本、功能开关、账号权限或资源限制，不能只比较应用提交号。

测试结论必须带着环境范围理解。在小数据、单实例和本地依赖下通过，可以证明这些条件下的行为；若要判断线上容量或跨实例一致性，还需要对应的环境证据。

## 1. 面试核心 {#core}

- 可重复的测试需要记录**应用制品、依赖版本、配置、数据与资源条件**。一个分支名或“测试环境”标签不足以重建失败。[卡](#environment-manifest)
- **进程启动不等于服务就绪**。迁移、初始化与依赖连接完成后，还应验证当前测试需要的能力。[卡](#readiness)
- 临时环境可以隔离变更，但**外部共享服务、数据与配额仍可能互相影响**，建立和销毁都需要明确归属。[卡](#ephemeral-environment)
- 服务虚拟化可控地模拟依赖行为，**只提供被模拟条件下的证据**；真实协议与部署集成仍需要实际依赖验证。[卡](#virtualization-boundary)
- 压测环境要说明拓扑、容量、数据与流量差异，**不能按机器数量简单线性放大结果**。[卡](#performance-environment)

## 2. 环境描述与重建 {#环境描述与重建}

环境描述应该回答“重新做一遍需要哪些条件”，而不只是给出一个可访问 URL。

| 内容 | 需要记录的例子 |
| --- | --- |
| 应用 | 提交、构建产物、实际部署版本 |
| 运行时 | JDK 或 Python 版本、架构与必要系统能力 |
| 依赖 | 数据库、缓存、消息服务及关键插件版本 |
| 配置 | 功能开关、连接池、超时、路由和访问策略的版本 |
| 数据 | schema 迁移版本、基线数据、规模和隔离范围 |
| 资源 | 实例数、CPU／内存约束、共享宿主机或资源池 |
| 外部系统 | 实际测试端点、沙箱或替身，调用配额 |

依赖标签可能变化。例如镜像标签相同，背后对应的内容却已更新。需要精确重建时，应记录不可变制品标识或摘要；同时保留有计划的更新流程，不把固定版本理解成永远不更新。

秘密配置只记录引用、权限范围和必要版本信息，不把密码、令牌写入测试报告。排障需要知道使用了哪个测试凭证，不意味着需要公开它的明文。

制品构建和交付的通用机制见 [可重复交付](../../system-design/production/docker-ci-cd-reproducible-delivery.mdx)。环境记录则补足该制品运行时实际使用的条件。

## 3. 建立、就绪与销毁 {#建立就绪与销毁}

一次环境准备可以依次执行：分配资源、部署依赖、应用迁移、准备基线数据、启动应用、检查就绪，再执行测试。任意一步失败，都应保留阶段与证据，而不是让所有用例继续报业务失败。

**就绪**表示已经具备当前任务需要的服务能力。进程存在、端口可连接、健康接口返回成功，分别提供不同强度的证据：数据库端口已打开，不代表迁移已经完成；应用健康，也不一定说明测试账号权限正确。

例如 Docker Compose 只按照依赖顺序启动容器时，不能假设数据库已能接受业务查询。可以使用健康条件等待，再独立确认 schema 与必要功能。健康检查也应有总等待上限，失败时输出对应阶段。

销毁则按归属回收应用、数据和外部测试资源。构建失败后也可能已经分配部分资源，清理不能只放在“全部成功”的分支。环境到期回收需要避免误删仍在执行的任务，并保留未回收项。

## 4. 临时环境与共享依赖 {#临时环境与共享依赖}

**临时环境**是为一次变更或一轮测试建立、结束后回收的环境。它可以减少不同分支抢占同一部署的冲突，但隔离范围取决于实际资源设计。

两个环境即使拥有不同应用实例，如果连接同一数据库、同一个消息主题或同一外部账号，仍可能互相影响。运行标签必须传到需要隔离的资源，具体数据策略见 [测试数据管理](test-data-management.mdx#并行隔离与运行标识)。

临时环境还有成本和适用边界：复制整个复杂系统很昂贵；少量实例不代表线上扩展行为；外部服务可能不支持随时创建独立沙箱。可以按目标保留必要真实依赖，将其他部分替换，但要在结果里清楚记录。

## 5. 服务虚拟化与环境差异 {#服务虚拟化与环境差异}

**服务虚拟化**是用受控实现模拟外部服务的交互，让测试能够稳定获得正常、错误、延迟或特定数据响应。它适合构造真实依赖难以重复提供的条件。

例如测试支付失败提示时，可以让虚拟依赖固定返回某个失败码；验证真实认证和协议兼容时，则需要接入实际测试服务。替身的版本与响应约定也应维护，否则它可能一直模拟一个真实服务早已改变的接口。

不要把所有环境差异都消除到完全一样。目标是知道哪些差异会影响当前结论，并为重要差异安排补充验证：

| 差异 | 可能影响 |
| --- | --- |
| 单实例与多实例 | 本地状态共享、负载分配与并发一致性 |
| 少量与大规模数据 | 查询计划、索引选择、内存和缓存命中 |
| 内存替身与真实数据库 | 事务、约束、排序规则和失败语义 |
| 本地调用与跨网络依赖 | 延迟、断连、重试与连接池等待 |
| 配置或开关不同 | 实际执行分支与权限边界 |

环境中没有观察到问题时，报告应指向已验证条件。遇到仅某环境失败，则先比较实际制品、配置、数据和依赖，保留差异证据，再定位具体机制。

## 6. 性能结果的适用范围 {#性能结果的适用范围}

压测结果取决于资源、拓扑、数据、依赖和负载模型。介绍项目时，应说明在哪个环境运行、是否与其他任务共享资源、使用什么数据规模，以及观测了哪些服务端指标。

两台实例测到的吞吐不能直接乘以五就得到十台实例的容量。数据库、连接池、热点键或外部限额可能是共享瓶颈；反过来，小环境缺少线上网络和副本，也可能低估某些成本。

功能环境中的一次短时请求成功也不是性能证据。只有环境和负载假设明确，吞吐、延迟、错误率等结果才有可解释范围。

精确重建时使用不可变标识或摘要，秘密只记录必要引用与权限信息。实际失败的输入和运行标识还需与环境记录关联。

### 7.2 所有容器都处于运行状态，为什么测试仍可能过早开始？ {#readiness}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：启动、健康与业务就绪的层次。

**相关内容**：[建立、就绪与销毁](#建立就绪与销毁)。

<details>
<summary>参考回答</summary>

**运行状态只说明进程已启动，不说明依赖初始化、schema 迁移和当前测试需要的能力都已准备完成。** 应等待相应健康条件，再验证必要前置。

准备失败应明确报告为环境阶段问题并保留日志，不能继续运行后把大量错误归为业务缺陷。等待本身也需要期限。

</details>

### 7.3 为每个分支创建临时环境后，还会发生测试互相污染吗？ {#ephemeral-environment}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：应用隔离与共享依赖的边界。

**相关内容**：[临时环境与共享依赖](#临时环境与共享依赖)。

<details>
<summary>参考回答</summary>

**仍然可能，独立应用实例不等于数据库、缓存、消息和外部账号也独立。** 需要列出共享资源，按测试目标建立命名空间、数据范围或更大粒度隔离。

建立失败和到期销毁也要定向回收，不能删除其他活跃任务的数据。报告应保留实际隔离范围。

</details>

### 7.4 用虚拟服务替换外部依赖后，哪些结论仍需要真实集成验证？ {#virtualization-boundary}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：模拟行为与真实协议、部署的区别。

**相关内容**：[服务虚拟化与环境差异](#服务虚拟化与环境差异)。

<details>
<summary>参考回答</summary>

**虚拟服务只能证明被测代码如何处理提供的交互条件，真实认证、协议兼容和部署连接仍需实际依赖证据。** 延迟或错误响应可以受控模拟，不能因此宣称真实服务一定按同样方式工作。

维护替身契约，并保留关键真实集成路径。测试结果明确标出哪些依赖被替换。

</details>

### 7.5 怎样说明项目压测使用的环境，以及结果可以用于哪些判断？ {#performance-environment}

**考察重点**：性能环境、差异与外推边界。

**相关内容**：[环境描述与重建](#环境描述与重建)、[性能结果的适用范围](#性能结果的适用范围)。

<details>
<summary>参考回答</summary>

**说明实例和资源配置、依赖拓扑、数据规模、共享情况与负载模型，再给出吞吐、延迟和错误等结果。** 结论首先适用于这些条件。

与线上不同的数据库规模、热点、网络和配额可能改变瓶颈，不能只按实例数量线性放大。需要进一步判断扩容或上线容量时，应补相应环境和负载证据。

</details>
