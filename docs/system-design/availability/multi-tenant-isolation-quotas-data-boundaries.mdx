# 多租户

**多租户**是让多个客户组织、团队或项目共享一套系统，同时隔离各自数据和资源的方式。共享可以提高资源利用率，但系统必须保证一个租户看不到其他租户的数据，也不能无限占用公共资源。

设计时要沿请求、存储、消息和运维工具检查租户范围。数据库查询带上 `tenant_id` 只是其中一步，身份来源、连接复用和资源配额同样会影响隔离结果。

## 1. 面试核心 {#core}

- 一个用户可以属于多个租户，因此要分别确认**用户身份、当前租户和租户内权限**。
- Pool 共享资源，Silo 使用专用资源，Bridge 混合两者。选择时要权衡**隔离要求、资源利用率和维护成本**。
- 数据访问、唯一约束、缓存和消息都需要**与业务一致的租户范围**，否则仍可能发生跨租户冲突或访问。[卡](#tenant-isolation)
- 行级安全是否生效取决于**执行角色和租户上下文**，超级用户等角色可以绕过策略，连接复用也可能带入旧上下文。[卡](#tenant-rls-boundaries)
- 租户配额与公平调度共同限制**单个租户对共享资源的影响**，还需全局上限保护总容量。

## 2. 租户身份 {#租户身份}

**租户**是系统中需要独立划分数据和资源范围的单位，可以是客户组织、团队或项目。用户与租户不是同一概念：一个用户可能属于多个租户，所以每次请求都要明确当前操作哪个租户。

租户上下文应来自验证后的令牌或服务端会话。客户端可以选择租户，但服务端还要校验用户是否属于该租户，不能直接相信传入的 ID。后台任务、消息和审计记录也要保留这个范围，范围缺失时默认拒绝处理。

## 3. 隔离模型 {#隔离模型}

多租户可以按共享程度采用三种模型：

| 模型 | 资源安排 | 主要取舍 |
| --- | --- | --- |
| Pool，共享池 | 租户共享应用与存储，用租户字段区分数据 | 利用率较高，但故障和资源竞争更容易影响多个租户。 |
| Silo，专用资源 | 为租户配置专用应用或存储 | 隔离更直接，部署和升级成本也更高。 |
| Bridge，混合模式 | 按租户或组件混合使用共享和专用资源 | 需要明确哪些部分共享、哪些部分独立。 |

选择要结合租户规模、性能要求和合同约束。独立 schema 能提供命名和权限边界，但如果仍共用一个数据库实例，CPU 和连接压力还是会相互影响。

## 4. 授权检查 {#授权检查}

**认证**确认用户是谁，**授权**确认他能在当前租户内执行什么操作。请求需要依次验证令牌、租户成员关系和资源归属；仅证明用户已登录，不代表他能访问任意租户的订单。

审计记录应包含操作主体、租户、资源与结果。全局管理员需要独立权限和完整审计，普通租户角色只访问自身范围，避免管理能力混入普通请求路径。

## 5. 数据访问 {#数据访问}

共享表需要明确每行数据属于哪个租户，租户键应设为非空。唯一约束也要符合业务范围：如果订单号只要求在租户内唯一，可以使用复合唯一索引：

```sql
CREATE UNIQUE INDEX uk_order_no
ON orders (tenant_id, order_no);
```

这样，不同租户可以使用相同的 `order_no`，同一租户重复插入才会触发唯一约束。跨表引用同样要检查两侧租户一致，避免把租户 A 的订单关联到租户 B 的数据。

查询可以通过 Repository、ORM filter 或行级安全统一过滤。缓存键、对象路径、搜索索引和消息也要包含租户维度，否则数据库查询即使正确，后续仍可能取得别人的结果。

### 5.1 行级安全与连接复用 {#行级安全与连接复用}

**行级安全**（RLS）是在数据库侧按策略限制行访问的机制。PostgreSQL 18 启用 RLS 后，如果没有适用策略，受 RLS 约束的访问默认被拒绝。`USING` 决定哪些现有行可见，`WITH CHECK` 检查新增或修改后的行是否符合条件。

策略是否生效，还取决于执行角色。超级用户和 `BYPASSRLS` 角色会绕过 RLS，表所有者默认也会绕过；可以用 `FORCE ROW LEVEL SECURITY` 让表所有者受约束。因此，应用连接需要使用受策略限制的角色。

连接池还会带来上下文复用的问题：租户 A 用完的物理连接，可能马上交给租户 B。如果用会话变量保存租户上下文，可以用 `SET LOCAL` 将设置限制在当前事务。提交或回滚后，它恢复为会话原值，所以会话默认值也应当没有租户权限。测试需要覆盖异常回滚后的复用，确认 B 不会继续沿用 A 的范围。

RLS 负责执行数据层限制，而“用户是否属于这个租户”仍需由可信入口验证。错误的租户上下文，即使被数据库严格执行，也会得到错误的授权范围。

## 6. 配额 {#配额}

**租户配额**是对单个租户资源用量的限制，可以覆盖请求速率、并发数、排队长度、存储、CPU、内存和第三方调用。

全局上限保护系统总容量，租户上限减少某一方占满资源的机会，两者需要配合。拥塞时，还要通过公平调度决定不同租户何时取得资源，并为公共管理功能和核心任务保留容量。

## 7. 噪声邻居 {#噪声邻居}

**噪声邻居**是共享资源中，一个租户的负载影响其他租户的现象。例如，慢 SQL 占用数据库资源、热点分区集中写入，或大量缓存写入挤走其他租户的缓存，都可能让别人的请求变慢。

诊断时应按租户观察延迟、错误和资源用量。查询限时、有界队列和并发隔离可以限制影响，负载特别大的租户也可以迁到独立资源池。配额需要与产品套餐及容量计划一致，否则系统承诺和实际可用资源会脱节。

## 8. 运维隔离 {#运维隔离}

运维操作也应限定租户范围。发布、迁移和回填可以按租户分批执行，先在小范围验证，再扩大范围；工具执行前展示目标租户和预计数据量，便于确认影响。

导出、删除和恢复同样需要隔离。需要从共享备份中恢复一个租户时，可以先在隔离环境中提取目标数据，校验后再通过受控流程写回，避免影响其他租户的当前数据。

## 9. 成本归因 {#成本归因}

按租户记录资源用量，既能解释谁造成了资源压力，也能为共享费用分摊提供依据。具体口径与计算见[成本归因](./performance-reliability-cost-attribution.mdx)。

## 10. 跨租户测试 {#跨租户测试}

隔离测试需要主动构造可能越过边界的情况，至少包括：

- 伪造、缺失或切换租户 ID。
- 两个租户使用相同业务资源 ID。
- 缓存、搜索和消息中的数据隔离。
- 管理员路径与权限撤销。
- 单租户占满并发、队列或存储。
- 导出、恢复、迁移和连接复用后的范围。

共享资源压测时，还要观察其他租户的服务质量目标（SLO）是否仍然满足。单个租户能跑出高吞吐，并不能证明系统已经隔离了它的影响。

## 11. 面试题 {#面试题}

### 11.1 多租户系统怎样避免数据越权和单个租户占满资源 {#tenant-isolation}



**题型**：综合题

**考察重点**

- 租户身份、授权和数据过滤的完整链路。
- Pool、Silo 与混合隔离模型。
- 按租户配额、噪声邻居和可观测性。

**相关内容**：[租户身份](#租户身份)至[跨租户测试](#跨租户测试)。

<details>
<summary>参考回答</summary>

**用可信租户上下文和授权控制数据范围，用租户配额与公平调度限制资源占用。**

请求先验证用户的租户成员关系，数据访问、缓存和消息沿用同一范围，唯一约束按业务定义包含租户键。

资源侧分别设置速率、并发和存储配额；大租户可使用独立资源。测试覆盖越权、连接复用时的上下文残留，以及单个租户拖慢其他租户的情况。

</details>
