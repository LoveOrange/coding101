# 成本归因

**成本归因**是把资源费用分配到具体业务和责任方的过程。它既要解释钱花在哪里，也要说明这些费用支撑了多少业务量。例如，每笔成功订单的成本，比单看服务器月账单更容易用于比较优化效果。

判断一次性能优化是否值得，需要同时看单位成本、用户体验和投入成本。账单下降可能来自效率提高，也可能只是采购价格或业务量发生了变化。

## 1. 面试核心 {#core}

- 单位成本用**明确的业务量作分母**，例如成功订单数；失败请求消耗的资源仍计入成本。
- 专用资源可以直接归属，共享资源需要按**可解释且稳定的用量口径**分摊。
- 优化前后应在可比条件下，同时检查**单位成本、吞吐、错误率和尾延迟**，避免只看一个指标。[卡](#optimization-worth)
- 判断收益要计入**研发、迁移和长期维护费用**，并保留业务正确性与可靠性的要求。
- 业务量增加会摊薄固定费用，因此**单位成本下降不能单独证明代码更高效**。[卡](#unit-cost-fixed-variable)

## 2. 业务单位 {#业务单位}

**单位成本**是某个统计范围内的总成本除以对应业务量。在线 API 可以计算每千次请求费用，交易链路可以计算每笔成功订单费用，存储可以计算每 GB 月费用。比较前后结果时，这个口径需要保持一致。

以成功订单数作分母，能把业务量和实际交付结果联系起来。失败请求虽然不增加成功订单数，但仍消耗资源，所以费用必须计入分子。业务类型差异大时应分别统计，避免大量低成本请求掩盖少量高成本交易。

## 3. 资源所有权 {#资源所有权}

归因先要确定资源由谁使用、为哪项业务服务。专用数据库可以直接归属某个服务或团队，共享网关、集群和消息平台则需要进一步分摊。

资源元数据可以记录产品、服务、环境和地域，应用侧再补充请求数、CPU 时间和存储量。租户层级与采购方式也会影响最终费用。

平台对标签和账单的生效规则不同，所以历史费用应按原始账单与当时的口径核算，不能直接用今天的标签解释全部历史成本。

## 4. 共享成本分摊 {#共享成本分摊}

共享费用可以按固定比例，也可以按实际用量分摊。无法直接测量费用时，选用的代理指标应尽量接近真正产生费用的因素。

例如，消息平台的费用可以结合写入字节、保留量和读取量分摊；认证平台可以按认证次数分摊。确实无法准确归属的部分，可以单列公共预算，保留不确定性。

分摊规则需要公开并保持稳定。修改规则时记录版本，否则某个团队的账单上升，可能只是分摊口径变了，却被误判为资源浪费。

## 5. 性能测量 {#性能测量}

性能优化需要在可比条件下测量。固定负载、请求分布、数据规模、缓存状态、实例规格和运行时版本，再记录吞吐、错误率、P95/P99 延迟及资源用量。P95/P99 分别表示 95% 和 99% 的请求延迟不超过的阈值，用来观察较慢请求的体验。

**安全吞吐**是在满足服务质量目标（SLO）的前提下，系统能够处理的请求量。容量规划应以它为依据，并保留故障接管余量。一次极限压测即使得到更高吞吐，也只能说明那组测试条件下的结果。

## 6. 可靠性投入 {#可靠性投入}

可靠性方案的成本包括建设、持续运行和维护复杂度。副本、跨地域复制、容量余量会增加资源费用，更高目标也可能要求更严格的发布控制和更多值班投入。

比较方案时，要明确它减少的是哪类故障，再结合业务损失和用户影响判断收益。可用性每增加一个 9，并没有固定的成本倍数，实际投入取决于尚未解决的故障原因。

## 7. 优化顺序 {#优化顺序}

优化顺序由预计收益、风险和验证成本决定。闲置资源、重复工作、无界重试可以先列为候选；查询、缓存和批处理优化则要同时验证结果正确性。

实例规格、自动扩容和采购折扣改变的是不同费用项，评估时应分开。如果方案需要重写服务或迁移数据库，还要把研发与迁移投入算进去，不能只比较运行账单。

## 8. 优化护栏 {#优化护栏}

节省费用时，需要明确哪些质量条件不能被破坏。减少副本会降低费用，也会减少接管余量；增加缓存 TTL 会减轻数据库负载，也会延长读到旧数据的时间。

实验应提前写明单位成本目标、SLO 下限、灰度范围、观察期和回滚条件。计算回收期时，先从持续节省中扣除新增维护费用，再看需要多久覆盖研发和迁移等一次性投入。

## 9. 成本差异分析 {#成本差异分析}

总成本变化要拆开看业务量、资源使用效率、采购价格和分摊口径。它们可能同时变化，例如业务量增加让总费用上升，而单价下降又抵消了一部分。把各项影响换算成金额，才能解释最终差额。

### 9.1 固定成本与边际成本 {#固定成本与边际成本}

**固定成本**是在给定容量范围内不随业务量变化的费用，**边际成本**是多处理一单位业务增加的费用。用一个简化模型说明：设固定月成本为 F，单笔变动成本为 v，业务量为 Q，在这个模型中边际成本就是 v。

```text
总成本 C = F + v × Q
单位成本 C / Q = F / Q + v
```

假设 F 为 1000 元，v 为 0.01 元。1 万单的总成本是 1100 元，每单 0.11 元；2 万单的总成本是 1200 元，每单 0.06 元。单笔变动成本没有变化，只是同样的 1000 元固定费用被更多订单分摊了。

因此，要判断代码优化是否有效，还需要在相近负载下比较资源用量。业务量跨过扩容阈值后，固定成本也可能阶梯式上升，不能一直沿用原来的 F。

同一模型还可以拆解前后两期的成本差额，其中下标 0 表示变化前，1 表示变化后：

```text
C1 - C0 = (F1 - F0) + v0 × (Q1 - Q0) + Q1 × (v1 - v0)
```

三项依次表示固定费用变化、按旧单笔费用计算的业务量变化，以及按新业务量计算的单笔费用变化。v 还可以继续拆成资源用量与采购单价，区分效率提高和价格下降。

## 10. 面试题 {#面试题}

### 10.1 怎样判断一次性能优化是否值得投入 {#optimization-worth}



**题型**：综合题

**考察重点**

- 业务单位、基线和资源成本归因。
- 尾延迟、安全吞吐与 SLO 护栏。
- 实现成本、持续成本和业务收益比较。

**相关内容**：[业务单位](#业务单位)至[成本差异分析](#成本差异分析)。

<details>
<summary>参考回答</summary>

**值得投入的优化应改善用户结果或长期单位成本。**

评估要使用一致的工作负载和成本口径。吞吐提高时，还需确认错误率与尾延迟符合目标。

预计节省需扣除研发、迁移和持续维护成本。灰度期间用 SLO、业务正确性和接管容量约束风险。优化后的账单还需区分业务量、效率和价格变化。

</details>
