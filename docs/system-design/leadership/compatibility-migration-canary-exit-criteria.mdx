# 架构迁移

**架构迁移**是把接口、数据或处理流程逐步转到新的实现。业务继续运行时，难点在于新旧系统会共存一段时间：旧调用方必须还能工作，新数据不能被旧逻辑破坏，出问题时还要知道能退到哪里。资深后端岗位的项目追问，需要用这些条件说明迁移为什么可控。

## 1. 面试核心 {#core}

- 按扩展、迁移、收缩分阶段推进，**先让新旧版本兼容，再切换使用方，最后删除旧能力**。[卡](#zero-downtime-migration)
- 每批迁移都要记录**进度、校验结果和回退边界**，中断后才能继续，失败时才能退回。
- 旧消费者归零、数据校验完成并关闭回退窗口后，**才具备删除旧路径的条件**。
- 回填与在线更新需要**共享顺序依据，防止旧值覆盖新值**。[卡](#backfill-concurrent-writes)

## 2. 兼容面 {#兼容面}

兼容要同时检查接口结构和业务行为。即使字段名、类型都没变，金额的舍入规则改变，也可能让调用方算出的结果不同。可以按下面的范围逐项核验：

| 兼容面 | 核验内容 |
| --- | --- |
| API | 请求、响应、错误码、认证和默认值 |
| 事件 | schema、顺序和投递语义 |
| 数据 | 表结构、索引和读写格式 |
| 运行 | 配置、权限、告警和审计字段 |
| 消费者 | SDK、批处理、报表和运维工具 |

每项都记录谁负责、谁在使用，以及需要兼容到什么时候。消费者范围还不清楚时，先用访问日志或登记机制补齐；否则，删除旧能力时无法确认会影响谁。

## 3. 扩展、迁移、收缩 {#扩展迁移收缩}

扩展、迁移、收缩把一次破坏性变更分成可以逐步验证的步骤：

1. **扩展**：增加新字段或接口，保留旧读写能力。
2. **迁移**：回填数据，逐批切换消费者。
3. **收缩**：确认旧路径停用，再删除兼容逻辑。

重命名列时，可以先新增目标列。过渡代码兼容两种结构，并明确权威写入方。回填完成后切换读取，最后删除旧列。直接改名会使滚动发布中的旧实例报错。

跨系统同步还要处理“一边成功、一边失败”，可结合[Transactional Outbox 与 CDC](../distributed-data/outbox-cdc-reliable-events.mdx)保存并传播增量。回填与在线更新怎样避免相互覆盖，见[回填与增量写入](#回填与增量写入)。

## 4. 迁移状态 {#迁移状态}

迁移状态要能回答某个对象走到了哪一步、现在可以做什么。可以按租户、分区或业务流程记录，例如：

```text
待迁移 → 回填中 → 增量追平 → 影子验证 → 灰度 → 已切换 → 已关闭回退
```

状态转换要满足幂等，也就是同一步重试不会重复产生业务影响。每次推进都保存检查点，记录数据范围、校验结果和操作者；任务中断后，从已确认的位置恢复，避免重新处理整批数据。

批次大小取决于故障范围和恢复耗时。低风险批次通过后，再覆盖高价值对象。每批结束后保留明确的观察窗口。

## 5. 灰度规则 {#灰度规则}

灰度切换要让同一个对象稳定进入选定路径，避免一次走新系统、下一次又走旧系统。具体分组和指标比较见[灰度发布](../microservices/canary-traffic-tagging-rollback.mdx)。

迁移计划还需将路由组与数据状态对应起来。数据尚未追平的租户继续使用旧路径。每次切换记录负责人、检查点和回退位置。

## 6. 影子流量与双读 {#影子流量与双读}

**双读**是让新旧路径都计算结果，由旧路径响应用户，新路径只用于对照。比较时可以过滤随机 ID、时间戳等允许的差异，但金额、权限、状态等差异要按业务规则判断，不能为降低差异率一并忽略。

**影子流量**是复制真实请求给新路径验证，而不使用它的结果响应用户。这些请求只做无副作用的计算，使用独立标识，也要计入下游容量。影子验证没有实际执行写入，因此并发写入和事务行为还需要真实小流量验证。

## 7. 回滚与向前修复 {#回滚与向前修复}

**回滚**恢复旧路径，**向前修复**则在当前状态上修正问题，用来处理无法直接撤销的变化。切回旧代码不等于数据也回到了旧状态，因此上线前要逐项核验：

- 旧代码能够读取新数据。
- 已发送事件有明确的处理方。
- 在途流程有稳定的版本归属。
- 切回后仍能阻止重复扣款或通知。

数据已经不可逆转换时，用开关关闭风险路径。随后通过兼容读取、对账或补偿修复结果。回滚阈值、权限和耗时都应提前演练。

## 8. 退出条件 {#退出条件}

迁移完成要有可核验的退出条件。新路径已经接流量，还不代表旧路径可以立即删除，至少要检查：

- 全部目标对象进入新路径。
- 技术与业务指标达到预设目标。
- 回填完成，数据差异有明确处理结果。
- 旧接口、字段和事件的消费者归零。
- 文档、告警和运行责任完成交接。
- 回退窗口关闭，旧资源与临时开关完成删除。

每项指定负责人，并保存完成证据。观察期要覆盖低频批处理与报表周期，否则“没有旧消费者”可能只是它们尚未运行。删除旧路径时，先关闭入口并观察，再删除存储。

## 9. 迁移复盘 {#迁移复盘}

复盘比较迁移前后的延迟、成本和故障范围。也要检查发布速度是否达到原定目标。目标未达成时，重新核验假设和实施边界。

兼容层与同步任务有明确的保留期限。关闭项目时核对清理结果，避免长期双轨维护。

## 10. 回填与增量写入 {#回填与增量写入}

回填必须处理与在线更新的先后关系，否则旧数据会覆盖新数据。例如，回填先读到余额 100，在线请求随后把它更新为 120，并已同步到新库。回填最后再无条件写入，新库的余额就退回了 100。

避免覆盖，需要让快照与变更日志衔接到同一顺序。按迁移工具的语义保存可恢复的日志位置、读取快照，回填期间保留持续产生的增量，再按源端顺序追平。写入端也可以检查源端行版本，拒绝更旧版本覆盖新值。

切换前既要确认增量追平，也要对账业务字段。前面的余额从 120 退回 100，行数没有变化，单纯比较行数就发现不了。因此，验证要覆盖金额、状态，以及回填期间的更新和删除。

## 11. 面试题 {#面试题}

### 11.1 一个核心接口怎样做到无停机迁移并保留回退能力 {#zero-downtime-migration}

**题型**：综合题

**考察重点**

- 说明 API、事件、数据和行为兼容。
- 理解分批状态、影子验证和灰度阈值。
- 理解数据回退、向前修复与退出条件。

**相关内容**：[兼容面](#兼容面)至[迁移复盘](#迁移复盘)。

<details>
<summary>参考回答</summary>

**无停机迁移依靠兼容扩展、分批切换和延后收缩。**

先列出 API、数据和事件消费者。每批保存回填进度与增量位置。灰度前核对数据，再按稳定对象分组放量。

回退方案同时覆盖路由、旧代码读新数据和在途流程。不可逆变化使用向前修复。指标稳定、旧消费者归零后关闭回退窗口。最后删除旧路径并核验迁移目标。

</details>

### 11.2 回填期间发生在线更新，怎样避免旧值覆盖新值？ {#backfill-concurrent-writes}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：说明快照与增量怎样衔接，并用业务字段校验迁移结果。

**相关内容**：[回填与增量写入](#回填与增量写入)。

<details>
<summary>参考回答</summary>

**需要将快照和增量日志衔接到同一顺序。**

回填先恢复基线，再按源端顺序追平变更。源端行版本也可用于拒绝过期覆盖。

切换依据包括日志追平和业务字段对账。仅比较行数会漏掉金额更新与状态差异。

</details>
