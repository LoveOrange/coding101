# 可观测性

**可观测性**是通过系统输出的信号理解内部行为的能力。指标反映总体变化，日志记录具体事件，调用追踪（Trace）把一次请求经过的操作连起来。排查故障时，需要用它们回答「影响有多大」「请求慢在哪里」和「当时发生了什么」。

三种信号要能关联，也要知道各自的限制：指标经过聚合，Trace 可能被采样，日志也未必记录了每个步骤。

## 1. 面试核心 {#core}

- 指标保存**聚合趋势**，日志记录**事件详情**，Trace 展示**调用路径**，三者提供不同层面的证据。[卡](#logs-metrics-traces)
- 指标标签的取值组合越多，**时间序列数量与存储成本越高**，用户 ID 等不受控的值不适合直接作为标签。
- Trace ID 关联一次技术调用，业务 ID 则用于**连接跨请求的业务流程**。
- 尾部采样只能选择已经收到的数据，**无法恢复前面已经丢弃的 span**。[卡](#tail-sampling-missing-spans)
- Histogram 保存的分布可以合并，但**多个实例的 P99 不能直接取平均**得到整体 P99。[卡](#histogram-aggregate-quantile)

## 2. 指标 {#指标}

**指标**是按时间记录的数值，适合观察请求量、错误率和资源占用的变化。Counter 记录累计量，gauge 记录当前值，histogram 用桶记录观测值的分布，可以据此估算延迟分位数。

告警优先关注成功率和延迟等服务质量指标（SLI），因为它们直接反映用户受到的影响。CPU、队列和连接池指标则帮助解释资源是否饱和。

标签让指标可以按路由、区域和版本拆分，但每一种取值组合都会增加时间序列。route、region 和 version 可以控制取值范围，用户 ID 和订单号却会不断增加，更适合放进有访问权限控制的日志或 Trace。这就是标签基数需要受控的原因。

## 3. 结构化日志 {#结构化日志}

**结构化日志**用稳定字段记录事件，例如时间、服务、版本、错误类型、Trace ID 和必要的业务键。字段一致，才能可靠地检索同一次请求或比较不同版本。

完整异常栈在负责处理失败的边界记录即可。中间层逐层重复打印，会让同一次失败产生多份日志，还可能把错误计数放大。

日志中要过滤 token、密码和敏感请求内容。预期业务拒绝使用相应事件级别，临时调试日志则限制范围和持续时间，避免把所有运行细节长期保存下来。

## 4. Trace {#trace}

**Trace** 记录一次请求经过的调用过程，由多个 **span** 组成；每个 span 表示其中一段操作，保存起止时间、状态、属性以及与其他 span 的关系。

请求跨越 HTTP、RPC 或消息边界时，要传播追踪上下文，下游 span 才能关联到同一次 Trace。已经埋点的阶段可以展示耗时和重试次数，没有埋点的队列或线程等待仍需要补充观测。

异步消费和批量消息可以用 span link 关联来源。分析耗时时还要看执行关系：并行 span 的时间区间会重叠，直接把它们相加，会重复计算同一段时间。

## 5. 关联 ID {#关联-id}

Trace ID 和业务 ID 解决不同的关联问题。Trace ID 用来追踪一次技术调用，订单或任务 ID 则可以连接多次请求，保留完整的业务过程。

外部传入的 request ID 要检查格式与长度，也可以在内部生成可信标识并保存映射。能用某个业务 ID 查日志，不等于拥有查看该业务数据的权限，查询端仍要限制访问范围。

## 6. 采样 {#采样}

**采样**是只保留一部分 Trace，以控制采集和存储成本。决定保留的时机不同，能依据的信息也不同：

- 头部采样（head sampling）在请求入口阶段决定，成本较低，但这时还不知道后面会不会出错。
- 尾部采样（tail sampling）等收到更多 span 后，再按错误或耗时选择，因此需要缓冲、状态管理和额外资源。

核心请求量与错误率要由独立指标完整统计，不能仅从被采样的 Trace 推算。安全审计也需要自己的留存管道。故障期间临时提高 Trace 采样率时，应限制范围和时间。

## 7. 上下文传播 {#上下文传播}

**追踪上下文**携带把当前操作连接到原请求的信息。W3C `traceparent` 传递 Trace 与父 span 标识，baggage 则携带额外属性，例如受控的实验标签。

baggage 会继续传给下游，所以要限制大小，避免放入敏感字段。它也不能代替独立的授权机制。

线程池、Future 和消息回调会改变任务的执行位置，因此这些边界也需要传播上下文。任务结束后还要清理，避免线程被复用时，把上一请求的信息带给下一任务。

## 8. 告警下钻 {#从告警下钻}

排查可以先用指标确认影响范围，再查看样本细节：

1. 用指标确定异常的时间窗口、区域和服务版本。
2. 选择慢请求或错误请求的 Trace，定位关键路径。
3. 按 Trace ID 查询事件日志和异常详情。
4. 核对对应组件的资源与依赖指标。
5. 修复后比较同一 SLI 和等待指标。

一条 Trace 只能解释这个样本。要判断问题是否普遍、修复是否有效，仍需回到聚合指标。

## 9. 遥测管道 {#遥测管道}

**遥测管道**负责把日志、指标和 Trace 等观测数据送到后端。它自身变慢时，不应让普通观测数据无限积压，拖慢业务请求。应用可以使用有界队列、批量导出，并按预设策略丢弃普通遥测。

同时监控丢弃的 span 数量、队列容量和导出器错误。否则，后端查不到数据时，无法分清是业务没有发生，还是观测数据没有送达。审计数据另设可靠性和留存策略。

## 10. 分位数聚合 {#分位数聚合}

**P99** 是 99% 的观测值不超过的值，取决于整个分布。每个实例的 P99 只留下一个数，直接求平均会丢失请求数量和分布信息，因此不能得到整体 P99。

Prometheus 的经典 histogram 保存各个桶的计数。实例使用相同桶边界时，可以先合并计数，再计算分位数：

```promql
histogram_quantile(
  0.99,
  sum by (le, route) (rate(http_request_duration_seconds_bucket[5m]))
)
```

这段查询先按 `le` 和 `route` 聚合桶，再估算各路由最近五分钟的 P99。结果精度取决于桶边界与请求数量，所以桶应在业务延迟目标附近有足够的区分度。

Summary 预先算出的分位数已经失去了这部分分布信息，不能用同样的方法跨实例合并。

## 11. 尾部采样的完整性 {#尾部采样的完整性}

尾部采样只能判断已经到达的数据。上游头部采样丢弃的请求，后面的采样器无法恢复，即使该请求最后发生错误也是如此。

同一 Trace 的 span 还需要汇聚到同一决策节点。等待窗口太短会漏掉迟到的 span，缓冲溢出也会降低错误样本的保留率。因此，查不到 Trace 时，要结合丢弃指标检查采样和导出链路，不能直接认定请求没有发生。

## 12. 常见问题 {#常见问题}

### 12.1 有了 Trace，还需要事件日志吗？ {#trace-与事件日志}

需要。Trace 展示调用关系和耗时，日志补充状态变化与异常细节，两者通过 Trace ID 关联即可。把完整日志重复复制进 Trace 会增加成本，也会扩大敏感信息的传播范围。

### 12.2 Correlation ID 可以直接使用 Trace ID 吗？ {#correlation-id-与-trace-id}

单次同步请求可以共用一个关联标识。跨请求的业务流程则更适合保留独立业务 ID，因为一次订单流程可能包含多次技术调用。Trace ID 继续用于各条技术链路的追踪。

## 13. 面试题 {#面试题}

### 13.1 日志、指标和 Trace 各自能证明什么，如何关联排障 {#logs-metrics-traces}

**考察重点**

- 理解聚合趋势、事件详情和单请求因果链。
- 理解追踪上下文（trace context）、业务关联 ID 和异步传播。
- 理解高基数、采样、隐私与遥测背压。

**相关内容**：[指标](#指标)至[遥测管道](#遥测管道)。

<details>
<summary>参考回答</summary>

**指标说明总体趋势，Trace 展示请求样本的调用路径，日志补充具体事件和异常。**

排障时先用 SLI 确认时间、区域和版本范围，再查看慢 span，并通过 Trace ID 找到对应日志。跨请求的业务过程由业务 ID 连接，但不把这类无界取值直接作为指标标签。

Trace 采样用来控制成本，完整请求统计由独立指标承担。导出采用有界缓冲并监控丢弃情况，才能判断缺少数据是业务现象还是采集链路的问题。

</details>

### 13.3 使用尾部采样后，为什么仍会查不到错误 Trace？ {#tail-sampling-missing-spans}

**考察重点**：前置丢弃、汇聚与等待窗口。

**相关内容**：[尾部采样的完整性](#尾部采样的完整性)。

<details>
<summary>参考回答</summary>

**尾部采样只能选择收到的数据，前面已经丢弃或导出失败的 span 无法恢复。**

同一 Trace 的 span 还需要到达同一决策节点。排查时依次核对头部采样、汇聚路径、等待窗口和缓冲丢弃，确认是否有错误 span 在决策前丢失或尚未到达。

</details>
