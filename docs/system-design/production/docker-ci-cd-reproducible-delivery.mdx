# 可重复交付

**可重复交付**是让同一份经过验证的产物依次进入测试、预发和生产环境。对于 Docker 应用，关键是确认部署的镜像就是测试过的镜像，并且能查清它来自哪次提交、使用哪版配置、怎样安全回退。

这需要把构建和部署分开：构建生成产物，后续流水线逐级放行同一产物，而环境配置在部署时注入。

## 1. 面试核心 {#core}

- 镜像 digest **按内容标识产物**，tag 则可以被重新指向，部署记录要能定位到准确内容。[卡](#delivery-pipeline)
- 多阶段构建把**编译环境与最终运行环境分开**，运行镜像只保留必要产物和运行时。
- 测试、预发和生产应**使用同一个已验证的 digest**，配置在部署时注入，避免上线前重新打包。
- 构建凭据通过 BuildKit secret mount **临时提供给指定步骤**，构建命令仍要避免把它写进产物或日志。[卡](#build-secrets-cache)
- exec 形式的 `ENTRYPOINT` 可以让应用**直接接收终止信号**；入口是脚本时，脚本需通过 `exec` 启动应用。[卡](#container-sigterm)

## 2. 镜像与 digest {#镜像与-digest}

**镜像**由文件系统层和配置元数据组成。`RUN`、`COPY` 等指令可以产生文件系统变化，`CMD`、`LABEL` 等指令主要修改配置元数据。

**tag** 是便于阅读的镜像标签，**digest** 是按内容计算的摘要，用来精确引用产物。同一个 tag 可能先后指向不同内容，因此部署记录要同时保存源码提交和镜像 digest。基础镜像也可以按 digest 固定，在更新后重新测试。

**构建上下文**是发送给构建器的文件集合，`.dockerignore` 用来排除不需要的文件，例如密钥、Git 历史和本地缓存。密钥不能先复制进镜像、再靠后续指令删除，因为旧层中仍可能保留原内容。

## 3. 多阶段构建 {#多阶段构建}

**多阶段构建**把编译和运行放在不同阶段：构建阶段使用 JDK、Maven 等工具生成 jar，运行阶段只复制必要产物并提供运行时。这样，编译工具就不必进入最终运行镜像。

运行镜像还要明确应用能以什么身份、向哪些目录写入。使用非 root 用户并收紧文件权限，临时文件放进指定可写目录，同时保留应用需要的证书与诊断能力。

## 4. CI {#ci}

**持续集成**（CI）负责对提交进行构建和验证，并生成可交付产物。流水线从固定的源码提交与工具链开始，可以按下面的顺序执行：

1. 校验依赖，完成编译与单元测试。
2. 执行静态检查、集成测试和契约测试。
3. 构建镜像，生成软件物料清单（SBOM，记录产物包含的软件组件）与构建来源记录。
4. 对实际镜像执行冒烟测试和漏洞检查。
5. 对通过检查的镜像签名，并按 digest 发布。

签名只有被部署端验证才有作用。部署端需要检查签名身份和来源是否符合策略，而生产凭据只授予需要它的部署阶段。

## 5. CD 晋升 {#cd-晋升}

**产物晋升**是把已通过上一阶段验证的产物交给下一环境使用。持续交付（CD）负责后续交付流程：测试、预发和生产引用同一个 digest，配置、Secret 和资源声明在部署时注入。

如果生产前重新打包，即使源码没变，也已经是另一份二进制，之前的镜像测试不能直接代表它。使用同一产物并记录配置版本，才能追溯部署内容；环境配置和外部依赖不同，各环境的集成行为仍然要验证。

## 6. 无损替换 {#无损替换}

替换实例时，要先让新实例就绪并接收流量，再让旧实例停止接收新请求、完成已有请求。这个过程称为排空，探针和端点传播的细节见[服务发现](../microservices/service-discovery-health-checks.mdx#上下线与连接排空)。

交付验收还要验证应用能否收到并处理 `SIGTERM` 终止信号。在宽限期内，任务应完成，或者保存可以恢复的检查点；仅仅启动成功，不能说明替换过程完整。

## 7. 数据库变更 {#数据库变更}

镜像回退不会自动撤销数据库变更，因此两者要分开管理。新旧应用能否同时使用变更后的数据库，取决于数据结构是否兼容，具体方法见[架构迁移](../leadership/compatibility-migration-canary-exit-criteria.mdx#扩展迁移收缩)。

流水线需要记录迁移版本、执行锁和检查点。耗时较长的 DDL 使用独立任务执行，避免多个应用实例启动时同时修改数据库结构。

## 8. 发布策略 {#发布策略}

发布策略要写清楚观察哪些业务指标，以及什么条件下停止。逐步放量的判断方法见[灰度发布](../microservices/canary-traffic-tagging-rollback.mdx)。

回退记录同时包含镜像 digest、配置版本和数据兼容状态。出现失败时，保留对应日志和调用追踪（Trace），才能在停止发布后继续定位原因。

## 9. 流水线故障演练 {#流水线故障演练}

故障演练用于验证流水线能否在失败处停住，并保留可查询的部署状态。可以分别模拟镜像仓库不可用、拉取失败、探针持续失败，也要验证数据库升级后是否还能回退镜像。

一次失败不能只留下「流水线失败」的结论。需要能查到哪些实例已经更新，以及它们对应的提交、镜像和配置，后续恢复才有依据。

## 10. 构建缓存与凭据 {#构建缓存与凭据}

构建缓存复用已完成步骤，但可重复构建仍然依赖固定输入。如果远程下载地址的内容会变化，同一份 Dockerfile 也可能得到不同结果。

构建私有依赖时，可以用 BuildKit 的 `--secret` 提供凭据，再由 Dockerfile 中的 `RUN --mount=type=secret` 挂载给指定步骤。挂载只在该步骤执行期间可见，但步骤中的命令仍不能把凭据复制进产物或打印到日志。

`ARG` 和 `ENV` 不适合传递密钥，因为值可能暴露在镜像或构建元数据中。secret 的内容变化本身不会使缓存失效；轮换密钥后如果确实需要重跑，可以改变非敏感版本参数，或禁用该阶段缓存。

## 11. 容器终止信号 {#容器终止信号}

exec 形式的入口可以让 Java 直接成为容器主进程，接收终止信号：

```dockerfile
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

应用收到信号后，关闭逻辑应停止领取新任务，并等待在途工作结束。收到信号和完成排空是两个步骤，都需要验证。

shell 形式会增加 `/bin/sh -c` 中间进程，不能依赖它自动转发应用需要的信号。如果使用包装脚本，可以通过 `exec java ...` 让 Java 替换脚本进程。无论采用哪种入口，排空超过宽限期后，平台仍会强制终止容器。

## 12. 常见问题 {#常见问题}

### 12.1 部署记录只保存 latest 可以吗？ {#latest-与部署记录}

不可以。`latest` 可以指向不同内容，之后再拉取它，未必得到当时部署的镜像。回滚清单应保存明确的 digest，易读 tag 则可以作为检索辅助。

### 12.2 镜像越小就越安全吗？ {#镜像体积与安全性}

镜像体积不能单独说明安全性。减少组件能降低需要维护的软件数量，但还要检查更新来源、漏洞和运行权限。裁剪镜像后，也要验证应用运行和诊断所需的能力是否仍然完整。

## 13. 面试题 {#面试题}

### 13.1 如何设计从提交到生产的可重复交付流水线 {#delivery-pipeline}

**题型**：综合题

**考察重点**

- 理解不可变镜像 digest、多阶段构建和构建输入。
- 理解同产物晋升、签名、SBOM 与审计。
- 理解就绪检查（readiness）、排空、数据兼容和回滚边界。

**相关内容**：[镜像与 digest](#镜像与-digest)至[流水线故障演练](#流水线故障演练)。

<details>
<summary>参考回答</summary>

**固定构建输入，验证实际生成的镜像，再让同一个 digest 逐级进入测试、预发和生产。**

CI 完成编译、测试和镜像检查，并为产物附上 SBOM、构建来源与签名。CD 校验来源策略，注入环境配置，保存源码提交、digest、配置版本与运行实例的对应关系。

发布时验证就绪、终止信号和连接排空。数据库变更需要保持兼容，单独验证旧镜像能否使用变更后的数据，才能确定回退是否可行。

</details>

### 13.2 构建私有依赖时怎样传密钥，轮换后缓存会失效吗？ {#build-secrets-cache}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：临时挂载、镜像层与缓存输入。

**相关内容**：[构建缓存与凭据](#构建缓存与凭据)。

<details>
<summary>参考回答</summary>

**用 BuildKit 的 `--secret` 和 secret mount 传入凭据；轮换密钥本身不会使缓存失效。**

凭据只挂载给指定构建步骤，步骤中的命令仍要避免把它复制进产物或打印到日志。确实需要重新执行时，可以改变非敏感缓存版本参数，或禁用对应阶段的缓存。

</details>

### 13.3 容器收到 SIGTERM 后，Java 应用为何仍被强制结束？ {#container-sigterm}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：PID 1、信号转发与排空时限。

**相关内容**：[容器终止信号](#容器终止信号)。

<details>
<summary>参考回答</summary>

**可能是 Java 没有收到终止信号，也可能是收到后未能在宽限期内完成排空。**

shell 形式入口会增加中间进程，需要检查信号是否传到 Java。exec 形式的 `ENTRYPOINT` 可让 Java 直接接收信号，包装脚本也可用 `exec` 启动它。应用还要停止领取新任务并完成在途工作，否则宽限期结束后仍会被强制终止。

</details>
