# 生产故障诊断

生产故障诊断通过跨层证据定位慢请求。本文负责 JVM、线程、SQL 与网络的联合分析。信号采集与关联方式见[可观测性](./logs-metrics-traces-correlation.mdx)。

## 1. 面试核心 {#core}

- 端到端耗时包含排队、应用执行和下游等待。
- CPU 较低时，连接池、锁和网络等待仍可抬高 P99。[卡](#p99-with-normal-cpu)
- RUNNABLE 线程也能等待 native I/O，状态名不足以证明 CPU 忙。
- JDK 21 虚拟线程在 synchronized 内阻塞会 pin 住载体线程。[卡](#jvm-diagnostic-evidence)
- 重启同时重置多种状态，恢复结果不足以确定根因。

## 2. 时间、范围与变更 {#时间范围与变更}

先确定异常时间、路由、实例和租户范围。记录错误码、吞吐、P50/P99 与最老请求年龄。

将发布、配置、流量和依赖事件放在同一窗口。只有新版本异常时，比较版本差异。多个服务同时异常时，检查共同依赖。

止血同时保留证据。摘除异常实例前，采集可控的线程栈与 JFR。数据库现场也需保存，避免重启后丢失等待关系。

## 3. 端到端耗时 {#分解端到端耗时}

比较客户端、网关和服务端耗时。Trace 只显示已埋点的阶段，缺失阶段需补指标。

例如服务处理只用 20 ms，网关总耗时却是 2 s。额外时间可来自建连、连接池等待或重试。应逐段对照，避免把差值全部归因于网络。

CPU 较低时，也要核对单核热点与容器 CPU 配额。实例平均值会掩盖局部计算瓶颈。

## 4. JVM 证据 {#jvm-证据}

GC 暂停需与慢请求时间对齐。回收后堆基线持续上升，才值得继续检查对象保留。

进程 RSS 还包含 native memory、线程栈等内容。容器 OOMKilled 可发生在 Java 堆尚有空间时。

JFR 可关联分配、锁、Socket、文件 I/O 和执行采样。采集堆转储前评估停顿与磁盘空间。类直方图也有开销，应按命令影响等级选择。

## 5. 线程栈 {#线程栈}

连续采集线程栈，比较相同线程的停留位置。

- 大量 BLOCKED 线程指向 monitor 竞争。
- worker 忙且队列增长，说明任务处理跟不上到达量。
- JDBC 连接等待需结合连接池 pending 与事务时间。
- RUNNABLE 需结合 CPU 采样判断实际执行。

线程名称与池指标应能互相对应。虚拟线程还需区分 JDK 版本和底层资源等待。

## 6. 数据库 {#数据库}

应用侧记录连接池等待、事务时长与 SQL 次数。数据库侧检查锁等待、执行计划和实际扫描行数。

慢 SQL 可来自统计信息变化、长事务或调用次数增长。索引存在时，范围过大仍会读取大量数据。

MySQL 8.0 的 `EXPLAIN ANALYZE` 会实际执行查询。生产重查询需先评估影响。锁诊断细节见 [InnoDB 锁](../../basic-knowledge/database/transaction/innodb-locking-ranges.mdx#8-用数据库证据查看锁等待)。

## 7. 网络 {#网络}

分开观察 DNS、TCP 建连、TLS 与首字节耗时。连接 reset、重传和代理日志用于补充证据。

长连接会继续访问原地址。负载均衡与 NAT 的空闲超时也需核对。TCP 状态含义见 [TCP 连接](../../basic-knowledge/network/tcp_handshake.mdx)。

HTTP/2 的多个 stream 共享 TCP 连接。连接丢包引发重传时，会影响该连接的交付进度。客户端排队也能使服务端看不到慢请求。

## 8. 跨层证据 {#建立证据链}

例如 JDBC pending、数据库锁等待同时增长。线程栈也持续停在同一查询时，等待链更明确。

时间相关性用于提出假设。再通过阻塞关系或受控干预验证原因。每次改变一个主要变量，并保留对照。

修复后在相近负载下比较原始 SLI。等待指标和业务结果也需恢复，才能确认效果。

## 9. 取证准备 {#取证准备}

预先配置诊断权限、GC 日志与证据保存路径。仪表盘关联服务版本、线程池、SQL 和网络阶段。

Runbook 记录采集开销和升级联系人。故障结束后，把有效证据转成指标或回归检查。

## 10. JDK 诊断命令与版本 {#jdk-诊断命令与版本}

以下命令适用于具备诊断权限的 JDK 21 进程。将 `1234` 换为目标 PID，文件名使用可写路径。

```bash
jcmd 1234 Thread.print -l
jcmd 1234 JFR.start name=incident settings=profile duration=60s filename=incident.jfr
jcmd 1234 VM.native_memory summary
```

`Thread.print` 用于平台线程栈与锁信息。虚拟线程可另用 `jcmd 1234 Thread.dump_to_file -format=json threads.json`。JFR 的 profile 配置比 default 有更高采集开销。

NMT 命令需在启动时启用 `-XX:NativeMemoryTracking=summary`。NMT 统计 JVM 内部 native 分配，并非进程 RSS 的完整清单。

JDK 21 中，虚拟线程在 synchronized 内阻塞会 pin 住载体。native 调用也会造成 pinning。可用 JFR 的 `jdk.VirtualThreadPinned` 事件定位。长时间阻塞的同步代码可评估改用 `ReentrantLock`。

## 11. 常见问题 {#常见问题}

### 11.1 低 CPU 与高 P99 {#低-cpu-与高-p99}

先核对实例、单核和容器配额，再看慢请求等待。线程池队列、JDBC pending 与 Trace 可缩小范围。CPU 平均值较低仍需这些运行证据。

### 11.2 重启恢复的解释范围 {#重启恢复的解释范围}

重启会重置线程、连接、缓存和本地状态。恢复只能说明这些变化中的某项改善了症状。根因判断仍需重启前证据与复现结果。
