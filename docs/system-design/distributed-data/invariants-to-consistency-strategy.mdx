# 分布式一致性

分布式一致性方案用来维护跨服务的业务规则。选择方案前，先要说明哪些状态绝不能出现、接口返回成功时已经完成什么，以及失败后怎样恢复。例如，搜索结果晚更新几秒，与用户被重复扣款，需要承担的代价完全不同。

这些条件决定哪些操作必须同步确认，哪些可以异步完成。协议名称只有放在具体规则和失败场景中，才能说明它是否适用。

## 1. 面试核心 {#core}

- 先把业务不变量写成**可验证的状态规则**，再选择一致性方案，例如同一支付请求最多扣款一次。[卡](#choose-distributed-transaction)
- 同一存储内的规则，优先用**本地事务与唯一约束、锁或条件更新**维护；仅把先读后写放进事务，不一定能避免竞态。
- 确认订单前先原子预留库存，才能维护**“确认即有货”**的规则，事后退款无法改变此前已经超卖的事实。[卡](#inventory-reservation-invariant)
- 最终一致流程需要定义**中间状态、传播时间目标和恢复入口**，才能判断何时需要干预。
- Outbox 保证**本地状态与待发事件共同提交**，Saga 负责跨步骤推进和补偿，两者可以组合使用。

## 2. 业务不变量 {#业务不变量}

**业务不变量**是在业务规定的边界上必须成立的规则。规则应具体到可以检查，例如：同一支付请求最多产生一次扣款，确认后的可用库存不能为负，已经取消的订单不能再进入发货流程。

资金变化需要有可核对的记录；接口向用户返回成功，也要明确承诺的是“已受理”还是“已完成”。如果成功的含义不清楚，就无法判断中间状态是否符合业务要求。

## 3. 原子提交范围 {#缩小原子提交范围}

必须共同成立的规则，优先放在同一个权威存储中维护，也就是由同一处数据作最终判断。这样可以用本地事务保证共同提交，再用唯一约束、锁或条件更新处理并发冲突。

事务本身不能替代并发设计。两个请求先读到相同旧值，再分别写入，如果缺少必要约束，仍可能破坏规则。服务拆分一旦切开原子提交范围，还会增加协调状态，因此边界需要同时考虑业务变化和一致性成本。

### 3.1 库存预留与并发不变量 {#库存预留与并发不变量}

**资源预留**是先把可用资源转为某个请求的占用，供后续步骤确认使用或释放。库存只有 1 件时，如果两个订单都先读到 1，再分别确认，就会接受两笔购买。事后退款可以修正结果，却已经违反了“确认即有货”的规则。

库存服务可以先用条件更新扣减可用量，取得预留资格：

```sql
UPDATE stock
SET available = available - 1
WHERE sku_id = ? AND available >= 1;
```

影响 1 行表示预留成功，影响 0 行表示没有可用库存或记录不存在。预留记录与扣减需要在同一事务内提交，并按业务请求设置唯一约束；重复请求应读取原结果，避免再次扣减。

支付失败后，按预留 ID 释放一次。预留到期与支付成功也可能同时发生，需要通过状态协调决定最终结果。具体转换见[2PC 与 TCC](./2pc-tcc-coordination-cost.mdx)。

## 4. 同步确认与异步完成 {#同步确认与异步完成}

接口应先定义返回成功时必须已经满足的条件。例如，业务可以要求库存已经预留、支付已经授权，才返回相应的成功结果；通知、搜索投影和分析事件则可以随后异步完成。

尚未完成的流程应显示“处理中”，并允许用户查询真实进度。用户重复点击时沿用原业务 ID，才能继续处理同一动作，而不是重新创建一笔业务。

## 5. 不一致窗口 {#不一致窗口}

**最终一致性**表示各处数据最终会收敛，但这个说法本身没有给出传播时限。工程上还需要设定目标，例如 99.9% 的索引变化在 30 秒内完成，超过 5 分钟就告警并进入恢复。

等待期间的用户体验也要明确。积分尚未到账时可以显示“处理中”；搜索结果暂时陈旧时，详情页可以查询权威状态。这样用户才不会把尚未完成误认为最终失败或成功。

## 6. 协调方式 {#协调方式}

不同机制维护的边界不同，需要按资源能力和允许的中间状态选择：

| 需要维护的边界 | 候选方式与前提 |
| --- | --- |
| 多个事务资源原子提交 | [2PC](./2pc-tcc-coordination-cost.mdx) 要求持久准备与协调恢复。 |
| 跨服务预留资源 | [TCC](./2pc-tcc-coordination-cost.mdx) 要求明确的预留模型。 |
| 可补偿的长流程 | [Saga](./saga-compensation-intermediate-state.mdx) 允许可见中间状态。 |
| 本地变化可靠产生事件 | [Transactional Outbox 与 CDC](./outbox-cdc-reliable-events.mdx) 连接本地提交与异步交付。 |

这些方式不必互斥。例如，Outbox 负责让本地变化留下可靠的待发事件，Saga 再根据事件推进流程或补偿。前者不能单独保证整个业务流程完成，后者也需要可靠的消息来源。

## 7. 补偿能力 {#补偿能力}

补偿能修正业务结果，却未必能撤销已经发生的影响。退款是一笔新交易，邮件发出后只能再发送更正。因此，流程设计要先判断哪些操作可补偿、补偿会产生什么成本，再决定步骤顺序。具体边界见[Saga](./saga-compensation-intermediate-state.mdx#补偿)。

## 8. 可追踪的状态 {#可追踪的状态}

恢复需要持久化的流程状态作为依据，包括稳定 ID、当前步骤、最后错误、尝试次数和下次重试时间。进程重启后，系统应能据此判断继续执行什么。

日志可以帮助诊断，但不应成为判断流程状态的唯一依据。幂等与人工处置的设计见[分布式流程恢复](./idempotency-reconciliation-manual-repair.mdx)。

## 9. 故障矩阵 {#故障矩阵}

**故障矩阵**是把流程中的失败位置和对应恢复方式逐项列出的检查表。设计时至少要检查这些断点：

- 本地提交前崩溃，事务是否能回滚。
- 提交后、发布前崩溃，待发事件能否恢复。
- 响应丢失，怎样核对实际执行结果。
- 消息重复或乱序到达，状态转换是否仍然合法。
- 补偿持续失败，怎样告警并转入人工处理。
- 重放历史请求，幂等记录是否仍覆盖对应时间范围。

每个断点都要写明检测信号、恢复方式和最大风险窗口，才能验证方案在故障时仍守住原来的规则。

## 10. 常见问题 {#常见问题}

### 10.1 规则必须严格成立，就一定要用 2PC 吗？ {#强规则与协议选择}

不一定。先看规则能否放进本地事务，再用约束或条件更新保护。确实需要跨资源提交时，才评估 2PC 或业务预留。缩小需要同步协调的范围，可以降低协调成本。

### 10.2 用了消息队列，就能保证最终一致吗？ {#消息传输与收敛条件}

不能仅凭消息传输保证收敛。事件需要可靠地产生，消费者需要执行合法状态转换，失败后还要能恢复。没有主动报错却产生的差异，则需要通过业务对账发现。

### 11.1 如何根据业务选择分布式事务方案 {#choose-distributed-transaction}

**按业务必须守住的规则和同步成功条件选择方案，再验证故障时能否恢复。**

- 同一存储内的规则，用**本地事务与并发约束**维护。
- 跨服务协调时，资源支持持久准备与恢复协议，可以评估 **2PC**；业务有明确的预留能力，可以评估 **TCC**。
- 允许中间状态的长流程，用 **Saga** 组织步骤和补偿，Outbox 保证本地变化可靠地产生待发事件。

选择后用故障矩阵检查结果未知、重放和恢复，确认方案确实守住业务不变量。

### 11.2 库存只剩一件时，为什么先确认订单再补偿不能保证不超卖？ {#inventory-reservation-invariant}

**考察重点**：同步不变量、条件更新与预留记录。

**相关内容**：[库存预留与并发不变量](#库存预留与并发不变量)。

<details>
<summary>参考回答</summary>

**两个订单都确认时，已经违反确认即有货的规则。**

退款只能修正后续业务结果。库存服务应先原子预留，只有成功者继续确认。预留记录与扣减共同提交，并用请求唯一键防止重复扣减。

</details>
