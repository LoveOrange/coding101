# 2PC 与 TCC

**两阶段提交**（2PC）让多个事务资源按同一个决定提交或回滚；**TCC**（Try–Confirm–Cancel）则先预留业务资源，再确认使用或取消预留。两者都需要协调器，但参与者保存的状态和占用的资源不同。

理解这两种方案，要能推演决定丢失、请求重复和消息乱序时如何恢复。正常路径只是其中一部分，资源会占用多久、是否能安全重试，才决定方案能否落地。

## 1. 面试核心 {#core}

- 2PC 参与者先持久化准备状态，协调器再持久化最终决定，驱动各方**按同一决定提交或回滚**。[卡](#2pc-vs-tcc)
- 已准备的参与者在决定未知时，**不能擅自回滚**，需要保留资源并等待恢复。
- 全局提交决定已经持久化后，临时执行失败应当**沿原决定重试完成**，不能自行改成取消。
- TCC 的 Try **预留业务资源**，Confirm 使用预留，Cancel 释放预留，每个阶段各用本地事务保存结果。
- TCC 要把**分支状态与资源变化共同提交**，才能处理重复请求、Cancel 先到的空回滚，以及迟到 Try 造成的悬挂。[卡](#tcc-empty-cancel)

## 2. 2PC 准备阶段 {#2pc-准备阶段}

2PC 的准备阶段让各参与者确认自己能否完成事务。**协调器**负责汇总结果并作出全局决定，**参与者**负责管理各自的事务资源。

协调器发送 prepare 请求后，参与者完成约束检查，并持久化足够的恢复信息。投赞成票意味着它承诺可以执行最终决定。数据库参与者此时仍会保留锁等事务资源；如果有参与者明确拒绝，协调器记录 abort，再通知各方回滚。

## 3. 2PC 提交阶段 {#2pc-提交阶段}

所有参与者准备成功后，协调器先持久化 commit 决定，再发送提交通知。响应丢失时可以重发，因为最终决定已经确定，恢复过程要做的是让各方完成这个决定。

参与者重启后，根据恢复日志查询决定。如果决定仍然未知，就不能自行回滚：其他分支可能已经提交，此时回滚会让结果分裂。因此，2PC 在这种状态下可能阻塞。协调器高可用可以缩短故障时间，但网络分区仍可能阻止决定传达。

2PC 保证的是提交决定一致。跨库读取能看到什么，还取决于事务管理和读取协议，不能仅凭使用了 2PC 就推断读取隔离性。

## 4. 资源管理器支持 {#资源管理器支持}

参与 2PC 的资源需要支持持久化准备状态。XA 和数据库的 prepared transaction 提供了这类能力；普通 HTTP 接口若要参与同样的协议，需要额外承担保存状态和恢复决定的责任。

PostgreSQL 18 可以通过 `pg_prepared_xacts` 查看准备事务。长时间停在 prepared 状态会保留锁，并影响 `VACUUM` 回收。处理这些事务前，要先核对协调器的权威决定，再执行对应的提交或回滚，不能仅因为等待时间长就取消。

参与者越多，网络往返和日志持久化越多，完成时间也会增加。这种持续持有事务资源的方式，更适合能够接受持锁成本的短事务。

## 5. TCC 的 Try {#tcc-的-try}

Try 用本地事务检查条件并预留业务资源，例如库存、额度或席位。预留成功后，Confirm 消费这份预留，Cancel 则释放它，各阶段分别提交自己的本地事务。

Try 提交后，数据库锁随本地事务结束而释放，但业务资源仍被占用。例如，已预留的库存暂时不能卖给其他订单，要等分支确认或取消。TCC 减少了长时间持有数据库锁的需要，并没有消除业务资源的等待成本。

## 6. Confirm 与 Cancel 的幂等 {#confirm-与-cancel-的幂等}

Confirm 和 Cancel 都需要幂等，也就是重复调用不能再次改变业务效果。协调器用全局事务 ID 和分支 ID 标识操作，参与者保存处理结果：重复 Confirm 返回已有确认结果，重复 Cancel 返回已有取消结果。

Confirm 应消费 Try 已经预留的资源，业务拒绝条件应尽量在 Try 阶段检查完。全局 commit 确定后，如果 Confirm 只是临时执行失败，就需要继续重试，不能临时增加一个业务条件把既定决定推翻。

## 7. 空回滚与悬挂 {#空回滚与悬挂}

**空回滚**是 Cancel 到达时，Try 还没有成功执行、没有资源可释放的情况。例如 Try 请求延迟，协调器已经决定取消，Cancel 反而先到达。参与者仍要记下取消终态，不能因为无资源可释放就什么也不保存。

**悬挂**是取消已经完成，迟到的 Try 却重新预留资源，导致这份预留无人释放。避免它的方法是让 Try 先检查取消终态，发现已取消就拒绝执行。

### 7.1 分支状态与并发转换 {#分支状态与并发转换}

分支状态记录 Try、Confirm 和 Cancel 已经执行到哪里。`TRIED` 表示已预留，`CONFIRMED` 表示已确认，`CANCELLED` 表示已取消，各请求按当前状态处理：

| 当前状态 | Try | Confirm | Cancel |
| --- | --- | --- | --- |
| 无记录 | 创建预留与 TRIED。 | 返回异常，核对协调状态。 | 写入 CANCELLED。 |
| TRIED | 返回已有预留结果。 | 消费预留并转 CONFIRMED。 | 释放预留并转 CANCELLED。 |
| CONFIRMED | 返回已有结果。 | 返回成功。 | 拒绝相反终态。 |
| CANCELLED | 拒绝迟到 Try。 | 拒绝相反终态。 | 返回成功。 |

分支唯一键用于限制并发创建，状态检查、资源变化和终态更新需要在同一事务内提交。否则，状态显示已释放，资源却没有加回，重试也无法正确判断。状态标记的保留时间还要覆盖协议重试窗口，避免旧请求在记录删除后重新执行。

预留超时只能说明等待过久，应触发全局决定核对。如果全局已经 commit，资源方却自行释放，后续 Confirm 就会找不到预留。

## 8. TCC 的成本 {#tcc-的成本}

TCC 把更多恢复责任交给业务实现。每项资源都要提供三个阶段、分支记录和异常处理；协调故障期间，预留还会继续占用库存或额度，所以监控需要关注最老预留的等待时间和重试次数。

外部接口没有预留或幂等能力时，不能直接套用 TCC，需要重新选择业务方案。允许中间状态的长流程，可以进一步评估[Saga](./saga-compensation-intermediate-state.mdx)的补偿机制。

## 9. 方案选择 {#方案选择}

选择 2PC，要确认资源支持持久准备，并能接受短事务期间的持锁；选择 TCC，要确认业务资源有明确的预留、确认和释放模型。

两者都需要持久化全局决定，并监控长时间停留的中间状态。人工解除异常也必须依据权威决定，保留操作审计，避免为了释放资源而破坏已有提交结果。

## 10. 常见问题 {#常见问题}

### 10.1 协调器做了高可用，2PC 就不会阻塞了吗？ {#协调器高可用与阻塞}

仍可能阻塞。高可用减少了协调器单点故障的影响，但参与者无法联系协调器、又不知道最终决定时，仍需要等待通信恢复或执行恢复协议。

### 10.2 TCC 的 Cancel 就是数据库回滚吗？ {#cancel-与数据库回滚}

不是。Cancel 是一个新的本地业务事务，用来释放 Try 已经提交的预留；数据库 rollback 撤销的是当前事务中尚未提交的修改。

## 11. 面试题 {#面试题}

### 11.1 2PC 和 TCC 的差异是什么，各自有哪些失败状态 {#2pc-vs-tcc}



**考察重点**

- prepare、持久决定和不确定等待。
- Try 预留、Confirm/Cancel 幂等。
- 空回滚、悬挂、资源持有和恢复。

**相关内容**：[2PC 准备阶段](#2pc-准备阶段)至[方案选择](#方案选择)。

<details>
<summary>参考回答</summary>

**2PC 在资源层协调原子提交，TCC 在业务层协调预留。**

2PC 参与者持久化 prepare 后保留事务资源。协调器记录最终决定，再驱动各分支完成。决定未知时会阻塞。

TCC 的 Try 提交预留，Confirm 消费预留，Cancel 释放预留。幂等和分支状态处理重复与乱序。Cancel 先到需记录终态，迟到 Try 应拒绝。TCC 减少长数据库锁，但增加业务模型与恢复成本。

</details>
