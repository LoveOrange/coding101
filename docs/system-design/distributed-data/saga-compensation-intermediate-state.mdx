# Saga

**Saga** 是用一系列本地事务推进跨服务业务流程的方式。每一步独立提交，后续步骤失败时，再通过补偿事务修正已完成步骤的业务效果。

例如，订单流程已经预留库存，支付却失败，可以释放这笔预留。但已提交的步骤可能被其他请求看到，补偿也可能失败，因此 Saga 需要明确中间状态、并发限制和恢复方向。

## 1. 面试核心 {#core}

- Saga 的每个本地事务**独立提交，中间结果可见**，不能按一个尚未提交的大事务来理解。
- 补偿是**新的业务事务**。退款、释放预留可以修正业务效果，却不会抹去原来的操作历史。[卡](#compensation-not-rollback)
- 编排式由**协调器发出后续命令**，协同式由**服务通过事件推进**，两者都需要可追踪的流程状态。
- Saga 不提供跨步骤隔离。补偿要**只撤销本流程的影响**，不能用旧快照覆盖其他流程的新状态。[卡](#saga-concurrent-compensation)
- 不可逆转折步骤（pivot）成功后，应**向前恢复后续步骤**；流程设计必须保证这些步骤可重试，或有明确的人工处理方式。

## 2. 本地事务步骤 {#本地事务步骤}

Saga 把跨服务流程拆成各自可提交的步骤。例如，创建订单、预留库存、授权支付和履约，每一步保存本地结果，再触发下一步。

因为步骤之间存在等待，API 需要暴露 `PENDING_PAYMENT` 等中间状态，让用户能够查询进度。用户重试时沿用原业务 ID，继续同一流程；只有满足全部成功条件后，才能显示最终成功。

## 3. 补偿 {#补偿}

**补偿**是通过新的业务操作修正此前已提交的效果。库存预留可以通过释放预留来补偿，支付授权可以撤销，正式扣款则需要退款。退款有自己的流水，也可能产生到账延迟或手续费。

因此，补偿不会让历史变得像原操作从未发生。邮件已发送、通知已读或商品已发出时，只能进一步更正或人工处理。补偿顺序也要按业务依赖确定，而不能默认所有动作都能直接反向执行。

## 4. 编排式 Saga {#编排式-saga}

**编排式 Saga** 由协调器记录流程步骤，根据参与者返回的结果发出后续命令。分支、重试和超时集中管理，适合需要较多步骤判断的流程。

协调器需要持久化流程状态和待发送命令，重启后才能按记录继续。它负责的是流程进度，各参与者仍负责自己的业务数据和规则。

## 5. 协同式 Saga {#协同式-saga}

**协同式 Saga** 由服务订阅事件并发布后续结果，让事件串起整个流程。简单流程可以由此省去集中编排器，但步骤增多后，事件之间的依赖也更难追踪。

即使没有集中协调器，系统仍需要稳定的 Saga ID 和可查询的流程视图，才能查明某个流程执行到哪里。测试也要覆盖事件循环触发和重复到达，避免流程被反复推进。

## 6. 补偿的幂等与重试 {#补偿的幂等与重试}

补偿需要能够安全重试。参与者可以按 Saga ID 和步骤 ID 保存结果，重复调用沿用同一标识，并把补偿状态与本地资源变化放进同一事务。

暂时失败可以退避重试；持续失败则进入明确的待处理状态，并限制继续扩大风险。不能因为补偿请求已经发出，就认为原业务影响已经消除。对账和人工恢复的处理见[分布式流程恢复](./idempotency-reconciliation-manual-repair.mdx)。

## 7. 并发隔离 {#并发隔离}

Saga 的两个步骤之间，其他流程仍可能读写同一资源，因此需要业务层面的并发限制。可以使用预留、版本检查或按业务键串行处理；也可以用**语义锁**，即让“处理中”等业务状态暂时拒绝不相容的操作。

### 7.1 并发补偿与旧快照 {#并发补偿与旧快照}

补偿只能修正本流程造成的变化，不能直接把资源写回旧值。假设可用库存为 10，流程 A 预留 2 件后剩 8，流程 B 再预留 3 件后剩 5。

A 失败时，如果把库存恢复成旧值 10，就连 B 的 3 件预留也抹掉了。正确做法是只释放 A 的 2 件，得到 7，并用 A 的预留 ID 识别这次释放。

实现时，把预留记录从 `RESERVED` 改为 `RELEASED`，与加回库存放在同一本地事务中。重复补偿看到已经释放的终态，就返回原结果，避免再加一次库存。

## 8. 不可逆步骤 {#不可逆步骤}

**Pivot** 是流程中改变恢复方向的不可逆转折步骤：成功前可以通过业务补偿退出，成功后则需要继续推进后续步骤，使流程完成。

发货等不可逆动作应放在必要检查和资源预留之后。pivot 后的步骤应设计为可重试；如果业务上仍可能永久拒绝，就需要重新设计步骤边界，或准备明确的人工履约方式。否则流程可能在无法撤回、又无法完成的状态中停住。

## 9. 超时与未知结果 {#超时与未知结果}

调用超时只说明协调器没有及时收到结果，不说明参与者没有成功。协调器可以按原业务 ID 查询、等待结果事件，或把流程记为 `UNKNOWN` 后继续核对。

补偿还可能与迟到的正向操作相遇，参与者需要通过状态机拒绝互相冲突的终态。如果支持提前记录取消意图，可以据此阻止迟到操作在取消后重新生效。

## 10. 常见问题 {#常见问题}

### 10.1 Saga 能保证整个流程的中间状态不可见吗？ {#saga-的一致性范围}

不能。各本地事务已经独立提交，中间结果可以被其他请求读到。Saga 通过重试和补偿走向合法终态，跨步骤隔离则需要业务设计；必须同步成立的严格规则，要先由本地约束或预留保护。

### 10.2 补偿多次失败，流程可以直接标记结束吗？ {#补偿失败与人工状态}

不能把尚未修复的状态当作已完成。系统应保存错误和处理责任，持续告警，并明确显示仍待恢复。需要人工处理时，也应在确认解决后再结束流程。

## 11. 面试题 {#面试题}

### 11.1 Saga 的补偿为什么不等于数据库回滚 {#compensation-not-rollback}



**考察重点**

- 已提交本地事务和可见中间状态。
- 业务补偿、不可逆动作与并发隔离。
- 编排、协同、超时未知和人工处置。

**相关内容**：[本地事务步骤](#本地事务步骤)至[超时与未知结果](#超时与未知结果)。

<details>
<summary>参考回答</summary>

**Saga 补偿执行的是新的业务事务。**

原步骤已经提交，其他请求也可读到结果。退款或释放预留修正业务效果，但保留历史和外部影响。

补偿需幂等，并避免覆盖其他流程的新状态。调用超时先核对原结果。不可逆边界后的步骤向前恢复。持续失败进入可告警的待处理状态，修复后再结束流程。

</details>
