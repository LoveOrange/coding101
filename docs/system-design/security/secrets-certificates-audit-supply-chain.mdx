# 密钥、证书、审计与供应链安全

密钥和证书用来证明身份，审计日志用来追踪操作，供应链信息用来核对软件的来源。它们都需要覆盖完整的使用过程：凭据怎样发放和撤销，证书是否真正加载到服务端，部署的镜像是否来自获准的构建。面试中要能沿这些过程说明，正常更新和发生泄漏时分别怎样处理。

## 1. 面试核心 {#core}

- 应用通过自身身份读取密钥管理服务，权限限定为**当前环境和业务需要的凭据**。
- 签名密钥正常轮换时，**先让验证方信任新公钥，再切换签发方**，避免新令牌被拒绝。[卡](#key-cert-rotation)
- TLS 服务身份验证要同时检查**证书链、有效期和目标名称**。
- SBOM 说明产物包含哪些组件，provenance 说明如何构建；部署前还要**核对可信身份与实际产物摘要**。[卡](#artifact-provenance)
- 已泄漏密钥应**立即撤销**，不能继续沿用正常轮换时的新旧密钥重叠期。[卡](#compromised-key-response)

## 2. 密钥管理 {#密钥管理}

**密钥管理服务**（secret manager）集中保存密码、API token 和私钥，并控制谁能读取它们。应用使用自身的工作负载身份，只获取指定环境和资源的凭据。开发、测试和生产使用独立凭据，避免一个环境的泄漏影响其他环境。

凭据不应写进代码、镜像或构建日志，应通过受控方式在运行时注入。命令行参数可能出现在进程列表中，也不适合直接放置凭据。运行后仍要限制诊断端点和内存转储的访问，因为这些位置也可能包含凭据。

## 3. 密钥轮换 {#密钥轮换}

**密钥轮换**是用新凭据替换旧凭据，并最终停用旧版本。正常轮换要给使用方留出切换时间，否则验证端已经停用旧凭据，尚未更新的实例就会认证失败。支持双凭据的服务可以按以下顺序操作：

1. 创建新版本凭据。
2. 验证端同时接受新旧版本。
3. 灰度切换使用方，并观察失败率。
4. 确认旧版本已停止使用。
5. 撤销旧版本，保留操作审计。

单密码系统需要双账号或协调切换。直接替换密码会使尚未刷新的实例认证失败。

对 JWT 来说，验证方根据密钥标识 `kid`，从已经信任的公钥集合中选择验证密钥。切换签发密钥后，旧 token 仍可能有效，因此旧公钥要保留到这些 token 全部到期，并计入允许的时钟偏差。

公钥集合可以通过 JWKS 发布，验证方按缓存有效期刷新。遇到未知 `kid` 时，可以触发受限刷新；仍找不到可信密钥或刷新失败，就拒绝验证。刷新请求需要合并并限速，否则攻击者可以不断提交未知 `kid`，制造大量远程请求。

## 4. 证书链 {#证书链}

**证书链**把服务证书与客户端信任的签发机构联系起来。TLS 客户端既要验证这条链和证书有效期，也要确认证书对应自己要连接的服务。RFC 9525 使用证书的主题备用名称（SAN）中的服务标识匹配目标；跳过身份验证，就可能把连接交给冒充该服务的攻击者。

双向 TLS（mTLS）还要求服务端验证客户端证书。证书可以确认调用的是哪个工作负载，但这个主体能访问哪些资源，仍需要授权规则判断。

## 5. 证书自动续期 {#证书自动续期}

证书续期完成，要以实际服务端口开始使用新证书为准。续期依赖控制器、验证服务、权限和时钟，监控应覆盖这些环节的错误，并读取端口当前提供的证书。新证书已经签发、服务却没有加载时，用户仍会遇到旧证书过期的问题。

私钥泄漏后应生成新密钥并重新签发证书。撤销旧证书，同时核对客户端的撤销检查能力。长连接与缓存的处理需纳入应急方案。

## 6. 审计日志 {#审计日志}

**审计日志**记录谁在什么时候对什么资源做了什么，以及结果如何，用于事后追踪行为。登录、权限变更、密钥读取和数据导出都应纳入审计。请求 ID 和策略版本可以把一条记录与具体请求、当时的授权规则关联起来。

审计需要记录凭据被谁读取，不需要记录凭据本身。字段应脱敏，审计存储与业务管理员权限隔离，避免有权修改业务数据的人也能随意删除操作痕迹。追加写、保留策略和完整性检查可以进一步降低篡改风险。

日志需要可检索，并对高风险行为告警。演练应验证从告警定位到具体操作所需的时间。

## 7. 依赖安全 {#依赖安全}

依赖安全首先要弄清楚构建实际使用了什么。锁文件、固定版本和产物摘要可以约束构建输入；Maven 的依赖管理机制（dependency management）可以统一版本选择。但版本号相同不一定意味着仓库中的内容不变，可被覆盖的产物仍需额外约束。

私有命名空间与仓库来源应明确。CI 使用短期凭据，并隔离不受信构建步骤。扫描结果需进入修复、例外审批和复核流程。

## 8. SBOM 与 provenance {#sbom-与-provenance}

**软件物料清单**（SBOM）列出软件包含的组件和版本，发现依赖漏洞时，可以据此定位受影响的服务。**构建来源证明**（provenance）记录源码、构建器和产物摘要，用于追溯产物是怎样构建出来的。

部署前，要把来源证明中的摘要与实际镜像比对，确认检查的确实是即将运行的产物。还要按预设策略核对签名者、构建器、源码仓库和构建参数，不能只看到签名验证通过就放行。

有效签名只能证明指定主体签署了这个摘要，不能说明产物没有漏洞。因此仍要进行漏洞扫描、测试，并限制产物运行时的权限。

## 9. 事件响应 {#事件响应}

凭据泄漏后，应优先撤销旧凭据、限制受影响权限，再签发新凭据、刷新验证端缓存并确认切换成功。正常轮换允许新旧版本暂时并存，是为了给使用方留出时间；泄漏后继续保留旧版本，也会给攻击者留下使用时间。

JWT 私钥泄漏后，攻击者可自行签发 token。应按密钥版本拒绝旧签名，并触发必要的重新登录。审计用于确定访问范围与受影响资源。

依赖漏洞则通过 SBOM 定位服务。修复后重新构建，并核对生产镜像摘要。证书过期、密钥泄漏和产物撤回都应演练。

## 10. 常见问题 {#常见问题}

### 10.1 凭据经过 Base64 编码后可以提交到仓库吗？ {#base64-与秘密存储}

不可以。Base64 是可逆编码，拿到内容的人可以还原凭据。即使删除当前文件，历史记录和已经克隆的仓库仍可能保留副本，因此误提交后还需要轮换凭据。

### 10.2 配置 TLS 后，还需要授权和审计吗？ {#tls授权与审计}

需要。TLS 保护传输并验证连接身份，授权决定该身份可以执行哪些动作，审计记录实际发生的行为。连接可信，不代表调用者可以执行任意操作，也不代表已经留下可追溯的记录。

## 11. 面试题 {#面试题}

### 11.1 如何管理 JWT 签名密钥和 TLS 证书的轮换？ {#key-cert-rotation}

**考察重点**：重叠窗口、JWKS 与实际端点证书。

**相关内容**：[密钥轮换](#密钥轮换)、[证书自动续期](#证书自动续期)。

<details>
<summary>参考回答</summary>

**JWT 正常轮换先发布新公钥、再切换签发密钥；TLS 续期还要确认新证书已在实际端口生效。**

验证方在过渡期接受新旧版本。等旧 token 全部到期，并计入允许的时钟偏差后，再移除旧公钥。

TLS 证书需自动续期并在服务端加载。监控应读取实际端点证书，而非仅看签发结果。发生私钥泄漏时，立即撤销旧身份。

</details>

### 11.2 签名私钥泄漏后，还能等待旧 JWT 自然过期吗？ {#compromised-key-response}

**考察重点**：正常轮换与紧急撤销的差异。

**相关内容**：[事件响应](#事件响应)。

<details>
<summary>参考回答</summary>

**应立即拒绝旧密钥签发的 token。**

攻击者掌握私钥后可以持续伪造新 token，所以等待已有 token 到期并不能结束风险。验证端需移除旧公钥并刷新缓存，签发端改用新密钥，受影响会话重新认证。随后用审计记录核查攻击期间的访问范围。

</details>
