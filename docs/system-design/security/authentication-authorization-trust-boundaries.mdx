# 认证与授权

**认证**确认请求来自谁，**授权**判断这个主体能对哪些资源执行哪些操作。用户登录成功，只能说明身份已经确认；他能不能读取某笔订单，还要检查订单归属和操作权限。理解这一区别，才能解释为什么网关通过了身份校验，业务服务仍然需要检查权限。

## 1. 面试核心 {#core}

- 认证确认身份，授权还要结合**资源、动作和上下文**判断权限；登录成功不代表可以访问所有订单。[卡](#horizontal-privilege-escalation)
- RBAC **按角色分配权限**，ABAC **按属性计算权限**，两者可以结合使用。
- ReBAC 根据**用户、群组与资源之间的关系**计算权限，适合表达共享与继承。[卡](#relationship-authorization)
- 多租户访问要同时约束**可信租户和资源归属**，不能只凭请求中的资源 ID 查询。
- 权限变更后，**主动失效缩短撤销延迟，TTL 限制旧缓存的有效时间**。[卡](#authorization-revocation)

## 2. 信任边界 {#信任边界}

**信任边界**是系统需要重新判断身份和数据是否可信的位置。请求从浏览器进入网关、再到业务服务，或消息从生产者进入消费者，都可能跨过这样的边界。处在内网只说明网络位置，不能代替调用者身份和访问权限的验证。

网关向下游传递身份时，应先删除客户端传来的同名请求头，再写入验证后的身份。否则，攻击者可能直接填写他人的用户 ID，让下游误以为这是网关确认的结果。下游还要通过经过认证的连接或签名确认调用来源，只接受受保护的身份信息。内部调用和异步消费也需要相应约束。

## 3. 身份验证 {#身份验证}

身份验证要区分用户和服务。用户可以通过密码、多因素认证或通行密钥（passkey）登录；服务之间可以使用双向 TLS（mTLS），或用工作负载身份识别正在运行的应用。验证结果应说明主体是谁、由谁确认，以及使用了哪种强度的认证方式。

业务代码从已认证上下文取得用户身份，不能直接相信客户端传来的用户名。同样，用户选择了某个租户，不代表他就是该租户的成员，服务端还要核对成员关系。

## 4. 授权决策 {#授权决策}

一次授权要回答四件事：谁发起请求、要做什么、操作哪个资源，以及当前满足哪些条件。规则据此决定允许还是拒绝：

```text
principal + action + resource + context → allow / deny
```

例如，`ROLE_USER` 只表示用户具有某个角色。判断他能否取消订单，还要知道订单属于谁、属于哪个租户，以及当前状态是否允许取消。没有明确允许规则的请求，服务端应默认拒绝。

每次资源访问都要经过授权，包括批量请求里的每一项。只检查第一笔订单，会让同一批次中的其他订单绕过检查。Controller、Service 与查询层应遵循同一套策略，避免换一个入口就能访问原本无权操作的数据。

## 5. RBAC 与 ABAC {#rbac-与-abac}

**基于角色的访问控制**（RBAC）先把权限分给角色，再把角色分给用户。职责稳定时，可以用角色表达基础权限，例如给审核员分配审核操作。

**基于属性的访问控制**（ABAC）根据主体、资源和环境的属性判断权限。例如允许退款的条件可以是租户一致，且退款金额低于当前用户的审批额度。这些属性必须来自可信数据源，并随业务状态更新，否则规则正确也可能得到错误结果。

两者可以结合：角色授予基础权限，属性条件进一步限定范围。如果把地区、金额等组合都建成角色，角色数量会不断增加；把这些条件作为属性判断，会更便于维护。

### 5.1 关系型访问控制 {#关系型访问控制}

**基于关系的访问控制**（ReBAC）根据主体与资源之间的关系授予权限。例如，用户属于编辑组，编辑组拥有某个文件夹的编辑权，文件又从文件夹继承权限。沿着这些关系，就能判断用户是否可以编辑文件。

这种模型适合文档共享、组织成员和资源继承。删除用户的组成员关系后，相关权限缓存也要失效，否则用户仍可能凭旧结果访问文件。计算关系时还要限制遍历深度，并检测继承环，避免沿关系反复查找。

## 6. 多租户边界 {#多租户边界}

多租户查询要从已验证的上下文取得租户 ID，再用租户和资源 ID 共同限定查询范围：

```sql
SELECT * FROM orders WHERE tenant_id = ? AND id = ?;
```

第一个参数来自已经核对的租户成员关系，第二个参数是请求中的订单 ID。这样，即使用户修改了订单 ID，也不能通过这条查询读到其他租户的订单。查到订单后，还要判断当前用户是否有权执行读取、取消等具体操作。

租户隔离还应覆盖缓存键、消息和对象路径，避免数据库查对了租户，却从缓存取到其他租户的数据。数据库行级安全或独立数据库可以进一步隔离。管理员需要跨租户操作时，应使用临时授权，并记录操作原因。

## 7. 网关与服务的授权分工 {#网关与服务的授权分工}

网关适合验证凭据、检查令牌的 API 访问范围（scope）；领域服务掌握资源所有者和业务状态，负责最终授权。例如网关可以确认调用者有订单接口的访问权限，但某笔订单能否取消，仍由订单服务判断。

异步任务应保留发起主体和租户信息，并按业务约定在执行时重新验证权限。高风险任务如果延迟执行，应使用执行时的权限状态，避免任务排队期间用户已经被撤权，任务却仍按旧权限运行。

## 8. 权限变更与撤销 {#权限变更与撤销}

权限改变后，令牌和授权缓存中的旧信息不会自动更新。只做离线验证时，令牌里保存的角色可能一直被使用到令牌到期；相关机制见 [JWT 撤销](./session-jwt-oauth-oidc.mdx#jwt-撤销)。服务端缓存的授权结果也需要单独处理。

授权缓存键应覆盖主体、资源、动作和策略版本，避免把一次允许操作的结果用于另一种操作。策略或资源归属变化时，要主动使旧结果失效。缓存有效期（TTL）则限制通知丢失后，旧结果还能继续使用多久。

高风险操作应实时检查权限或撤销版本。如果策略服务故障、无法确认权限，就拒绝这类操作。低风险读取可以按预先约定使用尚未过期的授权缓存，过期后则拒绝请求。

## 9. 授权审计 {#授权审计}

授权审计要能还原一次决定：谁对哪个资源执行什么动作、结果如何、依据哪个策略版本。高风险操作还要关联审批记录。拒绝日志只保留诊断所需字段，并限制写入速率，避免大量被拒请求把日志系统压垮。

审计存储与业务管理权限隔离。日志保护机制见 [审计日志](./secrets-certificates-audit-supply-chain.mdx#审计日志)。

## 10. 常见问题 {#常见问题}

### 10.1 管理员可以访问所有租户的资源吗？ {#管理员的资源范围}

不可以仅凭管理员角色就放行。租户管理员只管理指定租户；跨租户操作应另行授予权限，并限制有效期。

### 10.2 多个服务可以共用一个 token 吗？ {#服务凭据的隔离}

应让每个服务使用独立身份。共用 token 时，一个服务泄漏凭据会影响其他服务，也难以区分是谁发起了调用。独立身份便于单独撤销和审计，目标服务仍需按调用主体和动作授权。

## 11. 面试题 {#面试题}

### 11.1 为什么网关完成鉴权后仍可能发生水平越权？ {#horizontal-privilege-escalation}

**考察重点**：身份、资源归属与多租户条件。

**相关内容**：[授权决策](#授权决策)、[多租户边界](#多租户边界)。

<details>
<summary>参考回答</summary>

**网关确认了身份，业务服务若没有检查订单归属，仍可能发生越权。**

例如攻击者已正常登录，只是把请求中的订单 ID 改成了他人的订单。服务如果直接按 ID 查询并返回，网关的身份校验就挡不住这次访问。

领域服务应同时检查租户、所有者和具体动作。查询绑定可信租户与资源 ID，内部调用和异步消费也遵循同一策略。

</details>

### 11.2 文档共享权限适合使用 RBAC、ABAC 还是 ReBAC？ {#relationship-authorization}

**考察重点**：角色、属性与资源关系。

**相关内容**：[RBAC 与 ABAC](#rbac-与-abac)、[关系型访问控制](#关系型访问控制)。

<details>
<summary>参考回答</summary>

**文件夹继承和群组共享适合用 ReBAC 表达。**

例如用户属于某个群组，群组拥有文件夹权限，文件再继承文件夹权限，就可以沿关系判断用户是否有权访问。RBAC 可以提供基础管理权限，ABAC 可以追加设备、时间等条件。

关系变化后应使相关缓存失效，并明确继承规则、拒绝规则，让审计能还原这次授权依据的关系路径。

</details>

### 11.3 撤销权限后，怎样限制旧授权缓存的生效时间？ {#authorization-revocation}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：失效通知、TTL 与故障时的决策。

**相关内容**：[权限变更与撤销](#权限变更与撤销)。

<details>
<summary>参考回答</summary>

**主动失效缩短撤销延迟，TTL 限制失效通知丢失后旧结果仍能使用的时间。**

权限或资源归属发生变化时，主动删除旧缓存，或让旧策略版本、旧归属版本的结果不再命中。即使失效通知丢失，旧结果也只能使用到 TTL 到期。

高风险操作应实时核对撤销状态，策略服务不可用时拒绝执行；低风险读取只能在约定的有效缓存窗口内继续。

</details>
