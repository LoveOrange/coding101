# Spring Security

Spring Security 通过 Servlet 过滤器链处理请求的认证与授权：先选中适用的安全链，再恢复或验证身份，最后按规则判断是否允许访问。本文以 Spring Security 6.5 为基准。理解这条执行路径，才能排查接口没有受到保护、登录后仍是匿名身份，以及方法权限没有生效等问题。

## 1. 面试核心 {#core}

- `DelegatingFilterProxy` 把 Servlet 容器的调用**委托给 Spring 管理的 `FilterChainProxy`**。
- `FilterChainProxy` 每次只选择**第一条匹配的 `SecurityFilterChain`**，链的顺序会影响请求受到哪套规则保护。[卡](#security-filter-chain)
- Spring Security 6 默认要求**显式保存需要跨请求恢复的安全上下文**，只设置当前线程的身份不够。[卡](#explicit-context-save)
- `ExceptionTranslationFilter` 处理的是**下游抛出的安全异常**，再委托认证入口或拒绝处理器决定响应。
- `@EnableMethodSecurity` 启用方法授权；默认代理模式下，**同类内部调用绕过代理**，方法注解不会因此自动生效。[卡](#method-security-proxy)

## 2. DelegatingFilterProxy {#delegatingfilterproxy}

`DelegatingFilterProxy` 是连接 Servlet 容器和 Spring Bean 的过滤器。在 Spring Security 的配置中，它把容器收到的调用交给名为 `springSecurityFilterChain` 的 Bean，这个 Bean 的类型是 `FilterChainProxy`。后续安全处理因此可以使用 Spring 管理的对象。

自定义安全过滤器时要检查注册位置。同一个过滤器如果既注册到容器，又加入安全链，就可能沿两条路径重复执行。

## 3. FilterChainProxy {#filterchainproxy}

`FilterChainProxy` 负责选择安全链。应用可以配置多条 `SecurityFilterChain`，但一次只使用第一条匹配的链：`@Order` 决定先检查哪条，`securityMatcher` 决定每条链适用于哪些请求。

```java
@Bean
@Order(1)
SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.securityMatcher("/api/**")
        .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults());
    return http.build();
}
```

这段 Spring Security 6.5 配置只匹配 `/api/**`，并要求其中的请求经过认证。请求如果不属于这个范围，就需要由其他链保护，因此还应配置一条兜底链。

`requestMatchers` 的作用不同：它在已经选中的链里匹配授权规则。请求未命中任何安全链，就不会受到 Spring Security 保护。测试应覆盖管理端点、不同 HTTP 方法和错误转发，确认它们进入了预期的链。

## 4. SecurityContext {#securitycontext}

`SecurityContext` 保存当前请求的身份信息，其中的 `Authentication` 包含主体、认证状态，以及授予的权限（authorities）。业务代码通过 `SecurityContextHolder` 访问当前安全上下文。

Servlet 默认策略使用 `ThreadLocal`，把上下文关联到当前线程。请求结束后，安全链会清理它，避免线程池把同一线程分配给下一次请求时，仍然带着上一个用户的身份。

异步任务换了执行线程，需要显式安排身份传递。`DelegatingSecurityContextExecutor` 等包装器会在任务执行前设置上下文、结束时清理；业务仍要决定哪些身份信息和权限可以传给任务。

### 4.1 上下文持久化 {#上下文持久化}

当前线程能读到身份，与下一次请求能恢复身份，是两件事。Spring Security 5 默认自动保存 `SecurityContext`；Spring Security 6 默认使用 `SecurityContextHolderFilter` 读取上下文，保存则由认证流程显式完成。

自定义登录需要跨请求保留身份时，应调用所配置的 `SecurityContextRepository` 的 `saveContext`。仅设置 `SecurityContextHolder`，只会改变当前执行上下文，不能据此认为身份已经保存。

内置认证机制会按自身配置处理保存。排查自定义登录时，需核对仓库与保存时机。

## 5. AuthenticationManager {#authenticationmanager}

`AuthenticationManager` 接收认证请求，判断提交的凭据能否建立身份。认证过滤器先提取凭据、构造待认证的 `Authentication`，再交给它处理。使用 `ProviderManager` 时，它会寻找支持该认证类型的 `AuthenticationProvider` 执行验证。

验证成功后，`AuthenticationProvider` 返回认证结果，由过滤器写入上下文；验证失败则进入对应的失败处理流程。无论成功还是失败，凭据值都不应写入日志。

## 6. 过滤器顺序 {#过滤器顺序}

过滤器顺序由依赖关系决定：先读取上下文，再认证，最后授权。需要已认证身份的自定义过滤器应放在认证之后；负责建立身份的过滤器则必须在授权之前运行，否则授权时还没有它产生的身份。

`ExceptionTranslationFilter` 只捕获其下游抛出的安全异常。位于它之前的认证过滤器使用自己的失败处理器。调试时应查看实际链顺序，并检查重复注册。

## 7. ExceptionTranslationFilter {#exceptiontranslationfilter}

`ExceptionTranslationFilter` 把下游安全异常转换成相应的处理流程。需要启动认证时，它调用 `AuthenticationEntryPoint`：表单登录可以跳转到登录页，Basic 或 Bearer API 则可以返回 401。

对已完成认证但权限不足的主体，默认拒绝处理返回 403；匿名主体的授权失败则启动认证入口。自定义处理器可以改变响应形式，所以排查状态码时要同时看身份状态和处理器配置。

## 8. Session 与 Bearer Token {#session-与-bearer-token}

Session 登录通过上下文仓库跨请求恢复身份。无状态 API 每次验证 Bearer Token。

`SessionCreationPolicy.STATELESS` 控制 Spring Security 是否使用 Session 保存和获取安全上下文，不能据此判断请求没有 CSRF 风险。如果凭据仍放在浏览器自动携带的 Cookie 中，就仍需防护 CSRF，见 [XSS 与 CSRF](./injection-authorization-ssrf-deserialization.mdx#xss-与-csrf)。

## 9. 方法与数据级授权 {#方法与数据级授权}

`authorizeHttpRequests` 约束请求路径。`@EnableMethodSecurity` 启用方法权限。随后可用 `@PreAuthorize` 表达调用前检查。

默认代理模式下，权限检查发生在代理拦截调用时。同类内部直接调用带注解的方法，不经过代理，也就不会触发这次方法拦截。需要保护的调用应经过对应 Bean 的代理。

方法权限还需结合资源归属与租户条件。数据层边界见 [多租户边界](./authentication-authorization-trust-boundaries.mdx#多租户边界)。

## 10. 常见问题 {#常见问题}

### 10.1 配置了专用安全链，为什么请求仍进入通用链？ {#多链匹配范围}

因为只会选择第一条匹配的链。通用链排在前面且已经匹配，请求就不会再尝试后面的专用链。应先放专用链，再用覆盖所有请求的链兜底。

### 10.2 JWT 认证过滤器应该放在哪里？ {#自定义-jwt-过滤器的位置}

应放在授权之前，让授权过滤器能读取认证结果，同时为认证失败配置对应的处理流程。Spring Security 的 Resource Server 已提供 Bearer Token 支持，可以直接配置使用；确需自定义时，再核对实际过滤器顺序。

## 11. 面试题 {#面试题}

### 11.1 Spring Security 如何从请求进入过滤器链并完成鉴权？ {#security-filter-chain}

**考察重点**：容器委托、多链匹配与上下文生命周期。

**相关内容**：[DelegatingFilterProxy](#delegatingfilterproxy)、[过滤器顺序](#过滤器顺序)。

<details>
<summary>参考回答</summary>

**Servlet 容器通过 `DelegatingFilterProxy` 进入 `FilterChainProxy`，再由选中的安全链完成认证和授权。**

`FilterChainProxy` 选择第一条匹配的链，并按顺序调用其中的过滤器。认证过滤器委托 `AuthenticationManager` 验证凭据，结果进入 `SecurityContext`，授权过滤器再按当前身份和规则判断权限。

请求结束后清理上下文，避免线程复用时残留身份。安全异常根据发生位置，由相应认证入口、拒绝处理器或认证失败处理器处理。

</details>
