# Web 应用安全

Web 应用安全要控制两件事：外部输入会被当成什么执行，请求又能访问哪些资源。SQL 注入、XSS 和不安全反序列化涉及输入如何被解释，越权和 SSRF 则涉及访问范围。理解攻击发生在哪一步，才能判断参数绑定、权限检查和网络隔离分别能防住什么。

## 1. 面试核心 {#core}

- SQL 参数绑定把**数据与 SQL 指令分开**，动态表名、列名仍需使用白名单映射。[卡](#sqli-idor-ssrf)
- XSS 让恶意脚本在站点上下文中执行，防护时要让**输出编码匹配具体使用位置**。[卡](#xss-csrf-cors)
- CSRF 借浏览器自动携带的凭据发起请求，需要通过 **CSRF token 和来源检查**验证请求。[卡](#xss-csrf-cors)
- SSRF 防护要检查**实际连接目标和每次重定向**，并限制出站网络。[卡](#ssrf-dns-redirect)
- 反序列化要**限定可构造的类型和对象图规模**，更换数据格式不能代替这些限制。[卡](#deserialization-type-limits)

## 2. 注入 {#注入}

**注入**是指外部输入被当成指令的一部分解释，从而改变了原本要执行的操作。SQL、Shell、模板和 LDAP 查询都有这样的风险。下面的代码直接把 `name` 拼进 SQL：

```java
// 风险示例：输入成为 SQL 语法的一部分。
String sql = "SELECT * FROM users WHERE name = '" + name + "'";
```

`name` 中的引号可能改变 SQL 的语法结构，因此值参数应使用参数化查询，让数据库把它作为数据处理。参数绑定只处理值，不能替代任意表名或排序列；这类动态结构要由服务端从白名单中选择。

文件处理等操作优先使用专用 API。确实需要启动外部程序时，应固定可执行项并校验参数。绕开 Shell 可以避免输入被当成 Shell 语法，但程序自身仍可能接受危险选项，所以参数范围也要限制。

## 3. 输入校验 {#输入校验}

输入校验判断数据是否符合业务要求，包括类型、长度、枚举值和字段之间的关系。若数据需要解码或规范化，应在这些处理完成后再作安全判断。客户端校验能及时提示用户，但请求可以绕过客户端，因此服务端必须独立检查。

输入校验不能替代参数绑定。例如合法姓名可以包含引号，不应为了防注入就一律禁止；参数绑定会让引号作为数据处理。即使输入合法、SQL 也没有注入，用户能否查询这条记录，仍由资源授权决定。

## 4. 越权 {#越权}

**水平越权**是访问同级用户的资源，例如普通用户读取另一位用户的订单；**垂直越权**是执行超出自身权限的操作，例如普通用户调用管理员接口。两者都需要在服务端检查具体资源和动作，见 [授权决策](./authentication-authorization-trust-boundaries.mdx#授权决策)。

批量接口要逐项检查资源权限。UUID 降低枚举概率，但不提供访问权限。导出、对象链接和异步任务同样需要校验。

## 5. XSS 与 CSRF {#xss-与-csrf}

**跨站脚本攻击**（XSS）让攻击者提供的脚本在受害站点的上下文中执行。脚本可能来自已存储的内容、被响应直接返回的输入，或浏览器中的 DOM 操作，对应存储型、反射型和 DOM XSS。防护要看输入最终被放在哪里：HTML 正文、属性和 JavaScript 代码需要各自适用的输出编码。

只展示文本时，可以使用 `textContent`，让内容按文本处理。需要保留富文本格式时，使用 HTML 清理库筛除危险内容。内容安全策略（CSP）可以进一步限制哪些脚本能够执行，作为额外防护。

**跨站请求伪造**（CSRF）是借助浏览器自动携带的 Cookie 等凭据，诱使浏览器向目标站点发起请求。站点收到有效 Cookie，只能确认会话，不能据此判断操作是否出于用户意愿。因此还要验证 CSRF token、核对请求来源，并用 `SameSite` 增加限制。状态变更应使用非 GET 请求，但改变请求方法本身不能替代 CSRF 防护。

`HttpOnly` 阻止脚本读取 Cookie，但已经执行的 XSS 仍可借浏览器发送带凭据的请求。跨源资源共享（CORS）控制跨源脚本能否读取响应，而 CSRF 可能在读不到响应的情况下完成操作，所以 CORS 不能承担完整的 CSRF 防护。

## 6. SSRF {#ssrf}

**服务端请求伪造**（SSRF）是攻击者控制请求目标，让服务器代自己访问某个地址。URL 预览、Webhook 和下载接口都需要关注这个问题：服务器能访问的网络范围可能比用户更大，例如云元数据接口、回环地址和内网管理接口。

预登记目标可使用域名白名单。开放 URL 接口需限制协议、端口和地址范围。响应大小、读取时长与重定向次数也应设上限。

### 6.1 DNS 与重定向边界 {#dns-与重定向边界}

检查域名时通过，不代表连接时仍然安全。一次 DNS 解析可能得到公网地址，连接前再次解析却得到内网地址。因此，连接必须使用已经验证过的地址集合，校验范围还要覆盖 IPv4、IPv6 和特殊地址。

重定向也会改变目标：最初访问的是允许的地址，响应却可能要求跳转到内网。默认关闭自动重定向最容易控制访问范围；业务需要跟随时，每一跳都要重新验证。经过代理发起请求时，代理层同样需要遵守这些规则。

出站网络策略阻断敏感网段，作为第二层控制。仅检查 URL 字符串会遗漏实际连接地址。

## 7. 不安全的反序列化 {#不安全的反序列化}

**反序列化**是把外部数据还原成对象。对象反序列化在恢复对象及其引用关系时，可能执行类中的逻辑。如果攻击者能指定要构造的类型，就可能利用应用已有的类组合出危险调用。

接收外部数据时，应明确字段结构（schema），并只映射到限定的数据传输对象（DTO）。改用 JSON 后，如果仍允许输入指定任意多态类型，也会有同类风险。此外还要限制输入字节数、嵌套深度和集合大小，避免解析占用过多资源。

Java 17 可以用 `ObjectInputFilter` 检查对象输入，但过滤规则需要主动配置，并测试不允许的输入是否确实被拒绝。给数据签名可以验证来源和完整性，不能代替对可构造类型的限制。

## 8. 攻击链 {#攻击链}

一种漏洞可能为下一步攻击提供条件。例如，SSRF 让服务器访问到存放高权限凭据的接口，攻击者再用凭据导出数据。出站隔离限制第一步能访问的目标，最小权限和资源授权限制凭据泄漏后的影响；凭据本身的管理见 [密钥管理](./secrets-certificates-audit-supply-chain.mdx#密钥管理)。

## 9. 错误信息与日志 {#错误响应与日志}

客户端只接收错误类别和关联 ID。内部 SQL 与文件路径仅用于受控诊断。token 等凭据值应从响应和日志中移除。

日志需脱敏、限速，并清理换行等控制字符。监控按拒绝规则聚合，避免用完整 payload 作标签。

## 10. 安全测试 {#安全测试}

测试覆盖跨租户 ID、批量资源和未知类型。URL 接口还需覆盖重定向、IPv6 与 DNS 变化。富文本测试同时检查渲染位置和危险 DOM 接口。

依赖扫描与静态分析提供风险线索。资源授权仍需用业务测试验证。

## 11. 常见问题 {#常见问题}

### 11.1 使用 ORM 就不会有 SQL 注入了吗？ {#orm-的参数边界}

不能这样判断。ORM 的参数绑定保护值参数，但手写的原生 SQL、拼接的动态片段和排序表达式仍需单独审查。

### 11.2 过滤 URL 中的私有地址就能防住 SSRF 吗？ {#私有地址过滤的边界}

不够。域名解析和重定向都可能改变目标，必须检查实际连接 IP 和每次跳转。地址过滤还要配合协议限制与网络隔离，不能只检查最初的 URL 字符串。

## 12. 面试题 {#面试题}

### 12.1 如何同时防止 SQL 注入、水平越权和 SSRF？ {#sqli-idor-ssrf}

**题型**：综合题

**考察重点**：解释器、资源与网络边界。

**相关内容**：[注入](#注入)、[越权](#越权)、[SSRF](#ssrf)。

<details>
<summary>参考回答</summary>

**SQL 注入靠隔离数据与指令，水平越权靠资源授权，SSRF 靠目标校验与出站限制。**

SQL 值使用参数绑定，动态表名、列名使用白名单。资源服务按主体、租户、资源和动作判断权限，不能只确认用户已登录。URL 接口则校验实际连接地址和每次重定向，并在网络层限制访问范围。

三类控制解决的问题不同，测试也应分别覆盖动态 SQL、跨租户 ID 和重定向目标。

</details>

### 12.2 XSS 与 CSRF 有何区别，CORS 和 HttpOnly 能防什么？ {#xss-csrf-cors}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：脚本执行、凭据携带与浏览器边界。

**相关内容**：[XSS 与 CSRF](#xss-与-csrf)。

<details>
<summary>参考回答</summary>

**XSS 在站点内执行脚本，CSRF 借自动凭据发起请求。**

XSS 防护以安全输出和富文本清理为主。CSRF 防护验证 token 与请求来源。

HttpOnly 限制脚本读取 Cookie。CORS 限制跨源脚本读取响应。二者都无法覆盖所有伪造请求。

</details>

### 12.3 校验域名后再请求，为什么仍会发生 SSRF？ {#ssrf-dns-redirect}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：DNS 时间差、重定向与网络控制。

**相关内容**：[DNS 与重定向边界](#dns-与重定向边界)。

<details>
<summary>参考回答</summary>

**DNS 再解析或重定向会改变实际连接目标。**

校验应绑定连接使用的地址。每次跳转都重新检查，或直接禁用跳转。

IPv4、IPv6 和代理路径都要纳入校验。网络层另行阻断元数据和管理网段。

</details>

### 12.4 改用 JSON 后，怎样控制反序列化风险？ {#deserialization-type-limits}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：动态类型、schema 与资源限制。

**相关内容**：[不安全的反序列化](#不安全的反序列化)。

<details>
<summary>参考回答</summary>

**使用明确 DTO，并关闭任意多态类型解析。**

风险取决于解析器允许构造哪些对象，而不是文件是否叫 JSON。限定类型后，还要限制输入大小、嵌套深度和集合大小，控制解析消耗的资源。

若应用仍接收 Java 原生对象输入，可以配置 `ObjectInputFilter`。这些限制需要与依赖漏洞修复一起落实。

</details>
