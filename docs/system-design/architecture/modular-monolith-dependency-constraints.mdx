# 模块化单体

**模块化单体**是在同一个部署单元内，按业务能力划分模块的架构。模块共享进程和发布流程，但通过公开接口协作，各自维护内部实现和数据写入规则。

它保留了本地调用和事务的便利，同时要求模块边界可以被检查。理解这种架构，要能说明哪些依赖被允许、谁能修改数据，以及模块事件处理失败后如何恢复。

## 1. 面试核心 {#core}

- 模块化单体**共享部署单元，按业务接口划分模块**。是否拆成微服务，要看独立部署的收益能否承担分布式成本。[卡](#modular-monolith-vs-microservices)
- 模块边界需要**单向依赖和明确的数据写入方**，只拆目录无法阻止相互访问内部实现。
- 提交后处理的普通内存事件可能随进程退出而丢失。恢复需要**持久事件记录和幂等监听器**。[卡](#module-event-durability)
- Spring Modulith 的结构验证可以检查**依赖环和内部包越界**，并在 CI 中阻止违规依赖进入代码库。

## 2. 业务模块 {#按业务能力组织模块}

业务模块把一项业务能力的规则、接口和实现放在一起。例如，订单需求主要在订单模块内修改，模块内部再安排应用、领域和基础设施代码：

```text
com.example.shop
├── order
│   ├── OrderManagement.java
│   └── internal
├── inventory
│   ├── InventoryManagement.java
│   └── internal
└── payment
    ├── PaymentManagement.java
    └── internal
```

这里的 `order`、`inventory` 和 `payment` 分别负责自己的业务能力。其他模块通过 `OrderManagement` 等公开接口调用它们，内部实现放在 `internal` 中。它们仍在同一个进程中运行，也通过同一条流水线发布。

## 3. 模块接口 {#模块接口}

模块 API 应表达业务能力，例如用 `reserveInventory` 表达预订库存。Repository 和持久化实体留在模块内部，这样调用方就不必跟随内部存储结构一起变化。公开的类型越少，需要维护的外部约定也越少。

目录名本身不会限制 Java 访问权限。`package-private` 只允许同一个包访问，子包也是独立的包；而 `public` 类型即使放在 `internal` 包中，外部仍能引用，需要结构测试加以约束。

Spring Modulith 2.1 默认把根包的直接子包识别为模块，把模块根包中的公开类型视为 API。需要额外公开一组类型时，可以用 named interface（命名接口）声明范围。

## 4. 单向依赖 {#单向依赖}

模块之间应避免依赖环。A 调用 B，B 又引用 A，双方的理解和测试就会相互影响，初始化及后续拆分也会相互牵制。

出现依赖环时，先判断共同规则究竟归谁负责。可以把规则放回负责它的模块，将稳定契约单独抽出，或者用事件通知后续工作。共享包应只保留小而稳定的内容；把双方内部实现都移进去，只是换了一个地方继续耦合。

## 5. 同步调用与事件 {#同步调用与事件}

用例需要立即取得结果并作判断时，使用同步模块 API；只需通知后续工作时，可以发布事件。采用事件之后，还要决定监听器何时执行，因为这会改变失败对原事务的影响。

Spring 默认同步分发应用事件，监听器抛出的异常可以影响发布调用和原事务。若改为事务提交后异步处理，原事务不会等待监听器完成，却会出现“业务已提交、事件还没处理”的失败窗口。

### 5.1 事务事件与持久登记 {#事务事件与持久登记}

提交后异步处理的事件需要持久记录，才能在进程重启后继续执行。否则，业务事务刚提交，进程就在监听器运行前退出，内存事件随之丢失，重启后也不知道还有什么没做。

Spring Modulith 2.1 的 Event Publication Registry 用来登记事件处理进度。配置持久化实现后，发布记录随业务事务一起写入，每个事务监听器都有对应的处理记录。监听器成功执行后，再把记录标记为完成。

未完成记录保留下来，供重发机制恢复处理。不过，监听器可能已经成功执行，只是完成标记没有写入，所以重发仍可能造成重复。监听器需要幂等，保证重复处理不会再次产生业务效果。跨进程交付的机制见[Transactional Outbox 与 CDC](../distributed-data/outbox-cdc-reliable-events.mdx)。

## 6. 数据所有权 {#数据所有权}

共用数据库不等于可以任意写入其他模块的表。每张业务表应有明确的负责模块，其他模块通过它的 API，或专门的只读投影获取数据。

可以用 schema、表名前缀和迁移脚本标明责任。如果业务规则确实需要跨模块原子提交，可以使用跨模块事务，但要把这种依赖明确记录下来，在调整边界时一起评估。

## 7. 自动化结构检查 {#自动化结构检查}

模块依赖规则应由 CI 自动检查，避免每次都靠人工发现。以下测试验证应用中的模块结构：

```java
class ModuleStructureTests {
    @Test
    void verifiesModules() {
        ApplicationModules.of(ShopApplication.class).verify();
    }
}
```

`verify()` 在 Spring Modulith 2.1 中检查依赖环和内部包越界；配置 `allowedDependencies` 后，还会检查依赖是否在允许列表内。显式声明为开放模块时，则允许访问其内部类型。需要额外的包依赖或自定义规则，可以用 ArchUnit 补充。

这些检查覆盖的是代码关系，不能代替跨模块 SQL 检查，也不能证明运行时没有资源争用。

## 8. 模块的测试与观测 {#模块的测试与观测}

测试和运行指标都需要能定位到模块。测试应覆盖公开 API、领域规则和依赖契约，Spring Modulith 可以帮助缩小集成测试涉及的模块范围。

日志和指标加入模块维度后，事件积压、调用耗时和事务失败就能关联到具体模块。但所有模块仍共享进程，一个模块大量占用 CPU 或堆内存，会影响其他模块，逻辑边界并不提供资源隔离。

## 9. 适用场景 {#适用场景}

业务边界仍在变化、团队维护能力有限时，模块化单体可以保留本地调用和共库事务的便利，同时通过接口、写入权和结构检查约束代码。

当某个模块出现稳定的独立发布、扩容或故障隔离需求时，再评估拆分的收益。此前建立的模块边界能提供依据，但仅仅分好了目录，还不足以证明它适合独立运行。

## 10. 常见问题 {#常见问题}

### 10.1 拆成 Maven 模块就算模块化单体了吗？ {#maven-模块与业务模块}

不一定。Maven 模块提供构建边界，业务模块还要明确对外契约、允许的依赖和数据写入权。两者可以配合，但构建时分开并不能阻止业务规则相互穿插。

### 10.2 一个模块只能由一个团队维护吗？ {#模块维护责任}

不是，一个模块可以由多个团队协作。关键是明确谁决定接口和表结构的变化、谁负责评审。团队调整时，也要同步更新这些责任，避免边界存在却无人维护。

## 11. 面试题 {#面试题}

### 11.1 模块化单体与微服务怎样选择 {#modular-monolith-vs-microservices}



**题型**：综合题

**考察重点**

- 逻辑模块与部署单元的区别。
- 契约、依赖、数据所有权和结构检查。
- 独立部署收益与分布式成本。

**相关内容**：[业务模块](#按业务能力组织模块)至[适用场景](#适用场景)。

<details>
<summary>参考回答</summary>

**模块化单体适合边界仍在变化且运维资源有限的系统。**

模块共享进程，本地调用与事务较简单。微服务适合独立发布、扩容或隔离收益明确的能力。

两者都需要业务接口和数据所有权。单体可用单向依赖及 CI 结构测试维护边界。服务拆分则增加网络失败、契约兼容和运行成本。选择依据是可验证的收益与维护能力。

</details>

### 11.2 模块事件在事务提交后处理，进程崩溃时如何恢复？ {#module-event-durability}

**考察重点**：监听时机、持久登记与重复处理。

**相关内容**：[事务事件与持久登记](#事务事件与持久登记)。

<details>
<summary>参考回答</summary>

**持久事件登记为重启后的恢复提供依据。**

业务变化与发布记录在同一事务中提交。监听器完成后标记结果，未完成记录用于重发。普通内存事件缺少这份记录。监听器仍需幂等，以覆盖成功后确认丢失。

</details>
