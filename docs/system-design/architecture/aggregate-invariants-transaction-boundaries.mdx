# 聚合

**聚合**是一组需要共同维护业务规则的对象，外部通过其中的聚合根修改它们。例如，修改订单项的数量时，订单总额也必须一起更新。聚合设计要回答的就是：哪些状态必须一起提交，哪些状态可以独立变化。

判断边界是否合适，既要看业务规则，也要看并发写入的代价。把所有相关数据放在一起，会让无关操作互相争用；拆得太散，又可能让一次失败留下不一致的数据。

## 1. 面试核心 {#core}

- 聚合按**必须共同成立的业务规则**划分，由聚合根统一接收修改命令。[卡](#aggregate-boundaries)
- 实体**按身份识别**，值对象**按属性比较**。聚合根本身是实体，聚合内部可以同时包含实体和值对象。[卡](#entity-value-object)
- 聚合内的一次状态变化应在**同一本地事务中提交**，多张表也要共同成功或共同回滚。
- 聚合之间通过 **ID 或必要的业务快照**引用，避免把独立生命周期的对象一起加载和修改。
- 乐观锁用版本条件拒绝旧状态写入。发生冲突后，需要**重新读取状态并校验业务规则**，不能只换版本号。[卡](#aggregate-concurrent-update)

## 2. 不变量与聚合 {#不变量与聚合}

**不变量**是每次业务操作完成后都必须成立的规则。例如，订单总额必须等于有效订单项的金额之和，取消后的订单不能再确认，库存预订量不能超过可售数量。

聚合边界由这些规则决定。订单项和总额需要一起修改，因为只改其中一方会留下错误金额。页面上一起展示的数据却未必需要一起提交；数据库外键也只说明存储关系，不能直接决定聚合边界。

设计时可以先列出允许执行的命令，再看每条命令要修改哪些状态、检查哪些规则。必须原子维护，也就是必须一起成功或一起失败的状态，应放进同一个修改边界。

## 3. 聚合根 {#聚合根}

**聚合根**是聚合中负责接收外部修改请求、维护整体规则的对象。它的接口应表达业务动作：

```java
order.changeQuantity(productId, quantity);
order.confirm(confirmTime);
order.cancel(reason);
```

调用 `changeQuantity` 时，订单根先检查当前状态是否允许修改，再调整订单项和总额。外部不能绕过订单根单独修改订单项，否则总额规则就可能失效。内部对象仍可承担具体计算，聚合根负责控制修改入口。

用户是否有权限操作订单，由应用层鉴权；订单当前能否修改、确认或取消，则由领域模型检查。两类检查解决的问题不同。

### 3.1 实体与值对象 {#实体与值对象}

**实体**是按持续身份识别的对象。订单从待确认变成已确认，属性变了，但订单 ID 没变，它仍是同一笔订单。

**值对象**是按属性值识别和比较的对象。金额由数值与币种共同定义，两份数值和币种都相同的金额可以互换。值对象适合设计为不可变对象，需要修改时创建一个新值。

聚合根需要持续身份，因此它是实体。聚合内部可以包含其他实体和值对象。**仓储**负责加载和保存聚合，以聚合根作为操作入口；如果再给内部实体开放独立写入入口，就可能绕过聚合根的检查。

## 4. 事务边界 {#事务边界}

聚合内的一次修改需要整体提交。应用服务加载聚合、调用业务方法，再在事务中保存。提交前，业务规则必须成立；即使根对象和子对象存放在多张表中，也要一起成功或一起回滚。

一个事务修改一个聚合是设计取向，不是数据库限制。同一数据库可以原子修改多个聚合。不过，如果每条命令都要同时修改几个聚合，就需要重新检查：这些状态是否本来就应该属于同一边界。确实有独立生命周期的聚合，则可以通过异步流程协作，前提是业务允许中间状态。

跨服务时如何选择协调方式，见[分布式一致性](../distributed-data/invariants-to-consistency-strategy.mdx)。

## 5. 聚合之间的引用 {#聚合之间的引用}

聚合引用外部对象时，可以只保存 ID 或必要的业务快照，让外部对象独立变化：

```java
final class Order {
    private CustomerId buyerId;
    private List<OrderLine> lines;
}
```

`buyerId` 只标识购买人，订单不负责修改客户对象；`lines` 则属于订单内部，由订单根控制修改。

需要保存什么，取决于业务要用哪个时刻的信息。收货地址可以保存下单时的快照；需要当前会员等级时，则由应用层查询会员接口。这样，保存订单就不必连同整个客户对象一起保存。

## 6. 聚合规模与竞争 {#边界过大}

聚合越大，一次加载和保存涉及的状态越多，无关操作也越容易争用同一个版本或锁。

例如，把客户的全部订单放进一个聚合，两笔不同订单的修改都需要更新客户根版本。它们没有共同维护的业务规则，却会发生版本冲突。如果订单有独立生命周期，就应考虑让每笔订单成为独立聚合。这里讨论的是写入竞争，普通只读查询本身不会因此争用写锁。

## 7. 规则分散 {#边界过小}

把需要共同维护的状态拆开提交，会让部分失败破坏业务规则。例如，订单项数量已经保存，总额更新却失败，数据库中就会留下金额差异。

重复校验、固定的跨对象修改顺序，都是需要检查边界的信号：这些对象是否一直在共同维护同一条规则？判断依据是规则能否独立成立，表的数量与聚合数量没有固定比例。

## 8. 并发控制 {#并发控制}

聚合在内存中通过校验，不代表保存时仍然满足条件。两个请求可能同时读到旧状态，各自检查都成功，因此写入时还需要并发控制。

**乐观锁**是保存时检查版本是否仍与读取时一致的一种方式：

```sql
UPDATE orders
SET status = ?, version = version + 1
WHERE id = ? AND version = ?;
```

影响 1 行，表示版本匹配，本次更新成功。影响 0 行，表示记录不存在，或版本已经变化；调用方需要重新读取来区分原因。

子对象的修改也必须参与根版本检查，并与根版本更新放进同一事务。否则，即使根对象的更新被拒绝，子表仍可能留下旧状态产生的结果。竞争集中的热点命令，也可以考虑行锁或原子条件更新。

### 8.1 版本冲突与命令重放 {#版本冲突与命令重放}

版本冲突后，应在新状态上重新执行命令，不能只替换版本号。假设两个请求都读取订单版本 7：请求 A 取消订单，提交后版本变成 8；请求 B 确认订单，带版本 7 保存时影响 0 行。

B 应回滚本次事务，再重新加载订单。此时订单已经取消，确认命令应校验失败。如果只是把旧对象的版本改成 8 再保存，就会用确认状态覆盖合法的取消结果。

所以，允许重试的命令需要重新校验并计算结果。若命令涉及外部扣款等副作用，还要用业务幂等标识避免重复执行。

## 9. 常见问题 {#常见问题}

### 9.1 一个聚合只能对应一张表吗？ {#聚合与表的映射}

不是。一个聚合可以映射到多张表，只要仓储按聚合边界整体保存。报表查询也不必照搬写入模型，可以使用专门的读取模型组织数据。

### 9.2 领域事件应该在事务提交前还是提交后处理？ {#领域事件与提交时机}

要看事件影响的范围。用于本地规则协作的内部领域事件可以在事务内处理；跨服务事件应在提交后发布，避免通知其他服务一个尚未成功提交的结果。怎样保证提交后仍能可靠交付，见[Transactional Outbox 与 CDC](../distributed-data/outbox-cdc-reliable-events.mdx)。

## 10. 面试题 {#面试题}

### 10.1 怎样确定聚合边界，聚合过大或过小分别有什么问题 {#aggregate-boundaries}

<summary>参考回答</summary>

**聚合边界由必须原子维护的不变量决定。**

订单项和订单总额需要共同保存。聚合根提供修改入口，事务保证整体提交。跨聚合引用使用 ID 或必要快照。

过大的聚合增加加载量和版本竞争。过小的聚合让同一规则分散到多个提交步骤。独立生命周期有助于识别拆分点。并发写入还需版本条件或锁保护。跨聚合流程按实际一致性要求选择协调方式。

</details>
