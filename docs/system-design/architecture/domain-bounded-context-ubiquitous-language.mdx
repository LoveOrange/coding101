# 限界上下文

**限界上下文**是一套业务模型和术语含义成立的范围。例如，同样叫“客户”，会员业务关心等级和权益，结算业务关心签约主体和账期。两边可以识别同一个人，却不必共用同一套字段和规则。

设计上下文边界，要能解释哪些概念在内部保持一致、跨边界时怎样交换信息。边界明确后，才能判断哪些代码应该一起变化，哪些模型可以独立演进。

## 1. 面试核心 {#core}

- 子域划分的是**业务问题**，限界上下文划分的是**模型的适用范围**，两者观察的角度不同。[卡](#ddd-bounded-context)
- 统一语言让领域专家与开发者在同一上下文内使用**含义一致的术语**。同一个词在别处改变含义，是识别边界的线索。
- 同一客户 ID 可以跨上下文复用，但**共享身份不要求共享模型**，各方仍可保留自己的字段和规则。
- 防腐层需要**转换外部模型的业务含义**，避免把外部状态直接当成本地状态使用。[卡](#anti-corruption-semantics)

## 2. 领域与子域 {#领域与子域}

**领域**是软件需要处理的业务范围，**子域**是其中一部分业务问题。例如，电商可以分为商品、交易、库存和履约等子域。

子域可以按业务价值区分。核心子域承载产品的差异，值得投入专门建模；支撑子域帮助核心业务运行；通用子域可以评估成熟方案，例如身份认证。这种划分帮助团队决定把建模精力放在哪里。

**领域驱动设计**（DDD）用业务语言表达模型和规则。规则复杂、概念容易混淆时，这样做能帮助开发者理解业务；简单的增删改查则可以直接用事务脚本，也就是在一个过程里完成用例，不必为了套用模型增加对象。

## 3. 限界上下文 {#限界上下文}

限界上下文让一套模型只对明确的业务范围负责。以“客户”为例：

- 会员模型记录等级、积分和权益。
- 订单模型记录购买人 ID 和下单资格。
- 结算模型记录签约主体和账期。

三者可以共享客户 ID，但各自解释字段和维护规则。若强行共用一个全局 `Customer`，会员规则和结算规则就会挤在一起，调用方需要用条件分支区分当前场景。让模型分别归属上下文，可以保留它们真正需要的含义。

子域描述业务要解决什么，上下文描述用哪套模型解决问题。上下文可以先实现为进程内模块；是否需要独立部署，还要评估[微服务架构](./microservice-splitting-benefits-costs.mdx)中的收益和成本。

## 4. 统一语言 {#统一语言}

**统一语言**是业务人员与开发者在同一上下文中共同使用、含义一致的词汇。这些词应贯穿需求、验收条件、类名和接口，日志、错误码与运行手册也应沿用。

业务说“确认订单”，代码就可以提供 `confirm()`，在方法内检查订单状态和确认条件。相比之下，`updateStatus(3)` 只表达改了一个数，调用方还要另行查明 `3` 是什么、允许何时修改。

统一语言只在对应上下文内要求一致。跨边界时，要通过上下文名称和接口约定说明含义，不能因为字段同名就认为规则相同。

## 5. 边界识别 {#识别边界}

边界需要结合业务规则和实际变化来判断。可以沿一条完整业务流程检查五类信号：

1. 哪些规则由同一领域专家解释。
2. 哪些代码总是因同一个需求一起修改。
3. 哪些状态必须一起成功或一起失败。
4. 同一个术语在哪里改变了含义。
5. 谁负责决定数据定义和接口如何演进。

这些信号要放在一起看。共同事务只能提供一部分证据，一个上下文仍可包含多个独立聚合。需求变化后，也要重新检查边界是否仍符合实际的修改范围。

## 6. 上下文之间的协作 {#上下文之间的协作}

上下文通过明确的契约交换信息。**上下文图**记录谁依赖谁，以及双方怎样集成。提供信息的上游可以发布稳定 API 或业务事件，下游按约定使用这些信息，必要时先转换成本地模型。

**共享内核**是两个上下文共同维护的一小部分模型。共享范围越大，一次修改需要双方协调的地方就越多。因此，无论选择共享模型还是接口集成，都要明确字段含义、版本和失败时的行为。

### 6.1 防腐层与语义转换 {#防腐层与语义转换}

**防腐层**是将外部模型转换为本地模型的适配层，目的是让本地规则不依赖外部系统的表达方式。

例如，旧系统的 `status=2` 表示款项已授权，还没有完成扣款。新系统应把它映射为“已授权”，并保留待扣款状态。如果只按字段名把它映射成“已支付”，履约就会在尚未扣款时提前开始。

因此，转换要覆盖单位、状态和错误含义，无法识别的状态应进入异常处理。本地业务规则仍由本地模型负责，防腐层只负责把输入解释清楚。

防腐层可以是进程内适配器，也可以独立部署。后者会增加网络延迟和运维工作。无论怎样部署，都需要用契约测试验证双方的约定，尤其要覆盖旧接口语义发生变化的情况。

## 7. 订单协作示例 {#订单场景示例}

取消订单由订单上下文判断是否允许，并保存取消结果。之后，库存根据取消事件释放预占，支付判断需要退款还是撤销授权，会员按最终结果调整积分。

同一次取消，在各上下文中触发的规则不同。订单负责“能否取消”，库存负责“释放哪些预占”，支付负责“退回或撤销哪笔款项”。各方通过事件和接口取得所需信息，再用自己的模型完成后续工作。

## 8. 常见问题 {#常见问题}

### 8.1 领域服务和应用服务分别负责什么？ {#领域服务与应用服务}

**领域服务**承载不自然归属单个实体的业务规则；**应用服务**负责组织一次用例的执行，包括鉴权、事务和调用顺序。区分时看它是在决定业务上能否这样做，还是在安排这次操作怎样完成。简单查询没有这类复杂性时，无需为它创建空壳对象。

### 8.2 每个上下文都需要独立的数据库吗？ {#数据所有权与物理数据库}

不需要。多个上下文可以共用数据库实例，但数据定义和写入权仍要归属明确。即使表放在同一个数据库中，也应分清谁能修改它、谁负责迁移，避免一个上下文绕过另一个上下文的规则直接写表。
