# 绞杀者模式

**绞杀者模式**是让新旧系统并存，逐步把业务能力从旧实现迁到新实现的迁移方式。请求先经过稳定的入口，再按规则进入新系统或旧系统，直到旧路径可以退出。

这种方式把一次整体替换拆成多次可验证的迁移，但每一步仍要处理契约兼容、数据同步和回退。迁移方案是否可靠，取决于切换后数据由谁写入，以及出现问题时旧系统能否接回业务。

## 1. 面试核心 {#core}

- 绞杀者模式通过**稳定入口逐条迁移业务路径**，让新旧实现可以并存和验证。[卡](#strangler-migration)
- 契约演进遵循 expand–migrate–contract：**先扩展兼容，再迁移调用方，最后删除旧版本**。
- 数据切换需要**明确写入权和同步位置**，才能确认旧侧的最后写入已经到达新侧。[卡](#migration-write-handoff)
- 影子流量用于比较结果，灰度流量用于验证**真实业务及其副作用**，二者提供的证据不同。
- 回退需要同时满足**流量可切回、数据可接回**；旧路径和兼容结构退出后，迁移才算结束。

## 2. 迁移切口 {#选择迁移切口}

第一条迁移路径应当边界清楚、调用方可枚举、影响范围可控，并有可测量的收益，例如缩短发布耗时或实现独立扩容。

切口可以是一组 URL、一个租户或一类后台任务。计划中应写清新旧系统各自负责什么、依赖哪些数据、怎样验证结果，并在上线前确定成功指标和回退条件。这样才能判断何时扩大范围，何时停止迁移。

## 3. 路由入口 {#路由入口}

稳定的路由入口负责选择新旧实现，让调用方不必随每次迁移一起修改。它可以由代理、网关或 facade（对外统一接口）承担，根据请求特征分流。路由规则需要记录版本，并支持快速恢复。

入口本身也要有足够容量和高可用能力。绕过入口直连旧系统的后台任务同样需要列入迁移清单，否则部分业务会一直留在旧路径。若新旧系统对字段的理解不同，还需要做语义转换，见[限界上下文](./domain-bounded-context-ubiquitous-language.mdx#防腐层与语义转换)。

## 4. 契约演进 {#契约演进}

契约变更应留出新旧调用方同时运行的阶段。expand–migrate–contract 把这个过程分成三步：

1. 扩展契约，让新系统同时兼容旧字段和新字段。
2. 分批迁移调用方，并记录各版本的使用情况。
3. 确认旧消费者退出后，再删除兼容结构。

新增字段要说明缺省时代表什么，扩展枚举要测试旧消费者是否能处理新值。数据库变更也需要经历加列、回填、切换和删列，避免旧代码仍在运行时就删掉它依赖的结构。

## 5. 数据迁移 {#数据迁移}

迁移期间，同一业务数据必须有明确的写入方。全量回填复制已有数据，增量同步跟上持续发生的变化，两者需要衔接，才能得到完整结果。CDC 的交付边界见[Transactional Outbox 与 CDC](../distributed-data/outbox-cdc-reliable-events.mdx)。

复制前要对齐主键、金额单位和状态含义。每批记录处理范围、进度和校验结果；重复回放要能幂等处理，发现差异则进入对账任务。只知道“复制完成”，无法说明业务含义也保持一致。

### 5.1 写入权交接与增量位置 {#写入权交接与增量位置}

写入权交接需要一个可以核对的截止位置。直接让应用同时写新旧库，会产生两次独立提交：一边成功、另一边失败时，两侧数据就会分叉，回退也可能缺少数据。

一种可控方案是在切换窗口暂停目标范围内的业务写入，等待旧库的在途事务完成，再记录最后需要同步的位置。新库追到该位置并通过校验后，才接管写入。后台任务和回调也要服从这次交接，否则旧库仍可能继续产生新数据。

如果切换后还需要保留回退能力，就要准备反向同步，让旧库追平新系统产生的写入，并确保旧代码能理解新状态。不可逆的数据变更应安排在回退窗口关闭后。

## 6. 影子流量 {#影子流量}

**影子流量**是把真实请求复制给新路径执行，但仍把旧路径的响应返回给用户。这样可以比较新旧查询、计算和规则的结果，而不直接让新结果影响用户。

新路径中的扣款、通知和消息发布等副作用必须隔离，避免一次真实请求执行两遍。比较时还要规范化时间戳、随机 ID 等预期差异。影子流量无法完整验证真实写竞争和下游反馈，这些还需要灰度流量验证。

## 7. 灰度发布 {#灰度发布}

**灰度发布**是先让一部分真实业务由新系统处理，验证后再扩大范围。可以按租户、地域或业务键分组，但同一业务流程应保持路由稳定，避免步骤来回切换到新旧系统。

每一批都要观察成功率、延迟和数据差异，也要检查消息积压、资源余量和人工处理量。达到预先约定的样本量和观察期后，才能判断是否继续扩大范围。

## 8. 回退 {#回退}

回退不仅要把请求送回旧系统，还要让旧系统接得住新路径已经产生的数据和未完成流程。旧实现必须能读取这些状态，并明确由谁继续处理。

回退演练应验证流量、数据和依赖分别需要多久恢复。已经发送出去的事件不会随路由回退而消失，需要按业务语义继续处理或补偿。确实无法撤销的变化，则需要向前修复，让当前状态重新满足业务规则。

## 9. 退出条件 {#退出条件}

迁移完成的标志是旧路径可以安全退出。下线前需要确认：

- 目标流量已稳定运行约定周期。
- 数据差异已修复或有明确解释。
- 旧接口、事件和表已无消费者。
- 告警、运行手册和维护责任已转交。
- 回退窗口已关闭，旧资源可以下线。

如果一直保留双轨，新旧契约兼容和数据同步也会一直产生维护成本，因此退出条件应当是迁移计划的一部分。

## 10. 面试题 {#面试题}

### 10.1 怎样把一个遗留单体逐步迁移为新服务 {#strangler-migration}



**题型**：综合题

**考察重点**

- 业务切口、路由入口和防腐层。
- 契约兼容、数据所有权和分批校验。
- 灰度、回退和旧路径退出条件。

**相关内容**：[迁移切口](#选择迁移切口)至[退出条件](#退出条件)。

<details>
<summary>参考回答</summary>

**遗留系统可通过稳定入口逐条迁移业务路径。**

候选能力需要边界清楚，收益可测。契约先扩展兼容，再迁移调用方，最后删除旧版本。数据以唯一写入方和可核对的同步位置衔接。

影子流量比较结果，灰度承接真实业务。回退既要恢复路由，也要保证旧系统理解新数据。稳定观察、数据校验和旧消费者退出后，才能删除旧路径。

</details>

### 10.2 新旧系统切换写入权时，怎样避免漏数据并保留回退能力？ {#migration-write-handoff}

**考察重点**：在途事务、同步位置与反向兼容。

**相关内容**：[写入权交接与增量位置](#写入权交接与增量位置)。

<details>
<summary>参考回答</summary>

**切换需要把旧侧的最后写入与新侧接管衔接起来。**

可暂停目标范围写入，并等待在途事务结束。新侧追平记录的位置并校验后，再开放写入。回退还需旧侧追平新写入，并支持新数据格式。

</details>
