# 微服务架构

**微服务架构**按业务能力把系统划分为可独立部署的服务。拆分的价值在于让某项能力可以单独发布、扩容或限制故障影响，同时也会引入网络调用、跨服务一致性和额外的运维工作。

讨论微服务设计时，需要说明拆分要解决什么问题，以及如何证明收益足以承担这些成本。服务数量本身不能说明边界是否合理。

## 1. 面试核心 {#core}

- 服务按**业务能力和数据写入责任**划分，边界要能解释它负责哪些规则。[卡](#service-splitting)
- 独立部署需要**兼容契约、自动化测试和独立发布流程**，否则多个服务仍要一起发布。
- 远程调用超时只说明客户端没有及时拿到结果，**服务端可能已经执行成功**，重试必须考虑业务幂等。
- 拆分会增加**跨服务一致性、观测和运维成本**，需要与发布、扩容和隔离收益一起评估。
- 独立进程仍会通过同步等待传播故障，**超时和资源限制**才负责控制这部分影响。[卡](#service-fault-isolation)

## 2. 拆分目标 {#拆分目标}

拆分应针对一个可以测量的问题。例如，搜索需要单独扩容，订单希望提高发布频率，支付故障需要缩小影响范围，或者特定数据需要独立访问控制。

在拆分前记录发布频率、变更耗时、资源用量、故障影响和团队等待时间。拆分后再用同一口径比较，才能知道独立部署到底改善了什么。如果目标不明确，就难以判断增加的网络和运维成本是否值得。

## 3. 业务能力边界 {#按业务能力划分}

服务边界应包住一项明确的业务职责，以及执行它所需的规则和写入权。如果按控制器、业务逻辑、数据库访问等技术层拆服务，一次业务请求就必须跨越多个服务；按表拆分，也可能把需要共同成立的规则切开。

每个服务应有明确的接口，并由明确的团队负责代码、测试和发布。限界上下文提供模型边界的线索，但可以对应一个或多个部署单元。最终粒度要结合哪些能力一起变化、负载是否不同，以及团队能维护多少服务来决定。

## 4. 独立部署 {#独立部署}

独立部署要求一个服务更新时，调用方仍能按原有契约运行。因此，向后兼容的接口、自动化测试和独立发布流程需要一起具备。负载不同时，热点服务也可以单独增加实例。

如果每次需求都必须同时发布五个服务，就要检查哪些接口变更或共享数据迫使它们联动。部署包已经拆开，不代表变更也已经独立。

## 5. 网络调用的失败语义 {#网络调用的失败语义}

远程调用超时后，客户端无法仅凭超时判断服务端是否成功。例如，支付已经完成扣款，但响应没有及时返回，订单服务看到的仍是超时。此时重试需要业务幂等，保证重复请求不会再次扣款。

等待时间也需要按整条请求链分配，给每次下游调用设置合理上限。除此之外，服务还要用限流、熔断和有界队列控制负载。认证、证书、服务发现与链路追踪，也都成为拆分后需要维护的部分。

### 5.1 同步依赖与故障传播 {#同步依赖与故障传播}

同步等待会把下游故障传到上游。假设订单服务同步调用支付服务，支付变慢后，订单线程持续等待；线程池耗尽时，其他订单接口也无法获得线程，即使它们不调用支付，也会受到影响。

因此，调用方既要限制等待时长，也要限制并发调用数。超时预算应留出自身处理和返回结果的时间；重试要限制次数并设置退避，避免下游已经变慢，上游却继续增加请求。

失败后返回什么，还要看业务语义。支付结果尚不明确时，可以显示“处理中”，不能当作支付成功；推荐信息属于可选内容，可以返回默认结果。验证隔离效果时，应同时观察线程占用、请求延迟和业务结果。

## 6. 数据所有权与一致性 {#数据所有权与一致性}

每个服务应负责自己的数据定义、写入规则和写入入口。迁移阶段可以共用数据库实例，但仍要明确各张表由谁修改，否则一个服务的内部变更会直接影响其他写入方。

跨服务查询可以调用多个 API 汇总结果，也可以使用读取投影，即根据业务数据或事件整理出的查询副本。跨服务修改则需要按业务规则选择协调方式，见[分布式一致性](../distributed-data/invariants-to-consistency-strategy.mdx)。

## 7. 服务数量的运维成本 {#服务数量的运维成本}

每增加一个服务，就多了一组需要维护的构建、配置、监控、安全更新、容量计划和故障响应流程。这些工作不会因为服务流量小就消失。

服务增多后，要同时维护更多契约版本和测试环境，低流量服务仍需保留运行副本，值班人员也要理解更大的依赖关系。因此，自动交付和集中观测能力需要跟上拆分规模。

## 8. 拆分粒度 {#拆分过细的信号}

长同步调用链、频繁联动发布、大量跨服务事务，都是需要重新检查拆分粒度的信号。它们说明一次业务变化仍跨越许多边界，却已经承担了远程协作的成本。

如果一个单表增删改查服务没有独立变化的价值，或者两个服务长期共同修改和发布，可以考虑合并部署。保留独立服务时，则应能验证它确实带来了故障隔离或单独扩容的收益。

## 9. 渐进式拆分 {#渐进式拆分}

可以先在单体内明确模块接口和数据所有权，再挑选独立部署或扩容收益明确的模块。这样能先验证业务边界，再承担远程调用的成本。

迁移时选择一条可验证的业务路径，逐步放入真实流量，观察结果后再扩大范围。具体流程见[绞杀者模式](./strangler-migration-compatibility-rollback.mdx)。

## 10. 面试题 {#面试题}

### 10.1 微服务应该怎样拆，拆得太细会有什么问题 {#service-splitting}



**题型**：综合题

**考察重点**

- 拆分目标和业务边界。
- 独立部署、扩缩容与故障隔离的收益。
- 网络、数据、测试、运维和组织成本。

**相关内容**：[拆分目标](#拆分目标)至[渐进式拆分](#渐进式拆分)。

<details>
<summary>参考回答</summary>

**微服务应按业务能力和数据所有权划分。**

独立部署需要兼容接口与独立交付流程。独立扩容适合负载明显不同的能力。故障隔离还需超时、并发限制和降级。

拆得太细会增加同步调用、联动发布和协调成本。每个服务也会增加测试与值班负担。边界尚不清楚时，可先建立模块化单体。拆分后用发布频率、故障范围和资源成本验证收益。

</details>

### 10.2 服务已经独立部署，为什么下游故障仍会拖垮上游？ {#service-fault-isolation}

**考察重点**：同步等待、并发资源与降级语义。

**相关内容**：[同步依赖与故障传播](#同步依赖与故障传播)。

<details>
<summary>参考回答</summary>

**下游变慢时，同步等待会持续占用上游线程和连接，资源耗尽后故障就会扩大。**

超时限制等待时长，并发上限限制资源占用。有界重试避免继续放大下游负载。关键支付结果应显示处理中，可选推荐可以降级。

</details>
