# 配置中心

**配置中心**集中保存和分发应用参数，并记录变更历史。动态配置可以在不重新部署代码的情况下改变行为，但“发布成功”不等于所有实例已经生效。要安全刷新，需要明确应用何时读取配置、如何校验和切换，以及失败后能恢复到什么状态。

## 1. 面试核心 {#core}

- 动态配置先在候选快照上校验，再**原子切换整份不可变配置**，避免请求读到新旧字段的混合状态。[卡](#safe-config-rollout)
- 发布版本记录配置内容，**实例实际生效版本才说明应用进度**，收到更新不代表已经使用。
- 配置回退影响后续行为，**已经造成的数据变化需要单独修复**。
- 环境变量引用 ConfigMap 时，现有进程保留原值，**更新需要重建 Pod**。[卡](#configmap-refresh-modes)
- ConfigMap 普通卷最终会更新文件，但**应用仍要重新读取并应用配置**；`subPath` 挂载不接收更新。

## 2. 启动配置与运行时配置 {#启动配置与运行时配置}

配置能否动态生效，由应用的读取和应用方式决定。JVM 启动参数在进程创建时读取，不能只改配置中心就改变已有进程；限流阈值、功能开关则可以由应用实现运行时刷新。

每项配置都要声明读取时机、默认值和合法范围。动态项还要说明修改后会产生什么影响、是否需要替换连接池等资源。协议和表结构变化涉及新旧版本兼容，仍要按迁移流程处理。

## 3. 完整快照 {#完整快照}

**配置快照**是一份完整、对应某个版本的配置内容。一种分发方式是通知客户端检查更新，再由客户端拉取快照；定期核对版本，可以补上漏掉的通知。

客户端先在候选快照上完成解析和业务校验，通过后再原子替换引用。一次请求持有同一份不可变快照，就不会执行到一半又读到另一版参数。如果逐字段修改共享配置，请求可能恰好读到“一个字段已更新、另一个还没更新”的中间组合。

有可靠增量协议时，也可维护版本化增量。恢复失败则重新获取完整状态。

## 4. schema 校验 {#schema-校验}

**Schema** 描述配置允许的结构，例如字段类型、必填项、取值范围和字段之间的约束。发布前先按它校验，再检查引用的资源是否存在、当前应用版本是否支持这些配置。

客户端仍要再次校验，因为滚动发布期间可能同时运行不同版本。校验失败时保留旧快照并报告原因。结构合法也不代表值适合生产负载，例如阈值虽然在允许范围内，仍需要通过灰度观察实际影响。

## 5. 版本与审计 {#版本与审计}

版本记录需要同时覆盖发布和生效两个阶段。发布记录保存内容摘要、环境、作者和原因；每个实例则暴露已接收的配置版本与实际生效的版本。

查看各实例的生效版本分布，才能定位哪些还没更新。配置中心返回发布成功，只说明它接受了变更，不能代替应用端的确认。

版本语义由协议定义。自建系统可用单调发布序号，避免按客户端时间排序。

## 6. 配置灰度 {#配置灰度}

配置灰度按影响对象分组。整套运行参数可以按集群或实例标签分批应用；需要用户级功能开关时，则由应用按稳定的用户标识选择配置，避免同一用户反复切换行为。

高风险参数一次改变一个主要变量。观察错误、延迟和资源占用后再扩大范围。放量判断见[灰度发布](./canary-traffic-tagging-rollback.mdx)。

## 7. 回滚 {#回滚}

在不可变发布模型中，回滚是用新的发布标识重新发布旧内容，并记录它回退了哪次变更。这样既恢复配置，也保留完整审计历史。

回退前要检查旧值是否仍适配当前代码。如果配置已经触发数据转换，恢复参数不会把数据自动变回去，兼容读取和补偿需要另行处理。

## 8. 密钥管理 {#密钥管理}

密钥需要独立的存储、权限和审计。配置中心可以只保存密钥引用，或提供隔离的密钥管理能力，避免普通配置的查看权限同时暴露凭据。

配置 diff、日志与诊断接口需脱敏。轮换时允许新旧凭据短期并存。所有实例完成切换后，再撤销旧凭据。

## 9. 刷新监控 {#刷新监控}

监控接收延迟、应用延迟、拒绝原因和版本分布。业务指标可关联到配置版本。

连接池等资源不能只改一个数就算刷新完成。要先构造并验证新对象，再切换引用，等旧资源上的在途使用结束后关闭。部分刷新失败时，按预设策略回退或让实例停止接收新请求。

## 10. ConfigMap 刷新方式 {#configmap-刷新方式}

ConfigMap 更新后能否被应用看到，取决于 Kubernetes 如何把配置交给进程，以及应用是否重新读取：

| 读取方式 | 更新行为 |
| --- | --- |
| 环境变量 | 现有进程保持原值，需要重建 Pod |
| 普通卷挂载 | kubelet 最终更新文件，应用自行重读 |
| `subPath` 挂载 | 现有挂载不接收 ConfigMap 更新 |
| 直接调用 API | 应用订阅或轮询，并负责应用新值 |

普通卷中的文件更新也不是瞬时完成的，会受到 kubelet 同步和缓存传播延迟影响。即使文件已经变了，只在启动时读取一次的应用仍使用旧配置；尚未实现动态重载时，可以通过滚动重启重新读取。

## 11. 常见问题 {#常见问题}

### 11.1 配置中心不可用，新实例还能启动吗？ {#启动时的配置可用性}

如果有可信、仍有效的本地快照，普通参数可以支持离线启动。授权和密钥配置还要检查有效期限；缺少有效安全配置时，实例应保持未就绪，不能为了启动成功而跳过校验。

### 11.2 线程池参数都能直接动态修改吗？ {#动态线程池配置}

不能一概而论，要看具体实现。线程数、队列和拒绝策略需要一起校验；固定容量队列要通过替换才能改变容量。调整后观察活跃线程数、排队任务数、拒绝次数和任务耗时，确认新配置没有把压力转移到别处。

发布按稳定分组推进，指标关联配置版本。回滚重新发布旧内容，并检查代码兼容性。已经触发的数据变化通过对账或补偿处理。
