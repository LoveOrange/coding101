# 重试

重试用于恢复短暂故障，也会增加下游负载。本文负责错误分类、退避与重试预算。

## 1. 面试核心 {#core}

- **多层放大。** 多层各尝试 3 次时，四层最深调用上界为 `3⁴=81` 次。[卡](#retry-amplification)
- **退避抖动。** Full jitter 在当前指数退避上限内随机选择等待时间。
- **重试预算。** 单请求次数与系统级重试预算共同约束额外负载。
- **服务端等待建议。** `Retry-After` 支持秒数与 HTTP 日期，等待仍需服从总预算。[卡](#retry-after-budget)
- **并行备份请求。** Hedging 并行发送备份请求，消耗额外容量。

## 2. 可重试错误 {#可重试错误}

短暂连接错误与部分服务端错误可作为候选。参数错误、权限不足和确定性代码错误应直接失败。

是否重试还取决于接口语义与结果是否已提交。超时只能说明结果未知。持续过载时，继续发送会延迟恢复。

## 3. 写操作重试 {#写操作重试}

写请求需明确重复副作用边界。稳定请求标识与结果恢复见[幂等键](./idempotency-keys-safe-retries.mdx)。

协议声明为幂等的方法，也需实现对应语义。POST 可以通过业务幂等契约支持安全重发。

## 4. 指数退避 {#指数退避}

退避上限随失败次数增长，再受 cap 截断。

```text
a = 0 表示第一次重试
backoff = min(cap, base × 2^a)
```

例如 base 为 100 ms，cap 为 1 s。前三次重试上限为 100、200、400 ms。退避等待也计入请求总预算。

## 5. 抖动 {#抖动}

无抖动退避会使大量客户端同步醒来。Full jitter 从 `[0, backoff]` 采样等待时间。

实例需避免使用相同随机序列或固定整秒调度。仅有随机等待仍需限制总次数和额外流量。

## 6. 尝试次数 {#尝试次数}

总尝试 3 次表示首次调用加两次重试。配置与指标应明确是否包含首次调用。

四层各尝试 3 次时，最深调用上界是 `3⁴=81`。总时限与提前成功会减少实际次数，但过载时仍需防放大。

选择一层承担主要业务重试。其他层仅保留语义明确的局部恢复。

## 7. 重试预算 {#重试预算}

单请求上限无法控制全系统额外流量。重试预算可以约束总重试比例或并发数。

例如成功请求补充 retry token，重试消耗 token。错误持续时额度耗尽，请求快速失败。预算按下游或路由统计，避免一个故障耗尽全部配额。

## 8. Hedged request {#hedged-request}

Hedging 在首个请求变慢后，并行发送备份请求。它适合有独立副本与额外容量的幂等读取。

首个可接受成功结果返回后，取消剩余尝试。取消仍需下游配合。整体过载时新增备份会进一步消耗容量。

应限制 hedging 比例与并发，并观测真实放大倍数。

## 9. 故障注入验证 {#故障注入验证}

注入 reset、延迟、限流和局部实例故障。分别统计原始请求、attempt、成功率和 P99。

还需检查全体过载时预算是否停止追加请求。关闭重试后若系统恢复，应复查放大路径。取消后的在途数量也属于验收指标。

## 10. Retry-After 与剩余预算 {#retry-after-与剩余预算}

`Retry-After: 2` 表示等待 2 秒。HTTP 日期形式表示可以再次尝试的时间点。

客户端将服务端建议与本地退避共同纳入计划。一种策略是至少等待两者较大值，再加入有限抖动。日期形式还需考虑时钟偏差与解析失败。

例如总预算只剩 500 ms，而建议等待 2 秒。此时应结束自动重试，并返回明确结果。为赶 deadline 提前发送会破坏服务端的恢复节奏。

## 11. 常见问题 {#常见问题}

### 11.1 5xx 的重试条件 {#5xx-的重试条件}

5xx 只是服务端错误类别。确定性缺陷、资源过载和短暂故障需要分别处理。仅有状态码不足以证明下一次尝试有价值。

### 11.2 实例切换与副作用 {#实例切换与副作用}

切换实例可绕过局部故障。原实例已提交而响应丢失时，新实例仍需去重。重试安全性依赖业务契约。
