# 限流

**限流**是通过速率或并发上限，控制进入系统的工作量，避免请求超过资源承受能力。选算法之前，先确定要限制的是每秒请求数、同时处理的请求数，还是某个租户的配额。

这些限制不能互相替代。同样是 1000 QPS，请求耗时从 20 ms 变成 2 s 后，系统中积压的工作会大幅增加，即使速率没有超过阈值，线程池和连接池也可能耗尽。

## 1. 面试核心 {#core}

- 固定窗口实现简单，但**跨相邻窗口边界时会允许接近两倍阈值的短突发**。
- 滑动日志保存请求时间，能**精确统计最近窗口**；滑动计数器用较少状态换取近似结果。
- 排队式漏桶**平滑输出**，令牌桶则在长期速率受控的前提下**允许桶容量内的突发**。[卡](#rate-limit-algorithms)
- 稳定系统中，**平均在途数等于吞吐率乘平均逗留时间**，所以只限制 QPS 不能保证并发占用不变。[卡](#rate-concurrency-little-law)
- 分布式配额要**原子检查并扣减**，每个实例还要有独立于中心服务的本地资源上限。[卡](#distributed-rate-atomicity)

## 2. 固定窗口 {#固定窗口}

**固定窗口**将时间划成固定区间，例如每秒或每分钟，在区间内累计请求数，达到上限就拒绝。它实现简单，但窗口交界处仍可能集中放行大量请求。

例如每秒允许 100 次，前一秒末尾通过 100 次，后一秒开头又通过 100 次。两个固定窗口各自都没超额，跨越边界的很短一段时间内，却接近 200 次。

因此，固定窗口适合粗粒度配额。需要更平滑地保护资源时，要选用其他算法，或叠加并发上限。

## 3. 滑动窗口 {#滑动窗口}

**滑动窗口**随当前时间向前移动，统计最近一段时间内的请求。实现时可以选择保存完整记录，也可以保存分段计数：

- 滑动日志保存最近窗口内各次请求的时间，计数精确，但请求越多，需要保存的状态越多。
- 滑动计数器把时间分成小格，每格保存计数，用更少状态近似窗口内的请求量。

滑动计数器可以累计整格，也可以对边界格加权。加权依赖格内流量分布的假设，因此仍有误差。格子更细可以降低时间粒度误差，但也会增加状态成本。

## 4. 漏桶 {#漏桶}

**排队式漏桶**让请求先进入有界队列，再按固定速率取出处理，队列满时拒绝。它把输入的突发转成较平滑的输出，代价是请求需要等待。

因此，队列既要限制长度，也要限制最长等待时间，否则请求虽然最终得到处理，却可能早已超过调用方的时限。漏桶还有计量判定式实现，未必真的排队；本文讨论的是排队整形这一种。

## 5. 令牌桶 {#令牌桶}

**令牌桶**按速率 r 补充令牌，最多积累 B 个。请求取得并消耗足够令牌后立即通过，没有令牌时等待或拒绝。

初始桶满时，时间 t 内最多放行约 `B + r × t` 个单位：B 是积累下来的突发额度，r 控制长期补充速度。这解释了为什么令牌桶允许短时集中到达的请求，而不必像排队式漏桶那样逐个匀速放行。

额度单位也可以按成本设计。昂贵请求消耗多个令牌，使扣减量与 CPU、查询量等需要保护的资源更接近。

## 6. 并发限制 {#并发限制}

**并发限制**直接约束同一时刻正在处理或排队的工作量。速率相同的情况下，请求停留得越久，同时留在系统中的请求就越多。

在稳定系统中，Little's Law 用 `L = λ × W` 表达这个关系：L 是平均在途数，λ 是平均吞吐率，W 是平均逗留时间。

例如吞吐保持在 1000 次/秒，平均耗时 20 ms 时，L 为 20；平均耗时变成 2 s 后，L 就是 2000。速率限制没有变化，系统需要承受的在途请求却增加了。

计算必须使用同一系统边界下的平均值，不能把 P99 直接代入。得到估算值后，还要结合突发、资源上限和压测结果确定实际额度。

## 7. 限流键 {#限流键}

**限流键**决定哪些请求共用一份配额，可以按可信主体、租户或 API 划分。身份来源要可靠：共享 IP 可能让同一网络中的用户相互影响，直接信任可伪造的 header 则可能让调用方绕过限制。

入口全局上限与租户配额可以一起使用，高成本接口再单独计量。每个实例也需要本地并发和队列上限，避免整体配额尚有余量时，某个实例已经被占满。

限流键自身也消耗存储，因此要限制状态数量和保留时间，不能让大量低频键无限积累。

## 8. 分布式限流 {#分布式限流}

多个实例共享配额时，集中计数容易统一总量，但每次判断都增加一次远程依赖。把额度分配到节点本地可以降低延迟，代价是需要协调额度的发放和回收。

严格预分配只发放尚未占用的额度，安全回收并避免重复发放，可以保持总上限。先在本地放行、再异步统计纠偏的方案，则允许短时间超额。选择时要明确业务能否接受这种误差。

中心服务故障时，可以按接口风险拒绝请求，或退回保守的本地额度。无论哪种策略，本地并发上限都应独立生效，保护实例自身资源。

## 9. 限流响应 {#限流响应}

拒绝响应需要告诉调用方发生了什么，以及是否适合稍后重试。调用方超额可以返回 429，并附 `Retry-After`；整体服务临时过载也可以用 503 表达，具体语义由接口契约说明。

选择排队时，还要检查剩余时间。如果预计等待已经超过请求预算，就直接拒绝，不能为了削峰而无限延长队列。

## 10. 原子扣减与失效 {#原子扣减与失效}

检查额度和扣减额度必须作为一个原子操作执行。假设只剩一个名额，两个请求分别先读取再写回，它们可能都读到 1，并同时通过。

Redis Lua 可以把检查、计数和过期设置放在同一次执行中，避免这种并发竞态。脚本应保持短小，否则会长时间阻塞 Redis。

固定窗口的 TTL 应覆盖到窗口结束。如果每次请求都把 TTL 续成一个完整窗口，边界就会被不断推迟。原子执行也不保证故障转移后状态仍然完整，状态丢失的影响要另行评估。

## 11. 常见问题 {#常见问题}

### 11.1 什么时候选令牌桶，什么时候选漏桶？ {#令牌桶与漏桶}

需要平滑输出、且请求可以等待时，考虑排队式漏桶。后端能承受一定突发、请求不适合排队时，令牌桶更合适，它同时约束突发额度和长期速率。

### 11.2 QPS 没超限，为什么线程池仍然饱和？ {#qps-与线程池饱和}

请求变慢会增加平均在途量，共享线程池还可能承接其他接口的任务。因此，除了 QPS，还要联合观察请求逗留时间、队列长度和连接使用量，判断资源究竟被谁占住。

## 12. 面试题 {#面试题}

### 12.1 固定窗口、滑动窗口、漏桶和令牌桶如何选择 {#rate-limit-algorithms}

**考察重点**

- 理解窗口边界、状态成本、平滑输出与突发额度。
- 理解速率限制和并发限制的差异。
- 理解全局配额、本地保护与失败策略。

**相关内容**：[固定窗口](#固定窗口)至[限流响应](#限流响应)。

<summary>参考回答</summary>

**粗粒度配额可以用固定窗口，精确统计最近窗口用滑动日志，平滑输出用排队式漏桶，允许受控突发则用令牌桶。**

滑动计数器介于精度与状态成本之间，用较少状态换取近似统计。选择时要看后端能否承受突发、请求能否等待，以及需要保存多少状态。

算法之外还要设置并发和队列上限。分布式配额需要明确精度、协调成本和故障策略，租户配额保护公平，本地额度保护单个实例。

</details>
