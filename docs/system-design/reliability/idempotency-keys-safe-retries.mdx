# 幂等键

**幂等键**是客户端为同一次业务意图提供的稳定标识。请求超时后，客户端不知道服务端是否已经完成操作，可以带着原 key 再次请求；服务端识别出这是同一次操作，就不再重复产生副作用。

实现的关键不只是保存一个 key，还要让它与业务结果保持一致，并能在进程崩溃后判断操作究竟完成了没有。

## 1. 面试核心 {#core}

- 同一次业务意图的重试**复用原 key**，用户发起另一笔操作时使用新 key。
- 用主体、接口和 key 确定唯一范围，再用请求摘要**识别同 key、不同参数的冲突**。
- 业务与幂等记录在同一数据库时，用本地事务**共同提交业务变化和幂等结果**。[卡](#safe-retry-payment-api)
- 外部调用不能靠本地事务一起提交，需要**持久化下游请求号并核对结果**。[卡](#idempotency-crash-window)
- 幂等记录的保留期决定**能够识别多久以前的重复请求**，清理后就失去了这层识别能力。

## 2. 幂等键的含义 {#幂等键的含义}

key 标识的是一次操作意图，不是某次网络发送。客户端创建、支付或退款时生成 key，响应丢失、结果未知时继续复用它；用户主动发起另一笔交易，才生成新 key。

服务端按调用主体、接口和 key 隔离记录。同一个 key 对应的请求摘要必须一致，否则调用方把金额改了却沿用旧 key，服务端就无法判断它想重试还是发起新交易。此时应返回参数冲突。

幂等约束的是业务副作用，不要求每次响应字节完全相同。接口可以约定重放首次结果，也可以返回当前资源状态，但需要明确告诉调用方采用哪种方式。

## 3. 原子占用 {#原子占用}

**原子占用**是让并发请求中只有一个取得执行权。幂等记录可以保存下面这些信息：

```text
principal, operation, key, request_hash,
status, resource_id, response, expires_at
```

对主体、操作和 key 建立唯一约束，由数据库决定哪个事务能够插入成功。如果只是先查询「不存在」，再无约束地插入，两个请求可能都查到不存在，随后各自执行业务。

发生唯一键冲突的请求读取已有结果，或根据状态返回「处理中」。唯一约束解决的是谁先取得执行权，操作失败后怎样恢复，还要看幂等记录与业务结果怎样提交。

## 4. 与业务结果一致 {#与业务结果一致}

业务数据和幂等记录在同一数据库时，可以用一个本地事务完成占用 key、修改业务和保存结果。三步一起提交，才能避免业务已经成功、幂等结果却没有保存的间隙。

以 MySQL 8.0 的读已提交（RC）和可重复读（RR）为例，普通读取看不到未提交记录，但这不代表另一个请求就能成功插入同一个唯一键。重复插入会按数据库机制等待或冲突，之后再读取已提交的结果。

如果执行进程崩溃导致事务回滚，业务变化和 key 的占用一起回滚，后续请求就可以重新竞争执行权。

## 5. 处理中的重复请求 {#处理中的重复请求}

长任务或外部调用不适合一直依赖一个本地事务等待完成，可以先提交 `PROCESSING` 状态。这样，重复请求能看到任务已经开始，并取得状态查询入口。

但提前提交「处理中」也留下了恢复责任：执行者可能在后续任一步崩溃。因此，需要持久化工作流，并由恢复任务核对实际结果。租约过期只能说明可以尝试接管，不能证明外部支付尚未发生。

接口可以约定返回 202 和查询地址。若选择短暂等待原请求完成，也必须受当前请求的总时限约束。

## 6. 返回结果 {#返回结果}

保存首次响应和保存资源 ID，提供的是不同的返回语义。前者便于稳定重放，但要处理敏感字段和已经过时的响应头；后者重新读取资源，返回的是它的当前状态。

失败结果是否保存，也要区分执行前与执行后。Stripe 会保存进入执行后的结果，包括 500；参数校验失败或并发执行冲突则不保存。其他接口需要声明自己的规则，不能只根据「返回失败」判断这次操作有没有产生副作用。

## 7. 保留时间 {#保留时间}

保留期应覆盖自动重试、消息重投和人工补单可能发生的时间范围。记录一旦被清理，相同 key 就可能被视为新请求。

需要长期防重的业务，可以另外保留业务唯一号。短 TTL 缓存适合加速查询，但不能代替持久化的权威约束，否则缓存过期或淘汰后，识别重复请求的能力也会随之消失。

## 8. 条件状态转换 {#条件状态转换}

状态更新还要检查操作发生前是否处于合法状态。例如下面的 SQL 只允许支付从 `AUTHORIZED` 转为 `CAPTURED`：

```sql
UPDATE payment
SET status = 'CAPTURED'
WHERE payment_id = ? AND status = 'AUTHORIZED';
```

应用根据影响行数判断本次是否完成转换。影响 0 行时，再查询当前状态，区分操作已经完成还是前置条件不满足。

这个条件只保护数据库中的状态推进。如果更新前后还有外部扣款，仍要用稳定请求号和结果核对保护外部副作用。

## 9. 客户端重试 {#客户端重试}

结果未知时，客户端复用原 key，并在预算内重试，退避方式见[重试](./retry-backoff-jitter-storms.mdx)。总时限耗尽后停止自动发送，转为查询状态，避免为了等到响应而无限追加请求。

修改金额等业务参数意味着发起新的操作意图，要与原操作区分。不能一边改变参数，一边要求服务端把它当作原请求的重试。

## 10. 外部调用的崩溃窗口 {#外部调用的崩溃窗口}

外部调用最难处理的情况，是下游已经成功、本地还没来得及记录就崩溃。例如支付成功后进程退出，恢复任务只能看到 `PROCESSING`，无法据此判断扣款失败。

因此，下游请求号要在调用前持久化。恢复时先用这个号码查询结果；如果下游支持幂等，也可以按原协议用同一号码重发。确认成功后，再补上本地完成状态。

下游既不支持查询，也不支持幂等时，自动补发可能造成重复扣款，未知结果应进入对账或人工处理。即使采用 Outbox 保证消息可靠投递，消费者也仍需去重，因为可靠送达不代表只会送达一次。

## 11. 常见问题 {#常见问题}

### 11.1 有唯一索引，为什么还需要幂等记录？ {#唯一索引与幂等记录}

唯一索引负责阻止重复占用，幂等记录还需要告诉后续请求：参数是否相同、任务是否完成、应该返回什么。业务唯一约束与接口幂等记录可以一起使用，分别保护业务规则和请求恢复。

### 11.2 只在 Redis 中保存 key，可以保护数据库写入吗？ {#redis-与权威状态}

如果 Redis key 和数据库事务分开提交，就可能一侧成功、另一侧失败，无法据此保证业务与幂等状态一致。缓存淘汰还可能缩短识别窗口。关键写入需要把权威状态保存在持久存储中，并明确它与业务提交的关系。

## 12. 面试题 {#面试题}

### 12.1 如何设计一个支持安全重试的支付接口 {#safe-retry-payment-api}

**题型**：综合题

**考察重点**

- 理解幂等键作用域、请求摘要和原子占用。
- 理解业务事务、处理中状态和外部副作用。
- 理解 TTL、状态查询与条件状态转换。

**相关内容**：[幂等键的含义](#幂等键的含义)至[客户端重试](#客户端重试)。

<details>
<summary>参考回答</summary>

**用稳定 key 识别同一次支付意图，并让重复请求能够查询或复用已有结果。**

服务端对主体、接口和 key 建唯一约束，再校验请求摘要，防止同 key 被用于不同参数。同库业务变化与幂等结果在同一事务中提交。

外部支付要在调用前持久化下游请求号。崩溃恢复时先核对支付结果，再更新本地状态；处理中请求返回查询入口。记录保留期覆盖重试和补单窗口，长期业务唯一号可以提供额外约束。

</details>

### 12.2 外部扣款成功后进程崩溃，PROCESSING 过期就能重新扣款吗？ {#idempotency-crash-window}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：外部结果未知、稳定请求号与恢复。

**相关内容**：[外部调用的崩溃窗口](#外部调用的崩溃窗口)。

<details>
<summary>参考回答</summary>

**不能直接重新扣款，应先用原请求号核对外部支付结果。**

`PROCESSING` 过期只说明本地没有及时确认完成，外部支付可能早已成功。恢复任务应查询持久化的下游请求号；下游支持幂等时，也可按同一号码重发。缺少查询和幂等能力时，未知结果进入对账或人工处理。

</details>
