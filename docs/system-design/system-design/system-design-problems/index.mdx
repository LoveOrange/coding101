# 系统设计题

系统设计题用于练习需求、数据流和故障处理。本文负责选题、复盘标准与短链接示例。

## 1. 面试核心 {#core}

- 系统设计方案由**功能、负载和质量目标共同约束**。
- **访问模式决定数据模型**，**成功确认点决定恢复语义**。
- 短链接以短码唯一定位映射，**随机短码仍需冲突检测**。[卡](#url-shortener)
- 可修改的短链使用临时重定向时，**仍需显式设计缓存策略**。[卡](#short-link-redirect-cache)

## 2. 题型与能力 {#题型与能力}

不同题目可以按主要考点选择：

| 题型 | 示例 | 重点 |
| --- | --- | --- |
| 内容读写 | 短链接、Pastebin | 标识、缓存与生命周期 |
| 时间线 | 社交动态 | 推拉成本、热点与分页 |
| 搜索采集 | 网页爬虫 | 调度、去重与恢复 |
| 交易账务 | 订单、支付 | 状态机、幂等与对账 |
| 实时通信 | 聊天、通知 | 连接、顺序与离线恢复 |

先练习边界清晰的题目。能够完整说明主链路后，再增加多地域与多租户约束。

## 3. 需求与规模 {#需求与规模}

每道题都应记录功能范围、负载和允许的失败结果。容量计算见 [容量规划](../capacity-slo-failure-model.mdx)。

复盘时检查数字是否影响了决策。例如保留期决定总存储量，热点决定缓存规模。缺少这些关联时，应补足假设与依据。

## 4. 主链路 {#主链路}

写链路标出持久化位置与成功确认点。读链路标出权威数据和派生结果。

复盘时沿箭头说明输入、输出和失败结果。每个组件都应对应一个具体瓶颈或隔离需求。

## 5. 数据模型与访问路径 {#数据模型与访问路径}

练习至少列出实体、主键、查询条件与排序。数据拆分的推导见 [数据拆分](../read-write-paths-hotspots-sharding.mdx)。

缓存需定义 key、TTL 与回源预算。消息需定义顺序范围、幂等和积压恢复。把这些参数写在设计图旁，便于核对。

## 6. 故障场景 {#故障场景}

沿主链路选择一个实际失败窗口。例如数据库提交后，响应在网络中丢失。结果未知的处理见 [写入结果未知与幂等](../interview-process.mdx#写入结果未知与幂等)。

复盘还要覆盖缓存故障、消费者暂停和主副本切换。每项都写明用户结果、保护动作和恢复验证。

## 7. 短链接案例 {#短链接案例}

短链接包含创建、跳转和过期管理。创建接口存储短码、目标 URL、所有者和到期时间。短码使用唯一约束，冲突后重新生成。

随机短码可降低枚举概率。私有链接仍需身份授权。创建接口校验 URL 协议，并对恶意目标做治理。

### 7.1 重定向与缓存 {#重定向与缓存}

301 表示永久迁移，302 表示临时迁移。短链允许编辑或撤销时，可选择 302 并控制缓存。状态码本身无法保证撤销立即生效。

严格撤销场景可使用 `Cache-Control: no-store`。允许缓存时，TTL 会形成旧映射的可见窗口。CDN、服务缓存和数据库都应执行一致的到期规则。

跳转接口在读取映射时检查到期时间。后台删除仅负责空间回收。统计通过异步事件处理，避免阻塞跳转。

### 7.2 标识空间与容量 {#标识空间与容量}

长度为 n 的 Base62 短码共有 `62^n` 种取值。随机生成仍会碰撞，唯一约束是最终保障。

百万日活只能说明用户规模。跳转次数、热点比例与映射保留期才决定容量。分片需求由测量后的单库瓶颈触发。

## 8. 练习题目 {#练习题目}

1. 短链接练习标识、缓存和过期处理。
2. [网页爬虫](./web_crawler/index.mdx)练习调度、去重和礼貌抓取。
3. 社交时间线练习推拉模型与热点用户。
4. 搜索建议练习前缀索引与更新延迟。
5. 订单与支付练习幂等、状态机和对账。
6. 即时消息练习长连接、顺序和多端同步。
7. 多租户系统练习权限、配额和资源隔离。

每次保留一页设计记录。下一轮改变规模或故障条件，检查原方案是否仍成立。

## 9. 常见问题 {#常见问题}

### 9.1 方案评价标准 {#方案评价标准}

评价围绕目标、决策依据与恢复路径展开。需求变化后，合理方案也会变化。

### 9.2 讨论范围 {#讨论范围}

核心需求优先，其次深入最重要的瓶颈。组件数量无需作为评价指标。

## 10. 面试题 {#面试题}

### 10.1 设计一个支持百万日活的短链接服务。 {#url-shortener}



**题型**：综合题

**考察重点**：短码唯一性、跳转路径与故障恢复。

**相关内容**：[短链接案例](#短链接案例)、[故障场景](#故障场景)。

<details>
<summary>参考回答</summary>

**方案以短码唯一映射到目标 URL。**

创建时校验目标，生成短码并用唯一约束处理冲突。跳转时读取映射，检查到期时间后返回重定向。

容量需由跳转峰值、对象大小和保留期估算。热门映射进入缓存，缓存故障时限制回源。统计异步处理，过期判断留在读取路径。

</details>

### 10.2 短链需要支持修改和撤销，应怎样选择重定向与缓存策略？ {#short-link-redirect-cache}

**考察重点**：301、302、缓存窗口与过期检查。

**相关内容**：[重定向与缓存](#重定向与缓存)。

<details>
<summary>参考回答</summary>

**可使用 302，并显式限制缓存。**

严格撤销要求可设置 `Cache-Control: no-store`。

允许缓存时，TTL 会延长旧映射可见时间。服务端每次命中映射也需检查到期时间。后台清理只负责释放空间。

</details>
