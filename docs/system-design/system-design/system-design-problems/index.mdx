# 系统设计题

系统设计题用于练习如何把模糊需求逐步转换成可以验证的容量、数据模型、组件边界和故障处理方案。

## 1. 先按能力选择题目

不同题目表面上是不同产品，实际考察的能力可以归为几类：

- **内容读写**：Pastebin、短链接和对象存储，重点是标识生成、读写路径与生命周期。
- **时间线与推荐**：社交动态、排行榜和推荐流，重点是推拉模型、热点与一致性。
- **搜索与采集**：网页爬虫、搜索引擎，重点是调度、去重、索引和失败恢复。
- **交易与账务**：支付、订单和预算系统，重点是状态机、幂等、对账与审计。
- **实时协作**：聊天、协作文档和通知，重点是连接管理、消息顺序和离线恢复。

第一次练习时选边界清楚的题目。能够稳定完成需求、估算、主链路和故障讨论后，再进入跨地域、多租户或强一致性要求更高的题目。

## 2. 每道题先写需求和规模

开始画组件前，先限定设计范围：

1. 用户必须完成哪些动作，哪些能力暂不设计。
2. 日活、峰值 QPS、读写比例和对象大小大约是多少。
3. 延迟、可用性、数据正确性和保留时间有什么要求。
4. 哪些故障需要继续服务，哪些结果允许延迟或降级。

估算的作用是帮助选择方案。例如，单库已经覆盖预计三年的数据量时，不需要为了展示知识点立即分片；如果单个热点作者的写入已经超过一台机器能力，就要在时间线方案里优先处理热点。

## 3. 用主链路连接高层组件

高层设计先覆盖最重要的一条写链路和一条读链路。为每个组件说明输入、输出、保存的状态和失败结果，避免只画出 API Gateway、Cache、MQ、Database 等名称。

以发布动态为例，需要说明：

- 请求怎样获得稳定 ID 并完成鉴权。
- 动态正文写入哪里，何时对调用方可见。
- 时间线在写入时推送，还是读取时聚合。
- 缓存未命中、消息重复和消费者失败怎样处理。

主链路能够闭合后，再引入异步化、缓存、分片或多副本。每增加一个组件，都要指出它解决的瓶颈和带来的新故障窗口。

## 4. 深入数据模型与访问路径

系统设计需要落到可以执行的读写操作。至少写出核心实体、主键、常用查询条件和排序方式，再判断关系型数据库、键值存储、搜索索引或对象存储分别承担什么职责。

数据分片要说明分片键、热点、跨分片查询和扩容迁移；缓存要说明 key、TTL、失效和回源保护；消息要说明顺序范围、投递语义、幂等和积压恢复。名称相同的组件，在不同访问模式下会得到不同设计。

## 5. 用失败场景检查方案

完成正常链路后，按依赖逐个询问：超时、重复、乱序、节点重启、网络分区和容量耗尽时会发生什么。重点检查：

- 调用方能否判断请求结果，是否可以安全重试。
- 已确认的数据是否可能在主从切换后丢失。
- 缓存或消息系统故障是否会把全部压力推向数据库。
- 后台任务能否从检查点恢复，人工修复是否可审计。
- 降级结果是否符合产品语义，恢复后如何验证正确性。

故障讨论要与前面的数据流对应。泛泛列出熔断、限流、重试和降级，不能证明方案在具体窗口内成立。

## 6. 练习题目

建议按以下顺序练习：

1. **Pastebin 或短链接**：标识、基础读写、缓存和过期。
2. **[网页爬虫](./web_crawler)**：任务调度、去重、礼貌抓取和恢复。
3. **社交时间线**：推拉模型、热点用户和分页一致性。
4. **搜索建议**：前缀索引、热词更新和低延迟读取。
5. **订单与支付**：状态机、幂等、消息和对账。
6. **即时消息**：长连接、会话顺序、离线消息和多端同步。
7. **多租户 SaaS**：租户隔离、配额、审计和成本归属。

每次练习保留一页设计记录，写下假设、容量、核心决策和没有解决的风险。下一次用不同规模或故障条件重新检查，而不是只记住某一张架构图。

完整的讨论顺序可以参考[系统设计面试](../interview-process)。

## 7. 常见问题

### 7.1 系统设计题有唯一答案吗

没有。题目中的需求、规模和约束会改变合理方案。评价重点是决策是否有依据、组件是否形成完整链路，以及候选人能否指出代价和验证方法。

### 7.2 面试时要把所有组件都讲一遍吗

不需要。先覆盖核心需求，再围绕题目中最重要的瓶颈深入。没有数据规模或故障场景支持时，机械加入缓存、队列和分库分表会让设计更难解释。

## 8. 面试题

### 8.1 设计一个支持百万日活的短链接服务

**出现公司**：阿里巴巴

**考察重点**

- 需求澄清、容量估算和短码生成。
- 读写路径、缓存、数据库索引与热点。
- 唯一性、过期、故障恢复和可观测性。

**相关内容**：[每道题先写需求和规模](#2-每道题先写需求和规模)至[用失败场景检查方案](#5-用失败场景检查方案)。

<details>
<summary>参考回答</summary>

先确认短链是否允许自定义、是否需要过期与统计，并估算创建 QPS、跳转峰值和保存年限。核心数据用短码作为唯一键，保存目标 URL、创建者和过期时间；创建接口生成不可预测且冲突可检测的短码，跳转接口按短码读取并返回重定向。读多写少时可以缓存热门映射，但数据库仍是权威来源。

设计还要说明恶意链接治理、缓存未命中保护、过期清理和统计异步化。数据量超过单库能力时按短码哈希分片，并提前规划扩容迁移。缓存或单个分片故障时限制回源并降级统计，恢复后用跳转成功率、P99 和数据校验确认服务正常。每一项扩展都应由前面的容量或故障目标触发。
