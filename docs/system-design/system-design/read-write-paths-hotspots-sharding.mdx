# 读写路径、热点与数据拆分

系统设计需要沿一条请求说明数据经过哪些组件、在哪里排队、何时持久化，以及读请求可以看到哪个版本。分片只有在单个存储边界已经成为瓶颈时才有价值，它同时会把查询、事务和迁移变成跨分片问题。

## 1. 写路径先确定成功条件

一次写入可能经过鉴权、幂等检查、分片路由、主副本、索引、缓存失效和事件发布。接口返回成功前到底等待哪些步骤，要根据不变量说明。

例如订单创建可以要求主数据库事务和 Outbox 一起提交，再异步更新搜索；若搜索写入也放进同步路径，延迟和可用性会受它影响。若只写缓存后返回，则要解释缓存故障和落库失败时如何恢复。

画写路径时标出每个持久点、重试边界和结果未知窗口。

## 2. 读路径按一致性和查询形态选择

精确读取可以先查缓存，未命中回权威数据库；全文检索进入 Elasticsearch；大范围分析进入 OLAP。不同投影有不同新鲜度，API 要知道何时可以使用。

写后立即读需要最新状态时，可以短期读主、携带版本等待副本追上，或直接返回写入结果。所有读取都走主库会限制扩展，所有读取都走副本又会暴露复制延迟。

一条页面请求若扇出几十个服务，整体延迟和失败率会被最慢分支支配。可批量、并行、预计算或减少不必要的同步数据。

## 3. 分片键决定数据位置和并行边界

好的分片键让主要查询带上它、写入分布均匀，并让需要同事务或同顺序的数据尽量共址。用户、租户、订单或时间都可能成为候选，取决于访问模式。

按 tenant 分片便于隔离和迁移，但大租户会形成倾斜；按订单 hash 均匀，却让“查询用户全部订单”需要额外索引或扇出。选择时应列出高频读写、增长方向和跨键操作。

## 4. 哈希、范围和目录路由各有成本

- **哈希分片**：分布通常均匀，范围查询和扩容迁移较复杂。
- **范围分片**：范围扫描自然，但递增键容易把新写集中到尾部分片。
- **目录路由**：映射灵活、便于单租户迁移，但目录服务成为关键依赖。
- **一致性哈希**：节点变化时减少映射移动，仍需虚拟节点、复制和负载校准。

实际系统常把逻辑 shard 数固定得多于物理节点，再把逻辑 shard 分配到节点，扩容时迁移部分 shard。

## 5. 热点不一定来自分片数量不足

热门商品、超级租户、递增时间范围和单一全局计数都会把请求集中到一个 key 或 shard。整体 CPU 低并不能排除单分片饱和。

先按 key、tenant 和 shard 观察 QPS、字节、延迟和队列，再根据语义处理：

- 只读热点使用缓存、复制和请求合并。
- 可合并计数拆成分片计数。
- 大租户独立路由或再分片。
- 顺序敏感写入保持单所有者，并限制入口。
- 时间热点使用散列前缀或分层分区，但保留查询索引。

## 6. 跨分片查询需要显式代价

没有分片键的查询可能向全部 shard fan-out，再合并排序和分页。shard 数增长后，延迟、失败概率和资源消耗同步增加。

可以建立按另一维度组织的派生索引、冗余关系表或搜索投影。跨分片分页使用稳定排序键和各分片游标，不能简单对每个 shard 使用同一个 OFFSET 后拼接。

跨分片事务则需要协调或重划边界。若大多数核心操作都跨 shard，说明分片键与业务聚合不匹配。

## 7. 扩容迁移要保持读写可验证

迁移可以按以下阶段进行：

1. 创建目标 shard 并复制历史数据。
2. 捕获源端增量变化，持续追赶。
3. 对比计数、版本和校验值。
4. 灰度切换部分读，并保留回源。
5. 在短窗口切换写所有权，处理在途请求。
6. 再次核对后停止旧 shard，保留回退期。

无约束双写会产生两边提交顺序和失败窗口。更安全的是明确单写权威，通过日志复制增量，并用版本防止旧写覆盖。

## 8. 先验证单节点瓶颈再拆分

索引、查询、批量、缓存和数据生命周期优化常能延后分片。分片引入路由、全局 ID、跨 shard 查询、再平衡、备份和故障恢复成本。

当容量或隔离证据表明单节点无法满足目标，并且团队能够维护迁移与对账流程时再拆分。设计中同时给出“不分片到什么规模”和“达到什么阈值开始迁移”。

## 9. 常见问题

### 9.1 使用 user ID 分片后，如何按时间查询全站订单

这不是主分片适合的访问路径。可以把全站时间查询送到按时间组织的搜索或分析投影，或维护专用索引；直接 fan-out 所有用户 shard 只适合低频管理查询并需严格限流。

### 9.2 一致性哈希是否解决数据倾斜

它减少节点变化时的迁移比例，虚拟节点能改善节点级分布，但单个热点 key 仍只落在一个位置。热点检测和业务拆分仍然需要。

**考察重点**

- 主要访问路径、共址事务与数据分布。

<details>
<summary>参考回答</summary>

先列出高频查询、写入、不变量和增长方向，选择能让主要请求带键路由、强关联数据共址且负载尽量均匀的分片键。用户键适合用户内查询，但全站时间查询需要另一份按时间组织的搜索或分析投影；核心操作频繁跨 shard，说明边界不合适。

哈希分布均匀但范围查询弱，范围分片方便扫描却容易尾部热点，目录路由灵活但有控制面成本。监控要按 key 和 shard 看倾斜，读热点用缓存复制，超级租户独立迁移，严格顺序写保留单所有者。扩容时历史复制加增量追赶，以版本和校验对账，灰度切读并在明确时点切换写权威，避免无约束长期双写。
