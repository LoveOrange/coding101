# 数据拆分

**数据拆分**是把记录分配到不同分片，以扩展容量或隔离负载。拆分以后，系统不仅要知道数据存在哪里，还要处理跨分片查询、热点和扩容时的数据迁移。设计时先沿读写路径确定访问方式，再选择分片键，才能看清哪些请求会变简单，哪些操作需要额外协调。

## 1. 面试核心 {#core}

- 接口返回成功前要明确**写入完成了哪些步骤**，这决定故障后需要恢复什么结果。
- 分片键要兼顾**主要查询、负载分布和相关数据能否在同一分片提交**。[卡](#shard-key-hotspots)
- 一致性哈希减少节点变化时需要迁移的映射，**不会自动分散单个键的热点**。
- 跨分片 Top K 要合并各分片候选，排序键必须能**确定任意两条记录的先后**。[卡](#cross-shard-pagination)
- 在线迁移要明确**当前由哪个分片接受写入**，并阻止持有旧路由的请求继续提交。[卡](#shard-migration-fencing)

## 2. 写路径 {#写路径}

**写路径**是一条写请求从进入服务到数据保存的过程，应标出鉴权、幂等检查、分片路由和持久化的位置。接口返回成功前必须完成哪些步骤，要由业务承诺决定。

例如，Outbox 模式把订单和待发送事件放进同一个数据库事务。订单提交时，更新搜索所需的事件也可靠地保留下来，搜索投影随后异步更新。如果创建订单必须等搜索更新完成再返回，主链路就会增加延迟，也会依赖搜索服务的可用性。

重试语义见 [写入结果未知与幂等](./interview-process.mdx#写入结果未知与幂等)。

## 3. 读路径 {#读路径}

读路径取决于查询需要什么结果。按 ID 查询可以走缓存和作为数据依据的数据库，全文检索可以走搜索投影，大范围统计可以走分析存储。后两者是从原始数据生成的派生结果，API 应说明它们允许落后多久。

用户写入后需要立即看到结果时，可以直接返回写入结果、短期内读主副本，或携带写入版本，等待读副本追上。副本滞后超过允许范围时，要明确是回到主副本读取、等待，还是告知用户当前只能返回旧数据。

一次页面请求如果拆成多个并行查询，也就是发生**扇出**，整体返回可能被最慢的分支拖住。批量查询、预计算和减少同步依赖，可以缩短必须等待的处理路径。

## 4. 分片键 {#分片键}

**分片键**是决定一条记录放在哪个分片的字段或字段组合。理想情况下，主要请求都带着这个键，系统可以直接定位分片；需要共同提交的记录尽量放在一起，写入又不会集中到少数键上。这几个目标需要同时权衡。

按租户分片，便于把一个租户整体迁走，但大租户可能让某个分片远比其他分片繁忙。按订单 ID 哈希可以分散订单，代价是按用户查询订单时，无法仅凭用户 ID 确定分片，需要额外索引或投影。

选择前列出高频操作、数据增长和事务边界。若多数核心事务都跨分片，应重新考虑边界。

## 5. 分片方式 {#分片方式}

分片方式决定怎样把键映射到存储位置，各有适合的访问模式：

| 方式 | 主要收益 | 代价 |
| --- | --- | --- |
| 哈希分片 | 分散不同键 | 范围查询需扇出 |
| 范围分片 | 便于区间扫描 | 递增键集中到尾部分片 |
| 目录路由 | 支持独立迁移租户 | 路由目录需要高可用 |
| 一致性哈希 | 减少成员变化时的迁移 | 仍需处理节点权重与数据倾斜 |

哈希把不同键分散到不同位置，效果取决于键分布和散列函数。但同一个键每次仍映射到相同位置，所以一个热门商品即使所在集群增加了节点，也可能继续成为热点。

可以先把数据分成比物理节点更多的逻辑分片，每个节点承载一部分。扩容时迁走部分逻辑分片，就不必改变所有键的取模规则。数据如何复制、负载如何重新平衡，仍需要单独设计。

## 6. 热点 {#热点}

**热点**是访问集中在少数数据或分片上的现象，例如热门商品、大租户和全局计数器。其他分片空闲，并不能自动分担这些访问，所以集群平均 CPU 较低时，某个分片仍可能已经饱和。

监控应按分片与热点键观察吞吐、延迟和队列。处理方式取决于业务语义：

- 读取热点可通过缓存、复制与请求合并分担。
- 可合并计数可拆为多个子计数，再聚合读取。
- 大租户可独立路由，并在租户内部再分片。
- 严格顺序写保留单所有者，并限制入口速率。
- 时间热点可增加散列前缀，同时维护查询索引。

## 7. 跨分片查询 {#跨分片查询}

缺少分片键、又没有其他定位方式的查询，需要向多个分片发送请求，再合并结果。分片越多，需要协调的响应越多，延迟和部分失败的处理成本也随之增加。

如果另一个查询维度也很常用，可以为它维护专用投影。例如按用户分片后，为全站时间查询单独维护检索数据。这样减少了反复扫描所有分片的成本，但需要说明投影允许的更新延迟，以及出错后怎样修复和重建。

### 7.1 全局排序与分页 {#全局排序与分页}

全局 Top K 可以先从每个分片取前 K 项，再按相同规则归并，选出全局前 K 项。排序键必须形成**全序**，即任意两条不同记录都能确定先后。例如使用 `(created_at, id)`，先比较创建时间，时间相同时再用唯一 ID 区分。

翻页时，不能让每个分片都跳过相同数量的记录：全局已经返回的记录不一定平均来自各分片，这样会漏掉尚未返回的候选。可以用稳定排序键做游标分页，记录已经返回的全局位置，或分别保存各分片的消费位置。

游标只解决从哪里继续读取，不能冻结数据。并发更新仍可能让记录的排序位置跨过游标边界；如果要求多次翻页始终对应固定结果集，还需要一致快照或查询版本。

## 8. 扩容迁移 {#扩容迁移}

在线迁移既要复制已有数据，也要接住复制期间的新写入，最后再切换负责写入的分片。可以分成以下步骤：

1. 确定与历史数据复制对应的日志起点，复制历史数据。
2. 持续回放增量，保留删除信息与记录版本。
3. 对比计数、校验值和关键业务不变量。
4. 试读目标分片，核对结果并监控延迟。
5. 短暂阻止旧写，排空在途请求并追平尾部日志。
6. 切换写所有者和路由，再确认旧端拒绝写入。

### 8.1 路由版本与写入隔离 {#路由版本与写入隔离}

路由表更新后，客户端缓存和已经发出的请求仍可能指向旧分片。可以给每次写入所有权分配递增的版本号（epoch），由写入端检查请求携带的版本；旧版本请求被拒绝或重新路由。

这个检查必须在真正提交写入的位置执行。只更新路由表，却不限制旧分片继续写入，会让新旧分片同时接受变更，形成两份不一致的状态。

切换后，新写只进入目标分片。要回滚，就先把这些变更同步回源分片，或继续以目标分片的数据为准；直接改回旧路由，会让切换后的新数据不可见甚至丢失。

## 9. 分片前的优化 {#分片前的优化}

索引、批量、缓存和历史归档可减少单库压力。分片会增加路由、跨分片事务与恢复成本。

容量或隔离证据明确后再拆分。计划中同时写出触发阈值、迁移时长与核对方法。

## 10. 常见问题 {#常见问题}

### 10.1 按用户分片后，怎样查询全站某段时间的数据？ {#用户分片与全站时间查询}

高频查询适合维护独立的搜索或分析投影。低频管理请求可以向多个分片查询后合并，但应限制频率和扫描量，避免一次管理查询占用过多资源。

### 10.2 一致性哈希和虚拟节点能消除单键热点吗？ {#一致性哈希与单键热点}

不能。一致性哈希减少节点变化时需要调整的键映射，虚拟节点改善不同键在节点间的分布，但同一个键仍集中在一个逻辑位置。单键热点要根据它是读取、可合并写入还是严格顺序写入，采用 [热点](#热点) 中的处理方式。

## 11. 面试题 {#面试题}

### 11.1 如何选择分片键，并处理热点和跨分片查询？ {#shard-key-hotspots}

**考察重点**：访问模式、共址事务与倾斜。

**相关内容**：[分片键](#分片键)、[热点](#热点)、[跨分片查询](#跨分片查询)。

<details>
<summary>参考回答</summary>

**分片键要兼顾主查询路由、负载分布与事务共址。**

按用户分片有利于用户内查询。全站时间查询可使用另一份投影。

读取热点用缓存和复制分担。可合并写入可拆键，严格顺序写需保留所有者。迁移则明确写权威，并隔离旧路由。

</details>

### 11.2 跨分片查询怎样获得全局 Top K，并继续翻页？ {#cross-shard-pagination}

**考察重点**：候选归并、全序与并发变化。

**相关内容**：[全局排序与分页](#全局排序与分页)。

<details>
<summary>参考回答</summary>

**每个分片取前 K 项后归并，得到全局 Top K。**

所有分片使用相同全序，例如时间加唯一 ID。

下一页使用排序游标或各分片消费位置。固定结果集还需快照或版本。逐分片直接跳过相同 OFFSET 会遗漏全局候选。

</details>

### 11.3 分片路由切换后，怎样阻止旧客户端继续写源分片？ {#shard-migration-fencing}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：所有权版本、写端检查与回滚边界。

**相关内容**：[扩容迁移](#扩容迁移)、[路由版本与写入隔离](#路由版本与写入隔离)。

<details>
<summary>参考回答</summary>

**源分片必须拒绝过期所有权版本的写入。**

切换前排空旧写并追平日志，再激活新所有者。

`epoch` 检查要在最终提交写入的位置强制执行，不能只依赖客户端刷新路由。切换后的新数据以目标分片为准，回滚前需先同步这些变更，避免恢复到旧状态。

</details>
