# 系统设计面试

系统设计面试要求候选人把模糊题目逐步收敛为有明确假设、数据流、容量和故障边界的方案。

## 1. 确认功能范围与质量目标

先用几分钟确认系统服务谁、完成哪些核心动作，以及本轮暂不设计什么。功能需求之外，还要问清：

- 峰值流量、数据规模和读写比例。
- 延迟、可用性与数据正确性要求。
- 数据保存周期、隐私和合规边界。
- 单地域还是多地域，允许怎样的降级。

问题没有给出数字时，可以提出合理假设并明确写下。假设的用途是推进设计，面试官修正后应及时更新后续判断。

## 2. 只估算会影响决策的容量

容量估算用于判断单机能否承载、存储增长速度、网络带宽和缓存规模。通常估算峰值 QPS、并发连接、单条记录大小、每日增量和保留期即可。

如果估算结果不会改变当前方案，就不必消耗大量时间追求精确。数量级与单位要自洽，并在使用数字做分片、异步化或多地域决策时说明依据。

## 3. 定义接口与核心数据模型

在画组件前，列出最重要的接口、实体和访问模式。例如短链接服务至少需要创建短链与跳转接口，核心记录包含短码、目标 URL、创建者和过期时间。

数据模型需要回答：

- 用什么标识唯一定位记录。
- 高频查询按哪些条件过滤和排序。
- 哪些状态变化必须放在同一事务。
- 哪份数据是权威来源，哪些是缓存或派生结果。

这样后面的数据库、索引、缓存和消息选择才能落到具体读写路径。

## 4. 画出一条写链路和一条读链路

高层设计先连接入口、应用服务、存储和必要的异步组件。沿箭头解释请求经过哪里、在哪里确认成功、哪个组件保存状态，以及失败时调用方看到什么。

优先完成最小闭环，再引入缓存、消息队列、搜索索引或分片。每增加一个组件，都应指出它解决的瓶颈和新增的故障窗口。

## 5. 围绕核心难点深入

面试时间有限，通常选择一到两个与题目最相关的部分深入，例如：

- 唯一 ID、分片键与扩容迁移。
- 时间线的推拉模型和热点用户。
- 支付状态机、幂等与对账。
- 消息顺序、重复投递与积压恢复。
- 多地域复制、一致性与故障切换。

深入部分要给出数据结构、状态转换或关键伪代码，并解释为什么当前约束下选择这套方案。

## 6. 检查故障与恢复路径

对每个有状态组件依次检查超时、重复、节点故障、网络分区和容量耗尽。至少说明：

1. 请求结果未知时能否安全重试。
2. 主从切换是否可能丢失已确认数据。
3. 缓存或队列故障是否会压垮数据库。
4. 后台任务从哪里恢复，怎样避免重复副作用。
5. 系统如何监控、告警、回滚并验证恢复。

高可用不能只画多个实例。还需要健康判断、流量切换、数据复制和防止双主的具体机制。

## 7. 用权衡收束方案

最后回到开头的目标，说明方案满足了哪些需求、还保留哪些风险，以及规模或业务变化到什么程度时需要下一步演进。

良好的设计不要求使用最多的组件。它要求关键决策能由需求和数据支持，故障后有可执行的恢复路径，团队知道怎样验证系统达到目标。

## 8. 常见问题

### 8.1 面试官没有提供规模怎么办

提出一组简洁假设，例如日活、峰值 QPS、记录大小和保留期，并询问是否可以据此继续。后续所有容量决策沿用同一组假设，避免数字前后矛盾。

### 8.2 一开始要不要直接画微服务和分库分表

先看业务边界和容量。单体服务与单库已经满足目标时，从简单方案开始更容易说明正确性；只有出现独立扩缩容、组织边界或明确容量瓶颈时，再拆分并讨论新增成本。

**考察重点**

- 深入设计、故障恢复和方案权衡。

先确认核心功能、用户规模、读写比例，以及延迟、可用性和一致性目标；缺少数字时明确提出假设。随后做足以影响决策的容量估算，定义关键接口、实体和高频访问模式，再画出最小可运行的一条写链路和一条读链路。

高层链路闭合后，选择题目最重要的一两个问题深入，例如分片、热点、幂等或多地域复制。最后逐个检查超时、重复、节点故障和容量耗尽，说明监控、降级和恢复验证。收尾时把方案与开头目标对照，明确当前权衡、剩余风险，以及什么条件会触发下一阶段演进。
