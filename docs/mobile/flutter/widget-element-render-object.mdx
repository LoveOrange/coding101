Flutter 把界面描述、树中实例和实际布局绘制分开管理。**Widget** 描述配置，**Element** 维护配置在树中某个位置的实例及其关系，**RenderObject** 处理布局、绘制和命中测试等渲染工作。重新创建 Widget，不等于把已有状态和渲染对象全部丢弃。

这组区别直接影响列表重排、状态丢失和性能问题的判断。要解释一个计数器为什么换了位置却保留数值，首先需要找到谁保存状态，以及新旧配置怎样匹配。本文以 Flutter 3 的通用机制为主，示例和实现细节使用 Flutter 3.24.3。

## 1. 面试核心 {#core}

- **Widget 是不可变配置，Element 是树中实例，RenderObject 承担渲染职责**。三者不是同一类对象，也不要求三棵树的节点数量一一相等。[卡](#trees)
- **StatelessWidget 也可以多次 build；StatefulWidget 本身仍然不可变**。可变状态放在与 StatefulElement 关联的 State 中，新的 Widget 配置可以继续使用原来的 State。[卡](#stateful)
- **复用某个 Element 要满足新旧 Widget 的类型和 Key 相等**。这个条件用于已经找到的候选位置，不能理解为框架会在整棵树中任意搜索相同类型。[卡](#matching)
- **LocalKey 在同一父节点的子节点范围内帮助匹配身份**。列表重排时，用稳定业务标识作为 Key，才能让状态跟随项目，而不是跟随当前下标。[卡](#local-key)
- **GlobalKey 提供跨位置识别及相关对象访问**，可以在符合条件的同一帧内移动子树，但必须唯一且稳定持有；它不是给所有组件提速的开关。[卡](#global-key)
- **State 生命周期区分初始化、依赖变化、配置更新、暂时移除与最终销毁**。`deactivate` 后可能重新激活，`dispose` 后不能重新挂载。[卡](#lifecycle)
- **BuildContext 表示 Element 所在位置**。祖先查询从这个位置向上进行，不会自动找到当前 build 即将返回的后代节点。[卡](#context)
- **build、layout 和 paint 是不同阶段**。配置重建后，实际属性是否变化、渲染对象怎样标记失效，才决定后续工作，不能把一次 build 直接算成一次完整重绘。[卡](#rebuild)

## 2. 配置、实例与渲染对象 {#配置实例与渲染对象}

### 2.1 Widget 描述当前需要的界面 {#Widget描述界面}

Widget 保存构造时传入的配置，例如文本、颜色、子节点和回调。框架要求 Widget 的配置不可变；状态变化时，build 返回描述新状态的 Widget，而不是随意修改旧 Widget 的字段。

不可变不代表不能显示变化的数据。父节点可以根据新数据创建一个新的 `Text` 配置，状态组件也可以在自己的 State 变化后重新构建。Widget 是这次需要什么界面的描述，不是屏幕像素，也不等同于平台原生控件。

同一个不可变 Widget 对象可以出现在树中多个位置。每个位置都有独立的 Element；如果它是 StatefulWidget，还可能分别创建独立 State。因此，不能把 Widget 对象引用当作页面实例的唯一身份。

### 2.2 Element 维持树中的关系 {#Element维持树中关系}

Element 是一个 Widget 配置被放入树中某个位置后的实例。它连接父子节点，持有当前 Widget 配置，并参与更新、依赖登记与生命周期管理。父节点重新 build 后，新的 Widget 可以更新已有 Element，而不必重新创建这一位置的所有对象。

不同类型的 Widget 创建不同的 Element。`StatelessWidget` 对应 `StatelessElement`，`StatefulWidget` 对应 `StatefulElement`；后者还管理 State。`RenderObjectWidget` 通过相应的 `RenderObjectElement` 连接到渲染对象。

Element 不是永久不变。类型或 Key 不再匹配、子树被最终移除时，旧 Element 会退出，新的配置可能创建新的 Element。所谓“稳定”，指它可以跨多次配置更新继续存在，不是承诺应用运行期间永不销毁。

### 2.3 RenderObject 处理几何和绘制 {#RenderObject处理几何和绘制}

RenderObject 是渲染树中的对象，维护布局与绘制所需的信息。具体子类决定怎样接受约束、计算几何、安排子节点、绘制内容和处理命中测试。例如盒模型渲染对象围绕约束和尺寸工作，滚动布局还有不同的几何协议。

`RenderObjectWidget` 提供创建与更新 RenderObject 的配置接口。其他组合型 Widget 可以只通过 build 返回下层 Widget，本身并不创建独立 RenderObject。因此，Widget、Element 与 RenderObject 不是“每层各复制一棵同样的树”。

| 对象 | 主要保存或负责的内容 | 配置变化时的典型行为 |
| --- | --- | --- |
| Widget | 不可变的界面配置 | 创建新描述，或复用已有不可变实例 |
| Element | 树中位置、当前配置、父子关系与依赖 | 匹配成功后更新当前 Widget |
| State | 状态组件的可变数据与资源 | 在对应实例延续时保留，按回调处理变化 |
| RenderObject | 几何、布局与绘制等渲染信息 | 按新属性更新，必要时请求布局或绘制 |

Flutter 的绘制模型使大量界面可以共享跨平台实现，但平台宿主仍要提供渲染表面、输入和系统服务。嵌入原生视图、调用相机或访问系统授权，也仍有平台边界；理解三类对象不能替代这些集成条件。

## 3. StatelessWidget、StatefulWidget 与 State {#状态组件与State}

### 3.1 无状态不代表只构建一次 {#无状态不代表只构建一次}

StatelessWidget 不需要自己持有一份由 State 管理的可变状态。它可以根据构造配置和上下文返回界面。初次插入、父节点更新配置、所依赖的祖先数据变化，都可能使它再次 build。

StatefulWidget 也属于不可变配置。它通过 `createState()` 提供 State，让计数、订阅或控制器等可变内容有明确的生命周期。不要把业务字段随意放进 StatefulWidget 再修改；否则既破坏配置约定，也容易混淆框架究竟在复用谁。

### 3.2 配置更新时保留状态 {#配置更新时保留状态}

下面的 `CounterTile` 接收标签与初始值。初始值只在新 State 的 `initState()` 中使用；点击后计数存在 State 中，标签则始终来自当前 Widget 配置。

```dart
import 'package:flutter/widgets.dart';

class CounterTile extends StatefulWidget {
  const CounterTile({super.key, required this.label, this.initial = 0});

  final String label;
  final int initial;

  @override
  State<CounterTile> createState() => _CounterTileState();
}

class _CounterTileState extends State<CounterTile> {
  late int _count;

  @override
  void initState() {
    super.initState();
    _count = widget.initial;
  }

  @override
  Widget build(BuildContext context) {
    return GestureDetector(
      behavior: HitTestBehavior.opaque,
      onTap: () => setState(() => _count++),
      child: Padding(
        padding: const EdgeInsets.all(16),
        child: Text('${widget.label}: $_count'),
      ),
    );
  }
}
```

如果父节点在同一位置用相同类型、相同 Key 的新配置把 `label` 从 A 改为 B，原有 State 可以保留。此时标签显示 B，但点击积累的 `_count` 不会因为 Widget 是新对象就自动归零。

同理，父节点只修改 `initial`，也不会重新执行已有 State 的 `initState()`。若产品要求某个配置变化时重置计数，需要在 `didUpdateWidget` 中明确比较条件并更新状态，或者有意识地改变身份；不能把“初始值”同时当作持续受父节点控制的值。

## 4. 新旧配置的匹配 {#新旧配置的匹配}

### 4.1 类型和 Key 决定能否更新 {#类型和Key决定能否更新}

`Widget.canUpdate(oldWidget, newWidget)` 判断新配置能否更新使用旧配置的 Element。Flutter 3.24.3 的判断条件是两者 `runtimeType` 相等且 `key` 相等。

这个条件需要放在父子更新过程里理解。框架先根据父节点的子节点更新规则找到候选，再判断是否能复用。两个没有 Key 的同类型 Widget 不会因为标签文字相同，就自动在整个页面中找到彼此。

相同 Widget 实例还可能命中更新过程中的快捷路径，减少重复处理。`const` 可以帮助复用不可变配置，但不会冻结所有后代：依赖变化或某个后代自己的状态变化，仍然可以触发对应更新。

### 4.2 列表身份与 LocalKey {#列表身份与LocalKey}

**LocalKey** 在同一父节点的子节点范围内标识身份。`ValueKey` 使用给定值参与相等比较，适合稳定的业务 ID；`ObjectKey` 按对象身份识别；`UniqueKey` 只与自身相等，重新创建就意味着新身份。

下面沿用 `CounterTile`，显示两项计数器。示例假定 `labels` 中的值唯一；实际列表应使用不会随显示文案变化的业务 ID。

```dart
Widget counterRow(List<String> labels, {required bool keyed}) {
  return Directionality(
    textDirection: TextDirection.ltr,
    child: Row(
      children: [
        for (final label in labels)
          CounterTile(
            key: keyed ? ValueKey(label) : null,
            label: label,
          ),
      ],
    ),
  );
}
```

先显示 `[A, B]`，点击 A 一次，再把顺序改成 `[B, A]`：

| 配置 | 重排后的显示 | 原因 |
| --- | --- | --- |
| `keyed: false` | `B: 1`、`A: 0` | 同类型的无 Key 直接子节点按位置复用，计数状态留在原位置 |
| `keyed: true` | `B: 0`、`A: 1` | 父节点通过稳定 Key 匹配项目，A 的状态跟随 A |

用当前下标作为 Key，通常仍是在标记位置，不能解决项目重排时的身份问题。Key 还应放在实际被该父节点比较的直接子节点上：如果外面包了一层没有 Key 的 `Padding`，仅给更深处的计数器设置 LocalKey，不等于外层列表也能用它匹配。

### 4.3 GlobalKey 的范围和代价 {#GlobalKey的范围和代价}

**GlobalKey** 在整棵应用树中唯一标识 Element，并可访问关联的 context、Widget 或符合类型条件的 State。在 Flutter 3.24.3 中，BuildOwner 维护 GlobalKey 到 Element 的登记关系，相关访问通过它找到当前对象。

GlobalKey 的特殊能力是跨父节点移动子树时保留身份。旧位置移除后，新位置必须在同一动画帧内接入，框架才有机会重新挂载已有子树。这个过程可能触发 `deactivate`、重新激活和依赖重建，不能理解为没有代价的指针交换。

一个 GlobalKey 不能同时出现在两个位置。也不要每次 build 都 `GlobalKey()`：那会不断改变身份，丢失原有子树状态。通常由 State 长期持有，需要时再用于访问或移动；只是在兄弟节点之间匹配项目，用稳定 LocalKey 即可。

## 5. State 生命周期 {#State生命周期}

### 5.1 初始化、依赖与配置变化 {#初始化依赖与配置变化}

新 StatefulWidget 被实际放入树中时，框架创建 State，把它与 context 关联，再调用初始化流程。一次 State 生命周期中，初始化与更新分别承担不同职责：

| 回调 | 触发条件与职责 |
| --- | --- |
| `initState` | 新 State 的一次初始化，准备其拥有的资源 |
| `didChangeDependencies` | 初始化后调用；已登记的祖先依赖变化等条件下再次调用 |
| `build` | 根据当前 Widget、State 和上下文生成界面描述，可以多次调用 |
| `didUpdateWidget` | 同一实例接收到匹配的新 Widget 配置，处理新旧配置差异 |
| `deactivate` | 暂时离开当前树位置，仍可能在本帧重新接入 |
| `activate` | 暂时移除的 State 重新进入树中 |
| `dispose` | 永久移除，释放自身拥有的资源，生命周期结束 |

需要建立 `InheritedWidget` 依赖的初始化工作放在 `didChangeDependencies` 等允许登记依赖的位置，而不是在 `initState` 中调用依赖登记方法。`didUpdateWidget` 后框架会调用 build，因此只为让这次配置更新后的界面重建而额外调用 `setState` 是多余的。

订阅外部对象时，需要三处配合：初始化时订阅；新配置换了被订阅对象时，在 `didUpdateWidget` 中退订旧对象并订阅新对象；销毁时退订当前对象。只在 `dispose` 清理，不能处理同一个 State 继续存在、依赖对象却已更换的情况。

### 5.2 暂时离开与最终销毁 {#暂时离开与最终销毁}

`deactivate` 表示暂时离开当前位置，不保证即将销毁。GlobalKey 移动等情形可能让它在当前帧结束前重新激活；如果没有重新接入，框架才执行最终卸载与 `dispose`。

`dispose` 后 State 不会再次 build，也不能重新挂载。调用 `setState` 属于错误。应释放自己拥有的控制器、计时器与订阅，并停止不再需要的异步工作。检查 `mounted` 可以避免向已销毁的状态写入，但不会自动取消请求或停止计算。

`mounted` 也不是“屏幕可见”的同义词。路由被覆盖、应用进入后台或子树暂时离开活跃位置，都需要根据具体生命周期和可见性条件判断，不能只看一个布尔值。

## 6. BuildContext 与依赖位置 {#BuildContext与依赖位置}

**BuildContext** 是访问树中位置的接口，实际由 Element 实现。`Theme.of(context)`、`Navigator.of(context)` 等调用从传入 context 的位置寻找符合条件的祖先。

一个 Widget 的 build 收到的是它自己的 context，build 返回的子树位于它下面。如果这个 build 新建了一个祖先提供者，再用旧 context 查询，查询不会向下进入刚返回的子树。需要在其内部使用 `Builder` 或拆分子 Widget，取得更靠下的位置。

State 与自身 context 的关联在该 State 生命周期内保持一致，但这个 Element 可以移动到树中其他位置。因此，不应把某次祖先查询结果当作永远有效的关系。跨 `await` 使用 context 前还要确认它仍然有效；`context.mounted` 只说明没有被卸载，不保证业务请求仍然是最新的一次。

## 7. 重建与渲染失效 {#重建与渲染失效}

`setState` 先同步执行传入回调，再把相关 Element 标记为需要重建，后续由框架安排 build。回调不能声明成 `async`；异步工作应该在外部完成，只把同步状态修改放入回调。

build 产生配置后，匹配过程可以复用 Element 和 RenderObject。渲染属性变化会按各自语义触发后续工作：例如影响几何的属性可能需要重新布局，只影响颜色的属性可能只需重新绘制；没有相关变化时，不应假定一定重新执行所有阶段。

RenderObject 与合成使用的 Layer 也不是同一种对象。绘制层次还涉及边界和合成，不能把“Widget 树变了”直接换算成“GPU 重画了整屏”。分析性能时需要区分配置重建、布局、绘制记录和后续栅格化，而不是只统计 build 的打印次数。

**BuildContext 表示树中的位置，实际由 Element 实现，祖先查询从该位置向上进行。** 当前 build 的 context 位于它返回的子树之上，因此不能向下找到刚创建的提供者。应使用提供者内部的 Builder 或子 Widget 的 context。异步之后还要检查 context 是否仍挂载，但这不替代业务请求有效性判断。

</details>

### 8.8 调用 setState 后，会立即重新布局并重绘整棵树吗？ {#rebuild}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：同步修改、重建安排、对象复用及渲染失效。

**相关内容**：[重建与渲染失效](#重建与渲染失效)

<details>
<summary>参考回答</summary>

**不会直接等同于立即重绘整棵树。** `setState` 同步执行状态修改，再标记 Element 需要重建。build 后框架比较配置、复用或替换对象；实际属性变化才按相应规则触发布局、绘制等后续工作。因此要分别分析各阶段，而不是把 build 次数当作完整绘制次数。

</details>
