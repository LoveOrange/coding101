# 多 Agent 协作

多 Agent 协作通过分工和汇总完成任务。每个 Agent 可以拥有独立上下文和工具范围。本文负责组织方式、通信、共享状态与并发汇总。单 Agent 的停止条件见 [Agent 执行循环](./agent-loop.mdx)。

## 1. 面试核心 {#core}

- 多 Agent 通过上下文隔离和并行处理独立子任务。[卡](#multi-agent-design)
- 编排者分配任务、跟踪状态并汇总证据。
- 重复背景和结果汇总增加 Token 与协调成本。[卡](#multi-agent-risks)
- 并行写入需要资源所有权或显式合并规则。[卡](#multi-agent-isolation)
- 汇总策略规定失败子任务的重试与部分结果边界。[卡](#partial-results)

## 2. 组织方式 {#组织方式}

| 方式 | 结构 | 适用情况 |
| --- | --- | --- |
| 编排者—执行者 | 中心节点分配并汇总 | 独立调研、分模块检查 |
| 流水线 | 前一阶段输出进入下一阶段 | 抽取、校验、报告生成 |
| 层级 | 子编排者继续拆分任务 | 需要分层管理的任务 |
| 对等协作 | 多个 Agent 交换消息或共享状态 | 讨论与协商 |

对等协作需要明确的发言规则和终止条件。中心编排更便于追踪任务归属。具体选择取决于任务依赖和可观测性要求。

## 3. 通信与状态共享 {#通信与状态共享}

消息包含任务 ID、目标、输入范围和输出要求。执行者只接收完成子任务所需的信息。大产物放外部存储，消息返回摘要与引用。

```json
{
  "task_id": "review-3",
  "goal": "检查订单模块的接口兼容性",
  "scope": ["src/orders/"],
  "status": "done",
  "result_ref": "artifacts/review-3.json"
}
```

共享状态需要规定字段归属和合并规则。并发更新同一字段时，可用版本检查或归并函数。数据库、共享文件与图状态都要落实这些约束。

### 3.1 结果汇总 {#结果汇总}

编排者核对任务完成状态，再汇总结论和证据。冲突结论按来源、时间与适用条件复核。证据不足时保留争议，并说明影响。

### 3.2 部分失败与汇总策略 {#部分失败与汇总策略}

必需子任务失败时，父任务保留未完成状态。可选子任务失败时，可以返回部分结果。结果中列出缺失范围及其影响。

重试沿用子任务 ID，并增加尝试编号。编排者只接纳当前有效尝试的结果。父任务取消后，停止派发新工作并通知执行者。已发生的副作用仍要核对。

## 4. 拆分依据与代价 {#拆分依据与代价}

独立子任务、不同工具范围和大量材料适合拆分。任务强依赖时，传递完整上下文会增加协调开销。单 Agent 已达标时，先保留简单结构作为基线。

并行能缩短独立工作的等待时间。总耗时还包含最慢子任务、排队和汇总。每个子 Agent 都读取背景，也会增加输入用量。用同一任务集比较质量、耗时和总成本。

## 5. 资源竞争与隔离 {#资源竞争与隔离}

| 资源 | 风险 | 处理方式 |
| --- | --- | --- |
| 文件 | 同时编辑覆盖结果 | 文件所有权、独立 worktree、合并检查 |
| 共享数据 | 并发更新丢失 | 条件更新、锁或归并规则 |
| API 配额 | 并发触发限流 | 全局并发与速率预算 |
| 模型预算 | 子任务耗尽额度 | 子任务预算与总预算 |
| 上下文 | 无关信息干扰 | 独立消息历史、摘要与产物引用 |

消息隔离与工作目录隔离是两项配置。共享目录的 Agent 仍能看到彼此文件。执行权限见[工具授权与执行沙箱](../safety/tool-authorization-sandbox.mdx)。

## 6. 常见问题 {#常见问题}

### 6.1 A2A 与 MCP {#a2a-与-mcp}

A2A 面向 Agent 之间的任务协作。本文按 2026-10-13 的协议文档核对。Agent Card 描述能力，任务对象承载状态和产物。MCP 面向工具与数据接入，详见 [MCP](../tools/mcp.mdx)。

### 6.2 委派归属与转交上限 {#委派归属与转交上限}

每个子任务指定负责人。转交记录原因，并受次数与层级上限约束。超过上限或截止时间后，由编排者处理未完成部分。

**考察重点**

- 拆分的收益条件。
- 成本、通信失真、冲突和调试难度。

**相关内容**：[拆分依据与代价](#拆分依据与代价)。

<details>
<summary>参考回答</summary>

多 Agent 适合依赖少、上下文可分离的任务。强依赖任务需要大量信息交接，容易遗漏细节。

拆分增加重复背景、协调和汇总成本。并行写入会产生冲突，失败也需要跨轨迹定位。并行可以缩短耗时，但收益受最慢子任务约束。应以单 Agent 为基线，比较任务质量与总成本。

</details>

<summary>参考回答</summary>

竞争对象包括文件、共享数据、API 配额和模型预算。文件可按模块分工，也可使用独立 worktree。汇总后运行集成检查。共享数据用锁、版本号或归并函数更新。

API 与模型调用受全局并发及预算限制。各 Agent 保持独立消息历史，只接收必要材料。独立上下文仍需配合文件和工具权限隔离。

</details>

### 7.4 部分子 Agent 超时后，父任务怎样汇总和重试？ {#partial-results}

**出现公司**：暂无已核验的公开来源（本站自测）

**考察重点**：任务依赖、重复结果与取消传播。

**相关内容**：[部分失败与汇总策略](#部分失败与汇总策略)。

<details>
<summary>参考回答</summary>

汇总结果取决于失败子任务是否必需。必需任务失败时，父任务继续保持未完成。可选任务失败时，结果注明缺失范围。重试沿用任务 ID，并记录尝试编号。编排者丢弃过期尝试，按总预算限制重试。取消后还需核对已执行动作。

</details>
