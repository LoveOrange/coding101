# 大语言模型基础

**大语言模型**（LLM）是从大量文本中学习语言规律和知识关联的模型。这里讨论的是**自回归模型**：它根据已有文本预测下一个 Token，把选出的 Token 接到末尾，再用变长后的文本预测下一个。**Token** 是模型处理文本的基本单位，可以是一个词，也可以是词的一部分或几个字节。

调用模型时，你面对的就是这个「预测、追加、再预测」的循环，以及循环之前把文本切成 Token 的分词。不少实际问题都能从这两步推出来：中文和英文的用量为什么不同，输入太长为什么会变慢、变贵，同一个问题为什么每次回答不同，回答只有一句话为什么也会耗尽输出预算。这些问题分别对应四个知识点：文本怎样变成 Token，上下文窗口和用量怎样计算，一次生成经过哪些步骤，采样参数和推理预算各自控制什么。训练阶段和能力边界则说明模型能做什么、不能做什么。

## 1. 面试核心 {#core}

- Token 数**由分词器决定**，同一段中文在不同模型下数量不同。输入和输出都占上下文窗口，并**按不同单价计费**，实际用量以 API 返回的 `usage` 为准。[卡](#token-usage)
- 自回归生成先**预填充整段输入**，再一步步**预测、选择并追加下一个 Token**，直到遇到结束标记、停止序列或输出上限。[卡](#generation-flow)
- temperature **调整概率分布的形状**，top-k **保留概率最高的 k 个候选**，top-p **保留累计概率达到 p 的最小集合**。temperature 为 0 时，批次大小引起的浮点误差**仍可能改变候选 Token 的排名**，所以输出不保证逐字一致。[卡](#sampling-params) [卡](#temperature-zero-nondeterminism)
- 预训练让模型**学习语言和知识**，指令微调让它**学会按指令回答**，偏好优化让回答**更符合偏好**。
- 推理模型的输出上限**同时包含推理 Token 和可见回答**。所以用户看到的回答很短，也可能已经耗尽输出预算。[卡](#reasoning-budget)

## 2. Token 与上下文窗口 {#token-与上下文窗口}

一次请求能放进多少内容、要花多少钱，都按 Token 计算。而 Token 怎么切由分词器决定，所以先从分词器讲起。

### 2.1 分词器 {#分词器}

**分词器**（Tokenizer）把文本切成模型词表中的片段。**词表**记录了这些片段和它们的编号，编号称为 **Token ID**，模型实际接收的就是这串编号。片段可以是整个单词、单词的一部分（子词），也可以是字节片段。

同一段文本，换一个分词器，切出来的结果就不一样。下表用 tiktoken 0.14.0 实测了两种编码：cl100k_base 是 GPT-4 和 GPT-3.5 Turbo 使用的编码，o200k_base 是 GPT-4o 使用的编码。

| 文本 | cl100k_base（GPT-4） | o200k_base（GPT-4o） |
| --- | --- | --- |
| I'm learning programming on Coding101 | 7 个：I / 'm / ␣learning / ␣programming / ␣on / ␣Coding / 101 | 6 个：I'm / ␣learning / ␣programming / ␣on / ␣Coding / 101 |
| 我正在通过Coding101了解大语言模型 | 12 个：我 / 正在 / 通过 / Coding / 101 / 了 / 解 / 大 / 语 / 言 / 模 / 型 | 9 个：我 / 正在 / 通过 / Coding / 101 / 了解 / 大 / 语言 / 模型 |
| 学习 | 3 个：学 / `E4 B9` / `A0` | 1 个：学习 |
| 饕餮 | 6 个：`E9` / `A5` / `95` / `E9` / `A4` / `AE` | 4 个：`E9 A5` / `95` / `E9 A4` / `AE` |

「␣」表示这个 Token 以空格开头。`E4 B9` 这类十六进制数是汉字的 UTF-8 字节。

对照这张表，可以看出几条规律：

- 不同分词器对同一句话的切法不同。英文句子里，cl100k_base 把 I'm 切成 I / 'm，o200k_base 保留为一个 Token。中文句子里，「了解」「语言」「模型」在 o200k_base 中各是一个 Token，在 cl100k_base 中都拆成了两个字。
- 常见英文词通常是一个 Token，前面的空格也并入其中，比如表中的 learning、programming 和 on。Coding101 这样的少见词会拆成 Coding / 101 两段。
- o200k_base 收录的中文词组比 cl100k_base 多，所以表中同一句中文从 12 个 Token 降到了 9 个。
- 切分依据的是出现频率，不是语义。比如 o200k_base 把「今天天气」切成「今 / 天天 / 气」，因为「天天」在语料中出现得多，被合成了一个 Token。
- 词表没有收录的字，会按字节切分。一个常用汉字的 UTF-8 编码占 3 个字节，「习」是 `E4 B9 A0`。cl100k_base 收录了「学」，没有收录「习」，所以「学习」被切成「学」加上「习」的 2 个字节片段，共 3 个 Token；o200k_base 收录了整个词，只占 1 个。生僻词「饕餮」两种编码都没有收录，分别占 6 个和 4 个 Token。按字节切分保证了任何文字都能转成 Token，代价是生僻字更费 Token。

所以字数和 Token 数没有固定比例，估算时要用对应模型的分词器去数。

### 2.2 上下文窗口 {#上下文窗口}

**上下文窗口**是一次推理能容纳的 Token 总量上限。输入、可见输出和推理 Token 都要占用这个空间，输入占得越多，留给回答和推理的就越少。输出另外还有独立的长度上限，应用要同时满足这两项限制。超出窗口时，接口会按配置报错或截断内容。

窗口放得下，不代表模型能用好里面的全部信息。检索到的文档、对话历史和工具返回的结果都会进入窗口，输入越长，费用越高，处理时间也越长。在长文档问答等任务中，模型还容易遗漏位于中间的关键信息。因此应用应只放入与问题相关的内容，并检查回答是否用到了关键信息。

### 2.3 Token 用量与费用 {#token-用量与费用}

一次请求的用量由输入 Token 和输出 Token 组成，实际数值读取 API 返回的用量（usage）。消息模板和工具定义也会占用输入，所以只数自己写的那句话会低估用量。两部分包含的内容如下：

| 部分 | 内容 | 说明 |
| --- | --- | --- |
| 输入 Token | 系统提示、工具定义、对话历史、检索到的文档、本轮输入。系统提示规定模型的任务和行为；工具定义告诉模型有哪些函数可调用，以及参数格式；检索到的文档是程序从知识库中查出、交给模型参考的内容。 | 保留全部历史时，每一轮都要重新处理此前的消息，输入量会随对话轮数增长。 |
| 输出 Token | 模型生成的回答、工具调用参数，以及推理 Token。推理 Token 是推理模型在给出最终回答前用于内部推理的 Token。 | 输出单价通常高于输入单价，推理 Token 也按输出计费。 |

不同类别的单价不同，费用要按所用模型的输入、输出等类别分别计算，只看总 Token 数没法直接比较费用。另外，重复的输入前缀可以命中缓存，按更低的价格计费，原理见[前缀缓存](#前缀缓存)。

## 3. 一次生成的过程 {#一次生成的过程}

一次请求发出后，模型先处理整段输入，再逐个生成 Token。整个过程可以分成五步：

1. **序列化与分词**：服务先按模型的对话模板组织消息，这一步称为**序列化**。模板用角色等标记区分系统提示、用户消息和工具返回的结果。分词器再把组织好的文本转换成 Token ID 序列，交给模型计算。
2. **预填充**（prefill）：模型一次处理整段输入，计算每一层的 Key、Value。它们是注意力机制用来匹配和读取已有内容的中间结果，会存进名为 **KV Cache** 的缓存，供后面的生成复用。没有命中前缀缓存时，输入越长，这一步的计算越多，等待首个 Token 的时间也越长。
3. **解码**（decode）：模型根据已有序列，算出词表中每个 Token 作为下一个 Token 的概率，服务再按采样规则选出一个，追加到序列末尾。下一步读取已有的 KV Cache，只计算新增 Token 的 Key、Value 和再下一个 Token 的概率。缓存之所以能复用，是因为旧 Token 的计算只依赖它自己及之前的内容，新增 Token 不会改变它们。基本解码每步只新增一个 Token，所以输出越长，步数越多，总耗时也越长。
4. **停止**：模型输出特殊的结束 Token 时，生成结束。调用方也可以设置**停止序列**，也就是约定用来结束生成的文本标记。此外，生成达到输出上限时也会停止。
5. **反分词**：服务把生成的 Token 转回文本，供应用展示或解析。非流式接口等生成结束后一次返回；流式接口边生成边返回文本片段，你能更早看到第一段文字，但完整生成需要的时间并没有变短。

停止的原因不同，应用收到结果后的处理也不同，至少要区分三种情况：

- **正常完成**：可以按完整回答继续处理。
- **预算耗尽**：结果没有生成完，要按未完成处理，不能直接当作正常回答解析。
- **请求调用工具**：模型给出的是调用请求，要由程序执行对应的函数。

理解了这个过程，就能分开「开始输出慢」和「完整回答慢」。**首 Token 延迟**是从发出请求到收到第一个输出 Token 的时间，包括网络传输、服务端排队与调度、预填充，以及生成第一个 Token 的计算。完整回答的耗时还要加上后续每一步解码，输出越长越久。所以排查延迟时，要分别记录首 Token 延迟和完整响应时间：前者主要受输入长度和排队影响，后者主要受输出长度影响。

多轮对话就是把这个过程重复多次。模型本身不会记住另一次独立调用的内容，它能「接着聊」，是因为历史又被放进了这一次的输入。历史可以由应用保存，每轮重新发送需要保留的消息；也可以由服务端保存会话，在下一次推理时补入。无论哪种方式，续接的历史都计入输入用量，保留得越多，消耗的输入 Token 就越多。

### 3.1 前缀缓存 {#前缀缓存}

**前缀缓存**是把请求开头那段内容的 Key、Value 保存下来，让后续请求直接复用。多次请求经常带着相同的系统提示或工具定义，只要它们位于输入开头，就有机会省去这部分的重复计算。

复用之所以成立，原因和解码时复用 KV Cache 一样：在自回归模型中，每个 Token 的 Key、Value 只依赖它自己和它之前的 Token。同一个模型处理两个请求时，开头完全相同的那一段，算出来的 Key、Value 也完全相同，服务把它们存下来就能直接用。

这也解释了为什么要求前缀**完全相同**。只要前面有一个 Token 改变，它后面所有 Token 依赖的前文就变了，服务要从这个 Token 开始重新计算，只有它之前的共同部分还能复用。所以组装输入时，应把稳定的系统提示和工具定义放在最前面，把每轮变化的内容放在后面。具体的组装顺序见[上下文管理](../prompting/context-management.mdx#组装顺序与前缀缓存)。

命中缓存后，省掉的是这段前缀的预填充计算，新增的输入仍要预填充，输出阶段也仍要逐个 Token 解码。所以前缀缓存主要降低首 Token 延迟和输入费用，对长回答的生成耗时帮助不大。

输入费用能降，也是因为省了计算：服务直接读取保存好的 Key、Value，缓存命中的输入就按更低单价计费。缓存要占用服务端存储，所以有保存期限，长时间不用会失效。各提供方的规则也不同：OpenAI 会自动缓存足够长的相同前缀；Anthropic 可以显式标记缓存位置，写入缓存的输入按更高单价计费。

读用量时，要把总量和其中的明细分开看：命中缓存的 Token 数已经包含在输入总量里，推理 Token 数也已经包含在输出总量里。比如一次请求的用量如下，单位都是 Token：

- 输入为 1000，其中缓存命中为 600。
- 输出为 200，其中推理为 150。
- 输入与输出相加，总用量是 1200。
- 输入减去缓存命中量，未命中的部分是 400。

统计总量时，缓存和推理明细都不需要再加一次。

回到 KV Cache，两种复用的区别在于时机：解码时复用的是同一次请求内的 KV Cache，前缀缓存则把这些结果保留到后续请求中复用。KV Cache 的内部机制见 [Transformer 与注意力机制](./transformer.mdx#kv-cache-与推理成本)。

## 4. 采样参数 {#采样参数}

解码的每一步，模型都会给出很多候选 Token，最终选哪一个由采样决定。**采样**是根据候选概率选出下一个 Token 的过程，采样参数用来调整这种选择。

模型每一步先给词表中每个候选输出一个原始分数，称为 **logits**。要按概率选择，得先把分数转成概率：温度 `T > 0` 时，用 `softmax(logits / T)` 完成转换，softmax 会把一组分数变成总和为 1 的概率分布。服务按这个分布随机抽取，所以同一输入每次可能选出不同的 Token，生成不同的文本；调整温度或筛选候选，改变的是各候选被选中的概率。

调用模型时，常用下面这些参数或控制项调整生成：

| 参数或控制项 | 作用 | 常见取值方向与用途 |
| --- | --- | --- |
| temperature | 小于 1 时分布更尖锐，高分候选更占优势。大于 1 时分布更平坦，较低分候选更容易被选中。 | 抽取、分类、代码生成和工具调用从低值开始评测。创作、头脑风暴可比较较高值的效果。 |
| top-k | 只保留概率最高的 k 个候选，再从中采样。 | k 越小，候选范围越窄。它排除概率极低的 Token，避免偶然选中离题或错误的词。 |
| top-p | 按概率从高到低累加，保留累计达到 p 的最小集合。这个方法称为核采样。 | p 越小，候选范围越窄。候选数量随分布变化，调优时与 temperature 先选一个调整。 |
| 最大输出量 | 生成达到输出预算时停止，字段名称取决于 API。 | 按任务需要预留长度，用上限控制长输出和费用。推理模型还要预留内部推理的空间。 |
| stop | 在支持该参数的接口中，指定触发停止的文本序列。 | 适合生成到约定标记为止的任务，防止继续输出后续内容。 |

top-k 和 top-p 都会缩小候选范围，区别在于筛选条件：top-k 固定候选数量，top-p 按概率分布决定数量。比如四个候选的概率依次为 0.6、0.25、0.1、0.05，`top-k=2` 保留前两个；`top-p=0.9` 保留前三个，因为前两个的累计概率只有 0.85，加上第三个才达到阈值。

**贪心解码**是每一步都直接选分数最高的 Token。temperature 越接近 0，分布越尖锐，采样就越接近贪心解码。`T=0` 时上面的公式会除以零，没法直接计算，所以接口一般把 `temperature=0` 当作贪心解码处理。

### 4.1 输出一致性 {#输出一致性}

把 temperature 设为 0 能减少采样的随机性，但仍不能保证同一请求的回答逐字相同。原因在于服务端算出的 logits 本身会有细微差别。

这种差别来自浮点数。计算机里的浮点数只保留有限精度，加法不满足结合律，`(a+b)+c` 与 `a+(b+c)` 的结果可能差一点点。GPU 并行计算时，求和怎么分组、按什么顺序合并，就会影响最终结果。

推理服务会把多个用户的请求合成一批计算。负载一变，同一个请求就会被分进大小不同的批次，而计算程序为了充分利用 GPU，会随批次大小调整求和分组。比如批次小时，可能把一次求和拆给多个计算单元，再合并各组结果。相加顺序一变，logits 就出现微小差异。Thinking Machines Lab 在 2025 年的文章中分析了这一机制，并认为它是服务端输出不一致的主要来源。

微小差异平时不影响结果，但如果两个候选 Token 的分数非常接近，它就足以改变排名，贪心解码仍然选最高分，却选出了不同的 Token。后面每一步都基于已经生成的前文，前文一变，后续预测也跟着变，最初的一点差异就会随生成越滚越大。

除了批次变化，排查输出差异时还要看几项可能变化的条件：

- **模型版本**：**模型快照**是某次发布的固定模型版本。使用不带日期的模型别名时，提供方可能更新它指向的快照，同一个别名背后的模型已经换了，结果自然会变。
- **运行环境**：服务端更换硬件或推理程序，也会改变计算结果。
- **参数支持**：部分推理模型不支持或忽略 temperature，设置前要核对模型文档。Anthropic 的官方文档也说明，即使 temperature 为 0，结果仍非完全确定。

想让回答尽量一致，应用侧先固定带日期的模型快照，再保持完整输入一致：系统提示和示例、工具定义及其排列顺序、对话历史、检索到的文档和工具返回的结果，都要相同。在此基础上，模型支持时把 temperature 设为 0 或较低值。部分接口还提供 seed，也就是控制随机数生成的种子，固定 seed 有助于复现，但服务端计算的差异依然存在。

如果回答要交给程序解析，还要约束格式、检查内容。结构化输出约束回答的格式，再用 Schema（描述字段和类型要求的结构规则）检查字段和类型是否符合要求。格式通过后还要做业务校验，比如金额是否与订单记录一致；生成失败时，可以设置有限次数的重试。具体方法见[提示词工程](../prompting/prompt-engineering.mdx#结构化输出)。

对于完全相同的输入，如果要求每次回答逐字一致，最直接的办法是缓存之前的回答，后续直接复用。

自部署模型时，你还能控制计算环境：使用相同的硬件、相同版本的推理程序，并保持计算精度一致。在此基础上，可以采用批次不变的计算方式，让求和的分组与顺序不受批次大小影响；也可以采用确定性的计算方式，让相同条件下的重复计算得到相同结果。代价是限制了并行计算的优化空间，所以要在一致性和吞吐量（单位时间内能完成的工作量）之间权衡。

评估一致性时，在固定模型快照和完整输入的基础上，再固定采样参数，对同一输入运行多次。重点比较结论和关键字段是否一致，而不只看文字是否逐字相同。要比较参数效果，就每次只改一个参数，这样才能判断变化从哪里来。

### 4.2 推理预算与输出结束状态 {#推理预算与输出结束状态}

推理模型的推理 Token 和最终回答**共用同一个输出上限**，所以判断预算够不够用，要把两者放在一起看。

推理模型在给出回答之前，会先生成一段内部推理，这部分用掉的就是推理 Token。推理用得越多，留给回答的空间就越少。于是会出现这样的情况：回答只有一句话，甚至一个字都没有，输出预算却已经用完了。

遇到这种情况，应用要看接口返回的结束状态。预算耗尽时，接口会把响应标记为未完成。比如在 OpenAI Responses API 中，`max_output_tokens` 设置输出上限，达到上限而没有生成完时，响应状态是 `incomplete`。这时不能把已经收到的内容当作完整结果解析。例如一段 JSON 在中途被截断，就要重新生成或续接，再校验内容是否完整、格式是否正确。

调整时要分清推理预算和采样参数各管什么：推理预算限制推理用量的上限，采样参数改变每一步的候选概率。提高预算只是给了模型更多可用的推理空间，模型实际多用了推理 Token，耗时和费用才会增加。因此调整预算后，要同时比较三项指标：

- 任务成功率：更多推理空间是否帮模型完成了任务。
- 延迟：完成一次请求花了多长时间。
- 费用：完成任务实际花了多少钱。

## 5. 训练阶段与能力边界 {#训练阶段与能力边界}

前面讲的是调用时怎样生成和控制输出，这一节看模型的能力从哪里来。训练就是用数据调整模型参数，也就是模型内部参与计算的那些数值。

不同训练阶段用的**训练信号**不同，训练信号就是告诉模型该怎样调整的依据。三个阶段分别让模型学会语言、任务和回答偏好：

| 阶段 | 训练信号 | 主要作用 |
| --- | --- | --- |
| 预训练 | 在海量文本上预测下一个 Token，用实际后文纠正预测。 | 学习语言规律，以及训练数据中的知识关联。 |
| 指令微调（SFT，监督微调） | 用指令与高质量回答组成示范。 | 学习按指令完成任务，并遵循对话格式。 |
| 偏好优化 | 使用人类或模型对多个回答的偏好比较或奖励。 | 提高符合偏好的回答的生成倾向，例如更有帮助、更安全、更符合格式要求。 |

偏好优化里常见两个名称：RLHF 和 DPO。**RLHF** 指利用人类反馈进行强化学习，常见做法是先用偏好数据训练一个奖励模型，让它给回答打分，再用这些奖励调整语言模型。**DPO** 指直接偏好优化，它跳过奖励模型，直接用偏好对调整模型的回答倾向。偏好对是同一输入的两个回答，一个被偏好，另一个被拒绝。实际训练时，不同模型会组合使用不同的方法。

训练方式决定了模型在应用中有几类能力边界：

- **知识截止与私有数据**：训练数据有时间范围，训练之后的新事件需要外部信息补充。企业内部文档既没进入训练、也没放进当前上下文时，模型无从知道，需要程序提供。常见做法是先检索相关文档，再交给模型回答，这种方式称为**检索增强生成**（RAG）；也可以通过工具补充信息。
- **事实可靠性**：模型学的是文本生成规律，回答再流畅也可能包含错误事实。缺少证据时，它仍可能补出看似合理的细节，所以应用需要核对来源。事实错误的成因与处理方法见[模型幻觉](./hallucination.mdx)。
- **精确计算与长链推理**：多位数运算或严格计数容易出错，多步推理中前一步的错误还会带到后面的结论。需要精确结果时，应交给代码或工具计算，再校验结果。
- **工具调用**：模型通过训练学会的是按格式生成调用请求，真正的操作要由程序执行对应的函数才能完成。完整链路见 [Function Calling](../tools/function-calling.mdx)。

把模型用到具体任务上，有三种常见方式：用提示词说明当前要完成的任务，用 RAG 补充回答所需的相关文档，用微调让模型学会特定任务的格式、风格或领域用语。具体怎样选择与组合，见[检索增强生成（RAG）](../rag/rag.mdx#rag-与微调)。

## 6. 面试题 {#面试题}

### 6.1 一次模型请求的 Token 用量怎样计算？中文和英文有什么差异？ {#token-usage}

**考察重点**：解释分词器造成的中英文用量差异，以及历史增长对输入费用的影响。统计时区分输入、输出与已包含的缓存和推理明细。

**相关内容**：[Token 与上下文窗口](#token-与上下文窗口)、[Token 用量与费用](#token-用量与费用)。

<details>
<summary>参考回答</summary>

**一次请求的总用量是输入与输出 Token 之和，实际数值读取 API 的 `usage`。**

分词器按词表切分文本，常见英文词往往是一个 Token，罕见词会被拆开；中文可以按字、词组或更小的字节片段切分。不同词表对中文的覆盖程度不同，同一段中文的 Token 数也就不同。所以估算要用对应模型的分词器，实际用量以接口统计为准。

输入包含系统提示、工具定义、历史、检索到的文档和本轮消息。完整保留对话历史时，后续每轮的输入量都会增长；由服务端续接历史，这部分同样计入输入用量。控制成本时，要关注保留的历史和检索文档占了多少 Token。

输出包含回答、工具调用参数，推理模型还包含内部推理 Token。输出单价通常高于输入单价，命中缓存的输入按缓存价格计算，因为前缀缓存省去了重复前缀的预填充。缓存命中数属于输入总量，推理 Token 数属于输出总量，两项明细都已计入总量，费用要按各类别的实际单价分别计算。

</details>

### 6.2 完整描述一次大模型生成，底层发生了什么？ {#generation-flow}

**考察重点**：按顺序解释各生成阶段，说明输入和输出长度怎样影响延迟。能根据结束状态判断结果是否完整。

**相关内容**：[一次生成的过程](#一次生成的过程)、[前缀缓存](#前缀缓存)、[采样参数](#采样参数)。

<details>
<summary>参考回答</summary>

**一次生成依次经过分词、预填充、逐 Token 解码、停止判定和反分词。**

服务先按模型模板组织系统提示、工具定义和消息，再转换成 Token ID。预填充处理整段输入，把各层的 Key、Value 存入 KV Cache；输入越长，计算越多，首 Token 的等待时间也越长。首 Token 延迟还包括网络、排队和调度等耗时。

解码时，模型根据已有序列计算下一个 Token 的概率，采样规则选出一个 Token，追加后进入下一步。KV Cache 复用旧 Token 的 Key、Value，省去重复计算。基本解码每步只新增一个 Token，所以输出越长，步数越多。

遇到结束标记、调用方设置的停止序列或输出上限时，生成停止。服务把 Token 转回文本，流式接口可以在生成过程中逐段返回。应用要区分正常完成、截断和工具调用，再决定怎样处理结果。多轮对话的历史由应用重发或由服务端补入下一次上下文，续接的部分仍占输入用量。

</details>

### 6.3 temperature、top-p、top-k 分别是什么？不同场景应该怎样设置？ {#sampling-params}

**考察重点**：解释三个参数怎样改变下一 Token 的选择，并按任务选择取值方向。理解模型快照、完整输入与输出校验对一致性的影响。

**相关内容**：[采样参数](#采样参数)、[输出一致性](#输出一致性)、[结构化输出](../prompting/prompt-engineering.mdx#结构化输出)。

<details>
<summary>参考回答</summary>

**temperature 调整概率分布，top-k 按候选数量筛选，top-p 按累计概率筛选。**

温度低于 1 时，高分候选更占优势；高于 1 时，分布更平坦。top-k 只保留概率最高的 k 个候选。top-p 保留累计概率达到 p 的最小集合，候选数量随分布变化。

抽取、分类、代码生成和工具调用更看重稳定完成任务，可以从低温度开始评测；创作和头脑风暴可以比较较高温度的效果。调优时先只改 temperature 或 top-p 中的一项，便于判断原因。参数是否可用，要核对所用模型与接口。

温度接近 0 时，采样接近每步选最高分的贪心解码。但批次大小变化会改变求和分组，浮点误差可能改变分数接近的候选 Token 的排名，所以低温度也不能保证逐字一致。应用应固定模型快照和完整输入，并用结构化输出、Schema 和业务校验检查结果；生成失败时可以有限重试，事实是否正确仍要核对证据。

</details>

### 6.4 temperature 已经设为 0，为什么输出仍然不一致？ {#temperature-zero-nondeterminism}

**考察重点**：浮点加法、批次大小与候选 Token 排名的关系，以及前文变化对后续生成的影响。

**相关内容**：[采样参数](#采样参数)、[输出一致性](#输出一致性)。

<details>
<summary>参考回答</summary>

**temperature 为 0 时，服务端的计算差异仍可能改变候选 Token 的排名，让贪心解码选出不同的 Token。**

浮点加法不满足结合律，求和分组一变就会产生微小误差。服务会把多个请求合成一批计算，批次大小随负载变化，求和分组也跟着变。如果两个候选的分数很接近，这点误差就足以让贪心解码选出另一个 Token。后续预测基于不同的前文，差异会继续扩大。

此外，模型别名指向的快照、服务端硬件或推理程序都可能更新，部分推理模型还不支持或会忽略 temperature。判断差异时，要同时确认参数是否生效、服务端计算是否变化。

</details>

### 6.5 如何让 LLM 每次输出的结果尽量一致？ {#output-consistency}

**考察重点**：固定模型与输入、降低采样随机性、校验输出和缓存回答各能保证什么。

**相关内容**：[输出一致性](#输出一致性)、[结构化输出](../prompting/prompt-engineering.mdx#结构化输出)。

<details>
<summary>参考回答</summary>

**固定模型快照与完整输入，并降低采样随机性，可以让重复生成的结果尽量一致。**

应用应选用带日期的模型快照，固定系统提示、示例、工具定义及其顺序，对话历史、检索文档和工具结果也要一致。模型支持时，把 temperature 设为 0 或较低值；接口提供 seed 时，可以固定种子以尽量复现。服务端的批次和浮点计算仍会影响结果。

结构化输出与 Schema 校验让字段和类型稳定，业务校验检查内容是否满足要求。完全相同的输入如果要求逐字一致，可以缓存并复用之前的回答。自部署时，还可以采用批次不变或确定性的计算方式，代价是吞吐量下降。

验证时，对同一输入运行多次，比较结论和关键字段是否一致。措辞相近的回答也可能给出不同的金额或日期，所以要检查具体字段。

</details>

### 6.6 回答很短却耗尽输出预算，应怎样解释？ {#reasoning-budget}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：推理 Token、输出上限与未完成状态。

**相关内容**：[推理预算与输出结束状态](#推理预算与输出结束状态)。

<details>
<summary>参考回答</summary>

**推理 Token 也占用输出预算，所以可见回答很短时，预算仍可能耗尽。**

输出上限同时包含推理 Token 和可见回答。内部推理消耗的 Token 多，留给最终回答的空间就少。应用可以读取用量中的推理明细，确认内部推理用了多少 Token。

预算耗尽时，接口会把响应标记为未完成。应用应按未完成内容处理，检查剩余的上下文空间后，调整输出预算再生成。调整后要同时比较成功率、延迟和费用。

</details>
