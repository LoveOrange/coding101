# 大语言模型基础

**大语言模型**（Large Language Model，LLM）是从大量文本中学习语言规律和知识关联的模型。本文讨论的自回归语言模型根据已有上下文预测下一个文本单位，并通过反复追加它们生成文本。

## 1. 面试核心 {#core}

- 自回归 LLM **使用深度学习方法生成文本**。深度学习属于机器学习，生成式 AI 则按生成内容的目标分类，两者描述的是不同维度。[卡](#ml-dl-generative-ai)
- Token 是模型处理文本的基本单位，数量**由分词器决定，与字数没有固定比例**。同一段文字使用不同分词器，得到的 Token 数可能不同。[卡](#token-usage)
- 输入与本次生成的输出**共同占用上下文窗口**。模型能接着聊，是因为历史被放进当前上下文；普通对话不会自动更新模型参数。
- 预训练让模型**学习语言规律和知识关联**，指令微调让模型**学习按指令完成任务**，偏好优化则**提高符合偏好的回答的生成倾向**。
- 自回归生成先**预填充输入，再逐步预测、选择并追加 Token**，直到满足停止条件。后续预测依赖已经生成的内容。[卡](#generation-flow)
- temperature **调整概率分布**，top-k **按候选数量筛选**，top-p **按累计概率筛选**。它们影响下一步怎样选 Token，不能保证事实正确。[卡](#sampling-params)
- temperature 为 0 也**不保证逐字一致**。模型版本、完整输入和计算差异都可能影响结果。[卡](#temperature-zero-nondeterminism) [卡](#output-consistency)
- 模型生成的回答**不能保证事实正确**。新信息需要外部资料，精确结果需要验证，查询数据库等操作则需要程序实际执行。

## 2. 语言模型与生成式 AI {#语言模型与生成式-ai}

**语言模型**是学习语言序列中统计规律、对文本进行概率建模的模型。本文讨论的自回归 LLM 根据前文预测后续内容，可以通过不同的指令完成问答、翻译、摘要和代码生成等任务。

这些任务都可以表示成“给定一段输入，生成相应文本”。例如，我们把一段英文和翻译要求放进输入，模型生成中文译文；换成一篇文章和摘要要求，它就生成摘要。任务发生了变化，底层仍是在当前输入的条件下生成文本。

LLM 与机器学习、深度学习、生成式 AI 的关系，可以从学习方法和任务目标两个维度区分：

| 概念 | 含义 |
| --- | --- |
| **机器学习**（Machine Learning，ML） | 从数据中学习规律，用于预测、分类或生成等任务。 |
| **深度学习**（Deep Learning，DL） | 机器学习中的一类方法，使用深层神经网络学习逐层组合的表示。 |
| **生成式 AI**（Generative AI） | 以生成文本、图像、音频等内容为目标的一类 AI 模型。 |

自回归 LLM 使用深度学习方法，完成文本生成任务，所以同时属于深度学习和生成式 AI。一个只判断图片是猫还是狗的深层网络，也使用深度学习，但完成的是分类任务。

**模型参数**是神经网络中参与计算、通过训练调整的数值。模型从训练数据中学到的规律通过这些参数影响输出；它也会利用当前输入中提供的信息。

## 3. Token 与上下文窗口 {#token-与上下文窗口}

### 3.1 分词器 {#分词器}

**Token** 是模型处理文本的基本单位，可以是一个词、词的一部分，也可以是字节片段。模型接收的是 Token 对应的编号，而不是直接把“一个字”当成一个计算单位。

**分词器**（Tokenizer）把文本切成模型词表中的片段。**词表**记录了这些片段和它们的编号，编号称为 **Token ID**。同一段文本，换一个分词器，切分方式和 Token 数都可能不同。

下表展示两种编码对相同文本的切分。cl100k_base 是 GPT-4 使用的编码，o200k_base 是 GPT-4o 使用的编码：

| 文本 | cl100k_base（GPT-4） | o200k_base（GPT-4o） |
| --- | --- | --- |
| I'm learning programming on Coding101 | 7 个：I / 'm / ␣learning / ␣programming / ␣on / ␣Coding / 101 | 6 个：I'm / ␣learning / ␣programming / ␣on / ␣Coding / 101 |
| 我正在通过Coding101了解大语言模型 | 12 个：我 / 正在 / 通过 / Coding / 101 / 了 / 解 / 大 / 语 / 言 / 模 / 型 | 9 个：我 / 正在 / 通过 / Coding / 101 / 了解 / 大 / 语言 / 模型 |

“␣”表示这个 Token 以空格开头。英文中的 `I'm` 在两种编码下分别占两个和一个 Token；中文的“了解”“语言”“模型”在 o200k_base 中各占一个，在 cl100k_base 中各拆成两个字。

因此，字数和 Token 数没有固定比例，中文也不是一个汉字就对应一个 Token。估算时要用对应模型的分词器。

### 3.2 上下文窗口 {#上下文窗口}

**上下文**是模型当前能够利用的内容，包括本轮消息、保留的历史，以及任务需要的其他材料。规定任务与行为的**系统提示**、检索到的文档和工具说明，也都属于输入；开始生成后，已经生成的部分同样会成为后续预测的上下文。

**上下文窗口**是一次生成能容纳的 Token 总量上限，输入和本次生成的输出共同占用这个空间。输入越长，留给输出的空间就越少；模型还可能有独立的输出长度上限，需要同时满足。超出窗口时，接口会按配置报错或截断内容。

多轮对话能延续，是因为历史被重新放进了本次上下文。历史可以由应用重发，也可以由服务端补入，但模型只能使用实际保留下来的内容。例如，上一轮告诉模型“Lin 喜欢简洁的回答”，只有这条信息仍在当前输入中，才能作为本轮回答的依据。普通对话不会因此自动改变模型参数，也不意味着模型已经永久记住这项偏好。

窗口放得下，不代表模型能用好里面的全部信息。在长文档问答中，模型可能遗漏位于中间的关键信息，因此窗口大小不能直接代表长文本理解能力。材料的选择与裁剪见[上下文管理](../prompting/context-management.mdx#token-预算与材料选择)。

### 3.3 Token 用量与费用 {#token-用量与费用}

文本调用通常按输入和输出 Token 计量，实际用量以接口统计为准。输入包含本轮消息和其他上下文，输出除了可见回答，还可能包含工具调用参数。输入与输出通常使用不同单价，费用要分别计算后相加。

<span id="推理预算与输出结束状态" />

**推理 Token**（reasoning tokens）是模型为生成答案而进行内部推理时产生的 Token。这部分内容通常不会完整展示给用户，但也占用上下文，并计入输出用量。在采用统一输出预算的模型中，内部推理和最终回答共享预算。例如共允许生成 1000 个 Token，内部推理用了 900 个，就至多剩下 100 个用于回答。

因此，可见回答很短，也可能已耗尽输出预算。达到上限会使生成停止，但不代表回答已经完成。具体计费类别与成本控制见[延迟、成本与服务扩展](../safety/latency-cost-scaling.mdx#成本控制)。

## 4. 训练与生成 {#训练与生成}

<span id="训练阶段与能力边界" />

**训练**是根据数据和目标调整模型参数的过程，**推理**（inference）则是使用已有参数，根据输入计算结果的过程。对自回归 LLM 来说，生成回答属于推理；多聊几轮或补充文档，会改变它当前可用的上下文，普通模型调用不会因此自动更新参数。

### 4.1 训练阶段 {#训练阶段}

**自监督预训练**是从数据本身构造学习目标、训练模型的过程。对于自回归 LLM，我们把一段文本前面的 Token 交给模型，让它预测紧接着的 Token，再根据预测与实际后文的差距调整参数。训练目标直接来自文本，因此不必逐条人工标注答案。

预测后文需要利用词语搭配、语法、上下文关系以及文本中的知识信息。通过大量这样的训练，模型学到的规律可以支持多种文本任务。不过，学会接着写下去，还不等于能稳定地按用户要求作答。

**指令微调**用“指令与高质量回答”组成的示范继续训练模型，属于监督微调（SFT）。**偏好优化**则利用对多个回答的偏好比较或奖励，调整模型的回答倾向。三类训练的区别在于指导参数调整的依据，也就是**训练信号**：

| 阶段 | 训练信号 | 主要作用 |
| --- | --- | --- |
| 预训练 | 文本中实际出现的下一个 Token。 | 学习语言规律，以及训练数据中的知识关联。 |
| 指令微调 | 指令与高质量回答组成的示范。 | 学习按指令完成任务，并遵循对话格式。 |
| 偏好优化 | 对多个回答的偏好比较或奖励。 | 提高符合偏好的回答的生成倾向，例如更有帮助、更安全。 |

例如，预训练可以学习文章的内容与写法；指令微调可以用“请将这段文字概括为三点”及对应示范，训练按要求概括的能力。如果偏好反馈更认可准确、完整的概括，偏好优化就会让模型更倾向于生成这类回答。这些训练仍不能保证每次回答都正确。

### 4.2 一次生成的过程 {#一次生成的过程}

**自回归生成**是根据已有序列预测下一个 Token，把选出的 Token 接到末尾，再根据更新后的序列继续预测。每一步预测的依据既包含原始输入，也包含已经生成的内容。

**Transformer** 是一种处理序列的神经网络结构，其中的**注意力**机制会按相关程度汇总不同位置的信息。以使用因果 Transformer 的模型为例，Token ID 先转换成向量，也就是一组参与计算的数值。模型结合位置和前文信息计算，最终为词表中的候选 Token 给出分数，再转换成下一 Token 的概率。

“因果”表示每个位置只能利用自身及之前的信息，不能提前看到后文。训练时需要这个约束来防止模型看到要预测的答案；生成时，尚未生成的后文也确实不可用。注意力的具体计算见 [Transformer 与注意力机制](./transformer.mdx#自注意力的计算)。

一次请求按以下过程生成回答：

1. 服务先把消息**按对话模板组织并转换成 Token ID 序列**。模板区分系统提示、用户消息和工具结果等内容，分词器再把文本转换成模型接收的编号。
2. **预填充**（prefill）处理整段输入，为预测第一个输出 Token 准备结果。这一阶段还会保存后续生成可以复用的中间计算结果。
3. **解码**（decode）根据已有序列，逐步预测并追加 Token。模型给出下一 Token 的概率，按采样规则选出一个，追加到末尾，再继续预测。基本解码每步新增一个 Token。
4. 遇到**结束 Token、调用方设置的停止序列或输出上限**时，生成停止。服务将 Token 转回文本；流式接口可以在生成过程中逐段返回，让用户更早看到文字。

<span id="前缀缓存" />

预填充处理输入，解码逐步产生输出，因此输入长度和输出长度会影响不同阶段的工作量。生成时可以用 **KV Cache** 保存历史 Token 的部分中间计算结果，减少重复计算；复用原理和显存代价见 [Transformer 与注意力机制](./transformer.mdx#kv-cache-与推理成本)。

## 5. 采样参数 {#采样参数}

解码的每一步，模型都会给出很多候选 Token，最终选哪一个由采样决定。**采样**是根据候选概率选出下一个 Token 的过程，采样参数用来调整这种选择。

模型每一步先给词表中每个候选输出一个原始分数，称为 **logits**。要按概率选择，得先把分数转成概率：温度 `T > 0` 时，用 `softmax(logits / T)` 完成转换，softmax 会把一组分数变成总和为 1 的概率分布。服务按这个分布随机抽取，所以同一输入每次可能选出不同的 Token，生成不同的文本；调整温度或筛选候选，改变的是各候选被选中的概率。

下面三个采样参数分别调整概率分布或候选范围：

| 采样参数 | 作用 | 取值方向与用途 |
| --- | --- | --- |
| temperature | 大于 0 且小于 1 时分布更尖锐，高分候选更占优势。大于 1 时分布更平坦，较低分候选更容易被选中。 | 抽取、分类、代码生成和工具调用从低值开始评测。创作、头脑风暴可比较较高值的效果。 |
| top-k | 只保留概率最高的 k 个候选，再从中采样。 | k 越小，候选范围越窄；低概率候选被排除，但留下的候选仍可能包含事实错误。 |
| top-p | 按概率从高到低累加，保留累计达到 p 的最小集合。这个方法称为核采样。 | p 越小，候选范围越窄。候选数量随分布变化，调优时与 temperature 先选一个调整。 |

top-k 和 top-p 都会缩小候选范围，区别在于筛选条件：top-k 固定候选数量，top-p 按概率分布决定数量。比如四个候选的概率依次为 0.6、0.25、0.1、0.05，`top-k=2` 保留前两个；`top-p=0.9` 保留前三个，因为前两个的累计概率只有 0.85，加上第三个才达到阈值。

**贪心解码**是每一步都直接选分数最高的 Token。temperature 越接近 0，分布越尖锐，采样就越接近贪心解码。`T=0` 时上面的公式会除以零，没法直接计算，所以接口一般把 `temperature=0` 当作贪心解码处理。

### 5.1 输出一致性 {#输出一致性}

把 temperature 设为 0 能减少采样的随机性，但仍不能保证回答逐字相同。贪心解码固定的是“选最高分候选”这一规则，并不保证服务端每次算出的分数完全一样。

浮点数计算只保留有限精度。同一个求和过程换一种计算顺序，结果就可能有细微差别；服务端的并行计算方式可能引入这类差异。如果最高分的两个候选很接近，误差就可能改变排名，让贪心解码选出另一个 Token。后续生成又依赖已经生成的前文，这一步的差别可能继续影响整个回答。

模型版本或完整输入变化，也会影响结果。输入包含系统提示、历史、检索文档和工具结果，只保持用户最后一句话相同，并不等于模型收到的输入相同。

因此，让重复生成尽量一致，需要固定模型版本和完整输入，并在模型支持时降低采样温度。这能减少变化来源，但不能消除所有计算差异。低温度也不会补充事实依据，模型仍可能稳定地产生错误答案。

## 6. 能力边界 {#能力边界}

模型根据训练学到的规律和当前上下文生成回答。它能完成多种文本任务，但生成机制本身不会保证信息最新、事实正确或操作已经执行：

- 训练中未包含的新事件和私有数据，**需要外部信息提供依据**。训练数据有时间范围，企业文档也未必进入训练。程序可以先检索相关文档，再交给模型参考，这种方式称为**检索增强生成**（RAG）；它补充当前输入，不需要为每次查询重新训练模型。
- **文本流畅不能保证事实正确**。模型可能把学到的关联组合成没有依据的结论，偏好优化也不能消除所有错误。需要可靠事实时，应检查答案是否有证据支持；成因与处理方法见[模型幻觉](./hallucination.mdx)。
- **模型在精确计算和多步推理中可能出错**。前一步的错误会进入后续上下文，并可能影响最终结论。需要精确结果时，可以让代码或工具完成计算，再校验结果。
- **外部操作需要程序实际执行**。模型可以生成“已查询数据库”这样的文字，也可以生成工具调用请求，但只有程序真正执行了查询，才会得到外部结果。调用链路见 [Function Calling](../tools/function-calling.mdx)。

## 7. 面试题 {#面试题}

### 7.1 Machine Learning、Deep Learning 与 Generative AI 是什么关系？ {#ml-dl-generative-ai}

**考察重点**：机器学习与深度学习的关系，以及为什么深度学习不一定用于生成内容。

**相关内容**：[语言模型与生成式 AI](#语言模型与生成式-ai)、[训练与生成](#训练与生成)、[训练阶段](#训练阶段)。

<details>
<summary>参考回答</summary>

**回答要点**

1. 机器学习从数据中学习规律，**深度学习是其中使用深层神经网络的一类方法**。
2. **生成式 AI 以生成内容为目标**，例如文本、图像和音频。它描述模型用来做什么，深度学习描述模型使用什么学习方法，所以二者可以重合。
3. 自回归 LLM 使用深度学习来生成文本，**同时属于深度学习和生成式 AI**。只判断图片是猫还是狗的深层网络，也属于深度学习，但做的是分类，不属于生成式 AI。

**进一步探索**

- 经过预训练的模型能续写文本，但**未必能稳定地按指令作答**。指令微调训练它按要求完成任务，偏好优化则让它更倾向于给出被认可的回答。
- 模型能用你刚提供的信息回答问题，**不代表它已经永久记住了**。普通调用使用已有参数，不会自动修改参数；这条信息要继续作为后续回答的依据，仍需保留在上下文中。

</details>

### 7.2 一次模型请求的 Token 用量怎样计算？中文和英文有什么差异？ {#token-usage}

**考察重点**：Token 的统计范围、分词差异，以及多轮对话与计费的关系。

**相关内容**：[Token 与上下文窗口](#token-与上下文窗口)、[Token 用量与费用](#token-用量与费用)、[成本控制](../safety/latency-cost-scaling.mdx#成本控制)。

<details>
<summary>参考回答</summary>

**回答要点**

1. **一次请求的用量是输入 Token 与输出 Token 之和**，最终以接口统计为准。输入要算上本轮消息、系统提示、历史、工具定义和检索文档等；输出除可见回答外，还可能包含工具调用参数和内部推理 Token。
2. **中英文都不能按字数直接换算 Token 数**。一个英文单词可能被拆成几部分，中文的“语言”也可能占一个或两个 Token。具体切分由分词器决定，同一段文字换用不同分词器，数量也可能不同，所以要按所用模型的分词器估算。

**进一步探索**

- 每轮重新发送的历史，**都会再次计入输入用量**。只统计最后一条消息会漏掉这部分开销；裁剪不再需要的历史，可以减少后续轮次的输入。
- **未命中缓存的输入、命中缓存的输入和输出，要按各自的用量与单价计算费用，再相加**。前缀缓存复用的是已有的输入计算，命中的内容仍占用上下文。推理 Token 虽然通常不会完整展示，也要计入输出费用。

</details>

### 7.3 完整描述一次大模型生成，底层发生了什么？ {#generation-flow}

**考察重点**：预填充与解码的先后关系、KV Cache 的作用，以及输入输出长度怎样影响生成耗时。

**相关内容**：[一次生成的过程](#一次生成的过程)、[采样参数](#采样参数)、[KV Cache 与推理成本](./transformer.mdx#kv-cache-与推理成本)。

<details>
<summary>参考回答</summary>

**回答要点**

1. 服务先把消息按对话模板整理成 Token ID 序列，再由模型进行**预填充，处理整段输入**。这一步算出预测第一个输出 Token 所需的结果，同时保存后面可以复用的中间结果。
2. **基本解码每步根据当前序列选出并追加一个 Token**。模型先算出下一 Token 的概率，再按采样规则选择；新生成的内容也会成为后续预测的依据。
3. 遇到**结束 Token、停止序列或输出上限**时，生成结束。服务把 Token 转回文本；使用流式接口时，可以边生成边逐段返回。

**进一步探索**

- **KV Cache 省去历史 Key、Value 的重复计算，代价是占用显存**。因果注意力只使用当前位置和前文，追加 Token 不会改变旧位置的 Key、Value，所以这些结果可以留给后续步骤使用。上下文越长，通常要保存和读取的缓存也越多。
- **输入越长，未命中缓存时要做的预填充计算通常越多；输出越长，基本解码要走的步数也越多**。流式返回让用户更早看到文字，但并没有省去生成这些 Token 的计算。

</details>

### 7.4 temperature、top-p、top-k 分别是什么？不同场景应该怎样设置？ {#sampling-params}

**考察重点**：三个参数怎样影响 Token 的选择，以及不同任务适合从什么取值开始评测。

**相关内容**：[采样参数](#采样参数)、[输出一致性](#输出一致性)、[模型幻觉](./hallucination.mdx)。

<details>
<summary>参考回答</summary>

**回答要点**

1. **temperature 改变候选 Token 被选中的概率**。温度大于 0 且小于 1 时，高分候选更占优势；大于 1 时，分布更平坦，较低分候选更容易被选中。接口一般把温度为 0 当作每步直接选最高分候选处理。
2. **top-k 只留下概率最高的 k 个候选，top-p 则从高概率候选开始累加，保留累计达到 p 的最小集合**。因此，top-k 固定数量，top-p 留下的数量取决于概率分布。
3. **抽取、分类和工具调用可以从低温度开始测试，创作可以比较较高温度的效果**。先调 temperature 或 top-p 中的一项，更容易看清调整带来的影响。模型和接口是否支持这些参数，也要先确认。

**进一步探索**

- **`top-p=0.9` 保留多少个候选，要看概率怎样分布**。候选概率为 0.6、0.25、0.1、0.05 时，`top-k=2` 留两个，`top-p=0.9` 留三个，因为前两个加起来只有 0.85。如果第一个候选的概率已经达到 0.9，同样的 top-p 就只保留一个。
- **低温度不会给模型补充事实依据，仍可能让它稳定地产生错误答案**。它只是让高分候选更容易被选中，答案是否可靠还要看证据。

</details>

### 7.5 temperature 已经设为 0，为什么输出仍然不一致？ {#temperature-zero-nondeterminism}

**考察重点**：为什么每步都选最高分 Token，仍可能得到不同的回答。

**相关内容**：[采样参数](#采样参数)、[输出一致性](#输出一致性)。

<details>
<summary>参考回答</summary>

**回答要点**

1. **温度为 0 通常意味着每步选最高分 Token，但算出的分数仍可能变化**。浮点数只能保留有限精度，服务端并行计算的顺序不同，结果就可能有细微差别。
2. **两个最高分候选很接近时，这点误差就可能让模型选中另一个 Token**。这个 Token 会进入后续上下文，接下来的预测依据变了，整段回答也可能随之变化。

**进一步探索**

- **用户最后一句话相同，不等于模型收到的完整输入相同**。排查时要核对模型版本、系统提示、历史、检索内容和工具定义，并确认采样设置已经生效。把这些变化排除后，仍可能存在上面的计算差异。

</details>

### 7.6 如何让 LLM 每次输出的结果尽量一致？ {#output-consistency}

**考察重点**：哪些条件需要固定，以及为什么这些措施仍不能保证逐字复现。

**相关内容**：[输出一致性](#输出一致性)、[结构化输出](../prompting/prompt-engineering.mdx#结构化输出)、[前缀缓存与结果缓存](../safety/latency-cost-scaling.mdx#前缀缓存与结果缓存)。

<details>
<summary>参考回答</summary>

**回答要点**

1. **固定同一个模型版本，并确保每次发送的完整输入相同**。除了用户消息，系统提示、历史、检索文档、工具定义和工具结果都要保持一致。
2. **在模型支持时降低温度，可以减少采样带来的变化**。即使这些条件都固定，服务端的计算差异仍可能影响选出的 Token，所以重新生成只能尽量一致，不能保证逐字相同。

**进一步探索**

- **格式需要固定时，可以使用模型支持的结构化输出，约束字段和类型**。字段中的值是否符合事实和业务规则，仍然需要校验。
- **结果缓存能让相同请求返回已有答案，但要先确认权限、数据版本和时效仍然满足要求**。这时没有重新生成，而是直接返回了上次的结果。

</details>

### 7.7 回答很短却耗尽输出预算，应怎样解释？ {#reasoning-budget}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：推理 Token、可见回答与输出预算的关系。

**相关内容**：[Token 用量与费用](#token-用量与费用)、[上下文窗口](#上下文窗口)、[延迟的组成](../safety/latency-cost-scaling.mdx#延迟的组成)。

<details>
<summary>参考回答</summary>

**回答要点**

**在采用统一输出预算的模型中，内部推理也会消耗输出预算，可见回答只是其中一部分。** 推理 Token 通常不会完整展示给用户，所以不能根据回答长短判断实际用量。

例如总预算为 1000 个 Token，内部推理用了 900 个，就至多剩下 100 个用于回答。达到上限时，生成就会停止，即使回答还没写完。

**进一步探索**

- **提高输出上限，仍要留意上下文窗口的剩余空间**。窗口限制的是输入与输出的总量，输出上限限制的是本次生成量。
- **推理强度影响模型投入多少推理，与输出上限是不同的设置**。是否可调、怎样设置，要看具体模型。
- **短回答也可能等很久，因为内部推理同样需要时间**。分析耗时时，应结合实际推理用量，不能只看最终显示了多少字。

</details>
