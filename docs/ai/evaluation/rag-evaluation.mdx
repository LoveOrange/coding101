# RAG 评估

**RAG 评估**把一次问答拆成检索和生成两段分别衡量，再检查最终回答的质量。之所以要拆开，是因为只看答案对不对，没法知道错在哪一段：系统可能根本没找到证据，也可能找到了证据，却在生成时漏掉了关键条件。两种错误的修法完全不同，前者要改切分、检索或重排，后者要改上下文组装或提示。

要做好 RAG 评估，需要抓住三点：每一层用什么指标、指标需要什么样的标注；评测集怎样构造，才能既检查证据又检查答案；答案出错时，怎样沿着证据处理链路和对照实验，定位问题出在哪一层。

## 1. 面试核心 {#core}

- Recall@K 衡量前 K 项**覆盖了多少相关证据**，MRR 衡量**首个相关结果排得有多靠前**，是各问题首个相关项排名倒数的均值。[卡](#rag-metrics)
- 忠实度衡量回答中的陈述**是否得到检索文档支持**，答案正确率衡量**结论是否符合事实**。文档过期时，两者会给出不同的判断。[卡](#rag-metrics)
- 无检索、实际检索和理想证据**三组对照**，可以帮助区分检索缺证据和生成误用证据。[卡](#oracle-context)
- 评测样本要**关联问题、原文证据和文档版本**，并按问题类型分层，这样才能判断回答是缺少依据，还是依据已经过期。[卡](#rag-eval-dataset)
- 比较两套方案时，要**固定数据快照、生成配置和测量预算**，再分别比较各类问题的效果、延迟与费用。[卡](#compare-rag-systems)

## 2. 分层指标 {#分层指标}

RAG 的指标分三层：检索层看证据找没找全、排得靠不靠前，生成层看模型怎样使用这些证据，端到端从用户角度看答案对不对、引用能否支持结论。

| 层次 | 指标 | 含义 |
| --- | --- | --- |
| 检索 | Recall@K | 已召回相关项占全部相关项的比例。 |
| 检索 | Precision@K | 前 K 项中相关项的比例。 |
| 检索 | MRR | 各问题首个相关项排名倒数的均值。 |
| 检索 | NDCG@K | 按位置折扣累计相关性，再归一化。 |
| 生成 | 忠实度 | 陈述受到检索文档支持的程度。 |
| 生成 | 答案相关性 | 回答对问题的针对程度。 |
| 端到端 | 正确率 | 结论满足参考答案或验收标准的比例。 |
| 端到端 | 引用正确率 | 引用确实支持对应结论的比例。 |

### 2.1 检索指标与标注单位 {#检索指标与标注单位}

计算检索指标之前，要先约定什么算一个**相关项**。它可以是一篇文档、一个文本块，也可以是原文中支持答案的一段文字。单位不同，同一次检索算出来的分数也不同。

设人工标注的相关项集合为 R，检索结果去重后的前 K 项为 T。下面几个公式分别衡量覆盖率、相关项占比和排序质量：

```text
Recall@K = |R ∩ T| / |R|
Precision@K = |R ∩ T| / K
RR = 1 / 第一个相关项的排名
MRR = 所有问题 RR 的平均值
DCG@K = Σ(i=1..K) (2^rel_i - 1) / log2(i + 1)
NDCG@K = DCG@K / IDCG@K
```

Recall@K 看相关证据找全了多少，Precision@K 看返回的结果里有多少是相关的。RR（倒数排名）只关心第一个相关项排在第几，MRR 再对所有问题的 RR 取平均；前 K 项里一个相关项都没有时，这个问题的 RR 记为零。

NDCG 进一步考虑不同结果的相关程度。公式中的 `rel_i` 是第 i 项的相关性等级，位置越靠后，它贡献的分数越小。IDCG 是把全部已标注结果按相关性理想排序后，前 K 项的 DCG，用它做归一化后，不同问题之间才能比较。上式用 `2^rel_i - 1` 表示相关性带来的收益，称为指数增益；也可以直接用 `rel_i` 作为线性增益，但比较方案时要固定用同一种定义。

看一个例子：R 有 4 项，前 5 项命中了其中 2 项，那么 Recall@5 为 0.5，Precision@5 为 0.4。如果首个相关项排在第 2 位，RR 就是 0.5。另一个常见指标 Hit@K 只检查是否命中了任意一个相关项，所以它说明不了证据是否已经找全，对需要多处证据的问题尤其不够。

比较切分方案时要特别小心。切分策略一变，同一段证据会落进不同的块，甚至分散到多个块里，按块 ID 计分就失去了可比性。这时应按原文证据区间对齐，并对重复的块去重，避免重复计分。

还有两个计算边界要事先约定。返回结果少于 K 时，上式中的 Precision@K 仍以 K 为分母。没有相关证据的问题，Recall@K 的分母为零，没法计算，要单独评估拒答。

### 2.2 生成指标与证据条件 {#生成指标与证据条件}

检索找到了相关文档，还要判断回答是否正确使用了它们。这一层要分清三个指标：

- **忠实度**检查回答中的每条陈述是否得到检索文档支持。用受支持的陈述数除以陈述总数，就得到一个比例。
- **答案相关性**检查回答是否针对用户的问题。每句话都有依据但答非所问，仍然要扣分。
- **事实正确性**检查结论是否符合真实情况。文档过期或有误时，忠实复述也会给出错误答案。

Ragas 是一个提供这类评估指标实现的框架。它的 Faithfulness 使用回答和检索上下文，先把回答拆成陈述，再逐条判断是否受上下文支持。这样能定位到具体哪句话缺少依据，比笼统打一个总分更容易复查。

Ragas 的 Answer Relevancy 则从回答反向生成问题，再比较这些问题与原问题的向量相似度。也就是说，它检查的是回答和问题是否相关，与逐条核对事实依据是两回事。这类由模型充当评审的结果，都要用人工标注抽样校准。

不同指标需要的输入不同。比如按相关项 ID 计算 Recall，需要人工标注相关项；部分正确性或上下文召回指标则需要参考答案。所以选指标时，先确认具体实现要哪些输入，再准备标注。

### 2.3 拒答与引用 {#拒答与引用}

资料中没有答案时，系统应该说明无法回答；资料足够时，应该正常作答。所以评测要同时看两个数：无答案问题的正确拒答率，和有答案问题的误拒率。只看前者，一个什么都拒答的系统也能拿到高分。

引用同样要看两个数：**引用正确率**衡量已经给出的引用是否支持对应结论，**引用覆盖率**衡量需要证据的结论有没有附上支持它的引用。空回答或没有引用的样本要单独标记，否则「没有可检查的内容」会被当成「检查通过」。

## 3. 评测集 {#评测集}

评测集要能同时回答两个问题：证据找对了吗，答案答对了吗。所以每个样本除了问题，还要记录知识库版本、相关文档或块的 ID，以及原文证据的位置；要判断事实正确性时，再加上参考答案。

样本优先来自真实用户问题，也可以请领域专家编写。用模型根据文档生成问题和参考答案时，要由人工审核，并确认哪些原文支持答案。覆盖范围从三个维度检查：

- 文档类型要包含业务实际使用的正文、表格或扫描件等格式。
- 问题类型要覆盖事实查询、比较、多跳和无答案问题。**多跳问题**是需要结合多处证据才能得出答案的问题。
- 难度要覆盖简单查询、带多个条件的问题和业务边界场景。

标注证据时，要包含所有合理的证据。生成问题时会记录它的来源块，但不能把这个原块当成唯一答案；真实问题则由人工寻找并标注相关来源。否则系统找到另一段同样有效的证据，也会被误判为检索失败。

公开文档还有一个陷阱：其中的事实可能已经被模型在训练中记住，系统不检索也能答对。这会高估检索效果，掩盖证据缺失的问题。应对办法是加入可控的私有事实或新事实，并设置只给问题、不给证据的无检索基线。注意较新的日期本身证明不了模型没见过这些内容，评测仍要核对引用和证据的使用情况。

开发数据和留出数据按来源文档分组，相似的问法也放在同一组，避免近似样本同时出现在两边。文档更新后，同步更新参考答案、相关 ID 和证据位置，让评测依据和知识库版本保持一致。

## 4. 召回失败的排查 {#召回失败的排查}

「文档中有答案」只说明原始文件里有证据。证据还要经过解析、切分和排序，才能进入模型的最终输入，任何一步都可能把它弄丢。所以排查时要沿着证据处理链路，找到它在哪一步丢失：

1. **入库与权限**：按文档 ID 或关键词查询索引，确认文档已经处理完成，再核对版本和用户权限，看是否被错误过滤。
2. **文档解析**：把块中的文字和原文件对照，重点检查表格、扫描件和特殊格式，确认目标内容没有乱码、缺行或丢失列名。
3. **文本切分**：检查答案是否跨块，标题和例外条件是否完整。块过大时，多个主题混在一起，也会影响检索匹配。
4. **查询表达**：对照用户问题和文档用词，检查口语、缩写和正式术语的差异。可以用查询改写或同义词扩展补足表达，再核对实体、时间和条件有没有被改错。
5. **检索范围**：检查 Top-K 是否过小、相似度阈值是否过高、元数据过滤是否误伤。ANN 是只搜索部分候选的近似最近邻检索，可以与精确向量检索比较，判断是否因近似搜索漏掉了结果。
6. **融合与重排**：如果粗召回里已经有证据，就查看融合、重排和截断的记录，核对重排分数与截断阈值，定位证据在哪一步被淘汰。
7. **领域适配**：用领域问题集检查嵌入模型和重排模型能否识别专业术语。确认不适配后，再比较更换模型或用领域数据微调的效果。

BM25 根据词项匹配给文档打分，可以补充向量检索在专有名称和关键词上的不足。混合检索与重排的具体方法见[混合检索与重排序](../rag/hybrid-search-rerank.mdx)。

修复时，先用同一条失败样例确认原因，再跑完整的回归集，并把这条样例纳入其中。总的判断方向是：检索指标低，优先查检索链路；检索指标高而答案差，重点查上下文组装和生成。后一种情况下仍要核对证据时效、标注是否完整，以及多跳问题需要的证据是否齐全。

### 4.1 无检索与理想证据对照 {#无检索与理想证据对照}

要进一步区分检索问题和生成问题，可以固定生成模型、提示和输出预算，只改变提供的证据，运行三组对照：

1. **无检索组**只给问题，看模型靠已有知识能否回答。
2. **实际检索组**提供系统的检索结果，反映当前系统的表现。
3. **理想证据组**提供人工确认的完整证据，看证据齐全时模型能否答对。

实际组差、理想组好，说明证据齐全时模型能答对，问题在证据获取和组装链路。两组都差，就要继续检查生成、问题定义和评分标准。无检索组也能答对时，要核对模型到底有没有使用提供的证据。

这些对照给出的是诊断线索，单次结果不足以证明原因。可以重复运行，再去掉关键证据或换成无关文档，观察答案和引用怎样变化，才能进一步判断模型是否真的依赖这些证据。

比较两套系统时，同样要固定知识快照、测试问题和生成配置，并统一测量预算。除了检索、答案质量和拒答表现，还要记录延迟、费用和维护成本：

- 比较 P95 延迟，看较慢请求的等待时间能否接受。
- 比较单次查询费用，以及索引构建和更新的成本。
- 检查系统对文档格式的适应性、代码可维护性和监控能力。

效果接近时，优先选更简单、成本更低的方案。两套系统各有所长时，可以按问题类型组合使用，但组合后仍要用同一评测集重新验收。

**RAG 要分别评估检索、生成和端到端结果，再结合延迟与成本判断效果。**

**考察重点**：能沿解析、切分、查询与排序链路定位证据丢失的位置，并给出验证方法。

**相关内容**：[召回失败的排查](#召回失败的排查)、[文档解析与切分](../rag/chunking.mdx)、[混合检索与重排序](../rag/hybrid-search-rerank.mdx)。

<details>
<summary>参考回答</summary>

**应沿证据处理链路找到目标内容在哪一步丢失，再针对该环节修复。**

1. 按文档 ID 或关键词查索引，确认入库完成、版本有效、用户有权访问。
2. 对照原文检查解析结果，尤其留意表格、扫描件和特殊格式是否丢了内容。
3. 检查答案是否跨块、块是否过大，以及标题和例外条件是否保留。
4. 比较口语、缩写与文档术语，用查询改写或同义词扩展补足表达；BM25 可以补充关键词匹配。改写后再核对实体与条件。
5. 检查 Top-K、相似度阈值和过滤条件，并对比精确向量检索与 ANN 的结果。
6. 如果粗召回已有证据，再核对融合、重排分数和截断阈值。
7. 用领域样本确认模型是否适配，必要时比较更换或微调嵌入模型。

每次修改先验证这条样例，再做全量回归，并把样例加入评测集。

</details>

### 5.3 RAG 评测集怎样构造？公开文档可能已进入模型预训练数据，这会怎样影响评测？ {#rag-eval-dataset}

**考察重点**：能构造问题与证据标注，并用无检索基线判断训练记忆是否掩盖检索问题。

**相关内容**：[评测集](#评测集)。

<details>
<summary>参考回答</summary>

**评测集要把问题与原文证据对应起来，并防止模型的训练记忆掩盖检索缺陷。**

每条样本记录问题、知识库版本、相关文档或块的 ID，以及证据位置；检查事实正确性时再提供参考答案。问题覆盖事实、比较、多跳和无答案场景。优先采用真实用户问题，再由专家补充；模型生成的问题和答案要由人工审核。

公开文档中的事实可能已经进入预训练，导致不检索也能答对，从而高估检索效果。所以要加入可控的私有事实或新事实，并运行无检索基线。基线已经答对的题，仍要通过引用和证据依赖检查，判断检索是否真的起了作用。开发与留出数据按来源和相似问题分组，文档变化后同步更新答案和证据标注。

</details>

**题型**：综合题

**考察重点**：能在统一条件下比较分场景效果，再结合延迟、费用和维护成本选择方案。

**相关内容**：[分层指标](#分层指标)、[评测集](#评测集)。

<details>
<summary>参考回答</summary>

**应在统一条件下比较分场景效果，再结合延迟、费用和维护成本选择方案。**

两套系统使用同一知识快照、测试问题和生成配置，关键任务重复运行。分别统计检索、忠实度、相关性、答案正确率、引用和拒答表现，并按问题类型查看差异，才能发现总分掩盖的退化。

再比较 P95 延迟、单次查询费用，以及索引构建和更新成本；文档格式适配、代码可维护性和监控能力也会影响长期使用。效果接近时，优先选择简单、成本低的方案。如果按场景组合两者的优势，组合后仍要用同一评测集重新验收。

</details>

**考察重点**：能解释三组对照分别提供什么信息，以及为什么还需要重复验证和轨迹归因。

**相关内容**：[无检索与理想证据对照](#无检索与理想证据对照)。

<details>
<summary>参考回答</summary>

**理想证据对照检查证据齐全时模型能否答对，再与实际检索的结果比较，从而定位问题所在。**

固定生成配置，分别只给问题、给实际检索结果、给人工确认的完整证据。理想组正确、实际组错误时，重点检查证据获取和组装链路；理想组也错误时，继续检查生成、问题定义和评分标准。

无检索组答对时，模型可能只是在复述训练知识，还要核对引用和证据依赖。重复运行，并通过移除关键证据观察答案变化，再结合轨迹归因，判断才更可靠。
