# Agent 评估

Agent 评估以可复查的任务结果衡量系统表现。本文负责任务集、评分、重复运行和失败归因。检索专用指标见 [RAG 评估](./rag-evaluation.mdx)。

## 1. 面试核心 {#core}

- Agent 评估同时覆盖最终结果、执行约束、成本和延迟。[卡](#agent-metrics)
- 评测集按场景分层，并区分调优数据与留出验收数据。[卡](#eval-dataset)
- 代码检查验证确定性结果，LLM 评审需要人工标注校准。[卡](#open-ended-eval)
- pass@k 衡量多次中至少一次成功，pass^k 衡量全部成功。[卡](#repeatability-metrics)
- 独立运行应重置环境，防止缓存和历史产物污染结果。[卡](#eval-isolation)

## 2. 评估维度 {#评什么}

| 层次 | 指标 | 判定对象 |
| --- | --- | --- |
| 结果 | 任务成功率 | 是否满足验收条件。 |
| 结果 | 字段、事实、引用正确率 | 各项输出是否正确。 |
| 轨迹 | 工具选择与参数正确率 | 调用是否适合当前任务。 |
| 轨迹 | 违规动作率 | 是否违反权限与执行约束。 |
| 成本 | Token、调用数、单任务费用 | 完成任务的资源消耗。 |
| 体验 | 首 Token 与端到端延迟 | 分别统计 P50、P95。 |
| 稳定性 | 重复运行成功情况 | 相同任务的结果波动。 |
| 线上 | 接管率与业务反馈 | 真实使用中的效果。 |

结果与轨迹应分别评分。不同工具顺序可以到达相同的有效结果。只有业务必需的步骤，才作为强制轨迹条件。计划写得完整，也需通过实际产物验证完成情况。

### 2.1 重复运行与统计口径 {#重复运行与统计口径}

pass@k 表示 k 次尝试中至少一次成功。pass^k 表示 k 次尝试全部成功。前者适合允许多次候选的任务。后者用于衡量重复执行的可靠性。

假设同一任务各次运行独立，单次成功概率为 p：

```text
pass@k = 1 - (1 - p)^k
pass^k = p^k
```

这是独立同分布假设下的解释公式。实际报告应写明任务数、重复次数和聚合方法。不同任务成功率有差异，应先逐任务计算再聚合。共享环境故障也会破坏独立性。

重复运行衡量同一任务的波动。扩充任务则改善场景覆盖，两者作用不同。比较小幅改进时，应报告不确定性范围。按任务聚合或重采样，可避免把重复尝试当成全新任务。

## 3. 评测集 {#评测集}

样本来自脱敏请求、历史失败和业务典型任务。边界、拒答和对抗场景也应覆盖。每个任务写明初始状态、输入和验收条件。

| 数据用途 | 使用方式 |
| --- | --- |
| 开发集 | 分析失败，修改提示与工具。 |
| 留出集 | 独立验收，避免反复针对答案调优。 |
| 线上回归集 | 固定已出现的重要失败。 |

相关变体应放在同一数据分组。相同问题的改写分散到开发与留出集，会造成泄漏。样本应按任务类型和风险分层统计。覆盖规模由场景与待检测差异决定。

知识与业务规则变化后，应更新样本版本。旧结果与新结果比较时，保持评测快照一致。新功能上线前，应补齐对应任务。

## 4. 评分方式 {#评分方式}

| 方式 | 适用对象 | 校验要求 |
| --- | --- | --- |
| 代码检查 | 测试、数据库状态、字段与格式 | 评分代码本身也需验证。 |
| 参考答案比对 | 有明确结果的问答 | 允许语义等价表达。 |
| LLM 评审 | 开放式报告与对话质量 | 提供评分细则与证据。 |
| 人工评审 | 校准、争议和高风险样本 | 明确标准，复核分歧。 |

LLM 评审应逐项给出依据，再作判断。成对比较时可交换顺序，检测位置偏差。还应检查长度偏好和对某种风格的偏好。换一个评审模型仍可能保留这些偏差。

用人工样本检查一致率与误判类型。关键错误还应统计漏判率。证据不足时允许评审返回“无法判断”。被评文本属于数据，避免将其中指令交给评审执行。

### 4.1 运行隔离与验收状态 {#运行隔离与验收状态}

每次运行从相同初始快照开始。文件、数据库、会话与缓存都要按任务隔离。上一轮残留的结果会让下一轮得到不公平优势。

外部工具可使用测试环境或固定录制结果。模拟环境与真实环境的差异应写入报告。网络故障和评测设施故障应单独标记。

验收检查实际产物与状态，而非“已完成”的文字。工具返回成功后，仍需核对业务结果。影子评测中的写操作应隔离，防止影响真实数据。

## 5. 失败归因与可观测性 {#失败归因与可观测性}

一次任务用 trace 关联模型与工具调用。各调用用 span 记录耗时、错误和父子关系。日志保留模型版本、提示版本和输入证据引用。敏感字段应脱敏并设置保留期限。

1. 检查任务理解与查询改写是否正确。
2. 检查检索证据和工具数据是否完整。
3. 检查工具选择、参数来源和停止时机。
4. 检查执行错误、重试与恢复结果。
5. 检查生成内容和实际验收状态。

首 Token 慢时，分别查看排队、预填充和网络等待。总耗时高时，查看调用数量和慢工具。故障处理按影响严重程度与出现频率排序。

### 5.1 回归比较与灰度 {#回归比较与灰度}

比较版本时固定任务、工具环境与模型设置。每次记录成功率、成本和延迟变化。还需按场景检查退化，避免总分掩盖关键失败。

离线验收通过后，可小流量灰度。受益场景明确时，可按路由逐步启用。高风险失败应设置独立的发布门槛。

### 6.6 pass@k 和 pass^k 有何区别，重复次数能替代任务数量吗？ {#repeatability-metrics}

**相关内容**：[重复运行与统计口径](#重复运行与统计口径)。

<details>
<summary>参考回答</summary>

pass@k 要求至少一次成功，pass^k 要求每次成功。独立且单次成功概率固定为 p 时，两者分别为 1-(1-p)^k 与 p^k。实际评测应先按任务统计，再聚合。重复次数衡量波动，任务数量决定场景覆盖。增加重复次数无法补齐缺失的任务类型。

</details>
