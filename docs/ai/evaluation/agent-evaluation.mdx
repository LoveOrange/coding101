# Agent 评估

Agent 评估用一组代表性任务反复运行 Agent，按事先定义的标准判断结果，并统计成功率、成本、延迟等指标。模型输出有随机性、执行路径不固定，靠试几个例子判断“效果不错”无法支撑上线和迭代决策。本文讲评测集、评分方式、指标、失败归因和回归流程，以及线上的可观测性。

## 1. 面试核心 {#core}

- 评估对象分三层：最终结果是否正确（任务成功率），执行轨迹是否合理（工具选择、步数、错误恢复），以及成本与体验（延迟、Token、人工接管率）。[卡](#agent-metrics)
- 评测集来自真实请求和失败样例，按场景分层，包含正常、边界和应该拒绝的任务；新场景上线前先补用例。[卡](#eval-dataset)
- 评分优先用代码可验证的标准（测试通过、数据库状态、字段比对）；开放式输出用评分细则加 LLM 评审，并用人工标注校准评审结果。[卡](#open-ended-eval)
- 失败归因沿执行链路逐段检查：输入理解、检索、工具选择、参数、工具执行、生成。完整的轨迹记录是归因的前提。[卡](#bad-case-attribution)
- 每次修改都在完整评测集上回归，多次运行取统计结果；局部提升伴随整体下降时，按场景权重和失败严重程度决定是否上线。[卡](#regression-check)

## 2. 评什么 {#metrics}

| 层次 | 指标 | 说明 |
| --- | --- | --- |
| 结果 | 任务成功率 | 按验收标准判定完成的比例 |
| 结果 | 正确性分项 | 字段准确率、答案事实正确率、引用正确率 |
| 轨迹 | 工具调用准确率 | 选对工具、参数正确的比例 |
| 轨迹 | 步数、重复调用 | 是否绕路，是否出现循环 |
| 轨迹 | 违规动作 | 越权、未确认的高风险操作，应为零 |
| 成本 | Token、调用次数、单任务费用 | 和成功率一起比较方案 |
| 体验 | 端到端延迟、首 Token 延迟 | P50、P95 |
| 稳定性 | 多次运行的一致性 | 同一任务运行 k 次的成功比例 |
| 线上 | 人工接管率、用户反馈、业务指标 | 离线评测无法覆盖的真实效果 |

模型输出有随机性，同一任务要运行多次。常用两种统计：pass@k（k 次中至少成功一次，衡量能力上限）和 pass^k（k 次全部成功，衡量稳定性）。面向用户的生产系统更关心后者。

## 3. 评测集 {#dataset}

- **来源**：线上真实请求抽样（脱敏后）、历史 Bad Case、业务方提供的典型场景、人工构造的边界和对抗用例。
- **分层**：按场景、难度、是否需要工具、是否应该拒绝分组，分别统计，避免简单任务掩盖难任务的退化。
- **标注**：每个任务写明验收标准，能自动判定的写成检查代码，例如“订单状态变为已取消且退款记录存在”。
- **规模**：起步时几十个高质量任务就能发现主要问题；随着失败样例积累扩充。规模取决于场景数量和需要检测的差异大小：要检测几个百分点的变化，样本量需要足够大，或增加重复运行次数。
- **维护**：新功能上线前先加用例；线上新出现的失败加入评测集；定期检查用例是否过时。

## 4. 评分方式 {#grading}

| 方式 | 适用 | 注意 |
| --- | --- | --- |
| 代码检查 | 结果可验证：测试、状态、字段、格式 | 最可靠，优先使用 |
| 参考答案比对 | 有标准答案的问答 | 精确匹配过严，可以用语义比对 |
| LLM 评审 | 开放式输出：摘要、报告、对话质量 | 需要评分细则和校准 |
| 人工评审 | 校准、抽查、高风险场景 | 成本高，用于建立基准 |

**LLM 评审**（LLM-as-Judge）的做法：给评审模型明确的评分细则（每个维度的标准和示例），要求先给出依据再打分；对比两个方案时交换顺序各评一次，消除位置偏差；评审模型与被评模型不同，减少自我偏好。用一批人工标注样本计算评审结果与人工的一致率，一致率不够时修改细则，而不是直接相信评审分数。

评审模型也会出错，所以对关键结论抽样人工复核；能拆成可验证子项的（“是否包含以下五个要点”“引用是否存在于原文”）尽量拆开，用代码或简单判断完成。

## 5. 失败归因与可观测性 {#diagnosis}

线上和评测中的每一次运行都应记录完整轨迹：输入、每轮的上下文摘要、模型输出、工具调用和参数、工具结果、耗时和 Token。常用 OpenTelemetry 风格的 trace，把一次任务作为一个 trace，每次模型调用和工具调用作为 span。

归因按链路逐段排查：

1. **输入理解**：意图识别或查询改写是否正确。
2. **信息获取**：检索是否召回正确材料，工具是否返回正确数据。
3. **决策**：是否选择了正确的工具、参数是否正确、是否过早停止。
4. **执行**：工具是否报错、超时，错误是否被正确处理。
5. **生成**：材料正确时回答是否忠实，格式是否正确。

把失败按原因分类统计，优先处理占比最高的一类。延迟问题按 span 耗时定位：首 Token 慢看模型排队和输入长度，整体慢看步数和慢工具。

**出现公司**：字节跳动、阿里云、拼多多

**考察重点**

- 基线、相同环境下的回归比较和灰度。
- 分场景统计与权衡上线决策。

**相关内容**：[评什么](#metrics)、[评测集](#dataset)。

<details>
<summary>参考回答</summary>

每次修改都与基线在同一评测集、同一模型版本和参数、同一工具环境下比较，多次运行取统计结果，避免把随机波动当作改进。离线通过后灰度上线，与旧版本对比线上指标，也可以用影子流量在不影响用户的情况下运行新版本。

出现局部提升、整体下降时，按场景分层查看是哪些场景退化、退化的严重程度和流量占比。如果退化发生在高流量或高风险场景，不上线；可以把改动限定在受益场景（按路由启用），或继续修改直到不再退化。退化用例加入回归集，防止以后再次出现。

</details>
