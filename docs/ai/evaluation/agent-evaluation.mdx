# Agent 评估

**Agent 评估**是用一组代表性任务反复运行系统，再按事先定义的标准检查结果。之所以要「一组」「反复」，是因为模型输出有随机性，工具调用的路径每次也可能不同：演示时成功的几个例子，说明不了系统能不能稳定完成任务。

要把 Agent 评估讲清楚，需要抓住四点：除了结果，还要检查哪些维度；重复运行的结果怎样统计；评测集和评分方式怎样设计，才能信得过分数；任务失败后，怎样沿执行链路找到最早出错的那一环，并在改版后确认没有引入新的退化。

## 1. 面试核心 {#core}

- Agent 评估要**同时检查任务结果、工具执行轨迹、成本和延迟**，只看成功率会漏掉绕路、越权和用重试堆出来的成功。[卡](#agent-metrics)
- 评测集要**按场景分层**，并**区分调优用的开发集和独立验收用的留出集**。[卡](#eval-dataset)
- 确定性的结果**优先用代码检查**，开放式质量才交给 LLM 评审，而 LLM 评审**需要人工标注校准**。[卡](#open-ended-eval)
- pass@k 是 k 次尝试中**至少一次成功**的概率，pass^k 是 k 次**全部成功**的概率。重复次数**不能替代任务覆盖**。[卡](#repeatability-metrics)
- 每次独立运行都要**重置环境**，防止缓存和上一轮的产物让成功率虚高。[卡](#eval-isolation)

## 2. 评估维度 {#评什么}

评估既要确认任务完成了，也要检查是怎么完成的。**执行轨迹**是一次任务中模型与工具调用的完整记录，靠它才能发现绕路、循环和越权操作。

| 层次 | 指标 | 判定对象 |
| --- | --- | --- |
| 结果 | 任务成功率 | 是否满足验收条件。 |
| 结果 | 字段、事实、引用正确率 | 各项输出是否正确。 |
| 轨迹 | 工具选择与参数正确率 | 调用是否适合当前任务。 |
| 轨迹 | 违规动作率 | 是否违反权限与执行约束。 |
| 成本 | Token、调用数、单任务费用 | 完成任务的资源消耗。 |
| 体验 | 首 Token 与端到端延迟 | 分别统计 P50、P95。 |
| 稳定性 | 重复运行成功情况 | 相同任务的结果波动。 |
| 线上 | 接管率与业务反馈 | 真实使用中的效果。 |

结果和轨迹要分开评分，因为不同的工具顺序可以到达同样有效的结果。只有业务上必须遵守的步骤，才作为轨迹的强制条件。比如转账前核对授权是业务约束，必须检查；两个互不依赖的查询谁先谁后，就不该扣分。

分析轨迹时，还要记录步数、重复调用和重规划次数。步数和重复调用能暴露绕路或循环，重规划次数反映计划是否频繁调整。规划能力要结合计划完成率来判断，并用实际产物验证是否真的完成。无依据的陈述、虚构的工具和编造的参数要分别统计，这样才能看出错误来自哪里。

越权操作和未经授权的高风险操作，目标次数应该是零。比较方案时，要把成功率和成本放在一起看，否则一个方案可以靠大量重试换来表面的提升。延迟分别报告 P50 和 P95，也就是 50% 和 95% 的请求能在多长时间内完成。

### 2.1 重复运行与统计口径 {#重复运行与统计口径}

同一个任务偶尔成功和每次都成功，对用户的意义完全不同，所以重复运行时要区分两个指标。**pass@k** 表示 k 次尝试中至少一次成功的概率，适合可以生成多个候选、再从中挑选的任务。**pass^k** 表示 k 次尝试全部成功的概率，衡量的是重复执行的可靠性，面向用户的生产系统更关心这一点。

假设同一任务各次运行独立，单次成功概率为 p：

```text
pass@k = 1 - (1 - p)^k
pass^k = p^k
```

比如 p 为 0.8、k 为 3 时，pass@3 约为 0.99，pass^3 约为 0.51。同一个系统，看前者几乎总能成功，看后者只有一半的机会连续三次成功。

这两个公式成立的前提是各次运行相互独立，并且同一任务的成功概率不变。现实中这个前提经常被打破，比如共享的工具服务出故障时，多次运行会一起失败。所以报告里要写明任务数、重复次数和聚合方法。不同任务的成功率差别很大，应先逐个任务计算，再汇总。

重复运行和扩充任务解决的是不同的问题：重复运行让已有任务的估计更稳定，扩充任务才能覆盖缺失的场景。要比较几个百分点的改进，需要足够多的任务，并报告统计结果的不确定性范围。

估计这个范围时，可以按任务重采样，也就是反复抽取任务、重新计算指标，看指标的波动有多大。按任务而不是按单次尝试抽样，能保留同一任务内多次尝试之间的关联，避免把它们当成互不相关的新任务，低估了不确定性。

## 3. 评测集 {#评测集}

评测集要覆盖系统实际面对的任务，也要留住已经出现过的失败。任务可以从四类来源取样：

- 从线上真实请求中抽样，脱敏后纳入评测。
- 把历史失败改写成可复现的任务。
- 请业务方提供典型场景，补齐主要业务流程。
- 人工构造边界、应该拒答和对抗场景，检查系统的处理边界。

每个任务都要写明初始状态、输入和验收条件。比如取消订单任务的验收条件是「订单状态变为已取消，且退款记录存在」，这条标准可以写成代码，同时检查两项结果。只检查 Agent 的回复里有没有「已取消」，是验收不出问题的。

调优和验收要用不同的数据，否则无法判断系统是学会了处理这类问题，还是只记住了这几道题的答案。数据按用途分成三种：

| 数据用途 | 使用方式 |
| --- | --- |
| 开发集 | 分析失败，修改提示与工具。 |
| 留出集 | 独立验收，避免反复针对答案调优。 |
| 线上回归集 | 固定已出现的重要失败。 |

同一个问题的不同改写，要放在同一个数据分组里。如果一部分进了开发集、另一部分进了留出集，系统在验收前就已经见过近似答案，这就是**数据泄漏**。

统计时按场景、难度、工具需求和拒答要求分组，高风险任务单独查看。这样才能看出难任务有没有退化，而不是被大量简单任务的成功掩盖。起步时，几十个高质量任务就足以发现主要问题，之后随失败样例的积累逐步扩充；但要检测小幅提升，就需要更多任务和统计分析。

知识和业务规则变化后，要同步更新样本版本，并检查旧用例是否仍然适用。比较新旧系统时，要用同一份固定的评测数据，也就是同一个**评测快照**。新功能上线前先补齐对应任务，线上出现的重要失败持续加入回归集。

## 4. 评分方式 {#评分方式}

评分方式取决于结果能不能直接验证。测试是否通过、数据库状态是否改变，优先用代码检查；报告写得清不清楚，就需要明确的评分细则。

| 方式 | 适用对象 | 校验要求 |
| --- | --- | --- |
| 代码检查 | 测试、数据库状态、字段与格式 | 评分代码本身也需验证。 |
| 参考答案比对 | 有明确结果的问答 | 允许语义等价表达。 |
| LLM 评审 | 开放式报告与对话质量 | 提供评分细则与证据。 |
| 人工评审 | 校准、争议和高风险样本 | 明确标准，复核分歧。 |

**LLM 评审**是让模型按评分细则判断输出质量。细则要写明每个维度的标准和示例，并要求评审先逐项给出依据，再打分。比如一份报告可以拆成要点覆盖、事实依据和结构完整性三个维度；引用是否存在于原文，可以单独交给代码检查。如果任务要求包含五个要点，也可以拆成五项分别判断，这样能直接看出漏了哪一项。

评审模型自身也有偏差，要专门检查。比较两个答案时，交换顺序各评一次，可以检测**位置偏差**，也就是评审偏爱排在某个位置的答案。此外还要检查评审是否偏爱长答案、特定文风或自己生成的回答。选一个不同于被评模型的评审模型，有助于减少自我偏好，但其他偏差仍要验证。

校准靠人工标注。用人工标注的样本计算评审与人工的一致率，并分析具体的误判类型；一致率不够时，修改细则或换一种评分方式。关键错误还要统计漏判率，关键结论抽样人工复核。人工评审成本高，适合用来建立基准、做校准和处理争议，而不是评每一条。

证据不足时，允许评审返回「无法判断」，不要逼它猜。被评文本要作为待分析的数据传入，避免其中的指令影响评分。

### 4.1 运行隔离与验收状态 {#运行隔离与验收状态}

重复运行比较的是同一起点上的表现，所以每次都要恢复到相同的初始快照，文件、数据库、会话和缓存都按任务隔离。否则上一轮生成的文件或缓存下来的答案会被下一轮直接用上，成功率就虚高了。

外部工具可以接入测试环境，也可以重放预先录制的固定结果。后者更容易复现，但要在报告中说明它与真实工具的差异。网络故障或评测设施本身的故障要单独标记，不能和 Agent 的决策错误混在一起统计。

验收以实际产物和业务状态为准。即使工具返回了成功，也要核对订单等业务记录是否达到了预期状态。**影子评测**会把线上请求复制一份给新版本运行，用户仍然使用旧版本的结果；这时新版本的写操作必须进入隔离环境，否则会修改真实数据。

## 5. 失败归因与可观测性 {#失败归因与可观测性}

失败归因是找出错误最早出现在哪一环，再把后面被它连带影响的步骤区分开。一个错误的检索结果，会导致后面的工具参数错、回答也错，修的却只该是检索。要做到这一点，一次任务中的模型和工具调用必须串成一条可追踪的记录。

**trace** 表示一次任务的完整链路，**span** 表示其中的一次模型调用或工具调用。span 记录父子关系、耗时和错误，用来还原调用顺序。OpenTelemetry 或 Langfuse 都可以记录这些信息。

排查需要保留下面这些调用信息，敏感字段要脱敏，并设置保留期限：

- 输入和每轮上下文的摘要，用来确认模型当时看到了什么。
- 模型输出、工具参数和工具结果，用来确认错误发生在调用前还是调用后。
- 模型版本、提示版本和证据引用，用来重现同一个任务。
- 耗时、Token 用量和错误，用来分析延迟与成本。

拿到轨迹后，沿着任务执行链路逐段检查：

1. 意图识别和查询改写是否与用户要求一致。
2. 检索到的文档和工具数据是否完整、正确。
3. 工具选择、参数来源和停止时机是否合理。
4. 工具是否报错或超时，重试和恢复是否成功。
5. 回答是否忠实于证据、格式是否正确，实际产物是否通过验收。

把失败按原因分类后，再按出现频率和影响严重程度安排修复。延迟问题同样按 span 分解：首 Token 慢，分别看排队、预填充和网络等待，其中输入长度会影响预填充时间；总耗时高，则看调用步数和慢工具。线上还要为错误率、延迟和成本设置告警，及时发现异常。

### 5.1 回归比较与灰度 {#回归比较与灰度}

验证一次修改是否有效，要让新旧版本在相同条件下运行：固定完整评测集、工具环境和模型设置，重复运行，再比较成功率、成本和延迟。结果要分场景查看，总分提升的同时，某些场景可能在退化。

离线验收通过后，可以把少量线上流量交给新版本，这称为**灰度发布**；也可以用影子流量比较两个版本，并隔离新版本的写操作。

发现退化后，结合这些场景的流量占比和失败严重程度决定是否发布。高流量或高风险场景明显退化时，应暂停发布并修复。如果收益只在部分场景得到验证，可以通过路由只对这些场景启用新版本。退化样例要加入回归集，高风险失败还应设置独立的发布门槛。

## 6. 面试题 {#面试题}

### 6.1 如何评估 Agent 系统的整体效果？除成功率和耗时外，还应关注哪些指标？ {#agent-metrics}

**题型**：综合题

**考察重点**：能分别说明任务结果、执行轨迹、成本与体验怎样衡量，并解释重复运行为何必要。

**相关内容**：[评估维度](#评什么)、[评分方式](#评分方式)。

<details>
<summary>参考回答</summary>

**Agent 的整体评估要同时覆盖结果、执行轨迹、成本、体验和稳定性。**

结果按验收标准判定，再分别统计字段、事实和引用的正确率。轨迹检查工具选择与参数，并记录步数、重复调用和违规动作。成本记录 Token、调用数和单任务费用，延迟分别报告首 Token 和端到端的 P50、P95。

规划能力要结合计划完成率和重规划次数，用实际产物核对结果。幻觉按无依据陈述、虚构工具或参数、虚报执行状态分别核验。同一任务重复运行后，用 pass^k 观察稳定性。上线后再结合人工接管率、用户反馈和业务指标，通过灰度与旧版本比较。

</details>

### 6.2 Agent 评测集多大？样本从哪里来？新增场景如何更新评测集？ {#eval-dataset}

**考察重点**：能说明样本从哪里来、怎样分层，以及如何确定规模和保持独立验收。

**相关内容**：[评测集](#评测集)。

<details>
<summary>参考回答</summary>

**评测集可以从几十个高质量任务起步，规模取决于场景覆盖和希望检测的改进幅度。**

样本来自脱敏后的真实请求、历史失败、业务典型场景和人工构造的边界用例。按场景、难度、工具需求和拒答要求分层，每个任务写清初始状态和验收标准。比如取消订单要同时检查订单状态和退款记录。

调优用开发集，验收用留出集，相似的变体放在同一组。任务数量决定覆盖范围，重复次数用于观察波动，所以报告要说明任务数、尝试数和失败分布。新场景先补用例，线上失败加入回归集，业务规则变化后同步更新样本版本。

</details>

### 6.3 没有标准答案的开放式任务怎么评测？用 LLM 评估结果，评估模型本身也有幻觉怎么办？ {#open-ended-eval}

**考察重点**：能将开放式质量拆成评分维度，并用人工标注识别和校准评审偏差。

**相关内容**：[评分方式](#评分方式)。

<details>
<summary>参考回答</summary>

**开放式任务可以按明确的细则分项评分，并用人工标注校准 LLM 评审。**

例如把报告质量拆成要点覆盖、事实依据和结构完整性，每项给出标准与示例。引用是否存在、必需字段是否齐全，用代码检查；其余维度让评审模型结合证据说明理由，再打分。

评审本身的偏差要单独检查：成对比较时交换答案顺序，检查位置偏差，同时检查长答案偏好和自我偏好。可以换用不同的评审模型，再用人工样本检查一致率和关键错误的漏判率。偏差明显时修改细则或更换评分方式，证据不足时允许返回「无法判断」。上线后对关键结论抽样人工复核，并结合用户反馈。

</details>

### 6.4 如何对 Agent 的 Bad Case 进行归因？如何利用可观测链路定位问题？ {#bad-case-attribution}

**考察重点**：能用 trace 和 span 还原执行链路，定位最早的错误，并将修复结果纳入回归。

**相关内容**：[失败归因与可观测性](#失败归因与可观测性)。

<details>
<summary>参考回答</summary>

**归因要沿完整轨迹找到最早的错误，再区分由它引发的后续失败。**

一次任务对应一个 trace，每次模型或工具调用对应一个 span。记录输入输出、参数、版本、耗时和用量，并对敏感内容脱敏。排查时沿着任务链路检查：

1. 意图识别和查询改写是否保留了用户要求。
2. 检索或工具是否拿到了正确、完整的数据。
3. 工具选择、参数来源和停止时机是否合理。
4. 工具是否报错、超时，恢复是否成功。
5. 生成内容与实际验收状态是否一致。

延迟按 span 分解：首 Token 慢时看排队、输入长度和网络等待，总耗时高时看步数与慢工具。失败按频率和严重程度排序，修复后加入回归集，并为错误率、延迟和成本设置告警。

</details>

### 6.5 迭代后怎么验证效果？出现“局部提升、整体负优化”怎么办？ {#regression-check}

**考察重点**：能在固定条件下比较版本，并结合场景流量和失败严重程度判断是否发布。

**相关内容**：[评估维度](#评什么)、[评测集](#评测集)。

<details>
<summary>参考回答</summary>

**迭代效果要在相同条件下与基线比较，并分别查看各类场景是否退化。**

固定评测集、模型设置和工具快照，重复运行后报告分场景指标和不确定性范围。这样能排除外部差异，避免把随机波动当成提升。离线通过后，再用灰度或隔离的影子流量与旧版本比较。

出现退化时，看涉及场景的严重程度和流量占比。高流量或高风险场景退化时应暂停发布，继续修复。如果只有部分场景受益，可以只对这些场景开放，并把退化样例留在回归集中。

</details>

### 6.6 pass@k 和 pass^k 有何区别，重复次数能替代任务数量吗？ {#repeatability-metrics}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：能区分至少一次成功与每次成功，并说明重复尝试和扩充任务各自解决什么问题。

**相关内容**：[重复运行与统计口径](#重复运行与统计口径)。

<details>
<summary>参考回答</summary>

**pass@k 衡量 k 次中至少一次成功，pass^k 衡量 k 次全部成功，重复次数无法替代任务覆盖。**

各次尝试独立、单次成功概率固定为 p 时，两者分别是 `1-(1-p)^k` 和 `p^k`。前者适合可以多出候选再挑选的任务，后者关注能否稳定执行。实际评测要先按任务计算再汇总，不要混用不同任务的成功概率。

多运行几次，能更清楚地看到同一任务的波动；但要知道系统能否处理其他场景，只能新增对应的任务。

</details>

### 6.7 Agent 离线成功率虚高，怎样检查评测环境泄漏？ {#eval-isolation}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：能检查环境残留和答案泄漏，并通过实际业务状态验收任务。

**相关内容**：[运行隔离与验收状态](#运行隔离与验收状态)。

<details>
<summary>参考回答</summary>

**先检查环境是否彻底重置，再检查答案是否进入了提示或开发数据。**

每次运行都要从相同、干净的快照开始。逐项检查文件、数据库、会话和缓存，确认上一轮留下的答案已经清除。再检查开发集与留出集是否包含同一问题的相似变体。

验收以实际产物和业务状态为准，基础设施失败单独记录。评测中的写操作要进入隔离环境，避免真实业务变化反过来影响测试结果。

</details>
