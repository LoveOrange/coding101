# 工具授权与执行沙箱

**工具授权**决定 Agent 能执行哪些动作、动作能影响哪些资源；**执行沙箱**限制代码、命令和进程实际能访问哪些文件和网络。两者都由程序强制执行，不依赖模型自觉，目的是在模型判断失误或被攻击时，把损失控制住。

两者管的是不同层面。授权回答的是「这个用户此刻能不能做这件事」，比如能不能删除这三个文件；沙箱回答的是「这段代码跑起来最多能碰到什么」，比如一个 Python 脚本能不能读到工作区外的密钥。只有授权，被放行的命令可能借子进程越界；只有沙箱，沙箱内允许的操作照样可能越权。

## 1. 面试核心 {#core}

- 工具授权根据**当前用户、动作、参数和目标资源**判断是否放行，限制越权访问、误操作和数据外泄。[卡](#tool-risks)
- 审批要**绑定具体动作和参数**，执行时还要**再检查一次当前权限和目标版本**。[卡](#tiered-authorization)
- **凭据由工具在程序侧注入**，不经过模型；敏感数据用引用传递，**取回真实值时再做一次授权检查**。[卡](#secrets)
- 执行沙箱通过**文件、网络、进程、资源额度和生命周期**五个维度的限制，约束代码实际运行时的影响范围。[卡](#sandbox)
- **命令白名单只筛选调用入口**，解释器和子进程实际访问了什么，要靠运行时沙箱约束。[卡](#sandbox-command-boundaries)

## 2. 风险分级 {#风险分级}

判断一次工具调用能不能放行，要同时看三件事：它做什么，处理什么数据，影响哪些对象。只看第一件是不够的，比如读文件是只读操作，但读的如果是凭据文件，照样有外泄风险。按风险大致可以分成四级：

| 级别 | 例子 | 策略示例 |
| --- | --- | --- |
| 只读 | 搜索、查询订单 | 在用户数据范围内允许 |
| 可逆写入 | 工作区编辑、创建草稿 | 按会话授权，保留恢复手段 |
| 高风险或对外 | 删除、支付、邮件、发布 | 校验具体授权，必要时审批 |
| 禁止 | 越权读取凭据、扩大权限 | 执行层拒绝 |

分级不能只按工具来分，因为同一个工具的风险随参数变化。`run_command("ls")` 只是列出目录，`run_command("rm -rf /")` 却会尝试删除文件。所以程序要按「工具 + 参数 + 目标范围」来判断；编码 Agent 可以结合命令白名单和路径限制做这类检查。

权限还要跟着发起任务的用户走。工具即使用一个服务账号连接数据库，查出来的结果也要按当前用户的数据权限过滤。否则普通用户只要让 Agent 去查，就能借服务账号的高权限读到别人的数据。

可逆和不可逆的区别也会影响策略。工作区编辑可以按会话授权，出错了用版本管理或快照恢复；外部发布影响的是工作区之外的对象，撤不回来，要用更严格的授权策略。用户已经明确授权的具体动作可以直接执行，超出范围时再请求确认。

## 3. 确认与二次校验 {#确认与二次校验}

审批不是一次性的放行。用户批准时看到的对象，到真正执行前可能已经变了：用户的权限被收回了，或者要覆盖的文件已经被别人改过。所以一个需要审批的动作，要按下面的流程走：

1. 模型提出动作和参数，由程序接收这份执行请求。
2. 程序检查参数格式、当前身份和目标范围，拒绝超出授权的请求。
3. 需要审批时，展示具体对象、参数和影响。比如「删除 3 个文件：a、b、c」，让用户批准、修改或拒绝。
4. 程序保存动作摘要、目标版本、有效期和审批人，把审批与这次动作绑定。
5. 执行前原子领取批准记录，确保并发执行器只有一个能领取成功，再检查权限与目标版本。
6. 执行获准的动作，记录审批时间、实际参数和执行结果，供后续审计。

第 5 步就是**执行期二次校验**：在真正操作的那一刻，再核对一次当前权限和目标状态。参数被修改、或者目标版本已经过期，都要重新校验授权。版本检查还要和写入原子地一起完成，否则检查通过到写入之间，目标仍可能再被改一次。任务被重复恢复时，还要靠[幂等机制](../state/durable-execution.mdx#副作用与幂等恢复)防止动作执行两次。

这里的「审批、执行」两个阶段，只是为了核对用户批准的内容，和分布式事务里协调多个参与方提交的两阶段提交不是一回事。

审批也不是越多越安全。确认框弹得太频繁，用户就会不看内容直接点同意，这叫**审批疲劳**。所以要按风险和已有授权决定是否需要确认，可逆的操作用恢复手段兜底，把用户的注意力留给真正高风险的动作。

## 4. 凭据与敏感数据 {#凭据与敏感数据}

凭据的原则是不经过模型：工具需要凭据时，由工具实现自己读取和注入，模型只提供业务参数。比如数据库密码由程序从密钥管理服务取出来，直接用来建立连接。这样即使提示内容被看到了，凭据也不在里面。

工具用的短期令牌按用户和任务签发，限定访问范围和过期时间。还要留意凭据从侧面漏回来：错误信息、进程环境变量和日志里都可能带着它，这些输出一旦交给模型，凭据就又进了上下文。

多个步骤之间要传递敏感值时，可以让服务端保存真实数据，只返回一个短期**引用**，也就是用来查找真实值的标识。比如第一个工具取到了身份证号，模型和界面只拿到一个引用 ID 或脱敏后的值。下一个工具拿着引用来取时，程序校验用户、用途和有效期，确认后才取回真实值，这一步叫**解引用**。

引用本身也要受访问控制，持有引用不等于有权读数据。否则攻击者只要拿到 ID，就能读出原值，引用就失去了意义。

其余的输出也按同样的思路收紧：工具结果只返回任务需要的字段，日志按规则给密钥、手机号和证件号脱敏，日志查询和产物下载接口同样要检查身份。检索要在文档返回之前就按权限过滤，免得无权查看的内容先进了上下文。

## 5. 执行沙箱 {#执行沙箱}

授权检查的是「调用什么」，但模型生成的代码一旦运行，会自己去调用文件、网络和系统接口。沙箱就是在运行时限制这些访问，让出错或恶意的代码影响不到授权范围之外。限制分五个维度：

| 维度 | 约束 |
| --- | --- |
| 文件 | 限定可读写路径，隐藏凭据与系统数据 |
| 网络 | 控制出站目标和内部地址访问 |
| 进程 | 最小权限运行，约束系统调用与子进程 |
| 资源 | CPU、内存、磁盘、时间和进程数上限 |
| 生命周期 | 任务间隔离，按策略清理临时资源 |

落到配置上，比如：文件系统只暴露工作目录；网络默认关闭，或只允许白名单目标，并且要挡住内网的云元数据地址，否则代码可以从那里取到云环境的凭据；进程以非 root 用户运行，并限制系统调用（程序向操作系统请求服务的接口）；每个任务用独立的临时环境，结束后清理或销毁。

实现这些限制有几类隔离方式，隔离强度和开销各不相同：

- **操作系统沙箱**使用系统提供的访问约束。本地开发工具可结合 macOS Seatbelt，或 Linux 的 seccomp、namespaces 与 Landlock。它们分别参与系统调用过滤、资源视图隔离或文件访问限制，再配合操作确认。
- **普通容器**隔离进程和资源视图，但仍共享宿主机内核。挂载目录与容器权限会直接影响隔离效果。
- **gVisor**通过用户态内核处理许多系统调用，减少应用直接接触宿主内核接口的机会。
- **微虚拟机**通过虚拟化提供独立边界，Firecracker 是其中一种实现。多租户运行不可信代码时，可以评估这一类方案。

怎么选，取决于**威胁模型**，也就是你要防御哪些攻击。只防自家 Agent 误删文件，和多租户运行陌生人提交的代码，需要的隔离强度完全不同。启动时间、资源成本、挂载方式和网络规则都要实测，隔离效果看的是完整配置，而不是用了哪种技术。

配置好之后，用受控的越界操作验证限制确实生效：

- 尝试读取工作区外的禁止路径，检查文件访问是否被拒绝。
- 访问被禁止的域名和内部地址，检查网络规则是否生效。
- 在受控范围内触发资源上限，检查进程是否被限制或终止。

一个工具能不能在沙箱里自动执行，还要看它的来源和审核结果。自研且经过评审的工具，可以在已有授权和沙箱范围内自动运行。第三方工具要审核来源、代码和依赖，固定版本，并按实际需要收紧文件和网络权限；工具定义一旦变化就重新审核，防止新增的能力越过原来的授权范围。

### 5.1 命令、路径与网络边界 {#命令路径与网络边界}

白名单检查的是入口，但程序真正访问了什么，要到运行时才知道。命令、路径和网络各有一种典型的「入口合法、实际越界」。

命令：`python`、shell 和构建工具都在常见的白名单里，可它们都能执行任意脚本、启动子进程。白名单允许了 `python build.py`，并不能说明 `build.py` 里面做了什么，单看命令前缀覆盖不了后续行为。

路径：检查时要按实际的文件目标来校验。规范化能消除 `..` 这类片段，但符号链接会把一个看起来在工作区里的路径指到别处；而且检查时合法的路径，到执行前还可能被换掉。所以敏感操作要用受约束的文件访问机制，在访问发生的那一刻落实目录限制。

网络：控制要覆盖 DNS 解析结果、重定向后的地址和最终目标，因为一个允许访问的域名，完全可以把请求转到内网地址。数据经过允许的代理或工具传出去时，还要检查用途和内容。

最后再强调一次分工：沙箱管的是资源访问范围，当前用户能不能执行这次动作，仍由业务授权判断。

## 6. 面试题 {#面试题}

### 6.1 Agent 对工具调用不作限制，会有哪些风险？工具调用的安全控制怎么实现？ {#tool-risks}



**考察重点**

- 能说明工具能力怎样导致越权、误操作、外泄和资源滥用。
- 能把分级授权落实到程序检查，并保持当前用户的数据权限。

**相关内容**：[风险分级](#风险分级)、[确认与二次校验](#确认与二次校验)。

<details>
<summary>参考回答</summary>

**无限制的工具调用会导致越权读取、误删误写、数据外泄和资源滥用。**

比如高权限服务账号会让普通用户读取无权查看的数据，循环调用则持续消耗配额与费用。程序需要按当前用户检查工具、参数和目标范围，并设置调用次数与费用上限。

只读操作仍按数据权限过滤，可逆编辑保留恢复手段。删除、支付和外发等高风险动作按授权策略审批，执行时再次校验。代码和命令放在沙箱中运行，全部调用记录实际参数与结果，便于复核已经发生的副作用。

</details>

### 6.2 工具副作用分级授权和执行期二次校验如何落地？删除、覆盖等危险操作要人工审批吗？ {#tiered-authorization}



**考察重点**

- 能解释生成计划、审批与执行各自检查什么。
- 能处理审批之后的权限或目标变化，并解释如何减少审批疲劳。

**相关内容**：[确认与二次校验](#确认与二次校验)。

<details>
<summary>参考回答</summary>

**分级授权根据风险与已有授权决定是否审批，执行期二次校验则核对当前权限和目标状态。**

模型先提出动作，程序预校验参数、身份和范围。需要审批时，向用户展示具体对象与影响，把批准记录绑定到动作摘要、参数、目标版本和有效期。

确认到执行之间，用户权限可能被撤回，目标也可能被修改。因此，执行前要原子领取批准记录并重新校验，写入时用版本条件防止覆盖已变化的对象。参数改变时重新核对授权。

删除、覆盖、付款和外发按具体风险与授权范围决定审批。可逆的工作区编辑可以按会话授权执行，并用版本管理或快照恢复。这样可以减少审批疲劳，让用户把注意力留给高风险动作。

</details>

### 6.3 如何控制 Agent 执行中不暴露密钥？敏感数据如何在步骤之间传递而不暴露？ {#secrets}



**考察重点**

- 能说明程序侧如何注入凭据，以及错误输出如何带来泄漏。
- 能解释引用的授权边界，并把脱敏与访问控制分别落实。

**相关内容**：[凭据与敏感数据](#凭据与敏感数据)。

<details>
<summary>参考回答</summary>

**凭据由工具在程序侧读取和注入，步骤之间的敏感值则用受授权约束的短期引用传递。**

模型只提供业务参数，工具从密钥管理服务取得凭据。令牌按用户和任务签发，限定范围与有效期。工具错误、环境输出和日志也要检查，防止它们把凭据带回上下文。

敏感结果保存在服务端，模型和界面收到引用 ID 或脱敏值。下一个工具解引用时，再检查用户、用途和有效期，确认后取回真实数据。

日志中的密钥、手机号和证件号按规则脱敏，日志访问也需要授权。内部文档在检索返回前按当前用户权限过滤，输出时只保留任务需要的字段。

</details>

### 6.4 什么是 Agent 沙箱？如何判断工具是否可信，并允许它在沙箱中直接执行？ {#sandbox}



**考察重点**

- 能说明文件、网络、进程和资源限制分别控制什么。
- 能比较隔离方式的边界与成本，并通过工具审核和越界测试验证限制。

**相关内容**：[执行沙箱](#执行沙箱)。

<details>
<summary>参考回答</summary>

**Agent 沙箱是运行代码和命令的受限环境，工具经审核后仍需在授权范围内运行。**

沙箱分别限制文件、网络、进程和资源用量。比如只暴露工作目录，网络使用白名单并屏蔽内网元数据地址，进程以非 root 用户运行。独立任务环境在结束后清理，减少跨任务影响。

普通容器共享宿主内核，gVisor 用用户态内核减少直接接触宿主接口，微虚拟机提供虚拟化边界。选择时根据需要防御的攻击，实测隔离效果、启动时间和运维成本。

自研工具经过评审后可按已有授权自动执行。第三方工具需要核对来源、代码和依赖，固定版本，定义变化时重新审核。最后通过禁止路径、网络访问和资源上限测试，验证限制确实生效。

</details>

### 6.5 命令和路径都在白名单中，为什么仍需运行时沙箱？ {#sandbox-command-boundaries}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：能解释解释器、符号链接和重定向怎样改变实际访问目标。

**相关内容**：[命令、路径与网络边界](#命令路径与网络边界)。

<details>
<summary>参考回答</summary>

**白名单只筛选调用入口，运行时沙箱还要限制程序最终访问的资源。**

解释器和构建脚本能继续启动子进程，所以命令前缀无法描述全部行为。符号链接与检查后的路径变化，也会让实际目标偏离检查时的对象。网络还会经过 DNS 解析和重定向，最终地址同样需要约束。

因此，运行时限制要覆盖文件、网络及子进程，并用越界测试验证。业务授权另行检查当前用户能否执行这次动作。

</details>
