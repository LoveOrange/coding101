# 延迟、成本与服务扩展

Agent 服务的延迟和成本，主要来自三处：模型调用、工具执行和排队等待。和普通接口不同，一个 Agent 任务往往要循环调用模型很多轮，每一轮都要重新处理越来越长的历史，所以慢和贵经常是同一个原因造成的。

具体来说，要弄清时间花在哪条关键路径上，费用怎样按轮次和计费类别累计，以及请求多了以后，怎样用并发、速率和预算限制保护模型配额和下游服务。

## 1. 面试核心 {#core}

- 端到端延迟由**关键路径上的模型调用、工具执行和排队等待**共同决定；减少串行轮数往往比加快单次调用更有效。[卡](#reduce-latency)
- 分析慢任务时，用追踪记录区分**轮数增加、单轮变慢和等待变长**三类原因。[卡](#slow-task-analysis)
- 一次任务的费用是**各轮输入、缓存和输出费用，加上工具和检索费用**之和。[卡](#token-cost)
- **前缀缓存复用相同输入前缀的计算，结果缓存直接复用已有的业务答案**，后者要核对身份和时效。[卡](#cache-boundaries)
- **信号量限制同时执行的调用数，RPM 和 TPM 分别限制每分钟的请求数和 Token 数**，两类限制要分开控制。[卡](#concurrency-limits)

## 2. 延迟的组成 {#延迟的组成}

优化延迟之前，先要知道时间花在了哪一段。链路追踪会记录每轮模型调用和工具调用的起止时间，从中可以找出**关键路径**，也就是决定任务完成时间的那条最长的串行链。下表列出各环节要看的指标：

| 环节 | 观察指标 | 优化方向 |
| --- | --- | --- |
| 首 Token | TTFT、输入量、缓存命中 | 精简输入、复用前缀、减少排队 |
| 生成 | 输出长度、生成耗时 | 减少无用输出、评测模型选择 |
| 循环 | 轮数、重试和重规划 | 合并固定步骤、限制重复尝试 |
| 工具 | 单次耗时和依赖关系 | 缓存、安全并行、超时 |
| 排队 | 队列长度、等待时间 | 容量、优先级与背压 |

单次模型调用的耗时分两段。**首 Token 延迟**（TTFT）是从发出请求到收到第一个输出 Token 的时间；之后的生成耗时，可以近似看成剩余输出 Token 数乘以每个 Token 的平均耗时。推理模型还会先生成内部推理 Token，所以即使可见的回答很短，等待也可能很长。

多个步骤之间，串行的步骤要等上一步完成，耗时相加；独立的步骤并行后，主要等最慢的那个分支，再加上调度和汇总的开销。举个例子，三个各需 2 秒的工具串行要 6 秒，并行大约只要 2 秒多一点。所以减少串行轮数，经常比只加快其中一次调用更有效。

找到瓶颈后，按所在环节分别优化：

- **减少模型轮次**：固定的工具顺序由代码编排，同一轮可合并多个判断。无依赖且允许同时执行的工具可以并行，并设置最大步数限制重复尝试。
- **缩短单轮生成**：压缩历史和工具结果，只要求任务需要的输出。比如参数抽取可以返回结构化字段，省去长篇解释。简单步骤可评测更快的模型，减少不必要的推理耗时。
- **减少输入和网络等待**：稳定前缀有助于命中缓存，就近部署可缩短网络往返。TTFT 还包含服务端排队，因此要结合输入量、缓存命中与服务指标判断原因。
- **缩短工具等待**：缓存可复用的工具结果，给下游调用设置超时。工具有数据依赖时，仍需按顺序执行。
- **控制排队**：预留模型配额，按优先级处理请求。背压指下游忙不过来时，让上游放慢或拒绝新工作，避免队列无限增长。

还有两点和用户体验有关。流式返回让用户更早看到文字，改善的只是首次可见反馈，完整任务的耗时并没有变，要单独记录。长任务可以先返回任务 ID，再用 SSE（服务端持续向客户端推送事件的机制）推送进度，或者让客户端轮询。

另外，取消和超时要一路传到后续步骤。否则用户已经停止了任务，后台调用还在继续跑、继续花预算。

## 3. 成本控制 {#成本控制}

算费用的方法是：按任务把各轮用量累计起来，再分别乘以对应的单价。未缓存的输入、缓存读取和输出是分开计费的；提供方如果另收缓存写入、工具或检索的费用，也要一并算进去。推理 Token 算作输出用量，按所用模型的计费规则计算。

读用量字段时，要分清哪些是总数、哪些是总数里的明细。以 OpenAI Responses API 为例：

| Responses 用量字段 | 含义 |
| --- | --- |
| `input_tokens` | 本次处理的输入总量。 |
| `input_tokens_details.cached_tokens` | 输入中命中缓存的部分。 |
| `output_tokens` | 本次生成的输出总量。 |
| `output_tokens_details.reasoning_tokens` | 输出中用于推理的部分。 |
| `total_tokens` | 输入量与输出量之和。 |

`cached_tokens` 已经包含在 `input_tokens` 里，`reasoning_tokens` 也已经包含在 `output_tokens` 里，统计总量时不能再加一遍。算费用时则反过来，要把用量拆到各个计费类别，比如输入拆成「未缓存」和「缓存命中」两部分，分别乘以各自的单价。

多轮任务里有一项不太显眼的开销：重发历史带来的累计输入。假设第一轮输入为 B，之后每轮新增固定长度 d，并且每轮都重发全部历史。第 k 轮输入约为 `B+(k-1)d`，n 轮加起来就是 `nB+d*n*(n-1)/2`。后一项随轮数平方增长：轮数翻一倍，这部分输入大约变成四倍。这就是长循环特别费 Token 的原因。

压缩和裁剪减少的是后续每轮的输入量，前缀缓存减少的是重复输入的计算和费用。按成本来源，可以选择下面这些手段：

| 手段 | 做法 |
| --- | --- |
| 压缩 | 保留目标、约束、当前证据和产物引用 |
| 按需加载 | 工具与技能只展开相关部分 |
| 模型路由 | 按任务评测选择能力与成本组合 |
| 结果缓存 | 对满足身份和新鲜度条件的结果复用 |
| 批处理 | 用于可延后完成的离线任务 |
| 预算 | 限制单任务、用户和租户的累计开销 |

每种手段的要点如下：

- **上下文压缩**：保留目标、约束和结论的来源，工具的原始结果可以换成摘要和引用。具体取舍见[上下文压缩](../prompting/context-compaction.mdx)。
- **按需加载**：先只提供工具或技能的摘要，需要时再展开，减少每轮都要重复发送的固定输入。加载方式见 [Agent Skills](../tools/agent-skills.mdx)。
- **模型路由**：意图识别、参数抽取、记忆整理和压缩这类调用频繁、目标明确的任务，交给小模型；复杂推理交给能力更强的模型。小模型能达标时，累计费用和延迟都会下降。
- **结果缓存**：要设置过期时间，并按身份和数据版本判断结果是否仍然有效。语义检索的阈值只负责筛出候选，边界见下一节。
- **批处理**：时效要求低的离线任务，交给提供方的批量接口。
- **预算上限**：同时约束任务、用户和租户的 Token 和调用次数。达到上限就停止调用，并明确返回已经完成的部分。

模型选型不能只看单价。要用同一份评测集，比较成功率、延迟和**每个成功任务的总成本**：单价低的模型如果需要更多轮次或重试，总费用反而更高。输入和输出谁占大头也一样，取决于数量、单价和缓存命中，要看实际用量再下结论。

### 3.1 前缀缓存与结果缓存 {#前缀缓存与结果缓存}

两种缓存复用的东西不同，命中条件也就不同。

**前缀缓存**复用的是相同输入前缀的计算，省掉的是重复输入的预填充计算（原理见[大语言模型基础](../llm/llm-basics.mdx#前缀缓存)）。命中之后，模型仍然会为这次请求重新生成结果。所以组装输入时，把稳定的规则和工具定义放在前面，变化的内容放在后面，才能保持共同前缀；某处一改，从那里往后的部分都要重新计算，前面满足条件的部分仍可命中。是否命中还受模型、最小长度和保留时间等条件影响，要看 API 返回的缓存用量字段来验证。具体组装顺序见[上下文管理](../prompting/context-management.mdx#组装顺序与前缀缓存)。

**结果缓存**直接返回已有的业务答案，所以必须确认这个答案对当前请求仍然成立。缓存键要包含请求参数、租户、权限范围和相关的数据版本。语义相似度可以帮忙找候选，但不能代替这些核对：两个人都问「我的订单到哪了」，问题一模一样，答案却属于不同的用户。

结果缓存也替代不了幂等。支付、删除这类操作会改变外部业务状态（也就是有副作用），缓存不能保证副作用只发生一次，重复请求仍要靠业务的幂等机制处理。

## 4. 并发、限流与降级 {#并发限流与降级}

请求多起来以后，要同时保护两样东西：模型配额和工具的下游服务。先分清两个概念：**并发数**是同一时刻正在执行的调用数，**速率**是一段时间内发出了多少请求。

模型提供方按每分钟请求数（RPM）和每分钟 Token 数（TPM）限制用量。并发低不代表速率低：同时只跑 3 个请求，但每个请求都很短、很快完成，一分钟下来照样能把 RPM 用完。TPM 还和每次的输入量、输出预算有关。**信号量**用固定数量的许可来限制同时执行的调用数，只能管住并发，所以速率要另外控制。

容量风险主要有三类：

- **模型配额耗尽**：超过速率限制会收到 429 响应。立即大量重试会继续占用配额，让失败进一步增加。
- **下游容量耗尽**：数据库、内部接口和浏览器都有容量上限。多 Agent 或批量任务并行调用时，会把压力集中到同一个下游。
- **循环持续占用资源**：失控任务反复调用工具与模型，会挤占其他用户的配额。

对应的保护措施，可以放在链路上的五个位置：

1. **请求入口**按用户、租户和接口分配配额，用令牌桶等方式限制请求速率。
2. **任务队列**由固定数量的工作进程消费，并限制队列长度和最大等待时间。根据积压决定扩容、延后或拒绝任务。
3. **调用入口**为每个模型和工具设置独立的信号量，并累计速率用量。比如 100 个任务最多同时执行 3 个。收到 429 后有界退避，响应提供 `Retry-After` 时按它等待。
4. **降级流程**使用经过评测的备用模型，或关闭反思、重排序等非核心步骤。也可以返回只基于检索的简化结果，最终转人工或稍后恢复。
5. **业务隔离**让不同业务和优先级使用独立的队列与配额，减少相互影响。

几条约束要贯穿始终：重试要计入原任务的预算和总截止时间；备用模型和简化流程也要满足最低的验收要求；持续失败时保存进度，停止接收超出容量的新工作。

同时用多个模型或多家提供方时，还可以加一层**模型网关**，也就是应用和模型服务之间的统一调用层。用 LiteLLM 或自研网关，可以把下面这些能力集中到一处管理：

- 转换接口格式，并在程序侧管理调用凭据。
- 按任务选择模型，执行重试与故障切换。
- 统计用量，并统一实施限流。

## 5. 面试题 {#面试题}

### 5.1 一个 Agent 推理链路包含 3 个工具，请求频率也高，整体延迟较高，你会怎样优化？ {#reduce-latency}



**考察重点**

- 能把延迟拆到每轮模型调用、每个工具和排队等待，找到关键路径。
- 能根据依赖关系选择并行与缓存，并解释流式返回改善哪一段体验。

**相关内容**：[延迟的组成](#延迟的组成)、[组装顺序与前缀缓存](../prompting/context-management.mdx#组装顺序与前缀缓存)。

<details>
<summary>参考回答</summary>

**应根据关键路径减少串行等待，再优化单轮调用和高频请求中的重复工作。**

先比较每轮模型调用、三个工具和排队的耗时，并单独记录重试。工具顺序固定时，可以由代码编排，省去每步让模型决策的等待。三个工具相互独立时，让模型一次提出多个调用，再安全并行执行。

随后按测量结果优化**单轮耗时、重复调用和首次反馈**：

- 压缩历史与工具结果，限制无用输出，并用稳定前缀提高缓存命中。
- 按请求参数、身份和数据版本缓存工具结果，设置过期时间。
- 把路由和参数抽取等简单步骤交给经过评测的小模型。
- 使用流式返回改善首次反馈，长任务异步执行并推送进度。

每次修改都比较完整延迟和任务通过率，确认提速后仍能完成原任务。

</details>

### 5.2 在 Token 消耗上做过哪些成本控制？模型选型时怎样权衡能力和成本？ {#token-cost}



**考察重点**

- 能根据实际用量判断成本来源，解释多轮重发历史的累计开销。
- 能解释压缩、缓存、模型路由和预算的作用，并用评测比较每个成功任务的成本。

**相关内容**：[成本控制](#成本控制)、[Token 与上下文窗口](../llm/llm-basics.mdx#token-与上下文窗口)。

<details>
<summary>参考回答</summary>

**压缩重复输入、复用缓存并限制调用预算，可以减少任务的累计费用。**

先按任务记录未缓存输入、缓存用量、输出与工具费用，判断主要开销。多轮重发历史时，精简历史和工具结果的收益更大。工具与技能可先给摘要，按需展开；时效要求低的离线任务则可评估批处理。

意图识别、参数抽取、记忆整理和压缩，可以尝试交给小模型。是否采用要用同一份评测集比较成功率、耗时和每个成功任务的总成本。小模型若增加重试与轮次，单价优势就会被抵消。

只能使用一个模型时，可以改进检索，精简输入，并用结构化输出和程序校验提高成功率。任务与租户预算则限制反复尝试的累计费用，超限后返回已完成的结果。

</details>

### 5.3 为什么要限制 Agent 的并发？LLM 服务并发太高、很多用户同时使用时怎样限流和降级？ {#concurrency-limits}



**考察重点**

- 能说明提供方配额、下游容量和失控循环为什么需要分别限制。
- 能说明入口、队列和调用层各保护什么，以及故障时如何降级与隔离。

**相关内容**：[并发、限流与降级](#并发限流与降级)、[限流算法](../../system-design/reliability/rate-limiting-capacity-protection.mdx#rate-limit-algorithms)。

<details>
<summary>参考回答</summary>

**限制并发可以保护下游容量，再配合速率与预算限制，避免模型配额被耗尽。**

模型服务按 RPM 和 TPM 限速，工具访问的数据库与内部接口也有容量上限。失控循环还会持续挤占其他用户资源。因此，入口要按用户、租户和接口限流，长任务进入有界队列。

模型与工具各用信号量限制同时执行的调用数，例如 100 个任务最多同时运行 3 个。队列长度和等待时间用于判断扩容或拒绝，429 则采用有界退避并遵循 `Retry-After`。

高峰或故障时，可使用经过评测的备用模型，或关闭非核心的反思与重排序。无法完成的任务保存进度，返回部分结果或转人工。不同业务和优先级应使用独立配额与队列，减少故障扩散。

</details>

### 5.4 一个长任务平时 5 分钟结束，这次运行了 15—20 分钟，你会怎样分析原因？ {#slow-task-analysis}



**考察重点**

- 与正常任务对比，把差异拆到轮数、单轮耗时、工具和排队。
- 区分「做了更多步」和「每一步更慢」两类原因。

**相关内容**：[延迟的组成](#延迟的组成)、[失败归因与可观测性](../evaluation/agent-evaluation.mdx#失败归因与可观测性)。

<details>
<summary>参考回答</summary>

**应先对比正常任务与慢任务的追踪记录，判断是步数增加，还是单步耗时与等待时间增加。**

可以沿以下**三类差异**定位原因：

1. **步数增加**：检查重复工具调用、失败重试和反复重规划，再比较任务的数据规模。工具返回错误或空结果、压缩丢失进度，以及提示或模型版本变化，都值得核对。
2. **单轮变慢**：比较输入量、输出长度和工具耗时。TTFT 变长时，还要检查前缀缓存、服务端排队和内部推理，结合指标定位瓶颈。
3. **等待增加**：单独统计队列等待、429 和退避时间，避免把它们归入模型生成耗时。

确认原因后，修复对应环节，并设置最大步数与总时长预算。同一工具连续失败时提前停止，关键指标超过基线时告警，最后把这次任务加入回归集。

</details>

**考察重点**：能区分计算复用与答案复用，并说明身份、实体和时效怎样影响缓存有效性。

**相关内容**：[前缀缓存与结果缓存](#前缀缓存与结果缓存)。

<details>
<summary>参考回答</summary>

**前缀缓存复用输入计算，结果缓存复用业务答案；语义相似的请求仍需验证答案能否共享。**

前缀命中后，模型还会生成当前请求的结果。结果缓存则直接返回旧答案，因此要匹配用户身份、目标实体和数据版本。比如两个用户都查询「我的订单」，问题相似，授权范围却不同。权限变化或数据过期时，应使缓存失效或重新计算。

</details>
