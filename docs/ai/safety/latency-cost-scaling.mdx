# 延迟、成本与服务扩展

Agent 的延迟与成本来自模型、工具和排队。本文负责关键路径、Token 计费、缓存与并发预算。通用保护机制见[限流](../../system-design/reliability/rate-limiting-capacity-protection.mdx)和[熔断降级](../../system-design/reliability/circuit-breaker-degradation-bulkhead.mdx)。API 与缓存行为核对于 2026-10-13。

## 1. 面试核心 {#core}

- 端到端延迟由关键路径上的模型、工具和等待组成。[卡](#reduce-latency)
- 任务成本按输入、缓存、输出与工具费用累计。[卡](#token-cost)
- 信号量控制并发，RPM 与 TPM 限制时间窗口内的用量。[卡](#concurrency-limits)
- 慢任务通过轮数、单轮耗时和等待时间定位原因。[卡](#slow-task-analysis)
- 前缀缓存复用输入计算，结果缓存复用业务答案。[卡](#cache-boundaries)

## 2. 延迟的组成 {#延迟的组成}

| 环节 | 观察指标 | 优化方向 |
| --- | --- | --- |
| 首 Token | TTFT、输入量、缓存命中 | 精简输入、复用前缀、减少排队 |
| 生成 | 输出长度、生成耗时 | 减少无用输出、评测模型选择 |
| 循环 | 轮数、重试和重规划 | 合并固定步骤、限制重复尝试 |
| 工具 | 单次耗时和依赖关系 | 缓存、安全并行、超时 |
| 排队 | 队列长度、等待时间 | 容量、优先级与背压 |

串行步骤的耗时相加。独立并行步骤主要受最慢分支约束，另有调度与汇总开销。优化前按追踪记录定位关键路径。

模型调用还包含推理和服务端排队。TTFT 上升有多种原因，应结合输入量和服务指标分析。流式返回改善首次可见反馈，完整任务耗时仍需单独记录。

长任务可先返回任务 ID，再异步推送进度。取消与超时应传到后续步骤，避免后台继续消耗预算。

## 3. 成本控制 {#成本控制}

成本统计区分未缓存输入、缓存读取与输出 Token。提供方另有缓存写入或工具费用时，也需计入。推理 Token 的计费按所用接口口径统计。

若每轮新增固定长度 d，且重发全部历史，第 k 轮输入约为 `B+(k-1)d`。B 是固定前缀长度。n 轮总输入为 `nB+d*n*(n-1)/2`。压缩、裁剪和缓存会改变计费与计算开销。

| 手段 | 做法 |
| --- | --- |
| 压缩 | 保留目标、约束、当前证据和产物引用 |
| 按需加载 | 工具与技能只展开相关部分 |
| 模型路由 | 按任务评测选择能力与成本组合 |
| 结果缓存 | 对满足身份和新鲜度条件的结果复用 |
| 批处理 | 用于可延后完成的离线任务 |
| 预算 | 限制单任务、用户和租户的累计开销 |

成本占比由 Token 数、单价和缓存命中决定。输入量大时应检查历史重复，输出费用高时关注生成长度。选型比较成功率和每个成功任务的总成本。

### 3.1 前缀缓存与结果缓存 {#前缀缓存与结果缓存}

前缀缓存复用相同输入前缀的计算。稳定规则和工具定义放在前面，有助于保持相同部分。修改某处后，该处之后的前缀匹配会受影响。前方仍满足要求的部分可以继续命中。

缓存命中还受模型、最小长度、保留时间等条件影响。查看 API 的缓存用量字段，验证实际命中。上下文组织见[上下文管理](../prompting/context-management.mdx#组装顺序与前缀缓存)。

结果缓存直接复用业务答案。缓存键需包含租户、权限范围和相关数据版本。语义相似只帮助找候选，仍需检查身份、实体和时效。支付、删除等副作用通过业务幂等处理。

## 4. 并发、限流与降级 {#并发限流与降级}

并发数与速率是不同约束。即使同时只运行少量请求，短请求仍会迅速耗尽 RPM。TPM 则与输入、输出预算相关。

- 入口按租户分配配额，避免单方占满资源。
- 长任务进入有界队列，设置最大等待时间。
- 模型与工具各用并发上限，并累计速率用量。
- 遇到限流时有界退避，响应提供 `Retry-After` 时遵循它。
- 备用模型或简化流程需经过相同验收评测。

重试也占用配额，需计入总截止时间。持续失败时拒绝新工作或稍后恢复。模型网关可集中管理路由、用量、限流和故障切换。
