# 提示词工程

**提示词工程**（prompt engineering）是向模型写清任务、约束、输入和输出要求，并用评测结果持续改进提示的过程。重点在后半句：提示写得好不好，不靠读起来是否专业来判断，而要看它在一组固定任务上的表现。

做生产应用时，提示决定模型能不能按业务规则回答，输出能不能被程序解析，修改后会不会悄悄弄坏别的场景。要答好这个主题，需要讲清提示由哪些部分组成、示例和思维链各解决什么问题、怎样让输出结构可靠，以及怎样用评测证明修改有效。

## 1. 面试核心 {#core}

- 生产提示应写明**角色与任务范围、可检查的规则、输入数据、示例、输出格式和异常处理**。[卡](#prompt-structure)
- 提示质量**由固定评测集上的任务指标衡量**。修改要针对具体的失败原因，并检查正常任务有没有退化。[卡](#prompt-tuning)
- Few-shot 用示例**传达格式和判断边界**，CoT 用中间推导**帮助完成多步任务**，代价是更多输出和更高延迟。[卡](#cot-vs-few-shot)
- 严格 JSON Schema **只约束字段和类型**，订单是否存在、金额是否合规这类**业务内容仍要程序检查**。[卡](#structured-output)

## 2. 提示的组成 {#提示的组成}

一份提示既要让模型知道该做什么，也要让开发者能检查结果是否合格。写的时候可以按**六类信息**逐项确认：

- **角色与任务范围**：模型承担什么职责，可以处理哪些请求。
- **规则与约束**：字数、字段来源、转人工条件等具体要求。
- **输入数据**：业务记录或检索文档，并标明来源。
- **输入输出示例**：给出输入和期望输出，展示只靠文字难以说清的判断边界。
- **输出格式**：回答的语言、长度，或程序需要的字段。
- **异常处理**：信息不足、请求越界、工具失败时怎么办。

下面是一个售后任务的提示模板。`{{order_json}}` 是占位符，由程序填入本次查询到的订单数据：

```xml
<task>处理订单、物流和退款咨询。</task>
<rules>
订单号缺失时，询问订单号。
退款金额超过 500 元时，申请人工处理。
退款获批前，只说明正在申请处理，不承诺退款。
订单状态以 order 数据为依据。
信息缺失时，说明尚待确认的字段。
</rules>
<order>{{order_json}}</order>
<output_format>
使用中文，最多 120 字。
工单创建成功后，给出工具返回的工单号。
</output_format>
```

模板里每条规则都对应一个可以检查的行为：订单号缺失时，模型应该追问；订单状态只能来自 `order` 标签里的数据；120 字是能直接数出来的长度限制。500 元是示例业务规则，超过时模型可以调用工单工具 `create_ticket` 申请人工处理，只有工单创建成功，才能在回复里给出工具返回的编号。退款获批之前，回复只能说「正在申请处理」，不能提前承诺退款，因为申请工单不等于退款已经批准。

金额限制不能只靠模型遵守，执行器也要再校验一次，因为提示约束的是模型倾向，不是程序保证。执行器怎样检查授权，见[工具授权与执行沙箱](../safety/tool-authorization-sandbox.mdx)。

提示用到实际业务里，还要注意**规则依据、数据分隔和版本管理**：

- **规则依据**：把「回答要专业」改成能验证的要求，比如「不超过 120 字，必须引用订单状态字段」。必要时写出原因，例如「回复会被语音合成朗读，请使用完整句子，避免省略号」。知道约束的用途，模型才能把它推广到相近的情况。
- **数据分隔**：标签把指令和订单数据分开，也方便程序替换变量。外部输入里的特殊字符要转义，否则可能破坏标签结构。异常处理要写成具体动作，比如缺少信息时追问、工具失败时说明尚未完成。
- **版本管理**：提示模板放在仓库里，由模板引擎填充变量，每次修改记录版本，方便对照评测和回滚。填进去的订单或文档长度会变，所以要检查最终输入的 Token 预算。

## 3. Few-shot 与思维链 {#few-shot-与思维链}

示例和思维链解决的是两类不同的问题：规则难以用文字说清时，用示例展示期望结果；任务需要多步推导时，考虑让模型先推导再回答。

**Few-shot** 是在提示里提供少量「输入 → 期望输出」的示例。它适合传达难以描述的格式、风格和分类边界。示例要覆盖正例、反例和难例，尤其是容易混淆的边界情况。如果所有示例都属于同一类，模型的输出就会偏向这一类；示例太多又会占用上下文，还可能让模型照抄示例里的具体内容。数量多少合适，要靠评测来选。

**思维链**（Chain of Thought，CoT）是在提示里展示或要求中间推导，再给出最终答案。它适合计算、多条件判断和规划这类多步任务。推导写出来就要占输出 Token，延迟和费用都会增加，所以简单的分类、抽取和改写，可以先试直接指令。

推理模型会在内部先推理再回答。使用 OpenAI 推理模型时，可以先直接写清目标、约束和验收条件，再通过评测判断额外要求显式推导有没有收益。推理预算的含义见[大语言模型基础](../llm/llm-basics.mdx#推理预算与输出结束状态)。

两者也可以结合：在少量示例里展示从输入到结论的推导过程。选择时可以按下表的**任务要求**先确定要测试的方案：

| 任务 | 可先测试的提示方式 |
| --- | --- |
| 固定格式 | 明确格式加示例 |
| 分类边界 | 含边界正反例的 Few-shot |
| 多步计算 | 明确条件，比较推理模型与工具方案 |
| 简单抽取 | 直接指令加 Schema |

## 4. 结构化输出 {#结构化输出}

输出要交给程序解析时，既要约定格式，也要检查内容。只在提示里写「输出 JSON」，仍然会遇到前后多出解释文字、缺字段或字段类型不对等问题。

**JSON Schema** 是描述字段、类型和取值范围的结构规则。按约束强度，可以分成**三种格式控制方式**：

1. **提示格式**：用文字和示例说明期望格式，程序尝试解析并处理错误。效果完全取决于模型是否遵循提示。
2. **JSON 模式**：接口保证输出是合法的 JSON 语法，但字段是否齐全、类型是否正确，还要另行检查。
3. **严格 Schema**：提供方在生成时限制模型可选的输出，让正常完成的结果符合给定的 Schema。这种做法叫**约束解码**，能同时约束字段和类型。

OpenAI Responses 可以通过 `text.format` 指定 `json_schema`，并用 `strict: true` 启用严格模式。工具调用的参数约束则按接口而定：Chat Completions 默认不启用严格模式；Responses 省略 `strict` 时会尽量把 Schema 规范化为严格模式，做不到时退回非严格调用。需要保证参数符合 Schema 时，显式设置 `strict: true`，应用侧仍要再校验一次。

下面的 JSON Schema 定义了售后请求的意图和订单号：

```json
{
  "type": "object",
  "properties": {
    "intent": {"type": "string", "enum": ["refund", "logistics", "other"]},
    "order_id": {"type": ["string", "null"]}
  },
  "required": ["intent", "order_id"],
  "additionalProperties": false
}
```

`required` 要求 `intent` 和 `order_id` 都必须出现；`order_id` 未知时可以填 `null`；`enum` 把意图限定为退款、物流和其他三类；`additionalProperties: false` 表示结果里不能有未声明的字段。

这些规则管的只是结构。订单是否真实存在仍然要查询，退款金额是否超限也要程序判断。另外，各接口只支持 JSON Schema 的一部分能力，启用前要核对所用模型和接口支持哪些结构。

### 4.1 拒答、截断与流式解析 {#拒答截断与流式解析}

严格 Schema 只保证「正常完成」的结果符合结构，所以解析前先要确认响应确实正常完成了。模型拒答或输出被截断时，应用要先处理这些状态。比如 Responses 可能返回 `refusal` 拒答内容项，达到输出上限时返回 `incomplete` 状态。

流式输出是边生成边返回，接收途中 JSON 的括号或字符串还没闭合。界面可以用增量解析器展示已经确定的字段，也可以等完整结束后再解析。但执行工具、写数据库必须等完整结果，再依次检查 Schema、权限和业务规则。

检查失败后，按**格式错误、信息缺失和授权失败**分别处理：

- 格式或可修正的字段错误：把具体错误返回模型，要求重新生成。重试次数要有上限，超过后转人工或返回明确错误。
- 信息缺失：追问所需字段，补齐后再处理。
- 授权失败：停止对应动作。不能靠重复生成来绕过权限检查。

## 5. 评测驱动的调优 {#评测驱动的调优}

提示有没有效，要看它能否稳定完成目标任务。只有先固定评测请求和评分方式，才能判断一次修改是改好了还是改坏了。

一次调优可以按**评测集、任务指标、失败原因、提示修改和回归比较**推进：

1. 从真实请求中抽样，加入已知难例和失败样例，标注期望结果或评分标准。
2. 按任务定义指标。分类看准确率，抽取看字段正确率，格式要求看合规率。开放式回答由人工或模型按统一标准评分，工具任务还要检查参数来源和执行结果。
3. 把失败按原因归类，比如指令歧义、缺少信息、示例误导和格式错误。原因不同，要改的规则或输入也不同。
4. 每次只针对一类问题修改，并记录提示版本。一次改多处，结果变了也说不清是哪处起的作用。
5. 在整组任务上回归比较：既看目标问题是否改善，也看正常、边界和拒答任务有没有退化。

模型输出有随机性，关键结论要多次运行，比较平均分或通过率。除了正确率，还要记录任务成功率、耗时和费用。上线后持续收集新的失败样例，补进后续评测。

完整评审与重复运行方法见 [Agent 评估](../evaluation/agent-evaluation.mdx)。

### 5.1 开发集与留出集 {#开发集与留出集}

反复对着同一批样本改提示，提示会越来越贴合这批样本，在新请求上却未必更好。所以要把数据分成开发集和留出集。

**开发集**用来分析失败、修改提示，Few-shot 示例也从这里挑。**留出集**单独保留，只用于最后的独立验收。如果把留出集的样本或答案写进提示，模型等于提前看过考题，验收结果就失真了。

对比不同提示版本时，同一任务要用相同的模型版本和参数。换了模型要重新评测，因为在旧模型上有效的措辞和示例，换到新模型上效果可能不同。

## 6. 面试题 {#面试题}

### 6.1 Agent 的提示词一般包含哪些部分？如何设计？ {#prompt-structure}

**题型**：综合题

**考察重点**：说明提示各部分的作用，并解释怎样把规则写成可检查的条件、怎样验证和管理修改。

**相关内容**：[提示的组成](#提示的组成)、[评测驱动的调优](#评测驱动的调优)。

<details>
<summary>参考回答</summary>

**Agent 提示应包含角色与任务范围、可检查的规则、输入数据、示例、输出格式和异常处理。**

任务范围说明助手能处理什么，规则则明确字段来源、字数和转人工条件。输入数据用标签与指令分开，示例展示关键边界。异常说明要覆盖信息不足、请求越界和工具失败，让模型知道正常流程中断后该怎么做。

提示规则可以说明原因，帮助模型处理相似情况。模板存放在仓库中，由程序填充变量并记录版本。填充后还需检查 Token 预算，因为输入数据长度会变化。权限和金额限制交给执行器校验，提示修改通过评测后再发布。

</details>

### 6.2 系统 Prompt 如何调优？如何判断一个 Prompt 的质量？ {#prompt-tuning}

**考察重点**：解释怎样根据失败原因修改提示，并通过独立验收与重复运行判断效果。

**相关内容**：[评测驱动的调优](#评测驱动的调优)。

<details>
<summary>参考回答</summary>

**Prompt 质量应由固定评测集上的任务指标衡量，调优则围绕失败原因逐项修改并回归比较。**

从真实请求、已知难例和失败样例建立开发集，另留独立验收集。按任务定义准确率、字段正确率或格式合规率，开放式回答使用统一评分标准。再把失败按歧义、缺失信息、示例误导和格式错误归类，一次修改一类问题并记录版本。

修改后运行整组任务，检查目标问题是否改善，以及其他场景是否退化。固定模型版本和参数，多次运行关键用例，比较平均分或通过率，同时记录成本。上线后继续补充失败样例，更换模型时重新评测。

</details>

### 6.3 CoT 和 Few-shot 分别适合什么场景？ {#cot-vs-few-shot}

**考察重点**：说明两种技术分别解决什么问题，以及示例分布和显式推导如何影响效果与成本。

**相关内容**：[Few-shot 与思维链](#few-shot-与思维链)。

<details>
<summary>参考回答</summary>

**Few-shot 适合用示例传达格式、风格和分类边界，CoT 适合计算、多条件判断与规划等多步任务。**

Few-shot 应覆盖难例和反例。全部示例属于同一类，会让输出偏向该类；数量过多又会占用上下文，甚至让模型照抄内容。因此，要用评测选择有代表性的示例。

CoT 显式展示中间推导，会增加输出 Token、延迟和费用。推理模型可以先使用直接指令，简单抽取或改写也可以先测试清晰要求与输出格式。两者可以结合，在少量示例中展示推导过程，再评测是否提高任务成功率。

</details>

### 6.4 想要模型按照固定结构输出，应该怎么做？ {#structured-output}

**考察重点**：区分提示格式、JSON 模式和严格 Schema，并说明业务校验、拒答与流式结果怎样处理。

**相关内容**：[结构化输出](#结构化输出)。

<details>
<summary>参考回答</summary>

**接口支持时，应使用严格 JSON Schema 约束字段与类型，解析后再由程序检查业务内容。**

Responses 可用 `text.format` 的 `json_schema` 格式，并设置 `strict: true`。Schema 要符合接口支持的子集。工具调用也应显式启用严格约束；不支持严格结构时，可以使用 JSON 模式，并在程序侧检查字段和类型。

应用先检查是否拒答或未完成，再解析完整结果。Schema 通过后，仍需检查订单是否存在、金额范围和当前权限。流式片段可用于界面增量展示，工具执行或写库则要等结果完整并通过校验。

可修正的错误返回模型重试，次数超限后转人工或返回错误。缺失信息通过追问补齐，授权失败则停止对应动作。

</details>
