# 提示词工程

提示词工程用明确指令和示例定义模型任务。本文负责任务规则、Few-shot、思维链和结构化输出。上下文材料选择见[上下文管理](./context-management.mdx)。

## 1. 面试核心 {#core}

- 生产提示应明确任务、约束、输入、输出与异常处理。[卡](#prompt-structure)
- 提示质量由固定评测集上的任务指标衡量。[卡](#prompt-tuning)
- Few-shot 用示例传达格式和判断边界，CoT 展示推导步骤。[卡](#cot-vs-few-shot)
- 严格 Schema 约束输出结构，业务程序校验字段含义。[卡](#structured-output)

## 2. 提示的组成 {#提示的组成}

提示应让规则可以被检查。任务范围、证据来源和信息不足时的处理要明确。下面是售后任务的提示模板：

```xml
<task>处理订单、物流和退款咨询。</task>
<rules>
订单号缺失时，询问订单号。
退款金额超过 500 元时，申请人工处理。
订单状态以 order 数据为依据。
信息缺失时，说明尚待确认的字段。
</rules>
<order>{{order_json}}</order>
<output_format>
使用中文，最多 120 字。
工单创建成功后，给出工具返回的工单号。
</output_format>
```

500 元是示例业务规则，执行器也需检查该条件。标签用于区分材料，程序还需转义外部输入。授权机制见[工具授权与执行沙箱](../safety/tool-authorization-sandbox.mdx)。

- 可检查规则应包含长度、字段或引用要求。
- 示例应展示真实的边界判断。
- 异常说明应覆盖信息不足、越界和工具失败。
- 提示模板应保留版本，便于评测和回滚。

## 3. Few-shot 与思维链 {#few-shot-与思维链}

Few-shot 在提示中给出输入与期望输出。它适合传达格式、风格和分类边界。示例应覆盖正例、反例与难例。示例分布过于单一会影响输出倾向。

CoT 提示展示或请求中间推导。它用于计算和多条件判断等多步任务。显式推导会增加输出长度与延迟。对简单抽取，应先测试直接指令。

推理模型已在模型内部执行推理。OpenAI 推理模型可先使用直接提示。显式推导的收益需要按任务评测。应用需要说明的是任务目标、约束和验收条件。

| 任务 | 可先测试的提示方式 |
| --- | --- |
| 固定格式 | 明确格式加示例 |
| 分类边界 | 含边界正反例的 Few-shot |
| 多步计算 | 明确条件，比较推理模型与工具方案 |
| 简单抽取 | 直接指令加 Schema |

## 4. 结构化输出 {#结构化输出}

提示格式、JSON 模式和严格 Schema 是不同机制。提示中写“输出 JSON”只提供语言指令。JSON 模式约束 JSON 语法。严格 Schema 进一步约束字段、类型和支持的结构。

OpenAI Responses 可通过 `text.format` 指定 `json_schema`。严格模式使用 `strict: true`。工具调用也需按接口启用严格约束。普通工具定义本身不保证参数满足 Schema。

下面是输出内容的 JSON Schema：

```json
{
  "type": "object",
  "properties": {
    "intent": {"type": "string", "enum": ["refund", "logistics", "other"]},
    "order_id": {"type": ["string", "null"]}
  },
  "required": ["intent", "order_id"],
  "additionalProperties": false
}
```

`order_id` 必须出现，未知时可以为 null。enum 限定 intent 的取值。实际订单是否存在，仍需程序查询。支持的 JSON Schema 子集取决于模型和接口。

### 4.1 拒答、截断与流式解析 {#拒答截断与流式解析}

结构化调用也存在拒答与未完成状态。Responses 可以返回 `refusal` 内容项。达到输出上限时，可以返回 `incomplete`。应用应先处理响应状态，再读取结构化结果。

流式内容到达过程中，JSON 仍可处于未闭合状态。界面可以增量展示已确认的字段。工具执行和数据写入应等待完整结果。之后进行 Schema、权限和业务校验。

校验失败时，可将具体错误返回模型修正。重试次数应有上限。信息缺失应追问，授权失败应停止对应动作。

## 5. 评测驱动的调优 {#评测驱动的调优}

先定义指标，再比较提示版本。分类看准确率，抽取看字段正确率。工具任务还需检查参数来源与执行结果。

失败样例用于定位歧义、缺失信息和示例偏差。一次修改一个明确问题，便于追踪原因。修改后同时检查正常、边界和拒答任务。

### 5.1 开发集与留出集 {#开发集与留出集}

用于反复修改提示的样本属于开发集。另留一组任务，作为独立验收集。Few-shot 示例应来自开发数据。测试答案进入提示会污染比较结果。

相同任务应使用相同模型版本和参数。更换模型后，提示效果需要重新验证。完整评审与重复运行方法见 [Agent 评估](../evaluation/agent-evaluation.mdx)。

<summary>参考回答</summary>

推理模型可先使用直接指令。简单抽取可优先测试 Schema 输出。是否增加示例或推导，应由目标任务的评测决定。

</details>
