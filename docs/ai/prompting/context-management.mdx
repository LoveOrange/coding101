# 上下文管理

**上下文管理**（context engineering）是决定每次模型调用放进哪些信息、按什么顺序排列，以及哪些内容可以当作指令的工作。模型只能根据这一轮输入作答，所以漏掉关键事实、混进过期结果或塞入大量无关内容，都会直接影响它完成当前任务。

要讲清这个主题，抓住四件事：上下文由哪些部分组成，预算不够时留什么，怎样排列才能利用前缀缓存，以及外部内容为什么只能当数据、不能当指令。

## 1. 面试核心 {#core}

- 一次调用的上下文包含**应用规则、工具定义、相关记忆、对话历史、工具结果、检索文档和当前请求**，它们来源和更新频率都不同。[卡](#context-assembly)
- 把**稳定的规则和工具定义放在前部、动态内容放在后部**，更容易复用前缀缓存，降低输入费用和首 Token 延迟。[卡](#prefix-cache-order)
- 渐进式披露先给索引或摘要，再按任务读取细节，是**用更多调用轮次换更小的单轮输入**。[卡](#progressive-disclosure)
- 执行权限**由应用授权决定**，检索文档和工具结果只是**带来源的任务数据**；状态冲突时按来源、时间和适用范围判断哪条有效。[卡](#context-trust-freshness)

## 2. 上下文的组成 {#上下文的组成}

组装上下文时，先要分清每段内容从哪来、用来干什么。来源用来核对事实；消息角色和内容边界则标明哪些是指令、哪些是待分析的数据。这是两个独立的维度：工具调用成功返回，带回来的也可能是过期网页或恶意文本。

| 内容 | 来源 | 处理方式 |
| --- | --- | --- |
| 应用规则 | 开发者配置 | 放在对应的指令角色。 |
| 工具定义 | 本地配置或工具服务 | 审核用途与参数。 |
| 长期记忆 | 用户偏好或状态库 | 检查相关性、版本和权限。 |
| 检索到的内容 | 文档、网页、代码库 | 标注来源，作为数据引用。 |
| 历史消息 | 用户与模型 | 保留角色及工具调用关系。 |
| 当前请求 | 用户 | 在应用授权范围内解释。 |

这些内容的更新频率也不一样。应用规则随版本发布更新，工具定义随配置变化；用户偏好变得慢，但也可能过期；检索文档和当前请求每轮都变，对话历史随轮次增长。工具每执行一步还会产生新结果，要保留调用 ID 和返回时间。后面讲排列顺序时，正是利用了这种差别。

下面这个示意说明**规则、状态、历史与当前请求**怎样分层：

```text
应用规则：任务范围、输出规范
相关状态：目标、约束、有效偏好
近期历史：用户消息、模型消息、完整工具交互
检索内容：来源、版本、摘录
当前请求：用户本轮输入
```

具体的角色字段按所用 API 映射。在有消息角色的接口里，用户消息对应 `user`，模型消息对应 `assistant`；工具结果使用接口规定的工具消息形式，并通过调用 ID 关联发起它的调用；应用规则放在接口规定的指令位置。

用户偏好应作为带来源的状态传入，并且只挑和当前问题相关的条目，比如本次任务涉及的语言偏好或项目约束。不要把外部记忆直接拼进系统规则：那样其中的文字就获得了系统级的指令权限。它应该保留原来的来源和适用范围。

### 2.1 Token 预算与内容选择 {#token-预算与材料选择}

预算分配要保证模型既能读完输入，也还有空间继续生成。所以组装前先为输出和下一步的工具结果留出空间，再把剩下的预算分给固定指令、当前任务和相关证据。

组装后估算 Token 数。超出预算时，按**相关性、时效和必要性**决定留什么：

- 优先保留完成当前步骤所需的证据，移出离题文档和已经用过的旧工具结果。
- 同一事实有多个版本时，保留当前有效的版本，并记录来源与更新时间。
- 固定规则和当前请求中的必要条件要完整保留。必需文件本身就超限时，可以分段处理。

摘录文档时，标题、版本和引用位置要一起保留。模型给出结论后，程序或读者才能找回原文核对。

旧历史可以用摘要缩短，具体方法见[上下文压缩](./context-compaction.mdx)。

## 3. 组装顺序与前缀缓存 {#组装顺序与前缀缓存}

**前缀缓存**是模型服务复用相同输入开头部分计算结果的机制：多个请求的开头完全一样时，这一段不必重新计算，首 Token 延迟和输入费用都会下降。缓存原理见[大语言模型基础](../llm/llm-basics.mdx#前缀缓存)，这里只讲应用该怎样排列输入。

在保持消息角色和工具交互有效的前提下，按**内容的变化频率**从稳定到易变排列：

1. 工具定义和应用规则放在最前面，同一版本内保持不变。
2. 接着放较稳定的项目说明和相关用户偏好，保留各自的来源。
3. 然后是对话历史，新消息追加在末尾，尽量不改已有内容。
4. 最后放本轮检索文档和当前请求，时间戳、请求 ID 也放在这一段。

缓存匹配的是序列化后的相同前缀，也就是接口把消息组织成模型输入之后的开头部分。只要前面某个位置变了，从那里往后都无法复用。所以如果在开头插一个每轮都变的时间戳，共同前缀几乎就没了；随机调整工具定义的顺序也是一样。工具顺序要固定，动态信息尽量靠后。

能不能命中，还取决于提供方的最小长度、保存期限和请求路由等规则。OpenAI 提供缓存输入的用量明细，Anthropic 提供自动缓存或显式缓存控制。启用方式和计费规则按所用接口核对，实际收益看返回的用量（`usage`）。

压缩历史同样会改写前缀，只有变化位置之前的部分还能复用。替换旧历史时保留前面的稳定规则，就不必把整个输入重写一遍。压缩减少了后续输入，却也减少了缓存命中，所以要比较的是整次任务的费用和耗时。

## 4. 按需加载与渐进式披露 {#按需加载与渐进式披露}

**渐进式披露**（progressive disclosure）是先给模型一份索引或摘要，让它知道有哪些内容，再按当前任务读取细节。大文件和大量工具定义如果一次全部加载，很快就会占满窗口，这时就适合用它。

索引里要有稳定的文件或段落位置，模型选定以后，工具才能准确读到那一段。常见的**四类按需加载对象**如下：

- **文件与文档**：先返回目录、文件列表或章节摘要，并给出总长度。模型确定目标后，再按行号、页码或章节读取。
- **工具定义**：工具很多时，先提供类别或工具搜索入口，找到需要的工具后再加载完整定义和参数说明。
- **工具结果**：大结果写入文件，上下文里只放摘要、关键错误、总行数和路径，需要原文时再分页或搜索。
- **Skill**：Skill 是包含任务说明和可选脚本的技能包。先只展示名称和用途，匹配到任务后再读完整说明，按需加载脚本。

Skill 的加载机制见 [Agent Skills](../tools/agent-skills.mdx)。

渐进读取让单次输入变小，模型也更容易抓住当前步骤的重点，代价是工具调用轮次变多。要不要用，看完整内容有多大、实际用到多少。文件很小、每轮几乎都要读全文时，直接加载更简单。

## 5. 信任边界 {#信任边界}

上下文里的文档和网页可能包含看起来像指令的文字，比如「忽略以上规则」。应用要标明它们是待分析的数据，模型提出的操作能不能执行，由程序决定。

组装时要同时处理**内容边界、数据范围和执行权限**：

- 用明确的标签包裹外部文档，比如 `<document source="...">…</document>`，并在应用规则里说明其中内容只作参考，帮助模型识别来源。
- 检索前按用户和租户过滤数据。凭证、无关的内部规则和其他用户的数据，不进入本轮上下文。
- 工具结果引出高风险动作时，由程序校验权限和参数。模型负责理解文档，执行器负责判断操作是否获得授权。

标签只能帮模型区分内容，单靠它挡不住提示注入。具体防护见[提示注入](../safety/prompt-injection.mdx)。

### 5.1 状态冲突与时效 {#状态冲突与时效}

旧记忆和当前输入冲突时，先看冲突的是偏好、业务事实还是授权，三者的判断依据不同。为此每条状态都应记录主体、来源、时间和适用范围。

- 偏好：用户当前明确更正时，更新对应的旧条目。
- 业务事实：比如订单状态，以授权系统里的当前记录为准，而不是记忆里的旧值。
- 授权：以最新的授权状态为准。比如旧摘要写着「允许发送报告」，本轮用户撤回了授权，就应把授权标记为已撤回，执行器据此停止发送。旧摘要只记录过去的决定。

还有一种容易混淆的情况：检索文档里的「忽略规则」始终是文档内容。即使它被摘要或记忆转述过，也要带着来源，避免压缩以后被当成应用指令。

## 6. 常见问题 {#常见问题}

### 6.1 窗口足够大时，还需要选择信息吗？ {#长窗口与信息选择}

需要。输入越长，费用和处理时间越高，冗余内容还会让关键证据更难被用上。研究发现，在长文档问答中，位于中间位置的信息尤其容易被忽略。

所以目标是给出完成当前步骤所需的充分信息，同时移出无关内容。选择效果要在目标模型和任务上评测，检查回答是否真的用到了必要证据。

### 6.2 多任务之间怎样隔离上下文？ {#多任务上下文隔离}

每个任务或会话维护独立的历史和状态，读取时同时核对用户、租户和会话 ID。否则其他任务的结论或其他用户的数据可能混进当前输入。

授权范围一致时，稳定的规则和工具定义可以共享。子任务也可以放在独立的 Agent 上下文里执行，只返回结论、证据和未决事项，主任务据此继续，不必加载子任务的全部探索过程。

跨会话记忆的保存与读取见[Agent 记忆](../state/memory.mdx)。

## 7. 面试题 {#面试题}

### 7.1 用户消息、系统提示词、Memory 等信息如何组装并发送给模型？ {#context-assembly}

**题型**：综合题

**考察重点**：说明不同来源的信息怎样分层、怎样保留工具调用关系，以及如何在预算内选择内容。

**相关内容**：[上下文的组成](#上下文的组成)、[组装顺序与前缀缓存](#组装顺序与前缀缓存)。

<details>
<summary>参考回答</summary>

**应用应按消息角色与来源组装上下文，再按当前任务选择相关记忆、历史和证据。**

规则与工具定义放在稳定的前部，之后加入有效偏好和项目状态。对话历史保留用户、模型和工具消息的角色，工具结果通过调用 ID 关联原请求。本轮检索文档与当前输入放在后部，文档标明来源与版本，并与指令分隔。

长期记忆只读取当前任务需要的条目。组装前预留输出与后续工具结果预算，组装后估算 Token 数。超限时优先移出无关检索结果和已用过的旧工具输出，再压缩旧历史。固定规则与当前请求的必要条件应完整保留，事实时效和当前授权则分别核对。

</details>

### 7.2 Prompt 中静态内容和动态内容应该怎样排列，才能更好地利用前缀缓存？ {#prefix-cache-order}

**考察重点**：解释哪些输入变化会缩短共同前缀，以及怎样用缓存用量验证排列效果。

**相关内容**：[组装顺序与前缀缓存](#组装顺序与前缀缓存)。

<details>
<summary>参考回答</summary>

**把稳定规则和工具定义放在前部，把本轮文档与用户输入放在后部，有利于复用前缀缓存。**

缓存复用与之前请求完全相同的前缀计算。历史只在末尾追加时，已有前缀得以保留；修改中间内容时，变化位置之前仍可复用。因此，时间戳与请求 ID 应靠后，工具列表也应保持固定顺序。

命中还受缓存期限、最小长度和请求路由等条件影响，需要读取提供方的缓存用量明细验证。压缩历史时保留稳定规则，并比较压缩后整次任务的费用与耗时，才能判断是否有收益。

</details>

### 7.3 文档读取结果如何使用渐进式披露，避免上下文快速膨胀？ {#progressive-disclosure}

**考察重点**：解释模型怎样从索引定位到原文，并比较减少输入与增加调用的代价。

**相关内容**：[按需加载与渐进式披露](#按需加载与渐进式披露)。

<details>
<summary>参考回答</summary>

**渐进式披露先返回文档索引，再根据当前任务读取选中的片段。**

索引包含目录、章节摘要、总长度和稳定位置。模型据此选择章节，再通过工具的范围参数读取指定行或页。大型结果存入文件，上下文中保留路径、结论与关键错误，后续按引用搜索或分页读取。

这样能减少单轮输入，代价是增加调用次数。是否采用，要看完整内容大小和实际使用比例。文件很小且每次几乎都需要全文时，直接加载更简单。

</details>

### 7.4 旧记忆与当前输入冲突时，如何确定有效信息？ {#context-trust-freshness}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：区分偏好、业务事实和授权冲突，说明各自应以哪一类信息为准。

**相关内容**：[状态冲突与时效](#状态冲突与时效)。

<details>
<summary>参考回答</summary>

**有效信息要按来源、时间和适用范围判断，并区分偏好、业务事实与授权。**

用户明确更正偏好时，更新对应旧状态。业务事实则从授权系统读取当前记录。外部文档被写入摘要后仍是待分析的数据，保留来源有助于避免它被当作指令。

旧摘要中的授权如果已被撤回，执行器应按新状态停止对应操作。这样，过去的记录仍可追溯，当前动作也能遵守最新授权。

</details>
