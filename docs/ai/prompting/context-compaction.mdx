# 上下文压缩

**上下文压缩**（context compaction）是用更短的内容替换旧对话，让接近窗口上限的任务能继续执行。它本质上是有损的：被替换掉的原文，模型之后就看不到了。

因此设计压缩时，先想清楚下一步还需要知道什么。答好这个主题要抓住四点：选哪种压缩方案，摘要里留下哪些任务状态，什么时候触发压缩，以及压缩后消息序列和工具调用是否仍然有效。需要逐字核对的信息不能指望摘要，应另行归档。

## 1. 面试核心 {#core}

- 滑动窗口保留近期原文，摘要保留旧历史要点。前者会**丢掉较早的约束**，后者可能**遗漏或改写细节**，长任务通常组合使用。[卡](#overflow-strategies)
- 摘要要让下一轮能接着干活，应保留**任务目标、用户约束、关键决定、产物位置、未决错误和下一步**。[卡](#minimize-loss)
- 压缩要在窗口耗尽前触发，阈值应为**下一轮输入、工具结果和模型输出预留空间**。[卡](#compaction-trigger)
- 旧工具结果可以缩成**结论和原文引用**，原始结果留在外部存储，需要时再读。[卡](#tool-result-compaction)
- 裁剪历史时，工具调用和结果要**按调用 ID 成对保留**；恢复时先查执行状态，**不要盲目重跑有副作用的工具**。[卡](#compaction-tool-pairs)

## 2. 压缩方案 {#压缩方案}

选哪种方案，取决于下一步还需要哪些历史信息。下表是常见做法，长任务往往组合使用：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 截断 | 删除早期消息 | 早期约束会随消息消失。 |
| 滑动窗口 | 保留最近若干轮 | 远期事实需要另行保存。 |
| 摘要 | 用短文本表达旧历史 | 增加调用成本，也有遗漏风险。 |
| 窗口加摘要 | 近期留原文，远期留摘要 | 需要处理新旧事实冲突。 |
| 工具结果清理 | 旧结果缩为结论和原文引用 | 再次读取会增加调用。 |
| 外部存储加检索 | 归档原文，按需取回 | 依赖引用有效性和检索质量。 |

截断和滑动窗口不需要额外调用模型，实现也简单。**滑动窗口**只保留最近 N 轮原文，近期细节完整，长度也容易控制；代价是窗口外的信息直接移出，早期的目标和约束得另找地方保存。

**摘要**多花一次模型调用，把旧历史改写成较短的文本。它能留住远期要点，但改写时可能漏掉细节，甚至改变含义。窗口加摘要兼顾两头：近期看原文，远期看摘要。这时摘要最好用固定字段，并约定新旧事实冲突时以哪个为准。

在反复读文件、查日志的任务里，占满窗口的往往是工具结果，而不是对话本身。先清理已经用过的旧结果，能释放大量空间，同时保留对话主线。外部存储则把完整历史留在窗口之外，需要时再检索，代价是多一次读取延迟；而且原文虽然还在，模型也得能找到正确的那一段。

这几种方案丢信息的方式不同。删除重复结果只是变短，需要的事实还在；摘要则是改写，原话会被换成模型的理解。比如用户说「禁止修改公共接口」，摘要应该保留这句原话。如果被改写成「尽量减小改动」，一条硬性禁止就变成了对改动大小的偏好，后续步骤很容易越界。

## 3. 保留字段 {#保留什么}

摘要是写给下一轮的交接记录，所以要围绕任务状态来组织，而不是复述对话经过。压缩前可以把历史分成**必须保留、可以摘要和可以移出窗口**三类。

必须保留的信息用固定字段记录，比自由叙述更容易逐项核对，也不容易在多次压缩中被悄悄改掉：

- **目标与验收**：最终目标和完成条件。
- **约束与授权**：用户明确提出的约束和偏好，以及操作范围和已确认的事项。
- **决定与原因**：仍影响后续工作的选择，以及当时为什么这么选。
- **产物与状态**：文件路径、版本和实际修改结果。
- **错误与下一步**：未决问题、错误原文、失败过的尝试，以及接下来要做什么。
- **原文引用**：归档位置，方便按需恢复细节。

可以摘要的是探索过程：读过的代码和文档只留结论和位置。被否定的方案要留下否定的原因，否则恢复后模型可能再试一遍。可以移出窗口的是已经被后续结果替代的中间输出、重复的工具结果和寒暄。

下面用一个修复订单分页的任务，示范怎样记录**目标、约束与执行状态**：

```markdown
## 目标
修复订单分页最后一页的重复数据。
## 约束
禁止修改响应字段。
## 已完成
修改 src/order/repo.ts 的 offset 计算。
order.repo.test.ts 在当前提交通过。
## 未解决
orders.e2e 超时，原因未确认。
## 下一步
检查测试数据库，再重跑集成测试。
```

这份摘要把「单测通过」和「集成测试超时」分开写，恢复后一眼就能看出还差哪项验证。它还可以写得更完整：分页错误的原因是 `OrderRepository.page()` 用了 `page` 而不是 `page-1`，修改位置在 `src/order/repo.ts:41`，留下位置方便重新定位；约束也带上原因，比如「前端已经上线，所以响应字段必须保持不变」；下一步写成「启动本地测试数据库后重跑 e2e」，比「重跑集成测试」更具体。

摘要里的「已完成」只是历史记录，不等于现在的状态。所以文件路径是为了能重新读取产物，测试结果要附上所测的版本；恢复时还要重新核对文件、测试和外部系统，验收以当前检查结果为准。

目标和进度也可以写进上下文之外的进度文件，稳定的项目约束写进仓库指令。这样恢复时读的是原始记录，不是被摘要了好几遍的版本。持久化状态机制见[Agent 状态与持久化执行](../state/durable-execution.mdx)。

## 4. 触发时机与合并 {#触发时机与合并}

压缩必须在窗口耗尽前发生，否则下一轮的工具结果可能就放不下了。常见的**四种触发方式**适合不同任务：

- **Token 阈值**：已用 Token 达到窗口的某个比例时触发。阈值要为下一轮输入、工具结果和模型输出预留空间。
- **轮次**：每 N 轮压缩最早的一段，让历史定期缩短。同样的轮数里消息长短可能差很多，所以还要限制每轮长度。
- **任务边界**：子任务完成后，把探索过程压缩成结论。适合计划明确、能分阶段推进的长任务。
- **手动触发**：用户在切换话题前主动要求压缩，并指定要保留的重点。

编码 Agent 可以把预算检查接入自动压缩，同时提供手动入口。具体的触发比例和轮数属于应用配置，要按任务测试来定。

压缩不止一次时，还要决定旧摘要怎么处理。把旧摘要和新增历史**合并**成一份，总长度可控，适合预算紧张的任务；但每次改写都可能漏掉或改变早期内容，压缩次数越多，失真累积越多。

**分段保留**每次的摘要，可以少改写早期内容，适合需要保留阶段细节的任务，代价是摘要数量和总长度一直增长。实际可以折中：近期摘要分段保留，远期摘要再合并；最初的目标和仍有效的约束单独固定，不参与反复改写。

### 4.1 工具消息配对与重放 {#工具消息配对与重放}

压缩除了要留住任务信息，还要让剩下的消息序列符合 API 的会话规则。工具结果是通过调用 ID 关联到发起它的那次调用的。如果只删了调用、留下结果，这条结果就找不到来源，接口会直接报错。

所以裁剪时要把一次调用和它的结果当成一个整体，要么都留，要么都删；还没返回结果的调用，要保留到这次交互完成。即使用 LangChain 等框架裁剪历史，程序也应在生成摘要前检查配对是否有效。

需要旧工具结果时，应优先读归档，而不是重新调用工具。原因有两个：一是重新查询读到的是现在的状态，可能和当时的结果不同；二是支付、发邮件这类工具会改变外部系统，盲目重跑就会重复操作。这类操作恢复前要先查询执行状态，必要时使用**幂等标识**，也就是标记「这是同一次操作」的 ID，服务端收到重复请求时直接返回已有结果。

## 5. 常见问题 {#常见问题}

### 5.1 怎样验证压缩没有破坏任务？ {#压缩效果验证}

看任务压缩后还能不能正确完成。可以建立固定的回归用例：在长对话的早期或中途加入一条约束，触发压缩，再检查后续步骤是否仍然遵守。

对同一批任务，分别运行保留原文和启用压缩的版本，比较**三项指标**：

- 约束遵守率：早期的禁止事项和验收条件是否仍然有效。
- 任务成功率：压缩后能否继续完成原定目标。
- 恢复成本：重新读取文件和调用工具，多花了多少时间和费用。

出现失败时，对照压缩前后的字段，看目标、约束或未决错误是否被漏掉或改写，才能判断问题是不是出在压缩上。

### 5.2 摘要能还原成原文吗？ {#原文恢复}

不能。摘要只包含它保留下来的信息，丢掉的细节推不回来。需要逐字内容时，只能读压缩前归档的原文，所以压缩前要保存原始历史，并在摘要里留下能访问的引用。

引用要能定位到具体版本，读取时还要检查访问权限。如果是重新抓取外部页面，要记录抓取时间，因为页面内容会变。

## 6. 面试题 {#面试题}

### 6.1 对话超过上下文窗口时，有哪些处理方案？滑动窗口和动态摘要各有什么优缺点？ {#overflow-strategies}

**考察重点**：说明不同方案怎样保留信息，并比较调用成本与实现复杂度。

**相关内容**：[压缩方案](#压缩方案)。

<details>
<summary>参考回答</summary>

**超过窗口时，可以组合使用截断、滑动窗口、摘要、工具结果清理和外部检索。**

滑动窗口保留最近 N 轮原文，无需额外调用模型，实现简单且近期细节完整。窗口外的目标和约束会随旧消息移出，因此需要另行保存。动态摘要能留下远期要点，但多一次模型调用，也有遗漏或改写细节的风险。

组合方案可以固定保留系统规则、目标和约束，再用摘要记录旧过程，近期消息继续保留原文。大工具结果只放结论和归档位置。后续需要细节时，按引用读取原始历史。

</details>

### 6.2 压缩和摘要怎样尽量保留任务信息？ {#minimize-loss}

**考察重点**：说明哪些信息需要保留、摘要或移出窗口，以及怎样验证恢复后的任务。

**相关内容**：[保留字段](#保留什么)、[怎样验证压缩没有破坏任务？](#压缩效果验证)。

<details>
<summary>参考回答</summary>

**用固定字段保留关键任务状态，并保存原文引用，可以减少压缩造成的信息损失。**

目标、验收条件和用户约束决定后续工作的方向，应原样保留。授权范围、关键决定及其原因也应明确记录。产物位置、失败尝试和未决错误则告诉下一轮从哪里继续。探索过程可缩为结论与依据位置，被替代的中间结果可以移出窗口。

关键信息另存进度文件或状态库，摘要中区分已完成、已验证和计划执行。这样，恢复时可以读取实际产物，核对摘要记录。再用带远期约束的回归任务比较压缩前后表现，检查是否仍能遵守约束并完成目标。

</details>

### 6.3 常见的压缩触发机制有哪些？旧摘要和新摘要应该合并还是分别保留？ {#compaction-trigger}

**考察重点**：解释触发时机怎样影响剩余预算，以及合并和分段保留各适合什么场景。

**相关内容**：[触发时机与合并](#触发时机与合并)。

<details>
<summary>参考回答</summary>

**压缩可按 Token 阈值、轮次、任务边界或用户要求触发，摘要合并方式取决于预算和细节保留需求。**

Token 阈值要给下一轮输入、工具结果和输出留出空间。按轮次触发便于定期整理，但还需限制每轮长度。子任务完成时适合压缩其探索过程；手动触发则让用户指定保留重点。

合并摘要便于控制长度，适合预算紧张时使用。反复重写会改变早期内容，所以存在累计失真的风险。分段保留适合需要阶段细节的任务，但总长度会继续增长。可以固定目标和约束，近期分段保留，远期再合并。

</details>

### 6.4 Tool Result 如何淘汰或压缩？ {#tool-result-compaction}

**考察重点**：说明怎样控制工具结果的长度，并在清理后保留有效调用记录、避免重复操作。

**相关内容**：[压缩方案](#压缩方案)、[按需加载与渐进式披露](./context-management.mdx#按需加载与渐进式披露)。

<details>
<summary>参考回答</summary>

**工具结果可以在返回时限制长度，再把历史中已经使用过的旧结果压缩为结论和引用。**

大结果可以截断、分页或写入归档，上下文中保留摘要、总行数和路径。日志应先由程序按错误级别和请求 ID 过滤，让模型看到与任务相关的部分。

近期结果和未决错误保留原文。旧结果保留工具名、参数、调用 ID 和必要结论，便于追溯。清理后仍需满足调用与结果的配对规则。后续优先读取归档，避免重复执行支付、发邮件等有副作用的工具。

</details>

### 6.5 压缩后为何出现工具消息错误或重复操作？ {#compaction-tool-pairs}

**考察重点**：解释裁剪怎样破坏消息配对，以及重新执行工具为何会改变结果或造成重复操作。

**相关内容**：[工具消息配对与重放](#工具消息配对与重放)。

<details>
<summary>参考回答</summary>

**工具消息错误来自调用与结果失配，重复操作则会出现在旧结果被删除后盲目重跑工具的场景中。**

工具结果依赖调用 ID 找到原请求，所以压缩应按完整交互处理，并保留未完成调用。旧结果优先从归档恢复；重新查询会读到当前状态，写操作还会再次改变外部系统。因此，恢复写操作前应查询执行状态，并用幂等标识识别重复请求。

</details>
