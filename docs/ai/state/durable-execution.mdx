# Agent 状态与持久化执行

**Agent 状态**是任务执行到某一时刻的消息、进度和动作结果。**持久化执行**把这些状态保存到可靠存储里，进程崩溃、请求超时或者等人工审批时，任务都能从保存的位置接着推进，而不是从头再来。

这里要分清两件事。检查点解决的是「恢复进度」：知道做到了哪一步。但 Agent 会调用工具去下单、发邮件，恢复时如果把一个已经成功的写操作再执行一遍，就会重复扣款、重复发信，这要靠幂等机制来防止。人工介入的暂停和恢复，也是在这两者之上实现的。

## 1. 面试核心 {#core}

- 检查点把**消息、进度、动作结果和已用预算**写入持久存储，任务中断后从这里恢复。[卡](#resume-after-interrupt)
- 写操作用**稳定的幂等键加下游原子去重**，防止「执行成功但结果没记下来」时重复产生副作用。[卡](#retry-idempotency)
- **瞬时错误由程序有界重试**，需要改参数或换方案的错误交给模型，持续失败转入兜底。
- 人工介入把任务**保存为等待状态并释放工作进程**，收到有效输入后再恢复执行。[卡](#human-in-the-loop)
- LangGraph 恢复中断时**从节点开头重跑**，所以 `interrupt()` 之前的代码会再执行一次。[卡](#interrupt-node-replay)

## 2. 状态内容 {#状态包含什么}

恢复任务时，程序要知道两件事：已经完成了什么，接下来允许做什么。只存对话历史回答不了这两个问题，还要记录动作结果、任务状态和剩余预算。

| 内容 | 用途 |
| --- | --- |
| 任务、租户和用户标识 | 定位任务与隔离访问 |
| 消息与工具结果 | 恢复模型上下文 |
| 计划和进度 | 定位剩余工作 |
| 动作、参数与幂等键 | 核对执行结果 |
| 生命周期状态 | 控制运行、等待、完成和取消 |
| 已用预算与截止时间 | 防止恢复后重新获得完整预算 |

落到存储上，这些信息可以分成四组：

- **身份与会话**：任务 ID、会话 ID、用户和租户，用来找到任务、检查访问权限。
- **执行进度**：模型的输入输出、工具返回结果，以及待办、当前步骤和已完成步骤。
- **动作记录**：工具名、参数、幂等键、执行状态和结果，用来核对外部操作到底完成没有。
- **生命周期与预算**：任务处在运行、等待、失败、完成还是取消，以及累计用掉的步数、Token 和时间。预算要跟着状态保存，否则每次重启都会白得一份完整额度。

生命周期适合用**有限状态机**来描述，也就是一组明确的状态加上状态之间允许的转换。例如 `running` 表示正在执行，`waiting_approval` 表示等待审批，`failed` 表示执行失败，`done` 表示正常完成。应用可以规定：等待状态在批准后转为 `running`，被拒绝或超时后转为 `cancelled`。转换规则明确了，程序才能判断每个回调在当前状态下能做什么，比如一个迟到的审批回调遇到已经 `cancelled` 的任务，就应该被拒绝。

状态转换要用条件更新或版本检查，保证两个并发的恢复请求只有一个能推进任务。大文件这类产物放到外部存储，状态里只保留引用和版本，免得每个检查点都复制一遍完整文件。顺带一提，各步的输入、输出和状态记录，也可以用来排错、审计和构建评测集。

## 3. 检查点与恢复 {#检查点与恢复}

**检查点**是任务状态在某个执行位置的持久记录。任务崩溃后，程序加载最近一次可靠保存的检查点，先核对最后一个动作的结果，再决定接下来执行哪一步。

```text
步骤 1 → 检查点 1 → 步骤 2 → 检查点 2 → 步骤 3 崩溃
                                      ↑
                         恢复后核对动作，再推进步骤 3
```

设计检查点要定三件事：

- **写入时机**：可以在每个节点或每轮循环结束后保存，耗时长的步骤内部再加中间检查点。保存越频繁，故障时要重做的工作越少，写入开销也越大。如果是异步保存，还要估计最后几次更新可能丢失的窗口。
- **存储位置**：关系数据库、开启持久化的键值存储或对象存储都可以。只存内存的话，进程或节点一挂，状态就没了。Redis 的复制和落盘也有故障窗口，要按能容忍多少数据损失来选配置。
- **恢复流程**：加载最近的检查点，核对最后一个动作的执行结果，按幂等规则处理还没确认的动作，然后继续循环，并沿用原来的预算和截止时间。

具体框架的做法不同。LangGraph 用 **checkpointer**（负责读写检查点的组件）保存图状态，每个超步之后存一次；超步是图执行中，同一轮可运行节点一起推进的阶段。应用用 `thread_id` 标识一条执行线程，恢复时要用同一个 `thread_id` 和同一个检查点存储。注意 `InMemorySaver` 只把记录放在进程内存里，进程重启就取不回来了，需要跨进程恢复时要换成可靠的持久化存储。

Temporal 走的是另一条路：它保存事件历史，恢复时重放历史来重建工作流状态。重放要求工作流代码是确定性的，即同样的历史必须推出同样的执行决策，否则重放出来的状态就对不上。所以外部副作用要放进 Activity（工作流调用外部操作的执行单元）里执行，Activity 本身仍要考虑重试和幂等。

### 3.1 副作用与幂等恢复 {#副作用与幂等恢复}

检查点有一个它自己解决不了的问题：工具执行成功和本地记下结果之间，存在一个崩溃窗口。比如下单已经成功，进程却在写检查点之前退出了。恢复时检查点只显示「结果未记录」，程序并不知道单到底下没下，如果直接重试，就可能下两单。

解决办法是让写操作**幂等**，也就是同一个业务动作重复提交，仍然只产生一次业务效果。具体可以按下面的顺序执行：

1. 调用前持久保存动作意图、参数和幂等键，明确准备做什么。
2. 下游按幂等键原子去重，执行动作并保存结果，重复请求复用已记录的结果。
3. 恢复后按幂等键或业务 ID 查询结果，已完成时直接采用；需要重试时继续使用相同键。
4. 结果无法确认时保留未知状态，再通过对账或人工处理核对，避免贸然重复写入。

幂等键要绑定具体的业务动作和参数，去重记录的保留时间要覆盖整个重试窗口。不要拿模型的调用 ID 当幂等键：调用 ID 负责把工具结果关联到消息，业务幂等键负责去重，用途不同。

为什么第 2 步要求下游原子去重，而不是恢复时「先查一下，没有再执行」？因为查和执行之间有并发间隙：查询没结果时，原请求可能正在执行，还没写完。只有下游按幂等键原子去重，才能保证并发请求也只产生一次效果。只读动作可以直接重试，但第二次读到的数据版本可能不同，也可能多产生一次费用。

多步业务已经产生了部分效果时，可以准备补偿动作，例如取消订单或退款。补偿是用一个新的业务操作去修正结果，具体机制见 [Saga](../../system-design/distributed-data/saga-compensation-intermediate-state.mdx)。补偿本身也可能失败，同样要记录状态并重试；而已经发出去的邮件这类外部影响，是没办法完全撤回的。

## 4. 失败处理 {#失败处理}

失败后要不要重试，看的是参数不变时错误能不能自己消失。网络短暂中断，等一会儿再试就好；参数或业务条件错了，重试多少次结果都一样，必须改请求。

| 类型 | 处理 |
| --- | --- |
| 瞬时故障 | 有界退避，写入先满足幂等条件 |
| 参数错误 | 返回具体字段问题，供模型修正 |
| 业务拒绝 | 返回拒绝原因，调整方案 |
| 权限拒绝 | 保持受限状态，按授权流程处理 |
| 持续失败 | 熔断、稍后恢复或人工接管 |
| 模型不可用 | 保存状态，使用经过验证的备用方案 |

超时、429 和连接断开交给程序做指数退避，也就是每次失败后把等待间隔拉长一些，并限制重试次数。参数缺失时返回具体是哪个字段，订单不存在这类业务错误返回拒绝原因，让模型去调整方案。权限拒绝要走授权流程，不能让模型绕过已有约束。

同一个错误持续出现，就熔断，暂时不再调用出故障的下游；然后换用经过验证的备用工具或模型，或者保存任务等人工接管。

最后返回给用户时，要分清已完成、未完成和状态未知的动作，用户才能判断要不要去核对订单或重试任务。

## 5. 人工介入 {#人工介入}

**人工介入**（Human-in-the-loop，HITL）是让任务暂停下来，等人补充信息或作出决定。介入点通常放在三类位置：

- **高风险动作之前**：删除、转账、对外邮件和生产发布前，展示动作、参数与影响，让用户批准、修改或拒绝。
- **信息不足时**：保存当前问题，向用户澄清影响后续执行的信息。
- **反复失败后**：把已执行步骤和错误一并交给人工，便于接手处理。

实现上，人工介入就是前面检查点和状态机的组合。到达介入点后，程序保存检查点和待处理事项，把任务转为 `waiting_approval`，再通知审批人。因为等待状态已经持久保存，工作进程不用一直挂着，可以释放资源去处理别的任务；审批人可能过几个小时才回复，这一点很重要。

审批记录要绑定动作、参数、审批人和有效期限，并记下决定时间。回调或消息到达后，程序校验身份、任务版本和授权，再把决定写回状态：批准就继续执行，修改了参数就重新校验，拒绝就记录原因，终止或调整方案。

超时和重复回调同样要有明确的状态转换，否则一条过期的审批可能把已经取消的任务重新拉起来。授权细节见[工具授权与执行沙箱](../safety/tool-authorization-sandbox.mdx)。

### 5.1 LangGraph 中断节点重跑 {#langgraph-中断节点重跑}

LangGraph 恢复中断时，不是从暂停的那一行接着跑，而是**从中断节点的开头重跑**。

先看用法：配置了 checkpointer 后，节点里调用 `interrupt()` 会暂停执行并保存状态。之后应用用同一个 `thread_id` 传入 `Command(resume=...)`，`resume` 里的值会成为那次 `interrupt()` 的返回值。

问题在于，节点重跑时 `interrupt()` 前面的代码会再执行一遍。如果节点在请求审批之前先发了一封邮件，恢复时就会再发一封。解决办法是把副作用移到审批之后，或者拆到一个已经执行完的独立节点里。网络调用的结果和随机值也一样，要保存到状态里复用，否则重跑会得到不同的值。

把副作用移到审批之后也不等于万事大吉：执行时仍可能失败、重试，所以写操作还是要用同一个业务幂等键。

## 6. 面试题 {#面试题}

### 6.1 Agent 执行中断后如何恢复？检查点和快照怎么持久化？ {#resume-after-interrupt}



**考察重点**

- 能说明恢复需要哪些状态，何时写检查点，以及存储故障会丢失什么。
- 能区分进度恢复与业务动作核对，处理结果尚未记录的崩溃窗口。

**相关内容**：[状态内容](#状态包含什么)、[检查点与恢复](#检查点与恢复)。

<details>
<summary>参考回答</summary>

**任务通过持久检查点恢复进度，再核对未确认的动作结果，决定从哪里继续。**

检查点保存消息、计划、工具参数与结果，以及生命周期状态和已用预算。可以在每个节点或每轮结束后写入数据库等可靠存储，耗时步骤再增加中间检查点。保存的执行记录还可用于排错、审计与评测。

LangGraph 通过 `thread_id` 定位检查点，内存 checkpointer 在进程重启后会丢失记录。Redis 也要根据复制与落盘方式，评估故障时会丢失多少更新。

恢复时先加载最近记录，再核对最后一个动作。只读动作可以重新读取，写操作使用调用前保存的幂等键查询或重试，由下游原子去重。无法确认的结果保留未知状态，恢复后继续累计原预算。

</details>

### 6.2 工具调用失败时如何处理？重试时怎样保证不会重复执行？ {#retry-idempotency}



**考察重点**

- 能根据错误类型选择重试、修正参数、降级或人工处理。
- 能说明幂等键和原子去重如何配合，并解释查询为空为何仍需谨慎重试。

**相关内容**：[副作用与幂等恢复](#副作用与幂等恢复)、[失败处理](#失败处理)。

<details>
<summary>参考回答</summary>

**工具失败后按错误类型处理，写操作通过稳定幂等键和下游原子去重防止重复执行。**

超时与限流由程序指数退避，并限制次数。参数错误或业务拒绝作为工具结果交给模型，供它修改参数或方案。权限拒绝保持原有约束，持续失败则熔断、降级或转人工，并告知用户哪些动作已经完成。

调用前记录意图与参数，重试沿用同一个幂等键。恢复时可以查询下游已有结果，但查询为空也可能是原请求尚未完成。因此，查询之后的重试仍需下游原子去重。

无法确认的写入保留未知状态，已产生的部分业务效果按预定方案补偿。任务状态转换用版本号或条件更新保护，避免并发恢复请求重复推进。

</details>

### 6.3 Human-in-the-loop 如何实现？人工介入后任务怎样继续？ {#human-in-the-loop}



**考察重点**

- 能判断哪些动作、缺失信息或失败需要人工介入。
- 能解释等待期间如何释放资源，以及收到审批后如何校验并恢复。

**相关内容**：[人工介入](#人工介入)、[检查点与恢复](#检查点与恢复)。

<details>
<summary>参考回答</summary>

**人工介入通过持久化等待状态暂停任务，收到有效决定后再恢复。**

介入点可以放在高风险动作前、信息不足时，或多次失败后。暂停时保存检查点、动作参数和任务版本，并向审批人展示待处理内容及原因。随后释放工作进程，等待回调或消息。

收到决定后，程序校验身份、时效和状态版本。批准后执行，修改参数后重新校验，拒绝则记录原因并终止或调整方案。审批记录保留审批人与时间，超时和重复回调按状态转换规则处理。

LangGraph 可以用 `interrupt()` 配合 checkpointer 实现暂停。恢复时会重跑中断节点，因此副作用要放在合适的执行位置，并使用幂等键保护。

</details>

### 6.4 LangGraph 恢复 interrupt 后，会从暂停的代码行继续吗？ {#interrupt-node-replay}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：能说明恢复的执行起点，以及节点重跑为什么会重复触发副作用。

**相关内容**：[LangGraph 中断节点重跑](#langgraph-中断节点重跑)。

<details>
<summary>参考回答</summary>

**恢复会从中断节点开头重新执行，而不是从暂停的代码行直接继续。**

`Command(resume=...)` 的值会成为对应 `interrupt()` 的返回值，但此前的代码已经再次运行。因此，审批前发送邮件会触发重复发送。

副作用可以移到审批后，或拆进已经完成的独立节点。节点中需要复用的网络结果与随机值应保存到状态，写操作重试时继续使用稳定的幂等键。

</details>
