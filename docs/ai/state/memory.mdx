# Agent 记忆

**Agent 记忆**是在模型上下文之外保存信息，并在后续调用中按需取回的机制。这里的上下文，指本次请求实际交给模型的输入，它受窗口大小限制，请求结束就没了。用户偏好、过去任务的进度要想在下次还能用上，就得由应用或服务另外保存，到时候再取回来放进上下文。

所以设计记忆系统，核心问题有三个：什么值得存，什么时候取回、取多少，以及信息过时或被删除时怎样让它不再出现。外部存储的容量可以很大，但只有被取回、放进上下文的那部分，才会参与本次回答。

## 1. 面试核心 {#core}

- **短期记忆保存当前会话的消息和任务状态，长期记忆跨会话保存信息**，并按需取回。[卡](#short-long-memory)
- 记忆系统通过**提取、存储、检索和生命周期管理**四个环节，决定保存什么、何时复用、何时失效。[卡](#memory-system)
- 长期记忆只保存**有明确来源、适用范围和未来复用价值**的信息；来自外部文档的内容要先核对来源。
- 处理冲突要核对**主体、事实的适用时间和来源可信度**；用户明确更新后，把旧值标为失效。[卡](#memory-lifecycle)
- 删除记忆要**同步清理主记录、检索索引和派生缓存**，并阻止后台任务把旧内容写回。[卡](#memory-deletion-isolation)

## 2. 记忆的类型 {#记忆的类型}

**短期记忆**服务于当前会话或当前任务，**长期记忆**跨会话保存、在以后的会话里复用。短期和长期说的是作用范围；按保存的内容，还可以再细分成五种：

| 类型 | 内容 | 组织方式 |
| --- | --- | --- |
| 工作记忆 | 当前消息、工具结果与待办 | 会话状态 |
| 会话摘要 | 较早交互的重点 | 带来源的摘要记录 |
| 语义记忆 | 用户事实与偏好 | 结构化条目或档案 |
| 情景记忆 | 过去任务与结果 | 带时间及证据的记录 |
| 程序记忆 | 方法和稳定约定 | 规则文件、Skill |

它们的存储和保留方式各不相同：

- 工作记忆按会话 ID 存在内存、Redis 或数据库里。注意「短期」指的是作用范围：即使写进了持久化数据库，它服务的仍然只是当前任务。
- 会话摘要把较早轮次的重点存进数据库，保留多久由产品决定，比如数周到数月。摘要要记录来源，方便回查原始对话。
- 语义记忆保存「偏好 Python」「住在上海」这类事实和偏好，可以用键值库或文档库；需要按含义查询时，再建向量索引。
- 情景记忆保存一次具体经历，例如「上次部署因端口冲突失败」。要记下时间、处理过程和证据，以后的任务才能判断这条经验还适不适用。
- 程序记忆保存团队代码规范这类稳定的方法，可以写进规则文件、Skill 或受维护的系统提示，长期使用时定期更新。

实际系统常把几种组合起来。一种三层方案是：最近几轮保留原文，较早的轮次压缩成摘要，跨会话的信息从长期库取回。原文保证当前细节不丢，摘要控制历史长度不超出窗口，长期库让新会话也能用上以前的信息。具体分几层由任务决定，关键是讲清每一层什么时候写、什么时候读。短期历史太长时，也可以用滑动窗口只保留近期消息，再用摘要保存较早的重点。

## 3. 写入、存储与检索 {#写入存储与检索}

一次对话里的内容并不都值得长期保存，所以写入要先筛选：应用先提取候选信息，再核对来源、适用范围和复用价值。整个流程分四个阶段：

| 阶段 | 设计要点 |
| --- | --- |
| 提取 | 类型、主体、内容、来源和有效时间 |
| 存储 | 用户与租户命名空间、版本和过期时间 |
| 检索 | 权限过滤、语义或关键词召回、排序 |
| 注入 | 只放入当前任务需要的条目与来源 |

适合长期保存的，主要是**稳定偏好、长期事实和已验证的经验**：

- 用户明确要求记住的稳定偏好，例如以后都使用中文回答。
- 对未来任务有用的背景、长期目标和重要决定。
- 多次交互中重复出现，并经来源核对的事实。
- 已验证的任务经验，例如某次部署失败的原因与解决办法。

对比一下：「这次用英文回答」只约束当前任务，应该留在会话状态里，存成长期偏好反而会让以后的回答出错。重复出现也只是一个筛选信号，不能作为保存的依据：外部网页反复夹带同一条恶意要求，出现次数再多也要拦截。写入时保留来源，才能避免把提示注入当成用户偏好存下来。

比如用户说「以后都用中文回复」，提取后可以整理成这样一条记录：

```json
{
  "type": "preference",
  "subject": "user",
  "content": "回复使用中文",
  "source": "会话 123",
  "time": "2026-10-14"
}
```

`content` 是偏好本身，`source` 记录它从哪来，`time` 留给以后更新和判断冲突时用。`subject` 这里只写了 `user`，要由服务端把它关联到实际的用户，才能保证记录写进正确的用户空间。

写入时机有两种选择。即时写入能让下一轮马上读到新偏好，代价是拖慢当前请求；会话结束后在后台批量提取，调用次数少，但新记忆要等后台任务跑完才可用。需要立刻生效又想后台提取时，可以先把偏好放在当前会话状态里。

提取和压缩目标明确、调用又频繁，可以试着交给小模型做，省费用也省等待。采用前要用冲突、遗漏和归属错误的样例评测，确认它能正确识别主体和来源。

存储时，把用户 ID、类型、时间、来源和过期时间放进结构化字段，方便过滤、更新和删除。内容可以向量化，按含义相似度查找，也可以建关键词索引。每条记录还要归属到一个**命名空间**，也就是为每个用户或租户划出的存储分区，读写都限定在自己的分区里。

取回时，可以组合三种方式：

- **按问题检索**：每轮根据当前问题召回相关条目，再结合相关性、时间新近度和重要性排序，只取少量内容进入上下文。
- **固定读取核心字段**：用户名和语言偏好可以精确查询，直接加载，省去相似度检索。
- **通过工具查询**：把记忆检索提供为工具，让模型在需要回顾历史时发起调用，程序负责权限过滤。

如果记忆是按日期写在一个大文件里的，可以切成带主体、时间和来源的条目再建索引。这样每次只读相关的条目，匹配更准，也不会让整份历史占满上下文。

## 4. 更新与遗忘 {#更新与遗忘}

用户的情况会变，记忆也要跟着变：回答时只用当前有效的信息，同时保留必要的修改记录。处理两条相似记录时，判断标准是它们是不是在说同一主体、同一时间的同一件事。

写入前先检索相似条目，含义和适用范围都相同就合并，并更新出现次数和最近观察时间。但文本相似不代表重复，「上周在北京」和「本周到上海」可以同时成立。所以语义相近只是去重的候选，还要核对主体和时间。

真正冲突时，按来源处理。用户先说「住在北京」，后来明确说「已经搬到上海」，就把旧住所标为失效并保留修改历史，回答当前住所时只读有效条目。外部文档和用户的说法冲突时，要核对来源可信度和事实的适用时间。后到的文本不会自动更可信，判断不了时，标记为待确认或直接问用户。

遗忘也要设计。临时状态设置 TTL（条目的有效期限），比如「这周在出差」到本周结束就失效。长期没被访问、重要性又低的条目，可以降低检索权重或归档，免得干扰回答。产品还应明确保留期限，并提供查看、修改和删除记忆的入口，让用户能纠正错误事实、撤回偏好。

### 4.1 租户隔离与删除传播 {#租户隔离与删除传播}

隔离和删除要覆盖所有能把记忆送回模型的路径。只删主记录是不够的，向量索引或摘要里的旧内容仍然会被检索出来。

隔离的做法是：读写都绑定当前用户和租户，检索时先限定可访问的命名空间，再在范围内做相关性排序。顺序不能反过来，先排序再过滤，过滤一旦有遗漏，别人的记录就可能混进结果。模型给出的用户 ID 只是一个请求参数，实际能访问的范围由服务端根据当前身份核对。

删除时，要同步处理这几类副本：

- 清理主记录对应的向量条目与结果缓存，使检索结果及时失效。
- 使派生摘要失效或重新生成，移除摘要中继承的旧事实。
- 让后台任务在写回前检查删除标记，防止正在处理的旧条目再次出现。
- 按明确的保留策略清理备份与审计记录，说明它们的保留期限。
- 对运行中上下文已读入的内容，按产品策略清除或重开会话，停止继续使用。

## 5. 常见问题 {#常见问题}

### 5.1 编码 Agent 的文件记忆 {#编码-agent-的文件记忆}

编码 Agent 常把项目的稳定规则和长任务进度写在文件里，因为人和 Agent 都能直接读、直接改，还能通过版本管理看到变化。比如项目指令文件保存构建命令和代码规范，用户级文件保存个人偏好，待办或进度文件记录任务推进到哪一步。文件变长之后同样要维护和精简，否则过时的规则或进度会误导后续任务。`AGENTS.md`、`CLAUDE.md` 等文件的加载范围取决于工具，具体见[仓库指令](../development/repository-instructions.mdx)。

### 5.2 记忆与 RAG {#记忆与-rag}

两者关注的问题不同。记忆管理的是跨交互的信息生命周期：交互中哪些事实值得保存，什么时候更新、什么时候遗忘。RAG 是为当前这次生成检索外部证据，文档通常不是从对话里产生的；它的文档也可以按用户隔离，权限要求取决于具体应用。

相同之处在于都要从外部存储取回信息，所以可以共用一套向量或关键词检索设施。检索机制见[检索增强生成（RAG）](../rag/rag.mdx)。

## 6. 面试题 {#面试题}

### 6.1 Agent 的短期记忆和长期记忆分别如何实现？哪些信息适合长期保存？ {#short-long-memory}



**考察重点**

- 能解释短期与长期记忆保存在哪里、何时有效，以及如何进入上下文。
- 能按来源、稳定性与复用价值筛选长期信息，并处理一次性请求。

**相关内容**：[记忆的类型](#记忆的类型)、[写入、存储与检索](#写入存储与检索)。

<details>
<summary>参考回答</summary>

**短期记忆按会话保存当前消息与任务状态，长期记忆跨会话保存事实、偏好和经验。**

短期记忆可以存在内存、Redis 或数据库中，按会话 ID 读取。输入过长时，保留近期原文并压缩较早历史。长期记忆把结构化字段放入数据库，需要按含义查找时再建立向量索引。每轮只取回与问题相关的少量条目，放入当前上下文。

长期保存应有明确来源和未来用途，比如稳定偏好、背景事实、重要决定与经过验证的任务经验。一次性请求留在当前会话，临时但有用的信息设置过期时间。取回记忆前先过滤权限，再判断哪些内容值得占用本次输入空间。

</details>

### 6.2 一个完整的 Agent 记忆系统应该如何设计？Memory 如何提取、存储和检索？ {#memory-system}



**考察重点**

- 能说明提取、存储、检索与维护各自承担的职责。
- 能解释近期原文、历史摘要和长期库分别何时写入、何时读取。

**相关内容**：[写入、存储与检索](#写入存储与检索)、[更新与遗忘](#更新与遗忘)。

<details>
<summary>参考回答</summary>

**记忆系统需要提取、存储、检索和维护四个模块，也可以用近期原文、历史摘要和长期库分层组织。**

提取模块在会话结束或发现重要信息时，生成带主体、来源和时间的候选条目。小模型可以承担这类目标明确的任务，但要用冲突与遗漏样例确认效果。

存储模块把元数据放数据库，便于按用户、类型和时间过滤；文本按需建立向量或关键词索引。检索先限定用户权限，再按相关性、时间和重要性排序。核心偏好可以固定读取，其他信息按当前问题召回，或由模型通过工具查询。

维护模块处理去重、冲突、失效和删除。即时写入保证下一轮可用，后台写入减少前台等待。如果历史存在按日期的大文件中，应切分为带来源的条目并建立索引，减少无关内容进入上下文。

</details>

### 6.3 短期记忆如何转为长期记忆？长期记忆如何去重、过期和处理冲突？ {#memory-lifecycle}



**考察重点**

- 能判断哪些会话信息值得长期保存，并说明如何核验来源。
- 能根据主体与时间处理重复和冲突，并解释过期、删除如何生效。

**相关内容**：[写入、存储与检索](#写入存储与检索)、[更新与遗忘](#更新与遗忘)。

<details>
<summary>参考回答</summary>

**短期信息在具备明确来源、稳定含义和未来复用价值时，可以提取为长期记忆。**

用户要求记住的偏好、长期目标和经过验证的经验都适合筛选。多次出现可以作为信号，但还要核对来源，防止外部注入被保存为事实。会话结束时可批量提取候选，再与已有条目比较。

去重时核对主体、含义与有效时间，相同条目合并并更新出现次数。用户明确更新住所等事实时，使旧值失效并保留历史。时间不同的状态可以并存，无法判断的冲突则保留待确认。

临时信息设置 TTL，长期低价值条目降低权重或归档。用户可以查看、修改和删除记忆，删除还要同步清理索引、缓存和派生摘要。

</details>

### 6.4 长期记忆怎样避免跨用户泄漏，删除后如何防止再次被检索？ {#memory-deletion-isolation}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：能说明检索前的权限过滤，以及索引、摘要和后台写入对删除效果的影响。

**相关内容**：[租户隔离与删除传播](#租户隔离与删除传播)。

<details>
<summary>参考回答</summary>

**检索前按当前身份限定用户和租户范围，删除时同步使主记录与派生副本失效。**

服务端核对命名空间，模型传来的用户 ID 仅作为待校验参数。这样，相关性检索只会在当前用户有权访问的记录中进行。

删除主记录后，还要清理向量索引和缓存，重建含有旧事实的摘要。后台任务写回前检查删除标记，避免旧内容重新出现。备份与日志按各自保留策略清理，已进入运行中上下文的内容也要清除或通过重开会话停止使用。

</details>
