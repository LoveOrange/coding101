# Agent 框架选型

Agent 框架把模型调用、工具注册、执行循环、状态持久化和追踪等通用部分封装起来。面试中的框架问题很少考 API 细节，主要考两件事：能否说清框架替你做了什么，以及为什么在这个项目里选它、不选它或自研。本文以 LangChain 和 LangGraph 为主，比较常见框架的定位，并给出选型依据。框架版本变化很快，具体 API 以官方文档为准，本文内容核对于 2026-10。

## 1. 面试核心 {#core}

- LangChain 提供模型、提示、工具、检索器等组件的统一接口和组合方式，适合快速搭建线性链路和标准 Agent；LangGraph 用“状态 + 节点 + 边”的图描述流程，支持循环、分支、检查点、中断恢复，适合需要精确控制的长流程。[卡](#langchain-langgraph-native)
- 手写 Agent 的核心只是一个循环：调用模型、解析工具调用、执行、把结果追加回上下文。框架的价值在于持久化、人工介入、流式输出、追踪和生态集成，而不是循环本身。
- 选框架还是自研，看需求是否落在框架的抽象内：上下文策略、权限模型、部署环境有特殊要求，或团队需要掌控每一次调用时倾向自研；需要快速交付、标准能力足够时用框架。[卡](#framework-or-custom)
- LangGraph 的 State 定义各字段的合并方式：节点返回部分更新，没有声明归并函数的字段被覆盖，声明了的（如消息列表）按函数合并。条件边用路由函数决定下一个节点，检查点按线程保存每一步的状态，用于恢复和人工审批。[卡](#langgraph-state)
- 不同框架的定位不同：多 Agent 对话（AutoGen）、角色分工（CrewAI）、数据与检索（LlamaIndex）、提供方官方 SDK、Java 生态（Spring AI）、低代码平台（Dify、Coze）。[卡](#framework-landscape)

## 2. 框架替你做了什么 {#responsibilities}

一个可上线的 Agent 除了模型循环，还需要下面这些部分，框架覆盖的范围各不相同：

| 能力 | 手写时要做的事 | 框架中的对应 |
| --- | --- | --- |
| 模型接入 | 适配不同提供方的消息格式、工具调用格式、流式事件 | 统一的模型接口 |
| 工具 | 生成参数 Schema，解析调用，执行和错误回传 | 工具装饰器、工具节点 |
| 执行循环 | 循环、停止条件、最大步数 | 预置 Agent（ReAct） |
| 状态与持久化 | 保存每一步状态，进程重启后恢复 | 检查点（Checkpointer） |
| 人工介入 | 暂停、等待审批、带着输入恢复 | 中断与恢复 |
| 流式输出 | 转发模型 Token、工具进度事件 | 多种流式模式 |
| 可观测性 | 记录每次调用的输入输出、耗时和 Token | 追踪平台集成 |
| 生态 | 向量库、文档加载器、MCP | 集成包 |

这张表也是面试回答“框架带来了什么”的结构：先说自己项目需要哪几项，再说框架提供了哪些、哪些仍需自己实现。

## 3. LangChain 与 LangGraph {#langchain-langgraph}

**LangChain** 的出发点是“链”：把提示模板、模型、输出解析器、检索器等组件用统一的接口串起来，一个组件的输出作为下一个的输入，形成固定的处理链路。早期的大量预置链（问答链、摘要链）抽象较重，调试困难。1.0 版本以后，LangChain 收敛为以 `create_agent` 为中心的 Agent 开发接口，底层运行在 LangGraph 上，用中间件在模型调用、工具调用前后插入自定义逻辑（如摘要、人工审批、重试）；旧的链式接口移入单独的兼容包。

**LangGraph** 是更底层的编排框架，用有向图描述流程：

- **State**：全局状态的结构，每个字段可以声明归并函数（reducer）。
- **Node**：一个函数，读取状态，返回要更新的字段。
- **Edge**：固定边指定下一个节点；条件边由路由函数根据状态返回下一个节点名。图可以有环，这就是 Agent 循环。
- **Checkpointer**：每一步执行后按线程（thread）保存状态快照，用于恢复、回放和查看历史；生产环境使用数据库实现。
- **Interrupt**：节点内暂停执行等待外部输入，之后用同一线程 ID 恢复，用于人工审批和补充信息。

执行模型借鉴 Pregel：按“超步”推进，同一超步中可以并行执行多个节点，各节点的更新通过归并函数合并进状态，再进入下一超步。

| 维度 | LangChain（1.0 以后） | LangGraph |
| --- | --- | --- |
| 抽象层次 | 高层 Agent 接口与组件集成 | 底层图编排与运行时 |
| 适合 | 标准的工具调用 Agent、快速原型 | 多步骤、有分支和循环、需要持久化和人工介入的流程 |
| 控制粒度 | 通过中间件定制 | 每个节点和边都由自己定义 |
| 关系 | Agent 运行在 LangGraph 上 | 可以单独使用，也可以调用 LangChain 组件 |

## 4. 常见框架的定位 {#landscape}

| 框架 | 定位 | 适用场景 |
| --- | --- | --- |
| LangGraph | 图编排、持久化执行 | 复杂流程、长任务、人工介入 |
| AutoGen | 微软的多 Agent 对话框架，Agent 之间通过消息协作。已进入维护模式，微软的后续方向是合并了 AutoGen 与 Semantic Kernel 的 Agent Framework（2026-04 发布 1.0） | 多角色讨论、研究原型 |
| CrewAI | 按角色、任务、团队组织多 Agent | 分工明确的内容生成和业务流程 |
| LlamaIndex | 数据接入、索引和检索 | 以知识库为中心的 RAG 应用 |
| OpenAI Agents SDK、Claude Agent SDK、Google ADK | 提供方的官方 Agent SDK | 主要使用对应提供方的模型，需要其托管工具 |
| Spring AI | Java 生态的模型、工具、RAG、MCP 接入 | Java 后端团队，复用 Spring 体系 |
| Dify、Coze | 可视化编排平台 | 业务人员搭建、快速验证 |

编码 Agent（Claude Code、Codex 等）是面向具体任务的完整产品，它们的 Harness 设计可以作为自研 Agent 的参考，见 [Agent Harness](../agents/harness.mdx)。

## 5. 选型依据 {#selection}

1. **流程复杂度**：一次调用或固定几步，直接调用 API 或用轻量封装即可；有循环、分支、并行和长时间运行，才需要图编排和持久化。
2. **控制需求**：上下文怎样组装和压缩、工具怎样授权、何时停止，如果有框架无法表达的特殊要求，自研或只用底层组件。
3. **团队与语言**：Java 团队优先评估 Spring AI，Python 团队选择更多；团队对框架内部的熟悉程度决定出问题时能否定位。
4. **可观测与运维**：是否能拿到每一步的输入输出、Token 和耗时；检查点存储能否满足部署环境。
5. **版本稳定性**：框架接口变化频繁，核心业务逻辑（工具实现、提示、评测集）不要依赖框架私有的抽象，便于升级或替换。

自研不等于从零写所有东西。常见做法是用官方 SDK 调用模型、自己写循环和状态管理，在追踪、向量库等边缘能力上使用现成组件。

**考察重点**

- 归并函数决定覆盖或合并；检查点与中断恢复的机制。

**相关内容**：[LangChain 与 LangGraph](#langchain-langgraph)、[检查点与恢复](../state/durable-execution.mdx#checkpoint)。

<details>
<summary>参考回答</summary>

LangGraph 用有向图描述流程。State 是全局状态的结构，节点是读取状态并返回部分更新的函数，边决定下一个节点：固定边直接连接，条件边由路由函数根据状态返回节点名，异常分支可以在状态里写入错误信息，由路由函数转到处理节点。图允许有环，模型节点和工具节点之间的环就是 Agent 循环。执行按超步推进，同一超步可以并行运行多个节点，更新合并进状态后再进入下一步。

State 中每个字段可以声明归并函数：没有声明的字段，节点返回的新值直接覆盖；消息列表通常声明为追加合并，并行节点同时写同一字段时也依靠归并函数合并。设计 State 时只放流程需要传递的数据，如消息、当前计划、中间结果、错误和重试次数，大对象放外部存储只保留引用。

持久化依靠 Checkpointer：每个超步结束后按 thread_id 保存状态快照，进程重启后用同一个 thread_id 从最后的检查点继续。人工介入在节点中调用中断，执行暂停并保存状态，把待审批内容返回给前端；用户处理后，用同一 thread_id 带着输入恢复，从中断处继续。子图可以作为节点嵌入，父图与子图通过共享的状态字段或输入输出转换传递数据。

</details>

按定位区分：LangGraph 做图编排和持久化执行，适合长链路、有分支和人工介入的流程；LangChain 提供高层 Agent 接口和大量集成；AutoGen 以多个 Agent 互相发消息协作为核心，适合多角色讨论；CrewAI 按角色、任务和团队组织 Agent，适合分工明确的流程；LlamaIndex 侧重数据接入和检索，适合知识库应用；OpenAI、Anthropic、Google 的官方 SDK 与自家模型和托管工具结合紧密；Spring AI 面向 Java 团队；Dify、Coze 是可视化平台，适合快速验证。多模型接入时可以加 LiteLLM 这类网关统一接口和路由。

长链路场景优先考虑支持检查点、中断恢复和细粒度控制的图编排框架，或者在官方 SDK 上自研循环。回答时最好对比自己项目实际评估过的两三个选项，说出放弃其他选项的原因。
