# Agent 框架

Agent 框架封装模型接入、工具和运行状态。本文负责抽象层次、LangGraph 状态合并与选型。恢复语义见[Agent 状态与持久化执行](../state/durable-execution.mdx)。版本相关内容核对于 2026-10-13。

## 1. 面试核心 {#core}

- LangChain v1 的 `create_agent` 基于 LangGraph 运行。[卡](#langchain-langgraph-native)
- LangGraph 用 State、节点和边表达有状态流程。[卡](#langgraph-state)
- State 字段的 reducer 决定更新如何合并。[卡](#parallel-state-reducer)
- 框架选型取决于控制需求、集成与维护成本。[卡](#framework-or-custom)
- Agent 框架分别侧重编排、数据接入或开发生态。[卡](#framework-landscape)

## 2. 框架能力 {#框架替你做了什么}

| 能力 | 需要解决的问题 |
| --- | --- |
| 模型适配 | 消息、工具格式和流式事件的转换 |
| 工具管理 | Schema、执行和错误回传 |
| 循环与编排 | 节点调度、分支和停止条件 |
| 持久化 | 保存检查点并恢复 |
| 人工介入 | 暂停、接收输入、恢复 |
| 追踪 | 输入输出、耗时、用量和错误 |
| 集成 | 检索器、向量库、MCP 等组件接入 |

各框架的覆盖范围不同。业务授权、验收条件和部署配置仍由应用负责。选型时用项目要求逐项验证能力。

## 3. LangChain 与 LangGraph {#langchain-与-langgraph}

LangChain v1 以 `create_agent` 为高层入口。中间件能调整模型调用、工具处理和状态。旧版链等接口迁入 `langchain-classic`。LangChain Core 仍提供可组合的基础抽象。

LangGraph 用图描述流程。节点读取 State，并返回部分更新。固定边连接节点，条件边通过路由函数选择后继。图可以包含循环和并行分支。

执行按超步推进。同一超步内的节点可以并行。更新合并后，后继节点读取新状态。

| 维度 | LangChain v1 | LangGraph |
| --- | --- | --- |
| 层次 | 高层 Agent 接口 | 图编排与运行时 |
| 定制方式 | 中间件与组件配置 | 节点、边和状态模式 |
| 适用情况 | 标准 Agent 与生态集成 | 需要精确控制的有状态流程 |

检查点按线程保存状态，支持中断后恢复。具体行为见[检查点与恢复](../state/durable-execution.mdx#检查点与恢复)。

### 3.1 State 归并与并行更新 {#state-归并与并行更新}

未指定 reducer 的字段采用覆盖更新。同一超步并行写入此类字段，会产生更新冲突。字段需要多个结果时，应定义合并规则或拆开存储。

```python
from typing import Annotated, TypedDict
import operator

class ReviewState(TypedDict):
    findings: Annotated[list[str], operator.add]
```

两个节点分别返回 `{"findings": ["A"]}` 和 `{"findings": ["B"]}`。列表归并后包含两个发现。需要稳定展示顺序时，再按任务 ID 排序。

消息字段可使用 `add_messages`。它为新消息追加条目，遇到已有消息 ID 时更新条目。简单列表拼接只会追加，二者的更新语义不同。

## 4. 常见框架的定位 {#常见框架的定位}

| 框架 | 主要定位 |
| --- | --- |
| LangGraph | 图编排、状态与检查点 |
| AutoGen | 通过消息组织多 Agent 协作 |
| CrewAI | 按角色、任务和团队组织协作 |
| LlamaIndex | 数据接入、索引与检索 |
| OpenAI Agents SDK | Agent 循环、工具、转交和追踪 |
| Claude Agent SDK | 复用 Claude Code 的工具与执行能力 |
| Google ADK | 模块化 Agent 与工作流开发 |
| Spring AI | Spring 生态的模型、工具、RAG 与 MCP |
| Dify、Coze | 可视化编排与应用集成 |

SDK 的模型支持与部署方式应分别核对。官方 SDK 也能执行应用提供的工具。编码产品的运行时分工见 [Agent Harness](../agents/harness.mdx)。

## 5. 选型依据 {#选型依据}

- 流程简单时，直接 API 调用能减少依赖。
- 需要复杂状态和恢复时，验证框架的持久化能力。
- 有特殊上下文或授权要求时，检查扩展点覆盖范围。
- 线上排障需要逐步追踪，也需要明确存储与运维责任。
- 升级前固定版本，回归工具、状态和失败路径。

自研可以复用 SDK、存储和追踪组件。框架方案也需承担依赖升级和抽象调试成本。比较时采用同一任务集和运行预算。

### 6.5 LangGraph 并行节点同时更新 State 时，怎样避免覆盖或冲突？ {#parallel-state-reducer}

**相关内容**：[State 归并与并行更新](#state-归并与并行更新)。

<details>
<summary>参考回答</summary>

多节点共同更新的字段需要明确归并规则。无 reducer 的字段在同一超步收到多次更新会冲突。列表结果可用拼接归并，再按任务 ID 排序。消息可用 `add_messages`，它会更新相同 ID 的消息。归并函数还需匹配业务去重要求。

</details>
