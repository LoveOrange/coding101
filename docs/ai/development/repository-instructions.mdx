# 仓库指令

仓库指令保存编码 Agent 使用的项目约定。常见文件有 `AGENTS.md` 和 `CLAUDE.md`。本文负责内容组织、加载范围与效果验证。任务进度的保存见 [Agent Harness](../agents/harness.mdx#长任务的处理)。

## 1. 面试核心 {#core}

- 仓库指令保存构建命令、结构、约定和验收要求。[卡](#rules-file-content)
- 指令文件的发现范围和优先级由具体工具定义。[卡](#instruction-loading)
- 规则文件负责指导，CI 与权限检查负责强制约束。
- 指令变更通过固定任务与环境进行对照评测。[卡](#verify-instruction-change)
- 多工具协作共享项目约定、接口和验收标准。[卡](#multi-tool-collaboration)

## 2. 指令内容 {#写什么}

```markdown
# 项目说明

TypeScript 订单服务，入口 src/server.ts。

## 命令
- 单测：pnpm test
- 类型检查：pnpm typecheck

## 结构
- src/api：参数校验与 service 调用。
- src/service：业务逻辑。
- src/repo：数据库访问。

## 约定
- 金额用整数分，避免浮点舍入误差。
- 接口变化需要验证兼容性。
- 迁移文件通过新增版本演进。
```

指令写具体命令和项目特有约束。复杂背景放在独立文档中，并说明读取条件。目录、命令变化时，同步更新规则。

临时错误、当前待办和修改进度另存任务状态。稳定约定与临时状态分开，能减少过时信息。

## 3. 组织与维护 {#组织与维护}

规则随仓库版本评审。新增规则应对应反复出现的真实问题。过时或重复规则及时删除，防止占用无效上下文。

跨工具可以维护共同的项目规则。入口文件按各工具支持的方式引用或生成。需要验证实际加载结果，避免只有文件存在。

特定任务流程使用 [Agent Skills](../tools/agent-skills.mdx)。格式和权限等强制要求交给检查程序。Hook 的阻断条件见 [Agent Harness](../agents/harness.mdx#hook-的事件与阻断能力)。

### 3.1 Codex 指令发现与范围 {#codex-指令发现与范围}

以下规则核对于 2026-10-13 的 Codex 文档。Codex 先发现全局指令，再沿项目根目录走到当前目录。每层优先检查 `AGENTS.override.md`，再检查 `AGENTS.md`。随后才检查配置的备用文件名，每层最多采用一份。

文件按全局到目录的顺序组合。更深目录中的项目约定覆盖上层冲突项。项目文档合计受 `project_doc_max_bytes` 限制。默认上限为 32 KiB。

启动目录、文件名和大小限制都会影响加载。修改指令后，需验证新会话的实际发现结果。压缩后的保留与重载由宿主实现，关键规则应再核对。

## 4. 常见问题 {#常见问题}

### 4.1 仓库指令与系统提示 {#仓库指令与系统提示}

仓库指令来自项目维护者，系统提示来自应用开发者。宿主决定指令如何进入上下文及其优先级。文件内容仍需服从运行时权限。

- 字节跳动：https://www.nowcoder.com/feed/main/detail/7e8a821479a649fd914e449d312eeb95 （“你是怎么管理 AI 编程时的上下文的？”）

**出现公司**：安软、字节跳动

**考察重点**

- 稳定信息与临时状态的区分。
- 指令文件独立于对话历史加载的特点。

**相关内容**：[指令内容](#写什么)、[上下文压缩](../prompting/context-compaction.mdx)。

<details>
<summary>参考回答</summary>

规则文件保存稳定的命令、项目结构和行为约定。验证要求、数据处理约束和禁止事项也应明确。命令可执行，约定有具体适用范围。

当前进度、改动文件和错误属于临时状态。它们写入进度文件或压缩摘要。规则能否加载及压缩后保留，取决于具体宿主。恢复后应核对关键约束，避免假定文件存在就已生效。

</details>

### 5.2 更新 AGENTS.md 或 Skills 后，怎样验证效果确实提升？ {#verify-instruction-change}

<!-- 面试来源：
- 字节跳动：https://www.nowcoder.com/discuss/917561494512861184 （“自动更新 AGENTS.md 或 Skills 后，怎样验证效果确实提升？”“如何通过评价脚本或模型评审对比两个 Skill 的输出？”）
-->

**出现公司**：字节跳动

**考察重点**

- 用代表任务做修改前后的对照。
- 结果、成本与规则遵守情况的度量。

**相关内容**：[组织与维护](#组织与维护)、[编码 Agent 评测](./coding-agent-evaluation.mdx)。

<details>
<summary>参考回答</summary>

效果通过代表任务的前后对照判断。任务集覆盖目标问题和常规工作。固定模型、工具、代码版本与预算，分别运行新旧规则。

比较成功率、违规次数、Token 和人工修正量。难以自动判定的输出使用明确评分标准。人工抽查用于校准模型评审。规则改善目标问题且满足回归门槛后，再保留修改。

</details>

### 5.3 多人使用不同 AI 工具开发同一个功能时，怎样协作？ {#multi-tool-collaboration}

<!-- 面试来源：
- 快手：https://www.nowcoder.com/feed/main/detail/631e9b79e433415ca3dea24642f94b4c （“多个人用不同 AI 工具开发同一个功能时，你们怎样协作？”）
- 美团：https://www.nowcoder.com/feed/main/detail/50bcdc47e7754aa7be59b6318fea514b （“你本地搭建Agent工作流，还是团队有统一工作流平台？”）
-->

**出现公司**：快手、美团

**考察重点**

- 共享的规则、接口约定和验证标准。
- 版本管理与评审流程不因工具不同而改变。

**相关内容**：[组织与维护](#组织与维护)。

<details>
<summary>参考回答</summary>

协作依赖共同约定、接口和验收标准。不同工具可以保留各自入口，共享同一份规则内容。引用方式需确认被工具实际加载。

功能按模块明确负责人，并约定接口和数据结构。所有改动接受相同 CI 与代码评审。反复出现的问题进入共享规则或自动检查。

</details>
