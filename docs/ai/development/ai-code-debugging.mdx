# AI 代码调试

AI 代码调试用 Agent 辅助复现、定位和修复缺陷。本文负责假设验证、回归和失败会话恢复。完整开发流程见 [AI 辅助开发](./ai-assisted-development.mdx)。

## 1. 面试核心 {#core}

- 调试用复现、假设验证和回归连接现象与根因。[卡](#fix-failing-tests)
- 失败输入、实际输出和预期行为共同定义缺陷。
- 热更新通过解析校验后，再发布完整的新配置。[卡](#review-hot-reload)
- 会话恢复保留已验证结论、代码差异和复现命令。[卡](#recover-agent-session)

## 2. 调试步骤 {#调试步骤}

1. 运行失败测试，记录环境、输入和错误。
2. 沿调用链与状态变化缩小范围。
3. 提出可验证的原因，选择能区分假设的实验。
4. 根据实验结果修改导致缺陷的机制。
5. 运行缺陷用例与受影响的回归测试。
6. 对照 diff，说明原因、修复和验证范围。

例如分页结果错位时，检查 offset 的计算。使用第一页和第二页输入，验证边界差异。实验结果支持假设后，再调整计算规则。

### 2.1 回归测试的判别能力 {#回归测试的判别能力}

缺陷测试应在修复前失败，在修复后通过。已有正常用例还需继续通过。两组结果分别检查修复效果与已覆盖行为。

测试失败也会来自环境或测试自身。断言是否正确，应对照需求和行为契约判断。单次运行未复现并发问题时，继续固定触发顺序或隔离共享状态。

## 3. AI 参与方式 {#让-ai-参与的方式}

| 环节 | Agent 的工作 | 开发者的判断 |
| --- | --- | --- |
| 复现 | 执行命令、整理输出 | 环境是否匹配 |
| 定位 | 搜索引用、读取陌生代码 | 推断是否符合实际状态 |
| 假设 | 提出原因与实验 | 实验能否区分候选原因 |
| 修复 | 编写最小修改和用例 | 修改是否解决根因 |
| 回归 | 执行检查并整理差异 | 验证是否覆盖影响范围 |

要求 Agent 写出假设与证据，可在修改前发现误判。解释与代码一致后，再实施对应改动。

## 4. 常见陷阱 {#常见陷阱}

- 连续整体重写会引入新变量，应限制单次改动范围。
- 放宽断言会掩盖缺陷，修改测试需有需求依据。
- 针对失败输入添加特判后，还需检查同类路径。
- 错误结论会干扰后续尝试，应整理已确认事实。
- 未运行验证时，应明确标注修复尚未确认。

会话恢复前先检查工作区差异。保留用户改动及已验证的修复。需要撤销失败尝试时，仅撤销对应修改。恢复说明包含目标、约束、文件、证据和复现命令。

<details>
<summary>参考回答</summary>

热更新应在解析与校验通过后发布新配置。先明确失败策略、更新时机和并发读取要求。沿文件变化、解析、校验和发布路径审查实现。

发现共享配置被提前覆盖时，用错误文件复现。观察解析失败后旧配置是否仍可读取。修复为完整校验后原子替换，再验证正常与失败路径。连续修改和并发读取按业务要求补充验证。

<details>
<summary>参考回答</summary>

恢复任务需要保留事实、有效改动和可复现入口。先停止无效修改，检查工作区差异。只撤销已确认失败的尝试，保留用户和有效修改。

整理目标、约束、已排除假设与复现命令。压缩或重开会话后，重新核对当前代码。按小步骤继续验证，避免旧错误结论影响后续。

</details>
