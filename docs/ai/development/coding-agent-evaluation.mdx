# 编码 Agent 评测

编码 Agent 评测比较开发任务的质量与成本。团队效能度量则关注实际交付和缺陷变化。本文负责任务集、重复试验、检索对照和效能口径。通用轨迹评测见 [Agent 评估](../evaluation/agent-evaluation.mdx)。

## 1. 面试核心 {#core}

- 编码任务用修复测试与回归测试共同验收。[卡](#coding-benchmark)
- 对照实验固定任务和环境，只改变待比较变量。
- `pass@k` 衡量至少一次成功，`pass^k` 衡量全部成功。[卡](#pass-at-k-vs-pass-power-k)
- 代码检索同时评估召回与端到端任务结果。[卡](#codebase-index-eval)
- AI 代码生成率衡量参与程度，交付指标衡量效能。[卡](#ai-code-ratio)

## 2. 构建任务集 {#构建任务集}

SWE-bench 从真实仓库的问题与修复中构建任务。输入是问题描述和修复前代码。评测用测试检查候选补丁。

内部任务集需要完成以下工作：

1. 选择有明确行为要求的缺陷与小需求。
2. 固定仓库提交、依赖和测试环境。
3. 配置修复测试与原有回归测试。
4. 人工确认描述充分，测试允许合理替代实现。
5. 划分开发集和留出集，隔离参考补丁与验收答案。

现有仓库测试可以供 Agent 调试。隐藏验收测试由评测端运行，并防止被修改。内部或新任务能降低污染风险，但仍需检查答案泄漏。

### 2.1 运行隔离与失败归因 {#运行隔离与失败归因}

每次试验从相同代码和干净环境开始。缓存、数据库和临时文件按实验设计初始化。Agent 修改过的测试文件应单独审查。

运行记录区分任务失败、环境失败和评测器失败。例如依赖下载超时，不能直接算作补丁逻辑错误。报告需保留这些失败的数量与处理方式。

## 3. 指标与对照 {#指标与对照}

| 类别 | 指标 |
| --- | --- |
| 结果 | 任务通过率、回归通过率 |
| 稳定性 | 重复运行结果、`pass@k`、`pass^k` |
| 检索 | 相关文件或符号的 Recall@K |
| 过程 | 步数、工具错误、测试改动 |
| 成本 | Token、费用、耗时、索引维护成本 |
| 人工 | 接管比例与评审修改量 |

比较方案时固定模型快照、工具和运行预算。只改变索引、提示或待比较的模型。多次运行用于观察波动，报告分布与不确定范围。

检索层命中还需结合任务结果。读到目标文件后，Agent 仍可能理解或修改错误。成本比较采用预先确定的质量门槛。

### 3.1 多次尝试与重复成功率 {#多次尝试与重复成功率}

`pass@k` 表示 k 次尝试中至少一次成功。`pass^k` 表示 k 次尝试全部成功。前者适合多候选后验收，后者强调重复运行的可靠性。

假设各次独立且成功概率同为 p。至少一次成功的概率是 `1-(1-p)^k`。全部成功的概率是 `p^k`。任务难度不同或尝试相关时，需按任务统计。

增加尝试次数会消耗更多预算。报告须同时给出 k、总成本和候选筛选方法。

## 4. 团队效能度量 {#团队效能度量}

| 维度 | 指标 |
| --- | --- |
| 交付 | 周期、开发耗时、完成任务量 |
| 质量 | 缺陷、回滚、返工、评审修改量 |
| AI 参与 | 生成代码留存、人工接管比例 |
| 成本 | 模型费用、工具费用和人工时间 |

代码生成率先确定分母和归属规则。例如以最终提交的新增行作分母。删除内容排除，人机共同修改部分另列口径。

效能对照还需控制任务难度、人员与时间窗口。单纯前后比较会混入团队和项目变化。结果应同时展示速度、质量和成本。

固定模型、工具和预算，多次运行观察波动。比较成功率、读取量、Token、耗时和人工接管。索引构建、更新成本与版本新鲜度也需计入。失败轨迹用于区分未召回和读到后处理错误。

### 5.4 pass@k 与 pass^k 有什么区别，为什么要同时报告尝试预算？ {#pass-at-k-vs-pass-power-k}

**相关内容**：[多次尝试与重复成功率](#多次尝试与重复成功率)。

<details>
<summary>参考回答</summary>

`pass@k` 看至少一次成功，`pass^k` 看全部成功。独立同分布时，两者分别为 `1-(1-p)^k` 和 `p^k`。多次尝试提高找到可用补丁的机会，也增加成本。比较必须固定 k 或总预算，并说明如何选出最终补丁。

</details>
