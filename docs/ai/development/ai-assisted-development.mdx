# AI 辅助开发

AI 辅助开发指使用编码 Agent 或编码助手阅读代码、生成修改、运行命令并根据反馈继续迭代。面试中常见两种形式：询问实际使用方法，或者允许使用 AI 完成现场编码任务。两种形式考察的都是开发者能否明确需求、提供正确的上下文、验证结果并对交付负责。本文讲一次开发任务的完整流程、代码库上下文、提示与反馈，以及质量保障。

## 1. 面试核心 {#core}

- 流程是：明确需求和验收条件 → 让 Agent 读懂相关代码 → 确认计划 → 小步实现 → 运行测试和检查 → 审查 diff → 交付。模型“说完成了”不等于验收通过。[卡](#ai-dev-workflow)
- 提示的有效内容是目标、约束、相关代码位置和实际反馈（报错、失败输入、期望与实际的差异）；反复要求“再检查一下”几乎没有信息量。[卡](#ai-coding-prompt)
- 代码库上下文按需获取：编码 Agent 通常用搜索和读文件工具沿调用链定位，而不是把整个仓库放进上下文。[卡](#grep-vs-rag)
- 质量靠外部证据保证：测试、类型检查、静态分析和人工评审。生成的代码同样要求开发者能解释，能跑但设计差的代码要在评审中拦下。[卡](#ai-code-quality)
- 大段生成的方案和代码要按风险分配审查：高影响的接口、数据和权限变更由人重点审查，机械检查交给工具。[卡](#review-generated-code)

## 2. 一次开发任务的流程 {#workflow}

1. **需求与验收**：把需求拆成输入、输出、约束和验收用例。会改变实现的不明确之处先澄清，例如“配置解析失败时保留旧配置还是报错”。
2. **理解代码**：让 Agent 找到入口、相关模块和现有测试，复述它对调用链的理解；理解有误时先纠正，再写代码。
3. **计划**：对多文件或有风险的修改，先让 Agent 列出修改点和验证方式，确认后再实施。简单修改可以直接做。
4. **实现**：一次完成一个可验证的单元，避免一次生成跨越很多模块的大改动。
5. **验证**：运行相关测试、类型检查、构建；没有测试的行为补充测试，至少覆盖正常、边界和失败路径。
6. **审查**：阅读 diff，检查是否有无关修改、删除的断言、吞掉的异常、硬编码的值。
7. **交付**：说明改了什么、验证了什么、还有哪些没有验证。

现场 AI Coding 面试中，面试官通常会在第一版完成后指出问题或追加需求，观察候选人如何定位、如何给 AI 反馈以及能否解释修改。时间分配上要给验证和修正留出空间。

## 3. 代码库上下文 {#codebase}

编码 Agent 获取代码上下文的常见方式：

| 方式 | 做法 | 特点 |
| --- | --- | --- |
| 搜索工具 | grep、按文件名查找，然后读文件 | 精确匹配符号名，结果实时，不需要索引维护 |
| 语义检索 | 对代码块建向量索引 | 能按功能描述查找，但索引可能过期，代码切块会破坏结构 |
| 符号与调用关系 | LSP、代码图谱查询定义和引用 | 准确的跳转，需要语言工具支持 |
| 规则文件 | 仓库指令说明目录结构、命令和约定 | 每次会话自动加载，见[仓库指令](./repository-instructions.mdx) |

代码中的标识符精确、可搜索，Agent 可以像开发者一样边搜索边读，逐步缩小范围，读取的内容也总是最新的。语义检索在大型、命名不规范或需要按功能描述查找的仓库中有补充价值。

开发者能帮助 Agent 的是：指出相关目录和文件、说明业务术语对应的代码名称、提供复现命令和错误输出。

## 4. 提示与反馈 {#prompting}

一个有效的任务描述包含：

```markdown
目标：在 src/cache/ 中实现进程内 LRU 缓存，供 UserService 查询用户资料时使用。
约束：
- 容量可配置，默认 1000；条目支持 TTL。
- 多线程读写安全；不引入新的第三方依赖。
- 不修改 UserService 的公开方法签名。
验收：
- 新增单测覆盖：命中、过期、淘汰最久未使用、并发读写。
- 现有测试全部通过。
先阅读 UserService 和现有的 src/cache/README.md，给出实现计划后再写代码。
```

反馈要具体：

- 测试失败时，给出失败的用例、实际输出和期望输出，或者直接让 Agent 运行测试读取结果。
- 设计不符合要求时，指出具体位置和原因，例如“`get` 中加了全局锁，读多写少场景下会成为瓶颈，改为分段锁或读写锁”。
- 同一个错误反复修不好时，停下来让 Agent 解释它的假设，或者回退到上一个可用版本缩小范围，不要连续要求重写。

## 5. 质量保障 {#quality}

AI 生成代码的常见问题：

- 按字面需求实现，忽略隐含约束（并发、错误处理、兼容性）。
- 为了让测试通过修改测试或增加特殊分支。
- 重复实现已有的工具函数，不遵循项目约定。
- 吞掉异常、硬编码配置、留下无用代码。
- 能运行，但职责混乱、难以维护。

对应的保障：

- **事先**：在提示和仓库指令中写明约定和禁止事项；先确认计划。
- **测试**：测试从需求和行为契约出发，而不是从生成的实现反推；检查 Agent 是否修改了已有断言。
- **自动检查**：类型检查、lint、静态分析、安全扫描在提交前运行。
- **评审**：人工审查 diff；也可以让另一个模型实例评审，但它的结论同样需要代码和运行结果支持。
- **能解释**：开发者应能解释每一处修改为什么这样做，无法解释的代码不交付。

### 6.3 编码 Agent 为什么常用 grep 检索代码而不是 RAG？两者有什么区别？ {#grep-vs-rag}

- 蚂蚁：https://www.nowcoder.com/discuss/888874988554448896 （“Claude Code是给模型用grep检索，没有用RAG检索，这俩有什么区别？为什么没用rag？”）
- 携程：https://www.nowcoder.com/discuss/864142639816323072 （仓库代码检索）
- 快手：https://www.yukibloom.app/post/kuai-shou-ai-quan-zhan-er-mian （“你是如何评测自己写的 Codebase Index 方案的？”）
-->

**出现公司**：蚂蚁、携程、快手

**考察重点**

- 精确搜索与语义检索在代码场景的适配性。
- 索引新鲜度、结构完整性和迭代式探索。

**相关内容**：[代码库上下文](#codebase)。

<details>
<summary>参考回答</summary>

代码中的函数名、类名、错误信息都是精确标识符，grep 能直接命中；搜索结果总是基于当前文件，不存在索引过期的问题，Agent 修改代码后立即可以搜到。Agent 可以像开发者一样多轮搜索、读文件、再搜索，逐步缩小范围，只把需要的内容读入上下文。

RAG 需要预先切块和建索引：代码切块可能破坏函数和类的结构，代码频繁变化时索引会过期，语义相似也不等于调用关系相关。它的优势是能用自然语言描述功能来查找，适合命名不规范或非常大的仓库。实际工具中两者可以并存，再配合 LSP 等符号跳转。

</details>

<details>
<summary>参考回答</summary>

技术方案先对照需求看三件事：是否满足验收条件，关键取舍（数据模型、接口、一致性、失败处理）是否合理，有没有超出需求的复杂设计。只抓会影响结果和后续维护的点，细节可以在实现中调整。

</details>
