# AI 辅助开发

**AI 辅助开发**是借助编码 Agent 或编码助手阅读代码、生成修改并验证结果的开发方式。助手可以运行命令，再根据输出继续修改；需求是什么、选哪个方案、交付能不能验收，仍由开发者负责。

AI 让写代码变快了，但“代码写出来了”和“任务完成了”之间的距离没有变。用好它要抓住三点：给助手足够准确的代码上下文，把需求写成可验证的行为，再用测试、检查和审查证明修改是对的。无论是讲自己的使用方法，还是在允许 AI 的面试中现场编码，你都要能解释每处修改，并拿出检查结果。

## 1. 面试核心 {#core}

- 整个流程**以验收条件为依据**：先写清完成标准，再做代码阅读、小步实现、检查和差异审查。[卡](#ai-dev-workflow)
- 有效提示说明**目标、约束、代码位置和验收条件**；失败反馈要给出**实际输出与预期行为的差异**。[卡](#ai-coding-prompt)
- **关键词搜索能直接定位函数名、错误文本这类标识符**，语义检索补充按功能描述查找的能力。[卡](#grep-vs-rag)
- 代码能运行只证明部分路径可用，质量要靠**行为测试、类型检查、静态分析和人工评审共同验证**。[卡](#ai-code-quality)
- 人工评审**优先检查接口、数据、权限和并发变更**，格式与类型问题交给自动检查。[卡](#review-generated-code)

## 2. 一次开发任务的流程 {#一次开发任务的流程}

开发任务要先定义完成标准，后面每一步才有判断依据。一次任务可以分七个环节推进：

1. **需求与验收**：写清输入、输出、约束和验收用例。会影响实现的歧义先澄清，比如配置解析失败时是保留旧配置还是报错。
2. **理解代码**：让 Agent 阅读入口、相关模块和现有测试，再说明调用关系。发现它理解有误时，先纠正，再进入实现。
3. **计划**：多文件或风险较高的修改，需要列出改动点和验证方法。简单修改可以直接实施。
4. **实现**：每次完成一个可验证的小单元，及时查看 diff，也就是修改前后的代码差异。这样更容易把失败结果对应到具体改动。
5. **验证**：运行相关测试和类型检查，按影响范围补充构建与回归。新增行为缺少测试时，补上正常、边界和失败用例。
6. **审查**：检查接口兼容和错误处理，再查看是否混入无关修改。被删除的断言、被吞掉的异常和硬编码的值都要有合理解释。
7. **交付**：说明修改内容、已完成的验证和未验证部分。开发者需要能解释每处修改的原因。

验收方式要和改动匹配，不是每次都要跑全套。纯文案或低影响修改，用格式检查、差异检查就够了。

如果是现场 AI Coding 面试，第一版完成后可能还有追加需求或缺陷反馈，这时要定位问题、给助手具体反馈，并解释后续修改，所以要给验证和修正留出时间。

## 3. 代码库上下文 {#代码库上下文}

编码助手要先找到与任务有关的实现，才能沿用项目已有的设计，而不是另起一套。获取上下文有四种方式，可以组合使用，逐步缩小阅读范围：

| 方式 | 适用问题 | 使用边界 |
| --- | --- | --- |
| 关键词搜索 | 函数名、错误文本、配置项 | 依赖命名与搜索范围 |
| 语义检索 | 按功能描述寻找实现 | 依赖切块、索引更新和权限过滤 |
| 符号与调用关系 | 定义、引用与调用链 | 依赖语言服务和项目解析 |
| 仓库规则 | 命令、结构与约定 | 加载规则取决于具体工具 |

代码里的函数名、类名和错误文本都适合精确匹配。Agent 可以先用 grep 或文件名搜索找到入口，再读完整函数，沿引用继续查找。直接搜索读取当前磁盘内容，所以刚修改的代码也能立即搜到，省去了索引维护。

**语义检索**先把代码切成片段，再建立用于相似度查询的向量索引，按“意思相近”而不是“字面相同”来查找。它适合大型仓库、命名不规范的代码，以及只有功能描述的查找任务。不过，切块会割断函数或类的上下文，代码变更后也需要更新索引。所以，检索命中后还要读相关文件，确认调用关系和当前版本。

语言服务器协议（LSP）让编辑器和 Agent 能查询定义和引用，代码图谱也能帮助追踪调用关系。这类工具依赖语言服务与项目解析，可以和关键词搜索、语义检索一起使用。

开发者也可以直接提供定位信息，减少无关搜索：

- 指出相关目录、文件和调用入口。
- 说明业务术语在代码中对应什么名称。
- 提供复现命令和错误输出。

检索方案是否提高了任务成功率，见[编码 Agent 评测](./coding-agent-evaluation.mdx)。

仓库中的长期约定怎样组织，见[仓库指令](./repository-instructions.mdx)。

## 4. 提示与反馈 {#提示与反馈}

好的任务描述把目标写成可验证的行为。下面以实现一个进程内缓存为例。先说明两个术语：**LRU**（Least Recently Used）是按最近访问顺序、淘汰最久未使用条目的策略；**TTL**（Time To Live）规定条目的有效时间。前者决定容量满了淘汰谁，后者决定条目多久后失效，两者控制的行为不同，需求里都要写清。下面这段提示把代码位置、调用方、约束和验收条件放在一起：

```markdown
目标：在 src/cache/ 中实现进程内 LRU 缓存。
调用方：UserService。
约束：
- 容量可配置，默认 1000；支持 TTL。
- 多线程读写安全；沿用已有依赖。
- 保持 UserService 的公开接口兼容。
验收：
- 测试覆盖命中、过期、淘汰顺序和并发行为。
- 现有相关测试全部通过。
先阅读相关实现，再给出修改点和验证方式。
```

如果缓存用于查询用户资料，可以进一步说明 UserService 中的调用位置。仓库已有 `src/cache/README.md` 时，也应让 Agent 先阅读其中的约定，再确定修改方案。

第一版完成后，反馈要给出足以指导修改的具体差异，而不是一句“有问题，再改改”：

- 测试失败时，给出用例、期望值和实际值，也可以让 Agent 直接运行测试读取结果。
- 设计存在问题时，指出代码路径和受影响的约束。比如，全局锁让所有访问串行执行，需要结合并发要求检查锁的范围。
- 同类错误反复出现时，让 Agent 说明当前假设，保留已确认事实，再缩小修改范围。

锁的问题值得多说一句。直觉上 `get` 是读操作，可以用读锁并发执行；但 LRU 的 `get` 命中时要更新访问顺序，实际上会修改共享状态。Java 的 `LinkedHashMap` 在按访问顺序排列时也是这样，`get` 会把命中的条目移到链表末尾。所以评估读写锁或分段锁时，要同时检查访问顺序和淘汰是否仍然正确。

这类反馈有用，是因为模型能据此定位到具体差异。失败会话的恢复方式见 [AI 代码调试](./ai-code-debugging.mdx#常见陷阱)。

## 5. 质量保障 {#质量保障}

生成代码要同时满足业务行为和工程约束。程序能运行只是起点，边界输入、失败路径和设计是否合理还要继续检查。

评审生成代码时，可以从下面几种成因入手找缺陷：

- 需求只描述主流程时，生成实现容易遗漏并发、错误处理和兼容性要求。
- 读取的代码范围不足时，助手会重复实现已有工具函数，或采用与项目不同的约定。
- 围绕失败用例反复修改时，助手会放宽断言、跳过用例，或加入只匹配该输入的特殊分支。
- 为了尽快完成任务，生成代码还会出现吞掉异常、硬编码配置或残留无用代码的问题。
- 多轮修改各自解决局部问题后，模块职责会变得混乱，增加维护难度。

前两种可以在编码前预防：在提示和仓库指令中写明项目约定与禁止事项。复杂修改先检查计划，完成后再按下表验证。

| 检查对象 | 验证方式 |
| --- | --- |
| 业务行为 | 从需求推导正常、边界和失败用例 |
| 兼容性 | 核对调用方、接口和数据格式 |
| 错误处理 | 验证异常传播与资源清理 |
| 并发 | 检查共享状态与执行顺序 |
| 改动范围 | 审查 diff 和已有断言变化 |
| 机械规则 | 类型检查、lint、构建和静态分析 |

表里的业务行为测试，要从**行为契约**推导，也就是程序约定要满足的输入输出和边界要求。AI 可以帮忙写测试，但测试场景要从需求独立推导，不能从生成的实现反推：同一个错误假设会同时出现在实现和测试里，两者一致地错，测试照样通过。同样的原因，评审还要检查已有断言是否被放宽、用例是否被跳过。

类型检查、lint 和静态分析负责发现机械错误，安全扫描可补充检查已知风险。另一个模型实例也可以梳理调用关系、提出疑点，但结论仍需代码、需求或运行结果支持。

长方案先检查验收条件，再看数据模型、接口、一致性和失败处理的取舍。超出当前需求的设计需要说明必要性。代码则按功能和依赖拆开审查，优先看接口、数据、权限与并发变更。变更大到无法解释时，拆成更小的单元，确认每处改动的用途后再交付。

## 6. 面试题 {#面试题}

### 6.1 AI 辅助开发的完整工作流是什么？讲一下和 AI 交互完成一个功能的过程。 {#ai-dev-workflow}

**考察重点**

- 解释需求、代码阅读、计划、实现、验证和审查怎样衔接。
- 说明开发者负责哪些判断，以及用什么证据验收交付。

**相关内容**：[一次开发任务的流程](#一次开发任务的流程)。

<details>
<summary>参考回答</summary>

**完整流程从需求与验收条件开始，经过代码阅读和小步实现，再用检查与评审完成交付。**

开发者先写清输入输出、约束和验收用例，澄清影响实现的歧义。Agent 阅读相关代码后，说明调用关系与修改点，理解有误时先纠正。多文件或高风险任务再列出计划，拆成可验证的小单元。

每个单元完成后运行相关检查，缺少的行为测试按需求补充。失败输出交回 Agent，供它定位和修正。随后审查 diff，检查无关修改、断言变化和异常处理。交付时说明已验证范围与剩余问题，并解释每处修改的原因。AI 加快阅读与执行，开发者负责方案取舍和最终验收。

</details>

### 6.2 假如要基于内存实现一个缓存，写一下 AI Coding 流程中的提示词。 {#ai-coding-prompt}

**考察重点**

- 给出包含目标、约束、相关代码和验收条件的任务描述。
- 根据运行结果说明实际行为与预期行为的差异。

**相关内容**：[提示与反馈](#提示与反馈)。

<details>
<summary>参考回答</summary>

**提示应写清缓存的用途、行为约束和验收标准，让第一版实现有明确目标。**

可以这样描述这项缓存任务：

- 在 `src/cache/` 实现进程内 LRU 缓存，供 UserService 查询用户资料。
- 容量可配置，默认 1000，并支持 TTL 和多线程安全访问。
- 沿用已有依赖，保持 UserService 的公开接口兼容。
- 测试覆盖命中、过期、淘汰顺序和并发行为，现有相关测试全部通过。
- 先阅读调用方和已有缓存约定，再给出修改点与验证方式。

失败时提供具体输入、实际结果和期望结果。比如，全局锁限制了并发，需要检查锁覆盖了哪些操作。LRU 命中会更新访问顺序，所以调整锁策略后也要验证顺序维护。反复失败时先核对假设，再缩小修改范围。

</details>

### 6.3 编码 Agent 为什么常用 grep 检索代码而不是 RAG？两者有什么区别？ {#grep-vs-rag}

**考察重点**

- 解释精确搜索和语义检索分别适合什么代码查找任务。
- 说明索引新鲜度、代码结构和多轮搜索怎样影响查找结果。

**相关内容**：[代码库上下文](#代码库上下文)。

<details>
<summary>参考回答</summary>

**grep 能直接匹配函数名、类名和错误文本，适合代码中的精确查找，也省去了索引维护。**

搜索读取当前磁盘文件，所以 Agent 改完代码就能搜到新内容。它可以先搜索、再读函数、继续沿调用关系搜索，只把当前需要的代码放进上下文。

基于语义检索的 RAG 可以按功能描述查找，适合大型仓库或命名不规范的代码。代价是切块会割断函数与类的结构，代码变化后也要同步索引。语义相似的代码仍需通过调用关系确认是否相关。因此，两种搜索可以结合，再配合 LSP 查询定义和引用。具体产品采用何种索引，应以公开实现为准。

</details>

### 6.4 怎样保证 AI 生成的代码质量？为什么 AI 生成的代码能跑但逻辑很差？ {#ai-code-quality}

**考察重点**

- 解释生成代码为什么会遗漏约束、重复实现或降低可维护性。
- 说明任务约束、行为测试、自动检查和评审怎样共同保证质量。

**相关内容**：[质量保障](#质量保障)、[AI 代码调试](./ai-code-debugging.mdx)。

<details>
<summary>参考回答</summary>

**生成代码的质量要由行为测试、自动检查和人工评审共同验证，能运行只证明部分路径可用。**

- **测试覆盖真实需求。** 从输入输出和边界推导用例，检查并发、错误处理及兼容性，并审查断言是否被放宽。
- **自动检查发现机械错误。** 运行类型检查、lint、静态分析和适用的安全扫描。
- **人工评审判断设计与副作用。** 核对职责划分、已有能力复用、权限和数据变更，确认每处修改都能解释。

另一个模型可以帮助发现疑点，结论仍需代码或运行结果支持。

</details>

### 6.5 AI 一次生成大量代码或很长的技术方案时，人应该如何评审？ {#review-generated-code}

**考察重点**

- 根据变更的影响范围安排审查顺序，并拆分过大的改动。
- 区分自动检查、AI 辅助审查和人工判断各自能确认的事项。

**相关内容**：[质量保障](#质量保障)。

<details>
<summary>参考回答</summary>

**评审应按需求和风险安排重点，并把过大的方案或代码拆成可解释的单元。**

方案主要检查三个方面：

- 是否满足验收条件。
- 数据模型、接口、一致性和失败处理的取舍是否合理。
- 超出需求的复杂设计是否有必要。

代码按功能与依赖拆分，优先检查接口兼容、数据修改、权限和并发。格式与类型问题交给自动检查，AI 可以帮助梳理调用关系和提出疑点。每个结论都要有代码或运行证据，多个模型意见一致也需要验证。变更超出可审查范围时继续拆小，最终由人说明验证范围并对交付负责。

</details>
