# Agent Skills

**Agent Skill** 是把任务说明、脚本和参考资料打包在一起的一个目录。它保存的是「某类任务该怎么做」，Agent 需要时才读取并照着做。比如团队可以用 Skill 规定怎样写发布说明、怎样处理 PDF 表单、怎样检查数据库迁移。

理解 Skill 要抓住两点。一是它和 Tool 的分工：Skill 是方法，Tool 是执行接口，Skill 本身不执行任何动作，也不带来权限。二是它怎样按需加载：没用到的技能只占一小段描述，这正是安装很多技能也不会撑爆上下文的原因。选错技能、执行失败和怎样评测，都可以从这两点推出来。

## 1. 面试核心 {#core}

- **Skill 保存任务步骤和配套资源，Tool 提供执行接口**；实际动作和权限检查由程序完成。[卡](#skill-vs-tool)
- 渐进式加载**先只提供名称和描述**，选中技能后再读正文，执行到具体步骤时才读取资源或运行脚本。[卡](#skill-loading)
- 模型**根据名称、描述和当前任务选择技能**；描述里写清输入类型和业务边界，才能区分相似技能。[卡](#skill-selection)
- **MCP 提供工具和数据的接入协议，CLI 提供命令行接口，Skill 说明怎样组合它们**完成任务。[卡](#mcp-cli-skill)
- 评测分两组：**触发评测检查是否选对技能，执行评测检查选中后能否完成任务**并满足约束。[卡](#skill-eval-cases)

## 2. 结构 {#结构}

一个 Skill 就是一个目录：`SKILL.md` 是入口，执行时需要的其他文件放在旁边。下面以生成发布说明为例：

```text
release-notes/
├── SKILL.md
├── scripts/
│   └── collect_prs.py
├── references/
│   └── style-guide.md
└── assets/
    └── template.md
```

`SKILL.md` 开头是一段元数据，用来介绍和识别技能，其中 `name` 和 `description` 必填：`name` 是名称，`description` 说明它做什么、什么时候该用。元数据下面的正文写具体步骤、判断规则和验收要求。

其余文件按用途分三类：

- `scripts/` 放可执行脚本，例如收集已合并的 PR（Pull Request，提交给代码仓库的合并请求）。
- `references/` 保存详细规范，例如发布说明的措辞要求，需要时再读。
- `assets/` 保存输出模板等文件，让不同任务的产物保持相同格式。

下面是 `SKILL.md` 的简化示例：

```markdown
---
name: release-notes
description: 根据合并的 PR 生成发布说明。用户要求版本更新说明时使用。
---

# 发布说明

1. 用 scripts/collect_prs.py 收集合并的 PR。
2. 按功能、修复和破坏性变更分类。
3. 按 assets/template.md 输出。
4. 核对 PR 引用与版本范围。
```

这个技能的流程是收集 PR、分类、套模板、核对。实际写的时候可以更具体，比如收集范围从上一个版本标签开始，免得混进更早版本的变更；分类规则区分 feature（功能）、fix（修复）和 chore（维护），并单独列出破坏性变更。

正文只保留完成任务必需的说明，长篇规范放进 `references/`。但正文里要写清「哪一步读哪份规范」，否则模型不知道什么时候该去找它。

脚本是由模型通过命令工具运行的，所以运行脚本需要相应的命令执行权限。需要审核或修改脚本时，模型也可以直接读它的源码。

## 3. 渐进式加载 {#渐进式加载}

**渐进式加载**是把技能内容分三层、按需读取的方式。之所以需要它，是因为技能一多，如果把每份说明都塞进提示词，上下文就会被和当前任务无关的流程占满。

| 层级 | 内容 | 加载时机 |
| --- | --- | --- |
| 元数据 | 名称、描述和定位信息 | 宿主发现可用技能时 |
| 正文 | `SKILL.md` 指令 | 用户指定或模型选择后 |
| 资源 | 脚本、参考资料与模板 | 执行具体步骤时 |

表里的宿主，是负责组织模型请求、读取文件和执行工具的应用。它先把所有可用技能的名称、描述和位置交给模型，相当于一份简短目录。用户点名某个技能，或者模型判断任务和它相关之后，才通过读文件工具加载正文；正文里引用的模板和参考资料，等执行到对应步骤再读。

这样，没用到的技能只占元数据那一点空间。简短的元数据可以按几十到一百 Token 估算，正文最好控制在几千 Token 以内。实际开销取决于描述长度和宿主附加的信息，技能装得越多，目录本身也会越长，所以描述里重复和无关的内容要删掉。

脚本从另一个方向省 Token：解析文件、批量重命名、校验格式这类确定性工作交给脚本，模型只读必要的结果，不用自己生成代码，也不用读一大堆中间数据。

### 3.1 沙箱中的 Skill {#沙箱中的-skill}

Agent 在容器或远程沙箱里执行任务时，读文件工具只能看到这个环境里的文件。所以要先把审核过的 Skill 目录挂载或复制进沙箱，说明和脚本才找得到。

之后的流程和本地一样：模型用工具读取沙箱里的 `SKILL.md`，用命令工具运行脚本，结果通过工具响应回到上下文。区别只在于读取和执行都受沙箱权限约束。

元数据仍然由宿主发现并加进上下文，放在哪类消息里由产品决定。例如 OpenAI Responses 的 shell 技能目录放在用户提示上下文中。技能目录的位置、发现规则和指令优先级，都按所用产品的方式配置。

## 4. Skill、Tool、MCP、CLI 的分工 {#skilltoolmcpcli-的分工}

设计一项能力时，先分清它是「执行接口」还是「使用方法」：Tool 提供可调用的函数，Skill 说明完成任务时怎样使用这些函数。几种常见形式的分工如下：

| 形式 | 职责 | 示例 |
| --- | --- | --- |
| Tool | 以契约暴露执行能力 | 查询订单 |
| MCP Server | 统一发现与调用外部能力 | 接入代码托管服务 |
| CLI | 提供命令行接口 | git、搜索、测试命令 |
| Skill | 组织流程、规则和资源 | 按模板生成发布说明 |
| 常驻指令 | 给出反复适用的规则 | 项目构建与代码约定 |

Tool 的参数用 Schema（规定参数类型和必填字段的结构规则）描述。MCP Server 通过协议提供一组工具和数据，多个应用都能复用。CLI 是命令行接口，模型通过命令工具调用 git、搜索或测试程序，输出还能用管道交给下一个程序过滤。

一项能力该做成哪种形式，主要看**它怎样执行、多常用到**：

- 单步完成、参数明确的能力适合 Tool，例如查询订单。
- 需要组合多个工具，并遵循业务规则的任务适合 Skill，例如按团队规范生成发布说明。
- 只在部分任务中使用的知识适合放入 Skill，按需加载。
- 每个请求都适用的规则适合放入系统提示或仓库指令，例如项目构建约定。

这几种形式经常组合使用：Skill 说明发布流程，MCP 工具读取代码托管服务的数据，CLI 处理本地文件。MCP 本身的协议分工见 [MCP](./mcp.mdx)。

## 5. 常见问题 {#常见问题}

### 5.1 Skill 失效与回退 {#skill-失效与回退}

先分清是选错了技能，还是选对了但执行失败。两类问题要改的地方不同：前者改元数据，后者改正文和依赖。混在一起改，很容易掩盖真正的原因。

选错技能时，拿失败的请求对照名称和描述，看适用范围有没有写清。两个相似技能被混用，就在描述里补上输入类型或适用的业务线；差别很小、流程又重复的，干脆合并成一个，在正文里按条件分支处理。

选对了却执行失败，就检查正文步骤、输入和依赖。比如页面结构或接口字段变了，原来的操作步骤就会失效。脚本应该在执行前检查这些前置条件，失败时返回能定位问题的错误；反复出错的确定性步骤，可以改成脚本并加上校验。

Agent 收到明确的错误后，可以在已有权限内改用通用工具，或者如实报告任务未完成。没有匹配的 Skill 时，按普通流程处理即可。更新技能前先记下失败样例，改完后用这些样例和正常请求一起回归。

### 5.2 Skill 脚本的执行权限 {#skill-脚本的执行权限}

Skill 里的脚本没有特殊权限，它仍然通过宿主的命令工具执行，能做什么由宿主和沙箱共同限制。技能正文只是一份任务说明，不会自动带来文件、网络或系统的访问权限。

反过来说，第三方 Skill 里可能夹带恶意指令或脚本，一旦被执行，用的就是宿主给命令工具的权限。所以安装前要审核来源和文件内容，确认脚本会访问哪些目录、连接哪些服务。

### 5.3 触发与执行评测 {#触发与执行评测}

评测要分开回答两个问题：有没有选中正确的技能，选中后有没有把任务做完。前者叫触发评测，后者叫执行评测。

触发评测要覆盖三类请求：

- 明确应该使用该技能的请求，用来发现漏选。
- 与适用任务相近、但不该使用该技能的请求，用来发现边界上的误选。
- 完全无关的请求，用来检查是否随意触发。

即使只有一个技能，也会有「该用时没用、不该用时用了」的问题。所以要记下漏选和误选的具体请求，据此调整名称或描述。

执行评测检查最终产物、工具调用记录和约束是否满足，比如发布说明里的 PR 引用是否有效、版本范围是否正确。这一组失败时，优先修正正文步骤和依赖。每次更新后，两组都要回归，确认修好了原问题，也没有破坏原有行为。

## 6. 面试题 {#面试题}

### 6.1 Skill 和 Tool 有什么区别？什么情况下做成 Skill，什么情况下做成 Tool？ {#skill-vs-tool}



**考察重点**

- 解释 Skill 如何保存流程知识，以及 Tool 如何执行动作。
- 能根据任务步骤和使用频率，区分 Skill、Tool 与常驻指令。

**相关内容**：[Skill、Tool、MCP、CLI 的分工](#skilltoolmcpcli-的分工)。

<details>
<summary>参考回答</summary>

**Skill 保存完成任务的方法和资源，Tool 则提供程序可以执行的接口。**

Tool 用参数 Schema 规定输入，调用后可以读取数据或改变外部状态。Skill 告诉模型该按什么步骤完成任务，并可引用工具和附带脚本。实际执行与权限检查，仍由宿主的工具完成。

查询订单这类单步、参数明确的能力适合 Tool。按团队规范生成发布说明，需要组合多个步骤和业务规则，适合写成 Skill。少数任务才需要的知识按需加载；每个请求都适用的规则放入系统提示或仓库指令。

</details>

### 6.2 Skill 的核心原理是什么？为什么能减少 Token 消耗？ {#skill-loading}



**考察重点**

- 解释元数据、正文和资源为什么分层加载，以及各层何时进入上下文。
- 说明脚本执行怎样节省 Token，以及沙箱中如何读取和执行技能。

**相关内容**：[结构](#结构)、[渐进式加载](#渐进式加载)、[沙箱中的 Skill](#沙箱中的-skill)。

<details>
<summary>参考回答</summary>

**Skill 通过按需加载说明和资源，并让脚本处理确定性工作，减少模型需要读取和生成的 Token。**

宿主先提供技能名称、描述和位置，模型选中后再读取 `SKILL.md`。正文引用的参考资料和模板，留到对应步骤加载。因此，未使用的技能只占元数据空间；简短元数据可按几十到一百 Token 估算，实际值取决于内容和宿主。

解析文件、批量重命名等工作交给脚本后，模型只需读取必要输出，省去阅读代码和中间数据的开销。在沙箱中运行时，需要先挂载或复制技能目录，再通过工具读取文件和执行脚本。结果通过工具响应回传，执行仍受沙箱权限限制。

</details>

### 6.3 Agent 怎么选择要调用的 Skill？两个相似的 Skill 被调用错误怎么办？ {#skill-selection}



**考察重点**

- 说明名称、描述和任务内容怎样共同影响技能选择。
- 能区分误选、步骤错误与依赖失效，并用回归任务验证修复。

**相关内容**：[渐进式加载](#渐进式加载)、[Skill 失效与回退](#skill-失效与回退)。

<details>
<summary>参考回答</summary>

**Agent 根据技能的名称、描述和当前任务选择 Skill；相似技能误选时，应补充区分条件或合并重复技能。**

排查时，先把失败请求与描述对照，判断是否缺少输入类型或适用业务线。两份技能的差异很小时，可以合并成一份，再在正文中按条件分支处理。

如果技能选对了，却在执行时失败，就检查正文步骤、前置条件和依赖。把容易出错的确定性步骤改为脚本，并增加执行前校验。页面结构或接口字段变化时，脚本应返回明确错误，Agent 再在已有权限内改用通用工具或报告未完成。

没有匹配技能时，按普通流程处理任务。修订后同时测试应触发、不应触发和选中后的执行任务，确认误选与执行失败都得到处理。

</details>

### 6.4 MCP、CLI 和 Skill 分别适合什么场景？ {#mcp-cli-skill}



**考察重点**

- 解释 MCP、CLI 和 Skill 分别怎样支持接入、执行与流程复用。
- 能结合模型轮数、进程启动和网络往返分析延迟。

**相关内容**：[Skill、Tool、MCP、CLI 的分工](#skilltoolmcpcli-的分工)、[MCP](./mcp.mdx)。

<details>
<summary>参考回答</summary>

**MCP 适合让多个应用复用工具与数据接入，CLI 适合调用已有命令，Skill 适合复用组合这些能力的流程。**

比如，通过 MCP 接入 GitHub、数据库或内部服务，可以统一工具发现和调用。远程部署时，还要配合鉴权。CLI 可以调用本地 git、搜索和测试程序，并用管道过滤输出。Skill 则规定调用顺序、业务判断和验收要求。

延迟取决于模型推理轮数、进程启动和网络往返。CLI 可以访问远程服务，MCP 也可以在本地运行，所以需要按实际调用链测量。本地处理可直接用 CLI 或脚本；固定步骤合并进一个脚本后，能减少逐步等待模型决策的时间。

</details>

### 6.5 怎样区分 Skill 选择错误与执行错误，并设计评测？ {#skill-eval-cases}

**考察重点**：能用评测请求区分技能误选与执行失败，并分别检查触发边界和产物是否合格。

**相关内容**：[触发与执行评测](#触发与执行评测)。

<details>
<summary>参考回答</summary>

**选择错误是任务没有选中正确技能，执行错误则是选中后未完成任务或违反了约束，两者需要分开评测。**

触发评测覆盖应使用、相近但不适用、完全无关三类请求，记录漏选与误选。只有一个技能时，也要检查它是否在错误时机触发。执行评测则检查产物、工具调用记录和约束，例如发布说明的 PR 引用和版本范围。

根据结果分别调整名称、描述或正文步骤与依赖。每次修改后回归两组任务，才能判断是否修好原问题并保持已有行为。

</details>
