# MCP

**MCP**（Model Context Protocol）是连接 AI 应用与外部工具、数据源的开放协议。工具提供方实现一个 MCP Server，所有兼容 MCP 的应用都能用同一套方式接入它，不用每个应用各写一遍集成代码。

要讲清 MCP，需要抓住三点：谁和谁在通信（Host、Client、Server 三个角色），一次工具调用的消息怎么走，以及它和 Function Calling、业务 API 各管哪一段。安全问题也由此而来：接入一个 Server，就是让它的内容进入模型上下文、让它执行操作。本文按 2025-11-25 版规范讲解。

## 1. 面试核心 {#core}

- Host 是 AI 应用，它**为每个 Server 创建一个独立的 Client**，Client 和 Server 一对一连接。[卡](#mcp-flow)
- MCP 2025-11-25 用 **JSON-RPC 2.0** 交换消息，标准传输有 **stdio 和 Streamable HTTP** 两种。
- Server 提供三类能力：**Tools 执行操作，Resources 供应用读取数据，Prompts 供用户选择提示模板**。
- **MCP 负责能力的发现和调用，Function Calling 负责让模型表达请求**，具体业务仍由业务 API 实现。[卡](#mcp-vs-api)
- Roots **只声明工作目录**，文件访问靠进程权限和沙箱限制；认证之后，工具和数据访问**仍要逐次授权**。[卡](#mcp-security)

## 2. 角色与能力 {#角色与能力}

MCP 把应用、连接和能力提供方拆成三个角色，这样一个应用可以同时接入多个服务，每个连接互不干扰：

- **Host** 是用户使用的 AI 应用，例如 IDE 或桌面客户端。它组织模型请求，管理连接和授权。
- **Client** 是 Host 内部的协议客户端。每个 Client 对应一个 Server，负责建立连接和收发消息。
- **Server** 是提供工具、数据或提示模板的程序。它可以是本地子进程，也可以是独立部署的服务。

```text
Host（AI 应用）
  ├─ Client A ↔ Server A（本地 stdio）
  └─ Client B ↔ Server B（Streamable HTTP）
```

能力也分两边：Server 向应用提供能力，Client 也可以声明自己支持哪些特性，供 Server 反过来使用。

| 提供方 | 能力 | 用途 |
| --- | --- | --- |
| Server | Tools | 模型可选择的操作 |
| Server | Resources | 应用读取的 URI 资源 |
| Server | Prompts | 用户选择的提示模板 |
| Client | Sampling | 接受 Server 的模型采样请求 |
| Client | Roots | 向 Server 声明工作目录 |
| Client | Elicitation | 接受 Server 的用户信息收集请求 |

Server 的三类能力，区别在于由谁决定使用：Tools 由模型选择，Resources 由应用读取，Prompts 由用户挑选。

- **Tools** 是带参数规则的可执行操作，例如创建 Issue。参数规则使用 JSON Schema，说明字段类型和必填项，模型据此生成调用请求。
- **Resources** 是用 URI 标识的数据，例如文件内容或数据库表结构。URI 是资源的地址或标识，应用通过它读取内容，再决定是否交给模型。
- **Prompts** 是预定义的提示模板，由用户选择使用。例如，Host 可以把模板显示为斜杠命令，用户选择后再填入参数。

「由谁决定」只说明谁主导使用，具体的界面和授权流程仍由 Host 设计。

Client 一侧的三个特性里，Sampling 允许 Server 请求 Host 代它调用模型，Elicitation 允许 Server 请求 Host 向用户收集补充信息。双方在初始化时各自声明支持哪些能力，之后只使用协商成功的部分。

Roots 用来告诉 Server 当前工作的目录范围。要注意它只是一个声明，本身不能强制隔离文件：Server 进程如果有权限读整个磁盘，Roots 并不会拦住它。真正能读写哪些文件，取决于 Server 进程的权限和沙箱。

## 3. 交互流程 {#交互流程}

MCP 的消息格式是 **JSON-RPC 2.0**，这是一种用 JSON 表达远程调用的协议：请求用方法名指定操作，用 ID 和响应对应。一次工具调用从建立连接到拿到结果，要经过七步：

1. Client 发送 `initialize`，携带协议版本与客户端能力。
2. Server 返回支持的版本和服务端能力。
3. Client 确认版本兼容后，发送 `notifications/initialized`，表示初始化完成。版本无法兼容时，应结束连接。
4. Client 调用 `tools/list`，获取工具名称、描述和 `inputSchema`，后者定义输入参数的结构。
5. Host 把选定工具转换成模型 API 的工具定义，加入模型请求。
6. 模型提出工具调用后，Host 找到对应 Client，由它发送 `tools/call`，携带工具名和参数。
7. Server 执行并返回结果，Host 再转换成模型接口要求的工具结果。返回内容可以是文本、图片或资源引用，模型据此继续处理任务。

前四步是初始化和发现，后三步是真正的调用。注意第 5、7 步的转换由 Host 完成：模型并不知道 MCP 的存在，它看到的只是普通的工具定义和工具结果。

`tools/list` 支持分页，Client 要按游标（标记下一页位置的值）继续读取。工具列表也可能在连接期间变化：Server 声明了 `listChanged` 能力后，可以发送 `notifications/tools/list_changed`，Client 收到后重新拉取列表，才能发现新增、修改或移除的工具。

下面是查询订单 `SO100` 的 `tools/call` 请求：

```json
{"jsonrpc":"2.0","id":7,"method":"tools/call",
 "params":{"name":"get_order","arguments":{"order_id":"SO100"}}}
```

Server 的响应会带上同样的 `id`（这里是 `7`），表示它回应的是这次请求。这个 ID 只在 Client 和 Server 之间使用，模型接口还有自己的调用 ID，两者不是一回事。所以 Host 要记住两者的对应关系，才能把结果交回正确的那次模型调用。

### 3.1 传输方式 {#传输方式}

传输方式决定消息怎样到达另一端。2025-11-25 版规范提供两种：stdio 适合本地进程通信，Streamable HTTP 适合通过 HTTP 连接的服务。

**stdio** 用 Server 子进程的标准输入和标准输出交换消息。Host 启动子进程后，双方在本机直接通信，不经过网络。这里有个容易踩的坑：`stdout` 只能写协议消息，日志要写到 `stderr`，否则 Client 会把日志当成协议内容去解析。子进程能访问哪些文件和服务，仍由启动配置和沙箱决定。

**Streamable HTTP** 只用一个 MCP 端点，也就是 Client 访问的那个服务地址。Client 用 POST 发送消息，响应可以是普通 JSON，也可以是 SSE（服务端持续向客户端推送事件的数据流）。Client 还可以用 GET 建立一条接收服务端消息的流，服务端不提供这条流时返回 405。它适合远程或多用户的服务，也可以用于本机的 HTTP 服务。

旧版（2024-11-05）的 HTTP+SSE 传输用的是两个端点。新版传输里也会出现 SSE，所以看到 SSE 时，要再确认用的是哪一种方案。

### 3.2 错误类型与会话恢复 {#错误类型与会话恢复}

调用失败时，先判断失败发生在哪一层：协议、工具执行还是传输。层次不同，处理方式也不同，分别是修正请求、调整业务参数和恢复连接。

- **协议错误**：例如工具名未知或方法不可用，通过 JSON-RPC `error` 返回，表示请求在协议处理时出了问题。
- **工具执行错误**：例如日期格式错误、业务条件不满足或下游 API 失败，在结果中用 `isError: true` 表达。它仍是 `tools/call` 的结果，Host 可以把原因交给模型修正。
- **传输中断**：连接断开只说明消息没传到，不说明工具执行到了哪一步。尤其是写入操作，可能已经完成，只是结果没送回来，需要另外确认。

使用 HTTP 会话时，Server 可以在初始化响应里返回 `MCP-Session-Id`。之后 Client 的每个请求都带上这个 ID，以及协商得到的 `MCP-Protocol-Version`。带着会话 ID 的请求收到 404，说明会话已经失效，Client 应该重新初始化。

如果 Server 支持 SSE 消息恢复，Client 重连时可以用 `Last-Event-ID` 告诉 Server 最后收到的是哪个事件，Server 据此重放漏掉的消息。但这只解决「漏收响应」，解决不了「重复写入」：Client 如果因为没收到结果又发了一次写请求，防重仍然要靠业务侧的幂等处理，具体做法见[Agent 状态与持久化执行](../state/durable-execution.mdx#副作用与幂等恢复)。

## 4. Function Calling 与 API 分工 {#与-function-calling普通-api-的关系}

Function Calling、MCP 和业务 API 不是三选一，一次工具调用里三者经常同时出现，各自处在不同的位置：

| 层次 | 职责 |
| --- | --- |
| Function Calling | 模型表达工具选择与参数 |
| MCP | 应用发现并调用外部能力 |
| 业务 API | 服务执行具体业务操作 |

Function Calling 在模型 API 这一层，应用把工具定义交给模型。MCP 在 Host 和 Server 之间，工具定义由 Server 在运行时提供。业务 API 在服务和调用方之间，用接口文档或 OpenAPI 描述功能和参数。

串起来看一次调用：Host 先从 MCP Server 拿到工具定义，再通过 Function Calling 让模型选择工具、填写参数；然后 Host 通过 MCP 发起调用，Server 在内部调用已有的业务 API 完成操作。MCP 统一的是发现、描述和调用的方式，业务逻辑本身仍由服务实现。

这种统一的价值在于减少 **M×N 集成**。M 个应用分别接入 N 个服务，如果每对都单独适配，要维护的集成代码接近 M×N 份；应用和服务各自实现一次 MCP，就能互相复用，而且工具目录可以在运行时发现和更新。

代价也要算进去。复用的前提是双方的协议版本、能力和内容类型兼容；多了一层 MCP，就多了进程通信或网络往返的开销；接入第三方 Server，还要管理对它的信任。

## 5. 安全风险 {#安全风险}

接入一个 MCP Server，意味着两件事：它的描述和返回结果会进入模型上下文，模型生成的参数会交给它去执行。所以安全检查要同时覆盖「进来的内容」和「出去的访问」，主要有四类风险：

- **工具描述投毒**：恶意 Server 在描述或结果中夹带指令，诱导模型泄露数据或调用其他工具。这些内容会进入上下文，因此要按外部输入处理。
- **动态变更**：审核通过后，Server 又修改了工具定义。可以固定服务版本、记录定义的哈希，也就是用于检测内容变化的摘要值。定义变化时，重新检查访问范围和副作用。
- **过度权限**：本地进程能访问过多目录，或远程令牌允许过多操作，都会扩大错误调用的影响。因此，应按需要限制权限。
- **数据外泄**：模型把一个 Server 返回的敏感数据，放进另一个 Server 的调用参数，就会把数据传给新的接收方。执行前需要检查数据流向。

注入的指令怎样影响模型，见[提示注入](../safety/prompt-injection.mdx)。

鉴权方面，使用 HTTP 授权时，MCP 采用 OAuth 2.1 框架：Client 用访问令牌证明自己获得了哪些权限，Server 作为资源服务器，校验令牌的目标资源、有效期和权限范围。Server 访问下游服务时，要用为下游正确签发的凭据，规范禁止把收到的访问令牌直接透传给下游。

本地服务同样需要防护。本地 HTTP 服务要校验 Origin 请求头确认请求来源，并限制监听地址；stdio 进程按最小权限启动，用沙箱限制文件和网络访问。

无论哪种方式，认证只解决「你是谁」，具体能用哪个工具、访问哪些数据，仍要逐次授权。Host 应只接入审核过的 Server，按工具配置自动允许、需要确认和禁止三档，并记录调用；敏感操作按策略要求用户确认。具体的授权与隔离方法见[工具授权与执行沙箱](../safety/tool-authorization-sandbox.mdx)。

## 6. 面试题 {#面试题}

### 6.1 MCP 是什么？Agent 通过 MCP 调用工具的流程是什么？ {#mcp-flow}



**考察重点**

- 解释 Host、Client 和 Server 分别负责什么。
- 能沿初始化、发现和调用说明消息如何传递，以及使用什么传输方式。

**相关内容**：[角色与能力](#角色与能力)、[交互流程](#交互流程)、[传输方式](#传输方式)。

<details>
<summary>参考回答</summary>

**MCP 是连接 AI 应用与外部工具、数据源的开放协议，通过统一发现和调用方式让多个应用复用服务。**

Host 是 AI 应用，为每个 Server 创建独立 Client。Server 提供工具、资源和提示模板。协议消息使用 JSON-RPC 2.0，2025-11-25 的标准传输是 stdio 与 Streamable HTTP。

Client 用 `initialize` 协商版本和能力，确认兼容后发送 `notifications/initialized`。随后调用 `tools/list` 获取工具名称、描述和输入 Schema，Host 将它们转换成模型工具定义。

模型提出调用后，对应 Client 发出 `tools/call`。Server 执行并返回内容或错误标记，Host 再把结果交给模型。列表支持分页；Server 声明支持列表变化通知后，Client 可在收到通知时重新拉取定义。

</details>

### 6.2 MCP 和普通 API 调用、Function Calling 有什么区别？为什么 Agent 生态广泛采用 MCP？ {#mcp-vs-api}



**考察重点**

- 解释 Function Calling、MCP 和业务 API 各自解决的问题。
- 能说明 M×N 集成成本为何减少，以及兼容性、通信和信任管理的代价。

**相关内容**：[Function Calling 与 API 分工](#与-function-calling普通-api-的关系)。

<details>
<summary>参考回答</summary>

**Function Calling 让模型表达工具请求，MCP 统一应用接入外部能力的方式，业务 API 则提供具体服务接口。**

三者可以配合使用：MCP Server 提供工具定义，Host 交给模型选择并生成参数。Host 再通过 MCP 发起调用，Server 内部调用业务 API 完成操作。普通 API 的功能和参数由接口文档或 OpenAPI 描述，调用方据此编写集成。

M 个应用分别接入 N 个服务时，需要大量逐对适配。使用 MCP 后，应用和服务各自实现共同协议，就能减少重复的集成代码，并在运行时发现工具。这是它被采用的重要原因。

实际复用仍要求版本、能力和内容类型兼容。代价包括进程通信或网络往返，以及第三方 Server 的信任和权限管理。

</details>

### 6.3 Agent 调用 MCP 有哪些风险？MCP Server 应该如何鉴权？ {#mcp-security}



**考察重点**

- 解释工具描述投毒、动态变更、过度权限和数据外泄怎样发生。
- 说明远程 Server 如何校验令牌，以及本地进程为什么仍需隔离。

**相关内容**：[安全风险](#安全风险)、[工具授权与执行沙箱](../safety/tool-authorization-sandbox.mdx)。

<details>
<summary>参考回答</summary>

**MCP 的风险来自不可信内容、工具动态变更、过度权限和数据外泄，HTTP 授权还需要 Server 正确校验访问令牌。**

描述和结果会进入模型上下文，恶意指令可借此影响工具选择。审核后修改工具定义，也会改变原有访问范围。模型若把一个 Server 返回的敏感数据传给另一个 Server，就会发生跨服务外传。因此，Host 要审核服务、记录定义变化，并按工具限制访问与副作用。

采用 HTTP 授权时，Server 按 OAuth 2.1 框架校验令牌的目标资源、有效期和权限范围。访问下游要使用为下游签发的凭据，避免直接透传收到的令牌。认证之后，每次操作仍需检查业务权限。

本地 stdio 进程按最小权限启动，并通过沙箱隔离。Roots 只声明目录范围，实际访问限制由执行环境落实。Host 还应记录调用，按策略对敏感操作要求确认。

</details>

### 6.4 MCP 协议错误、工具执行错误和 HTTP 断线应如何区分？ {#mcp-errors-reconnect}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：能区分协议处理失败、工具业务失败与连接中断，并解释恢复消息与避免重复写入的区别。

**相关内容**：[错误类型与会话恢复](#错误类型与会话恢复)。

<details>
<summary>参考回答</summary>

**协议错误表示请求处理出了问题，工具执行错误表示操作失败，HTTP 断线则只表示传输中断。**

协议错误用 JSON-RPC `error` 返回，例如工具名未知。业务错误在 `tools/call` 结果中用 `isError: true` 表达，Host 可把原因交给模型调整参数。

带会话 ID 的 HTTP 请求收到 404 后，Client 应重新初始化。Server 支持 SSE 恢复时，可以根据 `Last-Event-ID` 重放遗漏消息。断线期间写入是否已经完成，仍要查询业务结果，并用幂等处理防止重复执行。

</details>
