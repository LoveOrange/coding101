# Function Calling

**Function Calling**（工具调用）是让模型按照工具定义，生成一个结构化调用请求的机制。请求里写明要调用哪个工具、参数是什么；模型自己并不执行，自定义工具由应用去执行，再把结果交回模型，模型才能接着回答。

理解这件事的关键是分工：模型只负责「提出请求」，校验、执行和兜底都在应用这一侧。抓住这一点，工具该怎么定义、参数错了怎么办、工具多了怎么选，都能顺着推出来。

## 1. 面试核心 {#core}

- 模型根据工具定义生成调用请求，应用校验并执行，再**按调用 ID 回传结果**，模型据此继续生成。[卡](#call-flow)
- **工具契约**用名称和描述说明用途，用 Schema 约束参数，并定义结果、错误和副作用；这些定义本身就是模型选择工具的依据。[卡](#tool-design)
- 严格 Schema **只约束参数结构**，业务规则和权限仍要程序校验；流式参数要**拼完整之后才能执行**。[卡](#strict-streaming-calls)
- 应用通过参数校验、权限检查、有限重试、幂等处理和重复调用检测，**控制调用失败和重复执行**。[卡](#call-reliability)
- 工具很多时，应用**先路由或检索出少量候选**，再把它们的完整定义交给模型选择。[卡](#many-tools)

## 2. 调用链路 {#调用链路}

一次工具调用由模型和应用轮流完成：模型决定请求什么，应用负责校验和执行，双方靠调用 ID 把请求和结果对上。展开来是五步：

1. 应用在请求里提供工具的名称、描述和参数 Schema。Schema 是一份结构规则，规定每个字段的类型、是否必填等。
2. 模型结合工具描述和对话，判断要不要调用。它可以直接回答，也可以返回一个或多个调用请求，每个请求带着调用 ID、工具名和 JSON 参数。
3. 应用检查工具是否存在，校验参数和权限，再执行对应的函数。
4. 应用把执行结果包装成工具结果，引用原来的调用 ID，放进下一次模型请求。
5. 模型读到结果后，决定继续调用工具，还是给出最终回答。

工具定义写得好不好，直接决定第 2 步模型能不能选对。比如 `get_order` 可以描述为「按订单号查询订单状态和物流信息，用户询问订单进度时使用」，参数 `order_id` 是必填字符串，要求以 `SO` 开头。模型有了这些信息，才有依据决定用不用这个工具、参数该怎么填。

下面的片段是第 4 步在 Anthropic Messages 里的写法。`execute_checked` 负责校验和执行，返回结果字符串和一个错误标记。片段先把模型的原响应原样加回消息列表，再收集这一轮所有的工具结果；完整实现还要处理停止原因和调用预算。

```python
messages.append({"role": "assistant", "content": response.content})
results = []
for block in response.content:
    if block.type == "tool_use":
        content, failed = execute_checked(block.name, block.input)
        results.append({
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": content,
            "is_error": failed,
        })
if results:
    messages.append({"role": "user", "content": results})
```

Messages 用 `tool_use_id` 把每个结果关联到原来的 `tool_use`。结果放在紧跟着的一条用户消息里，以 `tool_result` 块标识；虽然角色是 `user`，块类型已经说明这段内容来自工具。同一轮有多个调用时，结果一起回传，assistant 的原响应也要完整保留，否则下一次请求对不上。

OpenAI 的写法不同：Responses 用 `function_call_output` 和 `call_id`，Chat Completions 用 `role: "tool"` 的工具消息（Tool Message）和 `tool_call_id`。接入哪个 API 就按哪个 API 的字段转换，不要混用。

另外，调用时设置的输出预算（例如 1024 Token）只限制模型这一轮生成多长。工具执行的超时和整个任务的预算，要由应用另外控制。

### 2.1 工具结果与调用关联 {#工具结果与调用关联}

工具结果要单独标识，是为了让模型和应用都清楚「哪个调用返回了什么」。它解决三个问题：

- **请求对应**：一次回复可以有多个调用，完成顺序也不一定和请求顺序一致。调用 ID 让每个结果都能找回自己的请求。
- **来源区分**：工具结果类型说明这是执行反馈，不是用户说的话。但外部网页或接口返回的文本仍然是不可信数据，不能让其中的「指令」改变任务。
- **协议完整性**：接口要求每个调用都有对应结果。比如在 Messages 里，缺少对应的 `tool_result` 会直接报错，所以调用失败了也要回传一个错误结果，而不是什么都不返回。

## 3. 工具契约设计 {#工具契约设计}

**工具契约**是调用双方对用途、输入和输出的约定。模型选工具时读的就是名称、描述和参数说明，所以这些定义其实也是提示词的一部分，写含糊了，模型就会选错或填错。一份完整的契约包括：

| 部分 | 内容 |
| --- | --- |
| 名称 | 明确动作和对象，如 `cancel_order` |
| 描述 | 用途、适用条件与相似工具的区别 |
| 参数 | 类型、必填项、枚举、单位和来源 |
| 结果 | 状态、必要字段、分页或产物引用 |
| 错误 | 错误码、原因和可采取的下一步 |
| 副作用 | 写入范围、幂等条件与授权要求 |

设计时的目标是让模型容易选对、填对，也能读懂结果。可以从四个方面检查：

- **按任务封装**：查询、计算、写入这些确定的事交给程序做。比如 `schedule_meeting` 在内部先查日历再创建会议，模型就不用自己组合两个底层接口。封装之后，读取和写入的授权要求仍要分开说清楚。
- **区分相似工具**：名称用「动作 + 对象」，例如 `search_orders` 和 `cancel_order`；描述里写清适用条件和差别。流程重复、怎么写都难以区分的两个工具，可以考虑合并。
- **减少参数歧义**：固定选项用枚举，也就是列出所有允许的值；参数标明格式、必填项、单位和来源。优先用业务 ID，别让模型去换算单位或猜数据库的自增 ID。用户身份和凭据由程序注入，不交给模型填。
- **返回能看懂的结果**：用名称、状态这些业务字段，代替内部编码。结果太大时分页，或者写到文件里只返回引用；截断时要明说，例如「已截断，共 3200 行，可用 page 参数读取」。模型知道结果不全，才会决定继续读。

错误信息同样是写给模型看的。`INVALID_ORDER_ID: 订单号应以 SO 开头` 指出了哪里错、怎么改，比只返回一个 `500` 容易修正得多。错误码还应该区分两类：可以重试的瞬时故障，和必须改参数或先拿到授权才能继续的问题。

还要注意，格式正确不等于参数有效。订单号以 `SO` 开头，只说明它符合结构规则。如果工具要求这个 ID 必须来自 `search_orders` 的结果，就在描述里写明；程序执行前再核对 ID 是否真的来自前序查询，并检查订单是否存在、属于谁、当前是什么状态。

## 4. 可靠性保障 {#可靠性保障}

模型生成了一个合法的请求，不代表这个操作有效、也不代表允许执行。可靠性检查要覆盖从生成到结果回传的整个过程：

| 阶段 | 检查与处理 |
| --- | --- |
| 生成 | 用 Schema 和枚举表达可选值 |
| 执行前 | 校验类型、业务条件、身份与访问范围 |
| 执行中 | 超时、并发限制与有界重试 |
| 执行后 | 结构化错误、结果裁剪与日志脱敏 |
| 循环中 | 检测重复失败，执行总预算 |

执行前的校验分三层，各自拦不同的问题。Schema 校验看类型、必填项和枚举值；业务校验看 ID 是否存在、金额是否超限、时间是否在允许范围内；授权检查根据当前用户和操作风险，判断能不能访问这份数据、能不能执行这次写入。只做第一层，模型填一个格式正确但属于别人的订单号，就能直接被执行。

出错之后，处理方式要按原因分开：

- 参数错误：返回缺了哪个字段、哪个值非法，以及怎么改，让模型修正后再调用。
- 权限不足：保留拒绝状态，不要让模型换个参数绕过去。需要额外确认的操作，等拿到授权再执行。
- 限流或瞬时故障：可以退避重试，也就是等一段时间再试。重试要同时受次数和总截止时间限制，否则任务会一直卡住。

写入工具还要防重复执行。**幂等键**用来标识同一次业务操作，重复请求带着同一个键过来时，直接复用已有结果。写入超时尤其要小心：请求可能已经成功，只是响应没回来，所以要先确认操作有没有完成，再决定是否重试。具体的恢复方法见[Agent 状态与持久化执行](../state/durable-execution.mdx#副作用与幂等恢复)，授权和敏感信息的传递见[工具授权与执行沙箱](../safety/tool-authorization-sandbox.mdx)。

循环层面，应用要记录工具名、参数和执行结果（日志里的敏感信息要脱敏）。同一个调用反复出现、连续失败达到阈值时，就停止循环，返回已有的部分结果或转人工处理。某个工具持续故障时，还可以触发熔断，暂时不再向它发请求。

模型请求一个不存在的工具，或者编造参数值，这种情况通常叫「工具幻觉」。只提供当前任务需要的工具，可以缩小模型出错的范围；但真正能拦住它的，是执行前检查工具名是否在可用列表里、ID 是否来自前序查询。

### 4.1 严格模式与流式参数 {#严格模式与流式参数}

严格模式用来减少参数格式错误。在 OpenAI 接口里，设置 `strict: true` 后，生成的参数会遵守它所支持的 Schema。

开启时，每个对象都要设置 `additionalProperties: false`，表示不允许额外字段；所有属性都要列进 `required`，确实可选的字段改成允许 `null`。它保证的只是结构：订单是否存在、额度够不够、用户有没有权限，仍然要程序检查。接口返回拒绝或输出没有完成时，也要按对应的状态分别处理。

流式返回会带来另一个问题：参数是一段一段到的。应用要按调用 ID 或事件索引把片段累积起来，收到参数结束事件后，再解析完整的 JSON 并校验。中途的片段里，目标和数值都可能还没写完，比如金额 `10` 后面可能还跟着 `00`，所以片段只能用来展示进度，执行必须等完整请求到齐。

### 4.2 并行调用与依赖 {#并行调用与依赖}

模型可以在同一轮生成多个调用，这能减少往返次数，但执行顺序仍取决于调用之间的依赖。互不依赖的只读查询可以并行执行；后一步要用到前一步返回的 ID 时，就得分阶段执行。

OpenAI 的 `parallel_tool_calls=false` 会把每轮的函数调用限制为零个或一个，使用前要确认所用模型支持。它只限制每轮的调用数量，业务校验和整个循环的预算仍由应用负责。

## 5. 大量工具的选择 {#大量工具的选择}

工具不多、描述容易区分时，直接把完整定义都交给模型就行，十个左右的工具可以从这种方式开始评测。数量一多，问题就出来了：定义占用的上下文越来越多，相似的工具也越来越容易选错。

工具达到几十个以上时，可以评估下面几种**缩小候选范围**的做法：

- **分层路由**：先根据用户意图确定业务领域，只加载这个领域的工具。
- **工具检索**：给工具描述建关键词索引或向量索引，也可以两者组合。每次请求取相关性最高的 Top-K 个候选（只取排名最靠前的 K 项），再加载它们的完整定义。
- **按需发现**：提供一个「搜索工具」的接口，模型需要某项能力时自己去查、再加载。
- **合并固定流程**：经常一起调用的固定步骤，封装成一个高层工具，减少候选数量。需要模型按规则判断的流程，可以用 [Agent Skills](./agent-skills.mdx) 组织。

这些做法有没有效果，要靠评测来判断。建一个「请求—正确工具」的评测集，分两步看：**候选召回率**检查正确工具有没有进入候选，**最终选择准确率**检查模型最后有没有选中它。只选一个工具的场景，可以统计 Top-1 命中率，也就是首选是否正确。之后每次新增工具或修改描述，都用相近意图和不该用工具的请求一起回归。

选对工具之后，返回结果的大小也要控制。冗余数据占满上下文窗口，会影响模型后续的判断和回答。

## 6. 面试题 {#面试题}

### 6.1 Function Calling 的完整调用链路是什么？为什么工具结果需要单独的 Tool Message？ {#call-flow}



**考察重点**

- 解释模型提出调用、应用校验和执行的分工。
- 说明调用 ID 如何对应结果，以及工具结果类型为何要区分来源。

**相关内容**：[调用链路](#调用链路)、[工具结果与调用关联](#工具结果与调用关联)。

<details>
<summary>参考回答</summary>

**应用提供工具定义，模型提出调用，应用校验并执行，再按调用 ID 回传结果，模型据此继续生成。**

工具定义包含名称、描述和参数 JSON Schema。模型根据任务选择工具，给出工具名和参数；它本身不执行。应用检查参数、业务条件和权限后执行，把结果加入下一次请求，模型再决定继续调用还是回答。

工具结果单独标识，解决三个问题：

- 一次有多个调用时，靠 ID 把结果和请求逐一对上，不依赖完成顺序。
- 类型说明内容来自工具而不是用户，但外部内容本身仍按不可信数据处理。
- 接口要求每个调用都有结果，所以失败的调用也要回传错误，否则下一次请求会因消息缺失而报错。

Anthropic Messages 用 `tool_result` 和 `tool_use_id` 回传，OpenAI Responses 用 `function_call_output` 和 `call_id`。封装不同，接入时按所用 API 的字段来。

</details>

### 6.2 如何保障工具调用的可靠性？模型传入错误或危险参数怎么办？ {#call-reliability}



**考察重点**

- 解释 Schema 校验、业务校验和权限检查各自拦截什么问题。
- 说明错误回传、重试、幂等和重复调用检测怎样配合。

**相关内容**：[可靠性保障](#可靠性保障)、[工具契约设计](#工具契约设计)。

<details>
<summary>参考回答</summary>

**可靠性由应用侧的参数校验、权限检查和执行控制保障；校验不通过的请求返回错误，不执行。**

执行前做三层校验：

- Schema 检查类型、必填项和枚举值。
- 业务校验检查 ID、金额和时间范围。
- 授权检查判断当前用户能否执行这个操作。

工具要求 ID 来自前序查询时，程序还要核对来源，防止模型编造参数。

出错后按原因处理：参数错误返回原因和修正建议，让模型调整；权限不足保留拒绝状态，需要确认的操作等授权后再执行；限流和瞬时故障做有限的退避重试，持续故障通过熔断暂停调用。写入用幂等键防重复，超时后先核对操作结果再决定是否重试。

循环层面，记录工具名、参数和结果，检测相同调用是否重复、失败是否连续。达到阈值或总预算后停止循环，返回部分结果或转人工。

</details>

### 6.3 Tool 的设计原则是什么？如何设计参数 Schema 和错误码？ {#tool-design}



**考察重点**

- 说明怎样按任务封装工具，并设计名称、参数和返回字段。
- 能写出帮助模型修正的错误信息，并解释副作用声明与实际授权的关系。

**相关内容**：[工具契约设计](#工具契约设计)。

<details>
<summary>参考回答</summary>

**Tool 按用户任务封装查询、计算或写入能力，用清晰的契约说明用途、参数、结果和错误，因为模型就是靠这些定义来选择和填参的。**

名称用动作加对象，描述写清适用条件和与相似工具的区别。参数 Schema 标注类型、必填项、枚举和格式，字段说明给出单位和来源。优先用业务 ID，用户身份和凭据由程序提供，减少模型猜值。

结果只保留必要的业务字段，大结果分页或返回文件引用，截断时明确说明。错误码附上原因和修正建议，例如 `INVALID_ORDER_ID: 订单号应以 SO 开头`，并区分可重试的瞬时故障、需要修正的参数错误和需要授权的权限问题。

固定步骤可以合进一个工具，例如安排会议时在内部完成日历查询和创建。工具还要声明写入范围、幂等条件和确认要求，但声明只是说明，实际权限由程序在执行时检查。

</details>

### 6.4 工具扩展到几百上千个时，如何保证模型选中正确的工具？ {#many-tools}



**考察重点**

- 解释工具定义增加后，上下文开销与误选机会为何增长。
- 能区分候选召回率与最终选择准确率，并用评测检查路由和检索。

**相关内容**：[大量工具的选择](#大量工具的选择)。

<details>
<summary>参考回答</summary>

**先按领域路由或检索出少量候选，只加载它们的完整定义，再用评测检查是否选对。**

工具只有十个左右时，可以先全部放进上下文。数量增多后，定义会占满上下文，相似工具也更容易误选。这时可以用意图分类缩小领域，或对工具描述做关键词和向量检索，取 Top-K 个候选；也可以让模型通过工具搜索接口按需发现。固定的多步调用封装成高层工具，需要按规则判断的流程用 Skill 组织。

评测集记录每个请求应该用哪个工具。候选召回率看正确工具有没有被找回，最终选择准确率看模型有没有选中它，单工具场景可统计 Top-1 命中率。新增工具或修改描述后，用相近意图和不适用的请求回归，同时限制返回数据的大小。

</details>

### 6.5 strict 模式能保证工具调用安全吗，流式参数何时可以执行？ {#strict-streaming-calls}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->


**考察重点**：解释严格模式能约束什么，以及流式参数为何必须完整后再校验执行。

**相关内容**：[严格模式与流式参数](#严格模式与流式参数)。

<details>
<summary>参考回答</summary>

**不能。strict 模式只约束参数结构，安全仍靠业务校验和授权；流式参数要等完整请求到齐并通过校验后才能执行。**

`strict: true` 让参数遵守接口支持的 Schema，但订单是否存在、额度是否足够、用户有没有权限，都要程序检查。收到拒绝或未完成状态时，也要分别处理。

流式参数按调用 ID 或事件索引累积，收到结束事件后再解析完整 JSON。片段还没到齐时，目标或数值可能被后续内容补全，提前执行等于把一个未完成的参数当成了最终请求。

</details>
