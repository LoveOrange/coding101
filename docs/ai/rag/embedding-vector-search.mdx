# Embedding 与向量检索

**Embedding** 是把文本映射成固定维度的向量，也就是一组表示文本含义的数值；**向量检索**是找出与查询向量最相近的若干个文档块，作为 RAG 的候选证据。

这条链路上有几个容易讲混的地方：两段文本为什么「相近」，三种相似度度量什么时候等价，HNSW 这类近似索引为什么快、又会漏掉什么，以及加了权限过滤以后为什么会凑不够 K 条结果。把它们讲清楚，选模型、调索引参数和排查召回问题时才有依据。

## 1. 面试核心 {#core}

- 向量检索把查询和文档编码到**兼容的向量空间**，再按相似度选出**排名前 K 的文档块**。[卡](#vector-search)
- 查询和文档向量都**归一化为单位长度**时，余弦相似度、内积和欧氏距离给出的**排序相同**。[卡](#vector-search)
- HNSW 先用**上层稀疏图快速接近目标区域**，再在底层扩展候选，是**用少量召回损失换检索速度**。[卡](#hnsw)
- HNSW 的 `M` 控制**连接规模**，`efConstruction` 控制**建图时的搜索范围**，`efSearch` 控制**查询时的搜索范围**。[卡](#hnsw)
- ANN 只返回有限候选，过滤掉太多时**结果会少于 K 条**；扩大搜索范围或继续扫描能增加找到合格候选的机会。[卡](#filtered-ann)

## 2. Embedding {#embedding}

Embedding 模型把长短不一的文本转成同样维度的向量，检索器才能拿它们互相比较。用于文本检索的模型通常以 Transformer 编码器为基础，输出几百到几千维的向量。训练时，模型被要求让相关文本的向量靠近、无关文本的向量远离；相关文本对可以是问题和答案，也可以是两个同义句。

查询和文档要按同一个检索模型规定的方式编码。两个编码器可以共享权重，也可以分别训练，关键是输出落在同一个可比较的空间里。**非对称检索**是指查询和文档的形式或用途不同，比如用一个短问题去匹配一篇长文档。这类模型可能要求查询和文档加不同的前缀，让模型知道当前输入是哪一种。

选模型和入库时，要检查**语言、输入长度与版本兼容性**：

- **语言与领域**：中文问题要在中文文档上评测，专业场景要覆盖领域术语。测试集应包含缩写、罕见实体和相近概念。模型对领域理解不足时，可以用领域数据微调，再比较检索收益。
- **输入长度**：每个模型都有输入上限，超限时接口会报错或按配置截断。过长的块要在入库前处理，否则后半段根本没参与向量计算。
- **模型与预处理版本**：索引元数据要记录模型版本和文本处理规则。更换模型或改了不兼容的维度配置，就要重新生成全部文档向量。新旧向量即使维度相同，也不一定在同一个空间里，混在一起比较没有意义。

还要记住，向量相似度反映的是模型学到的关系，不等于「适用于当前问题」。比如同一种故障的几篇文档会很相近，但只有一篇对应当前产品。所以选模型仍要用实际业务问题来评测。

向量检索对精确编号和罕见专有名词容易匹配错，这类候选可以用关键词检索补充，具体方法见[混合检索与重排序](./hybrid-search-rerank.mdx)。

## 3. 相似度度量 {#相似度度量}

有了向量，还需要一个数值表示两个向量有多接近。常用的有三种：**余弦相似度**只看方向，**内积**同时受方向和长度影响，**欧氏距离**是两点之间的直线距离。

| 度量 | 定义 | 排序方向 |
| --- | --- | --- |
| 余弦相似度 | `a·b / (‖a‖‖b‖)` | 越大越相近。 |
| 内积 | `a·b` | 越大越相近。 |
| 欧氏距离 | `‖a − b‖` | 越小越相近。 |

表中的 `a·b` 是对应维度相乘再求和，`‖a‖` 是向量 a 的长度。余弦相似度除掉了两个长度，所以只剩方向的比较。

**归一化**是把非零向量除以它自身的长度，让长度变成 1。查询和文档都归一化之后，余弦相似度就等于内积，而且有 `‖a − b‖² = 2 − 2(a·b)`：内积越大，欧氏距离越小。三种度量于是给出相同的排序。实际中可以在写入时归一化文档向量，查询时也先归一化，再用内积比较，省去每次计算长度。

度量要和模型的训练目标、索引配置一致。如果模型本身靠向量长度表达相关性，强行归一化会改变检索结果。另外，很多服务会把原始距离转换成对外的分数，应用要核对返回值的定义和排序方向，别把「越小越近」当成「越大越近」。

## 4. 近似最近邻与 HNSW {#近似最近邻与-hnsw}

精确搜索要拿查询和全部 N 个 d 维向量逐一比较，工作量是 O(Nd)，向量越多，每次查询越慢。**近似最近邻**（ANN）借助索引减少比较次数，代价是可能漏掉一部分真正最近的向量。

数据到百万级以上时可以评估 ANN，但用不用还要看并发和延迟要求。精确搜索适合当基线：用它得到的真实最近邻，来衡量 ANN 漏掉了多少。

**HNSW**（Hierarchical Navigable Small World，分层可导航小世界图）是一种常用的 ANN 索引。它把每个向量当成一个节点，和若干相近节点相连。节点按概率进入更高的层：底层包含全部节点，越往上节点越少，每条连接跨过的距离也越大，有点像地图从省级道路到街道的分层。

查询通过**三步搜索**逐渐缩小范围：

1. 从最高层的入口节点出发，比较各邻居和查询的距离，移动到更近的邻居。
2. 当前层找不到更近的邻居时，下降一层，从刚才的位置继续。
3. 到达底层后，维护一个候选列表并不断扩展邻居，最后返回候选里最相近的 K 个，也就是 Top-K。

上层负责快速接近目标区域，底层负责细致搜索。候选列表越大，越有机会找回被短路径错过的近邻，但距离计算也越多。这正是 HNSW 三个参数调节的东西：

| 参数 | 作用 | 增大的主要代价 |
| --- | --- | --- |
| `M` | 控制图的连接规模 | 更多内存与构建工作。 |
| `efConstruction` | 控制建图时搜索候选数量 | 构建耗时增加。 |
| `efSearch` | 控制查询搜索范围 | 查询计算增加。 |

`M` 增大，每个节点连接更多，搜索能走的路径更多。`efConstruction` 增大，建图时比较更多候选，能选出更合适的邻居。`efSearch` 是查询时的搜索范围，可以按召回和延迟要求随时调整。参数增大的收益和数据分布有关，到一定程度会趋于饱和，所以要实测。

HNSW 的查询时间没有普适的对数级保证。图怎样存储、删除节点后怎样维护连接，也取决于具体数据库的实现。标记删除与空间回收的区别见[检索增强生成（RAG）](./rag.mdx#版本发布与删除)。

另外两种常见方法是 IVF 和 PQ。**IVF**（倒排文件索引）先把向量划分成簇，查询时只搜离查询较近的几个簇。**PQ**（乘积量化）用压缩表示减少向量占用的空间，代价是引入量化误差。两者可以组合，在大规模数据上同时减少搜索量和存储量。

## 5. 向量数据库 {#向量数据库}

实际系统除了搜索向量，还要保存原文、处理更新、按业务条件过滤。所以选型既要看索引搜索能力，也要看这些需求怎样和现有系统配合。

| 方案 | 示例 | 重点检查 |
| --- | --- | --- |
| 专用向量数据库 | Milvus、Qdrant、Weaviate | 分布式、过滤和索引维护。 |
| 关系数据库扩展 | PostgreSQL + pgvector | 事务、业务条件与执行计划。 |
| 搜索引擎 | Elasticsearch、OpenSearch | 全文与向量的联合检索。 |
| 向量搜索库 | FAISS | 单机索引与应用自行管理数据。 |

可以从现有需求出发，缩小这**四类方案**的范围：

- 需要分布式管理大规模向量时，评估专用向量数据库及其索引和过滤能力。
- 向量要和业务表一起查询、更新或参与事务时，评估 PostgreSQL + pgvector。
- 已经有全文搜索，又需要关键词和向量混合检索时，评估 Elasticsearch 或 OpenSearch。
- 单机原型或离线批处理可以用 FAISS，但原文存储、权限和数据服务要由应用自己补齐。

这些条件只能帮你缩小范围，最后还要用真实数据和并发压测。比较时关注召回率、P95 等尾延迟、更新成本和资源占用；P95 延迟是指 95% 的请求能在这个时间内完成。团队已有的技术栈和运维能力，也会影响实施成本。

### 5.1 过滤检索与候选不足 {#过滤检索与候选不足}

权限、租户或版本过滤会缩小真正可用的候选范围。过滤可以在搜索前、搜索中或拿到候选后执行，具体怎么做由检索引擎决定。

问题出在「拿到候选后再过滤」这种情况。ANN 只产生有限数量的候选，如果其中大部分被过滤掉，剩下的就不足 K 条。数据库里明明还有合格文档，但它们不在这批候选里，要继续搜索才能找到。过滤前置也有自己的问题：在图上直接排除节点，会改变搜索能走的路径。所以不同引擎的过滤效果要分别测试。

以 pgvector 为例，它从 0.8.0 起支持**迭代索引扫描**，即候选不足时继续扫描。设置 `hnsw.iterative_scan = strict_order` 后，扫描会持续到结果足够或达到扫描上限；`hnsw.ef_search` 则可以扩大初始搜索范围。两者都能增加候选，代价是更多查询计算。

如果过滤后只剩很少记录，可以先用业务索引定位这些记录，再对它们做精确相似度排序。也可以按租户分区，或者为固定的过滤条件建部分索引。具体选哪种，要结合执行计划比较召回和延迟。

无论怎样扩大搜索，授权过滤都必须在文档片段交给生成模型之前生效。扩大范围只是多找一些待选记录，原有的授权条件一条也不能少。

## 6. 面试题 {#面试题}

### 6.1 讲一下向量检索的原理。常用的相似度计算方法有哪些？ {#vector-search}

**考察重点**：解释文本如何进入兼容的向量空间，并说明三种度量的关系和近似搜索的取舍。

**相关内容**：[Embedding](#embedding)、[相似度度量](#相似度度量)。

<details>
<summary>参考回答</summary>

**向量检索将查询和文档映射到兼容的向量空间，再按相似度取排名前 K 的文档块。**

模型训练让相关文本对的向量接近，让无关文本的向量远离。查询和文档遵循各自的编码规则，例如使用模型要求的不同前缀。编码器可以共享权重，也可以配对训练，关键是输出空间兼容。

常用度量包括余弦相似度、内积和欧氏距离。余弦只比较方向，内积还受向量长度影响，欧氏距离越小表示越接近。双方归一化为单位向量后，三者排序一致，但度量仍要匹配模型训练目标。大规模检索可以用 HNSW、IVF 等 ANN 索引减少比较次数，再用精确搜索衡量召回损失。

</details>

### 6.2 HNSW 索引的原理是什么？关键参数如何影响效果？ {#hnsw}

**考察重点**：解释 HNSW 如何逐层接近目标，以及三个参数怎样影响召回、内存和计算量。

**相关内容**：[近似最近邻与 HNSW](#近似最近邻与-hnsw)。

<details>
<summary>参考回答</summary>

**HNSW 用分层近邻图逐步接近查询目标，三个参数分别控制连接规模、建图搜索和查询搜索。**

每个节点与相近节点相连，并按概率进入更高层。底层包含全部节点，上层更稀疏。查询从高层入口开始，移动到更近的邻居，找到当前层局部最近的位置后下降一层。到底层再维护候选列表，扩展搜索并选出 Top-K。

`M` 越大，图中连接越多，内存和构建成本也越高。`efConstruction` 越大，建图时比较的候选越多，有助于改善图质量。`efSearch` 越大，查询覆盖的范围越广，同时也更慢。具体收益需要在目标数据上验证，存储与删除策略则由数据库实现决定。

</details>

### 6.3 常见的向量数据库有哪些？如何选型？ {#vector-database}

**考察重点**：根据数据规模、业务过滤和混合检索需求比较方案，并说明需要怎样验证性能与运维成本。

**相关内容**：[向量数据库](#向量数据库)。

<details>
<summary>参考回答</summary>

**常见方案有专用向量数据库、关系库扩展、搜索引擎和向量搜索库，选择要结合业务查询与运维需求。**

Milvus、Qdrant、Weaviate 可用于评估分布式向量管理。PostgreSQL + pgvector 便于结合业务表过滤和事务。Elasticsearch、OpenSearch 适合评估全文与向量的联合检索。FAISS 可用于单机原型或离线计算，应用还要补齐数据服务。

最终要用真实数据、并发以及权限和版本条件压测。除了召回和 P95 延迟，还要比较更新成本、资源占用与团队维护这些系统的成本。

</details>

### 6.4 向量库有足够数据，过滤后为何不足 K 条？ {#filtered-ann}

<!-- 本题为本站原理自测，尚未核验对应公司面经，不作公司归属。 -->

**考察重点**：解释有限候选为何在过滤后不足 K 条，并比较迭代扫描、扩大搜索范围和先过滤后精确排序。

**相关内容**：[过滤检索与候选不足](#过滤检索与候选不足)。

<details>
<summary>参考回答</summary>

**ANN 只搜索了有限候选，过滤又淘汰其中一部分，所以有足够数据也会返回不足 K 条。**

以 pgvector 为例，从 0.8.0 起可设置 `hnsw.iterative_scan = strict_order` 继续扫描候选。扫描仍受上限约束，也可调大 `hnsw.ef_search` 扩大初始范围。若过滤后只剩少量记录，可先按业务条件定位，再精确排序；按租户分区也是可比较的方案。

调整后要同时观察召回与延迟，并保留权限过滤，确保增加的候选也在用户授权范围内。

</details>
